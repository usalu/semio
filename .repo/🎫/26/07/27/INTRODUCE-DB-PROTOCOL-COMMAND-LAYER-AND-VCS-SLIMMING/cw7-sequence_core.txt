======================================================================================

Scope: migrate CollectionOperation::Add/Move construction+pattern-matches and the
vcs::apply_collection_operation/invert_collection_operation/collection_diff_from_operation
call sites onto protocol::CollectionOperation's frozen shape (Add gains mandatory `id`,
`index`->`at`; Move `to_index`->`to`). Only file touched: sequence/core/rs/lib.rs.
Cargo.toml untouched — `protocol` was already a direct dependency (from an earlier wave's
mechanical sweep), no change needed.

Real usage confirmed (not a false positive): sequence_core has a live `DocumentVcs` region
(`🔖DocumentVcs`) implementing typed step/edge collection ops for `SequenceFixture` via
`vcs`'s generic `CollectionOperation<TId, TItem, TPatch>` helpers.

What changed
------------
1. Import switch (was `use vcs::{collection_diff_from_operation, invert_collection_operation,
   CollectionDiff, CollectionOperation, Identified, Operation, OperationDiff, Patchable};`):
   now `use protocol::{...same names...};` — all eight symbols moved to `protocol` (verified
   they're re-exported at the `protocol/rs/lib.rs` facade, not just `protocol_command`).

2. `CollectionOperation::Add` construction sites (4, inside `Operation::diff` and
   `Operation::backwards` for `StepsAdd`/`EdgesAdd`): rewritten from
   `CollectionOperation::Add { index: *index, item: item.clone() }` to
   `CollectionOperation::Add { id: item.id.clone(), item: item.clone(), at: *index }`.
   Id source: `item.id` — `SequenceStep`/`SequenceEdge` already carry a plain `pub id: String`
   field (the same field `Identified<String>::id()` returns for `Remove`/`Move`/`Patch` on
   this same collection), so the id is already present on the item being added; no new id
   generation logic needed, no counter/ULID involved for this crate's Add path.

3. `CollectionOperation::Move` construction sites (4, same two match blocks):
   `to_index: *to_index` -> `to: *to_index` (pure rename, per the frozen shape).

4. Pattern-match sites (`steps_operation_from_collection`, `edges_operation_from_collection`,
   which convert an inverted `CollectionOperation` back into this crate's own flat
   `SequenceOperation` enum):
   `CollectionOperation::Add { index, item }` -> `CollectionOperation::Add { id: _id, item, at }`
   (bound `id` but prefixed `_id` since this crate's own `SequenceOperation::StepsAdd`/
   `EdgesAdd` variants don't carry a separate `id` field — the id is already inside
   `item.id` — so the freshly-supplied `id` from the inverted op carries no additional
   information this match arm needs; verified `item.id` is always equal to it since
   `invert_collection_operation`'s `Remove` case sets `Add`'s `id` from `items[index].id()`).
   `CollectionOperation::Move { id, to_index }` -> `CollectionOperation::Move { id, to }`
   with `to_index: to` on the RHS construction (pure rename carried through).

5. `Identified<String> for SequenceStep`/`SequenceEdge`: signature unchanged
   (`fn id(&self) -> &TId`), now implements `protocol::Identified` instead of `vcs::Identified`
   (identical trait shape, pure re-anchoring via the import switch — no body change).

6. `Patchable<SequenceStepPatch> for SequenceStep` and `Patchable<SequenceEdgePatch> for
   SequenceEdge`: NOT a pure rename — `protocol::Patchable` splits `vcs::Patchable`'s single
   `apply_patch(&mut self, &TPatch) -> TPatch` (mutate-and-return-inverse) into two methods:
   `apply_patch(&mut self, &TPatch)` (mutate only, no return) and
   `diff_patch(&self, other: &Self) -> Option<TPatch>` (compute the patch that would turn
   `self` into `other`). This divergence is NOT called out as a distinct step in the CW7
   instructions doc (which frames step 6 as swapping `Identified`/`Patchable` import paths
   alongside `CollectionOperation`), but it is load-bearing: `protocol::invert_collection_operation`
   and `protocol::collection_diff_from_operation`'s own generic bounds require
   `TItem: Identified<TId> + Clone + Patchable<TPatch>` resolved against protocol's own
   trait definitions (not vcs's) once those two functions are called as `protocol::`, so
   keeping the old vcs-shaped single-method impl would not satisfy the new bound — this had
   to be split, not just re-pathed. Rewrote both impls:
     - `apply_patch`: same field-by-field `if let Some(x) = patch.x { self.x = x; }` mutation
       logic as before, minus the `inverse` capture/return.
     - `diff_patch`: field-by-field compare (`self.field != other.field`), producing
       `Some(other.field)` per differing field, `None` overall if nothing differs (matches
       `SequenceStepPatch`/`SequenceEdgePatch`'s `Default`+`PartialEq` derives already present
       on both patch structs). Verified this reproduces the exact same inverse-patch value the
       old code computed: `protocol::invert_collection_operation`'s `Patch` arm computes
       `after = prior.clone(); after.apply_patch(patch); after.diff_patch(&prior)` — since
       `apply_patch` only ever touches fields where the incoming patch is `Some`, all
       untouched fields stay equal between `after` and `prior`, so `diff_patch` flags exactly
       the touched fields, capturing `prior`'s old values — identical semantics to the old
       single-method `apply_patch` that captured `self`'s pre-mutation field values keyed by
       the incoming patch's `Some`-ness.
   Local generic helper `apply_collection_diff` (which calls `item.apply_patch(&patch.patch)`
   and already discarded the return value) needed no code change — its generic bound
   `TItem: Identified<TId> + Clone + Patchable<TPatch>` is spelled unqualified and now
   resolves through the switched `use protocol::{...}` import automatically.

7. `Operation`/`OperationDiff`/`OpText` trio (step 7 of the instructions): `vcs::Operation`,
   `vcs::OperationDiff`, `vcs::OpText` are literal re-exports of `protocol::{Operation,
   OperationDiff, OpText}` per vcs/rs/lib.rs's "TEMPORARY protocol shim" region (confirmed by
   reading it — `pub use protocol::{merge_concurrent_diffs, Edit, Operation, OperationDiff,
   OperationMeta, OpText, ReconcileReport, ReconcileSeverity};`), so this was a zero-behavior
   import-path cleanup, not a functional change:
     - `impl OperationDiff<SequenceFixture> for SequenceDiff` and
       `impl Operation<SequenceFixture> for SequenceOperation` already resolve to
       `protocol::{Operation, OperationDiff}` automatically once the top-of-region `use`
       switched (both names were already imported unqualified from that same `use` block).
     - `impl vcs::OpText for SequenceOperation` -> `impl protocol::OpText for SequenceOperation`,
       and its two internal `<SequenceOperationDsl as vcs::OpText>::...` calls ->
       `<SequenceOperationDsl as protocol::OpText>::...` (confirmed `SequenceOperationDsl`'s
       `dsl::DslOps`-derived impl already targets `::protocol::OpText` directly in the derive
       macro's generated code, so this just names the trait via its canonical path instead of
       vcs's shim alias). Left `vcs::TextError`/`vcs::TextSpan` untouched inside that impl per
       the instructions' "only for the Operation/OperationDiff/OpText trio, do not touch
       anything else" — `vcs::TextError` is itself a `pub use dsl_core::TextError` re-export,
       so it's the exact same concrete type protocol::OpText's signature expects; no behavior
       change either way.

8. Doc comments referencing `vcs::CollectionOperation`/`vcs::invert_collection_operation`/
   `vcs::OpText` near the `SequenceOperation` enum and `steps_operation_from_collection`
   updated to say `protocol::` for accuracy (docstring text only, no code-affecting change).
