CW7 — "preview law for gesture apps" (draw, lowpoly, layout, cad, puzzle)
==========================================================================
Scope per instructions: touch only the 5 named app plugin crates' own files. No vcs/, framework/plugin/,
framework/sync/, WIT, or os/core edits, even though the investigation below shows the real fix eventually
needs some of those.

ARCHITECTURAL FINDING (read this before the per-app sections — it governs all five)
-------------------------------------------------------------------------------------
`SyncSession::publish_preview` / `DocumentEvent::Preview` (framework/sync/rs/lib.rs) is HOST-ONLY. The
crate's own module doc says it plainly: "WASI-P2 plugins never link this crate — inside the sandbox a
store attaches vcs's pure `PortBackbone` (an in-memory queue relayed to the host). This actor is a
host-side concern only." It uses tokio/std::thread and is not part of any of the 5 apps' dependency graphs.

All 5 app plugin crates (draw-plugin, lowpoly-plugin, layout-plugin, cad-plugin, puzzle-plugin) compile as
WASI-P2 components (`crate-type = ["cdylib", "rlib"]`, `package.metadata.component.package = "semio:*"`)
and depend only on `semio-framework-plugin` / `semio-framework-os` / `vcs` / `protocol` — never
`framework/sync`. Confirmed by grepping every Cargo.toml.

The one channel a plugin CAN reach out through is `vcs::Backbone`/`BackboneMessage`, relayed via the WIT
host-import functions `host_backbone_send`/`host_backbone_poll` (exported from framework/plugin/rs). But
`vcs::BackboneMessage` (vcs/rs/lib.rs) has exactly three variants — `Snapshot`, `Operations`, `Ack` — no
preview-shaped variant exists. Adding one is a `vcs`/WIT/`framework/plugin/host` change, explicitly outside
this ticket's plugin-crate-only file ownership (vcs/rs/lib.rs is a listed "critical file"/serial cut-over
surface for this whole campaign).

Net result: **no app plugin crate can literally call `SyncSession::publish_preview` today**, regardless of
how cleanly its own gesture state is factored. This is not a per-app gap; it is a missing host bridge.
Per this ticket's own escape-hatch clause ("do the best minimal, correct addition you can and clearly
document what's still missing rather than forcing something fragile"), the concrete work below stops one
layer short of a live wire and stages the exact seam instead:

For each app, at the natural point where the app already tracks "gesture is live, not yet committed"
scratch state, I added:
  1. A pure, documented function turning that scratch state into a JSON-serializable preview payload
     (never reading/writing the app's document `Operation`/`Projection` types — only the ephemeral scratch).
  2. A `preview_seq: u64` counter, bumped once per live tick in the app's real gesture handler (the same
     per-`key` monotone counter `DocumentActorMsg::PublishPreview`/`SyncSession::publish_preview` expects,
     for staleness detection on a lossy, uncredited preview lane).
  3. A `fn gesture_preview(&self) -> Option<(&'static str, u64, Vec<u8>)>` accessor whose return shape is
     EXACTLY `SyncSession::publish_preview`'s `(key, seq, payload)` argument list — so wiring it up, once a
     host bridge exists, is a one-line call at whatever host-side relay point eventually reads it out of
     the plugin (today there is no such call site anywhere in the trusted host boundary either; that relay
     is the missing piece, not covered by this ticket).
  4. `#[allow(dead_code)]` on the accessor with a doc comment pointing at this file, since nothing in the
     crate calls it yet (by construction — there is nowhere reachable to call it TO). Exercised only by
     each crate's own `🧪Tests`.

None of the 5 additions touch persistent document state: every payload-building function reads only the
app's own ephemeral/scratch struct (never `Projection`/`Operation`), and every crate has a dedicated
"pure read" test asserting `gesture_preview()` never mutates the scratch state it reads. This mirrors
`db_preview`'s own hard law ("a preview never mutates authoritative state") at the one layer within this
ticket's reach to enforce it.

Grep-first check (as instructed): `publish_preview`/`DocumentEvent::Preview`/`drag_ghost_json`/
`PublishPreview` were searched across all 5 crates before starting — zero hits in any of them. Also
checked lowpoly_core vs a separate plugin crate for lowpoly, per the ticket's hint: lowpoly's
`DocumentApp` impl (`LowpolyPlayApp`) lives in `lowpoly/plugin/rs/lib.rs`, not `lowpoly/core/rs` (the
latter is pure mesh/document-model code with no plugin/gesture concerns) — confirmed the plugin crate is
the right file.

Also confirmed (relevant background, not touched): `PresencePeer::drag_ghost_json` (framework/core/rs)
is a DIFFERENT, older, unrelated mechanism — a presence-broadcast field for node-graph drag ghosts in
`framework/renderer/wgpu`, not connected to `db_preview`/`SyncSession::publish_preview` at all. It predates
CW5 and isn't part of the app plugin layer this ticket scopes.

A second, orthogonal architecture note worth recording: several of these apps ALSO have a live-drag UX
pattern that needs no preview at all — `ActionEmit::amend` (the "per-tick coalesced" pattern documented in
framework/plugin/rs's `🔖UtilityPreviewContract`). Ticks using `amend` (cad's gumball translate/rotate/
scale via `translateSelection`/`rotateSelection`/`scaleSelection`; layout's/cad's camera drags) are REAL,
already-committed (though undo-coalesced) operations that already flow through the normal
`DocumentEvent::RemoteOperations` sync channel every tick — collaborators already see these live, for
free, with no preview lane involved. The preview-law gap only exists for the OTHER blessed pattern,
"scratch + commit" (`ActionEmit::commit`), where the in-progress value lives purely in app-runtime state
and is invisible to collaborators until the whole gesture lands. That's what all 5 additions below target.


1) draw/plugin/rs/lib.rs
------------------------
Found: no existing preview publishing (grep confirmed). Seam: `GestureContext` (the `fsm`-driven gesture
statechart's shared scratch — method/utility/start/cursor/points/active), live during `marqueeing`/
`shape_dragging`/`drafting` states, read/written only by `DrawPlayApp::step_gesture`.

Added (region `🔖GesturePreview`, near `GestureContext`; accessor inside `impl DrawPlayApp`):
  - `draw_gesture_preview_payload(ctx: &GestureContext, is_idle: bool) -> Option<Value>` — `None` while
    `draw_gesture` is `idle` (`self.gesture.matches("idle")`, the exact idiom already used elsewhere in
    this file), else a JSON snapshot of method/utility/start/cursor/points/active.
  - `DrawPlayApp::preview_seq: u64`, bumped once per `step_gesture` call.
  - `DrawPlayApp::gesture_preview() -> Option<("gesture", seq, payload)>`.

Verification: 3 new tests in the existing `mod tests` (region `🔖GesturePreview`), driven directly against
`DrawPlayApp` (bypassing `VcsDocumentApp`, which has no accessor into the wrapped app) via `step_gesture`:
  - `gesture_preview_is_none_while_idle`
  - `gesture_preview_reflects_live_shape_drag_and_clears_on_commit` — pointer-down/move/up through a real
    shape drag; confirms zero operations mid-drag, live cursor tracking, monotone seq, and `None` again
    (with exactly one real committed operation) after pointer-up.
  - `gesture_preview_is_a_pure_read_never_mutating_gesture_context`
`cargo test -p draw-plugin --lib` (ran, not just planned): 3/3 new tests pass; 20/26 pre-existing tests
pass. The 6 pre-existing failures (`invalid catalog icon name` panics in `ui/wgpu`'s generated icon
catalog) are unrelated to this change — confirmed by reading each failing test body (label translation,
catalogue panel rendering, utility registry, bundle-manifest sanity — none touch gesture code) and by
`git status` showing no icon-catalog files modified (a committed, pre-existing baseline break, also
reproduced identically in cad-plugin below, on an unrelated icon asset).


2) lowpoly/plugin/rs/lib.rs
----------------------------
Found: no existing preview publishing. Seam: `TransformSession` (gumball drag scratch: `object_id`,
`before: LowpolyObject`, `doc: LowpolyDocument` — mid-drag ticks mutate `doc`, emit zero operations;
`commit_transform` diffs `before` vs the final `doc` into one real `ObjectsPatch`).

Design note: rather than a bare delta-per-tick (which would desync a receiver if the lossy preview lane
dropped a message), the payload is `object_patch_diff(before, after)` — the SAME base-anchored diff
`commit_transform` already computes for the real commit — read off the live scratch every tick. Anchoring
to the fixed drag-start `before` (not the previous preview tick) means a receiver only ever needs the last
canonical state it already has plus this one patch, never a chain of prior preview messages, so this stays
correct under message loss. `apply_transform` already calls `sync_meshes_to_projection()` every tick
(mid-drag world-scene rendering needs it regardless), so reading `session.doc.projection()` here is not new
per-tick cost.

Added:
  - `LowpolyPlayApp::preview_seq: u64`, bumped once per `transform_selection` tick while a drag is active.
  - `LowpolyPlayApp::gesture_preview()` (region `🔖GesturePreview`, end of the transform `impl` block) →
    `Some(("gesture:transform", seq, json!({objectId, patch: object_patch_diff(before, after)})))`.

Verification: 3 new tests, driven directly against `LowpolyPlayApp` (bypassing `VcsDocumentApp`) via
`transform_selection`/`commit_transform`:
  - `gesture_preview_is_none_without_an_active_transform_drag`
  - `gesture_preview_reflects_the_live_gumball_drag_and_clears_on_commit` — two translate ticks, confirms
    zero operations mid-drag, monotone seq, the patch accumulating BOTH ticks (not just the latest), and
    `None` again after `commit_transform` lands the one real operation.
  - `gesture_preview_is_a_pure_read_never_mutating_the_transform_session`
`cargo test -p lowpoly-plugin --lib`: 23/23 pass (3 new + 20 pre-existing), zero failures.

Scoped out (documented, not implemented): lowpoly also has a second scratch-commit gesture,
`PaintStrokeSession` (freehand paint stroke drag). It follows the identical established pattern and would
take an identical `gesture_preview`-shaped addition; left out to keep this change to one representative
"shape being dragged" gesture per app within the time available. Flagged here for whoever wires the real
host bridge, since the seam is trivial to replicate.


3) layout/plugin/rs/lib.rs
----------------------------
Found: no existing preview publishing. layout's most prominent "amend"-driven drag (camera) already syncs
live for free (see the architecture note above). The genuine scratch-commit gesture here is
`LayoutDropPreviewState` (`runtime.drop_preview: Option<{kind, x, y}>`) — set by `canvasDragOver` while
dragging a new frame in from the catalogue, cleared by `canvasDragLeave`, committed only on drop
(`addFrame`, a separate action). This is the one place layout renders a ghost purely from app-runtime state
before any document mutation (confirmed by the pre-existing test `drag_over_emits_ghost_and_leave_clears`,
which already asserts a `layout.drop-preview` overlay appears/disappears around this exact state).

Note: layout's `patchFrame` action (direct frame x/y/width/height edits) is NOT a scratch-commit gesture —
it has no held-back app-runtime state and no frontend caller was found in the repo (`grep` for
`patchFrame` across all `.ts`/`.tsx` returned nothing), so there was no live "drag an existing frame"
gesture-in-progress state to hook into for that action. Documenting this rather than fabricating one.

Added:
  - `layout_drag_preview_payload(state: &LayoutDropPreviewState) -> Value` (region `🔖GesturePreview`,
    just above `LayoutPlayApp`) — `LayoutDropPreviewState` already derives `Serialize`, so this is a
    direct `serde_json::to_value`.
  - `LayoutPlayApp::preview_seq: u64`, bumped once per `canvasDragOver` tick.
  - `LayoutPlayApp::gesture_preview() -> Option<("gesture:dropPreview", seq, payload)>`.

Verification: 3 new tests, driven through the REAL `DocumentApp::handle_action` trait method directly on a
bare `LayoutPlayApp` (a hand-built `DocumentView`/empty `HistoryView`, following the exact
"hand-built test fixture `HistoryView`" idiom already documented on `HistoryView` itself and used
elsewhere in the workspace, e.g. fem/plugin/rs), since `VcsDocumentApp` has no accessor into the wrapped
app:
  - `gesture_preview_is_none_without_a_live_drag_over`
  - `gesture_preview_reflects_the_live_drag_over_and_clears_on_leave` — two `canvasDragOver` ticks at
    different positions, confirms zero operations, monotone seq, live position tracking, and `None` again
    after `canvasDragLeave`.
  - `gesture_preview_is_a_pure_read_never_mutating_the_drop_preview_state`
`cargo test -p layout-plugin --lib`: 42/42 pass (3 new + 39 pre-existing), zero failures.


4) cad/plugin/rs/lib.rs
-------------------------
Found: no existing preview publishing. cad's gumball transform (`translateSelection`/`rotateSelection`/
`scaleSelection`) uses the `amend` pattern (real, already-synced per-tick operations — see the
architecture note above), so it needs no preview lane. The genuine scratch-commit gesture is the
interaction-catalog engagement session, `CadPlayRuntime.engagement_session: Option<CadEngagementSession>`
(`interaction_id`, `state`, `context: HashMap<String, Value>`, `pane`) — a multi-step guided modeling flow
(e.g. click two corners to place a box) with live rubber-band feedback. `worldPointerMove`'s own existing
doc comment names exactly this: "Live rubber-band preview during an active engagement session: applies
pointer.move ... without ever committing an object or touching VCS history."

Added:
  - `CadPlayApp::preview_seq: u64`.
  - `CadPlayApp::gesture_preview()` (new region `🔖GesturePreview`, small `impl CadPlayApp` block ahead of
    `impl DocumentApp for CadPlayApp`, since none existed before) → `Some(("gesture:engagement", seq,
    payload))` where payload is the whole `CadEngagementSession` (already `Serialize`) serialized verbatim.
  - `preview_seq` bump added to the existing `worldPointerMove` handler, right where it already calls
    `apply_event(session, "pointer.move", point)`.

Verification: 3 new tests, added directly after the pre-existing
`world_pointer_move_updates_live_preview_without_committing_or_emitting_operations` test, reusing this
crate's own established `drive(&mut app, &scene, action, args)` test helper (which already builds a bare
`CadPlayApp` + `DocumentView` + `empty_history()` — no wrapper needed here, unlike the other 4 apps):
  - `gesture_preview_is_none_without_a_live_engagement_session`
  - `gesture_preview_reflects_the_live_rubber_band_preview_and_clears_on_abort` — starts a real "box"
    interaction, two `worldPointerMove` ticks, confirms zero operations, monotone seq, live cursor
    tracking in the payload, and `None` again after `engagementAbort`.
  - `gesture_preview_is_a_pure_read_never_mutating_the_engagement_session`
`cargo test -p cad-plugin --lib`: 3/3 new tests pass; 80/81 pre-existing tests pass. The 1 pre-existing
failure (`cad_labels_translate_catalogue_typologies_in_german`, same `invalid catalog icon name` panic as

showing the icon catalog untouched.


5) puzzle/plugin/rs/lib.rs

"Never touches persistent document state" verification, concretely, per crate: every `gesture_preview`
accessor reads ONLY the app's own ephemeral scratch struct (`GestureContext` / `TransformSession` /

`self.preview_seq += 1`-equivalent line.


WHAT'S STILL MISSING (the honest gap, restated)
--------------------------------------------------
Every `gesture_preview()` accessor added above is currently `#[allow(dead_code)]` outside its own tests —
by construction, there is nothing else in any of these 5 crates that could call it, because there is no
reachable transport out of a WASI-P2 sandboxed plugin toward `SyncSession::publish_preview` today. Making
this live requires, in a follow-up ticket/wave (NOT this one, given its file-ownership boundary):
  1. `vcs::BackboneMessage` gains a `Preview { key, seq, payload }` variant (vcs/rs/lib.rs).
  2. The WIT plugin-host boundary (framework/plugin's `host_backbone_send`/host relay) or a new dedicated
     WIT export threads that variant across the sandbox — the plan's own Part 3 says "WIT unchanged" for
     this campaign, so this may need either reusing the existing backbone channel (the natural fit, given
     (1)) or a deliberate, separately-decided WIT amendment.
  3. Host-side (framework/product/os/core, wherever a plugin instance's `PortBackbone` traffic is pumped)
     relays a received `BackboneMessage::Preview` to the attached `SyncSession::publish_preview(key, seq,
     payload)` for that document's actor.
  4. Each of the 5 `gesture_preview()` accessors added here gets ONE call site added wherever step (3)'s
     relay reads per-tick preview state out of a live plugin instance (or, alternatively, each app's own
     per-tick handler pushes `gesture_preview()`'s tuple onto the existing `vcs::Backbone` queue directly
     via a new `BackboneMessage::Preview` variant, once (1) lands — a plugin already owns and pushes onto
     that queue for `Operations`/`Snapshot` today, so this is the more natural fit than (3) once (1)/(2)
     exist).

Until then, these 5 additions are a correctly-shaped, fully-tested, zero-runtime-cost staging area: the
exact payload semantics (base-anchored where a diff is involved, monotone seq, JSON-serializable, reads
only ephemeral scratch) are settled and proven by test, so wiring step (4) is expected to be small once
(1)-(3) exist.
