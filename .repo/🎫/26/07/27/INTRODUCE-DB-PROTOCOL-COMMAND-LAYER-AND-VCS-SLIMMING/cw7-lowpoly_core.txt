Id source for `Add`, and why: `LowpolyObject` already carries its own `id: String` field and
`impl Identified<String> for LowpolyObject { fn id(&self) -> &String { &self.id } }` already exists
(used by `Remove`/`Move`/`Patch` on this same collection). So at both `Add`-construction sites
(`apply_lowpoly_operation`'s `ObjectsAdd` arm and `invert_lowpoly_operation`'s `ObjectsAdd` arm) the
new `id` field is filled with `item.id.clone()` — no fresh id generation needed, the item already
carries its permanent identity. Crucially, `LowpolyOperation::ObjectsAdd { index, item }` itself
(the crate's own flat operation variant, `#[derive(dsl::DslOps)]`) was NOT given a new `id` field —
it never needed one, since `item.id` already round-trips through DSL/JSON as part of `item`. That's
also why `objects_operation_from_collection`'s `Add` match arm binds `id` as `_id` and discards it:
converting a generic `CollectionOperation::Add{id, item, at}` back to
`LowpolyOperation::ObjectsAdd{index, item}` only needs `item` and `at`; `id` is redundant with
`item.id` by construction and dropping it loses no information.

Undocumented-but-mandatory ripple inside this same file (found by the build, not anticipated by the
instructions doc): `protocol::Patchable<TPatch>` is NOT a pure relocation of `vcs::Patchable` — its
shape changed too. `vcs::Patchable::apply_patch(&mut self, patch: &TPatch) -> TPatch` (mutates and
returns the inverse patch in one call); `protocol::Patchable` splits that into
`apply_patch(&mut self, patch: &TPatch)` (returns `()`) plus a new required
`diff_patch(&self, other: &Self) -> Option<TPatch>` method (computes an inverse/delta patch by
comparing two states). Since `protocol::apply_collection_operation`/`invert_collection_operation`
require `TItem: Identified<TId> + Clone + Patchable<TPatch>` where `Patchable` now resolves to
`protocol::Patchable` (forced by the import switch — Rust trait resolution is nominal, so this
isn't optional), `impl Patchable<LowpolyObjectPatch> for LowpolyObject` had to be rewritten to the
new two-method shape. Verified this is the intended/expected pattern (not a scope overreach) by
checking other already-migrated sibling crates in this same wave (`sequence/core/rs`,
`layout/rs`, `architect/program/rs`, `gis/plugin/rs`, etc. all already have this exact
`apply_patch`+`diff_patch` split) — same field-by-field `Some(...).then(...)`/`then_some(...)`
diff pattern applied here. One test (`object_patch_apply_mutates_and_inverse_restores_all_fields`)
relied on `apply_patch`'s old inverse-returning signature; updated it to call `apply_patch` then
`object.diff_patch(&original)` to get the inverse before re-applying, same assertions preserved.
Flagging this because the instructions doc's step 6 described `Patchable` as moving "per the same
shape freeze" implying pure relocation, when in this crate (and evidently others) it also required
a real signature/behavior port — future crates in this wave should expect this too, not just an
import-path swap.
