BUGS FOUND AND FIXED DURING THE WAVE (worth flagging)
=====================================================================

1. `pack::content_hash(bytes: &[u8])` is NOT a general-purpose byte hasher — its
   actual implementation is `read_footer_only(&bytes).map(|footer| footer.content_hash)`,
   i.e. it reads a PACK FILE's footer and returns the hash already stored there. My
   first implementation of the content-addressed checkpoint id (and of the
   blake3-based `OperationMeta.payload_hash`) called this on arbitrary
   `serde_json::to_vec(...)` bytes, which is not a valid pack file — it silently
   errored and fell back to an all-zero `[0u8; 32]` digest for EVERY call, causing
   widespread, non-obvious checkpoint-id collisions (3 vcs test failures:
   `history_columns_assigns_distinct_lanes_...`, `snapshot_merge_into_a_nonempty_
   store_...`, `studio_member_checkout_switches_at_the_alternative_tip_...`). Fixed by
   adding `blake3 = "1"` as a direct vcs dependency and hashing with
   `blake3::hash(bytes)` directly (the same primitive `pack_core::ContentHash`/
   `protocol_format::Blake3Hasher` use internally) — all 76 (now 80 with the new
   tests) vcs tests pass after the fix. Flagging in case `pack::content_hash`'s name
   misleads a future caller elsewhere in the same way.

2. My first `impl From<ReconcileReport> for StudioConflict` mapped `kind:
   format!("{:?}:{}", report.severity, report.id)` — prefixing the severity onto the
   original id/kind string. This broke `framework/product/os/core`'s own
   `concurrent_delete_and_wire_reconciles_without_a_dangling_edge` test, which asserts
   `conflict.kind == "media-graph/edge-orphaned"` (an exact string match — `os/core`'s
   `reconcile` wrapper round-trips its own `StudioConflict.kind` through
   `ReconcileReport.id`, so the mangled prefix broke the round trip). Fixed to
   `kind: report.id` verbatim; `severity` has no field to land in on `StudioConflict`
   and is genuinely dropped (documented inline as a structural, not further-fixable-
   here, information loss). `semio-framework-os`'s test suite (55/55) and vcs's
   (80/80) both pass after the fix.

3. (Not a bug I fixed, but a documentation-vs-reality gap worth flagging for CW7/CW8:)
   the dsl_derive flip's generated `impl ::protocol::OpText for #name` uses an
   ABSOLUTE `::protocol::` path. The instructions assumed this "likely resolves for
   free through the shim" because "virtually every DslOps-deriving crate already
   depends on vcs" — but a re-export (`vcs`'s `pub use protocol::OpText`) only makes
   the ITEM `vcs::OpText` resolve; it does NOT make the bare crate name `protocol`
   itself resolvable via an absolute `::protocol::` path unless `protocol` is a
   DIRECT Cargo dependency of the crate being compiled. Confirmed via a real
   `E0433: cannot find 'protocol' in the crate root` in `semio-framework-os`. Fixed
   for all 38 affected crates (see the Cargo.toml sweep above) — this was anticipated
   in spirit by the instructions ("if you find such crates, add the minimal protocol
   path dep... this counts as part of the ~40-crate dep sweep") even though the
   stated mechanism (missing `vcs` dep) wasn't the actual cause.

   adaptation for every CURRENT `Operation::reconcile` override (verified: none of
   vcs's own three real impls, nor `OsOperation`, actually inspect `self` inside
   `reconcile` — only `projection`). If a FUTURE technology's `reconcile` override
   ever does depend on `self`'s own fields, "last applied operation" vs. "any
   instance of this type" could produce different results than the old per-TYPE
   associated-fn call did — worth a design review whenever the next real override is
   added, not urgent now.
