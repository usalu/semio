CW7 App fan-out — gis/plugin/rs (crate: gis-plugin)
=====================================================

Scope: migrate CollectionOperation::Add/Move construction+match sites, and
vcs::apply_collection_operation/invert_collection_operation/collection_diff_from_operation
calls in gis/plugin/rs/lib.rs onto the frozen protocol::CollectionOperation shape
(Add gains mandatory `id`, `index`->`at`; Move `to_index`->`to`). Also switch the
Operation/OperationDiff/OpText trio's import path from vcs:: to protocol:: while
in the file.

Real usage confirmed: YES. This crate has substantial CollectionOperation usage —
GisMapOperation::Positions/Routes/Regions wrap CollectionOperation<String, MapFeature,
MapFeaturePatch> for the GIS map document's three id-keyed feature collections
(positions/routes/regions), used in production code (positions_operations diffing,
patchRoutes action handler), a hand-rolled DSL twin (GisMapOperationDsl) for the
foreign-type orphan-rule workaround, and ~15 test call sites.

Files touched: ONLY gis/plugin/rs/lib.rs. Cargo.toml untouched — `protocol = { path =
"../../../protocol/rs" }` was already present (confirmed before editing).

What changed
------------
1. `domain` module's `use vcs::{ ... }` import block split: CollectionDiff,
   CollectionOperation, Identified, Operation, OperationDiff, Patchable, plus the
   collection_diff_from_operation/invert_collection_operation functions now come
   from `protocol::`. create_document_vcs_envelope, DocumentVcsCommand,
   DocumentVcsEnvelope, DocumentVcsStore, TextError (the VCS-store machinery, not
   part of the frozen CollectionOperation/Identified/Patchable/Operation contract)
   stayed on `vcs::`.

2. `MapFeature`'s `impl Patchable<MapFeaturePatch>` rewritten from the old vcs shape
   (`apply_patch(&mut self, &TPatch) -> TPatch`, mutate-and-return-inverse) to the
   new protocol shape (`apply_patch(&mut self, &TPatch)` mutate-only, plus a
   separate `diff_patch(&self, other: &Self) -> Option<TPatch>`). This was required
   because protocol::invert_collection_operation calls `.diff_patch()`, not the old
   single-method `.apply_patch()` — a genuine second-order consequence of switching
   the Patchable import, not just a rename. Verified against the same pattern
   already used by layout/rs's Patchable impls (TextStoryPatch/ImageLinkPatch:
   `(self.field != other.field).then(|| Patch { field: Some(other.field.clone()) })`).
   Confirmed by test: `positions_add_patch_remove_round_trip` exercises Add + Patch +
   Remove round-tripping through invert_collection_operation and still passes.

3. `Add { index, item }` construction sites rewritten to `Add { id, item, at: index }`
   across all three collections (Positions/Routes/Regions), in:
   - domain test module (round_trip helper calls, dispatch test) — id: literal
     "p1".into(), matching the id already used by the sibling Remove/Move calls in
     the same test.
   - `gis_map_operation_from_dsl` (DSL -> GisMapOperation conversion) — id:
     `item.id.clone()`, the item's own id field (the DSL twin's Add{index,item}
     variant has no separate id token; MapFeature already carries id as a field, so
     that's the natural/only available id source here, per the instructions doc's
     guidance).
   - `positions_operations` (production diffing helper in app_2d, before/after
     array diff) — id: `feature.id.clone()` where `feature: &MapFeature` is the
     loop variable already used for Patch's id lookup two lines below.
   - app_2d test module (op-line round-trip tests x3, dispatch test) — id: literal
     "p1".into(), matching the sibling Remove/Move/Patch calls in the same tests
     (all of which target the fixture MapFeature{id:"p1",...} returned by
     sample_patch_feature()).

4. `Move { id, to_index }` renamed to `Move { id, to }` (pure rename, no semantic
   change) at all pattern-match and construction sites: `gis_map_operation_to_dsl`/
   `gis_map_operation_from_dsl` (x3 collections each) and the op-line round-trip
   tests (x3). The local DSL twin's own field name (`GisMapOperationDsl::MovePosition
   { to_index: usize }`, printed via `#[dsl(key = "to")]`) is untouched — only the
   protocol::CollectionOperation::Move field it reads from/writes to changed name.

5. Pattern-match sites for `Add`/`Move` updated to bind the new `id`/`at` fields;
   `id` is bound `_id` (prefixed-unused) in `gis_map_operation_to_dsl`'s Add arms
   since the DSL twin's AddPosition/AddRoute/AddRegion variants carry no separate id
   field (MapFeature's own `.id` inside `item` already round-trips it — confirmed
   by `gis_map_positions/routes/regions_op_lines_round_trip` tests passing).

6. `impl vcs::OpText for GisMapOperation` -> `impl protocol::OpText for
   GisMapOperation`; the two `<GisMapOperationDsl as vcs::OpText>::{parse_op,
   print_op}` calls -> `<GisMapOperationDsl as protocol::OpText>::{...}` (per step 7
   of the instructions doc — the Operation/OperationDiff/OpText trio). Note:
   dsl::DslOps's derive macro already generates `impl ::protocol::OpText for
   GisMapOperationDsl` directly (confirmed in dsl/derive/rs/lib.rs), so this was
   already protocol-native on that side; only GisMapOperation's own hand-written
   impl needed the path switch. `vcs::TextError` in `parse_op`'s return type left
   as-is: `vcs::TextError` is a verbatim `pub use dsl_core::TextError` re-export in
   vcs/rs/lib.rs, i.e. the literal same type `protocol::OpText::parse_op`'s
   signature (`Result<Self, dsl_core::TextError>`) requires, so no functional
   change was needed there.

7. `use vcs::CollectionOperation;` in `app_2d` module -> `use protocol::
   CollectionOperation;`.

8. Two doc-comment references updated for accuracy (the `GisMapOperationDsl` twin's
   doc comment: `vcs::CollectionOperation<K,V,P>` -> `protocol::CollectionOperation
   <K,V,P>`, "declared in the `vcs` crate" -> "declared in the `protocol` crate",
   `vcs::OpText` -> `protocol::OpText`).

Id source rationale (step 2 of the instructions doc)
-----------------------------------------------------
Every Add site in this crate's collections (positions/routes/regions, all
Vec<MapFeature>) already has Remove/Move/Patch obtaining their TId from
`MapFeature.id: String` (a `#[dsl(positional)]` field on the `#[derive(dsl::
DslRecord)]` struct, implementing `Identified<String> for MapFeature` via
`fn id(&self) -> &String { &self.id }`). No fresh id is generated at insertion
time anywhere in this crate — every Add call site already has a fully-formed
MapFeature (with its id already set, either from a fixture, a document-derived
feature, or DSL-parsed input) before constructing the operation. So the id
source for every Add is simply the item's own `.id` field (or, in tests, the
literal id the fixture MapFeature is known to carry) — no counter/ULID/slug
generation logic existed to preserve.
