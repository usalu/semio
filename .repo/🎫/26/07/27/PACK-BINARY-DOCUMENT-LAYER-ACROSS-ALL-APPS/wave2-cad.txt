5. BLOCKER — NOT FIXED, OUT OF SCOPE (pack/value/rs/lib.rs)
--------------------------------------------------------------------------------
`cargo test -p cad_document` FAILS 2/15 tests (both newly-added pack-equivalence assertions):

  thread 'tests::cad_scene_round_trips_through_dsl_document' panicked at vcs/rs/lib.rs:3406:89:
  pack decode failed: schema error: expected a 3-item Tuple, found List([Float(1.0), Float(2.0), Float(3.0)]) at 1:1

Root cause (traced precisely, read-only — did not touch pack/** or dsl/**, both out of this
family's allowed directories):

  `CadScene.objects`/`building_objects`/`energy_objects`/`structure_classic_objects`/`nodes` are all
  `#[dsl(table)]` fields (`Shape::Table`, columnar Structure-of-Arrays pack encoding). `CadObject`
  (the row type) has several `Shape::Tuple`-shaped fields (`origin: [f64; 3]`, `orientation:
  Option<[f64; 4]>`, `scale`/`extent: Option<[f64; 3]>`).

  In pack/value/rs/lib.rs:
  - `encode_table`'s fallback column arm (~line 1022-1033, for any column shape outside
    Bool/Int/UInt/Float/Enum/Text, i.e. `elem_tag_for_shape` -> `ELEM_FALLBACK`) correctly calls
    `encode_value(ctx, Some(&field.shape), v, depth + 1, out)` — the real `Shape::Tuple(..)` is
    threaded through.
  - `decode_table_soa`'s mirroring fallback arm (~line 1112-1119) calls
    `decode_value(reader, None, ctx, depth + 1)?` — `None`, NOT the column's actual shape.
  - Wire tags `TAG_PACKED_F64`/`TAG_PACKED_VARINT` (the homogeneous-numeric packed forms
    `encode_seq` picks for a `[f64; 3]`'s 3 same-variant `Float` items) do NOT themselves encode the
    Tuple-vs-List bit — `decode_value`'s dispatch for those tags derives it purely from
    `is_tuple_shape(shape)`. With `shape = None`, that's always `false`, so a `[f64; 3]` origin
    column inside a `#[dsl(table)]` list decodes back as `FieldValue::List` instead of
    `FieldValue::Tuple`, and `dsl/rs/lib.rs`'s `impl<T, const N: usize> DslField for [T; N]::from_value`
    then rejects it with exactly the observed error.
  - This is a real asymmetry bug (encode threads shape, decode doesn't), not a CadScene-specific
    misconfiguration — it will reproduce for ANY `#[dsl(table)]` row type anywhere in the repo whose
    fields include a fixed-size array (`Shape::Tuple`) or any other `ELEM_FALLBACK`-shaped field
    (nested `List`/`Record`/`Map`/`Block`/`Value`/`Table`). `pack/value/rs/lib.rs`'s own inline unit
    tests around line 1356/1491 only exercise `Shape::Tuple` at the top level of a plain
    `encode_document`/`decode_document` call (never inside a `Table` column), which is why this gap
    went unnoticed through wave 0/1.

  I did NOT patch this — `pack/**` is explicitly off-limits for this family. Recommend a dedicated
  fix (`decode_table_soa`'s fallback arm needs the column's real `Shape`, which requires either
  passing the row type's `RecordSpec`/`fn() -> RecordSpec` into `decode_table_soa` — contradicting
  its current "no RecordSpec required" self-describing design — or encoding enough shape metadata
  per-column on the wire for the fallback case, e.g. widening `elem_tag_for_shape` to also flag
  "packed-eligible Tuple" so the fallback decode can rebuild `is_tuple` from the byte stream alone).

The two new `assert_dsl_pack_equivalence` calls were left in place (not reverted/removed) — they are
exactly what wave 2 instructions require, and they are correctly detecting a real bug, not a mistake
in my edits. `assert_dsl_round_trip` (pure DSL text path, unaffected by pack's table encoding) still
passes for both.
