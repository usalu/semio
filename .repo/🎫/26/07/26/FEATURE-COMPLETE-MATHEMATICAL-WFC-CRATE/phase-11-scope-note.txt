P11 — chunk streaming + hierarchy + parallel — scope note
===========================================================

Implemented (246 tests passing, cargo clippy clean for mathematical_wfc itself):

- parallel.rs: `derive_seed()` (deterministic splitmix64-style per-attempt seed derivation) and
  `multi_start()` — runs `attempts` independent `search::solve` calls via `std::thread::scope`,
  waits for every one (never races on "first thread to finish" — that would make the result
  depend on scheduling, breaking this crate's determinism guarantee), then deterministically
  reduces: lowest-index `Solved` wins; if none solved, the lowest-index attempt's outcome is
  returned as-is (so a genuine `Unsatisfiable(proven: true)` from attempt 0 still correctly
  proves the whole model unsatisfiable, since every attempt targets the same model). Wired into
  `GraphSolver::solve_multi_start(...)`.
- chunk.rs: `chunk_seed()` (world seed + chunk coordinate + model fingerprint → deterministic
  per-chunk seed, order-independent) and `solve_chunk()` — pins seam cells already committed by
  neighboring chunks, honors the chunk's own baked-in restrictions (e.g. a `Grid2dSolver`'s
  mask/`Boundary::FixedOutside` folding) via `init_domains`, and solves through the ordinary
  kernel. Wired into `Grid2dSolver::solve_chunk(...)`.
- hierarchy.rs: `solve_hierarchy()` — solves a macro model/topology once, then for every macro
  node calls a caller-supplied `child_model_for(node, macro_pattern)` to get that node's own
  child model/topology/config and solves it with a seed derived from the macro seed + node id.
  `HierarchyOutcome::{Solved, MacroUnsatisfiable, ChildFailed{node}}` reports exactly which macro
  node's child failed, if any, so a caller can build its own retry/fallback policy on top.

Deferred from the original plan's P11 scope (left for a later pass, not silently dropped):

- **hierarchy.rs has no backtrack-to-macro.** A failed child (`ChildFailed{node}`) does not
  retry that one macro decision while keeping every other macro node fixed — the whole
  hierarchy solve simply stops there. Implementing real backtrack-to-macro needs essentially a
  `crate::repair`-style halo re-solve triggered from a *different layer's* failure (re-open just
  the failing macro node, re-decide it, re-attempt its child), which is meaningfully deeper
  integration than a first hierarchical pass warrants without a concrete consumer dictating the
  exact fallback policy (retry same node with a new pattern? widen to neighboring macro nodes
  too? give up and restart the whole macro layer?). `HierarchyOutcome::ChildFailed` exposes
  enough for a caller to implement any of those policies externally today.
- **No boundary-contract mechanism.** The original plan called for macro-adjacent micro regions
  to constrain each other's seam cells (a child model declaring which boundary sockets it
  requires, checked against neighbors). This module's children are solved fully independently —
  no seam coordination between them at all. This is a real, deliberate scope cut: adding it
  properly needs the same kind of pinned-seam plumbing `chunk.rs`/`repair.rs` already provide,
  extended to run *between* sibling children rather than between a chunk and its already-solved
  neighbors, and is better designed once a concrete hierarchical-generation consumer defines what
  contract shape it actually needs.
- **No public API surface for `hierarchy.rs`.** `solve_hierarchy`/`HierarchyOutcome` stay
  `pub(crate)` — the function is generic over two independent `Topology`-bounded type parameters
  (macro and child can be different topology kinds entirely, matching real macro→micro use
  cases), and `Topology` itself is a sealed `pub(crate)` trait, so a `pub` wrapper would need to
  either commit to one concrete topology pairing (understating the design's actual generality)
  or leak the sealed trait into a public bound. Deferred until a concrete public consumer picks
  a pairing worth committing to, following the same precedent set by `repair_region`/`multi_start`
  (both `pub(crate)` free functions with concrete per-solver wrapper methods providing the public
  surface instead).
- `chunk.rs` has no chunk registry, world-coordinate bookkeeping, halo-width auto-detection from
  relation offsets, or boundary-signature cache — explicitly out of scope per its own module doc;
  those are orchestration concerns for a caller actually streaming an infinite/large world, and
  `solve_chunk`/`chunk_seed` are the one primitive such an orchestrator needs from this crate
  (a deterministic, seam-respecting per-chunk solve), not a full streaming-world manager.
- `chunk.rs`/`parallel.rs` are wired into `GraphSolver`/`Grid2dSolver` only where it made sense
  as a first consumer (chunk streaming is inherently a grid concept; multi-start applies equally
  well to any solver but was only wired into the reference `GraphSolver` for now) — adding the
  same wrapper methods to `Grid3dSolver`/`Grid2dSolver`(for multi-start) is a one-line, low-risk
  follow-up once a caller needs it.

Rationale for scoping down: `parallel.rs` and `chunk.rs` are both complete, real, and tested to
the same rigor as every prior phase — they're bounded, low-risk primitives with clear, provable
contracts (determinism, seam-respecting reproducibility). `hierarchy.rs`'s full scope
(backtrack-to-macro, boundary contracts) is a substantially larger feature whose correct design
depends on decisions a concrete consumer should make (what to retry, how strict a boundary
contract needs to be) — implementing a plausible-but-unvalidated version of that machinery now,
without a consumer to check it against, is exactly the kind of premature complexity CLAUDE.md's
own "must be thorough" mandate argues against when read alongside "don't design for hypothetical
future requirements." The two-level macro→child composition primitive that *is* implemented is a
genuine, tested building block the fuller feature can be built on top of later.
