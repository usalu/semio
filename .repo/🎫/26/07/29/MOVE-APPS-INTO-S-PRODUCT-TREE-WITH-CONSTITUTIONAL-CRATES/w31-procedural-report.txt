W31 constitutional split — procedural plugin (2d, 3d apps)
=============================================================

SCOPE: split the two-app `procedural` plugin (2d/rs 1168 lines, 3d/rs 1112
lines, plugin/rs 3651 lines containing both apps' engine+ui logic in
`pub mod app_2d { ... }` / `pub mod app_3d { ... }`) into two parallel
constitutional app trees per the recipe at w31-constitutional-split-recipe.md,
following the gis (multi-app, 2d/3d) precedent structurally and the fem
(foreign-type DSL-mirror pattern) precedent for content-mapping judgment.

RESULT: all 14 app crates + the thin bundle compile clean (0 errors,
`cargo check --all-targets`) and the bundle compiles standalone.

Final layout created:
  s/plugin/procedural/app/2d/{rs,engine,dsl,op,pack,protocol,ui}/rs
  s/plugin/procedural/app/3d/{rs,engine,dsl,op,pack,protocol,ui}/rs
  s/plugin/procedural/plugin/rs  (rewritten thin bundle, same path)

Crate names: semio-s-app-procedural-{2d,3d}[-{engine,dsl,op,pack,protocol,ui}]

Deleted: s/plugin/procedural/{2d,3d}/rs (Cargo.toml, lib.rs, pkg/ wasm-pack
build output, project.json, package.json, script.ts). example/ and play/
siblings under 2d/, 3d/ were left in place (fixtures, not moved) and are now

The 1 failing test (app/3d/ui/rs, `tests` module):
  - node_graph_hover_updates_preview_selection_and_graph_scene
Panics on `assert!(preview_json.contains(r#""hoveredId":"extrude""#) ||
preview_json.contains(r#""hoveredId": "extrude""#))`. Root-caused via a
temporary `[DEBUG]` eprintln (removed before finishing): the actual
computed `selectionJson` value IS correct (`hoveredId":"extrude"` present
with the right value) — but `ui_wgpu::World3dScene.selection_json` is a
plain `String` field with `#[derive(Serialize)]` (no raw-JSON embedding),
so when the outer `UiNode` is serialized the whole selection payload comes
out double-escaped: `\"hoveredId\":\"extrude\"`. The test's plain (unescaped)
substring assertion can never match against that escaped form, regardless
of runtime state. This is a pre-existing test/serialization-shape mismatch
in `ui_wgpu`/the original test body (both untouched, ported verbatim) —
not something introduced by this split. The underlying app behavior
(hover state correctly flows into the selection payload) is verified
correct; only the test's string-matching methodology is broken.

DEVIATIONS FROM THE RECIPE (all content-mapping judgment calls, no logic
rewritten):
  - Neither `Procedural2dDocument` nor `Procedural3dOperation` can derive
    `dsl::Dsl*`/`protocol::OpText` directly (their fields — `FlowFixture`,
    `Widget`, `GenerationPlayState`, etc — are foreign types from
    `flow_core`/`playbook`, so the orphan rule blocks a direct derive).
    The original file already solved this with a full parallel
    `*Dsl`/`*OperationDsl` mirror-type region (`ValueDsl`, `WidgetDsl`,
    `CameraJsonDsl`, `SynapseSpecDsl`, `FormGenerationDsl`,
    `Procedural{2,3}dDocumentDsl`, `Procedural{2,3}dOperationDsl` — same
    pattern as `fem_2d`'s `FemDof`, scaled up). Since `pack` must never
    depend on the app's own `dsl` crate (recipe's own dependency graph) but
    both the `DocumentDsl` and `DocumentPack` impls need the SAME mirror
    types, the whole `DslMirror` region (types + to/from-dsl conversion
    fns, made `pub`) went into `rs` alongside the manual
    `impl store::DocumentDsl`/`impl store::DocumentPack` for the document
    type — functionally identical to what a `#[derive]` would have given a
    directly-derivable type in `rs`, just hand-written. The mirrored
    `Procedural{2,3}dOperationDsl` (needed by the Operation enum's
    `OpText`/`OpBinary` impls) went into `op` instead, since it embeds
    `op`'s own `Procedural{2,3}dOperation` shape; it reuses `rs`'s
    (now-`pub`) `WidgetDsl`/`CameraJsonDsl`/etc mirror types and
    conversion fns rather than duplicating them.
  - `engine` ended up asymmetric between the two apps: 2d's engine is
    thin (fixture-diff JSON helpers, the DWG/SVG media-codec fns, the
    default-projection builder) because 2d has almost no unique compute of
    its own — it's mostly `flow_core`/`flow_module_draw` orchestration
    already living outside this plugin. 3d's engine is much larger: the
    entire `Procedural3dRuntime`/`Procedural3dPreviewCache` ephemeral-state
    structs, the whole mesh-preview evaluation pipeline
    (`evaluated_preview_payload`, `mesh_from_tessellation_json`,
    `geometry_handle_for_widget`, fallback mesh builders), and the whole
    `GumballTransforms` region moved to `engine` because they're pure
    fixture/mesh compute with no dependency on `ActionDescriptor`/
    `UiNode`/`ViewState`/other App-framework UI types — the same
    "no App-framework types" line used to decide 2d's split, just with
    much more content on the engine side of it for 3d. Only functions that
    return App-framework types (`ActionDescriptor`, `WindowMeasure`) or
    take the UI-only combined `Procedural{2,3}dPlayView` type stayed in
    `ui`. This is NOT literally what the recipe's terse `engine` bullet
    describes (tree helpers/id generation/media codecs) — it required
    reading every function's own signature to classify it consistently,
    since procedural's `plugin/rs` has no region boundary that lines up
    with the engine/ui split the way `note`'s did.
  - `Procedural2dPlayRuntime`/`Procedural3dRuntime` (ephemeral, never
    persisted, plain `Default`-able structs) live in `engine`, not `ui`,
    specifically so `engine`'s own mesh/preview functions (which take
    `&Runtime`/`&mut Runtime`) don't need a forbidden `engine` → `ui`
    dependency; `ui`'s `Procedural{2,3}dPlayApp` struct just holds one as
    a field.
  - `widget_id` (identical duplicate definition in both `{2,3}d/rs` AND
    the plugin file's `app_{2,3}d` modules in the original) was
    de-duplicated: kept once as `pub fn widget_id` in each app's `rs`
    crate (matching fem_2d's `element_id`/`load_id` placement precedent),
    with `op`/`engine`/`ui` all importing it rather than each carrying
    their own copy.
  - `dsl` crate tests intentionally KEEP both `assert_dsl_round_trip` AND
    `assert_dsl_pack_equivalence` calls together in the same test body
    (verbatim from the original file), rather than stripping the pack
    half out per the recipe's terse per-slot bullet — `pack`'s own crate
    ALSO independently re-derives the same fixtures and calls
    `assert_dsl_pack_equivalence` on its own. Confirmed this is required,
    not optional, by grepping the exact predicate
    `POLICY_PACK_COMPLETENESS_ALLOWLIST`'s check uses in root `script.ts`
    (any file with `assert_dsl_round_trip`/`assert_document_text_round_trip`
    but no `assert_dsl_pack_equivalence`/`assert_document_pack_round_trip`
    IN THE SAME FILE fails that policy check, and that allowlist is
    currently empty — matches the already-landed `puzzle` split's dsl
    crates, which do the same double-assertion thing verbatim).
  - No `s/plugin/procedural/shared/rs` crate created — 2d and 3d's `rs`
    files are structurally near-identical (same DSL-mirror pattern,
    independently invented) but share zero actual code/types; neither app
    imports anything from the other. Rule S not triggered.
  - `empty_procedural{2,3}d_projection()` (trivial `Document::default()`
    wrapper) added to each `engine` crate even though the original files
    already had one — the original definitions lived beside
    `Procedural{2,3}dDocumentVcs`'s wasm bridge in `{2,3}d/rs/lib.rs`,
    which is now `rs`+`ui` split; per the recipe's own explicit engine
    mapping (`empty_X_document()`) it belongs in `engine`, matching `note`/
    `gis`/`fem`'s identical placement.
