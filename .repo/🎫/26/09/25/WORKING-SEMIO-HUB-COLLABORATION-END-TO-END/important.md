## Architecture decisions (final)

1. `semio/client/lib/rs` (crate `semio`) is the **sole owner of domain logic**. The hub MUST NOT keep its own parallel domain model (the old per-entity `core.*` tables, `DomainCommand` enum, `EntityChange`, `FieldPatch`, … are removed). The hub embeds the native `semio` crate and keeps **one authoritative rs kit store per hub session** (same GraphQL control plane as the WASM worker and `semio-store`).
2. Collaboration = **operation replication**: clients send GraphQL mutation documents (operations) to the hub, the hub executes them in order on its authoritative store, assigns a monotonically increasing `version`, persists them, and broadcasts them. Other clients replay the same operation on their local (WASM) store. Every broadcast carries the resulting kit `hash`; on local/hub hash mismatch the client resyncs from `GET /sessions/{id}/kit` (+ `installProjection`). Operations that create entities MUST carry client-generated ids so replay is deterministic.
3. Persistence (Postgres, schema created by the hub at startup): persons, credentials, tokens, sessions, members, shares, operations log, periodic kit snapshots (for fast load + lookback), no per-entity tables.
4. Presence lives in the hub (in-memory per session, mirrored to `semio.person` for identity only) and is broadcast over the session websocket. AI agents (MCP) appear as participants with `kind: "agent"`.
5. The **semio MCP** for collaborative AI is served by the hub at `POST /mcp` (MCP Streamable HTTP, JSON responses, JSON-RPC 2.0), authenticated with a person bearer token. Tool calls execute operations on the authoritative session store exactly like a client, so every AI change is broadcast live to all collaborators. The local engine MCP (`semio/client/bin/engine`) keeps working for local kits.
6. Default ports: hub `8080` (`LISTEN_ADDR`), sketchpad dev `5173`, semio-store `4010`. Local dev DB: `postgres://semio:semio@localhost:5432/semio`.

## Hub Protocol v1 (all JSON bodies camelCase)

### Auth
- `POST /auth/register {name, email, password}` → `201 {token, person}`
- `POST /auth/login {email, password}` → `200 {token, person}`
- `GET /auth/me` (Bearer) → `{person}`
- `POST /auth/logout` (Bearer) → `204`
- `POST /auth/tokens {label}` (Bearer) → `201 {token, label, kind: "agent"}` — long-lived agent token for MCP clients; participants using it appear as `kind: "agent"`.
- `person = {id, name, email, color}`; tokens are opaque strings; `Authorization: Bearer <token>`; websocket uses `?token=<token>`.

### Sessions (a session = one shared kit)
- `GET /sessions` (Bearer) → `[{id, name, role, owner: {id, name}, version, hash, updatedAt, participantCount}]`
- `POST /sessions {name, kit?}` (Bearer) → `201 {id, name, role: "owner", version, hash}` — `kit` is a kit projection JSON (same format `installProjection` accepts); omitted → empty kit named `name`.
- `GET /sessions/{id}` → `{id, name, role, owner, version, hash, updatedAt, participantCount}`
- `DELETE /sessions/{id}` (owner) → `204`
- `GET /sessions/{id}/kit` (member or share token) → `{version, hash, kit}`
- `POST /sessions/{id}/operations {operationId, clientId, baseVersion, query, variables?}` (owner/editor) → `200 {version, hash, data}` | `4xx {error}`; idempotent on `operationId`.
- `POST /sessions/{id}/graphql {query, variables?}` (any member) → raw GraphQL response; read-only (mutations rejected with 400, use `/operations`).
- `GET /sessions/{id}/operations?after=<version>` → `[{version, operationId, clientId, personId, participantKind, query, variables, hash, createdAt}]`
- `GET /sessions/{id}/kit/at/{version}` → `{version, hash, kit}`
- `GET /sessions/{id}/members` → `[{person, role}]`; `POST /sessions/{id}/shares {role: "editor"|"viewer", label?}` (owner) → `201 {token, role}`; `GET /sessions/{id}/shares`; `DELETE /sessions/{id}/shares/{token}`; `POST /shares/{token}/join` (Bearer) → `{session, role}` (adds membership).
- `GET /sessions/{id}/presence` → `[participant]`
- Roles: `owner` > `editor` > `viewer`.

### Websocket `GET /sessions/{id}/ws?token=<token>&clientId=<uuid>&client=<sketchpad|mcp|engine|...>`
Server → client (`type` discriminated):
- `welcome {self: participant, participants: [participant], version, hash}`
- `presence.joined {participant}` / `presence.left {participantId}` / `presence.updated {participant}`
- `operation {version, hash, operationId, clientId, participantId, personId, query, variables}` (sent to everybody, including the origin, so the origin can confirm)
- `error {message}`
Client → server:
- `presence {focus?: {app, designId?, typeId?}, selection?: {designId?, pieceIds, connectionIds}, cursor?: {x, y, space}}` (partial updates merge)
- `operation {operationId, baseVersion, query, variables?}` (same semantics as the POST)
- `ping` → `pong`
`participant = {id, personId, name, color, kind: "human"|"agent", client, focus?, selection?, cursor?, joinedAt}`; on socket close the participant is removed and `presence.left` broadcast.

### MCP `POST /mcp` (Bearer; `initialize`, `tools/list`, `tools/call`, `resources/list`, `resources/read`, `prompts/list`, `ping`)
Minimum tool set: `list_sessions`, `create_session`, `read_kit`, `list_designs`, `read_design`, `list_types`, `create_design`, `add_piece`, `connect_pieces`, `update_piece`, `remove_pieces`, `remove_connections`, `list_participants`, `get_history`, `run_query` (read-only GraphQL), `run_operation` (GraphQL mutation as an operation). Every mutating tool = one hub operation (broadcast). While an MCP client works on a session it is a presence participant `kind: "agent"`, `client: "mcp"`, removed after 120 s idle.

## Notes
- F1: **Mutation choke point (for F2 hub replication).** Every kit-changing GraphQL mutation of a `@semio/js` `Session` (entity commands like `kit.createDesign`, `design.piece(id).…`, `startNewChange`, `save`, `installProjection`, …) goes through ONE public method `Session.executeOperation(operation: KitOperation): Promise<KitOperationEnvelope>` in `semio/client/lib/js/index.ts` region `🎛️KitOperations` (inside `🏪Store`). `KitOperation = {operationId, query, variables, origin: "local" | "remote"}` (`query` is the full `mutation …` document, `variables` includes the local `storeId`/`changeId` bindings). Wrap it with `session.useOperationMiddleware((operation, next) => …)` (returns an unsubscribe; middlewares compose in registration order; call `next(operation)` to execute locally). Remote hub operations are replayed with `session.executeOperation({ …, origin: "remote" })` so a middleware can skip re-forwarding them. `session.onOperation(listener)` observes every executed operation (after local execution, with its envelope). One sketchpad-open kit = one `Session` (1:1 with a hub session). Sketchpad never touches `@semio/js`: it goes `SketchpadShellController` → `@semio/react` `SemioKitClient.execute(run)` (region `🧩KitClient` in `semio/client/lib/react/index.ts`) → `@semio/js` entity command → `Session.executeOperation`. `SemioKitClient.session` exposes the js `Session` to F2's `@semio/react` re-exports. Caveat for H/F2: rs currently generates ids server-side for `create*` commands (non-deterministic replay); `storeId`/`changeId` variables are local and must be rebound by the receiver.
- F2: **Replication conventions (H + M please follow).** (1) An operation `query` is the kit-scoped mutation document exactly as `@semio/js` builds it: `mutation($storeId: ID!, $changeId: ID!) { session { store(id: $storeId) { theKit { unsavedChange(id: $changeId) { kit { … } } } } } }`. Clients send `variables` WITHOUT `storeId`/`changeId`; every executor (hub authoritative store and each replica) binds `storeId` to its own store id and `changeId` to a fresh `startNewChange` result before executing, and the hub broadcasts `query`/`variables` exactly as received (never its own bindings). Only these kit-scoped documents are operations (no `startNewChange`/`save`/`installProjection`/checkpoints). (2) **Deterministic ids:** F2 adds an optional `id: ID` argument to rs `createTag`/`createConcept`/`createQuality`/`createType`/`createDesign`/`createFolder`/`addFixedPiece` (rs mints only when omitted; golden SDL updated) and `@semio/js` always passes a client-minted uuid v7. **M:** MCP tools that create entities must pass `id: "<uuid v7>"` inside their operation documents. (3) **Kit hash:** F2 makes rs `Kit.hash` a content hash = blake3 over the canonical kit projection JSON and adds `Kit.projection: String!` (the same JSON `installProjection` accepts). **H:** compute the broadcast/`GET …/kit` `hash` with `query { session { stores { edges { node { wip { theKit { kit { hash } } } } } } } }` (or natively `kit.compute_hash()` on the materialized head kit) and serve `GET /sessions/{id}/kit` `kit` from `Kit.projection` (parsed JSON), so `installProjection(kit)` on a client reproduces the hub hash. (4) Hub echoes every operation to the origin too (contract) — clients confirm own ops by `operationId` and never re-apply them. F2 will rebuild the WASM after the rs change (F1: rebuild again if your build predates it).
- H: **Hub internals for M (Rust, `semio/server/hub/bin.rs`, all `pub`, re-exported at crate root).** Shared state `#[derive(Clone)] pub struct Hub` (axum state of `api::router`). Every call takes a resolved `Caller` and enforces roles itself (401/403/404 as `HubError`, which `impl IntoResponse` → `{error}`):
  `hub.authenticate(token: &str) -> Result<Caller, HubError>` (`Caller::Person(Principal { person: Person {id,name,email,color}, kind: ParticipantKind::Human|Agent })` or `Caller::Share(ShareGrant { session_id, role })`); `caller.principal() -> Result<&Principal, HubError>` (401 for share-only callers); `api::bearer(&HeaderMap) -> Option<String>`.
  `hub.list_sessions(&caller)`, `hub.create_session(&caller, name: &str, kit: Option<Value>) -> SessionSummary`, `hub.session(&caller, session_id: Uuid)`, `hub.session_kit(&caller, sid) -> KitState {version, hash, kit}`, `hub.execute_operation(&caller, sid, OperationRequest {operation_id, client_id, base_version, query, variables}, participant_id: Option<Uuid>) -> OperationResult {version, hash, data}` (persists + broadcasts `operation` to every websocket), `hub.execute_query(&caller, sid, query: &str, variables: Option<Value>) -> Value` (read-only GraphQL response), `hub.history(&caller, sid, after: i64) -> Vec<OperationRecord>`, `hub.kit_at(&caller, sid, version: i64) -> KitState`, `hub.members(&caller, sid)`, `hub.participants(&caller, sid) -> Vec<Participant>`, `hub.agent_presence(&caller, sid, client: &str) -> Participant` (join-or-touch a `kind: "agent"` participant keyed by person+client, broadcasts `presence.joined`; the hub sweeps agent participants idle > 120 s and broadcasts `presence.left`), `hub.update_presence(sid, participant_id, patch: &Value) -> Participant` (merges `focus`/`selection`/`cursor`, broadcasts `presence.updated`), `hub.leave_presence(sid, participant_id)`.
  **M wiring:** add your route inside `api::router` with one line `.route("/mcp", post(crate::mcp::handler))` where `async fn handler(State(hub): State<Hub>, headers: HeaderMap, body: String) -> Response`; nothing else outside `mod mcp`.
  **Operation execution (follows F2 conventions):** the hub accepts only kit-scoped mutations (root path `session → store → theKit → unsavedChange → kit`, anything else → 400), binds `storeId` (= session id) and `changeId` (= fresh `startNewChange`) itself, persists and broadcasts `query`/`variables` exactly as received. Rejected operations (GraphQL errors or `ok: false`) → 422 `{error}`, not recorded, store rebuilt from the log. `baseVersion > version` → 409. Duplicate `operationId` → original `{version, hash, data}`. Session `hash` = `Kit.hash` of the materialized `theKit.kit`; `GET …/kit` `kit` = `Kit.projection_value()` (created sessions are immediately re-based onto their own exported projection, so `installProjection(kit)` on a fresh store reproduces the hub hash). Snapshots every 50 operations (the live store is re-based onto the snapshot, so reload = snapshot + replay).
- M: **rs design operations (M implements in `semio/client/lib/rs/lib.rs`, golden names only).** The MCP tools need the design commands that are `not_implemented` today, so M implements them end to end (GraphQL resolver → `Operation` variant → `to_diff`/`to_backwards` → `Kit::apply_diff` → wire JSON): `DesignOperationInput.addChildPieceWithParentConnection` (+ optional `id`/`connectionId` args, piece is linked/unplaced), `deletePiece`/`deletePieces`/`deletePiecesAndConnections` (removing a piece also removes its connections), `PieceOperationInput.move(position)`/`rename(newName)`/`changeDescription(newDescription)`, plus one new golden-style command `DesignOperationInput.connectPieces(id, parentPieceId, parentConnector, childPieceId, childConnector, gap, shift, rise, rotation, turn, tilt, u, v, description): Response!` and `deleteConnections(ids)`; `DesignDiff` gains a `connections` collection diff. `addFixedPiece` will resolve the real blueprint (existing type/design id) instead of minting a placeholder type. F2 keeps the `id` args on `create*`/`addFixedPiece`; M edits only the design/piece command resolvers and the design/connection operation arms (re-reads before each edit). `parentConnector`/`childConnector` accept a connector id or connector name.
