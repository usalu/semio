## Developer Operations

Start `repo dashboard` at the monorepo root. Choose **New Task** (`Ctrl+B n`),
search by action and owner, complete the command form and choose **Start**. The
[dashboard guide](🔨️modules/🎛️dashboard/README.md#-daily-work) gives concrete
setup, testing, debugging, source navigation and repository workflows. Every
command uses the workspace daemon, so its status, output and cancellation remain
available after closing a view or restarting an editor.

Editor integrations provide source navigation and language editing. Executable
commands are maintained in owner dashboard metadata or Nx targets and selected
in the dashboard.

Repo-wide settings live in [`.🧬semio/🦑️repo/config.toml`](../.🧬semio/🦑️repo/config.toml) at the monorepo root.

| `logging.operations` | `true`     | Append derived `agent.<operation>.<phase>` events (requires `session = true`)      |

Set `logging.session = true` to enable session-file logging for debugging or coordinator ingestion.

# 🏗️ Build and run

`repo` is the only build entry. It is tool-neutral: every project target is declared once in a `📋️project.json`, a neutral graph describes all projects and targets, and two interchangeable implementations execute them: **Nx with Bun** (default) and **Bazel** (`--tool=bazel`). Never call `nx`, `bunx nx`, `npx nx`, `bazel`, raw `cargo` or `rustc` yourself. This is the rule of `AGENTS.md` that external tools sit behind a tool-independent interface and that the `repo` entry runs every command: `repo` is that interface for Nx, Bazel and Cargo. Paths that start with `📚️library/` are below `🔨️modules/` of this product. A German version of this chapter follows its last section.

```bash
repo run <project>:<target>[:<configuration>]       # one task; add --tool=bazel for the Bazel implementation
repo run-many --targets=<targets> [--projects=<projects>]
repo affected --targets=<targets>                    # projects that changed against HEAD, plus their dependents
repo exec --projects=<projects> -- <command>         # a command once per project, project root as working directory
repo run <project>:<target> --dry-run                # print the task graph, run nothing
repo show projects|project <name>|targets            # the neutral graph (also: repo graph)
repo cache status|clear                              # task cache of the selected tool
repo tools setup [nx|bazel|all]                      # provision the pinned build tools for this host
repo dependencies sync --all                         # install dependencies (--scope <owner> for one owner)
repo dependencies lock --all                         # regenerate bun.lock after a manifest edit
repo cargo --store=shared --configuration=prototype -- check -p <crate> --lib
```

- **Help.** `repo --help` prints every command and every flag; `repo <command> --help` (also with a subcommand, for example `cache clear --help`) prints that command's own usage, options and examples. The text is rendered from the operation catalogue in English or German: `--lang=en|de`, then `SEMIO_LANGUAGE`, then the locale (`LC_ALL`, `LC_MESSAGES`, `LANG`), then the first language of the catalogue. Help is answered before any tool or store starts.
- **Dependencies.** `dependencies sync` installs into the dependencies partition (`node_modules` at the root is a symlink into it). Any `package.json` or `bun.lock` edit makes the installed generation stale: run `dependencies lock --all`, then `dependencies sync --all` once, never an ad-hoc `bun install`. Before it installs, a sync retires every `j/<20 hex>` dependency generation that is neither a current plan generation nor the target of a live binding (progress `dependencies:retire-obsolete:<n>`). On macOS 27 the installer can fail with `EPERM: Operation not permitted: failed to link package`; see item 7 of Recovery, the sync repairs that case itself. A workspace package created after the last sync (a new `package.json`) cannot be resolved until `dependencies lock --all` and `dependencies sync --all` ran; every route that imports it fails with `Cannot find module` until then (seen on 2026-10-20 with a new framework package, which stopped the `verify` routes and the documentation-law tests). Sync cost: the verification passes were quadratic in the number of bindings. The installed-paths scan now compares a directory with itself when it closes instead of re-reading every ancestor of every entry (progress frames every `scanProgressWorkUnits` = 4,096 work units), the publisher re-checks only the strict ancestors of an endpoint's parent (`javascriptDependencyStrictAncestorsV1`), each published binding gets a 12-`lstat` endpoint fence (`requireJavascriptDependencyEndpointFenceV1`), and the complete fence runs every `fullFenceInterval` = 32 bindings and after the last one (constants in `📚️library/⚡️caching/🚀️bootstrap/📦️dependencies/💾️storage/🧬️schema/📥️install.json`). Measured on the primary host at load 31 to 52: the scan of one 84,345-entry generation fell from 168 to 302 s to 48 to 64 s, and the last green `dependencies sync --all` (2026-10-20 05:43) took about 31 minutes, where an earlier attempt ran 7,000 s without finishing. Leave the tree alone while a sync runs: a peer edit of a provider file during the walk failed one attempt with `Declared execution physical observation changed`. The suites that pin these fences are the targets `repo:test-javascript-installed-paths`, `repo:test-javascript-endpoint-fence` and `repo:test-javascript-provider-walk` (project `repo`, directory `⚡️caching`). Recorded on 2026-10-20 on the live tree under an issued envelope: the endpoint-fence suite passed (5 tests), the provider-walk suite failed its table test on the row `provider-relinked-in-first-replay` (expected refused; not diagnosed, open), and the installed-paths suite could not load because the installed generation predates the package `@semio-tech/framework-filesystem` that it imports.
- **Dependency generation receipt.** Every `repo` task or graph call first proves that the installed dependencies still match their sources. That proof used to be a complete walk of the workspace (eight directory-tree passes of about 617,000 operations and four provider walks per command, 36 to 58 s per tree pass under load). It is now a sealed receipt per dependency scope, checked cheapest tier first (`Protocol.tiers` in `📚️library/⚡️caching/🚀️bootstrap/📦️dependencies/🧾️generation/🧬️schema/🔣️.json`): `implementation` (content digest of every file in the runtime import closure of the walk and fence entries, read with `captureBuildSourceClosureV1`; 175 files, 2.1 MB on the measured tree), `runtime` (Bun and Node versions, Bun revision, platform, installer recipe), `producer` (the `.npmrc` and `bunfig.toml` files an installer level could read, and the `BUN_*`, `NPM_CONFIG_*`, proxy and certificate variables, by name and value digest only), `bindings`, `inputs` (manifests, lock, bunfig, patches), `membership` (every walked directory by stamp; a directory younger than 5 s is listed again and compared by projection digest) and `execution` (every physical observation the provider walk made, replayed). Any difference is a typed mismatch (`Protocol.mismatchClasses`) and the command falls back to the complete walk, which then passes or throws exactly as before. Receipts and their evidence are content-addressed files in `.cache/b/d/m/generation`; verification runs under the caller's shared store custody and publishes progress `dependencies:generation-verify:<n>`. Only an `inspect` with exclusive custody and the end of a `dependencies sync` publish a receipt (`publishJavascriptDependencyGenerationReceiptsElseV1`; best effort, a failure prints `[DATA]` and never fails the sync), and a capture defers while any closure file is younger than the process start minus 5 s, so a receipt only vouches for code that ran. Consequence: an edit of any file of the closure (126 of the 175 are process modules) costs the next command one complete walk. Measured read-only on the primary host at load 56 to 65: a complete receipt verifies in 3.6 to 12 s against 36 to 58 s for one tree pass; the closure and producer tiers add about 10 ms. Not yet verified: on 2026-10-20 the generation directory held three zero-byte `*.frontier.ndjson` files and no sealed receipt, so no live run has published and then verified one; Linux, Windows and the devcontainer were not run.
- **Waiting for a store.** A cache image and other shared resources are claimed through a queue (`acquireQueuedResourceLease`, resource `native-fixed-image:<partition path>`): tickets are served in arrival order, a shared ticket joins a cohort only when every earlier ticket is a shared cohort ticket, so a writer is not starved by readers that arrive after it, and a waiter reaps only its immediate predecessor when that process is dead. Waiters poll from 250 ms to at most 1,000 ms (factor 3/2) and sweep at most once per second (`🧰️framework/🔨️modules/🏃️process/🔒️leases/⏳️wait/🧬️schema/📜️policy.json`); with 14 waiters behind one holder for 15 s their CPU time fell from 15.2 s to 2.2 s. A waiter at position 2 or later publishes every 15 s a `lease-queue` progress line, shown in English or German, for example `Waiting for access to native-fixed-image:<path> (shared): position 3 of 15, behind the request of process 12528 (exclusive, queued 8040 s ago)`: the pid names the holder. A line `<command> remains active on dependencies:store-ownership:state:<N> (exclusive, <s> s)` is the generic progress line of a running walk (N counts work), not a wait. `upgradeQueuedResourceLease` turns a held queued shared lease into an exclusive one at its original queue position and consumes the shared hold; asking exclusively for a resource the same process already holds shared still waits for itself until the timeout. The raw `acquireResourceLease` (polling SQLite) is not queued and prefers readers, so mixing it with queued requesters can starve a queued writer; image paths use the queue unless `maximumLeaseDatabaseBytes` is set, and whether the raw primitive should prefer writers is an open owner decision. A single `repo run` that holds an image exclusively for hours (a store ownership walk after a dependency generation change) blocks every other command on that image: read the head ticket before restarting a sync. The target `test-resource-lease-fairness` of `@semio-tech/framework-process` runs the fixture-driven suite (queued Bun and Node clients against a queued writer, Python `sqlite3` readers as the independent client, dead predecessors, CPU cost, progress text, upgrade rules). Recorded: a plain `bun test` of the fairness file on the live tree on 2026-10-20 passed 10 of 11 tests; the failing case (`python-readers-queued-writer`, a timing case against Python readers) passed when run alone, so it is load sensitive. Not yet verified through `repo run`: the first check after the suite was applied (2026-10-20 05:05) is recorded as failed and was not repeated through the runner.
- **Cargo.** Raw `cargo` and `rustc` are refused by the compiler ingress gate in `.cargo/config.toml`. Compile through `repo cargo --store=shared|isolated --configuration=prototype|release [--parallelism=<cores>] -- <cargo subcommand> <args>`; `--store` and `--configuration` are mandatory and the Cargo subcommand follows `--`; without `--manifest-path` Cargo reads the `Cargo.toml` of the working directory (the root workspace when called from the root; `🏃️process/🦀️cargo/🚪️launcher`). Never create a private `CARGO_TARGET_DIR`: the shared store is a fixed-capacity partition and parallel private targets exhaust the disk. Before Cargo starts, `repo cargo` admits the Source of every compilation unit. The store-custody recheck inside that admission is throttled to one per 15 s (`storageRecheckGateV1`; `storageRecheck.intervalMilliseconds` in the admission schema; the first call and the completion call always recheck), and `rustc --print cfg` is computed once per exact argument vector; on a real image at load about 55 an admission unit with 12 reads dropped from 12.3 s to 3.0 s. A compile that finds the Rust image below the compiler charge (4 GiB) frees space through the recovery in `📚️library/⚡️caching/💾️storage/🔒️enforcement/🏗️compiler/📏️capacity/♻️recovery`, which compares the invocation identity of the control (`requireIssuedResourceControlInvocationV1`), not its signal. After a refactor that touches many crates, run small `repo cargo` invocations one after the other, never beside a dependency sync or a graph inference (all three take long store leases); the resumable plan that sequenced the 2026-10-20 recompile window (205 required steps over 644 crates, at most 8 `-p` packages each) is a tool of the coordination ticket, not a `repo` command. Not yet verified: when this was written that window had only started its first lock-refresh step, so the value-family, proctor and activation-closure compiles are still unproven.
- **Zero-touch.** The build CLI must boot on a fresh clone with no `node_modules`, no installed tool and no cache image, because the dependencies live inside a cache partition the CLI itself creates. Everything in the CLI import closure (`📚️library/🏗️build/📜️script.ts`) therefore imports by relative path, never through a bare `@semio-tech/*` specifier, and the `dependencies` command and the environment bootstrap run before the dependencies partition is pinned. After editing a library module, check `repo --help`: it must print the usage line. The same bootstrap must work unchanged in the devcontainer, native Windows, native macOS and native Linux (see Setup per platform below). The law `bun ./📜️script.ts verify zero-touch` keeps that closure honest (see Build owner registry).
- **Cancellation and progress.** The catalogue below declares every operation cancellable (`cancellable`) and every operation except `graph` and `show` as reporting progress (`progress`) in `📚️library/🏗️build/⚙️operations/🔣️catalog.json`; the implementations pass the caller's process control to every path (`runOwnedBuildInLeasesV1` in `📚️library/🏗️build/📜️script.ts`). Not yet verified: no per-operation cancellation run has been recorded.

## 🧭️ Neutral model

| Layer | What it is | Source |
|---|---|---|
| Manifest | One `📋️project.json` per project: targets with executor, command, inputs, outputs, `cache`, `continuous`, `dependsOn`. | schema `📚️library/🏗️build/🧬️schema/📋️project/🔣️.json` |
| Policy | `defaultTool`, the named input groups (`default`, `production`, `sharedGlobals`, `cargo`, `go`, `uv`, `dotnet`, `schemaSources`, `nativeSources`, `nativeTestSources`) and the files that may change the graph. | `📚️library/🏗️build/🔣️policy.json` |
| Graph | `BuildGraphV1`: projects, targets and dependency edges inferred in TypeScript from the manifests, Cargo, Go, `package.json` and `bun.lock`; independent of Nx. Snapshots live in the graph partition `g`. `show` and `graph` print it. | `📚️library/🏗️build/🕸️graph` |
| Operations | The catalogue of operations, which tool implements each one how, and the JSON shapes their results must have. | `📚️library/🏗️build/⚙️operations/🔣️catalog.json`, schema `⚙️operations/🧬️schema/🔣️.json` |
| Implementations | Nx adapter and Bazel adapter; each one only translates the neutral request into its tool. | Sections Nx implementation and Bazel implementation below. |

**Tool selection.** `--tool=nx|bazel` on the command line wins, then the environment variable `SEMIO_BUILD_TOOL`, then `defaultTool` of the policy (`nx`). The selected tool is exported as `SEMIO_BUILD_TOOL` to every nested task, so a task that calls `repo` again keeps the tool; the dashboard axis `build-tool` sets the same variable (see Command registry). Anything else is refused ("Unknown build tool"). Choose the compiler configuration with `--configuration=prototype|release` (or `-c`, a `:<configuration>` suffix on the task, or `SEMIO_BUILD_MODE`); disagreeing values are refused ("Conflicting build modes").

**Operations.** The state of each operation per tool: `native` = the tool's own command, `adapter` = our code drives the tool, `neutral` = tool independent, `missing` = not implemented and the call refuses.

| Operation | Nx | Bazel | `--dry-run` | Notes |
|---|---|---|---|---|
| `run <project:target[:configuration]>` | native | adapter | yes | A dry run executes nothing. |
| `run-many --targets=… [--projects=…]` | native | adapter | yes | |
| `affected --targets=…` | native | adapter | yes | Changed files are the tracked changes against `HEAD` plus untracked files; `--base`/`--head`, `--files`, `--uncommitted`, `--untracked` narrow them and `--all` selects every project. Affected projects (the same rule for both tools, asserted against Nx's own locators): the deepest project root that owns a changed file, projects whose target inputs name a changed `{workspaceRoot}/…` file, every project when `nx.json` changes, then all dependents. `--projects` is refused for every tool; use `run-many` to narrow. |
| `exec --projects=… -- <command>` | native | adapter | yes | Once per selected project, working directory is the project root, and the tool-neutral pair `SEMIO_PROJECT_NAME` (project name) and `SEMIO_PROJECT_ROOT` (project root relative to the workspace) is exported by both tools; the Nx implementation maps the names its own `exec` exports (see Nx implementation). Under Bazel each project gets an uncached `repo-exec` task. `--dry-run` prints the `repo-exec` plan and runs nothing. |
| `watch --projects=… -- <command>` | neutral | neutral | no | Reruns the command when selected source files change. |
| `graph`, `show projects\|project <name>\|targets` | neutral | neutral | no | |
| `reset` | adapter | adapter | no | Nx: invalidates the graph and runs `nx reset`. Bazel: invalidates the graph and empties `bazel/actions` (the disk cache), `bazel/outputs` and `bazel/workspaces` of the products partition. |
| `tools setup [nx\|bazel\|all]` | adapter | adapter | no | Without an argument the selected tool is set up (`--tool`, default `nx`). See Setup per platform below. |
| `preflight` | neutral | neutral | no | Checks the host before any store is provisioned, from `📚️library/🏗️build/🩺️preflight/🔣️policy.json`: CPU architecture, 8 GiB free, required tools (`cc` and `pkg-config` on Linux, `cc` and `hdiutil` on macOS) and, on Linux, atomic directory exchange (`renameat2` `RENAME_EXCHANGE`) on a case-sensitive workspace file system. |
| `dependencies sync\|lock --all\|--scope <owner>` | neutral | neutral | no | |
| `cargo …` | neutral | neutral | no | |
| `cache status\|clear` | adapter | adapter | no | Nx: the artifact directory of the rust partition. Bazel: the disk cache of the products partition. See the two implementation sections. |

**Flags.** Flags before `--` are portable and validated before any tool starts; an unknown flag, a stray positional argument or an invalid selector is refused. Everything after `--` is passed literally to the task. The flag list is part of the catalogue and is printed by `repo --help`; the task commands (`run`, `run-many`, `affected`, `exec`, `watch`) accept all flags of the table, but a flag only has an effect where the last column names its command.

| Flag | Meaning | Commands |
|---|---|---|
| `--tool=nx\|bazel` | Select the implementation (otherwise `SEMIO_BUILD_TOOL`, then the policy default). | all |
| `--help`, `-h`; `--lang=en\|de` | Print the usage of the command in English or German and stop. | all |
| `--projects`, `-p`, `--exclude` | Comma lists of project names with `*` wildcards, `tag:<tag>`, `name:<name>`, `directory:<root>`, `!<pattern>` negation. | `run-many`, `exec`, `watch`; `--exclude` also `affected` |
| `--targets`, `--target`, `-t` | Target names or `*` patterns. | `run-many`, `affected` |
| `--configuration`, `-c` | Compiler configuration (`cargo` takes the full name only). | `run`, `run-many`, `affected`, `cargo` |
| `--parallel=<n>`, `--bail`, `--verbose`, `--output=stream\|stream-without-prefixes\|static` (alias `--output-style`) | Concurrency, stop at first failure, detail, output style. | `run`, `run-many`, `affected` |
| `--skip-cache`, `--skip-remote-cache`, `--exclude-dependencies` (alias `--exclude-task-dependencies`) | Ignore the task cache, ignore the remote cache, run only the named tasks. | `run`, `run-many`, `affected` |
| `--dry-run`, `--graph[=<file>]` | Print the task graph as a `DryRunPlan` on stdout and execute nothing. `--graph` is the same flag on both tools; with a file the plan is written there (Nx: the file as given, Bazel: a report whose path is printed). | `run`, `run-many`, `affected`, `exec` |
| `--all`, `--base`, `--head`, `--files`, `--uncommitted`, `--untracked` | Change selection (`--all`: every project). | `affected`; `--all` also `watch` and `dependencies` |
| `--include-global-files` | `watch` also reacts to files outside any project. | `watch` |
| `--file=<path>`, `--json` | Write the result as a report file; print lists as JSON. | `graph`, `show` |
| `--scope <owner>` | Restrict the operation to one dependency owner (instead of `--all`). | `dependencies` |
| `--store=shared\|isolated`, `--parallelism=<cores>` | Cargo target store and core count. | `cargo` |

**Result shapes.** Results that scripts consume are specified by the schema `⚙️operations/🧬️schema/🔣️.json`:

- `DryRunPlan`: `{"tasks":{"roots":[<id>],"tasks":{<id>:{"id":…,"target":{"project":…,"target":…,"configuration"?:…}}},"dependencies":{<id>:[<id>]},"continuousDependencies"?:{<id>:[<id>]}}}`. A task id is `<project>:<target>[:<configuration>]`; `exec` uses the target `repo-exec`. The Bazel plan adds `selected` (the requested task ids) and lists dependencies on continuous tasks apart in `continuousDependencies`, because those only have to be running.
- `CacheStatus`: `{"version":1,"tool","available","directory","entries","bytes","activity"?:{"builds","actions","executed","cacheHits"}}` (`activity` is filled by Bazel). `CacheClear`: `{"version":1,"tool","cleared","removedEntries","removedBytes"}`.

## 📋️ Manifests

A task in `targets` of a `📋️project.json` uses these fields:

| Field | Meaning |
|---|---|
| `executor` | `repo:script` (default, runs `command` through the repo process authority) or `repo:noop` (ordering only, runs nothing). |
| `command`, `options.command`, `options.commands`, `options.args` | What runs; `args` are literal arguments that are never shell-interpolated. `configurations.<name>` may override `command`, `commands`, `cwd`, `env`, `args`. `defaultConfiguration` names the configuration used when none is requested. |
| `dependsOn` | Tasks that must finish first: `"target"` (same project), `"^target"` (dependency projects), `"project:target"`, or `{target, projects, dependencies, params}`. |
| `inputs` | What the result depends on, see below. |
| `outputs` | Paths the task writes, relative tokens `{projectRoot}`, `{workspaceRoot}` and option tokens such as `{options.env.SEMIO_BUILD_MODE}`. `[]` means "no files to restore". |
| `cache` | Boolean, see the classes below. |
| `continuous` | The task is a long-running service. |
| `metadata.semio.dashboard.ready` | How readiness of a continuous task is detected: the output shows `http://(127.0.0.1\|localhost\|0.0.0.0):<port>` and that address answers 2xx or 3xx; `port` or `portEnv` declares the port, `path` appends a path, `printed` takes the whole printed address. |

**Inputs.** A list of file globs (`{projectRoot}/**/*`, `{workspaceRoot}/…`, `!` excludes), named groups from the policy (`default`, `production`, `cargo`, …), `^<group>` (the same group of the dependency projects), and objects: `{"env": "NAME"}`, `{"runtime": "<command>"}` (the command's output), `{"externalDependencies": [...]}` and `{"dependentTasksOutputFiles": "<glob>", "transitive": true|false}` (the outputs of the tasks in `dependsOn`). Declare everything the task reads that is not reachable from its own project: data outside the project, spawned test files, tool and toolchain files, environment. A project can add its own `namedInputs` (for example `reads`, `testEnv`, `cargoToolchain`). `default` of a project replaces the workspace `default`, so re-add `sharedGlobals` (platform, Bun version, `SEMIO_BUILD_MODE`) there.

**Command source closure.** A `repo:script` target needs no hand-written list of the modules its script imports. The graph inference derives the closure of the command script (`📚️library/🏗️build/🕸️graph/📥️inference/🧭️script-inputs`): relative imports, imports through workspace package specifiers such as `@semio-tech/process/leases` (`workspacePackageModuleV1`; installed registry packages stay covered by their locked external dependency), literal `new URL("…", import.meta.url)` targets that exist (modules are followed, other files are hashed as resources), and literal module inputs a target declares (for example `{projectRoot}/…/x.test.ts`). The closure joins the target as named inputs `commandSources…`; in the hash representation of the graph it is the marker `{"env": "SEMIO_SOURCE_CLOSURE_<sha256 of the manifest>"}` and the manifest sits in the graph store under `build-input-closures`, which Nx reads when it hashes the task. Cargo lock projections are markers of the same kind (`SEMIO_CARGO_LOCK_<key>`). Bazel expands the markers itself (see Bazel implementation). Deliberately not covered: in-source test imports guarded by `import.meta.vitest`, files read through `import.meta.dir` or joined string paths, and targets that are never cached (continuous, live). Measured on a sample of 49 project scripts the closure grew from a median of 489 to 1,200 files (about 28 percent more CPU for the derivation, offset by an admission memo that cut the old cost by 35 percent). Not yet verified: the assembled inputs in a real graph load (`repo show projects` was stopped on 2026-10-20 after 4 hours; the later analysis found it garbage-collection bound under host memory starvation, not quadratic in the closure code: a project costs 0.3 to 0.45 CPU-s, the closure derivation takes about 29 percent of that, and a clean run is estimated at 25 to 40 minutes), an Nx hash of a real task, and a Bazel run with expanded closures against the production entry.

**Cache classes.** `cache` is the switch both tools read. Next to it the inference attaches a machine-readable decision `metadata.semio.cache = {"version":1,"class":…,"reason":…}` to every target it forces, synthesizes or refuses to replay (closed schema `📚️library/🏗️build/🏃️execution/🧬️schema/💾️cache.json`). The class names the physical fact that allows or forbids a replay:

| Class | Reasons | Meaning | Cached |
|---|---|---|---|
| `deterministic` | `pure-function-of-inputs`, `check-without-outputs` | A pure function of its declared inputs; every declared output is a plain restorable tree, or there is none. | yes, the only replayable class |
| `driver-owned` | `freshness-owned-by-driver` | The command compiles through the build driver, whose Cargo freshness and stage cache are the authority (playground `prepare-*` and `build-*-react*`, `component`). | no |
| `managed-output` | `outputs-are-store-links`, `outputs-in-managed-store` | Outputs live in the leased products store behind a binding or manifest protocol (TypeScript artifact `build`, wasm slots) and the manifest does not author `cache: true`; restoring a copy would be refused or bypass the store. With `cache: true` the target is `deterministic` instead, because its receipt is the restorable output (see Store receipts). | no |
| `continuous` | `serves-until-stopped` | Runs until stopped. | no |
| `side-effecting` | `publishes-live-state`, `publishes-remote`, `mutates-workspace` | Mutates state outside its declared outputs. | no |
| `live` | `drives-running-process` | Observes or drives a running process (names with `e2e` or `live`). | no |
| `aggregate` | `orders-prerequisites` | Orders prerequisites and does no work of its own. | no |
| `diagnostic` | `admission-refusal`, `measures-environment` | Reports a refusal or a measurement and is always re-evaluated. | no |

The Bazel adapter reads the decision (`bazelTargetCacheClassV1` validates it against the closed schema and refuses an invalid one with "Closed repository cache decision required") and derives its cache decision from the class, see the Bazel cache decision below. The Nx projection does not read it; Nx decides from `cache`, `continuous` and `outputs`. A manifest does not write it; the synthesized playground targets, the TypeScript artifact `test`, `check` and (with `cache: true`) `build` targets, and the wasm slot producers with `cache: true` carry `deterministic`, targets cached by the name rules below carry none. The policy that sets `cache` and the decision follows this order, the first matching row wins (`📚️library/🏗️build/🕸️graph/📥️inference/🎯️target-policy`, names from `📚️library/⚡️caching/🔣️policy.json`):

| Order | Rule | Cached | Decision attached |
|---|---|---|---|
| 1 | `continuous: true`, or a name `dev`, `serve`, `watch`, `start`, `test-watch`, `daemon` (also `<name>-…`) | no | `continuous` |
| 2 | `cache: false` in the manifest | no | none |
| 3 | A name of the `uncached` list (`audit`, `bench`, `clean`, `deploy`, `deps`, `install`, `publish`, `seed`, `setup`, `test-e2e`, `update`, …) or an exact name (`format`, `commit`, `os`, `parity`, …); `cache: true` is overridden | no | `live` (`e2e`, `live`, `os`, `semio`), `diagnostic` (`audit`, `bench`, `doctor`, `parity`, …), `side-effecting` (`publish`, `deploy` as `publishes-remote`, otherwise `mutates-workspace`) |
| 4 | `hub-live-catalog-check`, `hub-live-catalog-native-check`, `hub-live-catalog-oracle` | yes | none (exceptions to row 5) |
| 5 | A dash-separated word `clean`, `gc`, `prune`, `setup`, `fuzz`, `e2e` or `live` in the name | no | as row 3 |
| 6 | A deterministic family: `test`, `check`, `lint`, `typecheck`, `format-check`, `generate`, `schema`, `verify`, `build`, `wasm`, `native-build`, `package`, `*-contract`, … | yes | none; default inputs `default` and `^default`, outputs `[]` unless the manifest says otherwise |
| 7 | Anything else | **yes** unless `cache: false` | none |

Row 7 is fail-open under Nx (Bazel additionally requires an `outputs` array and a class that allows replay, see its cache decision): a target that touches host state and says nothing is cached, and a cache hit then skips its effect. Write `cache: false` for these reasons (the convention across the manifests, mirrored by the classes above): tests that exercise real storage, lease, process or toolchain state; live host, browser or server runs; writers that rewrite the tree or a store outside their declared outputs; launchers of long-lived tools; network downloads; steps whose input set is unbounded (digests of the whole workspace).

**Store receipts.** Products that are published into a leased, content-addressed store instead of the project directory (Cargo artifacts in the compiler store, Vite sites, wasm packages, TypeScript artifacts) cannot be restored by copying files into that store from outside. They declare a receipt as their only output, `{projectRoot}/.🧾️store/<target>.json` (schema `📚️library/🏗️build/🧾️store-receipt/🧬️schema/🔣️.json`, git-ignored, deliberately not below `dist`, which is a link into the store for TypeScript artifacts). The receipt names each published store path (`entries`: kind, bytes, files, SHA-256; a directory digest hashes its sorted file list) and each link that binds a project path to a store path (`links`). The central publishers write it after publication, so no build script changes: the artifact destination that the Vite and wasm publishers write through (`⚡️caching/📦️artifacts/🟦️.ts`), the compiler store publisher of Cargo `build` (`⚡️caching/📦️artifacts/🏗️native-build/🟦️.ts`, skipped when an observation output is requested) and the TypeScript artifact binder (`⚡️caching/📦️artifacts/🟦️typescript/🔗️binding/🟦️.ts`). Both adapters hand the receipt location to the one task that declares it (`SEMIO_TASK_RECEIPT`, issued by `issueStoreReceiptV1` in `📚️library/🏗️build/🧾️store-receipt/🟨️.mjs`; Nx: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/🟨️.mjs`, Bazel: `executeTask` in `📚️library/🏗️build/🔧️tools/🏗️bazel/📜️script.ts`); every other task has it unset, so a nested task never records into its parent's receipt, and a publisher does nothing without it (`recordStoreContentV1`).

After every `run` or `run-many`, both tools verify the receipt of each selected task and of its prerequisites. A receipt that is absent, damaged or points at a missing or changed store entry counts as a miss: that one task reruns alone and uncached (Nx: `run <task> --skip-nx-cache --excludeTaskDependencies`, the one extra child selection the caller admits, which also replaces the cache entry; Bazel: in-process with `skipCache` and without dependencies, which leaves the stale disk-cache entry in place, so a later hit repairs again) and is verified again, and the invocation fails closed otherwise. A failed first run is retried once after the repair. A task that declares a receipt but whose handler wrote none is an error, not silently accepted. TypeScript artifact `build` and wasm slot producers carry the receipt as their output: they replay when the manifest authors `cache: true` (decision `deterministic`) and stay `managed-output` otherwise. A target declares a receipt only when its `outputs` list the receipt path (`declaredStoreReceiptV1`): `check`, `test` and `lint` publish a verdict, not store content, and `publish` and the course `build` list other outputs or none. Alternating `prototype` and `release` runs of one target share one receipt file (its path has no mode), so a switch is expected to rerun the target once (inferred from the path rule, not observed). Not yet verified: no run has exercised the repair path (first proof: run `@teaching/proctor:build` twice, delete the compiler `published/<hash>` slot, run again and expect one `[store-receipt] re-executing` line, with `--tool=nx` and `--tool=bazel`).

The Bazel implementation decides per action from `cache`, `continuous` and `outputs` and is stricter about missing declarations (see its cache decision below).

## 🔌️ Nx implementation

Nx is the default (`defaultTool`). The repository does not use Nx project discovery; it feeds the neutral graph into Nx.

- **Plugin.** `nx.json` registers the plugin `@repo/emoji-project-json` (`📚️library/🟨️.mjs`) for `📋️project.json`. Its `createNodesV2` publishes the neutral graph as Nx projects and its `createDependencies` publishes the neutral edges; it refuses edges whose projects it does not know. Each target is projected onto an Nx executor and receives a private engine identity as an additional input, so a change of the executing implementation invalidates cached results.
- **Executors.** `@semio-tech/repo-lib:command` and `@semio-tech/repo-lib:owner-command` (`📚️library/📦️packages/🟦️typescript/📋️executors.json`) `command` runs the literal command arguments through the original process authority and the Bun shell, `owner-command` forwards the literal argv to the native or process owner without shell interpolation (descriptions in `executors.json`); `repo:noop` becomes `nx:noop`.
- **Translation.** `--skip-cache` becomes `--skip-nx-cache`, `--exclude-dependencies` becomes `--excludeTaskDependencies`, `--output` becomes `--output-style`, `--bail` becomes `--nx-bail`, `--dry-run` and a bare `--graph` (or `--graph=true`) become `--graph=stdout`, `--graph=<file>` is kept. `exec` runs the command in a Bun wrapper that copies the names Nx's own `exec` exports (`NX_PROJECT_NAME`, `NX_PROJECT_ROOT_PATH`) to the neutral `SEMIO_PROJECT_NAME` and `SEMIO_PROJECT_ROOT`; the Nx names exist only in this implementation. `affected` without a selector adds `--base=HEAD`, `--uncommitted --untracked` becomes `--base=HEAD`, `--all` becomes `run-many`. `exec --dry-run` prints the neutral `repo-exec` plan and runs nothing.
- **Boundary.** Production code outside `⚡️caching/🚀️bootstrap` never loads an Nx module. It goes through the typed port `⚡️caching/🚀️bootstrap/🛠️tools/🔌️sdk`, whose closed catalogue names the 13 Nx modules the repository may touch. A test scans every production file under `🦑️repo/🔨️modules` with an own tokenizer and the TypeScript compiler as an independent oracle and requires zero offenders.
- **Cache location.** Nx task results live in `.🧬semio/🦑️repo/⚡️cache/rust/fixed/m/nx/artifacts` (`cacheDirectory` in `nx.json`; the rust partition, 16 GiB, which also holds the shared Cargo target and build directories of `.cargo/config.toml`). The separate partition `n` (`.cache/b/n`, 1.5 GiB) is the Nx pool: it holds the Nx graph cache as funded child images (`⚡️caching/💾️storage/🔒️enforcement/🔌️nx/📦️graph`), not the task results. `repo cache status` walks the artifact directory and prints `CacheStatus`; `cache clear` runs `nx reset --onlyCache` inside the bounded namespace and prints `CacheClear`.
- **Not yet verified.** The whole flow (a real cold run that fills `nx/artifacts`, then a warm run served from it) is scripted but has not been run at the time of writing; the unit and contract tests of the pieces above passed on 2026-10-19 (`⚡️caching/🚀️bootstrap/🛠️tools/⚙️operations`, `🔌️sdk`, `🔁️probe`, `🏗️build/🧭️selection`, `🏗️build/🧭️invocation`: 23 tests, 0 failures). On 2026-10-20 the link `.nx/installation` pointed to a tree under `.cache/b/t/m/nx` that no longer exists (only `.stage-copy-*` leftovers), so every Nx call needs `repo tools setup nx` first.

## 🏗️ Bazel implementation

`--tool=bazel` (or `SEMIO_BUILD_TOOL=bazel`) selects Bazel 8.4.2 (`.bazelversion`, pinned download per OS and CPU). The adapter is `📚️library/🏗️build/🔧️tools/🏗️bazel`. It turns the selected tasks into real Bazel actions, so Bazel's own action cache, disk cache, optional remote cache and lazy evaluation do the work.

- **Generated workspace.** For each distinct selection the adapter writes a workspace under `<products>/bazel/workspaces/<namespace>`: `MODULE.bazel`, a `BUILD.bazel` file, the rules in `tasks.bzl` (`repo_task`, `repo_launch`, `repo_noop`), a task manifest `<label>.json` and a fingerprint `<label>.input` per action, and `s`, a link to the real checkout (a junction on Windows). A task label is `t_` plus 16 hex digits of the SHA-256 of the task id.
- **Minimal builds.** Only the selected tasks and the tasks reachable through `dependsOn` become actions, and the build is `bazel build` of exactly the selected labels; pure ordering tasks (`repo:noop`) vanish behind their producers unless they are selected themselves. A target that is not needed is never analyzed or run.
- **Declared inputs.** The `inputs` of a cacheable task (named groups, `^` expansion, globs, `!` exclusions, `externalDependencies` as `bun.lock` and `package.json`, `dependentTasksOutputFiles` as the producers' outputs) are resolved against the files of the checkout and declared as Bazel inputs: the files reach the action through shared `filegroup`s of labels `s/<path>` instead of one list per task: a directory whose files are all selected is one group `d_<hash>` (a project root is one group, single-child chains collapse), pattern units with more than two members are shared composites `k_<hash>`, and each task gets one composite `i_<hash>` (`bazelSourceCoverV1`; names are ASCII, emoji appear only in file labels). On the static graph of 1,466 projects this cut `BUILD.bazel` from 317 MB to 65 MB and workspace generation from 351 s to 37 s. `glob()` was tried and rejected: with `.bazelignore` it matches nothing, and without it follows symlink loops and git-ignored trees that Nx never hashes. `^name` and `dependencies: true` reach the transitive dependency closure, as Nx hashes them (`bazelTaskInputsV1`); a `dependsOn` that names an absent project or target is refused when the plan is built (`requireBazelDependencyV1`, "Unknown build task dependency") and `bazelDanglingDependenciesV1` lists all of them at once. Paths Bazel cannot name as labels (label-unsafe names, directories, dangling links, anything below a nested `BUILD` package) are hashed into the fingerprint instead. The fingerprint also carries the host platform and CPU, the Bun version, the build mode, declared environment values and `runtime` command outputs. The action manifest is content-stable: it names the task and the executing implementation but no workspace, runtime or snapshot path; the live data sits in `runtime.json`, outside every key.
- **Command closures.** Closure markers (`SEMIO_SOURCE_CLOSURE_<key>`, `SEMIO_CARGO_LOCK_<key>`) are expanded to the files they name before a declaration or a fingerprint is built (`📚️library/🏗️build/🔧️tools/🏗️bazel/🔗️closure`): `bazelClosureMarkersForPlanV1` collects the markers a plan can reach (task inputs, `^` edges and `{input, projects}` references), the manifests are fetched by content address (`managedBazelClosureFetchV1` through the graph store reader of the Nx hasher; a filesystem variant for tests), validated against a closed schema, and names that are absolute or contain `..` are refused. A marker met without loaded manifests is an error, not an empty list. Before this, no closure file reached a Bazel action key, so editing an imported module left a task cached (measured on 2026-10-20 in a scratch run: 106 of 111 modules of one script and 162 of 169 of another were undeclared). Checked with the real Bazel 8.4.2 in the test of that component (`🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️closure`, 9 tests passed on the live tree on 2026-10-20): a rule over the expanded labels executes once, stays at once after a change outside the closure and executes again after a change to an imported module. Not yet verified: the production fetch under the Bazel storage lease, and the re-measurement of the undeclared modules after the change.
- **Source link and `.bazelignore`.** The generated workspace links the checkout as `s` (`linkBazelSourcesV1`) and writes no `.bazelignore`; it removes a stale one. An earlier adapter listed the link there so that `//...` would not follow it without end, and a scratch run on 2026-10-20 showed the price: `s` was missing from the execroot symlink forest, so Bazel could not stat the declared inputs after a non-sandboxed action and skipped uploading every result (`Skipping uploading outputs because of concurrent modifications`); the disk cache stayed empty and every warm run executed again. Without the ignore, `//...` would follow the link without end, so queries name the root package with `//:all` (every task rule lives in it; 0.4 s in the scratch run). The adapter change was applied on 2026-10-20 at 11:36. Not yet verified: a production `repo --tool=bazel run` that shows the disk cache filling and a warm hit under the corrected adapter; the table below was recorded without the `.bazelignore`; the first scratch runs, with it, cached nothing.
- **Declared outputs.** Each task has exactly one declared tree-artifact output `<label>.snapshot`. A consumer receives the snapshots of its producers (the transitive closure when its input says `transitive: true`) as inputs. After the build the snapshots of the selected tasks are restored into the checkout; intermediate snapshots are restored only inside the consuming action.
- **Cache decision (fail-closed).** Each action carries `cache` and, when it is uncached, a machine-readable reason; the Starlark rule fails without one and tags the action `no-cache`. The adapter decides in this order (`bazelCacheDecisionV1`):
  1. An explicit `cache: true` against a plugin class other than `deterministic` is a conflict and throws ("Conflicting cache declaration"), unless the task is a pure ordering task.
  2. `continuous` (a service) is uncached with reason `continuous`.
  3. `--skip-cache` is uncached with reason `skipped`.
  4. A pure ordering task (`repo:noop`) is always cacheable.
  5. A class other than `deterministic` (see Cache classes) is uncached with the class name as reason: `driver-owned`, `managed-output`, `side-effecting`, `live`, `aggregate`, `diagnostic`.
  6. `cache: false` in the manifest is `declared` and wins even against a `deterministic` class.
  7. No `cache: true` and no `deterministic` class is `undeclared`: the task reruns until it declares one.
  8. `cache: true` or a `deterministic` class without an `outputs` array is `unbounded`: a hit could not restore what it produced.
  9. Everything else is cacheable.

  So declare `outputs` (`[]` for pure checks) on every cacheable target. On the static graph of 2026-10-20, before the owners' fix, 809 targets in 278 projects declared `cache: true` without `outputs` and therefore ran uncached under Bazel with the reason `unbounded`; `bazelUncachedReportV1` (closed schema `UncachedReport`) groups them per owning project, and no CLI command prints that report yet. Continuous tasks become `repo_launch` actions that run with `bazel run`, are waited for by their readiness declaration and share the build's server.
- **Execution requirements.** Every task and launcher action is tagged `no-remote-exec` (the `repo_noop` marker writes a file and runs no process). Actions that carry `host_state` are also tagged `no-sandbox`; today that is every task and launcher action, only the `repo_noop` marker is sandboxable (`STARLARK_RULES` in `🏗️build/🔧️tools/🏗️bazel/📜️script.ts`; `Actions.kinds` in `🏗️build/🔧️tools/🏗️bazel/🧬️schema/🔣️.json`). The two reasons the schema records (`ActionPolicy.kinds`): a *task* action runs the task process in the real checkout, with its working directory, declared source-tree and shared-store writes, the loopback control socket and the out-of-tree runtime channel, which a sandbox would hide or block; a *launcher* action binds exact execroot output paths and obtains authority over the invocation's control socket, which a sandbox execroot would change. Consequence: results are keyed by the declared inputs and fingerprint, not by what a sandbox observed, so a missing input declaration shows up as a stale hit, not as a failure. The repository `.bazelrc` sets no `--spawn_strategy`, `--sandbox_*` or `--strategy` flag today (the test "the repository .bazelrc carries exactly the authored static cache policy and no host paths" in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🧪️tests` pins its cache lines and rejects host paths, but nothing forbids a sandbox flag), so any action that is ever declared without `host_state` runs in Bazel's default sandbox.
- **Sandbox and host paths.** Bazel 8.4.2 on macOS handles non-ASCII paths of its own state incorrectly, in two places found by experiment: an emoji or accented `--install_base` crashes the server at startup ("Could not find or load main class"), and the `darwin-sandbox` profile is written from Bazel's byte-wise path strings but encodes each byte as UTF-8 a second time, so the write rules for a non-ASCII `--output_base` never match and every sandboxed action (including its `stats.out`) fails with "Operation not permitted". It looks location dependent only because `/private/tmp`, `/private/var/tmp`, `TMPDIR` and `~/Library/Caches` are allow-listed for any spelling. The production layout keeps the `install` base, the `outputs` root and the `server` output bases (`<products>/bazel/outputs/server/<hash>`) inside the native partitions below `.cache/b`, which is ASCII whenever the checkout path is ASCII (for example `/Users/<name>/Documents/semio`), and `requireBazelHostPathsV1` (called by `bazelCacheLayoutV1` in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🟦️.ts`, which every Bazel storage user builds) refuses a layout whose `install`, `outputs` or `server` path contains a non-ASCII character on darwin ("ASCII Bazel host path required on darwin: outputs"), at layout time instead of during a build. So keep the checkout path ASCII on macOS. `--sandbox_base` is not used. A sandboxed action can only write inside its execroot, the temp directories and `~/Library/{Caches,Logs,Developer}`; if a task that writes into the checkout or a partition is ever sandboxed it needs `--sandbox_writable_path=<ASCII path>`, which goes through the same encoder and so must be ASCII too. Linux was examined on 2026-10-20 (Bazel 8.4.2 linux/arm64 in an unprivileged container): a non-ASCII `--install_base` crashes the server there too ("Could not find or load main class", exit code 37) under every locale tried (unset, POSIX, C, C.UTF-8, en_US.UTF-8), so `requireBazelHostPathsV1` refuses a non-ASCII `install` path on Linux ("ASCII Bazel host path required on linux: install", `HostPaths.platforms.linux.guarded`), whereas a non-ASCII output base builds and caches on Linux and is not refused. Windows is covered by the readiness refusal for non-ASCII workspace and partition paths.
- **Emoji source labels.** Task sources are labelled `s/<path>` (`bazelSourceLabelV1`): the file reached through the `s` link, a target name inside the root package. Observed with the pinned 8.4.2 (the real-binary test in `🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️actions` replays the fixture names and is skipped without `SEMIO_TEST_BAZEL_BINARY`): Bazel accepts any non-ASCII character in a target name, including astral emoji, ZWJ sequences, skin tones, combining marks, CJK and a no-break space, also as action input and output names; only a backslash and control characters are rejected. Only package names must be ASCII, so the adapter never needs an emoji package; it treats a directory that holds `BUILD` or `BUILD.bazel` as a package boundary whatever its spelling and hashes everything below it (`bazelSourceClassesV1`). The adapter admits a path as a label when it matches `^(?:[A-Za-z0-9_@=,+~%./\-]|[^\u0000-\u007f])+$` (code point based, so it holds in Python, Rust and Go too) and hashes everything else (space, backslash, control characters, directories, dangling links, anything below a directory that holds `BUILD`) into the fingerprint instead. In a scratch experiment the Bazel disk cache and the cache keys were identical across `LANG=C` and a UTF-8 locale (no test covers it); the adapter sets a UTF-8 locale on darwin only (`LANG` and `LC_ALL` `en_US.UTF-8`, the `environment` of the darwin row of `PlatformRules`). On Linux arm64 the same emoji source, output and tree-artifact names built under every locale tried (unset, POSIX, C, C.UTF-8, en_US.UTF-8), so Linux needs no locale variable; Windows is `unverified` in the profile.
- **Disk cache.** `<products>/bazel/actions`, with garbage collection (`--experimental_disk_cache_gc_max_size` set to 40 percent of the products partition budget, aligned to MiB; `.bazelrc` adds `--experimental_disk_cache_gc_idle_delay=10s` and `--experimental_disk_cache_gc_max_age=30d`). Collection only runs inside a persistent server that has been idle (measured with Bazel 8.4.2: under `--batch` it never ran), so the adapter does not use `--batch` for builds. The repository contents cache keeps entries 3 days (`--repo_contents_cache_gc_max_age`). The module catalog and repository cache live in `<dependencies>/bazel/modules`; builds run with `--repository_disable_download`, so they never fetch modules.
- **Shared output base.** `--output_base` is `<products>/bazel/outputs/server/<first 16 hex of sha256(workspace directory)>`: one server per generated workspace directory (Bazel restarts a server that is moved between workspace directories), shared by the build and every `bazel run` of continuous tasks of that selection. The server idles out after 120 seconds. The disk cache is shared by all selections, which is what makes a second selection reuse the first one's results.
- **Remote cache.** Rendered from the tool-neutral remote cache contract (section "Remote cache"): `--remote_cache`, `--remote_instance_name`, `--[no]remote_upload_local_results`, `--[no]remote_cache_compression`, `--remote_download_outputs`, `--remote_timeout` and `--remote_retries`, and nothing while no endpoint is configured. `--skip-remote-cache` drops it for one invocation; `--skip-cache` adds `--noremote_accept_cached`. The adapter restores task snapshots from `bazel-bin`, so `minimal` downloads are refused. The access token never appears in a flag: a credential helper in the products `tmp` folder holds only the variable name and the token travels in the environment of the Bazel client (`--remote_header` would copy it into Bazel's `java.log` and build event stream).
- **Cache operations.** `repo --tool=bazel cache status` counts the files of the `ac` and `cas` folders of the disk cache and adds the recorded build activity (builds, actions, executed, cache hits), which each build appends to `<products>/bazel/outputs/server/metrics.json` from its build event stream. `cache clear` stops the persistent servers (by removing their pid file), removes their output bases (Bazel's local action cache) and empties the disk cache, so the next build is a miss; the Bazel binary, modules and toolchains stay.
- **Storage.** Bazel needs the tools, dependencies and products partitions (`bazel/bin` and `bazel/install` in tools, `bazel/modules` in dependencies, `bazel/workspaces`, `bazel/outputs`, `bazel/actions` in products). `repo --tool=bazel reset` invalidates the graph and empties `bazel/actions`, `bazel/outputs` (which holds the server output bases and the activity ledger) and `bazel/workspaces`; it does not stop a running Bazel server first, so run it when no build is active (`cache clear` stops them).
- **Platform profile.** Every platform-dependent decision of the adapter is one pure function of observed host facts, `bazelPlatformProfileV1` in `🏗️build/🔧️tools/🏗️bazel/🌐️platform` (rules and limits in `PlatformRules` of the Bazel schema; fixture `🧪️tests/📥️platform/🔣️.json`, 19 rows for darwin, linux, the devcontainer and win32 on x64 and arm64, including the refusals). Per platform it renders: the extra startup and command flags (`--nobuild_runfile_links` everywhere, because nothing runs `bazel run` and a runfiles symlink forest would need a symlink privilege on Windows; `--noenable_runfiles` and the startup option `--nowindows_enable_symlinks` on Windows, so the source link `s` is a junction and no developer mode or elevation is needed), the locale environment (`LANG`/`LC_ALL` `en_US.UTF-8` on darwin only), the launcher extension (`.exe` on Windows), the kind of the source link (`junction` on Windows) and the path budget `len(output base) + len(\execroot\_main\s\) + 256` in UTF-16 units against 259 (MAX_PATH) or, with `LongPathsEnabled`, 32766; a budget that does not fit, a Bun path that is not absolute (and `.exe` on Windows) and a devcontainer flag on a non-Linux host are refusals, thrown before Bazel starts. `--output_user_root` is gone: `--output_base` and `--install_base` are always explicit, so it was dead weight and (Windows) a second long path. Every action runs the Bun executable directly (`ctx.actions.run`, `executable = ctx.attr.bun`), never a shell, `genrule` or `run_shell`; the BUILD quotes the Bun path with `JSON.stringify`, which a real Bazel parses for a Windows path with backslashes. ## 🌐️ Remote cache

One schema-first contract (`🏗️build/🏃️execution/🧬️schema/🌐️remote-cache.json`, authored defaults in `🏗️build/🔣️policy.json`), two renderings and one server. The remote cache is off until an endpoint is set. The contract holds no secret.

| Variable | Contract field | Default |
|---|---|---|
| `SEMIO_REMOTE_CACHE_ENDPOINT` | `endpoint`: `http://` or `https://` origin | none (off) |
| `SEMIO_REMOTE_CACHE_INSTANCE` | `instance`: namespace, the first URL path segment | `main` |
| `SEMIO_REMOTE_CACHE_ACCESS` | `access`: `read-only` or `read-write` | `read-only` |
| `SEMIO_REMOTE_CACHE_UPLOAD` | `upload`: push local results (only effective with `read-write`) | `true` |
| `SEMIO_REMOTE_CACHE_COMPRESSION` | `compression` | `true` |
| `SEMIO_REMOTE_CACHE_DOWNLOAD` | `download`: `toplevel` or `all` | `toplevel` |
| `SEMIO_REMOTE_CACHE_TIMEOUT_SECONDS`, `SEMIO_REMOTE_CACHE_RETRIES` | `timeoutSeconds` (1-600), `retries` (0-10) | `30`, `3` |
| `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT` | `auth.tokenEnvironment`: name of the variable that holds the bearer token | `SEMIO_REMOTE_CACHE_TOKEN` |

- **Bazel** renders every field into the flags above and passes the token through a credential helper scoped to the cache host. **Nx** renders `endpoint/instance` into `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` and the token into `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`; Nx 23 has no switch for compression, download mode, timeouts, retries or withholding uploads, so read-only is enforced by a read-only token on the server. `bun repo cache remote status [--tool=nx|bazel]` prints the resolved contract, the rendering with its unsupported fields and a read-only probe of the route the tool uses.
- **Server.** `bun repo cache serve [--port <n>] [--host <address>] [--directory <path>] [--max-bytes <n>]` speaks Bazel's HTTP cache protocol (`GET`, `HEAD`, `PUT` on `/ac/<sha256>` and `/cas/<sha256>`, blobs verified against their digest, 400 on a mismatch) and the Nx self-hosted cache API (`GET`, `PUT` on `/v1/cache/<hash>`, 409 on overwrite, 401 with `text/plain`, 403 for a read token that writes), each under an optional `/<instance>` prefix. `/healthz` and `/status` are plain JSON. Bearer tokens come from `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` and `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; without a token it refuses to listen beyond loopback. The store (`.cache/remote-cache`, 4 GiB, 512 MiB per entry, 30 days idle by default) writes atomically, reserves bytes before streaming, evicts least recently used entries and publishes progress while it scans; cancelling the command stops the server. The dashboard tool `build-cache-serve` starts it on port 6090.
- **Tests.** `🏗️build/🌐️remote-cache/🧪️tests` replays the JSON fixtures (contract, renderings, wire scenarios, eviction) against Ajv, Python's `re` and `http.client` and `hashlib`; with `SEMIO_TEST_BAZEL_BINARY` a real Bazel builds against the server and hits the remote cache after `bazel clean`, and with `SEMIO_TEST_NX_BIN` (a pristine nx 23 install; the repository's patched Nx refuses to run in a scratch workspace) a real Nx does the same.

## 🪜️ Script entries

Commands that the build graph runs as `repo:script` start at the `📜️script.ts` of their module. The command-router law (`📚️library/🔍️discovery/🛣️ecma-command-routes`) accepts two shapes:

- **Router.** A class per command that extends `BundleScript`, a `ScriptRouter` that registers them and one terminal under `import.meta.main`. A thin entry keeps the process birth in the router and passes its own arguments on: `await receiveScriptProcessInvocation(process.env, original => runScriptMain(router, { invocation: original, argv: ["run"] }))`. The program parses its own `process.argv`; `argv` only names the registered command (`📚️library/⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/📜️script.ts`). The other accepted terminal is `router.run(process.argv.slice(2))` for routers that dispatch on the command line.
- **Bare entry.** `import { runScriptProgram } from "./🟦️.ts"; if (import.meta.main) await runScriptProgram();`, that is exactly one argument-free call of `runScriptProgram`, imported from a sibling `🟦️.ts`, under `import.meta.main` (`ecmaRouteOwnedProgram`). It is for programs that own their process birth and their exit code, in particular the child programs of tests under `🧪️tests` and `👷️child` (for example `📚️library/⚡️caching/🦀️cargo/📦️units/📥️descriptor/💾️cache/🧪️tests/📦️child/📜️script.ts`).

A router around everything does not work: a program that opens its own birth with `receiveScriptProcessInvocation` inside the router's birth cannot report after draining, and `track` in `🧰️framework/🔨️modules/🏃️process/🧭️routing/📥️invocation/🏃️process` copies every failing tracked operation into all ancestor scopes and closes their admission, so a failure that the program catches and reports still fails the outer birth (the lift repair measured exit 1 with the `custodian/cancel` child). A nested birth can never swallow a failure, so the program must be the outermost owner. The router-lift generators therefore emit the bare entry for scripts under `🧪️tests` and `👷️child` and the router with argument pass-through for all others (98 lifted scripts repaired on 2026-10-20: 74 router, 24 bare). Not yet verified: the lifted child suites under `repo run`; the `scope` suite still had four reds, the first from a `root-drain` admission that is identical with the pre-lift form.

## 🧰️ Setup per platform

`repo tools setup [nx|bazel|all]` provisions what the selected implementation needs, and `workspace:setup` depends on the target `deps-build-tools`, which runs `tools setup all` (next to the language environments it also prepares), so the devcontainer's `postCreateCommand` (`repo run workspace:setup`) and the native bootstrap scripts provision the build tools without a separate step.

- **`nx`**: installs the pinned Nx as an immutable toolset below `.cache/b/t/m/nx/<digest>`, points `.nx/installation` at it (a symlink, a junction on Windows) and checks `nx --version`.
- **`bazel`**: (1) checks the platform before any image is attached, (2) opens the tools, dependencies and products partitions, (3) downloads and verifies the pinned Bazel binary with progress lines (phase and every 10 percent), (4) prepares the Bazel module catalog and repository cache (offline-aware, cancellable), (5) prints `[bazel] ready binary=… modules=… lock=…` and a `[bazel] readiness {json}` line. A plain `--tool=bazel run` makes the same platform check.
- **`all`**: Bazel, then Nx.

| Host | Fixed cache images | What has to be true | Status |
|---|---|---|---|
| macOS (arm64, x64) | case-sensitive APFS disk images through `hdiutil` | Xcode Command Line Tools (the native bootstrap script prints the missing step). No privilege. The Bazel `install`, `outputs` and `server` paths (all below the checkout, so the checkout path itself) must be ASCII: the pinned Bazel crashes at startup on a non-ASCII install base, and its macOS sandbox profile mis-encodes a non-ASCII output base so that sandboxed actions fail with "Operation not permitted"; `requireBazelHostPathsV1` refuses such a layout. ## 💾️ Cache partitions

All build state lives in fixed-capacity partitions below `.cache/b/<partition>` (git-ignored, derived, safe to delete when nothing runs). On macOS each partition is a UDIF disk image formatted as case-sensitive APFS, `fixed.dmg`, mounted at `m` next to its `image.json` receipt (`ImageProtocol` fixes `UDIF` and `Case-sensitive APFS`; HFS+ was ruled out earlier because it lacks the atomic exchange `RENAME_SWAP` that publication and binding use, not re-checked here). Linux uses a directory-backed partition without any privilege (`fixed.dir`, `v`, `m`, switched by an atomic `renameat2(RENAME_EXCHANGE)`) and Windows a directory partition too, swapped by a journaled two-phase write-through rename instead of `renameat2` (implemented from source, not verified on those hosts; a swap fails with "A handle is still open inside the partition" while any process holds a file in it). The `hdiutil` steps below do not apply there: nothing is mounted, so stop all processes and remove the partition directory instead. Capacities come from `📚️library/⚡️caching/💾️storage/🔒️enforcement/📦️budget/🔣️policy.json`.

| Partition | Content | Capacity |
|---|---|---|
| `d` | dependencies, including `node_modules` generations | 8 GiB |
| `t` | tools: rustup, Bazel, Nx | 8 GiB |
| `g` | neutral build graph and inference records | 4 GiB |
| `o` | observations and diagnostics | 2 GiB |
| `p` | products: build outputs and published artifacts | 24 GiB |
| `l` | leases and locks | 64 MiB |
| `n` | Nx cache pool, namespaces are funded child images | 1.5 GiB |

`.cache/b/c` is the plain control directory (no image, at most 1 MiB; it holds the lease database of the images, `budget.controlDirectory`). The Rust target and build directories are a separate fixed partition at `.🧬semio/🦑️repo/⚡️cache/rust/fixed` (16 GiB). `bun ./📜️script.ts clean` never touches any of them, nor the `🗑️generated` folder of an open ticket.

**macOS volume silence.** macOS logs file system events of every mounted volume to `.fseventsd` and indexes it; on an image that only a build tool writes this fills the 63 MiB leases image and the small partitions. Each image therefore carries `.fseventsd/no_log` and `.metadata_never_index` (protocol constants in `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage/🍎️image/🤫️silence/🧬️schema/🔣️.json`). A write after mount does not work: with `-owners on` macOS creates `.fseventsd` as `root:staff 0700` with an ACL, and a log keeps growing until the volume is detached and attached again. So the images are created from a seed folder (`hdiutil create -format UDRW -srcfolder <seed> -size … -nospotlight` yields the same fixed image as `-type UDIF`, with the markers user-owned from the start), and `applyNativeImageVolumeSilenceV1` runs on attach and again whenever an already mounted image is opened: it creates the directory and the markers if they are missing and prunes logs (regular single-link files named by 16 hexadecimal digits, in batches of 64): every log on attach, and on open once more than 8 files or 1 MiB remain. A root-owned or symlinked `.fseventsd` and non-regular markers are refused with a remedy. A silenced volume has no FSEvents service, so the publication witness treats it as a volume without a service domain (`observeNativeVolumeEventServiceV1` returns `null`). Capacity: APFS holds 40,960 bytes less than the image, and 200 MiB less when the image is larger than 2 GiB (measured on 15 images from 32 MiB to 4,095 MiB), so every partition exposes `usableBytes` and for partitions up to 256 MiB the logical limit must fit it; that is why `leases.maximumLogicalBytes` is 62,914,560 of 67,108,864. Observed on 2026-10-20: the live images were mounted before their markers existed and macOS keeps logging until each partition is detached and attached again; after the open-time repair `.fseventsd` of `d`, `l` and `g` held 3, 5 and 1 entries (the dependencies image had held about 200 logs before), and every partition has `.metadata_never_index`. Not yet verified: a freshly created seeded image through the whole `tools setup` path, and the seeded creation on another macOS version.

### 🩹️ Recovery

Check items 1 to 6 before touching code when every `repo` call refuses at startup (the `hdiutil` commands are macOS only, see item 2 for Linux); item 7 concerns the dependency installer. Stop all `repo`, cargo and Nx processes first.

1. **"Pending Native image publication must settle"**: a killed run left `.cache/b/<partition>/.publication/intent.json`. Confirm no process is alive, move the file aside, rerun.
2. **Receipt or mount mismatch** ("Exact canonical persistent Native publication required", "Ambiguous Native backing kernel association", an `image.json` without its `fixed.dmg`): recreate the partition.
   ```bash
   hdiutil detach .cache/b/<partition>/m || umount -f .cache/b/<partition>/m   # diskutil may report it unmounted while it is not
   hdiutil info                                  # no image may still claim the path
   rm -rf .cache/b/<partition>
   repo --help && repo tools setup all   # the next call recreates it
   ```
   Never `mv` a partition directory while it is mounted: the image keeps its old path and the association becomes ambiguous. On Linux nothing is mounted: skip the `hdiutil` lines, confirm that `lsof +D .cache/b/<partition>` is empty (an atomic exchange succeeds even with open files, unlike `umount`) and remove the directory. A directory partition that `preflight` refuses ("Atomic directory exchange is unsupported by this kernel or filesystem", or a case-insensitive file system) cannot be repaired by recreating it: move `.cache` to a native case-sensitive file system, in the devcontainer onto its `.cache` volume.
3. **Nested attach "Permission denied"**: the parent was mounted `noowners`. With nothing open (`lsof +f -- .cache/b/<partition>/m` is empty) run `hdiutil detach` on the parent; the next call re-attaches with `-owners on`.
4. **Poisoned Nx pool** (every graph or Nx call fails "Exact original parent child allocation required"): `hdiutil detach .cache/b/n/m/<shard>/native/m`, then `rm -rf` the shard directory.
5. **ENOSPC in `d`**: empty `.cache/b/d/m/tmp` (installer leftovers), then rerun `dependencies sync --all`.
6. **Image created before the APFS switch** (ENOTSUP on rename): recreate it as in step 2.
7. **`dependencies sync` fails with `EPERM: Operation not permitted: failed to link package`** (macOS 27, observed on arm64): the kernel refuses to hard-link or clone files of the Bun package cache `.cache/b/d/m/bun-cache` that carry the `com.apple.provenance` attribute of another application identity or session, while files the current process created link fine (`ln` and `cp -c` of an old cache file give EPERM, a fresh copy links; `xattr -d` returns success but the attribute stays). The sync now handles it: it classifies that installer stderr as a cache link refusal, prints `[DATA] Store dependency cache link refused; purging the Bun package cache and retrying`, empties `bun-cache` in place (the directory keeps its identity; progress `dependencies:purge-bun-cache:<n>`), re-prepares the environment and retries the installer once per sync, so the retry re-downloads the packages it needs. If it still fails, empty `.cache/b/d/m/bun-cache` yourself with nothing running, or run the sync from the same application identity that populated the cache. Not yet verified end to end: the classifier, the generation selection and the tree removal are covered by fixture tests, but a full `dependencies sync` through the purge-and-retry path was not recorded.
8. **`.fseventsd` of a partition grows to hundreds of 16-digit log files, or a small image reports ENOSPC**: the volume was mounted before it was silenced. Any command that opens the partition prunes the residue. To stop the logging at its source, detach and attach the partition when nothing runs (macOS: the commands of item 2, then `repo --help`); a root-owned `.fseventsd` is refused by design and has to be removed with `sudo` by hand.

Recreating `d` costs one full `dependencies sync --all` (about 16 minutes with a warm package cache in the one recorded run on the primary macOS arm64 host, 2026-10-19), recreating `g` one cold graph inference (minutes; not timed for this documentation).

## 🐹️ Go layout

Go code follows the canonical taxonomy layout instead of package-root files:

- A member is a directory with one `🐹️.go` leaf: `<module>/📦️packages/🐹️go/<member>/🐹️.go`. The member name is registered in `📚️library/🔣️taxonomy.json` (`members-of-members-of-members-of-modules`).
- White-box tests are cases at the language-neutral owner: `<module>/🧪️tests/<case>/🐹️.go`, absorbed into the package when the package clause is the module's or `<package>_test`. Black-box adapters are never absorbed.
- Because files are not at the package root, plain `go test` and `go list` do not see the members. Run Go through the package `📜️script.ts` (`runCanonicalGoTests`) or `repo run <project>:test`, which pass the merged source overlay.

```bash
repo run-many --targets=<targets> [--projects=<projects>]
repo affected --targets=<targets>                    # Projekte, die sich gegenüber HEAD geändert haben, plus ihre Abhängigen
repo exec --projects=<projects> -- <command>         # ein Befehl je Projekt, Projektwurzel als Arbeitsverzeichnis
repo run <project>:<target> --dry-run                # Task-Graph ausgeben, nichts ausführen
repo show projects|project <name>|targets            # der neutrale Graph (auch: repo graph)
repo cache status|clear                              # Task-Cache des gewählten Werkzeugs
repo tools setup [nx|bazel|all]                      # die gepinnten Build-Werkzeuge für diesen Rechner einrichten
repo dependencies sync --all                         # Abhängigkeiten installieren (--scope <owner> für einen Eigentümer)
repo dependencies lock --all                         # bun.lock nach einer Manifest-Änderung neu erzeugen
repo cargo --store=shared --configuration=prototype -- check -p <crate> --lib
```

Der Text wird aus dem Operationskatalog auf Englisch oder Deutsch erzeugt: `--lang=en|de`, dann `SEMIO_LANGUAGE`, dann die Locale (`LC_ALL`, `LC_MESSAGES`, `LANG`), dann die erste Sprache des Katalogs. ### Manifeste

Felder einer Task: `executor` (`repo:script`, Standard, führt `command` über die Repo-Prozessautorität aus, oder `repo:noop`, nur Reihenfolge, führt nichts aus); `command`, `options.command`, `options.commands`, `options.args` (wörtliche Argumente, nie per Shell interpoliert) mit Überschreibungen je `configurations.<name>`; `dependsOn` (`"target"`, `"^target"`, `"project:target"` oder `{target, projects, dependencies, params}`); `inputs`; `outputs` (mit `{projectRoot}`, `{workspaceRoot}` und Option-Tokens wie `{options.env.SEMIO_BUILD_MODE}`; `[]` heißt „keine Dateien wiederherzustellen“); `cache`; `continuous`; `metadata.semio.dashboard.ready` (Bereitschaft: die Ausgabe zeigt `http://(127.0.0.1|localhost|0.0.0.0):<port>` und diese Adresse antwortet mit 2xx oder 3xx).

**Inputs.** Eine Liste aus Datei-Globs (`{projectRoot}/**/*`, `{workspaceRoot}/…`, `!` schließt aus), benannten Gruppen der Richtlinie, `^<gruppe>` (dieselbe Gruppe der Abhängigkeitsprojekte) und Objekten: `{"env": "NAME"}`, `{"runtime": "<command>"}`, `{"externalDependencies": […]}` und `{"dependentTasksOutputFiles": "<glob>", "transitive": true|false}`. Deklariere alles, was die Task liest und nicht aus dem eigenen Projekt erreichbar ist: Daten außerhalb, gestartete Testdateien, Werkzeug- und Toolchain-Dateien, Umgebung. Das `default` eines Projekts ersetzt das Workspace-`default`; füge `sharedGlobals` dort wieder hinzu.

**Quellabschluss eines Befehls.** Ein `repo:script`-Target braucht keine handgeschriebene Liste der Module, die sein Skript importiert. Die Graph-Inferenz leitet den Abschluss des Befehlsskripts ab (`📚️library/🏗️build/🕸️graph/📥️inference/🧭️script-inputs`): relative Importe, Importe über Workspace-Paket-Specifier wie `@semio-tech/process/leases` (`workspacePackageModuleV1`; installierte Registry-Pakete deckt weiter ihre gesperrte externe Abhängigkeit ab), wörtliche `new URL("…", import.meta.url)`-Ziele, die existieren (Module werden verfolgt, andere Dateien als Ressourcen gehasht), und wörtliche Modul-Inputs, die ein Target deklariert (etwa `{projectRoot}/…/x.test.ts`). Der Abschluss gehört als benannte Inputs `commandSources…` zum Target; in der Hash-Darstellung des Graphen ist er der Marker `{"env": "SEMIO_SOURCE_CLOSURE_<sha256 des Manifests>"}`, und das Manifest liegt im Graph-Store unter `build-input-closures`, das Nx beim Hashen der Task liest. Cargo-Lock-Projektionen sind Marker derselben Art (`SEMIO_CARGO_LOCK_<key>`). Bazel löst die Marker selbst auf (siehe Bazel-Implementierung). Bewusst nicht abgedeckt: Quelltext-Test-Importe hinter `import.meta.vitest`, Dateien, die über `import.meta.dir` oder zusammengesetzte Zeichenketten gelesen werden, und Targets, die nie gecacht werden (kontinuierlich, live). Gemessen an einer Stichprobe von 49 Projektskripten wuchs der Abschluss von im Median 489 auf 1.200 Dateien (etwa 28 Prozent mehr CPU für die Ableitung, ausgeglichen durch ein Zulassungs-Memo, das die alten Kosten um 35 Prozent senkte). Noch nicht verifiziert: die zusammengesetzten Inputs in einem echten Graph-Laden (`repo show projects` wurde am 2026-10-20 nach 4 Stunden gestoppt; die spätere Analyse fand es durch die Speicherbereinigung gebremst bei Speichermangel des Hosts, nicht quadratisch im Abschlusscode: Ein Projekt kostet 0,3 bis 0,45 CPU-s, die Ableitung des Abschlusses macht davon etwa 29 Prozent aus, ein sauberer Lauf wird auf 25 bis 40 Minuten geschätzt), ein Nx-Hash einer echten Task und ein Bazel-Lauf mit aufgelösten Abschlüssen über den Produktionseinstieg.

**Cache-Klassen.** `cache` ist der Schalter, den beide Werkzeuge lesen. Daneben hängt die Inferenz an jedes Target, das sie erzwingt, synthetisiert oder nicht wiederholt, eine maschinenlesbare Entscheidung `metadata.semio.cache = {"version":1,"class":…,"reason":…}` (geschlossenes Schema `📚️library/🏗️build/🏃️execution/🧬️schema/💾️cache.json`). Die Klasse nennt die physische Tatsache, die eine Wiedergabe erlaubt oder verbietet:

| Klasse | Gründe | Bedeutung | Gecacht |
|---|---|---|---|
| `deterministic` | `pure-function-of-inputs`, `check-without-outputs` | Reine Funktion der deklarierten Inputs; jeder deklarierte Output ist ein einfacher wiederherstellbarer Baum oder es gibt keinen. | ja, die einzige wiedergebbare Klasse |
| `driver-owned` | `freshness-owned-by-driver` | Der Befehl kompiliert über den Build-Treiber, dessen Cargo-Frische und Stage-Cache maßgeblich sind (Playground `prepare-*` und `build-*-react*`, `component`). | nein |
| `managed-output` | `outputs-are-store-links`, `outputs-in-managed-store` | Outputs liegen im geleasten Produkte-Store hinter einem Bindungs- oder Manifest-Protokoll (TypeScript-Artefakt-`build`, Wasm-Slots), und das Manifest schreibt kein `cache: true`; eine wiederhergestellte Kopie würde abgelehnt oder umginge den Store. Mit `cache: true` ist das Target stattdessen `deterministic`, weil sein Beleg der wiederherstellbare Output ist (siehe Store-Belege). | nein |
| `continuous` | `serves-until-stopped` | Läuft bis zum Stopp. | nein |
| `side-effecting` | `publishes-live-state`, `publishes-remote`, `mutates-workspace` | Verändert Zustand außerhalb der deklarierten Outputs. | nein |
| `live` | `drives-running-process` | Beobachtet oder steuert einen laufenden Prozess (Namen mit `e2e` oder `live`). | nein |
| `aggregate` | `orders-prerequisites` | Ordnet Voraussetzungen und leistet keine eigene Arbeit. | nein |
| `diagnostic` | `admission-refusal`, `measures-environment` | Meldet eine Ablehnung oder Messung und wird immer neu bewertet. | nein |

Der Bazel-Adapter liest die Entscheidung (`bazelTargetCacheClassV1` validiert sie gegen das geschlossene Schema und lehnt eine ungültige mit „Closed repository cache decision required“ ab) und leitet daraus seine Cache-Entscheidung ab, siehe unten. Die Nx-Projektion liest sie nicht; Nx entscheidet aus `cache`, `continuous` und `outputs`. Ein Manifest schreibt sie nicht; die synthetisierten Playground-Targets, die TypeScript-Artefakt-Targets `test`, `check` und (mit `cache: true`) `build` sowie die Wasm-Slot-Erzeuger mit `cache: true` tragen `deterministic`, per Namensregel gecachte Targets tragen keine. Die Richtlinie, die `cache` und die Entscheidung setzt, folgt dieser Reihenfolge, die erste passende Zeile gewinnt (`📚️library/🏗️build/🕸️graph/📥️inference/🎯️target-policy`, Namen aus `📚️library/⚡️caching/🔣️policy.json`):

| Rang | Regel | Gecacht | Angehängte Entscheidung |
|---|---|---|---|
| 1 | `continuous: true` oder ein Name `dev`, `serve`, `watch`, `start`, `test-watch`, `daemon` (auch `<name>-…`) | nein | `continuous` |
| 2 | `cache: false` im Manifest | nein | keine |
| 3 | Ein Name der Liste `uncached` (`audit`, `bench`, `clean`, `deploy`, `deps`, `install`, `publish`, `seed`, `setup`, `test-e2e`, `update`, …) oder ein exakter Name (`format`, `commit`, `os`, `parity`, …); ein geschriebenes `cache: true` wird überstimmt | nein | `live` (`e2e`, `live`, `os`, `semio`), `diagnostic` (`audit`, `bench`, `doctor`, `parity`, …), `side-effecting` (`publish`, `deploy` als `publishes-remote`, sonst `mutates-workspace`) |
| 4 | `hub-live-catalog-check`, `hub-live-catalog-native-check`, `hub-live-catalog-oracle` | ja | keine (Ausnahmen von Rang 5) |
| 5 | Ein durch Bindestriche getrenntes Wort `clean`, `gc`, `prune`, `setup`, `fuzz`, `e2e` oder `live` im Namen | nein | wie Rang 3 |
| 6 | Eine deterministische Familie: `test`, `check`, `lint`, `typecheck`, `format-check`, `generate`, `schema`, `verify`, `build`, `wasm`, `native-build`, `package`, `*-contract`, … | ja | keine; Standard-Inputs `default` und `^default`, Outputs `[]`, sofern das Manifest nichts anderes sagt |
| 7 | Alles andere | **ja**, außer bei `cache: false` | keine |

Rang 7 ist unter Nx fail-open (Bazel verlangt zusätzlich ein `outputs`-Array und eine Klasse, die Wiedergabe erlaubt, siehe seine Cache-Entscheidung): Eine Task, die Host-Zustand berührt und nichts sagt, wird gecacht, und ein Cache-Treffer überspringt ihre Wirkung. Schreibe `cache: false` bei Tests, die echten Speicher-, Lease-, Prozess- oder Toolchain-Zustand prüfen, bei Läufen gegen laufende Hosts, Browser oder Server, bei Schreibern außerhalb ihrer deklarierten Outputs, bei Startern langlebiger Werkzeuge, bei Netzwerk-Downloads und bei Schritten mit unbegrenzter Eingabemenge.

**Store-Belege.** Produkte, die in einen geleasten, inhaltsadressierten Store statt ins Projektverzeichnis veröffentlicht werden (Cargo-Artefakte im Compiler-Store, Vite-Sites, Wasm-Pakete, TypeScript-Artefakte), lassen sich nicht durch Kopieren von außen in diesen Store wiederherstellen. Sie deklarieren einen Beleg als einzigen Output, `{projectRoot}/.🧾️store/<target>.json` (Schema `📚️library/🏗️build/🧾️store-receipt/🧬️schema/🔣️.json`, git-ignoriert, bewusst nicht unter `dist`, das bei TypeScript-Artefakten ein Link in den Store ist). Der Beleg nennt jeden veröffentlichten Store-Pfad (`entries`: Art, Bytes, Dateien, SHA-256; der Digest eines Verzeichnisses hasht seine sortierte Dateiliste) und jeden Link, der einen Projektpfad an einen Store-Pfad bindet (`links`). Die zentralen Veröffentlicher schreiben ihn nach der Veröffentlichung, es ändert sich also kein Build-Skript: das Artefaktziel, über das die Vite- und Wasm-Veröffentlicher schreiben (`⚡️caching/📦️artifacts/🟦️.ts`), der Compiler-Store-Veröffentlicher von Cargo-`build` (`⚡️caching/📦️artifacts/🏗️native-build/🟦️.ts`, übersprungen, wenn ein Beobachtungs-Output angefordert ist) und der Binder der TypeScript-Artefakte (`⚡️caching/📦️artifacts/🟦️typescript/🔗️binding/🟦️.ts`). Beide Adapter übergeben den Ort des Belegs nur der einen Task, die ihn deklariert (`SEMIO_TASK_RECEIPT`, ausgestellt von `issueStoreReceiptV1` in `📚️library/🏗️build/🧾️store-receipt/🟨️.mjs`; Nx: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/🟨️.mjs`, Bazel: `executeTask` in `📚️library/🏗️build/🔧️tools/🏗️bazel/📜️script.ts`); bei jeder anderen Task ist er ungesetzt, eine verschachtelte Task schreibt also nie in den Beleg ihres Elternteils, und ein Veröffentlicher tut ohne ihn nichts (`recordStoreContentV1`).

Nach jedem `run` oder `run-many` prüfen beide Werkzeuge den Beleg jeder gewählten Task und ihrer Voraussetzungen. Ein fehlender, beschädigter oder auf einen fehlenden oder geänderten Store-Eintrag zeigender Beleg gilt als Fehltreffer: Diese eine Task läuft allein und ungecacht erneut (Nx: `run <task> --skip-nx-cache --excludeTaskDependencies`, die eine zusätzliche Kindauswahl, die der Aufrufer zulässt und die auch den Cache-Eintrag ersetzt; Bazel: im Prozess mit `skipCache` und ohne Abhängigkeiten, wobei der veraltete Disk-Cache-Eintrag bestehen bleibt, sodass ein späterer Treffer wieder repariert) und wird nochmals geprüft, sonst schlägt der Aufruf geschlossen fehl. Ein gescheiterter erster Lauf wird nach der Reparatur einmal wiederholt. Eine Task, die einen Beleg deklariert, deren Handler aber keinen schrieb, ist ein Fehler und wird nicht stillschweigend akzeptiert. TypeScript-Artefakt-`build` und Wasm-Slot-Erzeuger tragen den Beleg als Output: Sie werden wiedergegeben, wenn das Manifest `cache: true` schreibt (Entscheidung `deterministic`), sonst bleiben sie `managed-output`. Eine Task deklariert einen Beleg nur, wenn ihre `outputs` den Belegpfad nennen (`declaredStoreReceiptV1`): `check`, `test` und `lint` liefern ein Urteil statt Store-Inhalt, und `publish` sowie der Kurs-`build` nennen andere oder keine Outputs. Abwechselnde `prototype`- und `release`-Läufe eines Targets teilen sich eine Belegdatei (ihr Pfad enthält keinen Modus), ein Wechsel lässt das Target daher voraussichtlich einmal neu laufen (aus der Pfadregel gefolgert, nicht beobachtet). Noch nicht verifiziert: Kein Lauf hat den Reparaturpfad ausgeübt (erster Nachweis: `@teaching/proctor:build` zweimal ausführen, den Slot `published/<hash>` des Compiler-Stores löschen, erneut ausführen und eine Zeile `[store-receipt] re-executing` erwarten, mit `--tool=nx` und `--tool=bazel`).

Die Bazel-Implementierung entscheidet je Action aus `cache`, `continuous` und `outputs` und ist bei fehlenden Deklarationen strenger (siehe ihre Cache-Entscheidung unten).

### Nx-Implementierung

Nx ist der Standard. Das Repository nutzt keine Nx-Projektentdeckung, sondern speist den neutralen Graphen in Nx ein.

- **Plugin.** `nx.json` registriert `@repo/emoji-project-json` (`📚️library/🟨️.mjs`) für `📋️project.json`; `createNodesV2` veröffentlicht den neutralen Graphen als Nx-Projekte, `createDependencies` die neutralen Kanten und lehnt Kanten unbekannter Projekte ab. Jedes Target wird auf einen Nx-Executor abgebildet und erhält eine private Engine-Identität als zusätzlichen Input, damit der Wechsel der ausführenden Implementierung Ergebnisse ungültig macht.
- **Executors.** `@semio-tech/repo-lib:command` und `@semio-tech/repo-lib:owner-command` (`📚️library/📦️packages/🟦️typescript/📋️executors.json`) `command` führt die wörtlichen Argumente über die ursprüngliche Prozessautorität und die Bun-Shell aus, `owner-command` leitet die wörtliche argv ohne Shell-Interpolation an den nativen oder Prozess-Eigentümer weiter (Beschreibungen in `executors.json`); `repo:noop` wird zu `nx:noop`.
- **Übersetzung.** `--skip-cache` → `--skip-nx-cache`, `--exclude-dependencies` → `--excludeTaskDependencies`, `--output` → `--output-style`, `--bail` → `--nx-bail`, `--dry-run` und ein bloßes `--graph` (oder `--graph=true`) → `--graph=stdout`, `--graph=<file>` bleibt. `exec` führt den Befehl in einem Bun-Wrapper aus, der die Namen von Nx' eigenem `exec` (`NX_PROJECT_NAME`, `NX_PROJECT_ROOT_PATH`) auf die neutralen `SEMIO_PROJECT_NAME` und `SEMIO_PROJECT_ROOT` kopiert; die Nx-Namen existieren nur in dieser Implementierung. `affected` ohne Selektor ergänzt `--base=HEAD`, `--uncommitted --untracked` wird zu `--base=HEAD`, `--all` zu `run-many`.
- **Grenze.** Produktionscode außerhalb von `⚡️caching/🚀️bootstrap` lädt nie ein Nx-Modul, sondern geht durch den typisierten Port `⚡️caching/🚀️bootstrap/🛠️tools/🔌️sdk` mit einem geschlossenen Katalog von 13 Nx-Modulen. Ein Test scannt alle Produktionsdateien unter `🦑️repo/🔨️modules` mit eigenem Tokenizer und dem TypeScript-Compiler als unabhängigem Orakel und verlangt null Verstöße.
- **Cache-Ort.** Nx-Ergebnisse liegen in `.🧬semio/🦑️repo/⚡️cache/rust/fixed/m/nx/artifacts` (`cacheDirectory` in `nx.json`; die Rust-Partition, 16 GiB, die auch die gemeinsamen Cargo-Target- und Build-Verzeichnisse aus `.cargo/config.toml` hält). Die getrennte Partition `n` (`.cache/b/n`, 1,5 GiB) ist der Nx-Pool: Sie hält den Nx-Graph-Cache als finanzierte Kind-Images (`⚡️caching/💾️storage/🔒️enforcement/🔌️nx/📦️graph`), nicht die Task-Ergebnisse. `cache status` läuft über das Artefaktverzeichnis; `cache clear` führt `nx reset --onlyCache` im begrenzten Namensraum aus.
- **Noch nicht verifiziert.** Der Gesamtablauf (ein echter Kaltlauf, der `nx/artifacts` füllt, dann ein Warmlauf daraus) ist skriptiert, wurde zum Zeitpunkt dieser Dokumentation aber nicht ausgeführt; die Unit- und Vertragstests der Einzelteile bestanden am 2026-10-19 (`⚡️caching/🚀️bootstrap/🛠️tools/⚙️operations`, `🔌️sdk`, `🔁️probe`, `🏗️build/🧭️selection`, `🏗️build/🧭️invocation`: 23 Tests, 0 Fehler). Am 2026-10-20 zeigte der Link `.nx/installation` auf einen Baum unter `.cache/b/t/m/nx`, den es nicht mehr gibt (nur `.stage-copy-*`-Reste); jeder Nx-Aufruf braucht also zuerst `repo tools setup nx`.

### Bazel-Implementierung

`--tool=bazel` (oder `SEMIO_BUILD_TOOL=bazel`) wählt Bazel 8.4.2 (`.bazelversion`, festgelegter Download je OS und CPU). Der Adapter liegt in `📚️library/🏗️build/🔧️tools/🏗️bazel`. Er macht aus den gewählten Tasks echte Bazel-Actions, sodass Action-Cache, Disk-Cache, optionaler Remote-Cache und lazy Auswertung von Bazel selbst kommen.

- **Generierter Workspace.** Je eigenständiger Auswahl entsteht `<products>/bazel/workspaces/<namespace>` mit `MODULE.bazel`, `BUILD.bazel`, den Regeln in `tasks.bzl` (`repo_task`, `repo_launch`, `repo_noop`), je Action einem Manifest `<label>.json` und einem Fingerabdruck `<label>.input` sowie `s`, einem Link auf den echten Checkout (unter Windows eine Junction). Das Label einer Task ist `t_` plus 16 Hexziffern des SHA-256 der Task-ID.
- **Minimale Builds.** Nur die gewählten Tasks und die über `dependsOn` erreichbaren werden zu Actions; gebaut wird genau `bazel build` der gewählten Labels. Reine Reihenfolge-Tasks (`repo:noop`) verschwinden hinter ihren Erzeugern, es sei denn, sie sind selbst gewählt. Ein nicht benötigtes Target wird nie analysiert oder ausgeführt.
- **Deklarierte Inputs.** Die `inputs` einer cachebaren Task werden gegen die Dateien des Checkouts aufgelöst und als Bazel-Inputs deklariert: die Dateien erreichen die Action über gemeinsame `filegroup`s aus Labels `s/<pfad>` statt über eine Liste je Task: Ein Verzeichnis, dessen Dateien alle gewählt sind, ist eine Gruppe `d_<hash>` (eine Projektwurzel ist eine Gruppe, Ketten mit einem Kind werden zusammengezogen), Musterbausteine mit mehr als zwei Mitgliedern sind gemeinsame Verbunde `k_<hash>`, und jede Task erhält einen Verbund `i_<hash>` (`bazelSourceCoverV1`; Namen sind ASCII, Emoji stehen nur in Datei-Labels). Auf dem statischen Graphen mit 1.466 Projekten schrumpfte `BUILD.bazel` dadurch von 317 MB auf 65 MB und die Workspace-Erzeugung von 351 s auf 37 s. `glob()` wurde versucht und verworfen: Mit `.bazelignore` passt es auf nichts, ohne folgt es Symlink-Schleifen und git-ignorierten Bäumen, die Nx nie hasht. `^name` und `dependencies: true` erreichen den transitiven Abhängigkeitsabschluss, wie Nx es hasht (`bazelTaskInputsV1`); ein `dependsOn`, das ein nicht vorhandenes Projekt oder Target nennt, wird beim Bau des Plans abgelehnt (`requireBazelDependencyV1`, „Unknown build task dependency“), und `bazelDanglingDependenciesV1` listet alle auf einmal auf. Pfade, die Bazel nicht als Label benennen kann (label-unsichere Namen, Verzeichnisse, hängende Links, alles unter einem verschachtelten `BUILD`-Paket), gehen stattdessen in den Fingerabdruck ein; dieser enthält außerdem Plattform, CPU, Bun-Version, Build-Modus, deklarierte Umgebungswerte und `runtime`-Ausgaben. Das Action-Manifest ist inhaltsstabil: Es nennt Task und ausführende Implementierung, aber keinen Workspace-, Laufzeit- oder Snapshot-Pfad; die Live-Daten stehen in `runtime.json` außerhalb jedes Schlüssels.
- **Befehlsabschlüsse.** Abschluss-Marker (`SEMIO_SOURCE_CLOSURE_<key>`, `SEMIO_CARGO_LOCK_<key>`) werden zu den Dateien aufgelöst, die sie nennen, bevor eine Deklaration oder ein Fingerabdruck gebaut wird (`📚️library/🏗️build/🔧️tools/🏗️bazel/🔗️closure`): `bazelClosureMarkersForPlanV1` sammelt die Marker, die ein Plan erreichen kann (Task-Inputs, `^`-Kanten und `{input, projects}`-Verweise), die Manifeste werden über ihre Inhaltsadresse geholt (`managedBazelClosureFetchV1` über den Graph-Store-Leser des Nx-Hashers; für Tests eine Dateisystem-Variante), gegen ein geschlossenes Schema geprüft, und absolute Namen oder Namen mit `..` werden abgelehnt. Ein Marker ohne geladene Manifeste ist ein Fehler, keine leere Liste. Zuvor erreichte keine Abschlussdatei einen Bazel-Action-Schlüssel, eine Änderung an einem importierten Modul ließ eine Task also gecacht (am 2026-10-20 in einem Scratch-Lauf gemessen: 106 von 111 Modulen eines Skripts und 162 von 169 eines anderen waren nicht deklariert). Mit dem echten Bazel 8.4.2 im Test dieser Komponente geprüft (`🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️closure`, 9 Tests bestanden am 2026-10-20 auf dem Live-Baum): Eine Regel über die aufgelösten Labels läuft einmal, bleibt nach einer Änderung außerhalb des Abschlusses bei einmal und läuft nach einer Änderung an einem importierten Modul erneut. Noch nicht verifiziert: das Holen unter dem Bazel-Storage-Lease im Produktionseinstieg und die erneute Messung der nicht deklarierten Module nach der Änderung.
- **Quell-Link und `.bazelignore`.** Der generierte Workspace verlinkt den Checkout als `s` (`linkBazelSourcesV1`) und schreibt keine `.bazelignore`; eine alte entfernt er. Ein früherer Adapter führte den Link dort auf, damit `//...` ihm nicht endlos folgt, und ein Scratch-Lauf am 2026-10-20 zeigte den Preis: `s` fehlte im Execroot-Symlink-Wald, Bazel konnte die deklarierten Inputs nach einer Action ohne Sandbox nicht mehr stat-en und lud keine Ergebnisse hoch (`Skipping uploading outputs because of concurrent modifications`); der Disk-Cache blieb leer und jeder Warmlauf führte erneut aus. Ohne die Ignore-Datei würde `//...` dem Link endlos folgen, deshalb fragen Abfragen das Wurzelpaket mit `//:all` ab (jede Task-Regel liegt darin; 0,4 s im Scratch-Lauf). Die Adapter-Änderung wurde am 2026-10-20 um 11:36 angewendet. Noch nicht verifiziert: ein Produktions-`repo --tool=bazel run`, der das Füllen des Disk-Caches und einen Warmtreffer mit dem korrigierten Adapter zeigt; die Tabelle unten entstand ohne die `.bazelignore`; die ersten Scratch-Läufe damit cachten nichts.
- **Deklarierte Outputs.** Jede Task hat genau einen deklarierten Tree-Artifact-Output `<label>.snapshot`. Ein Verbraucher erhält die Snapshots seiner Erzeuger (bei `transitive: true` den transitiven Abschluss) als Inputs. Nach dem Build werden die Snapshots der gewählten Tasks in den Checkout wiederhergestellt.
- **Cache-Entscheidung (fail-closed).** Jede Action trägt `cache` und, wenn sie ungecacht ist, einen maschinenlesbaren Grund; die Starlark-Regel scheitert ohne einen und versieht die Action mit `no-cache`. Der Adapter entscheidet in dieser Reihenfolge (`bazelCacheDecisionV1`):
  1. Ein ausdrückliches `cache: true` gegen eine Plugin-Klasse außer `deterministic` ist ein Konflikt und wirft („Conflicting cache declaration“), außer bei einer reinen Reihenfolge-Task.
  2. `continuous` (ein Dienst) ist ungecacht mit dem Grund `continuous`.
  3. `--skip-cache` ist ungecacht mit dem Grund `skipped`.
  4. Eine reine Reihenfolge-Task (`repo:noop`) ist immer cachebar.
  5. Eine Klasse außer `deterministic` (siehe Cache-Klassen) ist ungecacht, der Klassenname ist der Grund: `driver-owned`, `managed-output`, `side-effecting`, `live`, `aggregate`, `diagnostic`.
  6. `cache: false` im Manifest ist `declared` und gewinnt auch gegen eine Klasse `deterministic`.
  7. Weder `cache: true` noch Klasse `deterministic` ist `undeclared`: die Task läuft immer, bis eines deklariert ist.
  8. `cache: true` oder Klasse `deterministic` ohne `outputs`-Array ist `unbounded`: ein Treffer könnte nicht wiederherstellen, was erzeugt wurde.
  9. Alles andere ist cachebar.

  Deklariere also `outputs` (für reine Prüfungen `[]`) an jedem cachebaren Target. Auf dem statischen Graphen vom 2026-10-20 deklarierten vor der Korrektur durch die Eigentümer 809 Targets in 278 Projekten `cache: true` ohne `outputs` und liefen deshalb unter Bazel ungecacht mit dem Grund `unbounded`; `bazelUncachedReportV1` (geschlossenes Schema `UncachedReport`) gruppiert sie je Eigentümerprojekt, und kein CLI-Befehl gibt diesen Bericht bisher aus. Kontinuierliche Tasks werden zu `repo_launch`-Actions, laufen mit `bazel run`, ihre Bereitschaft wird abgewartet, und sie teilen sich den Server des Builds.
- **Ausführungsanforderungen.** Jede Task- und Launcher-Action trägt `no-remote-exec` (der `repo_noop`-Marker schreibt nur eine Datei und startet keinen Prozess); Actions mit `host_state` zusätzlich `no-sandbox`, heute ist das jede Task- und Launcher-Action, nur der `repo_noop`-Marker ist sandboxfähig (`STARLARK_RULES` in `🏗️build/🔧️tools/🏗️bazel/📜️script.ts`; `Actions.kinds` in `🏗️build/🔧️tools/🏗️bazel/🧬️schema/🔣️.json`). Gründe laut Schema (`ActionPolicy.kinds`): Eine *Task*-Action führt den Task-Prozess im echten Checkout aus, mit Arbeitsverzeichnis, deklarierten Schreibzugriffen auf Quellbaum und gemeinsamen Store, dem Loopback-Steuersocket und dem Laufzeitkanal außerhalb des Baums, was eine Sandbox verbergen oder blockieren würde; eine *Launcher*-Action bindet exakte Execroot-Output-Pfade und erhält Autorität über den Steuersocket der Invokation, was ein Sandbox-Execroot ändern würde. Folge: Ergebnisse sind durch deklarierte Inputs und Fingerabdruck bestimmt, nicht durch das, was eine Sandbox beobachtet hat; eine fehlende Input-Deklaration zeigt sich als veralteter Treffer, nicht als Fehler. Die `.bazelrc` des Repositorys setzt heute kein `--spawn_strategy`, `--sandbox_*` oder `--strategy` (der Test „the repository .bazelrc carries exactly the authored static cache policy and no host paths“ in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🧪️tests` legt ihre Cache-Zeilen fest und lehnt Host-Pfade ab, verbietet aber kein Sandbox-Flag); jede Action, die je ohne `host_state` deklariert wird, läuft also in Bazels Standard-Sandbox.
- **Sandbox und Host-Pfade.** Bazel 8.4.2 unter macOS behandelt Nicht-ASCII-Pfade seines eigenen Zustands falsch, an zwei durch Experimente gefundenen Stellen: Eine `--install_base` mit Emoji oder Akzent lässt den Server beim Start abstürzen („Could not find or load main class“), und das `darwin-sandbox`-Profil wird aus Bazels byteweisen Pfadstrings geschrieben, aber jedes Byte ein zweites Mal als UTF-8 kodiert, sodass die Schreibregeln für eine Nicht-ASCII-`--output_base` nie passen und jede Sandbox-Action (auch ihre `stats.out`) mit „Operation not permitted“ scheitert. Es wirkt nur ortsabhängig, weil `/private/tmp`, `/private/var/tmp`, `TMPDIR` und `~/Library/Caches` für jede Schreibweise freigegeben sind. Das Produktionslayout hält die `install`-Basis, die `outputs`-Wurzel und die `server`-Output-Bases (`<products>/bazel/outputs/server/<hash>`) in den nativen Partitionen unter `.cache/b`, und die sind ASCII, solange der Checkout-Pfad ASCII ist (zum Beispiel `/Users/<name>/Documents/semio`). `requireBazelHostPathsV1` (aufgerufen von `bazelCacheLayoutV1` in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🟦️.ts`, das jeder Bazel-Speichernutzer aufbaut) lehnt unter darwin ein Layout ab, dessen Pfad `install`, `outputs` oder `server` ein Nicht-ASCII-Zeichen enthält („ASCII Bazel host path required on darwin: outputs“), und zwar beim Aufbau des Layouts statt mitten im Build. Halte den Checkout-Pfad unter macOS also ASCII. `--sandbox_base` wird nicht benutzt. Eine Sandbox-Action darf nur in ihr Execroot, die Temp-Verzeichnisse und `~/Library/{Caches,Logs,Developer}` schreiben; wird je eine Task sandboxed, die in den Checkout oder eine Partition schreibt, braucht sie `--sandbox_writable_path=<ASCII-Pfad>`, das denselben Kodierer durchläuft und deshalb ebenfalls ASCII sein muss. Linux (Bind-Mounts statt Profil) und Windows wurden nicht untersucht, die Sperre gilt nur für darwin; Windows deckt die Bereitschaftsprüfung für Nicht-ASCII-Pfade von Workspace und Partition ab.
- **Emoji in Quell-Labels.** Task-Quellen heißen `s/<pfad>` (`bazelSourceLabelV1`): die Datei hinter dem Link `s`, ein Target-Name im Wurzelpaket. Beobachtet mit dem festgelegten 8.4.2 (der Test mit dem echten Binary in `🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️actions` spielt die Fixture-Namen ab und wird ohne `SEMIO_TEST_BAZEL_BINARY` übersprungen): Bazel akzeptiert in Target-Namen jedes Nicht-ASCII-Zeichen, auch astrale Emoji, ZWJ-Sequenzen, Hautfarben, kombinierende Zeichen, CJK und das geschützte Leerzeichen, auch als Action-Input- und -Output-Namen; abgelehnt werden nur Backslash und Steuerzeichen. Nur Paketnamen müssen ASCII sein, der Adapter braucht also nie ein Emoji-Paket; ein Verzeichnis mit `BUILD` oder `BUILD.bazel` gilt ihm unabhängig von der Schreibweise als Paketgrenze, alles darunter geht in den Fingerabdruck (`bazelSourceClassesV1`). Der Adapter lässt einen Pfad als Label zu, wenn er `^(?:[A-Za-z0-9_@=,+~%./\-]|[^\u0000-\u007f])+$` entspricht (codepunktbasiert, gilt also auch in Python, Rust und Go), und nimmt alles andere (Leerzeichen, Backslash, Steuerzeichen, Verzeichnisse, hängende Links, alles unter einem Verzeichnis mit `BUILD`) stattdessen in den Fingerabdruck auf. In einem Scratch-Experiment waren Disk-Cache und Cache-Schlüssel unter `LANG=C` und einer UTF-8-Locale identisch (kein Test deckt das ab); der Adapter setzt unter darwin eine UTF-8-Locale (`LANG` und `LC_ALL` `en_US.UTF-8` in `runBazelTasksInStorageV1`).
- **Disk-Cache.** `<products>/bazel/actions` mit Garbage-Collection (`--experimental_disk_cache_gc_max_size` gleich 40 Prozent des Budgets der Produkte-Partition, auf MiB abgerundet; `.bazelrc` ergänzt `--experimental_disk_cache_gc_idle_delay=10s` und `--experimental_disk_cache_gc_max_age=30d`). Die Sammlung läuft nur in einem dauerhaften, untätigen Server (gemessen mit Bazel 8.4.2: unter `--batch` lief sie nie), deshalb nutzt der Adapter für Builds kein `--batch`. Der Repository-Contents-Cache behält Einträge 3 Tage. Modulkatalog und Repository-Cache liegen in `<dependencies>/bazel/modules`; Builds laufen mit `--repository_disable_download` und laden keine Module nach.
- **Gemeinsame Output-Base.** `--output_base` ist `<products>/bazel/outputs/server/<erste 16 Hexziffern von sha256(Workspace-Verzeichnis)>`: ein Server je generiertem Workspace-Verzeichnis, geteilt von Build und allen `bazel run` kontinuierlicher Tasks dieser Auswahl; er endet nach 120 Sekunden Leerlauf. Der Disk-Cache wird von allen Auswahlen geteilt, deshalb nutzt eine zweite Auswahl die Ergebnisse der ersten.
- **Remote-Cache.** Wird aus dem werkzeugneutralen Remote-Cache-Vertrag erzeugt (Abschnitt "Remote-Cache"): `--remote_cache`, `--remote_instance_name`, `--[no]remote_upload_local_results`, `--[no]remote_cache_compression`, `--remote_download_outputs`, `--remote_timeout` und `--remote_retries`, und nichts, solange kein Endpunkt gesetzt ist. `--skip-remote-cache` lässt ihn für einen Aufruf weg, `--skip-cache` ergänzt `--noremote_accept_cached`. Der Adapter stellt Task-Snapshots aus `bazel-bin` wieder her, deshalb wird `minimal` abgelehnt. Das Zugriffstoken steht nie in einem Flag: ein Credential-Helper im `tmp`-Ordner der Produkte kennt nur den Variablennamen, das Token reist in der Umgebung des Bazel-Clients (`--remote_header` würde es in Bazels `java.log` und den Build-Event-Stream kopieren).
- **Cache-Operationen.** `repo --tool=bazel cache status` zählt die Dateien der Ordner `ac` und `cas` des Disk-Caches und ergänzt die aufgezeichnete Build-Aktivität (Builds, Actions, ausgeführt, Cache-Treffer), die jeder Build aus seinem Build-Event-Stream in `<products>/bazel/outputs/server/metrics.json` fortschreibt. `cache clear` stoppt die dauerhaften Server (durch Entfernen ihrer pid-Datei), entfernt ihre Output-Bases (Bazels lokalen Action-Cache) und leert den Disk-Cache, sodass der nächste Build ein Fehltreffer ist; Bazel-Binary, Module und Toolchains bleiben.
- **Speicher.** Bazel braucht die Partitionen tools, dependencies und products (`bazel/bin`, `bazel/install`; `bazel/modules`; `bazel/workspaces`, `bazel/outputs`, `bazel/actions`). `repo --tool=bazel reset` verwirft den Graphen und leert `bazel/actions`, `bazel/outputs` (mit den Server-Output-Bases und dem Aktivitätsbuch) und `bazel/workspaces`; es stoppt einen laufenden Bazel-Server nicht, führe es nur aus, wenn kein Build läuft (`cache clear` stoppt sie).
- **Verifiziert und noch nicht verifiziert.** Bazel 8.4.2 wurde unter macOS arm64 in Scratch-Workspaces geprüft. Tests mit `SEMIO_TEST_BAZEL_BINARY` bestanden am 2026-10-19 (der Sandbox-Build der Storage-Suite mit Disk-Cache-Treffer nach `bazel clean`, der Emoji-Label-Test der Actions-Suite); am 2026-10-20 bestanden auf dem Live-Baum unter einer ausgestellten Prozesshülle mit dem echten Binary die Suiten `📥️sources` (10 Tests), `📥️workspace` (5), `📥️actions` (12), `📥️fingerprint` (2) und `📥️closure` (9). Die aggregierte Suite (`repo run workspace:test-build-tool-bazel`, also `🏗️build/📜️script.ts test bazel`) lief über den kanonischen Runner nie zu Ende (sie stand hinter dem Dependency-Sync in der Warteschlange); unter einer ausgestellten Hülle endete ihre Quellparitätsphase am 2026-10-19 bei 72 bestanden und 3 fehlgeschlagen (der Nx-Paritätstest braucht `tools setup nx`, dazu seine Folge und ein `afterAll`), und die Vertragsfestlegungen von `Command` und `MaterializedPaths` wurden neu gesetzt, nachdem die Verzeichnispartitionen die VHD-Actions entfernt hatten. Die neun Laufzeitphasen (cache, nested, uncached, birth, services, refusals, cancellation, configuration, offline) liefen nicht. Noch nicht verifiziert: jedes `repo --tool=bazel run` eines Produkts, das Aktivitätsbuch nach einem echten Lauf (`cache status` muss `activity.builds >= 1` zeigen), der CLI-Weg von `cache clear`, Sandbox-Task-Actions (jeder Spawn der Scratch-Läufe war `runner=local`), ein Remote-Cache, Linux, Windows und der Devcontainer.

### Remote-Cache

Ein schema-erster Vertrag (`🏗️build/🏃️execution/🧬️schema/🌐️remote-cache.json`, Standardwerte in `🏗️build/🔣️policy.json`), zwei Umsetzungen und ein Server. Ohne Endpunkt ist der Remote-Cache aus. Der Vertrag enthält kein Geheimnis.

| Variable | Feld | Standard |
|---|---|---|
| `SEMIO_REMOTE_CACHE_ENDPOINT` | `endpoint`: `http://`- oder `https://`-Ursprung | keiner (aus) |
| `SEMIO_REMOTE_CACHE_INSTANCE` | `instance`: Namensraum, erstes URL-Pfadsegment | `main` |
| `SEMIO_REMOTE_CACHE_ACCESS` | `access`: `read-only` oder `read-write` | `read-only` |
| `SEMIO_REMOTE_CACHE_UPLOAD` | `upload`: lokale Ergebnisse hochladen (wirkt nur mit `read-write`) | `true` |
| `SEMIO_REMOTE_CACHE_COMPRESSION` | `compression` | `true` |
| `SEMIO_REMOTE_CACHE_DOWNLOAD` | `download`: `toplevel` oder `all` | `toplevel` |
| `SEMIO_REMOTE_CACHE_TIMEOUT_SECONDS`, `SEMIO_REMOTE_CACHE_RETRIES` | `timeoutSeconds` (1-600), `retries` (0-10) | `30`, `3` |
| `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT` | `auth.tokenEnvironment`: Name der Variable mit dem Bearer-Token | `SEMIO_REMOTE_CACHE_TOKEN` |

- **Bazel** setzt jedes Feld in die oben genannten Flags um und reicht das Token über einen auf den Cache-Host begrenzten Credential-Helper durch. **Nx** setzt `endpoint/instance` in `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` und das Token in `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN` um; Nx 23 kennt keinen Schalter für Kompression, Download-Modus, Zeitlimit, Wiederholungen oder das Zurückhalten von Uploads, deshalb setzt ein Nur-Lese-Token auf dem Server read-only durch. `bun repo cache remote status [--tool=nx|bazel]` zeigt den aufgelösten Vertrag, die Umsetzung samt nicht unterstützter Felder und eine lesende Probe der Route des Werkzeugs.
- **Server.** `bun repo cache serve [--port <n>] [--host <Adresse>] [--directory <Pfad>] [--max-bytes <n>]` spricht Bazels HTTP-Cache-Protokoll (`GET`, `HEAD`, `PUT` auf `/ac/<sha256>` und `/cas/<sha256>`, Blobs gegen ihren Digest geprüft, 400 bei Abweichung) und die Nx-Self-Hosted-Cache-API (`GET`, `PUT` auf `/v1/cache/<hash>`, 409 beim Überschreiben, 401 mit `text/plain`, 403 für ein schreibendes Lese-Token), jeweils mit optionalem Präfix `/<instance>`. Bearer-Tokens stammen aus `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` und `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; ohne Token lauscht er nur auf Loopback. Der Speicher (`.cache/remote-cache`, standardmäßig 4 GiB, 512 MiB je Eintrag, 30 Tage Leerlauf) schreibt atomar, reserviert Bytes vor dem Streamen, entfernt die am längsten ungenutzten Einträge und meldet beim Einlesen den Fortschritt; Abbrechen des Befehls beendet den Server. Das Dashboard-Werkzeug `build-cache-serve` startet ihn auf Port 6090.
- **Tests.** `🏗️build/🌐️remote-cache/🧪️tests` spielt die JSON-Fixtures (Vertrag, Umsetzungen, Leitungsszenarien, Verdrängung) gegen Ajv, Pythons `re`, `http.client` und `hashlib` ab; mit `SEMIO_TEST_BAZEL_BINARY` baut ein echtes Bazel gegen den Server und trifft nach `bazel clean` den Remote-Cache, mit `SEMIO_TEST_NX_BIN` (eine unveränderte Nx-23-Installation; das gepatchte Nx des Repositorys läuft nicht in einem Scratch-Workspace) tut ein echtes Nx dasselbe.

### Befehlsregister

Das Befehlsregister ist die Befehlsoberfläche der Entwickler: Jeder ausführbare Befehl wird einmal neben seinem Quelltext deklariert und von Entwicklern im Dashboard (`repo dashboard`, **New Task**) gewählt; Agenten und Automation verwenden die werkzeugneutrale `repo`-Binärdatei und nie das Dashboard; keine IDE-Launch-, Task- oder Solution-Datei registriert Befehle (im Baum existiert kein Editor-Konfigurationsverzeichnis). `AGENTS.md` nennt die menschliche Oberfläche `repo dashboard`; in diesem Baum startet sie mit `repo dashboard`, dem Root-Paket-Skript für `repo run @semio-tech/repo-dashboard-rs:run --output=stream` (`dashboard:install` baut sie neu). `dashboard` ist keine Operation des Katalogs (`📚️library/🏗️build/⚙️operations/🔣️catalog.json`): Der Build-Einstieg bildet ein `run` der Targets `run`, `daemon` und `preferences` des Projekts `@semio-tech/repo-dashboard-rs` (`dashboardInvocation` in `📚️library/⚡️caching/🚀️bootstrap/🎛️dashboard/📦️installation`; `--output=stream` und `--skip-cache` entfallen) auf die Argumente des installierten nativen Clients ab, den `launchDashboard` unter der Compiler-Zulassung des Aufrufers startet, und führt jedes andere Target sowie jeden Aufruf mit `--graph`, `--batch`, `--parallel` oder `--exclude-dependencies` über das gewählte Werkzeug aus. Builds, Tests und Prüfungen durch Agenten und Automation laufen über `repo …`; ein Agent startet das Dashboard nie. Das Register besteht aus Daten: Die `📋️project.json` an der Wurzel enthält `metadata.semio.dashboard` mit `parameters`, `tools`, `compounds` und `groups`, geprüft gegen das Schema `🔨️modules/🎛️dashboard/🧬️schema/🎮️registry/🔣️.json` (`ProjectManifest`); andere Projekte deklarieren typisierte Steuerelemente an ihren Targets, Playground-Steuerelemente stammen aus Crate-Manifesten. Der [Dashboard-Leitfaden](🔨️modules/🎛️dashboard/README.md#-daily-work) führt die täglichen Zeilen auf; der Build-Teil ist:

| Tool-ID (`tool:workspace/…`) | Führt aus | Hinweise |
|---|---|---|
| `build-task`, `run-targets`, `build-affected`, `build-watch` | `repo run`, `run-many`, `affected`, `watch` | `run-targets` und `build-affected` haben wie `build-task` ein Flag `dry-run` (`--dry-run`). |
| `build-exec` | `repo exec --projects={projects} --dry-run={dry-run} --` plus die Befehlswörter in **Arguments** | `dry-run` ist eine Auswahl (`false` Standard, `true`) innerhalb der Wörter vor `--`, weil Argumente nach `--` zum Kindprogramm gehören; `--dry-run=false` ist wirkungslos. `bun-test`, `run-script` und `native-cargo` bieten dieselbe Auswahl. |
| `build-cache-status`, `build-cache-clear` | `repo cache status`, `cache clear` | Die Achse `build-tool` wählt, wessen Cache. |
| `build-preflight`, `build-deps-sync`, `build-deps-lock` | `repo preflight`, `dependencies sync --all`, `dependencies lock --all` | Host-Prüfung; Installation und Sperre für alle Eigentümer (`--scope <owner>` bleibt auf der Kommandozeile). |
| `build-graph`, `build-projects`, `build-targets`, `build-project`, `build-help`, `build-reset`, `build-tools`, `cargo` | `graph`, `show …`, `--help`, `reset`, `tools setup`, `repo cargo` | |

Globale Achsen (Parameter) des Wurzelregisters: `build-tool` (`SEMIO_BUILD_TOOL=nx|bazel`), `cache` (`use`, `skip-local` = `--skip-cache`, `skip-all` = `--skip-cache --skip-remote-cache`), `build-mode=ship` (Release-Build, beide Caches übersprungen), `dependencies` (`--exclude-dependencies`), `test-level`, `nextest-output`, `cargo-jobs`, `build-budget`. `build-tool` wird bei jedem Verb angeboten, das Build-Tasks ausführt, auch bei `publish`, `prepare`, `deploy`, `activate`, `serve`, `reset` und `inspect`; dieselbe Task läuft also im Dashboard unter Nx oder Bazel. Ein Gesetz vergleicht seine Verben mit den Verben des Rust-Registers (`VERBS`) plus dem Rückfall `task` plus `reset` und `inspect`. `cache` wird bei `dev`, `run`, `watch`, `clean`, `reset`, `inspect` und `setup` nicht angeboten, die kontinuierlich sind oder keinen Task-Cache haben. Eine frische native Build-Generation ist ein Registerparameter `generation=fresh` (`SEMIO_NATIVE_BUILD_GENERATION=fresh`) des Play-Targets `build` und des Wurzel-Targets `release`, kombiniert mit `build-mode=ship`.

Befehle des Wurzelskripts (`bun ./📜️script.ts verify …` und ähnliche) werden über Targets geleitet, die `metadata.semio.workspaceCommand` deklarieren: ein Array aus mindestens zwei Wörtern aus `[a-zA-Z0-9-]`, im ganzen Repository eindeutig (zum Beispiel `verify fem-combination-stress`). Eine fehlerhafte oder doppelte Deklaration lässt den Routenlader werfen („Invalid owned command“, „Duplicate owned command“) und bricht jede Route `verify …`; deshalb werden die Deklarationen des ganzen Baums gemeinsam geprüft.

Wähle im Dashboard **New Task** → `@semio-tech/repo-lib:test-dashboard-control`, um das Befehlsregister zu prüfen. Die Prüfung vergleicht das Wurzelregister mit Ajv 2020 und dem eigenen Schema-Compiler, neutrale Eigentümer-Fixtures mit SQLite und den Verben des Rust-Registers sowie Vorschauargumente mit `validateBuildTaskArgumentsV1` und `nxBuildArgumentsV1`. Ausgabe und Ergebnis bleiben an der Task. Agenten und Automation erreichen denselben Eigentümer über `repo run @semio-tech/repo-lib:test-dashboard-control`. Das Target `@semio-tech/repo-dashboard-rs:test-journeys` prüft zusätzlich den installierten nativen Client und tatsächliche Terminalabläufe.

### Script-Einstiege

Befehle, die der Build-Graph als `repo:script` ausführt, beginnen am `📜️script.ts` ihres Moduls. Das Befehlsrouter-Gesetz (`📚️library/🔍️discovery/🛣️ecma-command-routes`) akzeptiert zwei Formen:

- **Router.** Eine Klasse je Befehl, die `BundleScript` erweitert, ein `ScriptRouter`, der sie registriert, und ein Abschluss unter `import.meta.main`. Ein dünner Einstieg behält die Prozessgeburt im Router und reicht die eigenen Argumente weiter: `await receiveScriptProcessInvocation(process.env, original => runScriptMain(router, { invocation: original, argv: ["run"] }))`. Das Programm parst sein eigenes `process.argv`; `argv` nennt nur den registrierten Befehl (`📚️library/⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/📜️script.ts`). Der andere akzeptierte Abschluss ist `router.run(process.argv.slice(2))` für Router, die nach der Kommandozeile verteilen.
- **Nackter Einstieg.** `import { runScriptProgram } from "./🟦️.ts"; if (import.meta.main) await runScriptProgram();`, also genau ein argumentloser Aufruf von `runScriptProgram`, aus einem Geschwistermodul `🟦️.ts` importiert, unter `import.meta.main` (`ecmaRouteOwnedProgram`). Er ist für Programme, die ihre Prozessgeburt und ihren Exit-Code selbst besitzen, besonders die Kindprogramme von Tests unter `🧪️tests` und `👷️child` (zum Beispiel `📚️library/⚡️caching/🦀️cargo/📦️units/📥️descriptor/💾️cache/🧪️tests/📦️child/📜️script.ts`).

### Cache-Partitionen und Wiederherstellung

Der gesamte Build-Zustand liegt in Partitionen fester Größe unter `.cache/b/<partition>` (git-ignoriert, abgeleitet, löschbar, solange nichts läuft): `d` Abhängigkeiten (8 GiB), `t` Werkzeuge (8 GiB), `g` Graph (4 GiB), `o` Beobachtungen und Diagnose (2 GiB), `p` Produkte (24 GiB), `l` Leases (64 MiB), `n` Nx-Pool (1,5 GiB); die Größen stehen in `📚️library/⚡️caching/💾️storage/🔒️enforcement/📦️budget/🔣️policy.json`. `.cache/b/c` ist das einfache Steuerverzeichnis (kein Image, höchstens 1 MiB; es hält die Lease-Datenbank der Images, `budget.controlDirectory`), die Rust-Partition liegt getrennt unter `.🧬semio/🦑️repo/⚡️cache/rust/fixed` (16 GiB). Unter macOS ist jede Partition ein UDIF-Image mit case-sensitive APFS (`fixed.dmg`, bei `m` eingehängt, daneben der Beleg `image.json`; `ImageProtocol` legt `UDIF` und `Case-sensitive APFS` fest, HFS+ wurde früher ausgeschlossen, weil ihm der atomare Austausch `RENAME_SWAP` fehlt, den Veröffentlichung und Bindung nutzen, hier nicht erneut geprüft), unter Linux ein Verzeichnis ohne Rechte (`fixed.dir`, `v`, `m`, getauscht durch atomares `renameat2(RENAME_EXCHANGE)`), unter Windows ebenfalls ein Verzeichnis (journalisierter Zwei-Phasen-Tausch mit Write-Through statt `renameat2`; Linux und Windows aus dem Quelltext, nicht auf allen Hosts verifiziert). `bun ./📜️script.ts clean` berührt nie eine davon.

**macOS-Volume-Stille.** macOS protokolliert Dateisystemereignisse jedes eingehängten Volumes in `.fseventsd` und indiziert es; auf einem Image, das nur ein Build-Werkzeug beschreibt, füllt das das 63-MiB-Lease-Image und die kleinen Partitionen. Jedes Image trägt deshalb `.fseventsd/no_log` und `.metadata_never_index` (Protokollkonstanten in `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage/🍎️image/🤫️silence/🧬️schema/🔣️.json`). Ein Schreiben nach dem Einhängen genügt nicht: Mit `-owners on` legt macOS `.fseventsd` als `root:staff 0700` mit ACL an, und ein Protokoll wächst, bis das Volume gelöst und neu angehängt wird. Die Images werden deshalb aus einem Seed-Ordner erzeugt (`hdiutil create -format UDRW -srcfolder <seed> -size … -nospotlight` ergibt dasselbe feste Image wie `-type UDIF`, mit von Anfang an benutzereigenen Markern), und `applyNativeImageVolumeSilenceV1` läuft beim Anhängen und erneut, wenn ein schon eingehängtes Image geöffnet wird: Es legt Verzeichnis und Marker an, falls sie fehlen, und räumt Protokolle (reguläre Dateien mit einem Link, benannt mit 16 Hexziffern, in Stapeln zu 64) auf: beim Anhängen alle, beim Öffnen sobald mehr als 8 Dateien oder 1 MiB bleiben. Ein `.fseventsd`, das root gehört oder ein Symlink ist, und nicht reguläre Marker werden mit einer Abhilfe abgelehnt. Ein stilles Volume hat keinen FSEvents-Dienst, die Publikationszeugen behandeln es daher als Volume ohne Dienstdomäne (`observeNativeVolumeEventServiceV1` gibt `null` zurück). Kapazität: APFS fasst 40.960 Bytes weniger als das Image, bei Images über 2 GiB 200 MiB weniger (gemessen an 15 Images von 32 MiB bis 4.095 MiB), deshalb stellt jede Partition `usableBytes` bereit, und bei Partitionen bis 256 MiB muss das logische Limit hineinpassen; darum ist `leases.maximumLogicalBytes` 62.914.560 von 67.108.864. Beobachtet am 2026-10-20: Die Live-Images waren eingehängt, bevor ihre Marker existierten, und macOS protokolliert weiter, bis jede Partition gelöst und neu angehängt wird; nach der Reparatur beim Öffnen hielt `.fseventsd` von `d`, `l` und `g` 3, 5 und 1 Einträge (das Abhängigkeits-Image hatte etwa 200 Protokolle gehalten), und jede Partition hat `.metadata_never_index`. Noch nicht verifiziert: ein frisch erzeugtes Seed-Image durch den ganzen Weg von `tools setup` und die Seed-Erzeugung unter einer anderen macOS-Version.

Wenn jeder `repo`-Aufruf beim Start ablehnt, prüfe die Punkte 1 bis 6 vor jeder Codeänderung (die `hdiutil`-Befehle gelten nur für macOS); Punkt 7 betrifft den Abhängigkeits-Installer. Stoppe zuerst alle `repo`-, Cargo- und Nx-Prozesse.

1. **„Pending Native image publication must settle“**: Ein abgebrochener Lauf hat `.cache/b/<partition>/.publication/intent.json` hinterlassen. Prüfe, dass kein Prozess lebt, verschiebe die Datei, starte neu.
2. **Beleg- oder Mount-Konflikt** („Exact canonical persistent Native publication required“, „Ambiguous Native backing kernel association“, ein `image.json` ohne sein `fixed.dmg`): Partition neu anlegen: `hdiutil detach .cache/b/<partition>/m || umount -f …`, `hdiutil info` (kein Image darf den Pfad noch beanspruchen), `rm -rf .cache/b/<partition>`, dann `repo --help && repo tools setup all`. Nie ein eingehängtes Partitionsverzeichnis mit `mv` verschieben. Unter Linux ist nichts eingehängt: überspringe die `hdiutil`-Zeilen, prüfe, dass `lsof +D .cache/b/<partition>` leer ist (ein atomarer Austausch gelingt auch mit offenen Dateien, anders als `umount`), und entferne das Verzeichnis. Eine Verzeichnispartition, die `preflight` ablehnt („Atomic directory exchange is unsupported by this kernel or filesystem“ oder ein Dateisystem ohne Groß-/Kleinschreibung), lässt sich durch Neuanlegen nicht reparieren: verschiebe `.cache` auf ein natives Dateisystem mit Groß-/Kleinschreibung, im Devcontainer auf sein Volume `.cache`.
3. **Verschachteltes Anhängen „Permission denied“**: Das Elternimage war `noowners` eingehängt. Ist nichts offen (`lsof +f -- .cache/b/<partition>/m` leer), `hdiutil detach` auf dem Elternimage; der nächste Aufruf hängt mit `-owners on` neu an.
4. **Vergifteter Nx-Pool** (jeder Graph- oder Nx-Aufruf scheitert mit „Exact original parent child allocation required“): `hdiutil detach .cache/b/n/m/<shard>/native/m`, dann das Shard-Verzeichnis mit `rm -rf` entfernen.
5. **ENOSPC in `d`**: `.cache/b/d/m/tmp` leeren (Installer-Reste), dann `dependencies sync --all` wiederholen.
6. **Vor dem APFS-Wechsel erzeugtes Image** (ENOTSUP bei rename): wie in Punkt 2 neu anlegen.
7. **`dependencies sync` scheitert mit `EPERM: Operation not permitted: failed to link package`** (macOS 27, auf arm64 beobachtet): Der Kernel verweigert Hardlinks und Clones von Dateien des Bun-Paket-Caches `.cache/b/d/m/bun-cache`, die das Attribut `com.apple.provenance` einer anderen Anwendungsidentität oder Sitzung tragen, während Dateien, die der aktuelle Prozess erzeugt hat, sich verlinken lassen (`ln` und `cp -c` einer alten Cache-Datei ergeben EPERM, eine frische Kopie lässt sich verlinken; `xattr -d` meldet Erfolg, das Attribut bleibt). Der Sync behandelt das jetzt: Er stuft diese Installer-Ausgabe als Cache-Link-Verweigerung ein, gibt `[DATA] Store dependency cache link refused; purging the Bun package cache and retrying` aus, leert `bun-cache` an Ort und Stelle (das Verzeichnis behält seine Identität; Fortschritt `dependencies:purge-bun-cache:<n>`), bereitet die Umgebung neu vor und wiederholt den Installer einmal je Sync, wobei die benötigten Pakete neu geladen werden. Scheitert er trotzdem, leere `.cache/b/d/m/bun-cache` selbst, wenn nichts läuft, oder führe den Sync mit derselben Anwendungsidentität aus, die den Cache gefüllt hat. Nicht Ende-zu-Ende verifiziert: Klassifikator, Generationsauswahl und Baumentfernung sind durch Fixture-Tests abgedeckt, ein vollständiger `dependencies sync` über den Weg Leeren-und-Wiederholen wurde nicht aufgezeichnet.
8. **`.fseventsd` einer Partition wächst auf hunderte Protokolldateien mit 16 Ziffern, oder ein kleines Image meldet ENOSPC**: Das Volume war eingehängt, bevor es still gestellt wurde. Jeder Befehl, der die Partition öffnet, räumt den Rest auf. Um das Protokollieren an der Quelle zu beenden, löse die Partition und hänge sie neu an, wenn nichts läuft (macOS: die Befehle aus Punkt 2, dann `repo --help`); ein `.fseventsd`, das root gehört, wird absichtlich abgelehnt und muss von Hand mit `sudo` entfernt werden.

Das Neuanlegen von `d` kostet einen vollständigen `dependencies sync --all` (etwa 16 Minuten mit warmem Paket-Cache im einen aufgezeichneten Lauf auf dem primären macOS-arm64-Host, 2026-10-19), das von `g` eine kalte Graph-Inferenz (Minuten; für diese Dokumentation nicht gemessen).

### Developer Dashboard

Der [tägliche Dashboard-Ablauf](🔨️modules/🎛️dashboard/README.md#-daily-work) ist der Einstieg für Entwickler. Wähle **New Task**, suche die Operation und ihren Eigentümer und fülle dann das typisierte Formular aus. Die Vorschau zeigt Argumente und Umgebung vor **Start**. Ausgabe, Fortschritt, Bereitschaft, Quellnavigation, interaktives Debugging, Abbruch und Neustart bleiben an dieser Task.

Der Abschnitt Befehlsregister des Build-Kapitels führt die Build-Werkzeuge, die globalen Achsen (`build-tool`, `cache`, `build-mode`) und die Trockenlauf-Formen auf. Deklariere ausführbare Operationen neben ihrem Quelltext: Build-Targets in `📋️project.json`, typisierte Steuerelemente in `metadata.semio.dashboard` und selbst geschriebene Ticket-Werkzeuge in der `🎮️commands.json` des Tickets. Playground-Steuerelemente stammen aus `[[package.metadata.semio.playground]]` in Crate-Manifesten; native Crate-Targets stammen aus `📋️build-owners.json` und dem neutralen Build-Graphen. Parameterauswahl, Umgebungen, Bereitschaft und Compound-Mitgliedschaft gehören zu diesen Eigentümer-Deklarationen. Editoren bieten Quellnavigation und Bearbeitung; das Dashboard besitzt die Ausführung. Starte es mit `repo dashboard` (das `repo dashboard` aus `AGENTS.md`); ein Verb `repo dashboard` gibt es nicht. Menschliche Entwickler nutzen das Dashboard für jeden Befehl, Agenten und Automation nutzen `repo …`, und keine Editor- oder IDE-Konfiguration registriert oder startet Befehle.

### Go-Layout

Go-Code folgt dem kanonischen Taxonomie-Layout statt Dateien in der Paketwurzel:

- Ein Member ist ein Verzeichnis mit genau einem `🐹️.go`-Blatt: `<module>/📦️packages/🐹️go/<member>/🐹️.go`. Der Member-Name ist in `📚️library/🔣️taxonomy.json` registriert (`members-of-members-of-members-of-modules`).
- White-Box-Tests sind Fälle am sprachneutralen Eigentümer: `<module>/🧪️tests/<case>/🐹️.go`, in das Paket aufgenommen, wenn die Paketklausel die des Moduls oder `<package>_test` ist. Black-Box-Adapter werden nie aufgenommen.
- Weil die Dateien nicht in der Paketwurzel liegen, sehen einfaches `go test` und `go list` die Member nicht. Führe Go über das Paket-`📜️script.ts` (`runCanonicalGoTests`) oder `repo run <project>:test` aus, die die zusammengeführte Quell-Überlagerung übergeben.
