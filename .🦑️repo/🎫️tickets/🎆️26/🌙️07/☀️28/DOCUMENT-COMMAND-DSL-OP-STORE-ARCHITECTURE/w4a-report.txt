W4a report — protocol_history backwards + cursor persistence (closes G4)

Landed per w3-w4-design.md's D4-D6 decisions, with one deliberate implementation-level
simplification recorded below (D6-note).

1. protocol/history/rs/lib.rs 🔖️Model:
   - HistoryEdit gains `backwards: Vec<OpPayload>` (empty for text-compiled/imported logs).
   - New HistoryCursor { applied_edit_ids, redo_edit_ids, checkpoint_id } carrying the FULL
     applied list, not a tail-edit marker — per D5, a single marker cannot represent
     undo-then-apply interleavings (documented on the type + exercised by a dedicated test).
   - HistoryLog gains `cursor: Option<HistoryCursor>`.
   - OpPayload doc updated: `binary` is no longer a reserved seam (was always None; now carries
     the OpBinary encoding whenever the caller has one).

2. 🔖️TextGrammar: cursor_spec() (keyword "cursor", `applied=[...] redo=[...]
   checkpoint=<id>?`), F_CURSOR_* consts, parse_ops_text "cursor" branch (last-wins, matching
   "active"), print_ops_text emits it last (after active). Text stays forwards-only for ops
   (backwards is `.spr`-only per D6) but cursor IS text-representable — proven by
   protocol/rs's compile_ops_decompile_ops_round_trip test extension (see item 6).

3. 🔖️Payloads/🔖️Edit: new write_op_payload/read_op_payload helpers (op_tag bit1 = binary
   present) shared by both edit.ops and the new backwards section. encode_edit sets presence
   bit5 + writes backwards iff `!edit.backwards.is_empty()` (purely data-driven — see D6-note
   below for why this differs from the design's literal `options.write_backwards_section &&
   !edit.backwards.is_empty()` phrasing). decode_edit reads bit5 symmetrically. Layout comment
   updated to reflect the real bit5/op-payload shape (previously "always 0 on write").

   D6-note (deviation, with rationale): the design's presence formula implied `encode_edit`
   itself should consult `EncodeOptions`, but `encode_edit`/`HistoryAppender::append_edit` are
   both per-edit functions with no `EncodeOptions` in scope (only `encode_history`, the
   whole-log batch encoder, takes it) — threading it through would touch the streaming
   appender's API for no benefit, since a streaming caller already has full control by simply
   choosing what to put in `edit.backwards` before calling `append_edit`. Implemented instead:
   `encode_edit` is purely data-driven (bit5 iff backwards non-empty); `encode_history` is the
   ONE place that applies `options.write_backwards_section` as a batch policy switch — when
   false (the default), it strips `edit.backwards` before encoding even if the caller's
   `HistoryLog` has it populated, so a caller can build a log with real backwards data and still
   choose not to persist it via one `EncodeOptions` flag. `HistoryAppender::append_edit` keeps
   its original signature; the streaming path's "policy" is simply whatever data the caller
   supplies per edit. This is a stricter/safer implementation of the same design intent, not a
   scope change — verified in dedicated tests (see item 8).

4. New 🔖️Cursor sub-region (extension record, D4): `REC_CURSOR = 0x40` (non-critical bit,
   extension range 0x40..=0x7E per protocol_core's frozen kind table; foreign/older readers
   skip via the crate's existing catch-all `_ => {}` unknown-kind arm — no protocol_core change
   needed). encode_cursor/decode_cursor mirror encode_active/decode_active's style, using
   write_id_field/read_id_field for edit-id dict/ordinal refs (consistent with every other
   edit-id reference in the crate).

5. encode_history emits REC_CURSOR (critical=false) after REC_ACTIVE when log.cursor.is_some();
   decode_history_from's match gains a REC_CURSOR arm (last-wins, same as REC_ACTIVE).
   HistoryAppender gains append_cursor (mirrors set_active).

6. protocol/rs/lib.rs facade: re-exports extended with HistoryCursor, REC_CURSOR,
   encode_history, decode_history, parse_ops_text, print_ops_text (also chips at G21, the
   facade re-export gap). compile_ops_decompile_ops_round_trip test extended with a cursor
   (proving the text-tooling path preserves it byte-for-byte) — backwards was NOT added there
   since it's `.spr`-only by design (D6).

7. Every `HistoryEdit`/`HistoryLog` struct literal fleet-wide fixed (compiler-driven,
   backwards: Vec::new() / cursor: None defaults): protocol/history/rs (3 sites, one shared
   sample_log() fixture used by ~15 tests), protocol/rs (2 sites), protocol/io/rs (1),
   protocol/materialize/rs (1), protocol/testkit/rs (2, the general-purpose HistoryLogGen used
   workspace-wide), protocol/cli/rs (1).

8. New tests (protocol/history/rs, extending existing 🔖️TextGrammar/🔖️Payloads/🔖️Codec/🔖️Append
   regions only, per repo convention — no new test files):
   - ops_text_round_trips_a_cursor_line_with_undo_then_apply_interleaving (proves D5's full-list
     rationale concretely: edit-1 undone then edit-2 applied, edit-1 precedes edit-2 in file
     order but only edit-2 is in `applied`)
   - ops_text_without_a_cursor_line_leaves_cursor_none
   - edit_payload_round_trips_a_backwards_section_mixing_text_and_binary_payloads (proves
     op_tag bit1 is independent per-payload, not per-edit)
   - edit_payload_with_empty_backwards_omits_the_section_and_decodes_empty (byte-level presence
     bit assertion)
   - cursor_payload_round_trips_with_dict_and_ordinal_refs /
     cursor_payload_round_trips_without_a_checkpoint
   - history_round_trips_backwards_and_binary_payloads_and_cursor_when_write_backwards_section_is_set
     (whole-file round trip, the law from the design's item 7 "whole-log round trip" test)
   - history_strips_backwards_when_write_backwards_section_is_unset_even_if_populated (proves
     the D6-note batch-policy behavior)
   - append_cursor_then_decode_recovers_it
