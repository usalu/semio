5. CARGO TEST STATUS
--------------------------------------------------------------------------------
`cargo test -p sequence_core -p sequence-plugin -p sourcing_curate -p sourcing-plugin --lib`: ALL
GREEN (63 + 15 + 16 + 16 = 110 tests passed, 0 failed).

`cargo test -p shooting-plugin --lib`: GREEN (31 passed, 0 failed).

`cargo test -p shooting --lib`: 15 passed, 2 FAILED —
  `tests::shooting_dsl_round_trips_representative_fixture`
  `tests::shooting_dsl_round_trips_base_icon_example`
Both fail with the identical pre-existing bug already independently diagnosed and documented by the
cad and draw wave-2 families (see wave2-cad.txt / wave2-draw.txt in this ticket folder):
`pack/value/rs/lib.rs`'s `Shape::Table` SoA codec (`encode_table`/`decode_table_soa`) is asymmetric
in its ELEM_FALLBACK per-column branch — `encode_table` threads the real column `Shape` through to
`encode_value`, but `decode_table_soa`'s mirroring branch calls `decode_value(reader, None, ...)`,
dropping it. For a `Shape::Tuple(_, Some(N))` column (a plain fixed-size-array field, e.g. `ShootingAsset.origin:
[f64; 3]` / `.orientation: Option<[f64; 4]>` inside the `#[dsl(table)] assets: Vec<ShootingAsset>`
column), the packed-f64 wire tag decodes back as `FieldValue::List` instead of `FieldValue::Tuple`
(shape-derived `is_tuple_shape` sees `None` and defaults false), so
`__dsl_from_record`/`[T;N]::from_value` rejects it with "expected a 3-item Tuple, found List(...)".
Confirmed this is table-column-specific, not a general Tuple-shape bug: `shooting_dsl_round_trips_empty_fixture`
(camera's `[f64;3]` position/target fields, a plain `#[dsl(block)]` field, NOT inside a table) passes
fine; only fixtures with non-empty `assets`/`saved_cameras` tables (whose row types carry array fields)
fail. `assert_dsl_round_trip` (pure DSL-text path, unaffected by pack's table codec) still passes for
both fixtures — only the newly-added `assert_dsl_pack_equivalence` pack leg fails.
`pack/**` is explicitly outside this family's allowed directories, so NOT patched. The two new
`assert_dsl_pack_equivalence` calls are left in place (not reverted) — per the wave-2 brief and the
cad/draw precedent, they are correctly detecting a real pre-existing bug, not a mistake in this
family's edits.

One unrelated flake observed and NOT investigated further: `cargo test -p shooting-plugin --doc`
intermittently fails with "extern location for vcs does not exist: .../libvcs.rlib" / "can't find
crate for semio_framework_plugin" — classic concurrent-workspace-build artifact churn (another
session rebuilding the shared `target/` mid-run), not reproducible on every run and unrelated to any
edit in this family (`--lib` test runs for the same crate are consistently green). Not pursued further.
