What was implemented
---------------------

1. RecordKinds region — the 16 db_wal record kinds as `pub const u8`, packed densely into the SPR
   extension range 0x40..=0x4F (WAL_SEGMENT_HEADER=0x40 .. WAL_MIGRATION=0x4F), plus
   `is_wal_record_kind(kind)`.

2. Records region — `WalRecord` enum, one variant per WAL_* kind, with `encode()`/`decode()`
   round-tripping through `pack_core::ByteWriter`/`ByteReader`. `Command`/`Diff`/`Inverse`/`Event`/
   `Outbox`/`Migration` carry opaque bytes verbatim (per the contract's "no db crate below
   db_document interprets operation semantics" rule); `SegmentHeader`/`TxBegin`/`TxCommit`/
   `TxAbort`/`Frontier`/`VcsRef`/`SnapshotPub`/`IndexCkpt`/`Lease` are structured since db_wal
   itself owns their meaning. `WAL_COMMAND`'s payload is the caller's envelope bytes with zero
   extra wrapping, matching the contract's "envelope-bytes-verbatim zero-copy" note. Every record
   is marked critical (no optional WAL record exists in this design). All length-prefixed fields
   are validated with `db_core::check_len` before allocating.

3. GroupCommit region — `GroupCommitPolicy { max_delay_ms, max_bytes, max_records }` with
   `is_due(...)`, defaults 20ms / 256KiB / 256 records (this crate's own choice — the contract
   fixes the delay/bytes/count mechanism, not the numbers).

4. Sink region — `SharedBuf`, a `pack_core::PackSink` over `Arc<Mutex<Vec<u8>>>`. This is the one
   real design deviation forced by `protocol::SprWriter`'s actual API surface (documented inline
   and below).

5. Recovery region — `protocol_err` (maps `protocol::ProtocolError` to `DbError`), `decode_records`
   (FrameCursor over a trusted byte prefix, decoding WAL_* frames and explicitly recognizing
   REC_COMMIT via protocol_core::REC_COMMIT rather than silently treating "not ours" as "must be a
   commit"), `WalRecoveryReport`, and the public `replay_document(storage, document)` free function
   that decodes a document's entire WAL (every sealed segment fully, the active segment's trusted
   prefix) in order.

6. Segment region — `SegmentWriter`: one live `protocol::SprWriter<SharedBuf>` held open for a
   segment's whole lifetime, `append_record`, `commit_and_flush` (real group commit: physically
   `SprWriter::commit()` + `WalStorage::append` of only the unflushed delta + `WalStorage::sync
   (class)`), and `tip_chain_hash()` (reads back the segment's last REC_COMMIT payload to seed the
   next segment's cross-segment chain link).

7. DocumentWal region — the crate's main public type. `create` (genesis segment 0),
   `open` (crash recovery — see below), `submit` (writes one `WAL_TX_BEGIN..WAL_TX_COMMIT`
   transaction, then group-commits per policy, forcing an immediate commit for
   `Fsync`/`Quorum` durability regardless of policy thresholds, and rotates to a new segment once
   `max_segment_bytes` — 16 MiB default — is crossed), `force_flush`, and the private `rotate`
   (seals the active segment after a final commit, reads back its tip chain_hash, begins a new
   segment with `WAL_SEGMENT_HEADER.prev_chain_hash` set to that hash — the cross-segment hash
   chain the contract calls for).

8. Tests region — 12 inline `#[test]` fns covering: record-kind range/uniqueness, full
   encode/decode round-trip for every WAL_* kind, malformed/unknown-kind decode rejection,
   `GroupCommitPolicy::is_due` threshold logic, a clean single-segment write→commit→flush→recover
   cycle (verified byte-exact via `protocol_format::recover`), group-commit batching (asserting
   nothing physically flushes until the record-count threshold is crossed, then that it does),
   `Fsync` forcing an immediate commit regardless of policy, a genuine torn-tail recovery scenario
   (garbage bytes appended directly to storage past the last commit, simulating a crash mid-write;
   `DocumentWal::open` truncates/rebuilds and `replay_document` returns exactly the pre-crash
   committed records), tx-id resumption across a recovery cycle, a multi-segment rotation test
   (forces several rotations via a small `max_segment_bytes`, independently recomputes segment 0's
   tip chain_hash and asserts segment 1's `WAL_SEGMENT_HEADER.prev_chain_hash` matches it, and
   asserts `replay_document` returns all 20 commands across both segments in original order), and a
   corruption-rejection test (a torn NON-active sealed segment must fail `DocumentWal::open` with
   `DbError::Corrupt`, since `truncate_tail` can only ever repair the active segment).

Dependency additions (Cargo.toml)
----------------------------------
Added two path dependencies beyond the stub's `db_core`/`db_storage`/`protocol`/`pack_core`, plus
`blake3`:

- `protocol_format = { path = "../../../protocol/format/rs" }` — the `protocol` facade re-exports
  `SprWriter`/`FrameCursor`/`ReverseFrameCursor`/`RecoveryMode`/`RecoveryReport`/`ProtocolError`/
  `ProtocolLimits`, but NOT the free functions `protocol_format::recover`/`parse_commit_payload` or
  the constants `COMMIT_FRAME_LEN`/`HEADER_SIZE`. db_wal genuinely needs all four (crash recovery;
  reading back a just-sealed segment's tip chain_hash to seed cross-segment chaining), and the
  contract explicitly names `recover` as one of the reused protocol primitives, so this looks like
  a re-export gap in the protocol facade rather than an intentional omission. Worked around it with
  a direct path dependency rather than duplicating protocol_format's recovery logic in db_wal.
- `protocol_core = { path = "../../../protocol/core/rs" }` — same gap for `REC_COMMIT` (used to
  positively recognize a commit frame while decoding/replaying, and while reading back a sealed
  segment's tip commit) and `REQUIRED_HASH_CHAIN` (every db_wal segment is now opened with that
  header flag set, making the hash-chain requirement explicit/reader-enforced rather than an
  implicit convention).
- `blake3 = "1"` — needed directly for the `chain_0 = blake3(header)` fallback in
  `SegmentWriter::tip_chain_hash` (the case where a segment has never committed past its own
  header — should not occur in practice since `SegmentWriter::begin` always commits the header
  immediately, but handled honestly rather than assumed away). Same version pin pattern already
  used by `db_storage` and `protocol_format`.

Design deviations / choices (all documented inline in lib.rs, summarized here)
--------------------------------------------------------------------------------
1. SprWriter has no accessor for its private sink and no "resume mid-stream" constructor (the same
   constraint protocol_io::HistoryFile::open_append documents and works around). db_wal solves the
   "keep writing AND read back what's been written so far, to flush only the new suffix to
   WalStorage" problem by holding one live SprWriter<SharedBuf> open for a segment's entire
   lifetime, where SharedBuf is a small Arc<Mutex<Vec<u8>>> PackSink this crate defines so a second
   handle can snapshot the buffer without consuming the writer.
2. Recovering an existing (possibly torn) active segment cannot resume the writer either — for the
   same reason. db_wal applies the identical O(segment size) workaround protocol_io documents:
   decode the trusted prefix into WalRecords, delete+recreate the segment, and replay every record
   through a freshly-begun writer (coalescing what may have been several original commits into
   fewer new ones — logically equivalent, since recovery only needs to restore the committed
   record set, not the original commit boundaries).
3. Cross-segment chaining is carried by embedding the previous segment's tip commit chain_hash
   into the new segment's WAL_SEGMENT_HEADER record (protocol's own hash chain necessarily resets
   at chain_0 = blake3(header) on every fresh SprWriter::begin, so this is the mechanism that keeps
   a document's WAL one verifiable chain across segment rotation).
4. GroupCommitPolicy's exact numeric defaults (20ms / 256KiB / 256 records) and
   DEFAULT_MAX_SEGMENT_BYTES (16 MiB) are this crate's own choice, as invited by the contract
   ("db_wal's own choice within this range" applies to the record-kind byte values; the
   delay/bytes/count numbers and segment size are likewise unspecified by the contract beyond
   naming the mechanism).

Extension seams left for later waves
--------------------------------------
- `DocumentWal` exposes `submit`/`force_flush`/`open`/`create` as a synchronous API driven by a
  caller-supplied `now_ms` (no internal clock, no background timer thread) — deliberately, so
  `db_actor`'s mailbox/scheduler (not yet consumed here) can drive real group-commit timing
  deterministically, including under `db_testkit`'s SimClock. No stub/TODO/unimplemented!() — every
  path is real and tested against `db_storage::MemoryStorage`.
- `WAL_PAYLOAD`'s CAS-ref variant encodes/decodes a `pack_core::ContentHash` but this crate does
  not itself decide when to inline vs. CAS-reference a payload — that policy call belongs to
  `db_document` (which owns `db_storage::PayloadStorage` access); db_wal only provides the record
  shape.
- `WalRecord::Frontier`/`SnapshotPub`/`Lease`/`IndexCkpt`/`VcsRef` are fully encode/decode-tested in
  isolation but not yet wired into any higher-level "publish a frontier checkpoint every N commits"
  policy — that orchestration is `db_document`'s/`db_snapshot`'s job, consuming `DocumentWal::submit`
  with these record kinds as ordinary payloads.
