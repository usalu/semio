Design summary (regions, in lib.rs order)
------------------------------------------
- Identity: `TenantId`, `Principal { actor: protocol::ActorId, tenant, roles }`,
  `check_tenant(principal, resource_tenant)` — hard tenant-isolation boundary, deliberately kept
  outside the policy engine so a policy misconfiguration can never leak cross-tenant.
- Scope: `Action { Read, Write, Admin }` (one flat action set, orthogonal to scope granularity);
  `AuthzScope { Database, Document, CommandKind, Object, Field, Historical, Preview }` — the
  seven granularities named in the contract row, each rendering to a canonical path-segment
  sequence (`segments()`) nested under `["db","document",<id>,...]` so a document-rooted `**`
  grant covers every scope kind under that document.
- Policy: `Effect`, `Decision`, `Grant` (role + glob pattern + action set + effect),
  `RoleBasedPolicy::evaluate` — default-deny; `"*"` matches one path segment, a trailing `"**"`
  (only valid as the last pattern segment — this crate's own choice for an unambiguous matcher)
  matches the remainder; explicit `Deny` always short-circuits over any `Allow`.
- Signing: `Signature`, `sign_message`/`verify_signature` wrapping the injected
  `protocol::Signer`/`protocol::SignatureVerifier` traits directly (no concrete scheme chosen by
  this crate, per the contract wording), plus a `ProtocolError -> DbError` category mapper.
- Replay: `ReplayGuard` — bounded per-actor sliding-time-window dedupe on `OperationId`, evicted
  both by time (`window_ms`) and by count (`capacity_per_actor`, oldest-first) so memory can never
  grow unboundedly under a hostile/buggy high-volume actor. Deliberately a cheap in-memory replay
  catch, not a permanent ledger — documented as relying on WAL sequencing (db_wal/db_document,
  not yet implemented in this wave) for durable dedupe beyond the window.
- Budget: `BudgetRegistry` — per-string-key token buckets (lazy refill on each `try_consume` call,
  no background timer) for DoS budgeting at any caller-chosen granularity (actor, tenant, command
  kind, ...).
- Redaction: `redact_fields` — structurally walks a `serde_json::Value` object, replacing every
  dotted field path the policy denies `Action::Read` on (scoped as `AuthzScope::Field`) with a
  `{"$redacted": true}` marker; never recurses into a denied subtree (so nested fields under a
  denied field can't leak); depth-ceilinged (`MAX_REDACT_DEPTH = 64`, redacts conservatively
  beyond it) as a stack-safety/hardening measure against adversarially deep payloads. Arrays are
  left as opaque leaves (not walked) — documented as a deliberate scope limit: array-element
  redaction would need index-stable paths, which is payload-schema knowledge this crate must not
  depend on (command payloads are opaque below db_document per the contract).
- Audit: `audit_decision`/`audit_replay_rejected`/`audit_budget_exceeded` — emit
  `security.authz_allowed`/`security.authz_denied`/`security.replay_rejected`/
  `security.budget_exceeded` events via `db_core::Emit` (the family's existing observability seam
  — db_security does not depend on db_observe directly, matching every other db_* crate below
  db_document).
- Gate: `SecurityGate` — the composition root bundling `RoleBasedPolicy` + `ReplayGuard` +
  `BudgetRegistry` + `Arc<dyn Emit>` behind `authorize`/`admit_command`/`redact`. Intended as the
  piece db_document's pipeline ("admit -> dedupe -> base-resolve -> authz -> ...") calls for its
  admit/dedupe/authz stages; every building block is also independently usable since a deployment
  may wire only a subset (e.g. no signing configured).

Deviations from the contract
------------------------------
- serde_json dependency addition — see above, only deviation from the literal deps column.
- No other deviations; every other design choice (glob pattern matcher shape, token-bucket
  refill model, replay window bounding, redaction marker shape, audit event names, Action's flat
  three-value set) is this crate's own choice where the contract says "your choice" or leaves the
  exact mechanism unspecified, each documented inline at its point of decision.

Extension seams deliberately left (no TODOs, no panics, no stubs)
--------------------------------------------------------------------
- `RoleBasedPolicy` is the only policy engine shipped (linear grant scan, default-deny + explicit
  deny). A more advanced engine (e.g. attribute-based policy, external policy service) is a
  drop-in alternative behind the same `evaluate(&Principal, &AuthzScope, Action) -> Decision`
  shape; not made into a formal `trait Policy` in this pass since `SecurityGate` only needed one
  concrete implementation and an unused trait seam would be a hollow abstraction per the
  "honestly scoped" instruction. Adding that trait later is a non-breaking refactor.
- Signing is fully wired (sign/verify + error mapping) but nothing in this crate calls it
  automatically — `SecurityGate` does not itself require signatures, since the contract frames
  signing as "via injected Signer/Verifier traits" (opt-in per deployment), and no upstream crate
  (db_document, db_wal) exists yet in this wave to define what message gets signed (a commit's
  chain_hash, most likely, per db_core::Frontier). `sign_message`/`verify_signature` are ready for
  db_document to call once it exists.
- Array-element field redaction is out of scope (documented above) — the marker-and-object-only
  walk is the correct, tested, honestly-scoped subset for this turn.
