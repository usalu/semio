db_storage_sqlite — CW4 implementation report
================================================

Scope: db/storage/sqlite/rs (single file lib.rs). No other crate/file touched.

What was implemented
---------------------
Replaced the stub lib.rs with a full db_storage::DbStorage backend over rusqlite (bundled),
implementing every sub-trait from db_storage's frozen trait family against one
rusqlite::Connection behind a Mutex:

  - WalStorage: per-document, per-segment_index rows in `wal_segment` (document, segment_index,
    bytes BLOB, sealed INTEGER). append() grows the blob in-place via `bytes = CAST(bytes || ?
    AS BLOB)`; truncate_tail() shrinks via `CAST(substr(bytes,1,?) AS BLOB)`. seal() is
    idempotent by relying on SQLite's `changes()` counting WHERE-matched rows regardless of
    whether the assigned value actually changed. sync() is a documented no-op (see durability
    choice below).
  - SnapshotStorage: `snapshot_generation` (document, generation, bytes), upsert via
    `INSERT ... ON CONFLICT(document, generation) DO UPDATE`.
  - PayloadStorage: `payload` (hash TEXT PRIMARY KEY = hex ContentHash, bytes BLOB, len INTEGER),
    blake3-hashed, `ON CONFLICT(hash) DO NOTHING` for put-is-idempotent-under-content-equality.
  - CatalogStorage: single-row `catalog_root` (id INTEGER PRIMARY KEY CHECK(id=0), bytes, epoch).
    cas_root() runs inside an IMMEDIATE SQLite transaction (real write-lock acquired up front),
    so — unlike db_storage::FsStorage's Mutex-only fencing (documented there as in-process-only)
    — this genuinely serializes concurrent cross-process writers against the same .sqlite3 file,
    not just concurrent threads in this process.
  - IndexStorage: `index_run` (document, run_id, bytes), same upsert pattern as snapshots.
  - LeaseStorage: `lease` (resource TEXT PRIMARY KEY, holder, epoch, expires_at_ms). acquire/
    renew/release all run inside IMMEDIATE transactions for the same cross-process CAS reason.
  - DbStorage: accessor methods returning `self` for every sub-trait, plus capabilities()
    reporting durable=true, max_durability=Fsync, supports_fsync=true, supports_cas=true.

The whole implementation lives inside a `#[cfg(not(target_arch = "wasm32"))] mod sqlite_storage`
inner module (re-exporting only `SqliteStorage`), matching the crate's own Cargo.toml which
already gates the `rusqlite` dependency under
`[target.'cfg(not(target_arch = "wasm32"))'.dependencies]` — a wasm32 build of this crate is an
intentionally empty shell, per the contract's "everything storage/thread-touching is
#[cfg(not(target_arch = "wasm32"))] module-wrapped" rule.

Design choices (contract left unspecified / this crate's own call)
--------------------------------------------------------------------
1. Durability: opened with `PRAGMA journal_mode=WAL` + `PRAGMA synchronous=FULL`. In WAL mode
   with synchronous=FULL, SQLite fsyncs the WAL file on every commit, so every write this crate
   makes is already at DurabilityClass::Fsync by the time the call returns, regardless of which
   class the caller requested. WalStorage::sync() is therefore a real, documented no-op — it can
   never under-deliver (Memory/Os requests are simply over-delivered), only skip doing
   unnecessary extra work. A perf-motivated future revision could relax `synchronous` and give
   sync() real work to do for batching Memory/Os-class WAL appends; left as an extension seam
   since this wave's goal was correctness, not throughput.
2. Cross-process CAS: CatalogStorage::cas_root and every LeaseStorage mutation open an IMMEDIATE
   SQLite transaction (acquires SQLite's real write lock before the read), which is a step up
   from FsStorage's own documented limitation (in-process Mutex fencing only, cross-process CAS
   flagged there as an extension seam). This crate's single Mutex<Connection> already serializes
   in-process callers; IMMEDIATE additionally serializes against other OS processes opening the
   same .sqlite3 file.
3. u64 -> SQLite INTEGER (signed i64): every u64 index/generation/run_id/epoch/timestamp is
   validated via `to_sql_i64` (i64::try_from) before being bound as a SQL parameter, returning
   DbError::LimitExceeded on overflow instead of silently reinterpreting the bit pattern as
   negative. In practice these values never approach i64::MAX, but this keeps the "validate
   before use" invariant real rather than assumed.
4. SQLite `||` (concatenation) type quirk: found and fixed during testing — concatenating the
   `x''` (zero-length BLOB literal) seed value from create_segment with a subsequent BLOB
   parameter via plain `bytes || ?` silently produced a TEXT-typed result (rusqlite's
   `row.get::<_, Vec<u8>>` then errors "Invalid column type Text"). Fixed with an explicit
   `CAST(... AS BLOB)` around both the append() concatenation and the truncate_tail() substr()
   call, so the wal_segment.bytes column always round-trips as BLOB. This is exercised directly
   by the `wal_storage_append_seal_truncate_and_bounds_laws` test, which failed before the cast
   and passes after.
5. No `pub` API beyond `SqliteStorage::{open, open_in_memory}` plus the trait impls — nothing
   about the schema, SQL, or rusqlite is exposed publicly, matching the "external libs behind an
   interface" / "never export a type outside this codebase" rules.

code) — no duplicate-native-library link error.

Extension seams left (deliberately, not stubs)
-------------------------------------------------
- WalStorage::sync() doing real (rather than already-satisfied) work for a relaxed-durability
  mode — noted above, would need a `synchronous=NORMAL` variant plus an explicit
  `PRAGMA wal_checkpoint` or per-call `synchronous` toggle.
- No incremental/streaming BLOB I/O (rusqlite's `Blob` API) for very large WAL segments/
  snapshot generations — every read/append currently materializes the full row value in Rust
  memory once, bounded by MAX_BLOB_BYTES (1 GiB, matching db_storage's own MemoryStorage/
  FsStorage ceiling). Fine at this crate's tested scope; a real perf pass for multi-hundred-MB
  segments would want incremental blob I/O instead.
Neither seam panics or returns Unimplemented on any reachable path — both are pure "could be
faster later" notes, not missing correctness.
