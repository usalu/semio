Key design choice: bypassing the (then-stub) `db` facade
----------------------------------------------------------
At the time this crate was implemented, `db` (db/rs/lib.rs) was still an empty scaffold stub with
no `pub` items — plausibly a concurrent wave's in-flight work. Per the task's instruction to not
block on a still-stub dependency and work against the frozen contract's described API instead,
every subcommand here is written directly against the already-real, contract-frozen APIs of the
individual crates it needs:
  - db_engine::Database / DocumentHandle for the actor-mediated subcommands (inspect, doc, query,
    compact, health, verify's catalog listing) — this is exactly the contract-frozen
    Database::{open_at, create_document, document, catalog, health, shutdown} /
    DocumentHandle::{submit, query, frontier, history, ...} surface, just reached via db_engine's
    own crate root instead of via db's re-export of the identical types.
  - db_storage (FsStorage + the WalStorage/SnapshotStorage traits), db_wal (replay_document,
    DocumentWal::open, WalRecord), and db_snapshot (SnapshotManager, open_latest,
    SnapshotDescriptor) directly, for the raw storage-level introspection subcommands
    (wal-inspect, snapshot-inspect, replay, repair) — these need lower-level access than the
    actor-mediated Database API exposes anyway (there is no Database method that lists WAL
    segments or snapshot generations). Notably, db_snapshot's own module doc explicitly names
    db_cli as an intended caller of SnapshotManager::materialize_chain, confirming this is the
    intended shape, not a workaround.
  - db_conflict + db_state back conflict-simulate (real db_conflict::ConflictDetector run over
    two hand-built CommandTouch values — a pure, local simulation, no storage touched).
  - db_cluster backs replica-simulate (the real db_cluster::replicate_document primitive, run
    locally between two FsStorage roots — no network transport exists anywhere in this family
    yet, which is exactly why this stays a "simulate" rather than a real cluster op).
  - protocol / pack supply the id / verification-level types those APIs are expressed in terms
    of.

After this crate was finished, a concurrent session did land the `db` facade (see this folder's
cw4-db.txt) as a straightforward glob re-export of the very same crates this file already depends
on directly — so every type this crate names (db_engine::Database, db_wal::WalRecord, etc.) is
now ALSO reachable as db::Database / db::WalRecord / ... through the facade. I left this crate's
imports as direct dependencies rather than churning them to route through `db` post-hoc: the
behavior is byte-for-byte identical (the facade is pure re-export glue over these same crates),
the direct-dependency version is already fully built and tested, and revising working, tested
code purely for cosmetic import-path reasons under this ticket's "don't touch other crates,
don't leave things half-verified" discipline seemed like the wrong tradeoff. Noting this
explicitly as the one deviation from the literal instruction to write "against the actual db
facade crate's Database API" — functionally equivalent, just reached one hop earlier in the
dependency graph.

    independently via `db verify` to confirm the copied commands are genuinely durable and
    trusted on the follower side, not just that replicate_document returned Ok.
