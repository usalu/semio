WHAT COULD NOT BE VERIFIED, AND WHY
-------------------------------------
`cargo check` / `cargo clippy` / `cargo test` / `cargo build --target wasm32-wasip2` could NOT be run
to completion in this sandbox. Root cause, confirmed NOT specific to this crate or this migration:

    error: linking with `cc` failed: exit status: 69
    note: You have not agreed to the Xcode license agreements. Please run
    'sudo xcodebuild -license' from within a Terminal window to review and agree to the
    Xcode and Apple SDKs license.

This blocks the native `cc` linker for ANY fresh link on this machine. Confirmed via a completely
unrelated control: `cargo new hello_test && cargo build` on a brand-new empty binary crate in the
ticket scratchpad fails with the IDENTICAL error. This is a pre-existing, machine-wide toolchain
gate — not something introduced by this migration, and not something fixable from within this
session (accepting an Xcode EULA requires interactive `sudo` I must not attempt).

Mitigations attempted, all still blocked by the same wall:
  - Isolated overlay's own fresh target/ dir → blocked.
  - `CARGO_TARGET_DIR` pointed at the shared root `target/` (to reuse already-linked artifacts) →
    got much further (reused hundreds of already-compiled crates, including real framework crates
    like `semio-framework-plugin`/`semio-framework-os-kernel-store-sync`) but still hit a handful of
    proc-macro/build-script crates (`bytemuck_derive`, `zerocopy-derive`,
    `semio-framework-os-kernel-infinite-canvas`'s build script) that had never been linked before in
    this exact profile/target combination.
  - Copied root's `Cargo.lock` into the overlay first (to force identical dependency versions, hoping
    for fingerprint-matched cache reuse) → same result, got further but not all the way through.
  - `--target wasm32-wasip2`, `--profile wasm-release` (the real plugin build pipeline's own
    settings) → same wall (build scripts still run on the HOST during cross-compilation, so they
    still need the native `cc` linker).
  - `SDKROOT` pointed explicitly at the on-disk `MacOSX.sdk` (bypassing the `xcrun` lookup) → no
    effect, `cc` itself still refuses until the license is accepted.
