# Deriving a semantic mutation vocabulary for one artifact

> ⚠️ **Never derive a verb from `📓️taxonomy.md` alone. The shape rules below are more specific and
> win over its general axis.**
>
> `📓️taxonomy.md` holds the general axis (what each verb means; scalar vs structured; addressed vs
> root). **This** file holds the shape rules — id-keyed collection, ordered collection, edge
> collection, hierarchy. When both seem to apply, the shape rule governs.
>
> Worked example of the trap, from a real peer-ticket derivation: tree re-parenting looks like a
> single scalar link field with identity preserved, so the general axis says `change-folder-parent`.
> Rule 5 below says `move-to-<container>{id,new_parent}`, and rule 5 wins. The peer's measurement
> and reasoning were both correct — only their rulebook was incomplete.

Applies to any of the 107 `🧬️mutations` facets under `✏️s/🔌️plugins/**`. Read the facet's
`🧬️schema/📸️snapshot/🦀️component.rs` first — the vocabulary is derived from the SNAPSHOT shape, not
invented. Use `📓️taxonomy.md` (same ticket folder) for the verb table and naming mechanics.

## Recipe

1. **Document-level scalars** (name/description/icon/settings on the snapshot root): `rename-<artifact>`
   for the identity field, `change-<field>` per remaining scalar, `update-<facet>` ONLY for an
   inseparable ≥2-field facet that's never meaningfully set one-field-at-a-time (validated together
   — e.g. analysis settings).
2. **Per id-keyed collection**: `create-<singular>`, `delete-<singular>` (+ `delete-<plural>` if the
   editor multi-selects), `rename-<singular>` if it has a name/key/code, `change-<singular>-<field>`
   per remaining scalar, `add-/remove-<singular>-<member>` per `Vec` field, `replace-<singular>-<payload>`
   per large structured field (geometry/mesh/body), `reorder-<plural>` only if list order is
   user-meaningful (drop it for id-keyed sets with no display order).
3. **Per index-keyed ordered collection** (no stable id — pptx slides/shapes, paragraphs, rows):
   `insert-<singular>{index FINAL}`, `remove-<singular>{index BASE}`, `reorder-<plural>{from,to}`,
   plus `edit`/`move`/`resize` for content/spatial fields per element.
4. **Per relationship/edge collection**: `connect-<nouns>{endpoints,payload}` ↔
   `disconnect-<noun>{id}`; a parameterization gets `bind`/`unbind` instead.
5. **Per hierarchy** (parent_id / nesting field): `move-to-<container>{id,new_parent}`; add
   `group`/`ungroup` only if the editor has a real grouping gesture; add `flatten`/`unflatten` only
   if hierarchy collapse is a real gesture.
6. **Document-level whole-content replace**: NONE inside the mutation enum. Whole-document load
   (file open, paste-over, load-example) is NOT a mutation — it goes through the store's non-history
   `reset` path. If unsure whether a gesture is "replace everything" vs "a big but targeted change",
   default to modeling it as the targeted semantic verb (usually `replace-<payload>` on one field, or
   several batched semantic mutations under one `Edit`), not a snapshot swap.
7. **Spatial fields**: absolute `move`, relative `drag` (only if the editor supports dragging),
   `resize` for extents. Don't collapse move+resize into one combined "transform" setter unless it's
   truly one atomic facet per rule 1's `update` exception.
8. Register any domain verb per `📓️taxonomy.md`'s "Domain verbs" section, with its inverse partner
   in the SAME enum.

## Per-mutation implementation shape (matches `#[derive(dsl_derive::Mutations)]`'s requirements)

```
🧬️mutations/
  🦀️component.rs        <- dispatch enum only: #[derive(..., dsl_derive::Mutations)]
                            #[mutations(snapshot = XSnapshot, diff = XDiff, schema = "x.doc")]
                            every variant = EXACTLY one unnamed field wrapping a payload struct
  <slug>/                 <- e.g. ✏️rename-layer/
    🦠️mutation/🦀️component.rs   <- payload struct + impl MutationKind<XSnapshot, XMutation>
                                     (SEMANTICS const, diff/inverse DELEGATE to the sibling leaves
                                     below, label(), target())
    🔺️diff/🦀️component.rs        <- pub fn diff(payload, base) -> XDiff  (REAL handcrafted logic)
    ↩️inverse/🦀️component.rs     <- pub fn inverse(payload, base) -> Vec<XMutation> (REAL logic)
    (mirror .ts files, non-stub)
```

The dispatch enum's `impl Mutation<XSnapshot>`/`impl SemanticMutation<XSnapshot>` are GENERATED by
the derive — do not hand-write them. If a variant doesn't fit the single-payload-tuple shape, the
payload struct is wrong, not the derive.

## Forbidden (see taxonomy.md for the full list — repeated here as the fan-out checklist)

Reject and rewrite on sight: `SetSnapshot`, `NoMutation`, `CollectionMutation<` in a public enum,
bare `Set<WholeObject>` variants, option-bag `Patch` structs used AS a mutation payload (fine as an
internal diff-fragment type), apply-and-capture diff bodies, `Vec`-arg pseudo-bulk on a singular
verb, index addressing where the same collection already has a stable id.

## Scale estimate (for wave sizing — not exhaustive, a starting guess per family)

~1,200 mutations total across ~107 facets (up from 447 triads today): kit/design-shaped domain
facets ~10–16 mutations each; architect program's ~70 CollectionMutation registers become ~245
(create/delete per register + register-parameterized header verbs + register-specific semantic
ops); stdio structured formats (pptx/docx/xlsx/ifc/dwg/…) ~8–16 each; stdio opaque media (png/mp3/
pdf/…) ~3–5 each (mostly `change-<metadata-field>`); remaining domain plugins ~8–20 each.
