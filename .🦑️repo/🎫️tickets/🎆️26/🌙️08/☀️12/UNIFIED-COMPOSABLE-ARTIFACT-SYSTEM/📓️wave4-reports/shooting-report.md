## What shooting was duplicating — and what it was NOT

Read the artifact root (`🗿️artifacts/🎥️shooting/🦀️component.rs`) and its full snapshot (`assets: Vec<ShootingAsset>`, `savedCameras: Vec<ShootingSavedCamera>`, `scene: ShootingSceneLighting`, `shots: Vec<ShootingShot>`, `activeShotId`, `activeAssetId`) before touching anything, per the dispatch brief. This plugin is a **3D icon/product-render studio** — 3D assets get framed by saved cameras and lit by scene lighting into a **shot list** (each shot: id/label/width/height/format/shape/background/camera ref). It is not a literal video or audio recorder.

Exhaustive greps (not just for the literal words `video`/`audio`, but `recording`/`capture`/`footage`/`waveform`/`clip`/`take`) across every `.rs` file in the plugin returned **zero hits** for anything video- or audio-shaped. There is no inline content of either shape to kill — composing empty stub children for `video`/`audio` would invent vocabulary the plugin has no use for. `📌️important.md`'s own "leave a facet empty rather than fabricate" precedent (for mutation triads unable to be authored conformingly) argues against fabricating composition slots by direct analogy; `🌍️gis`'s already-migrated `gismap` plugin sets the closest precedent for "compose only what's real" — its own `image` slot is real, typed, and **honestly always `None`** because gis has no basemap-capture content today.

The ONE genuine hit: `ShootingSceneLighting.emblem_base64: Option<String>` — a raw base64 PNG overlay, embedded verbatim in the document, decoded exactly once at render time (`shooting_scene_to_semio_drawing`, which fed the raw bytes straight into a `DrawNode::Image` for re-encoding, never inspecting a pixel). This is exactly the shape `s.stdio.semio.image` already generalizes — a genuine, non-forced `C:image` composition.

`table` was investigated and explicitly declined, not skipped for lack of effort: `assets`/`shots`/`savedCameras` ARE row-shaped collections, but each already has its own real, granular, non-duplicative collection-diff shape (`ShootingAssetsDelta`/`ShootingShotsDelta`/`ShootingSavedCamerasDelta` — `added`/`removed`/`patched`/`reordered`, `🔺️diff/🦀️component.rs`), sparse-built directly from `(payload, base)` at every one of their 20 mutation triads (create/delete/rename/reorder/patch × 3 collections). This is EXACTLY the shape `📌️important.md`'s own D2/Concern-B section asks the rest of the repo to move TOWARD (away from whole-collection-replace diffs), not away from. Flattening any of the three into a single composed `SemioTableSnapshot` child would force a whole-handle-replace diff shape (the migration recipe §8's "always-present slot" convention — a composed child field in a diff is `Option<ArtifactChild<S>>`, a single re-mint, not a sparse row delta), regressing real per-row add/remove/patch/reorder granularity into an all-or-nothing re-mint on every single edit. This is a concrete technical reason to decline, per the recipe's own allowance ("unless you find a concrete technical reason they can't — document precisely if so, don't generalize from one blocked field to the whole plugin"). Full reasoning is preserved verbatim in the artifact root's `🔖️Composition` doc comment for any future reader who wants to re-litigate it.

## What changed

### Composition machinery (new, artifact root)

`🗿️artifacts/🎥️shooting/🦀️component.rs`, new `🔖️Composition` region (placed after `🔖️Domain`, before `🔖️CollectionSupport`):
- `ShootingEmblemChild = store::ArtifactChild<SemioImageSnapshot>` type alias.
- `shooting_emblem_child_handle(content) -> ShootingEmblemChild` — content-addressed mint via `DefaultHasher` over `serde_json::to_string(content)`, `store::os_io::ArtifactDialect{artifact_kind:"s.stdio.semio", standard:"v1", subset:"image"}`, same shape as `process3d::brep_child_handle`/`gismap::gis_map_drawing_child_handle`.
- **Real bidirectional converters**, not stubs: `shooting_emblem_image_from_bytes(bytes) -> SemioImageSnapshot` (wraps raw bytes verbatim as one opaque `SemioImageFrame`, `width=height=bitDepth=0`, one `encoding=opaque-bytes` metadata entry) and `shooting_emblem_bytes_from_image(&SemioImageSnapshot) -> Vec<u8>` (exact inverse). **Documented honest boundary, not a shortcut**: the plugin never decoded the emblem's PNG pixels before this migration either — the sole reader passed raw base64-decoded bytes straight into a `DrawNode::Image` for re-encoding, never inspecting a channel value. Round-trips byte-identical because encode/decode never interpret the bytes as pixels.
- `shooting_base64_decode`/`shooting_base64_encode` — moved the pre-existing hand-rolled decoder here from the schema module (alongside the rest of the emblem machinery) and added the missing encode direction (the pre-migration field only ever needed decode).
- **Working scene**: `SHOOTING_EMBLEM_SCRATCH: thread_local! RefCell<HashMap<child_id, SemioImageSnapshot>>` — the `EngineRep`-shaped bridge every wave-4 exemplar uses since no `LinkResolver`/child-dispatch seam reaches `ArtifactApp::handle` yet (checked directly against `🔌️plugin/🦀️component.rs`, W1-owned, read-only — confirmed still absent). `shooting_set_emblem_from_base64(snapshot, base64)` is the sole WRITE path (decode → mint → cache → set field; `None`/empty clears the slot) — this migration found **no mutation triad that ever touched the emblem** (grepped `emblem` across every mutation triad directory: zero hits), so the working scene's write side is exactly this one function, called from fixture/test construction. `shooting_emblem_image`/`shooting_emblem_bytes` are the READ accessors every call site now funnels through; both fail soft to `None` on a cache miss (fresh process loading a persisted document, or a handle surviving a store-level undo/redo that bypasses `ArtifactApp::handle`) — documented, matching every prior exemplar's staleness gap.

### Snapshot / composed child

`📸️snapshot/🦀️component.rs`: `ShootingSnapshot` gains `emblem: Option<ShootingEmblemChild>` (state class `persistent` at the time this field was authored, mechanically renamed to `artifact` mid-session by an unrelated concurrent taxonomy rewrite — see `## Concurrent-churn observations` — currently `#[state(artifact)]`; `#[child(kind = "s.stdio.semio.image")]` — REQUIRED by the `ArtifactSchema` derive on every `ArtifactChild<T>`/`Option<ArtifactChild<T>>` field, confirmed by reading `🧬️schema/✨️derive/🦀️component.rs`'s `classify_composition_field`/`parse_child_kind`). `ShootingSceneLighting.emblem_base64` is REMOVED (`🗿️artifacts/🎥️shooting/🦀️component.rs`).

**Codec**: `ShootingSnapshot` itself never derived `dsl::DslRecord` (it was already hand-rolled, delegating to a `ShootingSnapshotDsl` mirror struct that DOES derive `DslRecord` for the readable `assets`/`shots`/`savedCameras` table grammar). Rather than drop that derive wholesale (which would have meant hand-rolling the ENTIRE document grammar — the mathematical/cad/writer/gismap/process3d approach, appropriate when the composed fields are the bulk of the struct), `ShootingEmblemChild` — the ONLY field needing special handling — is instead carried through the EXISTING derive as an opaque hex/bracket-encoded `Option<String>` (`emblem: Option<String>` on `ShootingSnapshotDsl`, converted via a new local `🔖️ChildCodecPrimitives` region's `enc_child`/`dec_child`, `[hex(child_id),hex(target.to_uri())]`). This is a deliberate, narrower application of the SAME "structured field via string" escape hatch the recipe endorses (§2's `enc_json`/`dec_json` convention) — applied to a two-field child handle instead of arbitrary JSON — and it means the pre-existing human-readable `assets [id:TEXT name:TEXT ...] {...}` table grammar for the plugin's real domain-specific collections is **completely untouched**, not regenerated into a JSON-hex blob format. `shooting_snapshot_from_dsl` changed signature from infallible to `Result<ShootingSnapshot, String>` (the new field can fail to decode); its two callers (`ShootingSnapshot::parse_dsl`, `::decode_pack_with`) updated to propagate via `store::TextError`/`store::PackError::Schema`. The `ArtifactPack`/binary codec needed **zero additional changes** — it's generic over the same derived `ShootingSnapshotDsl` record spec, so the new field rides through both text and binary codecs identically, verified by real round-trip tests (see `## Verification`), not assumed.

`ShootingArtifact` (`🧬️schema/🦀️component.rs`, the UI-inclusive full-state struct) got the identical field addition (`#[child(kind="s.stdio.semio.image")]` here too); `Default`/`to_snapshot`/`from_snapshot`/`set_snapshot` updated.

### Diff

`🔺️diff/🦀️component.rs`: new `emblem: Option<Option<ShootingEmblemChild>>` field — double-`Option` per the recipe's §8 "optional slot" convention (outer = did presence/identity change, inner = is it now present), matching lowpoly's `mesh`/`✳️object`'s established shape, NOT writer's single-Option "always-present slot" shape (the emblem genuinely can be absent). No `#[child(...)]` attribute needed/possible here: read the derive source (`unwrap_option` strips exactly ONE `Option` level, so `Option<Option<ShootingEmblemChild>>` classifies as `CompositionFieldKind::None` for schema-derive purposes) — same as the pre-existing `hovered_asset_id: Option<Option<String>>` field, already precedented in this exact struct.

`🔺️diff/📝️text/🦀️component.rs`: `apply_to_artifact`/`MutationDiff::apply` both gained `if let Some(value) = &self.emblem { next.emblem = value.clone(); }`; `absorb`'s `take!` macro list gained `take!(emblem);` — mechanically identical to how `camera`/`locale`/`hovered_asset_id` are already handled, no new logic needed.
