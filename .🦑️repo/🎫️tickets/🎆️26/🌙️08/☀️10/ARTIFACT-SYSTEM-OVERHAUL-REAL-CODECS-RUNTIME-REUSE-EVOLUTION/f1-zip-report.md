## Design

`ZipDiff { comment: Option<String>, entries: Option<ZipEntriesDiff> }`. `ZipEntriesDiff { removed: Vec<String>, modified: Vec<ZipEntryModified{name, diff}>, added: Vec<ZipEntryAdded{index, entry}> }`, name-keyed exactly per the worked design in `🧬️schema-design.md`. `ZipEntryDiff` covers all 13 non-key `ZipEntry` fields as `Option<T>`, including `name: Option<String>` for renames and tri-state `unix_mtime: Option<Option<i64>>`. `local_extra`/`central_extra` are whole-vec weak-list replacements (never sub-diffed), per the recipe's weak-entity rule.

**Absorb algorithm** (the hard part): φ (base name → mid name) is built directly from `self`'s own `modified[].diff.name` renames — for a name-keyed collection this is exact and needs no positional bookkeeping (unlike index-keyed collections, names are stable identifiers). `other.removed` names are resolved back to base identity through φ⁻¹; a name that matches one of `self`'s own `added` entries annihilates that add instead of surfacing as a base-level removal; a `other.modified` patch targeting a still-pending `self`-added name patches directly into the carried payload instead of becoming a `modified` entry. `added`-index bookkeeping (ψ) is the one place with a genuine, documented information limit: a name-keyed collection's `removed`/`modified` carry no position data, so when `other` removes an *untouched, unrenamed* base survivor, the merged diff cannot know whether that survivor sat before or after a surviving `self`-added item without the real base. The chosen (and tested) convention — decrement by the count of such removals — is exact for the recipe's own canonical case (`Insert`+`Remove`-*before*) and is the natural, simplest convention; the symmetric "remove-after" case is a documented approximation (see `deviations`). `apply()`'s three-phase algorithm (`retain` on names → `find`+patch on names → stable-sort-by-index-then-sequential-`insert`) is what makes "two inserts at the same target index" resolve correctly (stability guarantees the later-listed insert lands at the lower final position, matching real sequential mutation application) — this is the exact bug class the ticket flagged in gif 89a's old op-slot absorb.

`DiffAlgebra::inverse` is derived generically and correctly by construction: `Self::between(&self.apply(base), base)` — since `between` is the single source of truth for turning a state pair into a diff, this needs no per-field duplication and is trivially law-compliant as long as `between`+`apply` are mutually consistent (verified by `between_roundtrip_law`).

## Deviations

1. **Real, on-disk `cargo test -p semio-s-plugin-stdio --lib "artifacts::zip"` pass/fail count could not be obtained this session** — blocked by unrelated F1-sibling (txt/xml/csv/deflate) compile errors in files this artifact does not own, confirmed via 9 independent `cargo check` runs with zero zip-attributable errors each time. The wave's verify/closer stage should re-run the real filter once siblings land — expected to be a clean pass given the scratch confirmation and repeated zero-error `cargo check` on zip's own files.
2. **`ZipEntriesDiff.added` index bookkeeping under absorb is exact for `Insert+Remove-before` (the recipe's own canonical case) but is a documented best-effort approximation when an untouched, unrenamed base survivor removed by the second diff in fact sat *after* the pending add** — name-keyed collections' `removed`/`modified` lists carry no position information (unlike index-keyed collections, where the key itself is the position), so this is a genuine, inherent information limit of the key-kind, not an oversight. Documented in `ZipDiff::absorb`'s doc comment. All curated `absorb_law` test cases (including the recipe-mandated `Insert+Remove-before`, `Insert+Insert-same-index`, `Add+SetField`, `Add+Rename`, `Modify+Remove`, plus a rename-then-remove and an insert-then-annihilate case) pass exactly, along with triple-absorb associativity.
3. **Sub-format grammar mirrors left unhandcrafted**: only the two *wired* grammar leaves per facet (`📖️component.grammar.semio` for text, `📡️component.protocol.semio` for binary — the ones actually `include_str!`'d and exposed as `COMPONENT_GRAMMAR_SEMIO`/`COMPONENT_PROTOCOL_SEMIO`) were rewritten for `diff`/`mutations`. Their sibling mirror files in the same `📝️text/`/`💾️binary/` directories (`.g4`, `.ebnf`, `.ksy`, `.spicy`, `.abnf`, plus per-subdir `.ts`/`.json`/`.graphql` copies) still carry the old `payload = *OCTET`-style placeholder content — these are not registered/loaded anywhere at runtime (confirmed: `register_pilot_languages()` only wires the *snapshot* facet's text/binary grammars, never diff's or mutations') but were pre-existing in the `POLICY_GRAMMAR_HONESTY` seeded baseline and were deprioritized under time pressure in favor of the core Rust diff/mutation/absorb correctness work and the facet-level (`🟦️/🔣️/🔗️/🛰️`) mirrors, which were fully rewritten. Flagged here rather than left silently incomplete.
4. **Snapshot's own grammar leaves (`📸️snapshot/📝️text/*`, `📸️snapshot/💾️binary/*`) were not touched** — the ticket brief states the snapshot is already complete and out of primary scope; its `payload = *OCTET` in the DSL envelope grammar is arguably honest as-is (the envelope's body genuinely is an opaque hex blob of the full ZIP container at that grain — decoding the entire ZIP binary format at the envelope-grammar level would duplicate the engine's own domain).
