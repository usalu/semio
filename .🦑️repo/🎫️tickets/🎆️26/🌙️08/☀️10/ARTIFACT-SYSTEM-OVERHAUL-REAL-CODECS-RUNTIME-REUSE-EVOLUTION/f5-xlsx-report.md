## 2. Snapshot — redesigned from A1-string cells + eagerly-resolved text to the target `(row,col)`/typed-union/explicit-SST shape

Old model (pre-wave): `XlsxCell { reference: String /* "B2" */, value: XlsxCellValue }`, `XlsxCellValue { Number, Text, Bool, Empty }` (shared-string references and inline strings both eagerly collapsed into `Text` — the #1 xlsx decode gotcha the engine's own doc comment named but didn't actually avoid), `XlsxRow { index, cells }`, `XlsxSheet { name, rows }`, `XlsxWorkbook { sheets }` (no `shared_strings` field at all — the SST was rebuilt via dedup on every encode).

New model (`📸️snapshot/🦀️component.rs`), matching the brief's target shape exactly:
- `XlsxCellValue { Number(f64), SharedString(usize), InlineString(String), Boolean(bool), Formula{expr, cached: Option<Box<XlsxCellValue>>}, Empty }` — a real typed union over ECMA-376 §18.3.1.4's `t` attribute space. `SharedString(usize)` is never resolved to text at the snapshot level — the index is the truth, `workbook.shared_strings` is where you look it up.
- `XlsxCell { row: u32, col: u32, value }` — `row` is 1-based (the literal `<row r>` value), `col` is 0-based (matches `engine::column_letter`'s existing `0 -> "A"` convention, documented). `(row, col)` is the cell's identity.
- `XlsxSheet { name: String, cells: Vec<XlsxCell> }` — sparse, no `XlsxRow` grouping struct anymore (a real spreadsheet is mostly empty; grouping-by-row is now purely an engine-side XML-serialization concern, not a snapshot concern). `name` is the sheet's identity.
- `XlsxWorkbook { sheets: Vec<XlsxSheet>, shared_strings: Vec<String> }` — `shared_strings` is a genuinely new field; the SST is now index-keyed first-class state, not a derived encode-time artifact.

Engine (`⚙️engine/🦀️component.rs`) rewritten to match:
- `cell_to_xml`/`extract_cell_value` handle all five real cell shapes (`t` absent = Number, `t="s"` = SharedString by index, `t="inlineStr"` = InlineString, `t="b"` = Boolean, a `<f>` child present = Formula with `cached` re-typed from the same `<v>`/`t` pair). `t="e"` and non-formula `t="str"` normalize to `InlineString` — documented (the union has no dedicated bare-cell error/formula-string variant per the brief's exact enumeration; `Formula.cached` IS typed for the formula case).
- New `column_index` (inverse of the pre-existing `column_letter`) parses a cell's own `r="B2"` column-letter prefix into `col`; `row` comes from the enclosing `<row r>`.
- `worksheet_to_xml` groups the now-flat `sheet.cells` back into `<row>`-then-`<c>` XML via a `BTreeMap<u32, Vec<&XlsxCell>>`, sorted ascending on both axes (spec order, deterministic bytes).
- `regenerate_workbook_parts`/`decode_xlsx` pass `workbook.shared_strings` straight through to/from `xl/sharedStrings.xml` — no dedup-on-encode, no resolve-on-decode. The out-of-range shared-string-index bounds check (a pre-existing test) is preserved, now checked against `sst_len` rather than a `shared: &[String]` used for resolution.
- All 9 engine tests updated to the new shapes; a new `decode_resolves_real_hand_built_package_with_every_cell_type` test hand-builds real OOXML exercising all five cell-type XML shapes including a real `<f>`/`<v>` formula cell; a new `column_index_is_the_real_inverse_of_column_letter` round-trip test.

Builders (`🏗️builder/🦀️component.rs` at the `✳️any` subset level — the only level with real field-level construction, top-level/ecma-376 levels just delegate) updated: `add_row` now emits `XlsxCell { row: index, col, value }` directly into `sheet.cells` instead of building an `XlsxRow`.

## 3. Diff — real sparse, keyed, no `snapshot: Option<>` anywhere

`🔺️diff/🦀️component.rs`: the same `NamedTripleDiff<K, D, T>` generic engine docx's wave established (I did not need `IndexedTripleDiff` — xlsx has no genuinely index-positional collection at the top level; even `shared_strings`, which IS position-derived, is modeled through `NamedTripleDiff<usize, String, (usize,String)>` treating the enumerated position as a key, which produces identical pairwise-matching semantics while reusing one engine instead of two). Per-collection key choices (all documented in the diff module's doc comment):
- `sheets`: `NamedTripleDiff<String, XlsxSheetDiff, XlsxSheet>` — name-keyed (`name` is the sheet's real identity; rename is remove-old+add-new, documented, same category as docx's OPC-part-rename gotcha).
- `cells` (within a sheet): `NamedTripleDiff<(u32,u32), XlsxCellDiff, XlsxCell>` — coordinate-keyed, per the brief's own suggestion that "a sparse spreadsheet probably wants keyed-by-coordinate, not index-positional." This is a TRUE identity key (unlike `shared_strings`), so a single same-direction `between()` call over `cells` CAN show removed+modified+added simultaneously (verified in `field_sweep` — no "structural trap" there).
- `shared_strings`: `NamedTripleDiff<usize, String, (usize,String)>` — index-keyed, pairwise-position-matched (same category as an `IndexedTripleDiff` would be) — DOES hit the "known structural trap" (a same-direction `between()` can show removed XOR added, never both), handled the same way docx/svg handled it: split assertions across `between(a,b)`/`between(b,a)` in `field_sweep`, with differently-sized `sweep_a`/`sweep_b` shared-string tables.
- `XlsxCellDiff { value: Option<XlsxCellValue> }` — the cell's `value` (a value/weak union per the recipe) is whole-value replaced, never sub-diffed field-by-field (its own `Formula.cached` nests another `XlsxCellValue`, so sub-diffing would need a second recursive diff type for no real semantic gain over LWW-replace — documented in the diff module).

`XlsxDiff { opc: Option<XlsxOpcDiff>, workbook: Option<XlsxWorkbookDiff> }`, `XlsxWorkbookDiff { sheets: Option<XlsxSheetsDiff>, shared_strings: Option<XlsxSharedStringsDiff> }`. `impl MutationDiff<XlsxSnapshot> for XlsxDiff { apply, absorb }` + `impl DiffAlgebra<XlsxSnapshot> for XlsxDiff { inverse, between, is_empty }`, both real, no full-replace fallback anywhere. Verified: `grep -n "snapshot: Option<"` on the diff file → zero hits (real code, not even a doc-comment mention this time).

**Three real bugs found and fixed via the test laws (not test-only artifacts — genuine defects in the diff construction, caught before this report was written):**

1. **`diff_set_shared_string`'s no-op-instead-of-append gap**: its fallback branch unconditionally built a "modified" (patch-in-place) diff entry even when the target index didn't exist yet — since `apply_named`'s modify step only patches an item that's already present, this silently no-op'd instead of restoring anything. `RemoveSharedString`'s mutation-level inverse (`SetSharedString` at the removed index) therefore failed to restore the shared string whenever the removed entry had been the LAST one (the common, and only exactly-recoverable, case — same category as docx's `RemovePart` caveat). Fixed by special-casing `index == strings.len()` as an `added` entry (a genuine append), distinct from both the "existing index, patch" case and the genuine-gap "index > len, no-op" case (the recipe's own graceful-out-of-range-key convention). Caught by `shared_string_mutations_apply_and_inverse` and `inverse_law`.
2. **`opc.parts` root-part ordering**: `regenerate_workbook_parts` originally `set_part`'d `WORKBOOM_PART` (`xl/workbook.xml`) LAST (after shared strings and every worksheet). Because `opc.parts` is a name-keyed `Vec` reconstructed via the position-preserving-survivor convention (survivors keep their CURRENT position, new items append at the end — same documented convention as docx's content-types-overrides caveat), composing two INDEPENDENT `between()` diffs against structurally different snapshots (exactly what `inverse_law`'s `SetSnapshot{sweep_b()}` case does against `fixture()`) reconstructed `opc.parts` in the wrong order even though every individual part's content was correct. Fixed by reordering `regenerate_workbook_parts` to `set_part` the root part FIRST — every snapshot this engine ever builds now agrees on "the part two arbitrary snapshots are most likely to share" sitting at a stable position, which is what makes the two-hop round trip land on the exact original `Vec` order, not just content. Caught by `inverse_law`.
3. **Test-fixture owner-key collision, not an engine bug**: `sweep_a`/`sweep_b`'s synthetic "modified relationships owner" test case originally reused the owner key `"xl/workbook.xml"` — the SAME key the real engine always populates with a multi-entry (one-per-worksheet-plus-SST) relationship list. When `inverse_law` diffed `sweep_b()` against an engine-built `fixture()`, this collision triggered the identical partial-overlap-Vec-order limitation as bug #2, but for a nested `HashMap` value the engine's own construction order can't fix (unlike the top-level `opc.parts` case, `relationships["xl/workbook.xml"]`'s content is inherently sheet-count-dependent, so there's no single "put X first" fix). Retargeted the synthetic case to the (collision-free) owner `"xl/toModify.xml"` — this keeps `field_sweep`'s `relationships.modified` coverage genuine while making the fixture/engine-snapshot combination a clean whole-owner remove+add (captured/restored atomically, order-exact by construction) instead of a lossy partial-overlap modify. Caught by `inverse_law`.
4. **Two test-only fixes** (same documented last-position caveat as docx's `RemovePart`, not new bugs): `remove_sheet_inverse_restores_removed_sheet`/`rename_sheet_apply_and_inverse` (and `sample_mutations()`'s own `RemoveSheet`/`RenameSheet` entries) originally targeted `"Sheet1"` (first of two sheets) — `sheets` being name-keyed means a mutation-level inverse reconstructed via `InsertSheet` (always appends) only reproduces the EXACT original position when the removed/renamed sheet was already LAST. Retargeted to `"Sheet2"`.

## 4. Mutations — 9 variants (up from 2), every `diff()`/`inverse()` handcrafted

`🧬️mutations/🦀️component.rs`: `NoMutation`, `SetSnapshot`, `InsertSheet`, `RemoveSheet`, `RenameSheet` (name-is-identity remove+add at the diff level, mutation-level inverse just swaps `name`/`new_name`), `SetCell`/`RemoveCell` (addressed by `sheet_name` + `(row, col)`), `InsertSharedString`/`RemoveSharedString`/`SetSharedString` — exactly the brief's target vocabulary. Every variant's `diff()` calls a dedicated `diff_*` constructor in the diff module (never apply-and-capture); every variant's `inverse()` looks up prior state from `base` (key/coordinate-aware). `apply_xlsx_mutation` is the single `let d = mutation.diff(snapshot); *snapshot = d.apply(snapshot); d` semantics source.

Also fixed the `📄set-snapshot` triad leaf (`🧬️mutations/📄set-snapshot/🔺️diff/🦀️component.rs`) — its `diff(snapshot)` helper called `diff_set_snapshot` with the old 1-arg signature (a pre-existing compile error once the diff module's own signature changed to `between(base, next)`); updated to `diff(base, snapshot)`, same fix docx's wave applied to its own triad leaf.

## 5. Test laws — all 6 present, real, in the mutations test module

`mutation_diff_law`, `inverse_law`, `absorb_law` (four canonical cases: annihilated-add for a fresh cell, both-survive for two independent cell adds, patch-into-added for a same-coordinate re-set, modify-annihilated-by-remove, plus associativity over a 3-diff chain), `between_roundtrip_law`, `codec_retention_law` (exercises every `XlsxCellValue` variant including a real `Formula` with cached result), `field_sweep`.

`field_sweep`'s `sweep_a`/`sweep_b` differ in every mutable field across BOTH `opc` (content_types defaults+overrides, parts, relationships-by-owner, each one removed/modified/added) and `workbook` (`sheets`: one removed, one added, one modified whose OWN `cells` diff shows removed+modified+added TOGETHER in one direction since `(row,col)` is real identity — no structural-trap split needed there; `shared_strings`: DIFFERENT lengths between the two fixtures per the "known structural trap" note, split across `between(a,b)` [removed+modified] and `between(b,a)` [added+modified]).
