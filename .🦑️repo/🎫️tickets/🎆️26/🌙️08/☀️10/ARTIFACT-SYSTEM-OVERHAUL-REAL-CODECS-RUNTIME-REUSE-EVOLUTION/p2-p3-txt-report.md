## 1. Headline finding: both binary codecs were ALREADY real before this wave

Per the mission brief's own hint ("check whether that means real binary op/diff frames may
ALREADY exist... and just need protocol-file documentation rather than fresh Rust work") — verified
by direct reading of the derive macros and the runtime helpers they call, not assumed:

- **`OpBinary::encode_op`/`decode_op`** (`🧬️mutations/🦀️component.rs`) forward straight to
  `dsl::variants_binary::encode_op`/`decode_op` (`🗣️dsl/🦀️component.rs`'s `OpRt` region), which
  itself calls `os_pack::encode_record_body`/`decode_record_body` — **never** `print_op().into_bytes()`.
  Confirmed empirically: `TxtMutation::NoMutation.encode_op() == [1, 0, 0, 0]` (format byte, ordinal
  varint, empty record body) — clearly not text bytes.
- **`DiffCodec::encode_diff`/`decode_diff`** (derive-generated by `#[derive(dsl::DslDiff)]`,
  `🗣️dsl/✨️derive/🦀️component.rs`'s `DslDiff` region) call `store::pack_rt::encode_document`/
  `decode_document` — **never** `print_diff().into_bytes()`. Confirmed empirically: a real
  `TxtDiff::encode_diff()` call starts with `[0x89, 'S', 'P', 'K', 0x0D, 0x0A, 0x1A, 0x0A, ...]` —
  the `.spk` pack-container magic, not JSON/text bytes.

**Neither `diffcodec_binary_upgraded` nor `opbinary_binary_upgraded` was needed** — both were
already genuinely binary. This wave's real work was documenting these real layouts in the
`.protocol.semio` files (which were still pre-F6 `body = utf8-json-string(eof)` fossils) and
writing the conformance tests/fixtures that prove it, not writing new Rust.

## 2. Grammar files rewritten (3)

- **`🧬️schema/📸️snapshot/📝️text/📖️component.grammar.semio`** — real DSL text form: envelope-mark
  (`"stdio.txt"`, matching the m5 harness's own envelope-id normalization convention every sibling
  artifact's grammar already follows) + `body = REST` (M1's raw-span, whole-body-to-EOF terminal —
  the ONE primitive built for exactly this case). This ports the artifact's OLD, unparseable ABNF
  placeholder — already called the single most conceptually accurate handcrafted grammar in the
  whole stdio set by Phase 1's own final-gate audit — into the real, parseable dialect,
  field-for-field.
- **`🧬️schema/🧬️mutations/📝️text/📖️component.grammar.semio`** — real one-line `OpText` grammar
  matching `TxtMutation`'s GENERIC `dsl::DslOps`-derived `print_op`/`parse_op` (no per-artifact
  custom printer — verified against real output for all 7 variants via a temporary debug test,
  removed before finishing). Same mechanism/conventions as sibling `stdio.zip`'s own already-real
  mutations grammar (copied its documented conventions). Unlike zip's own `SetSnapshot`/`AddEntry`
  (honestly modeled as `REST` — genuinely unbounded recursive nesting), `TxtSnapshot`'s own
  `#[dsl(block)]` payload is flat (4 scalar/single-level-list fields) so `SetSnapshot` is modeled
  **precisely, field for field**, not as an opaque `REST` fallback.
- **`🧬️schema/🔺️diff/📝️text/📖️component.grammar.semio`** — real one-line `print_diff`/`parse_diff`
  grammar matching `TxtDiff`'s derive-generated `DiffCodec` exactly (verified against real output
  for the empty diff, a scalar-only diff, and a diff exercising `TxtLinesDiff`'s full
  `removed`/`modified`/`added` triple simultaneously). No leading keyword (the derived
  `RecordSpec::keyword` is `None` for a struct diff with no container attribute).

## 4. Mechanism gaps found (recorded, worked around locally, none blocking)

Both below are **new findings specific to the derive-driven binary path** (P1's csv/json pilots
never hit this — their DiffCodec/OpBinary are hand-rolled with simple explicit layouts, not routed
through the framework's generic record/document encoders):

| id | engine_area | symptom | blocking |
|---|---|---|---|
| `txt-opbinary-record-body-wire-is-framework-generic` | protocol/pack | Past `OpBinary`'s own `format`/`ordinal` header, the remaining bytes are `os_pack::encode_record_body`'s own wire: a varint-prefixed STRING-SYMBOL TABLE followed by a self-describing, per-field-ID TAG+value encoding (`🎒️pack/🔢️value/🦀️component.rs`). This is NOT expressible by the protocol dialect's current `Array`/`Ref`/`repeat` primitives (no dynamic per-field-id tag dispatch, no symbol-table back-reference resolution) — the same root cause as P1 csv/json's own `csv-nested-record-array-unwalkable` gap, one level more fundamental here since it's the record-body wire ITSELF, shared verbatim by every `#[derive(dsl::DslRecord)]`/`DslOps`/`DslDiff` type in the repo, not anything artifact-specific. Worked around: `format`/`ordinal` genuinely, individually byte-walked; the record-body tail is one opaque `bytes` segment, same "opaque only where honestly irreducible" carve-out the plan already grants a compressed payload. | false |
| `txt-diffcodec-spk-container-is-framework-level` | protocol/pack | `#[derive(dsl::DslDiff)]`'s `encode_diff` routes through the FULL `.spk` document container (`store::pack_rt::encode_document`) — a real, checksummed, chunk-table-indexed, backward-scanned-footer (`FOOTER_MAGIC = "SPKFOOT1"`), optionally-deflate-compressed random-access file format (confirmed `REQUIRED_COMPRESSED` genuinely set on real output), not a lightweight per-message frame. The 32-byte fixed superblock header IS modeled precisely; everything past it (segment table, symbol table, the deflate-compressed record body, the 84-byte footer) is the SAME category of complexity M2 already excluded for DWG's compression pipeline and PDF/1.7's full indirect-object graph — an imperative checksum/compression-driven transform, not a declarative fixed layout. **This affects every future `#[derive(dsl::DslDiff)]`-derived diff type in the WHOLE Phase 2 program**, not just txt — a framework-level `pack_format.protocol.semio` file (mirroring M3's own `semio.envelope` precedent) would let every future artifact's own diff-protocol file `use` it instead of re-deriving this same opaque-tail treatment per standard. Recommended for a future M-wave, out of this per-artifact ticket's ownership boundary. | false |
