## Domain-verb → family mappings (with rationale)

- CAD `create-<x>-model` (energy/structure-classic/building/shape, singleton composed
  child slot, 4 leaves): mapped to **change/set** family, NOT `create`'s duplicate-id
  Fatal — the leaf's own docstring says overwriting an occupied slot is INTENDED
  design ("If the slot was already occupied, this OVERWRITES it"), so there is no
  "already exists" error concept, only Warning `no-op` when the candidate child
  already equals the current slot value.
- CAD `delete-<x>-model` (4 leaves): mapped to **clear** family, NOT `delete`'s
  target-missing Error — it's a single nullable slot, not an id-keyed collection
  member; the leaf's own docstring already called this "Idempotent (a no-op if
  already empty)", matching `clear ⇒ Warning no-op when already empty` exactly.
- CAD `create-drawing`/`delete-drawing`: real `create`/`delete` family (id-keyed
  collection) — Fatal duplicate-id / Error target-missing, unlike the model slots
  above, because `drawings` is a genuine `Vec<ArtifactChild>` collection.
- CAD `change-active-model-definition`: root scalar selector, no target — `change`
  family's Warning no-op only (no Error/Fatal possible, nothing to be "missing").
- CAD `replace-references`: `replace` family — Warning no-op when the new list already
  equals the stored one; no target-missing (the map key is a free string, always
  insertable, matching "genuinely nothing to check" for that half of the check).
- Trinity jack `change-data-property`/`remove-data-property`: mapped `change`/`remove`
  family's target-missing to the ENTITY (node/edge), not the property key — a missing
  property key on an existing entity is a genuine value-doesn't-exist state, so
  `change-data-property` treats "no such key yet" as a real change (not no-op, sets
  it), and `remove-data-property` treats "key already absent" as `no-op` (added
  enrichment beyond the bare `remove ⇒ Error` table row, since removing an
  already-absent key is naturally idempotent).
- Trinity jack `create-edge`: `create` family's "Fatal invariant on unknown container"
  mapped to a dangling-endpoint check (Fatal `mutation.invariant` when either
  `source`/`target` port's node id doesn't exist in the scene) alongside the normal
  Fatal `duplicate-id` on edge id collision.
- Trinity rewrite `remove-parameter-binding`/`remove-rule-layout-point`: mapped
  `remove`'s Error target-missing to **clear**'s Warning no-op instead — both are
  per-key removals from an unconstrained-key `BTreeMap` on a root document (no owning
  entity that can itself be "missing"), and the triad's own docstring already says
  "`None` signals a clear". Verified safe: `assert_mutation_inverse_law` calls in this
  facet's own `🔖️MutationLaws` region pass a `"ghost"` (never-existing) key through
  both remove leaves and assert `!rejected` (Error/Fatal only) — had I mapped these to
  Error, those pre-existing tests would break.
- Trinity rewrite `edit-rhs`/`edit-lhs`/`edit-before-fixture`: root scalar JSON bodies,
  no target — `edit` family's Warning no-op only, matching `change-active-model-
  definition`'s reasoning above.
- Energy `replace-model`: root-scoped composed-children overwrite, no target. Verb is
  `replace`, but per-leaf malformed-JSON handling is EXPLICITLY documented (ticket
  26/08/12/UNIFIED-COMPOSABLE-ARTIFACT-SYSTEM) as "honest degradation to
  `Model::default()`, never a panic" — turning that into a Fatal `mutation.invariant`
  would fight that documented, pre-existing product decision from another ticket, so
  this leaf is a deliberate message-free `MutationOutcome::new(diff)`, using the
  contract's own "root-scoped ... kinds may legitimately return message-free outcomes
  if there's genuinely nothing to check" allowance.

## Identity-diff config/presence mutations (CadConfigMutation, CadPresenceMutation,
JackConfigMutation, JackPresenceMutation, RewriteConfigMutation, RewritePresenceMutation,
HomeConfigMutation, HomePresenceMutation, SpaceConfigMutation, SpacePresenceMutation)

These 10 hand-written `impl Mutation<P>` blocks all have `type Diff = P` (the "diff" IS
the whole next state, `MutationDiff::apply` is identity `|self, _base| self.clone()`).
This is architecturally distinct from the sparse-patch `XxxDiff` types (`CadDiff`/
`JackDiff`/etc.) used by every mutation-KIND leaf: for a sparse-patch type,
`Default::default()` really does mean "no change" when applied, but for an
identity-diff type it means "reset every field to its baseline default" — genuinely
destructive. I verified against the lane's own verified working exemplar
(`🕸️dag/.../✏️editor/🎚️config/🦀️component.rs` `DagConfigMutation::diff` and
`.../👥️presence/🦀️component.rs` `DagPresenceMutation::diff`, both DONE by the lane
owner) that the correct, safe pattern for these types is:
  - NEVER use `::empty()`/`::error()`/`::fatal()` (they hard-code `diff =
    D::default()`, which would silently wipe the whole config/presence state).
  - `.warn()`/`.info()` ARE safe — they don't touch the diff, only append a message —
    so I used `MutationOutcome::new(base.clone()).warn("mutation.no-op", ..)` for
    CadConfigMutation/CadPresenceMutation/HomeConfigMutation's `Snapshot`/
    `SetContributions` arms (diff = the unchanged current state, safe to apply).
  - For the many-variant `JackConfigMutation`/`RewriteConfigMutation`/
    `SpaceConfigMutation` (10-14 `Set*` variants each), I matched the DAG exemplar's
    own choice exactly: unconditional `MutationOutcome::new(next)`, no no-op
    enrichment — adding a no-op branch per field would have meant per-field equality
    checks I couldn't verify compile (see cargo-check blocker below), and the
    exemplar itself didn't bother, so I didn't either, for consistency and safety.
