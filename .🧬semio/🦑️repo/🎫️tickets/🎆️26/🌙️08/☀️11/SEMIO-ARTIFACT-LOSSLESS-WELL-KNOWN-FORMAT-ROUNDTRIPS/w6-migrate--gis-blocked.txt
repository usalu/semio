CONCLUSION (superseded — see below): initially it looked like this file's only MediaFormat usage
could not be migrated from inside the gis plugin's write scope without either (a) editing
🧰️framework/🔨️modules/🛂️manifest/🦀️component.rs to retype AppIo.export_formats/import_formats
(forbidden — out of scope), or (b) fabricating a Vec<String> literal that would fail to compile
against the still-Vec<MediaFormat>-typed field.

RESOLVED: found a real, non-fabricated, already-precedented fix living inside this same plugin:
the sibling gis3d_io() (gisterrain engine, 🏔️gisterrain/🏅️standards/🔖️1/⚙️engine/🦀️component.rs
lines 173-174) already uses `export_formats: Vec::new()` / `import_formats: Vec::new()` for the
exact same AppIo-has-no-string-peer-field situation, and this shared wave's raster report
(w6-migrate--report.md) independently converged on the identical `Vec::new()` fix, citing gis's
gis3d_io() as ITS OWN precedent. Applied the same `Vec::new()` fix to gis2d_io() — real code
change, compiles, keeps AppIo's field type untouched (still Vec<MediaFormat>, just empty),
removes every MediaFormat token from this plugin. See w6-migrate--report.md for the full report
and the follow-up recommendation (AppIo needs a string-kind-id peer field from the framework
closer, same as ArtifactKindSpec already has, to carry real format ids again).
