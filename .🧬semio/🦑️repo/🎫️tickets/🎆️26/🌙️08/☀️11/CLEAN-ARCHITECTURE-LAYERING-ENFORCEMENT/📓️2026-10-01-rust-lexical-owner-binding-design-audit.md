# Rust Lexical Owner Binding Design Audit

Read-only design audit on 2026-10-01. No production edits, new tests, Cargo execution, describe/generation or runtime launches. Root owns policy and implementation. Native High owns compiler scheduling. This proposed semantic path census is separate from the current physical `#[path]`/include input census; neither this report nor the new physical scope claims that FEM's lexical imports are now enforced.

## Actual Reusable Owners

The owned syntax implementation is `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🔍️discovery/🟦️.ts`. `rustTokens` at line 6334 and `rustTokenPairs` at 6440 already discard literal/comment decoys and preserve token start/end offsets. `inspectRustModuleGraphFacts` at 8440 returns module, import/reexport and include facts. `RustModuleUseFact` at 6160 has modulePath, specifier, relation, visibility and conditional state, but no source span. Its parser visits item/module scopes and deliberately skips bodies of other items. It therefore cannot inventory fully qualified crate paths in expressions, signatures inside impls, function-local imports or their shadowing by merely adding a consumer loop.

The existing private `rustUseAliases` at 8202 expands nested use trees, renames, self branches and globs. Mutation metadata facts additionally record `extern crate` aliases. That narrow proof discards underscore aliases and rejects conditional routes; these are inappropriate omissions for a complete source dependency census. `use provider::Trait as _;` still imports a trait and creates a dependency. Conditional syntax still belongs to the all-configurations gate even when it does not establish one unconditional metadata declaration.

`inspectRustModuleGraph` at 8378 supplies file-membership-proven contexts: crateRoot, manifestPath, modulePath, sourceScope, moduleBase and sourceChain. A physical file can have multiple contexts, including `include!` expansion into another file's module. Preserve every actual context; choosing a nearest filesystem manifest or the first named crate would hide FEM's compilation inside two separate artifact packages. Graph target keys are rooted by compilation root plus logical module path; contexts must be joined on crateRoot and manifestPath as well as sourceScope.

The Cargo source projection owner is the same discovery file: `projectCargoProviderManifest` at 12023 already projects normal/dev/build and target-specific declarations, inherited workspace dependencies, package overrides and explicit library facts through the repository-owned `CargoProviderTomlParser` interface. `resolveCargoProviderBinding` at 12163 provides no-follow physical path authority and actual extern-name evidence. Its current contract deliberately accepts only one unconditional normal local dependency, uses repository `Cargo.toml` as governing workspace, rejects nested workspace disagreements, requires explicit provider lib name/path and excludes opaque paths. It cannot be called unchanged for every native crate context, dev/test, target cfg, implicit default lib or bridge standalone workspace and then suppress its failures.

Cargo direction inventory under `🕸️dependencies/🧭️direction/🦀️cargo/🟦️.ts` already understands authored workspace authorities, all dependency kinds, optional activation, target declarations and dependency/package aliases. Reuse that source authority rather than introducing a second differently classified package universe. Its package owner paths establish the target's real taxonomy owner; extern name still needs actual library identity, not only package-name hyphen replacement.

## Smallest Complete Extension

Add a separate lexical binding facet adjacent to physical Rust source direction, using the owned tokenizer and graph. Schema/fixture ownership belongs under the corresponding Repo Library taxonomy facet. Do not overload `RustCompileReference` with symbol paths or inflate physical include counts with semantic references.

The parser contract should return source-spanned facts with exact module and block scope, condition provenance and syntax kind: use-tree leaves including `_`/glob; extern crate/self aliases; module/type/type-alias/trait declarations; type and expression paths; macro invocation paths; qualified-self trait paths; local type parameters and value/pattern bindings that can shadow the leading identifier. Preserve leading `::`, raw-identifier canonical names and lexical visibility restrictions. A body scanner must distinguish a type path from an expression path: a local variable may shadow a value root without changing type namespace, while a local module/type can shadow the external crate's unqualified root. No regex scan for `semio_s_` is an adequate substitute.

For every fact, evaluate every graph-proven compilation context. Build that context's extern table from authored declaration kind/target/package rename plus provider lib name and workspace authority. Do not trust global `namedCrates` alone: unrelated packages can expose the same library name, whereas each consumer's selected declaration determines its extern provider. Normal dependencies contribute to library contexts, dev dependencies to actual test/example contexts, build dependencies to actual build-script contexts; optional/target-specific alternatives remain explicitly represented in the all-configurations graph. Mutually exclusive conditions may yield several valid context alternatives rather than one false ambiguous binding.

Resolve a path by Rust namespace/scope rules before consulting the extern table. `::provider` selects the external prelude in applicable modern editions; unqualified `provider` must consider lexical modules/imports/type parameters first. `crate`, `self` and repeated `super` traverse the current logical module graph. An extern alias at crate root must be visible only where Rust actually makes it visible; ordinary parent-module imports do not automatically inherit into child modules. Reexport routes honor `pub`, `pub(crate)`, `pub(super)` and `pub(in ...)` at every crossed boundary. Resolve use-tree renames and local module aliases with scope identity, not file-global substitution.

The edge's source remains the physical lexical file owner, even though its Cargo context is the artifact package. For a proven external root, emit a dependency on the selected provider crate owner regardless of whether its terminal item is used or public: a private/invalid terminal does not erase an imported dependency. For a local `crate::specific::Thing` route, emit each proven local source-owner hop and any external provider hop reached through its reexports. This catches general files depending on specific code within one compilation crate. It must not label `OwnType::Associated` external merely because an unrelated crate has the same name.

Public type spelling is not provider evidence. `pub struct SemioMesh` local to a module, `type SemioMesh = other::Mesh`, `pub use other::Mesh as SemioMesh`, an associated type and a genuine external `SemioMesh` need different route evidence. Generic type aliases carry actual dependency edges in their definitions even when downstream callers only mention the local alias. A provider-owned public reexport should retain both immediate provider and ultimate source route where the policy requires transitive source-owner checks; otherwise a permitted facade can conceal a specific implementation binding.

Return typed unresolved/ambiguous obligations with path span, lexical owner, compilation context and attempted routes. Unsupported use-tree grammar, shadowing whose namespace cannot be proved, malformed present Cargo manifest, unknown external root, unproven orphan file context, cyclic aliases/globs, exhausted route bounds and generated macro output must remain failed obligations. Standard/system extern roots require an explicit owned classification rather than silently treating every unresolved identifier as neutral. Token-template paths and macro-generated imports need staged expansion evidence analogous to include-template obligations; attribute/derive paths produce macro-provider edges, while generated output still needs consumer attribution. Preserve progress and cancellation and deterministic context/path ordering.

The specialized mutation metadata resolver must remain scoped to its canonical provider proof. In particular its swallowed binding errors, terminal-name shortcut, fixed provider table, depth-return-empty behavior and unconditional-only route filters must not become the universal layer census. Extract reusable syntax/path-authority mechanics behind general owned contracts; leave the stricter mutation proof's requirements intact.

## Portable Corpus Shapes

A language-neutral case should contain canonical repository locators and source bytes, Cargo manifest bytes and workspace authority, selected compilation roots/target kinds, lexical path facts with byte span and namespace, expected contexts/routes, exact policy edges and unresolved obligations. Keep roots as portable segments; filesystem harness constructs native absolute paths. Preserve original bytes rather than writing platform-specific Cargo paths.

Required positive and hostile families are:

- FEM-shaped general file mounted into two artifact crates, with direct stdio import resolving under both real provider declarations; exact lexical general→artifact edges survive valid artifact→artifact Cargo declarations.
- Direct absolute and unqualified external paths; dependency rename, custom `[lib] name`, inherited dependency, extern crate alias and self alias, Unicode/raw identifiers, comment/string decoys.
- Nested use groups, `self as alias`, `_` trait import, glob, chained aliases and reexports; ambiguous glob collision, cycle and route-bound exhaustion retain obligations.
- Local module named like an extern crate, block-local module/type alias, generic type parameter and value binding with the same spelling; namespace-specific positive and negative expectations.
- `crate`/`self`/multiple `super` routes, inline module versus mounted source, include expansion scope, parent import visibility, private/restricted reexport denial, local public type versus external public type versus associated item.
- Paths in function bodies, impl signatures, bounds, constants, trait defaults, derives/attributes, macro paths and `<Type as external::Trait>::Assoc`; unsupported/generated macro templates stay unresolved until actual expansion evidence.
- Same physical source in normal lib and test/dev contexts with different extern availability; optional/target cfg alternatives, standalone nested workspace authority, root real package and virtual-workspace orphan rejection.
- Deleted provider/member, malformed present manifest, symlinked provider/library/ancestor, missing target, external library outside approved inventory and duplicate extern identity.

These families should be authored before production resolver changes. Independent dev-only syn visitor validates lexical facts/spans and scope structures. syn alone does not prove name resolution: small real rustc consumer/provider rlibs, built with explicit `--extern` aliases under the native queue, validate shadowing, crate-qualified paths, visibility and multiply-mounted contexts. Compile-pass/compile-fail pairs distinguish local shadow routes from extern routes; provider functions or constants with distinct observable values establish which alias actually resolved. Dep-info proves source mounts and inputs but does not identify a symbol provider by itself. A Cargo source projection oracle may use existing third-party TOML tooling in tests; runtime contracts remain repository-owned and no external runtime parser is added.
