## Change

In `module_extension_bundle()`, chained a `.contributes_topic(...)` call immediately after the existing
`.contributes(Contribution::PlaybookBlockKind { .. })` call:

```rust
.contributes_topic(
    "playbook.blockKind",
    serde_json::json!({
        "appId": "playbook-play",
        "blockKind": "buildingComponent",
        "label": "Building Component",
        "iconId": "building",
        "defaultValueJson": r#"{"height":6,"radius":0.5,"sides":6}"#,
        "paramsBodyKey": BODY_PARAMS,
        "previewBodyKey": BODY_PREVIEW,
    }),
)
```

Field/topic values transplanted 1:1 from the existing `Contribution::PlaybookBlockKind` struct literal at the
same call site (`app_id`, `block_kind`, `label`, `icon_id`, `default_value_json`, `params_body_key`,
`preview_body_key` -> camelCase JSON keys). Topic string `"playbook.blockKind"` matches this crate's own
`Cargo.toml` metadata (`🧩️extensions/🌀️procedural/📦️packages/🦀️rust/Cargo.toml:16`,
`contributes = ["playbook.blockKind"]`), consistent with the prior wave's note.

Note: `label`, `icon_id`, etc. in the surrounding `Contribution::PlaybookBlockKind` literal are field names of
the struct literal (paired with string literal values via `.into()`), not local variables in scope — there are
no such bindings in `module_extension_bundle()`. The `json!` macro above therefore uses the literal string
values directly (matching what the struct literal assigns to each field), except for `BODY_PARAMS` /
`BODY_PREVIEW`, which are real crate-level `&str` constants already used the same way in the `.contributes(...)`
call right above.
