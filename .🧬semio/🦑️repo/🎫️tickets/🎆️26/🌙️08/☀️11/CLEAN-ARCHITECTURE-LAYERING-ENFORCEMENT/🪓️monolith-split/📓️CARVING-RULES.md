# 🪚 Crate Carving Rules (wave 3)

Goal: every first-party Rust crate passes the compiler-ingress source boundary: at most 4000 active lines, 32 files and 262144 bytes, counting embedded `include_bytes!`/`include_str!` files. Blank lines, comments and doc lines all count. A crate compiles only when every crate in its first-party closure passes.

1. Follow `PRODUCER-CRATE-RECIPE.md` exactly for every new crate: Cargo.toml naming and workspace inheritance, lib root placement, workspace member (byte-sorted), Nx project, `📋️build-owners.json` owner row, six prototype/release build/check/test launch routes in `.vscode/launch.json` and `.vscode/🧩️launch.seed.jsonc` with unused order keys, and a corpus row where the area has one.
2. Measure with the gate's canonical counter, `readRustSourceClosureV1`, via the census tool: `cd <monolith-split>/🗑️generated && ONLY=<crate-a>,<crate-b> bun census.ts`. Record the before and after rows for every crate you create or shrink. The target is at most 3500 active lines, 28 files and 230000 bytes, which leaves headroom for growth. Do not squeeze under the limit by deleting comments or blank lines; carve cohesive modules instead.
3. Embedded assets (fonts, images, data) must not be compiled into crates. Move them to a runtime asset channel that the host supplies through an explicit port or parameter; find the repo's existing asset or font loading mechanism first. Update every caller and fixture at once. Keep a test that loads the asset through the new path.
4. Dependencies point downward only. A carved child crate must not depend on its former parent. The parent depends on the children and re-exports only what external consumers need, as explicit `pub use child::{…}` items rather than globs, so the public API stays visible. Prefer updating consumers to depend on the new crate directly where that is cleaner.
5. Verification without cargo: run the patched full-resolution differential (`📓️RESOLUTION-ORACLE.md`) for each new crate root, with crate-name resolution simulated as the oracle describes, or per crate with `--extern` stubs where feasible. Also run rustfmt, path resolution, the census rows, `Cargo.toml` TOML parsing, and the six launch routes (both JSON files must parse). Try `bun repo cargo --store=shared --configuration=prototype -- check -p <crate>` once. If the launcher works and the closure passes the gate, run check and test for real and report the results.
6. Lock files: refresh with `bun repo cargo … -- update --workspace --offline` when the launcher works. If it does not, say so and leave the lock to the next refresh.
7. Never compile around the gate. Respect the parent fleet's active crates: `os-kernel`, `plugin`, `plugin-host`, `os-infinite`, `os-renderer-wgpu`, `replication`, `ui-contract`, `ui` and its producers, `job`, `2d`, `pack`. Only touch them with a minimal consumer-side `Cargo.toml` or import edit when your carve needs it.
