The actual Cargo direction implementation is `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🕸️dependencies/🧭️direction/🦀️cargo/🟦️.ts`. It inventories normal, dev, build, optional and target-specific declarations, resolves `workspace = true` and package renames, compares authored inventory against Cargo metadata, and checks both semantic roles and physical owner paths. Consequently, aliases do not evade a declaration-level rule. Actual taxonomy rules at `🔣️taxonomy.json:29153` onward cover framework→implementation, framework modules/packages→products, S modules→plugins/extensions, and plugin roots→artifacts/extensions. A module target under a plugin's artifact folder is rejected by its physical `🔌️plugins` ancestor even if its semantic role is artifact. Owner classification prioritizes artifact packages, plugin packages and extension packages before broad S and framework patterns. Relabeling a package cannot erase the physical selector.

The existing physical-source runner inspected here still walks only taxonomy areas whose layer is `framework`, at `🦀️source/🏃️execution/🟦️.ts:72`. Root is extending that scope and policy independently. `rustSourceDirectionEdges` evaluates the lexical source path against each strict rule and resolves `#[path]`, include and other compile-time input references using module/Cargo context. It rejects uncensused Rust inputs, links and missing files. This complements Cargo: a direct source mount does not require any Cargo dependency declaration, and fixture inputs can cross a deletion boundary without a package edge. Expansion obligations remain separate work already described in the ownership-cuts report.

Neither a wider physical-include census nor Cargo declarations alone proves every lexical source import obeys the deletion law. A generic file compiled inside a specific package can import that package's artifact dependency while its own directory has no package. In that situation Cargo sees the specific package's valid declaration, and the include graph sees a valid specific→general mount. An actual Rust crate-import ownership census must attribute imports from mounted files to their lexical general owner as well as retain their compiler context; import aliases and `crate`/`super` paths must not make the resulting dependency disappear. The example below is concrete, not a hypothetical parser preference.
