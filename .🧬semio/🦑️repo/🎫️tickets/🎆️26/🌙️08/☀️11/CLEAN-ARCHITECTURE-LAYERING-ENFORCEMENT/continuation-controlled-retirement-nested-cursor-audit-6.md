# Controlled Retirement Nested Cursor Audit 6

Read-only current source feasibility audit; no edits or runtime reruns.

The generic retirement enum exhaustive production consumer matches found are CursorStack.step in Value retirement/🦀️.rs 445–467 and ControlledRetirement.step in retirement/controlled/🦀️.rs 76–89. Other qualified Child/ProcessedBytes/BudgetExhausted occurrences in Generic graph, Pack JSON, Value paged-list and OS/S modules chiefly construct this enum or wrap SnapshotRetirementStep; similarly named ordered/flow retirement enums are different types and must not be confused with the Generic enum. Adding a Generic Failure(ValueError) variant requires both core consumers to return that exact error and retain ownership; any direct typed consumer discovered by compiler must do likewise. Do not use expect, panic, or BudgetExhausted to represent allocation/invariant failures. Existing paged-list cursor currently converts a next-release error to BudgetExhausted, which illustrates the risk rather than a valid model.

A nested ControlledRetirement<T> retains its original optional value and PagedList frontier inline. Moving it into a RetirementCursor Box has exactly sizeof ControlledRetirement<T> constructor birth; its existing value/frontier allocations are transferred, not reborn. Its support requires truthful controlled T membership, with recursive families finitely certified rather than runtime recursive support evaluation. Terminal Box release is sizeof Self only after inner terminal_is_empty proves original value gone and all frontier backing pages released.

The current parent ControlledRetirement already queries next_birth_bytes(body grant), checks capacity credit, invokes one child transition and records that birth only when the transition progresses. Therefore a nested cursor can forward next_work_byte_demand, inner next_capacity_byte_demand(body grant), and inner next_release_byte_demand. It can take one inner step and preserve categories: copied_bytes→ProcessedBytes, released_bytes→Bytes, capacity-only progress→explicit zero-byte transition with birth admitted once by the parent. Distinguish copied_items==1 from a fully zero Progress receipt; the latter must remain BudgetExhausted/unchanged, not false progress. Do not aggregate copied bytes with released bytes.

There are important conditions on that feasibility. close_step(maximum_bytes) does not receive maximum_capacity_bytes or maximum_depth, so spending inner capacity must be exactly the previously published demand (guarded by parent preadmission) and cannot silently enlarge any grant. A nested wrapper cannot independently recover the caller depth limit from the old byte-only cursor API; assigning usize::MAX hides a new nested stack limit. The clean mandatory granted-transition port should carry the independent RetainedCloneGrant through nested cursors, forwarding the remaining/cumulative depth authority explicitly. If the first slice uses demand-preadmitted forwarding under the current interface, record this bounded scope and retain a validated caller depth policy in the nested owner rather than inventing an unlimited one.

Current ControlledRetirement makes one transition per step: frontier reserve, root constructor birth, terminal cursor drop, empty frontier page release, or one cursor body action. This supports truthful exclusive receipt categories. Preserve this one-transition discipline; do not drain the entire nested frontier in one parent call. Parent and child frontiers have separate physical page allocations; both require their own exact births/releases and neither is merely payload credit.

Hidden hazards to verify before certification: current cursor constructor methods are infallible Box allocations despite preadmission; nested next-capacity errors need typed propagation rather than missing-authority None fallback; a child Failure must leave its value/frontier retained for eventual controlled retirement; terminal wrappers must not recursively drop a nonempty nested owner; an outer zero grant must not query-and-allocate an inner page; parent receipt must not doublecount capacity already retained before transfer. Original nested owner pages should be conserved by transfer and then released exactly once.

Neutral vectors should cover transfer with inline original value, transfer with already allocated frontier, pending nested child, capacity-only transition, three-byte copy, whole physical buffer release, terminal child cursor release, parent frontier release, exact-undergrant nonmovement, typed failure retention and depth exhaustion. Each vector separately declares payload3, capacity allocation layout and physical release size. Preserve existing value fixtures/oracles and original turn limits.
