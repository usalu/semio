WAVE-14 RE-SURVEY (cross-language differential oracles, ticket 26/08/23): a second IMPLEMENTATION in another language was built for five sibling subsets in this same artifact and works end to end, so the route was re-examined here and REJECTED on two concrete, nameable blockers rather than on absence. First, the envelope's own committed documents declare the wrapped arm OPAQUE: the snapshot grammar's `document = artifact-mark subset-line REST` hands off to the arm's own grammar, the binary protocol models the wrapped pack as one opaque trailing `payload` chain, and the mutations grammar is `op = "noMutation" | tag ":" REST`. An envelope-level second implementation can therefore reproduce both committed carriers byte for byte - and it can - but it can say nothing about whether a DELEGATED verb changed the arm it reached, which is exactly what eighteen of this vocabulary's twenty kinds measure. Second, nothing lets the two languages read the same arm input: this subset exports `parse_semio_envelope_dsl`/`print_semio_envelope_dsl` and `decode_semio_envelope_pack`/`encode_semio_envelope_pack` but NO JSON bridge for `SemioSnapshot` or `SemioMutation`, so the arm snapshots and the wrapped verbs can only be constructed in Rust, inside the subject crate, where a second language cannot see them. Registering a Python oracle that merely restated the routing table would be a transcribed expectation wearing an oracle's name - our own answer on both sides - and is the one thing this platform exists to prevent, so it was not done. The two changes that would unblock a real differential here, in order of leverage: export a JSON bridge for `SemioSnapshot`/`SemioMutation` the way `✳️cad` and `✳️document` already do, and re-export `store::ArtifactDsl`/`store::ArtifactPack` so an external adapter can decode the committed example assets.
