## 3. Rows deliberately excluded, and why

**RENDER-CACHE (8 rows, per the audit's own classification — no override needed):** `SET_WINDOW_UI_BY_WINDOW_ID`, `SET_WINDOW_ENGAGEMENTS_BY_WINDOW_ID`, `SET_WINDOW_MEASURES_BY_WINDOW_ID`, `SET_TOOL_MEASURES_BY_TOOL_ID`, `SET_PANEL_UI_BY_KEY`, `SET_SPAWNED_WINDOW_UI`, `SET_SPAWNED_WINDOW_ENGAGEMENTS`, `SET_SPAWNED_WINDOW_MEASURES`. These are serialized UiNode trees / engagement / measure-overlay caches — the renderer's business, not the SSOT's.

**TRANSIENT (6 rows, per the audit):** `SET_TUTORIAL_PLAYING`, `SET_TUTORIAL_RATE`, `SET_TUTORIAL_MUTED`, `SET_TUTORIAL_CAPTIONS`, `SET_TUTORIAL_RECORDING`, `SET_TUTORIAL_DEVIATED`. Playback transport state, UI-only, reset every session.

**`APPLY_TUTORIAL_UI_SNAPSHOT` — my own call, overriding the audit's SEMANTIC label.** Its payload (`TutorialShellUiSnapshot`) restores the RENDER-CACHE UI trees (windowUi etc.) for tutorial playback replay. Since those trees are out of scope by the same scope-discipline rule as the 8 RENDER-CACHE rows above, this command has no meaningful `ShellState` field to write to; including it would mean either (a) silently dropping its payload (violates "never silently no-op") or (b) reintroducing the very RENDER-CACHE surface the packet excludes. Tutorial UI-snapshot replay is renderer work, not SSOT work.

**ShellHost `useRef`s (44 entries, audit §2) — excluded as a block, not individually.** Every one is host-instance-local imperative bookkeeping: DOM/worker/callback handles (`importSpaceInputRef`, `backboneWorkerRef`, `openDocumentRef`, `displayHostRef`, …), memoized render caches (`uiRefreshCacheRef`), or debounce/diff-tracking state for one specific host's implementation strategy (`layoutChangeSettleTimeoutRef`, `noExampleResetInstanceIdRef`). None of them is something an LLM or a second host would ever need to read or drive — they have no cross-host meaning. `scope` and `openingPreferences` (both `useState`, not `useRef`) are the two exceptions promoted into the vocabulary (variants 62–63) because they are genuine user-facing preferences, not host plumbing.

**`identity`/`identityOffline` (ShellHost `useState`) — excluded.** Collaboration/hub identity is explicitly deferred by `📓️design-decisions.md` D7 ("Hub agent principal is deferred, gateway auth is loopback-token first") and `📌️important.md` flags `📇️directory`/`🌎️hub` as live churn zones under `FINISH-HUB-SPACES-COLLABORATION-END-TO-END` / `SHARED-PRESENCE-…` that I must not touch or model against.

**`extensionLedger`/`extensionLedgerRef` — excluded.** An append-only invocation log, structurally the same kind of thing as history/checkpoint tracking below — a projection built by observing `ShellEvent`s over time, not a field of "current state."

**History/checkpoint (`historyProjection`, wgpu `history_cursor`/`history_entries`) — excluded (audit's own "Unresolved Question #3").** `ShellState.revision` plus the `ShellCommand` log is the mechanism a host-side undo/redo layer needs (`ReplayShellCommand`, the one kernel effect explicitly named for this, replays a past command through `reduce`); a separate `history_entries: BTreeMap<revision, HistoryEntry>` field inside `ShellState` would just be a cache **of** that log, and CLAUDE.md forbids storing both a derived cache and its source. Undo/redo is later-packet adoption work built on top of this module, not inside it.

**Presence/collaboration (`presence_peers`, `shell_session_id`, wgpu `identity`) — excluded (audit's "Unresolved Question #4").** Same reasoning as `identity` above — different bounded context, actively churning under a peer ticket.

**App-label overlay scope — decided, not excluded.** Kept in (`SetAppLabelOverride`, variant 7) but I made an explicit persistence-scope call the audit left open: session-local, not document- or account-scoped, because it is `PluginAppLabelsOverlay` (a shell/session concept) rather than a document field.

**Terminology as `String`, not an enum — decided.** `uiTerminology`/`SetUiTerminology` keep the audit's `string` shape (an app-defined open id space, not a closed set); introducing a `Terminology` enum here would require enumerating every app's terminology options inside a domain-neutral crate, which is backwards.

## 4. Design decisions beyond a literal audit transcription

- **Dialog stack, not `Option<DialogState>`.** The audit's `SET_DIALOG` row carries a single `{dialogId, seedArgs} | null`. The packet brief explicitly calls out "dialog stacking" as a required tricky-path fixture, which a flat `Option` cannot express (a confirm dialog opened on top of a settings dialog). `ShellState.dialogStack: DialogState[]` plus `OpenDialog` (push) / `CloseDialog { dialogId: string | null }` (pop top, or remove by id) covers both the audit's original semantics (as the 1-deep case) and stacking.
- **Mode↔tool mutual exclusion**, the other named tricky path: `SetActiveTool` (with a tool id) clears the focused window's `activeUtilityByWindow` entry if set; `SetActiveUtility` (with a utility id) on the focused window clears `activeToolId` if set. Both directions emit a specific `ShellEvent` (`ActiveUtilityChanged`/`ActiveToolChanged`) alongside the always-present `Applied`. Neither the audit nor the ShellState field list stated this rule explicitly; it follows from the fields' own descriptions ("host-owned active mode tool" vs. "host-owned active utility per window" — the host can only own one interaction mode at a time per window) and is now enforced, not just implied.
- **Focus-after-close**, the third named tricky path: `SetExtraWindows` (replace-the-list) checks whether the *previously* active window (using the **input** state, not the mutated clone, to avoid a stale read) was an extra window and is no longer present in the new list; if so it refocuses the last remaining extra window, or clears focus, and emits `WindowFocusChanged`.
- **`ShellError` validation set** is intentionally small and evidence-based rather than exhaustively defensive: empty-string identifiers (`EmptyIdentifier`), unknown-id references that would otherwise silently no-op (`UnknownPlugin`, `UnknownDialog`, `UnknownConflict`), and non-finite/negative panel sizes (`InvalidPanelSize`). Every other field accepts any value in its type's range because `reduce` has no cross-field invariant to protect there (e.g. an unknown `windowId` in `FocusWindow` is not an error — nothing in `ShellState` enumerates "the" canonical window registry to validate against; `extraWindows` is one source among others the real host would combine).
- **`ShellEvent` is not a 1:1 mirror of `ShellCommand`.** Every accepted command emits exactly one `Applied { capabilityId, revision }` (a deterministic baseline every fixture asserts on) plus zero or more specific variants only where `reduce` does something beyond the literal field write the command already names (mutual exclusion, focus reassignment, dock reset, dialog open/close). A second event per command carrying the same payload as the command itself would be pure duplication.
- **`u64` fields render as `number`, not ts-rs' default `bigint`, in the TS mirror** (`ShellState.revision`, `ShellEvent::Applied.revision`, `PluginSupervisorState.lastSignalMs`, `TransientNotice.expiresAtMs`), via `#[ts(type = "number")]`/`"number | null"` overrides. This module's wire format is plain JSON (no binary codec, unlike `semio-framework-actor`'s `pack` module) — `JSON.parse` produces `number`, never `bigint`, so the ts-rs default would have made every fixture a type error on the TS side. Millisecond epoch timestamps and a monotonic revision counter never approach `Number.MAX_SAFE_INTEGER`.
- **All wire field names are `camelCase`**, including plain structs the audit's TS reducer didn't originally camelCase consistently — `#[serde(rename_all = "camelCase")]` on every multi-field type, so the vocabulary the LLM sees is uniform.

## 8. What the shells must do to adopt this (input to later packets)

This packet does **not** wire anything into the React shell, the wgpu shell, or the kernel — that is explicitly out of scope (§1 of the packet). For the packets that do:

1. **React `Shell/🟦️component.tsx` reducer.** Its `shellReducer(state, action)` becomes a thin adapter: translate each of the 76 `ShellAction` variants that map to a `ShellCommand` (all 60 SEMANTIC ones, per §2's table) into the matching `ShellCommand`, call `reduce(shellState, command, Date.now())` from `@semio-tech/framework-os-shell`, and:
   - on `{ok: true}`: replace the SEMANTIC slice of `ShellState` with `result.state`, keep dispatching the original action through the *existing* reducer unchanged for the RENDER-CACHE slices (`windowUiByWindowId`, engagements, measures, `appLabelsOverlay` stays SEMANTIC-only in this module — the render-cache dispatch path for it, if any, stays local) so nothing regresses mid-migration;
   - on `{ok: false}`: surface `result.error` (today's TS reducer never rejects — every dispatch is accepted unconditionally — so this is new, stricter behavior the host UI needs a place to show, e.g. a toast via the *existing* `transientNotice` mechanism, which is careful: `TransientNotice` is itself now SSOT-owned, so the adapter cannot use `ShowTransientNotice` to report a `reduce` rejection about `ShowTransientNotice` itself without special-casing — flagging this circularity for the adoption packet).
   - The 6 TRANSIENT tutorial-playback actions and the 8 RENDER-CACHE actions keep dispatching through the *unmodified* existing reducer only — they never touch this module.
2. **ShellHost `useState`/`useRef`.** `scope` and `openingPreferences` become derived reads of `shellState.storageScope`/`shellState.openingPreferences` (dispatched via `SetStorageScope`/`SetOpeningPreference`), replacing their local `useState`. Every other `useState`/`useRef` in the audit's §2 table is untouched (excluded from this SSOT by design, §3 above).
3. **wgpu `Shell/🧊️component.rs`.** The ~80 SEMANTIC-classified fields of its ~130-field `ShellState` struct become read-projections of `semio_framework_os_shell::ShellState`; the wgpu event/mutation pipeline that currently mutates those fields directly needs to route through `reduce()` instead, replacing direct field writes with `ShellCommand` construction + `reduce` + apply-`ShellEvent`-side-effects. The `shell.*` verb strings it already logs become (mostly 1:1, see §5's table) `ShellCapability.id`s, so its history/logging surface does not need to change shape, only its source of truth.
4. **MCP gateway (a separate, later packet, not part of this ticket's already-built P1–P4 gateway packets covered elsewhere).** `shell_capabilities()` is ready to compile directly into the gateway's tool catalog: each `ShellCapability { id, title, description, schema, observableOnly }` maps 1:1 onto an MCP tool definition (`id` → tool name, `schema` → input schema, `title`/`description` → tool metadata). The gateway's dispatch handler for a shell tool call is exactly: decode the JSON args into the matching `ShellCommand` variant (the `schema` is generated from `ShellCommand`'s own serde representation, so any JSON-Schema-conformant payload deserializes directly via `serde_json::from_value::<ShellCommand>`), call `reduce`, translate `Ok`/`Err` into the MCP tool-call result shape.
5. **Undo/redo (history), presence/collaboration, tutorial-UI-snapshot replay** remain explicitly unaddressed — §3 above records why each was excluded and what a follow-up packet needs to build on top of (a `ShellCommand` log + `ReplayShellCommand`, a separate `CollaborationState` slice, and renderer-owned snapshot replay, respectively).
