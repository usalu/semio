## `semio-s-plugin-block` — 17 → 9 warnings

Fixed (8):
- 3× `hidden lifetime parameters ... deprecated` on `fn compose(sources: &[ComposeSource])` in the
  block2d/block3d/block5d `🚪️io/🦀️component.rs` derived-composition impls — added `<'_>` to match
  the trait's own `fn compose(sources: &[ComposeSource<'_>])` signature
  (`🧰️framework/…/🔌️plugin/🦀️component.rs`).
- 3× `unused import: semio_framework_plugin::ArtifactAnalyzer` in the same three files — the
  `derive_artifact_facets!` macro generates an **inherent** `pub fn analyze(...)` on the analyzer
  struct alongside the trait impl, so `Block{2,3,5}dAnalyzer::analyze(...)` resolves without the
  trait import.
- 1× `unused doc comment` in `🗿️artifacts/🧊️3d/🦀️component.rs` — a doc comment sat *before* a
  `thread_local! { ... }` macro invocation instead of on the `static` item inside it; moved the doc
  comment inside the block.
- 1× `unused doc comment` in block2d's `✏️editor/🦀️component.rs` — a stale block of `///` doc
  comment had nothing left to document (the code it described was already removed); converted to a
  plain `//` comment.

**Left unfixed (9), all one family — genuinely NOT dead code, but statically untraceable by
rustc's dead_code lint in this plugin architecture:**

`BlockKindIdentity`, `BlockAttribute`, `BlockAuthor`, `BlockCompatibilityRule`,
`BlockRepresentation`, `BlockCamera2d`, `BlockCamera3d`, `BlockMeta` ("never constructed") and
`block_one_f64` ("never used"), all in `✏️s/🔌️plugins/🧱️block/🦀️component.rs`.

I spent a long time verifying these are real, load-bearing types (they're every artifact's
persisted-field shape — `Block3dSnapshot.object_kind: BlockKindIdentity` etc. — deleting them is
not an option, it would break the crate). I traced a complete, concrete, non-test construction
chain:

`Block3dPlayApp::initial_snapshot()` (real `ArtifactEditor` trait impl)
→ `empty_block3d_snapshot()`
→ `Block3dSnapshot::default()` (hand-written, **not** derived — explicit `Self { object_kind:
  BlockKindIdentity::default(), camera3d: BlockCamera3d::default(), meta: BlockMeta::default(), …
  }`)
→ constructs every one of the flagged types.

This is genuinely reachable at runtime: `PluginBuilder::editor::<Block3dPlayApp>(...)` (called
from this crate's own `plugin()`) builds a closure that calls
`VcsArtifactApp::with_registry(EditorApp::<Block3dPlayApp>::default(), …)`, and
`VcsArtifactApp::with_registry` directly calls `A::initial_snapshot()` — a plain, non-generic,
non-dynamic-dispatch call, no `dyn Trait` indirection. I confirmed with a `cargo build` (full
codegen, not just `cargo check`) that the **same 9 warnings persist** — so this isn't a
check-vs-build artifact either.

My best-supported conclusion: rustc's `dead_code` reachability pass is local to each crate's own
HIR and does not trace liveness through a *cross-crate* generic method body (here,
`semio-framework-plugin`'s own `PluginBuilder::editor::<E>()`) to see that it calls back into
`E::initial_snapshot()` for our locally-defined `E = Block3dPlayApp`. The `diff()`-family
functions in the same crate are *not* flagged, because they're reached through a **local**
derive-macro-generated trait impl (`impl protocol::Mutation<Block3dSnapshot> for Block3dMutation`,
generated by this crate's own `#[derive(dsl::Mutations)]`) calling directly into a same-crate free
function — no cross-crate generic hop involved.

I could not find a safe, non-cosmetic fix that doesn't either (a) fabricate a fake construction
site purely to satisfy the lint (a suppression-shaped hack, forbidden by policy) or (b) touch
unrelated architecture. Recommend either accepting these 9 as a known, verified-safe class of
false positive for this plugin pattern (likely repeats across every `s-plugin-*` crate's shared
"Identity/Camera/Meta" record types — worth a dedicated follow-up if it's worth chasing), or
revisiting with someone who can weigh in on whether `-Z` flags / a different lint pass would trace
it correctly.

Files touched: the three `🚪️io/🦀️component.rs` files under `🗿️artifacts/{◻2d,🖐️5d,🧊️3d}/…`, and
`🗿️artifacts/🧊️3d/🦀️component.rs`, `🗿️artifacts/◻2d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/🦀️component.rs`.

## `semio-framework-plugin` — 15 (+1) → 2 warnings

**Real bug fixed** (as flagged in the brief): `type TransactionProposalDraft is more private than
the item PluginApp::take_pending_transaction_proposal`. `PluginApp` is a `pub trait`, so its
method `take_pending_transaction_proposal(&mut self) -> Option<TransactionProposalDraft>` is
`pub`-reachable, but `TransactionProposalDraft` was `pub(crate)`. Widened the struct to `pub`
(left its fields `pub(crate)` — only the type itself needed widening to satisfy the trait method's
own visibility; nothing outside the crate can construct one anyway, only observe/pass it through).
This single change resolved all three "more private than" warnings at once (the trait method
itself, `VcsArtifactApp`'s impl of it, and a `pub fn assert_proposes_transaction` test helper).

Other fixes:
- 5× hidden-lifetime warnings on the trait definitions themselves —
  `ArtifactComposer::compose`, `ArtifactDecomposer::decompose`, `ArtifactAnalyzer::sniff`/
  `::analyze`, plus one `Vec<ComposeSource>` local binding — added `<'_>` throughout (these are the
  actual trait declarations the block/forms `<'_>` fixes above have to match).
- Unused imports: `FlowExtensionExecutableIdentity`/`FlowExtensionManifest` in
  `🏗️builder/🦀️component.rs` were only used by one `#[cfg(test)]` test — moved the `use` into that
  test module instead of the top-level import (idiomatic, not a suppression). `ChildStoreFactory`
  in the crate root was referenced only in doc-comment prose, never in code — removed.
- `encode_contributed_wire` and `commit_owner_mutation_roster` (`pub(crate)` fns) — grepped the
  whole crate: both are called only from `#[cfg(test)]` blocks. For
  `commit_owner_mutation_roster` specifically I found *why*: production plugin assembly
  (`PluginBuilder::try_build` → `extend_contributions`) has its own inline duplicate of the same
  owner-mutation-roster-merging logic that writes into `self.owner_mutations` directly, instead of
  going through this function's global-static `OWNER_MUTATION_ROSTER_REGISTRY`. That registry/
  reader (`owner_mutation_roster_registry()`, `mutation_roster_entries()`) looks like a superseded,
  parallel mechanism — but only `commit_owner_mutation_roster` (the writer) was actually flagged,
  so per the ticket's own hazard-2a playbook I gated just that one function with `#[cfg(test)]`
  rather than judging the whole subsystem dead (didn't want to make that call in a shared
  foundational crate without more certainty).
- Deleted 3 fully dead private methods on `AppActionRegistry`: `has_window_action`,
  `has_app_command`, `has_mode_command`. Verified zero call sites anywhere in the crate, including
  tests — every real caller uses the `Option`-returning siblings (`window_action`, `app_command`,
  `mode_command`) via `.map(...).ok_or_else(...)`, so the boolean variants were pure dead weight.
- 1 more warning turned up on a later full re-check that wasn't in my first scoped extraction of
  this crate's block (`sed` between "Checking semio-framework-plugin" and its own "generated N
  warnings" line — cargo's short-format output isn't always contiguous per-crate under concurrent/
  parallel builds, so don't trust that extraction pattern blindly): `unnecessary unsafe block`
  around a call to `semio_plugin_bundle_installer_link_shim()`, a `pub extern "C" fn` with an empty
  body — not actually `unsafe`. Removed the redundant `unsafe { }` wrapper.

**Left unfixed (2), both documented deliberate scaffolding, not accidental dead code:**
- `ArtifactDeclaration`'s `child_slots`/`link_slots` fields (line ~2812) — the field's own adjacent
  comment (dated 2026-08-12, UCAS review) says explicitly: "No registration function consumes
  these yet ... captured here so the declaration is a complete, single-source manifest of the
  artifact's shape, not because `register_all` calls anything with them today." Deleting these
  would retract an explicit, recent architectural decision, not clean up an oversight.
- `PluginRuntimeRegistry`'s `schemas`/`inferences`/`languages`/`app_schemas` fields (line ~3822) —
  aggregated from every plugin's declarations at assembly time but never read back out anywhere in
  the crate. Same shape as the field above (data captured for a not-yet-wired consumer) rather than
  a clear accident; I did not have enough confidence about the intended consumer to either wire one
  up (functional change, out of scope) or delete (retracts scaffolding) — left alone.

Verified 2 warnings, 0 errors with a fresh synchronous `cargo check -p semio-framework-plugin`.
