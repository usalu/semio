# Composition Bootstrap And Proof Ownership

## Host Policy Decision

The accepted OS renderer profile is one new explicit combined host allowance:33554432bytes,262144slots,262144owners. Its control partition is65536bytes,1024slots,1024owners, carved out of those totals. Data therefore has33488896bytes and261120slots/owners. Existing UI per-patch8388608-byte and aggregate33554432-byte policies are unchanged. This is a stricter combined host bound, not evidence that all apps fit, that every existing host allocation is already charged, or that logical counters equal physical JavaScript heap.

The actual same ledger must be injected into both renderer consumers when they belong to one composition/realm. Sharing numeric constants while constructing two ledgers would duplicate the allowance. The actor constructor takes a required residentLedger and creates none. A closing composition cannot silently be replaced while its earlier owners remain. The OS policy domain owns the declared profile; the domain-neutral actor has no implicit default. Guest pre-instantiation physical memory is a separate still-unmounted authority obligation, not paid merely by this host-buffer policy.

Root inspected both current getShardClient bootstraps and shared shard-runtime. They currently have separate module runtime singletons and duplicated budget constants; the shared factory itself is not a process singleton. The binding packet must preserve one actual ledger identity, and later one-pool/runtime acceptance must address simultaneous target ownership. The existing wallMs100 defaults are not an8ms enforcement certificate and remain an independent live-path obligation.

## UI Pool Construction

The original ShardClient composition owns one private charged pending pool-construction slot. It holds the neutral record capability before any UI pool allocation. The UI owns the private pool constructor and preadmitted OwnedUiResidentPoolRetirement witness. No public getter, structural callback or generic terminal predicate transfers the capability.

Agreed methods are prepareUiResidentPool(ledger,grant), installUiResidentPool(pool,grant), ownsUiResidentPool(pool), releaseUiResidentPool(pool,witness,grant), and static matchesResidentLedger(client,ledger). UI uses OwnedUiResidentPool.begin(client,ledger,grant), direct-private matchesComposition, and pool.retirement. Its pool envelope is uiResidentMetadataEnvelope('pool'), currently168logical bytes/3slots/3owners, plus neutral256/3/3. Extra Shard pending/phase/witness fields are separately declared, not hidden in these amounts.

A consumed prepare phase returns pending; later construction/installation cannot reuse its item/byte grant. Stored-shell identity and actual neutral-record-installed frontier are distinct. Once a shell exists, prepare cannot authorize a second allocation. If a real installation or detach succeeded before a wrapper threw, the original record's exact private observation recovers that frontier. The Shard owner drives abandoned pool close and checks the genuine UI witness on a later admitted turn; it does not depend on the original caller surviving.

## Cross-Owner Input Evidence

Actual source contains Release.#proof→Evidence{fragment,field,builder} and Fragment.#field→Field.#state→source/host/activation. Clearing the builder's local proof leaves this graph retained. Evidence therefore needs separately charged strong ownership until both the original UI observation and source consumer detach. Only then can actual descendant links clear and its own record retire. A small identity facade cannot conceal a retained InputOwner graph. This is not input-copy authority, raw native InputAck, semantic publication ACK or guest lifecycle retirement.

The native initialization proposal correctly distinguishes process-static native UI ownership from per-Wasm-activation guest statics. Host admission must precede actual component instantiation; first-poll numeric capacity cannot retroactively cover static/data/stack allocation. The inspected host512MiB per-memory limit is not a resident allocation permit. One required composition record through the existing canonical poll is a proposed API direction, not an approved live ABI mount yet.

The native owner must cover every actual producer and the bundle construction owner before this becomes a runtime admission claim. No second ABI, permissive default or synthetic allocation proof is accepted.
