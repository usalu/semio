## Exact Planned Storage

Specialize UiPatchOps into a fixed-capacity directory of one-operation Vec pages. Directory allocation and each payload allocation are separate admitted steps: on the current 64-bit representation, 27,672 and 6,320 bytes respectively. `next_allocation_bytes` exposes the next request before allocation; the runtime must reserve it in its existing ledger. `try_reserve_one` consumes only the caller-admitted physical amount and reports real directory/page capacity, retained in an O(1) allocated-byte counter. Empty allocated pages remain charged. A failed reservation leaves all prior owners intact.

Placement is separate from allocation and semantic retirement. `try_push_reserved` borrows `&mut Option<UiPatchOp>` and checks a physical placement grant of at least size_of::<UiPatchOp>() before taking the source. A 4,096-byte grant cannot place 6,320 bytes and returns blocked with its source unchanged. The existing runtime physical page grant is 32,768; it is not increased. Actual placed bytes are reported. Cancellation and `take_all` move only page/directory descriptors, never the inline operation; the moved-from owner has zero backing.

Typed retirement keeps the operation in its page, retiring initialized text/value descendants under the existing semantic byte grants. Only after exact typed terminal does it truncate the empty operation in place; it must not pop/move a 6,320-byte enum and claim one free item. Empty page allocation and empty directory release are subsequent explicit steps. No clone or cold convenience is credited as retained work.
