# Shared Retained UI Resident Admission

## Ownership Contract

The owning host composition must supply one `OwnedUiResidentPool` to every retained UI instance under that host. Its explicit capacities are resident payload bytes, allocated/reserved page slots and all live instance/payload/page-handle slots. There is no default capacity and no operation-local replacement pool. A declared field size and `maxPatchBytes` do not reserve any of these resources.

`bindInstance` joins an actual private `OwnedUiInstance`, exact activation object and native-issued three-field lifetime. Repeating that exact join returns the existing child; a foreign tuple or forged instance is refused. Each child may create payload owners while admission is active. `reservePage(length)` reserves the full 256-byte allocation and one page/handle slot before `allocate(grant)` creates its fixed array. Partial pages still reserve 256 bytes. Every captured page alias consumes another handle slot; page and byte credit remain charged until the final alias has scrubbed/detached its array and completed its separate metadata-release step.

Payload, instance and pool close prevent further admissions and retain their exact children in intrusive doubly linked owner rosters. Each close call advances one actual child, never scans or synchronously destroys the collection. Parents retain writer/reservation handles even when their caller throws or loses its returned reference, and retire those handles through the same fixed-step close. Captured read aliases preserve their bytes after parent close and revocation; they remain real issued-reader obligations until their consumer closes them. Neither garbage collection nor a lost alias handle is considered discharge. Closing remains available after activation revocation. No raw-input ACK, UI publication, declared completion or structural callback can release resident credit.

## Bounded Work

The dedicated allocation initializes exactly 256 bytes. A write step copies one byte. A final page close scrubs at most the admitted byte count from this one fixed page, then releases fixed metadata in a separate 64-byte step. A non-final alias close releases fixed metadata only. Capacity arithmetic is checked safe-integer subtraction before mutation; reference counts are bounded by the shared handle capacity. Object-slot accounting is not a claim about physical JavaScript object size, GC latency or an empirical 8 ms allocator guarantee.

## Exact Instance Join

The next neutral law exposed a real missing join: after `OwnedUiInstance.beginClose`, its resource scope still admitted a new payload. That RED reached the assertion (one failed, two passed, 631 skipped, 634 discovered, 13.47 seconds), in `🧪️renderer-owned-resident-roster-red-r3-2026-08-27.txt`.

The source now privately validates and attaches one lifetime scope to the exact instance during pool binding. A different pool cannot replace that scope. Instance close first stops its admission, then closes existing UI work and the resource roster; the final instance witness remains unavailable until the roster and all live read aliases are terminal. Removing the final resident-scope reference is its own fixed step after child completion. Pool binding entries are removed on scope retirement rather than accumulating closed weak-map values.

The new law deliberately throws after allocating/writing an unreturned writer page and retains an independent read alias on another page. Instance close must reclaim the abandoned writer, leave the alias readable before and after revocation, and refuse an early witness; closing the alias then permits complete teardown. R4 passed all three tests (631 skipped, 634 discovered, 8.60 seconds), and R5 repeated all three successfully after adding the explicit producer-side read-alias roster (6.86 seconds, 133 ms execution). Logs are `🧪️renderer-owned-resident-roster-r4-2026-08-27.txt` and `🧪️renderer-owned-resident-roster-r5-2026-08-27.txt`. Strict R2 completed with exactly seven tutorial diagnostics, no new errors, in `🧪️renderer-owned-resident-roster-strict-r2-2026-08-27.txt`.

Existing cancellation fixtures now create one exact instance owner per pool, matching the new one-scope attachment rule rather than rebinding one live owner across separate pools. The producer roster strongly retains captured reader facades, but that does not replace the next required atomic registration with a concrete consumer owner before a live reader is exposed. A caller throw between capture and consumer adoption must not create an unserviceable outstanding-reader obligation; this live builder/read-consumer join remains required.

## Remaining Integration

The canonical admitted domain is separately declared in `retained/💾️resident/🧬️schema.json` and `🧬️contract.json`. Unlike the oracle fixture format (which deliberately permits invalid test inputs), it admits only checked integers from zero through `Number.MAX_SAFE_INTEGER`, rejects additional capacity fields, and declares full-page charging, strong owner/alias transitions, revocation and terminal witness requirements. It supplies no default capacity. The collected pool test validates this domain with Ajv, including invalid capacities, and checks the private payload-to-instance owner verifier. The earlier R5 result predates these additions. Coordinator full React R23 subsequently passed 640/640 tests in five files, 162.90 seconds, with 33 captured hashes unchanged; that combined snapshot includes the domain assertions. Its separate strict R32 still reports exactly seven tutorial errors. See `📓️coordinator-renderer-react-full-r23-2026-08-27.md` and `📓️coordinator-strict-r32-2026-08-27.md`.

Production composition injection still must supply explicit shared capacities before live paged intake is admitted. The shared pool does not certify existing typed node/string/index allocations; those remain separate resource-admission obligations. Destination-page ownership will next use these leases with peer-owned `OwnedKernelReturnInputField`/fragment/release authority and privately issued copied/cancelled tokens. The actual payload builder/issued-reader participant must retain its source receipt and alias obligations; this pool cannot substitute a counter for that participant.
