# Shared Resident Ledger API

## Scope And Layering

The neutral source is `framework/🔨modules/🌱value/💾resident`. Its intrinsic implementation and standalone positive/fault tests are now present. The same composition-created ledger must fund pre-Open actor response backing and UI destination/scratch/frame reservations. No UI, actor, DOM component, activation or lifetime type enters the neutral implementation. System ArrayBuffer/Uint8Array/structuredClone are the storage platform boundary.

The core will own intrinsic storage and fixed registration records, rather than accepting arbitrary object finalizers, structural `isRetired` callbacks or public counter subtraction. Concrete actor and UI parent rosters still own their actual domain consumers. A neutral storage-retirement witness proves only the exact storage/registration root has retired; it never proves native input ACK, UI publication, an actor dispatch or a domain object is terminal.

## Concrete Interface To Implement

`OwnedResidentLedger(capacity)` takes the schema's explicit safe-integer `{bytes, slots, owners, control:{bytes,slots,owners}}`. `control <= total` is checked per axis. Data and control are disjoint partitions within that one total. Admission compares requested resources against remaining capacity before addition, so neither rounded sums nor overflow can grant credit.

`ledger.beginOwner(partition, grant)` returns a privately minted `OwnedResidentOwner | null`. The exact owner is linked strongly into the ledger before it can escape or be finalized. Its fixed owner and final-witness records are charged first. It carries no actor/UI provenance. A caller losing this facade does not lose the ledger's original registration.

`owner.reservePage(length, grant)` accepts an exact logical extent from 0 through 256, reserves the complete 256-byte backing plus storage and final-witness records, and returns `OwnedResidentPage | null`. `allocate`, `writeByte` and `seal` are separate steps; seal requires only the logical length, without hidden padding writes. A reader is created only through `owner.beginRead(pageOrExternalSlot, grant)`: the consuming owner is a mandatory strong registration before exposure, not a caller-only `page.capture()` sequence. Both same-owner and independent-owner readers are supported; close drains the same owner's readers first.

`owner.beginClose()` requests neutral retirement. It drives its issued readers before its writer/storage children, one retained child per turn. Closing a writer does not destroy storage held by another registered reader owner; that reader remains usable until its own owner closes. Ledger close remains blocked on the exact outstanding registrations/storage, not a global untrusted count. All child results and raw work counts are forwarded before a later wrapper unlink/refund phase.

`OwnedResidentRetirement.matches(witness, exactOwnerOrStorageOrReader)` validates the direct private brand and exact original root. The fixed witness is charged, constructed and strongly installed before finalization; only after intrinsic retirement does the root's `retirement` getter expose it as a valid proof. No allocation or fallible finalization occurs after refund. Typed domain wrappers keep their own private close checks and may join this concrete witness; the ledger never calls a supplied terminal predicate.

Logical charges, including every preadmitted witness, are: owner 192 bytes/2 slots/2 owner records; page 512 bytes/3 slots/2 owner records; reader 128 bytes/2 slots/2 owner records; external receiving slot `maximumBytes + 320` bytes/4 slots/3 owner records. The external metadata includes its separate custody receipt. These are declared fixed logical record envelopes, not measured JS heap sizes. The one composition ledger root is outside its admitted descendants. Empty externally retained facades/proofs can outlive intrinsic credit retirement; this is explicitly not a physical-GC certificate.

## Raw Response Admission Extension

The concrete API is `owner.reserveExternalBacking(maximumBytes, grant) -> {step: ResidentStep, slot: OwnedResidentExternalBacking | null}`. The slot is strongly registered before constructor/final-witness/custody finalization. Its reservation cannot assume a 4161-byte wire extent also funds decoded page copies, parser scratch, fixed record metadata or the producer's simultaneous backing. Those are separate same-ledger reservations.

`slot.beginReceive(grant) -> ResidentStep` is the irrevocable receiving fence before post. `slot.adoptTransferred(backing: unknown, grant) -> {step: ResidentStep, receipt: OwnedResidentBackingCustody | null}` accepts an intrinsic fixed ArrayBuffer within the admitted extent and calls the captured platform transfer, checking the original backing is detached. It accepts no typed-array subview or structural reader. `OwnedResidentBackingCustody.matches(receipt, slot)` proves that exact current intrinsic custody, not actor correlation. `slot.length`, `slot.byteAt(index)`, `beginClose`, `closeStep`, `terminalIsEmpty` and `retirement` are the remaining bounded read/close surface. Registered readers also work through the exact consuming owner.

Custody authority is invalidated immediately when its owner, ledger or slot begins close, before scrubbing. Existing registered readers retain their data until they close, but new readers are refused. Late actual backing delivery after close still transfers into the original slot for bounded retirement; it returns `pending` with no custody receipt and cannot authorize publication. A view-constructor throw after successful transfer retains the exact moved backing and keeps close serviceable; producer retry is permanently rejected. Unknown rejected input remains the actor caller's obligation, not falsely adopted by this slot.

Cancelled-unsubmitted reservations can retire without receiving a backing. Once actually posted, cancellation alone must retain the pending raw slot. The actor's private pending/response owner must retain that distinction until actual response custody or its exact terminal transport-close authority. A generic `posted: boolean`, arbitrary `cancelled` token or structural callback will not be introduced as a refund authority in the neutral core. The raw pending-owner integration and precise terminal transport-close join remain peer-owned and must be agreed before that extension is mounted.

# Current Admission API — R21

The current canonical signatures return explicit retained results: `beginOwner -> {step,owner}`, `reservePage -> {step,page}`, `beginRead -> {step,reader}`, `reserveRecord -> {step,record}` and `reserveExternalBacking -> {step,slot}`. Constructor-finalization rejection returns the exact already-linked close-only facade rather than throwing it away from the caller. Capacity refusal still returns null. There are no compatibility overloads. The earlier nullable-facade signatures below describe the historical R16 checkpoint, not the current API.
