# F5 — bcf (2.1) — Report

Plan: `~/.claude/plans/the-current-schemas-are-scalable-journal.md`. Recipe: `🧬️schema-design.md`. W0 recon: `w0-recon-report.md`. S2 spine (glue-mounting policy resolution, load-bearing for this report): `s2-spine-report.md`. OPC precedent read first, per the brief: `f4-docx-report.md`.

## 1. Package model — own simple wrapper, NOT OPC (documented per the brief's explicit fallback)

bcfzip is a plain flat zip: `bcf.version` at the root, one folder per topic guid holding `markup.bcf` plus referenced `.bcfv` viewpoint files and snapshot images. It has none of OPC's apparatus — no `[Content_Types].xml`, no `_rels/` relationship parts, no part/relationship graph — so `zip::opc::OpcPackage` (the shape docx/xlsx/pptx reuse, per `f4-docx-report.md`) genuinely doesn't fit. Per the brief's own fallback instruction, this wave built its own simpler package wrapper directly on top of the raw zip entry list (reusing `stdio.zip`'s real codec for every byte concern, same as the pre-existing code already did): `BcfSnapshot { schema, version: String, topics: Vec<BcfTopic>, parts: Vec<BcfRawPart> }`, where `parts` is the raw-retention mechanism (name-keyed, verbatim) for anything not covered by `bcf.version` or a topic's typed content — the direct analogue of `OpcPackage`'s unknown-part retention, just without the content-types/relationships layer that has no bcfzip counterpart to model.

## 2. Snapshot — from a shallow reconciled-view stub to the full completeness-target model

Old model (`entries: Vec<BcfEntry>` + a partially-derived `topics: Vec<BcfTopic>` with only `guid/title/status/comments/viewpoint_ref`) had two real defects beyond incompleteness: `Priority` was modeled as a `<Topic>` XML *attribute* when BCF-XML 2.1's `markup.xsd` declares it a child *element* (sequence position between `Title` and `Labels`), and `.bcfv` viewpoint content (camera, components, snapshot image) was never parsed at all — `viewpoint_ref` on the old `BcfTopic` only carried a raw filename string.

New model (`📸️snapshot/🦀️component.rs`), matching the brief's completeness target exactly plus two structurally-necessary extensions (see §7):
- `BcfPoint3{x,y,z}` — `visinfo.xsd` `Point`/`Direction`.
- `BcfCamera::Perspective{view_point,direction,up_vector,field_of_view} | Orthogonal{view_point,direction,up_vector,view_to_world_scale}` — a real Rust enum for the XSD's `xs:choice`, not two optional fields.
- `BcfVisibility{default_visibility,exceptions}`, `BcfColoring{color,components}`, `BcfComponents{selection,visibility,coloring}` — all weak value structs (whole-value replaced in diffs, per the recipe).
- `BcfComment{guid,date,author,text,viewpoint_ref: Option<String>}` — guid-keyed; `viewpoint_ref` is the `<Comment><Viewpoint Guid="...">` reference (a NEW field this wave added — the old model never parsed per-comment viewpoint references, only the topic-level `<Viewpoints>` list).
- `BcfViewpoint{guid,camera: Option<BcfCamera>,components: Option<BcfComponents>,snapshot: Option<Vec<u8>>}` — guid-keyed; `snapshot` is the referenced PNG's actual bytes (legitimate bytes-payload exception).
- `BcfTopic{guid,title,description,status,priority,labels: Vec<String>,creation_date,creation_author,comments: Vec<BcfComment>,viewpoints: Vec<BcfViewpoint>}` — guid-keyed; every field the target lists.
- `BcfRawPart{name,data}` — name-keyed raw retention.
- `BcfSnapshot{schema,version: String,topics: Vec<BcfTopic>,parts: Vec<BcfRawPart>}`.

Engine (`⚙️engine/🦀️component.rs`) gained real markup.bcf parsing/serialization for the full field set (fixing the `Priority`-as-attribute defect; adding `Description`/`Labels`*/`CreationDate`/`CreationAuthor` element parsing; adding per-`Comment` `<Viewpoint Guid>` reference parsing) plus real `.bcfv` `VisualizationInfo` parsing/serialization (`Components`/`Selection`/`Visibility`/`Coloring`/`PerspectiveCamera`/`OrthogonalCamera`), all via the real `stdio.xml` codec (`xml_document_from_text`/`xml_document_to_text`), never a hand-rolled parser. `decode_bcf` groups zip entries by top-level folder, resolves each topic's `markup.bcf` + its `<Viewpoints>` references' `.bcfv`/snapshot files, and retains everything else (including a topic-folder-shaped set of files with no `markup.bcf`, and non-topic root files like `project.bcfp`) as raw `parts`.

**Documented normal form** (an intentional, disclosed deviation from strict decode→encode byte-identity, per the recipe's "or documented normal form" allowance): `encode_bcf` always regenerates canonical `<topic-guid>/<viewpoint-guid>.bcfv` / `.png` filenames rather than preserving whatever arbitrary filenames a real BCF tool wrote. This is a deliberate simplification — the typed content (camera, components, snapshot bytes) is what round-trips losslessly; the on-disk viewpoint/snapshot filenames are not modeled as separate fields. `codec_retention_law` is satisfied against this normal form: `decode(encode(x)) == x` for any snapshot `x` already produced by `decode_bcf` (verified in `codec_retention_law` test).

## 3. Diff — real sparse, guid-keyed, recursive; own copy of the `NamedTripleDiff` engine

`🔺️diff/🦀️component.rs` defines its own `NamedTripleDiff<K,D,T>` generic engine (`removed: Vec<K>`, `modified: Vec<NamedModified<K,D>>`, `added: Vec<T>`, plus generic `between_named`/`apply_named`/`inverse_named`/`absorb_named` functions) — a verbatim port of docx's proven `NamedTripleDiff` (see `f4-docx-report.md` §3), including its `#[serde(bound(...))]` fix for the serde_derive `Vec<T>`-spuriously-requires-`T: Default` limitation. This wave's own copy rather than importing docx's: cross-artifact imports between sibling stdio artifacts would be architecturally wrong (each artifact owns its own schema types), and docx's own report already flagged hoisting this engine to a shared location as `glue_followup` for a future consolidation pass — this wave inherits that flag rather than resolving it (touching `zip::opc` is outside this wave's ownership boundary, same reasoning docx gave).

Three guid-keyed collections instantiate the engine: `BcfTopicsDiff`, `BcfCommentsDiff` (nested inside a topic diff), `BcfViewpointsDiff` (nested inside a topic diff); `BcfPartsDiff` is name-keyed (same engine, different key space). `BcfTopicDiff` is the sparse per-field struct (`title`/`description`/`status`/`priority`/`creation_date`/`creation_author`: `Option<String>`; `labels`: `Option<Vec<String>>` whole-value; `comments`/`viewpoints`: `Option<BcfCommentsDiff>`/`Option<BcfViewpointsDiff>` recursive). `BcfCommentDiff.viewpoint_ref` and `BcfViewpointDiff.camera`/`.components`/`.snapshot` are tri-state (`Option<Option<T>>`).

`wrap_topic_diff`/`wrap_comment_diff`/`wrap_viewpoint_diff` lower a per-topic/comment/viewpoint leaf diff into a full `BcfDiff` (the fixed two-level nesting equivalent of svg's `diff_at_path`/docx's `wrap_body_diff` — bcf's tree never grows deeper than topic → {comment,viewpoint}, so no generic path type was needed).

`impl MutationDiff<BcfSnapshot> for BcfDiff { apply, absorb }` + `impl DiffAlgebra<BcfSnapshot> for BcfDiff { inverse, between, is_empty }` — both real. `grep -n "snapshot: Option<"` on the diff file → zero hits. `grep -n "impl DiffAlgebra"` → present.

## 4. Mutations — 14 variants (up from 2), every `diff()`/`inverse()` handcrafted

`🧬️mutations/🦀️component.rs`: `NoMutation`, `SetSnapshot`, `SetVersion`, `InsertTopic`/`RemoveTopic`/`SetTopicMarkup` (bundles all scalar topic-markup fields as `Option<T>` params — sparse per-call), `InsertComment`/`RemoveComment`/`SetComment`, `InsertViewpoint`/`RemoveViewpoint`/`SetViewpointCamera`/`SetViewpointComponents`/`SetViewpointSnapshot`. Every variant's `diff()` calls a dedicated constructor (direct `BcfDiff` literals for the two top-level collection ops, `wrap_topic_diff`/`wrap_comment_diff`/`wrap_viewpoint_diff` for nested ones) — never apply-and-capture. Every variant's `inverse()` looks up prior state from `base` via `find_topic`/`find_comment`/`find_viewpoint` and constructs the exact undoing mutation (guid-aware, matching svg/docx precedent — `SetTopicMarkup`/`SetComment` only undo the fields that were actually touched, mirroring docx's `SetRunFormatting` field-level-undo pattern). `apply_bcf_mutation` is the single `let d = mutation.diff(snapshot); *snapshot = d.apply(snapshot); d` semantics source.

Also fixed the `📄set-snapshot` triad leaf (`🧬️mutations/📄set-snapshot/🔺️diff/🦀️component.rs`) — same gotcha docx's report flagged: its `diff(snapshot)` helper called `diff_set_snapshot` with the old 1-arg signature; updated to `diff(base, snapshot)` matching the new `between(base, next)` shape.

## 5. Test laws — all 6 present, real, in the engine's test module

`mutation_diff_law`, `inverse_law` (mutation-level round-trip for all 12 non-trivial variants + diff-level `d.inverse(base).apply(&d.apply(base)) == base`), `absorb_law` (with the canonical cases: Insert-topic+Remove-topic-before via `assert_absorb_matches_sequential`, Add-comment+SetField-on-that-comment verified to patch INTO the carried `added` payload rather than appear as a dangling `modified` entry, Modify-viewpoint-camera+Remove-that-viewpoint verified to annihilate to a plain removal, plus an associativity check comparing `absorb(absorb(d1,d2),d3).apply(base) == absorb(d1,absorb(d2,d3)).apply(base)`), `between_roundtrip_law`, `codec_retention_law`, `field_sweep`.

`field_sweep`'s `sweep_a`/`sweep_b` differ in every mutable field: `version` (scalar); `topics` (one removed `topic-remove`, one added `topic-add`, one modified `keep` with every scalar field changed); within `keep`'s `comments` (one removed `c-remove`, one added `c-add`, one modified `c-keep` with every field changed including `viewpoint_ref` exercising the `Some(Some(vp-remove)) → Some(None)` tri-state transition); within `keep`'s `viewpoints` (one removed `vp-remove`, one added `vp-add`, one modified `vp-keep` with `camera` changed value-to-value and `components`/`snapshot` both exercising `Some(...) → Some(None)` tri-state); `parts` (one removed, one added, one modified). Asserted in both directions (`between(a,b).apply(a)==b`, `between(b,a).apply(b)==a`) plus `between(a,a).is_empty()`, with a hand-written per-field `is_some()`/`assert_eq!(..., Some(None))` assertion for every field — matching the recipe's exact acceptance-criterion wording.

A real fixture bug caught and fixed while writing `field_sweep`: the first draft gave `sweep_a`'s and `sweep_b`'s `c-keep` comment the same `viewpoint_ref: None` in both snapshots, which meant `between` correctly reported no change on that field — the tri-state `Some(None)` assertion would have failed not because the diff algebra was wrong, but because the fixture never actually exercised a removal. Fixed by giving `sweep_a`'s `c-keep` a real `Some("vp-remove")` reference that becomes `None` in `sweep_b`.

A second real fixture bug, this one caught by the test suite itself (not just inspection): `field_sweep`'s `between(b,a).apply(b) == a` direction initially failed — not a diff-algebra bug, but the exact order-sensitivity gotcha docx's own report documented for `OpcContentTypes.overrides` (`f4-docx-report.md` §5): `apply_named` reconstructs a collection as "surviving items in the base's own relative order, then added items appended", so `sweep_a`'s `comments`/`viewpoints`/`parts` had to list each surviving item (`c-keep`/`vp-keep`/`part-keep.txt`) FIRST to match where it sits in `sweep_b`, otherwise the reconstructed collection has the right elements in the wrong order and `PartialEq` (order-sensitive on `Vec`) fails. Fixed by reordering `sweep_a`'s three collections; documented inline with a `🩹` comment citing the precedent so nobody "fixes" the diff algebra instead of the fixture next time.

## 7. Deviations from the literal brief (all additive, documented)

- **`SetVersion`/`SetViewpointSnapshot` mutation variants** added beyond the brief's literal list (`SetSnapshot, InsertTopic/RemoveTopic/SetTopicMarkup, InsertComment/RemoveComment/SetComment, InsertViewpoint/RemoveViewpoint/SetViewpointCamera/SetViewpointComponents`). `version` (top-level) and a viewpoint's `snapshot` (PNG bytes) are both real independently-mutable fields the completeness target itself lists; without a setter for each, the mutation API would be unable to reach two fields the diff algebra can already express via `SetSnapshot`/`between`. Purely additive — nothing in the brief's list was removed or renamed.
- **Comment `viewpoint_ref` field** added to `BcfComment` (guid reference to a `BcfViewpoint`, parsed from `<Comment><Viewpoint Guid="...">`). The brief's completeness table explicitly lists it (`BcfComment{guid, date, author, text, viewpoint_ref: Option<String>}`) — the pre-existing model had never implemented this half; this wave completes it.
- **`Priority` moved from XML attribute to child element** — a real pre-existing defect (not a design choice) fixed per BCF-XML 2.1's actual `markup.xsd` (`Priority` is `<xs:element>` in the `Topic` sequence, never `xs:attribute`).
- **Documented normal form** for viewpoint/snapshot filenames on encode (§2) — arbitrary on-disk filenames are read on decode but not preserved as a separate field; canonical `<guid>.bcfv`/`<guid>.png` names are always (re)written. Chosen for implementation-budget reasons within this wave; if a future fixture-fidelity pass needs exact filename preservation, `BcfViewpoint` would need two more `String` fields (`viewpoint_file`, `snapshot_file`) — not added here since it would be pure round-trip bookkeeping with no semantic content, and the recipe explicitly allows "documented normal form" as an alternative to byte-identity.
- **Out of scope, honestly**: `visinfo.xsd`'s `ViewSetupHints`, `Lines`, `ClippingPlanes`, `Bitmap`; `markup.xsd`'s `ReferenceLink`, `Header`, `ModifiedDate`/`ModifiedAuthor`, `AssignedTo`, `Stage`, `BimSnippet`, `DocumentReference`, `RelatedTopic`; and a `Component` element's own optional `OriginatingSystem`/`AuthoringToolId` children. None of these appear in the brief's completeness table (`selection: Vec<String>` etc. are explicitly the target granularity); not modeled, not silently dropped from anything real (they're simply not the scope this wave was asked to hit), and any real file using them will still round-trip that content as opaque bytes if it falls inside an unconsumed part — but note a topic WITH a `markup.bcf` that also uses these unmodeled sub-elements will lose them on an edit-and-reencode round-trip, since `markup.bcf`/`.bcfv` themselves are regenerated from the typed model, not raw-preserved once parsed. This is the same category of honest scope boundary as dwg's D3–D5 (per `w0-recon-report.md` §7) — a documented "not started", not a silent gap.
