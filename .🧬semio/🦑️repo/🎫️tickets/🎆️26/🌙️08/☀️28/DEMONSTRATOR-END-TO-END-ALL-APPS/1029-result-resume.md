## Design (coordinator decision implemented as stated)
`resume_task_command` no longer refuses. A resolved `TaskResolution::Command` is now QUEUED on the instance and delivered across funded turns through the runtime delivery lane (`drive_runtime_typed_command`: producer -> wire admission -> `dispatch_typed_command_inner`), exactly like the host-event queue. The reactor keeps its one-event-per-turn law and never waits.

1. Reactor `drain_task_resumes` -> `plugin_resume_task` Command arm -> `PluginApp::queue_task_resume_command(bytes, meta)` (sync; was async `resume_task_command(.., identity, cx) -> InvocationResult`): validates the `OpBinary` bytes (same `interactive-job.task-resume-command` fault) and `push`es onto `HostEvents.resumes`; no frames. `drain_task_resumes` returns `true` (more-work) when it handed a Command to an instance, so the next turn polls and the continuation phase runs. The `Emit` arm is unchanged (single direct `dispatch_emit`).
2. Instance owns the queue: new `TaskResumes<R = InvocationResult>` in the command crate beside the runtime-command producer it sequences (`🎮️command/🎟️typed/🔁️resumes`, re-exported from `original_typed_command`), stored as `HostEvents.resumes` (history crate) so no DispatchCtx/bundle struct changed: FIFO of `(command bytes, ActionMeta)`, `started`/`closing`, the unclaimed `outcome`, fairness `turn`; pure planner `plan(cancelled, source_pending, lane_busy) -> Idle|Close|Drive`; bounded at `TASK_RESUME_QUEUE_SLOTS = 1024` (full -> `interactive-job.task-resume-queue` fault).
3. Driver `DispatchCtx::task_resume_step` (instance-dispatch `📥️staging/🔁️task-resumes`): Idle -> nothing; Close -> `cx.with_original_retirement(|cx| source.close_step(cx))`; Drive -> lend bytes+meta, `drive_runtime_typed_command(source, || decode_op(bytes) boxed, ..)`, `Some(receipt)` -> `delivered` (front popped, receipt owed), `None` -> `restore` (unconsumed bytes/meta go back), `Err` -> `failed()` (source closes through paid steps, front dropped, next one starts) and the failure propagates unchanged. The command is decoded inside the producer's `make` closure, i.e. only once the producer is funded to take it.
4. Reactor wiring (instance-app `plugin-app-impl`): `advance_typed_operation_publication` has a rung `resumes.runnable() && resumes.take_turn()` (alternates with every other publication owner so a flood of resumes cannot starve the publication that frees typed-operation slots); `has_runnable_typed_operations` / `has_pending_typed_operations` include `resumes.pending()`; new `PluginApp::take_task_resume_outcome` (default `None`) is framed in `advance_typed_operation_output_with_leftover` like the reserved-commit outcome (unsolicited `AppFrame::Invocation`, `in_reply_to: 0`, plus side frames).
5. Shared-source exclusion: the delivery uses the composer's one `original_typed_command` source (so the existing close ladder / maintenance close / terminal checks already own its custody). A resume STARTS only when the source is idle and no host-event delivery runs (`plan(.., lane_busy = host_events.delivering)`); while one is in flight (`resumes.in_flight()`) the four other source users wait one turn (`Ok(None)`): `dispatch_action_received`, `dispatch_command`, `preview_addressed_action` (command-routes) and `handle_intent_frame` (plugin-app-impl).
6. Cancel/close: `cx.is_cancelled()` -> source closed step by step (`Close`), then the whole queue is cleared; an unclaimed receipt is claimed first. Instance close: the source is closed by the existing ladder rungs; closing instances are skipped by the continuation scan.

History semantics: a task follow-up is a normal applying command, recorded under its own verb (unlike host events, whose operations are inserted into `host_event_operations` and never become history rows) - this is the contract the retained `spawned-task-resume` law states.

## Risks / follow-ups
1. Failure of a delivery (e.g. `document_loading_refusal`, tool catalog refusal) propagates as a turn failure after the source is closed and the front dropped; the task result is lost (before: a fault frame). A fault-frame mapping needs an `OriginalTurnFailure -> Fault` conversion that does not exist yet.
2. A resume delivered while the document is loading is refused (same `admitted_while_loading` rule as any command) - not retried.
3. Runtime proof of the end-to-end path (generator pane task follow-up) belongs to the coordinator's serve/e2e run.


## Wave 2 (coordinator: fault frame, mounted tests, single helper)

### (1) A failed resume delivery answers its task with a fault frame
- `TaskResumes<R>` now defaults `R = Result<InvocationResult, Fault>`; `failed(answer: Option<R>)` closes the source through paid steps and then leaves `answer` as the receipt owed to the host (cancel drops it).
- `task_resume_step` maps a refused delivery to a `Fault` (`delivery_fault`): the original application diagnostic when the failure carries one, else `interactive-job.task-resume-delivery` with the failure text. A failure that carries partial retained progress, a receipt refusal or a context refusal is NOT swallowed (accounting must travel): it still propagates as the turn failure after the source is closed.
- `PluginApp::take_task_resume_outcome` -> `Option<Result<InvocationResult, Fault>>`; `advance_typed_operation_output_with_leftover` frames `Err(fault)` through the existing `push_app_fault` branch (`AppFrame::Error`, same shape as every other invocation failure).
- Law fixture `C... 🎮️command/🎟️typed/🧪️tests/🧫️fixtures/🔁️task-resumes/🔣️.json` gained `failure-closes-the-source-then-answers-the-task-with-its-fault`, `failure-without-an-answer-leaves-no-receipt`, `cancel-drops-the-fault-owed-for-a-failed-resume` (12 scenarios, test asserts >= 10). The mounted test below showed the fault frame path live: the refused delivery came back as `Fault{code: interactive-job.task-resume-delivery, message: "...requires its original committed tool catalog"}` and the turn did not fail.
