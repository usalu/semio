## Capacity queue priority classes (coordinator question, 10:40)

They exist, so no code change is needed. Two layers, both schema-declared:
1. Host capacity queue (`🔨️modules/🏃️process/🏗️build/🌡️host-capacity/📏️decision/🟦️.ts` `orderHostWaitersV1`): request priority `interactive` | `batch`; order = interactive, batch, then (grow/elastic requests last); inside a class weighted fair share between agent sessions, then arrival; batch is aged (`wait.agingMilliseconds` 300000). The operation table (`🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/🔣️policy.json` `hostCapacity.operations`) marks only `watch` interactive; `run`, `exec`, `cargo`, `show`, `graph` are batch.
2. The class of the calling process (`hostRequestPriorityV1` -> `leasePriorityClassV1`, `🔒️leases/📈️standing/🧬️schema/🔣️.json`): env `SEMIO_LEASE_PRIORITY` = `interactive` | `agent` | `background` wins over everything (default `agent`; a human terminal is interactive). `interactive` also gets a 1 h arrival advance in the lease queues, so both queues agree. A request becomes `interactive` in the capacity queue when its process standing is interactive.
The fleet runs at the default `agent`, the activation's nested `repo cargo`/`exec` requests too. Bazel actions inherit the run's `SEMIO_*` environment (checked on a live action: SEMIO_HOST_CAPACITY_GRANT/PLAN, SEMIO_BUILD_*), and `SEMIO_LEASE_PRIORITY` is already an ignored (non-keying) variable of the world witness, so it does not invalidate actions.

The repo itself relies on this at birth (`🍎️image/🪶️sparse`: `hdiutil resize -size <N>m <backing>` before first attach, which hands the whole size to the volume).
- Host volume: 146 GiB free, so 48 -> 96 GiB is admissible; `elastic.rust` (`💾️storage/🔒️enforcement/📦️budget/🔣️policy.json`: need 48 GiB x 125 %, `maximumBytes` 64 GiB, host-free reserve 50 %) only sizes a NEW image; `pinnedCapacityV1` / `effectiveCapacityV1` (`📐️elastic`) pin an existing image to the size in `image.json` ("a larger declaration takes effect only through the explicit reset that births a new image").

What a grow must change besides the file (found by reading the live state), i.e. why a plain `diskutil image resize` would break the store:
1. `image.json` receipt: `size`, `filesystemBytes`, `maximumPhysicalBytes` (= filesystemBytes + 1 MiB); dev/ino stay (same file), `bootSession`/`ancestry` stay.
2. `m/storage-events.jsonl` (journal): every child allocation carries `child.parentIdentity` = `[dev, ino, size, mountdev]` of the parent backing (here `[16777229,559683723,51538558976,16777268]`); after the resize those no longer match and every parent `recheck()` fails with "Exact original parent child allocation required" (the nested `cs/v` compiler-state image is such a child). They need an atomic re-stamp, ideally as a new schema event `resized` (old identity -> new identity) so the journal stays append-only and replayable.
3. Policy constants: `⚡️caching/🔣️policy.json` `storage.strictStorage.capacityBytes/filesystemBytes`, `budget/🔣️policy.json` `partitions.rust.capacityBytes/maximumLogicalBytes` and `elastic.rust.needBytes/maximumBytes` (the 64 GiB maximum would clamp a 96 GiB receipt back down: `effectiveCapacityV1` returns `min(receipt, maximumBytes)`), plus the headroom schema `maximumShareBasisPoints` ceilings which are fractions of the live volume (no change).
4. Consumers that read the volume size at open (`nativeImageVolumeBytesV1`, `measureVolumeV1` in headroom, `unitCacheCapacityBytesV1`) follow the receipt/statfs and need no change once 1-3 are consistent.

Exact plan for a repo operation `repo cache grow <partition> --bytes=<N>` (schema-first constant `elastic.<partition>.growTargetBytes`, refused above `min(maximumBytes, hostFree - reserve)`):
 a. preflight: partition is a fixed native image, host free >= N - current + floor, no pending `.publication/intent.json`, receipt valid, target > current and MiB aligned;
 b. take the image lease EXCLUSIVE (`native-fixed-image:<root>`; every cargo/component command holds it shared, so new commands queue behind the grow and running ones drain; tests of 30 min mean the drain can take that long - print who holds it, support cancellation and progress);
 c. nothing else may use the mount: `lsof +f -- m` empty, no compiler-writer/ballast/headroom row live; detach nested children first (`cs/v`), then `hdiutil detach m`;
 d. `diskutil image resize --size <N>m fixed.dmg` (rollback is built in; keep the old receipt as `image.json.pre-grow` until step g);
 e. re-attach with the schema `attachArguments` (`-nobrowse -noautoopen -owners on`) and verify statfs bytes >= old + (N - old) - container overhead;
 f. rewrite `image.json` and append the `resized` journal event re-stamping every child `parentIdentity`, in one publication (`.publication/intent.json`) so a kill is recoverable;
 g. release the lease, delete the pre-grow receipt, record before/after in the ticket.
Tests: (1) pure unit tests of the new size/identity arithmetic with a Python oracle; (2) an end-to-end test on a scratch 64 MiB -> 256 MiB seeded image (same code path the birth uses, no fleet), asserting statfs growth, receipt, journal re-stamp and a crash between d and f recovering to either state; (3) a refusal test for an attached image and for target > bound.
