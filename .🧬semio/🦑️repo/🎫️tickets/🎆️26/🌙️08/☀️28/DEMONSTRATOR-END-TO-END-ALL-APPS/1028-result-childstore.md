## Follow-up 1: `retiring`-phase row (killed mid-retire)
A funded child's `retiring`+`retired` events are appended in ONE write after the physical image and namespace are gone, so a persisted `retiring` row (append torn at the line boundary) means "physically gone, only `retired` owed". ## Follow-up 2: lock self-wait (root cause + fix + law)
Root cause: `🧹️cleanup/🎛️command/🟦️.ts` (successful persistent child retirement) takes the parent `native-storage-mapping` EXCLUSIVE (`scope.mapping=await acquireNativeStorageMappingWriterV1`) and released it only on the success tail. Any throw inside the retire body (the old code threw `Original recovered creator identities required` / `Unknown entry exceeds exact Native creator inventory` for the sidecar-only row) leaked the EX in the process-global `retained` set, forever. The next mapping read in the same process (`withNativeStorageMappingReadV1`, no frame, queued shared) then waits on its own process's lease: the daemon 10518 self-wait, and the same hang at `private-retire` teardown in tests. Reproduced with a `[DEBUG]` probe (removed) and with the fix disabled: the test hangs in "Waiting for access to native-storage-mapping (shared) … behind the request of process <own pid> (exclusive)".
Fix: the retire body after the acquire is wrapped in `try/catch`; on failure `scope.mapping` is cleared and the writer released (AggregateError if the release also fails), then the original error rethrown.
Law (funded test file): "a failed funded child retirement releases its parent mapping for the next retirement": births a namespace, puts a stray entry in the child directory, expects the retirement to reject, removes it, and expects a second retirement in the same process to succeed. With the release disabled it hangs on the self-wait; with the fix it passes.
