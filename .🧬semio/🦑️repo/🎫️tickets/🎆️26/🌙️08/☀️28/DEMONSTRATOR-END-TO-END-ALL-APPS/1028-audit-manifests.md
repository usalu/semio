# 1028 Manifest Audit (static, read-only)

Auditor: `manifestaudit` (Haiku). Scope: the 32 closure components of `♻️mit-bestand/🧺️demonstrator/🔨️modules/🧩️runtime/🧫️cases.json` (11 plugins + 21 extensions). No builds, no cargo, no edits outside this report and the auditor's tool folder.

## Status

RED (static): 0 manifest/dependency/feature/lock/workspace defects across the 32 components. 32/32 lack a `component` target in any `📋️project.json`, so the requested project.json check cannot pass as written. Owner-side build route is `package` (extensions) or none (hub compositions).

## Checks performed

For each component (catalog entry from `✏️s/🧑‍💻dev/🧩️catalog/🤖️generated/🧩️plugins/🟦️.ts`, `cratePath` + `packageName`):

1. Crate dir and `Cargo.toml` exist; `[package] name` equals catalog `packageName`.
2. Workspace resolution: `package.workspace` if set, else nearest ancestor `[workspace]`. Crate is a member (not excluded, not outside). Enclosing `Cargo.lock` exists and contains the package name.
3. `[lib] path` and `[[bin]] path` exist.
4. Every `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]` and `[target.*]` path dependency (including `workspace = true` entries resolved through `[workspace.dependencies]`): manifest exists, `[package] name` equals the dependency `package =` or key, the dependency name is present in the same `Cargo.lock`, a path dep located inside the workspace dir is a member, and requested `features = [...]` exist in the target crate (`[features]` keys or optional deps for `dep:`). Feature validator sanity-checked on a bad and a good input.
5. Owner: `📋️build-owners.json` plus the catalog. Checked whether a `component` target exists and whether `package` targets reference existing scripts and input paths.

Not checked: `feature/dep` strings of the form `dep/feat` (skipped), registry/`depends-on` metadata, `[package.metadata.semio.sources]`/`assets` roots, non-path (registry) dependencies, transitive deps beyond one level.

## Findings

1. **`component` target missing everywhere (32/32).** No `📋️project.json` in the component trees defines a `component` target. Hub composition owner `🌎️hub/🧩️compositions/📋️project.json` has `native`, `ownership`, `typescript`. Hub component crates' own `📦️packages/🦀️rust/📋️project.json` have `test` (plus `graph-generate`, `wasm`, etc. for flow/puzzle/gis). Extension owners `…/📦️packages/🦀️rust/📋️project.json` have `package` and `test` (brep also `canonical-architecture` and `test-mesh-oracle`; playbook procedural `canonical-architecture` and `geometry-contract`). The 32 `package` targets reference `repo ./📜️script.ts package` with existing input paths. Hub component packages have no `package` target. Either the brief's assumption is stale or the component wasm build is declared outside `project.json` (e.g. the registry/`📋️build-owners.json` route). I did not resolve which.
2. **Build-owners ancestor lookup.** `📋️build-owners.json` lists each Rust crate as its own owner with `Cargo.toml` manifest, and extension packages as `…/📦️packages/🦀️rust/📋️project.json` siblings (not ancestors) of the component crates. Owner resolution therefore fell back to the composition owner for hub components and to none for extensions. Not a defect in the manifests, but a gap in the owner mapping for the component crates.
3. **Workspace layout.** Hub components resolve against `🌎️hub/Cargo.lock` (workspace `🌎️hub`, `package.workspace` set on the cad component). Each extension component resolves against its own extension-root workspace and `Cargo.lock` (e.g. `✏️s/🔌️plugins/📐️cad/🧩️extensions/🏢️aec-building/Cargo.lock`). Framework path deps outside those workspaces (`🧰️framework/…`) are reached through path dependencies and resolve by name in the lock.
4. **Feature references.** All `features = [...]` in the 32 manifests resolve in their targets (e.g. `semio-framework-plugin` `artifact-app-testing`, which is defined in `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/📦️packages/🦀️rust/Cargo.toml`).
