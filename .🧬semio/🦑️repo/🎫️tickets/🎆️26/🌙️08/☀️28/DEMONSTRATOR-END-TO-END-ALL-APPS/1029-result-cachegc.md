# 1029 cachegc result

STATUS: DONE, live. New cargo admissions now reserve image headroom and queue instead of hitting ENOSPC. The GC reacts within a second and on demand. Tests are green (50 pass, 0 fail across the 7 touched or adjacent files), tsc is clean, and the real `repo cargo check` runs through the new code path (see "Live evidence"). Applies to new admissions only; no running cargo was touched.

## What was wrong (measured)
- 10 concurrent cargos wrote the 48 GiB image to 0 free. The memory gate had no image dimension.
- The watcher polled every 30 s and a burst fills 8 GiB in less than that.
- At 0 free the collector could not even create its claim file: `u/gc.log` ended in `ENOSPC … u/k/gc.lock`, so the "emergency" path died exactly when needed.
- A waiting or running command pins its pooled lane (live marker), so GC could never evict the space it was waiting for.

## Design (schema first, all bounds in JSON)
1. **Image headroom admission** (new, `unit-cache/🧹️gc/🏦️headroom/`). Policy, messages (EN/DE), record and history shapes are in `🧬️schema/🔣️.json`.
   - Reservation per cargo class (subcommand, then target, then crate set, each split warm/cold lane by the pool's own prediction `planPoolAcquireV1`): nearest-rank 0.9 quantile of what earlier commands of the class wrote to their lane (`lane bytes after − before`) plus a 15 % margin. The most specific class with at least 2 samples wins, else the prior (cold 2 GiB, warm 0.75 GiB). Never above 15 % of the image, never below 128 MiB.
   - A running command's outstanding bytes shrink linearly to 0 over its learned wall time (what it already wrote is already missing from `free`).
   - Admission rule (`decideHeadroomV1`, pure): `free − floor − Σ outstanding(running) − Σ reserved(waiting, earlier arrival) ≥ own reservation`. Floor = 3 % of the image, at least 1 GiB. Strict arrival order with backfill (a later small command passes when it fits after the ones ahead). Escape hatch: the only command left (nothing running, nothing ahead) goes on once one cleanup has completed (`alone`), so waiting can never deadlock; the existing ENOSPC retry handles a real shortfall.
   - Ledger: one record per command in `u/h/<id>.json` (heartbeat by mtime, dead pid or silent for 20 s is ignored, abandoned after 10 min is removed). The decision runs under the short `headroom` claim, so two processes never both take the last room. History in `u/h/history.json` (32 samples per class, 256 classes).
   - Waiting: progress line every 10 s ("waiting Ns for compiler image headroom: needs X GiB (free, still expected from N running, reserved ahead, kept free)"), exponential poll 250 ms → 2 s, cancellation through the invocation signal withdraws the record (verified live: SIGINT, exit 130, record gone).
   - **Admission happens before the lane is taken** (`withAgentLaneV1`), so a waiter pins no lane and GC can evict idle lanes for it. Also covers the component-driver lanes (`withRepositoryComponentLaneV1`).
2. **GC on demand** (`gc/🟦️.ts`). `planGcV1`/`collectGarbageSingleFlightV1` take `demandBytes`: the shortfall of waiting commands raises the need of every stage (incremental sessions, stale units, idle lanes oldest first, unprotected cold objects) whatever the water marks say; still lock-aware (unit `.lock`, profile build lease, lane live marker): nothing a running cargo holds is evicted. A waiter at the head of the queue triggers it (single-flight, at most every 2 s).
3. **Tighter trigger**. The watcher senses the image every `watchSenseMilliseconds` = 1000 (one statfs) instead of 30 000. Fill samples and profile scans keep the 30 s cadence. A collection that frees nothing is retried only after 30 s, and the "stalled" rule still counts 10 fruitless collections. Every admitted command also watches the image every 2 s and, the moment free falls below the floor, frees `2×floor − free` on demand in its own process (event-like, independent of the watcher).
4. **Ballast** (new, `unit-cache/🧹️gc/🛟️ballast/`). A 32 MiB real file `u/ballast` is given back when a claim, stamp or record write hits ENOSPC (`tryClaimWithBallastV1`, collector start, headroom records), so the collector and the admission still work on a full image. Re-created when the image has 4× its size free.

## Caveats and follow-ups
- Bytes are the lane's logical growth, so reflink restores from the unit cache count in full: estimates are conservative (a cold lane filled from cache hits is over-reserved), which shows as longer queues, never as ENOSPC. A physical measure (solo-run statfs delta, or APFS private size) would tighten it; not done.
- Conservative by design: a running command's outstanding bytes decay linearly over its learned wall time, so a command that runs slower than its class (memory-gated) is under-counted late and one that runs faster is over-counted early; with `quantile 0.9`, 15 % margin and several 5 to 7 GiB commands running, a new check can wait 10 minutes although `df` shows 20 GiB free. A closed-loop correction (write rate from the 2 s statfs monitor) is the next refinement; I did not add it because an under-reservation brings ENOSPC back.
- The first version used a 6.25 % floor and a 25 % cap and starved at the GC operating point (6–12 GiB free); the policy now is floor 3 %/≥1 GiB, cap 15 %, prior 2 GiB. If the queue is still too tight, the knobs are in the schema (`floorBasisPoints`, `maximumShareBasisPoints`, `estimate.quantileBasisPoints`, `estimate.marginBasisPoints`, `prior`); the real fix for throughput remains the larger image (diskcap result: reset to 60 GiB when the fleet is quiet).
- A waiting command still holds its memory grant (the host capacity gate does not lend it during an image wait).
- The image-wait does not extend an idle-window deadline of the invocation (it honors the signal only, like the lane-pool wait).
- Final-code run: `cachegc-chk3` (same command) RC 0, "Finished `prototype` profile … in 3m 02s", after queueing for image headroom (see its waiting and admitted lines in `🗑️generated/1029/cachegc-chk3.txt`).
- chk2 (started under the first policy) was cancelled by me with SIGINT (pid 9360) after 25 minutes in the queue; chk3 is the final-code run.
