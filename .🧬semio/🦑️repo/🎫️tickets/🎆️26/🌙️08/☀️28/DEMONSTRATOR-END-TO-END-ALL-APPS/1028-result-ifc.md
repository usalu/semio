## 2. Gate semantics (data is not exempt)
`🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/📥️source/{🟦️.ts,🎟️admission/🟦️.ts}`: closure = lib entry + `mod`/`#[path]` + `include!` (source) + `include_str!`/`include_bytes!` (embedded: bytes counted, 0 active lines). Limits = min(global 262144 B / 32 files / 4000 lines, per-crate `rust-source-boundary`), policy schema caps the per-crate value at the global, so no per-crate raise is possible. `include!(concat!(env!("OUT_DIR"),...))` and macro-expansion origins are refused outright ("Generated Rust input requires compiler ownership"), so a build.rs/OUT_DIR generated-data pattern is not available either. Only `provenance.kind==="workspace"` units are measured, but every `path =` crate is workspace provenance.
Existing patterns for large data: none usable. No wasm host asset import exists (`rg -i asset|blob` in all `*.wit` finds nothing), `include_bytes!` of big payloads is counted, and no crate in the repo carries a >256 KiB embedded table. The ifc tables are generated Rust literals (`4x3/…/⚖️validation/program.rs` 5.7 MB, `metadata-data.rs` 3.1 MB, `📚️catalog/data.rs` 2.7 MB, `🏷️templates/data.rs` 2.5 MB, `👁️mvd/data.rs` 0.4 MB) next to language-neutral sources (`🔣️.json` 1.9 MB, `IFC4X3_ADD2.exp` 0.4 MB) that are themselves > the 256 KiB cap, so "parse the schema at runtime from an embedded file" cannot pass either. Embedding the schema in a guest is therefore impossible under the gate; the only compliant options are (a) the guest does not link ifc at all, or (b) a new host asset ABI. (b) is a framework-level design item, not an executor fix.

## 4. Remaining blocker: gis (and vcs) statically link the full stdio catalog
Chain: `semio-hub-gis-component < semio-hub-gis < semio-hub-stdio-catalog < semio-s-artifact-stdio-ifc < ifc-4x3` (+ `< stdio-semio-catalog < stdio-semio-model-import/export < ifc-4-model`).
gis only needs the catalog as a trust commitment (`TopicContribution` `stdio.artifact-catalog.v1` + `PluginDependency("stdio")`), which `validate_native_artifact_catalog_contributions` in the hub compares byte-for-byte with the stdio component's. I did not change this: it is the artifact-authority trust model (tests in `🌎️hub/🗿️artifact-authority/*`, `🌎️hub/🧪️tests/🔏️trusted-catalog-profile`).
Findings that make a clean fix possible:
- `native_artifact_catalog` reads only `assembly.definition()` (identity, capabilities, descriptor bytes, claims, localizations) and the native-codec receipts. `ifc` has `native_codecs() == []`, so its projection is identical whether its assembly is `Runtime` or `Definition`.
- The contract already has `definition_only_assembly(artifact, definition)` (`✏️s/🔌️plugins/🗄️stdio/📇️registry/🧬️contract/🏗️assembly/🦀️.rs:718`) and `ArtifactAssembly::Definition`.
Recommended design (needs owner decision, touches trust code, not applied):
1. New light crate `semio-s-artifact-stdio-ifc-definition` (owns `📜️artifact-definition.json`, `definition()`, `formats()`, schema const); `semio-s-artifact-stdio-ifc` (runtime: composers, 4x3, 4, 2x3) depends on it.
2. Catalog crate gets a second roster (generated from the same `🧩️composition/🔣️.json`, schema-first) of definition-only contributions for artifacts without native codecs (ifc, and the semio import/export conversions that only matter for their definitions), consumed by a new `native_artifact_catalog_contribution()` used by gis/vcs/fixtures; the stdio component and native hub keep the full runtime roster. A test in the stdio component asserts both rosters produce byte-identical payloads (third-party-validated by the existing JSON-schema validator).
3. gis/vcs/process stop linking runtime ifc; `stdio-semio-catalog` needs the same split for `model-import/export` (they name `ifc-4-model` and `ifc`).
Risk: ~8 crates + generator + trusted-catalog tests; each wasm check queues 20-60 min. Alternative (b): add a host asset import and move the 16 MB tables out of the guest; larger.
