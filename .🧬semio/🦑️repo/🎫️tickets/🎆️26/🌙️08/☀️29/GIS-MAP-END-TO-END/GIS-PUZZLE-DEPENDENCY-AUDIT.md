# GIS Puzzle Dependency Audit

The GIS-specific development entry explicitly imports `PUZZLE_BOARD_SESSION_FACTORIES` from `@semio-tech/puzzle-2d` and passes it to `bootFrameworkOsDev`; its contribution schema explicitly declares the Puzzle Rust engine. This is not an accidental selection by a generic Play facet. The Vite config passes that declaration to `frameworkOsEngineFacetV1`, which selects `play` when the Puzzle source owner is declared. Serve artifact inputs and the managed WASM Vite plugin then select all four engines. Build mode explicitly selects `distribution` independently of this selection.

The imported factory module does not initialize Puzzle WASM at boot: its `createWasmModuleLoader` callback dynamically imports `@semio-tech/puzzle-wasm`, initializes it and installs assets on session creation. Vite must nonetheless resolve that literal dynamic import. The four registered factories exclusively match plugin `puzzle` and the Puzzle 2D/5D editor/viewer app IDs. The renderer resolves factories against the focused program's plugin and app identity. GIS's component has no Puzzle or board-2d references, and the specific dev boot filters by the selected variant. GIS map sessions, its inference presentation and its GIS worker have separate paths; no inspected GIS source references the Puzzle factory except the entry and declaration.

For a GIS-only serve, the narrow source change is to remove the Puzzle factory import and `surfaceSessionFactories` property from the GIS entry, remove its `browserSessionFactories` declaration (or use an empty list), and pass `contribution.browserSessionFactories ?? []` in its Vite config. This selects `renderer`, retaining Surface, Editor and NodeGraph while excluding Puzzle. Preserve the GIS inference presentation, format catalog and worker. Update the ownership assertion that currently requires Puzzle in the GIS entry and the engine contribution tests that currently assume every factory contribution selects `play`. Add tests proving GIS map/editor/viewer and actor UI continue to work without Puzzle and that Puzzle's own 2D/5D routes still receive factories. Do not change the shared Play entry or Puzzle variant: Play's own scoped Vite configuration already aliases the factory to an empty module only when its runtime targets contain no Puzzle; Puzzle scopes require the actual factories. Distribution builds remain a distinct concern.

This is a static audit, not a runtime verification. If this standalone GIS deployment intentionally permits launching Puzzle programs outside its selected GIS scope, removing its factories would break their board sessions; verify that product contract before applying. No build or lease was started.
