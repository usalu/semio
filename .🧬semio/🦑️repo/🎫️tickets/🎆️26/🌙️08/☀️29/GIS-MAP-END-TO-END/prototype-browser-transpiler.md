# GIS prototype browser transpiler prerequisite

Prototype run `wUqI5O6` completed the Cargo pass with status 0, one linked GIS component and 1,105 units in the final attempt. The component was 138,530,740 bytes and its main core had 287,988 defined functions. The compiler lane and both staged copies retain the output.

The browser stage failed before spawning the transpiler. The cause chain in `🗑️generated/react-launch-prototype-fresh-4.log` reports that `nativeTranspileBinaryV1` could not find `.cache/b/p/m/browser/release/tools/native-transpile/darwin/semio-native-transpile`. The simultaneous descriptor stage subsequently reported closed admission. The failed stage had produced neither transpiled files nor a completed component provenance receipt at inspection time.

The declared producer is `@semio-tech/os-plugin-native-transpile-rs:build`. Its host-specific build script publishes to the exact path the transpiler resolver expects after validating the captured executable. It is already a prerequisite of the graph-backed browser component build. The graph-free React playground path prepares browser support and the descriptor emitter, then enters the component closure without preparing the native transpiler. Add that preparation where the graph-free path handles its other boot component prerequisites, before linking starts.

The normal managed warm replay is the legitimate way to reuse the retained Cargo output while recording fresh provenance and publishing the browser facet. It can reuse the immutable warm Cargo result when the input and toolchain match. The failed stage directory alone does not establish the provenance required by `publishComponentBrowserV1`. No compiler rerun, transpiler build, or artifact copy was started during this investigation.

The graph-free launcher now prepares the selected native transpiler after checking which boot components are missing and before starting the component driver. It invokes the existing producer under the real launcher Original. That producer validates Cargo's recorded successful output before publishing to `.cache/b/p/m/browser/<mode>/tools/native-transpile/<platform>/<binary>`. `win32` uses `semio-native-transpile.exe`, Darwin and Linux use `semio-native-transpile`. The release tool path is the same as before. The graph target leaves publishing to the native producer because the existing graph host-output declaration cannot represent both Original modes accurately.

The browser stage uses the component's exact profile, honors `SEMIO_NATIVE_TRANSPILE_BIN`, and requires the selected executable before checking the transpile cache. The cache key includes a SHA-256 of that executable, so a different or invalid override cannot hit an entry for the previous tool. Both producer and consumer use the same path resolver. The test fixture covers cold prototype and release preparation, ready platform-specific publications, configured override success and refusal, rejection of a directory override and executable digest binding. Four focused tests passed with 39 checks. Cold native-tool production and the warm GIS browser replay remain unverified by these tests.
