# GIS core function count

The prototype GIS pass built 1,390 Cargo units. The sole failure was the GIS cdylib, after LLD had linked the core and `wasm-component-ld` attempted to encode it as a component. The failure was `functions count exceeds limit of 1000000` at offset `0x1d11`. The reported offset is a byte location in the module and does not disclose the declared function count. The managed pass log is `.cache/b/r/m/components/runs/wjJd6PU/l/cargo-prototype-00-retry-3.log` at lines 151160–151171. The run report is `.cache/b/r/m/components/runs/wjJd6PU/r/report.md`.

## Component-specific prototype profile

The existing managed release component profile uses size optimization, 16 codegen units, disabled incremental compilation and ThinLTO. The prototype WASM profile uses optimization level 1, 256 codegen units, incremental compilation and LTO off. The latter is also used by browser-canvas and browser-module producers.

The policy now has a `prototype-component` settings row to `🦀️profile/🧬️schema/🔣️.json` with `optLevel: "s"`, `debug: 0`, `codegenUnits: 16`, `incremental: false` and `lto: "thin"`. `planCargoProfilePolicyV1` selects this row for prototype mode and the resolved `component` role. The real GIS component driver in OS plugin build `🧩️driver-stages/🟦️.ts:101` supplies producer `artifact`. The profile policy maps that request to role `component` when the target is `wasm32-wasip2`, so matching only the literal `wasm-component` producer would miss the public path.

The existing renderer and verifier already derive prototype debug assertions and overflow checks from mode and strip component symbols from role. Keep these selectors and the target's 512 MiB linear-memory limit and 8 MiB stack. Browser producers continue to consume `prototype-wasm`. Preserve existing authored package constraints and host settings. Actual prototype validation still matters because its assertions, overflow checks and per-package constraints differ from release even with the same top-level optimization settings. ThinLTO requires recompilation of the prototype target units.

The updated language-neutral policy and effective-settings fixtures are in `🦀️profile/🧪️tests/🔣️.json` and `🦀️profile/🧪️tests/📥️consumption/🔣️.json`. Both `artifact` and explicit `wasm-component` requests at `wasm32-wasip2` are covered, with the browser rows as controls. `repo run @semio-tech/repo-lib:test-build-mode --lang=en` is a declared target. Its consumption test validates the actual rendered selectors using TOML parsing. The profile-oracle suite separately checks pinned Cargo unit graphs and compiler flags. Both regression tests failed against the previous profile with the expected four setting differences. After the change, the four selected policy, rendered TOML, effective selector and role tests passed using the pinned Bun. The rendered TOML check compares Bun against the independent @iarna/toml parser. The updated GIS guest has not been relinked in this investigation, and the product acceptance condition remains encoding, descriptor publication, and GIS2D interaction through the normal prototype command.

## Reusing the prototype link objects

The pinned WASM LLD rejects `--icf=all` as an unknown argument. Its garbage collection is already enabled in the failing invocation. Its LTO switches require bitcode; the normal prototype linker is consuming already generated Wasm object files. The linker log retains every library in order but abbreviates the 257 component objects and redacts sysroot archive suffixes. The warm `p63442a` lane still has exactly 257 root component `.rcgu.o` files. This supports a link-only diagnostic from the failed command and existing objects without rebuilding Cargo. A reconstruction from the abbreviated stderr has inferred object order and must be marked diagnostic. For an exact replay, capture a package-scoped Cargo rustc invocation with full link args under the same managed component lane. Avoid global RUSTFLAGS, which can invalidate the dependency closure.

The pinned `wasm-component-ld 0.5.26` exposes `--skip-wit-component`, so an admitted linker-only diagnostic can produce the core Wasm under the ticket's generated directory. Parse the core Function section's first unsigned LEB128 count to measure actual headroom or required reduction. The pinned linker also accepts `--wasm-ld-path`; a managed host launcher could run the pinned LLD, apply only the pinned Binaryen `--duplicate-function-elimination` pass to its output, and return that core to the existing pinned component encoder. This retains the existing WIT, WASI adapter and validation behavior, provided the optimization preserves the embedded `component-type*` custom sections and import and export interfaces. The core reduction and full-component runtime remain unmeasured. These hypotheses need a finite fixture comparing custom-section bytes, export/call behavior and before/after function counts, then the real core run under admission. Include the launcher and optimizer identities in compiler input custody before normal use. Browser-stage optimization already happens after component encoding and cannot address this failure.
