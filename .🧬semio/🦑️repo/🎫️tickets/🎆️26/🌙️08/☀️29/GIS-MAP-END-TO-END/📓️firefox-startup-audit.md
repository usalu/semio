# Firefox Startup Audit

The observed Firefox run reaches the shell at 53.4 s after GIS Wasm transfer finishes at 8.8 s; the Chrome run reaches it at 6.3 s after transfer finishes at 2.8 s. Firefox has fewer no-event crossings (2,433 versus 4,122), so crossing count alone does not establish the cause. Concurrent compilers and a single machine limit the comparison.

The shard worker's `📨️message-handler/🟦️.ts:103–153` polls once, then pumps silent `more-work` only while the original operation's remaining deadline and fuel permit. Its emitted `driveStopped` and `drivePolls` distinguish budget, pending input, carrier, and idle stops. The wall is the remaining original deadline after the first poll; each internal poll yields a MessageChannel macrotask for input delivery. An empty result is not proof of no progress: internal work may have advanced without publishing a carrier.

The host continuation scheduler `🧰️framework/🔨️modules/⏳️async/🪃️continuation/🟦️.ts` uses MessageChannel for immediate continuations and timers for positive deadlines. The command-ingress continuation loop `🔌️PluginRuntime/🚚️handle-turn-drive/🟦️.ts:375–400` treats `more-work` as immediately runnable for 15 seconds since the last observable carrier, then backs off 25–250 ms; other statuses wait 25 ms. That is an observable-output heuristic, not a measurement of actual internal progress, and its applicability to this startup must be established by tracing the actual path.

GIS reference birth invokes `default_document` (`✏️editor/🧭️play-app-editor/🦀️.rs:141–143`), which parses the bundled reuse DSL and adds derived child handles (`🚪️io/📝️text/📸️snapshot/🦀️.rs:201–210`). This identifies real initialization work, not its duration or the source of the browser difference.

Next bounded measurement: compare the existing continuation trace for the same startup in both browsers, partitioning time into first poll/worker execution, worker-to-host and host-to-next-request gaps, and requested timer waits; group by actor and `driveStopped`, `drivePolls`, status and carrier. Capture original remaining deadline/fuel after the first poll if the existing trace lacks them. A predominance of long inter-request gaps following the 15-second quiet threshold would support backoff; long guest intervals or budget stops instead point to work/capacity. No runtime change or browser run was made in this audit.
