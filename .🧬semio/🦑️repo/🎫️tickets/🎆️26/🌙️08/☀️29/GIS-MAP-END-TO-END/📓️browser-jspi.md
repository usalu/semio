# GIS Browser Promise Integration

All three pinned Playwright engines executed WebAssembly JavaScript Promise Integration (JSPI) by default on this macOS host. The installed Chrome channel already queued for the full GIS probe also passed. The capability test ran a core Wasm export that invokes a suspending async JavaScript import. The export remained deferred while the import waited and eventually returned 42, in both Window and dedicated Worker. These checks cover the JSPI prerequisite independently of WebGPU and GIS component publication.

The desktop profile user agents can report the Playwright profile's Chromium major even when the actual installed browser version differs. The pinned WebKit iPhone profile reported `maxTouchPoints = 0` in this lightweight capability probe, which did not synthesize a gesture. Apple announced JSPI in Safari 27 beta. ## What happens without JSPI

- The React plugin loader fetches the descriptor first, then initializes the activation registry. `getShardClient()` calls `assertShardJspiAvailable()` before workers are created. A missing API throws the typed bilingual `plugin.runtime.jspi-unavailable` fault. This occurs before actor activation and map rendering. The shell can surface the fault, but a GIS instance cannot boot in that browser. The description's unconditional Firefox-pref and headless-Chromium-flag advice is stale for the builds measured here. - The WGPU frame bridge requests pooled shard workers through the page's message-port handoff. The generated worker separately checks both JSPI methods before importing the component, posts a worker-wide trap, and throws on missing support. - There is no alternate execution path. The browser actor's WIT includes async host-side storage and blob operations, async checkpoint and restore, and async job calls including cancellation. Removing the gate, switching renderers, replacing the methods with shims, or omitting an async-mode option would leave the contract unsatisfied. ## Smallest contract-preserving alternative

For the tested current browser set, retain the capability gate and run GIS acceptance without changing its execution architecture. For engines where JSPI is missing, the existing typed capability refusal is the smallest correct behavior available today. To provide execution on those engines, reuse the real Wasmtime plugin host through an explicit actor transport with local storage authority where feasible. The host can execute the same async component WIT and the browser can retain the existing async lifecycle and turn boundaries. There is no existing browser transport selection for this fallback. It would need admission, ordering, progress, cancellation and ownership tests, and a server-only mode would change local-first and offline behavior. A fully in-browser alternative would require a separately validated continuation-capable compiler/runtime and the same WIT and actor lifecycle tests.
