# 💥️ `rust-lld` segfaults linking `s` for `wasm32-wasip2`

## What happens

```
error: linking with `wasm-component-ld` failed: exit status: 1
  Stack dump:
  4  rust-lld   lld::wasm::ElemSection::writeBody() + 80
  5  rust-lld   lld::wasm::SyntheticSection::finalizeContents() + 28
  7  rust-lld   lld::wasm::writeResult() + 160
  9  rust-lld   lld::wasm::link(...)
error: could not compile `semio-framework-os` (lib) due to 1 previous error
```

`rust-lld` crashes — a segfault, not a diagnostic — while writing the wasm **element section** (the
indirect-call function table) for `semio-framework-os`'s cdylib. 257 `.rcgu.o` objects in that link.
`rustc 1.99.0-nightly (c4af71034 2026-07-06)`.

## It is new, and it is not the link flag

This is a regression that landed **during** this session, in a ~2 hour window:

- **01:32–01:35** — the same crate linked fine. `semio_s_plugin_space.wasm` (64,238,894 bytes) was
  produced, transpiled by jco, and its `describe` export ran successfully under Node's JSPI engine.
  The materialized module in `🔌️plugin-modules/s/` is from that link and is still valid.
- **~03:30 onward** — every link of the same crate crashes.

I bisected the obvious suspect and was wrong, so it is worth writing down explicitly. The dev
pipeline builds plugins with `cargo rustc … -- -C link-arg=-zstack-size=8388608`
(`pluginCargoArgs`), which my own successful build did not pass, so the flag looked like the
trigger. It is not:

| command | result |
|---|---|
| `cargo rustc -p semio-s-plugin-space --target wasm32-wasip2 --profile dev -- -C link-arg=-zstack-size=8388608` | crash |
| `cargo rustc … --lib … -- -C link-arg=-zstack-size=8388608` | crash |
| `cargo build -p semio-s-plugin-space --lib --target wasm32-wasip2 --profile dev` (no link arg) | **crash** |

The third row is the control that kills the hypothesis: the identical invocation that succeeded at
01:34 now crashes with no link flag at all. So the trigger is the code that has landed since, not
anything about how the link is invoked.

## Why this matters

`ElemSection::writeBody` is where lld serializes the indirect function table. A crash there on a
crate that linked two hours earlier points at scale — the table crossing some limit as
`semio-framework-os` keeps growing — rather than at any single bad symbol. That makes it a shared
problem for everyone building a wasip2 plugin, not something local to `s`.

Two directions for whoever picks it up, in order of cheapness:

1. **Bisect the growth.** The window is narrow and the reproducer is one command, so
   `git log --date=iso` over `💻️os` between those timestamps should isolate it quickly.
2. **Split the crate or shrink the table.** If it really is a table-size limit, `semio-framework-os`
   accumulating every module behind one cdylib is the structural cause; fewer indirect-call targets
   (or a newer lld) is the fix.

## What is unaffected

The already-materialized `s` component is good and does not need this link to succeed:
`🔌️plugin-modules/s/` holds the current WIT world (`reactor`/`jobs`/`checkpoint`/`describe`, not the
retired `contributor`/`plugin`), a fresh 64 MB core wasm, and a descriptor generated by actually
executing the component. Only a *rebuild* is blocked.
