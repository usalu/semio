# MCP Client Discovery and Component Models

The existing client journey resolved context before discovery, which left early MCP discovery untested. The journey now sends the first tools, resources, and prompts list requests immediately after `notifications/initialized`. It requires the native tool census, the workspace resource, and the workspace exploration prompt before calling a tool. The journey also reads the client environment from the repository's MCP configuration.

The old guest resolver and journey preflight expected each component under its crate's `dist/components` directory. The preflight also expected a Wasm hash in the committed semantic descriptor. The current producer attaches the Wasm hash to a receipt and publishes a four-file component model in the products cache. The launcher now retains the available selected-mode models through the repository artifact group reader and verifies each receipt, descriptor pair, and component. The Rust gateway binds the launcher’s bounded manifest to the catalog plugin and crate, then loads both component and activation descriptor from the retained model. The end-to-end task builds only its two pinned models before opening its protocol phase. Automatic consent applies to the journey’s explicit test process.

Native discovery identified five authored semantic descriptors with missing tool-run `receiving` fields (dag, reasoning, remodel, trinity, and WFC) and an authored norm descriptor with the former `vec3` type. Folder discovery, native catalog compilation, and export metadata now use the same retained descriptor as guest activation whenever the launcher has published a model for that owner. The installed norm model uses the current type. Unbuilt plugins continue to use authored declarations for discovery and produce diagnostics when those declarations are stale.

## Native Test Inputs

Direct native folder tests that open a plugin component need the `SEMIO_PLUGIN_CATALOG` and retained `SEMIO_MCP_COMPONENT_MODELS` environment emitted by the MCP launcher. The manifest is selected in the launcher and held for the run by the artifact reader. Bare discovery and probe artifacts can run without a guest model. The ticket’s `build-mcp-journey-models.ts` runs the bounded two-model producer and can inspect the retained environment with `--inspect`.

The native fallback writes build outputs to this ticket's generated directory through `mcp-native-guest-build.ts`. The `mcp-native-journey.ts` driver uses the actual descriptor emitter to verify the two compiled guests, then runs the same OS protocol journey directly over native stdio and the Repo journey through its configured server. Native fallback model files stay inside the ticket's temporary workspace.

The protocol gate allows six minutes for both cold guest activations and the rest of the journey, with the existing control's progress, cancellation and per-call budgets. For repeated native checks, use `--emit-only=note` or `--emit-only=wfc` with `--verified-models=<ticket scratch path>` to stage each independently, then pass the same verified model path to the combined driver.

The separate `--probe-model=wfc` invocation uses the same pinned initial bitmap, schemas, admission limits and expected solver output as the full gate to isolate WFC behind a typed Note failure.

For a scoped diagnostic, append `--host-driver-policy=8000000` to the native journey. The driver copies its configured host policy into the temporary session directory and changes only `operation.maximumItems`. Ordinary journey runs keep the configured value.
