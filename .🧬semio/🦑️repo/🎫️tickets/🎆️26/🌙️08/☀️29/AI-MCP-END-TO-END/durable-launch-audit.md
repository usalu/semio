# Durable MCP Launch Audit

The configured `.mcp.json` invokes `repo dev mcp stdio os` with a catalog and its generation target. It supplies neither an executable override nor a component model manifest. The ordinary published launcher stages the gateway and catalog and then holds the exact admitted executable publication for the native process lifetime. An explicit `SEMIO_OS_MCP_BIN` bypasses the gateway producer, but is not configured and does not itself publish or retain the binary.

The launcher discovers component models only in the repository Products cache. `withMcpComponentEnvironmentV1` checks for the partition, takes the Products store and group reader, validates each retained model, and passes its bounded manifest to the child. Missing Products partition or models yields no manifest. The model location is `browser/<mode>/components/<first 24 hex characters of SHA-256(cratePath)>` within the actual Products store; a path alone is not a publication. The reader verifies the artifact ownership and inventory as well as the exact model roster, Wasm digest and length, descriptor pair, component receipt, and optional prepared actor binding.

The current publisher is `publishComponentModelV1`. It requires a live original compiler writer reservation, a declared exact linked component, its privately retained descriptor emission from the same publication scope, and source provenance. Its actual product publication uses repository scratch, destination custody, and `stageRepositoryArtifacts`. Ticket-local native fallback objects are not those live producer objects. Manually copying them or fabricating receipts and markers would not be the supported producer route. Likewise, the configured native executable is acquired through its exact admitted Cargo publication reader; an arbitrary copied fallback executable is not that publication.

No existing supported, low-space command to import these fallback files into managed gateway and model publications was established by this read-only audit. The genuine existing route is the owned admitted compiler producer and model publisher, which still requires working graph/compiler admission and a usable Products store. Avoid claiming configured readiness until that route succeeds and a clean configured discovery plus typed model operation runs after ticket generated cleanup. If that route remains infeasible under the current storage budget, the durable solution requires an explicitly designed and tested import/publication capability or a storage policy change; merely moving fallback bytes does not provide it.

## Exact entry points and limits

- Gateway: `repo run @semio-tech/framework-os-mcp-rs:build` selects the owned native build; the configured launcher itself invokes the same producer before opening its publication reader.
- Note: `repo "🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🏗️build/🧩️driver-stages/📜️script.ts" component --manifest "🌎️hub/🧩️compositions/🗒️note/🧩️component/📦️packages/🦀️rust/Cargo.toml"`.
- WFC: the same command with `🌎️hub/🧩️compositions/🀄️wfc/🧩️component/📦️packages/🦀️rust/Cargo.toml` as manifest. This authored driver chooses the browser facet, which includes the model and browser materialization; no standalone model-only command was identified. These are source-inspected routes, not successful runs in this audit.
- Catalog: `repo run @semio-tech/s-dev-composition:generate` is the configured owning target.

Products policy sets `.cache/b/p` to 25,769,803,776 bytes (24 GiB) minimum and nominal capacity, with an elastic maximum of 40 GiB. This is a configured partition capacity, not a measured size for the two models or a proof of actual sparse physical use. Their precise managed peak footprint was not established; browser materialization and temporary publication may need more than the final model bytes. No space allocation was attempted.

The supported executable override port is `SEMIO_OS_MCP_BIN`; it makes the ordinary launcher skip the gateway producer but still stages the catalog target. The launcher deliberately deletes any caller-provided `SEMIO_MCP_COMPONENT_MODELS` and builds its own from retained Products publications. Direct native test invocation can instead supply `SEMIO_PLUGIN_CATALOG` and a `SEMIO_MCP_COMPONENT_MODELS` manifest to the binary, as the ticket SDK tests already do; this bypasses the managed launcher reader and is a temporary explicit test route, not evidence that the configured launch remains usable after generated cleanup.
