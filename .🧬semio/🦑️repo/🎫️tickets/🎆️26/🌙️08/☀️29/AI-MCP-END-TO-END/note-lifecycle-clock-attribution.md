# Note lifecycle clock attribution

The kernel enforces a strict 5,000,000 μs lifecycle turn ceiling before it commits the lifecycle receipt. The timer starts immediately before the reactor future's actual `Future::poll` and accumulates time when that guest-language poll returns. The final verdict includes earlier polls plus the active poll up to `publish_turn_result`. It excludes guest-language Pending gaps and the later captured-output JSON serialization, caller decoding, and publication. It includes all native interpreter scheduling and host-import reply time that elapses while the guest-language poll is still on the stack.

The Rust WASI `Instant` used by that timer asks `wasi:clocks/monotonic-clock@0.2.0::now`. The authenticated Source's deadline and cancellation machinery has a separate bound `operation-clock-us` import. In the production native interpreter both import handlers currently sample the host Source's advancing `StepContext::now_us()`. The VM can suspend one Core invocation at a pending import, finite execution grant, or finite retained grant without returning from the inner guest Future. An import reply advances in later funded callbacks. Those interpreter handbacks and intervening host work therefore fall inside the guest's current elapsed samples.

The experiment used the genuine Note component `22d2393505844cd972e914a40d1efe0adad7bd98545b086d41800b05ca0b7a38`, real Bun WebAssembly, the same lifecycle request and owned Core exports, and real, unscaled monotonic and Source clocks. The baseline captured request sequence 1 on lifecycle turn 2 and completed the exact acknowledgment on turn 3. The capture was produced in Core Poll invocation 825, which made 35 actual WASI monotonic reads.

- After taking monotonic sample 4 during invocation 825, the JIT host waited 5.100 s before replying with the observed time. The following sample advanced by roughly 5.104 s. The actor returned the authentic failed `SAC3` header at epoch 978. Paid Publish, Read, Borrow, page acknowledgment and terminal acknowledgment exposed one 395-byte `plugin.reactor-turn-deadline` cause. Closing early remained blocked. After terminal acknowledgment and real retirement, the same instance completed capture and its exact acknowledgment.
- After the same Core invocation finished and before the caller consumed its receipt, the host waited the same 5.100 s. The guest captured sequence 1 and consumed its exact acknowledgment without a failure. This control completed in about 6.156 s including the pause.

This proves the attribution behavior. The existing native SDK logs show total operation wall and the actual VM execution-fuel count, which by themselves cannot identify how much of a particular focused turn was guest execution versus VM suspension. No wall limit or Source grant changed for the experiment.

The native caller now accumulates real elapsed time across productive interpreter advancement slices of one authenticated owned Poll invocation. Interpreter handbacks, host reply handling, and caller reconciliation sit outside those slices. Elapsed wall time during an active interpreter slice includes any OS preemption of that running thread. The guest samples a separate `actor-execution-clock-us` import at the same lifecycle Future and publication boundaries. Only the actual pending call from the original module, unaliased Poll export, and original bound Source can obtain that reading. The operation Source keeps its real advancing wall, cancellation, and lifetime authority. The general WASI monotonic import retains its prior clock. Ordinary component reactor paths keep their original Future timing, and component-only providers have no owned interpreter clock to lend.
