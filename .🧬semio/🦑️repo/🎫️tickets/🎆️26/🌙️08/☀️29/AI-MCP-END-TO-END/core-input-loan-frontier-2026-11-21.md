# Fixed Core Input execution loan

The latest optimized Note SDK probe still holds the first `semio_owned_admit_actor_input_v1` crossing, epoch 53,485, until ordinary host copy stock can no longer fund the acknowledgment frame. No fixed Input receipt appeared before retirement. The native ActorInput receiver completes the existing 480-byte Note fixture when funded with its 256-item, 1 MiB native construction grant and ample guest work. This verifies that input under that grant and fixture. It does not establish an atomic bound for every supported Poll ActorInput or show that a smaller grant reduces the cumulative physical work of the live VM.

## Authority and receipt boundaries

- The wake issuer constructs `RetainedTurnInput` from `header_grant` and `header_fuel` across the available semantic and infrastructure stock. The descriptor carries a separate purpose grant and work window. The guest initializes its JSON/decoder limits from `budget.input.grant` and runs under `budget.step_budget()`. This separation could express a narrower execution grant while preserving the wire limits.
- The issuer checks the first fixed-response reserve against both scopes before issuing the epoch, including the 144-byte Input header. The Poll input runtime stores that exact budget, journals the equality-matched receipt and acknowledges the same retained wire. An alternate loan cannot be substituted mid-crossing to recover a denied quote.
- The ordinary Input call, canceled Input continuation, and CloseOutput can all use 144-byte headers. The header length alone cannot select which execution window applies. Poll tracks the actual frontier separately and a production change must use that identity.

## Why the drive cap is unsafe as a general input contract

`GuestRelayOperationCaps::bind_request` validates operation stock and the cleanup, transit, and infrastructure reserves. It gives no minimum guarantee relating the host drive cap to the guest native decoder. The native bounded ActorInput test reaches the receiver allocation, verifies that one byte below the exact capacity demand makes no allocation or receiver advancement, and then progresses when exact capacity is available. The recorded receiver allocation was 534,928 bytes, and the subsequent seed required 534,931 copy bytes. See [MCP end-to-end observations](mcp-end-to-end-2026-11-20.md). A driver may validly declare a 131,072-byte drive while its Infrastructure grant funds that seed. Permanently intersecting each Input loan with that drive would not make the pending quote eligible. The production example drive uses 4,096 items and 1 MiB copy, while the SDK fixture drive uses 4,096 items and 16 MiB. The product configuration supplies neither a general minimum nor a portable convention for the execution quantum. Broadly capping work is also unsupported. Nested native receiving can select the caller work ceiling and local operations retain their admitted quote for recovery.

Reducing the outer ActorInput loop alone would still permit the first decoder call to spend its whole loan. `OriginalJsonOutputReceiving::advance` loops over parser and receiver frontiers in one `receive_step`; its `Phase::Receive` calls another looping `NativeReceivingOriginal::advance`. A conservative cooperative yield would need propagation through both loops, at a settled original action boundary. It would need to admit the selected atomic operation at the existing exact quote, preserve any in-flight grant and original response, and yield only after measurable decoder movement. The existing fixture and SDK traces do not establish that the added wire handoffs would reduce cumulative VM copy work.

No production source was changed. The analysis used the live SDK log, existing native receiver and independent ActorInput oracle results recorded in this ticket, plus a source audit. No compilation or SDK run was started in this investigation.
