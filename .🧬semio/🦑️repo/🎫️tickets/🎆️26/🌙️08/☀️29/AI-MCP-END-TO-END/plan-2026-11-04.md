# Semio MCP End-to-End Plan

The requested server is the `semio` entry in `.mcp.json`, implemented by `semio-os-mcp`, not the repository MCP server.

## Acceptance

1. A clean native Windows, macOS, Linux or devcontainer launch can initialize promptly and reach the real native server through the canonical `repo dev mcp stdio os` entry.
2. The server discovers its installed plugin catalog and exposes artifact, capability/action, transaction/history, inference, UI/navigation and job surfaces with valid protocol schemas.
3. Artifact reads and mutations use the actual workspace and plugin host. Validation must report actual evidence. Missing bindings must produce explicit typed failures.
4. Attached shell actions target the requested plugin instance. Deferred plans cannot cross instance ownership or repeat after consumption.
5. Source lifecycle tests and real native protocol tests run through repository-owned targets, with neutral fixtures checked by independent third-party oracles.
6. Completion requires successful real-server verification; source inspection or a warming handshake alone is insufficient.

## Fleet

- Coordinator: main chat, requested GPT 6.1 Sol High coordination.
- Initial exploration: three GPT 6.1 Sol Low agents (the available equivalent of requested Light).
- Execution: three GPT 6.1 Sol Medium agents for launch/publication, native server, and frontend bridge respectively.

## Ownership

- Launch: TypeScript frontend, native artifact publication and staging, catalog arguments, source lifecycle targets.
- Native: Rust bootstrap, artifact validation and native fixture/test gaps.
- Bridge: frontend transaction ownership, target routing and route integration tests.
- Coordinator: repository ticket/MCP routing, real native build, combined acceptance and review.

## Infrastructure

The connected repository MCP resolves its workspace to the Codex install directory. Its goals/tickets resources were empty and its `ticket_reopen` could not locate this ticket. `repo-mcp.ts` starts the same MCP locally with the actual workspace as cwd; it successfully reopened the existing ticket and owns the native build request. The repository model registry lacks GPT 6.1 Sol, so ticket attribution uses `codex` and records the actual requested model in the prompt.

All production changes stay in the shared checkout. No modifying Git commands, worktrees, AGENTS.md changes, or external runtime dependencies are authorized by this plan.
