## Per-axis calculation

Let `O` be the host operation total, `P0` the host debit at loan issue, `P` the current host debit, `E` all previously settled guest debits and held escrow, `C` host cleanup, `T` host transit, and `I` guest infrastructure. The semantic budget `S0` starts at `min(request, O − C − T − I, u32::MAX − I)`. With `E_sem` the semantic part of `E`, the active semantic loan holds `H = min(O − P0 − E − C − T, S0 − E_sem)`. Its header advertises both remaining guest purposes, but the host holds only the selected purpose's retained policy. The next ordinary driver grant is `min(drive, O − P − E − H − C)`. Each actual callback also intersects this grant with its live Source authority.

With the checked-in copy policy, `O = 3,000,000,000`, `C = T = I = 16,777,216`, and `S0 = 2,949,668,352`. At a Poll issue after at least 1,057,979,737 bytes of host copy, the physical term binds if semantic spend starts at zero and guest infrastructure usage fits its own scope. Even with `E = 0` the hold is at most 1,908,465,831 bytes, leaving exactly 16,777,216 ordinary copy bytes beside the hold and cleanup. The interpretation is consistent with a loan issued at roughly 1,070,940,974 bytes followed by depletion of the now-spendable transit stock. That issue amount is inferred by subtracting 16 MiB from the plateau. It was never logged. The retained run does not identify its policy arguments, exact issue debit, outstanding loan, escrow, or the acknowledgment callback's visible grant. If this had instead been a 12-billion-copy-byte run with 16 MiB cleanup, the guest's total copy authorization would still be at most `u32::MAX`, leaving at least 6,600,537,299 host copy bytes before the drive cap at the measured plateau. That would point to a different narrowing or budget axis.

## Acknowledgment and continued progress

The transit carve-out constrains loan issue. While the loan is held, ordinary host checkout may still spend transit on VM and Poll work. A scalar receipt acknowledgment needs one item, `control_bytes()` copy bytes, positive depth and one work unit in its real callback. Early refusal when this grant is too small bounds the failure time, but supplies no acknowledgment authority.

The smallest funding change at this boundary is to preserve that exact control quote from the existing finite host currency before a receipt-producing VM slice, and consume it only when acknowledging the actual held receipt. Retain the quote across callback handback, and return any unused amount when execution produces no matching receipt. Release the reservation after acknowledgment, before sizing the next receipt-producing slice. Reserve on every such slice and include every axis charged by the acknowledgment. This lets the current receipt clear even if the VM uses all the ordinary grant. It still needs ordinary currency for the next VM slice and for the frozen receipt path, which captures and validates the guest snapshot under the old hold before settling it. If the available host share is exhausted, another acknowledgment reserve alone cannot complete Note. The loan issuer must leave enough independently sized host execution and settlement currency beside the guest hold, or the work must become cheaper. Any such allocation must keep the same finite total and cleanup reserve.

Source owners are `admitted_bound_request`, `physical_policy`, and `scope_budget` in the Wake operation policy, `GuestLedger::usage` and `admit_guest_subloan_inner` in its guest ledger, and `acknowledge_scalar_progress_step` and `drive_inner` in Poll. No runtime policy was changed for this audit.
