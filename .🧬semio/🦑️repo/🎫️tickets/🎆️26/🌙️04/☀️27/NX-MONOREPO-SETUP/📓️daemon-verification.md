The running Nx 21.6.11 daemon retained the old in-process graph plugin after its authored source changed; a newly inferred component target was absent from the real graph although direct plugin tests passed. The regression passed both source and policy changes without stopping the fixture daemon, followed by Unicode watch rebuilding and cancellation of a stubborn callback. One daemon-only reset activated the updated callback wrapper in the previously running real daemon; it preserved Nx task results. A pending repo:test had passed its assertions but ended with EPIPE during that reset and is rerun separately.

## Shared Workspace State

A second live-workspace issue involved clients using different NX_WORKSPACE_DATA_DIRECTORY values with the same workspace-derived daemon socket. Nx records task details in the client database and task histories through the daemon; differing databases produced a foreign-key failure after an otherwise successful generator, and caller-specific directories also lost warm cache reuse. Root Nx execution now always uses the workspace .nx/workspace-data directory and a stable short OS-temporary socket path derived from that same directory. No task/agent/timestamp namespace is created. The isolated regression deliberately changed the caller data directory: it failed with unnecessary rebuilds before the change, then passed warm cache reuse after the change, along with live source/policy reload and watch cancellation. The previously active default socket was left alone so existing commands can finish.

## Nx Daemon Diagnostic Retention Gap

The active Nx 23.2.0 daemon log measured 9,155,932,348 bytes at 2026-09-08 08:36 UTC. Inspection of installed Nx daemon/client/daemon-environment.js shows overridable defaults NX_VERBOSE_LOGGING=true, NX_PERF_LOGGING=true and NX_NATIVE_LOGGING=nx=debug. The logger writes directly to an append-only daemon.log without a size bound. Workspace Nx launcher currently provides no overrides for these variables. This is separate from the task-result cache budget. Configure quiet defaults at all launcher/bootstrap surfaces and add bounded owned diagnostic retention; do not restart shared active tasks just to change logging. A mistakenly broad local diagnostic read was terminated without touching the daemon; subsequent inspection reads only an 8 KB file tail.

Quiet defaults now apply through devToolingEnv (all Nx launcher children), the native Windows/macOS/Linux editor terminal environments, and the devcontainer process environment. Explicit debug overrides remain supported. The language-neutral defaults probe failed before implementation and passes afterward; the updated repo:test compares the defaults with the installed Nx daemon environment constructor. The running shared daemon was not restarted, so this alone does not shrink its existing log or change its already-initialized native logger. Bounded diagnostic retention remains required.

The installed-Nx oracle disproved the initial environment-only solution: getDaemonEnv discarded all three overrides because they were in its exclusion list. A Bun-managed nx@23.2.0 patch now sets quiet defaults and admits only its declared overridable logging keys when constructing the daemon environment; the client graph-environment hash still excludes logging. The patch is recorded in package.json/bun.lock and applies through normal installs, using [Bun’s documented patch workflow](https://bun.sh/docs/pm/cli/patch). A fresh isolated installation and frozen-lockfile verification are running. The active pre-patch daemon still owns its existing logger and needs later bounded retention.

Fresh isolated Bun install and frozen-lockfile install both passed with the persisted patch. An independent Node process loaded the newly installed Nx package, verified quiet defaults, verified an explicit nx=debug override, and confirmed logging changes do not alter hashDaemonClientEnv. The complete repo:test contract suite also passed afterward in 54.6s (native-editor-patched-contracts.log).

Nx’s daemonProcessException also read the entire daemon.log before selecting its last twenty lines. The language-neutral tail probe reproduced that whole-file read against a 128 KiB fixture. The dependency patch now reads at most 64 KiB through a closed file descriptor and preserves the trailing error lines and internalDaemonError classification; the corrected Node-runtime probe passed. This bounds error-reporting memory, not retained disk usage.

A later process inspection observed Nx replacing the old daemon naturally (PID 31807, socket 4f87efdc176625a7a3c3); no task process was intentionally stopped for the patch. The existing append-only log remained 9,170,945,834 bytes at 09:03 UTC, so retention remains open despite quieter defaults.

## Retention implementation boundary, 2026-09-08

Read the installed Nx 23.2.0 `dist/src/daemon/logger.js` and `daemon/client/client.js`. The server logger writes to stdout, which is opened on `daemon.log` with append semantics when the daemon starts; clients call `appendFileSync` on the same pathname. Therefore renaming the log alone would leave the server writing its original inode. A bounded implementation must account for the live stdout/stderr descriptors as well as client appends; changing only the existing error-message tail reader cannot bound retention. No retention patch or live log deletion was performed during the active Print collection build.

The PDF target currently hashes the complete Bun lockfile to cover its three external rendering dependencies. This is correct but conservative: an unrelated lockfile change can invalidate these PDFs. Narrowing external dependency hashes needs an installed-package/lock closure contract or a populated Nx external dependency graph; the workspace currently disables @nx/js lockfile analysis. Do not remove the lockfile input without replacing that dependency identity coverage.

A three-second native sample of the active shared daemon at 11:22 UTC found its main thread predominantly waiting in `kevent` (404/420 samples). The graph-only custom worker exited before it could be sampled. The queued Report/editor/repository invocations then reported Python dependency graph construction. This brief sample does not establish the cause of the wider graph latency; it does disprove treating the earlier single process CPU reading as proof of continuous JavaScript computation. The daemon and other contributors' tasks were left running.

## Bounded daemon log candidate — 2026-09-08

The new language-neutral retention probe first failed because the installed logger left a sparse 16 MiB diagnostic file unbounded after an ordinary client log write. A Bun-managed Nx logger patch now limits retained diagnostics to an 8 MiB threshold and keeps at most the trailing 64 KiB when pruning. It truncates the existing regular file in place so the daemon's already-open append descriptors continue targeting the same inode. Server/client logger writes invoke the check; a daemon-only 30-second timer also covers direct native stdout/stderr writes. This is best-effort diagnostic retention with burst headroom, not an atomic audit journal: concurrently written diagnostic bytes during truncation are not guaranteed to survive.

The independent Node filesystem probe passed three over-budget cycles, exact recent-tail preservation, a bounded read, stable inode identity and continued writes through the original append descriptor. It also preserved missing paths, directories, hard-linked files and symlinked files/parents. No source/cache directory is removed by the routine, and no rotated log namespace is created.

A fresh isolated Bun installation and its frozen-lockfile repeat both passed, followed by the installed logger retention test and the earlier environment/tail tests. The workspace's existing `workspace:deps-javascript` Nx target is now applying the same persisted patch through normal frozen dependency synchronization. The active shared daemon has not been restarted, and the large live log has not yet been pruned in this checkpoint.

The real timer probe also passed: an ordinary native append descriptor grew the fixture log without a logger call, and the 30-second daemon timer bounded it while preserving continued writes through that descriptor. The workspace Nx dependency target applied the frozen install successfully in 2.10s of Bun work (2.9s producer critical path). New logger activity then reduced the real daemon log from about 9.197 GB to 104,971 bytes. The shared daemon was later observed under PID 4126 after its normal lifecycle; no manual reset/kill was used.

The dependency replacement overlapped with the Report cache probe's finalization and produced a transient `MODULE_NOT_FOUND` for Nx's `plugins/js/utils/register`. That file exists after installation. All three report directories had already restored byte-for-byte, but the failed exit invalidates that run as a complete qualification. The probe retains the interrupted logs, verifies/removes only its redundant backup copies, and is rerunning after installation. Dependency synchronization must be serialized against active Nx consumers in the eventual execution-resource model; this overlap is now measured evidence for that remaining work.
