# Preparation Traversal Scaling Source Diagnosis

The active process's reported high CPU and unsymbolicated sample do not identify an executing function. This read-only source analysis identifies concrete work patterns; it does not attribute the actual 15-minute delay to a measured hotspot. No profiling, tests, producer operations or source edits were performed.

Current `prepareCargoOwners` does **not** refresh the whole graph for every recipe-free manifest. Its missing-recipe and already-executed-recipe branches return before refresh. Whole physical owner discovery and document/member cache invalidation occur after each actually executed recipe and on every final fresh closure sweep. Each discovery recursively enumerates admitted owner pattern prefixes and parses owner manifests; each invalidated member inventory recursively expands member patterns and parses package ownership. That gives repeated tree/member work proportional to recipe mutation epochs, rather than manifest count alone.

Within each epoch, `binding` linearly searches the scope list and its owner member array for every dependency/manifest. Shared-owner graphs can therefore incur approximately O(E×M) membership lookup work, plus O(E×S) owner search, where E is visited dependency accesses, M owner member count and S scope count. Final closure and current recipe coverage repeat those binding accesses. These are concrete avoidable linear lookups; the current Map caches only the inventory array, not manifest→member bindings.

Program capture independently captures both selected producer and resolver script eager import closures for each recipe. For each source it walks all ancestor directories and rereads/hash-checks package.json/tsconfig/bunfig even when the configuration Map already contains those paths. Shared ancestors are repeatedly read. Each observed recipe also runs several fresh resolution-currentness subprocesses during capture/merge, final preparation validation and pair boundaries, with physical ancestor checks and input/source hashing. These operations preserve important freshness, but deduplication of shared identities within a single boundary/epoch could reduce repeated I/O and process work without reusing historical custody. Current pair member-roster capture and each boundary check also independently rediscover owner/member inventories.

Canonical candidate: schema-first transaction-owned graph epochs with indexed scope/member/manifest identities, one current physical discovery per required mutation/admission boundary, and per-boundary deduplicated source/configuration/resolution observations. An executed recipe invalidates relevant graph observations; the child-mutates-ancestor dependency pre-parent sweep must observe the resulting fresh graph before parent consumption. Final current recipe-key coverage and member admission must use a fresh whole closure. Shared program sources/configuration may be scanned/hash-bound once per current boundary only when the exact bytes/resolution remain independently current; no persisted receipt reuse or skip flag.
