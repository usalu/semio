# Outer Native Preparation Owner Boundary Diagnosis

Actual Native trace reports owner-command10810 → preparation Cargo.toml10812 before the normal dependency synchronization. Current defining source confirms this is NativeScript eager preparation, not merely a generic process wrapper: every owner-command synthesizes a Cargo `test --manifest-path` invocation and prepares it before launching its declared executable. Explicit test manifests likewise prepare before policy creation.

The inner dependency operation independently owns `withPreparedCargoDependencyPairV1`: acquires an exclusive preparation lease, runs selected preparation with observations once, publishes membership, captures manifests/member roster/source/import/input/output custody, runs unchanged update, rechecks, runs unchanged locked fetch, rechecks outputs and update-produced lock, then releases. Outer eager preparation has its own completed lease and no observation directory passed into this inner transaction. The outer result is not reused as inner authority.

For the adjacent update/fetch custody, the duplicate is extra work and lease acquisition; it does not weaken or replace the inner fresh observation/currentness boundary. Outer writes become inputs to the later preparation and the inner producer observations must remain current through update/fetch. This source-based conclusion supplies no successful current producer terminal. Outer preparation cannot establish freshness for arbitrary later command consumption after its lease is released, so it is also the wrong generic authority to reuse as a skip receipt.

Canonical design candidate: generic owned command execution owns process context, progress, cancellation and exact declared command, while explicit Cargo-consuming operations own the selected preparation and lifetime of its evidence. Schema-first owner requests should distinguish actual domain consumption from orchestration without relying on target-name strings. Dependency synchronization owns its adjacent transaction; other Cargo consumers obtain their preparation at their actual admitted operation boundary. A command merely orchestrating that transaction should not manufacture a test consumption. Existing genuine test-policy construction must retain its required current manifest/domain precondition when moved to that consuming boundary. No public skip flag, guessed target waiver or persisted receipt reuse is appropriate.

Candidate language-neutral TDD law should run the real outer declared owner-command → dependency pair route and count exact preparation recipe executions, unlike the existing pair-only law. Expect one execution for the complete orchestration, update then fetch unchanged, an independently parsed lock/metadata oracle, and no callbacks after source/input/new-resolution/member/recipe mutation. Separate actual direct Cargo and test-policy consumers must still prepare before consumption; cancellation during queued admission must prevent launch. The current outer route would be meaningful RED on the whole-route count. No such test or fix was run here, and no source/target/profile/sample/producer was changed. Current active operation was not disturbed.
