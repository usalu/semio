# Compiler Cold-Write Concurrency: Read-Only Design

This is a Source audit and proposed protocol, not an implementation or runtime qualification. No compiler/capacity/lease/image policy was changed or opened for this report. The16GiB Rust filesystem remains the hard enclosing physical bound. Current4GiB admission is required initial free headroom, not an enforced per-mode quota or measured per-unit peak.

## Why Replacing EX With SH Alone Is Incorrect

Two new children could both observe the same4GiB statfs sample and then spend it concurrently. Existing Native allocation ledger accounts authored logical charges; it does not constrain how many physical bytes a raw rustc child writes beneath its funded directory. A final rlib cap, source-size cap or observed prior peak does not bound LLVM/object/temp/link/dep-info/provenance and publication overlap. Monitoring or cancelling after crossing a limit can reduce damage but is not a hard per-unit physical write ceiling. The16GiB filesystem still enforces its hard cap and can legitimately produce ENOSPC; publication must refuse and accepted work must settle before cleanup.

Consequently a smaller concurrent quote needs either (1) a producer whose complete maximum write closure is actually constrained and computed before effects, or (2) a real per-operation enforcing backing/quota. The current direct-rustc implementation has neither proof yet. A pure numeric request or renamed artifact limit cannot supply it. No smaller bound is recommended solely from final receipt size.

## Proposed Narrow Protocol

1. Keep the **same exact global resource identity** as an exclusion gate. Old/current EX compiler and maintenance owners must continue conflicting with every new admitted writer. A future bounded writer retains genuine SH on this gate through its child, capture, publication/failed-output handling and complete accepted drainage. Maintenance retains EX; no EX acquisition while the same operation holds its own SH.
2. Add a separate canonical admission/commit ledger with its own short EX transaction. It records actual issued live write reservations, complete operation kind/identity/owned paths and schema-derived peak bytes. No receipt/path/marker reconstructs authority. Runtime handles bind real reservation/control/root/gate custody; escaped/foreign/copy tokens refuse. Every accepted promise is enrolled before effects and drained under its retained gate.
3. Under admission EX, recheck the actual image and statfs, then conservatively require `F >= R + W + S`: actual current free bytes F, sum of **full still-outstanding** accepted peak reservations R, new complete peak W, and authored shared/cleanup reserve S. Subtracting full reservations remains conservative when part of their writes is already reflected in F; do not subtract those consumed bytes a second time from R unless an authenticated owned measurement/commit protocol establishes the reduction. Safe underutilization is preferable to invented reclaimed headroom. Never count persistent mode charges as independent available capacity.
4. Commit reservation before first output/tmp write; keep it until child terminal, independent receipt/content verification, publication or failed-output cleanup and final rooted recensus. On success, the persistent bytes are now reflected by statfs; remove only the matching operation reservation under admission EX. On failed cleanup, keep an explicit charged unresolved owned state; do not announce capacity as released merely because the callback rejected. Crash reconciliation requires exact enforcing custody and authenticated owned files; PID absence is not permission. Unknown entries remain charged/refused.
5. If admission lacks capacity, release operation/gate SH and any own output/Cargo reader before requesting real maintenance EX. Maintenance uses only current compact or fully authenticated historical protocols, with actual Cargo/physical/descriptor/recensus guards. Return to admission with the same actual Original/deadline and a finite authored retry; revalidate every Source/dependency/output fact after the gap. Never upgrade SH in place or clear a failed accepted-operation ledger. Normal capacity refusal, if recoverable, needs private DATA before effects through every tracked boundary.
6. Lock order for a new bounded lane should be root gate → short admission transaction → deterministic output/dependency leases → effect; no waiting maintenance request after per-unit output EX. Current unit script obtains output EX before writer admission. A clean implementation must explicitly release/reacquire/revalidate its miss path or retain maintenance’s nonblocking per-output behavior; wrapping the new lane around the current opposite order can deadlock. Existing Nx output-held writer admission is nonblocking and must remain so until all exact callers share one proven order. No parent store/child handoff may hold a gate the child needs to acquire anew.

SH on the global gate permits independent bounded writers; their separate CPU grants remain one worker each for the current direct rlib adapter. The admission ledger is an overcommit protocol, not by itself an output-size enforcement mechanism. A complete producer-bound proof is required before enabling the small-W direct-rustc lane. Unbounded Cargo/fetch/build-script shapes should remain genuine EX until their complete write closure is constrained, rather than receiving guessed per-unit quotes.

## Useful Initial Separation

The strongest immediately measurable growth candidate is copy/publication/restore of already authenticated immutable inventories: source extents, file/entry allocation rounding, bounded metadata/terminal output, staging/previous-output overlap and failed cleanup can be enumerated. This can qualify the bounded reservation machinery without pretending rustc has the same closure. Preserve incoming cache verification, exact stable-output SH/EX and Native FK metadata contracts; an actual restore is a writer.

For direct rlib concurrency, first collect bounded actual peak data for scratch+temporary+receipt+publication copies, while designing an enforcing child boundary. A nested fixed-size workspace or actual supported OS quota would provide a hard per-unit ceiling but is an additional cross-platform image/lifecycle design and is **not** authorized or implemented here. Without such enforcement, a documented conservative empirical reservation may reduce overcommit risk but must not be claimed as a mathematical or hard runtime growth bound. The current serial policy remains truthful while that decision is made.

## Required TDD Before Any Lock Change

- Language-neutral reservation/event corpus with independent SQLite transaction oracle: simultaneous admits cannot double-spend; invalid/overflow/foreign tokens refuse; commit and failed cleanup remain charged; initial minimum and fixed16GiB envelope stay distinct.
- Real small privately funded image, two distinct accepted writer children and independent Python SQLite gate observations: both bounded writers overlap, EX maintenance and authenticated old opener cannot enter until both settle; later old opener conflicts with their actual SH gate.
- Exact pre-effect refusal under insufficient capacity, cancellation while queued, Error and undefined primary, ignored/detached child, late birth, partial output and real ENOSPC publication refusal. Parent retains healthy prefunded cleanup; no fresh Root or deadline extension.
- Output/staging peak oracle including two copies and prior stable output, Native restore growth, actual failed put/no artifact promotion, Source/dependency mutation during release/reacquire.
- No maintenance self-wait: writer pressure releases own SH/output custody before EX; actual parent/child compile adapters and legitimate unrelated reader/hit remain concurrent. Unknown old material and old enforcing-image guard requirements remain unchanged.

This checkpoint does not establish universal Rust writer enrollment, actual concurrent build speed, measured cold growth, per-unit quota enforcement, or new runtime behavior. No locks, caps, Source compiler adapters or physical cache state were modified.
