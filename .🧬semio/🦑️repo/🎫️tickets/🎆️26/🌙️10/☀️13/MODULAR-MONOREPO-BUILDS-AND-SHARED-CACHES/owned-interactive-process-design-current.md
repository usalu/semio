# Owned Interactive Child Process Design

The actual MCP client currently constructs raw ChildProcess instances, keeps unbounded notification/diagnostic arrays, grants a new request timer, and stops without joining. Six constructions in four actual consumer files require migration. Host or artifact scope alone does not qualify their process lifetime. The user explicitly authorizes build/API/tool architecture changes; global Native/publication HOLD stays in force.

Extend the existing Core owned capture's single private spawn/terminal/progress/cancellation owner. The new callback receives only an opaque privately registered channel, never ChildProcess, stdin, raw descriptor or a provider constructor. Public receive/write/close functions authenticate that exact private live scope; close can only drain/terminate its already accepted actual child and never create a new control. The existing separated capture remains on that same physical owner. Finite actual incoming control, inherited projected wire, closed finite input/output and pending-operation bounds apply before effects. Input reuses the actual immutable text/Base64 contract. Accepted writes/reads enroll before effects; first failure closes births, exact Error/undefined survives, all accepted work and actual terminal are joined before scope retirement. Closing resolves pending reads and drains accepted writes before normal termination; cancellation/error can immediately terminate the actual tree while joining all pending completions.

Schema-first neutral Source laws will exercise genuine Bun/Node subprocesses and independent Ajv/SQLite/CrossSpawn oracles. Any accepted-failure case is an isolated actual received Original; a healthy parent collects only terminal DATA. No Native factory, accepted fake provider, source-copy-as-artifact or physical build is used. After this transport is qualified, migrate the protocol owner to bounded first-party request correlation, notifications and carried-control timers and wrap all six actual callers in the scope. Credential fd3 and giant workspace wrappers remain separate actual-owner migrations until composed through the same mechanism. No default activation or complete MCP/Hub runtime claim before their actual genuine proofs.
