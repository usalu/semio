## Platform Source and Limits

Framework native-build/storage/fixed has the closed platform envelope, neutral mount/footer corpus and bounded original file/receipt observation. Linux image uses preallocated fallocate bytes, ext4 with nodiscard, actual effective CAP_SYS_ADMIN, actual writable whole loop mount parsed from /proc/self/mountinfo, and /sys/dev/block loop backing/offset/sizelimit validation. It refuses ordinary directories, tmpfs, subtree binds, nested mounts and missing mount capability. Windows image uses system PowerShell, an actual elevated token, available Hyper-V/Storage cmdlets, fixed VHD rather than dynamic VHD, footer checksum/type/length, and the actual attached image→disk→partition→NTFS access path. Preparation targets only a freshly owned RAW VHD, never an existing host disk.

The available Docker CLI could not reach a daemon: /Users/ueli/.docker/run/docker.sock does not exist. No Linux native mount, ENOSPC, cancellation or crash behavior was qualified here. No Windows host was available. Windows directory-fsync journal durability and fresh/preparation-failure physical cleanup still need actual qualification. Neither provider is claimed production-ready or silently used as a qualified default. No sudo, UAC bypass, foreign disk mutation, force detach, reset or process kill was performed.

[Kernel tmpfs documentation](https://www.kernel.org/doc/Documentation/filesystems/tmpfs.txt) describes filesystem allocation size limits and remount changes; tmpfs is intentionally excluded here because the current requirement includes retained fixed disk backing. [Microsoft New-VHD](https://learn.microsoft.com/en-us/powershell/module/hyper-v/new-vhd?view=windowsserver2025-ps) supplies the explicit fixed format. [Microsoft Get-DiskImage](https://learn.microsoft.com/en-us/powershell/module/storage/get-diskimage?view=windowsserver2025-ps) documents attached status and the disk/partition/volume pipeline used by the observer.
