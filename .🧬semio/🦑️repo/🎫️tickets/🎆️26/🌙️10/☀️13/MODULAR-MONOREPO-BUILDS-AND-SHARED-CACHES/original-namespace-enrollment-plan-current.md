## Bootstrap And Enrollment Transaction

The immutable bootstrap/control namespace stays separate from lease-image contents and is charged once within its existing finite control budget. Its exact image guard is already created and opens the physical leases image without recursively requesting that same image's namespace. This bootstrap exception has a closed fixed set of identities; arbitrary logical resources cannot opt into it.

Enrollment must happen at the actual root managed entry before that process retains nested tools/compiler/graph image readers or arbitrary resource bodies. It must use real enforcing image custody and the existing exact queue-catalog EX. A busy image or incompatible held reader is a typed refusal/defer before publication, never forced unmount, PID/age cleanup, cap increase or a new ordinary-directory fallback.

The proposed transaction stages all bounded files and populated identities while the current data namespace remains unchanged. It rechecks actual statfs, actual backing/mount identity, existing bootstrap guard, exact main-reserve inode, all catalog/PIN/GUARD caps, directory allocation and the complete peak. It flushes files and an explicit enrollment record. It then seals old data/claim *creation* and transitions the same existing main reserve to 128 KiB under its real catalog writer. New policy publication is committed only after validating the actual physical seal and extent state. Crash recovery must resume this same authenticated transaction and refuse ambiguous or foreign material. It must not truncate a file from its name or appearance, allocate duplicate reserves, reinterpret reserve bytes as a database, or delete old inodes.

A directory seal alone is insufficient to move an existing logical key onto a different guard. Existing old openers never enrolled in a new catalog or PIN. An old pre-opened descriptor can begin a transaction later; catalog EX, per-file SQLite EX, permissions or immutable-directory creation barriers do not by themselves revoke that descriptor. The actual old pending test demonstrates that an old uninitialized file can grow through its pre-opened handle before commit fails. Therefore the production transaction must not publish a new GUARD identity for a key still reachable through an old guard.

The clean required binding invariant is one authoritative namespace binding per logical resource, with immutable private capture of exact logical name, mode, namespace, physical guard path, device/inode and PIN/slot generation. Existing original guard identities retain their exact inode; no `old-path-if-present` compatibility fallback is acceptable. Before choosing a dynamic slot binding for an existing key, we need either a complete authenticated enrollment of its original guard into that authoritative binding set, or a real kernel/process-lifetime proof that every old opener is gone and cannot reopen. The latter cannot be inferred from a new catalog EX or from all current fleet handles being terminal. Non-forced physical unmount can detect open vnodes, but secure host mountpoint ingress during any unmounted interval is an additional unqualified prerequisite; this plan does not use forced detach or claim a safe cutover from that observation.

Parent review has selected the immutable baseline plus new-only pool. Every captured old logical key permanently retains its original guard inode. Captured unresolved target, queue, sidecar and claim hashes are reserved and refuse placement; an uninitialized preopened target is not remapped. The complete baseline is an authenticated immutable partition consulted before any new placement, rather than a live path-presence fallback. The independent same-inode prototype qualifies old preopen/reopen contention for initialized bindings. Complete census, bounded publication, persistent generation recovery and funding remain prerequisites to canonical publication; see `namespace-baseline-implementation-current.md`.

### Private Receiver And Control Rules

The canonical registry identifies actual invocation objects, not serialized envelopes. At a real receiving entry, the actual carried `process.env` envelope is admitted and one controller scope is created. An explicit authored root `withScriptProcessEnvelope` is also a real existing boundary; independently authored root scopes may coexist in one process. The staged global `received` boolean cannot be moved into production. Each root retains its own absolute deadline, signal handlers and private pending work.

A nested receiving helper must not convert a supplied environment object into a new controller. It uses the privately live active Original and verifies the carried policy/capabilities and nonextended deadline against that captured root. A different policy, changed capability view, expired scope or arbitrary copied invocation refuses. This does not authenticate a new environment outside a live root. Current helper-specific environment maps remain child launch inputs; they do not themselves issue root authority. The actual entrypoint still admits the real carried envelope before the first store open.

Synchronous controls are private derivations of that exact root, with command, start time, requested duration, inherited signal and optional actual additional signal captured immutably. Zero requests mean the remaining parent authority; they never turn a finite parent into an unbounded child. Requested controls retain their parent chain. Local preparation liveness checks must be composed inside the owned derivation rather than object-spreading a control. A structurally valid free phase control cannot pass this private lookup.

Accepted operation tracking is not satisfied by awaiting only an acquisition promise. For an acquired lease the private lifetime completes after its actual release/connection close; for an image it completes after provider close; for a captured child it completes after process settlement and callback consumption. Acquisition failures are observed on the exact public promise and remain parent failures even when a caller catches them. Returning a new async adopting promise without observing that exact return would reintroduce the already qualified detached-rejection bug. Root closes new admission before draining accepted work, then retires controls and removes handlers. Existing lease/image finally releases must remain usable during that drain and after business cancellation.

No global lease-data transaction is part of this Source integration. ## Global Placement And No Nested Wait Cycle

Sixteen catalogs with four rows each form one global search space, not sixteen independent capacity limits. Lookup uses deterministic full-namespace probing, verifies the full logical resource and the bound slot generation, and pins the selected exact identity. Catalog lookup holds a quick catalog SH and obtains the stable slot PIN SH; it releases catalog SH before waiting for the actual GUARD transaction. The actual A-held → A-waiter → new-B law proves why this order is necessary. Reassignment needs catalog EX, nonblocking PIN EX and GUARD EX, followed by exact binding/inode checks.

Catalog SHA-256 values are lookup hints rather than authority for equality. Full logical key equality must be checked without waiting on an EX-held GUARD while holding catalog SH. One concrete representation is a full bounded key in the independently readable PIN binding row, with its slot generation. That adds physical bytes beyond the earlier short-PIN census and must be measured before funding. The full 4,096-byte key cannot simply be copied four times into a 16 KiB catalog and assumed to fit.

If every safe slot is occupied, release admission/lookup locks and refuse immediately. Do not wait for a body-held identity while a nested body is trying to acquire another identity. CPU reservations currently consume one identity per reserved core plus picker/gate and surrounding image/compiler/artifact identities, so 64 is not a proved sufficient concurrency bound. No distinct live keys share a guard, even on hostile digest collisions. A future separate bounded CPU-token ledger may reduce this cardinality; it is not part of the current qualified implementation.
