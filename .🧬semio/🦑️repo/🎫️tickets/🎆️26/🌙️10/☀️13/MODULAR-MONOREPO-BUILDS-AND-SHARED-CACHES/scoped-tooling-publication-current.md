# Scoped Tooling Publication

The old bare admission callback was not a writer lifetime: the original actual lifecycle counterexample had five passing laws and two failures, allowing detached work to outlive registry custody and allowing two clone quotes to spend one admission. The replacement API owns each complete publication operation.

`ManagedToolingPublisherV1` accepts an asynchronous body and optional privately issued clone quote. `withManagedToolingProvisionV1` holds the actual exclusive `nx-tooling-provision` ResourceLease. Each submitted task is registered before its first await, tasks execute serially, and each task checks live Original custody, the current store, its current private quote or the unchanged 1.5 GiB cold floor, and actual available capacity. Callback return closes new task births; all accepted tasks settle before registry release. Detached task failures propagate, while a callback failure remains the primary failure. Nested writer admission refuses instead of recursively waiting for the same registry.

Root owns the complementary private clone-capacity module. The provider calls `withAdmittedNxSdkClonePublicationV1(store, quote, registry, body)` for an entire quoted writer. The quote is not a numeric admission override and the cold minimum cannot be lowered by a caller's request. Root's scope retains the exact snapshot reader and drains registered clone work.

## Actual writers

- Nx provisioning authenticates exact ready installations before requesting new capacity. All missing-generation staging, installation or authenticated clone, authorizer compilation, preflight, atomic publication and cleanup execute inside the publisher callback. The initially admitted Source-byte publication remains intact.
- Pinned Bun first checks its exact ready artifact under the actual reader. A missing Bun writer obtains registry custody before its Bun-specific exclusive resource; its complete download, integrity check, extraction, version check and receipt publication run inside the publisher body. It receives an existing publisher from an enclosing Nx/Rustup path rather than opening another registry scope.
- Rustup bootstrap similarly authenticates ready material before any cold admission. Its actual missing bootstrap body, download, checksum, executable and receipt publication are scoped.
- Rustup installation's actual home/generation intentions and directories, component downloads, real installer processes, sealed manifest and receipt, verification and cleanup are all inside the complete publication callback. The Node TOML bridge receives the same publisher; an actual new nested write refuses reentrancy.

No capacities, production deadlines, shared immutable permissions or unknown-generation retirement rules were relaxed.

## Qualification

The language-neutral `PublicationScenario` corpus is closed by the retention schema. Independent SQLite ordering produces the expected first-start/first-settled/second-start/second-settled sequence. Real issued tools8 storage and retained actual SDK quotes drive four scenarios: detached success, detached writer failure, callback plus writer failure, and awaited reentrancy.

The isolated predecessor prototype run passed seven tests / 102 assertions in 31.04 s; release strict ES2022/noUnchecked exited zero. Earlier fixture-only failures were recorded: AST shorthand parsing, expecting reentrancy after callback return had already closed births, and snapshotting global registry availability while another legitimate publisher could acquire it. Those did not establish production failures.

The current fixture replaces the final global-unheld snapshot with an independently launched Python SQLite waiter. While the first actual writer is held, Python first confirms it cannot acquire EX, announces waiting, then waits under the same finite Original deadline. The test releases its writer and awaits actual independent EX acquisition and child settlement. Closed-publisher checks run in each complete lifecycle scenario, avoiding a separate default-five-second test that conflated unrelated registry admission delay with escaped-context refusal. Neither change raises a production or test deadline.

The finite-waiter successor prototype (original 49976) passed all six tests / 105 assertions in 64.87 s. Every scenario printed the independent Python `waiting` then `acquired` sequence. Final release strict (original 9224) exited zero. A predecessor of that final strict run caught a nullable deadline in the test helper; the helper now explicitly requires a finite positive Original deadline before starting its subprocess. This changes no execution budget.

The matching release runtime (original 38665) passed all six tests / 105 assertions in 53.33 s. Final current strict ES2022/noUnchecked passed in both configurations (originals 7420 prototype and 9224 release). All own Originals settled and released their registry scopes before Root's separate corrected capacity gates. Production Source is frozen at this checkpoint.

Fresh SDK publication and the ordinary seven-phase Rust pair remain pending collective capacity qualification; this report does not claim them complete. Root's separate predecessor capacity BOTH result was seven passing laws and one failed independent oracle. Root identified Python APFS `f_bsize` as a 2 MiB preferred transfer size, while actual `f_frsize` was the 4096-byte allocation unit; its corrected oracle now agrees with the private quote (1,023,115,264 total bytes). That oracle correction does not change production capacity Source.
