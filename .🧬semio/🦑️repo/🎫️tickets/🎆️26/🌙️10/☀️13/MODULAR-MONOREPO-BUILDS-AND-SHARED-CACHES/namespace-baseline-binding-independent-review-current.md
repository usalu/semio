# Namespace Baseline Binding Independent Review

Read-only review on 2026-10-15 of `original-namespace-enrollment-plan-current.md` and current `🧰️framework/🔨️modules/🏃️process/🔒️leases/🟦️.ts`. No production edits, gates, tests, Originals or canonical mutation. The plan remains a design; no routing/enrollment implementation is claimed.

## Direction is sound, but baseline completion is a publication prerequisite

An immutable authenticated baseline that binds every existing old physical guard to its original full logical namespace/key, plus genuinely absent keys assigned only to new reusable slots, can preserve same-key exclusion without revoking old descriptors: old and new participants then reach the same actual inode. Existing keys must never become recyclable slot identities merely because current readers appear gone. This is a permanent authoritative partition, not `if old path exists` fallback.

The plan correctly recognizes that old descriptors can act after catalog EX and that directory barriers do not revoke them. Its current text still leaves the decisive cross-generation binding seam for parent review. Do not treat the high-level invariant as proof that the actual old baseline is complete.

## Concrete required closure

1. **Uninitialized old files need a binding or fail-closed exclusion.** Current generic opener computes the old hash path at 101–113, creates/opens it at 143, then initializes identity at 117–130. A preopened empty SQLite file may have no semio resource row/application identity yet; the new process cannot recover its full logical name merely from its basename. A census accepting only initialized rows omits exactly the demonstrated pending-target case. Before publication, authenticate that file's full key through an actual trustworthy original ownership source, or retain its immutable inode/hash reservation as unresolved and refuse any potentially matching new-key assignment. Do not invent a logical key from metadata or assign a slot on “no initialized row.” Unknown/ambiguous baseline material must not become a writable arbitrary path port.

2. **Stable old mapping must survive reopen and idle periods.** Baseline records need the exact canonical namespace, original relative path and verified dev/inode, full key where known, recognized DB state, and protocol version. Lookup checks immutable baseline membership before global slot placement and never expires/reassigns that membership. Old published queued waiters can first open their target only later (261); include their existing uninitialized target and all claim/queue identities needed for that continuation. If an old target path does not yet exist, the directory creation seal must genuinely prevent its creation and new code must not silently create a different same-key authority elsewhere.

3. **Current old code cannot understand new slots.** It always hashes the logical key to its old pathname. A seal can make its attempts for absent keys refuse; it cannot make old code participate in new-slot locks. Therefore the supported post-publication contract is old participants continuing only exact baseline bindings, while new-only resources require new issued routing. This is a truthful compatibility boundary, not transparent support for arbitrary old requests. Old openers must not be able to manufacture another old target through preopened directory handles or another ingress; that remains part of the actual seal proof.

4. **Private custody must bind both coordinates.** Current private issued row stores only path/signal/live (73,160), and custody recomputes the old hash path (75). Add actual privately captured logical namespace/key/mode and immutable baseline or slot generation, plus held physical identity. Public resource strings, a hash match, or serialized baseline receipt alone do not grant custody. Verify actual held transaction is on that binding; no caller-selected pathname fallback.

5. **Queue namespace participates in the baseline.** Current admission 243–249 derives queue from hashed target and opens its claim under catalog SH; poll 255 may create missing foreign claims and target 261 may be newly opened. Claim retirement unlinks physical paths under catalog EX. Baseline old claim/target records cannot be deleted/reassigned while old code can reopen them, and new physical slots must not silently rename the logical queue. A complete plan must state which immutable baseline claim files remain permanently charged and which exact already-issued operations may remove arrival tickets. See `lease-path-binding-independent-review-current.md` for consumer locations.

## Metadata and exhaustion are not yet fully bounded

The plan honestly requires remeasurement of full PIN keys and metadata. It does not yet specify a complete closed baseline schema/count/byte budget, number of unresolved old inodes, aggregate full-key bytes, path records, transaction stages/recovery records, per-slot key replacement peak, or the permanent baseline charge. Those are needed in addition to 16×4 reusable entries, claims/arrivals, seed/guards, directory blocks, journals and the same-inode 128 KiB reserve. Existing baseline files may exceed the new 16 KiB policy; do not imply the new cap retroactively bounds them without physical facts.

Current resource validation at 137 limits JavaScript string length to 4096, **not UTF-8 bytes**. A new 4096-byte full-key schema cannot silently assert equivalence with every old accepted resource. Bound and measure actual encoded bytes, preserve exact full string identity, and refuse unsupported new keys before allocation. Do not truncate/normalize keys or use digests as equality authority. Unresolved old hash reservations need conservative collision refusal because full equality is unavailable.

Global 64-slot probing with full-key PIN equality and catalog SH → PIN SH → release catalog → GUARD wait addresses the stated nested cycle. Exhaustion must remain immediate typed refusal after releasing all temporary locks; neither a per-shard fifth-row refusal nor waiting for an active nested body is acceptable. Count all simultaneous keys, including image/compiler/CPU picker/token identities and temporary allocation/enrollment locks, not just 64 user guards. No current evidence proves 64 sufficient, and the plan appropriately says so. Baseline-bound keys must not consume/release reusable slots dynamically or force eviction of another live key.

## Review result

No reason to reject immutable baseline plus new-only slots as the design direction. Approval to publish remains blocked on an authenticated complete old baseline including empty/pending targets, explicit unresolved-key behavior, durable queue binding semantics, exact full-key and metadata budgets, and real old preopen/reopen exclusion evidence. A new catalog EX or terminal fleet census cannot substitute for any of those facts.
