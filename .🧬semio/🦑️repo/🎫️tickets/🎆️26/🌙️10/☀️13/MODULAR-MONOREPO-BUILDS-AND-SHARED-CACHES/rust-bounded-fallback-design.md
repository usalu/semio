# Explicit Bounded Cargo Fallback Design

Pending production edit window after the genuine Nx compiler pair. This design preserves functionality while first-party adapters are extended; it does not satisfy independently cached units for unsupported selections.

The closed intent can declare an optional fallback object: `kind: bounded-cargo` and an explicit finite adapter list. Supported unit graphs always graft to independently cached compiler units. The selected graph may keep the original script command only when every unsupported root or predecessor maps to a declared machine-readable adapter category. Unsupported reasons must be typed at the Cargo materializer, never inferred from prose strings. Missing categories, generic validation errors, stale physical Source, storage admission failures, unsupported platforms, invalid manifests and unknown compiler configuration still fail before compiler dispatch.

The retained original target must remain `cache: false`, `outputs: []`, with its original uncached prerequisites, mode and selector facts. Selected graph authority projects a bounded-Cargo execution marker into the actual command environment, carrying the admitted intent identity. The package helper checks the marker against the current declaration before executing the existing `buildRepositoryCargoArtifacts` composition. Without that marker, an actual build task reaching its old command still triggers the no-recursion guard. A direct package script request continues to enter canonical owned Nx.

The fallback composition must retain the original process deadline/cancellation, build mode, network grant, compiler capacity, physical compiler-store lease, bounded prepared dependency store, tools lease and Source census. It invokes Cargo with the original package/default deliverables, explicit features/triple and forwarded compiler selectors after closed storage admission. It does not add aggregate artifact caching or claim per-unit reuse. The normal finite pipeline already executes `admitCargoSourceBoundariesV1` before compilation and stores Cargo target/build/tmp/capture beneath the issued compiler store; qualification must observe that actual runtime path.

Tests should first reject missing/extra adapter permissions and altered execution markers against a portable fixture plus Ajv. A real ordinary Repo YAML package build must enter the fallback through canonical Nx, report exactly which unsupported adapter categories were admitted, complete its original library deliverable and log actual finite storage/census custody. Binary routes need separate tests preserving coordinator/CLI/dashboard binaries and installation behavior. Both modes must remain uncached at aggregate level. Source-size excess and storage overrides must continue to refuse before compiler writes.

## Corrected Source Admission Prerequisite

Root corrected the Source closure walker to retain a first inline module after a leading inner attribute. The actual OS Kernel begins with a large inner allow attribute immediately before its DSL module. Earlier Kernel census values (~3.7 MB and 55k active lines) may omit that branch. Production fallback must use the corrected ordinary admission and remeasure Kernel if selected; genuine package-boundary failures must be recorded without widening limits or suppressing modules. No prior census is reused as current proof.

## Actual App Deliverable Consumers

The current neutral `buildCargoArtifacts` default staging directory belongs to the fixed compiler image: `published/<digest(manifest)>/<mode>`. CLI repo/mcp still execute `packageRoot/dist/build/prototype/semio-repo`, and dashboard installation still reads `packageRoot/dist/build/<mode>/semio`. These consumers need a shared repository published-artifact directory contract plus reader custody; copying mutable Cargo trees back to package `dist` would violate the new bounded artifact owner.

Coordinator run currently executes `cargo run` directly through the finite relay; it can first request its canonical package build and execute the resulting bounded published binary. CLI repo/mcp requests explicitly compile only `semio-repo`, while its default build includes both declared binaries. Exact scope preservation therefore needs a declared binary compilation target for repo/mcp and selected graph consumption of declarative intents on compilation targets beyond the literal name `build`.

Dashboard build currently compiles and installs `semio`. A pure compiler aggregate noop cannot discard installation behavior. The long-term route must split declared binary compilation and the uncached installation receipt barrier, retaining existing public build behavior through prerequisites. Its runtime staleness owner can request the canonical compile task and install the bounded published executable under the existing installation owner. Both installation and runtime must respect cancellation/progress and verify executable content/mode before use.
