# Native Failed Opening: Phase and Custody Design

This is a Source-only review after `native-failed-open-boundary-current.md`; no Native edits, system command, mount, physical observation or cleanup was executed. Current canonical image providers still do not consume the accepted Native cleanup enrollment. Existing cleanup evidence state is a neutral reducer, not an execution grant.

## Actual Seams

The macOS `storage/🍎️image/🟦️.ts` opener obtains shared image custody, upgrades to exclusive to provision/attach when necessary, then obtains shared custody and validates plist/mounted/backing identity. Its caller receives no handle until all these steps finish. `provisionNativeImageStorageV1` creates directories before its try, uses one supplied control for create/attach and catch-time detach, sets mounted only after attach success, suppresses detach rejection and can recursively remove the directory when that boolean is false. Thus a command that fails after kernel activation cannot safely be classified as inactive from its return status/boolean. Later receipt/verification failure after fresh provision also needs a declared owner for that new persistent activation.

`withIssuedNativeImageV1` starts its own try/finally only after `openNativePlatformStorageV1` returns. The repository store correctly drains issued/private accepted consumers before closing an already returned image, but cannot settle a Native opener that never returned its handle. The Linux/Windows shared fixed owner also needs the same conceptual lifecycle; this review does not claim its platform-specific partial-activation proofs.

Repository partition opening opens leases, creates its data directory and then opens the requested image under its reservation control. Generic Vite creates its narrower phase before entering the stores, but initial dependencies/products opens and Vite scratch creation still precede the artifact phase bridge. Passing a cancelled phase as the sole backing control would incorrectly remove cleanup/reservation authority.

## Minimal Safe Owner Contract

1. Before the first directory/create/attach effect, privately accept one `native-image` cleanup enrollment from the actual live base control under the exact canonical image resource. Existing `withAcceptedPhysicalCleanupV1` supplies a body cutoff and nonrenewable terminal reserve; use the existing10000ms image cleanup policy, refuse if unfunded. Register accepted child commands and progress before birth, and hold actual imageEX outside their complete drain. Never acquire a second EX beneath that same retained imageEX. The public fresh-only path and persistent opener must share one privately validated lower owner, not each invent cleanup heuristics.
2. Keep base reservation/image custody and effect phase as separate actual issued identities. Authenticate exact base Original plus private `requireIssuedResourceControlRefinementV1(base, phase)` before effects. Actual queue acquisition/inspection/create/attach must consume the carried phase’s live signal and remaining deadline. Returning a tuple or a copied control/store must not manufacture this relationship. A lease acquired under a phase remains releasable after phase stop; recheck/cleanup authority remains with its genuine enclosing owner, not by relabeling its private lease as base-owned. This requires an explicit lower Native operation seam; adding only a phase precheck around the existing base-controlled wait is insufficient.
3. Capture creator directory/backing inode/device/size and the exact activation request before submission. After the child joins, obtain complete bounded kernel mapping information under accepted cleanup custody, even on command failure. Classify exact inactive, exact active, or unresolved; do not infer inactive from a failed command or missing handle. Never detach an image that was shared/preexisting when this borrower entered.
4. Stop body births and JOIN accepted body/progress before cleanup. `beginAcceptedPhysicalCleanupV1` may itself report the retained body failure after joining; keep that failure and still attempt the already-funded cleanup after checking its live token. Perform at most one exact deactivation, then reobserve complete mapping and exact backing identity. Remove only the newly owned exact inactive backing/root/receipt with a complete child roster. Unknown or changed material is retained.
5. The current opaque cleanup token exposes cleanupSignal/remaining facts, but owned command capture still requires a live ResourceLeaseControl. No current API permits passing that token to hdiutil cleanup. Therefore implementation needs a narrowly typed canonical cleanup-command consumer (bound to actual accepted native-image token, exact resource and privately captured Native state) before wiring the provider. It must execute only the already-accepted finite observation/deactivation obligation and drain its real child. It must not mint a fresh control, execute arbitrary caller argv, reuse expired body control, use a longer sibling, or reconstruct deadlines. This is an explicit prerequisite, not an assumed existing port.
6. A successful new persistent publication explicitly transfers activation ownership to the validated persistent receipt/image protocol before releasing the opener’sEX. Failed publication retains new-image cleanup ownership. Existing persistent borrow failure releases only its own reader. Unresolved activation must remain charged and enter a genuinely accepted unresolved-owner handoff before releasing enclosing responsibility; a diagnostic path string is not a handoff authority.

## Required Proof Sequence

First extend the existing neutral cleanup schedule/schema and independent oracle to include failure-before-handle, command-failure-but-active, progress failure, publication failure, Error/undefined, expired funding and exact body/cleanup deadlines. A real small private fixture under a preaccepted healthy diagnostics parent then proves: cancellation while waiting has no creation effects; cancellation during attach joins the child before observation; actual activated mapping is removed only under creator custody; existing shared image is never detached; concurrent reader/future opener remains excluded by actualEX until settlement; replacement/unknown child refuses removal; failed detach/observation retains exact charged material and reports every failure. Use real private controls and Python SQLite custody observations, not the staged copied-control cancellation observer. Qualify macOS first and independently qualify Linux/Windows activation semantics.

Only after that lower owner is proved should store opening gain an explicit carried-phase operation input. Keep reservation base for persistent lifetime/cleanup; route all expensive opening waits/effects and pre-body temporary creation through the actual phase. Held/nested stores must enroll synchronously in the existing consumer frame and preserve both authentic owner and phase; no structural store rebasing or same-object exemption. Test phase cancellation before first store availability and during nested products→diagnostics borrowing separately. No current listener/store opening phase-compliance claim follows from the existing artifact bridge.
