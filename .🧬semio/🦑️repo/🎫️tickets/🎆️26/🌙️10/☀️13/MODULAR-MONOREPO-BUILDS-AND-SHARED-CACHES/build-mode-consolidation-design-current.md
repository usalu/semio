# Two Build Intent Consolidation Design

## Scope And Status

Source and configuration inspection only, following [the initial LOW audit](build-mode-profile-audit-current.md). No production profile, manifest, script, editor entry, compiler policy or test body was changed. No build, Cargo probe, Nx setup, SDK publication, maintenance or runtime test was launched. The currently executing SDK gates and their frozen test Source are unaffected. This is a concrete implementation proposal for Root review; the oracle and runtime qualification below have not run.

The proposed public and Cargo profile names are exactly `prototype` and `release`. Prototype minimizes iteration latency subject to unchanged safety and admitted product contracts. Release optimizes the shipped runtime and size; it does not promise that a single rustc opt-level simultaneously minimizes every workload's time and bytes. Target ABI requirements, compiler host work and product responsiveness constraints are explicit inputs to those intents, not extra selectable user modes.

## Existing Measurement Reasons

These are retained historical measurements, not new benchmark claims:

- The actual G5 report at `2026/09/23/END-TO-END-OS-HUB-COLLABORATION-MCP/📓️wp-g5.md` records a WFC workload at 112.7 s with debug Wasmtime/Cranelift versus 63.9 s with optimized dependencies; cold JIT compilation changed from about nine minutes to about 36 s. The optimized dependency rebuild plus relink cost 1 min 44 s. This supports an explicit runtime constraint, not a claim that opt3 makes compilation faster.
- `2026/09/23/BUILD-SEMIO-TECH-PLAY-FOR-CDN-DEPLOYMENT/📓️2026-10-13-describe-cleanup.md` records the descriptor tool cold release build at 945 s, versus 392 s with 16 codegen units/thin-local LTO, under different system loads. The committed host-tool run was 570 s under substantially higher load. Interleaved runtime descriptor hashes agreed and runtime differences were within load noise. This is a real reason for host-tool tuning, although it does not isolate a modern compiler's optimum.
- The scalable-build report in that same ticket records raster release codegen-unit 1 versus 16 at 612 s/10.6 GB/5.01 MB brotli versus 317 s/8.2 GB/5.13 MB brotli. That measured size/latency/memory tradeoff argues against blindly applying native release's single codegen unit to wasm.
- Current manifest notes retain the 8 ms interactive ceiling and a 10–11.5 ms lowpoly turn below opt2. The current browser hot-crate owner records roughly 25 ms text shaping at opt0 and roughly 85 ms editor painting. The report text behind the latter two was not independently rerun here; treat them as recorded constraints requiring a genuine current oracle before removal.
- Existing `.cargo/config.toml` owns 16 MiB browser/8 MiB WASI stacks, 512 MiB WASI memory, native test stack allowance and Linux linker selection. These are ABI, resource or correctness settings, not optimizer modes; preserve them.

## Proposed Schema-Owned Architecture

Extend the canonical `process/🏗️build/🎚️mode` owner with a nearby profile policy owner, schema and language-neutral corpus. Request fields are closed: `{version,mode,target,role,operation}`. Mode is exactly prototype/release; target is the actual declared triple; role is derived by the actual authored build owner (native artifact, WASI component, browser module, or descriptor emitter), not an arbitrary caller optimization string. Operation distinguishes build/check/test/doc without allowing it to select a third mode. A caller cannot submit optimizer numbers, a package override list, panic mode, output directory, or a custom profile name.

The response is a closed compiler plan: canonical profile name equal to mode; bounded immutable Cargo profile configuration; explicitly selected target/post-link settings; finite package-constraint rows with evidence IDs; and a digest over actual policy bytes and effective facts. The plan is data, not storage or Original authority. Existing issued compiler/configuration lifetimes still own execution and physical writes.

Use only `[profile.prototype]` and `[profile.release]` as authored Cargo profile names. Different target/host-role backends may require different settings inside those same profiles. Project their exact immutable Cargo config at the owned invocation boundary: Cargo has no general `[target.<triple>.profile]` facility, and package/build overrides cannot express LTO. Do not implement a fake target-profile table or sneak target-wide `-C` flags into a shared native and wasm dependency compilation.

The immutable effective-flag view currently records merged configuration and pins encoded flags; it is not yet an immutable consumed-profile view. Integration must extend actual profile consumption, include merged profile values and allowed environment precedence, and compare the resulting actual Cargo units. Merely recording a config digest while Cargo reopens mutable profile inputs is insufficient. Reuse the real configuration/store/Source custody and keep the consumed-manifest ABA limit explicit until independently closed.

Handcraft duplicate workspace tables away after the source-first oracle exists. Keep no generated migration, runtime legacy profile branch, alias or fallback. Standalone workspace cwd/config lookup must be qualified, rather than assuming every Cargo invocation finds the repository config. Authored raw-Cargo defaults may still exist inside Cargo itself; managed entries must always pass the admitted canonical profile. A static law rejects new authored third profiles and accidental duplicate policy.

## Proposed Effective Settings

| Intent/backend | Proposed starting policy | Rationale/qualification |
| --- | --- | --- |
| Prototype native ordinary units | opt0, debug1, 256 codegen units, incremental; explicitly disable cross/local LTO where admitted; assertions and overflow checks on. | Remove global inherited build-override opt3. Retain only evidence-owned runtime-hot package exceptions until current responsiveness qualification. Do not silently label those units unoptimized. |
| Prototype compiler host dependencies | opt0, debug0, 256 codegen units by explicit build-override; retain any required checks/panic semantics. | Cargo's fast host-build baseline. A blanket opt3 host override currently has no isolated evidence in this audit. Measure build-script/proc-macro execution before any future exception. |
| Prototype wasm components/browser | Preserve opt1 starting backend plus the exact evidenced hot package constraints, incremental, 256 units, assertions/overflow checks, symbols kept. | Current opt0 can increase final wasm function count/link cost and violate interactive contracts. Optimize total edit-to-usable latency, not just rustc frontend duration. Remove generic caller-supplied hot-package knobs. |
| Release native artifact | Preserve opt3, thin LTO, one codegen unit, no incremental as the first consolidated baseline. | Runtime/size tuning needs actual binary metrics; do not promise mathematical optimum. Keep current strip/panic behavior until the specific observer/ABI tests establish changes are safe. |
| Release wasm artifact | Preserve s/thin/16 units/symbol stripping/no incremental plus the existing admitted post-link shrink transform. | Supported by retained raster measurements. Full Cargo/backend/receipt identity distinguishes it from native release while the public and Cargo profile name is release. |
| Descriptor emitter | Select parent mode and owned host-tool backend. Release can retain opt3/16 units/thin-local policy via the immutable mode projection. Prototype follows build-speed intent with only evidenced runtime constraints. | Removes host-tool profile and release-only admission exception without discarding its measured role-specific rationale. Existing emitted semantic-descriptor equality must qualify both modes. |

This baseline does not introduce abort panics, remove debug assertions globally, disable overflow checks for prototype, change test unwinding, shorten correctness/resource deadlines, relax artifact caps, or strip symbol data required by actual consumers. Preserve current target-specific defaults and validate their actual rustc resolution. In particular, `lto=false` is not equivalent to off at nonzero optimization; schema should express the exact intended value and the Cargo oracle must observe the distinction.

## TDD And Independent Effective-Profile Oracle

Before implementation, author a closed JSON schema and corpus whose input rows include mode, actual target/host role, operation, fixture manifest/config/environment inputs, and expected effective unit observations. Output rows are package/unit role plus actual profile name, opt_level, debuginfo, codegen_units, debug_assertions, overflow_checks, panic, LTO and incremental/strip observations where the pinned Cargo exposes them. No production library reimplements Cargo inheritance as its authority.

The first genuine RED should be the actual current prototype inherited named opt3 and build opt3 facts conflicting with the closed intended policy; a separate RED rejects the current host-tool selector and unowned per-call browser tuning. Independent Ajv validates the neutral schema, SQLite checks the mode/role/priority mapping corpus, and Bun TOML plus an existing independent TOML parser compare authored policy projections. These are portable expected-output checks, not substitutes for Cargo.

The primary semantics oracle is the actual retained pinned `nightly-2026-07-20` Cargo through the genuine CompilerStore/Original, finite outputs, writer admission and existing config receiver. Use no-dependency tiny workspaces with a target library, host build script, proc macro and a dependency present in both host/target roles. Capture actual `cargo ... --unit-graph -Zunstable-options` and effective `config get` under the same exact arguments/view. Compile only small probes when the unit graph cannot establish a field; observe actual verbose rustc arguments and compiled values independently. Preserve exact planning/execution argument correspondence. No ambient compiler, fake port result or compiler wrapper added solely to fabricate profile observations.

Required cases: both intents; implicit native versus explicit target; normal target versus host build dependency; named package and wildcard precedence; build-override; inherited dev contamination; workspace-root versus dependency-manifest profiles; config-over-manifest and environment-over-config behavior; conflicting profile environment/args refused before compilation; both profile spellings `--profile X`/`--profile=X`; Nextest assertion profile independent of compiler profile; WASI/browser target ABI unchanged; descriptor role resolves to canonical mode; unknown/alias/extra mode rejected; and cache digest changes on a real effective profile change but not a source-neutral role spelling.

Native probe laws must confirm test panic unwinding/catch behavior and mode-sensitive assertions/overflow behavior without changing safety semantics to satisfy a faster benchmark. Target probes retain exact Wasm stacks/memory/caps. Product qualification then measures bounded cold, warm, changed leaf and sibling reuse, actual runtime latency and final/raw/compressed bytes. All expensive probes retain cancellation/progress and the actual Original deadline. Register both modes and strict commands in the existing permanent `📜️script.ts` and both editor catalogs before execution.

The current Cargo Book was inspected for inheritance/configuration/override semantics, with the pinned compiler planned as the final oracle. [Profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) documents named-package precedence over wildcard/build overrides, host-build defaults, inability to set panic/LTO/rpath in package overrides, and the distinction between false and off LTO. [Configuration](https://doc.rust-lang.org/cargo/reference/config.html#profile) documents the configuration side. Online documentation can move ahead of the pinned nightly; do not substitute new built-in profile behavior for measured pinned output.

## Implementation Sequence For Root Approval

1. Land only the independent closed policy/corpus and genuine Cargo effective-profile REDs under actual finite fixture ownership. Qualify package/config precedence before selecting production settings.
2. Implement canonical two-intent target/role projection and immutable consumed-profile integration, preserving current explicit Source/compiler/storage authorities and host/target separation. Refuse hostile profile environment or ad-hoc overriding args; preserve unrelated environment roles.
3. Handcraft all actual workspace/root profile declarations and consumers together: mode policy, generic native/wasm admission, descriptor emitter, component plans/receipts/provenance/catalog/help, browser hot-crate caller, Trunk settings and test fixtures. Public launch selectors become only prototype/release; semantic paths use those modes with no old-name compatibility route. Preserve generated artifact ownership and invalidate old identities honestly.
4. Run both-mode neutral/TOML/Cargo/strict gates, tiny native host/target/test probes, then measured representative descriptor, interactive wasm and release size/runtime laws. Any observed regression blocks the affected projection rather than weakening safety/time/resource caps. Retain measured constraints until replacement code meets the same product contracts.
5. Coordinate one fresh SDK Source freeze/publication only if the captured closure changes, then ordinary Nx/selected Rust cache invalidation qualification. Do not overlap this profile implementation with the currently pending full SDK publication/callback sequence.

Root approval is requested for this concrete two-name, target/role-projection implementation scope. No production settings have been changed or approved by this research checkpoint.
