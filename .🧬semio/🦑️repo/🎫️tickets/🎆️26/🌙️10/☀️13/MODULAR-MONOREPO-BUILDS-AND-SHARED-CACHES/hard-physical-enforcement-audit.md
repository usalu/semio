# Hard Physical Enforcement Audit

Read-only qualification on 2026-10-14. AGENTS.md, cache-hard-bound-plan.md and rust-crate-cache-hard-ceiling-audit.md were read. No compiler, installation, permission change, quota change, image creation or mount was executed. This document is the only authored file. No hard enforcement implementation is qualified by this audit.

## Result

An ordinary writable directory has no portable unprivileged aggregate hard-byte quota. A publication reservation ledger can prove a bound on cooperating artifact writes; it cannot stop Cargo, rustc, a linker or a build-script child from writing more scratch bytes than its reservation. Checking free space before launch and polling growth after launch cannot prove that a fixed ceiling is never exceeded. Source size, compiler-job count and per-file limits do not establish a total bound either.

The strongest honest universal zero-touch design is a capability gate: strict compilation and cache restore require an already-qualified bounded backing store; otherwise reject before launching writers. This guarantees refusal, not useful compilation, on unsupported hosts. Automatically provisioning a useful persistent bounded store on every native Windows/macOS/Linux host with no privilege and no additional dependency is not established and must not be advertised.

## Platform Mechanisms

| Platform | Actual enforcing mechanism | Prerequisites and limitations |
| --- | --- | --- |
| Native macOS | APFS volume quota, or a fixed-capacity filesystem image | Apple documents a volume allocation quota. Local diskutil help requires ownership of the affected disks; a custom mountpoint is root-only. A user-owned disk image is the most plausible native zero-touch route, but creation, attach authorization, effective capacity and failure behavior were deliberately not exercised. A fixed non-growing backing image gives a stronger host-file bound than a sparse bundle; include image header/footer and host allocation rounding. Never resize automatically. APFS quota is not proof of a byte-exact total host footprint including shared container metadata and snapshots. |
| Native Windows | Enforced NTFS user quota on a dedicated volume, or fixed VHD/VHDX | NTFS quota is per-user per-volume, not a repository-directory quota. It can interfere with unrelated files belonging to the same user. Microsoft documents VHD management with Administrator permissions and Backup Operators/Administrators membership. Thus stock ordinary-user zero-touch provisioning cannot be claimed. A preprovisioned dedicated bounded volume can support useful strict builds. A fixed VHD has finite backing size; include its container overhead. |
| Native Linux | Administrator-provisioned project/user quota or fixed filesystem; bounded tmpfs | A filesystem/mount must support and enable quotas. Mount/provisioning capabilities cannot be assumed for an ordinary user. User namespace availability varies by host policy and is not a universal mount capability. tmpfs has kernel-enforced allocated-byte and inode limits, is volatile, and can consume swap unless noswap is supported/configured. It is not a persistent disk-cache quota. |
| Devcontainer | Launch-time bounded tmpfs, or host-provisioned quota-backed mounted storage | Docker daemon/host performs mount provisioning; the container user need not receive mount privileges. tmpfs size bounds its data blocks, while inode limits must also be authored and memory/swap accounted separately. Container CPU/memory controls are not a bind-mount disk quota. An ordinary named volume or repository bind mount remains unbounded. A daemon storage-layer option is not proof that bind-mounted cache paths are limited. |

Primary references: [Apple APFS volume size options](https://support.apple.com/guide/disk-utility/add-delete-or-erase-apfs-volumes-dskua9e6a110/mac), [Apple disk images](https://support.apple.com/guide/disk-utility/create-a-disk-image-dskutl11888/mac), [Microsoft NTFS quotas](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-quota), [Microsoft VHD management](https://learn.microsoft.com/en-us/windows-server/storage/disk-management/manage-virtual-hard-disks), [Linux tmpfs limits](https://docs.kernel.org/filesystems/tmpfs.html), [Docker tmpfs mounts](https://docs.docker.com/engine/storage/tmpfs/), [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/). The platform choices above are engineering inferences from these capabilities, not tested provisioning recipes.

## Nx and Cargo Scope

[Nx maxCacheSize documentation](https://nx.dev/docs/reference/nx-json#max-cache-size) explicitly describes removal after the cache exceeds its limit, down to below 90%. This is a retention threshold, not an admission barrier or physical never-exceeded guarantee. Its environment override and default must not substitute for an authored fixed policy. Nx remains the task input/output identity and crate DAG owner; filesystem enforcement must include Nx restore, capture, metadata and cache publication as writers.

[Cargo build-cache documentation](https://doc.rust-lang.org/cargo/reference/build-cache.html) distinguishes final target-dir outputs from build-dir intermediates, incremental state and build-script outputs. Both roots must be bounded, along with Cargo home, TMPDIR/TMP/TEMP, linker temporary state, logs and publication staging. Setting CARGO_TARGET_DIR alone is insufficient. Build scripts can execute arbitrary processes; environment redirection is a routing convention, not a sandbox. To claim containment against arbitrary build scripts, a qualified sandbox must deny writes outside the bounded store. Otherwise the guarantee applies only to cooperating declared tools and explicitly excludes rogue/undeclared writes.

## Required Invariants

1. Separate scopes: managed artifacts, mutable compiler scratch, registry/download staging, restored outputs, indexes/logs and fixed backing-store overhead. Source/Git/user files and externally configured toolchains are not bounded by a cache policy. Predictable total repository size requires a separately enforced source/Git/output policy or a repository-wide bounded volume.
2. A single atomic reservation authority must cover every managed writer before any copy, extraction or publication. Charge the peak overlap of old artifact, staging artifact and replacement; do not count a rename as a second copy. Release reservations only after owned data is retired and open handles are closed. Serialize or transactionally reconcile crash recovery before reopening admission.
3. For controlled streaming writes, enforce per-chunk remaining bytes before the syscall. Reserve allocated-block rounding, file/directory metadata and bounded receipt/index/log capacity. A logical-size ledger alone is not a physical-byte proof. Hardlinks, clones, sparse files and snapshots require explicit accounting semantics; conservative duplicate charging is safe but can reduce usable capacity.
4. Scratch admission reserves capacity for each producer, but only a kernel/storage limit prevents a producer from exceeding it. Unknown-size artifacts use fixed producer allowance; hitting ENOSPC/quota is a supported failed build, never permission to grow the store. No publication follows a failed/truncated compiler output.
5. Strict startup must verify the bounded store identity, configured capacity, all routed output roots and writable-path containment. An ordinary-directory fallback, warning-only check, occupancy monitor or free-space sample must set hardPhysicalEnforcement=false and must not launch strict writers.
6. Keep minimum host headroom separately. A fixed-size image already occupies its accounted backing capacity; a sparse image can expand up to its maximum and requires host admission for that maximum, not its currently allocated bytes. Filesystem metadata overhead means a configured artifact allowance must be smaller than the finite store envelope.

## Local Readiness Evidence

The current machine reports Darwin, uid 501, and admin-group membership; group membership is not proof of unattended elevated privileges. hdiutil, diskutil, bun, cargo, rustc, docker and quota executables exist. mkfs.ext4 and unshare were not found by command -v. Root and system volumes are APFS. hdiutil create -help reports that command deprecated in favor of diskutil image create on this installed system. diskutil apfs addVolume help lists quota/reserve options, disk ownership and root-only custom mountpoints. docker version could not contact the local daemon socket because it does not exist. Thus Docker-backed containment is not ready here. No new image, volume or ENOSPC test was attempted, so macOS image-backed containment remains unqualified.

The local setrlimit manual defines RLIMIT_FSIZE as largest individual file, not total files. A compiler can create many files sequentially; RLIMIT_NOFILE only limits simultaneous descriptors. These controls cannot replace a aggregate storage boundary.

## Qualification Required Before a Hard Claim

Use tiny dedicated bounded stores on each supported platform. Verify cap-plus-one write failure, many-small-file/inode exhaustion, child/build-script writes, temporary-file placement, canceled/open-unlinked files, simultaneous producers, restore extraction bombs, crash recovery and nonpublication after ENOSPC. Observe console evidence with temporary [DEBUG] logs and retain the qualification report. Validate ledger decisions independently with SQLite and artifact/schema decisions with an existing third-party validator. Test quota/volume capacity and store identity, rather than inferring readiness from command presence. Until those checks run, a declaration of useful native cross-platform hard physical enforcement would be unsupported.
