# Hard Cache Bound and Crate Artifact Plan

The developer explicitly strengthened the build goal: Rust caches repeatedly fill the disk. Nx must own input/output artifact caching at crate boundaries, changing a crate must recompile it, cache size must be fixed and never exceed the configured ceiling, maximum repository storage must be predictable, and giant crates/rebuild amplification must be removed. The existing8GiBtrigger/16GiBtarget/32GiBlogical maintenance policy is not acceptance of this requirement.

Current fleet ownership: nx_continue owns granular crate producer DAG, mode/config/toolchain/dependency/source identity, exact artifact outputs and actual invalidation; native_continue owns enforced capacity/admission, bounded active compiler stores, crash/cancel cleanup and cross-platform constraints; rust_cache_audit is a GPT6.1Sol Light read-only audit of crate size/amplification and every physical cache root. Root finishes current relay admission/caller regression before hard-bound integration. Guest/Host unrelated runtime expansion is held. All current Source inputs and reports are retained.

Acceptance must distinguish committed Nx cache artifacts, active compilation workspaces, published outputs, tool/dependency caches and repository source/Git baseline. A fixed committed artifact cache alone does not bound a compiler workspace that can grow without limit. An asynchronous monitor can overshoot and must not be called a hard cap. No pruning of live/guarded outputs, resetting shared daemons or terminating other builders is authorized by this change.

The intended direction is granular crate outputs, authentic dependency-aware invalidation, shared bounded canonical working sets instead of indefinitely accumulating recipe slots, reservation before publication, and admission that refuses/queues when retained artifacts and active work cannot fit. Actual enforcement capability must be tested on each platform; unsupported physical bounds must be explicit, not represented as monitor-based guarantees.
