# Independent Development Hub Service Supervisor

This is Source-only design after Root's explicit selection of an independent service role. It implements no platform registration or start/stop command, opens no image/network and qualifies no native platform. The client Source successor is separate from actual service activation.

## Existing Real Entry And Custody

The authored executable command remains the existing registered `os-hub:local-hub-owner` Script route in `🌎hub/📦packages/🦀rust/📜script.ts`, whose DevLocalHubScript uses the real received Original. Its actual owner chain is Repo development state → real managed published Hub reader → state task → `local-hub:data:<genuine directory>` EX → actual Host → retained materializer → candidate validation/publication → real Hub child and callback broker → complete terminal/drain. This scope already preserves persistent data across Host close and never adopts a free OS_HUB_DATA path. Its zero requested phase inherits the actual service root; it cannot extend a UI parent root. The new UI client owns only genuine state SH and bounded broker reads, never that writer EX.

The actual old GIS contribution supplied `bun repo run os-hub:local-hub-owner --` and raw detached/unref startup appended a directory. That frontdoor is removed in the client successor: closed `{version:1,service:"local-hub",defaultProfileId}` DATA does not choose a program, path or argv. No service is implicitly started merely by opening the client callback.

## Required Independent Platform Owner

Native Windows/macOS/Linux and devcontainer need a genuine independently authored application service startup role, not a serialized renewal of the first UI's issued control. Root owns the canonical receiver/predeclared handoff design. It must authenticate its actual launch selection/parent startup relationship while keeping a single real public receiver; it may not copy the old cache-specific two-authored-birth helper. A one-time DATA receipt or PID does not grant the service lifetime. Every resource still belongs to its actual service Original and live controls.

The platform layer must bind a closed first-party per-user supervisor identity to canonical repository identity, exact service Source entry, actual selected mode/profile, actual managed runtime/tool executable and immutable service policy before effects. A free environment path, shell command, process.execPath string or DTO role cannot issue it. The bootstrap problem is explicit: an OS supervisor cannot open a runtime binary inside an unmounted Tools image by knowing its pathname. A real existing installed/bootstrap executable owner must establish that supported entry, authenticate the Tool/Native protocol and retain its own opening responsibility. No such generic platform supervisor owner was found or exercised by this bounded cut.

The three native platform integrations must each own their real registration storage, actual fixed system operations and rollback/retained-unresolved lifecycle under a preaccepted finite startup/cleanup grant. Platform user-service configuration is DATA only. macOS user launch registration, Linux user service management, Windows per-user supervised startup and devcontainer foreground supervision need their own exact host-specific command algebra and runtime tests; generic argv callbacks or platform-name aliases are insufficient. Native Windows state durability currently refuses before effects in the persistent owner, so Windows cannot be claimed complete merely from a generated service definition.

## Concurrency And Stop Contract

The supervisor runs at most one real service per canonical repository namespace. The authentic data EX remains the final cross-process exclusion guard, not the supervisor's process table. Clients can read the actual state under image SH while the service owns data EX. Client joins are bounded and authenticate broker runId against real readiness before using business session credentials. Starting/stopping one UI must neither release the service data EX nor terminate the independent service. Service stop belongs to its explicit actual supervisor/service control; all accepted credential work, broker close, native child terminal, publication readers, state task and guard must settle before service release.

A service that cannot prove bootstrap/runtime/Original custody must refuse before registration/start effects. Existing unknown platform registrations, old hub-dev directories and stale PID/log/owner files are retained; no rename/adoption/migration cleanup is authorized. A future positive gate must cover two clients, first-UI exit with second retained, service crash/restart and stale broker refusal, wrong registration/runtime/Source, cancellation, complete child join, physical backing quota and supported host Native receiver behavior. None is qualified by current pure/Source tests.
