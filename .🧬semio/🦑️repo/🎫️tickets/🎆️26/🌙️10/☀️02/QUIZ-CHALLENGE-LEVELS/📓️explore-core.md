## 0. The ten facts that matter most

1. **Nothing in the core knows "difficulty".** No `challenge`, `level`, `hint`, `timer`, `deadline`, `multiplier`, `bonus` exists in the
   schema, the modules, the README or the shared fixtures **[V]** (grep, section 6). The only "level" hits are Protocol v2 test tags
   (`@level-fundamental`) and the heading levels of React tests. "points" exists only as `score × 100` for the leaderboard.
2. **`start-run` carries `{ id, learner, run, quiz }` and nothing else** (`🧬️schema/🔣️.json:628-639`, `🧬️schema/🟦️.ts:264`,
   `🧬️schema/🦀️.rs:594`). There is no per-run option today, so there is no precedent to copy. The closest things are the per-quiz
   `draw` (in the quiz document, sheet-affecting), `Limits` (proctor config) and client-local preferences (`others`, `pets`).
3. **The sheet is a pure function of `(quiz, seed)` and `seed = FNV-1a(run id)`**, set at `run-started` (`🧾️lifecycle/🟦️.ts:111`,
   `🃏️sheet/🟦️.ts:53`). The sheet is *rebuilt* on every use: `record-answer` (`🧾️lifecycle/🟦️.ts:122`), `submit-run` (`:136`), `runView`
   (`👁️views/🟦️.ts:106`), the deputy (`🎯️targets/⚛️react/🔨️modules/🫡️deputy/🟦️.ts:151`), Rust the same
   (`🧾️lifecycle/🦀️.rs:217,231`, `👁️views/🦀️.rs:71`). A `challenge` that changes the sheet must therefore be stored in `RunState`
   and passed to `sheetOf(quiz, seed, challenge)` in all of these places.
4. **The sorting sheet never carries values.** `SheetItem = { id, label, icon? }` (`🧬️schema/🔣️.json:371-381`). True values reach the
   client only (a) in `RunResult` after submit (`SortingItemResult.value`), or (b) when the site ships `material` (the whole quiz with
   solutions) for the offline deputy (README:489-528). So "show the sort keys" cannot be done by adding the value to the sheet without
   leaking the solution. See section 2 for what "keys" could mean (the typed `guesses` field is the likeliest meaning **[I]**).
5. **The matching sheet DOES reveal numbers**: `SheetDimension.cards` is the multiset of true values per dimension
   (`🧬️schema/🔣️.json:344-355`; `🃏️sheet/🟦️.ts:46`). The solution is the assignment of card to item, not the values.
6. **Scores are `[0, 1]` everywhere and the schema enforces it**: `Score` has `maximum: 1` (`🧬️schema/🔣️.json:30-34`) and is used by
   `RunResult.score`, `TaskResult.score`, `DimensionResult.score`, `RunSummary.score`, `LearnerView.best`, `LeaderboardRow.best`. A
   points multiplier cannot be folded into `RunResult.score` without lifting that maximum; it needs a new field (`points`).
7. **"Points" are computed in only one place**: `total(best, catalog)` = sum over catalog quizzes of `best[quiz] × 100`
   (`👁️views/🟦️.ts:85-87`, Rust `👁️views/🦀️.rs` `total`). Best = max `score` per quiz (`bests`, `👁️views/🟦️.ts:73-82`). The multiplier
   plugs here, but "best per quiz" must then become "best points per quiz" (or best per quiz and challenge), which changes
   `TranscriptRun`, `Transcript`, `standing`, `LearnerView.total`, `LeaderboardRow.total/best`.
8. **The only clock is the decision time `now`/`at`** (proctor's HLC millis `context.now.millis`, `🎓️teaching/🛂️proctor/🔨️modules/🎭️actors/🦀️.rs:370`;
   the deputy passes the device clock). `RunState` keeps `startedAt` and `submittedAt` only; `answer-recorded` events carry `at` but
   `evolveLearner` drops it (`🧾️lifecycle/🟦️.ts:185-186`). There is **no notion of a task being shown/opened**, so a per-question timer
   has no server-side anchor. The `Place.task` in presence is ephemeral and client-reported (`🧬️schema/🔣️.json:1010-1021`).
9. **Lockstep surface is large**: schema JSON + TS twin + Rust twin (all `deny_unknown_fields`), TS/Rust modules, a Python reference per
   case (`🧪️tests/*/🐍️.py`, 13 of them), generated fixtures (`🧫️fixtures/*/🔣️.json`, "never edit by hand", generated by
   `.🧬semio/🦑️repo/🎫️tickets/🎆️26/🌙️09/☀️28/QUIZ-PRODUCT-AND-TEACHING-PROCTOR/generate_quiz_vectors.py`), the proctor
   (`🎓️teaching/🛂️proctor`, with `PROJECTOR_REVISION = 5` and its own `CrowdTally`), and the React outbox/deputy/session.
10. **`PROJECTOR_REVISION` is in the proctor, not in the quiz core**: `🎓️teaching/🛂️proctor/🔨️modules/🔭️projections/🦀️.rs:89`
    (`pub const PROJECTOR_REVISION: u32 = 5;`, stamped `"{rev}:{catalog fingerprint}"` at `:326`). Raising it rebuilds every projection.
    Any change to what `run-started`/`run-submitted` fold into transcripts/crowd/learner views needs a bump. The core has no such constant.

## 1. Schema (`🧬️schema/🔣️.json`, 1172 lines; twins `🧬️schema/🟦️.ts` 467 lines, `🧬️schema/🦀️.rs` 1113 lines) **[V]**

(`:6`). Object defs carry `"x-semio-formats": ["🔣️jsonschema","🦀️rust","🟦️typescript"]`, `additionalProperties: false`. Unions are

## 2. What the sheet reveals and hides today **[V unless marked]**

| Task kind | In the sheet (before submit) | Hidden until result | Where revealed |
|---|---|---|---|
| classification | task text, `axes`, **all categories with their `profile` values**, item `{id,label,icon}` | each item's correct `category`, `explanation` | `ClassificationItemResult.correct/credit/explanation` in `RunResult` |
| sorting | task text, `quantity {label, unit, scale, prefixed}`, item `{id,label,icon}` in shuffled order (never already ascending) | **every item's `value`**, `explanation`, true `rank` | `SortingItemResult.value/rank/explanation` in `RunResult` |
| matching | task text, dimensions with `quantity` and `cards` (the multiset of the drawn items' true values per dimension, shuffled), item `{id,label,icon}` | which card belongs to which item, `explanation` | `MatchingItemResult.correct` in `RunResult` |

- Verified in `🃏️sheet/🟦️.ts:30-50`: `sheetItem` copies only `id,label,icon`; sorting returns `quantity` and `items.map(sheetItem)`.
- The solution of a task is never a separate object: it is the quiz's own `Task` (items with `value`/`category`/`values`). It is
  revealed only inside `RunResult` once `run-submitted` (the `result` field of `RunView`, absent while open). `RunView.result` is set by
  `runView` from `found.result` (`👁️views/🟦️.ts:108`).
- **Leak paths for solutions** besides the result: (1) site `material` shipped to the web client for the deputy (README:489-528: "solutions
  included"; the proctor "still scores every run itself"), (2) the matching cards (numbers, not assignments), (3) crowd view after submit
  (aggregates only). `CatalogView` has no items at all (`catalogView`, `👁️views/🟦️.ts:45-53`).
- Sorting `guesses` are the learner's own numbers in the base unit, validated by `guessesFit` (`✅️validation/🟦️.ts:639-646`; Rust
  `answer_rejection` `🔨️modules/✅️validation/🦀️.rs:192-199`): keys are sheet items, values finite (and > 0 on a logarithmic scale), guessed
  items are in non-decreasing guess order within `order`. **Guesses never enter the score** (README:66-69, scoring code has no reference).
- **Interpretation of "keys" [I]:** since the sheet cannot show true values without handing over the solution, "sort keys shown" most likely
  means the *guess field* (the numeric key a learner types per item, shipped by ticket `QUIZ-SORTING-NUMERIC-GUESSES`, design in
  `.🧬semio/🦑️repo/🎫️tickets/🎆️26/🌙️10/☀️02/QUIZ-SORTING-NUMERIC-GUESSES/📓️design.md`), and "hard = keys hidden" means that field is not offered.
  If instead "keys" means true values displayed, the sheet/deputy contract has to change (and in `material` mode the client already has them).
- **A "hint when a guess is off by more than a factor 1000" needs the true value at decision time.** The decider has it
  (`context.quizzes[run.quiz].quiz`), the client normally does not. A pure `decideLearner` can only answer with events or a rejection
  (`Decision`, `🧾️lifecycle/🟦️.ts:20`); there is no reply payload. Hint delivery options **[I]**: an event (e.g. a hint fact folded into
  `RunState`, then exposed in `RunView`), a new rejection-like outcome, a new query, or computing it on the client from `material`. Each has
  different leakage: a hint whose condition is a pure function of (guess, hidden truth) leaks one bit per probe.

## 3. Scoring (`🔨️modules/📏️scoring/🟦️.ts`, `🦀️.rs`) **[V]**

Range and units: every task and dimension score is in `[0, 1]` (`Score`); a run score is the plain mean of its task scores in sheet order
(`scoreRun`, `📏️scoring/🟦️.ts:166-172`; Rust `score_run` `:40-50`). `mean([]) = 0` (`:50-52`). Perfect is exactly 1 (`concordance` returns
`1 - 0/total`, `:45-47`). Scores agree across cores within 1e-12 (only `log10` may differ by an ulp; README:155).

Entry points:
- `scoreTask(task: Task, sheetTask: SheetTask, answer: Answer): TaskResult | undefined` (`:157`) — `undefined` unless ids equal, `answerRejection(sheetTask, answer)`
  is undefined and `answerComplete` holds.
- `scoreRun(quiz: Quiz, sheet: Sheet, answers: Readonly<Record<string, Answer>>): RunResult | undefined` (`:166`) — scores each `sheet.tasks` entry; `undefined` if any is missing.
- Rust `score_task(task: &Task, sheet_task: &SheetTask, answer: &Answer) -> Option<TaskResult>`, `score_run(quiz: &Quiz, sheet: &Sheet, answers: &BTreeMap<Slug, Answer>) -> Option<RunResult>`.
- `scaled(value, scale)` = value (linear) or `log10(value)` (logarithmic) (`:40-42`).

Per kind:
- **Sorting** (`scoreSorting`, `:71-87`): over the learner's `order` (items resolved against the true task), for every pair `i<j`:
  `weight = |s(v[i]) - s(v[j])|`, `total += weight`, `if order[i].value > order[j].value: discordant += weight`;
  `score = total > 0 ? 1 - discordant/total : 1`. Result items: `{item, value, position (learner), rank (true ascending via ascendingItems; ties by definition index), explanation?}`. **`answer.guesses` is not read.**
- **Matching** (`scoreMatching`, `:90-114`): items in **sheet** order; per presented dimension: `truth[i]` true value, `assigned[i] = presented.cards[assignments[item.id]]`;
  `weight = |s(t_i) - s(t_j)|`; discordant `+= weight` when the order of `assigned` is opposite to the order of `truth`; `+= weight/2` when
  `assigned[i] === assigned[j] && truth[i] !== truth[j]`. Dimension score = concordance; task score = mean over dimensions.
- **Classification** (`scoreClassification`, `:127-154`): categories' profiles normalised `(v-min)/(max-min)` per axis (a profile missing an axis counts as no profile);
  `farthest` = max Euclidean distance over all profiled category pairs; credit = 1 if correct, else `max(0, 1 - d(assigned, correct)/farthest)` if both profiled and `farthest > 0`, else 0; task score = mean credit over sheet items.

Flow of the number after scoring:
- `submitRun` (`🧾️lifecycle/🟦️.ts:130-151`) -> `run-submitted { result }` event -> `evolveLearner` stores `result` in `RunState` (`:187-188`).
- `learnerView`/`bests`/`total` (`👁️views/🟦️.ts:73-95`): best score per quiz = max of `run.result.score` over submitted runs, `reachedAt` = `at` of the run that last
  raised any best; `total(best, catalog) = sum over catalog quizzes (catalog order) of best[quiz]*100` (`:85-87`). `LearnerView.total` is that sum.
- `transcript(state)` (`:120-128`) projects submitted runs to `TranscriptRun { quiz, score, at }` (`:56`) in submission order. **`TranscriptRun` is the only
  thing a standing sees; it carries no challenge or points.** `standing(transcript, catalog, scope)` (`:181-188`) filters runs by `BoardScope` (window, quiz), recomputes
  `bests`, `total`; `compareStandings` orders by `total` desc, badge count desc, `reachedAt` asc, learner id asc (`:191-193`); `leaderboard(...)` (`:196-212`) ranks, takes top
  `LEADERBOARD_TOP = 100`, counts `submissions = sum of transcript.runs.length`. Rust mirrors with `Merit { total, badges, reached_at }` (`👁️views/🦀️.rs:181-193`).
- Badges: `perfect-quiz` = some `result.score === 1` for the quiz; `perfect-tasks` = every selected task has some result with `taskResult.score === 1`; `completed-quizzes` =
  every catalog quiz has any result (`🏅️badges/🟦️.ts:9-22`). `earnedBadges(badges, quizzes, results, held)` consumes **`RunResult[]` only**, so it cannot tell levels apart
  today. Badge awards carry `run` so `TranscriptBadge.quiz` is derived by looking up the run (`👁️views/🟦️.ts:123-126`).
- Crowd: `scoreBin(score) = max(0, min(9, floor(floor(score*100 + 0.5) / 10)))` (`:235-237`), `crowdView(quiz, results)` bins `result.score` and each task's score; aggregates answer counts
  per category/value and normalized sorting positions (`:257-301`). It sees `RunResult` only (no challenge, no learner). The proctor keeps this incrementally in `CrowdTally`
  (`🎓️teaching/🛂️proctor/🔨️modules/👪️crowd/🦀️.rs`) and states it equals `quiz::crowd_view` bit for bit (header comment).

**Where a level multiplier or time component could plug in [I]:**
1. Score stays 0..1 and is *level-independent* (accuracy). Add a separate derived number, e.g. `RunResult.points` (or `challenge` + `points`), computed in `scoreRun` (or
   in `submitRun` right after it) as `round(score * 100 * multiplier(challenge))` and optionally a time term. Schema: `RunResult` (`:546-557`) gains optional/required `challenge`, `points`.
2. `TranscriptRun` (`👁️views/🟦️.ts:56`, Rust `:88`) gains `points` (and `challenge` if boards split by level); `bests`/`total` switch from `score*100` to `points`.
   Everything downstream (`LearnerView.total`, `LeaderboardRow.total`) is already a plain number `>= 0` (no upper bound in the schema: `"total": { "type": "number", "minimum": 0 }`).
   But `best: { quiz: Score }` (max 1) in `LearnerView`/`LeaderboardRow` would need a decision: keep as accuracy, or store points.
3. A time component needs a per-task anchor that the decider can trust (see section 4); the current `Timestamp at` per answer event is the only candidate.
4. Badges: `perfect-quiz` uses `score === 1`; decide if it should require a minimum challenge (rule field) — new `BadgeRule` fields mean schema + `badgeRule` validation
   (`✅️validation/🟦️.ts:366-375`) + Rust `BadgeRule` enum.

## 4. Lifecycle (`🔨️modules/🧾️lifecycle/🟦️.ts`, `🦀️.rs`) **[V]**

Signatures (TS):
```

evolveHandle(state: HandleState, event: Event): HandleState                                              // :75
decideLearner(state: LearnerState, command: Command, context: LearnerContext): Decision                   // :154
evolveLearner(state: LearnerState, event: Event): LearnerState                                           // :176
registrationRejection(learners: number, limits: Limits): Rejection | undefined                           // :59

type LearnerContext = { now: Timestamp; catalog: Catalog; quizzes: Readonly<Record<string, LoadedQuiz>>; limits: Limits }   // :29
type LoadedQuiz = { quiz: Quiz; revision: string }                                                       // :26
type RunState = { run, quiz, revision, seed, status, answers, recorded, result?, startedAt, submittedAt? }  // :32-43

```
Rust: `decide_handle(&HandleState, &Command, Timestamp) -> Decision`, `decide_learner(&LearnerState, &Command, &LearnerContext) -> Decision`,
`evolve_handle(&mut HandleState, &Event)`, `evolve_learner(&mut LearnerState, &Event)`; `enum Decision { Events(Vec<Event>), Rejection(Rejection) }`
(`🧾️lifecycle/🦀️.rs:25-28`); `RunState`/`LearnerState` derive `Serialize/Deserialize` with `deny_unknown_fields` (`:83-110`) because the proctor persists the folded
state (`Folded { seq, state: LearnerState }`, `🎓️teaching/🛂️proctor/🔨️modules/🔭️projections/🦀️.rs:94-98`).

Deciders per command (all start with `commandRejection(command)`, then `command.learner !== state.learner -> unknown-learner`, `:153-168`):
- **start-run** (`startRun`, `:102-113`): learner unregistered -> `unknown-learner`; quiz not loaded -> `unknown-quiz`; existing run id -> `run-open` | `run-closed`; open run of that
  quiz at the current revision -> `run-open`; `submitted.length >= limits.runs` or per-quiz `>= limits.runsPerQuiz` -> `runs-exhausted`; else
  `[run-started { learner, run, quiz, revision: loaded.revision, seed: runSeed(command.run), at: now }]`, prefixed by `run-voided` for a stale open run.
  **The command is not read beyond `run` and `quiz`.** The rule "at most one open run per learner and quiz" is `state.runs.find(run => run.quiz === command.quiz && run.status === "open")`.
- **record-answer** (`recordAnswer`, `:116-127`): `unknown-run`, `run-closed`, stale -> `quiz-revised`, `recorded >= answersPerRun` -> `answers-exhausted`; sheet rebuilt with
  `sheetOf(quiz, run.seed)`; task not in sheet -> `unknown-task`; `answerRejection(sheetTask, answer)` -> `answer-invalid`; else `[answer-recorded { learner, run, task, answer, at: now }]`.
  Latest answer per task wins in the fold. No time check whatsoever.
- **submit-run** (`submitRun`, `:130-151`): `unknown-run`, `run-closed`; stale -> `[run-voided]` (not a rejection); sheet rebuilt; any `!answerComplete` -> `run-incomplete`;
  `scoreRun(...)` undefined -> `run-incomplete`; badges via `earnedBadges(context.catalog.badges, quizzes, results, held)`; events `[run-submitted { result, at }, ...badge-awarded]`.
- **identify-learner** (`register` for anonymous, `decideHandle` for pseudonym/name) — unrelated to runs.

Folds (`evolveLearner`, `:176-192`): `run-started` pushes `{ run, quiz, revision, seed, status: "open", answers: {}, recorded: 0, startedAt: event.at }` (no challenge),
`run-voided` sets status, `answer-recorded` replaces `answers[task]` and `recorded += 1` (**the event's `at` is discarded**), `run-submitted` sets `status`, `result`, `submittedAt`,
`badge-awarded` appends `{ badge, run, at }`.

**Time in the core:** `Timestamp` = integer ms since the Unix epoch. `now` is supplied by the caller: proctor HLC millis (`🎓️teaching/🛂️proctor/🔨️modules/🎭️actors/🦀️.rs:335,370`),
the deputy's device clock (`🫡️deputy/🟦️.ts:118`, "decides `command` at `now`"). Stored per run: `startedAt`, `submittedAt`. Everything else with time is read-model windows
(`periodWindow`, `👁️views/🟦️.ts:146`). **There is no duration, deadline, per-task start, pause, or clock-skew handling.** The deputy case makes a client-decided deadline provisional
by definition ("the proctor decides every delivered command again with the same deciders, and its verdict is the one that counts", README:512-516), so an expert timer enforced in
`decideLearner` would be re-judged by the proctor with *its* `now` (later, because of delivery delay) and could contradict the device. A deadline defined in terms of event `at`s
that the proctor stamps is consistent only if the proctor is online. This is a real design constraint **[I]**.

**Seeds/randomness (MT19937)** **[V]**: `runSeed(run) = fnv1a32(run)` (`🎲️randomness/🟦️.ts:26`), stored in `run-started.seed`; `sheetOf` creates `new Mt19937(seed)`, shuffles the task index
list, keeps task 0 first (`order = [0, ...shuffled.filter(i => i !== 0)]`), then **presents every task in definition order consuming the generator** (`🃏️sheet/🟦️.ts:52-59`):
classification: `shuffle(items)` then `drawn(draw)`, then `shuffle(categories)`; sorting: `shuffle(items)`, `drawn`, then if already ascending (value, tie by definition index) rotate left by one;
matching: `shuffle(items)`, `drawn`, then per dimension in definition order `shuffle(cards)` where `cards` are the drawn items' values for that dimension (NaN if missing).
The consumption order is normative (Rust comment `🃏️sheet/🦀️.rs:3-8`). `uniformIndex` rejection-samples below `2^32 - (2^32 mod n)`, `n <= 1 -> 0` with no draw (`🎲️randomness/🟦️.ts:70-77`).
**Consequence:** a challenge-dependent sheet must not change the number or order of generator draws for the same `(quiz, seed)` unless that is intended and all vectors
(`🧫️fixtures/🃏️sheet-assembly`, `🧫️fixtures/🎲️seeded-randomness`, the Python reference, `numpy` oracle) are regenerated.

**Existing "mode" precedents [V]: none per run.** Candidates considered: `draw` (static per task in the quiz doc), `Limits` (proctor-wide), `Place` (ephemeral presence),
client preferences `others` (`never|submitted|always`) and `pets` (README:347, 439-456). None of them is carried by a command or an event. The nearest *shape* to copy for a
run-level attribute is `revision` (`run-started.revision`, stored in `RunState.revision`, used by `stale()` at every later decision).

## 5. TS <-> Rust twin conventions and lockstep **[V unless marked]**

- Every module has `🟦️.ts` and `🦀️.rs` side by side; `📦️packages/🟦️typescript/🟦️.ts` is `export *` over schema + randomness, sheet, validation, scoring, badges, lifecycle, views, presence
  (9 lines) and `📦️packages/🦀️rust/🦀️.rs` wires the same files with `#[path]` mods (36 lines) plus the root `🦀️.rs` that `pub use crate::{badges,lifecycle,presence,randomness,schema,scoring,sheet,validation,views}::*`.
  Adding a *module* means adding it in three places (TS barrel, Rust `#[path]`, root `🦀️.rs` re-export) and `📋️project.json` namedInputs if the glob does not cover it
  (`📦️packages/🟦️typescript/📋️project.json` lists `🧬️schema/**/*`, `🔨️modules/**/🟦️.ts`, `🧪️tests/**/🟦️.ts`, `🧫️fixtures/**/*`). Adding a *field/type* needs no glue change.
- Naming: TS `camelCase` functions (`sheetOf`, `scoreRun`, `decideLearner`), Rust `snake_case` (`sheet_of`, `score_run`, `decide_learner`). Types identical names. Event/command tags
  kebab-case on the wire; Rust enum variants PascalCase with `#[serde(rename_all="kebab-case", rename_all_fields="camelCase")]`.
- Rust unit tests live in `🔨️modules/<m>/🧪️tests/🔬️unit/🦀️.rs`; TS unit suites and Protocol v2 cases in `🧪️tests/<case>/` (`🟦️.ts`, `🥒️.feature`, `🐍️.py`, `🦀️.rs`). 13 cases have a Python
  reference: answer-validation, sheet-assembly, seeded-randomness, badge-rules, leaderboard, shared-presence, crowd-view, sorting-concordance, matching-concordance, profile-similarity,
  schema-conformance, learner-lifecycle, identity-shapes. Shared vectors `🧫️fixtures/<case>/🔣️.json` are **generated** from those Python references (header `$comment`: "never edit by hand"). Fixtures
  that contain `start-run`/`run-started` (these break when the shapes change): `🧫️fixtures/🏆️leaderboard` (25 hits), `🧾️learner-lifecycle` (39), `🪪️identity-shapes` (12).
- **Validators are not symmetric**: TS `quizIssues(quiz: unknown)` walks untyped JSON (`✅️validation/🟦️.ts:350`), Rust `quiz_issues(quiz: &Quiz)` takes the typed value (`🦀️.rs:123`) because serde
  already enforces structure (`deny_unknown_fields`). Any new quiz/catalog member needs: schema, TS `object(...)` allow-list in the matching validator function, TS type, Rust struct field.
  `commandRejection` TS is generic over member names (`["id","learner","run"]` must be ids; `["quiz","task"]` must be slugs; `✅️validation/🟦️.ts:489-494`), Rust matches the enum
  variant explicitly (`🦀️.rs:234-242`). **A new command member (`challenge`) is not validated by TS `commandRejection` at all** and is only enforced in Rust by serde (unknown enum value =
  deserialization error, not a `Rejection`). To get the same behaviour in both cores, validate it explicitly in `commandRejection` (TS + Rust) or in `startRun` and pick the rejection.
- Things that must change in lockstep when a rejection is added: `🧬️schema/🔣️.json:666-687` enum, TS `REJECTIONS`, Rust enum + `as_str`, README table (:172-197), React
  `quiz.rejection.*` phrases + translation-completeness test, `🎓️teaching/🛂️proctor/README.md:353` list, Python `learner-lifecycle/🐍️.py:488` area, lifecycle unit tests.
- Revision constants: **quiz core has none**. The proctor has `PROJECTOR_REVISION = 5` (`🎓️teaching/🛂️proctor/🔨️modules/🔭️projections/🦀️.rs:89`), stamped with the catalog fingerprint; the quiz
  *revision* (`LoadedQuiz.revision`) is SHA-256 of the quiz file bytes, so editing a quiz document voids open runs (`stale`). Adding a field to a persisted shape that the projector folds
  (`RunState`, `Transcript`, `Standing`, `CrowdTally`) requires bumping `PROJECTOR_REVISION`. Rust persisted structs are `deny_unknown_fields`, so old snapshots would fail to decode anyway
  (greenfield: acceptable per AGENTS.md; bump anyway so the stores rebuild).
- Taxonomy/member lists: `x-semio-formats` markers on each object def (add them to any new object def); enumerations are re-stated as `as const` arrays in TS (`TASK_KINDS`, ...) and the
  validator has its own literal lists (`BADGE_RULE_KINDS`, `IDENTITY_KINDS` in `✅️validation/🟦️.ts:77-80`). A new `CHALLENGES`/`Challenge` enum follows the `Scale`/`SCALES`/`Scale` pattern:
  schema enum def, TS `export const CHALLENGES = [...] as const` + `type Challenge`, Rust `enum Challenge` kebab-case, and a validator literal check.

### Open questions the code cannot answer (for the design, not the code)
1. Does a run get its level at `start-run` (immutable for the run) or per task? The code supports only run-level cheaply.
2. May a learner have one open run per quiz per level, or still one per quiz (`startRun` checks `run.quiz === command.quiz && status === "open"`, `:107`)?
3. Do the four levels share one leaderboard (points) or split per level? `Leaderboard` and `Query.leaderboard` have no level; all the "best per quiz" logic assumes one number per quiz.
4. Hint source: event-sourced fact, query, or client-side from `material`. Pure deciders return no payload (`Decision`).
5. Timer authority: the proctor's `now` vs the device's (deputy), see section 4. With `record-answer` the only timestamp is the decision time of that command, not the time the learner saw the question.
6. `answerRejection(sheetTask, answer)` has no run context; hiding keys (no `guesses`) requires either a field on the sheet task or a new argument.
