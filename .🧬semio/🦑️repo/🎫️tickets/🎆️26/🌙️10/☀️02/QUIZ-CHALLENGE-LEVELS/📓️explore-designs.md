## 0. The ten things to know first

1. **There is no earlier intent about levels, timers, hints or bonus points anywhere** [R] (searched all quiz ticket folders, the `💡️ideas`, `✍️notes` and `💬️prompts` of `🦑️repo`, the teaching and quiz READMEs; details in section 5). The only literal hit is a *negative*: the schema-conformance vector `undeclared-member` adds `"difficulty": "hard"` to a Quiz and expects it to be **rejected** (`Q/🧫️fixtures/🧬️schema-conformance/🔣️.json:826`, produced by `generate_quiz_vectors.py:1189`). Adding a `difficulty`/level member to `Quiz` flips that vector; the generator line and the fixture must change in the same stroke.
2. **Every sheet is solution-free by contract** [R]: `PD §4` "Sheet items carry only `{ id, label }`" (now also an optional `icon`), `R:3` "seeded solution-free sheets", schema `Sheet` ("The solution-free presentation of a quiz"), `RunView.result` only when submitted (audit R6 in `PD`-folder `📓️audit-final-requirements.md`). "Keys/values visible" for easy and medium sorting is therefore an explicit **supersession** of §4, of the README, of the schema description and of the sorting results semantics (the "Value" column exists only after submission). The **deputy** already holds all solutions in the site script (split-deploy design, decision 2), so it needs no new secret, but the proctor-served `RunView.sheet` does.
3. **`Score` is a number in [0, 1] and "perfect" means exactly 1** [R] (`Score` `$def`; `R:162` `perfect-quiz` "some result of the quiz scored 1"; `PD §7`). `scoreBin`, `LearnerView.best`, `RunSummary.score`, the crowd bins and all seven badges rest on it. "Harder levels earn more points" therefore cannot be a multiplier folded into `score` without breaking the schema, badges and bins [I]; points need their own quantity. Today `points` is only `score × 100`, unrounded: `LearnerView.total` and `LeaderboardRow.total` = sum over catalog quizzes of the *best* score × 100 (`Q/🔨️modules/👁️views/🟦️.ts:84-86`) [R]; the 4-quiz maximum is 400.
4. **Retakes: unlimited, the best run per quiz counts** [R]. Catalog intro: "you may repeat a quiz as often as you like; your best run counts"; "The leaderboard ranks everyone by the sum of their best quiz scores" (site catalog `🔣️.json`, introduction paragraphs 2 and 5); `quiz.quizPage.hint` ("Your best run counts", `QR/🔨️modules/🌐️i18n/🟦️.ts:216`). Caps: 1 000 submitted runs per learner, 200 per quiz, one open run per learner **and quiz** (`R:205-207`). A level must define whether "best" and "one open run" are per quiz or per (quiz, level) [I].
5. **Guesses never change a score** is a normative rule with a test: `QUIZ-SORTING-NUMERIC-GUESSES/📓️design.md` "Guesses never enter scoring"; `R:68`; `Q/🧪️tests/⚖️partial-credit-scoring/🟦️.ts:107` ("scores the order alone: guesses, right or wrong, change neither the score nor the item results"). A "hard" level in which the learner *must guess* and the guess is *judged* supersedes this rule in the design, README, schema text, TS/Rust/Python scoring, vectors and that test [I].
6. **Only two sorting tasks exist in the whole catalog** [R] (`powers` 14 items draw 10, `energies` 12 items draw 9, both `logarithmic`, `prefixed: true`, both in physics). The other seven tasks are matchings (all dimensions logarithmic) and two classifications. So "sorting levels" touch two tasks; the rule set for matching and classification is where most of the catalog needs a decision [R: scan of the four quiz files].
7. **No time exists in the domain except decision timestamps** [R]: `Timestamp` ms in events (`at` = `DecisionContext.now`, `PD §8`), `reachedAt`/`lastActivity` on the leaderboard, `DEPUTY_PATIENCE_MS` = 3 s. `Command` has **no** timestamp field (schema `Command`: `identify-learner`, `start-run`, `record-answer`, `submit-run`, each with only `id`, ids and payload). With the offline deputy the proctor re-decides on delivery "with the proctor's clock" (`R:514-517`), so `answer-recorded.at` is delivery time, not answer time. Server-verifiable per-question timers for "expert" need a client time on the command or a new "question opened" event [I].
8. **The crowd gate is client-side** [R] (crowd-plots report, decision "The gate is client-side"; `PD §20`): `quiz.crowd` is an open read and the thinking room publishes a learner's drafts (including sorting `guesses`) to peers regardless. For hard/expert, "others' answers" are one tap away ("Show it now") unless the level also closes that gate [I].
9. **Two other sessions are editing the exact files a level touches, right now** [R]: `QUIZ-ADAPTIVE-LAYOUT` (open; staged + unstaged edits to `▶️run`, `↕️sorting`, `🃏️matching`, `🗂️classification`, `🏁️results`, `🗳️crowd`, `🏆️leaderboard`, `🪟️chrome`, `🎨️.css`, last write 23:46) and `QUIZ-PETS` round 2 (open; its `📓️design-v2.md` §22 plans `data-pet-prop` on run items and results rows, preferences and i18n additions, and edits to the pets schema/validation, last write 23:52). Section 4 has the file map.
10. **Stale documents to be aware of** [R]: `R:96-98` still says "The task order is shuffled first", but `sheetOf` keeps the first task first (`Q/🔨️modules/🃏️sheet/🟦️.ts:55-61`; schema `Quiz`/`Sheet` descriptions say so; `PD §4` step 2 too is superseded without a note). `PD §14` names the site host `quizzes.…`; the split-deploy design (same day) re-targets to `quizze.architektur-und-technologie.de` (site) and `semio.iek.uni-hannover.de` (proctor) without annotating §14. Also "level" is overloaded in this repo: test levels (`test-quick|long|exhaustive`, `🛂️proctor/README.md:284`), design-system `WindowChrome level="dialog"` (`PD §14`), and the icon `Motion` enum; name new things `challenge…`, not `level…`/`motion…` [I].

## 1. Digest of design decisions that a challenge-level design must respect or supersede

Sources: `PD` = `📓️design.md` of `QUIZ-PRODUCT-AND-TEACHING-PROCTOR` (587 lines, §1–§20); `PL` = `QUIZ-PERIOD-LEADERBOARDS/📓️design.md`; `SG` = `QUIZ-SORTING-NUMERIC-GUESSES/📓️design.md`; `SD` = `QUIZ-POC-DEPLOY-BUNDLE/📓️split-deploy-design.md`; `CP` = `📓️crowd-plots-report.md`; `TI` = `📓️task-icons.md`; `NN` = `QUIZ-NAVBAR-NAVIGATION/📓️navbar-navigation-report.md`; `AFR` = `📓️audit-final-requirements.md` (the requirement table R1–R15 and notes N1–N7).

### 1.1 Scoring

1. **Task score in [0, 1]; run score = mean of task scores in sheet order** (`PD §6` l.85; `R:115`). `s(v)` = `v` (linear) or `log10(v)` (logarithmic; values must be > 0, else a validation issue).
2. **Sorting = magnitude-weighted pair concordance** (`PD §6` l.87-94): for `i < j` over the learner's order: `w = |s(v[o_i]) − s(v[o_j])|`, `total += w`, `discordant += w` if `v[o_i] > v[o_j]`; `score = total > 0 ? 1 − discordant/total : 1`. Verbatim: "Swapping near neighbours costs little, swapping a tea light and a nuclear plant costs a lot; perfect = 1, reversed = 0." Unit weights give `(1 + τ_a)/2` (scipy `kendalltau`), equally spaced ranks on a linear scale give `(1 + ρ)/2` (jStat/scipy). "(Corrected 2026-09-28: the earlier 's = rank ⇒ Kendall' claim is false for n ≥ 3.)"
3. **Matching** (l.95-98): per dimension, `a_i` the value of the assigned card, `t_i` the true value; discordant weight `w` if `sign(t_i − t_j)·sign(a_i − a_j) < 0`, half (`w/2`) if `a_i == a_j` and `t_i ≠ t_j`; task score = mean over dimensions in definition order.
4. **Classification** (l.99-102): credit 1 if correct, else `max(0, 1 − d(assigned, correct)/d_max)` over normalised axis profiles when both categories carry profiles, else 0; `d_max = 0 → 0`; score = mean credit.
5. **Rounding and parity** (l.106; `R:146-155`): cores agree within `1e-12` ("log10 may differ by one ulp"); "Perfect is exact (`discordant == 0`)"; scoring "never throws and never yields NaN on inputs that bypass validation" (`scoreTask`/`scoreRun` → `undefined`/`None`, mean over nothing 0, incomplete → `run-incomplete`). No score rounding anywhere in the core; display rounding only: `scoreBin(score) = min(9, ⌊points/10⌋)`, `points = ⌊score·100 + ½⌋` (`PD §20`); `formatScore`/`formatPoints` in `QR/🔨️modules/📏️quantity`.
6. **Results shape** (l.103-105): classification items in sheet order (`assigned`, `correct`, `credit`, `explanation`); sorting items in the learner's order (`value`, `position`, `rank`, `explanation`); matching per dimension in sheet order. Results exist only in `run-submitted`/`RunView.result`.
7. **Guesses never change a score** (`SG`, `R:68`, test above). `SortingItemResult` has no guess; the results table gets a "Your guess" column from the stored answer (`QR/🔨️modules/🏁️results/🟦️.tsx:105-123`).
8. **Why large misorders cost more** (`R:134-144`): the owner's request was "partial-credit scoring with rank-distance metrics for numerical sortings" (ticket description of `QUIZ-PRODUCT-AND-TEACHING-PROCTOR`; audit R7 "sophisticated metric punishing large misorders for numeric sortings"). Any level-dependent scoring must keep this metric as the base [I].

### 1.2 What a learner may see before submission (sheet secrecy, solutions, crowd gates)

9. **Sheet** (`PD §4`; `Q/🔨️modules/🃏️sheet/🟦️.ts`): `sheet(quiz, seed)` is a pure function of `(quiz, seed)`; sheet items `{ id, label, icon? }`; classification categories travel whole (axes, profile? **categories are copied "unchanged" including their profile**, only items lose their category); matching **cards are the multiset of the drawn items' true values** per dimension (shuffled) – so matching already shows its values, just not who owns which [R: `sheetTask` matching branch; `R:69-70`]; sorting sheet items carry no value.
10. **Results only after submit** (audit R6 [R]): submit is `aria-disabled` until every task is complete, `run-incomplete` otherwise; "no per-task feedback in the task views"; run view carries `result` only when submitted; learner view `score` only when a result exists. Hence "hint when off by more than a factor 1000" (easy) is new per-answer feedback during a run: it breaks "no per-task feedback" and must be specified as a pure function of (sheet values, guess) shown with no score effect [I].
11. **Others' answers** (`PD §20`, `CP`): preference `others: never | submitted | always` (default `submitted`); `crowdGate(others, place, { asked, submitted })` → `open | asked | locked | off`; in a run the others are `locked` until "Show it now" (ephemeral local-only `QuizState.asked`, ends with the run). "**The gate is client-side.** The learner may ask for the distribution at any time, so the proctor has nothing to withhold; `quiz.crowd` stays an open read." Live drafts keep being published to the thinking room (`ThinkingState { tag, answers }`, ≤ 2 Hz, bounded by `THINKING_LIMIT` = 64) – `PD §17`, decision "a learner's answers are still shared live; who sees them is decided on the viewer's side".
12. **Deputy trust** (`SD` decision 2): "Solutions travel in the site's scripts with this. That is inherent to scoring without a server; the proctor still scores every run itself, so the leaderboard never trusts a device."
13. **Seed trust** (`AFR` N2): the run id is client-generated, `seed = FNV-1a(run id)`; "a modified client can grind run ids for an easy draw. Same trust model as the password-less identity; low for a fun leaderboard". A level that raises points makes grinding more valuable [I].
14. **Presence** (`PD §15`, §17): drafts, cursors and drags are shared; "presence reveals no answers" was the §15 rule, **superseded in §17** ("This supersedes the §15 rule 'never share answers or drags'"). Pets "rest" during a run (`R:463-466`), icons never give an answer away (`R:82`, `TI`).

### 1.3 Run lifecycle and retakes

15. **Deciders** (`PD §8`, `R:167-207`): `start-run` rejects `unknown-learner`, `unknown-quiz`, `run-open` (open run at current revision), `runs-exhausted`; open run at a **stale revision** → `run-voided` + `run-started`; revision = lowercase hex SHA-256 of the quiz file bytes as loaded by the proctor (`PD §2`). `record-answer`: `unknown-run`/`run-closed`/`quiz-revised`/`answers-exhausted`/`unknown-task`/`answer-invalid`; "the latest answer per task wins". `submit-run`: stale → `run-voided`; incomplete → `run-incomplete`; else `run-submitted { result }` then `badge-awarded` per new badge. Commands idempotent by command id. `start-run` = `{ id, learner, run, quiz }` (schema) – **no room for a level yet**; `run-started` = `{ learner, run, quiz, revision, seed, at }`.
16. **One open run per learner and quiz; no abandoning** (`R:207`; `AFR` N5: "an open run cannot be abandoned … a new random draw needs a submission first, or a quiz revision"). Retakes after submission are free; each run is a new random draw (`quiz.quizPage.hint`).
17. **Which run counts**: the best submitted score per quiz (`LearnerView.best`, "Best submitted score per quiz id"); leaderboard rows are built from the transcript's submitted runs in scope (`PL §3`).
18. **Revision and levels** [I]: adding level data to the quiz *files* changes every quiz revision, which voids every open run at deploy (stale revision rule). Keeping level rules in code/catalog and not in the four quiz files avoids that.

### 1.4 Leaderboards (rows, `score`/`points`, periods)

19. **Row fields** (`LeaderboardRow` schema; `R:237-268`): `rank`, `tag` (FNV-1a of the learner id, 8 hex – the id is never public), `identity`, `total`, `reachedAt`, `best` (score per quiz), `badges`, `runs`, `lastActivity`. Order: `total ↓`, badge count `↓`, `reachedAt ↑`, learner id `↑` (`compareStandings`; `views/🟦️.ts:190-192`). `total` = sum of best scores in **points (score × 100)**, one quiz's best × 100 on a board of one quiz (UI label "Points" instead of "Total").
20. **Leaderboard view** (`PD §18`, `PL §2`): `Leaderboard { period, quiz?, window?, rows ≤ 100, learners, submissions, own? }`; query `{ type: "leaderboard", period, quiz?, learner? }`. `submissions` = runs submitted in the whole catalog, used as the crowd-refresh trigger.
21. **Periods** (`PL §1`): calendar windows in UTC (day, ISO week from Monday, month; all-time none), half-open `[from, until)`; "Same board for every viewer wherever they are, a pure function of `(events, instant)`, no time-zone database"; ranked **in the proctor per (period, quiz)** with a compact rank index (Rust `Merit`, 32 bytes per learner and board); one board per query. Adding level as a third board dimension multiplies indexes and queries [I]; rank by "points" would need `Merit` to hold them.
22. **Transcript** (`PL §3`, `R:247-256`): per learner the submitted runs in order (`quiz`, `score`, `at`) and the badges (`badge`, `quiz`, `at`); a standing is made of runs in scope; changes only on submit/badge/identity, never on answers. A level on a run needs to enter the transcript (hence `PROJECTOR_REVISION` bump) [I].
23. **Projector revisions** (`PD §20`): "`PROJECTOR_REVISION` 5 rebuilds the read models (4 was taken by the leaderboard periods the same day); the storage format stays v2." Next free number is 6 [R/I]. Storage format v2 "refuses v1 files (no migration)" (`PD §18`) – consistent with the AGENTS rule of no migrations.

### 1.5 Badges

24. **Rules** (`PD §7`, `R:157-165`): evaluated after every submission in catalog order over all submitted results of the learner including the new one; held badges skipped; award records the run and time. `perfect-quiz { quiz }` (some result has score 1), `perfect-tasks { taskKind?, quiz? }` (every matching catalog task has score 1 in some result; a selector matching no task never awards, issue `badge-unreachable`), `completed-quizzes`. Site catalog: `physics/heating/cooling/demand-expert` (perfect-quiz), `numerical-brain` (perfect-tasks sorting = the two physics sortings), `pattern-seer` (perfect-tasks classification), `completionist` (completed-quizzes). `numerical-brain` deliberately covers sorting only (`AFR` N3).
25. [I] With levels, a perfect easy run would award every "expert" badge unless the rules gain a level condition; rule evolution is a schema change (`BadgeRule` is a closed `oneOf`, so a new member is also a Rust/TS/validation/vector change).

### 1.6 Identity, threat model

26. **No passwords, by the owner's decision** (`PD §18`): a pseudonym or name is public and the only thing needed to continue as that learner; the learner id is a bearer credential and appears in no public payload. Handles normalized by the server (Latin alphabet, 1…64 code points); recall is a read, not an event; "Protection goal: a single script can neither read credentials, nor take the service or the host down, nor lock real learners out. A lecture hall of about 300 learners behind one NAT address must never be throttled." Consequence for levels [I]: points and badges stay "for fun"; no anti-cheat beyond what the proctor recomputes.

### 1.7 Offline deputy (`SD`, `R:489-528`)

27. The device runs the **core's own deciders** with the site's material (catalog + quizzes with solutions). A command goes straight to the proctor while it answers and nothing the deputy decided waits; otherwise the deputy decides, folds events into the held views, and the command waits in the outbox (all command kinds, in order, answers coalesced per run and task, delivery sequential under the command id). Everything decided by the deputy is **provisional**: the proctor re-decides with the same deciders and "its verdict is the one that counts" (its clock, its score). A handle already claimed → the device continues as the holder; a run the proctor will not start is voided on the device. "A learner waits `DEPUTY_PATIENCE_MS` (3 s) for the proctor's own decision."
28. Implication for levels [I]: every level rule must live in the shared core (TS+Rust twins, Python reference) so `learnerStateOf(...)` and the deputy decide as the proctor does; a sheet that is not the one the material deals for its seed marks a revised quiz and **voids** the run (`R:512-513`) – so the level must be part of what the sheet function takes or of the run record the material re-derives.

### 1.8 Wire mapping and projector (`PD §9a`)

29. `CommandEnvelope.kind` = `quiz.<Command.type>` (`quiz.start-run`), `version` 1, `commandId` = `idempotencyKey` = `Command.id`; target `{ tenant: <catalog id>, kind: "quiz-learner", id: <learner> }` (handle commands: `quiz-handle/<hex>` stream, `PD §18`); `payload` = UTF-8 bytes of the `Command` JSON; `EventRecord.kind` = `quiz.<Event.type>`; `QueryEnvelope.kind` = `quiz.<Query.type>`; `QueryResult` = snapshot bytes of the view JSON; a rejection carries the quiz `Rejection` string. Edge: request body ≤ 16 384 bytes (largest real command 2 952, `PD §18`) – a level field costs nothing; answers with guesses are the largest.

## 2. Sorting numeric guesses — in detail, and what it means for "hard"

Source `SG` (`QUIZ-SORTING-NUMERIC-GUESSES/📓️design.md`, ticket closed 2026-10-02; verified end to end by `TEACHING-ARCHITECTURE-DEPLOY-READY`: unit tests 640/297, parity 108/108, e2e 36/36, staged site in Chromium: both physics sortings ordered by typed guesses alone, 100 %).

### 2.1 Contract (schema-first) [R]
- `SortingAnswer { kind: "sorting", order: Slug[], guesses?: { <item id>: number } }`; guess in the quantity's **base unit, never SI-prefixed**, "positive on a logarithmic scale". Schema text: "Items with a guess stand in `order` in ascending guess order; an item without a guess has none."
- Rules, enforced identically by TS and Rust twins and a Python reference (`Q/🧪️tests/✅️answer-validation/🐍️.py`, shared vectors): (1) keys name sheet items, values finite, positive on logarithmic scale; (2) the guessed items appear in `order` in **non-decreasing guess order** (ties allowed; unguessed unconstrained) – "So an answer can never show a guess that contradicts its order" (`guessesFit`, `Q/🔨️modules/✅️validation/🟦️.ts:638-645`; an invalid fit → `answer-invalid`).
- **Guesses never change a score**; `SortingItemResult` carries `item`, `value`, `position`, `rank`, `explanation?` only.
- **Thinking drafts** (`ThinkingAnswer` sorting) may carry `guesses`: finite numbers, ≤ `THINKING_LIMIT` (64) entries, no cross-field rule (`thinkingProblem`, `too-many`/`duplicate-id`/`type-invalid`; `Q/🔨️modules/✅️validation/🟦️.ts:602-618`).
- A guess counts as an answer ("keep this order" no longer needed once something is guessed).

### 2.2 Parsing (`QR/🔨️modules/📏️quantity`, `parseQuantity`) [R]
Inverse of `formatQuantity`: number with optional exponent, optional SI prefix and unit (`2 kW`, `5 M`, `3,5 MWh`, `1e3 kW`); locale decimal mark; a lone `.`/`,` elsewhere is a decimal mark unless it groups three digits; spaces/apostrophes group by three; **prefix case-sensitive** (`mW` ≠ `MW`), unit case-insensitive, `u` reads as `µ`, `K` as `k`; value assembled as `Number("<digits>e<exp>")` so `1.5 kW` is exactly 1500. Oracles: `Intl.NumberFormat` round trips (`🧫️fixtures/📐️quantity-formatting`).

### 2.3 Interaction (`QR/🔨️modules/↕️sorting/🟦️.tsx`, read in full) [R]
- Per item a text field "Guess for <item>" (`quiz.sorting.guess`), placeholder "e.g. 2 kW" (`exampleGuess`: `2` + `k`unit if prefixed), preview `= 500 kg` of what the text reads as (`formatQuantity` with the best SI prefix), `aria-invalid` + `role="alert"` for unreadable text (positive-only message on logarithmic scales).
- Commit on Enter or blur; unchanged text does not re-commit (a rounded display must not overwrite an exact guess); Escape reverts. Reordering only on commit, via `ordered(order, guesses)`: guessed items sort by guess (stable) **among the places they occupy**, unguessed items stay. Focus follows the field (Enter) or the control tabbed to.
- Moving a guessed item by hand (buttons/drag) **drops that guess** (`without(guesses, id)`), announces "moveClears". Clearing the text removes the guess.
- Copy: `quiz.sorting.hint` "Order the items by {{quantity}}: smallest at the top, largest at the bottom."; `guessHint` "Optional: type your guess … Items with a guess order themselves by it; moving an item by hand removes its guess."; `keepHint` "The order counts once you move an item, guess a value or keep the current order."
- Results: sorting result table columns: position, item, **Your guess** (only when any guess; "No guess" mark for the rest), value, rank, explanation (`QR/🔨️modules/🏁️results/🟦️.tsx`).

### 2.4 What this implies for the levels [I unless marked]
- **Today's sorting experience is already close to "hard"**: the sheet shows labels only (no values), and typing a numeric guess is optional and unscored. "Hard = keys hidden, learner guesses" is the existing UI with guesses promoted from optional-and-unjudged to the expected way of working; if guesses must become *required* or *judged*, the `answer-invalid` rules (`guessesFit`), `answerComplete` ("a recorded sorting always [complete]"), scoring, results and the thinking-draft rule all change, in both cores and the Python reference.
- **Easy/medium ("keys visible")**: needs the sorting items' values on the sheet. That changes `SheetItem` (or `SheetSortingTask`), the sheet function (`sheetOf(quiz, seed)` → also takes the level or a level-specific projection), the deputy equivalence check, the Python `sheet-assembly` oracle and the `🃏️sheet-assembly`/`🎴️sheet-randomization` fixtures. Matching already shows its value cards; "keys" for a matching would have to mean something else (the dimension values on the items?) and needs its own definition.
- **Easy hint "off by more than a factor 1000"**: expressible exactly on `logarithmic` quantities as `|log10(guess / value)| > 3`; on a `linear` scale a ratio is not defined for ≤ 0 or mixed-sign values, and both existing sorting tasks are logarithmic. It uses a guess in the base unit, which the contract already provides; it needs the true value on the device (fine on easy where values are visible; on any level the deputy has them). A hint must not alter the score and should not be a live region (the crowd figures follow the same "never a live region" rule, `R:356-358`).
- **Guesses and peers**: guesses are broadcast in thinking drafts; on hard/expert this leaks a learner's reasoning to anyone who asks to see the crowd, but shows nothing about the true values – acceptable, but the level design should say so.
- **The magnitude weighting is the point of the metric**: with guesses visible/typed, the rank-distance score still measures order only; a "guess accuracy" score would be a second, new metric that needs an oracle (e.g. `|log10(guess/value)|` against `numpy`) per the AGENTS rule "same output with at least one third-party library".
