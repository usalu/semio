# Declared Cargo Artifact Acquisition Contract

## Concrete Source checkpoint

The initial closed schema and nine request vectors live at repository library `🏃️process/🦀️cargo/📦️acquisition/{🧬️schema/🔣️.json,🧪️tests/🔣️.json}`. They are descriptive DATA, not issued authority. Requests name an actual project/target/configuration and bounded executable arguments; caller manifest, output, program, capabilities, unknown modes, chained targets and NUL arguments are refused. The repository-owned target declaration names a project-relative manifest, Cargo package and executable. No production issuer or gateway wiring has changed.

## Genuine issuing path

`build/📜️script.ts` creates fresh native build caller capabilities before its Original envelope. `build/📥️caller/📤️child/🟦️.ts:createBuildBootstrapCapabilitiesV1` validates the closed operation catalog. `build/📥️caller/🟦️.ts:buildTaskEnvironmentV1` authenticates the actual build Original and canonical artifact authority. Its orchestration variant additionally requires a privately bound task context from the actual pinned graph and checks reachability and execution equality. These checks must remain; caller project strings or task environment variables cannot replace them.

The Cargo launcher currently accepts only compile/resolve/lock requests and has no qualified target acquisition contract. The fresh Cargo issuer can be reused only after it resolves the real declaration and issues a genuine child task context; passing the DevScript Original directly is insufficient. The existing non-Nx Bazel task executor provides the receipt lifecycle reference: actual target/root/outputs enter issueStoreReceiptV1, then settlement after execution. The helpers do not themselves confer Native authority.

## Publication and consumption

The normal MCP BuildScript omits `output`, so the Core publishes under Native `published(manifest,mode)`. The warm consumer still names `dist/build`; this is a genuine disconnected default. Its regression is independently owned by frontend. Acquisition must produce through the existing plan/compiler path, preserve declared StoreReceipt publication, release compiler lane/CPU custody before long-running consumption, and open the qualified published executable under actual store/artifact read custody. No raw output/path fallback is acceptable.

The actual StoreReceipt environment key is schema-owned `SEMIO_TASK_RECEIPT`; no literal `SEMIO_STORE_RECEIPT` exists in the current contract. `recordStoreContentV1` requires actual task project/target when that key is present.

## Actual implementation checkpoint

Production files now exist at acquisition/TS (closed immutable DATA readers and lexical/canonical containment), acquisition/issuer/TS (same Original/control, actual task graph and publication, actual target declaration/StoreReceipt, Native production and staged qualified reader), and acquisition/receipt/TS (actual completed capture byte observation). The producer receipt observer checks controlled bounded reads, extent and file identity. The staged handoff reacquires the complete canonical plan, validates identity, acquires exact published receipt under an outer owned reader task, rechecks Source while reader SH is held, returns the compiler lane, then admits consumer. Reader tasks are canceled and joined on failure. Existing authenticated retained-store reentrancy avoids a second SH acquisition behind a writer. This is code, not acceptance: CLI/gateway wiring and genuine lifecycle tests are still open.

The declaration now preserves optional sourcesRecord; MCP uses semio-os-mcp.sources.json. The repository publisher now passes its actual selectedEnvironment to recordStoreContentV1, allowing an authentically issued leaf receipt to reach its recorder rather than falling back to ambient process.env.

## Continuous reader lifetime remains a real gap

withRetainedRepositoryCompilerStoreV1 still encloses its entire body in compiler-store preparation ancestry (default maximum six hours). Lane settlement alone does not remove that lifetime. The current issuer therefore remains unwired and is not ready for a continuous MCP consumer. The correct fix needs genuine storage-reader ownership under consumer authority from birth, with preparation/toolchain work in bounded child phases; it cannot widen or detach a preparation control or borrow a shape-only store. Opening another SH while the producer image remains held may fairness-deadlock behind a writer and is not a shortcut. The ordinary fresh CLI default buildBudgetMs is zero; the proven finite restriction is preparation ancestry, not an inferred second six-hour CLI policy.

Static planning work is currently five full canonical graph/Source walks for production plus an initial and explicit recheck for handoff, before existing lower compiler capture work. Real counts/timings and all unchanged planning-footprint checks remain an execution obligation. No performance optimization, product-join or qualified StoreReceipt acceptance is claimed.
