# Fixed Store Installer Diagnostic Recovery

The original E2E preparation failed at the real owned installer terminal check. Its full terminal stdout/stderr existed only inside `captureOwnedCommandResultV1`; the producer retained their hashes in an exception cause, and Bun’s default exception output omitted that cause. Inspection found no persisted installer terminal receipts or logs. Recent diagnostics temporary files were process/descriptor audits. Staged roots with `node_modules` cannot establish which scope failed or why. The original terminal reason therefore cannot be recovered honestly from the existing evidence. Actual Bun is 1.3.14 while the authored package manager is 1.4.2; causality is unproven.

Added a closed terminal diagnostic projection and output policy to the existing install schema. The producer now emits scope, status/signal, byte counts/hashes, and a bounded stderr tail through the existing `writeOwnedCommandOutputV1` original-control interface before rethrowing the same installer primary. Output excludes raw stdout, environment, and arguments. The tail is limited to 4096 bytes/16 lines, strips control/ANSI sequences, redacts URLs, credential assignments, authorization tokens, and long token strings, and drops an initial truncated partial line. This is controlled recovery instrumentation, not a relaxation of storage or source guards.

The test-first source-extraction regression failed before these helpers existed. It now passes 1 test/208 assertions across six language-neutral fixture cases and both successful/failing output sinks. AJV validates the input/output schema and SQLite independently validates the UTF-8 byte bound. Runtime debug traces confirm original sink/control forwarding, preserved scope/status/reason and original installer failure despite sink failure. Fixtures cover frozen lock text as an example only, credentials, signal termination, multibyte truncation, ANSI/line bounds and partial secret lines; they do not claim the original child failed for one of these examples. The test is registered in the existing dependency contract suite.

A supported scoped sync is admitted as `bun repo dependencies sync --scope .`, and its producer restricts requested installers but still verifies all current owner plans plus required external owner readiness. Existing data does not prove that the original failure occurred in root scope, so narrowing to root would not faithfully diagnose that failure. The next authorized single managed diagnostic attempt will use `bun repo dependencies sync --all` with this instrumentation. No raw installer, compiler, guard bypass, OS limit mutation, or unrelated cache cleanup is used.

## Supported Read-Only Retry Gate

There is no existing `bun repo dependencies status` CLI. `bun repo --help` does not validate dependencies; OS preflight likewise does not validate Source membership or installed generations.

For a source-stable retry gate, use the existing exported `inspectBunWorkspaceOwnership(root,{kind:"all"},originalControl)` API in `🗂️workspaces/🟦️bun/🟦️.ts`, or retain the equivalent `withCurrentBunWorkspaceOwnershipV1` callback and await its `custody.recheck()`. These functions read and validate the complete current native ownership projection and manifest consistency without publishing Source or running installers. A completed successful read is a current Source observation, not authority to ignore later changes.

Operational trigger: wait for the external writer’s actual terminal state and released queue claim, together with its owner’s confirmation that the active manifest publication batch has finished. Prefer a successful terminal result; a vanished PID or terminal failure alone is not readiness. After a failed writer, an explicit source-owner handoff plus the same fresh read-only ownership validation is still required. Require that validation to succeed before starting one original managed sync. If that validation reports drift, remain read-only and wait for the source owner; do not spend another full sync attempt. The normal sync guard still revalidates during execution.

Installed readiness is a separate later signal: the existing `withJavascriptDependencyReadStorageV1` and its `readJavascriptDependencySourceOwnerScopeReadV1` witness must complete for the required scope under genuine custody before application launch. A successful lock-only run or mere node_modules presence is insufficient. No new runtime, installer, code, OS-limit mutation, or live session was started for this follow-up.
