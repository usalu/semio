# Existing Native Linux Frontend Provisioning Route

Read-only analysis; no command, copy, install, builder action or Source edit ran. Prior reports describing a blanket ban on guest binary installation were too broad: no such user ban is established. Native repo remains the outer interface; a guest native executable can be provisioned through existing owned ports.

## Concrete Existing Ports

The producer is repo-mcp:build. Its runBuildScript reads REPO_MCP_BIN, sets actual GOWORK and calls runCanonicalGoBuild(MODULE_DIR,[-o,binary,.]) with inherited environment. The Go artifact port extracts -o, builds into bounded private staging under compiler capacity, then stageArtifacts(dirname(output),owner,map(basename(output),artifact)). Thus a distinct absolute REPO_MCP_BIN is mechanically supported by the existing owner; no new publisher/class/compiler interface is necessary. GOOS=linux GOARCH=amd64 CGO_ENABLED=0 are inherited. Static closure has no cgo dependency found, but only an actual compile proves this target.

A minimal producer invocation is the usable host native repo run repo-mcp:build --configuration=release --skip-cache, with those three Go environment values and REPO_MCP_BIN pointing to a fresh dedicated ticket-generated subdirectory/native-linux-amd64/repo. SEMIO_BUILD_MODE must be release at original process birth; do not mutate an already-issued prototype envelope. The destination must be a dedicated fresh publication directory because stageArtifacts replaces its owned tree. Never point it at the ticket root or usable host frontend directory. The absolute path and publication temporary suffixes must fit256characters. SEMIO_TEST_ARTIFACT_DIR may select a separate ticket generated compiler capture directory.

Native repo exec --projects=workspace -- <program> <literal argv...> is the existing tool-independent external process port. It can invoke Docker as an internal implementation, including exact-ID projected inspection, binary copy and exact-ID guest execution; this is not raw outer Docker CLI. The generic port preserves host original process envelope and gives progress/cancellation through owned execution. Existing ticket command runner is unsuitable: its command branch hardcodes guest bun repo and stops whole builder on cancellation. Do not use it as a native bridge.

## Exact Gaps And Necessary Boundaries

Cross-target environment/destination are implementation-supported but not declared as manifest inputs/platform namespace. Skip-cache and distinct fresh destination are necessary; this route is a controlled task-specific provisioning invocation, not a claim of a general tested cross-target contract. No compiled Linux artifact exists from this review. Generic repo exec currently admits the entire graph before executing even workspace selection; Root63416 dry2 is still the sole pending operation, so do not launch a duplicate while it owns that admission.

The existing generic transport does not automatically bracket Docker operations with semantic container authentication or verify copied binary provenance. Those checks are available as retained identity functions and ordinary native exec observations, but they must be explicitly sequenced and reviewed; a bare repo exec docker cp alone is insufficient evidence. Current frozen observer performs running+identity checks for metadata, not installation. If Root requires one atomic authenticated provisioning operation with checked transport/cancel/cleanup boundaries, no such retained helper is presently demonstrated; the precise gap is that bounded orchestration, not Go cross-compilation or inability to install a guest executable.

Guest process cancellation cannot be inferred from cancelling the host Docker client: an executed guest native process may survive client disconnect. Provisioning help is bounded; expensive product gates require a destination-owned timeout/control and terminal receipt that Root can observe and cancel without stopping unrelated work. Do not reuse the old whole-builder-stop runner to fill that gap.
