# Genuine Debian X64 Container Builder Audit

## Conclusion

The reviewed authored policy does not prohibit Rosetta or QEMU CPU translation. A real Debian 12 linux/amd64 process can satisfy the existing architecture/ABI requirements without spoofing process facts, provided its fresh managed entry obtains all original authority and its actual storage/device checks pass. The earlier Ubuntu ARM64 probe establishes neither Debian 12 nor x64 readiness. A shared read-write bind of the current checkout is unsuitable because dependency setup publishes node_modules bindings into its source directories.

A genuine container route is therefore conditional rather than categorically rejected. It is not yet a validated build route: no Debian x64 Bun process, managed preflight, fixed allocation/mount, source-view isolation or compilation was run during this read-only audit.

- Docker Desktop engine 29.5.3, Linux kernel 6.12.76-linuxkit, aarch64, ten CPUs and 8,321,515,520 bytes memory.
- A short read-only, network-disabled Ubuntu probe used the existing image only. Its effective capability mask was 000001ffffffffff, and writable real loop-control/loop0/loop1 nodes were visible. Parent previously observed further loop devices and ext4 support. These facts alone do not establish an x64 process or Debian userspace.

## Authored Admission Boundaries

The course image producer checks actual process.platform equals linux and actual process.arch equals x64. Its executable context additionally checks a retained release artifact and ELF64 machine 62. The native caller projection carries the original workspace, mode, child budget and network grant. No reviewed condition inspects a physical CPU brand or rejects a translated x86_64 process.

The early repository preflight branches before cache opening and dependency bootstrap. It observes the invoking process's platform/architecture, /etc/os-release, /proc/self/status CapEff, writable block/character devices, unused loop backing files, required executable tools and actual workspace statfs. The current authored course values require Debian 12, x64, CAP_SYS_ADMIN, seven unused writable loops and 72 GiB available. Observations themselves grant no compiler or storage authority.

The currently reviewed Linux fixed backend independently requires effective CAP_SYS_ADMIN, sufficient parent filesystem capacity, full fallocate allocation (file.blocks * 512 at least file.size), bounded size, an ext4 loop mount and exact /proc/self/mountinfo plus /sys/dev/block loop backing_file/offset/sizelimit agreement. It checks real backing identity throughout custody. The physical host backing caveat remains separate: guest extents do not by themselves prove the sparse outer Docker.raw has reserved the corresponding host bytes. Linux backend work by other contributors is ongoing, so these statements describe the source inspected during this audit.

## Source And Cache Isolation Required

The dependency binder derives sourceDirectory as workspace/member/node_modules and publishes current per-platform generations there. Reusing the host checkout read-write would replace shared macOS aliases with Linux aliases. Reusing its macOS cache backing would likewise confuse platform-specific receipts and mounts. Neither is an acceptable route.

A candidate route can expose the live checkout as a read-only lower tree and use a private container-owned writable overlay view, with an independent Linux cache mount. The original Linux controller would start inside that actual view. Existing host-generated node_modules aliases must be hidden in the private view before first admission, rather than removed from or rewritten in the shared checkout. This is source-view isolation, not a copied ticket checkout or replacement compiler authority. The current controller's physical ancestry, source-change and binding checks must still accept the actual view; no bypass is proposed. No overlay was created during this audit.

## Honest Next Validation Boundary

A bounded next probe could run a pinned actual Debian 12 amd64 userspace and matching actual Bun runtime under the already-enabled translation, mount the checkout read-only, and invoke the early managed preflight with an original Linux entry. It must print actual runtime/OS facts and keep all source/cache mutations private. This would settle the architecture/ABI/capability question without starting a compiler or allocating fixed stores.

It would still not establish physical backing or a deployable release. A subsequent authorized storage probe must demonstrate the real backing and kernel identity required by the unchanged backend, and the host physical budget must cover the admitted stores. The final compiler/image build can proceed only after those controls pass. No blanket emulation refusal and no claim of a validated container compiler follows from the current evidence.
