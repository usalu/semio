# Storyboard: grasshopper / trees (`Beat5_DataTrees`)

Video `grasshopper_trees`, file `G/🌳️trees/🐍️.py`, title `{en: "Data Trees on the Tower", de: "Datenbäume am Turm"}`. 22 clauses, about 4.5 minutes. Facts: `research-grasshopper.md` §3, §4, §7; `research-nakagin.md` §2, §3.4. Every number below is read from the engine (`tree()` of the Nakagin model, `Tree` operations of the GH engine); the figures in this file are the expected values and are asserted by the scene tests.

## Learning goals

1. A flat list cannot say which capsule belongs to which storey; a data tree keeps that address.
2. Read a path `{B;T;S;F}` segment by segment (building, tower, storey, facade), a branch (Ast) as one list, an item by its index `[i]`.
3. Inspect trees with Panel (tree mode), Param Viewer and Tree Statistics before wiring them.
4. Restructure trees on purpose: Flatten, Graft, Simplify, Path Mapper, Flip Matrix; predict path and count of the result.
5. Branch matching: two data sets only pair the way the paths say; mismatched trees give silent wrong results (longest-list style repetition), fixed by matching paths.

## Misconceptions addressed (research-grasshopper §3.5, §7)

- Flatten merges all branches, Simplify keeps them (4); Graft does not keep the grouping, every item gets its own branch and the new last index is its old list index (2).
- A Panel shows the paths and these, not the list order, decide matching (9).
- `{0}` and `{0;0}` are not the same structure (4, 5).
- Short list against a tree repeats in every branch (§3.4), no error is raised (5).
- Path Mapper silently drops what the target does not name; check counts (3).

## Screen layout and visual rules

Tool side (left, about 55 percent): the Grasshopper canvas strip with the real components (Panel, Param Viewer, Tree Statistics, Flatten Tree, Graft Tree, Simplify Tree, Path Mapper, Flip Matrix, Custom Preview) and the tree diagram below it. Building side (right): the aggregated Nakagin tower drawing (both towers, lit capsules). Both are on screen whenever a value is shown.

Tree diagram (drawn from the engine tree, not typed): trunk = building, boughs = towers, branches = storeys, twigs = facades (these are the Grasshopper branches, each carries its path), leaves = capsule items. 70 twigs are drawn as a compressed fan; the focused subtree (tower A, storey 0) is drawn in full size beside it.

Path segment colours are fixed for the whole clip and shared by path text, tree level, and tower highlight: building white, tower cyan, storey yellow, facade green, item index orange. Tower A and B keep a tint (A cyan family, B yellow-orange family) only in the matching section where colours are the subject. Wires carry the data kind (item thin, list double, tree dashed double).

Numbers: en `140`, de `140`; no unit needed for counts, each count has its object ("capsules", "branches", "Äste").

## Open questions answered by the engine (resolved at scene time)

- Exact path ordering of the 70 branches (tower, then storey, then facade) is taken from `tree()` order, not assumed.
- Whether branch matching pairs by path or by order in the engine; the scene shows the outcome of `evaluate` and the Param Viewer text only, so it holds either way as long as the mistake and fix evaluate as stated here. If the engine reports a different result the clauses 17, 19 and 20 text is adjusted to it.
- Facade numbering (0 to 3) and which side is item 0: read from the model slots.
