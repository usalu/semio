## 2. Design (what the package is)

* **Snapshot** (generated by `T/r3-f1-gen-model.ts` from `T/r12-w2-wp18-psets-model.ts`): `PropertyTemplate` (collection `property_templates`: name, `applies_to: Vec<TemplateTarget>` (26 element and type kinds), `properties: Vec<PropertyDef>`), `PropertyDef` (name, `PropertyKind` text/real/integer/boolean/length/area/volume/angle, unit, description, required, default value, allowed values, minimum, maximum), `ClassificationSystem` (collection `classification_systems`: name, edition, source, `entries: Vec<ClassificationItem{code,title,parent}>`). `classifications` is now `holder -> (system id -> code)` (a keyed list per system); the old `Classification{system,code,title}` struct is gone. `properties` is keyed by element **or type** id (eight type libraries hold data). Hand-written helper kit: `🧬️schema/📸️snapshot/🏷️property-kit` (value kind/number/equality, violation order kind, range, enumeration, definition and template soundness, entry-table soundness, tree navigation).
* **Mutations (8 leaves, binary tags 18000 to 18005 plus the reshaped 906/907):** `create/set/delete-property-template` (🧰 🛠 🗜), `create/set/delete-classification-system` (📚 🔏 🔐), `set-element-classification {id,system,code}` (🗂), `remove-element-classification {id,system}` (🗄). `set/remove-element-property` accept type ids. The eight `delete-*-type` leaves cascade the properties and classifications keyed by the type and keep them in the inverse rows. Deleting a system cascades its assignments; deleting a template is free (templates only constrain). Nothing migrates code: 106 fixture documents, 18 after-snapshots and the house/office examples were converted by hand scripts (`T/r12-w2-wp18-psets-migrate.py`, kept as input).
* **Inference `effective-properties`** (`🧬️schema/💡️inferences/🏷️effective-properties`): per holder (element or type with data or under a template, instances of a type with data) the effective values with source `Own` > `Type` > `Default`, and findings (`Missing`, `KindMismatch`, `BelowMinimum`, `AboveMaximum`, `NotAllowed`). A type is checked against the templates of its own kind and of the kind it types (once if both list it); an inherited value is reported at its type only. Graph: `NodeKind::Properties`, instance node has its type node as parent (inheritance is a graph edge), `Diagnostics(Data)` planned only when data exists, schedules read effective values (`rows::with_effective`).
* **Diagnostics (en+de):** `property.required-missing`, `property.kind-mismatch`, `property.out-of-range`, `property.not-allowed`, `classification.unknown-code`, `reference.classification-system`.
* **Editor:** library entities `property-template` and `classification-system` (rows, create, inferred rows), commands `applyTemplate`, `editTemplate`, `editClassification`, `searchClassification`, rewritten `setClassification`/`removeClassification` (per system), classification browser panel (`📌️panels/🗂️classification`: tree by depth, search per system, check mark, assignment rows, all labelled and keyboard reachable), properties panel sections (properties of any holder incl. types, effective view with source, template apply, classification per system, template definition rows, entry table rows). Labels en+de in the terminology table.
* **IO:** IFC 2x3/IFC4 by the sub-agent (see its report). The sqlite snapshot codec under `🚪️io/🪶️sqlite` still names the removed entity and is mounted nowhere (dead tree): not touched.
* **Examples:** seed systems as library data in house and office: Uniclass 2015 (Pr/EF subset, verified against the published table), DIN 276, OmniClass Table 23 (curated subset); 8 templates; type-level properties; classifications converted by hand (`T/r12-w2-wp18-psets-examples.ts`).
