# Primary EXPRESS Evidence Boundary

The targeted audit initially described containing-SELECT TYPEOF closure as a concrete native defect. Subsequent inspection found the TypeScript reference and IfcOpenShell implementation also omit it. Their agreement therefore cannot independently approve either interpretation, and the finding is now a shared conformance candidate. The executor was instructed to prioritize concrete aggregate result-kind/deduplication discrepancies and preserve the semantic publication refusal.

The current public text for the full ISO clause was located only in an unauthenticated translated mirror; it is a research lead, not an authenticated primary basis for claiming normative conformance. Primary buildingSMART Annex A can establish actual SELECT declarations and membership, but that alone does not prove TYPEOF's complete result contract.

Primary sources searched/read during coordination: [buildingSMART EXPRESS language guide](https://standards.buildingsmart.org/documents/Implementation/The_EXPRESS_Definition_Language_for_IFC_Development.pdf), [official schema EXPRESS](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2_TC1/HTML/annex/annex-a/general-usage/IFC4_ADD2.exp.htm), [ISO 10303-41 support resource](https://www.steptools.com/stds/smrl/data/resource_docs/fundamentals_of_product_description_and_support/sys/26_schema.htm), and [JSDAI EEntity API](https://doc.jsdai.net/jsdai_doc/api_ref/jsdai/lang/EEntity.html). The EEntity.typeOf method returns entity definitions; it is not itself the complete EXPRESS Value.typeOf builtin contract. The separate Value documentation URL could not be opened by the browser tool. No source found here authenticates the unresolved closure clause.

The low audit's actual TypeScript probe and native source counterexamples distinguish aggregate result typing and deduplication. They remain source/native-test targets, not native execution. See retained-express-type-inverse-audit.md when finalized for exact cases, caveats and disposition.

## Authenticated IFC Counterexample Found Later

The official [IfcFillAreaStyle](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcFillAreaStyle.htm) MaxOneColour semantic proposition explicitly limits colour assignments to one. Its pinned WHERE counts instances whose TYPEOF includes the IfcColour SELECT. The actual full reference validator accepted two distinct RGB colours, with a named MAXONECOLOUR=true result. This authenticates a concrete IFC4x3 conformance defect independently of the unavailable full ISO text or the external helper's mistaken agreement.

The correction and one/two-colour tests are in typeof-select-implementation.md. Independent IfcOpenShell declaration metadata plus NumPy Boolean graph closure verifies all 1,312 released named seed sets and three direct API cases. This establishes released SELECT graph closure, not every wider ISO interpretation.

Public upstream issue3187 describes the same omitted SELECT behavior; closed proposal8528 offers a proposed fix. Public metadata is retained by semantic-upstream-evidence.py. The proposal was AI-assisted and its closed state is not evidence of merging or correctness. No proposed upstream code was used as the semantic authority.
