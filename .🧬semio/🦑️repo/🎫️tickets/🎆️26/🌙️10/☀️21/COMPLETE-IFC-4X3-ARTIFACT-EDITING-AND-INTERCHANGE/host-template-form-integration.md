# Guided Template Entry Integration

The smallest existing staging surface is the per-window action pane, not an IFC document mutation. `ShellHelpers/🪟️window-panes/🟦️.tsx::buildActionCategoryTree` already reads `stagedArgsByKey[actionStageKey(windowId, actionId)]`, renders staged argument controls, and submits exactly one `ActionDescriptor` using the staged values. `Shell/♻️slice-reducers/🟦️.ts::actionPaneReducer` handles `STAGE_ACTION_ARG` and `RESET_ACTION_ARGS` without changing the document. This local ephemeral state is suitable for selecting a released template and collecting an application before submission.

The current generic pane renders a static `expandedAction.args` list. It has no source-owned declaration-dependent nested form callback. IFC4x3 also declares `NoDraft`/`NoDraftMutation`; there is no existing retained IFC template draft to reuse. Changing the template-name argument to 760 actual options improves selection but does not produce typed entry rows or identities.

Recommended source boundary: a domain-neutral staged-form producer interface receives the selected action and current staged values, returning a bounded form description and staged-field events. An IFC extension resolves exactly the selected released declaration and emits only its entry controls. Selection changes must explicitly discard incompatible old rows. The UI event reducer stages the existing closed application shape; final Execute sends the unchanged `ApplyTemplate { application }` command through the current retained template receiver, planner, semantic admission and central Store publication. The form cannot grant admission or produce graph mutations.

Property controls must follow each selected declaration's actual property kind and declared domain: single, enumerated, bounded, list, table and reference values use distinct closed structures; quantities retain their distinct dimensions. Decimal identities and scalar real-bit representations stay in the existing application contract. Reference choices are queries over the captured graph with complete addressing, not a truncated candidate list. Newly staged graph identities need a source-owned allocation command/result tied to the original application request; UI-generated guessed IDs cannot be treated as retained identities. Owner history and performance use their own typed nested forms rather than permissive flattened unions.

For native/cross-device parity, the same form description and stage events must feed the native renderer. An IFC-only React component would leave that requirement open. If drafts must persist across reloads, add a schema-first IFC local-only Draft and DraftMutation through the existing draft Store owner interfaces; do not silently turn current ephemeral shell staging into persisted/shared state.

This is an inspected integration recommendation, not implemented guided authoring. English/German labels, keyboard focus/error association, request progress/cancellation, stale-revision rejection and reset behavior require neutral form fixtures plus renderer/native tests before closure.
