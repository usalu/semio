# IFC4x3 MVD Source Follow-Up

The [official buildingSMART MVD database source](https://github.com/buildingSMART/technical.buildingsmart.org/blob/main/MVD-Database.md) can be read through its GitHub mirror even when the main documentation site challenges access. Its table enumerates IFC4 ADD2 TC1 and IFC2x3 views but does not provide a current IFC4x3 view release list. This source therefore does not resolve IFC4x3 current approval status.

The [official mvdXML repository](https://github.com/buildingSMART/mvdXML) describes mvdXML 1.2 as used for IFC4.3 software certification, while distinguishing that from a formally published mvdXML standard. Do not treat the exchange syntax specification as a complete IFC4x3 MVD constraint dataset.

The [Standards-builds repository](https://github.com/buildingSMART/Standards-builds) contains separate development and release snapshots. GitHub API inspection of `IFC/RELEASE/IFC4_3` and its HTML directory found the published EXPRESS and XSD files and PSD archive. No top-level mvdXML file was exposed by those directory listings. An older indexed `IFC4.3.x-output/master/IFC4.3.mvdxml` URL now returns 404 after the repository transition. Further search must pin a valid published constraint input rather than substitute an older IFC4 view.

The goal remains to edit every declared entity and value while retaining MVD-specific headers and semantics. Complete MVD validation and specialized interactions remain explicit follow-up work; neither the complete declaration catalog nor STEP round trips alone prove it.

## Pinned Release Scope and Current Source Follow-Up

The [official standards landing page](https://standards.buildingsmart.org/?do=register), as indexed on 2026-10-21, lists IFC4.3 ADD2 Alignment based View and Reference View as integrated HTML documentation. Direct fetches still intermittently return a 403, so normative scope inputs were read from the [official release mirror at commit 610ee3f95db9d0380b1eb8de4dc6e17833531518](https://github.com/buildingSMART/Standards-builds/tree/610ee3f95db9d0380b1eb8de4dc6e17833531518/IFC/RELEASE/IFC4_3/HTML).

The release's `annex-b1.html` has all 876 entities, direct RV/AbRV inclusion causes and a universal product/type annotation. `concepts/content.html` has 312 concept paths with their own badges. The complete rows are now retained under the artifact's `🧬️schema/👁️mvd`, with both source hashes and exact release identifiers. See `mvd-implementation.md` for independent parse5/Ajv checks and native execution limits. These informative scope listings do not contain executable concept/parameter constraints and are not promoted to conformance proofs.

GitHub API inspection of the current [IFC4.3.x-development schemas](https://github.com/buildingSMART/IFC4.3.x-development/tree/master/schemas) additionally found `mvd.csv`, a `mvd/GeneralUsage` tree and `mvd/ReferenceView/BodyTessellationGeometry.csv`. Development code `templates_to_mvdxml.py` constructs general-usage template graphs from Markdown concepts and UML bindings, and `determine_mvd_scope.py` derives entity reachability. Current development selection differs from the pinned release badges; it must not silently replace the ADD2 release scope. A complete, correctly versioned executable constraint input still needs to be pinned and evaluated.

Another targeted primary-source search during the glTF integration wave did not locate a correctly versioned ADD2 executable mvdXML input. Indexed release notes describe older IFC4 concept-template XML as experimental documentation, which does not establish current IFC4x3 constraint coverage. Search absence is not proof that no suitable dataset exists. No development or legacy IFC4 constraints were substituted, and no conformance flag was promoted.

Direct inspection of the pinned release [Actor Assignment concept](https://raw.githubusercontent.com/buildingSMART/Standards-builds/610ee3f95db9d0380b1eb8de4dc6e17833531518/IFC/RELEASE/IFC4_3/HTML/concepts/Object_Assignment/Actor_Assignment/content.html) and [IfcWall usage page](https://raw.githubusercontent.com/buildingSMART/Standards-builds/610ee3f95db9d0380b1eb8de4dc6e17833531518/IFC/RELEASE/IFC4_3/HTML/lexical/IfcWall.htm) exposes rendered generic relationship diagrams and recommended General Usage tables, plus inherited concept-use prose. These pages do not expose an executable mvdXML definition in their inspected source. Their diagrams/prose alone are not sufficient to invent a complete per-view constraint graph; the existing catalog remains informative and editing remains unrestricted by unlisted badges.

The latest inspected [official mvdXML technical page](https://technical.buildingsmart.org/standards/ifc/mvd/mvdxml/) says 1.1 is its official publication, discusses phasing out the format because of specification/schema ambiguities, and says draft 1.2/1.3 did not pass the buildingSMART standards process. It describes MVD integration into IFC's core/XMI and recommends IDS for separate information requirements. This strengthens the requirement to distinguish the pinned IFC4x3 release's actual view requirements from an arbitrary draft mvdXML parser or an IFC4 view file. It does not establish that the current informative scope badges prove complete per-view conformance, or remove the user's all-MVD requirement.
