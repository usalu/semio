# Remaining EXPRESS Aggregate Membership Semantics

The current QUERY implementations already select only predicates that evaluate TRUE; UNKNOWN predicates do not enter the result. This agrees with the [EXPRESS Language Foundation query tutorial](https://www.expresslang.org/learn/tutorial/express-advanced-03-global-constraints). QUERY is not the remaining aggregate gap.

Both current evaluators explicitly refuse SET union and aggregate difference/intersection when instance equality leaves output membership indeterminate (`aggregate-indeterminate`). This is an honest incomplete-evaluation outcome; it does not invent a concrete membership list or mark a rule evaluated successfully. The remaining feature is the full specified aggregate result/propagation behavior for those cases, including multiplicity and identity.

The [current EXPRESS overview](https://www.expresslang.org/learn/jotne-express/02-express-language) distinguishes LIST/ARRAY order and SET/BAG multiplicity, but does not establish the detailed indeterminate-operand algebra needed for a safe implementation change. The [official ISO 10303-11:2004 listing](https://www.iso.org/standard/38047.html) identifies Edition 2 as the current reference manual; accessible overview/search results alone are insufficient to choose between a symbolic aggregate, a wholly indeterminate aggregate value, or another normative representation. No source change was made on an unsupported inference.

Before this slice is implemented, retain authoritative operator semantics and a neutral matrix for TRUE/FALSE/UNKNOWN instance comparisons, SET/BAG/LIST combinations, duplicate multiplicities, SIZEOF/EXISTS and nested expressions. Differential tests must compare an actual independent EXPRESS implementation rather than merely reproduce our algorithm. The retained native evaluator work and complete MVD execution remain separate outstanding goal requirements.

A subsequent targeted search located the historic [NIST EXPRESS toolkit design](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=821300), the [NIST working-form programmer reference](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir4814.pdf), and an [early PDES working draft](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir88-4004p2.pdf). Their search metadata does not establish the exact Edition 2 operator rules, so no result was inferred from those older references. The independent IFC validation interface remains available, but a failed or unsupported rule generator is not a normative answer to the unknown-membership question.
