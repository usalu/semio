# BIM Semantic Exchange Independent Next-Frontier Research

## Recommendation

Implement explicit occurrence property sets on the already supported Site/Building/Storey records as the next bounded BIM exchange slice. Start with the four dimensionless authored variants Text, Real, Integer and Boolean, with an explicit unsupported diagnostic for the remaining measure variants until their unit semantics are implemented. This connects real canonical mutations, an existing adjustable properties panel and current prepared relationship queries without guessing wall/family geometry, type inheritance or material composition. It is a proposed clean incremental semantic contract, not a claim that the existing partial spatial exchange loses data silently or that arbitrary IFC property graphs fit the BIM model.

## Coverage Census and Ranking

The fresh portable ticket `bim-semantic-frontier-census.py` scanned unchanged original46 byte declarations only:23 IfcRelDefinesByProperties,31 IfcPropertySingleValue,26 IfcRelDefinesByType,100 IfcRelAssociatesMaterial,3 IfcRelAssignsToGroup,2 IfcRelVoidsElement and0 IfcRelAssociatesClassification. Per-file SHA/count observations are generated/bim-semantic-frontier-census.json. These counts are bounded lexical evidence, not reachability, applicability or full EXPRESS validity.

1. Occurrence single-value properties on existing spatial holders: strongest existing domain/mutation/editor/index fit, and original property graph evidence exists.
2. Site boundary authored polyline: compact Point2 domain, but IFC site Body/FootPrint curves are not automatically legal property boundaries; coordinate frame/closedness and intended representation need an explicit schema contract first.
3. Classification systems/assignments: existing rich domain and editor, but the46 original corpus has no classification relation example. Parent/child reference identity, system edition/source and absent code semantics need authored physical evidence.
4. Type/material exchange: high original coverage, substantially larger semantic decision. BIM type layers/functions/material categories are not derivable from arbitrary IfcMaterialLayerSet/Constituent/ProfileSet without a declared mapping. Inherited IFC type property overrides cannot be flattened into authored occurrence values silently.
5. Openings and groups: real IFC void/fill ownership and BIM hosted opening semantics are larger than a profile hole or generic group. Existing geometry diagnostics for relational voids remain appropriate; no fill, Boolean subtraction or workset correspondence is inferred here.

## Proposed Closed Contract

Use a language-neutral schema containing holder kind/key, set name, property name, exact value tag/payload, optional relation-sharing case and expected result/diagnostic. Encode Real by existing exact binary64 words where fixtures require signed zero; restrict TS Integer admission to genuinely exactly representable values or explicitly refuse rather than round an IFC bigint. Export Text as IfcText (do not narrow arbitrary UTF8 text to IfcLabel), Real as IfcReal, Integer as IfcInteger and Boolean as IfcBoolean. Initial contract requires PropertySingleValue.Unit unset and one supported nominal scalar branch. LOGICAL UNKNOWN, null nominal values, references, enumerated/list/table/complex properties and unit-bearing measures remain explicit unsupported cases, never coerced to false/empty/text.

Resolve exact owning slots: IfcRelDefinesByProperties.RelatedObjects/RelatingPropertyDefinition; IfcPropertySet.Name (IfcRoot owner) and HasProperties; IfcProperty.Name (IfcProperty owner); IfcPropertySingleValue.NominalValue/Unit. Preserve selected source roles/status: a late unknown constituent must not become a unique match; duplicate names or ambiguous owner projections must not be last-write-wins. The BIM map cannot represent duplicate property names, duplicate same-name sets or absent set names: reject those selected projections explicitly. Shared IFC property sets may be read into each holder's authored map but export need not preserve source entity identity; report this projection boundary.

Keep semio_BimStorey reserved authored Level/Height/CutHeight handling separate. A generic property with that exact reserved set name requires a closed conflict policy before implementation; silently overwriting the derived/authored spatial convention is forbidden. Do not import inherited type properties as occurrence-authored properties. Nonspatial holders remain unsupported until their own exchange route exists. No header, arbitrary property-set name or successful selected rule creates MVD certification.

## Test-First Execution and Controls

Author same schema cases for TS and future genuine native implementation: four kinds, empty/UTF8 text, signed zero, safe integer bounds, duplicate/missing names, duplicate owner/lateunknown, wrong relation/property role, shared sets across two spatial holders, two differently named sets, preserved reserved-storey fields and explicit unsupported nominal kinds/units. Add source-sized many-relations/many-properties cancellation frontiers, original observer identity including undefined/class instances, mutable options substitution, source immutability and final-publication abort. Every expensive roster/name/aggregate copy must use original cooperative controls.

Run BIM set-element-property→canonical diff→apply→inverse in both inverse forms, export IFC→STEP→parse→import and compare exact selected authored values. Also start from IFC, edit only actual nominal payload through existing IFC mutation/details binding, diff/inverse/STEP round trip, and compare unrelated source entities unchanged. Test the property-panel exact kind display/change, localized labels, keyboard-accessible add/remove and seven/page-style bounds only if the existing panel imposes them; do not invent a UI cap as schema cardinality.

Independent test-owned IfcOpenShell metadata/parse/full EXPRESS plus util.element.get_psets can corroborate actual selected property values and ownership. Plain object identity must separately observe shared sets and occurrence-vs-type distinction; get_psets' convenience inheritance/flattening must not authorize our contract. SQLite/AJV can corroborate exact names/uniqueness and ordered source records, while raw IFC duplicate-invalid cases must retain actual validator behavior. No runtime dependency, external public type, full-BIM fidelity or native capability is introduced by this research.

No production/frozen input was edited. This is planning evidence based on inspected source, not a new executed BIM implementation or a whole official-corpus validation run.

## Concrete Integer Domain Refinement

Subsequent direct inspection of BIM snapshot/💠️values/🦀️.rs confirms PropertyValue::Integer.value is i32 (line735), stricter than the initial research's proposed safe-JS numeric bound. The existing domain is authoritative: the new exchange must use inclusive −2147483648..2147483647 on both directions, preserving raw IFC integers outside that target domain in the IFC graph and explicitly refusing their BIM projection. This refinement does not authorize changing IFC integer64/raw STEP/evaluator arithmetic or rounding into the narrower target. High's initial physical large-integer clamp evidence must remain raw rather than be relabelled independent exact preservation.
