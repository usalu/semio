# Issued Vector Owner Follow-On Plan

This schema-first follow-on is active while the FEM self-weight checkpoint is frozen. New unregistered vector data, fixtures, public tests and ticket-owned external observations may progress; existing evaluator/catalog/control/interchange production remains unchanged. It targets six among33 still-unscored function owners; existing tests elsewhere are not classified as absent.

## Actual Source Dependency

IfcNormalise, IfcDotProduct, IfcCrossProduct, IfcOrthogonalComplement, IfcBuild2Axes and IfcBuildAxes call actual derived Dim attributes. A bare ExpressEvaluator does not resolve those derived fields. Tests must use the existing IfcExpressContext initialized over one freshly parsed test-owned STEP source with the actual canonical issued program and original control. They must borrow that context's actual entity values; injecting a fabricated Dim field or a custom attribute-resolution substitute would not exercise the released implementation. Result entities created inside the functions retain actual constructor/composition identity and are observed through the same context attribute resolver.

The first slice should cover2D/3D direction normalization with exact axis and3-4-5 ratios; parallel/opposite/orthogonal normalized dot products; dimension mismatch returning indeterminate;3D cross-product orientation/magnitude and parallel zero magnitude;2D cross-product refusal; signed2D orthogonal complement and intentional3D refusal; default2D axes; and3D default/given axis construction. A valid zero-magnitude IfcVector tests the explicit Normalise indeterminate result without presenting an invalid zero-ratio IfcDirection as a physically valid model. Any deliberately malformed source belongs in a separately labeled negative admission case.

## Schema, Observation and Controls

Author a closed language-neutral source-body/entity-address/function/projection/expected-status contract before tests. Inputs should retain original source ordinal/ID and complete raw bytes. Projection must handle nested entity/aggregate outputs through genuine attributes rather than pointer equality or implicit defaults. Actual output kinds, nested orientation/magnitude, unknown statuses and source/input immutability are retained. Exact axis cases require exact comparison; nonterminating real arithmetic needs an explicit neutral tolerance justified by the actual numeric calculation, never a broad catch-all equivalence.

Reuse canonical context initialization and original controlled ticks for preparation and function calls. Original cancellation during both phases, exact observer failures, denied work/iteration/depth budgets and no false complete result need authored laws. No extra population preparation, whole graph clone inside the test evaluator, source mutation callback, new donor wallet or alternate host/native adapter is justified.

The actual official [Normalise](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcNormalise.htm), [DotProduct](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcDotProduct.htm) and [CrossProduct](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcCrossProduct.htm) pages were read directly. Their semantics match the pinned function bodies: undefined/zero normalization, undefined dimension mismatch, and unitless three-dimensional cross product with zero magnitude for parallel inputs. CrossProduct returns its raw normalized-input cross ratios in Orientation and their norm in Magnitude; projection must not silently renormalize that stored orientation. OrthogonalComplement preserves raw input scaling, whereas Build2Axes normalizes before its complement. Constructor outputs and bare numeric observations are scored separately from full schema validity.

## Independent Proof and Limits

The same source file and actual entity IDs should pass to the existing test-owned IfcOpenShell interface, with independently generated helper results and full physical diagnostics retained separately. A SQLite numeric projection can corroborate exact dot/cross arithmetic and ordered axes, but does not supply all EXPRESS derived/type semantics. Unsupported external constructor, derived resolver or indeterminate mappings remain explicit. The exact pinned EXPRESS SHA and function-source lines remain primary. No production correction should occur without a genuine discriminating red and independent primary interpretation.

This plan does not enable a native implementation or change semantic publication/capability flags. Native compiler ingress101 remains a genuine limitation. Even complete success for these selected functions would not prove full function branch coverage, full IFC validation or released-view conformance.
