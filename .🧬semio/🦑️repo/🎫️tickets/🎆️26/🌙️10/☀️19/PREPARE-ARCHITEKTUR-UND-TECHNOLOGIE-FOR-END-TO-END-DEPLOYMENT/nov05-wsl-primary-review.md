# November 5 WSL Activation Primary-Source Review

Read-only research. No OS command, installer, elevation, distribution, daemon, credential or remote mutation was performed. The staged MSI/rootfs verification is reported by the preparation owner and was not independently repeated here.

## Boundaries and Selective Plan

Microsoft's [offline install](https://learn.microsoft.com/en-us/windows/wsl/install) calls for the WSL MSI and elevated VirtualMachinePlatform enablement using `dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart`, with a likely restart. Hardware virtualization and SLAT are required; nested virtualization is relevant if the host is itself a VM. [Troubleshooting](https://learn.microsoft.com/en-us/windows/wsl/troubleshooting) specifically directs a restart after enabling VMP. A package present, feature requested, or pending reboot is not proof a WSL2 VM can run.

Distinguish current Store/MSI WSL from the legacy inbox/manual sequence. The current [WSL CLI documentation](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) calls `--enable-wsl1` the option that additionally enables the legacy Windows Subsystem for Linux optional component. The offline WSL2 instructions mention VMP, not that feature. Thus do not assume WSL1 must be enabled for this selective Store/MSI WSL2 route; older inbox/manual flows and specific observed errors may require different remediation. Do not disable existing features.

The [standard Windows Installer options](https://learn.microsoft.com/en-us/windows/win32/msi/standard-installer-command-line-options) support `msiexec /package <verified-msi> /quiet /norestart`; wait for the owned process and capture its actual exit status before proceeding. Quiet alone can restart automatically, so the explicit no-restart switch is essential. [Microsoft's MSI return-code table](https://learn.microsoft.com/en-us/intune/configmgr/apps/deploy-use/create-applications) classifies 0 as success, 3010 as soft reboot required, 1641 as reboot initiated, and 1618 as another installation in progress; 1602 is cancellation. Treat nonzero statuses explicitly, halt for reboot when indicated, and never interpret process launch as success. These are general MSI semantics; I did not establish a 3.0.3-specific installer implementation or prove this host's privileges. MSVC installer cancellation 1602 is a separate actual outcome; no repeated prompt or bypass follows from it.

After each state transition verify real facts: Windows build/architecture and virtualization; VMP actual feature state and pending reboot; WSL package version and effective CLI; then `wsl --list --verbose` for exact name, ownership and version. If the unique proposed name is occupied, refuse rather than adopt, unregister, overwrite, or modify it. Confirm an empty owned install location and the verified tar, then the [documented import](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) is `wsl --import <owned-name> <owned-install-location> <verified-tar> --version 2`. A successful import and a name alone still do not prove Linux readiness: start only that owned distro and verify kernel/architecture, /etc/os-release Debian 12, WSL version, and expected usable storage/network. Do not set a global default distro/version or use global shutdown.

For per-distro configuration, [Microsoft documents](https://learn.microsoft.com/windows/wsl/wsl-config) `/etc/wsl.conf` and `[boot] systemd=true`; Debian slim must first actually contain suitable systemd packages, and the change takes effect only after that distro fully stops and restarts. `wsl --terminate <owned-name>` targets one distribution; `wsl --shutdown` stops all and is inappropriate for shared work. Verify actual systemd after restart. Unregister destroys all data and is not a routine cleanup shortcut. Import, configuration, package installation, termination and daemon startup are separate effects and were not performed here.

## Docker Provisioning Principles

[Docker's Debian documentation](https://docs.docker.com/engine/install/debian/) supports Debian 12 bookworm and the official signed apt repository. Provision the owned environment using its documented keyring/repository and explicit Engine, CLI, containerd, Buildx and Compose plugin packages, with pinned versions and verified package provenance appropriate to the release contract. The slim OCI rootfs does not establish that apt prerequisites, systemd, networking, storage drivers, kernel support, or Docker packages are present. Docker's Debian package installation may automatically start its service: treat package installation as a daemon-starting effect, plan it accordingly, and observe actual state rather than assuming it stays stopped. Do not use Docker Desktop, paid services or its convenience script as an implicit prerequisite.

Docker's [post-install guidance](https://docs.docker.com/engine/install/linux-postinstall/) says daemon socket access via the docker group grants root-equivalent access. Avoid changing host-wide groups; choose an explicitly owned access model and verify the actual Engine server, Compose plugin and container operation against the release gates. Image pulls are network reads and any registry pushes or Pages deployment remain separate remote mutations. No readiness claim follows from a CLI version alone.

Sources describe supported mechanisms, not proof of current machine capabilities or a 3.0.3 MSI-specific implementation. No OS state was changed during this review.
