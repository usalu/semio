# Native Windows Compiler Provider Assessment

The corrected awaited attempt's `🗑️generated/dd_cpp_decompression_log.txt` records pinned bootstrapper 18.11.12328.437 extraction in 2.344 seconds from its owned ASCII junction, followed by `User may have declined UAC prompt` and `0x80070642: Failed to start the process`. The vendor log says “may”; it does not establish who or what canceled authorization. The wrapper returned 1602. Subsequent process and linker checks found no remaining vendor process or installed MSVC linker.

Microsoft's [MSVC acquisition instructions](https://learn.microsoft.com/en-us/cpp/overview/acquire-msvc?view=msvc-160) document Visual Studio Installer UI, command line and WinGet as the ways to acquire the compiler, and require an administrator command prompt for scripted installation. Its [permissions guidance](https://learn.microsoft.com/en-us/visualstudio/ide/user-permissions-and-visual-studio?view=visualstudio) requires administrator permissions for initial installation and configuration. Its [policy guidance](https://learn.microsoft.com/en-us/visualstudio/install/configure-policies-for-enterprise-deployments?view=visualstudio) documents a machine policy that permits selected manual standard-user installer operations, but explicitly excludes standard-user `--quiet` or `--passive` programmatic installation regardless of policy. No policy change or bypass is proposed.

Microsoft publishes the [Windows SDK](https://learn.microsoft.com/en-us/windows/apps/windows-sdk/downloads) through NuGet, including Microsoft-owned [native SDK](https://www.nuget.org/packages/Microsoft.Windows.SDK.CPP/) and [x64 SDK](https://www.nuget.org/packages/Microsoft.Windows.SDK.CPP.x64/) packages. These establish potential headers and Windows libraries, not a complete MSVC compiler, linker, C runtime development libraries, tool discovery or a demonstrated canonical build. The [MSVC Build Tools FAQ](https://learn.microsoft.com/en-us/lifecycle/faq/visual-c-faq) distinguishes the build tools, including compiler, linker and development libraries, from redistributable runtimes. No Microsoft-supported per-user distribution and installation procedure for a complete standalone `cl.exe` / `link.exe` toolchain was established in this investigation. Unpacking opaque Installer payloads and imitating installation would not establish that support or the repository's existing compiler-discovery contract.

Rust documents the existing [Windows MSVC target](https://doc.rust-lang.org/rustc/platform-support/windows-msvc.html) as native PE/COFF and recommends supported Visual Studio host tooling. Rust also documents `clang-cl` and `lld-link` for specific [linker-plugin LTO](https://doc.rust-lang.org/stable/rustc/linker-plugin-lto.html) scenarios, but this does not supply the Windows SDK and MSVC C runtime headers/libraries, prove the course's native dependencies, or establish an existing repo-managed Windows provider. The repository's native bootstrap currently discovers `vswhere` and an architecture-specific MSVC `link.exe`; its native bootstrap tree has no `clang-cl`, `lld-link`, or xwin provider. The Cargo configuration selects the repository's pinned native Rust target; its explicit self-contained LLD rule is limited to Linux. Switching the compiler target or injecting a linker would therefore be a new, unproven provider, not an already-supported route.

The supported next step remains a successful authorized native Build Tools installation and actual linker/SDK-backed canonical builds. Follow with the managed focused oracle suites and unchanged public course test, typecheck, check, development stack and browser gates. No new provider or package extraction was implemented without a complete documented, verified toolchain and without demonstrating the unchanged canonical build.

Read-only host checks found the pinned Rust toolchain's `rust-lld.exe`, but the conventional `C:/Program Files/LLVM/bin` and `C:/Program Files (x86)/Windows Kits/10/Lib` locations are absent. This is a bounded check of those locations, not an exhaustive claim that no other compiler or SDK exists anywhere on the machine. The Rust linker by itself does not supply the absent SDK and CRT development libraries.
