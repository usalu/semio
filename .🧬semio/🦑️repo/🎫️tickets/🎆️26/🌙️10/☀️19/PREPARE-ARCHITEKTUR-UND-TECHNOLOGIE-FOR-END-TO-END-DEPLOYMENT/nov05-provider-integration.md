# Native Windows Compiler Provider Integration

The unhooked four-field receipt and existence-based readiness function were removed because neither authenticates a tool-store publication. The remaining portable module provides only path construction and a non-authoritative eligibility classification; it cannot select a compiler or establish readiness. Its schema-driven neutral fixture covers 16 cases, including case-insensitive compiler, target linker, Cargo target, SDK version, library path and explicit empty values. A native governed harness compared all 16 results with SQLite and exited 0. Full Ajv validation awaits dependency publication.

The existing `toolEnvironmentV1` and `runToolV1` preparation are synchronous and lack issued tool-store custody. A correct provider cannot infer a ready store from a marker at this boundary. Managed publication should instead hold a genuine `RepositoryToolingStoreV1` reservation and appropriate publication/read lease, authenticate pinned recipe and full archive-derived inventory, recheck no-follow source and destination identities, and carry the resulting verified custody through the tool process. Candidate extraction and MSI/CAB provenance remain with the package owner. No readiness receipt, provider hook, tool environment, global setting or staged file was published by this work.

The existing Cargo compiler store already holds a real tooling-store and Rust-generation scope around its native compiler lifetime; this is the integration boundary for a verified Windows provider, rather than a synchronous receipt probe. The package owner is producing a complete inventory whose canonical format is newline-terminated compact JSON `{version,recipeSha256,files:[{path,bytes,sha256}]}`, with paths sorted by UTF-8 bytes and rooted at `VC/` or `sdk/`. Only compact provenance and digest pins belong in Source.

A schema-first inventory metadata validator now rejects unbounded extents, duplicate or case-fold-colliding names, unsafe Windows paths, device names, extra fields and noncanonical ordering. Its result is descriptive metadata only and grants no Ready or publication authority. A governed native harness passed nine neutral cases against SQLite ordering evidence; Ajv remains pending. The verified inventory digest, physical store verifier, publication and actual compiler integration are not yet implemented.

The actual verified metadata describes 494 compiler files with a largest member of 23,327,602 bytes and 4,453 SDK files with a largest member of 89,891,698 bytes; the SDK totals 1,113,686,631 bytes. The schema's 12,000-file, 256 MiB per-file and 4 GiB total ceilings bound inventory parsing above these observations; exact byte/image authority will still come from the pinned canonical digest and held tool-store verification, not these ceilings.

The observed compact inventory passed the canonical validator with 4,947 files, 1,513,389,488 bytes and SHA-256 `1baafc58de2b0d376d6d60c20735c485fbb64931fe32a8004b1c7d97374aa01d`. It is evidence only: its recipe digest includes ticket prototype source and must be regenerated from the final production extractor before pinning.
