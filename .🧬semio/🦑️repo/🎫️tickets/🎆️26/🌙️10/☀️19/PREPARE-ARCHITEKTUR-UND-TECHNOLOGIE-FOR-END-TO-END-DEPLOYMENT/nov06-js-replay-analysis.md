# JavaScript input replay analysis

`⚡️caching/🚀️bootstrap/📦️dependencies/💾️storage/🟦️.ts` owns `runJavascriptDependencyStoreProducerV1` and its `fence`. Every fence checks the actual Store and ownership custody, all retained source stamps, preservation source, every accumulated input receipt and retained preservation descriptors. Each receipt replay walks the selected immutable input directories, validates named and held identities, hashes every file, checks exact EOF and rechecks the named identity. A fresh group is also fully verified once at stage time; an existing or resumable group is fully verified on capture. Progress is published after each 64 charged directory, entry or chunk operations.

For a build attempt with F freshly processed scopes and no retries, the loop executes three receipt-bearing fences per scope (before the reuse/adopt/install path and twice around its completion), followed by one per fresh ready receipt and two final fences. If borrowed-provider and singleton publication is needed, three more fences surround those operations. This is approximately `4F + 2 + 3P` complete replay passes after staging, where P is 1 only when those provider operations run; existing material adds a receipt-bearing pre-stage fence and capture pass. Reuse, retries, cache purge or other branches can change the count. In publish, existing inputs are captured again, followed by at least five receipt-bearing fences, three more if provider operations run, and one for every full binding-fence interval. All receipt groups are replayed, so repeated work scales with the entire selected input set rather than just the scope being installed. These are source-level counts, not proof of which phase the live writer has reached; its progress label does not identify scope or fence.

The Windows descriptor API tracks child capability lifetimes and verifies root-family ancestry and exact file facts. Its bounded reads and handle metadata calls are synchronous within the Bun thread. Merely placing them in a promise pool cannot parallelize the blocking operations and may conflict with quiescent publication checks. A possible future measured design would need genuinely issued independent worker custody, a strict bound on concurrent workers and open handles, unchanged per-file bytes/EOF/identity and directory ancestry checks, cancellation and failure propagation, and complete draining before mutations or publication. No such port or speedup has been proven. Even the two fences around reuse bracket a progress publication and a yield; removing either without a verified ordering contract and a replacement check immediately before the next effect would weaken the existing timing. No fence was removed and the single live writer was not changed or restarted.

The next evidence needed is controlled, phase- and scope-tagged elapsed time and replay counts under the existing governor, followed by identity replacement, concurrent mutation, cancellation and error-drain tests for any proposed bounded implementation. The present data supports neither a safe unverified fast path nor a duration estimate for the active sync.

Coordinator bounded reread: current descriptor-group verification uses finite input byte bounds, rejects zero-length reads before expected extent, increments actual read position, and emits progress/yields at charged work boundaries. Preservation rechecks inspect capsule metadata and bounded i/r record bytes without traversing opaque payload trees. These observations do not identify the current PC or justify weakening a fence; live18168 CPU/OtherIO sampling remains the actual liveness evidence. No Source edit made.

Producer continuation reread confirms scope adoption/reuse/export/installed-path verification and subsequent provider/ready publication are separate effects with intervening fences. Final descriptor replay alone does not identify which continuation is current. Existing scopes and resumable generations use different branches; no fixed duration or completion percentage follows from the last input-replay label.
