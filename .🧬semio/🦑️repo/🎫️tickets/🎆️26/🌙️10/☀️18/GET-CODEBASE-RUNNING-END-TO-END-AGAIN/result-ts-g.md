## Findings
1. **Soundness law holds**: warm incremental diagnostics equal the full non-incremental `tsc --noEmit` in 22 of 22 course steps and 12 of 12 ui-react steps (type error appear/disappear, deleted and created modules, JSON key rename, ambient `declare global` added/removed, tsconfig option on/off, `paths` change). A stale `.tsbuildinfo` did not mask or invent an error in any step.
2. **Heap bound: measured, rejected.** Course cold tsc: default heap (4.3 GB limit) 28.0 CPU-s / 1,964 MB; `--max-old-space-size=2560` 28.4 / 1,993 MB; 1792 29.8 / 1,864 MB; 1280 ABORTS (OOM after 43.7 CPU-s of GC thrash). RSS is heap need + ~700 MB; a cap saves < 100 MB and turns a big program (the ✏️s program needs 4-5 GB) into a crash. RAM stays governed by admission, not by a tsc flag. No edit.
3. **Vitest worker bound: measured, applied.** Course suite, same machine state: default 44.8 s wall / 48.7 CPU-s / 2,129 MB (11 processes); `--maxWorkers=1` 61.9 / 48.0 / 1,288; 2: 73.1 / 52.2 / 1,471; 4: 85.4 / 55.9 / 1,405 (wall of the 1-4 runs is load drift, CPU is flat). A bound of 4 saves ~0.7 GB (33 %) at unchanged CPU; the default of one worker per core would grow with the suite (ui-react: 1,212 tests).
4. **vitest `--changed`/`related` selection: rejected as unsound.** It follows the static import graph; the course tests read fixtures, JSON, the workspace and spawn vite/tsc at run time (deploy test: site build + tsc), none of it in the module graph. Sound selection needs traced per-test-file read sets (a per-test-file action with a kernel read oracle, keys-g's Seatbelt finding); not built. The suite stays full.
5. **Unit-wise typecheck (`typecheck units`, the shared engine) measured on the course family** (28 units, plan 0.8 s / 175 MB): no-op **1.6 s, 105 MB**; body edit in one unit **4.6-5.7 CPU-s, 0.3-0.6 GB**; new export in a leaf 12; edit of a widely imported module (signature) **13 units re-run, 95 CPU-s, 1.7 GB** (worse than warm monolithic 12-13); cold 138 CPU-s (every unit re-parses libs); tsconfig option or `paths` change re-runs all 28 (150 CPU-s). Equivalence with the full compiler: counts equal in 21 of 22 steps. **One real miss**: a new `declare global` augmentation in a test file produced 2 errors in unit mode against 44 in the full program (units do not see globals of files they do not import). Blockers before the course could use it: (a) the family's `types: ["vite/client", ...]` do not resolve from the generated unit config (28 false TS2688; fixed in my driver by resolving `types` entries to `typeFiles` and forcing `types: []`), (b) one declaration-boundary finding, TS2742 on `export default defineOwnedBuildConfigFactory(...)` in `🏗️builder/🌐️vite/🟦️.ts` (generic `T extends OwnedBuildConfigFactory` returns the unnameable literal type; annotating or returning the non-generic type clears it), (c) the global-augmentation miss. Not applied: it stays a development gate.
6. **Hermetic classes cannot use a tsbuildinfo seed.** The class is selected so the action can run remotely (`strategies` start with `remote`) and "reads only declared inputs"; a host-side seed has no meaning there and the sandbox refuses undeclared reads and writes. The Bazel-native answer is one action per unit with a declaration output (early cutoff by output digest, as rules_ts does): the engine, receipts and the neutral unit model exist (`C/result-conc-ts.md`, `C/result-polyglot-units.md`), but `repo units` has no `typescript` language yet (enum: go, python, dotnet, cpp, wit, tex) and no Bazel emitter for TS units, so this is a graph-generator task (needs inference + generation rebuild, 60-120 min), not done tonight.
7. **vitest alias resolution seeding: measured, rejected.** Seeding the persisted ownership index (`seedBunWorkspaceOwnershipIndexV1`) leaves the same 129,695 operations: 3.35 s cold, 2.85 s seeded, 5.7 s unseeded; the 17 s seen earlier was machine load.
