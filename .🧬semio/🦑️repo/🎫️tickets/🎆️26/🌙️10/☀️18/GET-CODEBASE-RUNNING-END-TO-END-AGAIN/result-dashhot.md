## 0. Batch `split` (18:02): `build` = cacheable artifact, install = local, idempotent, receipt-checked

Measured first (g41-dash3, 10.0 s by product.py, which samples every 5 s, so the real wall lies in 5-10 s like the course's 10.1): the uncached build action itself costs 0.79 s Bazel elapsed (course hot: 0.16-0.37 s); the other ~9 s are the outer door, admission, deps, graph memo hit and `plan reused … (2.2 s)`. So the split buys ≤ ~0.6 s of wall on a pure no-op; its larger value is that a `:build` no-op starts no process and that the artifact is content-addressed by Bazel.

Why not "key on installed.json": a cached action cannot restore an installation it did not write (edit A→B→A→B: the 4th run hits the key recorded by the 2nd while the 3rd installed A). So the cacheable thing must be a plain, restorable output, and installation a separate local step:
- `build` (project.json): `cache: true`, class `deterministic`/`pure-function-of-inputs`, inputs = compile's (`default`, `^default`, `reads`, `cargoToolchain`) + root Cargo/toolchain files + the out-of-module-root dirs the binary includes (TUI `#[path]` modules, element TUI targets, generated axes, the process storage schema; measured from the binary's dep-info: 50+ files outside every crate module), output = `{workspaceRoot}/.🧬semio/🦑️repo/⚡️cache/🎛️dashboard/{options.env.SEMIO_BUILD_MODE}/artifact` (executable + `artifact.json`). Its action (only on a key miss) asks `currentDashboardArtifactV1` first and runs no nested compile when the artifact is current; otherwise nested compile → `exportDashboardArtifactV1` (copies the published binary under the exclusive `artifact:` lease, clone-copy, atomic renames).
- Records: one schema for artifact and installation (version 5; `path` differs). `compiled` = Cargo's whole freshness basis (dep-info files + every crate manifest + workspace manifests/lock + toolchain files + the package declaration) with the sha256 each file held at the build start. Rule (`changedDashboardSourceV1`): changed iff missing, or touched at/after the build start AND other bytes. So a revert/checkout of identical bytes, and an older artifact restored from the action cache, stay current (stat-gated: only touched files are read).
- `installDashboardArtifactV1` (local, idempotent, receipt-checked): refuses a missing/foreign artifact (`dashboard.artifact-required`, EN/DE) or one behind its basis (`dashboard.artifact-behind-sources`, names the file); when the installation already names the same bytes and the pin is in place it only refreshes the record (fresh stat-digest capture, no tools store, no lease); otherwise pins into the tools store. Used by `install`, by `📜️script.ts build` outside the build tool (the launcher's rebuild: runs `repo run …:build` only when the artifact is not current; the request stays the exact authorised one, no `--skip-cache` needed), by `dashboardExecutable` and the store-backed laws (`installDashboard` = export + install).
- Launcher contract unchanged (`staleDashboard`, `launchDashboard`, `rebuildDashboard`; the transpiled launch law passes untouched).
Laws (mirror `dhs`, graph-free envelope): `🧾️compiled` rewritten, 5/5 (10 authored mutations incl. 2 identical rewrites; independent SQL oracle now content-aware; artifact current ⇔ basis unchanged, installation stale ⇔ stat digest ∨ basis; executable in place; build target cacheable with exactly the artifact output, install side-effecting; schema v5 requires `digests`; install fast path refreshes the record without `.cache/b/l` and a revert ends staleness; missing/foreign/stale refused; build of a current artifact = one EN/DE line and no nested compile) — RED on base (`Export named 'currentDashboardArtifactV1' not found`); store-free installation laws 10/10; intent 10/10 (build now cached/deterministic); catalog 3/3 (2 new keys EN/DE, used); `tsc` on the 6 TS files: 0 new errors (1 pre-existing in `🏃️process/🧪️testing/🟨️bun/🚧️operands`, same on base); `scan.ts` 6 files, 0 bad.
Residual risks (stated, not hidden): (1) the graph's acceptance of a cached orchestration target with a `{options.env…}` output under `.🧬semio` is proven only by dh4 (precedent: `os-dev` uses the same token for an uncached output); (2) declared inputs vs. the dep-info: an undeclared input change makes `:build` hit with a stale artifact; installation then refuses it by name (never installs a stale binary), and `build --skip-cache` after removing the artifact directory rebuilds; (3) the first `repo dashboard` after landing installs once (the v4 installation record is refused as foreign: version 5).

Answers to the brief's questions:
- Outer action: re-executes every run BY DECLARATION (`no-cache`), not by a cache miss; `3 processes: 1 disk cache hit (ui-styling-tokens:generate), 1 internal, 1 worker (build)`.
- Nested run: own slot (dashplan works: the outer s4 kept `plan reused` in g25-dash2), graph from the pinned generation but still a graph child, nested plan never reused (control URL).
- Cargo fingerprinting: cargo is a no-op (86/86 fresh), ~10 s of the 52 s compile action; the rest is orchestration.
- Binary replacement lease / `repo dashboard` holding the binary: not a factor. Install pins a content-addressed immutable directory (same digest every run) under `artifact-capture` (exclusive, < 0.5 s); a running `semio` holds `artifact:<its dir>` shared, never in conflict. No human dashboard ran in any gate window.
- Measured read-only on live (`bun C/dashhot-tools/stale.ts /Users/ueli/Documents/semio`): the installed dashboard IS current for its recorded sources (1136 files, executable bytes + permissions match); that check costs 26-33 ms / 77 MB. Every 140-216 s run rebuilds exactly what is installed.

Soundness hole found in the existing freshness rule (`staleDashboard`, used by every `repo dashboard` launch): its stat digest walks the crate roots and SKIPS `.ts/.md/…` and everything outside the roots, but the binary's own Cargo dep-info (`…/t/<hash>/prototype/semio.d`, 452-458 files) includes files it never sees: `🌱️value/🧬️schema` `include_str!("../../🟦️.ts")` and 6 schema JSON files under `📚️library/🏗️build/…` and `🔨️modules/🏃️process/📦️artifacts/…`. Proven on base (`bun C/dashhot-tools/holeprobe.ts <root> <scratch> 3`): editing such a file leaves `staleDashboard` = current. A `build` short-circuit on the old rule would have been unsound; the fix records the dep-info.

## 2. Batch `fresh`: a dashboard no-op runs no nested build (the no-op path becomes ~1-2 s inside the action)

Design (one rule in one place, schema-first, fail closed):
- The `compile` intent declares `sourcesRecord: "semio.sources.json"` (new optional intent field, only with `scope: binary`; schema + reader + Ajv fixture rows). `runDeclaredRustBuildV1` passes it to the existing native-build `sourcesRecord` option (already used by os-mcp): Cargo's own dep-info of the binary and the build start are staged beside the executable in the same atomic publication.
- `installDashboard` refuses a publication without that record and copies it into `installed.json` (schema version 4, new required `compiled: {builtAtMs, sources}`, paths relative to the installation root; constants in `definitions.CompiledSourceProtocol`).
- `changedDashboardSourceV1` = Cargo's rule (`cargoBinarySourcesFreshnessV1`, shared with os-mcp) over the whole dependency closure, on max(mtime, ctime) so a replacement that keeps old timestamps counts. `staleDashboard` now also answers `its compiled source <path> changed after the build that produced it` (closes the hole for `repo dashboard` launches too).
- `currentDashboardV1` (stats only): valid v4 record for host+mode, the SAME captured sources (roots, manifests, digest), no compiled source changed, immutable executable in place with recorded size and permissions. `buildAndInstallDashboard` asks it right after capturing the sources and then returns the installed executable without any nested run, printing one EN/DE line (`bootstrap` catalog key `dashboard.installation-current`).
- Laws wired into the official targets: `test-source-freshness` and `test-execution` now also run `🧪️tests/🧊️execution/🧾️compiled/🟦️.ts`; feature file gains 2 scenarios; README paragraph.
- Not covered on purpose (documented in README): a change of the build tool's own code does not make a current installation stale (same contract the launcher already had); `repo run @semio-tech/repo-dashboard-rs:compile` then `:install` forces.

Laws (mirror `dhm`, graph-free Script envelope `C/dashhot-tools/env-run.ts`):

| NEW `🧾️compiled` (4 tests): 8 authored mutations (crate edit, out-of-root include edit, included `.ts` edit, replace keeping timestamps, remove, unrelated edit, read only, nothing) decide stale = digest ∨ compiled; independent oracle = SQL over raw stat facts (bun:sqlite); executable removed/resized/re-permissioned → not current; record schema requires `compiled`; intent record name = installation record name; `buildAndInstallDashboard` on a current installation returns without the nested compile and prints exactly one line, on a stale one it goes on to build | RED (`Export named 'changedDashboardSourceV1' not found`; holeprobe: out-of-root edit → current) | 4/4 |

## 4. Not done / next (owners)
- True Bazel action-cache hit of the outer `build` (no action spawn at all): unsound as long as the action's effect is the installation (a cached hit cannot restore it; keying on `installed.json` fails on edit→revert→edit: the third run hits a key recorded by the first edit while the second installed the other binary). The clean form: `compile` becomes a declared Bazel dependency of `build` (the cache schema itself says a verb that re-enters the build tool should declare its targets as dependencies), `compile` gets a restorable output (the published binary + sources record) and `build` shrinks to the cheap install step. That removes A1-A4 (~60 s) from every REAL rebuild too (dashboard one-line edit target < 2 min). Owners: graph/orchestration + native-build.
- The nested run plans its graph in a child although the invoking build pins the generation (A1), and the rust graph phase (A2, ~30 s) runs every time: both only matter for real rebuilds after `fresh`.
- Existing `staleDashboard` reasons are English only (pre-existing); my new reason follows them, my new console line is EN/DE.
- If the gate's dh1 shows `Dashboard executable sources record required`: the nested compile did not publish the record (check `[nx-native] staged 2 deliverables`); revert `fresh`.
