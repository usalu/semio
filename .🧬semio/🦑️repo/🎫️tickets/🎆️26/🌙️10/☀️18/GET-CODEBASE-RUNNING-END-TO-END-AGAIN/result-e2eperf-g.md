## Design (landed, graph-free verified; official runs below)
- Shards (schema first): `🎓️teaching/🏛️architecture/📚️course/🎭️e2e/🔒️sessions/🔣️.json` is the shard table (`shared` = desktop, phone, layout, pets, parallel; `exclusive` = presence, shortage, away, faults, one worker, own proctor; layouts: dev = two stacks `[[shared],[exclusive]]`, rehearsal = one stack running both waves in turn because its release build bakes the proctor origin in). Schema `🧬️schema/🔣️.json`, vectors `🧫️fixtures/🔣️.json`, pure planner in `🔒️sessions/🟦️.ts` (`planStacksV1`, `scheduleStacksV1`, `allocateWorkersV1`, `workerBudgetV1`, `waveArgumentsV1`, `splitProjectArgumentsV1`).
- Gate (`🎭️e2e/🟦️.ts`): stacks come from the schedule (dev: `dev-shared` + `dev-exclusive` boot one after the other, then their Playwright waves run at once; granted stacks fewer than needed -> merged one stack per topology -> one after the other); every stack first runs the `boot` project as warm-up (so a cold dev server is warm before a wave and the second dev server finds the optimized dependency cache of the first: no two Vite optimizers race); each wave is one `playwright test` process with the projects of its shard and its workers; a wave with no matching test (`--grep`) counts as empty, all empty fails; `--project`/`--workers` forwarded arguments are cut per wave (`--workers` only for the shared shard).
- Workers: total budget = the worker policy's Playwright plan (`SEMIO_PLAYWRIGHT_WORKERS` override, cores of the grant, memory of the share) cut to the memory left after the stacks that run at once; stacks that run at once keep 1 worker each and share the rest among stacks with a parallel wave (16 GB profile: shared 3, exclusive 1).
- Config (`🎭️e2e/🎚️config/🟦️.ts`): no project depends on a project of another shard (no `boot` dependency, `pets` no longer behind `faults`, `presence` no longer behind desktop/phone/layout); `phone` fullyParallel.
- Spec change (pets owner area, minimal): the ladder + rope spec is split into two specs (`🪜️mischief-ladder-and-phone/🟦️.ts`: a ladder on a quiz's page, a rope on the home screen; helpers `lively`, `carriedOn`), so the longest spec no longer sits alone on the critical path. Spec count 76 -> 77 (`playwright test --list`: boot 1, shared 64, exclusive 12), plus one `boot` warm-up per additional stack.
- Laws: `🧪️tests/🎭️sessions/🟦️.ts` (12 pass, was 6): Ajv draft-07 agreement on the table and every vector, Python oracle (`C/e2eperf-g-tools/shards_oracle.py` reproduces every derived vector from its inputs: `python3 shards_oracle.py <table> <fixtures>` prints "oracle agrees"), config law (every Playwright project in exactly one shard, dependencies stay inside the shard), exclusive waves always 1 worker, never more workers than the budget. `🧱️local-stack` + `🎛️dashboard/🎚️parameters` 71 pass; `tsc` over the touched files 0 errors (13.6 s, 1.2 GB).

## What blocks the target (needs the capacity owners / gate-g)
1. Grant size (see FINDING above): an official admitted run sees `{jobs:1, cpu:1, memoryMegabytes:2048}`; the sharded gate then plans 1 stack and 1 worker: the control. The speed-up exists only when the run is granted what the gate needs: either the e2e task declares an envelope of its own (`cpu` 4, 6 GB) in the capacity policy / target metadata, or a runner marked `scope: run` counts on the whole grant of a single-task run (testmem-g open item 2). Not implemented here (library/process, gate rule); with `SEMIO_HOST_CAPACITY=off` the gate plans from the host share.
2. Staged batch `C/e2eperf-g-tools/staged/apply.py` (worker policy rows, see FOR gate-g above).
