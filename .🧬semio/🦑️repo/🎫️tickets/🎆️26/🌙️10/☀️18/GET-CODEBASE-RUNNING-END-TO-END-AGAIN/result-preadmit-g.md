## What was wrong
A no-op `run` (plan reused, every action a cache replay) waited in the machine-wide queue for the SAME grant as a real build (5.6 GB default, up to 13 GB learned), e.g. gate-g row 1: capacity wait 356 s for a run that then needed < 1.5 GB. Phase-g's phased reservation still reserves the highest phase to come at the door, and noop2-g could not shrink it at the door: the door does not know the graph freshness and a wrong forecast would under-reserve a run that then compiles Rust. The sound form needs a capacity UPGRADE primitive; it did not exist.

## Design (schema first, all texts EN + DE)
1. Upgrade primitive in the host-capacity gate (process module). A held grant of a run that was forecast quiet grows into its full request in the same fair queue:
   - Schema: `Request.quiet`, `Waiter.upgrade`, `Grant.{quiet,arrivedAtMs,upgradedAtMs}`, `Operation.forecast`, `memory.maximumQuiet`, `estimates.{quietReferenceMegabytes,quietShareBasisPoints,quietMinimumSamples,quietMaximumMegabytes}`, protocol `upgradeSuffix`, `upgradePollMilliseconds` (100), messages `quiet`, `upgrading`, `upgraded`, `upgradeWithdrawn`, `grantQuiet`, `waiterUpgrade` (EN + DE).
   - Decision (`evaluateHostCapacityV1`, still a pure function): an upgrade waiter REPLACES the held grant of its id: only the difference has to fit (the freed small reservation counts in both the observed and the budget room, the memory the run already holds is returned exactly), cpu, ramp slot and the "nothing of ours is running" override are accounted without the old grant. Law: an upgrade decides exactly as a fresh request in the world where the grant is released and its observed memory returned (200 seeded cases, plus the Python oracle). A quiet request passes the queue barrier (strict `queue-order`) only within `memory.maximumQuiet` grants, never becomes a barrier head and does not count as overtaking, so it can starve nobody (it is small, bounded and every hard stop still applies).
   - Fair queue position: the upgrade keeps the ARRIVAL the run had at the door (`Grant.arrivedAtMs`, also written into the queue file name): the run is never worse off than without the forecast and never better than asking for the full grant at the door would have been (a request that arrived after the run but before its upgrade waits behind it; one that arrived before it is served first). Aging and the bypass limits count from that arrival.
   - Atomicity: the holder is the only writer of its grant row. The upgrade is decided under the gate lock and the row is replaced in one atomic rename (new jobs, cpu, reservation, restarted ramp, `quiet` removed): the reservation never drops to nothing and never counts twice. While waiting, the small grant stays in the ledger.
   - Cancellation: any process of the run asks by writing `grants/<id>.upgrade` and polling the grant row (`requestHostCapacityUpgradeV1`, counted as an admission wait so a deadline whose clock stops at admission waits is credited exactly like at the door); aborting its control removes the request unless another asker of this process still waits; the holder withdraws the queue entry, keeps the small grant and says so (`upgradeWithdrawn`). A vanished request file is rewritten by a live asker. A nested invocation that inherits a quiet grant upgrades before its body. A failing quiet run is never parked for a restart.
   - Progress for waiters (EN + DE): `[capacity] run: work has to run, waiting 12s to grow the reservation from 1500 MB to 5632 MB: not enough free memory (... MB spare above the ... MB floor; N running, M ahead)`, `... reservation grown from ... MB to ... MB after ...s`, `repo capacity status` lists `quiet <id>` and `growing <id>` rows.
2. Forecast (`🌦️forecast`, pure): per class the runs that executed nothing are learned under `<class>~quiet`, the others under `<class>~busy` (peak against `quietReferenceMegabytes`, so the quiet size is an absolute number). The door forecasts quiet iff enough decayed quiet runs exist (>= 2), they are >= 80 % of quiet+busy, the NEWEST run was quiet (one busy run, i.e. the run after an edit, flips the forecast at once) and the learned quiet size is <= 4096 MB. A wrong forecast costs nothing: the upgrade protects, and its wait is the wait the run would have had at the door.
3. Wiring (library `withBuildCapacityV1`, Bazel only: `operation.forecast` is set for `run`, `run-many`, `affected`, and the tool must be `bazel`, because only Bazel's executors are gated): a forecast-quiet run takes the small `quiet` request (id of the full request, no queue barrier wait) and the handle carries the FULL envelope (jobs, plan), so the tool is told what it may use after the upgrade. `upgradeBuildCapacityV1` is called before: the Bazel planner child (plan not reused), a graph rebuild (`markBuildCapacityPhaseV1("rebuild")`), and the first Bazel action that really starts (the control server answers the action's `join` only after the upgrade, so a pure cache replay never joins, never upgrades and executes nothing: that is the definition of "executes nothing"). Learning: a run that executed nothing teaches only `<class>~quiet`, NOT the class of real builds (before, hot no-ops lowered the reservation of the next real build); a run that executed teaches the class as before plus `<class>~busy`.

## Limits and decisions
- The door forecast is class history (`~quiet`/`~busy`), NOT noop2-g's plan record: at the door neither the graph digest nor the world are known, and the record's key needs both. The plan record is consumed where it is sound: a plan-reuse HIT skips the planner and with it the planner upgrade (`if(reuse.result)return` precedes `upgradeBuildCapacityV1`), so a reused plan with replayed actions never leaves the quiet grant; a miss upgrades before the planner child starts. Every wrong forecast is caught by an upgrade trigger, so soundness never depends on the forecast.
- Upgrade jobs are pinned to the jobs the tool was told (`minimumJobs = preferredJobs` of the upgrade): the tool already got `--parallel=N` and the plan of the full envelope; under high cpu load the upgrade waits for load room instead of running with fewer jobs (the old door admitted reduced jobs). A forecast-wrong run under heavy load can therefore wait longer than before; memory pressure behaves identically.
- A tiny grant, not none: the small reservation keeps the ledger honest (the Bazel server is attached to the grant and its RSS counts) and gives the upgrade an identity and a queue position.
- Only Bazel (`operation.forecast` + tool `bazel`): the other executors (Nx, cargo, scripts) have no action gate, they keep asking for the full grant.
- Quiet reservation: bounded by `quietMaximumMegabytes` 4096 (the estimator clamps the ratio at 200 % of the 2048 MB reference), at most `maximumQuiet` 4 quiet grants beside each other, never when the quiet size would not undercut the upgrade target. The first two runs of a class after the apply ask for the full grant (no quiet history yet).
- The invocation budget: the wait for the upgrade counts as an admission wait (`beginAdmissionWaitV1`), so a deadline is credited exactly like for the wait at the door.
- A holder killed with SIGKILL leaves `grants/<id>.upgrade` (like `.attached` and `.phases` files today): ids are random, so nothing removes them yet (the grant directory has no GC of side files).
- Not run: Windows/Linux (no platform code beyond `fs` calls, same as the existing gate files), the real Bazel chain, `repo capacity status` against a live fleet.
