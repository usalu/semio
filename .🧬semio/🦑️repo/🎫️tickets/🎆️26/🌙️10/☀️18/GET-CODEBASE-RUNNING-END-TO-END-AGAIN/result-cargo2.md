## (1) Print-test lease-order rows (`cargo:configuration-view`, `cargo:configuration-publication`)
Live cause (both rows on every print-rs:test, test.log lines 140 and 963):
- `runCargoTestsV1` / `runCargoLintV1` (`🔨️modules/🏃️process/🧪️testing/🦀️cargo/🟦️.ts`) took the build lease (`semio.cargo.store-lease`, rank 2) FIRST, then opened the input scope whose repository port (`🎟️admission/🟦️.ts` `execute`) captured the configuration view (`cargo:configuration-view:N`, rank 1) -> row 1.
- The port held the compiler writer (`repo:compiler-writer:`, rank 7) around the whole continuation, and every plan step (nextest list, nextest run) opened a NESTED input scope inside it, which publishes and captures a configuration view again (`cargo:configuration-publication`, rank 2) -> row 2. That is also a `strictWaits` rule (writer holder requesting `cargo:configuration-`, enforced); it only did not throw because nothing contended.
Fix (cargofix's design, completed):
- neutral port `📥️inputs/🟦️.ts`: a view may offer `admit` (step admission); the continuation gets `admitArguments(args)` (identity when the port offers none).
- runners: ONE input scope; inside it the build lease, then planning + Source admission, then every step's arguments admitted under the held view, then `withWriter` around the compile/assert steps only. A build-lease release failure is reported to the original control after the scope settled (keeps the primary failure first, as before).
- repository port: offers `writer` and `admit` instead of holding the writer.
- `⚙️configuration/🟦️.ts`: `repositoryCargoConfigurationStepArgumentsV1(view,args)` renders a step by the view's own storage + profile rules (exactly what a nested scope would issue) and refuses a step whose `--config` selectors differ; helper `cargoHeadConfigurationArgumentsV1` shared with the `cargo config get` capture.
Order now: publication (2, transient) -> view (1) -> registry (2) -> store/build/custody (2) -> writer (7) -> compile; nothing is requested under the writer.

## (2) Print one-line edit (105 s): the edited crate compiled from scratch
### Why not incremental (root cause, fixed)
The unit-cache wrapper (`⚡️caching/🦀️cargo/🗃️unit-cache/📜️script.ts` `wrapRustcV1`) compiles only the FOCUS crates (the `-p` packages) with rustc's incremental session; every other unit goes through the shared cache and, on a miss, was compiled with `-C incremental` STRIPPED (`stripIncremental`). print-rs:test selects `-p semio-framework-print-tests`, so the edited crate `semio-framework-print` (a dependency) was a miss compiled from scratch: 46.3 s (g33p), 76.0 s (g31p), 69.7 s (g28p) (unit events, lane `p32deb6`: `miss semio_framework_print`, reason `source:` changed only). The lane holds sessions only for `semio_framework_print_tests` (34 MB).
Fix (batch `incremental`): a miss compiles the command line Cargo gave, so a workspace unit that Cargo compiles incrementally keeps its session in the lane and is still published (keys unchanged: the key already ignores the incremental directory; registry crates never get the flag). Miss events of such units carry the suffix ` incremental:lane`. Focus crates unchanged.
Measured (stable rustc 1.95, synthetic 12k-line crate, 256 CGUs, debuginfo 1, this host): non-incremental 17.1 s, incremental from scratch 17.6 s (+3 %), after a trailing one-line edit 2.3 s (7x); session 844 MB vs 243 MB outputs. Costs: +~3 % on the first compile of a workspace crate in a lane, and session disk (bounded by the existing collector: incremental sets first, 10 % share).
Law NEW `🗃️unit-cache/🧪️tests/🌱️incremental` (real Cargo + rustc, recording inner compiler): two edits of the dependency `core` of the focused `leaf` are misses that keep `-C incremental=`, are published twice, the lane's sessions equal those plain Cargo (third party) creates, another lane is served `core` from the cache, `CARGO_INCREMENTAL=0` keeps none; Python oracle over the recorded command lines and the plain target. ### Why "1 core" (finding: not the print limiter; no capacity change staged)
- The quoted line `[repo cargo] shared store, 1 of 10 cores admitted, rustc memory budget 2.6 GiB` is NOT in any print log; it comes from `bun repo cargo` compiles (course typegen `cargo test`: g31-course lines 1363/1538, g7/g12/g22/g25/g28). print-rs:test compiles through `runRepositoryCargoTests` (unit-cache lane, no scheduler, no compile-units plan, no jobserver override): Cargo runs with its default `-j` (10) and rustc keeps the authored `-Z threads=0`. The 46-76 s are the non-incremental compile, consistent with all cores (rustedit-g: 10 threads 67-87 s under load; 1 thread 500 s).
- Where 1 core does happen: `planCompileUnitsV1` (`🏗️build/🎟️capacity/🧮️units`) caps a compile at the jobs the door granted the run (`grantedJobs` from `SEMIO_HOST_CAPACITY_PLAN`). g31-course was admitted `with 1 of 8 job(s): the host cannot carry more right now` (fleet memory) -> `-j1`, broker budget 1/10 of the rustc share. A quiet grant grows (g33-course: quiet 1 job -> upgraded 8 jobs -> 5 cores), a REDUCED grant never grows when memory frees later, so the whole run stays at 1 core. The cap itself is consistent with the run's reservation (one Bazel job = one action of ~2 GB, 1 cpu in `kinds`), so widening it in compile-units alone would overbook memory.
- FOR capacity owner (quietfc/buildmem): (a) let a reduced grant ask to grow like a quiet one (same upgrade queue, keeps its position) and let compile-units read the CURRENT grant row instead of the plan frozen at admission; (b) the `kinds.build` row models a Cargo action as 1 cpu / 2 GB, a multi-core Cargo action needs its own class (cpu = planned units, MB = units x megabytesPerUnit).
