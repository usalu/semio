## Decision: Bazel's Remote Execution API over gRPC (subset, implemented in-house), not a private protocol

| Question | Evidence | Consequence |
| --- | --- | --- |
| Can Bazel hand actions to a non-REAPI backend? | Bazel 8.4.2 has exactly one remote-execution switch, `--remote_executor` (grpc, grpcs, unix); its other spawn hooks (persistent workers, dynamic execution, sandboxes) run on the local machine | A private protocol (the `semio` backend protocol) would leave every Bazel action local: "0 local spawns" would be unreachable. The wire protocol Bazel speaks is the only door |
| Can the HTTP cache of `remote-cache` stay beside the executor? | Probe on the pinned binary: `--remote_executor=grpc://… --remote_cache=http://…` answers `ERROR: Cannot combine gRPC based remote execution with HTTP-based caching` | The executor must serve CAS, action cache and ByteStream over gRPC itself, backed by the shared `remote-cache` store; the Bazel implementation drops its HTTP `--remote_cache` flag while an executor is configured |
| Where do the message definitions come from? | Bazel's own `A-server.jar` embeds the serialized `FileDescriptorProto`s that protoc generated for `remote_execution.proto`, `bytestream.proto`, `operations.proto`, `status.proto`, `error_details.proto` and the well-known types (`reapi_extract.py`) | The wire schema (96 messages, 5 enums, 6 services) is generated from those descriptors (`📡️wire/🐍️generator`); no field number is transcribed by hand and the same descriptors are the oracle of the tests |
| gRPC without a library? | Node's own `http2` module (a framework system library; Bun 1.3.14 supports h2c, trailers, flow control) carries the protocol; framing, status trailers, deadlines, cancellation, gzip frames and TLS are ours behind `startGrpcServerV1`/`connectGrpcV1` | No runtime dependency; `protobufjs`, Python and `curl` appear only as test oracles |

The neutral core is separate from the front end: `RemoteExecutionSchedulerV1` (queue, dedup, leases, retries, cancellation), the content interface `RemoteExecutionContentV1` (HTTP implementation for the shared store), the worker agent and the sandbox strategies know nothing about gRPC. A second front end (for example `--tool=semio` submitting its own tasks) would call `scheduler.execute()` directly; it is not built.

## Not verified / open

- Linux and Windows were not run (no machine): the Linux `bubblewrap` command line is unit-tested as an argument list only; `isolated-root`, process-group kill (`taskkill` on Windows), `COPYFILE_FICLONE` fallback and `node:http2` are portable APIs but unexercised there. macOS `darwin-sandbox` is exercised for real.
- The `bun repo remote-execution` path through `📜️script.ts` (issued envelope, `advanceScriptInvocation`) is staged but cannot run before the apply (live freeze); the command module itself is exercised with the same context shape, including `serve` with a real worker process.
- Real repository targets were not run remotely (no hermetic class is proven live yet; the law uses the generated hermetic workspace, the same rules and runner).
- `unix:` executor endpoints are not served (grpc and grpcs only); compression (zstd) is not advertised, Bazel runs with `--noremote_cache_compression` while an executor is on.
- Performance indications (shared host at load 26): see above; `FindMissingBlobs` costs one HEAD per digest against the HTTP store (parallel 32); a batch route on the cache server or an in-process store handle would remove that cost for 30k-file inputs.
- Network isolation is enforced on macOS (sandbox) and Linux with bubblewrap; on Windows and Linux without bubblewrap the private root alone applies (documented in the README).
- No GPU/`container-image` style platform pools beyond exact property matching; worker pools are the `--properties` mechanism.
