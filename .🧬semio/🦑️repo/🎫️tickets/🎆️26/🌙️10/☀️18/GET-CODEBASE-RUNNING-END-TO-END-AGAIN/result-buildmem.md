## 1. What holds the memory (evidence)
- Production: every print refresh (g27-print1 57 projects 10.0 GB, g31 9.2 GB, g32 92 projects 13.6 GB, g33 90 projects 15.0 GB peak tree RSS) infers in-process in the graph child; peak correlates with the grant the child's heap is told: g32 grant 8190 MB -> 13.6 GB, g33 grant 12185 MB -> 15.0 GB. `buildGraphChildHeapBytesV1` set `BUN_JSC_forceRAMSize = max(2 GiB, grant)`, and the memory governor budget is 0.5 x grant (4-6 GB above the baseline), so neither bound bites.
- Graph-free harness (`buildmem-tools/run.sh` + gram4's `full.mjs`, production parent loop `emojiProjectJsonNodes` in ONE process, cold scratch store, workers off as in production, concurrency 8, plan `{"jobs":8,"memoryMegabytes":8190}`), the 36 named heavy projects of the g33 refresh (`buildmem-tools/refresh-roots.txt`: framework, framework-rs, os-dev, repo-lib, print, ...). Time line (N36d): RSS climbs with each heavy project, the steps are framework-rs (159 k rows; 29 k with D1 walks), plugin-registry/framework-os-dev (TypeScript program of 1224 files), repo-lib, renderer-wgpu; footprint max 5.2 GB at the end of inference.
- Live data at the end of inference (after a full collection): 2650 MB (2235 MB with D1). Attribution by clearing one cache at a time (BMTRIAL, run t36): closure entries of `🧭️script-inputs` (`resetClosureEntriesV1`) 749 MB, `closureScriptsV1` (script input cache, still needed by later closure verification, so not released) 545 MB, settled reads 54, project images 45, source analysis images 25, interned strings 14+13, inventory memo 32, results 18; the rest (~1.14 GB) is loaded modules + TypeScript state. The production `release` frees 997 MB of 2241 MB on top of D1 (run DT36).
- Allocator: after a collection the freed pages stay mapped as reclaimable (`MIMALLOC_PURGE_DECOMMITS=1` and `Bun.shrink()` change nothing, micro test), so RSS is the high-water mark; what lowers it is collecting before the garbage grows, i.e. a smaller JavaScriptCore RAM size.
