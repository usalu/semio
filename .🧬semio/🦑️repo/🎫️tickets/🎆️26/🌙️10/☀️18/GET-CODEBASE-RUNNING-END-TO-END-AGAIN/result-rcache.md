# result-rcache: remote cache contract, Bazel and Nx renderings, own cache server

`C` = this ticket. `L` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`. `B` = `L/🏗️build`. Stage-only: nothing outside `C/` was written. Everything lives under `C/rcache-tools/` and is applied by `C/rcache-tools/apply.sh` after "PAUSE LIFTED".

## Verdict
One schema-first contract (`B/🏃️execution/🧬️schema/🌐️remote-cache.json`, authored defaults in `B/🔣️policy.json#remoteCache`) is rendered by both adapters and served by our own server (`bun repo cache serve`, Bun/TS stdlib only). A real Bazel 8.4.2 and a real, unpatched Nx 23.2.0 each build against that server and hit the remote cache after the local cache is gone; wrong tokens, read-only tokens and the token-on-disk question were tested with the real clients. One deliberate deviation from the brief (credential helper instead of `--remote_header`) is justified by measurement below.

## Findings that shaped the design (measured, not assumed)
1. `--remote_header=Authorization=Bearer <token>` writes the token to disk: Bazel 8.4.2 copied it into the output base `java.log` and into the build event JSON (`structuredCommandLine`, 5 hits). The adapter also passes the same `options` to `captureOwnedCommandV1(... "info" ...)`, whose failure message prints `args.join(" ")`. So the Bazel adapter renders the token through `--credential_helper=<cache host>=<helper>` instead. The helper holds only the variable name; the token travels as one entry of the Bazel client environment (Bazel passes the client env to the helper, verified: 200 responses with the token only in the env). After this change `grep -rl <token>` over output base, workspace and install base finds nothing (asserted by the real-Bazel test). Residual: Bazel records the whole client env as hidden `--client_env=` options in the build event stream; the adapter deletes that file right after reading it (`recordBazelBuildMetricsV1`), so the token is on disk only for the duration of one build. Option to close the window later: write the stream to a FIFO or scrub the line before it is written.
2. `writeBazelRuntimeV1` persists the complete Bazel environment object to `runtime.json`. The token is therefore NOT put into `environment`; the adapter builds `client()=()=>({...environment,...cache.environment})` used only for the three Bazel client calls.
3. Bazel's HTTP cache has no instance concept: `--remote_instance_name` is gRPC-only. The namespace therefore also travels as the first URL path segment (`--remote_cache=<endpoint>/<instance>`, `NX_SELF_HOSTED_REMOTE_CACHE_SERVER=<endpoint>/<instance>`), both verified against real clients; the flag is still rendered.
4. `--remote_cache_compression` has no effect over HTTP in Bazel 8.4.2 (a 872 byte blob above the 100 byte threshold was stored plain). It is rendered, the server accepts only plain bodies, and Nx reports the field as unsupported.
5. Nx 23.2.0 (`dist/src/tasks-runner/cache.js` `getHttpCache`, native `http_remote_cache.rs`): reads `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` and `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`, calls `GET|PUT <server>/v1/cache/<numeric hash>`. A 401 aborts the run ("Unauthorized"); the 401 response must be `text/plain` (otherwise "Misconfigured remote cache endpoint: Requests should respond with text/plain on 401s"). A 403 on PUT is ignored silently and the task succeeds, so read-only can only be enforced by the server's token scope. Nx has no switch for compression, download mode, timeouts, retries or withholding uploads: `cache remote status` prints these as `unsupported` and `uploadEnforcedBy: server`.
6. The repository's installed `node_modules/nx` is patched (frozen authorizers around `applyRemoteCacheResults`/`put`, "Immutable fixed cache custody") and cannot run in a scratch workspace; the real-Nx cross-check therefore uses a pristine nx@23.2.0 + `@nx/nx-darwin-arm64@23.2.0` assembled offline from the bun cache (`rcache-tools/assemble-nx.sh`, no network). Whether the patched Nx promotes remote hits in the real repo is not verified.
7. Bazel's task adapter restores snapshots from `bazel-bin`, so `--remote_download_outputs=minimal` would break restoration: the Bazel rendering refuses `minimal` (`restoresOutputs`), the committed default is `toplevel`.
8. Bun 1.3.14: `ReadableStream` async iteration and `reader.cancel().catch` fail on request bodies; the server uses the reader directly. Replying before the body was read made clients see "connection reset": the handler now drains the unread body (bounded) after every response, and Bun's own body limit is twice the entry bound so small oversize requests still get a clean 413 (30 of 30 repeated runs of the wire fixture pass).

## The contract
Schema `B/🏃️execution/🧬️schema/🌐️remote-cache.json` (draft-07, next to `💾️cache.json`): `Contract`, `Policy`, `Defaults`, `Names`, `ServerPolicy`, `Rendering`, `Probe`, `Status`, `Endpoint`, `Instance`, `Access`, `Download`, `Token`, `EnvironmentName`. Resolved fields: `endpoint` (http/https origin, no credentials/path), `instance`, `access` (read-only|read-write), `upload`, `compression`, `download` (minimal|toplevel|all), `timeoutSeconds` (1-600), `retries` (0-10), `auth.tokenEnvironment` (name of the variable that holds the token; never the token). Effective upload = `upload && access==read-write`. Off unless `SEMIO_REMOTE_CACHE_ENDPOINT` is set; env names `SEMIO_REMOTE_CACHE_{ENDPOINT,INSTANCE,ACCESS,UPLOAD,COMPRESSION,DOWNLOAD,TIMEOUT_SECONDS,RETRIES,TOKEN_ENVIRONMENT}`; token variable default `SEMIO_REMOTE_CACHE_TOKEN`. gRPC/unix endpoints of the old Bazel-only switch are dropped (HTTP is what both tools speak).

## Deviations from the brief (explicit)
1. Bazel token delivery via credential helper instead of `--remote_header` (finding 1).
2. Bazel `--remote_instance_name` is rendered but the namespace is additionally the URL prefix, because HTTP has no instance field (finding 3).
3. Verification overlay of the storage and operations tests runs in `/private/tmp/rco` (copy of the overlay) because the repository's own 256 UTF-16 unit path rule rejects `⚡️caching/.../🏪️store/🟦️.ts` at the overlay's depth inside the ticket (266 units). The contract/server/real-client tests run inside `C/🗑️generated/rcache-overlay`. Bazel scratch output bases lived in `/private/tmp/rcache-bz` (macOS needs an ASCII output base). All of it is removed. The CLI runs created two APFS disk images under `/private/tmp/rco/.cache/b/{l,o}`; both were detached and deleted.
4. The Nx cross-check needs a pristine nx (finding 6); the gate variable is `SEMIO_TEST_NX_BIN`.

## Not run / open items
1. Not run: the production Bazel adapter end to end with a remote cache (`bun repo --tool=bazel run`, blocked by the freeze and dependency sync); Windows and Linux (the `.cmd` credential helper and `Bun.serve`/`link` on NTFS are untested; the sh helper and server ran on macOS arm64 only); the taxonomy verification of the new folders (`🌐️remote-cache` with `💾️store`, `🖥️server`, `⌨️command`, `🧪️tests` under `🏗️build`; `🌐️remote-cache` under `🏗️bazel` and `⚡️caching/🚀️bootstrap/🛠️tools`; I checked that no sibling uses the emoji `🌐️`, nothing more); the dashboard registry tests for the two new root tools; the repository's patched Nx with a remote cache.
2. The server store lives at `.cache/remote-cache` (self-bounded) and is not one of the finite cache partitions (`rust|tools|graph|dependencies|products|diagnostics|nx|leases`); moving it into a partition image needs the owners' decision.
3. Bazel build event stream still carries the token transiently (finding 1); FIFO or scrubbing would remove that window.
4. Nx cannot withhold uploads: `access=read-only` or `upload=false` relies on the server rejecting writes; `cache remote status` reports `uploadEnforcedBy: server` and does not probe writes (it would store data).
5. No per-request log line by default (the handler has an `onRequest` hook; a `--verbose` flag can print it).
6. Compression over HTTP is not implemented in client or server (finding 4).
7. The `.bazelrc` edit and the policy/schema edits re-key every Bazel action (implementation identity); expect one cold run after applying.
