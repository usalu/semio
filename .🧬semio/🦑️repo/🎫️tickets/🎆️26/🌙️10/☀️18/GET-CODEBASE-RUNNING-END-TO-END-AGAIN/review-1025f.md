### 5. dflake-d `bind_guard` (`🌀️daemon/🚚️transport/🦀️.rs:114`): correct, three small gaps
Reasoning (own): the guard is an advisory `flock` (`File::lock`, MSRV 1.95 >= 1.89) on `<runtime>/bind.guard` held in `Listener::bind` across `lock_runtime_file` (claim) + `sweep` (probe of every other `.lock`) + bind + `record_endpoint`, bound with `let _guard` so it is released on every exit path. The kernel releases it when the holder dies at any point, so a crash while holding never leaves a stale guard; the guard file itself is never removed (harmless, 0 bytes). Both lock users (claim and sweep) are inside the guard, so the probe/claim race the comment describes cannot happen between daemons; the only unguarded `try_lock` users are the workspace lease `daemon.lock` (different file, different directory) and preferences. The inode re-check of `lock_runtime_file` covers the unlink-by-`Drop` race. The in-process test (16 roots x 24 rounds, threads) uses separate open-file descriptions, which conflict like separate processes under flock, so it does exercise the kernel path.
Windows: no counterpart is needed or present; the pipe is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, which is the atomic single-listener claim (ERROR_ACCESS_DENIED maps to AlreadyExists), and there are no lock/socket files to sweep. Linux = macOS code path (`cfg(unix)`).
Gaps: (a) `guard.lock()` blocks without deadline or cancellation (AGENTS.md: cancellable expensive operations): a SIGSTOPped or wedged holder blocks every daemon start of that runtime directory for good; use a `try_lock` loop with a bounded deadline and a clear error. (b) `Listener::drop` unlinks socket and lock without taking the guard; a restart that opens the old lock inode in the instant before the unlink fails `try_lock` and reports "already listening" instead of retrying once (very narrow window, only for stop-then-start without waiting for exit). (c) No cross-process law; the thread test cannot show a holder that dies while holding.
