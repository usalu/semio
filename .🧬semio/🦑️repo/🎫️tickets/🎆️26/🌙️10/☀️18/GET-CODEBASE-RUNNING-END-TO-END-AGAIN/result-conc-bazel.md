`C` = this ticket. `Z` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/🔧️tools/🏗️bazel`. Tools and staged set: `C/conc-bazel-tools/` (`staged/` = 8 new files, `edits.py` = 50 anchored edits in 8 existing files, `apply.py`, `mkoverlay.py`, `mkov.sh`, `verify.sh`, `tsc.sh`, `mkfixture.py`, `exp/` = the scratch harness of the experiments).

**READY** (group 1) and **READY2** (group 2, below) (staged, verified in an overlay with real Bazel 8.4.2, NOT applied; waits for the coordinator's GO). `python3 C/conc-bazel-tools/apply.py --root <checkout>` against the live tree: `summary {"new": 8, "pending": 50} problems 0`, dry run writes nothing. Idempotent (second run all `applied`), `--undo <backup>` restores, drift is refused per anchor, `bases.json` lists the staged base hashes.

## What was wrong (measured, not inferred)
Scratch fixtures, provisioned Bazel, one shared disk cache, load average 18-26 on 10 cores.

| # | Experiment | Result |
|---|---|---|
| E1 | 3 builds, 3 workspaces, 3 output bases, in parallel | wall 16.3 s for 3 x 5 s actions, no `Another command` message. The current per-selection output bases do not meet in one lock |
| E2 | 2 builds of different targets in ONE output base | 11.4 s instead of 5.3 s and `Another command (pid=...) is running. Waiting for it to complete on the server`. This is the serialization the brief names: it hits every two commands that share a server (same selection, `affected`, a continuous task and a build) |
| E3 | rebuild in a fresh output base, other package path, same content | `INFO: 2 processes: 1 disk cache hit, 1 internal`, marker file untouched: action keys do not depend on output base or package path |
| E4 | `--repo_contents_cache=<shared>` with two fresh output bases | one cache entry for `@platforms`; `external/platforms` in both output bases is a symlink into it: external repositories are fetched once |
| E5 | one slot, workspace directory changes | server restarts (warning `needs to be killed`), 2.9 s; the same workspace again 0.19 s. Hence the affinity rule below |

The audit (`C/audit-locks-1020e.md`) ranks 8 (`bazel-snapshot-restore`, one key per checkout) and 10 (one output base per workspace) are covered. What the old scheme really did: one output base **per selection hash** (unbounded count and disk: each holds an execroot, external links and a JVM of up to 2 GB heap), one global restore lease, and for `affected` a fixed workspace plus an exclusive lease.

## Design (schema-first, tool-neutral contract, Bazel rendering in the adapter)
New module `Z/🧵️sessions/` (`🧬️schema/🔣️.json`, `🟦️.ts` pure, `🔌️port/🟦️.ts` repository leases and files, tests and fixtures):

1. **Slots instead of per-selection output bases.** `s0 ... s{K-1}`; slot `sN` owns the output base `<products>/bazel/outputs/server/sN` (16 characters shorter than the hash name, ASCII by construction: macOS 256 / Windows 260 / Linux non-ASCII guard of `result-bzl-sandbox.md` and the short-path budget of `handoff-bazel-short-paths.md` only gain slack) and the packages `<products>/bazel/workspaces/sN/<selection key>` (at most `retention.packagesPerSlot` = 6 per slot, 7 days).
2. **One holder per slot, no server lock wait possible.** A session claims one slot with an exclusive repository lease (`bazel-slot-sN`, non-blocking probe, like the compiler capacity cores). The same selection run by two agents at once lands in two slots with two private packages and two servers, sharing every action result through the cache. Generated packages cannot collide: the package directory contains the slot.
3. **Fair waiting.** Sessions order themselves behind a queued picker lease (`bazel-slot-picker`), the head polls (250 ms), prints `[bazel] all 3 Bazel server slots are in use; waiting for one (12 s)` every 5 s (EN/DE via `SEMIO_LANGUAGE`/locale), honours cancellation and the invocation deadline.
4. **Affinity.** A slot remembers the key of its last selection and the keys of its kept packages (`sN.session.json`, valid only while the output base exists, so reset, cache clear and an unmounted partition never leave stale affinity and nothing is written below an unmounted partition). Order: slot whose last selection it is (warm server + warm package) > slots that keep the package > never used > least recently used. An edit-run-edit loop of one agent therefore keeps its server.
5. **Bounded servers from the host budget.** `K = clamp(floor(max(0, memory - floor) * 3000bp / residentMB), 1..6)` and `K <= cores / 2`, with the host capacity floor rule (`hostCapacity.memory`: 20 % clamped 4-8 GB). This host (32 GB, 10 cores): floor 6553, budget 7864 MB, 2560 MB per server => **3 slots**; 16 GB laptop 1; 128 GB 6. `SEMIO_BAZEL_SERVERS=N` (1-99, anything else is refused) overrides. Server heap comes from the plan (`--host_jvm_args=-Xmx<heap>m`, replaces the literal 2048), idle exit stays `policy.serverIdleSeconds` (120). Local resources: the capacity grant when present, else `--local_resources=cpu=cores/K`, `memory=share/K` so K concurrent servers never oversubscribe together.
6. **Nested sessions cannot deadlock.** A session started inside a Bazel action (`SEMIO_BAZEL_SELECTION_CHAIN` set) gets 4 overflow slots on top, so it never waits for the slot its own parent holds.
7. **Slot taken outside every store scope.** `runBazelTasksV1` and `bazelAffectedProjectsV1` hold the slot first and open the tools/dependencies/products stores inside it, so a waiting session holds no image lease (lock order: capacity -> slot -> storage; compatible with the conc-leases classes, `bazel-` is already the `tool-singleton` prefix).
8. **Shared content-addressed cache layers.** Disk cache `--disk_cache` (Bazel's own concurrent-safe CAS + action cache with its GC lock, shared by every slot, bounded 40 % of products); fixed module catalog repository cache (existing); NEW `--repo_contents_cache=<products>/bazel/contents` shared by all output bases (E4); install base shared (existing). The optional remote layer is unchanged and sits on top: `SEMIO_BAZEL_REMOTE_CACHE=grpc://127.0.0.1:8980` (bzl-rbe Buildbarn CAS/AC) gives disk-first, remote-second reads and, with `..._UPLOAD=true`, shared writes across machines/devcontainers. I did not add a local CAS daemon: the shared disk cache already is the zero-process local CAS, and a daemon would be a second copy of the same bytes.
9. **Restore lock per tree, not per checkout** (`audit-locks` rank 8): `bazel-restore:<path>` hierarchical locks, roots exclusive, ancestors shared. Two restores conflict exactly when one tree contains the other (proven against a brute-force path oracle); unrelated outputs restore side by side; more than 64 resources fall back to the exclusive root resource that every restore holds shared. Keyed by output root rather than by snapshot identity because the conflict domain is the checkout path being written, not the snapshot.
10. **GC of slots** (`collectBazelSessionsV1`, run best-effort by every session after it has its slot and its stores): packages beyond count/age (newest and the slot's last never), output bases of slots beyond the current capacity or idle > 14 days, **foreign entries** (the hashed output bases and packages of the old scheme, one-time cleanup, no compatibility layer). A held slot is never touched; a server is stopped first by removing its `server.pid.txt` (no Bazel binary, no JVM start, same mechanism as `cache clear`); read-only Bazel trees are made writable and retried. `cache clear` now removes slot bases and `*.session.json`.

## READY2: group 2, service slots (long-running watch/serve/dev sessions never pin a build slot)
Staged as the second group of the same apply tool: `python3 C/conc-bazel-tools/apply.py --root <checkout> [--group 1|2|all]` (default `all`; group 2 needs group 1, applied before or in the same run; dry run on the live tree for `all`: `new 8, pending 58, upgrade 8, problems 0`; group-2 files may replace only the group-1 version of themselves, anything else is a conflict). Group-2 sources are `C/conc-bazel-tools/staged/g2/`.

- **Two slot classes, two queues, two bounds.** Build slots `s0..` (K, from the host budget, unchanged) are held only while a build cycle runs. Service slots `d0..` (default 4, `servers.serviceMaximum`, override `SEMIO_BAZEL_SERVICES`, build count still `SEMIO_BAZEL_SERVERS`) are held for the lifetime of a session that launches long-running tasks. A selection is a service when any task of its plan is `continuous` (`bazelSelectionV1`); everything else, including each rebuild cycle of `watch` (its children are separate invocations) and `affected`, is a build. Each class has its own fair picker lease (`bazel-slot-picker`, `bazel-slot-picker:service`), so a queue of waiting dev servers never delays a build and vice versa; the waiting line names the class (`... Bazel service slots are in use ...`, EN/DE).
- **Why a separate class instead of releasing between cycles.** The service binary runs out of its output base (`bazel run` launcher, runfiles). Handing that output base to a build session would rebuild into the directory a running executable lives in (in-place overwrite of a running binary kills it on macOS and fails on Windows). Service slots are never used by builds, so a running service is never touched, and the shared caches (disk cache, repository cache, repository contents cache, optional remote cache) are the same as for builds, so a dev server still starts from cached dependency builds.
- **Memory.** After the launch build the server of a service slot idles out (`--max_idle_secs=120`), so a pinned dev server costs a slot name and an output base on disk but no JVM; JVMs exist during builds and launches only. Worst case K + 4 JVMs at once, in practice K plus the services that are launching right now; every `run`/`watch` invocation is still admitted by the host capacity gate.
- **Everything else follows the class:** garbage collection treats `d0..` as valid up to the service count (retired service slots are collected), `cache clear` removes them, the planner workspace shape check accepts `[sd]<n>/<16 hex>`, the status table lists both classes.
- **Verification (overlay, groups 1+2):** sessions suite **21 pass** (new: 4 pinned services + 3 builds all admitted without a waiting line, a fifth service waits on its own queue while a freed build slot is granted at once, DE wait line, per-class queues through the real production port, service override/refusals, GC rows for service slots against the Python oracle); `tsc` strict clean; existing adapter suites identical to the unpatched baseline (storage 7/1, operations 10/0, implementation 0/1 pre-existing, actions 9/1 pre-existing, workspace 4, platform 0/1 pre-existing, delegation 1, sources 9, fingerprint 2, outputs 2, closure 8); the 7 publish-function assertions re-checked by AST on the patched file. **Real Bazel conformance with 3 service sessions pinned for the whole scenario** (load 32): 3 builds in slots s0/s1/s2 in parallel, wall 15.2 s (14.8/14.9/14.3 s each), no waiting line, no lock wait; 4th session in a fresh slot `1 disk cache hit` 0 spawns; warm return; control shows the lock wait. Group 1 alone is unchanged and still green.
- **Not verified:** a real `bun repo --tool=bazel watch`/`run <serve>` end to end (needs the live adapter); that Windows/Linux treat a launcher in an idle output base identically; the exact class of every real target (it uses the plan's `continuous` flag, the same flag the adapter already uses to start services).

## Behaviour notes and open items
- Long-lived sessions are solved by group 2 (next section): they no longer pin a build slot.
- `bazel-metrics` (activity ledger) is still one short global lease per build, `parallelism:false` tasks are still only exclusive inside one package (as before: the lock is keyed by package directory), `bazel-modules-<identity>` unchanged.
- No CLI surface yet: `bazelSessionStatusV1`/`renderBazelSessionStatusV1` (EN/DE table) and `collectBazelSessionsV1` exist but are only called by the adapter; `repo cache sessions status|gc` needs a catalogue entry and help snapshots (conflicts with mem-gov/regen-help), so left for a follow-up.
- The deletion of the old hashed output bases is a one-time GC, not a migration script, and runs only for entries that do not match the slot pattern.
- One accidental side effect: an early `bazel shutdown` in my scratch harness without `--install_base` may have extracted an install under the default `/private/var/tmp/_bazel_ueli`; not removed (a peer's server uses that directory).
- Scratch servers and `/private/tmp/conc-bazel` removed; `C/🗑️generated/conc-bazel` removed after its numbers were copied above.
