## 1. What changed in the architecture (answers the audit-swap finding)

Neutral code no longer names a backend on the paths that run, plan, cache, set up or reset. One authored registry `B/🔌️backends/📋️registry/🔣️.json` has one row per backend (nx, bazel, semio): title EN/DE, kind, the adapter module, the conformance driver module, the dependency model, the per-operation support, the claim for each of 17 capabilities with EN/DE notes, and the declared native-snapshot protocol. Neutral code reaches a backend only through `loadBuildBackendV1(id)` (`B/🔌️backends/🟦️.ts`) and the neutral interface `BuildBackendV1` (`setup`, `reset`, `prepareStorage`, `cache`, `remoteCache`, `execute`, optional `affectedProjects`, `bootstrapArguments`).

- Dispatch (`B/📜️script.ts`): the `selected.tool==="nx"` branch, the Bazel branch with its direct adapter import, the `tools setup`, `reset`, remote-cache and cache-tool ternaries are replaced by registry lookups. The code moved verbatim (cut by `T/gen-backends.py`, slice hashes guard against drift) into `B/🔧️tools/🧶️nx/🔌️backend/🟦️.ts` and `B/🔧️tools/🏗️bazel/🔌️backend/🟦️.ts`.
- Closed lists replaced by registry-derived values: `BuildToolNameV1`, caller capability types (+ `.d.mts`), `parseBuildInvocationV1` (validates against the registry), `prepareBuildToolStorageV1` (now delegates to `backend.prepareStorage`), remote-cache tool/protocol/mechanism types, incremental/parity/ci-report tool types, 7 schemas (`BuildTool`, caller/authoring patterns, remote-cache, operations `ToolName`, incremental, parity, ci-report), the incremental/concurrency `--implementations` default and error texts, the catalogue (`valueName`, `tools setup [...]`), the child launch computation (`buildBackendBootstrapArgumentsV1`), and the help renderer (`{backends}` expands to the registry alternation before layout).
- The 19 per-tool `implementations` rows of the catalogue are gone (schema property removed): per-operation support lives in the registry row. `NX_DAEMON` and `SEMIO_NX_NATIVE_SOURCE_SNAPSHOT` literals in `B/📥️inputs/🎯️selected/*` come from the row that declares `nativeSnapshot`.
- `B/🧮️task-model/🟦️.ts` is the neutral planner, input expansion and cache decision (needed by the in-house engine). A differential test proves it equals `planBazelTasksV1` on dependency patterns, configurations and `excludeDependencies`; the Bazel adapter is NOT re-pointed to it in this set (its source-reading tests would move), see section 7.
- Adding a backend now touches: its own module (`B/🔧️tools/<id>/...`: backend, conformance driver) + one registry row + a regenerated help snapshot (column width grows with the alternation; `regen-help.py` does it). Proven by the law tests (section 4) and by adding semio as the third row.

Neutral-literal ratchet (`"nx"`, `"bazel"`, `tool==="nx"|"bazel"`, the closed unions) over the build library outside the adapters, tests and the new modules: 190 hits in 40 files before, 93 hits in 28 files after. The law test `🔌️backends/🧪️tests` keeps 18 cleaned files at zero and caps the 14 remaining ones.

## 2. The conformance suite (language-agnostic, schema-first)

`B/📐️conformance/`: schema `🧬️schema`, 20 scenarios in `📋️scenarios` (EN/DE titles, 16 evidence links), a self-contained stub task body `🎭️stub` (reads declared files, writes outputs that are a pure function of them, leaves start/end markers no backend can fake), the judge and report `🟦️.ts`, the runner `🏃️runner`, `repo conformance list|plan|run` in `⌨️command` (catalogue row, flags `--scenario`, `--implementations`, `--keep`, `--file`, `--json`, EN/DE, progress, cancellation), and the independent Python oracle in `🧪️tests/🐍️oracle`.

- Workspace: 15 stub projects (diamond, cut-off pair, multi-output, failing, failing test, slow, single-flight, three parallel). The same data becomes an Nx workspace, a Bazel workspace (rule instances running the stub) or the neutral graph of the in-house engine; ground truth for "executed" is the marker file, not the backend's own record.
- Capabilities (17), one or more scenarios each: plan, run (cold, ordered, lazy closure), cache-restore (also after deleting outputs), invalidation, early-cutoff, uncached, outputs (nested), failure-isolation (+ failure never cached), test-results, affected, cancellation (stops within 5 s, nothing published, next run completes), progress, parallelism (bound and overlap), concurrent-invocations, single-flight, remote-cache (fresh checkout, empty local cache, shared server), run-record.
- Verdicts combine the registry claim with the measurement: `pass`, `gap` (claimed missing and failing = documented), `regression` (claimed and failing), `stale-claim` (claimed missing but passing), `unobserved` (the binding gives no way to observe it: counted apart, never a pass), `error`.
- Reuse, not duplication: each scenario cites the existing evidence it generalises (`incremental` scenario ids, `parity` sample ids, `concurrency` workloads, Bazel contract phases); a test verifies every cited id exists in those suites. The real-repo harnesses (`repo incremental`, `repo verify build-parity`, `repo concurrency`, `workspace:test-build-tool-bazel`) stay the level-2 evidence; the new suite is level 1 and runs in seconds to minutes with any backend that has a driver.

## 3. The third backend, `--tool=semio`

`B/🔧️tools/🐙️semio/`: an in-house engine behind the same interface, no external tool. Planner = neutral task model; action key = SHA-256 of the canonical task identity, resolved execution, arguments, declared outputs, the contents of every selected input file, environment inputs and the output digests of the dependencies (so equal outputs cut off dependents, like Bazel); a content-addressed local store (blobs by digest, entries by key, atomic temp+rename, damaged entries are misses); single-flight locks across processes (`wx` lock files with heartbeat, dead or stale owners broken); a scheduler with a parallel bound, failure skipping, `--bail`, cancellation that kills the whole process tree, progress events and a run record; a shared-cache client for the in-house server's write-once blob route (`/v1/cache/semio-<key>`, bearer token, every failure is a miss); `repo inputs`, dry-run plans, `affected` through the neutral rule, store receipts, EN/DE messages. Fail-closed: any input it cannot interpret (runtime, unknown objects) makes the task uncached.

Status against the suite: all 20 scenarios pass (in this overlay, real processes, real shared-cache server). What it lacks, exactly: (a) it has only been run through the engine and its conformance driver, NOT through `bun repo --tool=semio` on the live checkout (no GO yet); (b) `run --watch=<target>` and continuous tasks are refused (clear bilingual error); (c) `repo-exec` environment, Cargo directory pinning, orchestration manifests (nested `repo` calls get the tool through the environment only), hermetic/remote-execution classes and `bazel test` classes are not reproduced; (d) closure markers and `runtime` inputs make a task uncached instead of being resolved; (e) the store is a directory of the products partition, not yet a registered area of the cache ledger/GC (`cache gc` does not size it), and file digests are memoised per process only (hot-cache executor owns the persisted stat cache); (f) the inventory lists the whole workspace per run (a pathspec-limited list would be faster on this repository).

### 9.6 READY4: audit-staged-1021b findings
- BLOCKER, store lock (`semio_store.ts`): the lock file now carries a token (pid, random nonce, time). A failed refresh (`touch` rejects) or a refresh that finds another token aborts the holder's work through the second argument of the body (`held` signal) and fails the call with an EN/DE reason; nothing is swallowed. Release and takeover are compare-and-swap: the lock is renamed to a tombstone, what was moved is verified (token for release, still stale for takeover), then unlinked, or linked back without clobbering a newer lock. A holder that finds at the end that it no longer owns the lock fails with "taken over / übernommen". The leases module was checked: it needs an issued invocation phase (`control`), which the engine's store and its conformance driver do not have, so the lock stays private to the store (documented in the docstring). Lock timing and the touch are injectable (`SemioStoreV1(directory,{touch,timing})`). Tests: failed heartbeat aborts with both languages; takeover then old holder's release leaves the successor's lock and leaves no tombstone; a foreign token found by the heartbeat aborts the holder.
- HIGH, git fallback (`semio_scheduler.ts`): the inventory walks only when the workspace is no Git work tree or the Git tool is missing (`ToolErrorV1` code `tool-missing`); any other Git failure fails with status and stderr in EN and DE. Test with a broken `.git`.
- HIGH, `Bun.Glob`: gone from `taskmodel.ts`, `conformance.ts`, `semio.ts`, `semio_store.ts` (they use the runtime-seam `GlobV1`, new token `@@RUNTIME@@`) and from `stub.ts` (self-contained matcher and walk for `*`, `**`, `?`, `{a,b}`, cross-checked against picomatch in a test).
