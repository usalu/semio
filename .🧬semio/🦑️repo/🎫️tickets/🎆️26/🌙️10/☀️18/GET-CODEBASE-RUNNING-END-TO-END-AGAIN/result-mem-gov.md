## Problem
Watchdog kernel panics 09-28/29 and 10-20 16:03 under load: `show projects` (~4 GB) + several builds + agents + a codex peer. Nothing in `bun repo` knew what the machine could carry, so every command started immediately and each tool (nx, Bazel, cargo) sized itself to the whole host.

## Design (schema-first, tool-neutral, one admission domain per user)
- Schema: `P/🏗️build/🌡️host-capacity/🧬️schema/🔣️.json` (Policy, Host, Request, Waiter, Grant, Decision, Evaluation, Plan, bilingual en/de messages). The authored budget lives in `B/🔣️policy.json` under `hostCapacity` (staged `policy-host-capacity.json`):
  - memory: free-memory floor = 20 % of host memory clamped to 4-8 GB (6553 MB on this 32 GB host); admission only while free memory minus floor minus the unrealized part of running reservations covers the request; total reservations stay under the budget share;
  - CPU: load ceiling 2 per core, counted together with the cores of running grants; swap ceiling 25 % while swapping, swap-out rate limit 64 MB/s; memory pressure `critical` admits nobody, `warn` waits;
  - open files (new this round): machine-wide open file table must stay under 80 % of its maximum (macOS `kern.num_files/kern.maxfiles`, Linux `/proc/sys/fs/file-nr`; Windows has no machine-wide table, so unknown = never blocks);
  - hdiutil attaches (new this round): fewer than 32 attached disk images (macOS `hdiutil info`, bounded to 3 s and optional; Linux loop devices in `/proc/mounts`; Windows unknown). `files` and `attaches` are soft reasons like raised pressure: waited out, and overridden after 120 s only when nothing of ours is running (a leaked image never goes away by waiting). Memory and the hard pressure/swap reasons are never overridden;
  - per-kind estimates (test 1.5 GB, check 4 GB, generate 1 GB, build 2 GB, script 0.75 GB, service 2 GB) and per-operation shapes (`tasks` = fixed block + jobs x kind, `fixed` = one block: `show`/`graph` 5 GB, `dependencies` 6 GB).
- Decision (`📏️decision`): pure function `evaluateHostCapacityV1(policy, host, ledger, waiters, now)`; FIFO with an interactive-first priority, a barrier behind a waiting head, jobs reduced to what fits (`reduced`), oversized requests clamped to the whole budget (run only on an idle machine).
- Sampling (`📡️sampling`): parsers for macOS (`vm_stat`, `sysctl`), Linux (`/proc/meminfo`, vmstat, PSI, cgroup v2 limit files) and a Windows fallback (`os.freemem`, busy-CPU load), all behind injected ports so every platform parses from fixtures on any machine; process-tree RSS observation feeds the unrealized-reservation accounting.
- Gate (`🎫️gate`): one directory per user (`~/Library/Caches/semio/host-capacity`, `$XDG_CACHE_HOME`/`~/.cache`, `%LOCALAPPDATA%`) shared by all checkouts; fair queue with progress lines (en/de, `SEMIO_LANGUAGE`/locale), cancellation (SIGINT/SIGTERM and the caller's control, deadline respected), grants reclaimed when the owner dies or the boot session changes, nested commands inherit the parent grant through `SEMIO_HOST_CAPACITY_GRANT`/`_PLAN`, `SEMIO_HOST_CAPACITY=off` switches the governor off explicitly (and says so).
- `bun repo` glue (`B/🌡️host-capacity`): `runBuildCliV1` and `runOwnedBuildInvocationV1` admit every heavy operation (`run`, `run-many`, `affected`, `exec`, `watch`, `cargo`, `show`, `graph`, `dependencies`) before any work starts and rewrite `--parallel`/`--parallelism` to the granted jobs; light commands pass untouched. New operation `repo capacity status [--json]` and `repo capacity run [--operation=|--memory= [--cpu=]] [--jobs=] -- <cmd>` (admits any ad-hoc heavy command such as a test runner); catalogue + schema + help snapshots (en/de) carry it.
- Tool adapters (the same plan, rendered per tool, with an honest per-field mapping exact/approximate/unsupported):
  - Bazel (`B/🔧️tools/🏗️bazel/🌡️host-capacity`): `--local_resources=cpu=N`, `--local_resources=memory=MB`, `--jobs` from the worker plan (which now sees only the granted cores/memory), and Starlark `resource_set` callbacks keyed by mnemonic from the per-kind estimates so Bazel's resource manager books actions at their estimate instead of 1 core/250 MB;
  - Nx (`L/⚡️caching/🚀️bootstrap/🛠️tools/🌡️host-capacity`): `NX_PARALLEL` = granted jobs (Nx has no memory/core budget; reported as approximate);
  - cargo: `--parallelism` rewritten to the granted jobs.
- `P/📦️artifacts/🏗️native-build/📈️telemetry` now delegates its memory-counter parsing to the sampler (one parser, no duplicate).

## Residual risks and decisions
- Every heavy `bun repo` command can now wait: that is the point. Waiting prints progress; Ctrl-C cancels; an idle machine always admits after the override patience for soft reasons. If the coordinator's own session needs to bypass, use `SEMIO_HOST_CAPACITY=off`.
- Windows: no machine-wide file/attach counters and no pressure level (free physical memory and busy-CPU load only); not exercised on a real Windows host (parsers/portability only through injected ports).
- Attach count is sampled with `hdiutil info` (about 0.1-0.3 s, shared 1 s sample cache, 3 s bound, null on failure), so a stalled hdiutil cannot stall admission.
- The governor admits; it does not kill. Processes started outside `bun repo` (agents' ad-hoc `cargo`, `bun test`) are only governed when wrapped in `bun repo capacity run`; the grant ledger observes their RSS only when they run under it.
- Live Bazel/Nx concurrency proofs are written but skipped until GO (they spawn the real tools).

## Hotfix 19:5x: spare memory held at 7 MB although the host was 89 % free (coordinator report)
Diagnosis against the live gate directory (`~/Library/Caches/semio/host-capacity`), not assumed:
- Availability was NOT the defect. The sampler already counts free + inactive + speculative pages on darwin (purgeable pages are a subset of those, adding them double counts), `MemAvailable` (and the cgroup limit) on Linux, and `os.freemem()` = `ullAvailPhys` on Windows. Live `sample.json` said 17,513 MB available, equal to the coordinator's own 284,561 + 762,076 pages x 16 KB.
- Root cause 1, unrealized reservations never decayed: two long-running grants (`run` x4 reserved 9,728 MB but holding 3,003 MB; `exec` reserved 3,584 MB holding 137 MB, both running for over an hour) kept 10,172 MB subtracted as "still to come" forever, so headroom was 788 MB.
- Root cause 2, strict FIFO: the first refused waiter (a 10-job `cargo`, waiting 1 h) turned every later request into `queue-order`, including the `show projects` that only needs one fixed block.
Fix (schema-first, same independent oracle):
- `memory.rampMilliseconds` (300 s): a reservation counts as unrealized, and in the budget at its full estimate, only while the grant ramps up; afterwards the memory it really holds speaks for itself (observed, or its reservation when the platform cannot observe, as on Windows) and the live availability already reflects it.
- `wait.backfillMilliseconds` (60 s): a refused waiter lets later requests that fit pass; once it has waited its patience it becomes a strict barrier, so nobody starves (bounded wait = patience + the runtime of requests backfilled inside the window).
- New tests: 5 hand cases (ramp expiry, unobserved budget, backfill, strict barrier after patience, shared room in service order), the corpus regenerated from the SQLite oracle (now with ramp and patience), a changed invariant (strict barrier only behind patient waiters) and a real two-scenario gate test. Replaying the exact live snapshot (grants, 4 waiters, 17,513 MB): old rules admit nobody; new rules admit the waiting `cargo` with 4 jobs immediately.
- `apply.py`: `--tolerate-drift` (skips patches whose anchors were edited by peers, e.g. incremental flags in the catalogue, and keeps those files as they are), `patches.policy` replaces an existing `hostCapacity` section.

## Round 2: conc-leases fairness delta folded into the one evaluator (supersedes `wait.backfillMilliseconds`)
READY (staged, verified in overlay, NOT applied; chain15 `show projects` pid 97995 still running, apply.py refuses until it ends).
- One coherent design, schema-declared in `hostCapacity.wait`: `bypassMilliseconds` 30000, `maximumBypasses` 6, `agingMilliseconds` 300000 (replaces the interim `backfillMilliseconds`). `proposals/host-capacity-fairness-delta/` in conc-leases-tools is NOT to be wired: its logic lives in `evaluateHostCapacityV1` now (single pass instead of the wrapper's repeated evaluation); its six tests were ported into `test-decision.ts`.
- Rules: (a) a waiter refused for memory or load never holds later requests back while they fit; (b) it becomes a strict barrier only if finishing our own grants would admit it (drained host: available + what our grants hold, no unrealized, no soft reason, load without our cores) AND it has waited `bypassMilliseconds` or been overtaken `maximumBypasses` times (grants admitted since it arrived, plus those admitted in this round); foreign pressure alone never creates a barrier; (c) a batch waiter older than `agingMilliseconds` ranks as interactive. Starvation bound: bypass time + one small duration (simulated stream test).
- Oracle: the SQLite recursive query now also carries the barrier flag, the highest overtake count among draining heads, the drained-room test, the bypass-since-arrival subquery and the aging order, written as a different formulation than the implementation (per-head list vs running maximum). 39 hand cases (9 new/changed, numbers worked out by hand) plus the seeded 160-case corpus agree; corpus coverage measured: count rule differs in 32 cases, aging in 85.
- Replay of the live 19:38 snapshot: `cargo` (waiting 1 h) is admitted with 4 jobs, `run` waits for memory and, having waited past its patience and being drainable, is a barrier for the later `exec`/`show`; nothing is blocked by foreign pressure any more.
- Hardened a timing-sensitive multi-process gate test (polling instead of fixed sleeps; it failed 1 of ~15 runs under load). Suites in overlay: decision 17, sampling 8, gate 16 (5 consecutive full runs), `bun repo` glue 9, Bazel adapter 4, Nx adapter 1; tsc: no errors from our files (only the pre-existing ♻️reset and 📤️child errors).

## Round 3b (READY3): foreign load must not hold a request
Defect (live): `show projects` waited 9 min with "load above its ceiling (need 5120 MB; 8878 MB spare, load 33; 1 running)": the load was foreign (editors' git polling), memory was ample.
- Rule now: load only scales jobs down. A request whose memory fits is admitted with at least its minimum jobs however high the foreign load is; what must stay under `load.perCoreCeiling` x cores is OUR cores: the cores of running grants plus those admitted this round plus the request's minimum. Reason `load` therefore means "our own jobs book all cores" (message en/de updated); a request wider than the whole ceiling still waits and overrides after `overrideAfterMilliseconds` when nothing of ours runs. Drain test for the barrier uses the same own-cores rule.
