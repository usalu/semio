## 4. Proposals not staged (owners)
- Runtime rows of the plan-reuse check: each of the 3 `x` rows spawns a full `repo tools exec --light …` door (0.14-0.23 s wall, 60 MB) on every hot run (~0.5 s of `bazel.reuse`); recording the stat identity of the resolved tool binary in the witness would let a hot run skip them (witness/toolsetup owners).
- Door streaming hand-off: the door still holds ~210 MB only to wait; streaming the snapshot rows to fd 3 (hash pass, then write pass, per-file bytes) instead of one text would keep it near its 75 MB boot size; needs `auxiliaryInput` streaming in `🔨️modules/🏃️process` `runOwnedCommand` (process owners). `Bun.gc(true)` after the hand-off does NOT lower RSS (measured: heap 136 → 47 MB, RSS unchanged), and `BUN_JSC_forceRAMSize` 1 GiB / 512 MiB changes nothing for these peaks (303/290 vs 293 MB).
- Memo parent rule (hit rate under peer edits, after clonejournal): a journal `m` row of a FILE no fact read is relevant when its parent directory is in the relevance (a listed directory); in 07:37-08:34 26,917 rows were relevant only through their parent (`hotpath-tools/memorule.ts`, e.g. peers editing `🧪️testing/🧫️fixtures/…` files of modules the course lists). The planner itself keeps serving in that case (a readdir fact survives a content edit), the memo replans the whole graph. The rule is conservative on purpose (FSEvents `CREATED|REMOVED` does not say in which order, so a file can appear behind an `m`). Refinement for the memo owner: keep the readdir facts of the relevance directories in the sidecar and re-check only the listing of such a parent with the engine (one readdir) instead of refusing.
- Dependency vouch `cursor:lost` in the profiled hot runs: the stored cursor's journal answer was a loss; with clonejournal a mirror no longer floods the journal, re-check after landing (verify2 owners).
