## 1. The process chain of one hot `bun repo run <product>:build` (why two boots, plus a third)
| # | process | started by | what it loads | boot cost (CPU) |
|---|---|---|---|---|
| 0 | `bun repo` -> Go launcher -> pinned bun running `B/🚪️door/📜️script.ts` (the DOOR) | shell | 8 modules (door plan answers `--help` etc. itself) | 50-60 ms to `boot.main`, 0.12 s CPU for a light command |
| 1 | EXECUTOR `repository:command` (`bun --eval <stream loader> -- <digest> …`) | door (`executeImplementationV1` -> `runOwnedCommand`, snapshot through a pipe on fd 3) | the whole closure of the build tool (1,520 files / 18.5 MB snapshot) | 0.55-0.73 s user + 0.1 s sys, 416 MB RSS |
| 2 | GRAPH CHILD `build:graph-plan` | executor (`loadBuildGraphInChildV1` -> `runAdoptedCapturedBuildSourceV1`, the SAME snapshot again through a pipe) | the same closure again; then verifies the generation (frontier stat pass + ~76k facts), assembles, writes the plan file | the same boot + the graph plan |
| 3 | CAPTURED PLANNER `bazel:captured-planner` | executor (Bazel adapter) | the same closure a third time | skipped when toolsetup-g's `probes` make the planner reusable |
| 4 | Bazel client + warm server | executor | JVM, 0.4-0.5 s for a no-op | outside this lane |
So the "two executor boots" are 1 + 2: the executor and the graph child. Both boot the identical snapshot; the third (planner) only when the plan-reuse oracle refuses.

## 3. Delivered: the GRAPH MEMO (`graph-memo`): a hot repeat never starts the graph child
### 3.1 Design (schema-first: `🧠️memo/🧬️schema/🔣️.json`)
The first planner run of a request keeps a LIGHT record (the slice text, the generation pin, the journal cursor taken BEFORE the child started). The next run of the same request starts the child once more with `SEMIO_BUILD_GRAPH_MEMO_OUT` set; the child, which already holds the generation, classifies every fact of it (535,723 rows on the live generation) and writes the SIDECAR (relevance + recheck set); the parent seals. From the third run on, `loadBuildGraphInChildV1` asks the journal ("what changed since the cursor") and, when nothing the generation read changed, returns the stored slice with a re-owned pin: no child process, no frontier walk, no fact verification. A cold edit-and-run loop never pays the sealing cost (it is paid only by a repeated request).
- Key: root, args, tool, build mode, implementation digest (+ loader identity), runtime, the `SEMIO_BUILD_/GRAPH_/REPO_` environment minus volatile names. Memo directory = the private runtime directory of the change journal (dies with its epoch, never in the checkout, per user).
- Relevance: every fact row is classified by the closed table in the schema: `path` rows read the entry they name, `text` rows (derived) the paths inside their key, `resolve` rows a request and its result (a bare module request, a symbolic-link-following kind or anything in an excluded region / outside the root is rechecked), `none` rows nothing. R = every vouchable entry, its directory and all directories above up to the root, plus the frontier directories. A journal row is relevant when it names a directory of R or lies directly inside one (a directory-modify row only matters to the directories themselves). Packed as sorted 53-bit hashes (a collision only adds a relevant entry).
- Out of the journal's sight (excluded names/regions, outside the root, anything below a symbolic link found by `lstat` at seal time, `realpath`/`typescriptRealpath` kinds, bare requests, analyses in excluded regions): re-checked by the next lookup itself with the engine's own `observationsHold` (and the recorded stat identity for analysed sources), 32,228 rows on the live generation (CPU ~0.9 s).
- Fail closed: an unknown fact kind, a journal refusal (epoch, gap, overflow, no service), a moved pointer, a changed key, a tampered plan/relevance file, a stale re-check, a failing pin all mean "plan the graph" (profile mark `graph.memo` = `miss:<reason>`).
### 3.2 Why it is sound (what rev4-g should attack)
A hit means: same key, same generation (pointer generation + manifest), the journal is exact since a cursor taken before the verifying child started, no journal row names or lies directly in a directory any vouchable fact read, and every fact the journal cannot see still holds by the engine's own check. A change between the cursor and the end of the verification is reported next time (conservative); a change after it likewise. Case/normalisation: hashes are folded on case-insensitive hosts. Atomic save (rename over), rename (file/dir/case-only), symbolic-link retarget, mode change, directory touch, creation of a probed-missing file are all rows of directories the facts read.
Known limits (all conservative): a directory-level granularity (a sibling's change in a read directory invalidates); a whole-graph criterion (any relevant change anywhere re-plans the whole request; a slice-specific criterion is the follow-up); the sealing pass costs 8.9 s CPU / 1.2 GB RSS on the live generation (measured below) and runs only in the child of the repeated request.

## 4. The executor/graph-child snapshot hand-off (investigated, NOT staged)
In a `cache status` run in the mirror the executor spent 3.85 s of its 7 s wall blocked in `readSync(3)`, i.e. waiting for the door to push the 18.6 MB snapshot through the pipe (the door writes 64 KB chunks from its event loop, every chunk needs both processes scheduled). With a regular file as descriptor 3 the pinned bun reads the 18.6 MB in 1-8 ms (`/tmp/fd3b.js`). But an A/B of the transports in isolation (python feeder vs file fd, 5 pairs) showed no difference in wall (2.1-8.3 s, noise of the load), so the wait is the door's, not the pipe's. Not worth a change of the shared `🎛️owned-execution` library without a quiet-host A/B; the design is `auxiliaryInput:{version:1,file}` (open read-only with O_NOFOLLOW, pass as stdio[3]) in sealed mode only, with the loader unchanged (its digest check covers any source).

## 5. Process chain in SEALED mode (measured 21:55 in mirror `b`, `SEMIO_REPO_IMPLEMENTATION=sealed repo cache status`, steady state, `tree-cpu.py`) and the projected hot no-op budget
Steady sealed run: trampoline 0.29 s CPU (56 MB) + SEALED DOOR 1.41 s CPU (455 MB, a full loader boot of the 1,553-file snapshot just to run the door) + EXECUTOR 0.98 s CPU (377 MB, a second full loader boot); whole tree 2.8 s CPU without the mirror wrapper. So "two executor boots" = sealed door + executor (about 1 s CPU each), then the graph child (third) and the planner (fourth). FOR seal-g: the heavy-command path could run the executor kernel inside the sealed door process (no second spawn, no snapshot pipe) or spawn the executor straight from the trampoline; saves ~1 s CPU and one snapshot transfer; needs `receiveScriptProcessInvocation` to accept an in-process re-entry; not attempted.

## 6. Open / decided against
- Persistent warm executor: rejected (multi-user safety, peer edits, heap that JSC never returns).
- Loader precompile sidecar (~0.4 s CPU per boot): not built; with the memo only ONE boot (the executor) remains on a hot run.
- Slice-specific memo (per-owner closure of the facts): follow-up; needs the index classes per owner.
- Incremental sidecar (derive R of generation N from N-1 plus the dirty owners' rows of the delta manifest): follow-up; would cut the 8.9 s sealing pass.
