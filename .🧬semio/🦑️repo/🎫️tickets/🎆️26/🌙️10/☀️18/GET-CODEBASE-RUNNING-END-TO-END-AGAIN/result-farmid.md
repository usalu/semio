## 1. What was wrong and what the batch does
- Root cause (buildmem): the graph child runs from the captured snapshot (fd 3 = snapshot, reads of captured modules answered from images), the farm started its workers as `process.execPath <physical 👷️worker/🟨️.mjs>` (fd 3 = IPC channel), so the worker loaded the library from disk and its record identity (sealed module-load rows) never equalled the child's: 18/18 refreshing gate runs refused. Reproduced graph-free on base (run b1 below: `refused (identity differs)`, 0 of 36 adopted).
- Launch from the same snapshot: `adoptedCapturedBuildLaunchV1()` (`📥️source/🔏️closure/🚪️command/🟦️.ts`) names the stream loader + the adopted digest + the captured-process variables; `runAdoptedCapturedBuildSourceV1` now uses it too (one place builds the loader command line). The farm (`🏊️project-farm/🟨️.mjs`) writes the snapshot text ONCE per farm (`proof.text()`, one 19.6 MB string, `wx` 0600 file in a 0700 `mkdtemp` dir, removed at close; oncecapture: no per-worker serialization or hashing in the parent, the worker's loader verifies the digest) and starts every worker as `bun --eval <loader> -- <digest> --semio-role=graph-farm-worker` with that file opened read-only (O_NOFOLLOW) per start as descriptor 3 and the IPC channel on descriptor 4 (`createFarmV1({auxiliaryFile})`, `🏊️pool/🟨️.mjs`).
- The role: new module `🏊️project-farm/🪆️captured/🟨️.mjs` (role constant, farm identity, `runCapturedGraphFarmWorkerV1` with literal imports so every snapshot carries worker + service: runtime snapshot 1,581 -> 1,584 files, +18 KB). The shared kernel entry `⌨️command/📥️entry/🟦️.ts` serves the role after the proof check, without an invocation; the sealed entry routes it to the runtime kernel.
- Identity = captured implementation + record identity (`graphFarmIdentityV1`): a worker is adopted only when both equal the parent's (the session/job wire is private to one implementation; the records must be the ones the parent would write). Implementation = the digest the worker's own loader verified (never a disk re-read).
- Found by the first adopted runs and fixed: (a) staging race: a recycled worker deleted its own staging on shutdown while the parent was still adopting its leaves (ENOENT in w0-g1); the service no longer removes it, the parent does after exit (`retired`) and at close. (b) farm rows != in-process rows in 5 then 1 owners: three once-per-process memos recorded their facts only into the FIRST project that asked (`precisionContextV1` rules + engine + schema in project-assembly; the TypeScript compiler revision in `prepareSourceAnalysesV1`; the presentation resources of the build policy in script-inputs), so a project's rows depended on what the same process inferred before it; each now goes through `memoizedObservedComputationV1`, which replays the facts into every receiving project. This is also a soundness fix for plain in-process builds (every project that applies the precision rules now depends on them). Hence the project-assembly stamp bump (output-stamps record renamed, digests unchanged: values did not change, only rows).
