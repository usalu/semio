## 1. Findings (measured) and fixes
1. **Governor sample was O(heap).** `v8.getHeapStatistics()` in Bun walks the heap: 0.7 ms at 30 MB, 32 ms at 100 MB, 150 ms at 350 MB, 323 ms at 650 MB (`/private/tmp/ga1022/heapbench.mjs`), sampled every 25 ms for the whole inference. Profile of a warm 100-project run: `heapStats` = 15.6 of 52 s (30 percent). Fix: `process.memoryUsage()` (heapUsed + external, 0.001 ms at any heap). Warm 100 owners, same records: inference CPU 15.5 -> 8.8 s, steady parent CPU 143 -> 71 ms/owner, wall 33 -> 28 s. At 3,741 projects the heap is 10x larger, so the saving is far larger (not measured).
2. **Budget was absolute, the working set is not.** The builder starts inference with a 3-4 GB fixed working set; budget 2.5-3 GB made the governor permanently over budget: one project at a time with a synchronous full collection per project. Live builder pid 82797 (11:36-12:03): `graph: waiting for memory (3759 of 3072 MB in use, 1 projects running)` on every project from ~300 on, 12 projects/min, physical footprint 8.0 GB (peak 11.3 GB) at project 457, 735 projects after 15 min in a second run. Fix: `createMemoryGovernorV1({baselineBytes})`: only growth above `measureMemoryBaselineV1()` (one collection at the start of the inference) is charged. Laws: fixture scenarios `baseline-is-not-charged` (4 parallel with a 4,000 MB base and a 300 MB budget) and `growth-over-baseline-is-charged`, Python oracle checks `usedBytes - baseline <= budget`.
3. **Budget default derived, not constant** (coordinator request): `graphMemoryBudgetBytesV1(env, policy, hostMegabytes)` = env `SEMIO_GRAPH_MEMORY_MB` if set, else clamp(max(hostShare 0.25 x host memory, grantShare 0.5 x (plan.fixedMegabytes + plan.memoryMegabytes)), minimum 1024, maximum 16384) MB; host memory = `os.totalmem()` or the container limit (`process.constrainedMemory`). 32 GB host -> 8,192 MB (what the coordinator set by hand), 8 GB laptop -> 2,560 MB, unknown host -> 1,024 MB. `defaultBudgetMegabytes` (3072) is gone from the policy. 16 fixture rows, Python model.
4. **Reader assembly is small; the expanded graph is huge.** Real generation (4,006 owners, 310 MB of fragment JSON, 15,076 distinct closure files = 997 MB): fragments + expansion + schema validation of the whole graph = 7.5 CPU-s, 10 s wall, 650 MB heap, 2.4 GB RSS. The expanded graph is **2.2 GB of JSON** (`JSON.stringify` of it throws "Out of memory" in Bun; per project it takes 5.3 CPU-s): 16.2 M expanded input paths. So no persistent cache of assembled chunks can help (writing and reading 2.2 GB costs more than the 7.5 s of recomputing); the reuse across readers is the content addressing that already exists (fragments, closures `build-input-closures`), plus the new reuse across chunks inside a reader (point 6).
5. **Cold index build** (`createFactIndexV1`, live data: 468,442 rows, 51 M row/owner pairs, 14,499 classes): 15.7-27 s and +1.3 GB heap before (per-row `consumers` arrays, a `Set` per owner, one 18 KB `join` string per row); now typed arrays and an exact hash-bucket partition: 8.2 s, +0.4 GB heap. Output byte-identical to the old implementation on the live data (`canonicalJson` equal) and to a Python partition model on seeded corpora.
6. **Streaming assembly.** `store.assembleStream(current, {names, compare, signal, progress})`: `nodes()` yields `[name, node]` in code point order with at most 32 fragments resident, `finish()` gives dependencies / external nodes / unavailable / generation / membership; `assemble()` is now exactly "collect the stream". `loadGenerationGraphV1` expands chunk by chunk while the nodes arrive (`expandStreamV1`, the same fixed project / UTF-8 byte groups as `expandInChunksV1`, proven equal on the portable corpus) so raw and expanded copies never coexist. `portableInputs` keeps the expanded list of every closure it read (bounded by `maximumCachedClosureEntries` 4,194,304, repo + content address as key) so each distinct closure is read once per process (39,978 token occurrences, 15,076 distinct).
   Synthetic corpus, resident heap while a consumer drops what it was given vs collecting: 1,000 projects 2.5 MB vs 24.6 MB, **5,000 projects 5.2 MB vs 123 MB** (bound asserted: stream peak(5,000) < 1.5 x peak(1,000) + 16 MB and collected > 4 x stream).
7. **No whole-graph JSON in memory when printing.** `bun repo graph` / `show` printed `JSON.stringify(result, null, 2)`: impossible at 2.2 GB. New `writeJsonStreamV1` writes the exact `JSON.stringify(v, null, indent)` text in pieces of 64 K characters with backpressure and cancellation; the runtime prints through it. A 400 MB text is written with < 64 MB resident.
8. Not a cause (checked): JSC `forceRAMSize` (a 1 GB value made the warm run 5x slower with the same RSS; the harness default `GP_RAM` of 1 GB distorts CPU of large heaps, use `GP_RAM=34359738368` for timings). Warm per-project retained heap is 0.3 MB (cold 2.5 MB); physical footprint of a harness process is 0.8 GB for an RSS of 2 GB.
