## Cause (not a one-plan-per-root store, not a dashboard witness input)
The plan record (`plan.receipt.json`, witness, cursor) lives IN the generated package of a Bazel slot, and a slot has ONE stable package (`bazelSessionWorkspaceV1`, `🧵️sessions/🟦️.ts:50`: path `<workspaces>/<slot>/0000000000000000`, content replaced in place by the next selection; `removeBazelPlanRecordV1` at `📜️script.ts:~756`). So a slot holds the plan of its LAST selection only.
A dashboard run is TWO Bazel sessions: the outer `repo-dashboard-rs:build` (slot s4) and a nested `repo run @semio-tech/repo-dashboard-rs:compile` started inside the Bazel action while the parent holds s4. Logs `C/gate-g-tools/run/g{12,14,17,18,19,20,21}-dash.log` all show the same two lines: `session slot s4: warm server and package for this selection` and later `session slot s3: the package of the slot is replaced in place for a different selection, the server stays` (s3 is the COURSE slot), each followed by `planning again`. Every course `hot1` that follows a dashboard run shows `s3 ... replaced in place` (g15, g18, g19, g20, g21 hot1), every course run that follows a course run shows `s3: warm server and package` (g14/g16/g17 hot1, all hot2/hot3, g22-prof*, g23-course).
Why the nested run picks s3 although other slots are unused: `rankBazelSlotsV1` (`🧵️sessions/🟦️.ts:55-56`) had a tier 1 "slots that still keep its package" = `state.keys.includes(key)`; `keys` is the retention list of the last 6 keys of the slot (`nextBazelSlotStateV1`, line 62), a leftover of the per-key package design. Once the course key and the nested key have ever shared a slot, each is in the other's `keys`, so each run ranks that slot tier 1 (before never-used slots, tier 2) and overwrites the other's package + record: self-perpetuating ping-pong. Evidence in the stored state `.cache/b/p/m/bazel/outputs/server/s3.session.json`: `key` = course (4c63bbcb...), `keys` = [course, 5aa2a917 (nested dashboard compile), ...]; the course receipt in `workspaces/s3/0000000000000000/plan.receipt.json` is sealed (racy null, unstable 0, tainted 0, 65,392 observations) but gets replaced after every dashboard run.
The outer dashboard plan is NOT evicted: `workspaces/s4/.../plan.receipt.json` (recorded 02:07:59 by g21-dash, 11,130 observations, same shape: racy null, unstable 0, tainted 0, 97-100 `e` rows with stable values). Its `planning again` in g17-g21 coincides with a landed batch between every pair of dashboard runs (jobskey, grantenv, ignoredenv, yieldenv reversal change the executor identity part of the key) so the logs cannot show a dashboard-vs-dashboard reuse failure; the proof sequence above does.
Ruled out: one slot per root/workspace (there are 11 slots s0-s10, each with its own package); a dashboard-specific key part or witness observation (outer record sealed and stable); graph digest (dash digest 56c784... identical in g17-g21).

## Fix (schema-first, one rule in one place)
A slot holds the package and plan record of its last selection only, so the order is: (0) the slot whose last selection it is (most recent first), (1) slots never used, (2) every other used slot, least recently used first; the `keys` retention list no longer influences the choice (bounded LRU by slot count; nested sessions already get `nestedExtra` slots). Files (flat batch, `C/dashplan-tools/staged/manifest.json`):
- `🧵️sessions/🟦️.ts` rankBazelSlotsV1 (tier 1 removed, docstring says why)
- `🧵️sessions/🧬️schema/🔣️.json` SlotState description (`keys` = selections served before, a record only)
- `🧵️sessions/🧪️tests/🟦️.ts` order test (SQL ORDER BY oracle updated) + new law
- `🧵️sessions/🧪️tests/🧫️fixtures/🔣️.json` 2 rows changed, 2 rows added; every expected order recomputed by the independent Python oracle `C/dashplan-tools/rank_oracle.py` (5 unchanged rows agree with the old expectations, so only the tier-1 rows moved)
- `🦑️repo/README.md` affinity paragraph.
