## 1. Finding: every loss today is FSEvents `UserDropped`, caused by a utility-priority callback queue during clone bursts
- Live journal epoch `b756e961…` (since 11:25:40): 1,870 records, **170 losses, all `["user-dropped",""]`** (scope "" = everything) in 37 distinct minutes; 0 `kernel-dropped`, 0 `must-scan`, 0 `overflow`, 0 `watcher-exit`/trust losses, one epoch (no restart, no stale heartbeat), one 1 MiB segment (rotation/GC never reached: `floor` would be its refusal, not `lost`). So: not segment rotation, not journal GC (diskbud only sweeps abandoned sibling dirs), not heartbeat staleness, not the row bound.
- Every loss burst coincides with a mirror create (`$TMPDIR/sm/.meta/*.json` created times vs loss times): tb 14:43, tcap 14:48, tp1 14:49, tl1 14:52 (30 losses), agA 15:04, tm1 15:21, cp-main 15:24, tg2 15:34, nl-main 16:19, q6 16:19, my own jl-w 16:26 (3 losses). A mirror create `clonefile`s ~16,400 live files: APFS reports `ItemCloned` on every clone SOURCE (in the watched tree). clonejournal (landed G30) drops them in the callback, but they still travel fseventsd -> client.
- Live A/B (`jlprobe`, three read-only observers on the live root with the live exclusions, 8 min, 16:13-16:21, two peer mirror creates at 16:19): ~3,400 clone-only events/s reach the client, 0 emitted rows; the default-QoS probes got `UserDropped` (nice 15: 15 markers in 6 s; nice 0: 9 markers) **at the same seconds as the live journal (records 1639-1643)**; the probe whose dispatch queue has QoS user-initiated got **0**.
- Why: the watcher's FSEvents dispatch queue is created with no attributes; libdispatch runs it at **priority 20 (utility tier)** — `ps -M` of the live watcher 38459 and of the probes: 20T with a NULL queue attribute at nice 0 and nice 15, 31T with QoS user-initiated or user-interactive (at nice 0 and nice 15). Every build process runs at 31; at load 30-78 a priority-20 thread waits, fseventsd's per-client queue overflows, fseventsd sets `MustScanSubDirs|UserDropped` on the root, the watcher emits `lost("user-dropped","")`, and every cursor (graph memo, dependency vouch, plan cursor) answers `lost` for every agent.
- Second amplifier (base code): `emit` writes stdout synchronously inside the callback, so a slow consumer (the journal service runs at nice 15 under load) also blocks the dispatch queue.
- Exclusions: rooted exclusions ARE applied at source (`FSEventStreamSetExclusionPaths`, 8 slots, `exclusionOk 1`): 16k creations in a rooted-excluded dir never dropped (harness, 7 runs). Name exclusions (`node_modules`, `target`, …) are NOT applied at source: 16k creations below a `node_modules` caused 7 losses + a 60 s fence timeout in `base-nat4`. Live, every `node_modules` is a symlink into the DMG volume `.cache/b/d/m` (another device), so this does not hit the live root today. Tickets, `.cache`, `⚡️cache` are rooted (source-excluded); mirrors live in `$TMPDIR/sm` (outside the root); only the clone SOURCES hit the stream, which no exclusion can avoid.
- History is complete: after every forced drop the volume history held every unreported path (`inHistory` = `unreported`, 1439/1439, 915/915, 7405/7405, 21469/21469), so a drop is repairable without a loss.
- Trap found while building the fix: fseventsd delivers a history replay OUT of event-id order (gen 7 of a debug run: 1,315 order breaks, the fence row arrived as event 14,686 of 16,002). A replay emitted as it arrives lets a fence row overtake earlier changes = silent misses (325-2,082 per run in my intermediate build). The existing restart path (`--since`, supervisor replay after a watcher exit) has the same hazard today; the batch fixes both.

## 2. The batch `jloss` (watcher only; protocol, schema, journal and consumers unchanged)
| part | what | why |
|---|---|---|
| QoS | FSEvents dispatch queue `dispatch_queue_attr_make_with_qos_class(SERIAL, QOS_CLASS_USER_INITIATED)` | priority 20 -> 31; the measured cause |
| writer thread | every frame goes through one writer thread (`mpsc`), callbacks never block on stdout; queued bytes bounded at 64 MiB: beyond it batches are dropped and the first batch after draining to half is preceded by one `lost("overflow","")` (no fence can be answered before that loss) | consumer stalls no longer stall the callback; memory bounded (Rust law `admit`) |
| replay instead of loss | `UserDropped` (without `KernelDropped`) retires the stream (generation) and opens a new one `since` the cursor of the oldest of the last 8 delivered callbacks (or the stream start); history rows are buffered and leave as ONE batch at `HistoryDone` (fence-ordered); 8 replays in a row without a clean delivery -> `lost("user-dropped","")` and continue from now; any `--since` stream (supervisor restart) is buffered the same way | the volume history holds every dropped event (measured); bounded |
| bounded subtree | `MustScanSubDirs` without a drop flag below the root -> one structural row `["n",1,scope]` (the journal's own "directory row means its subtree"); at the root -> `lost("must-scan","")`; `KernelDropped`, root-changed, mount stay losses | only the coalesced subtree is re-checked (memo: a structural row of an ancestor of read entries is relevant, sound) |
| Linux | inotify rows leave every 8,192 rows or after the latency even without a quiet gap (`due`) | a gap-free burst could build one record > 65,536 rows -> journal `overflow` loss |
| Windows | RDCW buffer 1 MiB on local volumes, 64 KiB after `ERROR_INVALID_PARAMETER` (network shares) | xplat5: a build burst in `target`/`.cache` (not excludable at the kernel) overflowed 64 KiB |
| test hook | `#[cfg(semio_watch_stall)]`: generation 0 sleeps 20 ms per callback (never in production builds) | deterministic forced drops for the law |

Laws (`R/🧪️tests/🔭️watch/🕳️drops/🟦️.ts`, darwin): (1) stall build: writes continue until a drop has been replayed (12k-60k files, a fence every 500); whenever a fence row arrives every earlier file is reported (or covered by a subtree row), no `lost` frame, >= 1 replay — base+same stall FAILS (base never even delivers the fence within 90 s: `Received: false`); (2) no watcher thread working during a burst runs at priority <= 20 — base FAILS (20). ## 4. Linux / Windows / devcontainer
- inotify: excluded directories are never watched (`tree()` skips them), so exclusion IS at the source; the remaining loss is `IN_Q_OVERFLOW` (kernel queue `fs.inotify.max_queued_events`, default 16384, not changeable unprivileged): the writer thread keeps the read loop draining; the new `due` bound keeps records under the journal's 65,536-row bound. No history to replay on Linux: an overflow stays a loss (correct). devcontainer = Linux backend.
- Windows RDCW: no kernel exclusion for subtree watches; overflow (`ERROR_NOTIFY_ENUM_DIR` / 0 bytes) stays a loss; 1 MiB buffer makes it 16x rarer (not measurable here; type-checked for both MSVC targets). No history replay (the USN journal would be the equivalent; not done: needs a Windows host to measure).
- macOS-only parts are behind the existing `cfg(macos)` backend; the drop laws `skipIf(!darwin)`.
