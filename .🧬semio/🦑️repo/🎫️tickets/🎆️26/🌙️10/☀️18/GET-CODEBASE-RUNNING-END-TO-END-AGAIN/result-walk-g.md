## Item 1: the repository walks of the input precision are derived facts (batch `walks`)

Where the rows came from (sealed generation 561, `readdir-census.mjs`): `workspace` 125,970 `readdir` rows (90 k under `✏️s/🔌️plugins`, 20 k under `🧰️framework/🛍️products`), `s-dev-composition` 91,639 (90.7 k under the plugins). Cause, by reading and by the row counts of the harness: two walks of the precision engine recorded their listings into the project that asked, (a) `precisionCargoManifestsV1` (crate index, whole repository; cached per process, so only the FIRST project of a process recorded its rows: a latent soundness gap, now every project that used it holds the digest) and (b) the include/entry walks of `deriveProgramV1`/`entryFilesV1` (tsconfig `**/*`).

Design (schema first, no new runtime dependency, all in the existing derived-fact machinery of cutoff-g/derive-g):
- Engine (`🎯️precision/🟦️.ts`): the walks are pure functions of an injected listing (`cargoManifestDirectoriesV1`, `crateNamesV1`, `includeRootsV1`, `entryFilesV1`), host ports `crateNames()` / `sourceRoots(question)` (optional: absent = walk in place, the old path, so every existing host and law is unchanged), schema `DerivedWalk` (closed: `crate-index` with a skip list, `source-roots` with an `entries`/`include` question) and `readDerivedWalkV1`.
- Closure api (`🧭️script-inputs`): `api.derive(recipe)` (late mode: the walk is a closure ENTRY computed once per process with its observations detached; the project records ONE `closure` row `[workspace, recipeKey, ["digest"]]` and carries the recipe in its `closureRecipes` table, the same persistence as every command closure), `derivedWalkV1` (the listings are one shared layer named by `{derive:1, workspaceRoot, recipe}` + the digest of the answer, so `resolve()` returns a derived fact whose support is that layer and keeps the listings out of the project rows), `deriveClosureFactV1` answers `derive: 1` questions (re-ask), `derivedWalkAnswerV1`.
- Project assembly: `preciseInputsV1` gets the per-call closure api; in late mode the host handed to the engine is the shared host plus the two ports; the engine's program memo is keyed by `host.program` so per-call hosts still share it.
- Soundness: the answer digest covers EVERYTHING the project used (the whole value), the support covers EVERYTHING the walk read (listings, `exists`, the Cargo.toml bytes of the names), an answer-preserving edit (a new README anywhere) re-asks once and keeps every holder, an answer-changing edit invalidates exactly the holders.

Oracle (law `🚶️repository-walks`, 7 tests, 10,008 expectations; independent Python walker `🐍️oracle/🐍️.py`, standard library only, own glob dialect, own package-name scanner, replays the edits on its own copy of the tree): (1) 22 recorded steps (content rewrite, unrelated file, TS file in included/excluded/vendored directory, crate added/renamed/duplicated earlier+later, crate directory renamed, crate moved below a vendored directory, hidden crate, directory symlink, symlink named `x.ts`, excluded directory removed, source removed/renamed out of the globs, deep tree below a braced include, directory renamed, file becomes directory, whole tree removed and returned) with the frozen `changes` of each; (2) 40 seeded sequences x 14 steps (adds, removals, renames, rewrites of files and directories anywhere, into hidden/vendored/skipped places). After EVERY step: the in-place walk equals the oracle; the derived fact asked again equals the oracle's digest; and whenever every supporting row still holds (`observationRowsHoldV1`) the answer MUST be the one the holders hold (a violation fails the law). Non-vacuity counted: answers that stayed equal while their support went stale (kept) and answers that moved are both asserted in the hundreds. Mutation proofs: an unobserved listing of one directory -> "entries2 moved although every supporting row holds" (red); an exclude check dropped -> in-place walk differs from the oracle at step 0 (red). Also in the law: closed recipes (7 bad shapes refused), the crate index equals `Bun.TOML.parse` package names (third-party), a project that used a walk records 1 row (direct path: >120), the derived fact's support is apart from the project rows, unknown questions are refused. Engine law +1 test (the ports derive exactly what walking in place derives for every fixture rule, program with and without entries).

## Item 2: the observer and the learned estimates read the footprint (batch `footprint`)

Sources measured on this Mac (4.4 GB process): `footprint -f bytes --noCategories -p <pid>…` 60-70 ms and prints the kernel's `phys_footprint` (+ peak) per pid, several pids in one call, a vanished pid prints one error line and the rest stays valid; `top -l 1` 0.84 s; `vmmap --summary` 1.26 s. Chosen: `footprint` (a system tool of macOS, tool-independent interface, no FFI), membership from the existing `ps` table. Linux: `/proc/<pid>/smaps_rollup` `Pss` + `SwapPss` per member (no external tool, resident set from `status` per member when unreadable). Windows: private working set (`Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`) in the same `pid ppid kilobytes` table shape.
- Schema (`🧬️schema/🔣️.json`): `Observers` (measure `footprint`; per platform the commands/files/fields), message `footprintFallback` EN+DE, optional store stamp `measure`.
- Code (`📡️sampling`): `observeTreeMegabytesV1(pid, run, platform, proc, notify, measure = "footprint")` (the gate calls it without a measure = footprint; `"resident"` keeps the old reading), `parseFootprintV1`, `parseSmapsRollupV1`, `treePidsV1`, `HostMemoryMeasureV1`; a source that fails or prints nothing falls back to the resident set, once per process in both languages; a partial `footprint` output (non-zero exit with stdout) is used. `📐️estimates`: the store file is stamped `measure: "footprint"` on write and a store of another measure reads as EMPTY, so resident-set peaks (up to 2.5x too high on macOS, p90 quantile!) never mix with footprints; `estimates.json` keeps its name, no migration script.
- Law `🔬️footprint` (11 tests, 108 expectations): recorded macOS outputs (verbatim `footprint`/`ps` on Darwin 27.0.0: three processes, one vanished, nothing printed) + authored cases (a process that freed memory: 7,208 MB resident against 2,700 MB footprint; a name with spaces and brackets; root not running), authored Linux `smaps_rollup` (kernel format) and trees (one member without it, none), Windows table; every parse equals the frozen values AND the independent Python oracle (`🐍️oracle/🐍️.py`); call sequences asserted (`ps`, then ONE `footprint` with exactly the tree members), fallbacks and notices EN+DE, the store stamp. LIVE on macOS (skipped elsewhere): a Python child allocates 200 MB and reads its own footprint through `ctypes` `proc_pid_rusage` (third-party kernel API), the observer agrees within 16 MB; a Bun child that dropped 3 M objects holds >150 MB resident and the observed footprint is below half of it (411 MB vs 10 MB measured). Mutation proof: pricing by the resident set instead -> 3 red. Windows and Linux are fixture-only here (no Windows host, Docker daemon off): marked NOT RUN live.
- Existing laws adapted (resident behaviour keeps its tests, passing `"resident"`): Windows table (3 calls), Linux fixtures + live ps comparison (3 calls); the Windows blind-host law now expects the footprint fallback line pair plus the blind pair (4 lines).
