## Root cause (code)
- `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🧩️component-pass/🟦️.ts` `runNativeBuildDriverV1`: `planContinuations.start(consume => withCargoCompilerInputsV1(first, withPassInputs…, consume), async actual => { completed = await executePasses(actual.control); })`. `executePasses` starts pass-level owners through `inputContinuations.start(...)` (`runAdmittedPass`); each owner parks on `await gate` until `inputContinuations.close()`.
- Routing law (`🧭️routing/📥️invocation/🏃️process/🟦️.ts` `track` + `settle` + `drain`): a loan (`withRequestedIssuedResourceControlV1`) settles only after its callback AND every accepted child operation (registered on all ancestors) has settled, also when the callback failed.
- Success path is ordered correctly: the returned `completed()` closes `inputContinuations` (inner) and later `planContinuations.close()`. Failure path is not: `executePasses` throws ("Native build failed: …", `stallReason`, cancellation, storage refused) -> plan loan `drain` waits for the parked pass owner -> the owner waits for `inputContinuations.close()` which sits in the outermost `finally`, after `await planContinuations.start(...)` => circular wait, forever. Every failing/cancelled/stalled real build with at least one started pass hits it; the stub tests never saw it because their ports hold nothing.
- So "lost exit" was a misdiagnosis for this class: the child exited, 'close' fired, the report and failure are even recorded; only the teardown order is wrong. (Other earlier idle cases may be the nx-b claim-retirement/own-shared-ticket fault, fixed separately.)

## Fix (live)
- `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/📥️inputs/🤲️continuations/🟦️.ts`: new `withNestedInputOwnersRetiredV1(nested, body)` (runs `body`; on failure closes the nested owners first, then rethrows the primary).

## Addendum 08:55: coordinator question "cargo holder queues a second shared request behind exclusive waiters" (cycles `43773 -> 42933 -> 64570 -> 64570/q`)
- FINDING: phantom, not a deadlock. `leases status` (`🔒️leases/📋️status/🟦️.ts buildLeaseReportV1`) lists every arrival-queue ticket that is not in the leading holder run as a WAIT, also when the registry says the same pid HOLDS that lease: a held queued lease keeps its arrival ticket. With an exclusive request at the queue head (waiting for the shared holders to leave) every shared holder's own ticket sat behind it and was drawn as `<pid>/q waits for <exclusive>` => cycle `exclusive -> holder -> holder/q -> exclusive`. Live proof 08:50: host-capacity holders 81675/43867/42933/88855 (all running; 43867 had an active cargo child, its run log grew) each showed a `WAITING shared host-capacity` row with exactly the same age as its hold, plus `4 deadlock cycles`; ten minutes later (exclusive request gone) 0 cycles, 0 waiters. 64570 had exited by then, so its row could not be re-inspected; same pattern (compiler-writer shared held + own ticket).
- The re-entrant fast path itself is fine: `acquireOrderedQueuedResourceLeaseV1` grants an own/inherited shared re-entry at once (`holdsSharedInProcessV1`: process holds, `SEMIO_LEASE_INHERITED`, or `SEMIO_BUILD_INVOCATION_PID` registry); nothing indicated a second real request.
- FIX: `buildLeaseReportV1` skips a queue ticket as a wait when `known.has(h pid key)` (registry shows the pid as holder of that resource); registry waits stay the truth. Test `🔒️leases/🧪️tests/📋️status/🟦️.ts` (2 tests, pass with `bun test`; imported by the `resource-lease-order` suite file `🧭️order/🧪️tests/🟦️.ts`): holder tickets behind an exclusive head are neither waits nor cycles; a genuinely queued pid still waits with blockers.
- Teardown fix is live in source (`withNestedInputOwnersRetiredV1` at the plan body in `🧩️component-pass/🟦️.ts`); processes started before 08:20 (e.g. 43867 hub-space-component, 42933, env `SEMIO_SCRIPT_STALL_MS=14400000` from invocation 11541) still carry the old code, so a FAILED build in them can still park.
