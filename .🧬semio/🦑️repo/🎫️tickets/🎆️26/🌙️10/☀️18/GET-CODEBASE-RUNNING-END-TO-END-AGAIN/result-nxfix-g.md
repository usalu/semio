## Item 2: the Nx path never restarted on exit 75
Facts (g10 log, `print:build`, 14:13): `build-report` ran a nested command (`build:nx-command`) that printed `Another process kept editing env:BUN_INSTALL while this command read it … then starting the command again with a new snapshot (1 of 6)` and exited 75 (the declared restart code); Nx reports that task as an ordinary failed task (run.json `status: 1`, never 75), so the outermost command can only learn about the restart from the OUTPUT of the nx process. The Nx lane already classifies the output tail like the Bazel lane (`settleNxRunV1`), and the TS launcher restarts on stale-implementation errors, so two things were missing:
1. The announcement texts of a nested restart (`editfailure`, `loadfailure` of the format-stamp protocol, EN+DE) were not in the refusal table at all (only the moved-stamp text was): now declared as messages of the existing reexec classes `escaped-concurrent-edit` and `half-edited-module` (sites = the format-stamp schema that owns the texts; the table's own Python scan counts the occurrences).
2. The evidence was out of reach: the tail keeps the last 262144 characters of everything nx printed; in g10 the announcement came 3,026,358 bytes before the end (`[script]` progress of the sibling tasks keeps flowing while Nx finishes), so even a declared text would not have been in the tail. The tail now also keeps every complete line that names a refusal class by its own words (`declaredRefusalClassOfTextV1`, decided when the line arrives, per channel; bounded by the policy: 64 lines of at most 2048 characters, an unfinished line is decided when the text is read, distinct lines only, newest win): `text()` returns the kept lines the tail no longer holds, then the tail. Everything else (settle, bound, announcement, restart through the stale error) is the existing schema-first policy, i.e. the same restart the TS launcher performs.
Perf trap found on the way (and avoided): the exhausted-text pattern is `.+?`-based, quadratic on a long line (a 267 KB line without newline hung the test for minutes); `declaredRefusalClassOfTextV1` now checks that all literal parts of the pattern occur before it runs the pattern (same decision, linear).
Laws (all green in the mirror, single files): `failure-tail/🧪️tests` 9 (new: 4 text vectors EN/DE for the two new messages, classified by the table AND by the independent Python scan; 9 transcripts replayed by the implementation and by an independent Python model `🐍️.py` that must give byte-identical `text()`: early refusal survives 1 MB of later progress, a German line cut between two chunks, interleaved stdout/stderr lines do not mix, the unfinished last line, the same line once, newest 64 of 70, a retry announcement is no evidence, an ordinary failure has none, one endless line is not scanned twice (< 2 s)); refusal table law 6 (new vectors); `🌊️races/🔁️layers` + `churn` + Bazel `failure-tail` 23 green. ## Item 4: "the loader does not exit after a green Nx run" - it does; the tail is 72 s, and 59 s of it is the nx client
MEASURED (probe `nxfix-g-tools/probe-exit.py`, no reaper, default route Nx, `@semio-tech/mit-bestand-praesentation-projektetage:build`, one of the two targets nx2-f had to reap; run 15:09-16:11, 36 min in the capacity queue + graph wait of a peer, then 12 min of Nx): `NX Successfully ran target build …` at t0; the whole `bun repo` tree (7 processes) was sampled every 3-4 s; `bun repo` exited with rc 0 at t0 + 72.2 s.
| t after summary | alive | CPU |
|---|---|---|
| 0 - 59 s | door, runtime, launcher, loader (`96679`, 0.2-0.6 % CPU, 270 MB), **nx client** (`8182`, 400-480 MB, 5-66 % CPU) and one child of it (`8962`, 3-19 %) | the nx client is BUSY, the loader idles |
| 59 - 72 s | door, runtime, launcher, loader only (loader 8-10 % CPU: post-run graph inventory, resource retirement scan, lease sweep) | |

Open descriptors of the door/runtime: 1 dir, 4-7 files, no socket, no pipe, 2 kqueue (idle). No orphan, nothing left after rc 0 (`ps` after: nothing of the run). So there is NO leaked handle (timer, socket, child): fault N of nx2-f was an artifact of its driver (`drive.py` kills the tree 20 s after the first summary line); the same arithmetic on the older logs (heartbeat span between the summary and the last heartbeat) gives 20-40 s for every rc-0 run (g1 course:test, g3/g4 print:test) and 70-80 s for the two "reaped" runs (g11 print:build, projektetage f2) - the reaper just cut the slower ones. The process DOES exit after every green summary; the real defect is the TAIL: 20-80 s per Nx run, of which the nx client is 59 of 72 s here.
What the nx client does in that time (log of the same run, lines after the summary): 113 `nx:daemon-startup` lease cycles ("Verifying build tools" 81, "Preparing build tools" 32), 239 before the summary in the 12 min of the run; at about 2 per second. The cause is in the Nx patch: `startDaemonIfNecessary()` is called by `sendMessageToDaemon` for EVERY message to the daemon, and the patch wrapped the whole function body in `withNxDaemonStartupV1(...)`, which takes the exclusive `nx:daemon-startup:<hash>` lease, opens the tools store, verifies the SDK sources, and starts a birth server (`withNxDaemonServiceBirthV1` -> `withNxToolingUseV1`) BEFORE the body can look at `_daemonStatus == CONNECTED` and return (upstream returns first). So each message of every client costs a full startup cycle and all clients of a namespace serialize on one exclusive lease; this is also where the `nx:daemon-startup (rank 2) requested while nx:fixed-cache (graph 4) held` lock-order lines come from.
FIX (batch `nx-patch`, 2 files): the patch adds `if (this._daemonStatus == DaemonStatus.CONNECTED) return;` as the first statement of `startDaemonIfNecessary()`, hunk counts and cumulative coordinates of the following hunks adjusted (`assertToolingPatchV1` accepts the new patch). A not-connected client still goes through the startup owner unchanged (only the no-op entry is gone). LAW (`🧬️lifetime/🧪️tests`): the patch text is EXECUTED, not matched: the statements the patch puts before the startup owner run against a stand-in client; connected -> returns without loading or entering the owner (zero `require`), disconnected/connecting -> reaches the owner; the first statement is read by @babel/parser (third-party) as an `if (this._daemonStatus == DaemonStatus.CONNECTED)`; negative control: the same test against the live patch fails (`VariableDeclaration` is the first statement). Ran standalone (the real file needs the live checkout, the mirror path exceeds the path-unit limit of the source capture).
NOT MEASURED: the effect on the 59 s. The nx-patch batch changes the toolkit identity, so a before/after needs the batch landed and one Nx run of the same target; gate-g (or I, on request) compares the post-summary window with `probe-exit.py` (before: 72.2 s total, 113 + 239 startup cycles).
