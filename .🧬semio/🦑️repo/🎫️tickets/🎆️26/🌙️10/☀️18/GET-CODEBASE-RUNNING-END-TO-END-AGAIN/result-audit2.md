### F1 HIGH (quietfc round 2): two runs that both have to grow wait on each other forever and block the whole machine queue
- Code: `🧰️framework/🔨️modules/🏃️process/🏗️build/🌡️host-capacity/📏️decision/🟦️.ts:151`, the sole-run partial admit requires `active.length===1`.
- Scenario: agents X and Y run hot builds inside the follow-up window; both get quiet grants (2 GB each) and both reach real work (`upgradeBuildCapacityV1`, the run is paused before its planner). Each upgrade is refused for `memory` (the other's quiet reservation + foreign memory), neither is "sole", neither can finish (each is paused in its own upgrade). The earlier one is a strict barrier head (finishing our own grants would admit it, and it has waited > `bypassMilliseconds` because the upgrade keeps the run's ORIGINAL arrival), so `blocked=true` and every later request of every agent on the machine is refused `queue-order`. Lending is the only thing that can break the cycle, and only when a holding process has NO live descendant for `lendAfterMilliseconds` of declared waiting (`🎫️gate/🟦️.ts:221-227`, `liveChildPidsV1` lists every descendant, an unreadable process table counts as "children alive"); I did not prove whether holders are childless at the upgrade points (`🚏️marks` `rebuild`, `script.ts:789`). Even when lending applies, every other request on the machine waits >= 30 s behind the barrier first. Without it, the cycle ends only when foreign memory frees up or the runs' budgets expire. The decision function itself (the bug) is pure and reproducible.
- Live red (pure function, mirror `a2`): 32 GB host, 12 GB available, two quiet grants (2048/1500 MB) each asking to grow to free+2500 MB, plus a third 1000 MB interactive request: at t, t+30 s and t+4 h the decisions are `[first wait memory, second wait queue-order, third wait queue-order]`. - Fix (staged): the partial admit applies while every other live grant is a quiet grant with its own pending upgrade (`growing` set from the waiters); only the first in queue order (`admitted===0`); once it grew it is a real competitor and the later run waits `memory` for it (second law case). ### F2 MEDIUM (quietfc round 2): the sole-run partial grow can drive the host into swap; not staged (policy decision)
- `admit(request.minimumJobs,"override",max(held, min(wanted, held+freeObserved, freeBudget)))`: the reservation shrinks to what is free NOW, the run keeps every job it was admitted with (the tool's `--parallel` was fixed at the quiet admission; `minimumJobs=preferredJobs` for the upgrade), and the hard stops (critical pressure, swap) are checked only at that instant. A print-rs:test that really peaks at 8-11 GB admitted with 3 GB free (peers outside the gate) runs into swap/compression on a 16 GB host; this host already had watchdog panics under fleet load. During its ramp the partial grant does reserve all free memory, so OTHER gated runs are protected; the overshoot is the run's own.
- Recommendation (owner quietfc): admit partially only when the grantable size is >= the class's own measured peak (without the 25 % margin) or after `policy.load.overrideAfterMilliseconds` of patience; otherwise keep waiting with the progress line. Needs the owner's call on starvation vs. swap.

### F3 MEDIUM (leaseord staged2 premise; pre-existing hazard): a Rust compiler-code publisher waits for a peer's whole build and is refused after 15 s
- Code: `📚️library/⚡️caching/🦀️cargo/📦️units/🏗️compiler/🔏️code/🟦️.ts` (publication block). The directory is content-addressed; two builds that miss the reader loop concurrently compile identical bytes. A publishes and holds `rust-code:<dir>` SHARED around its whole build callback; B takes `rust-code-publication:` exclusive and QUEUES for `rust-code:<dir>` exclusive. The writer path itself handles an existing directory (collision check), so leaseord's argument "the publication writer only writes a digest directory that does not exist yet, so no reader can hold it" is false. Outcome: B waits for A's build and is refused by `holdAndWait` (enforce, 15 s; no `namespace -> pin` edge; leaseord's own order law line 210 asserts this refusal) -> B's build fails. Window = the authorizer compile time after every change of its sources, or after a cache wipe; plausible with a fleet.
- The rank-0 `pin` itself is safe: `outOfOrder` is `observe`, ranks only change diagnostics; hold-and-wait and cycle detection (enforce) are unchanged except that `rust-code:` waits under held `graph`/`compiler-capacity` exclusives are now exempt from hold-and-wait (edges `graph -> pin`, `compiler-capacity -> pin`); no code path takes `rust-code:` under those today (census).
- Fix (staged): `claimRustUnitCodeWriterV1` tries the writer with `timeoutMs:0`; on timeout a directory whose two files carry the expected digests needs no writer (only readers can hold it while we hold the publication lease), else it queues as before. Law `🔏️code/🧪️tests/🖊️writer/🟦️.ts` (real leases, enforce, peer reader in a child process): RED on live 1/2, GREEN 3/3; test 3 characterizes the live protocol (`LeaseOrderErrorV1 {hold-and-wait, held namespace, requested pin}`). Neighbour `⚡️caching/🦀️cargo/📦️units/🧪️tests` 10 pass / 18 fail on base and with the batch (identical set, invocation envelope).

### F4 LOW (cargofix synchronize): the preparation witness does not bind WHICH cargo the child would use
- `cargoPreparationWitnessHoldsV1` re-stamps the tool paths recorded by the child (`witness.tools`, `store.toolchain.cargo` of the generation the child opened) but never compares them with the generation the next child would open; the receipt's `tool` (`cargo --version`) is the only binding of a toolchain pin change that does not go through `rust-toolchain(.toml)` or the `CARGO_*`/`RUSTUP_TOOLCHAIN`/`RUSTFLAGS`/`RUSTC` env. Scenario: the repository's Rust toolchain policy moves to a new sealed generation while the old one is retained -> old stamps hold -> no child -> no `cargo update`/`fetch --locked` under the new cargo (resolver v3 is rust-version aware, so the lock can legitimately differ). Self-heals when the old generation is collected. Fix sketch (owner cargofix): pass the launcher's current tool path(s) into `cargoPreparationInvocationCurrentV1` and require equality with `witness.tools[].path`, or hash the toolchain policy file into `hashed.sources`. Not staged.
