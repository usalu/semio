## Real defect found and fixed (staged): watcher events dropped, graph memo refused
Symptom: 8 of 12 peer1 runs and all early controls printed `graph: the memo cannot serve this request (journal: lost)` (or `light`, the seal that never happened), so every hot control replanned the graph (200-537 s at load 70) instead of 10-40 s; stage 09/10 (load 33-46) were `199 projects served from the memo`.
Root cause: the resident journal has 216 `lost` rows today, 184 `["user-dropped",""]` (whole-root scope): FSEvents tells the client it was too slow and drops events for good, and `since()` refuses every cursor older than a loss. The watcher (`🔭️watch/🦀️rust/🦀️.rs`) wrote every batch with a blocking `write_all`+`flush` on stdout INSIDE the FSEvents callback, so a consumer that does not drain the pipe (the single-threaded service, nice 15 here: both pids 38435/38459 are nice 15, inherited from the job that started them) blocks the callback; plus the callback queue ran at default QoS under load 70.
Measured (std-only Python harness, files created inside a watched root while the reader does not read, 3 s): base binary 1,000 of 8,000-20,000 paths seen and `lost user-dropped` in every run (12 of 12); decoupling alone (outbox thread, adjacent batches coalesced): 0-7 losses per run at load 60 (callback formatting/queue contention left); decoupling + `QOS_CLASS_USER_INTERACTIVE` dispatch queue: 0 losses, all paths seen, 10/10 runs (also under `nice -n 15`).
Fix (`C/peerrun-tools/staged/watchpipe/`, 2 files: watcher source + its provision row sha256/bytes): `Outbox` (event callbacks only append under a short lock; a writer thread owns stdout; adjacent batches fold with an order-aware rule while the consumer is slow; lines such as `lost`/`history-done` are barriers; `n` assigned at write time; `finish()` drains with a 2 s bound before every exit incl. `scan`/`version`/`bye`/`fail`), serial queue at user-interactive QoS. Laws: 4 new rust unit tests (stalled consumer never blocks the producer, with a watchdog instead of a timer; exhaustive a/m/r sequences up to length 5 vs an existence-simulation oracle; line barrier; sequence numbers), language-agnostic `law-stall.py` (oracle = the file system; red on base: `--expect-loss` PASS on the base binary, green on the fix), linux+windows cfg type-check, existing bun watch suite 13/13, `stage.py` mode law OK. Verified on mirror `pr-watch` (dropped). Not fixed: the service still inherits the nice level of whichever job starts it (cannot be lowered without privilege); QoS mitigates, a restart from a normal-priority shell is the operational remedy. Cost: the watcher source grows 37.3 KB to 49.8 KB (8 KB of tests).
