## 0. Verdict (read this)

1. **A cold all-workspace graph can never be published, whatever its speed (certain).** Reconstructing the exact portable graph from the 3,680 persisted project records and the 14,232 referenced closure leaves gives **about 859 MB of JSON** (records 434 MB + 428 MB of expanded closure inputs), the publication limit in `G/🟦️.ts` (and the snapshot limit in the graph policy) is **536,870,912 bytes**. `loadBuildGraphAttemptV1` stringifies the *expanded* graph, so every cold run ends in `Build graph cache exceeds its finite publication limit` after the whole inference. `.cache/b/g/m/graph.json` is still the 114-byte placeholder of 10-18: no all-graph run has ever completed on this machine. Fix staged: publish the compact form (closure inventories stay `{env:SEMIO_SOURCE_CLOSURE_…}` references, which every reader already expands: `image()` and `withRepositoryBuildGraphPublicationV1` call `portableInputs`), estimate **431 MB** (84 percent of the cap, headroom about 80 MB; the real fix for growth is the follow-up F2). Measured with `graph-speed-tools/size.mjs` (reads only).
2. **Why pid 15549 burns hours (evidence certain, mechanism probable).** At 18:09-18:25: 100-115 min, 66-75 CPU-min, 50 percent of one core, footprint 3.4 GB. `sample` (3 s): about 75 percent of the main thread sits in the same stripped addresses as the three Heap Helper threads (GC marking) or waits for them; the rest is JS. **No inference record has been written since 17:33** (424 of 3,656 records rewritten between 16:28 and 17:33; none in the next 50 min), the stderr log has **no `build:projects` line since line 11,300** while 1,000+ `resource-directory-admission:v1` lease lines (0.45 per second, a cycle of 3 lines with one 1 s wait) keep coming; `lsof` shows no input-closure or np file open, 435 read-only `.pack` descriptors. So every project worker is blocked inside `observeProjectInferenceV1`, and the only work in flight is the reuse predicate `inferenceInventoryReferencesHoldV1`, whose first caller verifies **all 17,713 closure leaves** (`build-input-closures` 14,342 + `build-lock-closures` 3,371) through the managed read batch (per leaf: ancestry walk, three descriptor verifications, two storage rechecks, a per-character JSON scan, a deep freeze, a lease admission). The same leaves read, hashed and validated with the production validators in a plain loop take **42.8 s at load 22** (`inv.mjs`, 2.4 ms per leaf, 0 invalid). The inference is therefore not CPU-bound in our code; it is bound by per-leaf custody overhead and by a 3.4 GB heap that the GC walks again and again. I could not attach a JS profiler (bun is stripped, no inspector); `[graph-phase]` rows (below) will prove or refute this on the next run.
3. **Why a builder blocks readers.** `loadBuildGraphV1` always entered `withBuildGraphStateV1` -> `withGraphFactWriterV1`, which takes `repository-graph-facts:<workspace>` EXCLUSIVE for the whole attempt, **including the cached-receipt check** that a valid sealed graph needs. Every `show projects` / `exec --projects=workspace` therefore queued behind a running builder even when a sealed graph was current. Staged: a shared cache-store reader (`withRepositoryCacheStoreV1`, no facts writer, no `build-graph-state` lease) serves a valid sealed graph first; only a missing/stale seal enters the exclusive builder, which re-checks the seal first (double-checked, existing behavior), so queued commands behind one build reuse its result instead of rebuilding. Limit: while a builder is still inferring and the seal is stale, a reader still waits (it needs a graph that matches the tree); the lease-queue line already tells it who holds what (`lease-queue:` label, EN/DE).
4. **fd leak (certain).** `observedRecordStoreV1` keeps every project's pack store (index map + read descriptors) until the whole graph writer closes. Staged: process-wide LRU of 32 pack descriptors in the record store (`RECORD_STORE_DESCRIPTOR_LIMIT`) and each project's store is closed and unregistered as soon as its record is persisted.
5. **Targets (warm 30 s, cold 5 min) are NOT measured**: the host is under a 15549-owned lease and a freeze; `graph-speed-tools/measure-after-lift.sh` prints the phase table, the peak `.pack` descriptor count and the reader probe in one go. Estimates: lean verification of the whole inventory 15-45 s once per process instead of per 10 min window; closure expansion (14,232 leaves) 30-40 s per cold or warm process; inference per `C/result-graph-perf.md` (6.7 CPU-min); the rest is not estimable.

## 4. Handoffs

- **input-precision (448 s `✏️s` typecheck derivation):** it runs inside the observed inference of one project record, so it is cached only as long as that project's record holds; any edit of any file it read re-derives all of it. Required: key the derived input set by the digest of the tsconfig/closure inputs and keep it in the pack record store (`recordKey("ts-program-v1", tsconfigSha, closureDigest)`), never re-derive on a warm graph. The record store, its bounded descriptors and its release (this set) are the right place; the hook belongs to `🧱️project-assembly` in that set.
- **x-graph:** its persisted per-owner records fit the same release/descriptor discipline; nothing to change, but it should not run before this set because the compact publication changes what `selected/<scope>.json` contains for large selections.
- **F2 (not staged, design):** a persisted `closure-table` (all inventory leaves in one brotli table keyed by name, stamp per leaf) would make warm expansion O(lstat) instead of O(read); needs a declared graph namespace in the storage schema. F3: build the all-graph in an inference dataset namespace (`withRepositoryBuildInferenceDatasetV1`) so the builder holds a shard lease and the facts lease only to publish; needs one cold rebuild of the np cache. F4: the 431 MB compact graph is still a monolith; project-level graph shards would remove the cap problem for good.
