## Round 16 (20:30): ROOT CAUSE of the daemon hang and of the idle lease holders - nested shared queue self-deadlock
- Run 23 (bundle law green, lease store 13 %): the daemon (pid 90592) built nothing for 25 min after `graph-construction progress`; its event loop was alive (WATCHER logs every 250 ms) but `bun repo leases status` showed it HOLDING `…/snapshots/7cb6….json` shared (1396 s) and WAITING for the SAME resource shared, `position 2 of 2` - at the same age, i.e. the second nested acquisition by the same process queued behind its own first (still held) ticket. In `awaitQueuedTurn` a non-cohort shared request may only proceed as queue head (or in a cohort of `sharedCohort` shared tickets); the existing re-entrant bypass only fires when an EXCLUSIVE ticket is queued (`exclusiveTicketQueued`), so with no exclusive in the queue the nested shared request waited for its own holder forever. The loader (88713) held the same snapshot twice, so the pattern is common; `holdAndWait`/`selfDeadlock` do not see it (shared/shared never conflict).
- Fix (`🔒️leases/🟦️.ts` `awaitQueuedTurn`): `ownShared` - a shared request proceeds when every ticket ahead of it is a SHARED ticket of THIS process and the process (or its parent) already holds that resource shared (`holdsSharedInProcessV1`, under the existing `fairness.reentrantShared`); other processes' tickets still order FIFO, upgrades keep their queue position. Test `🔒️leases/🧪️tests/♻️nested-shared/🟦️.ts`: fails (5 s timeout) with the fix disabled, passes (49 ms) with it; SQLite `begin exclusive` oracle proves both shares keep the lock until both are released and an exclusive is granted afterwards.
- This very likely also explains the coordinator's idle drivers that sat "waiting" after `claim-retirement-scan` (they were queued behind their own held shared tickets). SIGTERM of the stuck loader and daemon ended both within 15 s (termination guard verified again). Run 24 (see pids.txt) verifies.
