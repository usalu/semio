## Why a module split alone does not narrow the capture (measured on the real 1275-file `implementation.json` of 19:50)
`captureBuildSourceClosureV1` follows (a) the parent's per-file import resolution maps (including every dynamic import the parent ever executed), (b) every quoted relative path literal in a file (type-only imports, `typeof import()`, `new URL("./x")` lists) when the parent loaded the target, (c) all `🧬️schema/*.json` beside a module. Replaying that rule over the real snapshot (`ckey-d-tools/real-closure.py`, `whatif.py`): seeds = the 281-file static value closure of the executor module give 1275 files = the whole adapter. Leaks, by size: `storage/🔒️enforcement/…/🕸️graph/📏️headroom/🧾️closures/🟦️.ts` (graph closure-retirement maintenance; dynamic worker `👷️read.mjs`) pulls 570 files; `📥️caller/🟦️.ts` (dynamic imports of 🕸️graph, 🧭️invocation, 🧭️selection inside `withBuildOrchestrationTaskEnvironmentV1`, type imports of graph) ~ 25-35; `📥️inputs/💾️storage/🟨️.mjs` (cache-gc launch, resolution, generations), `runtime/🧭️selection` (bun/node adapters by literal), small ones in leases/host-capacity/opening. With literal scanning off and those dynamic edges cut the closure would be ~300 files (static 281 + a few lazy roots).
Conclusion: narrowing needs three source changes besides the split: (1) move `withBuildOrchestrationTaskEnvironmentV1` out of `📥️caller/🟦️.ts` and give `BuildExecutionV1` a leaf home (else graph/selection/invocation come in); (2) decouple the graph-image store opening from the closure-retirement maintenance (`🧾️closures`), a layering fix in the storage enforcement owner's area; (3) a narrow capture mode (static value imports + declared lazy roots, no literal scan) in `📥️source/🔏️closure`. None of these is done yet.
