## 1. Lock order: rustup:home then host-capacity

Root cause. The declared global order (schema `🔒️leases/🧭️order/🧬️schema/🔣️.json`, authored table `🧭️order/🔣️policy.json`) ranked `compiler-capacity` (1) before `tool-singleton` (2), and put `rustup:*` in `tool-singleton`. The code does the opposite and has to: `withRepositoryRustToolchainV1` (`⚡️caching/🚀️bootstrap/🛠️tools/🦀️rustup/📥️installation/🟦️.ts`) holds `rustup:home` shared plus `rustup:generation-shard:N` for the whole life of the compiler store (the sealed generation is retained "through every consumer"), and the cargo / wasm / native builds take `host-capacity`, `cpu-picker` and the cpu slots inside that body. All 346 recorded violations of the registry log were this one pair (173x host-capacity, 173x cpu-picker, held `rustup:home`). A static census confirms store-first everywhere capacity and store meet (`cargo/🚪️launcher`, `cargo/🧪️testing/📦️executable`, wgpu `🏗️compiler/🌐️wasm/📜️script.ts`: the store call precedes the capacity call).

Which side is wrong: the declaration. Reordering the code is not possible (the reader must hold the generation while it compiles, and capacity is only known inside the build) and it would be wrong: the total order that excludes deadlocks is toolchain reader -> capacity, because a reader that waits for capacity while a capacity holder waits for an exclusive provisioning of the toolchain home would deadlock (a provisioner holds the home exclusively and needs no capacity, so the order home -> capacity has no cycle).

Fix (declaration only, schema unchanged):
- new class `toolchain` (rank 1, checkout scope) matching `rustup:` (taken out of `tool-singleton`); every other rank shifts by one (compiler-capacity 2, tool-singleton 3, cargo-coordination 3, graph 4, namespace 5, artifact 6, native-whole-retirement 6, image 7). No rank is hard-coded anywhere else (grep).
- new declared edge `tool-singleton -> toolchain` with bilingual reason: provisioning an absent generation takes the managed-tooling provision lease (`nx-tooling-provision`, tool-singleton) while it already holds `rustup:home` exclusively, then publishes `rustup:generation-shard:N`; every toolchain lease except the home is requested only while the home is held, so no second party can wait on it from the other side. There is deliberately NO edge `compiler-capacity -> toolchain`.
- File: `🧰️framework/🔨️modules/🏃️process/🔒️leases/🧭️order/🔣️policy.json`.

Tests (language-agnostic): fixture `🧭️order/🧪️tests/🧫️fixtures/🦀️toolchain/🔣️.json` (replayed acquisition sequences: cargo-check reader = home shared, shard, host-capacity, cpu-picker, cpu slot, cargo build lease; provisioning = home exclusive, nx-tooling-provision, shard; capacity then tool activation (declared edge); reader then graph; and the refused directions capacity -> toolchain, graph -> toolchain) replayed through `checkLeaseOrderV1` on the authored policy AND through an independent bun:sqlite oracle (class rank by longest prefix / exact name, self-join with the declared edges); plus a rank-order law test. In `🧭️order/🧪️tests/🟦️.ts`: 65 pass. Negative control: the same cargo-check sequence replayed on the previous policy (reconstructed) yields `rustup:home -> host-capacity`, `-> cpu-picker`, `-> cpu/v1/3` (the audit finding).
