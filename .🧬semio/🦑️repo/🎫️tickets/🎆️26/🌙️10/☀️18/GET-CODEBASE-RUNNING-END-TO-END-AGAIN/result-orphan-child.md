`C` = this ticket. `S` = `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage`. Tools: `C/boot-rebind-tools/` (live apply script, backups in `C/🗑️generated/boot-rebind/`).

## 1. boot-rebind (P0, applied LIVE 16:25-16:40)

### Cause
After the 16:03 kernel panic the Data volume's `st_dev` changed (16777232 to 16777229). Every macOS image receipt (`.cache/b/<d,t,g,o,p,l,n>/image.json`, `🧰️framework/.cache/b/{l,t}`, `.🧬semio/🦑️repo/⚡️cache/rust/fixed`) pins `dev` and `mountDirectory.dev`; `st_dev` is only stable inside one boot, so `inspectPersistentReceiver` refused every partition ("Exact canonical persistent Native publication required ... backing:[16777229,16777232,...]"). The images cannot be attached after a reboot, so every partition is necessarily inactive.

### Change (schema first, no compat)
- `S/🧬️schema/🔣️.json`: `ImageReceipt` now REQUIRES `bootSession` (uppercase UUID) and `ancestry` (inode chain of the image directory's ancestors, 1..64 decimal strings). New definitions `BootSession`, `Ancestry`, `PriorImageReceipt` (the boot-stable subset a receipt of an earlier boot or from before this change must satisfy), `BootRebindObservation`, `BootRebindCase`; `ImageProtocol.bootSession` (sysctl program/arguments, Linux boot_id file, limits). Script: `C/boot-rebind-tools/schema.py`.
- New module `S/🌐️platform/🥾️boot/🟦️.ts`: `readNativeBootSessionV1(control,cwd)` (darwin: owned capture of `/usr/sbin/sysctl -n kern.bootsessionuuid`; linux: `/proc/sys/kernel/random/boot_id`; memoized per process), `nativeBootSessionV1()` (sync accessor, throws if unread), `readNativeImageAncestryV1(dir)`, pure `decideNativeReceiptBootV1(observation)` returning `keep | rebind | refuse`.
- `S/🧹️cleanup/🎛️command/🟦️.ts` (`C/boot-rebind-tools/apply.py`, anchored, counted, backed up):
  - `inspectPersistentReceiver` reads the boot session, and when `receipt.bootSession !== boot` (also: missing field = old receipt) calls the new `rebindPersistentReceiptV1`: validates the prior receipt, proves the root is the empty underlying directory, proves via the kernel inventory (`hdiutil info -plist`, shared roster) that no image claims the path and nothing is mounted at or below the root, runs `decideNativeReceiptBootV1` (ino, size, allocated blocks within the envelope, mount directory ino and mode, ancestry inode chain when present). Under the SHARED lease it only returns `inactive` (so the caller takes the exclusive writer lease); under the EXCLUSIVE writer lease (`receiver.stage==="writer"`) it rewrites the receipt: temp file `image.json.rebind` (O_EXCL, nofollow, 0600), fsync, CAS on the receipt stamp, `rename`, directory fsync, then re-inspects. Same-boot `dev` mismatch is not touched and stays fatal; a boot-stable mismatch or an attached image is fatal with the facts in the message.
  - `writePersistentReceipt` (fresh birth, partitions and funded children) writes `bootSession` and `ancestry`.
- `S/📤️publication/🎛️owner/🟦️.ts`: the darwin receipt built by publication carries `bootSession` and `ancestry` (type and value).
- Deviation from the request, on purpose: the rewrite is an atomic rename under the exclusive image lease, not the heavy `publishNativeImagePublicationV1` ceremony (that path needs a mounted payload witness; an inactive image has none). A crash between temp write and rename leaves either receipt valid and the next open rebinds again (residue `image.json.rebind` is removed by the next writer).

Both are append-only history pinned to the parent volume's mount device (which also changes at every parent re-attach, not only at reboot). I checked all seven journals: no live funded child row exists now (only the store charges, plus the persistent-state orphan charge of section 2), so nothing is blocked. A crash-surviving funded child needs a boot-recovery sweep that retires it (retirement is keyed by the same stale identity) or an identity formula without the volume device; follow-up, not applied.

## 2. orphan-child (STAGED, not applied; apply on "ROUND 2 GO")

### 2.1 Why the roster is not the cause (task 1)
- The failing run of the peer course session (15:13-15:20) reported `readNativeStorageMountedChildV1` at `S/🟦️.ts:203`. The pre-ingress file has the check at line 203, the patched file at line 210 (the +7 lines are the journal-revision `read` that ingress-perf applied at 15:12:32). The failure therefore happened in the OLD code path too, and x-keys at 15:35 hit it in the new one.
- Diff of `verifyPersistentManagedChildrenV1` before/after: only the observer wrapper (`observeNativeImageInventoryV1` to `nativeImageRosterV1.observe`) and the one-capture memo; the `accept` function (rows below the parent root, device, image path) is byte-identical, and so is the `retain` loop. The roster returns the same rows for the same `hdiutil` text. Nothing to fix in the roster semantics; none changed.
- What made it visible only at ~15:12 is not provable from files (the child's kernel attach history is gone). The mechanism is the same for any command that rechecks the products partition while the child is mounted.

### 2.2 Root cause (task 2)
`verifyPersistentManagedChildrenV1` accepts a mounted descendant only when the parent journal has a `compiler-state` row whose `child.directory === dirname(mount)`; the journal law (`nativeStorageEventV1`) forbids a `child` request on every other kind. The persistent development state (`withNativePersistentStateV1`, kind `persistent-state`, no child row) mounts exactly such an unfunded child under `persistent/development/m`. Its own birth calls `charge.recheck()` (physical recheck of the parent) while the child is mounted, so the FIRST birth of a persistent state fails and leaves the half-born child (reserved charge, `persistent-development.pending.json`, mounted empty image), and after that every parent recheck fails. A healthy bound state would fail the same way during its body. This is a design hole, not only an orphan.

### 2.3 Fix (staged)
Design decision: do NOT retire the orphan. A `persistent-state` charge is non-recomputable user state and the journal law forbids `retiring/retired` for it (`Persistent state cannot be retired`, tested). The designed recovery for a half-born state is already "resume" (reserved charge + intent + backing, no binding): the next owner re-enters the birth under the exclusive `persistent-state:<root>` gate and the parent lease, binds, and appends the `committed` event (settled journal record). What was missing is that the parent no longer refuses to be rechecked while that child is mounted.
- Schema: `ImageProtocol.persistentNamespace = "persistent"`, `DescendantCase`/`DescendantCorpus`.
- New pure module `S/📜️journal/🧷️descendant/🟦️.ts`: `classifyNativeStorageDescendantV1(state, parentRoot, directory)` returns `funded` (a `child` request owns the directory), `persistent-state` (directory directly inside `<parent>/persistent` while a live, non-retiring, child-less `persistent-state` charge exists) or `unfunded`.
- `S/🟦️.ts`: `isNativeStoragePersistentDescendantV1` (path check first, then one journal read under the parent's mapping scope).
- `cleanup/🎛️command`: the retain loop tolerates a `persistent-state` descendant (no per-child read, skipped in the final claim pass, still part of the roster stability comparison); every other unfunded descendant stays fatal.
- Not a retire path: if the half-born image is inconsistent the state owner keeps refusing (`Unbound persistent state is retained without adoption` / `Incomplete persistent backing retained`), only for `os dev`, no longer for unrelated commands. The reserved row `37fd31e5...` still in `.cache/b/p/m/storage-events.jsonl` (the coordinator removed the directory and pending file but not the row) is recovered by the existing `recover-intent` action, so nothing needs hand repair.

### 2.4 Test pollution (task 3)

The creator at 2026-10-19 23:06 is most likely an `os dev` serve/e2e probe killed mid-birth, plus the design hole above (any first birth fails and strands the child).
