## Finding 1 (MEDIUM-HIGH): a derived serve leaves stale rows in the sealed generation; a later partial revert is served without asking the question
- Code (live `🧠️memo/🟦️.ts` `settleMemoEditsV1` + `lookup`): rows that do not hold are sent to the `derive` port; when every derived question answers the same, the memo serves and moves the journal cursor past the edit. The sealed generation keeps the OLD facts of those rows (nothing is re-recorded; the planner, by contrast, writes the held questions' new supports into a new generation via `derivedUpsertsV1`). Every later lookup re-checks only the rows the NEW journal rows name, against those old facts. So the invariant round 1 relied on ("every fact of the sealed generation holds on the tree, except what the journal names since the cursor") is broken after the first derived serve.
- Scenario (course TS program, realistic): the TS-program question reads the text of many program files A, B, …; it is named only by its project/tsconfig, so an edit of A in another directory is settled through its `typescriptText` row. Step 1 (one stretch, e.g. a refactor across two files): A and B change so that the program answer is unchanged → served via the derive child (A, B rows stale, cursor moved). Step 2: the developer reverts ONLY A (`git checkout A`): A's row now holds against the sealed bytes, B is not named by the new journal rows → served WITHOUT asking the question, although the answer on (A sealed, B edited) may differ (that combination was never evaluated). The graph keeps the old project inputs/closure while the planner would re-infer.
- Law (appended to the wired law `🧠️memo/🧪️tests/✏️edit/🟦️.ts`; `harvest`/`sealed`/`planner` now take the deriver and its oracle; real memo + real relevance builder + real observation module + real derive settlement; second model question `deriveTexts` = "how many imports of lib/d.ts name a file whose text contains `yes`", targets in another directory so only their text rows name them; oracle = the planner's verdict on the FINAL tree, `textsAnswer` by plain reads): 4 two-step sequences — targets swap their marker then the first restored (answer 1→2: MUST plan), then the second restored (1→0: MUST plan), swap undone (sealed tree: served, nothing left to carry), target edited keeping its marker then restored (served). Negative control: a record that forgets the carried rows is wrong somewhere. RED on live: the memo SERVES sequence 1 while the planner verdict is stale (`the memo served what the planner would plan … Expected true, Received false`). GREEN with the fix (edit law 9/0, memo 9/0 incl. REAL watcher, slice 2/0, reseal 1/0, verified 2/0, carry 2/0, retention 6/0).
- Fix (schema-first): `Record.relevance.carried` (row positions in the edit fact index, 1..4096, requires `edit`, `$comment`); `settleMemoEditsV1` re-checks the carried rows together with the rows the journal names and returns `stale` (the rows that did not hold but whose questions answered the same); the lookup writes `carried = edited.stale` (absent when empty) on every settled hit and keeps it on a hit without relevant rows (nothing changed since the questions were last asked); `readRecord` validates it. A fresh seal (planner) never carries. Cost: after a derived serve, every later lookup WITH a relevant change re-checks the carried rows (and asks the questions again while they stay stale) until a revert makes them hold again or the planner re-seals; a hot no-op is unchanged.
- Other derived questions asked, no finding: (a) answer equal but read set changed: `deriveGraphMemoSuspectsV1` refuses (`uncovered`) when the new support reads a (kind, path) the old support did not; a new file visible to the program is either read (new `typescriptText` path → uncovered) or only probed through a listing/probe row the old support already had (its directory is strict for derived facts, so the row is re-checked); tsconfig/`paths`/`types` edits make the tsconfig text row stale → asked again; a node_modules relink touches a symbolic link → `settleMemoEditsV1` refuses any touched path that is a link; out-of-sight rows (outside the journal) are in the recheck set, checked by value on every lookup. ## Finding 2 (LOW-MEDIUM, latent in this repo): `planmemo` serves a stale plan after a glob-declared workspace gains a member
- Code (live `📥️capture/🧠️memo/🟦️.ts` + `📥️capture/🟦️.ts`): the recorded inputs are the workspace `Cargo.toml`/`Cargo.lock` bytes, the manifests of the packages IN the old metadata and their discovery paths. When `[workspace].members` is a glob (`"crates/*"`, `"extra/*"`), a new member directory moves none of them; the lock step before the recall (`ensureCargoLockCurrentV1`) answers `current`, because the repository lock receipt (`🦀️cargo-workspace/🔒️lock`) only re-reads the manifests it recorded. ## Finding 3 (LOW): `memoout` drops an output directory from the watched names although a fact reads an entry below it
- Code (live `📤️relevance/🟦️.ts`): a listing of a `.🧾️store` directory is deferred to the recheck set and the directory is removed from `directories` unless a vouched fact names the directory ITSELF (`!vouched.has(path)`). A vouched fact that reads an entry BELOW it (e.g. `file …/.🧾️store/build.json`) keeps that entry named but no longer the directory. When the whole directory is replaced by a rename (prepare `next/`, `rm -rf .🧾️store`, `mv next .🧾️store`; the journal reports only the two directory names) and its parent is neither strict nor stamped, no row is relevant, the deferred listing still holds (same names) and the changed entry is served stale.
- Exposure: no live course/print fact reads an entry inside `.🧾️store` (hotpath2's measurement), and package directories are frontier directories (stamped/strict, which makes the rename relevant there), so this needs a fact reading inside an output directory under a non-frontier parent. The declared assumption ("the graph takes no entry from such a directory") is not enforced by the code.
- Law (memo suite, real builder + real observation module): relevance of `readdir out/.🧾️store` + `file out/.🧾️store/build.json` with no frontier; replace the directory by a rename; the engine says the listing holds and the entry changed; RED on live (`the output directory is a name a change must not touch while an entry below it is read`: false), GREEN with the fix.
- Fix: the directory leaves the names only while no vouched name lies at or below it (`read` = confirmed directories already in `memoDirectoriesV1(vouched)`, computed before the frontier is merged). The course `.🧾️store` behaviour (memoout's purpose: the store rewrite rows are irrelevant) is unchanged; the REAL watcher law with the 3 store mutations stays green.
- Asked and NOT a finding: a new input file inside an output directory that a glob includes. A derived walk or plain listing that reads the directory is either a deferred listing (re-checked by value on every lookup → stale → plan) or a following/resolve/derived fact (directory strict → the row is relevant); either way the new file is caught.
