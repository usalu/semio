## Developer Operations

Start `repo dashboard` at the monorepo root. Choose **New Task** (`Ctrl+B n`),
search by action and owner, complete the command form and choose **Start**. The
[dashboard guide](🔨️modules/🎛️dashboard/README.md#-daily-work) gives concrete
setup, testing, debugging, source navigation and repository workflows. Every
command uses the workspace daemon, so its status, output and cancellation remain
available after closing a view or restarting an editor.

commands are maintained in owner dashboard metadata or Nx targets and selected
in the dashboard.

# 🏗️ Build and run

`repo` is the only build entry. It is tool-neutral: every project target is declared once in a `📋️project.json`, a neutral graph describes all projects and targets, and two interchangeable implementations execute them: **Nx with Bun** (default) and **Bazel** (`--tool=bazel`). Never call `nx`, `bunx nx`, `npx nx`, `bazel`, raw `cargo` or `rustc` yourself. This is the rule of `AGENTS.md` that external tools sit behind a tool-independent interface and that the `repo` entry runs every command: `repo` is that interface for Nx, Bazel and Cargo. Paths that start with `📚️library/` are below `🔨️modules/` of this product. Start with the Build tools guide; the sections after it are the reference. A German version of this chapter follows its last section.

```bash
repo run <project>:<target>[:<configuration>]       # one task; add --tool=bazel for the Bazel implementation
repo run-many --targets=<targets> [--projects=<projects>]
repo affected --targets=<targets>                    # projects that changed against HEAD, plus their dependents
repo exec --projects=<projects> -- <command>         # a command once per project, project root as working directory
repo run <project>:<target> --dry-run                # print the task graph, run nothing
repo show projects|project <name>|targets            # the neutral graph (also: repo graph)
repo cache status|clear                              # task cache of the selected tool
repo cache remote status                             # the remote cache contract, its rendering for the tool, whether the endpoint answers
repo cache serve [--port <n>]                        # serve a bounded remote cache for Bazel and Nx until stopped
repo tools setup [nx|bazel|all]                      # provision the pinned build tools for this host
repo dependencies sync --all                         # install dependencies (--scope <owner> for one owner)
repo dependencies lock --all                         # regenerate bun.lock after a manifest edit
repo cargo --store=shared --configuration=prototype -- check -p <crate> --lib
```

- **Help.** `repo --help` prints every command and every flag; `repo <command> --help` (also with a subcommand, for example `cache clear --help`) prints that command's own usage, options and examples. The text is rendered from the operation catalogue in English or German: `--lang=en|de`, then `SEMIO_LANGUAGE`, then the locale (`LC_ALL`, `LC_MESSAGES`, `LANG`), then the first language of the catalogue. Help is answered before any tool or store starts.
- **Dependencies.** `dependencies sync` installs into the dependencies partition (`node_modules` at the root is a symlink into it). Any `package.json` or `bun.lock` edit makes the installed generation stale: run `dependencies lock --all`, then `dependencies sync --all` once, never an ad-hoc `bun install`. Before it installs, a sync retires every `j/<20 hex>` dependency generation that is neither a current plan generation nor the target of a live binding (progress `dependencies:retire-obsolete:<n>`). On macOS 27 the installer can fail with `EPERM: Operation not permitted: failed to link package`; see Recovery, the sync repairs that case itself. A workspace package created after the last sync (a new `package.json`) cannot be resolved until `dependencies lock --all` and `dependencies sync --all` ran; every route that imports it fails with `Cannot find module` until then (seen on 2026-10-20 with a new framework package, which stopped the `verify` routes and the documentation-law tests). Sync cost: the verification passes were quadratic in the number of bindings. The installed-paths scan now compares a directory with itself when it closes instead of re-reading every ancestor of every entry (progress frames every `scanProgressWorkUnits` = 4,096 work units), the publisher re-checks only the strict ancestors of an endpoint's parent (`javascriptDependencyStrictAncestorsV1`), each published binding gets a 12-`lstat` endpoint fence (`requireJavascriptDependencyEndpointFenceV1`), and the complete fence runs every `fullFenceInterval` = 32 bindings and after the last one (constants in `📚️library/⚡️caching/🚀️bootstrap/📦️dependencies/💾️storage/🧬️schema/📥️install.json`). Measured on the primary host at load 31 to 52: the scan of one 84,345-entry generation fell from 168 to 302 s to 48 to 64 s, and the last green `dependencies sync --all` (2026-10-20 05:43) took about 31 minutes, where an earlier attempt ran 7,000 s without finishing. Leave the tree alone while a sync runs: a peer edit of a provider file during the walk failed one attempt with `Declared execution physical observation changed`. The suites that pin these fences are the targets `repo:test-javascript-installed-paths`, `repo:test-javascript-endpoint-fence` and `repo:test-javascript-provider-walk` (project `repo`, directory `⚡️caching`). Recorded on 2026-10-20 on the live tree under an issued envelope: the endpoint-fence suite passed (5 tests), the provider-walk suite failed its table test on the row `provider-relinked-in-first-replay` (expected refused; not diagnosed, open), and the installed-paths suite could not load because the installed generation predates the package `@semio-tech/framework-filesystem` that it imports.
- **Dependency generation receipt.** Every `repo` task or graph call first proves that the installed dependencies still match their sources. That proof used to be a complete walk of the workspace (eight directory-tree passes of about 617,000 operations and four provider walks per command, 36 to 58 s per tree pass under load). It is now a sealed receipt per dependency scope, checked cheapest tier first (`Protocol.tiers` in `📚️library/⚡️caching/🚀️bootstrap/📦️dependencies/🧾️generation/🧬️schema/🔣️.json`): `implementation` (content digest of every file in the runtime import closure of the walk and fence entries, read with `captureBuildSourceClosureV1`; 175 files, 2.1 MB on the measured tree), `runtime` (Bun and Node versions, Bun revision, platform, installer recipe), `producer` (the `.npmrc` and `bunfig.toml` files an installer level could read, and the `BUN_*`, `NPM_CONFIG_*`, proxy and certificate variables, by name and value digest only), `bindings`, `inputs` (manifests, lock, bunfig, patches), `membership` (every walked directory by stamp; a directory younger than 5 s is listed again and compared by projection digest) and `execution` (every physical observation the provider walk made, replayed). Any difference is a typed mismatch (`Protocol.mismatchClasses`) and the command falls back to the complete walk, which then passes or throws exactly as before. Receipts and their evidence are content-addressed files in `.cache/b/d/m/generation`; verification runs under the caller's shared store custody and publishes progress `dependencies:generation-verify:<n>`. Only an `inspect` with exclusive custody and the end of a `dependencies sync` publish a receipt (`publishJavascriptDependencyGenerationReceiptsElseV1`; best effort, a failure prints `[DATA]` and never fails the sync), and a capture defers while any closure file is younger than the process start minus 5 s, so a receipt only vouches for code that ran. Consequence: an edit of any file of the closure (126 of the 175 are process modules) costs the next command one complete walk. Measured read-only on the primary host at load 56 to 65: a complete receipt verifies in 3.6 to 12 s against 36 to 58 s for one tree pass; the closure and producer tiers add about 10 ms. Not yet verified: on 2026-10-20 the generation directory held three zero-byte `*.frontier.ndjson` files and no sealed receipt, so no live run has published and then verified one; Linux, Windows and the devcontainer were not run.
- **Waiting for a store.** A cache image and other shared resources are claimed through a queue (`acquireQueuedResourceLease`, resource `native-fixed-image:<partition path>`): tickets are served in arrival order, a shared ticket joins a cohort only when every earlier ticket is a shared cohort ticket, so a writer is not starved by readers that arrive after it, and a waiter reaps only its immediate predecessor when that process is dead. Waiters poll from 250 ms to at most 1,000 ms (factor 3/2) and sweep at most once per second (`🧰️framework/🔨️modules/🏃️process/🔒️leases/⏳️wait/🧬️schema/📜️policy.json`); with 14 waiters behind one holder for 15 s their CPU time fell from 15.2 s to 2.2 s. A waiter at position 2 or later publishes every 15 s a `lease-queue` progress line, shown in English or German, for example `Waiting for access to native-fixed-image:<path> (shared): position 3 of 15, behind the request of process 12528 (exclusive, queued 8040 s ago)`: the pid names the holder. A line `<command> remains active on dependencies:store-ownership:state:<N> (exclusive, <s> s)` is the generic progress line of a running walk (N counts work), not a wait. `upgradeQueuedResourceLease` turns a held queued shared lease into an exclusive one at its original queue position and consumes the shared hold; asking exclusively for a resource the same process already holds shared still waits for itself until the timeout. The raw `acquireResourceLease` (polling SQLite) is not queued and prefers readers, so mixing it with queued requesters can starve a queued writer; image paths use the queue unless `maximumLeaseDatabaseBytes` is set, and whether the raw primitive should prefer writers is an open owner decision. A single `repo run` that holds an image exclusively for hours (a store ownership walk after a dependency generation change) blocks every other command on that image: read the head ticket before restarting a sync. The target `test-resource-lease-fairness` of `@semio-tech/framework-process` runs the fixture-driven suite (queued Bun and Node clients against a queued writer, Python `sqlite3` readers as the independent client, dead predecessors, CPU cost, progress text, upgrade rules). Recorded: a plain `bun test` of the fairness file on the live tree on 2026-10-20 passed 10 of 11 tests; the failing case (`python-readers-queued-writer`, a timing case against Python readers) passed when run alone, so it is load sensitive. Not yet verified through `repo run`: the first check after the suite was applied (2026-10-20 05:05) is recorded as failed and was not repeated through the runner.
- **Cargo.** Raw `cargo` and `rustc` are refused by the compiler ingress gate in `.cargo/config.toml`. Compile through `repo cargo --store=shared|isolated --configuration=prototype|release [--parallelism=<cores>] -- <cargo subcommand> <args>`; `--store` and `--configuration` are mandatory and the Cargo subcommand follows `--`; without `--manifest-path` Cargo reads the `Cargo.toml` of the working directory (the root workspace when called from the root; `🏃️process/🦀️cargo/🚪️launcher`). Never create a private `CARGO_TARGET_DIR`: the shared store is a fixed-capacity partition and parallel private targets exhaust the disk. Before Cargo starts, `repo cargo` admits the Source of every compilation unit. The store-custody recheck inside that admission is throttled to one per 15 s (`storageRecheckGateV1`; `storageRecheck.intervalMilliseconds` in the admission schema; the first call and the completion call always recheck), and `rustc --print cfg` is computed once per exact argument vector; on a real image at load about 55 an admission unit with 12 reads dropped from 12.3 s to 3.0 s. A compile that finds the Rust image below the compiler charge (4 GiB) frees space through the recovery in `📚️library/⚡️caching/💾️storage/🔒️enforcement/🏗️compiler/📏️capacity/♻️recovery`, which compares the invocation identity of the control (`requireIssuedResourceControlInvocationV1`), not its signal. After a refactor that touches many crates, run small `repo cargo` invocations one after the other, never beside a dependency sync or a graph inference (all three take long store leases); the resumable plan that sequenced the 2026-10-20 recompile window (205 required steps over 644 crates, at most 8 `-p` packages each) is a tool of the coordination ticket, not a `repo` command. Not yet verified: when this was written that window had only started its first lock-refresh step, so the value-family, proctor and activation-closure compiles are still unproven.
- **Zero-touch.** The build CLI must boot on a fresh clone with no `node_modules`, no installed tool and no cache image, because the dependencies live inside a cache partition the CLI itself creates. Everything in the CLI import closure (`📚️library/🏗️build/📜️script.ts`) therefore imports by relative path, never through a bare `@semio-tech/*` specifier, and the `dependencies` command and the environment bootstrap run before the dependencies partition is pinned. After editing a library module, check `repo --help`: it must print the usage line. The same bootstrap must work unchanged in the devcontainer, native Windows, native macOS and native Linux (see Setup per platform below). The law `bun ./📜️script.ts verify zero-touch` keeps that closure honest (see Build owner registry).
- **Cancellation and progress.** The catalogue below declares every operation cancellable (`cancellable`) and every operation except `graph` and `show` as reporting progress (`progress`) in `📚️library/🏗️build/⚙️operations/🔣️catalog.json`; the implementations pass the caller's process control to every path (`runOwnedBuildInLeasesV1` in `📚️library/🏗️build/📜️script.ts`). Not yet verified: no per-operation cancellation run has been recorded.

## 📘️ Build tools guide

This guide is the working view of the tool-neutral build system: which tool to pick, what each operation does, how results are cached and shared, how work is spread over workers and executors, and how to classify a new target. The reference sections after it (Neutral model to Remote cache) hold the contracts, the measurements and the open items. Every command below is an operation of the catalogue `📚️library/🏗️build/⚙️operations/🔣️catalog.json`; `repo <command> --help --lang=en|de` prints the same usage in English or German. Where `repo` is not on the `PATH`, write `bun repo`, the root package script. A German version of this guide follows in the German chapter (Build-Werkzeuge im Alltag).

### 🔀️ Choose the tool

- **Select.** `--tool=nx|bazel` wins, then the environment variable `SEMIO_BUILD_TOOL`, then the policy default `nx`. The choice is exported as `SEMIO_BUILD_TOOL` to every nested task, so a task that calls `repo` again stays on the tool you chose. The dashboard axis `build-tool` sets the same variable. Anything else is refused ("Unknown build tool").
- **Provision.** `repo tools setup all` installs the pinned Nx and Bazel for this host; `repo tools setup nx` or `repo tools setup bazel` installs one. `workspace:setup` runs the same step.
- **One graph.** Both tools run the same neutral graph with the same task ids (`<project>:<target>[:<configuration>]`). A selection that resolves to different tasks under the two tools is a defect, not a feature.

| | Nx (default) | Bazel (`--tool=bazel`) |
|---|---|---|
| What runs | one `nx run` per selection | one generated workspace per selection; a task is a Bazel action, a selected cached `test` task is a Bazel test, a service is a `bazel run` target |
| Local cache | task results in `nx/artifacts` of the rust partition | action cache of the output base plus the disk cache `bazel/actions` of the products partition |
| Remote cache | Nx self-hosted cache API | Bazel HTTP cache protocol, token through a credential helper |
| Remote execution | no | opt-in for targets that declare `metadata.semio.hermetic` |
| Concurrency | `NX_PARALLEL` | persistent workers and `--jobs` |
| Reuse across selections | by task hash in the task cache | by action key in the disk cache: a second selection reuses the first one's results |

Use Nx for the default flow. Choose Bazel when you want results shared across selections and machines, workers, or remote execution. Both are driven by the same flags; where a tool cannot honour a setting, `repo cache remote status` lists it as `unsupported` (see Remote cache for the Nx fields).

### ⚙️ The neutral operations

| Operation | What it does | Example |
|---|---|---|
| `run` | one task and the tasks it depends on | `repo run @semio-tech/semio-tech-play:serve --tool=bazel` |
| `run-many` | the same targets in many projects (`--projects`, `--exclude`, `tag:`, `name:`, `directory:`, `!` patterns) | `repo run-many --targets=test --projects=tag:rust --tool=bazel` |
| `affected` | targets in the projects changed against `HEAD` (tracked changes plus untracked files) and their dependents | `repo affected --targets=build --base=main --head=HEAD` |
| `exec` | a command once per project, project root as working directory, `SEMIO_PROJECT_NAME` and `SEMIO_PROJECT_ROOT` exported | `repo exec --projects=@semio-tech/repo-client -- bun test` |
| `--dry-run`, `--graph` | print the task graph as a `DryRunPlan` and run nothing; `--graph=<file>` writes it | `repo run-many --targets=build,test --dry-run` |
| `show`, `graph`, `watch` | the neutral graph, and a command rerun on source changes | `repo show projects --json` |
| `cache status`, `cache clear` | count or empty the selected tool's local task cache | `repo cache status --tool=bazel` |
| `cache remote status`, `cache serve` | the remote cache contract and a local cache server (see Caching model) | `repo cache remote status --tool=bazel` |
| `reset` | invalidate the graph and reset the tool's local state | `repo reset --tool=bazel` |
| `remote-execution serve`, `status`, `env` | run, inspect or describe the optional local remote execution cluster (see Remote execution) | `repo remote-execution status` |

- **Dry runs and graphs.** `--dry-run` and `--graph` print the same `DryRunPlan` for every tool and start neither Nx nor Bazel: `roots`, `tasks` and `dependencies` (under Bazel also `selected`, and dependencies on services in `continuousDependencies`). The plan says what would run, not what is cached; use `cache status` for that.
- **Affected.** The rule is the same for both tools: the deepest project that owns a changed file, projects whose target inputs name a changed `{workspaceRoot}/…` file, every project when `nx.json` changes, then all dependents. Bazel answers it with a `rdeps` query over a generated package, cross-checked against Nx's own locators on four of five change sets; a change to `bun.lock` alone is the known difference (Nx treats it as "everything", the neutral rule and Bazel see only path ownership). `--projects` is refused for `affected`; narrow with `run-many`.
- **Cancel and progress.** Every operation can be cancelled (Ctrl+C) and reports progress lines while it walks, queues or downloads; a cancelled run stops at the next checkpoint.
- **Bazel specifics.** A selection builds exactly the transitive closure of the selected tasks, nothing else is analysed. `run-many` is one Bazel invocation with all labels, so shared dependencies run once. When a selected task is a test the invocation is `bazel test` (with `--build_tests_only` only when every selected label is a test); `--skip-cache` adds `--nocache_test_results`.

### 🗣️ Language and option spelling

- **No default language.** The CLI never assumes a language for its help, progress and refusal texts. It takes the first source that names an offered language (`en`, `de`): `--lang=<en|de>`, `SEMIO_LANGUAGE`, `LANGUAGE` (first offered entry), the first non-empty of `LC_ALL`, `LC_MESSAGES`, `LANG` (`C` and `POSIX` name none), then the operating system language list (macOS preferences, the Windows user locale; other systems state theirs in the environment). `--lang` and `SEMIO_LANGUAGE` must name an offered language; a locale that names an unoffered one is skipped. When nothing resolves, the command refuses before it starts, in English and German, and names every way to choose (for example `SEMIO_LANGUAGE=en` in CI). One module owns the rule: `🧰️framework/🔨️modules/🏃️process/🏗️build/🗣️language`.
- **Keine Standardsprache.** Die CLI nimmt für Hilfe, Fortschritt und Ablehnungen nie eine Sprache an. Maßgeblich ist die erste Quelle, die eine angebotene Sprache (`en`, `de`) nennt: `--lang=<en|de>`, `SEMIO_LANGUAGE`, `LANGUAGE` (erster angebotener Eintrag), die erste nicht leere Variable aus `LC_ALL`, `LC_MESSAGES`, `LANG` (`C` und `POSIX` nennen keine), danach die Sprachliste des Betriebssystems. Lässt sich nichts bestimmen, verweigert sich der Befehl vor dem Start auf Englisch und Deutsch und nennt alle Wege zur Auswahl (etwa `SEMIO_LANGUAGE=de` in CI).
- **Options.** An option with a required value (`--tool`, `--workers`, `--lang`, `--configuration`, `--store`, `--output`, `--projects`, ...) may be typed as `--option value` or `--option=value`, also by its short alias; the CLI door rewrites it to `--option=value` before anything else reads it. Options with a separate or optional value and everything after `--` stay as typed. `repo <command> --help` lists, for a subcommand, only the options and examples that belong to it, followed by the notes of its operation.
- **Temporary directories.** `repo incremental` keeps its disposable copy in the folder `sinc` of the temporary directory of the process (inside a test sandbox, the sandbox directory); pass `--root` when that path is longer than 100 characters.

### 💾️ Caching model

A result is reused when the key of the task is unchanged. Each tool derives its key from the same declared `inputs` (files and named groups, environment values, `runtime` command outputs, the closure of the files the command script imports, platform, Bun version, build mode) and from the identity of the build tool itself. Consequences: a file the task reads but does not declare does not invalidate it (a stale hit, not a failure); an edit to the build tool's own implementation re-keys its tasks once (for Bazel the captured implementation is an input of every action), so expect one cold run after pulling such a change; a task that declares the whole repository as input re-keys on any edit and is an owner problem, not a cache problem.

| Layer | Where | Cleared by |
|---|---|---|
| Nx task cache | `.🧬semio/🦑️repo/⚡️cache/rust/fixed/m/nx/artifacts` (rust partition) | `repo cache clear` (`nx reset --onlyCache` inside the bounded Nx namespace) |
| Bazel action cache | output base `bazel/outputs/server/<hash>` of the products partition, one per generated workspace directory; the server idles out after 120 s | `repo cache clear` stops the servers and removes the output bases |
| Bazel disk cache | `.cache/b/p/m/bazel/actions`, collected down to 40 percent of the products budget, entries older than 30 days dropped | `repo cache clear`; survives `bazel clean` and the loss of a server |
| Remote cache | an HTTP endpoint you configure, or `repo cache serve` (store in `.cache/remote-cache`) | the server's own bound and eviction |

All build state below `.cache/b/<partition>` is derived and safe to delete when nothing runs (partitions `d` dependencies, `t` tools, `g` graph, `o` observations, `p` products, `l` leases, `n` Nx pool; see Cache partitions). `--skip-cache` ignores the local task cache of the run (for Bazel it also stops accepting remote hits), `--skip-remote-cache` ignores only the remote cache, and the dashboard axis `cache` offers `use`, `skip-local` and `skip-all`.

- **Early cutoff.** Under Bazel a task whose output snapshot is byte-identical after its input changed does not re-run its dependents (measured: a whitespace-only edit of a generator input re-ran the generator only).
- **Store receipts.** Products that live in a leased store, not in the project directory, declare a receipt as their only output; both tools verify it after every run and re-run that single task uncached when the receipt is damaged. See Store receipts.

**Remote cache.** It is off until `SEMIO_REMOTE_CACHE_ENDPOINT` names an `http://` or `https://` origin; the contract and its variables are in the Remote cache section.

```bash
repo cache serve --port 6090
```

```bash
SEMIO_REMOTE_CACHE_ENDPOINT=http://127.0.0.1:6090 SEMIO_REMOTE_CACHE_ACCESS=read-write repo run @teaching/architecture-course:test --tool=bazel
repo cache remote status --tool=bazel
```

In PowerShell the same is `$env:SEMIO_REMOTE_CACHE_ENDPOINT = "http://127.0.0.1:6090"`, `$env:SEMIO_REMOTE_CACHE_ACCESS = "read-write"`, then `bun repo run @teaching/architecture-course:test --tool=bazel`.

- **Access.** The default is `read-only`; results are pushed only with `SEMIO_REMOTE_CACHE_ACCESS=read-write` and `SEMIO_REMOTE_CACHE_UPLOAD` not `false`. The token is read from the variable `SEMIO_REMOTE_CACHE_TOKEN` (or the variable named by `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT`) and never appears in a flag or on disk beyond one build: Bazel receives it through a credential helper, Nx through its own variable. Nx cannot withhold uploads, so for Nx read-only means a read token on the server.
- **`cache remote status`.** Prints the resolved contract (`configured: false` while no endpoint is set), the rendering the selected tool gets with its `unsupported` fields, whether the token variable is set (never its value) and a read-only probe of the endpoint: `reachable`, `authorized` and the HTTP status. It stores nothing.
- **`cache serve`.** Serves Bazel's HTTP cache protocol (`/ac/<sha256>`, `/cas/<sha256>`, blobs verified against their digest) and the Nx self-hosted cache API (`/v1/cache/<hash>`) from this machine until you stop it. Options: `--port` (default 6090, `0` picks a free one), `--host` (default `127.0.0.1`), `--directory`, `--max-bytes` (default 4 GiB, at least 1 MiB; the least recently used entries go first). Tokens come from `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` and `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; without a token the server refuses to listen beyond loopback. The dashboard tool `build-cache-serve` starts it.
- **Download modes.** `toplevel` (default) and `all`. `minimal` is not part of the contract and the schema refuses it: the Bazel adapter restores the snapshot of every selected task from `bazel-bin`, and with `minimal` the snapshot stays in the remote store, so the restore fails with `ENOENT` and nothing reaches the checkout (measured). Nx always fetches everything.
- **What is shared.** Bazel keys of today's tasks contain the absolute Bun path and the checkout root of the captured implementation, so a hit across machines needs the same user and checkout path. Hermetic actions (next section) have host-independent keys (measured: the same inputs at a different checkout path hit the disk cache).

### 🌍️ Remote execution

Remote execution is optional and opt-in per target. The build system defines the contract and the Bazel rendering; it ships no executor.

- **Declare.** A target is a hermetic action only when its manifest says so: `"metadata": { "semio": { "hermetic": { "version": 1, "tools": ["bun"] } } }` (schema `🏗️build/🏃️execution/🧬️schema/🔒️hermetic.json`). It must also be cached with a declared `outputs` array, run plain `command` strings, have only file inputs (no `runtime` or `env` input, no `{options.…}` or `{env.…}` token), not be continuous and not orchestrate other builds. A target that does not qualify keeps host state; the reason is closed (`undeclared`, `unsupported-execution`, `host-inputs`, `uncached`, `continuous`, `orchestration`, `tool`). No target in the repository declares it yet, so nothing runs remotely today.
- **What a hermetic action is.** It runs under a pinned Bun that is a declared tool input (downloaded under a lease with progress, verified by size and SHA-256 before extraction), in a sandbox or on a worker, with a strict environment (`LC_ALL=C`, `TZ=UTC`, `SOURCE_DATE_EPOCH=0`, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0`), no host path in its key, normalised outputs, and it fails on an undeclared write. Hermetic actions run the pinned Bun, not the one on your `PATH`.
- **Switch.** Unset keeps every action local; a malformed value fails closed.

| Variable | Meaning | Default |
|---|---|---|
| `SEMIO_REMOTE_EXECUTION_ENDPOINT` | `grpc://`, `grpcs://` or `unix:` URI of the executor | none (local) |
| `SEMIO_REMOTE_EXECUTION_PLATFORM` | worker platform: `darwin`, `linux` or `windows` plus `-arm64` or `-x64` | `linux-x64` |
| `SEMIO_REMOTE_EXECUTION_PROPERTIES` | extra worker properties, `name=value,…` (up to 16), added to the platform's `OSFamily` and `Arch` | none |
| `SEMIO_REMOTE_EXECUTION_JOBS` | concurrent actions while the executor is on | 128 (at most 512) |

- **Routing.** Only hermetic actions go to the executor, with `--noremote_local_fallback`: an unreachable executor fails the build, it never runs the action locally. Host-state actions stay local (`no-remote-exec`).
- **Executor requirements.** A service for Bazel's Remote Execution API v2 with content store, action cache and scheduler; workers whose properties match the platform (Buildbarn matches exactly; BuildBuddy uses `container-image` and `pool`); Linux workers need only the uploaded Bun, no checkout. Execution flags never carry cache settings: the cache endpoint, instance, upload, download mode and token stay with the remote cache contract, whose endpoint is an `http(s)` origin. Pointing Bazel at one gRPC service for cache and execution is not defined by the contract yet.
- **Platforms.** Network isolation of a hermetic action is enforced on Linux and on remote workers; macOS' sandbox cannot block it (measured with Bazel 8.4.2). On Windows there is no sandbox, so the runner refuses a hermetic action there (the source link is a junction); run Windows hermetic targets remotely.
- **Optional local cluster.** `repo remote-execution serve` runs a local Buildbarn cluster (storage with content store and action cache, frontend, scheduler, worker, runner) in containers until you stop it and then removes the containers and volumes. It needs a running container runtime with the compose plugin; every image is an official one, pinned by digest. The frontend answers on `127.0.0.1:8980` and its health route on `8981` (`--port` and `--diagnostics-port` move them); the cluster has no authentication and listens on loopback only. `--platform=<id>` selects the worker platform (default: the one that matches this machine's CPU, `linux-arm64` or `linux-x64`). `repo remote-execution status` shows the runtime, the containers and whether the frontend answers, and `repo remote-execution env --platform=linux-x64` prints the variables a client sets, one `NAME=value` per line. The runner has no network, so a hermetic action there gets a real network namespace without a network. It is a developer service, never a dependency: with `SEMIO_REMOTE_EXECUTION_ENDPOINT` unset every action stays local.

### 👷️ Worker pools

Persistent workers keep a process alive between actions, so an action no longer pays for starting and loading the build tool again.

- **Switch.** `--workers on|off`, then `SEMIO_BUILD_WORKERS`, then the worker policy in `📚️library/🏗️build/🔣️policy.json` (`enabled`, on by default). `--parallel <n>` or `SEMIO_BUILD_PARALLEL` sets the number of concurrent tasks (default: the number of cores, at most 8).
- **Kinds.** The kind is derived from the target name and continuity, never from the tool; the first matching rule wins.

| Kind | Target names | Instances at most |
|---|---|---|
| `service` | `continuous: true` | none (never a worker) |
| `test` | `test`, `smoke`, `mutation`, `bench`, `e2e` (also `<name>-…`) | 8 |
| `check` | `check`, `lint`, `verify`, `typecheck`, `format-check`, `contract`, `schema`, `stdio` (also `<name>-…`), and names ending in `-check` | 8 |
| `generate` | names with `generate` or `generator` | 4 |
| `build` | `build`, `prepare`, `activate`, `wasm`, `native`, `package`, `bundle`, `cpp`, `publish`, `canonical`, `preview`, `setup`, `deps` (also `<name>-…`) | 2 |
| `script` | everything else | 4 |

- **Budget.** All pools together may use 30 percent of the host's memory at 512 MB per worker. Each kind gets one instance first (test, check, generate, build, script, as far as memory holds), the remaining instances go to the kinds in the same order up to their bound and the job count; a kind that finds none runs without workers.
- **Bazel.** Workers speak Bazel's JSON worker protocol, run the action body inside the worker process (leaf commands stay separate process trees), support cancellation and shrink the pool under memory pressure. Worker and non-worker actions have the same action key, so caches are shared across both modes. Actions that never use workers: services, hermetic actions and tests run as `bazel test`. Cargo tasks run one at a time.
- **Nx.** Nx forks a process per task, so only `NX_PARALLEL` is mapped (to the job count); `NX_BATCH_MODE` is set only for an executor that registers a batch implementation, which none does. Every other worker setting (pools, instance bounds, memory, sandboxing) is unsupported under Nx.
- **Measured.** CPU per action fell from 2.50 s to 1.46 s in steady state; wall clock was not consistently better on a saturated host, because 85 percent of a warm in-worker request is opening the graph cache store.
- **Turn them off** with `--workers off` to compare against one process per action, to debug a single task, or when memory is scarce.

### 🚦️ Task dispositions

Every task has a tool family (`bun-script`, `tsc`, `vitest`, `bun-test`, `vite`, `playwright`, `go`, `python`, `dotnet`, `latex`, `wasm`, `cargo`, `docker`, `aggregate`) and one disposition. Nx runs all of them as `nx run`; Bazel maps them as follows (`📚️library/🏗️build/🏃️execution/🧬️schema/🎯️coverage.json`).

| Disposition | Meaning | Under Bazel |
|---|---|---|
| `action` | cached, replayed from the action cache | cached build action, output snapshot restored into the checkout |
| `test` | cached and named `test` or `test-…`, `outputs: []`, nothing else selected consumes it, at most 10,000 declared files | `bazel test`: the passed result is cached, `(cached) PASSED` on the next run; not used where the platform has no runfiles (Windows) |
| `interactive` | `continuous`, runs until stopped | `bazel run` target; it starts on every run and is never produced |
| `uncached` | always executes; its recorded reason says why | action tagged `no-cache` |
| `refused` | `cache` or `outputs` left undeclared (reasons `undeclared`, `unbounded`) | fail-closed until the owner declares what is missing |

Static census of 2026-10-20 (8,028 tasks of the reconstructed graph, with the classification sets applied): 3,771 cached (actions and tests), 1,320 interactive, 2,937 uncached with a recorded class, 0 refused and 0 uncached for the reason `declared` (373 before).

### 🏷️ Classify a new target

Answer these in order; the first yes decides.

1. **Does it run until stopped** (server, watcher, shell)? `"continuous": true`, class `continuous`, reason `serves-until-stopped`. It becomes `interactive`.
2. **Does it read only repository files, write only declared outputs (or none), use no network, host store, lease, clock or running process?** Then cache it: `"cache": true`, `inputs` for everything it reads outside its project, `outputs` (`[]` for a pure check), and give it a cached name family or its own decision (below).
3. **Otherwise** `"cache": false` plus the decision that names the reason.

| Class | Reasons | Use for |
|---|---|---|
| `deterministic` | `pure-function-of-inputs` (declare outputs), `check-without-outputs` | cached checks, tests, generators with declared outputs |
| `continuous` | `serves-until-stopped` | servers, watchers, shells |
| `live` | `drives-running-process`, `exercises-host-resources` | e2e against a running process, tests of real locks, storage, process trees |
| `side-effecting` | `mutates-workspace`, `mutates-host-store`, `publishes-remote`, `publishes-live-state` | formatters, scaffolders, installers, releases |
| `diagnostic` | `measures-environment`, `reads-caller-input`, `admission-refusal` | benchmarks, doctors, tools driven by their arguments |
| `aggregate` | `orders-prerequisites`, `reenters-build-tool` | pure ordering; a verb that runs other targets through `repo` should declare them in `dependsOn` instead |
| `managed-output`, `driver-owned` | `outputs-in-managed-store`, `outputs-are-store-links`, `freshness-owned-by-driver` | store-published builds and driver-owned playground steps |

The policy resolves a target name in this order (`🎯️target-policy`): continuous names, `cache: false`, the policy's uncached names, mutating and live names, then your decision in `metadata.semio.cache`, then the policy's `targetClasses` (name families such as `test`, `check`, `lint`, `typecheck`, `verify`, `build`, `generate`), then a `verify` command. **A target that none of them classifies never replays** (`unclassified`, `no-cache-classification`), and `"cache": true` alone does not change that, so give an unusual name its decision:

```json
"digest-inputs": {
  "executor": "repo:script",
  "cache": true,
  "inputs": ["default", "^default"],
  "outputs": [],
  "options": { "command": "bun ./📜️script.ts digest-inputs" },
  "metadata": { "semio": { "cache": { "version": 1, "class": "deterministic", "reason": "check-without-outputs" } } }
}
```

```json
"measure-startup": {
  "executor": "repo:script",
  "cache": false,
  "outputs": [],
  "options": { "command": "bun ./📜️script.ts measure-startup" },
  "metadata": { "semio": { "cache": { "version": 1, "class": "diagnostic", "reason": "measures-environment" } } }
}
```

- **Outputs.** A cached target must produce every declared output that is not a glob: otherwise it fails with "Declared output of a replayed Bazel task was not produced". Set `metadata.semio.optionalOutputs: true` only for an output that is legitimately absent. A `pure-function-of-inputs` target without declared outputs is demoted to `side-effecting`.
- **Test under Bazel.** Name it `test` or `test-<what>`, keep it cached with `outputs: []` and under 10,000 declared files (every declared file is linked into the test's runfiles before every run, even on a hit).
- **Remote execution.** Add the `hermetic` declaration (see Remote execution) only when the target truly reads its declared inputs alone.
- **Law.** The cache-correctness law (`📚️library/⚖️laws/🔒️cache-correctness`) reads every manifest through the production policy and fails for an unclassified target, a cached target that the policy overrides, an uncached target without a recorded reason, empty inputs, a producer without outputs, an unhashed environment override, a named input nobody declares, outputs that escape or overlap, and a mutating or network command in a cached target.

### 🔁️ Incremental builds and how to verify them

An incremental build re-runs exactly the tasks whose declared inputs changed and replays the rest. Prove it with the operations you already have; the CI job `smoke` is written to do the same for both tools on `@teaching/architecture-course:test` (the workflow has not run yet).

```bash
repo cache clear --tool=bazel
repo cache status --tool=bazel
repo run @teaching/architecture-course:test --tool=bazel
repo cache status --tool=bazel
repo run @teaching/architecture-course:test --tool=bazel
repo cache status --tool=bazel
```

1. Note the counts after `cache clear`; after the first run `entries` and `bytes` grew and, for Bazel, `activity.executed` counts the actions that ran.
2. The second run spawns no work: Bazel's summary shows no `local`, `worker` or sandbox spawn (or `disk cache hit`), `entries` do not grow and `activity.executed` stays, while `activity.cacheHits` counts the hits.
3. Edit a file the task declares: only that task and its dependents run (a dependent whose input snapshot is unchanged is replayed). Edit a file it does not declare and nothing runs: the input list is too short.
4. `repo cache clear` followed by the run proves a cold miss; `--skip-cache` forces execution once without clearing; `--dry-run` shows the plan the run would execute.
5. Expect extra work after: editing the build tool's own files (every action is re-keyed once), switching `prototype` and `release` (the mode is part of every key), and editing a declared input while the build runs (Bazel prints `Skipping uploading outputs because of concurrent modifications` and the next run executes again).

### 🖥️ Cross-platform notes

| Host | Notes |
|---|---|
| macOS | Cache partitions are case-sensitive APFS images, no privilege. Keep the checkout path ASCII (Bazel crashes at startup on a non-ASCII install base and its sandbox mis-encodes a non-ASCII output base; the layout is refused up front). The adapter sets a UTF-8 locale. |
| Linux | Directory-backed partitions, no root and no loop device; needs a case-sensitive file system with atomic directory exchange (ext4, xfs, btrfs). A non-ASCII `install` path is refused; a non-ASCII output base works. In an unprivileged container Bazel falls back to `processwrapper-sandbox` (same results, weaker isolation); `linux-sandbox` needs a privileged container. The adapter never names a sandbox strategy. |
| Devcontainer | As Linux. `.cache` is a named volume private to the checkout (a bind mount from a case-insensitive host is refused by `repo preflight`); `postCreateCommand` runs `repo run workspace:setup`. |
| Windows | Directory partitions swapped by a journaled rename on NTFS with per-directory case sensitivity. Needs `LongPathsEnabled` and a short ASCII checkout root (the Bazel path budget is `len(output base) + len(\execroot\_main\s\) + 256` against 259, or 32766 with long paths). The source link is a junction (no developer mode, no elevation), runfiles are off (`--noenable_runfiles`, startup `--nowindows_enable_symlinks`), so tests run as cached actions instead of `bazel test`, and hermetic actions are remote-only. Set variables with `$env:NAME = "value"` in PowerShell and call `bun repo`. Not run on Windows. |

No cache path may exceed 256 characters on any host. Bazel and Bun are pinned per OS and CPU (darwin, linux, windows on arm64 and x64) with checksums, so `repo tools setup` needs no manual download.

### 🩹️ Troubleshooting

- **A command refuses after a reboot or image reattachment** ("Exact canonical persistent Native publication required …"). Publication receipts remain immutable. Device numbers are scoped to the current kernel namespace and can change after a reboot or a parent image reattachment within the same boot. A current publication is observed through the freshly anchored backing device while its published inode, mode, required ancestor chain, physical limits and kernel association remain exact; this does not rewrite a receipt or transfer deletion authority. An unsupported receipt is refused. The fixed **Reset Inactive Nx Cache** control covers only the canonical inactive macOS Nx capsule; other changed, mounted, busy or unknown states remain diagnostic refusals (Recovery).
- **A command waits.** Stores are claimed through a first-in-first-out lease queue. A waiter at position 2 or later prints a `lease-queue` line every 15 seconds that names the holder's process id; a line `remains active on …` is progress of a running walk, not a wait. Do not kill a holder that is making progress; read the head ticket first.
- **A receipt fails.** Store receipt: one task re-runs uncached (`[store-receipt] re-executing`). Dependency generation receipt: an edit of any file in its closure costs the next command one complete walk (progress `dependencies:generation-verify:<n>`). Image receipt: see the first item.
- **No cache hit.** Check in this order: `--skip-cache` or the dashboard axis `cache` set to a skip value; the target's decision in the manifest (`unclassified` never replays); an undeclared or too wide input; the mode (`prototype` vs `release`); another process editing declared inputs during the build; for a remote hit a different user or checkout path.
- **Remote cache.** `repo cache remote status` shows `configured: false` when no endpoint is set, `reachable: false` when the endpoint does not answer and `authorized: false` for a wrong token (Nx aborts a run on 401, ignores 403 on upload silently).
- **Workers.** Rerun with `--workers off` to separate a worker problem from a task problem. A build that fails with "Captured implementation Source changed" saw a build-tool file change under it; rerun it.
- **Installed packages.** `Cannot find module` for a workspace package means the dependencies are older than the sources: `repo dependencies lock --all`, then `repo dependencies sync --all`. On a fresh clone the Nx setup may need the installed workspace links: if it stops with `Cannot find module`, run the sync first.
- **Nx reports `.nx/installation` missing.** Run `repo tools setup nx`.

**Tool selection.** `--tool=nx|bazel` on the command line wins, then the environment variable `SEMIO_BUILD_TOOL`, then `defaultTool` of the policy (`nx`). The selected tool is exported as `SEMIO_BUILD_TOOL` to every nested task, so a task that calls `repo` again keeps the tool; the dashboard axis `build-tool` sets the same variable (see Command registry). Anything else is refused ("Unknown build tool"). Choose the compiler configuration with `--configuration=prototype|release` (or `-c`, a `:<configuration>` suffix on the task, or `SEMIO_BUILD_MODE`); disagreeing values are refused ("Conflicting build modes", stated in English and German, naming the fixed-mode targets such as `dev` that pin a mode). The mode is one invocation axis, not a per-target setting: the Bazel implementation accepts `prototype` and `release` for every target whether or not the target declares them as configurations, every planned task of every target carries the mode in its id, label and workspace, the dependencies of the selected task inherit the mode, the original caller's mode is the authority every task environment exports (`SEMIO_BUILD_MODE`) and is part of every action key, and the plan refuses a task whose mode differs from the caller's and a dependency whose target is fixed to another mode. Only `prototype` and `release` can be selected at the command line; other configuration names exist only in the Bazel adapter. The course verbs that need release (`publish`, `test-e2e` rehearsal, `docker-image-build`, `docker-image-publish`, `deploy-check` of `@teaching/architecture-course`) read the original caller's mode and refuse a prototype caller in English and German; select release with `bun repo [--tool=bazel] run @teaching/architecture-course:publish:release`.

**Operations.** The state of each operation per tool: `native` = the tool's own command, `adapter` = our code drives the tool, `neutral` = tool independent, `missing` = not implemented and the call refuses.

|---|---|---|---|---|

| `--help`, `-h`; `--lang=en\|de` | Print the usage of the command in English or German and stop. | all |
| `--projects`, `-p`, `--exclude` | Comma lists of project names with `*` wildcards, `tag:<tag>`, `name:<name>`, `directory:<root>`, `!<pattern>` negation. | `run-many`, `exec`, `watch`; `--exclude` also `affected` |

**Result shapes.** Results that scripts consume are specified by the schema `⚙️operations/🧬️schema/🔣️.json`:

- `DryRunPlan`: `{"tasks":{"roots":[<id>],"tasks":{<id>:{"id":…,"target":{"project":…,"target":…,"configuration"?:…}}},"dependencies":{<id>:[<id>]},"continuousDependencies"?:{<id>:[<id>]}}}`. A task id is `<project>:<target>[:<configuration>]`; `exec` uses the target `repo-exec`. The Bazel plan adds `selected` (the requested task ids) and lists dependencies on continuous tasks apart in `continuousDependencies`, because those only have to be running.
- `CacheStatus`: `{"version":1,"tool","available","directory","entries","bytes","activity"?:{"builds","actions","executed","cacheHits"}}` (`activity` is filled by Bazel). `CacheClear`: `{"version":1,"tool","cleared","removedEntries","removedBytes"}`.

## 📋️ Manifests

A task in `targets` of a `📋️project.json` uses these fields:

| Field | Meaning |
|---|---|
| `executor` | `repo:script` (default, runs `command` through the repo process authority) or `repo:noop` (ordering only, runs nothing). |
| `command`, `options.command`, `options.commands`, `options.args` | What runs; `args` are literal arguments that are never shell-interpolated. `configurations.<name>` may override `command`, `commands`, `cwd`, `env`, `args`. `defaultConfiguration` names the configuration used when none is requested. |
| `dependsOn` | Tasks that must finish first: `"target"` (same project), `"^target"` (dependency projects), `"project:target"`, or `{target, projects, dependencies, params}`. |
| `inputs` | What the result depends on, see below. |
| `outputs` | Paths the task writes, relative tokens `{projectRoot}`, `{workspaceRoot}` and option tokens such as `{options.env.SEMIO_BUILD_MODE}`. `[]` means "no files to restore". |
| `cache` | Boolean, see the classes below. |
| `continuous` | The task is a long-running service. |
| `metadata.semio.dashboard.ready` | How readiness of a continuous task is detected: the output shows `http://(127.0.0.1\|localhost\|0.0.0.0):<port>` and that address answers 2xx or 3xx; `port` or `portEnv` declares the port, `path` appends a path, `printed` takes the whole printed address. |

**Inputs.** A list of file globs (`{projectRoot}/**/*`, `{workspaceRoot}/…`, `!` excludes), named groups from the policy (`default`, `production`, `cargo`, …), `^<group>` (the same group of the dependency projects), and objects: `{"env": "NAME"}`, `{"runtime": "<command>"}` (the command's output), `{"externalDependencies": [...]}` and `{"dependentTasksOutputFiles": "<glob>", "transitive": true|false}` (the outputs of the tasks in `dependsOn`). Declare everything the task reads that is not reachable from its own project: data outside the project, spawned test files, tool and toolchain files, environment. A project can add its own `namedInputs` (for example `reads`, `testEnv`, `cargoToolchain`). `default` of a project replaces the workspace `default`, so re-add `sharedGlobals` (platform, Bun version, `SEMIO_BUILD_MODE`) there.

**Command source closure.** A `repo:script` target needs no hand-written list of the modules its script imports. The graph inference derives the closure of the command script (`📚️library/🏗️build/🕸️graph/📥️inference/🧭️script-inputs`): relative imports, imports through workspace package specifiers such as `@semio-tech/process/leases` (`workspacePackageModuleV1`; installed registry packages stay covered by their locked external dependency), literal `new URL("…", import.meta.url)` targets that exist (modules are followed, other files are hashed as resources), and literal module inputs a target declares (for example `{projectRoot}/…/x.test.ts`). The closure joins the target as named inputs `commandSources…`; in the hash representation of the graph it is the marker `{"env": "SEMIO_SOURCE_CLOSURE_<sha256 of the manifest>"}` and the manifest sits in the graph store under `build-input-closures`, which Nx reads when it hashes the task. Cargo lock projections are markers of the same kind (`SEMIO_CARGO_LOCK_<key>`). Bazel expands the markers itself (see Bazel implementation). A target opts into more derived closure with `metadata.semio.closure`: `modules` lists `{projectRoot}`/`{workspaceRoot}` globs of module files (a test directory the router never imports) whose matches join as entries together with their import closure, and `typescript` lists tsconfig paths whose compiler program (include set, path mappings, `.d.ts` siblings, type-only imports, `extends` chain) joins the closure and names the installed type packages it resolved. References such as `new URL("x.json", origin(import.meta.url))` and `join`/`resolve(<module directory>, "x.json")` with literal segments join as files. Deliberately not covered: in-source test imports guarded by `import.meta.vitest`, files read through computed paths, and targets that are never cached (continuous, live). The course keeps this honest with `🏗️build/🕸️graph/📥️inference/🧪️tests/🎓️course-inputs` (esbuild, the TypeScript program and an independent Python implementation against the manifest). Measured on a sample of 49 project scripts the closure grew from a median of 489 to 1,200 files (about 28 percent more CPU for the derivation, offset by an admission memo that cut the old cost by 35 percent). Not yet verified: the assembled inputs in a real graph load (`repo show projects` was stopped on 2026-10-20 after 4 hours; the later analysis found it garbage-collection bound under host memory starvation, not quadratic in the closure code: a project costs 0.3 to 0.45 CPU-s, the closure derivation takes about 29 percent of that, and a clean run is estimated at 25 to 40 minutes), an Nx hash of a real task, and a Bazel run with expanded closures against the production entry.

**Cache classes.** `cache` is the switch both tools read. Next to it the inference attaches a machine-readable decision `metadata.semio.cache = {"version":1,"class":…,"reason":…}` to every target it forces, synthesizes or refuses to replay (closed schema `📚️library/🏗️build/🏃️execution/🧬️schema/💾️cache.json`). The class names the physical fact that allows or forbids a replay:

| Class | Reasons | Meaning | Cached |
|---|---|---|---|
| `deterministic` | `pure-function-of-inputs`, `check-without-outputs` | A pure function of its declared inputs; every declared output is a plain restorable tree, or there is none. | yes, the only replayable class |
| `driver-owned` | `freshness-owned-by-driver` | The command compiles through the build driver, whose Cargo freshness and stage cache are the authority (playground `prepare-*` and `build-*-react*`, `component`). | no |
| `managed-output` | `outputs-are-store-links`, `outputs-in-managed-store` | Outputs live in the leased products store behind a binding or manifest protocol (TypeScript artifact `build`, wasm slots) and the manifest does not author `cache: true`; restoring a copy would be refused or bypass the store. With `cache: true` the target is `deterministic` instead, because its receipt is the restorable output (see Store receipts). | no |
| `continuous` | `serves-until-stopped` | Runs until stopped. | no |
| `side-effecting` | `publishes-live-state`, `publishes-remote`, `mutates-workspace`, `mutates-host-store` | Mutates state outside its declared outputs. | no |
| `live` | `drives-running-process`, `exercises-host-resources` | Observes or drives a running process (names with `e2e` or `live`), or exercises the real locks, storage, process tree or clock of this machine. | no |
| `aggregate` | `orders-prerequisites`, `reenters-build-tool` | Orders prerequisites and does no work of its own. | no |
| `diagnostic` | `admission-refusal`, `measures-environment`, `reads-caller-input` | Reports a refusal or a measurement and is always re-evaluated. | no |
| `unclassified` | `no-cache-classification` | No row, declaration or verifying command classifies the target, so it never replays until the policy names its kind (fail-closed). | no |

The Bazel adapter reads the decision (`bazelTargetCacheClassV1` validates it against the closed schema and refuses an invalid one with "Closed repository cache decision required") and derives its cache decision from the class, see the Bazel cache decision below. The Nx projection does not read it; Nx decides from `cache`, `continuous` and `outputs`. A manifest may declare it itself (a target with `cache: false` records its reason this way, see the Build tools guide); the synthesized playground targets, the TypeScript artifact `test`, `check` and (with `cache: true`) `build` targets, and the wasm slot producers with `cache: true` carry `deterministic`, targets cached by the name rules below carry the class of their row. The policy that sets `cache` and the decision follows this order, the first matching row wins (`📚️library/🏗️build/🕸️graph/📥️inference/🎯️target-policy`, names from `📚️library/⚡️caching/🔣️policy.json`):

| Order | Rule | Cached | Decision attached |
|---|---|---|---|
| 1 | `continuous: true`, or a name `dev`, `serve`, `watch`, `start`, `test-watch`, `daemon` (also `<name>-…`) | no | `continuous` |
| 2 | `cache: false` in the manifest | no | none |
| 3 | A name of the `uncached` list (`audit`, `bench`, `clean`, `deploy`, `deps`, `install`, `publish`, `seed`, `setup`, `test-e2e`, `update`, …) or an exact name (`format`, `commit`, `os`, `parity`, …); `cache: true` is overridden | no | `live` (`e2e`, `live`, `os`, `semio`), `diagnostic` (`audit`, `bench`, `doctor`, `parity`, …), `side-effecting` (`publish`, `deploy` as `publishes-remote`, otherwise `mutates-workspace`) |
| 4 | `hub-live-catalog-check`, `hub-live-catalog-native-check`, `hub-live-catalog-oracle` | yes | none (exceptions to row 5) |
| 5 | A dash-separated word `clean`, `gc`, `prune`, `setup`, `fuzz`, `e2e` or `live` in the name | no | as row 3 |
| 6 | The decision the target declares in `metadata.semio.cache`, else the first matching row of `targetClasses` in `📚️library/⚡️caching/🔣️policy.json` (ordered rows of exact names, heads, tails and tokens, each with a decision; an exact name beats the rest): `deterministic/check-without-outputs` for the heads `test`, `check`, `lint`, `typecheck`, `format-check`, `verify`, `schema`, `stdio`, a trailing `-check`, `-test`, `-oracle`, `-lint`, `-source` or `-native`, the token `contract` and a list of exact names; `deterministic/pure-function-of-inputs` for the heads `build` and `generate` and a list of exact producers; `side-effecting/mutates-workspace` for the head `generator` | yes when the class is `deterministic`, otherwise no | the class of the row; for `deterministic` the default inputs `default` and `^default`, outputs `[]` unless the manifest says otherwise |
| 7 | A `verify` command in the target | yes | `deterministic/check-without-outputs` |
| 8 | Anything else | **no** | `unclassified/no-cache-classification` |

Row 8 is fail-closed under both tools: a target that nothing classifies runs every time, whatever its `cache` field says (`unclassified`); the cache-correctness law (`📚️library/⚖️laws/🔒️cache-correctness`) reports it together with every `cache: true` that the policy overrode and every `cache: false` without a recorded reason. A `deterministic/pure-function-of-inputs` target that declares no output is demoted to `side-effecting/mutates-workspace` before either tool sees it (`cachedOutputsAdmittedV1`), because a hit would replay an empty success. Bazel additionally requires an `outputs` array and a class that allows replay, see its cache decision. Write `cache: false` plus a decision for these reasons (the convention across the manifests, mirrored by the classes above): tests that exercise real storage, lease, process or toolchain state; live host, browser or server runs; writers that rewrite the tree or a store outside their declared outputs; launchers of long-lived tools; network downloads; steps whose input set is unbounded (digests of the whole workspace).

**Store receipts.** Products that are published into a leased, content-addressed store instead of the project directory (Cargo artifacts in the compiler store, Vite sites, wasm packages, TypeScript artifacts) cannot be restored by copying files into that store from outside. They declare a receipt as their only output, `{projectRoot}/.🧾️store/<target>.json` (schema `📚️library/🏗️build/🧾️store-receipt/🧬️schema/🔣️.json`, git-ignored, deliberately not below `dist`, which is a link into the store for TypeScript artifacts). The receipt names each published store path (`entries`: kind, bytes, files, SHA-256; a directory digest hashes its sorted file list) and each link that binds a project path to a store path (`links`). The central publishers write it after publication, so no build script changes: the artifact destination that the Vite and wasm publishers write through (`⚡️caching/📦️artifacts/🟦️.ts`), the compiler store publisher of Cargo `build` (`⚡️caching/📦️artifacts/🏗️native-build/🟦️.ts`, skipped when an observation output is requested) and the TypeScript artifact binder (`⚡️caching/📦️artifacts/🟦️typescript/🔗️binding/🟦️.ts`). Both adapters hand the receipt location to the one task that declares it (`SEMIO_TASK_RECEIPT`, issued by `issueStoreReceiptV1` in `📚️library/🏗️build/🧾️store-receipt/🟨️.mjs`; Nx: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/🟨️.mjs`, Bazel: `executeTask` in `📚️library/🏗️build/🔧️tools/🏗️bazel/📜️script.ts`); every other task has it unset, so a nested task never records into its parent's receipt, and a publisher does nothing without it (`recordStoreContentV1`).

After every `run` or `run-many`, both tools verify the receipt of each selected task and of its prerequisites. A receipt that is absent, damaged or points at a missing or changed store entry counts as a miss: that one task reruns alone and uncached (Nx: `run <task> --skip-nx-cache --excludeTaskDependencies`, the one extra child selection the caller admits, which also replaces the cache entry; Bazel: in-process with `skipCache` and without dependencies, which leaves the stale disk-cache entry in place, so a later hit repairs again) and is verified again, and the invocation fails closed otherwise. A failed first run is retried once after the repair. A task that declares a receipt but whose handler wrote none is an error, not silently accepted. TypeScript artifact `build` and wasm slot producers carry the receipt as their output: they replay when the manifest authors `cache: true` (decision `deterministic`) and stay `managed-output` otherwise. A target declares a receipt only when its `outputs` list the receipt path (`declaredStoreReceiptV1`): `check`, `test` and `lint` publish a verdict, not store content, and `publish` and the course `build` list other outputs or none. Alternating `prototype` and `release` runs of one target share one receipt file (its path has no mode), so a switch is expected to rerun the target once (inferred from the path rule, not observed). Not yet verified: no run has exercised the repair path (first proof: run `@teaching/proctor:build` twice, delete the compiler `published/<hash>` slot, run again and expect one `[store-receipt] re-executing` line, with `--tool=nx` and `--tool=bazel`).

The Bazel implementation decides per action from `cache`, `continuous` and `outputs` and is stricter about missing declarations (see its cache decision below).

## 🔌️ Nx implementation

Nx is the default (`defaultTool`). The repository does not use Nx project discovery; it feeds the neutral graph into Nx.

- **Plugin.** `nx.json` registers the plugin `@repo/emoji-project-json` (`📚️library/🟨️.mjs`) for `📋️project.json`. Its `createNodesV2` publishes the neutral graph as Nx projects and its `createDependencies` publishes the neutral edges; it refuses edges whose projects it does not know. Each target is projected onto an Nx executor and receives a private engine identity as an additional input, so a change of the executing implementation invalidates cached results.
- **Executors.** `@semio-tech/repo-lib:command` and `@semio-tech/repo-lib:owner-command` (`📚️library/📦️packages/🟦️typescript/📋️executors.json`) `command` runs the literal command arguments through the original process authority and the Bun shell, `owner-command` forwards the literal argv to the native or process owner without shell interpolation (descriptions in `executors.json`); `repo:noop` becomes `nx:noop`.
- **Translation.** `--skip-cache` becomes `--skip-nx-cache`, `--exclude-dependencies` becomes `--excludeTaskDependencies`, `--output` becomes `--output-style`, `--bail` becomes `--nx-bail`, `--dry-run` and a bare `--graph` (or `--graph=true`) become `--graph=stdout`, `--graph=<file>` is kept. `exec` runs the command in a Bun wrapper that copies the names Nx's own `exec` exports (`NX_PROJECT_NAME`, `NX_PROJECT_ROOT_PATH`) to the neutral `SEMIO_PROJECT_NAME` and `SEMIO_PROJECT_ROOT`; the Nx names exist only in this implementation. `affected` without a selector adds `--base=HEAD`, `--uncommitted --untracked` becomes `--base=HEAD`, `--all` becomes `run-many`. `exec --dry-run` prints the neutral `repo-exec` plan and runs nothing.
- **Boundary.** Production code outside `⚡️caching/🚀️bootstrap` never loads an Nx module. It goes through the typed port `⚡️caching/🚀️bootstrap/🛠️tools/🔌️sdk`, whose closed catalogue names the 13 Nx modules the repository may touch. A test scans every production file under `🦑️repo/🔨️modules` with an own tokenizer and the TypeScript compiler as an independent oracle and requires zero offenders.
- **Cache location.** Nx task results live in `.🧬semio/🦑️repo/⚡️cache/rust/fixed/m/nx/artifacts` (`cacheDirectory` in `nx.json`; the rust partition, 16 GiB, which also holds the shared Cargo target and build directories of `.cargo/config.toml`). The separate partition `n` (`.cache/b/n`, 1.5 GiB) is the Nx pool: it holds the Nx graph cache as funded child images (`⚡️caching/💾️storage/🔒️enforcement/🔌️nx/📦️graph`), not the task results. `repo cache status` walks the artifact directory and prints `CacheStatus`; `cache clear` runs `nx reset --onlyCache` inside the bounded namespace and prints `CacheClear`.
- **Not yet verified.** The whole flow (a real cold run that fills `nx/artifacts`, then a warm run served from it) is scripted but has not been run at the time of writing; the unit and contract tests of the pieces above passed on 2026-10-19 (`⚡️caching/🚀️bootstrap/🛠️tools/⚙️operations`, `🔌️sdk`, `🔁️probe`, `🏗️build/🧭️selection`, `🏗️build/🧭️invocation`: 23 tests, 0 failures). On 2026-10-20 the link `.nx/installation` pointed to a tree under `.cache/b/t/m/nx` that no longer exists (only `.stage-copy-*` leftovers), so every Nx call needs `repo tools setup nx` first.

## 🏗️ Bazel implementation

`--tool=bazel` (or `SEMIO_BUILD_TOOL=bazel`) selects Bazel 8.4.2 (`.bazelversion`, pinned download per OS and CPU). The adapter is `📚️library/🏗️build/🔧️tools/🏗️bazel`. It turns the selected tasks into real Bazel actions, so Bazel's own action cache, disk cache, optional remote cache and lazy evaluation do the work.

- **Generated workspace.** For each distinct selection the adapter writes a workspace under `<products>/bazel/workspaces/<namespace>`: `MODULE.bazel`, a `BUILD.bazel` file, the rules in `tasks.bzl` (`repo_task`, `repo_launch`, `repo_noop`), a task manifest `<label>.json` and a fingerprint `<label>.input` per action, and `s`, a link to the real checkout (a junction on Windows). A task label is `t_` plus 16 hex digits of the SHA-256 of the task id.
- **Minimal builds.** Only the selected tasks and the tasks reachable through `dependsOn` become actions, and the build is `bazel build` of exactly the selected labels; pure ordering tasks (`repo:noop`) vanish behind their producers unless they are selected themselves. A target that is not needed is never analyzed or run. A selected cached `test` task without declared outputs and without selected dependents runs as a Bazel test with cached test results (see Task dispositions in the Build tools guide).
- **Declared inputs.** The `inputs` of a cacheable task (named groups, `^` expansion, globs, `!` exclusions, `externalDependencies` as `bun.lock` and `package.json`, `dependentTasksOutputFiles` as the producers' outputs) are resolved against the files of the checkout and declared as Bazel inputs: the files reach the action through shared `filegroup`s of labels `s/<path>` instead of one list per task: a directory whose files are all selected is one group `d_<hash>` (a project root is one group, single-child chains collapse), pattern units with more than two members are shared composites `k_<hash>`, and each task gets one composite `i_<hash>` (`bazelSourceCoverV1`; names are ASCII, emoji appear only in file labels). On the static graph of 1,466 projects this cut `BUILD.bazel` from 317 MB to 65 MB and workspace generation from 351 s to 37 s. `glob()` was tried and rejected: with `.bazelignore` it matches nothing, and without it follows symlink loops and git-ignored trees that Nx never hashes. `^name` and `dependencies: true` reach the transitive dependency closure, as Nx hashes them (`bazelTaskInputsV1`); a `dependsOn` that names an absent project or target is refused when the plan is built (`requireBazelDependencyV1`, "Unknown build task dependency") and `bazelDanglingDependenciesV1` lists all of them at once. Paths Bazel cannot name as labels (label-unsafe names, directories, dangling links, anything below a nested `BUILD` package) are hashed into the fingerprint instead. The fingerprint also carries the host platform and CPU, the Bun version, the build mode, declared environment values and `runtime` command outputs. The action manifest is content-stable: it names the task and the executing implementation but no workspace, runtime or snapshot path; the live data sits in `runtime.json`, outside every key.
- **Command closures.** Closure markers (`SEMIO_SOURCE_CLOSURE_<key>`, `SEMIO_CARGO_LOCK_<key>`) are expanded to the files they name before a declaration or a fingerprint is built (`📚️library/🏗️build/🔧️tools/🏗️bazel/🔗️closure`): `bazelClosureMarkersForPlanV1` collects the markers a plan can reach (task inputs, `^` edges and `{input, projects}` references), the manifests are fetched by content address (`managedBazelClosureFetchV1` through the graph store reader of the Nx hasher; a filesystem variant for tests), validated against a closed schema, and names that are absolute or contain `..` are refused. A marker met without loaded manifests is an error, not an empty list. Before this, no closure file reached a Bazel action key, so editing an imported module left a task cached (measured on 2026-10-20 in a scratch run: 106 of 111 modules of one script and 162 of 169 of another were undeclared). Checked with the real Bazel 8.4.2 in the test of that component (`🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️closure`, 9 tests passed on the live tree on 2026-10-20): a rule over the expanded labels executes once, stays at once after a change outside the closure and executes again after a change to an imported module. Not yet verified: the production fetch under the Bazel storage lease, and the re-measurement of the undeclared modules after the change.
- **Source link and `.bazelignore`.** The generated workspace links the checkout as `s` (`linkBazelSourcesV1`) and writes no `.bazelignore`; it removes a stale one. An earlier adapter listed the link there so that `//...` would not follow it without end, and a scratch run on 2026-10-20 showed the price: `s` was missing from the execroot symlink forest, so Bazel could not stat the declared inputs after a non-sandboxed action and skipped uploading every result (`Skipping uploading outputs because of concurrent modifications`); the disk cache stayed empty and every warm run executed again. Without the ignore, `//...` would follow the link without end, so queries name the root package with `//:all` (every task rule lives in it; 0.4 s in the scratch run). The adapter change was applied on 2026-10-20 at 11:36. Not yet verified: a production `repo --tool=bazel run` that shows the disk cache filling and a warm hit under the corrected adapter; the table below was recorded without the `.bazelignore`; the first scratch runs, with it, cached nothing.
- **Declared outputs.** Each task has exactly one declared tree-artifact output `<label>.snapshot`. A consumer receives the snapshots of its producers (the transitive closure when its input says `transitive: true`) as inputs. After the build the snapshots of the selected tasks are restored into the checkout; intermediate snapshots are restored only inside the consuming action.
- **Cache decision (fail-closed).** Each action carries `cache` and, when it is uncached, a machine-readable reason; the Starlark rule fails without one and tags the action `no-cache`. The adapter decides in this order (`bazelCacheDecisionV1`):
  1. An explicit `cache: true` against a plugin class other than `deterministic` is a conflict and throws ("Conflicting cache declaration"), unless the task is a pure ordering task.
  2. `continuous` (a service) is uncached with reason `continuous`.
  3. `--skip-cache` is uncached with reason `skipped`.
  4. A pure ordering task (`repo:noop`) is always cacheable.
  5. A class other than `deterministic` (see Cache classes) is uncached with the class name as reason: `driver-owned`, `managed-output`, `side-effecting`, `live`, `aggregate`, `diagnostic`, `unclassified`.
  6. `cache: false` in the manifest is `declared` and wins even against a `deterministic` class.
  7. No `cache: true` and no `deterministic` class is `undeclared`: the task reruns until it declares one.
  8. `cache: true` or a `deterministic` class without an `outputs` array is `unbounded`: a hit could not restore what it produced.
  9. Everything else is cacheable.

  So declare `outputs` (`[]` for pure checks) on every cacheable target. On the static graph of 2026-10-20, before the owners' fix, 809 targets in 278 projects declared `cache: true` without `outputs` and therefore ran uncached under Bazel with the reason `unbounded`; `bazelUncachedReportV1` (closed schema `UncachedReport`) groups them per owning project, and no CLI command prints that report yet. Continuous tasks become `repo_launch` actions that run with `bazel run`, are waited for by their readiness declaration and share the build's server.
- **Execution requirements.** Every task and launcher action is tagged `no-remote-exec` (the `repo_noop` marker writes a file and runs no process). Actions that carry `host_state` are also tagged `no-sandbox`; today that is every task and launcher action, only the `repo_noop` marker is sandboxable (`STARLARK_RULES` in `🏗️build/🔧️tools/🏗️bazel/📜️script.ts`; `Actions.kinds` in `🏗️build/🔧️tools/🏗️bazel/🧬️schema/🔣️.json`). The two reasons the schema records (`ActionPolicy.kinds`): a *task* action runs the task process in the real checkout, with its working directory, declared source-tree and shared-store writes, the loopback control socket and the out-of-tree runtime channel, which a sandbox would hide or block; a *launcher* action binds exact execroot output paths and obtains authority over the invocation's control socket, which a sandbox execroot would change. Consequence: results are keyed by the declared inputs and fingerprint, not by what a sandbox observed, so a missing input declaration shows up as a stale hit, not as a failure. The repository `.bazelrc` sets no `--spawn_strategy`, `--sandbox_*` or `--strategy` flag today (the test "the repository .bazelrc carries exactly the authored static cache policy and no host paths" in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🧪️tests` pins its cache lines and rejects host paths, but nothing forbids a sandbox flag), so any action that is ever declared without `host_state` runs in Bazel's default sandbox.
- **Sandbox and host paths.** Bazel 8.4.2 on macOS handles non-ASCII paths of its own state incorrectly, in two places found by experiment: an emoji or accented `--install_base` crashes the server at startup ("Could not find or load main class"), and the `darwin-sandbox` profile is written from Bazel's byte-wise path strings but encodes each byte as UTF-8 a second time, so the write rules for a non-ASCII `--output_base` never match and every sandboxed action (including its `stats.out`) fails with "Operation not permitted". It looks location dependent only because `/private/tmp`, `/private/var/tmp`, `TMPDIR` and `~/Library/Caches` are allow-listed for any spelling. The production layout keeps the `install` base, the `outputs` root and the `server` output bases (`<products>/bazel/outputs/server/<hash>`) inside the native partitions below `.cache/b`, which is ASCII whenever the checkout path is ASCII (for example `/Users/<name>/Documents/semio`), and `requireBazelHostPathsV1` (called by `bazelCacheLayoutV1` in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🟦️.ts`, which every Bazel storage user builds) refuses a layout whose `install`, `outputs` or `server` path contains a non-ASCII character on darwin ("ASCII Bazel host path required on darwin: outputs"), at layout time instead of during a build. So keep the checkout path ASCII on macOS. `--sandbox_base` is not used. A sandboxed action can only write inside its execroot, the temp directories and `~/Library/{Caches,Logs,Developer}`; if a task that writes into the checkout or a partition is ever sandboxed it needs `--sandbox_writable_path=<ASCII path>`, which goes through the same encoder and so must be ASCII too. Linux was examined on 2026-10-20 (Bazel 8.4.2 linux/arm64 in an unprivileged container): a non-ASCII `--install_base` crashes the server there too ("Could not find or load main class", exit code 37) under every locale tried (unset, POSIX, C, C.UTF-8, en_US.UTF-8), so `requireBazelHostPathsV1` refuses a non-ASCII `install` path on Linux ("ASCII Bazel host path required on linux: install", `HostPaths.platforms.linux.guarded`), whereas a non-ASCII output base builds and caches on Linux and is not refused. Windows is covered by the readiness refusal for non-ASCII workspace and partition paths.
- **Emoji source labels.** Task sources are labelled `s/<path>` (`bazelSourceLabelV1`): the file reached through the `s` link, a target name inside the root package. Observed with the pinned 8.4.2 (the real-binary test in `🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️actions` replays the fixture names and is skipped without `SEMIO_TEST_BAZEL_BINARY`): Bazel accepts any non-ASCII character in a target name, including astral emoji, ZWJ sequences, skin tones, combining marks, CJK and a no-break space, also as action input and output names; only a backslash and control characters are rejected. Only package names must be ASCII, so the adapter never needs an emoji package; it treats a directory that holds `BUILD` or `BUILD.bazel` as a package boundary whatever its spelling and hashes everything below it (`bazelSourceClassesV1`). The adapter admits a path as a label when it matches `^(?:[A-Za-z0-9_@=,+~%./\-]|[^\u0000-\u007f])+$` (code point based, so it holds in Python, Rust and Go too) and hashes everything else (space, backslash, control characters, directories, dangling links, anything below a directory that holds `BUILD`) into the fingerprint instead. In a scratch experiment the Bazel disk cache and the cache keys were identical across `LANG=C` and a UTF-8 locale (no test covers it); the adapter sets a UTF-8 locale on darwin only (`LANG` and `LC_ALL` `en_US.UTF-8`, the `environment` of the darwin row of `PlatformRules`). On Linux arm64 the same emoji source, output and tree-artifact names built under every locale tried (unset, POSIX, C, C.UTF-8, en_US.UTF-8), so Linux needs no locale variable; Windows is `unverified` in the profile.
- **Disk cache.** `<products>/bazel/actions`, with garbage collection (`--experimental_disk_cache_gc_max_size` set to 40 percent of the products partition budget, aligned to MiB; `.bazelrc` adds `--experimental_disk_cache_gc_idle_delay=10s` and `--experimental_disk_cache_gc_max_age=30d`). Collection only runs inside a persistent server that has been idle (measured with Bazel 8.4.2: under `--batch` it never ran), so the adapter does not use `--batch` for builds. The repository contents cache keeps entries 3 days (`--repo_contents_cache_gc_max_age`). The module catalog and repository cache live in `<dependencies>/bazel/modules`; builds run with `--repository_disable_download`, so they never fetch modules.
- **Shared output base.** `--output_base` is `<products>/bazel/outputs/server/<first 16 hex of sha256(workspace directory)>`: one server per generated workspace directory (Bazel restarts a server that is moved between workspace directories), shared by the build and every `bazel run` of continuous tasks of that selection. The server idles out after 120 seconds. The disk cache is shared by all selections, which is what makes a second selection reuse the first one's results.
- **Remote cache.** Rendered from the tool-neutral remote cache contract (section "Remote cache"): `--remote_cache`, `--remote_instance_name`, `--[no]remote_upload_local_results`, `--[no]remote_cache_compression`, `--remote_download_outputs`, `--remote_timeout` and `--remote_retries`, and nothing while no endpoint is configured. `--skip-remote-cache` drops it for one invocation; `--skip-cache` adds `--noremote_accept_cached`. The adapter restores task snapshots from `bazel-bin`, so `minimal` downloads are refused. The access token never appears in a flag: a credential helper in the products `tmp` folder holds only the variable name and the token travels in the environment of the Bazel client (`--remote_header` would copy it into Bazel's `java.log` and build event stream).
- **Cache operations.** `repo --tool=bazel cache status` counts the files of the `ac` and `cas` folders of the disk cache and adds the recorded build activity (builds, actions, executed, cache hits), which each build appends to `<products>/bazel/outputs/server/metrics.json` from its build event stream. `cache clear` stops the persistent servers (by removing their pid file), removes their output bases (Bazel's local action cache) and empties the disk cache, so the next build is a miss; the Bazel binary, modules and toolchains stay.
- **Storage.** Bazel needs the tools, dependencies and products partitions (`bazel/bin` and `bazel/install` in tools, `bazel/modules` in dependencies, `bazel/workspaces`, `bazel/outputs`, `bazel/actions` in products). `repo --tool=bazel reset` invalidates the graph and empties `bazel/actions`, `bazel/outputs` (which holds the server output bases and the activity ledger) and `bazel/workspaces`; it does not stop a running Bazel server first, so run it when no build is active (`cache clear` stops them).
- **Platform profile.** Every platform-dependent decision of the adapter is one pure function of observed host facts, `bazelPlatformProfileV1` in `🏗️build/🔧️tools/🏗️bazel/🌐️platform` (rules and limits in `PlatformRules` of the Bazel schema; fixture `🧪️tests/📥️platform/🔣️.json`, 19 rows for darwin, linux, the devcontainer and win32 on x64 and arm64, including the refusals). Per platform it renders: the extra startup and command flags (`--nobuild_runfile_links` everywhere, because nothing runs `bazel run` and a runfiles symlink forest would need a symlink privilege on Windows; `--noenable_runfiles` and the startup option `--nowindows_enable_symlinks` on Windows, so the source link `s` is a junction and no developer mode or elevation is needed), the locale environment (`LANG`/`LC_ALL` `en_US.UTF-8` on darwin only), the launcher extension (`.exe` on Windows), the kind of the source link (`junction` on Windows) and the path budget `len(output base) + len(\execroot\_main\s\) + 256` in UTF-16 units against 259 (MAX_PATH) or, with `LongPathsEnabled`, 32766; a budget that does not fit, a Bun path that is not absolute (and `.exe` on Windows) and a devcontainer flag on a non-Linux host are refusals, thrown before Bazel starts. `--output_user_root` is gone: `--output_base` and `--install_base` are always explicit, so it was dead weight and (Windows) a second long path. Every action runs the Bun executable directly (`ctx.actions.run`, `executable = ctx.attr.bun`), never a shell, `genrule` or `run_shell`; the BUILD quotes the Bun path with `JSON.stringify`, which a real Bazel parses for a Windows path with backslashes. Evidence of 2026-10-20 (Bazel 8.4.2): macOS arm64 and Linux arm64 (container built from `.devcontainer/Dockerfile`, user `vscode`, no capability, `.cache` on a Docker ext4 volume): `SEMIO_TEST_BAZEL_BINARY` run of the new suite passed on both (Bazel's own `help` lists every rendered flag name, a BUILD with a Windows Bun path parses, a build of an emoji source through the `s` link with the rendered flags is served from the disk cache after `clean`: `disk cache hit`); the pinned linux/arm64 binary was downloaded and matched its pin; `bun repo --help`, `bun repo preflight` and `bun repo tools setup bazel` (47 s: binary, 156 module blobs, readiness line) ran unprivileged on Linux. ## 🌐️ Remote cache

One schema-first contract (`🏗️build/🏃️execution/🧬️schema/🌐️remote-cache.json`, authored defaults in `🏗️build/🔣️policy.json`), two renderings and one server. The remote cache is off until an endpoint is set. The contract holds no secret.

| Variable | Contract field | Default |
|---|---|---|
| `SEMIO_REMOTE_CACHE_ENDPOINT` | `endpoint`: `http://` or `https://` origin | none (off) |
| `SEMIO_REMOTE_CACHE_INSTANCE` | `instance`: namespace, the first URL path segment | `main` |
| `SEMIO_REMOTE_CACHE_ACCESS` | `access`: `read-only` or `read-write` | `read-only` |
| `SEMIO_REMOTE_CACHE_UPLOAD` | `upload`: push local results (only effective with `read-write`) | `true` |
| `SEMIO_REMOTE_CACHE_COMPRESSION` | `compression` | `true` |
| `SEMIO_REMOTE_CACHE_DOWNLOAD` | `download`: `toplevel` or `all` | `toplevel` |
| `SEMIO_REMOTE_CACHE_TIMEOUT_SECONDS`, `SEMIO_REMOTE_CACHE_RETRIES` | `timeoutSeconds` (1-600), `retries` (0-10) | `30`, `3` |
| `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT` | `auth.tokenEnvironment`: name of the variable that holds the bearer token | `SEMIO_REMOTE_CACHE_TOKEN` |

- **Bazel** renders every field into the flags above and passes the token through a credential helper scoped to the cache host. **Nx** renders `endpoint/instance` into `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` and the token into `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`; Nx 23 has no switch for compression, download mode, timeouts, retries or withholding uploads, so read-only is enforced by a read-only token on the server. `bun repo cache remote status [--tool=nx|bazel]` prints the resolved contract, the rendering with its unsupported fields and a read-only probe of the route the tool uses.
- **Server.** `bun repo cache serve [--port <n>] [--host <address>] [--directory <path>] [--max-bytes <n>]` speaks Bazel's HTTP cache protocol (`GET`, `HEAD`, `PUT` on `/ac/<sha256>` and `/cas/<sha256>`, blobs verified against their digest, 400 on a mismatch) and the Nx self-hosted cache API (`GET`, `PUT` on `/v1/cache/<hash>`, 409 on overwrite, 401 with `text/plain`, 403 for a read token that writes), each under an optional `/<instance>` prefix. `/healthz` and `/status` are plain JSON. Bearer tokens come from `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` and `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; without a token it refuses to listen beyond loopback. The store (`.cache/remote-cache`, 4 GiB, 512 MiB per entry, 30 days idle by default) writes atomically, reserves bytes before streaming, evicts least recently used entries and publishes progress while it scans; cancelling the command stops the server. The dashboard tool `build-cache-serve` starts it on port 6090.
- **Tests.** `🏗️build/🌐️remote-cache/🧪️tests` replays the JSON fixtures (contract, renderings, wire scenarios, eviction) against Ajv, Python's `re` and `http.client` and `hashlib`; with `SEMIO_TEST_BAZEL_BINARY` a real Bazel builds against the server and hits the remote cache after `bazel clean`, and with `SEMIO_TEST_NX_BIN` (a pristine nx 23 install; the repository's patched Nx refuses to run in a scratch workspace) a real Nx does the same.

## 🎛️ Command registry

The command registry is the developer command surface: every executable command is declared once beside its source and selected by developers in the dashboard (`repo dashboard`, **New Task**); agents and automation use the tool-neutral `repo` binary and never the dashboard; no IDE launch, task or solution file registers commands (no editor configuration directory exists in the tree). `AGENTS.md` calls the human surface `repo dashboard`; in this tree it starts with `repo dashboard`, the root package script for `repo run @semio-tech/repo-dashboard-rs:run --output=stream` (`dashboard:install` rebuilds it). `dashboard` is not an operation of the catalogue (`📚️library/🏗️build/⚙️operations/🔣️catalog.json`): the build entry maps a `run` of the targets `run`, `daemon` and `preferences` of the project `@semio-tech/repo-dashboard-rs` (`dashboardInvocation` in `📚️library/⚡️caching/🚀️bootstrap/🎛️dashboard/📦️installation`; `--output=stream` and `--skip-cache` are dropped) to the arguments of the installed native client, which `launchDashboard` starts under the caller's compiler admission control, and runs every other target, and any call with `--graph`, `--batch`, `--parallel` or `--exclude-dependencies`, through the selected tool. Builds, tests and checks by agents and automation go through `repo …`; an agent never starts the dashboard. The registry is data: the root `📋️project.json` holds `metadata.semio.dashboard` with `parameters`, `tools`, `compounds` and `groups`, validated against the schema `🔨️modules/🎛️dashboard/🧬️schema/🎮️registry/🔣️.json` (`ProjectManifest`); other projects declare typed controls on their targets, playground controls come from crate manifests. ## 🪜️ Script entries

Commands that the build graph runs as `repo:script` start at the `📜️script.ts` of their module. The command-router law (`📚️library/🔍️discovery/🛣️ecma-command-routes`) accepts two shapes:

- **Router.** A class per command that extends `BundleScript`, a `ScriptRouter` that registers them and one terminal under `import.meta.main`. A thin entry keeps the process birth in the router and passes its own arguments on: `await receiveScriptProcessInvocation(process.env, original => runScriptMain(router, { invocation: original, argv: ["run"] }))`. The program parses its own `process.argv`; `argv` only names the registered command (`📚️library/⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/📜️script.ts`). The other accepted terminal is `router.run(process.argv.slice(2))` for routers that dispatch on the command line.
- **Bare entry.** `import { runScriptProgram } from "./🟦️.ts"; if (import.meta.main) await runScriptProgram();`, that is exactly one argument-free call of `runScriptProgram`, imported from a sibling `🟦️.ts`, under `import.meta.main` (`ecmaRouteOwnedProgram`). It is for programs that own their process birth and their exit code, in particular the child programs of tests under `🧪️tests` and `👷️child` (for example `📚️library/⚡️caching/🦀️cargo/📦️units/📥️descriptor/💾️cache/🧪️tests/📦️child/📜️script.ts`).

A router around everything does not work: a program that opens its own birth with `receiveScriptProcessInvocation` inside the router's birth cannot report after draining, and `track` in `🧰️framework/🔨️modules/🏃️process/🧭️routing/📥️invocation/🏃️process` copies every failing tracked operation into all ancestor scopes and closes their admission, so a failure that the program catches and reports still fails the outer birth (the lift repair measured exit 1 with the `custodian/cancel` child). A nested birth can never swallow a failure, so the program must be the outermost owner. The router-lift generators therefore emit the bare entry for scripts under `🧪️tests` and `👷️child` and the router with argument pass-through for all others (98 lifted scripts repaired on 2026-10-20: 74 router, 24 bare). Not yet verified: the lifted child suites under `repo run`; the `scope` suite still had four reds, the first from a `root-drain` admission that is identical with the pre-lift form.

## 🧾️ Build owner registry

`📋️build-owners.json` at the repository root lists every module that owns a build manifest (`owners`) and the catalog providers. A law keeps it equal to the tree: `bun ./📜️script.ts verify build-owners` (root targets `workspace:verify-build-owners`, cached with `outputs: []`, and bare `verify`/`workspace:verify`) fails with one finding per mismatch, for example `project-without-row`, `cargo-without-row`, `missing-manifest`, `name-mismatch`, `cargo-row-shadows-project`, `missing-native-root` or `package-stale` (`📚️library/🏗️build/🧬️schema/🧾️owner-consistency.json` lists all kinds); `verify build-owners sync` (target `workspace:verify-build-owners-sync`, uncached) repairs what is mechanical (drops rows of vanished modules (only when no manifest exists and git tracks nothing at the path; the manifests under the row's `nativeRoots` are registered again as rows of their own), relocates a moved module, renames a renamed project, hands a Cargo row over to a `📋️project.json`, adds rows for new manifests in byte order) and then fails on what remains: findings that need an author (catalog providers) and rows whose paths git still tracks while the files are absent (a concurrent move in progress). Rows whose manifest sits under a git-ignored path are exempt, so a fresh clone does not fire the law. The scaffolding writers (crate carve, subset scaffold, mutation tree) call the same reconciler with a scope. An applied move plan reconciles the registry for the subtrees it touched (`reconcileBuildOwnerRegistry` in `📚️library/🧹️normalization/🎮️command-contract/🔁️workflow/🟦️.ts`); any other directory move or rename is caught by the law and fixed by `verify build-owners sync`. The core and its fixture cases live in `📚️library/🏗️build/🕸️graph/🧾️registry-consistency`; the registry file holds one row per module that owns a manifest (3,729 rows counted on 2026-10-20), and `bun ./📜️script.ts verify build-owners` printed `passed` on 2026-10-19. On 2026-10-20 the 28 tests of `registry-consistency` passed; the route itself could not load that day for the same reason as `verify zero-touch` (see Dependencies).

The tools that run before the dependencies are installed (`repo` help, preflight, `tools setup`, `dependencies lock` and `sync`, the native dependency installers, the wasm tools, the Bazel bootstrap, and the root script's router, `setup` and entrypoint routes) must run on a checkout without `node_modules`. A law keeps their import closures relative: `bun ./📜️script.ts verify zero-touch` (root target `workspace:verify-zero-touch`, cached, and bare `verify`/`workspace:verify`) walks the closures listed in `🏗️build/📥️source/🛗️zero-touch/🗂️closures/🔣️.json` and fails for a bare workspace specifier (`workspace-specifier`), any other external package such as `typescript` (`external-package`), a closure entry or seam that is gone (`missing-entry`) and a static import of a post-install seam (`seam-static`, for example the graph inference that reads sources through the TypeScript compiler; seams may only be loaded dynamically). The roster has nine closures: `repo-cli`, `dependencies-js`, `dependencies-native`, `wasm-tools`, `bazel-bootstrap`, `build-bootstrap`, `root-router` (static imports only), `root-setup` and `root-entrypoints`, and two seams: the graph inference (`🏗️build/🕸️graph/📥️inference/🟨️.mjs`, which reads sources through the TypeScript compiler and the TOML parser of the installed workspace) and the Nx graph consumer path. Imports are found with the system compiler (`Bun.Transpiler`), not a regular expression; the check against the repository is a static counterpart of the capture refusal `External implementation runtime dependency refused: <specifier>`. Verified: the 22 tests (13 closure cases including conditional and wildcard package exports, type-only imports, cycles and emoji paths; Ajv validates fixture and roster; the TypeScript compiler AST agrees with the scan on about 900 real closure files) passed on 2026-10-19 and again on 2026-10-20, and `verify zero-touch` printed `passed.` on 2026-10-19 (on 2026-10-20 the route could not load until the pending lock and sync installs a new workspace package, see Dependencies). Not yet verified: `repo --help` on a checkout with `node_modules` hidden. The remaining lazy root routes (verify lanes, dev, lint, …) run after the install and are covered by the layering law, not by this one.

## 💾️ Cache partitions

All build state lives in fixed-capacity partitions below `.cache/b/<partition>` (git-ignored and derived, retired only through their owning controls). On macOS each partition is a UDIF disk image formatted as case-sensitive APFS, `fixed.dmg`, mounted at `m` next to its `image.json` receipt (`ImageProtocol` fixes `UDIF` and `Case-sensitive APFS`; HFS+ was ruled out earlier because it lacks the atomic exchange `RENAME_SWAP` that publication and binding use, not re-checked here). Linux uses a directory-backed partition without any privilege (`fixed.dir`, `v`, `m`, switched by an atomic `renameat2(RENAME_EXCHANGE)`) and Windows a directory partition too, swapped by a journaled two-phase write-through rename instead of `renameat2` (implemented from source, not verified on those hosts; a swap fails with "A handle is still open inside the partition" while any process holds a file in it). Recovery follows the owning provider’s platform protocol; use the dashboard recovery controls below. Capacities come from `📚️library/⚡️caching/💾️storage/🔒️enforcement/📦️budget/🔣️policy.json`.

| Partition | Content | Capacity |
|---|---|---|
| `d` | dependencies, including `node_modules` generations | 8 GiB |
| `t` | tools: rustup, Bazel, Nx | 8 GiB |
| `g` | neutral build graph and inference records | 4 GiB |
| `o` | observations and diagnostics | 2 GiB |
| `p` | products: build outputs and published artifacts | 24 GiB |
| `l` | leases and locks | 64 MiB |
| `n` | Nx cache pool, namespaces are funded child images | 1.5 GiB |

`.cache/b/c` is the plain control directory (no image, at most 1 MiB; it holds the lease database of the images, `budget.controlDirectory`). The Rust target and build directories are a separate fixed partition at `.🧬semio/🦑️repo/⚡️cache/rust/fixed` (16 GiB). `bun ./📜️script.ts clean` never touches any of them, nor the `🗑️generated` folder of an open ticket.

**macOS volume silence.** macOS logs file system events of every mounted volume to `.fseventsd` and indexes it; on an image that only a build tool writes this fills the 63 MiB leases image and the small partitions. Each image therefore carries `.fseventsd/no_log` and `.metadata_never_index` (protocol constants in `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage/🍎️image/🤫️silence/🧬️schema/🔣️.json`). A write after mount does not work: with `-owners on` macOS creates `.fseventsd` as `root:staff 0700` with an ACL, and a log keeps growing until the volume is detached and attached again. So the images are created from a seed folder (`hdiutil create -format UDRW -srcfolder <seed> -size … -nospotlight` yields the same fixed image as `-type UDIF`, with the markers user-owned from the start), and `applyNativeImageVolumeSilenceV1` runs on attach and again whenever an already mounted image is opened: it creates the directory and the markers if they are missing and prunes logs (regular single-link files named by 16 hexadecimal digits, in batches of 64): every log on attach, and on open once more than 8 files or 1 MiB remain. A root-owned or symlinked `.fseventsd` and non-regular markers are refused with a remedy. A silenced volume has no FSEvents service, so the publication witness treats it as a volume without a service domain (`observeNativeVolumeEventServiceV1` returns `null`). Capacity: APFS holds 40,960 bytes less than the image, and 200 MiB less when the image is larger than 2 GiB (measured on 15 images from 32 MiB to 4,095 MiB), so every partition exposes `usableBytes` and for partitions up to 256 MiB the logical limit must fit it; that is why `leases.maximumLogicalBytes` is 62,914,560 of 67,108,864. Observed on 2026-10-20: the live images were mounted before their markers existed and macOS keeps logging until each partition is detached and attached again; after the open-time repair `.fseventsd` of `d`, `l` and `g` held 3, 5 and 1 entries (the dependencies image had held about 200 logs before), and every partition has `.metadata_never_index`. Not yet verified: a freshly created seeded image through the whole `tools setup` path, and the seeded creation on another macOS version.

### 🩹️ Recovery

Use the dashboard task that owns the failing operation. Its output preserves the exact refusal, progress and cancellation; retry or stop that task without terminating unrelated developers’ work. Publication and directory-swap recovery run through their owning operation. Receipts and intent files are observations of that protocol, not files to move aside or edit.

For an inactive macOS Nx cache with an unsupported publication, **New Task → Reset Inactive Nx Cache** selects the fixed recovery owner. It checks the canonical Nx capsule, actual physical exclusion, kernel associations and complete descriptor observations before removing the exact inactive contents. Mounted, busy, foreign, replaced or incompletely observed contents refuse. A durable current reset intent lets an interrupted reset resume. The next operation recreates the cache. This control does not detach images or reset arbitrary partitions and is unavailable for Linux and Windows directory partitions.

For compiler-storage pressure, preview and retire through the dashboard’s declared maintenance controls. Reported logical deletion bytes and freshly observed physical headroom are separate results. Dependency sync retries a recognized Bun cache-link refusal once through its own owned purge; an unresolved refusal remains attached to the task. Unsupported filesystem, permission, unknown publication and foreign-reader errors require correction in the owning provider. Cache recovery never requires manually detaching an image, forcing an unmount, changing receipts or deleting cache directories.

### Build-Werkzeuge im Alltag

Dieser Leitfaden ist die Arbeitssicht auf das werkzeugneutrale Build-System: welches Werkzeug du wählst, was jede Operation tut, wie Ergebnisse gecacht und geteilt werden, wie Arbeit auf Worker und Executor verteilt wird und wie du ein neues Target einordnest. Die Referenzabschnitte danach (Neutrales Modell bis Remote-Cache) enthalten die Verträge, die Messungen und die offenen Punkte. Jeder Befehl unten ist eine Operation des Katalogs `📚️library/🏗️build/⚙️operations/🔣️catalog.json`; `repo <command> --help --lang=en|de` gibt dieselbe Verwendung auf Englisch oder Deutsch aus. Wo `repo` nicht im `PATH` liegt, schreibe `bun repo`, das Skript des Wurzel-Pakets. Die englische Fassung steht im Kapitel „Build tools guide“.

#### Werkzeug wählen

- **Wählen.** `--tool=nx|bazel` gewinnt, dann die Umgebungsvariable `SEMIO_BUILD_TOOL`, dann der Standard der Richtlinie `nx`. Die Wahl wird als `SEMIO_BUILD_TOOL` an jede verschachtelte Task weitergegeben; eine Task, die `repo` erneut aufruft, bleibt also bei deinem Werkzeug. Die Dashboard-Achse `build-tool` setzt dieselbe Variable. Alles andere wird abgelehnt („Unknown build tool“).
- **Einrichten.** `repo tools setup all` installiert das gepinnte Nx und Bazel für diesen Rechner; `repo tools setup nx` oder `repo tools setup bazel` installiert eines davon. `workspace:setup` führt denselben Schritt aus.
- **Ein Graph.** Beide Werkzeuge führen denselben neutralen Graphen mit denselben Task-IDs aus (`<project>:<target>[:<configuration>]`). Eine Auswahl, die unter beiden Werkzeugen zu verschiedenen Tasks führt, ist ein Fehler und kein Merkmal.

| | Nx (Standard) | Bazel (`--tool=bazel`) |
|---|---|---|
| Was läuft | ein `nx run` je Auswahl | ein erzeugter Workspace je Auswahl; eine Task ist eine Bazel-Action, eine gewählte gecachte `test`-Task ein Bazel-Test, ein Dienst ein `bazel run`-Target |
| Lokaler Cache | Task-Ergebnisse in `nx/artifacts` der Rust-Partition | Action-Cache des Output-Base plus Disk-Cache `bazel/actions` der Produkte-Partition |
| Remote-Cache | selbst gehostete Nx-Cache-API | Bazel-HTTP-Cache-Protokoll, Token über einen Credential-Helper |
| Remote-Ausführung | nein | wählbar für Targets, die `metadata.semio.hermetic` deklarieren |
| Nebenläufigkeit | `NX_PARALLEL` | persistente Worker und `--jobs` |
| Wiederverwendung zwischen Auswahlen | über den Task-Hash im Task-Cache | über den Action-Schlüssel im Disk-Cache: Eine zweite Auswahl nutzt die Ergebnisse der ersten |

Nimm Nx für den Standardablauf. Wähle Bazel, wenn du Ergebnisse über Auswahlen und Rechner hinweg teilen, Worker oder Remote-Ausführung nutzen willst. Beide werden mit denselben Flags gesteuert; wo ein Werkzeug eine Einstellung nicht einhalten kann, listet `repo cache remote status` sie als `unsupported` (siehe Remote-Cache für die Nx-Felder).

#### Die neutralen Operationen

| Operation | Was sie tut | Beispiel |
|---|---|---|
| `run` | eine Task und die Tasks, von denen sie abhängt | `repo run @semio-tech/semio-tech-play:serve --tool=bazel` |
| `run-many` | dieselben Targets in mehreren Projekten (`--projects`, `--exclude`, Muster `tag:`, `name:`, `directory:`, `!`) | `repo run-many --targets=test --projects=tag:rust --tool=bazel` |
| `affected` | Targets in den gegenüber `HEAD` geänderten Projekten (verfolgte Änderungen plus unverfolgte Dateien) und ihren Abhängigen | `repo affected --targets=build --base=main --head=HEAD` |
| `exec` | ein Befehl je Projekt, Projektwurzel als Arbeitsverzeichnis, `SEMIO_PROJECT_NAME` und `SEMIO_PROJECT_ROOT` gesetzt | `repo exec --projects=@semio-tech/repo-client -- bun test` |
| `--dry-run`, `--graph` | geben den Task-Graphen als `DryRunPlan` aus und führen nichts aus; `--graph=<file>` schreibt ihn in eine Datei | `repo run-many --targets=build,test --dry-run` |
| `show`, `graph`, `watch` | der neutrale Graph und ein Befehl, der bei Quelländerungen neu läuft | `repo show projects --json` |
| `cache status`, `cache clear` | zählen oder leeren den lokalen Task-Cache des gewählten Werkzeugs | `repo cache status --tool=bazel` |
| `cache remote status`, `cache serve` | der Remote-Cache-Vertrag und ein lokaler Cache-Server (siehe Cache-Modell) | `repo cache remote status --tool=bazel` |
| `reset` | verwirft den Graphen und setzt den lokalen Zustand des Werkzeugs zurück | `repo reset --tool=bazel` |
| `remote-execution serve`, `status`, `env` | startet, prüft oder beschreibt den optionalen lokalen Remote-Execution-Cluster (siehe Remote-Ausführung) | `repo remote-execution status` |

- **Dry-Run und Graph.** `--dry-run` und `--graph` geben für jedes Werkzeug denselben `DryRunPlan` aus und starten weder Nx noch Bazel: `roots`, `tasks` und `dependencies` (unter Bazel zusätzlich `selected` und Abhängigkeiten auf Dienste in `continuousDependencies`). Der Plan sagt, was laufen würde, nicht, was gecacht ist; dafür dient `cache status`.
- **Affected.** Die Regel ist für beide Werkzeuge gleich: das tiefste Projekt, dem eine geänderte Datei gehört, Projekte, deren Target-Inputs eine geänderte `{workspaceRoot}/…`-Datei nennen, jedes Projekt bei einer Änderung von `nx.json`, dann alle Abhängigen. Bazel beantwortet sie mit einer `rdeps`-Abfrage über ein erzeugtes Paket, gegen die eigenen Locators von Nx bei vier von fünf Änderungsmengen geprüft; eine Änderung allein an `bun.lock` ist der bekannte Unterschied (Nx behandelt sie als „alles“, die neutrale Regel und Bazel sehen nur Pfad-Zugehörigkeit). `--projects` wird bei `affected` abgelehnt; schränke mit `run-many` ein.
- **Abbruch und Fortschritt.** Jede Operation lässt sich abbrechen (Strg+C) und meldet Fortschrittszeilen beim Durchlaufen, Warten und Herunterladen; ein abgebrochener Lauf endet am nächsten Prüfpunkt.
- **Bazel im Besonderen.** Eine Auswahl baut genau den transitiven Abschluss der gewählten Tasks, nichts sonst wird analysiert. `run-many` ist ein einziger Bazel-Aufruf mit allen Labels, gemeinsame Abhängigkeiten laufen also einmal. Ist eine gewählte Task ein Test, lautet der Aufruf `bazel test` (mit `--build_tests_only` nur, wenn jedes gewählte Label ein Test ist); `--skip-cache` fügt `--nocache_test_results` hinzu.

#### Cache-Modell

Ein Ergebnis wird wiederverwendet, wenn der Schlüssel der Task unverändert ist. Jedes Werkzeug leitet seinen Schlüssel aus denselben deklarierten `inputs` ab (Dateien und benannte Gruppen, Umgebungswerte, Ausgaben von `runtime`-Befehlen, der Abschluss der Dateien, die das Befehlsskript importiert, Plattform, Bun-Version, Build-Modus) und aus der Identität des Build-Werkzeugs selbst. Folgen: Eine Datei, die die Task liest, aber nicht deklariert, macht sie nicht ungültig (ein veralteter Treffer, kein Fehler); eine Änderung an der Implementierung des Build-Werkzeugs vergibt die Schlüssel seiner Tasks einmal neu (bei Bazel ist die erfasste Implementierung ein Input jeder Action), erwarte also nach dem Holen einer solchen Änderung einen kalten Lauf; eine Task, die das ganze Repository als Input deklariert, wird bei jeder Änderung neu geschlüsselt und ist ein Problem des Eigentümers, nicht des Caches.

| Schicht | Ort | Geleert durch |
|---|---|---|
| Nx-Task-Cache | `.🧬semio/🦑️repo/⚡️cache/rust/fixed/m/nx/artifacts` (Rust-Partition) | `repo cache clear` (`nx reset --onlyCache` im begrenzten Nx-Namensraum) |
| Bazel-Action-Cache | Output-Base `bazel/outputs/server/<hash>` der Produkte-Partition, einer je erzeugtem Workspace-Verzeichnis; der Server schläft nach 120 s ein | `repo cache clear` stoppt die Server und entfernt die Output-Bases |
| Bazel-Disk-Cache | `.cache/b/p/m/bazel/actions`, abgeräumt bis auf 40 Prozent des Budgets der Produkte-Partition, Einträge über 30 Tage werden verworfen | `repo cache clear`; übersteht `bazel clean` und den Verlust eines Servers |
| Remote-Cache | ein HTTP-Endpunkt, den du konfigurierst, oder `repo cache serve` (Speicher in `.cache/remote-cache`) | die eigene Grenze und Verdrängung des Servers |

Aller Build-Zustand unter `.cache/b/<partition>` ist abgeleitet und darf gelöscht werden, wenn nichts läuft (Partitionen `d` Abhängigkeiten, `t` Werkzeuge, `g` Graph, `o` Beobachtungen, `p` Produkte, `l` Leases, `n` Nx-Pool; siehe Cache-Partitionen). `--skip-cache` ignoriert den lokalen Task-Cache des Laufs (bei Bazel nimmt es zusätzlich keine Remote-Treffer an), `--skip-remote-cache` ignoriert nur den Remote-Cache, und die Dashboard-Achse `cache` bietet `use`, `skip-local` und `skip-all`.

- **Früher Abbruch der Kette (early cutoff).** Unter Bazel führt eine Task, deren Ausgabe-Snapshot nach einer Input-Änderung byte-identisch bleibt, ihre Abhängigen nicht erneut aus (gemessen: Eine reine Leerraum-Änderung am Input eines Generators führte nur den Generator erneut aus).
- **Store-Belege.** Produkte, die in einem geleasten Store statt im Projektverzeichnis liegen, deklarieren einen Beleg als einzigen Output; beide Werkzeuge prüfen ihn nach jedem Lauf und führen genau diese eine Task ungecacht erneut aus, wenn der Beleg beschädigt ist. Siehe Store-Belege.

**Remote-Cache.** Er ist aus, bis `SEMIO_REMOTE_CACHE_ENDPOINT` einen `http://`- oder `https://`-Ursprung nennt; der Vertrag und seine Variablen stehen im Abschnitt Remote-Cache.

```bash
repo cache serve --port 6090
```

```bash
SEMIO_REMOTE_CACHE_ENDPOINT=http://127.0.0.1:6090 SEMIO_REMOTE_CACHE_ACCESS=read-write repo run @teaching/architecture-course:test --tool=bazel
repo cache remote status --tool=bazel
```

In PowerShell lautet dasselbe `$env:SEMIO_REMOTE_CACHE_ENDPOINT = "http://127.0.0.1:6090"`, `$env:SEMIO_REMOTE_CACHE_ACCESS = "read-write"`, danach `bun repo run @teaching/architecture-course:test --tool=bazel`.

- **Zugriff.** Der Standard ist `read-only`; Ergebnisse werden nur mit `SEMIO_REMOTE_CACHE_ACCESS=read-write` und einem `SEMIO_REMOTE_CACHE_UPLOAD`, das nicht `false` ist, hochgeladen. Das Token wird aus der Variablen `SEMIO_REMOTE_CACHE_TOKEN` gelesen (oder aus der Variablen, die `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT` nennt) und steht nie in einem Flag oder länger als einen Build auf der Platte: Bazel erhält es über einen Credential-Helper, Nx über seine eigene Variable. Nx kann Uploads nicht zurückhalten; für Nx bedeutet read-only daher ein Lese-Token auf dem Server.
- **`cache remote status`.** Gibt den aufgelösten Vertrag aus (`configured: false`, solange kein Endpunkt gesetzt ist), die Umsetzung für das gewählte Werkzeug mit ihren `unsupported`-Feldern, ob die Token-Variable gesetzt ist (nie ihren Wert) und eine lesende Sondierung des Endpunkts: `reachable`, `authorized` und den HTTP-Status. Es speichert nichts.
- **`cache serve`.** Stellt das HTTP-Cache-Protokoll von Bazel (`/ac/<sha256>`, `/cas/<sha256>`, Blobs gegen ihren Digest geprüft) und die selbst gehostete Cache-API von Nx (`/v1/cache/<hash>`) von diesem Rechner aus bereit, bis du ihn stoppst. Optionen: `--port` (Standard 6090, `0` wählt einen freien), `--host` (Standard `127.0.0.1`), `--directory`, `--max-bytes` (Standard 4 GiB, mindestens 1 MiB; die am längsten ungenutzten Einträge gehen zuerst). Die Tokens kommen aus `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` und `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; ohne Token weigert sich der Server, außerhalb von Loopback zu lauschen. Das Dashboard-Werkzeug `build-cache-serve` startet ihn.
- **Download-Modi.** `toplevel` (Standard) und `all`. `minimal` gehört nicht zum Vertrag, und das Schema lehnt es ab: Der Bazel-Adapter stellt den Snapshot jeder gewählten Task aus `bazel-bin` wieder her, und mit `minimal` bleibt der Snapshot im Remote-Store, die Wiederherstellung scheitert mit `ENOENT` und nichts erreicht den Checkout (gemessen). Nx holt immer alles.
- **Was geteilt wird.** Bazel-Schlüssel der heutigen Tasks enthalten den absoluten Bun-Pfad und die Checkout-Wurzel der erfassten Implementierung; ein Treffer über Rechner hinweg braucht daher denselben Benutzer und Checkout-Pfad. Hermetische Actions (nächster Abschnitt) haben hostunabhängige Schlüssel (gemessen: dieselben Inputs unter einem anderen Checkout-Pfad trafen den Disk-Cache).

#### Remote-Ausführung

Remote-Ausführung ist optional und wird je Target gewählt. Das Build-System definiert den Vertrag und die Bazel-Umsetzung; es liefert keinen Executor mit.

- **Deklarieren.** Ein Target ist nur dann eine hermetische Action, wenn sein Manifest es sagt: `"metadata": { "semio": { "hermetic": { "version": 1, "tools": ["bun"] } } }` (Schema `🏗️build/🏃️execution/🧬️schema/🔒️hermetic.json`). Es muss außerdem gecacht sein und ein deklariertes `outputs`-Array haben, schlichte `command`-Strings ausführen, nur Datei-Inputs haben (kein `runtime`- oder `env`-Input, kein `{options.…}`- oder `{env.…}`-Token), nicht continuous sein und keine weiteren Builds anstoßen. Ein Target, das nicht passt, behält Host-Zustand; der Grund ist geschlossen (`undeclared`, `unsupported-execution`, `host-inputs`, `uncached`, `continuous`, `orchestration`, `tool`). Kein Target des Repositorys deklariert es bisher, also läuft heute nichts remote.
- **Was eine hermetische Action ist.** Sie läuft mit einem gepinnten Bun, der ein deklarierter Tool-Input ist (unter einem Lease mit Fortschritt geladen, vor dem Entpacken nach Größe und SHA-256 geprüft), in einer Sandbox oder auf einem Worker, mit strenger Umgebung (`LC_ALL=C`, `TZ=UTC`, `SOURCE_DATE_EPOCH=0`, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0`), ohne Host-Pfad im Schlüssel, mit normalisierten Outputs, und sie scheitert bei einem nicht deklarierten Schreibzugriff. Hermetische Actions nutzen das gepinnte Bun, nicht das in deinem `PATH`.
- **Schalter.** Ungesetzt bleibt jede Action lokal; ein fehlerhafter Wert scheitert geschlossen.

| Variable | Bedeutung | Standard |
|---|---|---|
| `SEMIO_REMOTE_EXECUTION_ENDPOINT` | `grpc://`-, `grpcs://`- oder `unix:`-URI des Executors | keiner (lokal) |
| `SEMIO_REMOTE_EXECUTION_PLATFORM` | Worker-Plattform: `darwin`, `linux` oder `windows` plus `-arm64` oder `-x64` | `linux-x64` |
| `SEMIO_REMOTE_EXECUTION_PROPERTIES` | zusätzliche Worker-Eigenschaften, `name=value,…` (bis zu 16), zu `OSFamily` und `Arch` der Plattform hinzugefügt | keine |
| `SEMIO_REMOTE_EXECUTION_JOBS` | gleichzeitige Actions, solange der Executor an ist | 128 (höchstens 512) |

- **Routing.** Nur hermetische Actions gehen an den Executor, mit `--noremote_local_fallback`: Ein nicht erreichbarer Executor lässt den Build scheitern, die Action läuft nie lokal. Actions mit Host-Zustand bleiben lokal (`no-remote-exec`).
- **Anforderungen an den Executor.** Ein Dienst für die Remote Execution API v2 von Bazel mit Inhalts-Store, Action-Cache und Scheduler; Worker, deren Eigenschaften zur Plattform passen (Buildbarn vergleicht exakt; BuildBuddy nutzt `container-image` und `pool`); Linux-Worker brauchen nur das hochgeladene Bun, keinen Checkout. Die Ausführungs-Flags tragen nie Cache-Einstellungen: Cache-Endpunkt, Instanz, Upload, Download-Modus und Token bleiben beim Remote-Cache-Vertrag, dessen Endpunkt ein `http(s)`-Ursprung ist. Bazel auf einen einzigen gRPC-Dienst für Cache und Ausführung zu richten, definiert der Vertrag noch nicht.
- **Plattformen.** Die Netzwerkisolation einer hermetischen Action wird unter Linux und auf Remote-Workern durchgesetzt; die Sandbox von macOS kann sie nicht sperren (mit Bazel 8.4.2 gemessen). Unter Windows gibt es keine Sandbox, der Runner lehnt dort eine hermetische Action also ab (der Source-Link ist eine Junction); führe hermetische Windows-Targets remote aus.
- **Optionaler lokaler Cluster.** `repo remote-execution serve` betreibt einen lokalen Buildbarn-Cluster (Speicher mit Inhalts-Store und Action-Cache, Frontend, Scheduler, Worker, Runner) in Containern, bis du ihn stoppst, und entfernt danach Container und Volumes. Er braucht eine laufende Container-Laufzeit mit dem Compose-Plugin; jedes Image ist ein offizielles und per Digest gepinnt. Das Frontend antwortet auf `127.0.0.1:8980`, seine Gesundheitsroute auf `8981` (`--port` und `--diagnostics-port` verschieben sie); der Cluster hat keine Authentifizierung und lauscht nur auf Loopback. `--platform=<id>` wählt die Worker-Plattform (Standard: die zur CPU dieses Rechners passende, `linux-arm64` oder `linux-x64`). `repo remote-execution status` zeigt Laufzeit, Container und ob das Frontend antwortet, und `repo remote-execution env --platform=linux-x64` gibt die Variablen aus, die ein Client setzt, je Zeile `NAME=Wert`. Der Runner hat kein Netzwerk, eine hermetische Action dort erhält also einen echten Netzwerk-Namensraum ohne Netzwerk. Es ist ein Entwicklerdienst, nie eine Abhängigkeit: Ist `SEMIO_REMOTE_EXECUTION_ENDPOINT` ungesetzt, bleibt jede Action lokal.

#### Worker-Pools

Persistente Worker halten einen Prozess zwischen Actions am Leben, sodass eine Action nicht jedes Mal das Starten und Laden des Build-Werkzeugs bezahlt.

- **Schalter.** `--workers on|off`, dann `SEMIO_BUILD_WORKERS`, dann die Worker-Richtlinie in `📚️library/🏗️build/🔣️policy.json` (`enabled`, standardmäßig an). `--parallel <n>` oder `SEMIO_BUILD_PARALLEL` setzt die Zahl gleichzeitiger Tasks (Standard: die Zahl der Kerne, höchstens 8).
- **Arten.** Die Art ergibt sich aus Target-Name und Dauerbetrieb, nie aus dem Werkzeug; die erste passende Regel gewinnt.

| Art | Target-Namen | Höchstzahl Instanzen |
|---|---|---|
| `service` | `continuous: true` | keine (nie ein Worker) |
| `test` | `test`, `smoke`, `mutation`, `bench`, `e2e` (auch `<name>-…`) | 8 |
| `check` | `check`, `lint`, `verify`, `typecheck`, `format-check`, `contract`, `schema`, `stdio` (auch `<name>-…`) und Namen mit Endung `-check` | 8 |
| `generate` | Namen mit `generate` oder `generator` | 4 |
| `build` | `build`, `prepare`, `activate`, `wasm`, `native`, `package`, `bundle`, `cpp`, `publish`, `canonical`, `preview`, `setup`, `deps` (auch `<name>-…`) | 2 |
| `script` | alles andere | 4 |

- **Budget.** Alle Pools zusammen dürfen 30 Prozent des Hauptspeichers des Rechners belegen, 512 MB je Worker. Jede Art erhält zuerst eine Instanz (test, check, generate, build, script, soweit der Speicher reicht), die übrigen Instanzen gehen in derselben Reihenfolge an die Arten bis zu ihrer Grenze und der Jobzahl; eine Art, der keine bleibt, läuft ohne Worker.
- **Bazel.** Die Worker sprechen das JSON-Worker-Protokoll von Bazel, führen den Action-Rumpf im Worker-Prozess aus (Blattbefehle bleiben eigene Prozessbäume), unterstützen Abbruch und verkleinern den Pool unter Speicherdruck. Worker- und Nicht-Worker-Actions haben denselben Action-Schlüssel, Caches werden also über beide Modi geteilt. Actions, die nie Worker nutzen: Dienste, hermetische Actions und als `bazel test` laufende Tests. Cargo-Tasks laufen nacheinander.
- **Nx.** Nx startet je Task einen Prozess, abgebildet wird daher nur `NX_PARALLEL` (auf die Jobzahl); `NX_BATCH_MODE` wird nur für einen Executor gesetzt, der eine Batch-Implementierung registriert, was keiner tut. Jede andere Worker-Einstellung (Pools, Instanzgrenzen, Speicher, Sandbox) wird unter Nx nicht unterstützt.
- **Gemessen.** Die CPU-Zeit je Action sank im eingeschwungenen Zustand von 2,50 s auf 1,46 s; die Wanduhrzeit war auf einem ausgelasteten Rechner nicht durchgehend besser, weil 85 Prozent einer warmen Anfrage im Worker das Öffnen des Graph-Cache-Stores sind.
- **Ausschalten** mit `--workers off`, um gegen einen Prozess je Action zu vergleichen, eine einzelne Task zu debuggen oder wenn Speicher knapp ist.

#### Task-Dispositionen

Jede Task hat eine Werkzeugfamilie (`bun-script`, `tsc`, `vitest`, `bun-test`, `vite`, `playwright`, `go`, `python`, `dotnet`, `latex`, `wasm`, `cargo`, `docker`, `aggregate`) und eine Disposition. Nx führt alle als `nx run` aus; Bazel bildet sie so ab (`📚️library/🏗️build/🏃️execution/🧬️schema/🎯️coverage.json`).

| Disposition | Bedeutung | Unter Bazel |
|---|---|---|
| `action` | gecacht, aus dem Action-Cache wiedergegeben | gecachte Build-Action, Output-Snapshot wird in den Checkout zurückgespielt |
| `test` | gecacht und `test` oder `test-…` benannt, `outputs: []`, keine andere gewählte Task verbraucht sie, höchstens 10.000 deklarierte Dateien | `bazel test`: das bestandene Ergebnis wird gecacht, beim nächsten Lauf `(cached) PASSED`; nicht verwendet, wo die Plattform keine Runfiles hat (Windows) |
| `interactive` | `continuous`, läuft bis zum Stopp | `bazel run`-Target; es startet bei jedem Lauf und wird nie erzeugt |
| `uncached` | läuft immer; der festgehaltene Grund sagt warum | Action mit Tag `no-cache` |
| `refused` | `cache` oder `outputs` nicht deklariert (Gründe `undeclared`, `unbounded`) | fail-closed, bis der Eigentümer deklariert, was fehlt |

Statische Zählung vom 2026-10-20 (8.028 Tasks des rekonstruierten Graphen, mit den angewendeten Klassifikationsmengen): 3.771 gecacht (Actions und Tests), 1.320 interactive, 2.937 ungecacht mit festgehaltener Klasse, 0 refused und 0 ungecacht mit dem Grund `declared` (vorher 373).

#### Ein neues Target einordnen

Beantworte der Reihe nach; das erste Ja entscheidet.

1. **Läuft es bis zum Stopp** (Server, Watcher, Shell)? `"continuous": true`, Klasse `continuous`, Grund `serves-until-stopped`. Es wird `interactive`.
2. **Liest es nur Repository-Dateien, schreibt es nur deklarierte Outputs (oder keine), nutzt es kein Netzwerk, keinen Host-Store, kein Lease, keine Uhr und keinen laufenden Prozess?** Dann cache es: `"cache": true`, `inputs` für alles, was es außerhalb seines Projekts liest, `outputs` (`[]` für eine reine Prüfung) und gib ihm eine gecachte Namensfamilie oder seine eigene Entscheidung (unten).
3. **Sonst** `"cache": false` plus die Entscheidung, die den Grund nennt.

| Klasse | Gründe | Verwendung |
|---|---|---|
| `deterministic` | `pure-function-of-inputs` (Outputs deklarieren), `check-without-outputs` | gecachte Prüfungen, Tests, Generatoren mit deklarierten Outputs |
| `continuous` | `serves-until-stopped` | Server, Watcher, Shells |
| `live` | `drives-running-process`, `exercises-host-resources` | E2E gegen einen laufenden Prozess, Tests echter Locks, Speicher, Prozessbäume |
| `side-effecting` | `mutates-workspace`, `mutates-host-store`, `publishes-remote`, `publishes-live-state` | Formatierer, Gerüstbauer, Installer, Releases |
| `diagnostic` | `measures-environment`, `reads-caller-input`, `admission-refusal` | Benchmarks, Doctors, von ihren Argumenten gesteuerte Werkzeuge |
| `aggregate` | `orders-prerequisites`, `reenters-build-tool` | reine Reihenfolge; ein Verb, das andere Targets über `repo` ausführt, sollte sie stattdessen in `dependsOn` deklarieren |
| `managed-output`, `driver-owned` | `outputs-in-managed-store`, `outputs-are-store-links`, `freshness-owned-by-driver` | im Store veröffentlichte Builds und vom Treiber verantwortete Playground-Schritte |

Die Richtlinie löst einen Target-Namen in dieser Reihenfolge auf (`🎯️target-policy`): continuous-Namen, `cache: false`, die uncached-Namen der Richtlinie, mutierende und Live-Namen, dann deine Entscheidung in `metadata.semio.cache`, dann die `targetClasses` der Richtlinie (Namensfamilien wie `test`, `check`, `lint`, `typecheck`, `verify`, `build`, `generate`), dann ein `verify`-Befehl. **Ein Target, das nichts davon einordnet, wird nie wiedergegeben** (`unclassified`, `no-cache-classification`), und `"cache": true` allein ändert das nicht; gib einem ungewöhnlichen Namen daher seine Entscheidung:

```json
"digest-inputs": {
  "executor": "repo:script",
  "cache": true,
  "inputs": ["default", "^default"],
  "outputs": [],
  "options": { "command": "bun ./📜️script.ts digest-inputs" },
  "metadata": { "semio": { "cache": { "version": 1, "class": "deterministic", "reason": "check-without-outputs" } } }
}
```

```json
"measure-startup": {
  "executor": "repo:script",
  "cache": false,
  "outputs": [],
  "options": { "command": "bun ./📜️script.ts measure-startup" },
  "metadata": { "semio": { "cache": { "version": 1, "class": "diagnostic", "reason": "measures-environment" } } }
}
```

- **Outputs.** Ein gecachtes Target muss jeden deklarierten Output erzeugen, der kein Glob ist: Sonst scheitert es mit „Declared output of a replayed Bazel task was not produced“. Setze `metadata.semio.optionalOutputs: true` nur für einen Output, der zu Recht fehlen darf. Ein `pure-function-of-inputs`-Target ohne deklarierte Outputs wird zu `side-effecting` herabgestuft.
- **Test unter Bazel.** Nenne es `test` oder `test-<was>`, halte es gecacht mit `outputs: []` und unter 10.000 deklarierten Dateien (jede deklarierte Datei wird vor jedem Lauf in die Runfiles des Tests gelinkt, auch bei einem Treffer).
- **Remote-Ausführung.** Füge die `hermetic`-Deklaration (siehe Remote-Ausführung) nur hinzu, wenn das Target wirklich allein seine deklarierten Inputs liest.
- **Gesetz.** Das Cache-Korrektheits-Gesetz (`📚️library/⚖️laws/🔒️cache-correctness`) liest jedes Manifest durch die Produktionsrichtlinie und schlägt fehl bei einem nicht eingeordneten Target, einem gecachten Target, das die Richtlinie überstimmt, einem ungecachten Target ohne festgehaltenen Grund, leeren Inputs, einem Erzeuger ohne Outputs, einer nicht gehashten Umgebungsüberschreibung, einem benannten Input, den niemand deklariert, Outputs, die ausbrechen oder sich überlappen, und einem mutierenden oder Netzwerk-Befehl in einem gecachten Target.

#### Inkrementelle Builds und ihre Prüfung

Ein inkrementeller Build führt genau die Tasks erneut aus, deren deklarierte Inputs sich geändert haben, und gibt den Rest wieder. Beweise es mit den vorhandenen Operationen; der CI-Job `smoke` ist dafür geschrieben, dasselbe für beide Werkzeuge auf `@teaching/architecture-course:test` zu tun (der Workflow ist noch nie gelaufen).

```bash
repo cache clear --tool=bazel
repo cache status --tool=bazel
repo run @teaching/architecture-course:test --tool=bazel
repo cache status --tool=bazel
repo run @teaching/architecture-course:test --tool=bazel
repo cache status --tool=bazel
```

1. Notiere die Zahlen nach `cache clear`; nach dem ersten Lauf sind `entries` und `bytes` gewachsen, und bei Bazel zählt `activity.executed` die Actions, die liefen.
2. Der zweite Lauf startet keine Arbeit: Die Zusammenfassung von Bazel zeigt keinen `local`-, `worker`- oder Sandbox-Spawn (oder `disk cache hit`), `entries` wachsen nicht und `activity.executed` bleibt, während `activity.cacheHits` die Treffer zählt.
3. Ändere eine Datei, die die Task deklariert: Nur diese Task und ihre Abhängigen laufen (ein Abhängiger mit unverändertem Input-Snapshot wird wiedergegeben). Ändere eine Datei, die sie nicht deklariert, und nichts läuft: Die Input-Liste ist zu kurz.
4. `repo cache clear` gefolgt vom Lauf belegt einen kalten Fehltreffer; `--skip-cache` erzwingt die Ausführung einmal ohne Leeren; `--dry-run` zeigt den Plan, den der Lauf ausführen würde.
5. Erwarte zusätzliche Arbeit nach: Änderungen an den eigenen Dateien des Build-Werkzeugs (jede Action wird einmal neu geschlüsselt), dem Wechsel zwischen `prototype` und `release` (der Modus gehört zu jedem Schlüssel) und der Änderung eines deklarierten Inputs während des Builds (Bazel gibt `Skipping uploading outputs because of concurrent modifications` aus und der nächste Lauf führt erneut aus).

#### Hinweise je Plattform

| Rechner | Hinweise |
|---|---|
| macOS | Cache-Partitionen sind case-sensitive APFS-Images, ohne Privileg. Halte den Checkout-Pfad ASCII (Bazel stürzt beim Start bei einer Nicht-ASCII-Install-Base ab, und seine Sandbox kodiert eine Nicht-ASCII-Output-Base falsch; das Layout wird vorab abgelehnt). Der Adapter setzt eine UTF-8-Locale. |
| Linux | Verzeichnis-basierte Partitionen, kein Root und kein Loop-Device; verlangt ein case-sensitives Dateisystem mit atomarem Verzeichnisaustausch (ext4, xfs, btrfs). Ein Nicht-ASCII-`install`-Pfad wird abgelehnt; eine Nicht-ASCII-Output-Base funktioniert. In einem unprivilegierten Container fällt Bazel auf `processwrapper-sandbox` zurück (gleiche Ergebnisse, schwächere Isolation); `linux-sandbox` braucht einen privilegierten Container. Der Adapter nennt nie eine Sandbox-Strategie. |
| Devcontainer | Wie Linux. `.cache` ist ein benanntes Volume, privat für den Checkout (ein Bind-Mount von einem Host ohne Groß-/Kleinschreibung wird von `repo preflight` abgelehnt); `postCreateCommand` führt `repo run workspace:setup` aus. |
| Windows | Verzeichnis-Partitionen, getauscht durch eine journalisierte Umbenennung auf NTFS mit Groß-/Kleinschreibung je Verzeichnis. Verlangt `LongPathsEnabled` und eine kurze ASCII-Checkout-Wurzel (das Pfadbudget von Bazel ist `len(output base) + len(\execroot\_main\s\) + 256` gegen 259, oder 32766 mit langen Pfaden). Der Source-Link ist eine Junction (kein Entwicklermodus, keine Erhöhung), Runfiles sind aus (`--noenable_runfiles`, Startup-Option `--nowindows_enable_symlinks`), Tests laufen daher als gecachte Actions statt als `bazel test`, und hermetische Actions laufen nur remote. Setze Variablen in PowerShell mit `$env:NAME = "value"` und rufe `bun repo` auf. Unter Windows nicht ausgeführt. |

Kein Cache-Pfad darf auf irgendeinem Rechner 256 Zeichen überschreiten. Bazel und Bun sind je Betriebssystem und CPU (darwin, linux, windows auf arm64 und x64) mit Prüfsummen gepinnt, `repo tools setup` braucht also keinen manuellen Download.

#### Fehlersuche

- **Eine Operation wird nach Neustart oder erneutem Einhängen abgelehnt** („Exact canonical persistent Native publication required …“). Veröffentlichungsbelege bleiben unverändert. Gerätenummern gehören zum aktuellen Kernel-Namensraum und können sich nach einem Neustart oder erneutem Einhängen eines Elternimages innerhalb derselben Boot-Sitzung ändern. Eine aktuelle Veröffentlichung wird über das frisch verankerte Trägergerät beobachtet; veröffentlichter Inode, Modus, erforderliche Vorfahrenkette, physische Grenzen und Kernel-Zuordnung bleiben exakt. Das schreibt keinen Beleg um und überträgt keine Löschberechtigung. Ein nicht unterstützter Beleg wird abgelehnt. **Inaktiven Nx-Cache Zurücksetzen** gilt ausschließlich für den kanonischen inaktiven macOS-Nx-Container. Andere veränderte, eingehängte, belegte oder unbekannte Zustände bleiben diagnostische Ablehnungen (Wiederherstellung).
- **Ein Befehl wartet.** Stores werden über eine First-in-first-out-Lease-Warteschlange beansprucht. Ein Wartender ab Position 2 gibt alle 15 Sekunden eine `lease-queue`-Zeile aus, die die Prozess-ID des Halters nennt; eine Zeile `remains active on …` ist der Fortschritt eines laufenden Durchlaufs, kein Warten. Beende keinen Halter, der vorankommt; lies zuerst das Kopf-Ticket.
- **Ein Beleg scheitert.** Store-Beleg: Eine Task läuft ungecacht erneut (`[store-receipt] re-executing`). Generations-Beleg der Abhängigkeiten: Die Änderung einer Datei seines Abschlusses kostet den nächsten Befehl einen vollständigen Durchlauf (Fortschritt `dependencies:generation-verify:<n>`). Image-Beleg: siehe den ersten Punkt.
- **Kein Cache-Treffer.** Prüfe der Reihe nach: `--skip-cache` oder die Dashboard-Achse `cache` auf einem Skip-Wert; die Entscheidung des Targets im Manifest (`unclassified` wird nie wiedergegeben); ein nicht deklarierter oder zu weiter Input; der Modus (`prototype` oder `release`); ein anderer Prozess, der deklarierte Inputs während des Builds ändert; bei einem Remote-Treffer ein anderer Benutzer oder Checkout-Pfad.
- **Remote-Cache.** `repo cache remote status` zeigt `configured: false`, wenn kein Endpunkt gesetzt ist, `reachable: false`, wenn der Endpunkt nicht antwortet, und `authorized: false` bei einem falschen Token (Nx bricht einen Lauf bei 401 ab und ignoriert 403 beim Upload stillschweigend).
- **Worker.** Starte mit `--workers off` neu, um ein Worker-Problem von einem Task-Problem zu trennen. Ein Build, der mit „Captured implementation Source changed“ scheitert, hat erlebt, dass sich eine Datei des Build-Werkzeugs unter ihm änderte; starte ihn neu.
- **Installierte Pakete.** `Cannot find module` für ein Workspace-Paket heißt, dass die Abhängigkeiten älter sind als die Quellen: `repo dependencies lock --all`, dann `repo dependencies sync --all`. Auf einem frischen Klon braucht die Nx-Einrichtung möglicherweise die installierten Workspace-Links: Stoppt sie mit `Cannot find module`, führe zuerst den Sync aus.
- **Nx meldet `.nx/installation` fehlend.** Führe `repo tools setup nx` aus.

#### Verifiziert und noch nicht verifiziert

Verifiziert am 2026-10-20 (macOS arm64, Bazel 8.4.2, Nx 23.2.0; Linux-arm64-Container für die Plattformzeilen): echte Bazel-Läufe kalt, warm, nach `clean` und nach Serververlust mit dem Produktions-Task-Eigentümer, früher Abbruch der Kette, Tests als gecachtes `bazel test`, `affected` gegen Bazel-`rdeps` und die Locators von Nx, echtes Bazel und ein unverändertes Nx gegen `repo cache serve` (Remote-Treffer nach dem Leeren des lokalen Caches, falsche und Nur-Lese-Tokens), persistente Worker gegen echtes Bazel, das Hermetik-Gesetz, die Einrichtung im Linux-Container und die Fixture-Suites jeder Komponente. Noch nicht verifiziert: ein Produktionslauf `repo --tool=bazel run` nach der Integration, Nx mit der gepatchten Installation des Repositorys gegen einen Remote-Cache, ein echter Remote-Executor und die Remote-Ausführung irgendeines Repository-Targets, Windows, der Lebenszyklus des Devcontainers und jede End-to-End-Kette unter beiden Werkzeugen (siehe Verifikationsstand).

**Werkzeugwahl.** `--tool=nx|bazel` auf der Kommandozeile gewinnt, dann die Umgebungsvariable `SEMIO_BUILD_TOOL`, dann `defaultTool` der Richtlinie (`nx`). Das gewählte Werkzeug wird als `SEMIO_BUILD_TOOL` an jede verschachtelte Task weitergegeben; die Dashboard-Achse `build-tool` setzt dieselbe Variable (siehe Befehlsregister). Alles andere wird abgelehnt („Unknown build tool“). Die Compiler-Konfiguration wählst du mit `--configuration=prototype|release` (oder `-c`, einem Suffix `:<configuration>` an der Task oder `SEMIO_BUILD_MODE`); widersprüchliche Werte werden abgelehnt („Conflicting build modes“, auf Englisch und Deutsch, mit den Targets mit festem Modus wie `dev`, die einen Modus vorgeben). Der Modus ist eine Achse des Aufrufs, keine Einstellung je Target: Die Bazel-Implementierung akzeptiert `prototype` und `release` für jedes Target, ob es sie als Konfigurationen deklariert oder nicht, jede geplante Task jedes Targets trägt den Modus in Id, Label und Workspace, die Abhängigkeiten der gewählten Task erben den Modus, der Modus des ursprünglichen Aufrufers ist die Autorität, die jede Task-Umgebung exportiert (`SEMIO_BUILD_MODE`), und gehört zu jedem Action-Schlüssel, und der Plan lehnt eine Task mit abweichendem Modus sowie eine Abhängigkeit ab, deren Target auf einen anderen Modus festgelegt ist. Auf der Kommandozeile lassen sich nur `prototype` und `release` wählen; andere Konfigurationsnamen gibt es nur im Bazel-Adapter. Die Kurs-Verben, die release brauchen (`publish`, `test-e2e` im Probelauf, `docker-image-build`, `docker-image-publish`, `deploy-check` von `@teaching/architecture-course`), lesen den Modus des ursprünglichen Aufrufers und lehnen einen prototype-Aufrufer auf Englisch und Deutsch ab; release wählst du mit `bun repo [--tool=bazel] run @teaching/architecture-course:publish:release`.

### Manifeste

Felder einer Task: `executor` (`repo:script`, Standard, führt `command` über die Repo-Prozessautorität aus, oder `repo:noop`, nur Reihenfolge, führt nichts aus); `command`, `options.command`, `options.commands`, `options.args` (wörtliche Argumente, nie per Shell interpoliert) mit Überschreibungen je `configurations.<name>`; `dependsOn` (`"target"`, `"^target"`, `"project:target"` oder `{target, projects, dependencies, params}`); `inputs`; `outputs` (mit `{projectRoot}`, `{workspaceRoot}` und Option-Tokens wie `{options.env.SEMIO_BUILD_MODE}`; `[]` heißt „keine Dateien wiederherzustellen“); `cache`; `continuous`; `metadata.semio.dashboard.ready` (Bereitschaft: die Ausgabe zeigt `http://(127.0.0.1|localhost|0.0.0.0):<port>` und diese Adresse antwortet mit 2xx oder 3xx).

**Inputs.** Eine Liste aus Datei-Globs (`{projectRoot}/**/*`, `{workspaceRoot}/…`, `!` schließt aus), benannten Gruppen der Richtlinie, `^<gruppe>` (dieselbe Gruppe der Abhängigkeitsprojekte) und Objekten: `{"env": "NAME"}`, `{"runtime": "<command>"}`, `{"externalDependencies": […]}` und `{"dependentTasksOutputFiles": "<glob>", "transitive": true|false}`. Deklariere alles, was die Task liest und nicht aus dem eigenen Projekt erreichbar ist: Daten außerhalb, gestartete Testdateien, Werkzeug- und Toolchain-Dateien, Umgebung. Das `default` eines Projekts ersetzt das Workspace-`default`; füge `sharedGlobals` dort wieder hinzu.

**Quellabschluss eines Befehls.** Ein `repo:script`-Target braucht keine handgeschriebene Liste der Module, die sein Skript importiert. Die Graph-Inferenz leitet den Abschluss des Befehlsskripts ab (`📚️library/🏗️build/🕸️graph/📥️inference/🧭️script-inputs`): relative Importe, Importe über Workspace-Paket-Specifier wie `@semio-tech/process/leases` (`workspacePackageModuleV1`; installierte Registry-Pakete deckt weiter ihre gesperrte externe Abhängigkeit ab), wörtliche `new URL("…", import.meta.url)`-Ziele, die existieren (Module werden verfolgt, andere Dateien als Ressourcen gehasht), und wörtliche Modul-Inputs, die ein Target deklariert (etwa `{projectRoot}/…/x.test.ts`). Der Abschluss gehört als benannte Inputs `commandSources…` zum Target; in der Hash-Darstellung des Graphen ist er der Marker `{"env": "SEMIO_SOURCE_CLOSURE_<sha256 des Manifests>"}`, und das Manifest liegt im Graph-Store unter `build-input-closures`, das Nx beim Hashen der Task liest. Cargo-Lock-Projektionen sind Marker derselben Art (`SEMIO_CARGO_LOCK_<key>`). Bazel löst die Marker selbst auf (siehe Bazel-Implementierung). Bewusst nicht abgedeckt: Quelltext-Test-Importe hinter `import.meta.vitest`, Dateien, die über `import.meta.dir` oder zusammengesetzte Zeichenketten gelesen werden, und Targets, die nie gecacht werden (kontinuierlich, live). Gemessen an einer Stichprobe von 49 Projektskripten wuchs der Abschluss von im Median 489 auf 1.200 Dateien (etwa 28 Prozent mehr CPU für die Ableitung, ausgeglichen durch ein Zulassungs-Memo, das die alten Kosten um 35 Prozent senkte). Noch nicht verifiziert: die zusammengesetzten Inputs in einem echten Graph-Laden (`repo show projects` wurde am 2026-10-20 nach 4 Stunden gestoppt; die spätere Analyse fand es durch die Speicherbereinigung gebremst bei Speichermangel des Hosts, nicht quadratisch im Abschlusscode: Ein Projekt kostet 0,3 bis 0,45 CPU-s, die Ableitung des Abschlusses macht davon etwa 29 Prozent aus, ein sauberer Lauf wird auf 25 bis 40 Minuten geschätzt), ein Nx-Hash einer echten Task und ein Bazel-Lauf mit aufgelösten Abschlüssen über den Produktionseinstieg.

**Cache-Klassen.** `cache` ist der Schalter, den beide Werkzeuge lesen. Daneben hängt die Inferenz an jedes Target, das sie erzwingt, synthetisiert oder nicht wiederholt, eine maschinenlesbare Entscheidung `metadata.semio.cache = {"version":1,"class":…,"reason":…}` (geschlossenes Schema `📚️library/🏗️build/🏃️execution/🧬️schema/💾️cache.json`). Die Klasse nennt die physische Tatsache, die eine Wiedergabe erlaubt oder verbietet:

| Klasse | Gründe | Bedeutung | Gecacht |
|---|---|---|---|
| `deterministic` | `pure-function-of-inputs`, `check-without-outputs` | Reine Funktion der deklarierten Inputs; jeder deklarierte Output ist ein einfacher wiederherstellbarer Baum oder es gibt keinen. | ja, die einzige wiedergebbare Klasse |
| `driver-owned` | `freshness-owned-by-driver` | Der Befehl kompiliert über den Build-Treiber, dessen Cargo-Frische und Stage-Cache maßgeblich sind (Playground `prepare-*` und `build-*-react*`, `component`). | nein |
| `managed-output` | `outputs-are-store-links`, `outputs-in-managed-store` | Outputs liegen im geleasten Produkte-Store hinter einem Bindungs- oder Manifest-Protokoll (TypeScript-Artefakt-`build`, Wasm-Slots), und das Manifest schreibt kein `cache: true`; eine wiederhergestellte Kopie würde abgelehnt oder umginge den Store. Mit `cache: true` ist das Target stattdessen `deterministic`, weil sein Beleg der wiederherstellbare Output ist (siehe Store-Belege). | nein |
| `continuous` | `serves-until-stopped` | Läuft bis zum Stopp. | nein |
| `side-effecting` | `publishes-live-state`, `publishes-remote`, `mutates-workspace`, `mutates-host-store` | Verändert Zustand außerhalb der deklarierten Outputs. | nein |
| `live` | `drives-running-process`, `exercises-host-resources` | Beobachtet oder steuert einen laufenden Prozess (Namen mit `e2e` oder `live`) oder prüft die echten Locks, den Speicher, den Prozessbaum oder die Uhr dieses Rechners. | nein |
| `aggregate` | `orders-prerequisites`, `reenters-build-tool` | Ordnet Voraussetzungen und leistet keine eigene Arbeit. | nein |
| `diagnostic` | `admission-refusal`, `measures-environment`, `reads-caller-input` | Meldet eine Ablehnung oder Messung und wird immer neu bewertet. | nein |
| `unclassified` | `no-cache-classification` | Keine Zeile, Deklaration und kein prüfender Befehl ordnet das Target ein, es wird also nie wiedergegeben, bis die Richtlinie seine Art benennt (fail-closed). | nein |

Der Bazel-Adapter liest die Entscheidung (`bazelTargetCacheClassV1` validiert sie gegen das geschlossene Schema und lehnt eine ungültige mit „Closed repository cache decision required“ ab) und leitet daraus seine Cache-Entscheidung ab, siehe unten. Die Nx-Projektion liest sie nicht; Nx entscheidet aus `cache`, `continuous` und `outputs`. Ein Manifest darf sie selbst deklarieren (ein Target mit `cache: false` hält seinen Grund so fest, siehe Build-Werkzeuge im Alltag); die synthetisierten Playground-Targets, die TypeScript-Artefakt-Targets `test`, `check` und (mit `cache: true`) `build` sowie die Wasm-Slot-Erzeuger mit `cache: true` tragen `deterministic`, per Namensregel gecachte Targets tragen die Klasse ihrer Zeile. Die Richtlinie, die `cache` und die Entscheidung setzt, folgt dieser Reihenfolge, die erste passende Zeile gewinnt (`📚️library/🏗️build/🕸️graph/📥️inference/🎯️target-policy`, Namen aus `📚️library/⚡️caching/🔣️policy.json`):

| Rang | Regel | Gecacht | Angehängte Entscheidung |
|---|---|---|---|
| 1 | `continuous: true` oder ein Name `dev`, `serve`, `watch`, `start`, `test-watch`, `daemon` (auch `<name>-…`) | nein | `continuous` |
| 2 | `cache: false` im Manifest | nein | keine |
| 3 | Ein Name der Liste `uncached` (`audit`, `bench`, `clean`, `deploy`, `deps`, `install`, `publish`, `seed`, `setup`, `test-e2e`, `update`, …) oder ein exakter Name (`format`, `commit`, `os`, `parity`, …); ein geschriebenes `cache: true` wird überstimmt | nein | `live` (`e2e`, `live`, `os`, `semio`), `diagnostic` (`audit`, `bench`, `doctor`, `parity`, …), `side-effecting` (`publish`, `deploy` als `publishes-remote`, sonst `mutates-workspace`) |
| 4 | `hub-live-catalog-check`, `hub-live-catalog-native-check`, `hub-live-catalog-oracle` | ja | keine (Ausnahmen von Rang 5) |
| 5 | Ein durch Bindestriche getrenntes Wort `clean`, `gc`, `prune`, `setup`, `fuzz`, `e2e` oder `live` im Namen | nein | wie Rang 3 |
| 6 | Die Entscheidung, die das Target in `metadata.semio.cache` deklariert, sonst die erste passende Zeile von `targetClasses` in `📚️library/⚡️caching/🔣️policy.json` (geordnete Zeilen aus exakten Namen, Anfängen, Endungen und Bestandteilen, jede mit einer Entscheidung; ein exakter Name schlägt den Rest): `deterministic/check-without-outputs` für die Anfänge `test`, `check`, `lint`, `typecheck`, `format-check`, `verify`, `schema`, `stdio`, eine Endung `-check`, `-test`, `-oracle`, `-lint`, `-source` oder `-native`, den Bestandteil `contract` und eine Liste exakter Namen; `deterministic/pure-function-of-inputs` für die Anfänge `build` und `generate` und eine Liste exakter Erzeuger; `side-effecting/mutates-workspace` für den Anfang `generator` | ja, wenn die Klasse `deterministic` ist, sonst nein | die Klasse der Zeile; bei `deterministic` die Standard-Inputs `default` und `^default`, Outputs `[]`, sofern das Manifest nichts anderes sagt |
| 7 | Ein `verify`-Befehl im Target | ja | `deterministic/check-without-outputs` |
| 8 | Alles andere | **nein** | `unclassified/no-cache-classification` |

Rang 8 ist unter beiden Werkzeugen fail-closed: Ein Target, das nichts einordnet, läuft jedes Mal, was auch immer sein Feld `cache` sagt (`unclassified`); das Cache-Korrektheits-Gesetz (`📚️library/⚖️laws/🔒️cache-correctness`) meldet es zusammen mit jedem `cache: true`, das die Richtlinie überstimmt hat, und jedem `cache: false` ohne festgehaltenen Grund. Ein `deterministic/pure-function-of-inputs`-Target ohne deklarierten Output wird zu `side-effecting/mutates-workspace` herabgestuft, bevor eines der Werkzeuge es sieht (`cachedOutputsAdmittedV1`), weil ein Treffer einen leeren Erfolg wiedergäbe. Bazel verlangt zusätzlich ein `outputs`-Array und eine Klasse, die Wiedergabe erlaubt, siehe seine Cache-Entscheidung. Schreibe `cache: false` samt Entscheidung bei Tests, die echten Speicher-, Lease-, Prozess- oder Toolchain-Zustand prüfen, bei Läufen gegen laufende Hosts, Browser oder Server, bei Schreibern außerhalb ihrer deklarierten Outputs, bei Startern langlebiger Werkzeuge, bei Netzwerk-Downloads und bei Schritten mit unbegrenzter Eingabemenge.

**Store-Belege.** Produkte, die in einen geleasten, inhaltsadressierten Store statt ins Projektverzeichnis veröffentlicht werden (Cargo-Artefakte im Compiler-Store, Vite-Sites, Wasm-Pakete, TypeScript-Artefakte), lassen sich nicht durch Kopieren von außen in diesen Store wiederherstellen. Sie deklarieren einen Beleg als einzigen Output, `{projectRoot}/.🧾️store/<target>.json` (Schema `📚️library/🏗️build/🧾️store-receipt/🧬️schema/🔣️.json`, git-ignoriert, bewusst nicht unter `dist`, das bei TypeScript-Artefakten ein Link in den Store ist). Der Beleg nennt jeden veröffentlichten Store-Pfad (`entries`: Art, Bytes, Dateien, SHA-256; der Digest eines Verzeichnisses hasht seine sortierte Dateiliste) und jeden Link, der einen Projektpfad an einen Store-Pfad bindet (`links`). Die zentralen Veröffentlicher schreiben ihn nach der Veröffentlichung, es ändert sich also kein Build-Skript: das Artefaktziel, über das die Vite- und Wasm-Veröffentlicher schreiben (`⚡️caching/📦️artifacts/🟦️.ts`), der Compiler-Store-Veröffentlicher von Cargo-`build` (`⚡️caching/📦️artifacts/🏗️native-build/🟦️.ts`, übersprungen, wenn ein Beobachtungs-Output angefordert ist) und der Binder der TypeScript-Artefakte (`⚡️caching/📦️artifacts/🟦️typescript/🔗️binding/🟦️.ts`). Beide Adapter übergeben den Ort des Belegs nur der einen Task, die ihn deklariert (`SEMIO_TASK_RECEIPT`, ausgestellt von `issueStoreReceiptV1` in `📚️library/🏗️build/🧾️store-receipt/🟨️.mjs`; Nx: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/🟨️.mjs`, Bazel: `executeTask` in `📚️library/🏗️build/🔧️tools/🏗️bazel/📜️script.ts`); bei jeder anderen Task ist er ungesetzt, eine verschachtelte Task schreibt also nie in den Beleg ihres Elternteils, und ein Veröffentlicher tut ohne ihn nichts (`recordStoreContentV1`).

Nach jedem `run` oder `run-many` prüfen beide Werkzeuge den Beleg jeder gewählten Task und ihrer Voraussetzungen. Ein fehlender, beschädigter oder auf einen fehlenden oder geänderten Store-Eintrag zeigender Beleg gilt als Fehltreffer: Diese eine Task läuft allein und ungecacht erneut (Nx: `run <task> --skip-nx-cache --excludeTaskDependencies`, die eine zusätzliche Kindauswahl, die der Aufrufer zulässt und die auch den Cache-Eintrag ersetzt; Bazel: im Prozess mit `skipCache` und ohne Abhängigkeiten, wobei der veraltete Disk-Cache-Eintrag bestehen bleibt, sodass ein späterer Treffer wieder repariert) und wird nochmals geprüft, sonst schlägt der Aufruf geschlossen fehl. Ein gescheiterter erster Lauf wird nach der Reparatur einmal wiederholt. Eine Task, die einen Beleg deklariert, deren Handler aber keinen schrieb, ist ein Fehler und wird nicht stillschweigend akzeptiert. TypeScript-Artefakt-`build` und Wasm-Slot-Erzeuger tragen den Beleg als Output: Sie werden wiedergegeben, wenn das Manifest `cache: true` schreibt (Entscheidung `deterministic`), sonst bleiben sie `managed-output`. Eine Task deklariert einen Beleg nur, wenn ihre `outputs` den Belegpfad nennen (`declaredStoreReceiptV1`): `check`, `test` und `lint` liefern ein Urteil statt Store-Inhalt, und `publish` sowie der Kurs-`build` nennen andere oder keine Outputs. Abwechselnde `prototype`- und `release`-Läufe eines Targets teilen sich eine Belegdatei (ihr Pfad enthält keinen Modus), ein Wechsel lässt das Target daher voraussichtlich einmal neu laufen (aus der Pfadregel gefolgert, nicht beobachtet). Noch nicht verifiziert: Kein Lauf hat den Reparaturpfad ausgeübt (erster Nachweis: `@teaching/proctor:build` zweimal ausführen, den Slot `published/<hash>` des Compiler-Stores löschen, erneut ausführen und eine Zeile `[store-receipt] re-executing` erwarten, mit `--tool=nx` und `--tool=bazel`).

Die Bazel-Implementierung entscheidet je Action aus `cache`, `continuous` und `outputs` und ist bei fehlenden Deklarationen strenger (siehe ihre Cache-Entscheidung unten).

### Bazel-Implementierung

`--tool=bazel` (oder `SEMIO_BUILD_TOOL=bazel`) wählt Bazel 8.4.2 (`.bazelversion`, festgelegter Download je OS und CPU). Der Adapter liegt in `📚️library/🏗️build/🔧️tools/🏗️bazel`. Er macht aus den gewählten Tasks echte Bazel-Actions, sodass Action-Cache, Disk-Cache, optionaler Remote-Cache und lazy Auswertung von Bazel selbst kommen.

- **Generierter Workspace.** Je eigenständiger Auswahl entsteht `<products>/bazel/workspaces/<namespace>` mit `MODULE.bazel`, `BUILD.bazel`, den Regeln in `tasks.bzl` (`repo_task`, `repo_launch`, `repo_noop`), je Action einem Manifest `<label>.json` und einem Fingerabdruck `<label>.input` sowie `s`, einem Link auf den echten Checkout (unter Windows eine Junction). Das Label einer Task ist `t_` plus 16 Hexziffern des SHA-256 der Task-ID.
- **Minimale Builds.** Nur die gewählten Tasks und die über `dependsOn` erreichbaren werden zu Actions; gebaut wird genau `bazel build` der gewählten Labels. Reine Reihenfolge-Tasks (`repo:noop`) verschwinden hinter ihren Erzeugern, es sei denn, sie sind selbst gewählt. Ein nicht benötigtes Target wird nie analysiert oder ausgeführt. Eine gewählte gecachte `test`-Task ohne deklarierte Outputs und ohne gewählte Abhängige läuft als Bazel-Test mit gecachten Testergebnissen (siehe Task-Dispositionen in Build-Werkzeuge im Alltag).
- **Deklarierte Inputs.** Die `inputs` einer cachebaren Task werden gegen die Dateien des Checkouts aufgelöst und als Bazel-Inputs deklariert: die Dateien erreichen die Action über gemeinsame `filegroup`s aus Labels `s/<pfad>` statt über eine Liste je Task: Ein Verzeichnis, dessen Dateien alle gewählt sind, ist eine Gruppe `d_<hash>` (eine Projektwurzel ist eine Gruppe, Ketten mit einem Kind werden zusammengezogen), Musterbausteine mit mehr als zwei Mitgliedern sind gemeinsame Verbunde `k_<hash>`, und jede Task erhält einen Verbund `i_<hash>` (`bazelSourceCoverV1`; Namen sind ASCII, Emoji stehen nur in Datei-Labels). Auf dem statischen Graphen mit 1.466 Projekten schrumpfte `BUILD.bazel` dadurch von 317 MB auf 65 MB und die Workspace-Erzeugung von 351 s auf 37 s. `glob()` wurde versucht und verworfen: Mit `.bazelignore` passt es auf nichts, ohne folgt es Symlink-Schleifen und git-ignorierten Bäumen, die Nx nie hasht. `^name` und `dependencies: true` erreichen den transitiven Abhängigkeitsabschluss, wie Nx es hasht (`bazelTaskInputsV1`); ein `dependsOn`, das ein nicht vorhandenes Projekt oder Target nennt, wird beim Bau des Plans abgelehnt (`requireBazelDependencyV1`, „Unknown build task dependency“), und `bazelDanglingDependenciesV1` listet alle auf einmal auf. Pfade, die Bazel nicht als Label benennen kann (label-unsichere Namen, Verzeichnisse, hängende Links, alles unter einem verschachtelten `BUILD`-Paket), gehen stattdessen in den Fingerabdruck ein; dieser enthält außerdem Plattform, CPU, Bun-Version, Build-Modus, deklarierte Umgebungswerte und `runtime`-Ausgaben. Das Action-Manifest ist inhaltsstabil: Es nennt Task und ausführende Implementierung, aber keinen Workspace-, Laufzeit- oder Snapshot-Pfad; die Live-Daten stehen in `runtime.json` außerhalb jedes Schlüssels.
- **Befehlsabschlüsse.** Abschluss-Marker (`SEMIO_SOURCE_CLOSURE_<key>`, `SEMIO_CARGO_LOCK_<key>`) werden zu den Dateien aufgelöst, die sie nennen, bevor eine Deklaration oder ein Fingerabdruck gebaut wird (`📚️library/🏗️build/🔧️tools/🏗️bazel/🔗️closure`): `bazelClosureMarkersForPlanV1` sammelt die Marker, die ein Plan erreichen kann (Task-Inputs, `^`-Kanten und `{input, projects}`-Verweise), die Manifeste werden über ihre Inhaltsadresse geholt (`managedBazelClosureFetchV1` über den Graph-Store-Leser des Nx-Hashers; für Tests eine Dateisystem-Variante), gegen ein geschlossenes Schema geprüft, und absolute Namen oder Namen mit `..` werden abgelehnt. Ein Marker ohne geladene Manifeste ist ein Fehler, keine leere Liste. Zuvor erreichte keine Abschlussdatei einen Bazel-Action-Schlüssel, eine Änderung an einem importierten Modul ließ eine Task also gecacht (am 2026-10-20 in einem Scratch-Lauf gemessen: 106 von 111 Modulen eines Skripts und 162 von 169 eines anderen waren nicht deklariert). Mit dem echten Bazel 8.4.2 im Test dieser Komponente geprüft (`🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️closure`, 9 Tests bestanden am 2026-10-20 auf dem Live-Baum): Eine Regel über die aufgelösten Labels läuft einmal, bleibt nach einer Änderung außerhalb des Abschlusses bei einmal und läuft nach einer Änderung an einem importierten Modul erneut. Noch nicht verifiziert: das Holen unter dem Bazel-Storage-Lease im Produktionseinstieg und die erneute Messung der nicht deklarierten Module nach der Änderung.
- **Quell-Link und `.bazelignore`.** Der generierte Workspace verlinkt den Checkout als `s` (`linkBazelSourcesV1`) und schreibt keine `.bazelignore`; eine alte entfernt er. Ein früherer Adapter führte den Link dort auf, damit `//...` ihm nicht endlos folgt, und ein Scratch-Lauf am 2026-10-20 zeigte den Preis: `s` fehlte im Execroot-Symlink-Wald, Bazel konnte die deklarierten Inputs nach einer Action ohne Sandbox nicht mehr stat-en und lud keine Ergebnisse hoch (`Skipping uploading outputs because of concurrent modifications`); der Disk-Cache blieb leer und jeder Warmlauf führte erneut aus. Ohne die Ignore-Datei würde `//...` dem Link endlos folgen, deshalb fragen Abfragen das Wurzelpaket mit `//:all` ab (jede Task-Regel liegt darin; 0,4 s im Scratch-Lauf). Die Adapter-Änderung wurde am 2026-10-20 um 11:36 angewendet. Noch nicht verifiziert: ein Produktions-`repo --tool=bazel run`, der das Füllen des Disk-Caches und einen Warmtreffer mit dem korrigierten Adapter zeigt; die Tabelle unten entstand ohne die `.bazelignore`; die ersten Scratch-Läufe damit cachten nichts.
- **Deklarierte Outputs.** Jede Task hat genau einen deklarierten Tree-Artifact-Output `<label>.snapshot`. Ein Verbraucher erhält die Snapshots seiner Erzeuger (bei `transitive: true` den transitiven Abschluss) als Inputs. Nach dem Build werden die Snapshots der gewählten Tasks in den Checkout wiederhergestellt.
- **Cache-Entscheidung (fail-closed).** Jede Action trägt `cache` und, wenn sie ungecacht ist, einen maschinenlesbaren Grund; die Starlark-Regel scheitert ohne einen und versieht die Action mit `no-cache`. Der Adapter entscheidet in dieser Reihenfolge (`bazelCacheDecisionV1`):
  1. Ein ausdrückliches `cache: true` gegen eine Plugin-Klasse außer `deterministic` ist ein Konflikt und wirft („Conflicting cache declaration“), außer bei einer reinen Reihenfolge-Task.
  2. `continuous` (ein Dienst) ist ungecacht mit dem Grund `continuous`.
  3. `--skip-cache` ist ungecacht mit dem Grund `skipped`.
  4. Eine reine Reihenfolge-Task (`repo:noop`) ist immer cachebar.
  5. Eine Klasse außer `deterministic` (siehe Cache-Klassen) ist ungecacht, der Klassenname ist der Grund: `driver-owned`, `managed-output`, `side-effecting`, `live`, `aggregate`, `diagnostic`, `unclassified`.
  6. `cache: false` im Manifest ist `declared` und gewinnt auch gegen eine Klasse `deterministic`.
  7. Weder `cache: true` noch Klasse `deterministic` ist `undeclared`: die Task läuft immer, bis eines deklariert ist.
  8. `cache: true` oder Klasse `deterministic` ohne `outputs`-Array ist `unbounded`: ein Treffer könnte nicht wiederherstellen, was erzeugt wurde.
  9. Alles andere ist cachebar.

  Deklariere also `outputs` (für reine Prüfungen `[]`) an jedem cachebaren Target. Auf dem statischen Graphen vom 2026-10-20 deklarierten vor der Korrektur durch die Eigentümer 809 Targets in 278 Projekten `cache: true` ohne `outputs` und liefen deshalb unter Bazel ungecacht mit dem Grund `unbounded`; `bazelUncachedReportV1` (geschlossenes Schema `UncachedReport`) gruppiert sie je Eigentümerprojekt, und kein CLI-Befehl gibt diesen Bericht bisher aus. Kontinuierliche Tasks werden zu `repo_launch`-Actions, laufen mit `bazel run`, ihre Bereitschaft wird abgewartet, und sie teilen sich den Server des Builds.
- **Ausführungsanforderungen.** Jede Task- und Launcher-Action trägt `no-remote-exec` (der `repo_noop`-Marker schreibt nur eine Datei und startet keinen Prozess); Actions mit `host_state` zusätzlich `no-sandbox`, heute ist das jede Task- und Launcher-Action, nur der `repo_noop`-Marker ist sandboxfähig (`STARLARK_RULES` in `🏗️build/🔧️tools/🏗️bazel/📜️script.ts`; `Actions.kinds` in `🏗️build/🔧️tools/🏗️bazel/🧬️schema/🔣️.json`). Gründe laut Schema (`ActionPolicy.kinds`): Eine *Task*-Action führt den Task-Prozess im echten Checkout aus, mit Arbeitsverzeichnis, deklarierten Schreibzugriffen auf Quellbaum und gemeinsamen Store, dem Loopback-Steuersocket und dem Laufzeitkanal außerhalb des Baums, was eine Sandbox verbergen oder blockieren würde; eine *Launcher*-Action bindet exakte Execroot-Output-Pfade und erhält Autorität über den Steuersocket der Invokation, was ein Sandbox-Execroot ändern würde. Folge: Ergebnisse sind durch deklarierte Inputs und Fingerabdruck bestimmt, nicht durch das, was eine Sandbox beobachtet hat; eine fehlende Input-Deklaration zeigt sich als veralteter Treffer, nicht als Fehler. Die `.bazelrc` des Repositorys setzt heute kein `--spawn_strategy`, `--sandbox_*` oder `--strategy` (der Test „the repository .bazelrc carries exactly the authored static cache policy and no host paths“ in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🧪️tests` legt ihre Cache-Zeilen fest und lehnt Host-Pfade ab, verbietet aber kein Sandbox-Flag); jede Action, die je ohne `host_state` deklariert wird, läuft also in Bazels Standard-Sandbox.
- **Sandbox und Host-Pfade.** Bazel 8.4.2 unter macOS behandelt Nicht-ASCII-Pfade seines eigenen Zustands falsch, an zwei durch Experimente gefundenen Stellen: Eine `--install_base` mit Emoji oder Akzent lässt den Server beim Start abstürzen („Could not find or load main class“), und das `darwin-sandbox`-Profil wird aus Bazels byteweisen Pfadstrings geschrieben, aber jedes Byte ein zweites Mal als UTF-8 kodiert, sodass die Schreibregeln für eine Nicht-ASCII-`--output_base` nie passen und jede Sandbox-Action (auch ihre `stats.out`) mit „Operation not permitted“ scheitert. Es wirkt nur ortsabhängig, weil `/private/tmp`, `/private/var/tmp`, `TMPDIR` und `~/Library/Caches` für jede Schreibweise freigegeben sind. Das Produktionslayout hält die `install`-Basis, die `outputs`-Wurzel und die `server`-Output-Bases (`<products>/bazel/outputs/server/<hash>`) in den nativen Partitionen unter `.cache/b`, und die sind ASCII, solange der Checkout-Pfad ASCII ist (zum Beispiel `/Users/<name>/Documents/semio`). `requireBazelHostPathsV1` (aufgerufen von `bazelCacheLayoutV1` in `🏗️build/🔧️tools/🏗️bazel/💾️storage/🟦️.ts`, das jeder Bazel-Speichernutzer aufbaut) lehnt unter darwin ein Layout ab, dessen Pfad `install`, `outputs` oder `server` ein Nicht-ASCII-Zeichen enthält („ASCII Bazel host path required on darwin: outputs“), und zwar beim Aufbau des Layouts statt mitten im Build. Halte den Checkout-Pfad unter macOS also ASCII. `--sandbox_base` wird nicht benutzt. Eine Sandbox-Action darf nur in ihr Execroot, die Temp-Verzeichnisse und `~/Library/{Caches,Logs,Developer}` schreiben; wird je eine Task sandboxed, die in den Checkout oder eine Partition schreibt, braucht sie `--sandbox_writable_path=<ASCII-Pfad>`, das denselben Kodierer durchläuft und deshalb ebenfalls ASCII sein muss. Linux (Bind-Mounts statt Profil) und Windows wurden nicht untersucht, die Sperre gilt nur für darwin; Windows deckt die Bereitschaftsprüfung für Nicht-ASCII-Pfade von Workspace und Partition ab.
- **Emoji in Quell-Labels.** Task-Quellen heißen `s/<pfad>` (`bazelSourceLabelV1`): die Datei hinter dem Link `s`, ein Target-Name im Wurzelpaket. Beobachtet mit dem festgelegten 8.4.2 (der Test mit dem echten Binary in `🏗️build/🔧️tools/🏗️bazel/🧪️tests/📥️actions` spielt die Fixture-Namen ab und wird ohne `SEMIO_TEST_BAZEL_BINARY` übersprungen): Bazel akzeptiert in Target-Namen jedes Nicht-ASCII-Zeichen, auch astrale Emoji, ZWJ-Sequenzen, Hautfarben, kombinierende Zeichen, CJK und das geschützte Leerzeichen, auch als Action-Input- und -Output-Namen; abgelehnt werden nur Backslash und Steuerzeichen. Nur Paketnamen müssen ASCII sein, der Adapter braucht also nie ein Emoji-Paket; ein Verzeichnis mit `BUILD` oder `BUILD.bazel` gilt ihm unabhängig von der Schreibweise als Paketgrenze, alles darunter geht in den Fingerabdruck (`bazelSourceClassesV1`). Der Adapter lässt einen Pfad als Label zu, wenn er `^(?:[A-Za-z0-9_@=,+~%./\-]|[^\u0000-\u007f])+$` entspricht (codepunktbasiert, gilt also auch in Python, Rust und Go), und nimmt alles andere (Leerzeichen, Backslash, Steuerzeichen, Verzeichnisse, hängende Links, alles unter einem Verzeichnis mit `BUILD`) stattdessen in den Fingerabdruck auf. In einem Scratch-Experiment waren Disk-Cache und Cache-Schlüssel unter `LANG=C` und einer UTF-8-Locale identisch (kein Test deckt das ab); der Adapter setzt unter darwin eine UTF-8-Locale (`LANG` und `LC_ALL` `en_US.UTF-8` in `runBazelTasksInStorageV1`).
- **Disk-Cache.** `<products>/bazel/actions` mit Garbage-Collection (`--experimental_disk_cache_gc_max_size` gleich 40 Prozent des Budgets der Produkte-Partition, auf MiB abgerundet; `.bazelrc` ergänzt `--experimental_disk_cache_gc_idle_delay=10s` und `--experimental_disk_cache_gc_max_age=30d`). Die Sammlung läuft nur in einem dauerhaften, untätigen Server (gemessen mit Bazel 8.4.2: unter `--batch` lief sie nie), deshalb nutzt der Adapter für Builds kein `--batch`. Der Repository-Contents-Cache behält Einträge 3 Tage. Modulkatalog und Repository-Cache liegen in `<dependencies>/bazel/modules`; Builds laufen mit `--repository_disable_download` und laden keine Module nach.
- **Gemeinsame Output-Base.** `--output_base` ist `<products>/bazel/outputs/server/<erste 16 Hexziffern von sha256(Workspace-Verzeichnis)>`: ein Server je generiertem Workspace-Verzeichnis, geteilt von Build und allen `bazel run` kontinuierlicher Tasks dieser Auswahl; er endet nach 120 Sekunden Leerlauf. Der Disk-Cache wird von allen Auswahlen geteilt, deshalb nutzt eine zweite Auswahl die Ergebnisse der ersten.
- **Remote-Cache.** Wird aus dem werkzeugneutralen Remote-Cache-Vertrag erzeugt (Abschnitt "Remote-Cache"): `--remote_cache`, `--remote_instance_name`, `--[no]remote_upload_local_results`, `--[no]remote_cache_compression`, `--remote_download_outputs`, `--remote_timeout` und `--remote_retries`, und nichts, solange kein Endpunkt gesetzt ist. `--skip-remote-cache` lässt ihn für einen Aufruf weg, `--skip-cache` ergänzt `--noremote_accept_cached`. Der Adapter stellt Task-Snapshots aus `bazel-bin` wieder her, deshalb wird `minimal` abgelehnt. Das Zugriffstoken steht nie in einem Flag: ein Credential-Helper im `tmp`-Ordner der Produkte kennt nur den Variablennamen, das Token reist in der Umgebung des Bazel-Clients (`--remote_header` würde es in Bazels `java.log` und den Build-Event-Stream kopieren).
- **Cache-Operationen.** `repo --tool=bazel cache status` zählt die Dateien der Ordner `ac` und `cas` des Disk-Caches und ergänzt die aufgezeichnete Build-Aktivität (Builds, Actions, ausgeführt, Cache-Treffer), die jeder Build aus seinem Build-Event-Stream in `<products>/bazel/outputs/server/metrics.json` fortschreibt. `cache clear` stoppt die dauerhaften Server (durch Entfernen ihrer pid-Datei), entfernt ihre Output-Bases (Bazels lokalen Action-Cache) und leert den Disk-Cache, sodass der nächste Build ein Fehltreffer ist; Bazel-Binary, Module und Toolchains bleiben.
- **Speicher.** Bazel braucht die Partitionen tools, dependencies und products (`bazel/bin`, `bazel/install`; `bazel/modules`; `bazel/workspaces`, `bazel/outputs`, `bazel/actions`). `repo --tool=bazel reset` verwirft den Graphen und leert `bazel/actions`, `bazel/outputs` (mit den Server-Output-Bases und dem Aktivitätsbuch) und `bazel/workspaces`; es stoppt einen laufenden Bazel-Server nicht, führe es nur aus, wenn kein Build läuft (`cache clear` stoppt sie).

Tests mit `SEMIO_TEST_BAZEL_BINARY` bestanden am 2026-10-19 (der Sandbox-Build der Storage-Suite mit Disk-Cache-Treffer nach `bazel clean`, der Emoji-Label-Test der Actions-Suite); am 2026-10-20 bestanden auf dem Live-Baum unter einer ausgestellten Prozesshülle mit dem echten Binary die Suiten `📥️sources` (10 Tests), `📥️workspace` (5), `📥️actions` (12), `📥️fingerprint` (2) und `📥️closure` (9). ### Remote-Cache

Ein schema-erster Vertrag (`🏗️build/🏃️execution/🧬️schema/🌐️remote-cache.json`, Standardwerte in `🏗️build/🔣️policy.json`), zwei Umsetzungen und ein Server. Ohne Endpunkt ist der Remote-Cache aus. Der Vertrag enthält kein Geheimnis.

| Variable | Feld | Standard |
|---|---|---|
| `SEMIO_REMOTE_CACHE_ENDPOINT` | `endpoint`: `http://`- oder `https://`-Ursprung | keiner (aus) |
| `SEMIO_REMOTE_CACHE_INSTANCE` | `instance`: Namensraum, erstes URL-Pfadsegment | `main` |
| `SEMIO_REMOTE_CACHE_ACCESS` | `access`: `read-only` oder `read-write` | `read-only` |
| `SEMIO_REMOTE_CACHE_UPLOAD` | `upload`: lokale Ergebnisse hochladen (wirkt nur mit `read-write`) | `true` |
| `SEMIO_REMOTE_CACHE_COMPRESSION` | `compression` | `true` |
| `SEMIO_REMOTE_CACHE_DOWNLOAD` | `download`: `toplevel` oder `all` | `toplevel` |
| `SEMIO_REMOTE_CACHE_TIMEOUT_SECONDS`, `SEMIO_REMOTE_CACHE_RETRIES` | `timeoutSeconds` (1-600), `retries` (0-10) | `30`, `3` |
| `SEMIO_REMOTE_CACHE_TOKEN_ENVIRONMENT` | `auth.tokenEnvironment`: Name der Variable mit dem Bearer-Token | `SEMIO_REMOTE_CACHE_TOKEN` |

- **Bazel** setzt jedes Feld in die oben genannten Flags um und reicht das Token über einen auf den Cache-Host begrenzten Credential-Helper durch. **Nx** setzt `endpoint/instance` in `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` und das Token in `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN` um; Nx 23 kennt keinen Schalter für Kompression, Download-Modus, Zeitlimit, Wiederholungen oder das Zurückhalten von Uploads, deshalb setzt ein Nur-Lese-Token auf dem Server read-only durch. `bun repo cache remote status [--tool=nx|bazel]` zeigt den aufgelösten Vertrag, die Umsetzung samt nicht unterstützter Felder und eine lesende Probe der Route des Werkzeugs.
- **Server.** `bun repo cache serve [--port <n>] [--host <Adresse>] [--directory <Pfad>] [--max-bytes <n>]` spricht Bazels HTTP-Cache-Protokoll (`GET`, `HEAD`, `PUT` auf `/ac/<sha256>` und `/cas/<sha256>`, Blobs gegen ihren Digest geprüft, 400 bei Abweichung) und die Nx-Self-Hosted-Cache-API (`GET`, `PUT` auf `/v1/cache/<hash>`, 409 beim Überschreiben, 401 mit `text/plain`, 403 für ein schreibendes Lese-Token), jeweils mit optionalem Präfix `/<instance>`. Bearer-Tokens stammen aus `SEMIO_REMOTE_CACHE_SERVER_READ_TOKEN` und `SEMIO_REMOTE_CACHE_SERVER_WRITE_TOKEN`; ohne Token lauscht er nur auf Loopback. Der Speicher (`.cache/remote-cache`, standardmäßig 4 GiB, 512 MiB je Eintrag, 30 Tage Leerlauf) schreibt atomar, reserviert Bytes vor dem Streamen, entfernt die am längsten ungenutzten Einträge und meldet beim Einlesen den Fortschritt; Abbrechen des Befehls beendet den Server. Das Dashboard-Werkzeug `build-cache-serve` startet ihn auf Port 6090.
- **Tests.** `🏗️build/🌐️remote-cache/🧪️tests` spielt die JSON-Fixtures (Vertrag, Umsetzungen, Leitungsszenarien, Verdrängung) gegen Ajv, Pythons `re`, `http.client` und `hashlib` ab; mit `SEMIO_TEST_BAZEL_BINARY` baut ein echtes Bazel gegen den Server und trifft nach `bazel clean` den Remote-Cache, mit `SEMIO_TEST_NX_BIN` (eine unveränderte Nx-23-Installation; das gepatchte Nx des Repositorys läuft nicht in einem Scratch-Workspace) tut ein echtes Nx dasselbe.

### Befehlsregister

Das Befehlsregister ist die Befehlsoberfläche der Entwickler: Jeder ausführbare Befehl wird einmal neben seinem Quelltext deklariert und von Entwicklern im Dashboard (`repo dashboard`, **New Task**) gewählt; Agenten und Automation verwenden die werkzeugneutrale `repo`-Binärdatei und nie das Dashboard; keine IDE-Launch-, Task- oder Solution-Datei registriert Befehle (im Baum existiert kein Editor-Konfigurationsverzeichnis). `AGENTS.md` nennt die menschliche Oberfläche `repo dashboard`; in diesem Baum startet sie mit `repo dashboard`, dem Root-Paket-Skript für `repo run @semio-tech/repo-dashboard-rs:run --output=stream` (`dashboard:install` baut sie neu). `dashboard` ist keine Operation des Katalogs (`📚️library/🏗️build/⚙️operations/🔣️catalog.json`): Der Build-Einstieg bildet ein `run` der Targets `run`, `daemon` und `preferences` des Projekts `@semio-tech/repo-dashboard-rs` (`dashboardInvocation` in `📚️library/⚡️caching/🚀️bootstrap/🎛️dashboard/📦️installation`; `--output=stream` und `--skip-cache` entfallen) auf die Argumente des installierten nativen Clients ab, den `launchDashboard` unter der Compiler-Zulassung des Aufrufers startet, und führt jedes andere Target sowie jeden Aufruf mit `--graph`, `--batch`, `--parallel` oder `--exclude-dependencies` über das gewählte Werkzeug aus. Builds, Tests und Prüfungen durch Agenten und Automation laufen über `repo …`; ein Agent startet das Dashboard nie. Das Register besteht aus Daten: Die `📋️project.json` an der Wurzel enthält `metadata.semio.dashboard` mit `parameters`, `tools`, `compounds` und `groups`, geprüft gegen das Schema `🔨️modules/🎛️dashboard/🧬️schema/🎮️registry/🔣️.json` (`ProjectManifest`); andere Projekte deklarieren typisierte Steuerelemente an ihren Targets, Playground-Steuerelemente stammen aus Crate-Manifesten. Der [Dashboard-Leitfaden](🔨️modules/🎛️dashboard/README.md#-daily-work) führt die täglichen Zeilen auf; der Build-Teil ist:

| Tool-ID (`tool:workspace/…`) | Führt aus | Hinweise |
|---|---|---|
| `build-task`, `run-targets`, `build-affected`, `build-watch` | `repo run`, `run-many`, `affected`, `watch` | `run-targets` und `build-affected` haben wie `build-task` ein Flag `dry-run` (`--dry-run`). |
| `build-exec` | `repo exec --projects={projects} --dry-run={dry-run} --` plus die Befehlswörter in **Arguments** | `dry-run` ist eine Auswahl (`false` Standard, `true`) innerhalb der Wörter vor `--`, weil Argumente nach `--` zum Kindprogramm gehören; `--dry-run=false` ist wirkungslos. `bun-test`, `run-script` und `native-cargo` bieten dieselbe Auswahl. |
| `build-cache-status`, `build-cache-clear` | `repo cache status`, `cache clear` | Die Achse `build-tool` wählt, wessen Cache. |
| `build-preflight`, `build-deps-sync`, `build-deps-lock` | `repo preflight`, `dependencies sync --all`, `dependencies lock --all` | Host-Prüfung; Installation und Sperre für alle Eigentümer (`--scope <owner>` bleibt auf der Kommandozeile). |
| `build-graph`, `build-projects`, `build-targets`, `build-project`, `build-help`, `build-reset`, `build-tools`, `cargo` | `graph`, `show …`, `--help`, `reset`, `tools setup`, `repo cargo` | |

Globale Achsen (Parameter) des Wurzelregisters: `build-tool` (`SEMIO_BUILD_TOOL=nx|bazel`), `cache` (`use`, `skip-local` = `--skip-cache`, `skip-all` = `--skip-cache --skip-remote-cache`), `build-mode=ship` (Release-Build, beide Caches übersprungen), `dependencies` (`--exclude-dependencies`), `test-level`, `nextest-output`, `cargo-jobs`, `build-budget`. `build-tool` wird bei jedem Verb angeboten, das Build-Tasks ausführt, auch bei `publish`, `prepare`, `deploy`, `activate`, `serve`, `reset` und `inspect`; dieselbe Task läuft also im Dashboard unter Nx oder Bazel. Ein Gesetz vergleicht seine Verben mit den Verben des Rust-Registers (`VERBS`) plus dem Rückfall `task` plus `reset` und `inspect`. `cache` wird bei `dev`, `run`, `watch`, `clean`, `reset`, `inspect` und `setup` nicht angeboten, die kontinuierlich sind oder keinen Task-Cache haben. Eine frische native Build-Generation ist ein Registerparameter `generation=fresh` (`SEMIO_NATIVE_BUILD_GENERATION=fresh`) des Play-Targets `build` und des Wurzel-Targets `release`, kombiniert mit `build-mode=ship`.

Befehle des Wurzelskripts (`bun ./📜️script.ts verify …` und ähnliche) werden über Targets geleitet, die `metadata.semio.workspaceCommand` deklarieren: ein Array aus mindestens zwei Wörtern aus `[a-zA-Z0-9-]`, im ganzen Repository eindeutig (zum Beispiel `verify fem-combination-stress`). Eine fehlerhafte oder doppelte Deklaration lässt den Routenlader werfen („Invalid owned command“, „Duplicate owned command“) und bricht jede Route `verify …`; deshalb werden die Deklarationen des ganzen Baums gemeinsam geprüft.

Wähle im Dashboard **New Task** → `@semio-tech/repo-lib:test-dashboard-control`, um das Befehlsregister zu prüfen. Die Prüfung vergleicht das Wurzelregister mit Ajv 2020 und dem eigenen Schema-Compiler, neutrale Eigentümer-Fixtures mit SQLite und den Verben des Rust-Registers sowie Vorschauargumente mit `validateBuildTaskArgumentsV1` und `nxBuildArgumentsV1`. Ausgabe und Ergebnis bleiben an der Task. Agenten und Automation erreichen denselben Eigentümer über `repo run @semio-tech/repo-lib:test-dashboard-control`. Das Target `@semio-tech/repo-dashboard-rs:test-journeys` prüft zusätzlich den installierten nativen Client und tatsächliche Terminalabläufe.

### Script-Einstiege

Befehle, die der Build-Graph als `repo:script` ausführt, beginnen am `📜️script.ts` ihres Moduls. Das Befehlsrouter-Gesetz (`📚️library/🔍️discovery/🛣️ecma-command-routes`) akzeptiert zwei Formen:

- **Router.** Eine Klasse je Befehl, die `BundleScript` erweitert, ein `ScriptRouter`, der sie registriert, und ein Abschluss unter `import.meta.main`. Ein dünner Einstieg behält die Prozessgeburt im Router und reicht die eigenen Argumente weiter: `await receiveScriptProcessInvocation(process.env, original => runScriptMain(router, { invocation: original, argv: ["run"] }))`. Das Programm parst sein eigenes `process.argv`; `argv` nennt nur den registrierten Befehl (`📚️library/⚡️caching/🚀️bootstrap/🔌️nx-plugin/📤️arguments/📜️script.ts`). Der andere akzeptierte Abschluss ist `router.run(process.argv.slice(2))` für Router, die nach der Kommandozeile verteilen.
- **Nackter Einstieg.** `import { runScriptProgram } from "./🟦️.ts"; if (import.meta.main) await runScriptProgram();`, also genau ein argumentloser Aufruf von `runScriptProgram`, aus einem Geschwistermodul `🟦️.ts` importiert, unter `import.meta.main` (`ecmaRouteOwnedProgram`). Er ist für Programme, die ihre Prozessgeburt und ihren Exit-Code selbst besitzen, besonders die Kindprogramme von Tests unter `🧪️tests` und `👷️child` (zum Beispiel `📚️library/⚡️caching/🦀️cargo/📦️units/📥️descriptor/💾️cache/🧪️tests/📦️child/📜️script.ts`).

Ein Router um alles funktioniert nicht: Ein Programm, das seine eigene Geburt mit `receiveScriptProcessInvocation` innerhalb der Geburt des Routers öffnet, kann nach dem Leeren nicht mehr berichten, und `track` in `🧰️framework/🔨️modules/🏃️process/🧭️routing/📥️invocation/🏃️process` kopiert jede fehlschlagende verfolgte Operation in alle Vorfahren-Scopes und schließt deren Zulassung, sodass ein Fehler, den das Programm fängt und meldet, die äußere Geburt trotzdem scheitern lässt (die Lift-Reparatur maß Exit 1 mit dem Kind `custodian/cancel`). Eine verschachtelte Geburt kann nie einen Fehler schlucken, das Programm muss der äußerste Eigentümer sein. Die Router-Lift-Generatoren erzeugen deshalb den nackten Einstieg für Skripte unter `🧪️tests` und `👷️child` und den Router mit Argument-Durchreichung für alle anderen (98 angehobene Skripte am 2026-10-20 repariert: 74 Router, 24 nackt). Noch nicht verifiziert: die Kind-Suiten der angehobenen Skripte unter `repo run`; die Suite `scope` hatte noch vier Rote, das erste aus einer `root-drain`-Zulassung, identisch zur Form vor dem Anheben.

### Build-Owner-Register

`📋️build-owners.json` an der Wurzel führt jedes Modul auf, das ein Build-Manifest besitzt (`owners`), und die Katalog-Provider. Ein Gesetz hält es gleich dem Baum: `bun ./📜️script.ts verify build-owners` (Wurzel-Targets `workspace:verify-build-owners`, gecacht mit `outputs: []`, sowie bloßes `verify`/`workspace:verify`) scheitert mit einem Befund je Abweichung, zum Beispiel `project-without-row`, `cargo-without-row`, `missing-manifest`, `name-mismatch`, `cargo-row-shadows-project`, `missing-native-root` oder `package-stale` (`📚️library/🏗️build/🧬️schema/🧾️owner-consistency.json` nennt alle Arten); `verify build-owners sync` (Target `workspace:verify-build-owners-sync`, ungecacht) repariert das Mechanische (entfernt Zeilen verschwundener Module (nur wenn kein Manifest existiert und git am Pfad nichts verfolgt; die Manifeste unter den `nativeRoots` der Zeile werden als eigene Zeilen neu eingetragen), verschiebt ein bewegtes Modul, benennt ein umbenanntes Projekt um, übergibt eine Cargo-Zeile an eine `📋️project.json`, fügt Zeilen für neue Manifeste in Byte-Reihenfolge ein) und scheitert danach an dem, was bleibt: Befunden, die einen Autor brauchen (Katalog-Provider), und Zeilen, deren Pfade git noch verfolgt, obwohl die Dateien fehlen (eine laufende gleichzeitige Verschiebung). Zeilen, deren Manifest unter einem git-ignorierten Pfad liegt, sind ausgenommen, damit ein frischer Klon das Gesetz nicht auslöst. Die Gerüst-Schreiber (Crate-Carve, Subset-Gerüst, Mutationsbaum) rufen denselben Abgleicher mit einem Geltungsbereich auf. Ein angewandter Verschiebeplan gleicht das Register für die berührten Teilbäume ab (`reconcileBuildOwnerRegistry` in `📚️library/🧹️normalization/🎮️command-contract/🔁️workflow/🟦️.ts`); jede andere Verzeichnisverschiebung oder -umbenennung fängt das Gesetz, und `verify build-owners sync` behebt sie. Kern und Fixture-Fälle liegen in `📚️library/🏗️build/🕸️graph/🧾️registry-consistency`; die Registerdatei hält eine Zeile je Modul mit Manifest (am 2026-10-20 gezählt: 3.729 Zeilen), und `bun ./📜️script.ts verify build-owners` gab am 2026-10-19 `passed` aus. ### Cache-Partitionen und Wiederherstellung

Der gesamte Build-Zustand liegt in Partitionen fester Größe unter `.cache/b/<partition>` (git-ignoriert, abgeleitet, löschbar, solange nichts läuft): `d` Abhängigkeiten (8 GiB), `t` Werkzeuge (8 GiB), `g` Graph (4 GiB), `o` Beobachtungen und Diagnose (2 GiB), `p` Produkte (24 GiB), `l` Leases (64 MiB), `n` Nx-Pool (1,5 GiB); die Größen stehen in `📚️library/⚡️caching/💾️storage/🔒️enforcement/📦️budget/🔣️policy.json`. `.cache/b/c` ist das einfache Steuerverzeichnis (kein Image, höchstens 1 MiB; es hält die Lease-Datenbank der Images, `budget.controlDirectory`), die Rust-Partition liegt getrennt unter `.🧬semio/🦑️repo/⚡️cache/rust/fixed` (16 GiB). Unter macOS ist jede Partition ein UDIF-Image mit case-sensitive APFS (`fixed.dmg`, bei `m` eingehängt, daneben der Beleg `image.json`; `ImageProtocol` legt `UDIF` und `Case-sensitive APFS` fest, HFS+ wurde früher ausgeschlossen, weil ihm der atomare Austausch `RENAME_SWAP` fehlt, den Veröffentlichung und Bindung nutzen, hier nicht erneut geprüft), unter Linux ein Verzeichnis ohne Rechte (`fixed.dir`, `v`, `m`, getauscht durch atomares `renameat2(RENAME_EXCHANGE)`), unter Windows ebenfalls ein Verzeichnis (journalisierter Zwei-Phasen-Tausch mit Write-Through statt `renameat2`; Linux und Windows aus dem Quelltext, nicht auf allen Hosts verifiziert). `bun ./📜️script.ts clean` berührt nie eine davon.

**macOS-Volume-Stille.** macOS protokolliert Dateisystemereignisse jedes eingehängten Volumes in `.fseventsd` und indiziert es; auf einem Image, das nur ein Build-Werkzeug beschreibt, füllt das das 63-MiB-Lease-Image und die kleinen Partitionen. Jedes Image trägt deshalb `.fseventsd/no_log` und `.metadata_never_index` (Protokollkonstanten in `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage/🍎️image/🤫️silence/🧬️schema/🔣️.json`). Ein Schreiben nach dem Einhängen genügt nicht: Mit `-owners on` legt macOS `.fseventsd` als `root:staff 0700` mit ACL an, und ein Protokoll wächst, bis das Volume gelöst und neu angehängt wird. Die Images werden deshalb aus einem Seed-Ordner erzeugt (`hdiutil create -format UDRW -srcfolder <seed> -size … -nospotlight` ergibt dasselbe feste Image wie `-type UDIF`, mit von Anfang an benutzereigenen Markern), und `applyNativeImageVolumeSilenceV1` läuft beim Anhängen und erneut, wenn ein schon eingehängtes Image geöffnet wird: Es legt Verzeichnis und Marker an, falls sie fehlen, und räumt Protokolle (reguläre Dateien mit einem Link, benannt mit 16 Hexziffern, in Stapeln zu 64) auf: beim Anhängen alle, beim Öffnen sobald mehr als 8 Dateien oder 1 MiB bleiben. Ein `.fseventsd`, das root gehört oder ein Symlink ist, und nicht reguläre Marker werden mit einer Abhilfe abgelehnt. Ein stilles Volume hat keinen FSEvents-Dienst, die Publikationszeugen behandeln es daher als Volume ohne Dienstdomäne (`observeNativeVolumeEventServiceV1` gibt `null` zurück). Kapazität: APFS fasst 40.960 Bytes weniger als das Image, bei Images über 2 GiB 200 MiB weniger (gemessen an 15 Images von 32 MiB bis 4.095 MiB), deshalb stellt jede Partition `usableBytes` bereit, und bei Partitionen bis 256 MiB muss das logische Limit hineinpassen; darum ist `leases.maximumLogicalBytes` 62.914.560 von 67.108.864. Beobachtet am 2026-10-20: Die Live-Images waren eingehängt, bevor ihre Marker existierten, und macOS protokolliert weiter, bis jede Partition gelöst und neu angehängt wird; nach der Reparatur beim Öffnen hielt `.fseventsd` von `d`, `l` und `g` 3, 5 und 1 Einträge (das Abhängigkeits-Image hatte etwa 200 Protokolle gehalten), und jede Partition hat `.metadata_never_index`. Noch nicht verifiziert: ein frisch erzeugtes Seed-Image durch den ganzen Weg von `tools setup` und die Seed-Erzeugung unter einer anderen macOS-Version.

### 🩹️ Wiederherstellung

Nutze die Dashboard-Task der fehlgeschlagenen Operation. Ihre Ausgabe bewahrt die genaue Ablehnung, Fortschritt und Abbruch. Wiederhole oder stoppe diese Task, ohne andere Entwicklungsarbeit zu beenden. Veröffentlichung und Verzeichnisaustausch werden durch ihre eigene Operation wiederhergestellt. Belege und Absichtsdateien beschreiben dieses Protokoll; sie werden weder verschoben noch bearbeitet.

Bei einem inaktiven macOS-Nx-Cache mit nicht unterstützter Veröffentlichung wählt **New Task → Inaktiven Nx-Cache Zurücksetzen** den festgelegten Eigentümer. Er prüft den kanonischen Nx-Container, tatsächlichen physischen Ausschluss, Kernel-Zuordnungen und vollständige Deskriptorbeobachtungen, bevor er den genauen inaktiven Inhalt entfernt. Eingehängte, belegte, fremde, ersetzte oder unvollständig beobachtete Inhalte werden abgelehnt. Eine dauerhafte aktuelle Rücksetzabsicht erlaubt die Fortsetzung nach einem Abbruch. Die nächste Operation legt den Cache neu an. Diese Aktion hängt keine Images aus, setzt keine beliebigen Partitionen zurück und steht für Linux- und Windows-Verzeichnispartitionen nicht bereit.

Bei knappem Compiler-Speicher nutze Vorschau und Bereinigung über die deklarierten Dashboard-Aktionen. Logisch entfernte Bytes und anschließend gemessener freier physischer Speicher bleiben getrennte Ergebnisse. Die Abhängigkeitssynchronisierung wiederholt eine erkannte Bun-Cache-Link-Ablehnung einmal mit ihrer eigenen kontrollierten Bereinigung. Eine verbleibende Ablehnung bleibt an der Task. Nicht unterstützte Dateisysteme, Berechtigungsfehler, unbekannte Veröffentlichungen und fremde Leser werden beim zuständigen Provider behoben. Cache-Wiederherstellung erfordert kein manuelles Aushängen, erzwungenes Unmounten, Ändern von Belegen oder Löschen von Cache-Verzeichnissen.

### Developer Dashboard

Der [tägliche Dashboard-Ablauf](🔨️modules/🎛️dashboard/README.md#-daily-work) ist der Einstieg für Entwickler. Wähle **New Task**, suche die Operation und ihren Eigentümer und fülle dann das typisierte Formular aus. Die Vorschau zeigt Argumente und Umgebung vor **Start**. Ausgabe, Fortschritt, Bereitschaft, Quellnavigation, interaktives Debugging, Abbruch und Neustart bleiben an dieser Task.

Der Abschnitt Befehlsregister des Build-Kapitels führt die Build-Werkzeuge, die globalen Achsen (`build-tool`, `cache`, `build-mode`) und die Trockenlauf-Formen auf. Deklariere ausführbare Operationen neben ihrem Quelltext: Build-Targets in `📋️project.json`, typisierte Steuerelemente in `metadata.semio.dashboard` und selbst geschriebene Ticket-Werkzeuge in der `🎮️commands.json` des Tickets. Playground-Steuerelemente stammen aus `[[package.metadata.semio.playground]]` in Crate-Manifesten; native Crate-Targets stammen aus `📋️build-owners.json` und dem neutralen Build-Graphen. Parameterauswahl, Umgebungen, Bereitschaft und Compound-Mitgliedschaft gehören zu diesen Eigentümer-Deklarationen. Das Dashboard enthält Quellnavigation, Bearbeitung und alle Entwicklungsoperationen. Starte es mit `repo dashboard`. Menschliche Entwickler nutzen das Dashboard für jeden Befehl, Agenten und Automation nutzen `repo …`, und keine Editor- oder IDE-Konfiguration registriert oder startet Befehle.

### Go-Layout

Go-Code folgt dem kanonischen Taxonomie-Layout statt Dateien in der Paketwurzel:

- Ein Member ist ein Verzeichnis mit genau einem `🐹️.go`-Blatt: `<module>/📦️packages/🐹️go/<member>/🐹️.go`. Der Member-Name ist in `📚️library/🔣️taxonomy.json` registriert (`members-of-members-of-members-of-modules`).
- White-Box-Tests sind Fälle am sprachneutralen Eigentümer: `<module>/🧪️tests/<case>/🐹️.go`, in das Paket aufgenommen, wenn die Paketklausel die des Moduls oder `<package>_test` ist. Black-Box-Adapter werden nie aufgenommen.
- Weil die Dateien nicht in der Paketwurzel liegen, sehen einfaches `go test` und `go list` die Member nicht. Führe Go über das Paket-`📜️script.ts` (`runCanonicalGoTests`) oder `repo run <project>:test` aus, die die zusammengeführte Quell-Überlagerung übergeben.
