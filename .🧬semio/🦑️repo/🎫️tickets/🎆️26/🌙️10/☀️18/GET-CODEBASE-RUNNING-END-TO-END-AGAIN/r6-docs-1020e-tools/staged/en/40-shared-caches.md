### 🗃️ Shared caches and budgets

Caches are shared where sharing is safe and private where a second writer would corrupt or serialize the first. Every shared cache is content addressed (a key is the hash of its inputs, an entry is written to a temporary name and renamed into place), so two agents that compute the same key at the same time at worst compute it twice.

| Cache | Shared by | Bounded by | Cleared or collected by |
|---|---|---|---|
| Dependency generations (`.cache/b/d`, `j/<key>`) | every command; a generation is immutable once its ready marker exists | partition `d`, 8 GiB; a sync retires generations that no plan and no binding names | `repo dependencies sync`; the retention rule below |
| Nx task cache (`nx/artifacts` in the rust partition) | all agents (concurrent writers of one hash are safe) | {{^cache-ledger::Nx's own default of 10 percent of the file system::3 GiB, declared in `nx.json` as `maxCacheSize`}} | `repo cache clear` |
| Bazel disk cache (`.cache/b/p/m/bazel/actions`) | all selections and all sessions | 40 percent of the products budget; entries older than 30 days dropped | `repo cache clear` |
| Bazel output bases | {{^bazel-sessions::one per selection (a second command in the same base waits for the first)::one per session slot (`s0`, `s1`, ...; a slot has one holder)}} | {{^bazel-sessions::no bound on their number::at most 6 build slots and 4 service slots, 6 generated packages per slot, 7 days}} | {{^bazel-sessions::`repo cache clear`::`repo cache clear` and the collector of slots}} |
| Cargo build state | {{^cargo-lanes::the shared store `m/b/p`, `m/t/p` of the rust partition, one writer at a time::a private lane per agent (`m/u/l/<id>`) plus one content-addressed unit cache (`m/u`) for all}} | the rust partition, 16 GiB | {{^cargo-lanes::the cleaner of `repo cargo`::idle lanes after 24 hours, then by recency when less than 10 percent is free}} |
| Project graph (`.cache/b/g`) | every command | partition `g`, 4 GiB | `repo reset` |
| Test sandboxes | none (one per run, below the OS temporary directory) | removed on disposal; dead owners are reclaimed | the next sandbox creation |
| Remote cache | other machines and users | the server's own bound | the server |

The partitions and their capacities are described in Cache partitions.

**Cache ledger** ({{@cache-ledger}}). {{?cache-ledger::::The commands below belong to the staged set. }}Every cache byte has exactly one home: a fixed partition, a nested area inside a partition with its own budget (`nx-artifacts` 3 GiB, `cargo-store` the remainder of the rust partition, `bazel-actions` 40 percent of products), or a budgeted area of a declared loose root (`repository` capped at 20 GiB, `native` at 256 MiB). Anything else is `retired` (a one-time rule in the ledger, removed after its quiet time; dead installs of old tools, the old lease, closure and preparation roots) or `undeclared` (no declared writer; collected after 14 days without use, native after 7). The runtime door `repoCacheDirectory` refuses an undeclared first segment with an English or German message, and a law scans the tracked sources for `⚡️cache` literals, so a new cache needs a ledger entry first.

```bash
repo cache status
repo cache gc --dry-run
repo cache gc --area=<id>,<id>
repo cache status --tasks --tool=bazel
```

- **`cache status`** prints the ledger: each home, its budget, its use (`at least` when the entry cap of the walk was hit) and what is collectable; it takes no lease, so it works while the dependency image is held. {{?cache-ledger::::Today `repo cache status` prints the task cache of the selected tool; with the ledger that report is `repo cache status --tasks`. }}`--json` prints JSON and `--lang=en|de` selects the language.
- **`cache gc` collects by default.** Always run `--dry-run` first and read the list: it proposes whole dead installs below `.🧬semio/🦑️repo/⚡️cache/tools` (about 25 GiB) and age-eligible undeclared directories, and you must check that none of them is a live cache of a product.
- **Lock-aware.** Collection re-measures every unit right before removing it and never removes a unit that is a lease database whose exclusive transaction cannot be taken without waiting, that sits in a queue with a ticket of a living process, that lies in an area whose declared lease cannot be taken immediately, that was touched within the area's quiet time or that changed after the scan. Hard links count once and links are never followed. Removal is batched, cancellable (exit code 130) and reports progress. Areas that their own tool manages (Nx, Cargo, Bazel, the dashboard) are reported, not collected; test evidence is delegated to the same pruning call as `cache-prune`.
- **Not verified.** A live run, the `statfs` path of a mounted image (tests cover detached, directory and absent states), Linux, Windows, and Nx honouring `maxCacheSize` at run time.

**Dependency generations** ({{@deps-concurrent}}). {{^deps-concurrent::Today a cold install takes the dependency image exclusively for the whole sync (more than an hour on a cold machine), and every command that needs a shared lease on that image queues behind it::A writer runs in phases and holds only what each phase needs}}. {{?deps-concurrent::::The rest of this paragraph describes the staged set. }}`build` installs fresh scopes into new generations under a shared image lease plus one builder lease; `publish` switches the bindings and replaces the per-scope pointer atomically (the only window in which readers are refused, 400 ms in the test, waiting at most 15 minutes for readers to drain); `collect` removes unreferenced generations through a tombstone rename. Readers hold the bindings gate and a pin on the generation they read. A second `ensure` that finds the builder busy rechecks readiness every 5 s and returns as soon as the build made it unnecessary; four concurrent ensures start one build. Retention: an unreferenced generation is kept 6 hours after it was retired, the newest retired generation of a scope 24 hours (rollback target), both shrink to 0 while the image has less than 25 percent free, at most 16 are removed per run and a pinned generation never. One manifest edit builds one scope. Maintenance and admission ({{@deps-concurrent-admission}}): collection holds only the shared image, with no build lease, no bindings gate and no whole-image hold, so a running build never blocks it; a generation goes only if no pointer's current one, no live binding and no pin holds it and the retention rule is due (pin, tombstone rename, delete), and the builder pins every plan generation before it creates or resumes it, which is what makes lease-free collection safe. Before every fresh scope the expected size (the size recorded in that scope's pointer, else the largest recorded, else 1 GiB, times 1.15) must fit the free bytes; if it does not, collection reclaims at once (with the pressure grace, which also frees rollback targets), the size is measured again, and if it still does not fit the sync refuses before any install with an English or German diagnostic (`admissionRefused`); published generations stay untouched and the next `ensure` resumes with the scopes already built. {{?deps-concurrent-admission::::Until then a scope larger than the free space fails with `ENOSPC` without touching readers. }}Open: writing under shared custody has not run on a real image, whole-image maintenance that needs quiescence (reset, layout) still waits for a build, and there is no command yet to collect dependency generations by hand.

**In CI** ({{@ci}}). {{?ci::::The following describes the staged workflow. }}`.github/workflows/build-system.yml` is built around one value, `BUILD_TOOL` (default `bazel`; the dispatch input `tool` switches to `nx`), and every build step is a `bun repo` call that takes the tool from `--tool="$BUILD_TOOL"`: no step names an implementation, an installer, a flag or a cache path. The jobs are `plan` (the `affected` range of the pull request, push or dispatch), `smoke` (Linux, macOS and Windows: zero-touch start, `tools setup`, `dependencies sync --all` and a cache proof that stores once and serves the second run with the remote cache skipped), `affected` (builds and tests only the changed projects and their dependents, reports the hit rate and uploads the JUnit XML of every executed test) and `parity` (both tools select the same tasks for the range). The shared remote cache is configured only by repository settings: the variable `SEMIO_REMOTE_CACHE_ENDPOINT` (an `http(s)` origin of `repo remote-cache serve` or any Bazel HTTP cache that also speaks the Nx cache API), the optional variable `SEMIO_REMOTE_CACHE_INSTANCE` and the secrets `SEMIO_REMOTE_CACHE_READ_TOKEN` and `SEMIO_REMOTE_CACHE_WRITE_TOKEN`; pull requests, forks and dispatches get read-only access without upload and the read token, only a push to the default branch gets `read-write` with upload and the write token. Without an endpoint the local task cache directory travels through the GitHub cache (key `disk-<tool>-<os>-<arch>-<sha>`, restored always, saved only by default-branch pushes). After every Bazel `test` step the adapter exports the `test.xml` of each label to the directory named by `SEMIO_BUILD_TEST_RESULTS_DIR`. The workflow has not run yet; likely first failures are `preflight` and `tools setup` on the Linux and Windows runners, and a core change selects almost every project (hours on a cold first run).

**Across machines.** The remote cache is the cross-machine layer (see Caching model and Remote cache). Hermetic actions have host-independent keys; the keys of today's host-state tasks contain the Bun path and the checkout root, so a hit across machines needs the same user and checkout path. The Cargo unit cache and the TypeScript declaration store are local to a machine; a remote layer for them is not defined.
