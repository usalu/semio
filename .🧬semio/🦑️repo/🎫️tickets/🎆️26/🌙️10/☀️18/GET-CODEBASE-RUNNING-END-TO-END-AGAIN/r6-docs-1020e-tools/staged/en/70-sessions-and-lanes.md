### 🧵️ Sessions: Bazel slots, Cargo lanes and Nx pools

Each tool had one place where two agents in one folder serialized. This section says what happens today and what the staged sets change; each paragraph carries its state.

**Bazel server slots** ({{@bazel-sessions}}). {{^bazel-sessions::Bazel keeps one output base per selection and one server per output base. Two commands that share a server (the same selection, `affected`, a continuous task and a build) run one after the other, and Bazel prints `Another command (pid=N) is running. Waiting for it to complete on the server`; measured, two builds of different targets in one output base took 11.4 s instead of 5.3 s. Every selection also leaves an output base behind (an execroot, external links and a JVM of up to 2 GB heap), without a bound on their number, and one global restore lease serializes the restore of outputs into the checkout.::A session claims one slot `s0`, `s1`, ... with an exclusive lease; a slot owns one short output base and the generated packages of its selections, and there is exactly one holder per slot, so a server lock wait cannot happen.}}

- **Slots.** {{?bazel-sessions::::The rest of this list describes the staged set. }}The number of build slots K comes from the host budget: K = clamp(floor((memory minus floor) times 30 percent divided by the resident size of a server), 1 to 6) and at most cores divided by 2; on a 32 GB host with 10 cores that is 3 (16 GB: 1, 128 GB: 6). `SEMIO_BAZEL_SERVERS=<n>` (1 to 99; anything else is refused) overrides it, and the server heap comes from the plan instead of a literal. A session started inside a Bazel action gets 4 overflow slots, so it never waits for the slot its parent holds.
- **Service slots.** A selection in which any task is `continuous` (a dev server, `serve`) holds a service slot `d0`, `d1`, ... for its lifetime (default 4, `SEMIO_BAZEL_SERVICES=<n>`), with its own fair queue; every other selection, including each rebuild cycle of `watch`, is a build, so a queue of waiting dev servers never delays a build and a running service is never rebuilt over. After the launch the server idles out after 120 s, so a pinned dev server costs a slot name and an output base on disk, not a JVM.
- **Affinity and waiting.** A slot remembers its last selection; a session prefers the slot whose last selection it is, then a slot that keeps the package, then a never-used slot, then the least recently used, so an edit-run-edit loop keeps its warm server. When every slot is busy the head of a fair queue polls every 250 ms and prints `[bazel] all 3 Bazel server slots are in use; waiting for one (12 s)` every 5 s (English or German); it honours cancellation. A waiting session holds no store lease: the order is capacity, then slot, then storage.
- **Shared layers.** The disk cache, the repository cache and a new repository contents cache (`<products>/bazel/contents`, one fetch of every external repository for all output bases) are shared by all slots, and action keys do not depend on the output base or the package path (a fresh slot rebuilt the same content with one disk cache hit and no spawn). Restores into the checkout lock the tree they write (`bazel-restore:<path>`, ancestors shared) instead of the whole checkout.
- **Measured** with real Bazel 8.4.2 and three slots: three sessions on three disjoint targets (4 s action each) took 13.3 s and 12.7 s against 35.4 s and 36.5 s summed; a fourth session in a fresh slot had 0 spawns; with three service sessions pinned the builds took 15.2 s; the control (two commands forced into one output base) showed the lock wait. Not verified: Windows and Linux hosts, three servers on the real 134k-target graphs, a real `watch` or `serve` end to end.

**Cargo lanes and the unit cache** ({{@cargo-lanes}}). {{^cargo-lanes::Every `repo cargo` holds the exclusive lease `repo:compiler-writer:<image root>` for its whole compile, so two agents compiling different crates run one after the other and a long compile window blocks everybody. Every run also holds the Cargo registry lease shared for its whole duration, so one pending fetch waits for all running compiles and blocks every later one; and it re-admits every workspace unit (about 4,300 durable journal transactions per run).::A lane is the private target and build directory of one agent, `m/u/l/<id>/{t,b,m,v}`, so no two Cargo processes ever share a build directory.}}

- **Lanes.** {{?cargo-lanes::::The rest of this list describes the staged set. }}The lane id is `SEMIO_CARGO_LANE`, else derived from the nearest agent-client ancestor process (claude, codex, cursor, windsurf, copilot, antigravity, droid, kiro: one lane per agent session), else `d`. A busy lane overflows into `<id>1` to `<id>31`, which start empty and fill from the unit cache. `--store=shared` means "lane plus shared unit cache"; `--store=isolated` is unchanged. All lanes live inside the issued rust image and are bounded, so the 926 GB of private targets cannot recur. The launcher creates the directories itself and `.cargo/config.toml` names the default lane.
- **Unit cache.** Cargo runs the repository's rustc wrapper, which keys each unit by the toolchain, the normalised command line, the SHA-256 of the root source and of every extern artifact, and then verifies the dependency file rustc wrote (every file it read, by content). A hit restores the outputs by reflink where the file system supports it (APFS, btrfs, XFS; a real copy elsewhere) and replays rustc's JSON messages; a miss compiles once, publishes content-addressed objects and the entry last. Units of the packages selected with `-p` keep `-C incremental` in the lane and are never published.
- **No deadlock, bounded concurrency.** The first process that misses a unit claims its key; the others wait for the finished entry (bounded to 30 minutes, a dead holder is replaced). Host-wide compile slots (`SEMIO_UNIT_CACHE_SLOTS`, default the core count) are served first in first out; the lock order is claim, slot, rustc. The writer custody of the image is shared and escalates to exclusive only to recover missing headroom; registry fetches coalesce per request; the admission result of an unchanged unit is remembered under stamps.
- **Disk.** Idle lanes (24 h) go first; with less than 10 percent of the image free, incremental sets, then lanes, then cache objects are removed, oldest first; the shares are objects 25, lanes 20 and incremental 10 percent, live lanes are never touched. The launcher runs this at most every 10 minutes after a lane is released.
- **Build scripts and component passes** ({{@cargo-buildscript}}). {{^cargo-buildscript::Cargo gives no hook around a build script run, so every build script reruns in every new lane (its compile is a cache hit, its execution is Cargo's), and the per-generation component passes keep their own generation directories and do not use the cache::The compiled build script is replaced by a stand-in that keys a run by the SHA-256 of the real executable, the toolchain, its arguments and Cargo's per-package, feature, cfg, target, rustflags and `DEP_*` variables; a hit writes the recorded `OUT_DIR` and replays the recorded `cargo:` lines and warnings without starting the script, a miss runs it once across all lanes and records `OUT_DIR`, both streams and the facts (every `rerun-if-changed` path, every `rerun-if-env-changed` value, the package tree, with `*.rs` ignored when the script declares inputs). A script whose `OUT_DIR` holds links or a binary that embeds the lane path, an output over 256 MiB or a package over 4,096 files runs normally; the stand-in needs a POSIX host, and the launcher exports `SEMIO_UNIT_CACHE_BUILD_SCRIPTS=on`. Component passes (the per-generation builds) use the same wrapper chain: a hit tells the scheduler broker a `cached` unit with the recorded peak memory and CPU, so the unit list, the critical path and the provenance reports stay complete and the scheduling history ignores cached units}}. {{?cargo-buildscript::::Measured on the 26-crate workspace: 8 distinct scripts ran once for three parallel sessions and the fourth session started none (7.5 s down to 4.8 s). Not verified: a real generation build (it needs the compile window).}}
- **Measured** on a 26-crate wasm workspace with three concurrent sessions: 32 distinct units compiled once instead of about 70, and a fourth session was served 32 of 32 from the cache; the wall time stays dominated by build scripts. Limits: proc-macros that read files without `tracked_path` can serve a stale hit, Windows reports no process ancestry (lane `d` with overflow lanes), reflink falls back to copying on ext4 and NTFS. The deadlock of many Cargo processes on one fine-grain-locked build directory (12 observed) was not reproduced with three; it is removed by construction because no two processes share a directory.

**Nx** ({{@nx-generation}}). {{^nx-generation::A pinned run (`run`, `run-many`, `exec`) rebuilds the whole Nx project graph on every invocation (3.5 to 6 minutes, 158 MB) even when the finished graph exists. The namespace pool lease is taken exclusively for every namespace acquisition and, inside it, the roster is inventoried twice, a blocking shared lease is taken and idle namespaces are evicted; a cache put blocks every restore of every agent.::A generation receipt binds the three graph files of the digest namespace to the graph digest, the plugin implementation, the Nx tooling and the identity files; when it holds, `NX_FORCE_REUSE_CACHED_GRAPH=true` and Nx re-reads the workspace files but not the graph.}} {{?nx-generation::::The remaining sentences describe the staged set. }}Measured on a stock Nx graph of 2,500 projects: 6 to 7 s cold, 0.7 to 1.5 s with the receipt (expected on the live tree: about 24 s to the first task instead of 210 to 350 s). The pool follows the order namespace, then pool: attaching an existing namespace takes no pool, a birth is a short pass that only try-locks the namespace, and eviction runs outside the pool under its own queue. All users hold the fixed cache shared, so a put no longer blocks restores. Two concurrent stock Nx runs over the same 50 hashes, then a put of 150 and a restore of 50, had no failures. Open: the graph file copy of a publication still holds the pool. Daemon policy ({{@nx-daemons}}): finite daemons (`run`) are capped at the smaller of 2 and a quarter of the host memory divided by 2 GiB, watch daemons at 6 (`SEMIO_NX_DAEMONS=<finite>[,<watch>]`, 0 turns them off, at most 16); every daemon holds a numbered slot lease `nx:daemon-slot:<root>:<kind>:<k>` for its whole life and refuses to start when its family is full; a run reuses the live daemon of its namespace, is admitted while fewer than the cap are live, and otherwise runs with `NX_DAEMON=false` (graph from the receipt, plain hashing); an explicit `NX_DAEMON` of the caller wins; finite daemons drain after `SEMIO_NX_DAEMON_IDLE_MS` (default 10 minutes) without an open request. Put slots ({{@nx-put-slots}}): puts no longer take the exclusive compiler-writer custody; they run under shared custody inside one of 4 put slots (`SEMIO_NX_PUT_SLOTS`, 1 to 16) behind a first-in-first-out gate, with the headroom measured as free space minus the maximum artifact size of every other slot in use, so concurrent puts cannot overcommit the image, and they degrade to one at a time when it is tight; the put slots need the shared writer custody of the Cargo set.
