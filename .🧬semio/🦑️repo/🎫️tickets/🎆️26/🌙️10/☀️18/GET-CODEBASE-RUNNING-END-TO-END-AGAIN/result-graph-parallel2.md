## 1. Design (why it differs from the staged round 1/2)

The old sets made the workers produce *sealed records* and facts and made the parent replay them (round 1: parent keeps 100-150 ms per project) or made the workers write into the parent's custody (round 2: the audit BLOCKERs). New design: **the farm only pre-populates the record store, the parent then reads the records exactly like a warm run.**

- A worker runs the REAL project inference (`observeProjectInferenceV1`, same key, same observation scope as the parent) with the graph directories redirected to a **private staging directory of its own** (`withBuildGraphStagingV1`, ordinary path, no writer custody, no quota, nothing shared). It answers only the names of the leaves it published (record, blocks, receipts, pack files, closures).
- The parent adopts those leaves under its own writer custody (`adoptStagedGraphLeavesV1`, one batched optional publication per project: one durable ledger intent for all leaves), then `observeProjectInferenceV1` finds the record valid (new `prepare` hook: called only when no valid record exists, then the record is looked up once more). Nothing about a project's value or record can depend on the farm; a farm failure only means the parent computes that project itself.
- **Duplicate leaves cannot race by construction**: a worker writes only into its own directory; the single adopter writes a leaf by temporary name + rename; content-addressed leaves (closures, `ob/<sha>.br` blocks) are verified against their names (hash of the content) before they are written, an existing identical leaf is kept (first writer wins), an existing damaged block is repaired by the verified copy, an existing different closure is a hard error; receipts and pack files that stand are the first writer's. The record that names the other leaves is written last, so a failing batch never leaves a dangling record.
- **Capacity**: the worker count is what the host capacity governor grants (`requestBuildFarmCapacityV1`: a fresh request in the fair machine-wide queue beside the invocation's own grant, jobs and megabytes per worker from the governor, upper bound = min(projects/6, cores-1)); the grant is held until the farm is closed and **never released by a timer** (the round-2 1 h lease timer is gone); a grant below two jobs is given back. The request is made lazily, only when the work proves cold (at least 24 projects without a valid record and 25 percent of the projects seen), and the parent keeps inferring itself while the request waits and while workers start, so a warm run asks for nothing.
- **Verified-block memo** (from the old set): a block that this process validated, or that the adoption verified by hash (`adoptVerifiedBlockV1`), is not read, inflated and validated again while its leaf keeps device, inode, mode, links, size and both ns stamps.
- Progress: the existing inference counter plus EN/DE lines (waiting / starting / lost / failed / declined / recycled / finished). Cancellation: the invocation signal closes the pool (children killed, staging removed), jobs settle as lost, the parent stops through the control it already honours. Worker death/timeouts: the job is sent again to a fresh process (2 attempts), more than 8 lost processes disable the pool (announced, the rest runs in the parent); a worker whose record identity (record stamp + module-load authority digest) differs from the parent's disables the pool before any job. A failing project is inferred by the parent, which reproduces the project's own error. These are announced degradations of an accelerator, not compatibility layers; the serial path is the reference implementation.

Reading, honestly: (1) The gain on this host is 1.0-1.9x in steady state and 1.1-1.5x over the whole phase, because the workers (CPU 1.1-1.3 s per project under load; ~0.5 s on a quiet core) share ten saturated cores with 20 other processes. The farm cannot create CPU. (2) The parent still does about 250-300 ms CPU per adopted project under this load (adoption 40 ms, record lookup 61 ms, then twice `retainObservationsV1` of ~13,000 rows, the value image, GC of a growing heap): the rows of a project (13,600, 98 percent shared closure facts, see `graph-perf-profile-1022.md` finding 4) must be materialised in the parent once per project whoever infers them. This bounds the farm at about 2-3x of the serial CPU per project, as the old analysis predicted. (3) Per-project parent cost fell from 0.5-0.7 s (compute + persist + validate + 3.5 ledger publishes) to ~0.25 s; the ledger publishes fell 3.5x (batched per project). (4) Worker boot is 2-3 s, not a problem; the parent infers the first ~24 + ~10 projects itself before the workers answer.

Model for the 3,741 projects of the live generation (clearly a model, not a measurement): quiet 10-core host, 8 workers: workers 3,741 x 0.5 s / 8 = 4 min, parent 3,741 x 0.15-0.25 s = 9-16 min, plus the sequential pre-phases (owner discovery, cargo targets of 2,140 crates, ~3 min): **cold generation about 12-20 min instead of the 2+ h wall of the first v3 build (27 projects/min = pid 29009, log `C/🗑️generated/graph-receipt/live-show-2.log`)**; on a loaded host the CPU the machine can give decides.

## 5. Not proven / open (in order of value)

1. **No real `bun repo` cold generation ran with the farm.** Real writer custody (the batch publication through the real `scope.ledger`/`optionalQuota`, member index per leaf, `requireRepositoryBuildGraphObservationPathV1` on managed paths), the real capacity gate under a running invocation with its 5 GB grant, real cancellation and the captured-source loader (the worker is a plain bun process importing the library by its physical origin like the harness does) are covered only by the harness (ledger + quota modelled with the real SQLite ledger), the capacity law on real gate files and the unit laws. A forced cold generation in a scratch `.cache` root needs a scratch repository root with its own graph partition; I did not find a supported way to point the CLI at one without a full dependency sync, so I did not recreate anything under `.cache/b/g`. First live exercise decides; `SEMIO_GRAPH_WORKERS=0` switches the farm off, `SEMIO_GRAPH_PHASES=1` prints `[graph-farm] {...}` statistics (jobs, queued/worked/boot ms, worker CPU, adoption ms, leaves, lost, failed).
2. Parent floor (F1): materialise the rows of shared blocks once per generation instead of once per project (block-level `retainObservationsV1` / `current` / intern), drop the second `inherit` on the reuse path, parse blocks lazily. This is where the next 2x is; it belongs to the owner of graph-mem.
3. The sequential pre-phases (`discoverNativeBuildOwnersV1` ~9-14 s per 115-300 projects, the cargo-targets loop of 2,140 crates in the parent, a 512 KB project value per cargo crate that is written to a job file) and the dependency pass (`collectImportEdges`, parser records in one thread) are not parallel; the old module farm is not part of this change.
4. Worker repeated work: each worker re-analyses the shared closure files once (~1.1-1.3 s CPU per project at 300 projects, falling with the run length); a parser-record seed from the parent would remove it (old F3).
5. Windows / Linux / devcontainer untested (stdlib `node:child_process`, `node:v8`, `realpathSync(tmpdir())` so macOS `/var` symlinks do not trip the physical ancestry check; the record-last law is skipped on win32).
6. `existing suites`: stamps 17, interned closures 3, record-header 2, host-capacity 9 pass. The laws that need the repo SDK (`📦️projects`, the optional-cache fixture laws; the latter fails for a path-length refusal of the lease directory that predates this work) were not runnable here.
