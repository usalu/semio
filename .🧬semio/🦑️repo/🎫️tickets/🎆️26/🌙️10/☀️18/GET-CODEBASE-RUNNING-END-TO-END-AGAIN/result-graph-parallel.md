## 0. Verdict (read this)

1. **Why one core.** `emojiProjectJsonNodes` runs the project inference as 8 async loops inside ONE JavaScript thread (`projectConcurrencyV1`), so a cold build is one core by construction. Half of its per-project cost is not inference at all but persistence and bookkeeping in the same thread (CPU profile of 40 and 150 real projects): the record is compressed at brotli quality 5 (up to 165 ms per project in the lap timings), every block of the record is read back and validated again to prove that it is present (15-25 percent of the serial time in the profiles), the project value is walked, printed and parsed repeatedly, the facts are retained three times.
2. **Design (staged).** A farm of worker PROCESSES (not threads: a terminated Bun worker thread does not give its memory back, a process does; each worker gets its own heap switch). The parent keeps what needs the writer custody, the workers do the pure work:
   - the worker infers one project in a *detached observation* (the real `inferProjectBodyV1`, now shared by the parent and the worker), under the implementation pin, with all graph storage redirected to a private staging directory;
   - it answers the project value as JSON text, the facts it consumed (each distinct fact once per worker as an identifier, once overall as a body, aliased by a 128-bit content digest the parent broadcasts), the parser records, the files the inference would have published (closure inventories, input-precision and cargo receipts) and a **sealed record**: the exact bytes of the np record (header with the shared blocks named, compressed with the value) and the compressed bytes of the blocks the parent does not hold yet;
   - the parent adopts the staged files under its custody, replays facts and parser records into the project scope that awaits them, and writes the sealed bytes through the unchanged persistence gate (`observeInferenceComputationV1`: consistency, racy rule, freshness check of every fact, quota publication). A seal of another digest or another fact count is ignored and the record is built as before.
   - Every failure is invisible to the caller: a worker that dies, times out, fails a job, reports another implementation revision or cannot get host capacity makes `infer` answer `undefined`, and the parent infers that job itself.
3. **Determinism.** A project's value is a pure function of the project and the sources, so merging by project is independent of the worker count, the completion order and the assignment (law: the real generation engine publishes byte-identical store files and graph for 2 and 5 workers with randomized completion order, section 3). What is NOT deterministic, and never was: which project is *attributed* the process-level first-touch facts (ancestor `lstat` rows of the shared library, the TypeScript compiler load, the policy file): in serial runs they land on the first project that touches them, in farm runs on the first project of each worker. Over all projects the unions of facts are equal (one run: 48,382 = 48,382 rows; another differs by the one policy-file row that serial reads in the parent's pre-state); per project they differ. The closure-inventory `reusable` predicate remains the backstop for those facts.
4. **Memory.** Per worker: the runtime heap switch (`BUN_JSC_forceRAMSize` = 0.75 x the budget, one GC marker, no concurrent GC; node gets `--max-old-space-size`) and a restart after a job when its RSS passes the budget (`SEMIO_GRAPH_WORKER_MB`, default 1,536, minimum 512). The switch alone lowers a 100-project serial run from 3.5 GB to 2.0-2.4 GB at the same wall time. Measured: workers 0.8-1.6 GB, farm parent 1.4-1.9 GB against 2.0-3.6 GB for the serial parent. The graph-mem governor (not applied) bounds the parent's managed heap; the two compose, the loops it wraps wait on the farm.
5. **Sizing** (`planGraphFarmV1`, pure): the smallest of the work (6 projects per worker, minimum 24 projects), the processors left to the workers (cores - 1), the memory the host (50 percent of the cgroup-aware total) and the parent leave them, and 12. `SEMIO_GRAPH_WORKERS=0|auto|N` overrides. The host-capacity budget: the farm asks the machine-wide gate for its workers (`acquireBuildFarmCapacityV1`, a fresh request beside the invocation's own grant, 30 s wait, never a second wait for ever) and uses the jobs it is granted; the request happens only when the first project that is not stored yet needs a worker, so a warm run asks for nothing and starts nothing.
6. **Dependency pass.** `collectImportEdges` parses every source file in one thread when the parser records are missing. The module farm prepares the missing parser records in workers (batches of 64 files, probe of 64 files first so a warm pass pays nothing) and the existing loop then finds every record: 3,534 real files, edges 1,595 and published module facts byte-identical serial / 2 / 4 workers, parent CPU 9.2 s -> 1.1 s.
7. **Independent finding (serial path too).** The verified-block memo alone (a block this process verified is not read, inflated and validated again while its leaf keeps its device, inode, mode, links, size and both nanosecond stamps) doubles the steady-state rate of the serial inference: 81 -> 163 owners/min on 55 real owners, identical output. That is part of the set because the farm's parent needs it.
8. **What limits the farm (measured, section 4).** The parent still does about 45-60 percent of the serial per-project CPU (value deserialization, fact replay, the guard of the persistence gate, adoption of about 28 small files per project, block presence checks): 230 ms -> 98-156 ms per project. The speedup of the inference phase is therefore bounded near 1.5-2.3x however many workers run, and the workers burn about as much CPU in total as the whole serial run (46-62 s against 32 s for 139 projects, startup included: each re-analyses the files not in the parent's seed, startup 10-20 s per worker). Projection for 3,738 projects with the whole set on a quiet 8-core host: 15-25 min cold (against 60-90 min), unproven; the goal of 15 min needs the follow-ups F1/F2.

## 2. Pinned semantics, custody

- The worker runs the same implementation (`accept` compares the revision it loaded with the parent's; any other revision disables the farm and everything runs in the parent) and every job under `withImplementationPinV1`, so an edit during the build does not abort it.
- Nothing is published by a worker. Its fact directories are a private staging root (`withBuildGraphStagingV1`, only the worker service enters it); the parent adopts closure inventories (name must equal the digest of the content), and optional leaves through the unchanged `withBuildGraphOptionalPublicationV1` and the quota ledger. A sealed record is written by the parent through the unchanged persistence gate.
- The farm is never used for an owner admission (`options.ownerAdmission`), and never when the project count is below 24.

## 4. Measurements (honest)

Conditions: the host (10 cores, 32 GB) ran at load 13-37 from other work during every run, my trees were niced; wall times below are therefore NOT the numbers of a quiet machine, CPU seconds and memory are. A harness run starts with 10-20 s of pre-state and module load before the first project; the farm adds worker startup (10-20 s per worker under load).

|---|---|---|---|---|

Reading: (a) the farm moves the pure work out of the parent but not the persistence bookkeeping; sealed records took the parent from 227 to 142 ms per project, adoption, replay and the guard of the persistence gate remain; (b) at 107-150 projects the 10-20 s worker startup is as long as the work, so no wall clock speedup can show; (c) under load 30 the processes share the cores with the other agents; (d) my 4 GB cap allowed two workers on the heavier samples only (3 workers once, one 2-worker run was stopped by the guard at 4.1 GB), so scaling beyond 3 workers is a model, not a measurement. Model for 3,738 projects at steady state, parent-bound: parent 100-150 ms x 3,738 = 6-9 min, workers (190 ms per project / 8) hidden behind it, plus about 1 min startup and the dependency pass (module farm) -> **cold 10-15 min only if the parent stays below about 100 ms per project; 15-25 min at the 140-150 ms measured under load.** Warm: the farm adds nothing (lazy, no spawn, no gate request); records-valid resume costs 37 ms of parent CPU per project; the warm path of the generation engine does not call the project inference at all.

## 5. Not verified (be explicit)

- No live run: the real writer custody (adoption into the mounted graph image, quota ledger accounting of staged leaves and sealed blocks, the refusal paths of the quota), the real host-capacity gate under a running invocation, the real invocation cancellation. The text laws, the fixture storage and the ordinary-path harness cover the logic; first live exercise decides.
- Cargo resolution receipts and input-precision receipts of a worker are adopted as optional leaves; a refused quota only costs the next recomputation.
- Windows / Linux / devcontainer: stdlib `node:child_process` + `node:v8` + `bun:` heap switches behind `graphFarmRuntimeEnvironmentV1`; `/Volumes` and macOS-only measurements were not used by the code; untested on those hosts. The farm needs a Bun (or Node) able to run the library's TypeScript imports, like the rest of the build.
- Speedup at production scale, more than 3 workers, host load below 12, the dependency pass at 33,000 files.

## 6. Follow-ups, in order of value

- **F1 (the limit):** parent persistence per project. Options: write the immutable content-addressed leaves (closure inventories, blocks, receipts) from the worker straight into the graph directory by tmp + rename and let the parent only account them (needs the storage owner's sign-off: custody and quota), asynchronous adoption, drop of the per-block `lstat` inside one writer scope, skipping `rr/` receipts in workers and producing them lazily. Target: parent below 60 ms per project.
- F2: start the workers during the parent's pre-state (they boot in 10-20 s while the parent walks owners); keep a worker pool across builds.
- F3: gossip the parser records between workers through the parent (the seed already removes the shared library closure; project-specific closures are still parsed once per worker).
- F4: fix the attribution of first-touch facts (process-level memos should replay their facts into every consumer); then per-project fact sets become comparable across runs.
- F5: `projectImages` retention and the 8 stringify/parse passes of a value in `observeProjectInferenceV1` (graph-mem's bounded retention is the place).
