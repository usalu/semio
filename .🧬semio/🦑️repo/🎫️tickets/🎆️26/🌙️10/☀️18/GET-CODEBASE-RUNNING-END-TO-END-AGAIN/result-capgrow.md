## (1) A reduced grant grows later (same safety as the quiet-forecast grow)
Why it never grew: a grant admitted `reduced` (fewer jobs than preferred, memory short at admission) was final; only a quiet grant had an upgrade path, and the Bazel `--parallel` of a reduced run was rewritten to the granted jobs, so even a raised plan could not raise `--jobs`.
Change (host-capacity framework + gate):
- Decision (`📏️decision`): a grow request (`Waiter.grow`, with `upgrade`) is decided after every other request (`orderHostWaitersV1` ranks it last) and takes nothing from them: `queue-order` while any other request of ours waits or a barrier holds (fair to peers), `ramp` while the grant still ramps (its last reservation is not yet observed: it cannot grow twice on the same memory), soft and hard stops like any request, else the most jobs whose memory fits with the memory of `Protocol.growSpareJobs` (1) more job left free (hysteresis margin) and whose cores fit the load room; never the partial/override path, never a barrier, never a smaller reservation. Bounded by the measured per-job footprint: the request is the door's `growth` request (scaled at the class's grow ratio, capped by the class bound of quietfc round 1).
- Time hysteresis: `settleHostGrowthV1` grows only after `Protocol.growSettleAttempts` (2) consecutive admitted attempts (one per heartbeat, 15 s live), to the fewest jobs they admitted; one refused attempt starts over. Jobs only go up: no oscillation.
- Holder (`🎫️gate`): a grant with a full request (`options.upgrade`, i.e. Bazel-gated runs) and fewer jobs than it asked for runs `growHostGrantV1` (`🔼️upgrade`) once per heartbeat under the gate lock; the grow request is never written to the queue, so no other run ever waits for it. A growth rewrites the row atomically (jobs, cpu, reservation max(old, need), restarted ramp, `Grant.grownAtMs`) and prints EN/DE `grown`. The admission prints `reducedGrows` (EN/DE) instead of `reduced` when the run can grow. The phase resizer now uses the current jobs (`state.jobs`, was the admitted `held.jobs`, wrong after any growth incl. staged3's partial one).
- Followers: `followHostGrantPlanV1` + `readLiveHostCapacityPlanV1` (plan followed to the live row, both directions); `adoptUpgradedHostPlanV1` (staged3, shrink only) now follows both ways, so the Bazel script's `capacity.upgrade` point (after the graph phase, before `--jobs` is computed) picks the grown jobs; the handle of a growable run tells the tool its preferred jobs (`--parallel=8`, as for quiet grants) while the plan holds the granted ones (`--jobs=min(parallel, plan.jobs)` is already live from staged3); a nested invocation that inherits the grant carries the followed plan; compile-units reads the live row.
- How it composes with staged3: staged3's partial growth (sole quiet run grows to 4 of 8) leaves a non-quiet grant with fewer jobs: this batch lets exactly that grant grow back to 8 when memory frees. quietfc-mutual is untouched (grow requests are not upgrade competitors: `growing` only collects quiet upgrades).
- Cost (documented in the guide): a growth only helps work that starts afterwards (a running Bazel keeps its `--jobs`); the grown reservation counts in full for the run's ramp, then by observed memory.

## (2) A Cargo/rustc compile action is multi-core with its measured footprint
Why 1 core: compile-units capped a planned compile at the run's Bazel job count (`grantedJobs`, one action = 1 cpu / 2 GB), so a 1-job grant compiled on 1 core (g31 `1 of 10 cores`, broker 2.6 GiB) and an 8-job grant on 5 cores with a 13 GiB broker budget that no reservation covered.
Change (`🎟️capacity/🧮️units` + launcher):
- `Host` gains `grantedMegabytes` (the job memory of the live grant: `plan.memoryMegabytes` followed to the row) and `unitMegabytes` (measured unit footprint, `compileUnitMegabytesV1`: nearest-rank p75 of the newest peak RSS of every unit in the rustc broker's `units.jsonl`, min 256 MB, the authored 2048 MB until 8 units are measured). The granted limit becomes `max(grantedJobs, floor(grantedMegabytes / unitMegabytes))` (never fewer cores than before), the free-memory limit uses the measured footprint, and `Decision.budgetMegabytes = max(grantedMegabytes, preferred x unitMegabytes)` under a grant (null without).
- `bun repo cargo` launcher: reads the unit history before planning and passes it; the broker's `physicalBytes` is `min(share of physical memory, reserve + budgetMegabytes)`, so the rustc broker never holds more than the grant gives the compile. Example: a 1-job grant (2048 MB job memory) with 900 MB units compiles on 2 cores with a 2048 MB budget instead of 1 core / 2.6 GiB; an 8-job grant with 5734 MB job memory keeps 5 cores with a 10240 MB budget (2048 MB units) instead of 13 GiB.
- print-rs:test (finding, no change staged): its cargo runs through `runCargoTestsV1` without compile-units, jobserver or broker (Cargo default `-j10`, rustc `-Z threads=0`), so it was never capped to 1 core; what applies to it is (1): a partial or reduced print grant now grows back when memory frees, and its Bazel `--jobs` follows at `capacity.upgrade`. Bounding its cargo by the grant (CARGO_BUILD_JOBS from compile-units in `📚️library/🏃️process/🦀️cargo/🎟️admission`) would cut it from 10 cores to the 50 % share (5): a policy call for the coordinator, not staged.
