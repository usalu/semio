| `exec` | dry-run: the Bazel plan of the injected `project:repo-exec` tasks equals `buildExecPlanV1` (ids, targets, deps); execution: per project, cwd = project root, `NX_PROJECT_NAME` and `NX_PROJECT_ROOT_PATH` (root relative, like Nx's `exec.js`) via the neutral `buildExecEnvironmentV1` in `bazelTaskBaseEnvironmentV1` | test asserts plan equality, env values, cwd, uncached; Nx `exec.js` source checked for the same two names |
| `graph`, `show`, `watch` | neutral for both tools, no Bazel code needed | unchanged |
| `cache status` | counts files and bytes of `ac/` and `cas/` of the products-partition disk cache (not `tmp/`, `gc/`; links not followed; ENOENT races tolerated; progress every 128 directories; cancel at every directory), plus `activity` = `{builds, actions, executed, cacheHits}` totals since the last clear, read from a ledger | see Verification (real binary, real partition) |
| `cache clear` | queued whole-image exclusive maintenance (same door as `reset`), then: remove each persistent server's pid file (Bazel exits ~3 s later, verified), wait until the pids are gone (10 s bound, error otherwise), remove the per-workspace output bases (Bazel's local action cache and execroots; symlinks unlinked, never followed; read-only directories chmod-retried), remove ledger and event streams, empty `ac/` and `cas/` keeping `tmp/`, `gc/` and the folders. Toolchains (`bazel/bin`, `install`), modules and workspaces stay. Chunked with progress every 128 entries and a cancellation check per directory/entry. | real binary: after `clear` the next build is a full miss (3 executed, 0 hits) and the cache regrows to the same entry count |

Why the output bases go with `cache clear`: a plain `bazel clean` (observed) drops the local action cache, and a surviving output base would make the next build "up to date" without touching the disk cache, which breaks the `clear` then "run grows entries" proof the CI workflow (`build-system.yml`) relies on.

## Build activity ("Bazel's own metrics")

`runBazelTasksInStorageV1` now passes `--build_event_json_file=<server base>.events.json` to the `build` command only (the file sits beside the per-workspace output base, so concurrent selections never share one) and, in `.finally` of that build (success, failure or cancel), calls `recordBazelBuildMetricsV1`, which parses the Build Event Protocol `buildMetrics.actionSummary.runnerCount` (`total` = actions, runner names ending in ` cache hit` = restores, `internal` = no process, everything else executed), adds it to `<server>/metrics.json` under a lease, deletes the stream and never throws (warning only, silent on abort). Observed with Bazel 8.4.2: cold build `{total 4, internal 1, darwin-sandbox 3}`, after `bazel clean` `{total 4, disk cache hit 3, internal 1}`, up to date `{total 1, internal 1}` (these three real events are the fixture; `remote cache hit` and `remote` rows are synthetic and marked so).
