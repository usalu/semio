## 1. HIGH: the reservation is a 60-second promise (ram-g)

`P/🏗️build/🌡️host-capacity/📏️decision/🟦️.ts:116-117`: a grant counts its full reservation only while `now - (resumedAtMs ?? admittedAtMs) < rampMilliseconds`; afterwards `committed` is `observedMegabytes ?? reservedMegabytes`. `rampMilliseconds` went 300000 -> 60000 (`B/🔣️policy.json` hostCapacity.memory). So the learned ratio (`📐️estimates`, floor 30 %, `scaleHostRequestV1`) decides how many runs are admitted in ONE minute, and after that every run is accounted by what it holds at the last 15 s heartbeat.

Failing scenario (16 GB host, 9 GB available, the law in `B/🌡️host-capacity/🧪️tests/🟦️.ts` "16 GB law"): six identical `run` requests, class learned at 30 %: four are admitted within seconds (the law's success criterion, ">= 4"). Each reserves ~1.1 GB; at second 61 all four are accounted by what they hold (still 1-2 GB each while the graph loads and the Bazel/Nx actions start), the next two are admitted, and 3-6 minutes later all six climb to their real peak. The real store written this morning (`~/Library/Caches/semio/host-capacity/estimates.json`, 21 classes at 09:01) shows what "real peak" means: `run:test` samples 4501-16657 bp of the default (45 %-167 %), active times 36-1418 s, `exec` 8015-10854 bp, `run:build:...print:build` 7352 bp over 1088 s. The pressure and swap gates only refuse NEW admissions (`decision:126,134`); a running grant is never throttled, so the overshoot ends in the compressor and swap. The old 300 s ramp covered five times as much of the growth; the simulation could not see the difference because it ramps "to its peak in 30 s" (result-ram-g, Simulation: model).

The law proves the admission count, never the memory: nothing asserts that the sum of real peaks of the admitted runs fits.

Fix (owner ram-g or a successor): (a) store `peakAtMs` (time to peak) per sample and use `ramp = clamp(q0.9(peakAtMs), 60 s, 600 s)` per class (default stays 300 s for an unknown class); (b) an admission rate rule: at most two grants whose learned time-to-peak exceeds the ramp may be inside their ramp at once, so a burst cannot all ramp together; (c) a law with a memory simulation fed by the real bimodal samples above (hot 45-65 %, cold 160 %), asserting `sum(real peak of admitted) <= available` for q0.9 and for a deliberately wrong class.

Related, same file and store: the `q0.9` of at most 16 samples is the second largest sample (`estimates:31-35`, cumulative weight >= 0.9 of the total). A cold mode (graph rebuild inside the run after a library edit) in one run of ten is invisible: the run reserves the hot size and then needs 5-13 GB. The opposite happens when the cold mode is frequent: `run:test` above reserves the cold size for hot runs. The class key (`operation:kind:target`) cannot tell hot from cold; the simulation's "4 peak strata = 4 classes per operation" assumed it could. Fix: let the gate tag a run that rebuilt the graph (the planner child already exports it) and learn it under `:cold`, or keep the learned reservation at the median and let the free-memory check carry the tail.

Decay and caps are otherwise sound: the quantile is invariant under uniform decay, trust falls with the effective sample count (3 days half-life) so an unused class returns to the conservative default, pooled evidence can only shave (`estimates:44`, `min(DEFAULT, ratio)`), the store is bounded (16 samples, 256 classes, 1 MiB) and read failures degrade to empty. The bounds that can hurt are the lower one (30 %, 512 MB) and the 50 % share cap, which by design reserve less than a 13 GB run needs.

## 2. MED: failed, cancelled and restarted runs are learned (ram-g)

`P/🏗️build/🌡️host-capacity/🎫️gate/🟦️.ts:202`: `learn` runs in the `finally` of every non-adopted, non-parked grant with `peak > 0`. The outcome carries no status. A run cancelled at second 40, a run that died on a churn ENOENT, a stale-implementation restart that is not parked (exit 75 with no restart wrapper) records its partial peak. Under peer churn tonight such runs were common; with 16 samples and a 0.9 quantile, two early deaths among sixteen no longer matter, five do, and they bias exactly the classes that churn most. Fix: add `outcome: "ok"|"failed"|"cancelled"` to `Outcome` (schema `Outcome` + `HostRunV1`), record only `ok`, and record non-ok only when the partial peak already exceeds the current estimate (it can only raise).

## 3. MED: "stuck" ignores what the watchdog already knows (lease-g)

`P/🔒️leases/📈️standing/🟦️.ts:49-58, 95-99` and `P/🧭️routing/📥️invocation/🏃️process/🟦️.ts` (publish feeds `noteLeaseProgressV1`): liveness is "any `control.publish` line". A holder compiling the dashboard binary (one long `cargo`/`rustc` child, no publish for an hour) is "stuck" after 60 min (20 min for graph custody). The same file already measures real liveness: `startScriptProcessWatchdogV1` tracks tree CPU activity and only declares a stall when the whole tree is idle (`🐕️watchdog/🟦️.ts:70-81`, exit 124). Two notions of liveness disagree.

Consequence with the DEFAULT mode (`request`): a waiter files the request, the holder re-judges itself with the same progress clock and accepts (`🤝️yield/🟦️.ts:43-44`); the handler (`B/🧷️format-stamps/🟨️.mjs:136-139`) aborts the root with `SEMIO_LEASE_YIELD` or, when no root is registered, `process.exit(1)`. Exit 1 is a permanent failure for the person who ran it, not the exit 75 the stale path uses, and the child compile is cancelled. Fix: have the watchdog activity sampler call `noteLeaseProgressV1({stage:"activity"})` whenever the tree advanced (one line where `startScriptProcessActivitySamplerV1` already knows), and make a stuck yield end with the restartable code only when the holder has no output to keep (otherwise refuse). Law: a holder whose child burns CPU for longer than the stuck bound is never asked.

## 4. MED: terminate mode (opt-in) (lease-g)

`SEMIO_LEASE_RECLAIM=terminate` is off by default, so these are latent, but the mode exists to be switched on during exactly the nights it is dangerous:

a. FIXED (F2): a head holder with NO registry entry was `legacy` and, after 90 min, SIGTERM/SIGKILLed with no request and no grace (`🤝️yield/🟦️.ts:112-113`). The registry prunes entries silent for 5 minutes (`🧭️order/🗂️registry/🟦️.ts` STALE 300 s), so a healthy holder after a laptop sleep or a swap storm that starved its 60 s heartbeat became "legacy" and killable. An unknown holder is not a legacy holder.

b. `legacy` age is `nowMs - input.headArrivalMs` (`:57`, ticket arrival of the queue head), which includes the time the holder itself waited in the queue. A pre-lease-g builder that queued 70 min and worked 25 min is "95 minutes old". Tonight's shard-7 queue had 60-130 minute waits and rebuilds of 60-120 minutes, so even the correct age (`legacyAfterMilliseconds` = 90 min, `📈️standing/🧬️schema/🔣️.json` reclaim) is shorter than a legitimate rebuild. Fix: age from `hold.sinceMs` (pass it as a separate input, extend the corpus and the Python model), and raise `legacyAfterMilliseconds` above the longest observed legitimate hold (4 h), or drop the legacy kill: legacy holders disappear with the next restart.

c. `:117-120`: SIGTERM, wait up to 15 s in the waiter's wait tick (a Ctrl-C of the waiter is ignored for that time), then SIGKILL of the head pid only, with no second identity check between the two signals (pid reuse inside 15 s is unlikely but the check is cheap) and without the holder's children: a wedged executor that does not run its SIGTERM handler leaves the planner/builder child (5-13 GB, memory note "Killed Build Orphan Holds Target Lock") running and holding its own locks. Fix: before SIGKILL, kill the children listed by `liveChildPidsV1(headPid)` (they are known from the same process table the gate reads), and re-run the start-time check.

d. win32: `osStartedAtMs` is undefined, so every tick prints "reclaim.refused ... unknown" in both languages (`:114`) for as long as a stuck holder exists. Print it once per holder.

Priority classes and aging themselves are sound: filed arrival = real arrival - advance, so an interactive request overtakes only requests that arrived within 60 minutes before it, a background request is overtaken only by requests arriving within 60 minutes after it (`⚖️priority/🟦️.ts:16-23`, simulation law). There is no preemption: an interactive waiter still waits out a 120 minute background holder.

## 5. MED: stale yield trusts the claim (lease-g)

`🤝️yield/🟦️.ts:39-42`: the holder compares its own components with `request.requesterComponents`, a claim written by the requester, and accepts when they differ and the requester started later. It never reads the disk. Scenario: peer A edits a bound stamp schema, a waiter W starts and loads the new value, the peer reverts the edit (W now carries a stamp the disk no longer has). Holder H, 100 minutes into a build and current against the disk, is asked to yield and aborts; W then fails its own guard (`B/🧷️format-stamps/🟨️.mjs:88`, `ensureCurrent`) and restarts, so the 100 minutes bought nothing. The docstring promises that the holder "checks the claim itself"; it checks it against the claim. Fix: accept a stale request only when `formatStampsV1.moved(bound)` (disk now vs the holder's own declared stamps) is non-empty, and add a corpus row "claim differs, disk equals holder" -> refuse.

## 6. MED: the reaper's memory rule reads the ledger (bzsrv-g)

`B/🔧️tools/🏗️bazel/🧵️sessions/🟦️.ts:217-222` keeps no idle server when `headroomMegabytes < 0`; the caller feeds `port.spare()` = `evaluation.headroomMegabytes` (`📜️script.ts:729` area, `spare` port). That number is `min(available - floor - unrealized, cap - committed)` (`decision:118-119`): negative whenever grants are ramping, with 10 GB really free (ram-g's trace of the old policy shows `-13494 MB spare` with 10 GB really available; the shorter ramp makes it rarer, not impossible). Every session that starts while another run ramps therefore stops EVERY idle server, including the one a peer released five seconds ago and is about to reuse (cold JVM + analysis 14-16 s instead of 1.3-1.6 s, bzsrv-g's own numbers). The slot claim protects a server during the stop, not its warmth. Growth (`bazelGrowthAllowanceV1`) should use the ledger headroom; the "below the floor" rule should use `host.availableMegabytes - floorMegabytes`. Fix: a second port member `floorSpare` (true free above the floor) used only by `planBazelServerReapV1`, law: ledger headroom -5000 with true free 9000 keeps the budgeted idle servers.

Other bzsrv-g points checked and fine: the reaper claims each victim's slot before it stops it, a slot taken between plan and claim is skipped (`🔌️port/🟦️.ts:73-79`); a server a session "is about to use" can only be one it has not claimed yet, and a lost race costs warmth, never correctness; held slots count as demand before their server exists; `stopBazelServerV1` never signals a process (removes the pid file, waits, throws on timeout), so a recycled pid is harmless; attach reads the pid file of the server just used. `-Xmx1536m` is twice the measured RSS peak of the biggest package (673-745 MB), but a package larger than today's 20 811 targets on the 8 GB profile (1126 MB heap) has no margin; the JVM flags (`G1PeriodicGCInterval`) need JDK >= 12, true for the embedded JDK 24 and unchecked for a user-supplied `--server_javabase`.

## 7. MED: quota eviction cannot see a live reader (disk-g)

`B/🧹️cache-gc/🏃️runner/🟦️.ts:303-312` derives per-area budgets `min(declared, quota share)` and feeds the old planner, whose only liveness signals are SQLite locks, queue tickets, leases and "recency = max(mtime, atime) of the unit's files" (`measureCacheTreeV1:57-74`). The tool areas (`go`, `playwright`, `elan`, `cmake`, `dotnet`, `tectonic`, `bin`, `vite`, ...) have `custody: "quiet"` with a 10 min to 1 h quiet time (`⚡️caching/💾️storage/🧾️ledger/🔣️policy.json`). A toolchain that is READ continuously is never modified, and atime does not carry the signal everywhere: Linux `relatime` refreshes it at most daily, `noatime` mounts never (a devcontainer may use one), Windows disables last-access updates by default. Before this wave a unit needed `unusedAgeMs` (14-90 days) to go; the quota path evicts by LRU as soon as the area is over its derived budget and the unit is older than the quiet time.

Failing scenario (Linux, relatime): a 3 hour Playwright run uses Chromium from `tools/ms-playwright/chromium-1234`; its atime was refreshed at the start; at hour two `repo cache gc` runs under a budget that this machine does not meet (the default 40 GiB total against 69 GiB used: "over by 84 GiB"); the unit is older than the 1 h quiet time and the oldest in its area; it is removed under a running browser (new file opens fail, the test flakes or fails). disk-g's own report says the loose-area LRU enforcement was kept dry-run "because those caches are in use by lanes": the planner would have cut caches in use.

Fix: tool caches get `custody: "lease"` and their launchers hold a shared lease for the process lifetime (the custody mode exists, `runner:288`); or quota eviction (not the age rule) requires `max(quietMs, 24 h)`; or quota eviction skips areas whose files sit on a volume without reliable atime. The re-measure right before removal (`:328-331`) narrows the race to milliseconds but cannot see a reader that opened nothing yet.

Dedupe (F1, fixed; the rest holds): a replacement is a copy-on-write clone written to a temp file and renamed over a file that was quiet for an hour, unchanged since it was hashed (ino, mtime, size re-read twice), not a hardlink, not a volatile name, on a volume that clones or not at all. A reader sees old or new bytes, both identical; a COW clone cannot write through. Residual risks: LOW 10a.

## 8. MED: the scheduling prefixes are directories, not contracts (exec-f)

`L/🏗️build/📥️source/🔏️closure/🗓️scheduling/🔣️.json`, domain `store-custody` ("It decides where bytes live, never what they are") lists `🏗️build/🕸️graph/🕰️generations/`. That directory holds more than custody: `🌍️environment` ("Reads the one field of a manifest that other projects' edges depend on ... The same function derives a fact and checks it"), `✂️cutoff` (which derived rows survive), `🧮️fact-codec` ("the byte identity of every stored document and the identity of a fact"), `🔌️load`. These DERIVE and ENCODE graph facts, i.e. they influence outputs through the graph. The generation digest is deliberately "the declared stamp of every inferrer and the bytes of every data file ... never the bytes of code" (`🕰️generations/🔌️load/🟨️.mjs:129`), so a semantic edit to the extractor or the cutoff moves no generation stamp (the maintainer must bump one by hand) AND, since 04:12, moves no command-closure key either (`withoutSchedulingV1` at `🧭️script-inputs/🟨️.mjs:251/399`, `schedulingSourceExclusions` input, the executor overlay). Before 04:12 the closure key was the only automatic net.

Failing scenario: someone fixes `🌍️environment` so a Cargo workspace member is no longer missed; no stamp is bumped; the generation is served as current (coverage stamp), every cached `generate`/`build` action keeps its key, nothing re-runs, the dashboard keeps its stale edge until a stamp is bumped or `cache gc` drops the generation. The same holds for the retry domain: `🔁️churn` exports `churnProtocolV1().settleMilliseconds`, which `📥️inputs/🔏️revision/🟨️.mjs` uses as the settle window of every source capture; it is a correctness bound of the captured bytes, not "when to read again".

The laws are green because they test what the table says (ports, split, identity) and the empirical oracle is "re-keyed generators had identical outputs" (result-exec-f, Laws), which holds for lease/progress edits but cannot hold for a codec or extractor fix. Fix: narrow `store-custody` to the custody directories (`🕰️generations/🧷️pin`, `🔭️coverage`, `🧩️claims`) and keep `🌍️environment`, `✂️cutoff`, `🧮️fact-codec`, `🔌️load`, `🌊️json-stream` keyed (one-time re-key of ~3.7k projects, regenerate the traced module lists, the trace law is red today anyway); move `settleMilliseconds` out of the retry domain's ports or key it; add a law "no file of a scheduling prefix exports a function that the output-writing modules call for content" (the ports law already finds the call edges, it needs the content/identity annotation).

The remaining domains (`leases`, `capacity`, `process-supervision`, `progress-reporting`, the storage ledger and budget code) read as true scheduling: they change when and where, and I found no path from them to output bytes. `nativeKeyed` is kept for the Nx family and, per its docstring, "the Bazel executor identity still treats them as scheduling"; today the scope table covers only `command` actions, not the Rust compile actions, so no Rust output is affected, but the day a `cargo` class joins the table the native recipe code (`📦️artifacts/🏗️native-build/🎯️recipe|📥️inputs|⚙️configuration`) leaves its key unless the executor path honours `nativeKeyed`. Add that to the scope law now.

## 9. LOW

- ram-g `B/🌡️host-capacity/🟦️.ts:107`: `interactiveTerminal: client==="human"`. `human` is the default client of ANY process without an agent session: a cron job, CI, a script. The lease module requires a TTY (`📈️standing/🟦️.ts:63-65`); the capacity queue does not, so headless non-agent runs rank interactive. Use `currentLeasePriorityV1(agentSession, environment)` (export it from the facade). Also `hostRequestPriorityV1` promotes every class learned "quick" (median active <= 120 s) to interactive, which includes the hot no-op rebuilds of all agents, diluting the human class that the simulation credits with the p90 gain (`NEW without priority` vs `NEW`: 322 vs 222 s).
- Windows (`📡️sampling/🟦️.ts:112-130`): one PowerShell + CIM start per sample, shared through `sample.json` for 1 s, so about one 0.5-1 s PowerShell per second machine-wide while anything waits; the 3 s bound aborts it on a loaded machine and the sample silently falls back to `freemem()` without swap data (safe, but the swap gate is blind). Read `os.freemem()` every time and the page-file counters at most every 10 s. `observeTreeMegabytesV1` returns null on win32 (`:185`), so a Windows run never heartbeats, never learns, and holds its full default reservation for its whole life: correct and conservative, worth one sentence in the README.
- macOS: the learned peak is `ps` RSS, which excludes compressed pages; a run measured under pressure looks smaller than it is, so pressure lowers the next reservation (a feedback loop, bounded by the pressure and swap gates). Prefer the physical footprint of the process (`proc_pid_rusage`) or discard samples taken while `pressure != normal`.
- `B/🌡️host-capacity/🟦️.ts:45` builds the class key from up to three parts of 120 characters; `EstimateStore` allows `{1,200}` (schema `EstimateStore.classes.propertyNames`), so a long cargo package name makes the whole write invalid and that run's sample is dropped silently (`estimates:105-108`). Cap the lineage to the schema bound.
- `estimates:96-103`: stale-lock takeover can run two writers; the last rename wins (a lost sample, never a torn file), but the first writer's `finally` removes the second writer's lock. Own the lock with a token file. Also the learn step runs before `cleanup()` (`gate:202-203`), so a held `estimates.lock` keeps the grant's reservation for up to 10 s after the body ended.
- `gate:47-55,177`: `grants/<id>.attached` is removed only by `cleanup`; a SIGKILLed run leaves it (the grant file is pruned by `readGrants`, the `.attached` file is not, because `names()` filters `.json`). The attached pid is not checked against a start time, so a recycled pid would add an unrelated process to the observed tree (over-reserves, safe).
- infer-f: the host-granted farm pools (`requestBuildFarmCapacityV1`) request the default `exec` size and never learn (no `learn` port), while the census shows the heaviest projects at 2.5-3 GB per worker against 2048 MB reserved; workers recycle at 2.5 GB. The observed tree counts them, so the ledger corrects after 60 s; the reservation at admission stays 30-50 % low for the heavy tail.
- 10a. disk-g dedupe: `.dedupe-<pid>-<n>` temp clones survive a SIGKILL between clone and rename (shared blocks, so cheap, but visible in output trees); sweep them at the start of the next dedupe run. The volatile-name denylist (`dedupe:20`) is the only protection of a file held open for append that has been idle for an hour; `.out`, `.err`, `.trace`, `.events.json` are missing. An allowlist per declared place (launchers, `implementation.json`, `adapter.json`) is safer than a denylist.

## 11. chain-g loader memory (`B/📥️source/🔏️closure/🍞️bun/🟦️.ts:37`): no defect found

Read as a data-flow change: the two per-module `define` texts became identifier defines of one frozen global (`__semioCapturedSelectionV1.physical|resolutions`, deep-frozen, non-configurable, non-writable). Checked: every consumer is read-only (`📥️source/🔏️closure/🟦️.ts:31-50` validates and iterates, `📥️inputs/🔏️revision/🟨️.mjs:14-18` builds a Map), the sort order (`Buffer.compare` of UTF-8) equals the code point order the consumers demand, the overlay merge happens before `orderedSourceFiles` is computed, a second evaluation in one process is impossible because the auxiliary variant refuses anything but exactly one `--eval` and the file variant is a script entry. The immutability argument holds: modules cannot replace the global (non-configurable), and a frozen shared object cannot be edited by one module for another, as the literal copies could not either.
- FOR chain-g: (a) `loaderIdentity()` is evaluated inside `onLoad` for every module (`:38`, the `import.meta.semioCapturedLoaderIdentity` define): the evaluated variant hashes the 24 KB loader text 1455 times, the file variant reads the loader file from disk 1455 times. Compute it once beside `expected`. (b) Add a one-line law that the global is defined exactly once with a clear refusal when the loader text is evaluated twice in one process (today a second `defineProperty` throws a generic "readonly property" TypeError). (c) The requeue design (door alone while a peer builds the graph) is correctly not landed; it would also need the lender rule of the gate to see the door as childless.
