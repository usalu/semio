### How the 16 GB machine is emulated (read this before judging a verdict)
Declared, not capped: the harness puts `SEMIO_HOST_CAPACITY_TOTAL_MEGABYTES=16384` and `SEMIO_HOST_CAPACITY_CORES=8` into the three commands' environment (`M.environment` strips every other `SEMIO_*`). The governor then sees `available = min(real free, 16384)`, floor 2048 MB, so the reservation ceiling is 14336 MB; the real 32 GB host keeps all its memory and its foreign load. Hence the measurement is only clean when the real host has >= 14.3 GB really available (the preflight gate and `--wait-quiet` enforce it, using the governor's own definition of available). The criteria judge our own footprint (3 trees + all Bazel servers) against 16384 - 2048, swap growth <= 512 MiB, swapouts <= 1 GiB, free memory >= 5 %, no wait row >= 60 s with nothing else of ours running, queue <= 2x own run above 120 s, progress rows at least every 60 s, EN and DE rows in the agent's language (A en, B de, C en).

## 3. Root cause of the predicted starvation under the live estimates, and the staged fix `narrow`

Trace (`hot-firstedit`, h16, live store): B (print) is admitted quiet and grows to its full 5486 MB / 8 jobs first; A's growth then asks for all 8 jobs (`minimumJobs = preferredJobs`, allrun) = 5066 MB, with 2.5 GB spare it waits `not enough free memory ... behind print-rs:test (running, 8 job(s), 5486 MB)` for B's whole 283 s run. Two causes stack: (a) the full reservation is p90 x 1.25 over a class that mixes cold graph refreshes (4-5 GB) with hot edits (3.4-3.6 GB real footprint), and the peer's whole reservation counts in full while it ramps (time-to-peak learned from the same mixed samples, up to 30 min); (b) an upgrade never narrows: it waits for ALL jobs' memory, however long. (a) needs per-phase estimates (agents16's open item, no tool emits phase marks); (b) is a missing bound.

Fix (b), staged, `narrow`: after `wait.bypassMilliseconds` (30 s) in `upgradeHostGrantV1` the waiter's request is rewritten with `minimumJobs = protocol.upgradeNarrowedMinimumJobs` (1, new schema constant) and one spare job of memory (`protocol.growSpareJobs`, the margin a grow keeps; without it two runs side by side dipped 364 MB below the floor in busy2/h16-tight and failed the quiet16 `--busy` law). The pure decision is untouched: it admits the largest job count whose memory fits (`reduced`, EN/DE `upgradedReduced` line), the holder's grower adds jobs when memory frees, the width gate keeps born actions inside the grant's live jobs. No upgrade waits longer than 30 s plus a poll for memory that carries one job and a spare.
- Law (real module, in-memory ledger, fake clock): `🧪️tests/🔼️upgrade/👥️agents/🟦️.ts` + feature scenario. A quiet run beside a busy 8-job peer whose reservation still ramps (spare 4000 MB, request 404 + 700/job): with the window it is admitted with 4 jobs and 3904 MB (closed form `floor((spare + held - fixed - perJob) / perJob)`), EN and DE line asserted; with the window disabled it keeps waiting. RED on base (`Expected "upgraded", Received "withdrawn"`), GREEN with the batch; the file is 11 tests in 1.2 s.
- Simulation law (same real decision module, sim mirrors the upgrade loop): live store, all 11 scenarios x hosts: LAW FAIL on base -> LAW PASS with the batch (A course-edit 316 s -> 110 s, queue 266 s -> 30 s, makespan 316 s -> 286 s; busy3/h16-busy A 564 s -> 30 s; busy3/h16-tight A 927 s -> 30 s). Snapshot store: LAW PASS before and after, `--busy` memory law included (min free 11.7 % vs 11.2 % base on h16-tight).
