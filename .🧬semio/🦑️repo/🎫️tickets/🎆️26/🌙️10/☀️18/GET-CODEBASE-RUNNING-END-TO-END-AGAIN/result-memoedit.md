### Design
- Settlement: a re-checked group that does not hold is checked row by row; the stale rows and every derived fact a touched path names go to the `derive` port. `🧮️derive`: `graphMemoSuspectsV1` = the planner's `splitStaleConsumersV1` over every class (a stale row a project or `@env` holds itself → refuse `direct:<owner>`; a named derived fact's pseudo owner by `derivedOwnerNameV1`; unsupported → refuse; ≤ `maximumDerivedQuestions` 64). The suspects go to a CHILD of the same invocation (the planner child's launch refactored into `child(label, environment)` in `loadBuildGraphInChildV1`, label `build:graph-derive`, request/answer files closed by the schema `DeriveRequest`/`DeriveAnswer`; the runtime answers `SEMIO_BUILD_GRAPH_MEMO_DERIVE` before any tool or graph work). The child opens the planner's own deriver exactly as `generationHostV1.deriveAgain` (`libraryBootstrap`, `prepareSourceAnalysesV1`, `openGenerationDeriverV1` with the workspace registry) and runs the planner's `settleSuspectsV1`; served only when every question held AND its new support reads only (kind, path) entries the old support read (the sealed relevance watches only the old support; otherwise `uncovered` → plan). Text `derived` EN/DE; `edited.questions` in the answer.
- Why a child: in-process the two course TS-program questions cost 9.6-12.7 s CPU and grow a process to 2.2-4.2 GB (measured), which the long-lived executor would keep (JSC never returns heap).
- Soundness: a stale raw row held only by pseudo owners is exactly what the planner settles by cutoff (`splitStaleConsumersV1` → `settleSuspectsV1`; held → no owner dirty); everything else is round 1. Conservative extras: owners outside the slice count as direct holders, a held answer with a new support entry plans, a closure/stamp row held only by pseudo owners is asked again (the planner skips those).

## 1. Design (schema-first: `M/🧬️schema/🔣️.json`, `$comment` "Edit refinement")
- Sealing (child, once per key): `buildGraphMemoRelevanceV1` also records, per vouched fact, the entries it names and the directories whose children it reads; the writer maps each fact's walk position to its id in the generation's fact index and writes `stem.rix` (`SME1`: (53-bit hash, row id) pairs for `named` and `inside`, hash sets `above` (directories with something relevant below), `frontier`, `members`). The sidecar header names the fact index and frontier digests; the sealed record keeps `relevance.edit = {id, index, frontier}`; retention owns the `.rix`.
- Lookup: `collectMemoChangesV1` gathers every relevant journal row (not only the first); pending stamps that fail become "listed" directories. Without edit ports / an edit index the answer is the old `changed: <path>`. Otherwise `settleMemoEditsV1`:
  - a row naming an entry → re-check the rows that name it; a directory with relevant entries below it must be a frontier directory with the same, known inode (nothing renamed over it); a member must keep its mode;
  - a row directly inside a strict or stamped directory (and a stamped directory whose stamp moved) → re-check the rows that read its children; a frontier directory is listed again with the planner's own walk predicates (`buildWalkDescendsV1`, `graphMemberPredicateV1`) and its subdirectories + members (+ modes) compared with the frontier (= `advanceFrontierV1` for the named directories);
  - refuse: an unexplained path (hash collision), a touched path that became a symbolic link (the journal cannot see behind it), a row the check cannot verify (`derived`, `closure`, `stamp`, `registry`), a retired fact index or frontier, > `maximumEditPaths` (256) paths or > `maximumEditRows` (4096) rows;
  - rows come from the immutable generation store by id (`graphMemoEditPortsV1`, sha-checked index view); the check is `memoFactsHoldV1` = the planner's `holdsByStat` (environment rule for `field`/`digest`, the engine's `observationsHold` with the source analyses registered, nothing stable), so an analysis is replayed and compared by its result: an edit that keeps a file's imports/modules holds.
- Re-seal: the cursor moves past the edit (as on every hit); a stamped directory listed again gets the stamp it had before the checks (if unchanged and outside the 2 s racy window) in a new content-addressed `.lst`, so the next sibling edit there is settled by the stamp alone. Text `edited` (EN/DE) + mark `graph.memo=hit:edited`.
- Soundness (what an attacker must break): served ⇒ every fact not named by a journal row is unchanged (journal exact since the cursor), every fact whose entry or listed directory a row names held by the planner's own check after the rows were read, membership at every named frontier directory equals the frontier, no named path is a symbolic link, no named directory was replaced; the out-of-sight recheck runs as before.

- Conservative refusals by design: a directory recreated with a new inode, a file replaced by a symlink to identical bytes, Windows/unknown inodes (frontier ino 0) for named directories.
- Large changes (> 256 paths / 4096 rows, e.g. a branch switch) plan, as the planner is cheaper there.
- The `.rix` pair sort could use a radix sort (+0.7 s CPU once per key today).
