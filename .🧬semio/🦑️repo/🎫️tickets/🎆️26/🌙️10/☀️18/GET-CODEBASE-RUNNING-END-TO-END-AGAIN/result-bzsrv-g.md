## Measurements
Method: production flag builders (`flags.ts` uses `bazelCacheFlagsV1`, `bazelSessionStartupV1`, `bazelPlatformProfileV1`, `bazelSessionCommandV1`) against scratch output bases under the session scratchpad, real Bazel 8.4.2 (JDK 24), nice 10, machine load 16-25 so wall times are noisy; RSS is the process subtree of the server, sampled every 200 ms.
- Cross-slot warm hit (`crossslot.ts`, 30 cacheable actions, 3 slots = 3 output bases and 3 different package paths, one shared `--disk_cache`): s0 `30 darwin-sandbox`, s1 `30 disk cache hit`, s2 `30 disk cache hit`, hot server again 0.39 s. So a warm action built in one slot is a hit in every slot. Real packages: `bazel aquery` of the same selection in slot s1 and s2 (`aquery-slots.ts`) is byte-identical after replacing the package/root paths (args, strict env `PATH=/bin:/usr/bin:/usr/local/bin`, exec info), and `BUILD.bazel`, `tasks.bzl`, `adapter.json`, `sources.json` are `cmp`-equal across slots. Caches: disk cache = one directory (`layout.actions`, 6.9 GB now, GC cap 10.3 GB), repo contents cache = `layout.outputs/../contents` shared (64 KB: nothing external fetched), repository cache shared; what is per slot: output base (action cache, execroot, outputs) and analysis cache in the JVM.
- Server RSS, biggest real package (20811 targets, analysis only): -Xmx2048m peak 673 MB; -Xmx1024m peak 558 MB; -Xmx1536m peak 745 MB (load noise); SerialGC slower (25 s vs 16 s) and not smaller. Idle after 40 s: default G1 480-570 MB (macOS later compresses to 26 MB), with the periodic-GC arguments 688 -> 384 -> 211 -> 94 -> 149 -> 109 MB. Heap cap is not the lever; server count and idle time are.
- Fleet sample (`fleet-sampler.py`, 50 min, 598 samples, passive `ps`): production Bazel servers 0 / 1 / 2 alive in 131 / 348 / 119 samples, max 760 MB total; max 2 persistent workers; no worker without a server; Bun repo chains 10-17 GB RSS (22-28 processes) and swap up to 14.7 GB, Bun RSS up to 19.4 GB: the Bazel servers are not the RAM problem of this fleet, the Bun chain is (chain-g, gram-g).
- Persistent workers (profiles of 27 recent commands, `command-*.profile.gz`): workers are in use (`RepoTest` 18 actions 1958 s of which 19 requests via "Worker #1 working"; "preparing execution" 0.5 s for 19 requests): spawn overhead is negligible, the win is the library load that stays in the worker; keep as is (max instances test 8 / check 8 / generate 4 / build 2, total worker memory from the grant).
- 3 concurrent runs at 16 GB (`scenario.ts`: three distinct selections, 20 s hold each, host headroom 2500 MB = a busy 16 GB machine, plan from `planBazelServersV1`):
  | | before (old policy, old floor) | after (this change, ram-g floor) |
  |---|---|---|
  | planned servers | 1 | 2 |
  | peak live servers / peak RSS | 1 / 738 MB | 2 / 832 MB |
  | all three runs done | 133 s | 87 s |
  | waits of runs 2 and 3 | 75 s, 107 s | 18 s, 54 s |
  | idle exit | 120 s | 600 s, reaper bounds idle servers to the budget |
  Before: the capacity gate admits two runs on 16 GB but Bazel had ONE planned slot, so the second run held its grant while waiting for the slot. The old policy could not have run with growth either (headroom < 4096). With an idle machine (headroom >= 4096) the old code opened up to 11 growth servers at once (cached headroom); now one per 4096 MB.
- Crash / orphan facts (real Bazel, `orphan.ts`, `orphan2.ts`, gated law): SIGKILL of the client does NOT cancel a running command: the server (and its `sleep` action) kept running for the whole observation (200 s); removing the pid file stops the busy server in 1.4 s (SIGTERM 0.6 s) but not the action process tree (process-wrapper child is re-parented). Production actions end themselves when the control socket to their parent closes (`bazel.action-control-disconnected`), so a crashed repo leaves a server that goes idle within seconds and exits by `max_idle_secs` or by the reaper; workers exit on input EOF (`serveWorkerV1` returns when the input ends; no worker without a server in the fleet sample).
