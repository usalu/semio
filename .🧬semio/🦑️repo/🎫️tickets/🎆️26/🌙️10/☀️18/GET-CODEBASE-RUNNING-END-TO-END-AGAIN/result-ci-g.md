## Decisions
- Windows rows of the broad sweep are advisory, the Windows laws above are blocking. Reason: no suite carries `platforms` yet, so POSIX-only suites will be red on the first Windows run; the report shows which, and the fix is the reported tag (`platforms`), after which the row can lose `continue-on-error` (set `advisory` to false for `windows` rows in the matrix; the test then needs the one expectation changed).
- One `repo run` per suite, not `run-many`: a per-suite log, exit code, wall and memory window are the artifacts asked for, and a hung suite is ended on its own budget plus 10 min slack.
- Host memory is machine-wide (free memory, swap, pressure from the capacity gate's own sampler) and the tree is the sweep process's; children started by a resident service outside this tree are not in it. Per-process peaks of those stay with the capacity gate's learning.
- `tools verify` is report-only in the new jobs: `python` is a "system" tool (>=3.14) and the runners may carry another version; `tools setup all` is what provisions (Go, uv, Python through uv, Bazel, Rust, dotnet) and it is blocking.
- The orchestrator is a repo script that calls `repo` (nested). `repo <script>` spawning `repo --version` works here (probe `ci-g-tools/nest-probe.ts`); `repo run` nested in it is the same mechanism but was not run.
