### 🕸️ Project graph and graph policy

`repo show projects`, `repo graph` and every task command start from the neutral project graph, which is {{^graph-generations::one sealed document for the whole workspace::a chain of immutable generations}}.

- **Live today.** A reader whose seal is current is served by a shared reader that takes no facts writer lease and never queues behind a builder. A missing or stale seal sends the command to the single exclusive builder, which holds `repository-graph-facts:<workspace>` for the whole rebuild; everybody who needs a fresh graph queues behind it, including agents that did not touch the edited project (on 2026-10-20 one `repo exec --dry-run` held that lease for 2.5 hours while three other commands waited). Publication itself had to change too: the expanded graph is about 859 MB of JSON, above the 512 MiB publication limit, so the graph is published compactly (closure inventories stay references that every reader expands, about 431 MB), pack descriptors are bounded (a least-recently-used set of 32), the owner lookup of each file walks up its path instead of scanning 3,656 projects, and every build prints per-phase counters and one `[graph-phase]` summary line (`SEMIO_GRAPH_PHASES=1` or `SEMIO_BUILD_PROFILE_INPUTS=1` print every row).
- **Generations.** {{?graph-generations::::The rest of this item describes the staged set. }}Every build publishes an immutable generation: one content-addressed fragment per owner (its neutral node, its outgoing edges, its module facts) and one fact index in which every distinct observation row is stored once. The pointer `current.json` flips by a single compare-and-swap after all documents are written, so a reader always sees one complete generation and takes no lease. An edit dirties its own owner and the owners that consumed the same fact (a membership proof from directory stamps replaces the tree walk); only the dirty owners are inferred, in one call, so the shared import closure is walked once per build. Writers coalesce on one builder custody, and the holder returns a peer's generation when the work is already done. The facts lease is held only for the pointer swap (a test holds a 300 ms build for at least 290 ms under the build lease and under 100 ms under the facts lease). `repo show project <name>` expands only the closure of that project.
- **Policy.** {{?graph-policy::::Staged as well. }}`--graph-policy=fresh|current` (or `SEMIO_BUILD_GRAPH_POLICY`) applies to `graph` and `show`; task commands (`run`, `run-many`, `affected`, `exec`, `watch`) always use `fresh`.

| Policy | Serves | Waits |
|---|---|---|
| `fresh` (default) | a generation that verifies against the tree; the dirty owners are rebuilt first when something it needs is dirty | only for the builder, and only when something is dirty |
| `current` | the newest sealed generation at once, possibly older than your last edit | never |

- **Builds survive edits** ({{@graph-pinning}}). A build completes with the implementation it loaded. An edit of an implementation file (the graph and inference modules themselves) no longer aborts a running build with "Stale loaded ...; restart required": while a build is pinned, the 12 self-checks of that kind return and the inference keeps the revision it computed first, with no mid-build swap. The pinned scopes are the command door, an owned build invocation and the generation load; the strict path (baseline, reuse, selected graphs) is unchanged. The next fresh load refreshes only the projects that consumed the edited module: each fragment records a digest fact (path, SHA-256, size, modification time) for every module it consumed, where inert modules (the ledger) are consumed by nobody, node-shaping modules (project nodes, target policy, playground and component targets, generator outputs) by the valid projects and every other module by every project and the environment. The manifest of a generation carries the digest of the loaded implementation (25 graph files and 63 inference files); `current` serves any generation of the registry identity and says `stale` in English or German when its stamp differs from the reader's, `fresh` verifies the rows and refreshes exactly the consumers, and a reader that loaded an older implementation than the one on disk finds the newer generation verified and serves it. The first read of an authority datum (the owner registry, the graph declarations: policy and schemas) holds for the whole pinned invocation. Proof: 300 projects (30 unavailable) built while an editor rewrote a node module every 250 ms published in one pass within 1.2 times the quiet time plus 0.5 s, the next fresh load refreshed exactly the 270 valid projects and the following one nothing. The retirement of optional graph files, which held the graph image exclusively for the whole run, now works in exclusive windows of 15 s with rechecks every 64 files and releases the image between windows.
- **Oracle.** `SEMIO_BUILD_GRAPH_VERIFY=1` runs the unchanged full inference once more and names the first project whose node, edges, external nodes or named inputs differ. Use it after changing graph code.
- **Applying the generations.** {{?graph-generations::The change invalidated every graph receipt and every project record once; the next graph build after it was cold and `repo tools setup nx` ran again afterwards.::Applying the set invalidates every graph receipt and, through a new observation revision, every project record once, so the next graph build is cold, and `repo tools setup nx` runs again afterwards.}}
- **A cold graph is the slowest command.** On 2026-10-20 the all-workspace inference of 3,735 projects ran at 6 projects per minute at host load 39 and at 33 per minute at load 21 to 27; it is bound by garbage collection of a 7 to 8 GB heap, not by leases or disk, so keep the host load below 25 while it runs. {{^graph-generations::The inference is also one record inside a settle loop: when a file that many projects read (the shared command-line closure, for example a bootstrap module or the process progress catalogue) is edited during the build, the facts of different projects contradict and the round repeats, and it restarted nine times in about two and a half hours while peers edited; do not edit such files while a cold graph runs::A pass publishes the snapshot it saw: a project that raced an edit is published and marked stale for the next generation, never restarted. Files that are not code (a JSON catalogue, a label, a schema) are recorded by shape and code files by their import analysis, so a body edit of a closure file no longer stales the roughly 670 native records (an import change still does); the closure revision is the digest of the path list; and the rows that thousands of records repeat are stored once as shared content-defined blocks (`np/<24 hex>.json`)}}. The persisted per-project records survive a restart, but a restart repeats the pre-project phases (5 to 8 minutes) and every waiting command with it.
