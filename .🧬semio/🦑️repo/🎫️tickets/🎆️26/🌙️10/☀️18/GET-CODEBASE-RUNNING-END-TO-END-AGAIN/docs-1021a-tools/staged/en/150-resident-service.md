### 🛰️ The resident service and `--service`

A cold `repo run` pays for loading the build library (0.7 to 2.3 s on the real closure), taking the image custody (about 1.2 s) and proving membership and the closure digest (0.2 to 0.5 s) before any tool starts. The resident service keeps that state warm, per worktree and per user, and answers a warm command in milliseconds. {{?resident::::It is a staged set: until it is applied every command takes the one-shot path. }}State: {{@resident}}.

```bash
repo service start
repo service status
repo run <project>:<target> --service=require
repo run <project>:<target> --service=off
repo service issue
repo service stop
```

- **Who answers.** After the launcher has found the checkout and before it chooses or provisions the runtime, a plain `run`, `test` or `run-many <targets>` (flags that cannot change a task only) goes to the service over a unix socket or a named pipe. Anything else, an absent service, a directory that is not private to the user, a missing key, an unresolved language or a retry hint falls back silently to the one-shot path and prints nothing (MCP clients read that output). `--service=auto|off|require` chooses: `auto` is the default, `off` forces the one-shot path, `require` refuses in English and German when no service answers. A busy service answers with exit code 75 and its text; a connection lost after acceptance is exit code 70.
- **What it keeps.** An event-sourced state of the member and directory map (the graph frontier), per owner file digests (only dirty files are rehashed), the environment digest, task keys and a result memo. A native file watcher (one Rust file, standard library only: FSEvents on macOS, inotify on Linux, ReadDirectoryChangesW on Windows) delivers changes; directories such as `node_modules` are excluded in the kernel, so 20,000 writes inside one deliver zero rows. After a restart the persisted FSEvents cursor replays the edits made while it was down (20 of 20 recovered, no rescan).
- **The fence is the correctness core.** Before it answers, a request writes a unique file into the fence directory and waits for its event; all earlier events on that stream are applied first, so an agent that edits and immediately runs sees its own edit. Trust is reported by `repo service status`: `exact` (events and fence), `verify` (every answer re-proved by `stat` of the closure's files, with a racy-window rehash) or `none`. It drops to `verify` when the start canary fails (a bind mount that forwards no host edits is caught this way), when a fence is missed, when the watcher dies, or permanently when the inotify watch limit is reached. After an event gap (overflow, must-scan, mount change) the scope is re-walked and remembered outputs are re-verified. The tool keeps the last word whenever the service has any doubt; the service is an accelerator on top of the tool caches, never the authority on whether a task is current.
- **Numbers** (macOS arm64, 10 cores, load 26 to 48, so absolute tails are inflated and the ratios are the reliable part; a synthetic workspace of 33,000 files and 1,500 projects): a warm no-op through the native client takes p50 11.6 ms at load 26 (p50 28.6, p90 78, p99 166 ms at load 46), the service side alone p50 8 to 12 ms, of which 11 ms are the fence; from an edit to the first tool process p50 37, p90 136 ms (fresh process without the service: 378 ms; with the measured custody added 280 to 335 ms); edit to dirty in the service p50 11.5 to 12.2 ms with FSEvents; 16 clients issue 181 to 362 requests per second with p99 59 to 219 ms and no refusal. The service costs about 120 MB resident and is ready 0.55 to 1.7 s after the start. The real CLI path end to end is projected, not measured.
- **Executing in the service.** Plain task commands run in the service only through one declared kind in the authority core: a grant (`worktree`, key digest, operations, request and concurrency limits) is created at the door only for the hidden executor entry of the service, from the private key file the service wrote (mode 0600 in a 0700 directory of the user). During a request the launches that the one-shot door computes for exactly these arguments become visible through one function; the grant never reaches a child. A law fails when a second reader of `launches` appears. Each refusal (14 codes) has an English and German text. Executors are off by default (`SEMIO_RESIDENT_EXECUTORS=n`); a command that the service may not execute runs in a pre-warmed one-shot worker (module load 0.3 to 0.5 ms instead of 0.7 to 2.3 s) or cold.
- **Tokens.** `repo service issue` mints a capability for an agent session (scopes, projects, expiry; 1 h by default, 24 h at most) and keeps the token in a private file; the record never carries it. Tokens are bearer tokens and the key file is the root of trust: any process of the same user that can read the key can mint any token, so the binding to an agent is an accident and audit control, not a security boundary.
- **Limits.** Windows keeps executors off; the Bazel path is declared through the same launches but not exercised; the real `runOwnedBuildInvocationV1` inside the held custody has not run; the service measured here is the prototype in an overlay, and the first live run decides.
