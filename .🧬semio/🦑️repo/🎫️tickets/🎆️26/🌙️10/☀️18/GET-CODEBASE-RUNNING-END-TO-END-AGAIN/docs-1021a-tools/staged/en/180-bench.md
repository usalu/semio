### 🏎️ Performance objectives: `repo bench`

Speed is a requirement with numbers, and the numbers are a table. `repo bench` measures them in the disposable copy that `repo incremental prepare` provisions, judges them against one SLO table and compares with a stored baseline. {{?bench::::The command is a staged set and must be applied after the resident service and the polyglot units. }}State: {{@bench}}.

```bash
repo bench list
repo bench run --slo=probe:cli-help --runs=25
repo bench run --slo=kind:edit --runs=5 --save-baseline=<report>
repo bench run --prepare --slo=all --max-load=1 --baseline=<report> --markdown=<file>
repo bench compare --current=<report> --baseline=<report>
```

- **The user goals** are exact: a warm no-op `run` or `test` answers in at most 300 ms (resident p95 is blocking; the one-shot median is advisory, goal 300 ms and gate 1,000 ms), an edit to the start of the rebuild takes at most 500 ms (resident p95 per language is blocking, the one-shot median advisory) and a second run hits the cache 100 percent (minimum over runs, blocking, for a build and a test target). Further objectives: `repo --help` p95 goal 200 ms, a cold scope graph gate of 5 minutes, a warm scope graph, peak memory goal 512 MiB, and the longest wait of a concurrent agent for an unrelated project (goal 1 s, gate 5 s). 32 objectives with 62 rows (objective times implementation) exist; 8 objectives (16 rows) are blocking and the rest advisory, because nothing is blocking that cannot be reached today. Objectives without a goal and a gate (edit to green, makespans) only record and are guarded by the baseline.
- **21 probes** go through the copy's own `repo` CLI: `repo --help`; the warm no-op for a build and a test target, one-shot and through the resident service; the edit to the start of the rebuild and to green for four language units (TypeScript, Rust, Go, Python; each edits one source file with a private-body line and restores it byte for byte, also on failure and cancellation); the scope graph cold (once, only on a copy this run prepared) and warm; the second-run hit ratio (Bazel's compact execution log or the Nx run record; uncached tasks are not counted); three concurrent agents; and the peak memory of the process tree.
- **Statistics are honest.** n, minimum, p50, p95, p99, maximum and mean; percentiles interpolate linearly (the inclusive method of Python's `statistics.quantiles` and NumPy's default); a statistic needs enough samples (p50 and mean 3, p95 20, p99 100), otherwise the row is `unproven: too few samples`. Failed commands are counted and left out. The start of a rebuild counts only from a tool marker line; without one the value is a bound (first output = lower, process exit = upper) and the row stays unproven unless the bound already decides it.
- **Verdicts**: `pass`, `warn` (gate met, goal not), `fail`, `recorded`, `unproven` with a reason (`no samples`, `too few samples`, `probe failed`, `service unavailable`, `not cold`, `host saturated`, `start unobserved`, `unsupported`). Host load per core is annotated (quiet below 0.5, saturated from 1.5): a time that misses its gate on a saturated host is `unproven` because load only inflates it, a met goal stays met. `--max-load=<per core>` refuses a busy host.
- **Baseline and comparison.** Per objective and implementation: `improved`, `same`, `regressed`, `inconclusive` (a regression on a saturated host), `incomparable` (another host class, platform-arch-cores, or an unproven side), `new`, `missing`, with a tolerance per objective (a relative share plus an absolute margin). `--save-baseline=<file>` stores the report (the report format is the baseline format). Blocking objectives that fail or regress make the exit code fail after the reports were written.
- **Output**: text or `--json`, `--file=<report>`, `--markdown=<file>` (a GitHub step summary), English or German, progress per probe and sample (`bench:<probe>:<tool>:<i>/<n>`), cancellation before every command. CI gets a job `bench` on Linux and macOS with `continue-on-error: true` first; it stores a new baseline only after a push to the default branch.
- **Open.** Until the resident service is applied the resident rows are `unproven (service unavailable)`; the start markers per tool must be calibrated on the first live edit run; the warm scope-graph gate of 2 s, the help p99 gate of 1 s and all tolerances are provisional; and the speed-up over the serial reference is collected but has no objective, because that reference follows the concurrent run and is warm.
