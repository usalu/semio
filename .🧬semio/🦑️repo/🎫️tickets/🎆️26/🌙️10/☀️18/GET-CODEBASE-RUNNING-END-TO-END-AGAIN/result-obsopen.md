## 1. Nested fixture hang (blocks "path custody") - ROOT CAUSE AND FIX
Wait found with a probe (nested outer/inner fixtures, step markers; `C/obsopen-tools/probe`, mirror only): the hang is not the inner fixture's open, it is the inner fixture's CLOSE after the OUTER fixture's `withMaintenance` ran inside the inner body.
- `withRepositoryCacheGraphFixtureV1` (`⚡️caching/…/🏪️store/🟦️.ts`) reopens its receiver epoch after every maintenance with `openEpoch()`, called in the CALLER's async context. `withRepositoryCacheStoreChildStorageV1` enrolls its child in `consumerFrames.getStore()`, i.e. in the frame of whoever called the maintenance. Called from inside the inner fixture's body, the reopened outer epoch (a task that lives until the OUTER fixture closes) is enrolled in the INNER consumer frame; the inner frame settles only when its pending set is empty, so the inner close waits for the outer close, which waits for the inner body to return: a self-deadlock, no timeout anywhere on the way (the law's 120 s bun timeout was the only bound).
- Fix (product, 2 anchored edits): `const home=AsyncLocalStorage.snapshot(),openEpoch=()=>home(async()=>{…})`: every epoch (first and every reopen) runs in the async context of the fixture's own consumer frame, whoever calls `withMaintenance`. Probe: base hangs (inner body done, "inner closed" never), snapshot variant 8/8 steps; a narrower variant (`consumerFrames.run(home,…)` only) still hung, because other async-local stores (controls, backings) leaked the same way.
- Bound: new helper `withinV1` (docstring `⏱️`) in the blocks law file; both nested-fixture awaits race a 60 s timer and fail with `Nested Graph fixture settlement exceeded 60000 ms` instead of wedging the law (and the whole bare file) until the 120 s test timeout.
- Laws: new law `observation block nested fixtures settle an outer maintenance that reopens beneath an inner fixture` (independent oracle: the filesystem: inner root removed after the inner close, outer receiver image replaced, outer still admits a consumer on the new image, outer root removed after its close) and the existing `path custody` law (now bounded). RED on base: `Nested Graph fixture settlement exceeded 60000 ms` (68 s); GREEN with the fix (both 2/0 in 50 s at load 40).

## 3. SIGINT children: regression found while verifying (progress `sigint` batch, G46)
After G46 the blocks `cancel`/`cancel-close` rows, the presence `terminal cancel`/`maintenance cancel` rows and the reuse `cancelled predicate` rows were red with `JSON Parse error: Unexpected EOF`: a child that simulates a cancel with `process.emit("SIGINT")` is now ended by the process' termination guard with status 130 as soon as its interrupted work settles, BEFORE it prints its report (it printed after the receiver returned). Fix in the 3 child scripts: the report is a synchronous `writeSync(1, …)` function registered once on `process.once("exit")` and called on the normal path; the receiver callback records the terminal primary before rethrowing; the parents expect status 130 for the cancel rows (named constant `interruptedStatusV1`) and 1 otherwise. Proven on the mirror: blocks `cancel`, `cancel-close`, `deadline` rows 3/0 (base after G46: 0/3).

## 5. Intermittent boot-session capture - ROOT CAUSE AND FIX
`readNativeBootSessionV1` (`/usr/sbin/sysctl -n kern.bootsessionuuid`) failed with `Complete owned separated capture required` in about a quarter of the fixture births on the mirror (10 of 28 on base before 19:10; the 1/40 rate is reproducible in a bare bun test with plain `spawn` + `settleOwnedChildV1`, `C/obsopen-tools/probe/lost.test.ts`).
- Evidence (instrumented settlement, mirror only): the child is gone from the process table at the first liveness tick (250 ms after the spawn); `child.exitCode` is 0, `child.stdout.readableEnded` true, but NO `exit`, NO `close` and no `data` event is ever delivered (bun 1.4.2 loses every event of a fast child; the event loop itself keeps ticking every 250 ms). After the 2 s grace `settleOwnedChildV1` settles it as `lost` with `code:null, signal:null`; the capture then built `{status:null,signal:null}` and died in the schema check with an error that says nothing about a lost child. Status and output of a lost child are unknown; the first reading (stall of the event loop) was disproved by the tick log.
- Fix (2 layers, closed typed vocabulary, schema first): (a) `settlement` schema `Lost` (const kind/message) + `LostCause`, `ownedChildLostErrorV1` / `isOwnedChildLostErrorV1` / type `OwnedChildLostV1`; the capture refuses a `lost` settlement with that error (`Owned child terminal events lost: <program>`, `cause {version:1,kind:"terminal-lost",program,pid}`) instead of a terminal without status; (b) storage schema `BootSessionRead` (`maximumAttempts: 3`) and `BootSessionReadCase`; `retryNativeBootReadV1(control, read, attempts)` repeats the idempotent read only after that cause, honouring the control between attempts, never after another failure. No other capture (non-idempotent commands) is repeated.
- Laws (independent oracles): settlement test `only a lost child is refused with the closed typed cause…` (SQLite `kind='lost'` per fixture child row, Ajv `LostCause`, negative cases, structural check of the capture glue); boot test `a boot session read repeats exactly after a lost child…` over `🧪️tests/🧫️fixtures/🔣️.json` (6 rows incl. all-lost, fault never repeated, fault after lost not repeated; SQLite computes attempts and result from the outcome list). RED on base (both files fail at import: the new exports do not exist), GREEN with the fix (settlement 4/0, boot 4/0).
- Honest rate statement: after the 19:10 mirror refresh (G46 landed meanwhile) the event loss did not recur: 0 of 16 on base and 0 of 30 + 100 bare reads with the fix (no `stayed open` notice in any log). The mechanism and the 1/40 isolated reproduction stand; a product run that sees the notice `Child process N (/usr/sbin/sysctl) ended but its output streams stayed open` now continues instead of failing.
