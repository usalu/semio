## Finding 1 (HIGH): the memo seals a slice nobody verified after its cursor -> every later identical request is served a stale graph
Code (live): `🧭️invocation/🕸️graph/🧠️memo/🚪️command/🟦️.ts` `planGraphWithMemoV1` starts the sealing child with the door's `SEMIO_BUILD_GRAPH_REQUESTED_AT` unchanged; the child's `refreshClosure` then serves `covered` (`🕸️graph/🕰️generations/🟨️.mjs` `refresh` -> `coverageOfV1`: any peer stamp with `atMs >= requestedAt`) without verifying a single fact, or `pinned` (a nested command bound to its outer invocation's pin, `readPinnedGenerationV1`). `📤️relevance/🟦️.ts` `writeGraphMemoSliceSidecarV1` seals that slice with the cursor taken by the parent (`openGraphMemoV1`), which can be minutes after the door time (capacity admission, executor boot).
Scenario: request R (door at t0) waits for admission; a peer's graph build starts observing at t1 > t0 and stats `pkg/a/src/index.ts`; the user saves that file at t2; R's executor opens the memo (cursor c at t3 > t2: the save is before the cursor, so the journal will never report it again) and starts the sealing child; the child is `covered` by the peer's stamp (t1 >= t0), serves generation G1 (old bytes), the sidecar seals G1 with cursor c. From now on every identical request gets `graph: … served from the memo`, the planner never runs, the edited file's project keeps its old node (old source digests/inputs) until some unrelated relevant change happens. The planner itself would re-infer it on the next request (its own coverage rule only serves requests older than the stamp; the memo wrongly extends that to all future requests). Same with `pinned`: the pin's verification time is the outer invocation's, and `SEMIO_BUILD_GENERATION_PIN`/`INVOCATION_PID(S)` are denied from the memo key, so a top-level request hits the record a nested command sealed.
Likelihood: needs a peer graph build overlapping the sealing (2nd identical) run; normal in this fleet (several agents + gate run graph builds concurrently, admission waits of minutes are logged).
Law `🧠️memo/🧪️tests/🕰️verified/🟦️.ts` (new, graph-free, real generation store + mock repository host + real `planGraphWithMemoV1`/`openGraphMemoV1`/sidecar writer, exact fake journal that reports nothing because every edit precedes the next cursor):

## Investigated and cleared (no finding; the argument, so nobody re-audits it)
- memo journal race: `since`/`cursor` are fenced (the client writes a fence file and waits for its own event), so FSEvents latency cannot hide a save made before a lookup; a hit advances the cursor to the fence of the vouching answer; seal uses the cursor taken before the child.
- memo `closure` = `none`: matches the planner, whose `holdsByStat` skips `closure` rows too; the command walks behind them are `derived` rows whose supports live in pseudo owners that `scopeWithDerivedV1` puts into the slice. `stamp` = `none` is covered by the implementation identity in the key. `registry` rows: the registry source `📋️build-owners.json` lies in the root directory, which is always relevant.
- memo pointer check covers `invalidate` and `refreshMetadata` (both publish a new pointer); identity (catalog providers) comes from root-level files (relevant).
- memo key: `--parallel`/`SEMIO_BUILD_PARALLEL` are read nowhere in graph planning (only `📥️caller` treats `--parallel` as a resource); the yield/requested-at names do not shape the slice.
- jobskey: `request.parallel` is consumed by no planner code; grantenv: the host capacity plan is read only in the run phase (`bazelHostPlanV1` after publish), not by the planner; ignoredenv: no declared task `env` input in any project config names an ignored variable (grep of all `"env": "<NAME>"` rows), so no fingerprint head carries an unrecorded value.
- planfp: the copy is racy-aware (`racy` rows always recaptured), torn copies retried, a vanished file removes the record and replans, a crash between plan record and refresh self-heals (the manifest is written last; a replaced destination's mtime differs); hashed paths are fingerprinted by content (`bazelSourceIdentityV1`), not by stat identity; the plan-reuse journal cursor is taken before the planner and changed rows are re-statted (k/K rows included).
- racy: identity is computed only after the skip check; kind rows never set it.
- Low, pre-existing, no fix staged: the snapshot's reuse rule compares mtime/ino/size but not ctime, so an in-place same-size write that restores the previous mtime (`cp -p`/`touch -r` onto the same inode) keeps a stale copy; needs an adversarial tool sequence.
