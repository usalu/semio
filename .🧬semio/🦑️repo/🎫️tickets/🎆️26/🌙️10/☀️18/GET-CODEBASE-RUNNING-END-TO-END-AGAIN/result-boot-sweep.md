Progress and cancellation: every recovery step publishes `boot-recovery:<stage>:<done>/<total>:<target>` through the control's `publish`; the engine honours `control.signal` between steps and writes `abort` to the ledger; a failing sweep is reported as `boot-recovery:failed:<reason>` and never blocks the command, cancellation always propagates. Ledger: `<cache>/boot-recovery/<sha256>.jsonl` (append-only, torn-tail/corrupt tolerant, compacted, fsync + directory flush through `flushNativeDirectoryV1`, so Windows works).

## Design (schema first, multi implementation)
- Schema `R/🧬️schema/🔣️.json` (generated by `boot-sweep-tools/build_schema.py`): Protocol constants (tolerance, phases, bounds, scopes `stable|host-boot|image-attach|process` of every persisted identity family, boot epoch sources per platform, leaked-image policy), closed Fact/Step/Plan/LedgerEvent/Corpus.
- Pure planner `R/📋️plan` (no fs, clock, process table), observer `R/📡️observe` (only lstat/readdir/read), executor `R/🧯️act` (confined plain-file effects + kernel-authority effects), ledger `R/📒️ledger`, clock `R/🕰️clock` (boot epoch darwin sysctl, linux /proc/stat, win32 CIM), orchestration `R/🩺️heal`, API `R/🟦️.ts`.
- Language-agnostic test: `R/🧪️tests/🔣️.json` corpus (58 plans, 11 identity, 11 backing, 10 epoch, 10 ledger cases) replayed by the TS planner and by an independent Python re-implementation `R/🧪️tests/🐍️oracle.py`; third-party cross-checks: Ajv (strict) validates corpus/plans/mutations, in-memory SQLite CASE tables re-derive publication, ticket and leaked-image decisions.
