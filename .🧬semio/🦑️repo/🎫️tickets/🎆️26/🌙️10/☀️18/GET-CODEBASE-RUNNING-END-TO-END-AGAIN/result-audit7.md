## Finding 1 (MEDIUM): a farm worker writes content of OTHER generator contracts under the key its parent computed; a later revert serves the stale record
- Code (live `📦️project-nodes/🟨️.mjs`): `emojiProjectJsonNodes` reads the generator contracts of `📚️library/🔣️taxonomy.json` ONCE (`readTaxonomyProjectionV1`, outside every project scope) and keys every project record with `projectAuthority = sha256([contracts])` (`head[0]`); the contracts are therefore no row of any record, only part of its key. The farm session hands the worker the registry, command inputs, roots, but not the contracts: `createProjectInferenceEnvironmentV1(session)` reads the taxonomy AGAIN when the worker opens (seconds to minutes later: the farm engages after 24 misses, recycled workers re-open after every 96 projects or a memory recycle), and `produceProjectRecordV1` writes the record under the parent's `job.head`. The parent's re-check of an adopted record (`lookup` → `sharedObservationsHoldV1(header.observations)`) checks only the record's rows, so nothing compares the contracts.
- Scenario: a peer edits `generatorContracts` (any lane touching the 1.3 MB taxonomy; 282 KB of it are contracts) while a refresh runs; every worker opened or recycled after the edit infers with contracts C2 and stores the records under the key of C1. The parent's graph receipt fails (its own taxonomy row moved), but the records stay in `np/`. The peer reverts (or `git checkout`s) the taxonomy: the next run computes the C1 key again, the adopted records' rows hold, and the graph is served with targets/generated outputs of C2 until each project's own inputs change. In-process inference cannot do this (one read keys and computes every project), so this breaks farmid's own contract ("the farm changes how fast a record appears, never what it holds").
- Laws (appended to `🏊️project-farm/🧪️tests/🪆️captured/🟦️.ts`): (a) a worker environment opened from a session that carries the parent's contracts uses exactly those (subprocess with the real `libraryBootstrap`, the real `createProjectInferenceEnvironmentV1` under `observeInferenceSnapshotV1` on the real root; independent oracle: Python reads the disk contracts, proves they differ from the parent's, and computes the parent's `head[0]`, which must equal sha256 of what the worker uses), and refuses a session without contracts; (b) `openProjectFarmV1` hands its workers the contracts it was given (the session file deserialized at the worker's `init`). RED on live: (a) `Expected - 5 / Received + 2351` (the worker used the 35 disk contracts), (b) session without contracts. GREEN with the fix.
- Fix (`contracts`, 6 files): `projectGeneratorContractsV1(workspaceRoot)` is the one reader (graph construction and the generation deriver, which keeps reading the live taxonomy as before, in the same observation scope); the farm session (version 3) carries the parent's `contracts`; `createProjectInferenceEnvironmentV1` requires them (`Generator contracts of the parent inference required`); `openProjectFarmV1` takes `contracts` (typed required in `🟨️.d.mts`); the existing farm laws pass `contracts:{}`. No record key, stamp or content changes.

## Finding 2 (LOW): a killed graph child leaves its 19.6 MB snapshot copy, staging and session directories in the temp directory forever
- Code (live `🏊️project-farm/🟨️.mjs`, `🏊️pool/🟨️.mjs`): `semio-graph-farm-image-*` (the snapshot text, 19.6 MB in production), `semio-graph-farm-*` (staging of in-flight leaves) and `semio-farm-session-*` (serialized session + job files) are removed only by `farm.close()` in the `finally` of the inference loop. A graph child that is killed (OOM, budget kill, `kill` of a build chain, SIGTERM of a terminated build: Bun runs no `finally` then) leaves all three; nothing in the repository removes them (`cache gc`'s `tmps` unit only sweeps `.cache/b/a/m/nx/tmp`). Live today: 24 such directories in the user temp directory (test-sized so far; the farm only works in production since G44).
- Security (asked, holds): `mkdtemp` 0700 directory + `wx` 0600 file under `realpath(tmpdir())`, opened per worker with `O_NOFOLLOW`; the loader verifies the digest; on Linux `/tmp` the 0700 directory keeps other users out.
- Law (appended to `🔒️farm-close/🟦️.ts`): a REAL farm in a subprocess starts its pool from a captured stand-in snapshot and is `SIGKILL`ed; a second farm process starts its pool in the same temp directory; the killed farm's three directories must be gone, a directory named with a RUNNING pid and a name the farm does not write must stay. RED on live: `+ semio-graph-farm-izQyNN, semio-graph-farm-image-JwS1XJ, semio-farm-session-werpGu`. GREEN with the fix.
- Fix (`reclaim`, 5 files, schema-first): `Policy.temporaryDirectories` (prefixes per kind + the pattern with the `pid` group); `createFarmTemporaryDirectoryV1(kind)` names every farm directory `<prefix><pid>-XXXXXX` and, on the first call of a process per directory, removes those whose process is gone (`process.kill(pid, 0)` answering `ESRCH`; any other answer, a malformed name or a live pid keeps it, so a platform that cannot tell never deletes); used for the image, the staging bases and the session directory. Untagged leftovers from before the landing stay (remove `$(getconf DARWIN_USER_TEMP_DIR)semio-{graph-farm,farm-session}-??????` by hand once if wanted).

## No finding (reviewed against the live code)
- Adopted records vs a peer edit during a refresh (beyond Finding 1): after `prepare` the parent runs `lookup` again on the adopted record (`header.digest === digest`, then `sharedObservationsHoldV1`/`current` of every row, then `reusable` incl. `inferenceInventoryReferencesHoldV1`), exactly as for a record a previous run left; a worker that read a file after a peer edit records the NEW fact, which holds on the tree the parent sees, and on a revert it no longer holds (re-inferred). Contradictory facts between projects are legitimate in snapshot scope and the outer receipt re-checks everything. The other head parts are safe: `registryDigest` (the registry comes from the session), `commandRevision` (the symbolic closure is resolved lazily INSIDE the project scope, its derived rows are in the record), `assemblyAuthority` (the worker's fresh native cache records its native facts as rows; more rows than in-process = more conservative). Only the contracts are read outside every project scope in the worker AND only keyed in the parent (Finding 1). `selectedTargets` is `undefined` in the worker's key: for a parent with selected targets the keys differ and the record is simply not reused (no stale serve).
- Record identity: the worker's announced `records` identity is `inferenceRecordIdentityV1()` sealed after its environment opened; the implementation is the digest its own loader verified; the parent compares both at every worker start, and in a non-captured parent (`launch:null`) a worker of other module bytes differs in its load-authority digest (refused).
- Recycle race (farmid (a)): `retired()` runs only from an `exit` event or synchronously when `exitCode` is already set, which in Node/Bun means `exit` was emitted and `lose()` already took the job; the adoption is a microtask continuation of `run()`'s settle, before any `exit` macrotask.
- fd inheritance into grandchildren (macOS measured, `probe/fdprobe2.mjs` with the pinned Bun 1.4.2): a worker started with `[ignore, inherit, inherit, <file fd>, ipc]` reads fd 3 and keeps it; grandchildren it starts through `Bun.spawnSync`, `child_process.execFileSync` and `child_process.spawn` see NO snapshot descriptor (their fd 3 is a FIFO of their own runtime, inode ≠ snapshot inode) and no `NODE_CHANNEL_FD` (Bun removes it from `process.env`). Linux: Bun's own spawn closes every descriptor above the mapped stdio in the child (not run here: no container runtime, as linuxdc reported).
- Windows (not runnable here): descriptor 3 = a regular file handle + `ipc` on 4 rides libuv's `lpReserved2` CRT descriptors, the same mechanism the pre-existing captured commands use for their pipe on 3; the decisive law already exists (`🪆️kernel-role`: real spawn, real stream loader, real channel on 4) and must run in Windows CI. Residual risk to watch there: the inherited handle is inheritable inside the worker, so a long-lived grandchild started by inference would keep the snapshot file open and `close()`'s `rmSync(image.directory)` (not in a `try`) could fail; with `reclaim` a later farm removes it once the process is gone.
- obsrows2 `retention-ledger` (closure classifier): it only classifies `snapshots/retained.ledger` for the storage closure proof (validated `{at,bytes}` in the read worker); `snapshots/` is no retirement group (`groupCoordinate` admits only `inference/...` role directories), so the ledger is never a retirement candidate and no build input changes; the visible effect is that optional cache maintenance runs again instead of throwing. Its temp sibling `retained.ledger~xxxxxxxx` (crash between write and rename) would again throw `Unknown closure reference publication` and block maintenance, as any other crash leftover in the store does today (pre-existing fail-closed design, not new).
