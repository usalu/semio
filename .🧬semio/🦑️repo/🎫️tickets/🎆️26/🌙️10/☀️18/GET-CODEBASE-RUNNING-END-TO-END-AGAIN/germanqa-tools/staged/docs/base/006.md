# 🚀️ Launcher

`repo` without a JavaScript runtime installed. The launcher is the small native program behind the `repo` command: it finds the repository, provisions the pinned JavaScript runtime itself from a schema-declared registry, and hands the process over to the repository implementation with the exact arguments, the runtime's own PID, streams, signals and exit code. Nobody types `bun` anymore; the runtime is an adapter that the registry can swap.

```
repo --version
repo preflight
repo run @semio-tech/repo-cli-go:test
repo ./📜️script.ts build
```

## 🧱️ How it works

1. **Root.** The nearest ancestor of the working directory (start: `SEMIO_WORKSPACE_ROOT`, `REPO_ROOT`, the working directory; at most 32 levels) with a regular `📋️project.json` next to a `package.json` that declares `workspaces`. A malformed `package.json` is refused, never skipped.
2. **Registry.** `🗂️registry/🔣️.json` (schema next to it) pins every runtime: version, the archive per operating system, architecture and C library with its size and SHA-256, how the runtime starts a script, and which implementation entries exist. It also holds the EN/DE texts. The registry belongs to the checkout, so a checkout pins its own runtime; bumping the runtime is a registry edit.
3. **Provision.** A runtime is looked up in the tools partition (`.cache/b/t/m/<runtime>/<sha256>/`, written by the build implementation's own tools setup) and then in the user cache (`SEMIO_RUNTIME_CACHE`, else the operating system's cache directory under `semio/runtimes/`). When it is absent it is downloaded once (progress on stderr, Ctrl+C cancels, concurrent starts wait for one download), size and SHA-256 are checked before anything is unpacked, the executable is extracted with a size bound, its version is probed, and the directory is published with one atomic rename. Nothing is installed on a failed check. `SEMIO_RUNTIME_MIRROR` points at a mirror (https, or loopback http); the pins still decide.
4. **Hand-over.** The launcher starts `runtime [fixed arguments] [mapped options] script [entry prefix] arguments…`. On macOS, Linux and in the devcontainer it replaces itself with the runtime; on Windows it runs the runtime as a child that shares the console, forwards interrupts and settles with its exit code. The runtime directory and the launcher directory lead the child's `PATH`, so every nested command resolves the same pinned runtime and the same `repo`.

## 🧭️ Routes

| Arguments | Route | What starts |
|---|---|---|
| `run`, `run-many`, `affected`, `exec`, `watch`, `dependencies`, `cargo`, `tools`, `reset`, `cache`, `preflight`, `show`, `graph`, `dashboard`, or a leading `--tool` | `build` | the build implementation (`implementation.entries.build`) |
| nothing, `--help` or `-h` first | `build` | the same front door: the one help of the operations catalogue (the full `repo` appends the native commands) |
| `dev mcp stdio os …` | `workspace` | the OS MCP workspace script (`implementation.entries.workspace`) |
| `[--watch] [--cwd <dir>] <file>.ts\|.mjs\|.js …` | `script` | that script through the runtime; the options map to the runtime's own flags (`launch.options`) |
| `mcp` | `mcp` | the full native command (stand-alone launcher: refuses with the install command) |
| anything else | `domain` | the full native command (stand-alone launcher: refuses with the install command) |

`dashboard` is the human control plane: it is only a routed verb here (it expands to the dashboard run target); agents never start it, and no staged code, test or script runs it.

The routes are the shared native entrypoint vectors (`⌨️cli/🧫️fixtures/🚪️entrypoint`); the Go full command and this launcher plan with the same function.

## 🔌️ Resident service hook

`Host.Forward` is the one place a resident build service attaches: `Execute` offers every `build` route to it before the language, the registry runtime or any download is touched. It answers `handled=true` with the exit code, or `handled=false` (silently) to continue with the normal start. It is nil by default.

## 🏷️ Versions and language

`repo --help` is the help of the operations catalogue, nothing else: the launcher starts the build front door for it, so `repo --help`, `repo -h`, `repo` and `bun repo --help` print the same text and no command list is kept in the launcher. The full `repo` appends the commands of its own command tree (`repo <command> --help`, `dashboard`, `dev mcp stdio os`) after it.

`bun repo --version` (the root script starts the build entry as a script route with its prefix) is answered by the launcher with the same text; any other script start is untouched.

`repo --version` prints the launcher version with its registry contract, every runtime the entries use (pinned version, and its path when provisioned; it is never fetched for this), and the implementation version (`🧰️framework/🛍️products/🦑️repo/package.json`). There is no default language: `--lang`, `SEMIO_LANGUAGE`, `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, then the system language list decide (the shared protocol and fixture of the build language module). When none resolves, the launcher refuses in every offered language and says how to choose. A start with a provisioned runtime prints nothing and needs no language.

## 📌️ Runtime guard

Nobody has to start the pinned runtime by hand, whatever Bun is on the `PATH`. The checkout's `bunfig.toml` preloads `📌️runtime-pin/📜️script.ts` for `bun <script>` and for `bun test` (`[test] preload`). When the running Bun is not the version the registry pins, the guard reads the exact command line of the process (`/proc` on Linux, the kernel's process arguments on macOS, `GetCommandLineW` on Windows; all through `bun:ffi`) and runs it again, with the same flags and arguments and the exit code of the child, under the provisioned pinned Bun (tools partition, then user cache; an install counts only with a receipt that names the pinned archive). When it is not provisioned yet, the `repo` launcher on the `PATH` gets the script as a script route, or the tests through `repo tools exec --light bun -- test …`, and provisions it. Without a launcher the start is refused with exit code 2 and the install command, in the chosen language or in every language when none is chosen. A start that was already re-run by a guard and still is not pinned is refused instead of looping; the marker (`SEMIO_RUNTIME_GUARD`) is cleared as soon as the pinned Bun runs, so nested starts of another Bun are guarded again. The Go launcher and this guard read the one registry; the shared fixture `🧫️fixtures/📌️runtime-pin` is judged by both and by an independent Python implementation (`🧪️tests/📌️runtime-pin-contract`). `bunfig.toml` is only read in the directory a Bun starts in: start repository work from the repository root, or use `repo`.

## 📥️ Install

One command per platform builds the launcher from the checkout. It needs no Go and no JavaScript runtime installed: the installer is stage 0 of a bare machine and fetches the pinned Go itself (curl, tar and a SHA-256 tool; Windows PowerShell 5.1 or 7):

- macOS, Linux, devcontainer: `bash "🧰️framework/🛍️products/🦑️repo/🔨️modules/🚀️launcher/📥️install/🐚️.sh"`
- Windows: `powershell -NoProfile -ExecutionPolicy Bypass -File "🧰️framework\🛍️products\🦑️repo\🔨️modules\🚀️launcher\📥️install\🔵️.ps1"`

**Pinned Go, no prebuilt launcher.** The Go toolchain is found in this order: `go` on the `PATH` that reports exactly the pinned version, the repository tools partition (`.cache/b/t/m/native/go/<version>/<host>-<sha16>/bin/go`), the user cache (`SEMIO_GO_ROOT`, else `${XDG_DATA_HOME:-~/.local/share}/semio/go/v<version>`, on Windows `%LOCALAPPDATA%\semio\go`). Otherwise the pinned archive is downloaded from the row of `🔩️native/🥾️bootstrap/🧬️schema/🔣️.json` (https only; `SEMIO_GO_MIRROR` may name an https or loopback http directory), its SHA-256 is checked before it is unpacked, concurrent installers wait for one lock, the toolchain is published with one rename, progress is printed (a progress bar on a terminal) and Ctrl+C exits with 130 and leaves no partial directory, lock or launcher. The launcher is then built from the checkout with `GOTOOLCHAIN=local`, `GOWORK=off`, `-trimpath`. Why not a prebuilt, checksummed launcher per platform: the repository has no release host, a prebuilt binary would need signing and a release process of its own, it would age against the registry in the checkout, and it adds a second trust chain; the pinned Go rows (the same rows the toolchain-pins law ties to the toolchain policy) are the only trust the build needs and the result is reproducible.

From a bare machine use the full bootstrap (`🔩️native/🥾️bootstrap/🐚️.sh setup` or `🔵️.ps1 setup`): it installs Node, Go, rustup and uv from pins, builds this launcher, and then runs `repo run repo-mcp:install`, which installs the full native `repo` command (that command embeds this launcher). No Bun is installed by hand anywhere.

## 🔌️ Another runtime

A runtime is a `runtimes.<name>` row: `version`, `executable` names, a `probe`, a `download` (https base, `zip`, the member inside the archive), `launch.before` (fixed leading arguments), `launch.options` (the flags of `watch` and `cwd`), `launch.environment`, and its `distributions`. Select it with `selected`, per entry with `entry.runtime`, or per run with `SEMIO_RUNTIME=<name>`. The launcher knows nothing else about Bun.

## 🔁️ Registry contract and busy service

The registry carries a `contract` number that is read before anything else: a registry of another contract is refused as such (never as a malformed field) with the exact command that rebuilds and reinstalls the launcher (`📥️install/🐚️.sh`, `🔵️.ps1` on Windows), in every language. A change of the registry schema must raise the contract: the schema digest (prose left out) is pinned next to the contract in the launcher fixture (`registryShape`) and `🗂️registry-contract` fails otherwise. The one install location is `${XDG_DATA_HOME:-$HOME/.local/share}/semio/launcher/bin`; the installer names every other `repo` on the `PATH` with the `ln -sf` that keeps one copy. A resident service that refuses with "busy, later" is asked again with the restart policy of the build (`restart.policy` of the registry: the format stamp protocol, 6 restarts, 0.25/1/4/12/30/30 s, one notice per restart in every language); after the last restart the exit code is 75, and 130 when the caller cancels.

## 🧪️ Tests

Language-agnostic vectors: `🧫️fixtures/🔣️.json` (selection, script options, launch vectors, PATH, provisioning mutations), the shared entrypoint vectors, the shared language fixture and the shared workspace corpus. Third-party references: Ajv validates the registry against its schema (`🗂️registry-schema`), the SQLite and Ajv oracles of the entrypoint case judge the route, and the language case reads the same rows as the TypeScript resolver.

`🗂️registry-contract`, `🗂️registry-schema`, `🧭️route-contract`, `🧭️root-contract`, `🗣️language-contract`, `📥️provision-contract`, `🏗️entry-contract`, `🔖️version-contract`, `📥️install-contract` (the installer against a synthetic Go archive and a loopback mirror: one download, checksum before unpacking, reuse, refusals, cancellation; SHA-256 checked with `shasum` as the independent reference), `🧱️cache-isolation`, `📌️runtime-pin-contract` (the runtime guard: selection, verified installs, the decision table and the command-line readers, against a shared fixture, the Go launcher and an independent Python oracle).

# 🚀️ Launcher (Deutsch)

`repo` ohne installierte JavaScript-Laufzeit. Der Launcher ist das kleine native Programm hinter dem Befehl `repo`: Er findet das Repository, stellt die gepinnte JavaScript-Laufzeit aus einer schema-deklarierten Registratur selbst bereit und übergibt den Prozess mit den genauen Argumenten an die Repository-Implementierung, mit PID, Strömen, Signalen und Exit-Code der Laufzeit. Niemand tippt mehr `bun`; die Laufzeit ist ein Adapter, den die Registratur austauschen kann.

## 🧱️ Ablauf

1. **Wurzel.** Das nächste übergeordnete Verzeichnis des Arbeitsverzeichnisses (Start: `SEMIO_WORKSPACE_ROOT`, `REPO_ROOT`, Arbeitsverzeichnis; höchstens 32 Ebenen) mit einer regulären `📋️project.json` neben einer `package.json`, die `workspaces` deklariert. Eine fehlerhafte `package.json` wird abgelehnt, nie übersprungen.
2. **Registratur.** `🗂️registry/🔣️.json` (Schema daneben) pinnt jede Laufzeit: Version, das Archiv je Betriebssystem, Architektur und C-Bibliothek mit Größe und SHA-256, wie die Laufzeit ein Skript startet und welche Implementierungs-Einstiege es gibt. Sie enthält auch die EN/DE-Texte. Die Registratur gehört zum Checkout; ein Checkout pinnt also seine eigene Laufzeit, und ein Laufzeit-Update ist eine Änderung der Registratur.
3. **Bereitstellen.** Die Laufzeit wird in der Werkzeug-Partition (`.cache/b/t/m/<Laufzeit>/<sha256>/`, geschrieben vom Werkzeug-Setup der Build-Implementierung) und dann im Benutzer-Cache gesucht (`SEMIO_RUNTIME_CACHE`, sonst das Cache-Verzeichnis des Betriebssystems unter `semio/runtimes/`). Fehlt sie, wird sie einmal geladen (Fortschritt auf stderr, Strg+C bricht ab, gleichzeitige Starts warten auf einen Download), Größe und SHA-256 werden vor dem Entpacken geprüft, die ausführbare Datei wird größenbegrenzt entpackt, ihre Version geprüft und das Verzeichnis mit einer atomaren Umbenennung veröffentlicht. Bei einer fehlgeschlagenen Prüfung wird nichts installiert. `SEMIO_RUNTIME_MIRROR` zeigt auf einen Spiegel (https oder Loopback-http); die Pins entscheiden weiterhin.
4. **Übergabe.** Der Launcher startet `Laufzeit [feste Argumente] [abgebildete Optionen] Skript [Einstiegs-Präfix] Argumente…`. Auf macOS, Linux und im Devcontainer ersetzt er sich durch die Laufzeit; unter Windows läuft die Laufzeit als Kindprozess mit der Konsole des Launchers, Unterbrechungen werden weitergereicht und der Exit-Code übernommen. Das Laufzeit- und das Launcher-Verzeichnis stehen vorn im `PATH` des Kindes, damit jeder verschachtelte Befehl dieselbe gepinnte Laufzeit und dasselbe `repo` findet.

## 🧭️ Routen

`run`, `run-many`, `affected`, `exec`, `watch`, `dependencies`, `cargo`, `tools`, `reset`, `cache`, `preflight`, `show`, `graph` und alle weiteren Operationen des Operationskatalogs (die Verben werden aus dem Katalog gelesen, nicht von Hand geführt) sowie `dashboard` und ein führendes `--tool` gehen in die Build-Implementierung (`build`); `dev mcp stdio os …` ins OS-MCP-Workspace-Skript (`workspace`); kein Argument, `--help` oder `-h` als erstes gehen ebenfalls in die Vordertür (die eine Hilfe des Operationskatalogs; der vollständige `repo` hängt die nativen Befehle an); `[--watch] [--cwd <Ordner>] <Datei>.ts|.mjs|.js …` startet das Skript über die Laufzeit (`script`, die Optionen bildet die Registratur auf die Flags der Laufzeit ab); `mcp` und alles andere sind der vollständige native Befehl (der eigenständige Launcher verweigert mit dem Installationsbefehl). `dashboard` ist die Bedienoberfläche für Menschen; Agenten starten sie nie.

## 🔌️ Hook für den residenten Dienst

`Host.Forward` ist die eine Stelle, an die sich ein residenter Build-Dienst hängt: `Execute` bietet ihm jede `build`-Route an, bevor Sprache, Laufzeit oder Download berührt werden. Er antwortet `handled=true` mit dem Exit-Code oder (still) `handled=false`, um normal zu starten. Standardmäßig ist er nil.

## 🏷️ Versionen und Sprache

`repo --help` ist die Hilfe des Operationskatalogs und sonst nichts: Der Launcher startet dafür die Build-Vordertür, also geben `repo --help`, `repo -h`, `repo` und `bun repo --help` denselben Text aus; der Launcher führt keine eigene Befehlsliste. Der vollständige `repo` hängt danach die Befehle seines eigenen Befehlsbaums an (`repo <Befehl> --help`, `dashboard`, `dev mcp stdio os`).

`bun repo --version` (das Root-Skript startet den Build-Einstieg als Skript-Route mit seinem Präfix) beantwortet der Launcher mit demselben Text; jeder andere Skript-Start bleibt unberührt.

`repo --version` nennt die Launcher-Version mit ihrem Registratur-Vertrag, jede Laufzeit der Einstiege (gepinnte Version und, wenn bereitgestellt, ihren Pfad; dafür wird sie nie geladen) und die Version der Implementierung. Es gibt keine Standardsprache: `--lang`, `SEMIO_LANGUAGE`, `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, dann die Sprachliste des Systems entscheiden. Löst keine auf, verweigert der Launcher in jeder angebotenen Sprache und nennt die Wege zur Wahl. Ein Start mit bereitgestellter Laufzeit gibt nichts aus und braucht keine Sprache.

## 📌️ Laufzeit-Wächter

Niemand muss die gepinnte Laufzeit von Hand starten, egal welches Bun im `PATH` liegt. Die `bunfig.toml` des Checkouts lädt `📌️runtime-pin/📜️script.ts` vorab für `bun <Skript>` und für `bun test` (`[test] preload`). Ist das laufende Bun nicht die Version, die die Registratur pinnt, liest der Wächter die genaue Kommandozeile des Prozesses (`/proc` unter Linux, die Prozessargumente des Kernels unter macOS, `GetCommandLineW` unter Windows; alles über `bun:ffi`) und führt sie mit denselben Optionen und Argumenten und dem Exit-Code des Kindes erneut unter dem bereitgestellten gepinnten Bun aus (Werkzeug-Partition, dann Benutzer-Cache; eine Installation zählt nur mit einem Beleg, der das gepinnte Archiv nennt). Ist es noch nicht bereitgestellt, bekommt der `repo`-Launcher im `PATH` das Skript als Skript-Route oder die Tests über `repo tools exec --light bun -- test …` und stellt es bereit. Ohne Launcher wird der Start mit Exit-Code 2 und dem Installationsbefehl abgelehnt, in der gewählten Sprache oder in allen Sprachen, wenn keine gewählt ist. Ein Start, den ein Wächter schon erneut ausgeführt hat und der immer noch nicht gepinnt ist, wird abgelehnt statt zu kreisen; die Markierung (`SEMIO_RUNTIME_GUARD`) wird gelöscht, sobald das gepinnte Bun läuft, damit verschachtelte Starts eines anderen Bun wieder bewacht werden. Der Go-Launcher und dieser Wächter lesen dieselbe Registratur; die gemeinsame Fixture `🧫️fixtures/📌️runtime-pin` wird von beiden und von einer unabhängigen Python-Implementierung beurteilt (`🧪️tests/📌️runtime-pin-contract`). Die `bunfig.toml` wird nur im Startverzeichnis eines Bun gelesen: Arbeit am Repository vom Repository-Wurzelverzeichnis aus starten oder `repo` verwenden.

## 📥️ Installation

Ein Befehl je Plattform baut den Launcher aus dem Checkout; weder Go noch eine JavaScript-Laufzeit muss installiert sein: Der Installer ist Stufe 0 eines leeren Rechners und holt das gepinnte Go selbst (curl, tar und ein SHA-256-Werkzeug; Windows PowerShell 5.1 oder 7): siehe die Befehle oben. Go wird in dieser Reihenfolge gefunden: `go` im `PATH` mit genau der gepinnten Version, die Werkzeug-Partition des Repositorys, der Benutzer-Cache (`SEMIO_GO_ROOT`, sonst `${XDG_DATA_HOME:-~/.local/share}/semio/go/v<Version>`, unter Windows `%LOCALAPPDATA%\semio\go`); sonst wird das gepinnte Archiv aus der Zeile von `🔩️native/🥾️bootstrap/🧬️schema/🔣️.json` geladen (nur https; `SEMIO_GO_MIRROR` darf auf ein https- oder Loopback-http-Verzeichnis zeigen), seine SHA-256 vor dem Entpacken geprüft, gleichzeitige Installer warten auf eine Sperre, die Toolchain mit einer Umbenennung veröffentlicht, Fortschritt ausgegeben, und Strg+C endet mit 130 ohne Teilverzeichnis, Sperre oder Launcher. Warum kein vorgebauter Launcher je Plattform: Das Repository hat keinen Release-Host, ein fertiges Programm bräuchte eigene Signatur und einen eigenen Release-Prozess, würde gegen die Registratur im Checkout altern und fügte eine zweite Vertrauenskette hinzu; die gepinnten Go-Zeilen sind das einzige Vertrauen, das der Bau braucht, und das Ergebnis ist reproduzierbar. Auf einem leeren Rechner nimm das vollständige Bootstrap (`🔩️native/🥾️bootstrap/🐚️.sh setup` oder `🔵️.ps1 setup`): Es installiert Node, Go, rustup und uv aus Pins, baut diesen Launcher und führt dann `repo run repo-mcp:install` aus, das den vollständigen nativen Befehl `repo` installiert (er enthält diesen Launcher). Nirgends wird Bun von Hand installiert.

## 🔁️ Registratur-Vertrag und ausgelasteter Dienst

Die Registratur trägt eine `contract`-Nummer, die vor allem anderen gelesen wird: Eine Registratur eines anderen Vertrags wird als solche abgelehnt (nie als fehlerhaftes Feld), mit dem genauen Befehl, der den Launcher neu baut und installiert (`📥️install/🐚️.sh`, unter Windows `🔵️.ps1`), in allen Sprachen. Jede Änderung des Registratur-Schemas muss den Vertrag erhöhen: Der Schema-Digest (ohne Prosa) ist in der Launcher-Fixture (`registryShape`) neben dem Vertrag festgehalten, sonst schlägt `🗂️registry-contract` fehl. Der eine Installationsort ist `${XDG_DATA_HOME:-$HOME/.local/share}/semio/launcher/bin`; der Installer nennt jedes andere `repo` im `PATH` mit dem `ln -sf`, das nur eine Kopie behält. Ein residenter Dienst, der mit "ausgelastet, später" ablehnt, wird mit der Neustart-Richtlinie des Builds erneut gefragt (`restart.policy` der Registratur: das Formatstempel-Protokoll, 6 Neustarts, 0,25/1/4/12/30/30 s, je Neustart ein Hinweis in allen Sprachen); nach dem letzten Neustart ist der Exit-Code 75, bei Abbruch des Aufrufers 130.

## 🧪️ Tests (Deutsch)

Sprachneutrale Vektoren: `🧫️fixtures/🔣️.json`, die gemeinsamen Einstiegsvektoren, die gemeinsame Sprachfixture und das gemeinsame Workspace-Korpus; Drittreferenzen: Ajv (Registratur-Schema) und SQLite (Routen). Jeder Text des Launchers existiert in Englisch und Deutsch; kein Fehlertext wird roh ausgegeben.

## 🔌️ Andere Laufzeit

Gewählt wird sie über `selected`, je Einstieg über `entry.runtime` oder je Lauf über `SEMIO_RUNTIME=<name>`. Der Launcher weiß sonst nichts über Bun.
