## 1. What was slow, and what replaces it

Every top-level command resolves the agent session identity (`currentAgentSessionV1` → `systemAncestryV1`), the lease custody check (`ancestorDepth` pids) and the capacity handover (`parentIdentityV1`, `selfStartedV1`). On Windows that was one `powershell.exe -NoProfile -Command "Get-CimInstance Win32_Process | ForEach-Object {…} | ConvertTo-Json -Compress"`: a process start, the .NET runtime, a CIM/WMI query for every process on the machine and a JSON round trip, in the hot path, against a 10 s hot no-op. The chain needs at most 16 processes.

| piece | before | now |
|---|---|---|
| list | WMI query of all processes | one Toolhelp32 snapshot (a few hundred rows, in-process) |
| start time | `CreationDate` text, microsecond resolution | `GetProcessTimes` FILETIME of the 16 ancestors, spelled `yyyy-MM-ddTHH:mm:ss.fffffffZ` and floored to the microsecond (the CIM spelling) |
| command | `CommandLine + ' ' + Name`, trimmed | the same string: `NtQueryInformationProcess(60)` + the snapshot's image name |
| cost | 300-1500 ms (estimate, `result-windows.md` W9) | expected 1-3 ms (1 snapshot + ≤ 16×3 calls); measured on the first Windows run by the Windows-only law (it prints both timings) |

Design (follows the boot-clock precedent `🕰️clock/🪟️native`, ticket xplat2-g):

- Port, not a library: the module uses `runtimeNativeSystemV1()` (the repo's foreign-function port; Bun's `bun:ffi` behind it), system libraries only (`kernel32.dll`, `ntdll.dll`), nothing external, no new runtime dependency, nothing exported that needs a foreign type. A runtime without `ffi` (Node) or an architecture other than x64/arm64 answers `null` and the old PowerShell program runs.
- Three layers, each replaceable: `WindowsProcessBindingV1` (the 8 kernel calls as a call table), `WindowsProcessHostV1` (semantic: `entries()` once, `detail(pid)` on demand; no handle ever leaves it, every handle is closed in `finally`), and the session walk `windowsHostAncestryV1` (pure, same rules as `windowsAncestryV1`: id ≤ 4 or a missing parent ends the chain; a parent that started after its child is a recycled id).
- Schema-first: layouts and constants live in `identity.ancestry.windows` of the agent-sessions schema (library names, architectures, snapshot flag, access mask, `PROCESSENTRY32W` offsets, `UNICODE_STRING` header, command-line buffer size, FILETIME constants). Code reads them; the Python oracle reads the same schema file and checks them against `ctypes`.
- Honest degradation: a process the snapshot lists but that refuses a query handle (protected or elevated) makes `windowsHostAncestryV1` answer `undefined` and `systemAncestryV1` falls back to PowerShell, because a shorter chain than the machine has would change the agent identity. Same for a process that exited between the snapshot and its query. `PROCESS_QUERY_LIMITED_INFORMATION` is granted for same-user processes across integrity levels, so this is the exception.
- Command lines: 65,568-byte buffer (16-byte header + 32,767 UTF-16 units + NUL, rounded to 16), one buffer per host; a refused query or an odd/oversize length gives an empty line, so the command is the image name (what CIM reports for a process without a readable line).

## 2. Laws (`C/winps-tools/staged/native/src/native.test.ts`)

1. Layout and spelling vs the independent oracle (`oracle.py`, Python `ctypes` structures after `tlhelp32.h`/`winternl.h`, `datetime` arithmetic; no shared code): `sizeof(PROCESSENTRY32W)` 568, offsets 8/32/44, 260 units, `UNICODE_STRING` 16, pointer size 8, buffer capacity ≥ the longest command line; `windowsFileTimeIsoV1` equals the oracle for 6 instants incl. 1970, leap day, 2262 and 9999 and for the 7 fixture instants, for 100 ns remainders (floored) and refuses ≤ epoch, year 10000 and `u64` max.
2. Corpus equivalence: the Windows fixture listing of the agent-session suite (`windows.listing`, with recycled id, orphan, single row, System) becomes records encoded by the oracle behind a kernel model; for 8 first-pids × 5 limits `windowsHostAncestryV1` equals `windowsAncestryV1` over the PowerShell JSON of the same corpus (`toEqual`, so pid, `started` text and `command` text are byte-identical).
3. Call model: the model validates the snapshot flag, the access mask, `dwSize` before the first call and after every `Next`, the information class, the buffer length, pointer lengths and handle kinds, and tracks handles: one snapshot per host, one open per described process, every handle closed once, both libraries closed, row schema keys and bounds from the schema's `Ancestor`.
4. Command lines: emoji path, 32,767-unit line, a name that fills all 260 units without NUL, a refused query, an odd or oversize length, a failing status.
5. Degradations: unreadable ancestor (open refused, times refused) → `undefined` → `null`; invalid, zero or empty snapshot, failing `dlopen`, throwing `use`, throwing `CloseHandle`, non-win32, ia32/arm, no `ffi` → `null`, nothing leaked, libraries closed exactly once; the unsupported-host cases never call the opener.
6. Resolver: with a native chain `systemAncestryV1("win32", …)` returns it without a shell (a spawned PowerShell cannot exist on the test host, so an answer proves none ran); `null` takes the PowerShell route; the PowerShell program text keeps its words.
7. Windows host only (skipped elsewhere): the kernel chain for `process.pid` equals the CIM chain (pids, commands; `started` within 1 ms) and is faster; both timings are printed with the `[winps]` prefix.

## 4. W10: the tools partition and the running runtime (design and fix)

Finding, from the code (`📁️directory`: `activate/deactivate` = one rename swap of `m` and `v` through the journaled `MoveFileExW` port; refusal text `windowsOpenHandle`: "close every user of the partition before it is swapped"): the launcher prefers `bun.exe` from `.cache\b\t\m\bun\<sha>`; a running Windows image keeps a handle on its file, which pins every ancestor directory, so `m` cannot be renamed while any command runs from it, and the command that wants to detach the partition is itself running from it (a self-pin, not only a peer pin). The swap refuses cleanly (no corruption), but it can then never succeed from a `repo` command. On macOS the same copy sits on the DMG mount; the equivalent is a busy detach.

Fix (batch `pin`): on `win32` the runtime never runs from the partition. `Locate` looks in the user cache first; when only the partition holds the runtime, `Ensure` adopts it: executable and receipt are copied into a `.prepare-<token>` directory beside the destination, verified (`verifyInstalled`: regular file, receipt archive, size), then renamed to `%LOCALAPPDATA%\semio\runtimes\bun\<sha>` (peers racing end with one valid copy; an invalid leftover is removed first, like `fetch`). Any failure (read-only cache, path too long) keeps the partition copy, so a start never fails because of the adoption. No download, no admin right, nothing per command beyond the existing `Locate` (the copy happens once per runtime sha). The partition's other residents (node, uv, cargo) are children of a command and are covered by the lease protocol (a detach needs the exclusive partition lease, which no running command grants); only bun was a pin of the command itself.

Not done (needs Windows): whether `MoveFileEx` of `m` really fails with a running image under it. The Go law `TestWindowsRunningImagePinsItsDirectory` proves it on the first Windows run (it renames a directory that holds a running copy of the test binary: must fail, then renames the tools dir while the adopted copy runs: must succeed). It also answers CI item 4 of `result-windows.md` (record `windowsOpenHandle` or not).
