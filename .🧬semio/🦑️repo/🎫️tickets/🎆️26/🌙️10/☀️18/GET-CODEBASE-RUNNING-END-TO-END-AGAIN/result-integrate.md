## 3. Method

Each set was run with its own apply tool on a COPY of the live library (plus the manifests, README and process modules it needs), giving a per-file result. Files touched by several sets were folded with a 3-way merge against the file as the set saw it, starting from the live file (so peers' edits and applied sets stay). The Bazel adapter is a set of very long single lines, so the merge also runs at token level (split after `; , { } ( )`), which resolved most overlaps automatically. Textual conflicts were resolved by hand per block; overlaps that merged cleanly but did not work together were integrated by anchored semantic patches (`semantic.py`, 46 patches, 2 hand-written files, 1 exclusion). Verification roots are copies in `/private/tmp/ig` (a short path: the product limits absolute paths to 256 and the ticket depth plus library depth exceeds it; deviation from "under C/🗑️generated/integrate-*"); bare packages resolve through a `tsconfig` `paths` entry to the live `node_modules` (read only), no symlinks.

## 4. Conflicts and how they were resolved

Textual (hand blocks, in `resolutions/`): only the Bazel adapter `BZ/📜️script.ts` (rexec, bworkers, bzl-coverage, bzl-rust, bzl-xplat, bzl-lazy: 1, 1, 4, 4, 4, 13 blocks), the actions fixture (bzl-coverage vs bworkers) and the help fixture (rcache vs a peer's `bun repo` to `repo` change; regenerated, not merged).

Semantic decisions (each is one design, not stacked patches):
1. `runBazelTasksInStorageV1`: rcache's credential-helper write and rexec's execution flags both sit before the module lock write; both kept in that order. The job count of the command plan is the worker plan's `localJobs`, raised to the executor's when hermetic actions run remotely. One startup rendering for run and affected: idle bound, shared install base, heap, rc isolation, the cache contract's output base and the platform profile (xplat drops `--output_user_root`, the output base carries the path budget).
2. ONE `repo_test`: bzl-coverage's cross-platform launcher (birth protocol, no `/bin/sh`) wins over bzl-lazy's shell launcher. Classification has one authority, the neutral coverage disposition; bzl-lazy keeps its command plan (`--build_tests_only` only when all members are tests, cached test results, `--test_output`), the 10,000-file runfiles limit (recorded at generation in `kinds.json`) and affected-by-rdeps. bzl-lazy's second test-name policy (`testTargets`, `TestAction`, `bazelTestActionV1`) and its `testrule-test.ts` were removed. Cargo actions stay serialized `repo_task` (exclusive `resource_set`, never tests, never workers); tests and hermetic actions never run in workers; tests are disabled where the platform profile has `--noenable_runfiles` (Windows without symlinks); the load statement names `repo_test` only when a test exists.
3. Worker (bworkers) vs hermetic (rexec) vs test (bzl-coverage) vs Cargo exclusive (bzl-rust): all four flags live on one action record with the exclusions above.
4. Fixtures: the two overlapping test-kind enum entries and the doubled `timeout` row were fixed (fixture and schema), the fingerprint law injects the Cargo toolchain key as a stub for its non-Cargo fixture, the worker rule-count law counts the two new plain requirement uses.
5. Index of the Bazel suites: the new adapter-local suites are registered next to the hermetic ones.
