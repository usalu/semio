## 1. Windows lock branch in the leases (done, tested)
Gaps found: (a) `acquirePhysicalFileLocksV1` refused every host but macOS/Linux, so the Cargo build-lock custody had no Windows backend; (b) the lease store treated a sharing violation like a fault in four places (retirement unlink after the exclusive transaction, ticket-upgrade rename, ticket removal, `SQLITE_CANTOPEN`).
- Physical lock (`🔒️leases/📁️physical`): split into a backend contract (`retain / tryLock / verify / close`) with two implementations selected by `physicalLockBackendV1(platform)`: POSIX `flock` (code moved unchanged, still bound by loader name) and Windows `kernel32` `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK|FAIL_IMMEDIATELY)` over the whole range, the exact range and flags Cargo/Rust `File::try_lock` take, so Cargo and this lock exclude each other. The file is opened by `CreateFileW` (share read|write|delete, `FILE_FLAG_OPEN_REPARSE_POINT`, `\\?\` extended path via `windowsExtendedPathV1`), not through the runtime's descriptor (a Node/Bun fd is not a Win32 handle). Identity = volume serial + file index from `GetFileInformationByHandle` of the held handle against a second metadata-only open of the name (the same API twice: no mixing with libuv's `st_ino`, which differs on ReFS); a reparse point or directory is refused. Contention = `ERROR_LOCK_VIOLATION` (33); any other error is a loud refusal with the Windows error number. All refusals now come from a schema catalog (`Messages`, EN+DE, `PhysicalLockErrorV1.key/.texts`, `message` stays the English text so existing matchers hold).
- Lease files (`🔒️leases/🪟️windows`, schema-first policy `🧬️schema`): `leaseFileBusyV1` (Windows: EBUSY, EPERM, EACCES are busy, the same codes on POSIX stay refusals), `settleLeaseFileV1` (retry on 10/40/160/640 ms, cancellable, a persistent violation comes back as `settled:false`, any other error is thrown at once), `leaseRemovalOptionsV1` (Node's bounded `maxRetries 3 / retryDelay 50` on Windows only), `leaseDatabaseUnopenableBusyV1` (Windows `SQLITE_CANTOPEN`, primary code 14, including extended codes). Applied: retirement unlink goes through `settleLeaseFileV1` with injectable ports (`limits.files`), a persistent violation counts as `kept` and the next sweep retires it; `rmdir`/ticket removals tolerate busy; `renameSync` of the ticket upgrade is settled; `rmSync` of the five ticket removals carries the Windows retry; a transient `SQLITE_CANTOPEN` is retried on the same pauses at open and in the acquire loop, bounded, then explained by the existing `explainUnopenableLeaseV1`; `resourceLeaseBusyV1` (retirement probes) knows it. Defect found by the tests: the real `sleep` ignored an already-aborted signal; fixed.
- Tests (all green): `📁️physical/🧪️tests/🪟️windows` (6): layouts of `BY_HANDLE_FILE_INFORMATION`/`OVERLAPPED` and the extended-path rule equal an independent Python oracle (ctypes SDK field lists with 32-bit DWORD, `ntpath`); a kernel32 model (per-handle ownership, error 33, close drops locks, structure written with the oracle's offsets) runs the SAME scenario table as the REAL POSIX flock backend and the outcomes are equal (take both, close twice, check after close, held without wait, wait then take, no handle or library leaked); one-handle-excludes-another; 7 refusal scenarios each close every handle; negative control (contention code 32 and a wrong index offset fail 4 of 6). `🪟️windows/🧪️tests` (5): classification table equals the churn race table, a REAL SQLite open failure classified under both rules, settle pauses/exhaustion/no-retry/cancel, a REAL `EACCES` (read-only directory) final under POSIX rules and retried under Windows rules, and retirement over REAL lease databases (busy twice then retired; persistent busy keeps the lease, Python's own sqlite3 reads it back intact and unlocked, a later sweep retires it; POSIX rules still throw). The old test fails against the old main file (verified). `🧭️order/🧪️tests/🪟️registry-root` (1): registry root per platform. `provePhysicalFileLocksV1` now observes with `msvcrt.locking` on Windows and `fcntl.flock` elsewhere; the descriptors test runs on win32 too.
- Not verified: `GetLastError` read as a second FFI call (the usual trick; if a runtime call in between clobbered it the Windows lock would refuse loudly with the error number, never silently), 64-bit handles as `i64`, Cargo itself against this lock on Windows.

## 3. Boot clock without PowerShell (done, Windows numbers pending)
- Cause: `readNativeBootClockV1` started `powershell.exe` + a CIM query once per process (memoized only inside the process), i.e. on every `repo` start on Windows.
- Fix: `🕰️clock/🪟️native`: one in-process `NtQuerySystemInformation(SystemTimeOfDayInformation)` through the runtime FFI (`BootTime` FILETIME -> epoch ms, floored like the textual path; older 32-byte record retried; any refusal returns null and the unchanged PowerShell route runs). `readHostBootEpochMsV1` holds the per-host route table (ports for native, command, file, pinned PowerShell). Schema `bootEpoch.win32.native` (library, symbol, class 3, lengths 48/32, epoch offset).
- Tests (4): record layout (ctypes) and FILETIME conversion equal Python datetime arithmetic on 6 instants, and equal the PowerShell text path for the same instant (`parseNativeBootEpochV1` of the 7-digit `o` string); an ntdll model checks class, buffer lengths, fallback and library close; routing (native wins, shell only when null, macOS/Linux routes keep text and parser, garbage still refused). Real-Windows law (runs in the new CI job): in-process value within 1 ms of PowerShell's, within 5 s of `now - uptime`, and prints both timings.
- Measurement (proxy, this Mac, `C/xplat2-g-tools/boot-clock-bench.ts`, 40 rounds, twice): `sysctl -n kern.boottime` as a child process 4.1-4.5 ms median (min 2.7) vs one in-process FFI call (dlopen, buffers, call, close) 0.061-0.064 ms median = 64-73x, tool RSS 26 MB. That is the floor for a tiny native binary; Windows PowerShell 5.1 start + CIM query is not measured here (no host) and is known to be hundreds of milliseconds, so the real ratio is far larger. The CI line `[xplat2-g] windows boot clock: in-process X ms, PowerShell Y ms` is the measurement to read.
- Risk accepted and bounded: `bootSession` on Windows is a hash of the epoch ms, so two processes must agree; the CI law pins native vs PowerShell to within 1 ms. If the first Windows run shows more, set the schema row to the shell route (one line) before relying on it.
