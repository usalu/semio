## Minimal design (what each process must earn) and what changed
1. `bun repo` (script runner, 2-8 MB) exists only for `bun repo`; the Go `repo` launcher execs the pinned bun in place (no extra process). Kept.
2. Door: live code that plans the route, waits for machine capacity (alone: 35-75 MB), issues the Original envelope, captures the source closure once and supervises. Kept. Its capture (1457 files, 17 MB, 6-27 s, 400 MB peak) is noop-g's memo.
3. Executor loader (`bun --eval`): runs the immutable implementation snapshot, so a peer edit cannot change a run in flight. Kept. Memory: 1.5-2.0 GB -> 240 MB after the kernel import (this batch).
4. Graph planner loader: exists because JavaScriptCore never returns a construction heap, so planning must happen in a process that exits. Kept, but it is now started by the executor directly from the snapshot it holds: the `bun repo` runner (2.5 MB), the second door (60-116 MB, a second 17 MB capture, 6-27 s) and the third hop are gone.
5. Tool adapters (Bazel server, Nx daemon, cargo): other lanes.
Removed per graph-running run: 2 processes, one 17 MB source capture, ~1.2 GB native memory per loader (3 loaders in the old shape -> 2).
Waiting: at the capacity gate the run is the door alone (law: < 100 MB, no loader child). In the graph builder queue it is door + executor + planner (104 MB compressed measured, ~0.6 GB uncompressed estimate); the requeue protocol (see FOR lease-g / hold-g) would make that the door alone; not built.
Not done / follow-ups: (a) neutral children (`runOwnedBuildChildInvocationV1`) still start `bun repo` + door + loader: the ones a loader starts (watch callbacks, Bazel backend launches) can adopt its snapshot exactly like the planner whenever `repositoryCommandKernelV1(args).entry` equals the adopted entry; the Rust build intents and dashboard task routes start theirs from an ordinary action script process that holds no snapshot, so they cannot; (b) door capture memo (noop-g); (c) scheduling-domain for process-launch code (FOR exec/keys owners); (d) Bazel/Nx actions that run `bun repo ...` from a tool process are full chains by construction.
