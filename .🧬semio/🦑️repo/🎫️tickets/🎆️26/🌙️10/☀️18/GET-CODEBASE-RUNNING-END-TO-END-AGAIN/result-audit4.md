## Finding 1 (MEDIUM): the machine-wide capacity gate lock is not a mutual exclusion once a holder stalls; two runs can admit/grow into the same memory
- Code (live; `🔨️modules/🏃️process/🏗️build/🌡️host-capacity`): `🎫️gate/🟦️.ts` `takeLock` breaks a lock whose owner is ALIVE as soon as `now - since > wait.lockStaleMilliseconds` (10 s, `🔣️policy.json`); every holder gives the lock back with an unconditional `rmSync(join(directory,"lock"))` (admission `🎫️gate`, `growHostGrantV1` and `upgradeHostGrantV1` in `🔼️upgrade`, `claimHostGrantHandoverV1` in `🤝️handover`) and writes its grant row without checking that it still owns the lock; the admission and upgrade loops even `await control.publish(...)` + `yieldContinuation()` INSIDE the locked section (progress branch). red-gaterace (G38) fixed only the mkdir/owner-write race; capgrow (G38/G40) added a third holder path that runs every heartbeat per growable run.
- Scenario: holder H1 (any run's admission or a growing grant) stalls > 10 s inside the section (swap storm, a stopped process, a slow caller behind `publish`); H2 breaks H1's lock (alive but "stale"), takes it and evaluates the ledger; H1 resumes, writes its grant/growth computed on the ledger it read before H2's decision, then its `finally` removes H2's lock; H3 enters while H2 is still deciding. H1 and H2 (and H3) are admitted into the same headroom: over-commit of exactly what the gate exists to prevent, plus cascading loss of the lock for every later holder in that window.
- Law `🌡️host-capacity/🧪️tests/🔏️fence/🟦️.ts` (new; real `withHostCapacityV1`, real `growHostGrantV1`, real `takeHostLockV1`; the stall is simulated by a peer breaking and taking the lock at `now + lockStale + 1 s` from inside the section): (a) the peer's lock survives the stalled holder's release, (b) a growth whose holder lost the lock writes no grown row, (c) a waiting request publishes progress only after it released the lock. **RED on live 3/3** (peer lock removed; growth published under the peer's lock; publish seen while `lock/owner` = own pid). GREEN with the fix.
- Fix (staged `gatelock`): `takeLock` remembers the owner text it wrote (per lock and pid); new `holdsLock` (owner file still holds that text) and `releaseLock` (removes only while it does) join the ledger primitives (`📋️contract` `HostLedgerPrimitivesV1`, `custody()`); every holder releases through `releaseLock` and checks `holdsLock` right before it writes a grant, an upgrade, a growth or a handover (a holder that lost the lock writes nothing and retries / asks again); the progress `publish`/`yieldContinuation` run after the release. Exports `releaseHostLockV1`/`holdsHostLockV1` for laws (as `takeHostLockV1`). The time-based break stays (it is what recovers a hung holder or a recycled pid); residual window = a stall exactly between the ownership check and the rename of the grant file. Unused imports dropped (`rmSync` in upgrade, `rmSync`/`join` in handover).

## Investigated and cleared (the argument)
- capgrow/grownow decision: during the admission ramp the grower's own reservation is added back once (`freeObserved += unrealized`, `freeBudget += committed`) and the growth pays `need - held`: no double count, no over-commit; peers decided earlier in the same evaluation consume room before the grow (`admit` updates the rooms); grow ranks last and refuses on any waiting/blocked peer (`queue-order`), so it cannot starve peers; settle (2 heartbeats, fewest jobs) only grows on memory seen twice; `--parallel=8` of a growable run reaches only consumers that cap by the plan (Bazel `--jobs=min(parallel, plan.jobs)`, Nx `NX_PARALLEL` from the host plan first). Note, pre-existing and smaller than before capgrow: compile-units `budgetMegabytes = max(granted, units x unit)` can exceed the grant (8 jobs/5734 MB -> 10240 MB broker budget); bounded by the free-memory limit at plan time and by observed accounting after the ramp.
- rev3fix: no hold-and-wait (prefetch upgrades before any claim; `book()` inside the claimed chunk only appends a phase mark, the resize never waits; lane retention under the trimmer's claim takes no second lock; pool acquisition polls holding nothing). Boot anchor, LOW and not staged: `hostBootAnchorV1` misses a reboot whenever the first post-reboot reader's uptime is >= the uptime stored by the first reader of the previous boot (the mark is never refreshed); effect needs a pre-reboot grant whose pid is recycled at the first post-reboot ledger read (pids restart low, so practically nil). Fix if wanted: refresh `uptimeMs` to the newest seen uptime.
- red-leasesentry bridge key: `Symbol.for` is realm-local, so no cross-process leakage; in one process the LAST evaluated routing instance wins (the docstring's "the issuing instance wins" is imprecise); harmful only with two live instances whose controls interleave in one realm: none in production or bun test (no cache-busting imports of the routing module), Vitest isolates files.
- Sealed (seal2 + sealflip): explicit rule disables seal2's detached refresh (verdict returns before the light branch); a command reads the pointer once (benign at read); the child gets the whole snapshot through the fd/pipe and decodes lazily from memory, so snapshot GC (current + 2, 10 min quiet) cannot pull code from under a running command; Bazel actions run the invocation's captured build source (`bazelCapturedImplementationV1` proof), not a nested trampoline, so a promotion mid-build cannot mix implementations inside actions (nested light door chains get the new digest; known, documented).
- diskbud memo eviction: every memo file is content-addressed (sha names), a lookup verifies plan bytes/sha and relevance before serving and rewrites the record on a hit (newest mtime), the sealing child collects after writing its own record: a concurrent eviction can only cause a miss (or a record naming a removed file, healed by the next seal), never a stale serve. The 1 GiB budget is not binding today (104 MiB).
- diskbud journal GC: only `<container>/<12-hex>/journal` siblings, never the own id, held = the service's own lock rule, quiet age measured over `state/journal/*` (heartbeat included), epoch is random so a recreated state never matches an old cursor; the residual TOCTOU (a service reclaiming a stale lock of a 7-day-quiet / root-gone sibling at the same millisecond) is availability only and practically unreachable.
- conv-g: the converted constants are value-preserving where read (jitter `1 - j + 2jr` = `0.75 + 0.5r` at 2500 bp; backoff `ceil(poll * 15000/10000)`; `startPollMilliseconds` read from the policy, type fixed by the gate).
- cargo2 sessions: sessions leave the pool quota but stay bounded by the collector's `incrementalShare` (incremental sets first); acquisition/trim unchanged.
