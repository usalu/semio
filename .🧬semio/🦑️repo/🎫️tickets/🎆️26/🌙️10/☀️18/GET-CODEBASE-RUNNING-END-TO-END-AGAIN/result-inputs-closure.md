# result-inputs-closure: import-closure inputs for every repo:script target (nx and Bazel)

`L` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`, `C` = this ticket, tools = `C/inputs-closure-tools/`. HARD FREEZE respected: nothing under `L` or any other repo path was edited; everything is STAGED and applied by `C/inputs-closure-tools/apply.sh` (anchored, idempotent, refuses while a dependency sync runs). Anchors were re-checked against the live files after bzl-stage/walkperf were applied (all 5 targets: every anchor occurs exactly once).

## Verdict (the premise needed correcting)
The plugin already derived the command import closure, but with two real holes, and Bazel could not see any closure at all.

1. Nx/plugin already emits it. `projectWithDefaults` adds `genericTargetCommandInputs` / `nativeTargetCommandInputs` as `commandSourcesN` named inputs (hash representation: `{env: SEMIO_SOURCE_CLOSURE_<sha256 of manifest>}` + manifest in the graph store `build-input-closures/<key>.json`; Nx hashes the file bytes at task-hash time via `🧮️digest`). Persisted records of 3,655 projects (`.cache/b/g/m/inference/np`, 2026-10-18): 17,422 `repo:script` targets, 11,869/11,869 cacheable ones carry a closure (median 470 files, p90 494), plus 5,131 uncached ones; 422 uncached (313 `activate*`, 94 `test*` with cache false) carry none. The "106 of 111 modules undeclared" finding of `result-bzl-real.md` came from the STATIC graph reconstruction, which never runs the plugin.
2. Hole A (Nx and Bazel): the closure follows only RELATIVE imports. `commandSourceImports(...).filter(s => s.startsWith("."))`. Imports through workspace package specifiers (`@semio-tech/process/leases`, `@semio-tech/schema-validator-ts`, ...) and `new URL("<test file>", import.meta.url)` (how scripts point at the test files they run) were dropped. Proof with the library's own digest function (`C/inputs-closure-tools/nx-digest.ts`): fixture script importing `@fixture/pkg/sub` -> shipped closure = `[script]`, changing the imported module leaves `sourceClosureDigest` unchanged (`importedChangeMovesDigest:false`); patched closure = script + sub + deep, digest moves, changing an unimported module does not. Bun-bundler oracle over 49 sampled project scripts (stride 17): shipped misses 1,086 modules in 16 entries; patched misses 70 in 1 entry, all of them `import.meta.vitest`-guarded in-source test imports that the analyzer excludes on purpose.
3. Hole B (Bazel only, the decisive one): the Bazel adapter never expands closure markers. In the real (hash representation) graph the closure AND every compacted `default` source list is only `{env:"SEMIO_SOURCE_CLOSURE_<key>"}`; `bazelTaskSourcePathsV1` ignores env objects and `taskFingerprint` digests `process.env[key] ?? null`, so no closure file ever reached a Bazel action key (stale cache hits). Same for `SEMIO_CARGO_LOCK_<key>`.

## Measured cost (real tree, read-only harness `measure.ts`/`bazel-overhead.ts`, load average 25-50, so CPU seconds are quoted)
- 833 project `📜️script.ts` entries; sample of 49 (every 17th), cold, same process settings: shipped 22.8-25.6 CPU-s / 1,129 distinct files / median closure 489; full patch 29.7-30.8 CPU-s / 1,704 files / median closure 1,200 (x2.45 per target, +51% distinct files): about +28% CPU. The admission memo alone (no feature) takes shipped to 14.6-15.6 CPU-s (-35%), which pays for the larger closure. New code itself (analysis, 6,084 resolves, URL checks) is about 1 s of that run.
- Extrapolated whole tree (estimate, not measured): closure derivation about 1.5-2 CPU-min cold in one process; warm graphs reuse persisted `np` records. Nx hash time grows with closure size (about 1,200 files per script closure, hashed once per unique key per batch).
- Bazel side on persisted real records (3,656 projects, 402 sampled tasks): 7,123 reachable manifests loaded in 15-26 s, expansion of 3.67 M entries (avg 9,137 per task, 29,616 distinct paths) in 3-16 s, bzl-stage index selection 4.4 s for 40 heavy tasks. The per-task lists are as large as Nx's own scope for native tests (`{input,projects}` references to many dependency projects).
