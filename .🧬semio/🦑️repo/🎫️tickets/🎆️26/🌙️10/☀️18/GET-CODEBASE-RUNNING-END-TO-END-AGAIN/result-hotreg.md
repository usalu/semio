## Root cause 1 (proven): the plan record counts the executor's `failures` folder as a file the planner wrote
1. A Bazel slot has ONE stable package directory; the planner writes its files into it and `recordBazelPlanV1` seals the identity (dev, ino, mode, size, mtime, ctime) of every root entry that `bazelPlanOwnsV1` calls planner-owned (`plan.receipt.json` -> `outputs`; g47: 146 entries).
2. `bazelPlanOwnsV1` excludes `runtime.json`, `plan.*`, `MODULE.bazel.lock`, `bazel-*`, dot files, `*.tmp` and the snapshot links, **but not `failures`** (the folder of the failed-action output tails, `🪵️failure-tail` Policy.directory). Every build empties it first (`runBazelBatchWithChurnV1` -> `clearBazelFailureTailsV1` = `rm -rf`), every failed action refills it.
3. A replan in a slot whose previous run FAILED (course:test, print:test, repo-mcp:test leave tails; a different selection that takes the slot, `session slot sN: the package of the slot is replaced in place`) records `failures` among the outputs. The build of that very run empties it. The next run: `lstat(failures)` fails -> `planning again: the generated workspace changed` -> a second planner run (25-50 s) that records without the folder, so only one more run is lost per failure episode and it looks random.
4. g47 timeline matches: hot1 `s2` replaced in place for a different selection (course's slot s1 had been taken by print: ctest s0, dash s4+s5, print s1) -> key replan (legit once) and a record beside a leftover `failures`; hot2 `s2` warm -> `outputs` mismatch -> replan 46 s; the edit probe right after reused `s2` fine (record without the folder). g46/g45 probably had the same shape after red course:test / print runs (their slot logs are not kept). g48 hot1 reused because slot s2 stayed warm and clean.
5. Reproduced live today: `hotreg-4` (a replan in slot s1 after print's selection, 23:45) left a receipt with the folder `failures` listed and the run removed it (`outputs_drift.py` -> `MISSING failures`, 107 outputs checked).

**Fix (staged, root cause):** `bazelPlanOwnsV1` also excludes the failure-folder name, read from the authored failure-tail schema (no second copy of the string); `the generated workspace changed` now names the first moved file (`{subject}` in the witness Reasons, EN+DE; the same text is documented in `📓️build-guide.md`, EN+DE). ## Finding 2 (hypothesis, NOT fixed): the graph memo stayed `light` twice in g47
- What `light` means: the memo record of this request is not sealed yet (first run of a request keeps a light record, the next run's graph child classifies the slice and seals it, from the third run on the slice is served; build-guide row `graph: the memo cannot serve this request (light)`). Normal pattern 10-27: hot1 light (child plans, 20-30 s), hot2 served (10 s). g47 broke it twice (hot1 AND hot2 light), g46-hot2 and g45b-hot2 too, g48 and today's hotreg runs behave (hot1 30 s light + plan reused, hot2 8.3 s served).
- Not caused by tree churn: the change journal (`~/Library/Caches/semio/repo/<id>/journal/*.log`) shows NO tracked-source change between 21:33 and 21:39 except fence noise and one `mit-bestand` .tex edit at 21:36:26 (another project). Generation numbers: 684 (print, ends 21:35) -> 685 published by somebody during hot1/hot2/mcp -> 686 only at g48-course.
- Candidate (code-read, unproven): `writeGraphMemoSliceSidecarV1` refuses to seal when the generation pointer moved between the child's graph load and its sidecar (`moved` / `other-generation`: `header.pointer.manifest !== manifest of the pin`), so any peer publication during the ~20 s child run defers sealing by one more request. In a quiet host (g48, today) it seals. If it matters: seal against the generation the pin served (immutable, content-addressed; `carry` already serves a moved pointer) instead of the live pointer.
- To prove or kill it on the next regression, no code needed: `python3 -I C/hotreg-tools/sidecar_watch.py <out dir> 600 &` while the hot runs (copies the child's sidecar header `memo.json` before the parent removes it; its `unsealable` field is the reason; self-tested), and `SEMIO_REPO_PROFILE=1` prints `graph.memo-seal`.
