## What was already live, what was missing
x-paths (round 2) is applied live: source labels of host actions are `a/<10 hex of the directory path hash>/<name>` (alias farm, junctions on Windows, `sources.json`), a per-OS path budget (`PathBudget`, `bazelPathBudgetV1`) over measured label closures. Missing, and done here:
1. hermetic actions still named inputs `s/<repository path>` and the runner built its private root under the long execution root (`.hermetic/<hash>/root/s/<path>`): the root plus the longest repository path (232 units) overflowed MAX_PATH on every Windows layout;
2. no short fixed output root per checkout (the output base sat under the partition path);
3. the budget measured one closure maximum, not every declared target, and had no law that fails a target.

## Design
- **Schema `BZ/📐️path-plan/🧬️schema/🔣️.json`** (closed, `PolicyShape`): `outputRoot` per platform (`win32`: `{drive}\b\{first 8 hex of sha256(lowercased backslash checkout path)}`; darwin/linux `null`, the production layout is unchanged there), `hermeticRoot` per platform (`win32`: `{drive}\b\w\<6 hex>\r`; darwin/linux: `/tmp/<12 hex>/r`), fillers for the law.
- **(1) Output root.** `bazelOutputRootV1` / `linkBazelOutputRootV1` (`BZ/📐️path-plan/🟦️.ts`): `bazelCacheFlagsV1` (storage) gets `checkout`; on a host with a root it emits `--output_user_root=<root>` and `--output_base=<root>\<slot>` instead of the partition path. The root is a link (junction on Windows) to the real directory of the output bases, so the data stays inside the finite products partition; the link is reconciled idempotently and a real directory is refused. Both adapter call sites pass the checkout and link the root; the platform profile budgets the short base automatically. Case, slash and drive-letter spellings of one checkout give one root (fixture rows).
- **(2) Staging with a declared mapping.** Hermetic actions now take the alias view like host actions (`view("alias")`, no `s/` label, the `repositoryLabels` measurement is gone so the `real` closure and the `sandbox-source` family stay empty). The manifest carries `aliases` (repository directory to `a/<hex>`, the declared mapping, closed schema, location independent) and `scratch` (the private root policy by platform). The runner (`🏭️runner`) copies/clones each declared input from `a/<alias>/<name>` into its own private root `<base>/<work>/r` (random work name; the Windows base is a fixed short `C:\b\w`, POSIX `/tmp`), runs there and removes the root; an input directory without an alias fails loudly. Labels of tasks, snapshots and trees are unchanged; readers of outputs still use the snapshot files (already `t_<16>.snapshot/files/<32 hex>`). Without `aliases` the caller's `s` is the isolated root (the runner unit tests); the old "symlinked `s`" heuristic is gone.
- **(3) Law `bazelPathLawV1`.** For each declared target (hermetic or host) it computes, in UTF-16 units, the longest path of each family a tool opens: `host-source` (checkout + path), `alias-source`, `sandbox-alias-source`, `sandbox-stash` (Bazel 8 stash copy of the snapshot, found by the real-Bazel law), `hermetic-root` (private root + repository path), `snapshot`, `tree` (longest dependency-tree entry); limit = min(256, Windows MAX_PATH - 1 or the extended limit with long paths). Families that need the output base or checkout are skipped when the caller cannot name them. The generator runs it for every hermetic candidate and keeps a target over budget on the host (`[bazel] hermetic task kept on the host ...`) instead of failing the build at run time.

## Numbers (corpus, fixture rows computed by the Python oracle)
Windows, short root `C:\b\<8hex>\s0`, MAX_PATH 259: the 226-unit relative deep plugin path (the audit's 250-unit worst with its 24-unit checkout root) is read as `a/<10 hex>/🔣️.json` (53 units from the output base), and the private root `C:\b\w\<6>\r\` costs 16 units, so repository paths up to **240** units fit hermetically and 241 fails (corpus rows `hermetic-240` fits, `hermetic-241` over). With the old long root the same layout needed 111 + the path. POSIX `/tmp/<12>/r/` costs 20 units, so 236 fit under the 256 repository rule. A dependency-tree entry deeper than about 130 units fails the `tree` family (row `hermetic-tree-deep`): trees stay a risk on Windows (`node_modules` depth), the law now names it.

## Open
- Tracked paths of 241 to 256 units (audit: 42 over 240, ticket copies and plugin snapshot fixtures) still cannot be hermetic on Windows; the law reports them (demotion) and the repository-side fixes in the audit (flatten `🪆️subsets`, drop VS16, no staged copies in tickets) remain the lever.

- Host (non-hermetic) actions run in the checkout, so their paths are bounded by the checkout path itself (law family `host-source`, not enforced at generation).
