### witdelta (follow-up 1), design
The witness listing stamps hashed only the sorted sub-directory/manifest names, so any new directory under `🧰️framework` failed the replay. Now each `list` observation also keeps its `entries`; on a stamp mismatch the replay holds iff (a) every appeared entry is a directory whose name every listing plan skips (dot names, the 7 opaque names shared by `discoverPlan` and `membersPlan`, schema `skippedNames`) or whose plan-visible subtree holds no `Cargo.toml` (bounded walk, `maximumAppearedEntries`), and (b) below every vanished entry no recorded question read a manifest, a file kind or a present path (those recorded questions are then skipped). Exact w.r.t. the plans: they act only on directory names and manifests, so such deltas leave owners, rosters and manifests, hence the hashed receipt, unchanged. Old witnesses (no entries) keep today's strict behaviour until the child rewrites them. Laws: cargofix's witness law extended from 12 to 20 edits (new directory/tree/inside-member/skipped/hidden/below-skipped hold; new manifest directory, removed member move it), its independent Python oracle reimplements the delta rule and agrees on all 20, and whenever the child is skipped `cargo metadata --no-deps` of the workspace is byte-identical before/after (Cargo as oracle). RED on live (`new-directory`: child 1), GREEN with the batch; 21 suites: no failure outside the pre-existing set (one known flaky `actual Cargo command uses its required owner…`, green alone).

### planmemo (follow-up 3), design
Key = sha-256 of program, prefix, arguments, cwd, workspace root, `cargo config get` digest (all config files + `CARGO_*` config env), compiler identity (`rustup which rustc` digest, host, cargo path), cargo binary stamp, and the Cargo-read environment (`CARGO_*`, `RUST*`, `HOME`, `PATH`, minus jobserver/jobs). Record = gzip `{key, inputs, metadata, units}`, ≤ 4 per store (LRU by mtime) under the unit cache layout `p`. Inputs, derived from the metadata: workspace `Cargo.toml` + `Cargo.lock` bytes, every local package manifest's bytes, Cargo's target auto-discovery paths per package (`build.rs`, `src/main.rs`, `src/lib.rs` presence; `src/bin`, `examples`, `tests`, `benches` listings and their nested `main.rs`), and every ancestor manifest Cargo's workspace search reads. A record is written only when no asked path (or, if absent, its nearest existing directory) changed within 2 s before the capture started, so a record never vouches for an answer older than its inputs. Law (real nightly Cargo, 13 cases): served exactly in `unchanged`, `source edit`, `unrelated file`, `unrelated environment`; refreshed on member/workspace manifest, lock, new test target, nested `src/bin/x/main.rs`, build script, `CARGO_PROFILE_*`, `.cargo/config.toml`, `--features`; in every case the served graph equals the graph planned by a memo-less port (Cargo itself, now). RED on live capture code (`unchanged` not served), GREEN with the batch; 27 suites identical; tsc 0.

- The 10 s action heartbeat cannot resolve it; the artifact runner's own progress timer can. `startNativeProgress("artifact-rust:…:test")` starts a 10 s `setInterval` right before `runRepositoryCargoTests`; its FIRST tick is printed late by exactly the time the event loop was blocked. - That phase: `runRepositoryCargoTests` (`L/🏃️process/🦀️cargo/🎟️admission/🟦️.ts`) calls `cargoRepositoryPackageSelections(repository, ["semio-framework-print-tests"])` only to learn that package's manifest. - From the logs: the tick (= end of the synchronous inventory) is immediately followed by `cargo:workspace-selection`; from there to the first unit-cache event is ~12-14 s (g39q: tick at artifact +19.4 s, cargo at action +32.5 s; `t_art + rest` = 14-17 s in g33p/g39p/g39q). So of cargo2's "selection + admission 20 s", ~15 s was the inventory above (it sits before the first selection row but after `test running`, hence it was booked as boot/selection depending on the 10 s window).
- The memos ARE hit inside the action: source admission reports 41 read operations for 380 units (testmemo), the Cargo preparation witness held in g39p/g39q (written 12:28:05 by g39-print1, no `synchronize` child), the registry fetch is receipt-gated.
- What the remaining ~12 s consists of (component costs measured on live, read-only, at load 4-9): `cargo metadata --format-version=1 --locked --offline` on the 573-member root workspace 2.4-2.5 s (19 MB JSON), `cargo test --unit-graph` ~2 s, `cargo fetch --locked` 1.9 s when its receipt misses, preparation witness 10 MB JSON parse 16 ms + replay of 30,877 observations 0.25 s, foreign inventory (~3k registry files stat'ed against the digest book), `rustup which` ×2 + `rustc -vV`, lane + store/build/writer leases, the nested `repo` boots (two: `native owner-command` and the print script's `test`; ~1-3 s each per boot-g §2).
- Two further Cargo processes after the compile, measured with a PATH shim on a scratch workspace (`cargo-nextest 0.9.140`): `nextest list` runs `cargo metadata --format-version=1 --all-features --filter-platform <host>` before `cargo test --no-run`, and `nextest run --binaries-metadata …` runs the SAME `cargo metadata` again (2.4 s each on the root workspace); with `--cargo-metadata <file>` `run` starts no Cargo process at all. `list` refuses `--cargo-metadata` together with `--manifest-path`, and `run` needs the workspace manifest dropped when given the file.
