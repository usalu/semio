## 2. Batches READY
### `freshmtime`: restored units stop being dirty for Cargo
- Cause (measured): `restoreUnitV1` copies an output with `copyFileSync(…, COPYFILE_FICLONE)`. Bun clones files above 128 KiB with `clonefile(2)`, which KEEPS the source's mtime (131,072 B → fresh, 131,073 B → source mtime; same with the pinned bun 1.4.2); Windows `CopyFile` keeps it too; Linux `FICLONE` does not. The source is the cache object, whose mtime is its last use by ANY lane (touched after the copy). A restored rlib/rmeta therefore carries an arbitrary older time (live: `…reactor_app…rlib` 14:35:36 beside its own `.d` 14:37:46). Cargo's fingerprint rule (`check_filesystem`: a dependency output newer than this unit's newest output ⇒ stale; kept under `checksum-freshness`) re-runs the unit on later builds, the wrapper serves it again with another old time, and dependents follow. `lanestale.py` at 16:56: pb25b27 77/423 stale (1 root: `os_store_engine` 7,792 s older than its dependency's rmeta), pda16a9 141/325, pd79dce 31/43, pfcc142 19/75, pa7535d 13/21.
- Fix (`U/💾️store/🟦️.ts`): the destination gets the restore time (`utimesSync(destination, now, now)` before its digest stamp), as rustc writes outputs at the end of a compile. Template rows were already fresh; build-script OUT_DIR restores keep their time on purpose (older generated inputs keep the library fresh).
- Law NEW `U/🧪️tests/🕰️freshness/` (real nightly Cargo + rustc, crates padded above the clone threshold; lanes: a1 compiles core→mid→leaf, c1 builds `other` (uses core's object later), b1 is served all three, then an unchanged `cargo build -v` in b1). Oracles: Cargo's own `-v` verdict (`Dirty`/`Fresh`), the wrapper's event log, the independent Python model of Cargo's rule. RED on base in both freshness modes (plain mtime and `CARGO_UNSTABLE_CHECKSUM_FRESHNESS=true` = the repository config): `[leaf, mid]` from all three; GREEN with the batch: `[]` and all `Fresh`. 29 unit-cache + compiler-lane suites on mirror e3 with the batch: 157 pass / 0 fail.
