## What it is

`repo concurrency list|plan|run` is the acceptance test for conc-graph, conc-bazel, conc-cargo, conc-deps and conc-leases. N simulated agents work in ONE disposable checkout copy (the one `repo incremental prepare` provisions; `repo incremental discard` removes it) and edit different projects at the same time while they run build, test and check through `--tool=nx` and `--tool=bazel`. It is a sibling of `repo incremental` rather than a sixth subcommand so that the live incremental catalogue entry, its help pages and its 29 tests stay untouched; it reuses that harness's clone/prepare/discard, slice builder (the Bazel adapter's own planner), Bazel compact execution log observer, Nx run-record reader, child environment scrub and path-budget guards.

One workload run per tool is three phases: the setup (serial; may hold an edit that makes every cache stale), the sessions at the same time (barriers line them up), and the same sessions once more in a row as the serial reference. Everything is data in `🤝️concurrent/🎬️workloads/🔣️.json`, closed by `🤝️concurrent/🧬️schema/🔣️.json` (48 definitions, Policy const), so a second implementation in another language only needs the schema, the workload data, the fixture and the oracle.

- Authored workloads (live targets read from the project.json files): `disjoint-projects` (TypeScript `@semio-tech/framework-graph:test`, Rust `@teaching/proctor:build`, Go `@semio-tech/repo-move-go:test`, schema crate `@semio-tech/framework-schema:test-subset-contract`: edit, barrier, run, revert, run, each in its own group), `same-target-cold` (one stale-making edit, three agents build the same target, staggered 0/250/500 ms), `warm-fanout` (primed, three agents build the same target), `readers-while-edit` (an editor lists projects after a source edit while two readers list projects: the graph-facts seal case). `--sessions=n` takes the first n sessions (default 3, at most 8).
- Lock classes (ordered patterns, data): `graph-facts` (`repository-graph-facts:`), `dependency-image` (`native-fixed-image:`), `bazel-server` (Bazel's wait line), `cargo-units` (`cargo:` / `cargo-unit`), `capacity-admission` (`semio.host.capacity/`, `compiler:capacity`), `toolchain-acquisition` (bun/bazel/cargo/node binary paths), `other`. Typed progress prefixes of other publishers (`javascript-source-provider:`, `build:graph-phase:`, `dependencies:`, `boot-recovery:` ...) are an ignore list in the Policy.
- Criteria sets (declared in the schema, five rule kinds): `default` = all steps succeed + results equal the serial run (exit code, declared output digests, stdout digest) + for every class "no wait above 5 s for an UNRELATED project" + `executes-once` ("a task executes in one session only; the others execute no action for it", uncached tasks excluded); `warm` = the same with `max-executed 0` instead; `smoke` = success and serial equality only. Every rule names its executors (`owners`), and the report prints one acceptance verdict per executor: pass, fail, or unproven when only skipped rules remain.
- Attribution: a wait is `unrelated` when every other session that ran a command while it lasted belongs to another group, `related` when one of the same group did, `external` when nobody of the harness did (counted as unrelated). Groups are declared; before a run `plan`/`run` refuse a workload in which an agent edits a file that another, unrelated agent's targets declare as an input (slice-based independence check).
- Report: per session wall time, wait time, executed and restored tasks; per session and lock class the number of waits, total, longest, unrelated count; criteria with value, limit and offenders; acceptance per executor. EN/DE (`--lang`), `--json`, `--file=<report>`, progress per workload/tool/phase/session/step (`concurrency:...`), cancellation checks before every step, exit code failing when any criterion failed.

## Key finding that shaped the design: lock waits are not measurable from progress rows

The CLI prints `[script] {"activity":{resource,mode,elapsedMs}}` rows on stderr while it waits for a lease, but the queued lease publishes them only every 15 s. The real chain15 log shows `native-fixed-image` rows at 14 ms, 15,143 ms, 30,220 ms, 45,306 ms and `repository-graph-facts` at 18, 15,151, 30,378 ms: a 12 s wait is one 14 ms row, i.e. invisible, and the 5 s criterion cannot be proven. The harness therefore derives three kinds of waits and says how reliable each is:

- Bazel (`Another command (pid=N) is running. Waiting for it to complete on the server`) and Cargo (`Blocking waiting for file lock on ...`) wait lines: precise, the wait ends at the next line. Validated against a real Bazel 8.4.2: the second of two concurrent builds in one output base reported 16.9 s, Bazel's own `Elapsed time: 17.044s`.
- Lease progress rows: a lower bound (`precise:false`). A bound above the limit still fails a criterion; a bound below it leaves the criterion `skipped` (unproven), never a silent pass.
- Lease trace: each command gets `SEMIO_LEASE_TRACE=<file>`; one JSON row per lease acquisition that waited (`startedMs`, `acquiredMs`, `pid`) is exact (`precise:true`) and supersedes the derived lease waits it overlaps. The lease module does not emit it yet: group `trace` stages the emitter (3 anchored edits in `🔒️leases/🟦️.ts`: `appendFileSync` import, `traceLeaseV1` wrapping the public `acquireResourceLease` and `acquireQueuedResourceLease`, only acquisitions of at least 100 ms, never fails an acquisition). conc-leases must either apply it or emit an equivalent row; without it conc-graph/conc-deps/conc-leases can only be proven failing, not passing.

Nx writes one `run.json` per cache directory, so concurrent Nx runs overwrite each other: the harness accepts a record for a session only when the record's own `run.startTime`/`endTime` lie in the command's window (`window`), is `exact` only when no other Nx run overlapped, and otherwise marks the run `ambiguous` (criteria that need task observations are skipped). Follow-up for conc-graph/bazel: a per-invocation Nx task report behind `SEMIO_BUILD_TASK_REPORT`.
