## (a) Storage reservation gate: SOUND

Old invariant: a reservation is a bearer capability of one Original cancellation source: `originalReservations.get(reservation) === control.signal`. New: the issuing control (stored with the reservation in `reservationPolicies`) must carry that signal as before, and a presenting control with a different signal must be a live issued descendant of the issuer (`requireIssuedResourceControlDescendantV1`: private `controls` map, parent chain walk, live issuance of both ends, schema policy `ControlDescendant` with `restrictionEquivalence:false`).
- Why it preserves the invariant: every derived control's signal is `AbortSignal.any([parent signal, ...])` and its deadline is the minimum over the whole chain (`remaining()` walks `parentControl`), so a descendant is strictly narrower than the issuer: same Original, same cancellation fate, never more time. Descendants of a different Original, siblings, cousins and the issuer's own parent are not in the issuer's parent chain and stay refused; retired descendants are refused (`live` is false, error text `Live Original resource control issuance required` raised by `checkResourceLeaseControl` before the catch); the catch that rewrites a failed lineage check into the reservation text can only see "not issued / not a descendant / retired issuer", because any cancellation or deadline of the issuer already surfaced in `checkResourceLeaseControl(control)` (the descendant's `remainingMilliseconds` includes the issuer's rows).
- Every effect of the reservation (`recheck`, `commit`, `retire`) still runs under the issuing control captured at birth (`operate` -> `withIssuedResourceOperationV1(control, ...)`), and `readNativeStorageReservationPolicyV1` still requires the exact issuing control (`captured.control === control`), so a descendant can present the receipt to a consumer but cannot read the policy or act under the issuer's authority. Pid reuse / dead process: the receipt is an in-process object in WeakMaps, there is no cross-process identity to forge.
- Law (new, red-capable, green now): `📦️artifacts/🏗️native-build/💾️storage/🧪️tests/🎟️gate/{🟦️.ts,🔣️.json,🥒️.feature}` + schema `🧬️schema/🎟️gate.json`: 9 closed vectors (issuer, narrowed child, renewable child, grandchild accepted; retired child, sibling, issuer's parent, unrelated control of the same Original, fabricated control refused) against an independent recursive SQLite lineage query over the controls the law derived; real reservation through `acquireNativeStorageV1` with a stub enforcing port.
- RISK (pre-existing, same in the old code, NOT introduced by the change, not changed): the signal-equality path accepts any control object that carries the issuer's signal: a fabricated frozen object `{signal: issuer.signal, ...}` and an unrelated top-level control of the same Original (`createIssuedResourceControlV1(original, …, 0)` shares the invocation signal) both pass (probe `authrev-d-tools/gate-probe.ts`: `forged-same-signal=accepted | sibling-top-same-signal=accepted | retired-loan-same-signal=refused`). Exploiting it needs code that already holds the signal inside the same process; many call sites also call `requireIssuedResourceControlV1` themselves. Fix when wanted: when the issuer is a live issued control require identity-or-descendant (`issued===control || descendant`) and keep signal equality only for non-issued fixture controls; needs a census of the ~35 call sites for sibling same-signal callers first, so it was not applied in a wave that is still moving.

## (b) Draining Original admission: FIXED

Old invariant: after the callback returned (`drain` sets `accepting=false`) nothing new is admitted anywhere beneath the Original, `settle` then retires it (`live=false`) and every accepted operation has settled by then. New code relaxes this: `admit` accepts a draining birth when a live accepting parent control is named and the birth has no failure; `track` checks only the owner for `accepting` and the ancestors for `live` and "no failure".
- Defect found: the relaxation opens a window between the moment `drain`'s loop observes `pending.size === 0` and the moment `settle` sets `live=false` (two microtask ticks: `drain` returns, `await drain` resumes). A continuation that reaches `withIssuedResourceOperationV1(syncControl, …)` in exactly that window was admitted into the pending set of an Original that then retired without waiting for it: the operation completed after the Original had settled. Reproduction (`authrev-d-tools/drain-probe.ts`, `AUTHREV_HOPS=2`): `w1-end,original-settled,late-end`; with 0 or 1 microtask hops it is joined, with 3 or more it is refused, with 2 it was orphaned.
- Red law first, then fix at the source: new law `🧭️routing/📥️invocation/🏃️process/🧪️tests/🌊️drain/{🟦️.ts,🔣️.json,🥒️.feature}` + schema `🧬️schema/🌊️drain.json`: vectors `scope in {process, control}` x `hops 0..8` (the continuation reaches the admission after `hops` asynchronous steps); invariant: the operation is joined or refused and never completes after settlement, checked with an independent SQLite event log (`late.seq > settled.seq` count must be 0); `hops=0` on the process scope must be joined (the relaxation itself). Red before the fix (`{"scope":"process","hops":2,…} Expected: 0, Received: 1`), green after.
- Fix (`🧭️routing/📥️invocation/🏃️process/🟦️.ts`): `Scope.drained`; `drain` sets `owner.drained = true` in the same synchronous step that observes the pending set empty; `track` and `admit` refuse when `row.drained` (docstring on `drain`). Admission therefore closes exactly when the owner is known empty; hops 2.. are now refused instead of orphaned; nothing else changes.
- Other angles, all fine: (1) a new top-level control, a new top-level loan and a nested process envelope under a draining Original stay refused (`admit` without parent), pinned by new test 2 of the law; only operations and narrowed controls beneath a still live, accepting owner are admitted. (2) Failure: any failure of accepted work poisons every ancestor (`failures.length > 0`), so the "first failure" and "retry after tracked failure" laws still hold (`🚪️admission`, `☣️retry-after-tracked-failure`, `🥇️first-failure` green). (3) Drain that never completes: new admissions require `requireIssuedResourceControlV1`, which throws on the Original's cancellation signal and on every deadline of the chain, so a self-renewing chain ends at cancellation or deadline; without any deadline it is an unbounded body like any other (not new). Cancellation pinned by new test 3 of the law: after the signal fired a nested operation beneath a live owner is refused with the cancellation reason and the accepted work is still joined. (4) Control loans still refuse nested creation while they drain (`admit` walks `parentControl` with the old `accepting` rule); only the birth was relaxed, so the physical-cleanup body (`beginAcceptedPhysicalCleanupV1`, which stops body admission) still refuses new nested controls; operations beneath an already existing nested control are now joined into the body drain, and the same `drained` flag covers its join. (5) The leftover timers of a refused `controlFor` are cleaned when the parent retires (unchanged).
- Orphaned law family reinstated: `📥️issuance/🧪️tests/📥️drain/🟦️.ts` exports `proveAcceptedOriginalDrainV1` (parent waits for accepted child, late admission refused, interrupt drain, nested drain, detached failure) but NO file in the tree (nor HEAD) calls it: zero coverage of the drain laws that guard exactly this change. New driver `📥️drain/🧭️modes/{🟦️.ts,🔣️.json,🥒️.feature}` runs the four self-contained modes, each as the only Original of its own process (the image/baseline modes need native image options and stay with their owners, still uncalled: FOR the native-image owner). All four modes pass on the current tree, with the fix.

## (c) Capacity-grant handover: FIXED (+ two RISK-low)

Design reviewed (`🏗️build/🌡️host-capacity/🎫️gate/🤝️handover/🟦️.ts`, `📏️decision/🟦️.ts` `decideHostHandoverV1`, restart custody registry in `🔁️churn`, `🔄️reexec/🟨️.mjs`, `systemAncestryV1`).
- SOUND: a claimant needs (all under the gate lock, first failing check names the reason): well-formed `<id>.<token>`, a current live grant row (pid alive, boot tolerance, fresh heartbeat), the exact one-time token (`timingSafeEqual`, row rewritten without `handover` on adoption, so a second claim is refused), offer younger than 120 s, its OWN parent equal to the offerer by pid AND start time (`ps lstart` / `/proc` tick / CIM date, read the same way on both sides), `grant.pid === fromPid`, same operation. The token is also readable in the ledger file, so it is not a secret: the binding is the parent identity, and only the replacement is started by the offering wrapper. Pid reuse cannot pass (pid + start time), a dead offerer fails `alive(grant.pid)` and a re-parented replacement fails the parent read: all fail closed into the normal queue with an EN/DE reason. A killed offerer leaves a row whose pid is dead, reaped like any other. Two competing claimants are serialised by the lock. Cancellation: the claim waits for the lock in the gate's own cancellable loop and removes the lock only after taking it. The park bound (120 s) and the 30 s maximum restart backoff keep a parked grant from holding capacity beyond the gap; the registry holds at most the one grant of the outermost command in practice (nested/daemon scopes never park: `restartExpectedV1` needs an open outermost wrapper).
- Defect fixed: the claim read the parent's identity (`systemAncestryV1`, a synchronous `ps` listing with a 20 s timeout, or a PowerShell CIM listing on Windows) INSIDE the critical section. The gate lock goes stale after `lockStaleMilliseconds` (10 s in the shipped policy) and `takeLock` steals a stale lock, so a slow listing under fleet load let a waiter into the critical section while the claimant rewrote the row, and the claimant's `finally` then removed the thief's lock. The identity does not depend on ledger state, so it is now read BEFORE the lock is taken (`claimHostGrantHandoverV1`; equivalent verdict: while the offerer is alive it stays the replacement's parent). Red law first: new test in `🧪️tests/🤝️handover/🟦️.ts` (+ feature scenario) asserts the lock directory does not exist while the parent reader runs, and that a refused claim leaves no lock; it failed (`seen = [true]`) before, passes now. Handover law file 9/9 green.
- RISK-low (not changed): `parkHostGrantV1.release` removes the row without taking the gate lock (`row.pid === input.pid` check then `remove`). If the 120 s park bound fires in the milliseconds between the replacement's row read and its rewrite, the offerer's release could delete the adopted row; it needs a restart wrapper that waits close to 120 s between park and spawn, while the declared backoffs are at most 30 s. A lock-taking release needs an async or best-effort release path (the `exit` handler is synchronous), so it was left for the owner.
- RISK-low (not changed): the parent identity comes from a 1 s resolution `lstart` on macOS/POSIX; a recycled pid inside the same second would need ~100 k forks/s, so it is ignored; Linux uses the start tick, Windows the CIM date.
