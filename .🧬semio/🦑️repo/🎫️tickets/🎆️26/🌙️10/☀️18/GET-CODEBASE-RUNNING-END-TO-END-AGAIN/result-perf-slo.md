## What it is

`repo bench list|run|compare` (a sibling of `repo incremental` and `repo concurrency`, live module path `B/📏️incremental/🏎️bench/`) measures the performance objectives of the build system in the disposable checkout copy that `repo incremental prepare` provisions (`bench run --prepare` does that itself, fresh), judges them against one SLO table and compares with a stored baseline. Everything it measures goes through the copy's own `repo` CLI (`bench` itself names no build tool; `nx|bazel` are only the existing `--tool` values, the tool output markers are data in the schema policy).

- **Schema first** (`🧬️schema/🔣️.json`, 42 definitions, closed, Policy const): units, probes, objectives, samples, series, verdict rows, report, comparison, fixture. `🎯️slo/🔣️.json` is the table (labels EN+DE for every text, 110 keys), `🟦️.ts` the model, `🏃️runner` the probes and real ports, `⌨️command` the CLI.
- **Probes** (21, kinds `cli-help noop edit graph cache concurrency`, lanes `oneshot` and `resident`): `repo --help`; warm no-op `run` and test target one-shot and via the resident service; edit to rebuild start and edit to green for four language units (TypeScript `framework-graph:test`, Rust `proctor:build`, Go `repo-move-go:test`, Python `ui-styling-py:test`; each edits one source file with a unique private-body line, restores it byte for byte afterwards, also on failure and cancellation); graph of the selected scope (`run <target> --dry-run`) cold (once, only on a copy this run prepared) and warm; second-run cache hit ratio (through the incremental harness: Bazel compact execution log or Nx run record; uncached tasks are not counted); three concurrent agents (the real `repo concurrency` in process: makespan, longest wait for an unrelated project, speed-up over the serial reference); peak resident memory of the process tree (sampled in separate runs so timing stays clean).
- **Objectives** (32, 62 objective x implementation rows, `goal` = what we want, `gate` = what CI checks now, `source` names where a number comes from): user goals are `warm no-op <= 300 ms` (resident p95 blocking, one-shot median goal 300 / gate 1000 ms advisory), `edit -> rebuild start <= 500 ms` (resident p95 blocking per language, one-shot median advisory) and `second run 100 % cache hits` (min over runs, blocking, build and test target); further: help p95 goal 200 ms (cli-latency), cold scope graph gate 5 min (graph-speed), warm scope graph, memory goal 512 MiB (hot-cache), concurrent-agent wait goal 1 s / gate 5 s (conc-harness). Objectives without goal and gate (edit to green, makespans, TypeScript memory) only record; the baseline comparison guards them. 8 objectives (16 rows) are blocking, all others advisory (nothing is blocking that cannot be reached today: the resident rows are `unproven (service unavailable)` until hot-cache lands).
- **Statistics**: n, min, p50, p95, p99, max, mean; percentiles interpolate linearly between ranks (the inclusive method of Python's `statistics.quantiles` and NumPy's default); a statistic needs enough samples (p50/mean 3, p95 20, p99 100, otherwise `unproven: too few samples`); the table admission refuses an objective whose probe can never supply that many (`--runs` overrides the authored counts for quick runs). Failed commands are counted and left out.
- **Verdicts**: `pass` (goal met), `warn` (gate met, goal not), `fail`, `recorded`, `unproven` with a reason (`no samples`, `too few samples`, `probe failed`, `service unavailable`, `not cold`, `host saturated`, `start unobserved`, `unsupported`). Host load is annotated per series (load per core: quiet < 0.5, busy, saturated >= 1.5, unknown on Windows): a time that misses its gate on a saturated host is `unproven` (load only inflates), a met goal stays met, a warn is flagged `*`. The rebuild start counts only from a tool marker line: without one the value is just a bound (first output = lower, process exit = upper) and the row stays unproven unless the bound already decides it (same discipline as the lock-wait bounds of `repo concurrency`).
- **Baseline and compare**: `bench run --baseline=<report>` or `bench compare --current=<report> --baseline=<report>`: per objective x implementation `improved | same | regressed | inconclusive (regression of a time on a saturated host) | incomparable (other host class: platform-arch-cores, or either side unproven) | new | missing`, tolerance per objective (`relative` share + `absolute` margin, strict edges); `--save-baseline=<file>` stores the report (the report format is the baseline format). Blocking objectives that fail or regress make the exit code fail, after the reports were written; advisory ones are only reported.
- **Output**: text or `--json` on stdout, `--file=<report>` (through the repository report store), `--markdown=<file>` (GitHub step summary ready), EN/DE (`--lang`, no default language), progress per probe and sample (`bench:<probe>:<tool>:<i>/<n>`), cancellation check before every command, `--max-load=<per core>` refuses a busy host, `--slo=<id|probe:<id>|kind:<kind>|all>` selects (cold probes run first, probes then in kind order).
- **CI** (`C/perf-slo-tools/wire.py` workflow edit of `.github/workflows/build-system.yml`): job `bench` (linux, macos), after `smoke`, `continue-on-error: true` (non-blocking first), pinned actions, no step names an implementation: `preflight`, `tools setup all`, Bun store restore, `dependencies sync --all`, `bench list`, `incremental prepare --fresh`, `bench run --slo=all` with the baseline of the last default-branch run of the same runner class (GitHub cache), JSON + markdown report uploaded and appended to the step summary, new baseline stored only by default-branch pushes. Blocking rows fail the step, never the workflow, until the job loses `continue-on-error`.

4. Calibrate the start markers on the first live edit run: `Policy.markers` in the schema lists the line patterns (`^> nx run `, Bazel `Analyzing|Analyzed` and `[n / m]`); the report prints how the start was observed per series (`marker / first-output / exit`). Until every sample has a marker the start rows stay unproven (a lower bound can still prove a failure), which is intended.
5. Flip the CI job to blocking only after a few default-branch baselines exist: remove `continue-on-error` in the workflow; flip individual objectives with a data edit (`enforcement`).

## Open items

- Targets are only as good as their source: the three user goals are exact; 200 ms help, 5 min cold graph, 512 MiB memory and 1 s / 5 s waits come from earlier results (`source` names them); the warm scope graph gate (2 s), the p99 help gate (1 s) and all tolerances are provisional. Edit to green has no absolute target on purpose (recorded, regression-guarded).
- `speedup` over the serial reference is collected but has no objective: the harness' serial run follows the concurrent one and is therefore warm (see result-conc-harness open items).
- `bench run` does not yet check that a unit's edited file reaches its target (the incremental `plan` does for the TypeScript and Rust pairs; the Go and Python pairs are authored from the concurrency workload and the project.json): run `repo incremental plan`-style checks once after apply, or add the unit slice check to the runner.
- The resident lane is detected by the operation `service` in the copy's catalogue and driven by `repo service start|stop`, `--service=require|off` as staged by hot-cache; if its final CLI differs, it is data (`Policy.serviceOperation`, `oneshotFlag`, `residentFlag`) plus the start/stop arguments in the runner.
- README EN+DE section belongs to docs-build (`--help` and the catalogue are the authoritative text).
