# result-bworkers: worker pools for Bazel and Nx behind one neutral contract

`C` = this ticket. `L` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`, `B` = `L/🏗️build`, `Z` = `B/🔧️tools/🏗️bazel`. Phase rule respected: **everything is staged as copies under `C/bworkers-tools/staged/`, nothing is applied to the checkout** (no PAUSE LIFTED seen). Provisioned Bazel 8.4.2, Bun 1.3.14, Nx 23.2.0, macOS arm64, host load 27-63 on 10 cores during all measurements.

## Verdict
- The neutral worker contract (policy + plan + JSON worker protocol) exists schema-first with EN+DE help for its CLI flag, and **both tools map it**: Bazel with persistent JSON workers (singleplex and multiplex, cancellation, memory limit, per-mnemonic strategies and instance bounds), Nx with `NX_PARALLEL` and (only where an executor registers one) `NX_BATCH_MODE`. Every contract field is mapped exactly once per tool and reported as `exact | approximate | unsupported`.
- Persistent Bazel workers run the **real production action path** (birth handshake, control channel, snapshot capture, restore, cancellation) in-process, verified end to end with the staged production adapter against real Bazel: warm workers across builds, failure exit codes, `SIGINT` of the owner, a protocol-level `{"cancel":true}`, multiplexing, and a disk-cache hit of an action that another strategy produced (worker and non-worker actions have the **same action key**, so caches are shared across modes and, later, remote).
- Measured effect on this saturated host: **CPU per action 2.50 s -> 1.46 s in steady state (-42 %)**, startup 1.5 CPU-s per worker, break-even after 1.4 actions per worker. **Wall clock is not consistently better** (see Measurement): 85 % of an in-worker request is the per-action open of the `graph` cache store partition, which workers do not remove. That is the next lever (open items 1).

## Neutral contract (schema-first)
Files (all new unless marked): `B/👷️workers/🧬️schema/🔣️.json` (JSON Schema: `Policy`, `Plan`, `Kind`, `Rule`, `Mapping`, `WorkRequest`, `WorkResponse`, protocol bounds), `B/🔣️policy.json` (**edited**: new `workers` section, the authored data), `B/👷️workers/🟦️.ts` (policy reader, classification, plan resolution, switch parsing, `workerContractFieldsV1`), `B/👷️workers/📨️protocol/🟦️.ts` (request parser, response encoder, serve loop, output capture, input reader, digest-keyed module cache).

| Contract field | Authored value (`workers` in `B/🔣️policy.json`) |
|---|---|
| action kinds | `test check generate build script service`, classified from the target name and continuity by ordered rules (first match, default `script`); no tool vocabulary |
| `maxInstances` per kind | test 8, check 8, generate 4, build 2, script 4, service off (upper bounds) |
| `multiplex` / `inProcess` per kind | false / true everywhere (schema forbids `multiplex && inProcess`: an in-process body borrows the process environment) |
| local job count | `min(cores, 8)` unless `--parallel` / `SEMIO_BUILD_PARALLEL` |
| memory budget | 30 % of host memory for all pools, 512 MB per worker; the plan gives each kind one instance first (priority test, check, generate, build, script) as far as memory holds instances, then spreads the rest up to the bounds; kinds that no longer fit run without workers |
| sandboxing | false (see open item 3) |
| cancellation, protocol, cleanup | true, `json`, garbage collection every 256 requests (a worker never exits between requests: a pool may hand it the next request at any moment) |

CLI surface (EN+DE help in `B/⚙️operations/🔣️catalog.json`, 44 help snapshots regenerated): global flag `--workers on|off` next to `--tool`, also `SEMIO_BUILD_WORKERS`. `parseBuildInvocationV1` consumes it (never after `--`), `runBuildCliV1` puts it into the invocation environment, `selectBuildTasksV1` returns `workers` for Bazel, `nxBuildEnvironmentV1` reads it for Nx.

## Bazel
- **Mnemonics the adapter emitted before:** only `RepoTask` (every non-continuous task) and `RepoLauncher`. All 8,026 targets of the static graph run `bun ./📜️script.ts <sub>` (the real tool, tsc / vitest / cargo / vite, is a child of that script), so the Bazel action itself is always a bun/TS process. Census by neutral kind (8,026 targets): build 2,609, test 2,249, check 883, script 812, generate 165, service 1,308 (launchers, never workers).
- **Now:** `RepoTest RepoCheck RepoGenerate RepoBuild RepoScript` (from the kind) and `RepoLauncher`. `repo_task` takes `mnemonic` and `multiplex` attributes; the rule always declares `supports-workers`, `requires-worker-protocol=json`, `supports-worker-cancellation` (and `supports-multiplex-workers` when the policy says so), passes `manifest output snapshots...` in **one multiline flagfile** and the implementation (`runner`, `source`) as `tools` (a changed implementation restarts the workers). Whether workers are used is decided only by flags, so BUILD and action keys do not depend on the strategy.
- **Flags generated from the plan** (`bazelWorkerSettingsV1`): `--jobs`, per mnemonic `--strategy=M=worker,sandboxed,local` (`sandboxed` alone refuses the `no-sandbox` host-state actions; measured) or `--strategy=M=sandboxed,local` when off, `--worker_max_instances=M=N`, `--worker_max_multiplex_instances`, `--worker_multiplex|--noworker_multiplex`, `--worker_sandboxing`, `--experimental_worker_cancellation`, `--experimental_worker_strict_flagfiles`, `--experimental_total_worker_memory_limit_mb` + `--experimental_shrink_worker_pool`. Not used: `--experimental_worker_memory_limit_mb` (kills a busy worker and fails the build) - the per-worker bound is kept by the runtime (garbage collection above the bound).
- **Worker runtime** (adapter edit): `work-action --persistent_worker` serves the JSON protocol on stdin/stdout (stdout carries only responses: everything an action prints is captured per request through `AsyncLocalStorage` and returned in `output`); `work-action @flagfile` is the one-shot fallback and runs the old child-process path. Per request: `recheck()` of the captured implementation, the unchanged birth handshake against the owner, then the action body **in the worker process** (`runBazelActionV1`, extracted from the old child entry) with the environment the child would have received; leaf commands stay separate process trees (`bun exec`), their stdin is an empty pipe (the worker's stdin is the protocol), `cancel` aborts the request through the existing control-channel cancellation and kills the leaf tree. `multiplex` kinds (policy: `inProcess=false`) run one child per request concurrently; in-process bodies are serialized by a lock.
- Edited: `Z/📜️script.ts` (+113 changed lines, listed anchors in `C/bworkers-tools/build_adapter.py`), new `Z/👷️workers/🟦️.ts` (mapping).

## Nx (verified in `node_modules/nx` 23.2.0)
Available: `parallel` (`NX_PARALLEL`, `--parallel`, `nx.json parallel`; the repo's contract test pins `nx.json parallel` to undefined, so the env route is used), `NX_BATCH_MODE` / `--batch` (batch implementation of an executor, `tasks-schedule.js`), `useDaemonProcess` (graph only). The repo's executors (`📋️executors.json`) register **no** `batchImplementation`. Mapping (`nxWorkerSettingsV1`, new `L/⚡️caching/🚀️bootstrap/🛠️tools/👷️workers/🟦️.ts`, wired in `nxBuildEnvironmentV1`): `NX_PARALLEL` = explicit `SEMIO_BUILD_PARALLEL` / `NX_PARALLEL` else the plan's job count (exact); `NX_BATCH_MODE=true` only for multiplexed kinds and a batch-capable executors file (approximate, never today); worker pools, instance bounds, in-process, memory budgets, sandboxing: `unsupported` (Nx forks a process per task); cancellation: `approximate`. Oracle: Nx's own `readParallelFromArgsAndEnv` reads our value back.

## Open items
1. **Hold the `graph` store open across requests** (the dominant per-action cost, 80+ % of a warm request). It needs an invocation-independent store session in `withRepositoryCacheStoreV1` / leases (library, frozen); until then the worker saves CPU, not latency.
2. Apply the staged set after PAUSE LIFTED (`python3 C/bworkers-tools/apply.py`, inspect, `--write`; if drift is reported rerun `C/bworkers-tools/build_all.sh`), then run the list above live plus the `SEMIO_BAZEL_INTEGRATION=1` purpose tests (cancellation phases) and `bun repo --tool=bazel run` on T1/T3.
3. Sandboxed workers: host-state actions are `no-sandbox`; with `--worker_sandboxing` relative work request paths would resolve in the sandbox directory but births grant absolute execroot paths (refused, fail closed). Default stays off until the sandbox owner (bzl-sandbox) lands.
4. In-process **leaf** execution: `WorkerModuleCacheV1` (digest reset rules) is built and tested but not wired; repo scripts rely on `import.meta.main`, so they need an exported entry convention (`runWorkerCommandV1(argv, context)`) before they can opt in.
5. Behavior notes: every `repo_task` action re-keys once (new command line); mnemonic `RepoTask` is gone; Nx falls back to the plan's job count when neither `SEMIO_BUILD_PARALLEL` nor `NX_PARALLEL` is set (previously Nx's 3; the CLI always sets it through `devToolingEnv`, so unchanged there).
6. A worker cannot restart itself between requests (Bazel may write the next request first), so memory is bounded by garbage collection plus Bazel's total limit with pool shrinking; a runaway action would still need the per-worker kill (`--experimental_worker_memory_limit_mb`) which can fail the build.
7. Peers edited a file of the captured closure during two runs (`🧬️schema/📈️progress.json`): the adapter failed closed ("Captured implementation Source changed"); the harness retries. The same can happen to a worker request mid-build by design (recheck per request).

## Deviations from the brief
- Scratch root: the brief asks for copies under `C/🗑️generated/bworkers-*`. The adapter refuses captured paths over 256 characters and the library has paths of 159 characters, so any root below `C` (111 characters) breaks it (297). Test overlay (copies, never symlinks into the checkout) is `/private/tmp/bworkers/r`; its `node_modules/@semio-tech/*` are links to overlay copies (the production closure capture requires realpaths inside the root), none points into the checkout. Bazel runs used the live root read-only (like `result-bzl-real.md`) with synthetic projects under `C/🗑️generated/bworkers-synth*`; they open the shared `.cache/b` graph store as every task does and wrote nothing into tracked files.
