#### Der Remote-Cache-Server

Der geteilte Ergebnis-Cache ist ein hauseigener Server und kein Skript: Ein Prozess bedient das HTTP-Cache-Protokoll von Bazel und die selbst gehostete Cache-API von Nx aus einem Verzeichnis, mit einem Budget und einer Verdrängung. {{?remote-cache-server::::Der eigene Befehl unten ist ein vorbereitetes Set; heute erledigen `repo cache serve` und `repo cache remote status` diese Aufgabe und sind unter Cache-Modell und Remote-Cache beschrieben. }}Zustand: {{@remote-cache-server}}.

```bash
repo remote-cache serve --port 6090
repo remote-cache serve --read-only --tls-certificate <cert> --tls-key <key>
repo remote-cache status
repo remote-cache gc --dry-run
```

- **Ein eigener Befehl.** `repo remote-cache serve|status|gc` ersetzt `cache serve` und `cache remote status` (kein Alias); Meldungen gibt es auf Englisch und Deutsch (`--lang`, `SEMIO_LANGUAGE`, Locale; löst sich keine auf, werden beide ausgegeben); der Fortschritt läuft über `remote-cache:open|scan|ready|serving|probe|verify|remove`; Strg+C beendet `serve` (Exit 0) und `gc` (Exit 130).
- **Protokolle.** `/ac/<sha256>` und `/cas/<sha256>` mit GET, HEAD und PUT und einem optionalen Präfix `/<instance>`; der CAS-Körper wird beim Streamen gehasht und bei Abweichung mit 400 abgelehnt; der Action-Cache wird atomar ersetzt. Nx nutzt `/v1/cache/<hash>` (einmal beschreibbar: 409 beim zweiten Schreiben, 411 ohne Länge) im selben Index, Budget und derselben Verdrängung.
- **Action-Ergebnisse werden geprüft.** Ein strikter Decoder von `ActionResult` und `Tree` (Wire-Typen, UTF-8, kleingeschriebene Digests, Größenkonsistenz) läuft bei jedem PUT. Mit der Standardrichtlinie `complete` wird ein PUT mit 400 abgelehnt, es sei denn, das Ergebnis ist wohlgeformt und jeder Blob, den es nennt, und jede Datei eines Ausgabebaums ist gespeichert (Bazel lädt Blobs zuerst hoch); ein GET antwortet mit einem Fehltreffer und verwirft den Eintrag, sobald ein Blob den Store verlassen hat. `structure` und `off` sind wählbar.
- **Atomar und nebenläufig.** Temporäre Datei plus Umbenennen oder Link in einem Temp-Verzeichnis je Prozess (Verzeichnisse toter Prozesse werden gekehrt), eine Byte-Reservierung, ein Server je Verzeichnis (eine Sperre; ein zweiter Start scheitert mit klarem Text), eine getrennte Collector-Sperre. Zwei echte Fehler des früheren Stores fanden die neuen Tests und behoben sie: Die Byte-Buchhaltung driftete, wenn gleichzeitige Schreiber denselben Schlüssel ersetzten, und wenn ein Lesen mit einem Ersetzen wetteiferte.
- **Budget und Verdrängung.** Ein reiner Plan (zuerst hängende Einträge, dann Leerlaufalter, dann am längsten nicht benutzte bis auf 90 Prozent der Grenze, deterministische Gleichstände) wird vom Server und von `remote-cache gc` benutzt, das auch läuft, während ein Server läuft. Das Standardverzeichnis zog von `.cache/remote-cache` (außerhalb jedes Budgets) in den Ledger-Bereich `remote-cache` (Repository-Wurzel, 3 GiB); die Server-Grenze ist 2,5 GiB; `repo cache gc` delegiert den Bereich an denselben Collector.
- **Zugriff.** Inhaber-Tokens zum Lesen und Schreiben (Vergleich in konstanter Zeit, 401 als Klartext, 403 für ein Lese-Token, das schreibt); `--read-only` oder `SEMIO_REMOTE_CACHE_SERVER_READ_ONLY` lehnt jedes Schreiben ab; `--tls-certificate` und `--tls-key` bedienen HTTPS; ein Listener außerhalb von Loopback braucht ein Token. Die Client-Seite ist unverändert: Der Vertrag wird für Bazel (`--remote_cache`, `--[no]remote_upload_local_results`, ein Credential-Helper) und für Nx (Umgebung) umgesetzt, und `remote-cache status` gibt den Vertrag, beide Umsetzungen, eine Probe je Protokoll, das eigene `/status` des Servers und den lokalen Store aus. Das hauseigene Backend `--tool=semio` schreibt `/v1/cache/semio-<key>` mit derselben Einmal-Regel.
- **Gemessen.** Echtes Bazel 8.4.2: Ein kalter Build lädt hoch, ein sauberer Neubau ergibt 2 Remote-Treffer, und eine Kopie des Workspaces in einem anderen Verzeichnis mit zweiter Output-Base baut nur mit Remote-Cache-Treffern; anonymer Zugriff erhält 401, und ein Nur-Lese-Client schiebt nichts. Echtes Nx 23.2.0: 0 von 2, danach 2 von 2 (100 Prozent) nach dem Löschen des lokalen Caches; ein falsches Token bricht den Lauf ab. Richtwert für den Durchsatz eines Prozesses bei Last 40: 4,6k PUT pro Sekunde und 5,6k GET pro Sekunde mit 4 KiB, 23k Fehltreffer pro Sekunde. Drei Python-Prozesse mit je 24 Threads schrieben überlappende Schlüssel ohne Teildatei und mit Server-Buchhaltung gleich dem Plattenscan.
- **Nicht verifiziert.** Bazel über HTTPS mit einer privaten Zertifizierungsstelle (der Bazel-Client vertraut dem JDK-Store, eine öffentliche Stelle funktioniert), Windows und Linux, HTTP-Kompression (in Bazel 8.4.2 nicht unterstützt), ein Protokoll je Anfrage (ein Haken existiert); der CI-Workflow ruft noch das alte `cache remote status` auf.
