So the invalidators are exactly two, and neither is an implementation/stamp/schema identity:
1. **The command source closure is recorded row by row in every project record.** Every target that runs a `repo ...` script has the transitive import closure of that script (about 2,000 files) as its input roster (`SEMIO_SOURCE_CLOSURE_<sha(roster)>` token, `compactSourceInputs`). The np record of each of 3,170 owners therefore carries ~13,000 observation rows (analysis, resolve, exists, file, lstat, readdir ... of every closure file). A peer edit that changes the IMPORTS of any closure file (fleet: every few minutes) changes the roster/analysis result of one closure shared by all of them, so all 3,170 records go stale, and each re-inference costs ~0.3 s wall (persisting/validating those 13k rows) = 18-25 min; meanwhile new peer edits arrive, so the next reader starts the same rebuild again (livelock).
2. **A dependency-generation change flips `resolve` rows.** A bare-specifier resolution inside the closure (e.g. `@iarna/toml`, `typescript`, `nx/src/native`) is recorded as the absolute path inside `.cache/b/d/m/j/<generation id>/node_modules/...`, so every dependency generation change (any `package.json`, lock or patch edit) stales these rows although the resolved package kind is the same and the roster contains only workspace files.

Not causes (checked): `identity`, `implementation` (stamps + data digests), `env`, `membership` and `global` digests of gen 28..32 are all equal; `sourceAnalysisFactHoldsV1` replays correctly after the reuse fix (28 edited files with an unchanged import structure stayed valid); the lease `repository-graph-facts` is held only by builders that re-infer for the reasons above.

## 4. Structural fix still open (design, not built)
The np value of each project embeds the concrete token `SEMIO_SOURCE_CLOSURE_<sha(roster)>` (and `externalDependencies`, `generatedDependencies` that are functions of the same closure), and its record carries the ~13k closure rows. Needed: (1) the closure walk records ONE composite fact (`entries`, digest of the closure result: roster + generated imports + packages) re-validated by recomputation through a registered computation provider (like the source-analysis providers), instead of 13k rows; (2) the np value holds a stable alias `SEMIO_SOURCE_CLOSURE_REF_<sha(recipe)>` (recipe = entries + literal inputs + exclusions, stored content-addressed), and the generation layer resolves aliases to concrete tokens when it shapes/assembles owners (per distinct recipe, memoized), so a roster change rewrites tokens (seconds) instead of re-inferring owners; non-token closure outputs (generated dependencies) must stay validated by the composite fact. Touches observation (new fact kind + schema), script-inputs (provenance of closure lists), project-assembly (`internCommandSources`), `compactSourceInputs`, generation shaping/assembly, fixtures. Candidate owner: a dedicated wave with a harness differential (late-bound vs full inference over 100 projects).
Operational mitigations until then: readers that only need current tool behaviour can use `SEMIO_BUILD_GRAPH_POLICY=current` (serves the newest sealed generation without verification, no builder lease); the admission policy reserves 5,120 MB per `show`/`graph` although a verified-generation reader peaks at about 2.4 GB (8 `show` commands were queued at 02:38; editing `build/🔣️policy.json` is itself a declared-data change that stales every owner, so it must be done together with another unavoidable rebuild).

Design (what was built, all `L/🏗️build/...`):
- `👁️observation/🟨️.mjs`: fact kind `closure` (a QUESTION put to a closure entry, answer stored as a JSON string; schema enum extended, record stamp unchanged because records of either kind stay valid); `registerClosureProviderV1({answer, settle})`; `settleClosureRowsV1` called before facts are checked (np lookup, `observationsHold`); `observeDetachedV1(compute)` runs a computation with its observations detached from the project that asked and returns `{value, rows, layers}`: the rows it observed itself plus the stored row arrays of the shared computations it reused KEPT BY REFERENCE (`DetachedScopeV1`), so a thousand recipes over one closure hold that closure once; memo hits validate a stored row array once per validation round (`memoRowsHoldV1`, by array identity) instead of once per user.
- `📥️inference/🧭️script-inputs/🟨️.mjs`: recipes (`native-command`, `native-target`, `generic-target`, `closure-of`, `target-sources`: the kind of command input and the target fields that decide it, never files), `closureApiV1(scripts, workspaceRoot)` (one interface for project assembly: in the late mode `nativeCommandInputs/nativeTargetCommandInputs/genericTargetCommandInputs/closureOf` return symbolic lists, a Proxy over `[]` that iterates as the single item `{closureRef:<recipe key>}` and throws on any other read; the queries `some`, `query(...)` (whole-workspace keys), `targetClosureSome`, `generatedDependencies` answer from the entry and RECORD the answer as a `closure` fact; in the direct mode they run on the lists), the provider (entries computed once per process with detached observations, kept while their rows hold; `answer` only while the entry holds, otherwise `!stale`), `resolve(recipes)`.
- `📥️inference/🧱️project-assembly/🟨️.mjs`: every read of a closure goes through the API (predicates are queries now: native driver reach, Cargo test driver reach, vitest/context reach, generated dependencies, whole-workspace key check); groups with symbolic items stay symbolic and the project carries `closureRecipes` + `symbolicGroups`; `resolveClosureRefsV1` brings every named entry up to date, replaces the markers by the files in place, compacts the symbolic groups exactly as the direct inference does and merges groups that came from different recipes but hold the same files (renumbered as the direct inference numbers them).
- `📥️inference/📦️project-nodes/🟨️.mjs`: late mode when the caller is the generation builder (`snapshot` + `onOwnerObservations`, never the owner-admission slice path, never the legacy whole-graph receipt path); `commandRevision` of the record key is the recipe key, the key head carries `closure-references` so a late record is never read by another mode; after the record the owner's observations are the record's rows PLUS the rows of the entries it names (`onOwnerObservations`); farm workers receive the recipe and rebuild the handle (`lateClosures` in the session).
- `🕸️graph/🟦️.ts` `holdsByStat`: `closure` rows are not probed by the planner: their validity is subsumed by the entry rows that are part of the same owner (an owner whose closure moved is dirty through those rows, and its np record then answers the questions again).
Why a roster change no longer stales a record: the record depends on the closure only through the answers it was given (a handful of booleans/lists), never through the roster; the roster reaches the graph only through the resolution step, which is recomputed per owner from shared entries.
Measured (120 live projects = 110 owners, scratch cache, `graph-b-tools/inf-b.sh`, oracle `cmp2.py` = effective input set per target after group expansion + everything else byte-equal): 0 of 110 differ semantically from the direct inference (also with 3 farm workers); the only byte differences are the order of `{env: SEMIO_BUILD_MODE}` relative to the group names, and token values of rosters that moved between the two runs. Rows per record 1,780,808 -> 157,835 in total (median 15,370 -> 859), np disk 16.6 -> 8.7 MB, cold inference CPU 33.8 -> 18 s, warm run 0 of 110 recomputed (the direct inference recomputed 37 of 38 minutes later because peers had edited the closure). Law: NEW `🧪️tests/🔗️late-closures` (3 pass): fixture + schema; a record is reused when a new import moves the roster, when an edit moves no import and in a process that has no entries (`resetClosureEntriesV1`), recomputed when the question's answer moves; the roster equals the independent Python walker AND esbuild at every step; record rows < 40 while the entry rows are more; third test: groups from different recipes with equal files are merged and renumbered.
Residual closure sensitivity: projects whose targets use input-precision rules (`preciseInputsV1` derives files through `importClosure`), print documents and TypeScript artifact projects still record closure rows in their record (about 10 percent of the sample: max 14.8k rows). Pre-existing red suites unchanged by this work: inference `💾️cache` (2), `🧷️closure-facts` (3, a text law on a function body a peer changed, a block-count assertion), `🎓️course-inputs` (3), `🔌️providers` (1) (all about `📈️progress.json` or fixture layout of peers).
Live proof: see the status line (r3).

## 9. Final round (artifact packages, pre-existing reds, profile of the slow projects)

Pre-existing reds fixed: course-inputs 3 (presentation resources are deliberately outside the command closure; `📈️progress.json` fixture layout), providers 1, cache 2 (fixture/realpath and driver reach boolean), closure-facts 3 (the census reads `ob/<digest>.br`; production fix `observationBlockDamagedV1`: a damaged or absent block is a miss, not a crash, and is unlinked on rewrite), plus `📦️project-nodes/🧪️tests/🚦️governed-dispatch` (red since HEAD: the inference call was behind a `run` variable; it now sits lexically inside `governor.run(...)`, which is also what the memory governor needs).
Profile of the slow projects (harness, `graph-b-tools/nodes-probe-b.mjs` with `TIMES=`, `FILTER=`, `NOEXIT=1` and `BUN_ARGS=--cpu-prof` exported to `inf-b.sh`): of 287 cold projects the median is 0.10 s and only one is above 1 s (the first, 8-12 s, is the once-per-process boot of the library, not a project). The slow ones are TypeScript artifact packages with a large import closure: `@semio-tech/framework-renderer-wgpu` costs 3.1 s after the boot (CPU profile: `observedSourceAnalysisV1` 5.9 of 12.5 s, TypeScript `createSourceFile` 3.4 s, `readFileSync` 1.4 s, `existsSync` 0.8 s). A refresh with every record removed but the other caches kept costs the same (the analyses are not persisted across records), so a refresh is parse bound: every TS file is parsed THREE times (`sourceImports` scopes `all`, `command`, `production` of `⚡️caching/📥️inference/🟨️.mjs` each run `createSourceFile`). APPLIED (it rides the full re-inference the next fix forces anyway): `sourceImports` now parses a file once and answers all three scopes from the same tree (`scopedImports`, one `remember` per scope). Oracle: the HEAD implementation against the new one over 3,460 repository files x 4 wrappers = 13,840 comparisons, 0 differences (`graph-b-tools/imports-diff.mjs`); harness wgpu subset (128 projects, cold) 18.4 -> 14.0 s without the boot, `@semio-tech/framework-renderer-wgpu` 3.06 -> 0.57 s, projects byte-identical (`projectsSha` equal), only the analysis rows move with the parser stamp. Microbenchmark of the idea: 400 files / 3.6 MB, 0.58 -> 0.22 s (`graph-b-tools/parse-once.mjs`).
