## Findings (base = live 15:00) and what is staged
1. HIGH starvation - booked cores + all-jobs growth (`allrun`). A quiet run's growth asks for all 8 jobs (`minimumJobs = preferredJobs`); our grants book `jobs x cpu`, the ceiling is 2 x 8 declared cores = 16. One 8-job run plus the 1-core quiet grants of two other agents = 17: both growths wait `load`, the first becomes a barrier head, the second waits `queue-order` - both for the whole long run (mixed-long: 404-426 s for a 50 s and a 10 s run while 3.6-4.2 GB of 16 GB are really in use). Fix (decision): a growth whose whole request fits the memory but not the cores is admitted with the jobs the cores leave (`reduced`, keeps the memory of its whole request; the capgrow grower adds jobs later), and an agent session with nothing else running gets its first job past our booked cores (bounded: one job per session above the ceiling). EN/DE `upgradedReduced`.
2. HIGH concurrency cap 2 - ramp slots (`allrun`). `memory.maximumRamping` 2 applies to every learned reservation (every class is sized below its 17920 MB default), so the third agent always waits `ramp` (hot: 43 s with 5.8 GB spare; print's learned ramp is 525-825 s). Fix: a reservation backed by the class's OWN measured peaks (`hostClassBoundV1` source `measured`) takes no ramp slot; thin evidence still does (the memory-fit burst law is unchanged).
3. MEDIUM bug - a nested invocation that inherits a quiet grant works with 1 job (`allrun`). `withHostCapacityV1`'s inherited branch upgrades the quiet grant, then hands its body the row it read BEFORE the upgrade: `handle.jobs = 1` -> `SEMIO_BUILD_PARALLEL=1`, `--parallel=1`, and the Bazel script's `--jobs=min(parallel, plan.jobs)` = 1. Every gate run today is a follow-up (quiet forecast) and the door re-executes the script under the inherited grant, so this very likely runs every product build with 1 local Bazel job (proved with the real gate: probe `sim/inherited-probe.ts` -> `handleJobs 1, rowJobsNow 8`; flags are not logged, so the product effect is unmeasured). Fix: re-read the row after the growth.
4. MEDIUM farm (`allrun` + `farmfree`). The graph farm's request (exec, 9 jobs, min 3584 MB) carries no agent session (ranks as holding nothing), can become a barrier head after 30 s, its grant observes the graph child it runs in (the run's grant counts that tree too: double count) and it holds 1-4 jobs / 3.6-9.7 GB until the graph construction closes although every gate refresh g11-g43 refused its workers (buildmem). Fix: the request is `elastic` (decided after every other request, never makes one wait, never a barrier, never an override), carries the run's session, observes 0 (its workers are descendants of the run's grant); `farmfree`: a disabled pool gives its host grant back at once.
5. MEDIUM progress (`behind`). No waiting/growing line said what it stands behind (operation is `run`/`exec`, counts only), and `N running` counted the grower's own quiet grant. Fix: requests carry a `label` (the target of `repo run`; `graph-farm`), grants keep it, `hostBlockersV1` names by reason what holds the waiter back (memory: our grants by committed MB; load: by booked cores; ramp: ramping slot grants; quiet-limit: quiet grants; queue-order: the requests served first; same-round admissions included; the host itself otherwise), max 3, largest first; EN `; behind A (running, 8 job(s), 3649 MB), …`, DE `; hinter A (läuft, 8 Job(s), 3649 MB), …`; the `[capacity] waiting Ns for run:` prefix and the `(… ahead)` part are unchanged (harness3 `logsignals.py` regexes still match).
