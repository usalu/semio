# Continuation Catalog Identity Design Review

A schema-owned new current catalog resource identity is legitimate for a materially different immutable SQLite layout, rather than accepting/reinterpreting the old one-table layout. It must be a coherent current protocol identity change, not a fallback selected after error. Keep strict two-table validator unchanged; initialize only a fresh empty database, no old-format acceptance, migration, raw deletion or override. Coordinate ownership with the other continuation implementation thread.

Material dependency: metadata/🟦️.ts retainResourceQueueMetadataHeadroomV1 currently hardcodes queue-claim-catalog in requireResourceLeaseCustodyV1. It must derive the exact current resource from the same schema; otherwise every new catalog writer fails headroom admission. resourceQueueCatalogPathV1 and continuation identity validation already derive retention resource from schema. Search all exact catalog literals/test oracles before release.

Lock ordering remains meaningful across old loaded and new processes if admissionResource stays resource-directory-admission:v1 and claim/resource paths remain unchanged. Queue catalog acquisition takes actual data directory admission with matching mode before catalog. Claim retirement holds data admission EX/catalog EX then claims admission EX; resource retirement holds data admission EX/catalog EX and genuine candidate SQLite EX. Old/new catalog SH operations therefore cannot overlap a genuine data EX retirement even though their catalog file hashes differ. Exact claim/resource guards retain conflict identity; continuation watermarks are coordination cursors, not deletion authority.

Do not claim old catalog is automatically retained forever. Old one-table idle catalog can satisfy generic readOwnedResourceLeaseV1 count1/table/resource/path ownership, whereas two-table new catalog is skipped by that generic reader. Existing active old owner retains admission/SQLite locks and can close its loaded lease directly; new protocol does not force-release it. If preserving old catalog is an explicit requirement, that needs separately authored current cleanup classification rather than assuming identity change excludes it. No direct cleanup is part of this proposal.

Required Source laws: new fresh two-table identity initializes; old file byte/stat unchanged through new acquisition; old/new data SH blocks either cleanup EX; actual kernel claim/resource contention persists; metadata headroom accepts exact new catalog and rejects copied/old writer; layout/page caps unchanged; arbitrary failure/drain/close ordering; distinct cursor state cannot skip safety observations. No actual catalog/protected read or schema edit performed. Recommendation: proceed only as coordinated schema-owned current-layout identity correction with the hardcoded metadata dependency fixed and genuine cross-process SQLite laws; no evidence of an unsafe lock split if shared directory admission remains invariant.
