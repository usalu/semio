## Current Contract

Every queue opener and claim retirement now uses one canonical catalog inside its own data namespace. There is no caller-selected catalog directory: supplying `claimCatalogDirectory` at runtime is rejected before writes. The catalog's shared custody covers opening a claim through acquisition of its original kernel transaction and ticket publication. The queue's stale-ticket reader also uses that catalog. Retirement holds the same catalog exclusively, verifies the exact owned SQLite application identity, resource-to-filename hash, bounded regular single-link file and inode, and nonblockingly acquires the original claim exclusively. An active claim therefore survives. After an abandoned ticket is removed, the claim transaction is released and its database handle closed before the exact inode is unlinked. No held file is truncated, resized or unlinked. A crash before unlink leaves a valid ordinary claim for the next retirement turn; no truncation recovery protocol or migration is needed.

Each ordinary maintenance turn examines at most 256 claims using the declared retention limit, original signal, deadline, awaited progress and continuation. Queue catalog, claim and stale-ticket waits retain the original requested timeout budget; zero remains nonblocking. Resource databases, the fixed image, its receipt and unrelated files remain intact.

An absent or zero-byte canonical catalog is bootstrapped through the actual lease image's exclusive maintenance callback. That existing API first releases the opener's shared image custody and waits for all other original users to finish. Only in that genuine whole-image quiescent scope does the repository remove a bounded set of validated, exclusively acquired and then closed original claims. It then reopens shared custody and establishes the canonical catalog. Ordinary openings with an established catalog use catalog retirement directly, avoiding a nested image-lock upgrade. The physical lease capacity remains unchanged.

The existing source correction preserves the original SQLite initialization exception if rollback itself fails. A valid 4,096-character multibyte resource against a 16 KiB SQLite cap forces the real INSERT to return SQLITE_FULL and automatically roll back; the owned API now exposes that primary error.
