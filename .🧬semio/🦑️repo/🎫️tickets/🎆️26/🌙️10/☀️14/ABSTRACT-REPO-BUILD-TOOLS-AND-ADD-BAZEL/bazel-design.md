# Bazel Backend Design

The bootstrap pins Bazel 8.4.2 and verifies each downloaded executable against its authored byte length and SHA-256. Official embedded-runtime binaries cover macOS, Windows, and Linux on x64 and arm64. The official release endpoints were checked on 2026-10-14. The bootstrap follows the repository's existing pinned Bun acquisition pattern, with resource leases, cancellation, progress, private staging, and atomic publication.

Bazel owns task dependency scheduling and action caching. The neutral project graph supplies all task definitions without asking Nx to construct a graph. Finite task actions execute their owner commands and publish declared output snapshots; cached snapshots are restored into the real workspace. Output files are flattened under hashed names, keeping cache paths short. Content and ancestry checks avoid deleting unchanged products while concurrent consumers use them. Interactive tasks use native Bun executable launch targets, with hardlinks and copy fallback instead of privileged Windows symlinks. Continuous dependencies start before consumers, honor readiness markers, and are cancelled when their selected task closure completes.

Each stable task selection receives its own workspace, runtime envelope, admission lease, and Bazel output base. Nested orchestration selecting a different task therefore never waits for the parent's workspace lease. An inherited selection chain rejects same-selection recursion before waiting. Explicit root task arguments take precedence over parameter-free dependency discovery; project selector exclusions and dotted owner-option output tokens are resolved before publication. Runtime envelopes use mode 0600 inside mode 0700 workspace directories and are never logged.

Actual macOS execution revealed that the embedded Java runtime cannot load its server JAR when its canonical path includes supplementary Unicode characters. An ASCII `.cache/bazel/install/<version>/<platform-architecture>` installation path fixes the observed failure. Product/action caches remain under the normal repository cache. The Bazel process also receives the supported macOS UTF-8 locale. This behavior was diagnosed by testing both the original JAR path and an actual ASCII-path copy; a symlink alias did not fix class loading.
