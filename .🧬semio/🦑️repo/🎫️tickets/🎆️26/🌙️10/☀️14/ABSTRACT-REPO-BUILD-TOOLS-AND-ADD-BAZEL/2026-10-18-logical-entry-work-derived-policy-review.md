# Work-Derived Logical Entry Policy Review

Recommendation: this is a principled explicit supported-cardinality policy change, provided schema and all dependent fixtures/output/refusal bounds are handcrafted coherently and Source tests prove the defining counter relation. The old262144 fuse is an independent product acceptance restriction, but the current implementation does not rely on it to bound resident memory or otherwise-unmetered per-entry work. Removing that smaller restriction while retaining the same67,108,864 cumulative work ceiling changes admitted cardinality, not physical authority or the work/memory/byte envelopes. It should be described exactly that way, not as unchanged262144 semantics.

## Defining Source Proof

The only entries increment is in visit, after check(); charge(); path/depth/cardinality validation; lineage verification and named observation. charge validates integer nonnegative units against maximumMetadataWork minus current work, then increments monotonically. Thus every increment of entries has a prior distinct successful debit of at least1 to the same closure-owned global work counter. There is no decrement/reset of work or entries anywhere in recursive traversal. Consequently entries <= work <= maximumMetadataWork at every reachable point, including partial failure, and all counts are safe integers because this ceiling is far below2^53. Each serialized entry frame costs an additional debit, but that stronger relation is not necessary for the simple safe upper bound.

Cancellation before debit cannot increment entries. A Native meter refusal after private work increment only increases work relative to entries. Failure after entries increment still retains its visit debit. Later byte/frame/close/lineage failure cannot erase the prior debit. Child recursion, page replay and terminal checks share the same account; they never create a subtree budget. No early return can mint a successful incomplete result: visit(root), final root equality, final lineage verify, forced progress and final check precede output. Named hardlink aliases remain separately visited and charged/summed.

The direct directory count also increments only after a charged directory read plus name debit. It is bounded by cumulative work independently of the old per-directory maximumEntries comparison; complete rescans only consume more work. Replacing that comparison's ceiling with the derived same work ceiling does not permit unmetered enumeration. Page memory remains at most64 selected names plus the bounded ancestry and active resident4160; no global array/map proportional to entries is introduced. Each frame and final result remain bounded16KiB, path256/depth64 unchanged. Every existing raw read, hash, sort insertion and lineage operation retains its existing debit semantics.

## Contract And Limits

Prefer schema documenting entriesBoundSource=maximumMetadataWork with one canonical derivation, not two unrelated hardcoded numbers that can drift. If the subset schema cannot express derivation, exact Source binding and language-neutral schema equality/inequality laws must enforce it. Handcraft LogicalObservation result limits, refusal maximumEntries/cases and current purpose fingerprints consistently. Do not raise maximumMetadataWork, maximumResidentRows, maximumLogicalBytes, Native cumulative meter, Original duration or physical funding in the same change. Existing strict/full-content witness defaults and preservation equality remain unchanged.

This does not prove complete Tools fits67,108,864 work or64GiB, and does not justify claiming all262144 historical entries were valid ownership. Actual traversal may next refuse work, bytes, path, depth, resident, drift or cancellation. The choice nevertheless has a finite existing resource basis and avoids arbitrary repeated count doubling or cosmetic partitions. No SDK/generation/object exclusion is needed. Full actual acceptance still requires a complete current witness and canonical terminal, not merely a larger declared supported cardinality.
