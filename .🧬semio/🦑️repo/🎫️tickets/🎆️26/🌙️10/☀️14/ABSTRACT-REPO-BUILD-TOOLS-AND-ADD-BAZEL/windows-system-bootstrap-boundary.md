## Pinned First Kernel32 Load

Bun1.3.14 open() calls std.DynLib.open(name), then retries a cwd-derived absolute path only when that first load fails. Its pinned Zig commit is 04e7f6ac1e009525bc00934f20199c68f04e0a24. That stdlib's WindowsDynLib.open uses openEx with no loader flags; sliceToPrefixedFileW keeps a simple relative kernel32.dll name relative (it does not expand that name to cwd), then LoadLibraryExW receives it. Thus the first call uses the Windows loader rather than a hand-built cwd path. Neither pinned API lets this JS caller set LOAD_LIBRARY_SEARCH_SYSTEM32 or disable Bun's later cwd retry. [Bun FFI](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/src/runtime/ffi/ffi.zig), [pinned Zig selection](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/scripts/build/zig.ts), [pinned DynLib](https://raw.githubusercontent.com/oven-sh/zig/04e7f6ac1e009525bc00934f20199c68f04e0a24/lib/std/dynamic_library.zig), [relative-name conversion](https://raw.githubusercontent.com/oven-sh/zig/04e7f6ac1e009525bc00934f20199c68f04e0a24/lib/std/os/windows.zig).

Microsoft documents loaded-module and KnownDLL resolution before ordinary filesystem search. For an unqualified module name, an already loaded matching basename succeeds; if more than one matches, the first-loaded one is selected. Pinned stdlib itself statically uses Kernel32 GetProcAddress to resolve symbols, so a normal trusted Bun process already requires that system module. This supports a **trusted-process inference** that exact constant kernel32.dll will match the existing system import. It is not a generic proof that every bare DLL is safe. DLL redirection/SxS precede ordinary searches, and native process compromise cannot be repaired by a later JS check. [LoadLibrary contract](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryw), [loader order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order), [redirection](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-redirection).

Strictly refusing every loader-failure→cwd-retry path is **not expressible through this pinned dlopen API** for an unqualified name. Prechecking a diagnostic module path or postchecking GetModuleFileNameW can improve observations but cannot undo execution of an unwanted DllMain. Therefore Root/Low must decide whether the existing trusted system-import inference is sufficient for the narrow x64 binding. This report does not call the retry unreachable or silently accept it as a failclosed guarantee. Existing jobserver/observation bindings use the same bare-name precedent, not a stronger policy.

## GLOBALROOT Candidate

Candidate exact executable is `\?GLOBALROOTSystemRootSystem32WindowsPowerShell1.0powershell.exe`. Microsoft documents GLOBALROOT as reaching the true object-manager root independently of per-session Win32 namespace links. It also says extended namespace support is API-specific. This establishes the prefix meaning, **not** a contract that every process creator accepts the complete candidate. [Naming files and namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

A bounded direct-URL pass through Microsoft object names, Object Manager, WinObj, ZwCreateFile/OpenFile and symbolic-link APIs did not establish a normative exact `SystemRoot` link-to-current-Windows-directory contract. Microsoft exposes NtOpenSymbolicLinkObject/NtQuerySymbolicLinkObject but labels them subject to change; invoking them would still need the initial native binding. An example showing a conventional system path is weaker than a stable link/ACL/namespace guarantee. This remains an explicit candidate/inference, not an authenticated bootstrap route. [Object names](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/object-names), [native symbolic-link API](https://learn.microsoft.com/en-us/windows/win32/devnotes/ntquerysymboliclinkobject).

CreateProcessW explicitly accepts a full application path and recommends non-NULL lpApplicationName to avoid ambiguous command-line executable selection. Its reference does not explicitly promise GLOBALROOT application names. No cmd.exe/shell intermediary is justified. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

The exact pinned Bun argv path can bypass its PATH lookup when an explicit env has no PATH; getArgv0 copies the exact supplied argv0 in that case. If lookup occurs, whichWin treats absolute paths separately but passes them through the PosixToWinNormalizer, so an arbitrary normalization claim would be premature. The current owned command path uses node:child_process under Bun and must be traced through its actual receiver as well, not merely equated to raw Bun.spawn. [Pinned argv handling](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/src/runtime/api/bun/js_bun_spawn_bindings.zig), [pinned Windows path lookup](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/src/which/which.zig).

Bun pins oven-sh/libuv commit 4dcfac4780d394e0dc2d3fb30335ca01b553eb46. Its Windows process path copies a leading-double-backslash directory without cwd, uses GetFileAttributesW for the resulting exact filename first, and passes the selected application_path non-NULL to CreateProcessW. This is positive Source evidence for preserving an extended absolute spelling, but not actual kernel acceptance or SystemRoot semantics. That search implementation may append .com/.exe if the exact file is absent; any approved owner must prevalidate the exact executable and forbid alternate-name adoption. The library can also supply required inherited environment fields when omitted; a clean bootstrap environment must explicitly fix those fields rather than assume omitting PATH/SystemRoot prevents all inheritance. [Pinned libuv dependency](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/scripts/build/deps/libuv.ts), [pinned Windows process implementation](https://raw.githubusercontent.com/oven-sh/libuv/4dcfac4780d394e0dc2d3fb30335ca01b553eb46/src/win/process.c).

## Conditions for a Future Candidate Probe

Root may separately authorize a bounded **read-only Windows** qualification: exact constant application path, actual Original/phase, owned capture with full abort/exit/stream drain, no fallback or source-selected executable, closed bounded JSON from OS .NET SystemDirectory/shared Windows directory APIs, then exact file identity/reparse/path comparison. The process must start from independently authenticated OS namespace evidence; its own post-launch output does not authenticate an arbitrary initial program. Test non-C and Unicode installations plus x64/ARM64 only where the actual host exists. No such probe ran here.

Until the missing object-link/process acceptance evidence is resolved, GLOBALROOT cannot be promoted into Source as a claimed universal replacement. The alternatives remain the reviewed narrow x64 trusted-Kernel32 process assumption, a separately approved first-party bootstrap artifact/runtime capability, or an honest unsupported-platform result. No upgrade, download, registry modification, UAC, service, privilege grant or guessed shell path is proposed for automatic execution.
