## Canonical frame and eligibility

The existing Witness owner and its schema remain the sole implementation. Ordinary regular files admit positive link counts. For `nlink > 1`, the existing per-name file frame appends `ino` and `links` as exact positive decimal strings after `sha256`. Inode must be positive. The single-link frame remains byte-identical; no device number enters a stable frame because mount devices can change on reattachment. A named hardlink frame has the shape `{path,kind:"file",mode,bytes,sha256,ino,links}`. Schema definitions close this extension and require both relation fields together, with links at least two. The relation definition is used by portable test data and the actual frame oracle. No production inode map, cached content digest, alias skipping, temporary relation database or new runtime file is introduced.

Every named alias is opened under the existing descriptor owner and independently streamed in full. Existing root-device, FD/name identity, size/link/inode/time stamps, complete ancestry, same-volume and private EX-observer checks remain. Both complete censuses and both cross-publication captures remain. The actual producer already validates the whole mounted filesystem root and rejects descendant kernel mappings; the generic witness itself makes only a root-namespace observation.

Equal inode fields encode observed within-root name equivalence. This does not claim the number of observed names equals `nlink`; a generic subtree can have names outside its root. Such outside names are never traversed or adopted. The captured link count records that fact without inventing their paths. Actual persistence of inode/link identities across detach and reattach is a separate physical qualification gate. If a filesystem does not preserve the relation, equality must refuse rather than suppress it.
