# Windows Publication Integration: Independent Design Review

The current integration proposal correctly treats the nofollow refusal and unconditional POSIX witness binding as blockers, rather than removing the guard in isolation. Existing Windows payload/host/session machinery is not sufficient until every shared owner, Fixed backing/footer, reserved record, mapped/underlying root and ordinary receipt consumer uses the same native identity model. No production change or NTFS result is qualified by this design review.

The proposed actual accepted writer/enrollment session, separate body/terminal views, fresh mapped evidence for each witness and shared cumulative meter preserve the required authority boundaries. A new witness context must remain one-use even when both phase contexts share the same account. Async physical checks must run immediately before/after actual effects; a cheap synchronous scope check cannot silently replace a former backing CAS with cached native facts. Every uncertainty must retain guard/session/pending state and prevent success.

The platform-discriminated native underlying-root receipt and all its ordinary open/prepare/retire consumers are mandatory prerequisites, not later optional cleanup. Full native128 identity/security must survive, with any numeric tuple independently observed on the same real handle. No synthetic mode, truncated ID, legacy decoder, generic callback or caller-issued context is acceptable. Existing POSIX behavior and closed unsupported exact/prepared Windows purposes remain unchanged.

Recommended batch release checks are the design's actual-defining-function structural counterlaw proving no POSIX host open/mode/mutation branch is reachable on Windows, negative body/terminal/copy/expired context and high-half ID tests, same-account two-phase metering, exact typed metadata predecessor transitions, cancellation/primary/ambiguous-close retention, then current Source closure captures without raising512/256 caps. Actual NTFS x64 mounted association, sharing, privilege and durability remain separate required physical qualification; ARM64 remains unsupported until real implementation/proof. No new material design objection was found, provided these dependencies remain a single coherent release boundary.
