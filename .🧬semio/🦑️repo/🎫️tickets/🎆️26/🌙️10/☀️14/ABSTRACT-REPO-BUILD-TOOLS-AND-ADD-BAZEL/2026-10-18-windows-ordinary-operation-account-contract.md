# Windows Ordinary Operation Account Lifecycle

The contained receiver-attempt readonly account remains the qualified baseline. Full ordinary operation integration needs an explicit new lifecycle contract, not an unchanged-count performance claim. A later genuinely admitted borrower operation may receive a fresh bounded observation account only after the preceding operation completed its child drain, descriptor closes and final canonical association proof. Nested borrower/observation/journal work for the same actual outer borrower frame shares that account, even when requested child controls differ. Baseline/opening and actual accepted terminal phases retain their existing accounts.

Fixed cannot infer an outer borrower operation from matching control fields or a newly entered callback. The canonical Native borrower owner will need a readonly nominal operation identity accessor issued only by its actual private live outermost same-owner frame. The token supplies identity/lifetime DATA, not writer, funding or transition permission; it cannot be registered externally or restored from wire. It expires on actual frame settlement. Fixed privately binds it to the exact receiver, guard, options, current owner and actual descendant control before choosing the account. This reuses the existing borrower module rather than adding Source files or structural global registries.

The receiver retains a sticky failure/unresolved state independently of any successful operation account. Undefined/frozen body or final fence/close/mapping failures poison the receiver body attempt, so abandoning a key cannot retry with fresh counts. Accepted cleanup remains a separate finite authority. New top-level admission also reserves the exact receiver synchronously; concurrent unrelated top operations refuse before physical effects. Same live nested operation uses the parent frame. A successful complete operation can release this reservation and allow a later legitimate operation; it cannot reset an unresolved failure.

Schema-first countercases: two sequential successful real borrower operations; nested same-owner borrower with different requested controls; parallel operations; copied/foreign/expired operation token; sibling owner/resource; abandoned failed operation followed by identical input; undefined/frozen primary; final Native close/mapping failure; terminal after body cancellation; escaped continuation. Existing body16/terminal3/work bounds are unchanged within each newly defined operation attempt. No new Original, deadline, allocation or caller-provided budget exists.

This contract precedes implementation and requires independent model review. It is not current public Windows runtime behavior or a reason to remove the dispatcher guard.
