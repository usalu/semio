## Proposed Concise Change

Add a private `allocateNativeFixedVhdV1(operation)` beneath the existing fixed owner, with a nearby domain-owned allocator schema/corpus/test slice. It reads immutable options/control/cleanup/writer/parent/path identities from the actual FixedPreparation WeakMap. It takes no path, numeric quota, caller assertion or fabricated control. Snapshot operation authority references and primitives before the first await. Generate UUID and VHD-epoch timestamp once through existing system primitives; feed the real captured values to the held pure codec.

Keep the closed `allocate` action and one existing body-action count. In captureNativeFixedActionV1 dispatch the Windows allocation action to the private writer instead of building a New-VHD process. Keep Linux fallocate and all other activate/format/information/inactive/deactivate actions unchanged. Track the entire write/sync/observation/close work in the existing pending action and actual issued-operation lifetime. No second admission path or cleanup-only allocate permission is introduced. Remove the unreachable Windows New-VHD builder after the private branch is integrated; do not retain an optional fallback.

The writer creates exactly `options.directory/fixed.vhd` using exclusive fresh creation and platform-supported nofollow flags, captures actual FD plus named dev/ino/nlink immediately, and rechecks actual preparation, parent and physical ancestry. Add explicit private creator-descriptor facts because `scope.backing` currently includes file size: assigning the final fixedStamp before a sequentially growing write would falsely invalidate normal growth. Keep the final stable backing stamp contract. During allocation require the exact live creator FD/inode and the measured current extent; after completion bind the existing final backing stamp.

Write the entire data region sequentially using a schema-owned bounded reusable zero buffer and actual returned short-write counts. A small fixed IO buffer is memory/cadence policy, not a storage quota increase. For every awaited open/stat/write/sync/progress/yield/observation/close, check the actual issued body phase before and after and reprove the named/FD identity before the next effect or acceptance. Publish existing resource progress using the actual control and yield between bounded chunks; keep detailed byte counters in an owned debug/progress data record rather than inventing fields on ResourceLeaseControl. A zero-progress write refuses. Do not use truncate, seek-to-last-byte, sparse/decommit calls or SetFileValidData.

Append the real512-byte footer only after the complete data region, handling short footer writes. File length must be exactly filesystemBytes+512, within maximumPhysicalBytes. Sync the actual file, observe physical allocation as described below, close/drain the actual descriptor, then verify named identity/size/footer and recheck the preparation before allowing activate. No unowned source file, source copy or external runtime package is needed for the sequential writer.

## Physical Allocation Observation Is a Required Port, Currently Missing

The current Windows observe path179–180 checks footer, logical file size, an upper bound from lstat.blocks and the mounted Storage mapping. It has no lower allocation bound or first-party Windows allocated-space observer. Bounded searches of PROCESS found no GetFileInformationByHandleEx/FILE_STANDARD_INFO/AllocationSize implementation. Sequential zero writes and a correct footer alone must not be promoted into proof of full physical allocation.

The required private observation is bound to the actual creator descriptor/Native preparation and captures file identity, allocation size, EOF, number of links, delete-pending/directory state and sparse/compressed/encrypted/reparse attributes. Require one regular owned file, exact EOF/filesystemBytes+512, allocated size>=EOF and<=existing maximumPhysicalBytes, unchanged FD/named identity and supported local backing. Microsoft documents FileStandardInfo's AllocationSize as allocated file space and distinguishes EOF, links, delete-pending and directory fields. [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info). The real handle-based call and failure result are specified by [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex).

Proposed private shape: `observeNativeFixedCreatorV1(operation, actualDescriptor)` derives its exact path/parent/control from the private owner and returns a detached closed facts record; no public free-file observer or caller-supplied proof. Its actual Windows implementation must authenticate the real Windows handle (including fd/HANDLE ABI if FFI is used), not infer it from logical Node size. Compare bigint allocation/EOF/rounding safely; never silently substitute stat.size when allocation information is missing. The existing Node blocks field may be used only if the pinned Windows runtime implementation and a real independent Windows observation establish its semantics; the present Source check is not that proof.

This port is not implemented or qualified by the pure VHD codec. The prior provisioning plan records pinned Bun1.3.14 FFI/ARM64 limitations; do not declare a new x64-only host restriction or add a circular Rust compiler bootstrap. A PowerShell/.NET native-information implementation would need its own explicit first-party system ABI/handle binding and compilation/temp-file ownership design; Add-Type is not an already available authenticated port and is not selected as an unreviewed fallback. Existing PowerShell Storage attachment remains necessary independently. Root must release the concrete physical-observer/system-binding slice before claiming a complete zero-touch Windows allocator.

## Failure and Cleanup

Register creator FD/inode before writing. Preserve the body primary, including undefined/frozen values; successful-body sync/close/observation failures remain fatal. The generic withArtifactDescriptorV1 preserves arbitrary body errors through close but does not expose proven-close state, so it alone cannot justify releasing image EX after a close fault. Track close success explicitly in the actual preparation. A still-unproved open descriptor keeps unresolved custody; do not assume finally implies close.

The existing accepted cleanup must join outstanding writes before inspecting/removing the partial owned file. Reuse the already funded terminal reserve/owner and exact creator identity; do not start a fresh clock or issue a cleanup Original after failure. Never unlink a mounted, changed, foreign, pre-existing or unproved creator backing. Preserve all unrelated entries. Once the partial FD is proved closed, unmounted state and exact named identity are proved under the same real image writer, normal current cleanup may remove only the owned partial backing. Failed sync/observation is not rollback, and no receiver/receipt success is published.

An important model boundary is current outer preparation code's `backing` capture after platform.prepare failure. A new async descriptor must be retained privately early enough that a close fault cannot be mistaken for a safe named partial file. Keep the accepted operation and parent lifetime until real drain, then either close safely or retain unresolved failure/custody. Do not solve this by widening the reserve or ignoring cleanup failure.
