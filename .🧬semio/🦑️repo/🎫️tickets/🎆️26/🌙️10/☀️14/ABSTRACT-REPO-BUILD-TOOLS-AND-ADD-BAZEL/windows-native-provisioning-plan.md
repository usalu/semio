# Windows Native Provisioning Plan

This is a read-only, ticket-only design. Permanent Source remains held. No Windows execution, platform spoof, Native image/store operation, compiler, hdiutil, diskutil or format oracle ran. The existing ticket and goal remain owned by Root. This extends [the provisioning follow-up](windows-native-provisioning-follow-up.md) and [the metadata proposal](windows-state-metadata-port-proposal.md).

## Decision and Concrete Limits

A first-party fixed VHD encoder plus bounded sequential allocator can remove Hyper-V **creation** from the existing Native interface. It does not remove Windows attachment privileges, establish physical allocation from logical size, or solve the current prebirth image.json publication barrier. Resolve the system paths through documented Windows APIs, keep the existing Storage attachment/format/mapping route, and add a distinct private preparation-owned containing-volume barrier. Do not invoke the ready-image capability during preparation.

The current Cargo profile Request matrix admits Windows x86_64-pc-windows-msvc only; this plan does not add an ARM64 build target. Separately, the canonical Bun bootstrap distribution table explicitly includes both win32/x64 and win32/arm64 at version 1.3.14, so ARM64 host provisioning is not an invented target. The pinned FFI implementation is plausible for x64 but disabled on ARM64. Treat that as an existing host-matrix inconsistency, not a reason to expand this contained implementation. A first-party prebuilt bootstrap or approved runtime capability would be a separate decision; compiling a Rust helper through the stores it must provision is circular. No runtime upgrade/download, architecture restriction or fallback is authorized here. Exact matrix owners: library/⚡️caching/🚀️bootstrap/🛠️tools/🟦️bun/🔣️.json and library/🏗️build/🎚️mode/🦀️profile/🧬️schema/🔣️.json.

## Current Source Boundaries

The owner is process/📦️artifacts/🏗️native-build/💾️storage/🧱️fixed/🟦️.ts. Its closed Windows allocate action invokes New-VHD -Fixed. fixedExecutable and fixedCommandSpec hardcode C:\Windows in both the executable and sanitized environment. publishFixedPersistentReceipt writes/fsyncs the receipt and then opens/fsyncs its containing directory; that last operation is still POSIX-only. This is a fresh-open blocker independently of Hyper-V allocation.

FixedPreparation already authenticates an exact private operation, options, live writer proof, accepted cleanup, physical directory/backing identities and pending children. Extend that actual owner. Do not introduce a public path-token constructor, caller callback assertion, arbitrary volume/program string, new Original, widened phase or unrelated host-volume API.

State and NativeArtifactCache already retain actual parent image operations while child images open. A nested preparation must carry that actual retained parent identity into its private owner; an initial host-backed preparation is a distinct authority case. The child's mounted NTFS volume is not the volume containing its VHD file or image.json.

The newly present cleanup/♻️retirement/💾️durability helper is explicitly POSIX descriptor IO. Its check callback is supplied by an authenticated Native cleanup owner; it does not itself authenticate Windows storage. Reuse its identity/drain principles, not an inferred Windows allowlist. Current fixed cleanup has a separate retained-reader Windows path; its Get-Volume -FilePath directory query and lack of the ready path's physical chain stamp were separately reported to Root for its owning batch. This plan does not edit that peer Source.

## System Root and Pinned Bun

Use private Kernel32 bindings for GetSystemDirectoryW and GetSystemWindowsDirectoryW. The former supplies the system executable directory; the latter supplies the shared Windows installation directory. GetWindowsDirectoryW can refer to a per-user Terminal Services directory. Bound UTF-16 buffers/results and total path length, reject zero/truncation/NUL/noncanonical results, and build PowerShell, SystemRoot, WINDIR and PSModulePath from OS results. Do not execute a process.env-selected program and only then validate itself. [System directory](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemdirectoryw), [shared Windows directory](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemwindowsdirectoryw).

Existing first-party analogues are native jobserver and Repo Native observation Bun FFI bindings, and the authored native-temporal Windows Rust owner using GetSystemDirectoryW. These are implementation precedents, not platform qualification. Keep all external FFI representation behind a private codebase-owned interface. The first DLL binding must be the actual system Kernel32 module: the Windows loader's loaded-module/KnownDLL behavior is relevant, but does not authorize arbitrary bare DLL names or Bun's cwd fallback. [Windows loader order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order).

Pinned bun-v1.3.14 tree SHA is 0d9b296af33f2b851fcbf4df3e9ec89751734ba4, matching the retained installed revision prefix. Its config computes TinyCC false for Windows ARM64, passes that flag into Zig, and its dlopen implementation rejects disabled TinyCC. x64 defaults enabled. This verifies a Source limitation, not actual x64 ABI correctness. Current latest FFI docs describe a different engine and cannot override the pin. ## Fixed VHD Owner

Microsoft's fixed format has a data region followed by a 512-byte footer, without a dynamic allocation table. The footer contains big-endian fields: conectix cookie, version/features, fixed sentinel, timestamp/creator, original/current size, geometry, fixed disk type 2, checksum, UUID, saved state and reserved bytes. Author a pure encoder against that specification, with the exact current fixed format only. Refer to the documented CHS algorithm; do not copy a dynamic-image implementation or add 511-byte compatibility. [Microsoft VHD specification](https://www.microsoft.com/en-us/download/details.aspx?id=23850).

The official DOC was downloaded solely as research to generated/microsoft-vhd-spec.doc: 185344 bytes, SHA256 f2aca9d584b41a2b83ec12190236befa33097b97a7296b1fccff6138438a062d. Plain text extraction is retained beside it. The 8-byte fixed sentinel must be validated against an independent reader; the old prose abbreviates the hexadecimal value.

Private proposed operations are encodeFixedVhdFooterV1(facts), allocateFixedVhdV1(actualPreparation), and publishFixedPreparationReceiptV1(actualPreparation). The last two derive exact paths/options from the private owner rather than accepting free paths. Names are proposals, not landed APIs. Place the schema/encoder/corpus close under the existing fixed owner; preserve absolute path limits and existing public task registration.

Create one fresh O_EXCL/no-follow file, record the actual descriptor/inode immediately, and write the complete finite data region sequentially with a reusable bounded buffer and short-write handling. Check actual control before/after each awaited chunk, publish byte progress and yield. Append the footer only after all data, sync the actual file, close, then verify named inode, length and footer. Do not use truncate, a single final-byte write, sparse zero-range decommit, SetFileValidData or hidden quota increases. Allocation work and its accepted descriptor remain drained before cleanup; arbitrary undefined/frozen primary survives. A failed partially created owned image is removed by exact identity, never adopted or mistaken for a foreign file.

Physical allocation requires a separate actual Windows observation. FILE_STANDARD_INFO exposes AllocationSize and EndOfFile through GetFileInformationByHandleEx; bind the actual handle and reject sparse/compressed/encrypted or inadequate allocation. Logical length/zero readback alone are insufficient. These system observations require x64 ABI and real filesystem qualification. [Handle information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [standard information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info). Full zero allocation may exceed today's finite budget on slow storage; retain that honest failure rather than increase the cap.

## Preparation-Owned Parent Metadata Barrier

The required sequence is: actual EX preparation admission → owned backing allocation/attachment/format observation → exact receipt file write and file sync → **containing-volume metadata barrier** → rechecks → acknowledged/ready. Parent image lifetime and accepted child/descriptor work must drain before parent close; the new barrier must not acquire a ready-child borrower or wait on itself.

Issue a private preparation binding only from the real FixedPreparation registry. Capture its exact receipt and parent directory identities, actual file handle, immutable receipt bytes/hash, private writer proof and actual control. Hold the directory/ancestry stable across child dispatch. Resolve the containing local volume from the owned real file, not a directory argument to FilePath and not the child image root. Get-Volume documents FilePath as a full **file** path. [Get-Volume](https://learn.microsoft.com/en-us/powershell/module/storage/get-volume?view=windowsserver2025-ps).

For robust delete/rename cleanup, retain the containing directory handle and capture its volume GUID through GetFinalPathNameByHandleW with VOLUME_NAME_GUID before removing the last owned file. Microsoft documents directory handles and resolved GUID paths; this avoids inventing a probe file or relying on a deleted path. Open/recheck no-alias physical ancestry, volume/file identity and exact named receipt before/after flush. A retained handle alone does not authenticate an arbitrary caller's directory: issuance still requires the exact private preparation. [Final path by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew).

For a nested image, independently compare that containing-volume identity with the actual retained parent Native binding. For initial host creation, permit only the preparation's exact owned file/directory publication on its captured local host volume. A boot/system host volume may be the legitimate containing volume here; the ready **child-image** rule rejecting boot/system disks cannot be copied blindly. This narrow host permission does not authorize raw host cache cleanup or flushing unrelated directories. Reject remote/cluster/ambiguous mapping and changed identities.

Invoke MSFT_Volume.Flush only on the exact locally resolved instance, require numeric ReturnValue 0 and exact pre/post mapping, bound stdout and await the owned process/streams/progress using the same actual phase. Flush failure must retain honest intent/partial state and never imply rollback. Stop new births after first failure, retain its arbitrary value, and preserve an earlier body primary. The method documents a filesystem cache flush, not hardware power-loss guarantees or privilege exemption. [MSFT_Volume.Flush](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/msft-volume-flush).

Factor only pure mapping/receipt validation and a closed command builder with the ready/retained-cleanup paths. Preparation, body and accepted cleanup each authenticate their own private owner and actual phase. No caller callback or raw volume assertion becomes authority. This also prevents a NativeStorage↔platform runtime cycle.

## Schema-First Laws and Qualification

Proposed closed language-neutral datasets cover footer sizes/geometry boundaries/checksum/endian/UUID, malformed reserved/type/sentinel fields, short writes and early stop; actual controls versus copied/foreign/stopped/expired phases; file/ancestor replacement, links/aliases, insufficient physical allocation; first undefined failure plus later frozen failure; receipt malformed/oversize/string-zero/nonzero Flush and mapping change; initial host versus actual nested parent, parent close waits for child drain, no prebirth-ready selfcycle; non-C Windows system directories and unsupported FFI architecture. Independent Ajv plus SQLite arithmetic validate corpus shape and offset/checksum expectations. They do not establish VHD interoperability.

No declared QEMU/libvhdi library or installed qemu-img/vhdiinfo was found in the bounded inspection. The local hdiutil man page was read only; it delegates imageinfo to diskutil image info and does not document VHD support. Therefore hdiutil is not a verified oracle yet. A separately authorized unmounted readonly probe could establish support, or an approved test-only third-party VHD reader can supply the independent format oracle. Actual Windows Mount-DiskImage/Get-DiskImage remains required kernel qualification. Our own existing footer parser is not an independent third-party oracle.

Native VHD attachment requires administrator privileges; Create/AttachVirtualDisk documentation also has explicit storage/privilege constraints. Removing New-VHD eliminates one optional Hyper-V module dependency, not OS administration. Do not add UAC, services, privilege grants or guessed DiskPart syntax. Storage provider availability, NTFS mount/reparse/dev identity behavior, x64 FFI handle ABI, native ARM64 bootstrap and performance inside the unchanged phase remain explicit gates. [Mount-DiskImage](https://learn.microsoft.com/en-us/powershell/module/storage/mount-diskimage?view=windowsserver2025-ps), [AttachVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-attachvirtualdisk).

Implementation release should first land the schemas and actual Source-model REDs, then the contained private owners, focused strict/independent corpus GREEN and Low review. Production Source capture and SDK provenance must refresh afterward. Root alone releases physical macOS/Windows/native/store qualification; none is claimed here.


## Pinned No-FFI Alternative Investigation

The pinned Windows diagnostic report actually calls EnumProcessModules on the current process and GetModuleFileNameExA for each module, exposing paths through process.report.getReport().sharedObjects on both x64 and ARM64. This is OS-derived data rather than inherited environment. However, its implementation uses fixed 1024-module storage without checking needed against capacity, and ANSI MAX_PATH names converted as UTF-8 without preserving the numeric length. Consequently it is not a complete Unicode, bounded, authenticated system-root port. Do not execute PowerShell selected merely by a matching kernel32.dll basename in that report. A unique system-module path could be a bounded diagnostic candidate, but cannot discharge the permanent all-path contract without additional authenticated OS evidence. No such child was run. [Pinned Windows report](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.3.14/src/jsc/bindings/BunProcessReportObjectWindows.cpp).

Microsoft says module enumeration can return incorrect data during load/unload and explicitly requires retrying when the needed array exceeds capacity. ModuleFileNameExA may succeed with truncation; its numeric length is needed to detect bounds. A JS consumer cannot repair the discarded native facts or ANSI-to-UTF8 loss. process.execPath identifies the Bun executable, which is not required to live under Windows/System32. An environment-selected executable, cmd/path search, or a child that self-reports after launch does not independently authenticate the first executable. Thus no correct pinned ARM64 no-FFI bootstrap was established in this bounded review. This is an explicit Source finding; it does not block the separately admitted x64 implementation assignment. [Module enumeration](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-enumprocessmodules), [module filename](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getmodulefilenameexa).
