## Why A Separate Transition Is Needed

The existing protected producer reader intentionally admits only missing or single-link endpoints. The newly held generic binding API keeps that rule. An ordinary directory/file cannot become an admitted link merely because it is named node_modules. The existing ordinary producer's path-based fallback moves a physical endpoint to workspace .cache/held-javascript and records only limited facts; it is not the proposed rooted/current authority and must not be called as an administrative adapter.

If the actual selected endpoint is an ordinary current Source directory/file, a fully prepared funded producer can replace the binding without adopting or deleting that content by moving the complete existing entry to an explicit retained Source capsule. This is a distinct current owner intent: preserve the selected exact opaque entry, then publish the separately qualified binding. It proves no historical installer identity, dependency receipt, recomputability, funding or right to delete the preserved bytes. Other endpoint kinds continue to refuse.

The fixed domain issuer still requires genuine setup-all Original/refinement/live control; the exact protected Dependencies parent and Core retain-allocation token; unchanged whole committed row/full policy/backing/raw journal CAS; current ALL Bun ownership; and actual global javascript-dependency-bindings EX. All scopes, manifests, generation outputs, desired targets and complete new paths must be prepared and qualified before any Source transition. Missing/unqualified current links never prove inactivity. This operation retires neither the allocation nor pending-publication metadata.

## Deterministic Retained Capsule

For the domain endpoint node_modules (12 units), derive a sibling basename .p followed by8 hexadecimal units from the full canonical intent SHA (10 units). This abbreviated name is only a deterministic address. It never proves ownership; any preexisting slot refuses even when a marker looks matching. Full intent SHA/fields remain in the record. Collision means a fresh explicit decision is required; there is no retry suffix, prefix sweep, marker adoption or legacy recovery.

The freshly exclusively created private capsule contains fixed single-basename roles i (intent), p (the whole preserved payload) and r (settled preservation receipt). Each full endpoint root/slot/role path is checked <=256 before effects. Parent/.pXXXXXXXX/p is no longer than Parent/node_modules; existing descendant paths therefore never get longer. No source file is copied or recursively rewritten. This does not claim unknown preexisting descendant paths were already within256; if the eventual acceptance requires that global assertion, an additional bounded inventory is required before release.

The planned intent file is bounded4096 bytes, receipt4096 bytes, at most64 explicit endpoints per command and the existing shared32 live-owner registry. Payload size is not compared to the Native allocation: no bytes are copied into that allocation and no charge is retired. Work/name/metadata limits remain separate from logical extents and hardlink alias sums. Admission is sequential with progress/cancellation and all accepted descendants drained before their parent closes.

A durable intent and its parent barriers precede the first Source-name move. The intent records purpose/version, exact source/owner/parent/leaf facts, the complete prior ancestor-observation SHA (the live owner still retains and checks every full ancestor record), proposed capsule/p role, prepared producer request SHA and target, plus adopted:false and deletePayload:false. Hashes do not create recovery authority or stand in for the live full comparisons. The capsule's actual exclusive creation and live held identity authorize only this attempt; an old name or file does not. Receipt r records only verified terminal preservation facts and belongs to the exact private capsule. Fixed append-only transition events may record intent-prepared, payload-retained, binding-published and unsettled failure, with finite record bytes. The design does not introduce a generic mutable metadata store.

## Recommended POSIX Refinement And Actual Reader Boundary

The first straightforward proposal used preservation rename followed by the strict missing binder on every platform. Current Source review shows only the authenticated consuming wrapper holds the existing global SH gate through its body (DS withJavascriptDependencyReadStorageV1); current framework callsites include Print and VSCode. Existing Source test helpers directly resolve/import TypeScript and other node_modules test tools outside that wrapper. This is not a complete inventory proving every bootstrap/administrative reader is gated. Therefore the global EX alone cannot currently justify an invisible controlled gap for all first-party Source readers.

Prefer a distinct POSIX preserve-and-publish primitive: after durable intent, prepare the already qualified new link as the exact capsule/p entry, then atomically exchange Source/node_modules with capsule/p. Both entries exist, complete roster and exact private expectations are checked, and the actual displaced ordinary file/directory is retained permanently in the capsule. This never calls or widens the missing/link binder. It does not unlink the displaced ordinary entry. The actual Darwin binding fault harness already exchanged a directory and symbolic link successfully; the new feature must add its own exact positive preservation body and independent bytes/inode oracle. Linux documents unlike-kind exchange. Unsupported exchange refuses rather than introducing a silent two-step fallback.

POSIX can thus avoid the name gap while preserving the old inode. An external actor can still race the precheck; unexpected displaced state remains retained and the command fails without rollback. This is atomic namespace exchange plus post-verification, not atomic inode-CAS. Windows has no established equivalent for arbitrary ordinary directory/junction exchange here. Its separate controlled-gap route remains blocked for an end-to-end compatibility claim until relevant framework reader serialization is actually established and real NTFS behavior qualifies. This is a concrete implementation gate, not permission to modify the existing held binding5 or broaden sharing.

## Platform Distinctions

POSIX should use the stronger genuinely descriptor-relative preserve-and-publish exchange (Darwin renameatx_np RENAME_SWAP, Linux renameat2 RENAME_EXCHANGE). A separate pure-preserve operation, if ever required, must use absent-only move (Darwin RENAME_EXCL, Linux RENAME_NOREPLACE). Plain overwrite-capable rename and silent two-step fallback are forbidden. The kernel does not atomically predicate rename on the expected inode. An uncooperative actor can swap Source after the last check: the new/foreign entry may be moved into the private capsule. Exact post-move mismatch must retain that entry and fail, never delete it or automatically roll it back over an unknown current Source leaf. This remains preservation of the actually moved entry, not proof the desired old inode was transitioned. Real parent/leaf close and both directory sync results are required.

Windows must use the genuine ordinary no-reparse rooted Source parent/capsule and a held nofollow ordinary file/directory with DELETE rights. Rename uses NT relative RootDirectory plus one basename and replacement=false on the same volume. No junction conversion or Node.rename replacement assumption applies; this step preserves the ordinary object. Exact full128-bit ID/volume/security/stream/7facts and actual named state must agree before/after. Open descendants, sharing/privilege, pending IO, directory move and real durability can refuse. Parent GENERIC_WRITE/shareRead versus NT RootDirectory rename access remains a physical qualification gap from binding5; do not widen sharing as a fallback. No NT Source model is actual NTFS acceptance.
