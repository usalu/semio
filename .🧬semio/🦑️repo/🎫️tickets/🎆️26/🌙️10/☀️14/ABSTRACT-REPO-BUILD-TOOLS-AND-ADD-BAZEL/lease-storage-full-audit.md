# Lease Storage Full Audit

Read-only Source audit following NESTED41927. No database was opened, no lease or native store acquired, and no storage was changed. Root reports SQLITE_FULL at lease initialization, with the canonical 64 MiB lease filesystem nearly full; those observations are separate from this Source review.

The existing queue retirement owner in PROCESS/leases retires authenticated queue claims only, at most 256 per call, under the queue-claim catalog writer and nonwaiting per-claim transactions. Busy, foreign, and unrecognized databases remain. It does not retire ordinary top-level resource databases or compact SQLite. Its 4 MiB metadata-headroom file is retained only after catalog acquisition; it cannot by itself establish recovery when catalog initialization already fails for space. Per-database page limits do not establish aggregate filesystem capacity.

A safe ordinary-resource retirement design needs one directory admission gate followed by the existing queue-claim catalog and then the target SQLite transaction. Every ordinary opener must retain directory SH from before path opening until the real transaction is acquired, or until its failed database connection is closed. Retirement requires directory EX, nonwaiting target EX, authenticated resource/hash/application identity and stable regular-file inode, then connection close and exact named-inode unlink while directory EX remains held. Existing successful lease release rolls back and closes synchronously. Gate acquisition consumes the same original timeout and cancellation; it cannot restart a deadline.

The gate itself needs a private ungated primitive and exclusion from retirement. Existing claim GC acquires claim-catalog EX before calling the ordinary lease opener: blindly adding directory SH there creates a lock-order inversion/reentry risk. Acquire directory custody first and pass only a privately authenticated held-gate proof to the inner operation. Never expose an arbitrary bypass. Do not unlink ordinary resource databases after releasing the gate: an opener retaining an old inode could otherwise split resource identity. Preserve all busy or unknown peer resources, quota, journals, and opaque files. Whole-image or fleet quiescence cannot be inferred merely from this read-only census.

Failed opener cleanup must close its database before dropping that reader, with independent cleanup preserving arbitrary undefined or frozen primary failures. Cancellation must not produce an unfenced open connection. Busy retirement stays nonwaiting. Appid plus a matching resource row/hash is insufficient if the database has additional user tables/triggers/views or an altered lease schema; unrecognized schema and sidecars must be preserved. These are design conditions, not assertions about an implementation that has not yet been reviewed.

## Reviewed Close Correction and Private Concurrency Scope

Current adapters now keep private closed state, changing it only after underlying close succeeds. Repeated close becomes a no-op. Lease release marks released/dead only after successful close. This addresses the observed retry-success-finalizer replay gap by Source inspection; fault-law execution remains executor-owned. Immediate post-open stop checks are now visible before database operations in opener, raw claim reader and ordinary retirement. A private finalizer retains failed connections with their admission gates until close succeeds.

The separate Core concurrency owner and strict worker were reviewed read-only: real received Original/wire receipt, genuine worker controls, actual onWait witness before opened-wait retirement, nonzero expected-negative child isolation, and owned command settlement before private-root removal. Scope is private Bun/Node SQLite, not canonical native image or SDK. In expected-primary cleanup rows, an already settled child can skip another receipt validation; therefore those rows alone do not independently prove a closed=true receipt, although owned command settlement proves process termination. No new blocking issue was found in that test slice.

## Canonical Opening Integration Finding

The observed openRepositoryLeasePartitionV1 integration requests whole lease-image EX with wait:false after every successful image open. Other legitimate partition scopes retain that image SH for their lifetime. Consequently this unconditional maintenance step conflicts with ordinary overlapping or nested borrowed opens. Retirement must have explicit recovery/maintenance ownership or an appropriately proven conditional path; shared successful opening must remain possible. This is a Source lock-order finding, not an executed canonical failure. Executor and Root were notified before acceptance.

Correction after reading the actual native maintenance implementations: the earlier mandatory-EX blocker was an incorrect inference. Both fixed and persistent wait:false methods return acquired:false on exact busy after closing their own reader; the opening helper then reacquires SH. Legitimate peer SH therefore does not force an error. The optional EX attempt is not a demonstrated correctness failure.

Core concurrency follow-up now always validates a previously unvalidated child receipt even if already settled and asserts zero cleanup errors before accepting an expected undefined/frozen primary. The earlier receipt-coverage limitation is resolved in current Source. The ninth explicit Node retirement action expands adapter coverage; runtime results remain Core-owned.

## Final Narrow Source Verdict

The reviewed corrections resolve the reported blockers: idempotent successful-close state, retained admission custody across failed-close retries, post-open stop checks, and native maintenance busy returning acquired:false. Ordinary GC now uses an exact metadata reserve only when already present, avoiding new 4 MiB allocation in arbitrary private/Cargo directories and failing closed without reserve recovery. Exact eligibility/exclusions, nonwaiting contention, and connection-close plus named inode unlink under directory EX remain visible. No further blocking finding was found in this reviewed slice. This is a Source verdict with executor/Core reported private laws, not independent canonical reclamation, all-platform runtime, public aggregate, or SDK currentness proof.
