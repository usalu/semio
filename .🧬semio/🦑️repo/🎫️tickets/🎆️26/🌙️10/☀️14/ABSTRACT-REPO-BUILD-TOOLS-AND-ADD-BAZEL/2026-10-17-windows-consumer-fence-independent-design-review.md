# Windows Consumer Fence: Independent Design Review

The proposed closed receiver-specific mechanical mode is appropriate to preserve the existing synchronous cleanup recheck contract. A closed prior snapshot is DATA, not a live fence; globally relaxing cleanup checks or continuing cached values would be unsound. Conversely an actual authorized journal write can legitimately update VHD/mapped-root write/change timestamps, so strict PUB observation mechanics must not be reused with silent exception handling.

Keep a distinct schema-owned nominal receiver mode inside the actual private Fixed owner, with real held descriptors and fresh synchronous native facts on every fence. Host/receipt remain fully exact; backing/root retain all immutable native128/device/volume/security/streams/extent/kind/link/creation/attribute checks, with only the exact two declared timestamp fields mutable. No caller ignored-field list or structural context registration. Actual enforcing/journal ownership remains separate; a mechanical handle grants no Store/token/funding authority.

Actual fixed command/named-root mapping proofs before/after must use genuine current body or captured terminal authority and existing bounded command/account policies, not ad hoc probes or cached association assertions. Result is not a globally atomic mount snapshot. Same requested0/accepted-cleanup drain, exact guard/account identity/failure poison and escaped fence refusal remain required. PUB strict mode and existing POSIX behavior must stay exact. No conceptual objection under these constraints; Source syscall-port/Root0 counterlaws and real NTFS/coherent consumer/create/retire/PUB qualification remain pending. No Native/protected reads or Source mutation performed.
