## Source Cost And Batching

verify currently awaits an async exact→async named chain for each ancestor lstat even on POSIX. It runs before each visit, before and after each full directory census, and after each entry; therefore repeated ancestry observation is O(entries×depth), with additional scans below. Every io uses full private observer checks before/after; directory step wrappers add more full checks. At current observed8.5ms per entry, Promise allocation alone is unlikely to explain the full cost; an expensive private observer can dominate. This is a Source diagnosis, not a measured attribution.

Directory order is selected in bounded64-name pages by reopening and scanning the COMPLETE directory for each page, plus a terminal empty page. A directory with n children causes n×(ceil(n/64)+1) raw entry reads, plus EOF/close work, so high fanout is quadratic in n/64. That rescan is how the current resident bound avoids an unbounded sorted name array. Do not silently replace it with unstable OS enumeration order or an unbounded retained list. A bounded external ordering/index design would itself need ownership, IO and work contracts; small resident heaps alone do not remove repeated complete scans.

The safest first performance change keeps EXACT existing I/O sequence, per-syscall genuine control/observer checks, charge counts, before/after fact comparisons and close fences, but executes POSIX synchronous lstat/read batches directly. Avoid an async Promise/await for every synchronous operation; yield after the same64-operation window with genuine progress and cancellation checks. Native asynchronous mechanics keeps its issued operation/drain model. Generated counterlaws can compare full old/new syscall AND observer/control/debit traces, output hashes and failure prefixes; do not claim a speedup until measured.

The existing full-content POSIX verify uses a different pattern: full observer fences around a synchronous chunk and cheap genuine control checks for each lstat. Adopting that observer cadence in metadata would be an explicit check-frequency change, not identical trace preservation. It may be justified only for a private fixed pure current-authority observer under its actual held custody, with full pre/post64 fences and per-syscall live control. It can miss a transient observer-visible drift that appears and disappears entirely within a batch, so do not describe it as observationally equivalent without a stronger domain invariant. Prefer exact-call batching first; require a separate Source contract for any reduction.
