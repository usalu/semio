## Post-install boundary and pending publication

The inspected producer `📦️dependencies/📜️script.ts` discovers the exact authored workspace scopes, then enters withJavascriptDependencyStorageV1 for each before calling prepareJavascriptDependencies. That wrapper opens the ordinary dependencies RepositoryCacheStore and its exclusive javascript-dependency-bindings gate. requireJavascriptDependencyStorageV1 validates a real reservation, store recheck and exact dependencies partition root. There is no pending-publication bypass or public producer accepting a maintenance token as a Store.

After the actual Bun child, the producer rechecks Source/custody/store and publishes workspace symlinks plus a durable exact bindings receipt. Its receipt/reuse checks do not perform a complete installed recursive maximum-path census before publishing. Thus a Source-first prepublication layout verifier is a plausible feature if actual diagnostic evidence identifies output path overflow. The verifier should run under this already authentic store/control and exclusive bindings custody, before bindings receipt/source-link publication; reuse must also require evidence tied to the same complete recipe/generation. It needs bounded complete traversal, cancellation/progress and exact path-unit/byte accounting, with real Generated Bun install fixtures and an independent oracle. A shallow generated example or successful input-path validation cannot prove all installed output paths.

A new short recipe must be authored before installation and included in generation identity. Existing staging helpers supply captured config/material/membership and exact immutable binding identity; full Witness traversal provides the current path policy semantics, but cannot simply be called as an authority-free scanner. During pending publication, ordinary producer admission remains refused; no existing Source route identified here lawfully mutates the declared dependencies image through this ordinary Store API.
