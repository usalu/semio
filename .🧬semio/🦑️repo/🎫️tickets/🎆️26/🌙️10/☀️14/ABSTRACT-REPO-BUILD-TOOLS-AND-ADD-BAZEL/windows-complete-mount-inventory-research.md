## Documented API Contract

[FindFirstVolumeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstvolumew) returns a GUID-volume string and search HANDLE; failure returns INVALID_HANDLE_VALUE. Its WCHAR count includes the supplied capacity, and results have no meaningful enumeration order. [FindNextVolumeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findnextvolumew) returns BOOL; only ERROR_NO_MORE_FILES establishes complete exhaustion. Other failure is refusal, not end. [FindVolumeClose](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findvolumeclose) owns closure of that search HANDLE; do not substitute CloseHandle or retry an uncertain close. These are Kernel32 APIs.

[GetVolumePathNamesForVolumeNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamesforvolumenamew) returns drive letters and mounted-folder paths as double-NUL-terminated MULTISZ. Counts are WCHARs, not bytes. Success reports copied characters; ERROR_MORE_DATA reports required size and may leave a partial list, which must never be accepted. A bounded implementation may retry only within its predeclared WCHAR/work/retry bound; buffer growth is not a reason to increase a policy limit. Empty path list is distinct from API failure and does not mean absent volume.

[Naming a Volume](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-volume) explicitly says one volume can have multiple GUID paths and can have no drive letter. Mounted folders can expose a volume through another volume’s directory. Therefore GUID string inequality and drive-letter prefix alone are not sufficient physical distinction. [GetVolumeNameForVolumeMountPointW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumenameforvolumemountpointw) requires a trailing slash and returns only the first GUID path from mount-manager cache when aliases exist. It cannot erase other aliases from the inventory.

Microsoft’s [Displaying Volume Paths](https://learn.microsoft.com/en-us/windows/win32/fileio/displaying-volume-paths) demonstrates volume enumeration plus all mount paths. Its unbounded resize example is API guidance, not an admissible repository policy implementation. An actual backend must produce a complete bounded result or refuse.

For robust actual-parent descendant detection independent of its drive-letter aliases, [FindFirstVolumeMountPointW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-findfirstvolumemountpointw) scans mounted folders on an exact GUID volume; [FindNextVolumeMountPointW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-findnextvolumemountpointw) exhausts only at ERROR_NO_MORE_FILES. These return mounted-folder paths rather than drive letters/GUIDs and have their own FindVolumeMountPointClose lifecycle. This parent-volume view can complement global GUID/path data; direct own-root enumeration avoids pretending all possible aliases can be reconstructed by a single textual prefix. NTFS scope remains explicit; unsupported filesystems refuse.

[GetLastError](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-getlasterror) is thread-local and must be captured immediately after the failing API, before observer/check/other calls can overwrite it. Existing Bun NTSTATUS observer avoids this issue with direct status returns; these Win32 APIs do not. A real binding must establish same-call/thread status capture (or existing P/Invoke SetLastError cached status semantics), not read a stale JS-layer last-error after an await. No new child or grant is authorized by this research.

## Complete Association, Not Ownership

Return bounded closed volume GUID/path/mount records as DATA. Authenticate the actual target backing→disk→partition→NTFS GUID through its existing selected-image command and native root handle; match inventory aliases to full native volume identity instead of deleting aliases. Normalize only closed local absolute path forms, case and component boundaries with explicit ambiguity refusal. Reject relative/dot/device/ADS/unrecognized reparse paths; do not adopt a descendant merely because a path is below root. Every actual child mount, including mounted folders and aliases, blocks parent publication until the real child owner settles. Parent EX excludes participating users but cannot make mount-manager enumeration atomic against unrelated administrators.

Use two complete canonical inventories bracketing protected facts and compare the relevant own-root/descendant association subset; no stable-order assumption. Unknown or changing aliases, duplicate conflicting associations, access-denied volume, partial list or missing final exhaustion refuses. The API documents do not promise an atomic global snapshot or identify each VHD file/producer from its volume GUID; exact VHD association and child ownership remain separate proof obligations.
