# Selected Tools Retirement Cost Source Audit

Read-only current ADMIN `retireRepositorySelectedToolingTreeV1`, owner checks and metadata durability helper; no protected payload/process observation and no intervention in the active owner. Structural costs below are not elapsed-time attribution.

The fixed postorder loop is finite and monotone: one sorted array of at most200000 captured rows, one removal per row, deletion from remaining, parent remaining-name deletion and final remaining.size zero. No traversal restart or retry loop appears here. Directory iteration has a200000-name cap and ends on actual EOF; hardlink peer sets shrink with remaining. Actual stalled iteration cannot be excluded by Source alone, but no algorithmic infinite loop is evident.

For a directory with m direct children, every removal verifies its complete current parent roster before unlink and enumerates it again afterward. Those scans consume exactly m+(m-1)+...+1 plus (m-1)+...+0 = m² child-name returns, plus2m EOF reads, before initial complete-capture/verification costs. Each returned name and EOF has before/after `requireRepositorySelectedToolingOwnerV1`; those checks repeat actual live control/refinement, parent read.check and registry/generation lease proof checks. Sorting and JSON serialization of both actual names and expected remaining sets are repeated per boundary. Across directories the roster term is Σm_d², not merely row count.

Each removed row also invokes syncNativeCleanupDirectoryV1. For ancestry depth h from its parent to Tools root, this performs h initial lstat observations, then h in-descriptor and h post-close ancestry rechecks, one parent descriptor stat/fsync/close: approximately3h path metadata reads per row plus genuine checks at each step. The row itself gets name/descriptor CAS, unlink, absence proof and hardlink peer observation when applicable.

Full Core journal/token reauthentication and tooling.json content SHA are in `recheckRepositorySelectedToolingOwnerV1` at logical tree boundaries, not directly once per row. However each cheap-looking check invokes the existing parent `read.check`; do not describe it as a cached pure boolean. Binding/witness/generation integrity and complete inventory are captured/rechecked around tree retirement; object retirement separately does full owner proofs per selected object. No complete Source ALL scan appears in the per-row postorder body.

Lowest-authority next improvement: preserve every physical roster read, exact check/cancellation boundary, work/progress and fsync order, but remove repeated pure expected-roster sorting/serialization. Construct each private directory expected-name array once in the exact existing JS sort order; update by exact verified deletion, compare actual sorted names elementwise, and avoid JSON serialization/allocation. Cache row depth and encoded path sort keys once before the unchanged postorder comparator. This does not eliminate Σm² physical observations, so no large runtime speedup is claimed. Schema-first law should compare full modeled IO/check/control/progress/primary traces before/after, independent SQLite remaining-name sequence and allocation/sort counters, including unknown-name injection, directory drift, hardlinks, undefined/frozen failure and cancellation.

Reducing physical roster replay or durability checkpoints would change observation/failure timing and needs a separately authored stronger descriptor/custody contract; it is not the above semantics-preserving optimization. No timeout increase, live-owner cancellation or partial-retirement adoption is proposed.
