# Windows Native Journal Async Commit Contract

The actual Native storage transaction callback currently receives synchronous append/checkpoint functions. Each append writes and fsyncs before returning; first-party creators may rely on that durable ordering before a physical child birth. A Windows mechanism cannot hide asynchronous IO behind those functions, nor defer all writes until callback return. Conversely, a long loop of synchronous Native writes cannot honestly provide cooperative progress/cancellation between partial writes.

The clean candidate is explicit async append/checkpoint, with all first-party call sites handcrafted to await the durable event before subsequent authority/effects. Existing journal event codec, byte representation, capacity, replay and row identities remain unchanged; this is an internal current API change with no compatibility layer. Only one mutating command may be pending per actual transaction; concurrent unawaited mutation refuses. The transaction retains real journal EX and closes/drains accepted mutation work before releasing. State/text advance only after durable commit. Undefined/frozen primary and dirty metadata cleanup semantics remain truthful.

The actual enforcing Windows port must provide closed journal mechanics under its actual Native frame plus genuine exact journal writer proof. The body proof binds the real SQL EX to canonical leaseDirectory/native-storage:<fullactualbackingidentity>; accepted cleanup uses its actual captured loan/writer proof. The readonly sampled baseline or a journal path is insufficient. Reads do not supply a writer. No public registry or caller program/provider/Store is introduced.

System mechanics should use separately acquired rooted no-reparse Native file handles and bounded closed read/create/append/checkpoint commands; read descriptors must not be promoted to writable handles. Append compares complete current named/held file identity, size and prior raw hash, writes positive partial chunks at exact expected offsets, refuses zero/overflow, then flushes and performs final same-object/named/association proof. Every actual read/write checks the same owner/control/account and yields progress cooperatively. Existing 64KiB chunk/32 descriptors/path256 stay; a distinct journal operation work formula must include authentic bounded journal bytes and worst-case one-byte positive IO, not pretend the readonly receipt budget already covers it. No caller budget/reset.

Checkpoint replacement needs explicit Native sharing/rename proof. Root-relative names are supported by NtCreateFile; FILE_CREATE is absent-only while FILE_OPEN never creates. FILE_RENAME_INFORMATION itself names a target basename, not an expected file ID. It must not be treated as conditional inode CAS. A controlled retained-old/no-replace sequence under genuine journal EX may be appropriate, with durable known staging/cleanup ownership and exact fences, but any new filename/temporary-gap/recovery semantics must be closed/schema-owned rather than inferred from arbitrary old files. Generic conditional FILE Windows currently refuses and cannot stand in for this proof.

Prospective schema/TDD: all Source append/checkpoint calls awaited before simulated creator effect; exact old/new POSIX IO order/count and replay; 1-byte/short/zero writes; early cancellation, undefined/frozen failure; pending concurrent append; current tail/hash/native128 replacement; exact root/mapping drift; exclusive create collision; checkpoint foreign target and close/flush uncertainty; admitted-child drain and no postclose authority. Native/NTFS qualification remains separate.

The checkpoint design above is an inference and remains unimplemented/reviewable; these documents do not establish an inode-conditional rename primitive.
