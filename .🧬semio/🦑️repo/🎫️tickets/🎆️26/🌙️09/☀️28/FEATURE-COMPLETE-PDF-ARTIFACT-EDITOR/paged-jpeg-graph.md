# Native PDF DCT Graph Reloan and Placement

The PDF snapshot represents an image twice. `images` carries a typed `PdfImageBody::Artifact` reference. `objects` carries the original encoded COS stream with singular typed `Dct` filter. `admitted_stream_roles` supplies the outer object number and generation for a qualified compiled image. A role binds a structural dependency and can carry a claimed reference. Role validation alone does not attest that the claimed digest matches the original byte stream.

`NativePdfDctLookup` is a staged subsection of the existing native PDF artifact port. It parses the typed reference into the fixed digest and resolves one role or graph object row per work turn. It accepts the same small original image dictionary shape as the controlled reader and checks the dimensions, precision, colorspace, DCT filter chain and exact object generation. It hashes at most 4,096 bytes per turn from the original retained stream and compares the actual digest. It then produces a `PdfDctImageView` over the exact native row without cloning its encoded body. The view can be reborrowed by `DctObjectWriter` or the future preview job from the same canonical revision. This path covers controlled direct-image roles with a root object identity. Other native resource shapes continue through their existing routes.

`PendingDctPlacement` is the staged authored transaction boundary for JPEG import. It takes the exact `AdmittedPdfJpeg` emitted by the paged proof, stores it next to `SetImage` and one ordinary paint change, and emits the admitted reference and verified dimensions into the typed image. The new image shares the same existing image/form namespace allocation and page insertion or exact replacement helpers as PNG. Replacement uses a new named resource, preserving other placements of the replaced resource. Taking the native resource and both mutations requires the captured full revision. The pending transaction hands the original owner back to the caller for paid retirement on rejection or abandonment. This is private assembly before the durable store commit.

## Verification

`paged-jpeg-graph-stage.py` builds the staged sources and focused harness in `🗑️generated/paged-jpeg-graph`. The probe mounts the actual qualifier, dictionary accessors, graph lookup, placement assembly, repository SHA-256 state and classic PDF writer with narrow stand-ins for artifact model fields and the pending admitted owner. It reloaned the actual 2,125,603-byte fixture as an already retained native COS row, verified unchanged storage address and exact digest, and fed that same view to the bounded writer. A changed source octet with the old role reference was rejected. Wrong canonical revision and unavailable placement were rejected. Insert produced the expected save/transform/paint/restore group. Replacement produced the exact operator replacement and kept the prior image untouched. Publication or rejection preserved the original source address in the harness.

MuPDF 1.26.7 reopened the PDF generated directly from the verified graph view without repair. It matched the original DCT codestream SHA-256, dimensions, declared length, filter parameters, exact fixture crop and the native reference. The sequential writer used at most a 4,096-byte source window under injected sink backpressure. The graph view is ready for a future preview consumer. Mounted preview, the paid owner transaction and durable history replay still need the production boundaries below.

## Durable Commit and Ingress

The existing per-operation revision gate in `ArtifactCommandInputs::operation.canonical_base_revision` is the source of authority. Its paid input entry points are `receive_original_command` and `receive_original_wire`. The similarly named `receive_original_output_chunks` is wired for segmented **output** custody. A picked JPEG needs the host/guest ingress to transfer an original `ControlledRetirement<PagedBytes<4 MiB>>` under the captured document and target. Feed it into `PdfJpegAdmission` and move the admitted owner into `PendingDctPlacement::prepare`. Only the store's compare-and-install transaction may call `take_for_publication` and install the returned native row together with both mutations. The stale check and the store commit belong under that same publication authority.

A persistent native resource lane or store-owned content-addressed resource attachment still needs an invertible history reference and controlled custody handoff. The current generic PDF apply path clones its whole base snapshot, and the current mutation/history publication only accepts typed mutation rows from `Emit`. The retained graph object stream uses `Vec<u8>`. Simply moving compliant pages into an additional snapshot field would make existing cold clones duplicate the JPEG on later edits. The snapshot's handwritten native Value and text-Pack projections, SQLite snapshot codec, and conformance snapshot clone also need resource support. `PagedBytes` has controlled clone/retirement and borrowed octet reads, and its ordinary controlled Value encoding currently refuses through the trait default. A durable owner must provide a shared immutable native-custody record or retained resource-store attachment with paged persistence, so ordinary edits and history aliases never require cold original-byte copies. Save consumes the resource view after the same commit and the published resource must survive undo/redo and reopen.
