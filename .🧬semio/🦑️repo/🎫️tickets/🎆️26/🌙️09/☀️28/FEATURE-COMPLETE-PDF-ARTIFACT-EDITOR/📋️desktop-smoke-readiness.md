# PDF 1.7 desktop smoke readiness

The generated catalog and the published session projection both select variant `stdio-pdf-1-7`, plugin `stdio-pdf`, and app `s.stdio.pdf@1.7/*#editor`. The canonical native entry point itself instructs callers to use `repo run @semio-tech/framework-os-dev:run-<variant>-native-<profile>`. Thus the intended desktop target is `repo run @semio-tech/framework-os-dev:run-stdio-pdf-1-7-native-prototype`; its native runner accepts `--smoke` after the selection. Pass it through the repository target argument boundary (`-- --smoke`) when the target forwards arguments. Confirm forwarding in the target output; this audit did not launch or build it.

The native runner loads the selected playground session and native runtime, resolves the catalog app, and launches the native WGPU host with `--plugin stdio-pdf-1-7 --app s.stdio.pdf@1.7/*#editor`. With `--smoke`, the native entry point calls `run_smoke` instead of creating a presentation host. That path loads the actual Wasm plugins, boots the shell, refreshes UI and prints JSON containing `booted`, `session.pluginId`, `session.appId` and `windowDocuments`. The smallest useful later check is a successful exit with `booted: true` and the exact PDF app and plugin IDs; inspect window documents as additional evidence. This is a headless shell integration check, not GPU painting, file import, edit, save, or proof of a desktop window. The separate headless renderer I/O test uses a JSON fixture and does not establish PDF integration.

The session projection exists at `.cache/b/p/m/browser/prototype/sessions/stdio-pdf-1-7/🎠️playgrounds.json`. The mounted E2E report records artifact-reader validation of the Editor, Surface and NodeGraph six-file Wasm products and font receipt; its active component build still owns Stdio and PDF publication. This does not establish a native runtime manifest or native host. The earlier report explicitly found neither native runtime nor renderer staged. A direct filesystem observation found no `.cache/b/p/m/native/prototype`, but that guessed path alone is not a canonical artifact-reader verdict. Native runner requires both `withNativeRuntimeV1` and a materialized native host executable, in addition to the session. The component build completing for React does not by itself prove those native prerequisites.

The catalog declares browser WGPU port 6360. No app-specific React or WGPU activation directory was present at the inspected browser runtime paths. Browser WGPU was therefore not exercised; its separate host/renderer staging and actual browser session still need validation.
