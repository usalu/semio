# Pinned build implementation

## Finding
- The pin exists (`implementationPinnedV1`, `withImplementationPinV1`, `withReceivedImplementationPinV1`): the front doors, `script.ts` and every received script invocation open it, and about 20 self-checks (observation, revision reader, inputs, cargo descriptors, cache store, graph closures) return early under it. The command also runs from a captured snapshot (live capture, or the sealed store with `SEMIO_REPO_SEAL=sealed`).
- Hole 1 (fixed): the format-stamp registry (`🏗️build/🧷️format-stamps/🟨️.mjs`) was the one self-check that ignored the pin. `guard` (every exclusive lease admission and queue round) and `ensureCurrent(kind=yield)` (graph discovery) compared the stamps the process loaded with the live schema files, so any peer edit of a stamp schema made a pinned run yield, exit 75 and restart; six such restarts end with "The stamps moved again after the restart".
- Hole 2 (fixed in follow-up, see below): `requireLoadedCargoProfilePolicyV1` (`⚡️caching/💾️storage/🔒️enforcement/🏗️compiler/🚪️ingress/⚙️configuration`) throws `staleImplementationV1` when the cargo profile policy file differs from the loaded digest, pin or not. That file is both implementation and a consumed Cargo input, so a pinned bypass needs the loaded digest in the inputs and a skipped recheck; left for its own change.
- Hole 3 (not fixed, by design): the default `SEMIO_REPO_SEAL` is `live` (`🏛️sealed/🔣️.json`), the tool-editing mode. Script processes that import the live library directly (the ticket's `pdf-browser-direct.ts`) still load lazily from the live tree and can hit half-edited modules (`load` origin). `SEMIO_REPO_SEAL=sealed` removes that for door commands.
- The exact trigger of the five 15:23-15:53 aborts was not recoverable: `components.log` was overwritten by the 20:51 retry.

## Change
- `ensureCurrent` returns at once for `kind=yield` while pinned. `kind=refuse` (a store newer than the loaded code) still throws, so a pinned run never reads a format it cannot parse. Cache keys already carry the loaded implementation digest (graph memo, Bazel plan, observation rows name the loaded digest), so what a pinned run publishes names the start-time implementation; an edit reaches the next run only.
- Residual risk: a pinned run may publish its older store format after a peer moved a stamp; readers validate markers and refuse or rebuild (`cache.graph-image`, `graph.record`).

## Follow-up
- Cargo policy: `loadedCargoProfilePolicyDriftedV1` (same module as `requireLoadedCargoProfilePolicyV1`). Pinned and the policy Source differs from the digest the process loaded: no restart; the run keeps the profile it rendered, its inputs name the loaded digest and its recheck skips that file, so the edit reaches the next run. Unpinned behaviour is unchanged (still refused). Torn policy bytes under a pin count as drift, not as an error. Test: `⚙️configuration/🧪️tests/👁️profile-recheck`.
- Default seal mode (evaluated, not flipped). Every door command already runs pinned from text captured at its start in `live` mode (`executeCapturedBuildSourceV1`); `sealed` additionally runs a promoted, shared snapshot, so a run neither re-captures 1,500+ files while peers edit (capture churn, 10-40 s) nor moves the implementation digest that keys the graph memo and Bazel plan. The principled default is therefore: long runs (`run`, `cargo`, `test`, `run_many`, e2e chains) pin and seal; short interactive and light commands stay `live` (cheap, see the newest code). It is not made the global default because the mode is chosen from the environment before argv is read (`liveImplementationStartV1`), and `explicit` promotion has no promoter in this shared-replica setup (no landing gate), so a flip would leave every agent on a stale snapshot for up to 24 h. Recommended use: `SEMIO_REPO_SEAL=promote repo` once after the last tool edit, then `SEMIO_REPO_SEAL=sealed` for the long run (`e2e-chain.sh` does this). A per-verb default (heavy sealed, light live) needs argv threading in the trampoline; left for its own change.
- Store markers: the graph image marker is validated against the loaded `Marker` schema (`planRepositoryGraphFormatV1`, `cache.graph-image`) before any read; only an image with exactly the loaded format is read, any other (older or newer) is refused. A pinned run only reads that marker; only the exclusive initialiser writes it. Test: `📇️format/🧪️tests` (pinned run, equal marker read, v3, snapshot 3 and 1 refused). So a pinned older run cannot make a newer reader accept an older store, nor read a newer one.
