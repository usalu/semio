### 2.1 Self-`$id` references → bare JSON pointers (36 rows, 7 files)

A `$ref` that names its **own** document's `$id` is a module-internal reference written the long way.
The harness classifies any non-`#/$defs/` fragment on an absolute URI as unresolved regardless of whose
document it is (`schemaRefDiagnostics` tests the fragment shape at `:4790`, before the
`targetScope === scopeId` short-circuit at `:4795`), and execution contract §A says module-internal
helpers are addressed `#/definitions/<helper>`. So `<own $id>#/definitions/x` → `#/definitions/x`.

## 3. `schema-export-incomplete` / `schema-export-parser-missing` — `framework.interaction`

30 + 2 rows, one scope. It is the only scope in the partition that provides four formats
(`🔣️jsonschema`, `🔗️graphql`, `🦀️rust`, `🟦️typescript`) — GraphQL already declared all 16 exports; Rust
and TypeScript published them, but in a form that names none of them.

### 3.1 Rust — `pub use` block → sixteen named `pub type` re-exports

`🕹️interaction/🧬️schema/🦀️.rs` published its exports as one grouped
`pub use super::{DomainHover, DomainSelection, …}`. `declaresSchemaExport` asks Rust for
`^\s*pub\s+(?:struct|enum|type)\s+<Export>\b`, per contract §A ("Rust `pub struct|enum <Export>`"), and
a grouped `pub use` matches nothing. Each of the 16 `$defs` exports is now its own
`pub type <Export> = super::<Export>;` — the same items, published under names a reader and the gate
can both see. `InteractionRef`/`InteractionTopology` are **not** `$defs` exports and stay a plain
`pub use`.

> **Contract friction, reported not silently resolved.** Execution contract §A (line 26, added during
> this pass) says "a Rust re-export is `pub use` (a private `use` declares nothing)", but the harness's
> Rust vocabulary does not accept `pub use`. Either reading is defensible; I made the module satisfy the
> **implemented** rule rather than change a harness in another partition. See §6.2.

### 3.2 TypeScript — named types plus sixteen `parse<Export>()` entry points

`🟦️.ts` re-exported the declaration types as `export type { … } from "../🟦️.ts"`, which likewise names
nothing the TS vocabulary recognises, and defined `PresenceDomain`/`PresenceInteraction` with **no**
entry point (the 2 `schema-export-parser-missing` rows). The leaf now publishes
`export type <Export> = root.<Export>;` for the 14 root-owned exports, keeps the two locally-defined
presence types, and adds a hand-written `parse<Export>()` for all 16 — a type alone is erased at
runtime, so a consumer handed a `schema://framework.interaction/<Export>` payload had no way in.

The parsers are ours (no runtime validator dependency, CLAUDE.md): a small
`members`/`text`/`flag`/`list`/`keyed`/`member` kit that enforces `required`, `additionalProperties:false`,
`minItems`, the three closed enums and the `kind`-tagged `HierarchyProvider` union, refusing with the
export and the member it refused on.

### 3.3 The oracle that keeps them honest

New language-agnostic corpus `🧬️schema/🧪️tests/🔬️parser-oracle/🔣️.json` — **51 cases, at least one
accepted and one rejected per export** — and a runner `🟦️.ts` that puts each case through **both** our
`parse<Export>()` and **Ajv** compiled from the same `🔣️.json`, then asserts they agree case by case
(third-party oracle per CLAUDE.md). It also asserts the corpus covers every export in both directions,
so an export added later without vectors turns the suite red.

The Rust side gained the twin law
`every_declared_format_leaf_declares_the_export_by_name` (`🧪️tests/🔬️unit/🦀️.rs`): for each of the 16
exports it asks each of the four leaves for the entity in that leaf's own vocabulary — the exact
question the gate asks from outside — instead of only proving the file resolves and is non-empty.

`framework.ui.contract`'s 2 rows were closed by the ui worker during this pass (`pub struct` +
`"x-semio-formats": ["🔣️jsonschema","🦀️rust"]`); verified on disk, not touched by me.

**No `x-semio-formats` annotation was added anywhere in this partition.** The rule (`📓️wp1c` §2.1) is
that an annotation must be exact in both directions; `framework.interaction` genuinely carries all 16
exports in all four formats, so restricting it would have been a lie that happened to silence the gate.

## 4. Placement (3 rows over 2 files)

### 4.1 `📡️replication/🔗️causal/🧪️fixtures/🧬️mutations/➕️causal-add` (2 rows)

`schema-placement-outside-module` + `schema-fixture-defines-schema` on one
`➕️causal-add/🛂️schema/🔣️.json`. It is the payload schema of a **test-only dummy** mutation leaf:
`CausalAddOp` lives entirely inside `🔗️causal/🧪️tests/🔬️unit/🦀️.rs` (`#[cfg(test)]`), the leaf sits in a
`🧪️fixtures` tree (never an eligible owner, contract §A), and the file had **zero** readers repo-wide —
`resolvePayloadSchemas` never sees it either, since it only walks `<owner>/🧬️schema/🧬️mutations/<leaf>`.

Resolved by the precedent the same module family already sets: the sibling test-only leaf
`📡️replication/🎮️mutation/🧪️tests/🔬️mutation-leaf-metadata/🦀️.rs:11` declares
`payload_schema: "🦀️.rs#InsertPage"` with `required_language_surfaces: &[Rust]`. So the causal dummy now
declares `payloadSchema: "🦀️.rs#CausalAddOp"` and `requiredLanguageSurfaces: ["rust", "binary"]` (it does
implement `OpBinary`), the JSON file is deleted, and both sides of
`causal_add_fixture_has_exact_required_descriptor` were changed together — proven by a real run (§5.4).
No JSON-Schema-surface coverage is lost: 229+ real stdio leaves exercise that shape.

### 4.2 `🕸️graph/🤖️generated/🔣️manifest.schema.json` (1 row)

`schema-placement-forbidden-filename`. The graph catalog generator emitted a **hand-written literal**
JSON Schema of `GraphManifestDocument` into its generated output root, under a `*.schema.json` name the
taxonomy retires — and the owner module's own `Outputs` export *required* that retired name
(`"jsonSchema": {"pattern": "^[^/\\\\.]+\\.schema\\.json$"}`). Renaming the output only trades the
finding for `schema-placement-outside-module`, because a `$schema`-bearing document outside a
`🧬️schema/` module is a finding whatever it is called, and `🤖️generated/` is not an eligible owner.

So the contract moved to its owner and the duplicate went away (contract §A: a scope never restates
another scope's `$defs`; §B: dev-tool outputs that are serialized and consumed are scope contracts):

* `🕸️graph/🛂️manifest/🧬️schema/🔣️.json` gains `$defs.GraphManifestDocument`, authored draft-07 from the
  generator's own reader types (`ManifestDocument`/`ManifestKindRow`/`ManifestPropertyDef`) and its
  emitted `GraphManifestDocument` interface — `additionalProperties:false` at every level, typed kind
  rows (the generated literal said only `{"type":"array"}`), plus `blockKinds`, which the emitted TS
  type declares and the generated schema had silently dropped.
* `shared.jsonSchema` is removed from the `Outputs` export, from `🛂️manifest/📇️outputs.json`, from the
  generator's `GraphOutputCatalog` type/`record()`/`path()` and from `🧪️tests/🔣️outputs.json`
  (`shared` + `expectedPaths`); `emitJsonSchema()` and its `artifacts.push` are deleted.
* The module is now multi-export, so its root `allOf` is dropped (the convention of
  `📓️wp4-framework-modules.md` §2) and its one consumer, `🧪️tests/🧩️suite/🟦️.ts`, binds
  `#/$defs/Outputs` explicitly.
* `bun ./📜️script.ts generate` re-rendered the tree without the file; the stale copy is gone.

Proof the new export is not narrower than reality: **9 of 9** real `*.manifest.json` documents in the
tree validate against it (§5.3).

`declaresSchemaExport("🦀️rust", …)` accepts only `pub struct|enum|type <Export>`. The two statements
cannot both hold. Either

* the harness regex gains `pub use` (then `🕹️interaction/🧬️schema/🦀️.rs` could go back to one grouped
  `pub use`, though a grouped one still names no export to a *reader*), or
* contract §A drops the sentence and per-name publication (`pub type X = super::X;`, what this pass
  did) is the declared Rust form.

Nothing else in the partition is affected either way — `framework.interaction` and
`framework.ui.contract` are the only Rust-providing scopes in it.

### 6.3 W1c — the two-measurement problem is worth a flag in the gate

`test schema --under <path>` reports 0 `schema-ref-*`/`schema-export-*` rows **by construction**, which
reads as "this subtree is clean" to anyone who does not know line 4860. Consider either running
resolution and filtering its rows by the `--under` prefix, or printing one line saying resolution was
skipped. `wp4d-framework-measure.ts` in this ticket folder is a working shape for the former.
