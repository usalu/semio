# Native PDF Consumer Boundary Audit

Read-only review of the retained consumer inputs, the PDF package manifest, and the current public crate root. No restored-output consumer build has been run by this audit.

The consumer source [🧪️native-pdf-consumer/🦀️.rs](🧪️native-pdf-consumer/🦀️.rs) imports exactly one Semio crate: `semio_s_artifact_stdio_pdf`. It calls four public package functions: `artifact_kind`, `native_codecs`, `definition`, and `contribution`. It does not name a stdio parent/catalog crate, a framework crate, a source module, or a workspace-relative path. The PDF manifest’s direct stdio edges are only Binary, the shared Stdio contract, and Deflate; it has no stdio parent/catalog dependency. Framework crates are legitimate implementation dependencies of PDF, but none is an API import or explicit consumer dependency.

The checked public values are declared at [🦀️.rs](/Users/ueli/Documents/semio/✏️s/🔌️plugins/🗄️stdio/🗿️artifacts/📖️pdf/🦀️.rs:28): `definition` derives an executable definition from `native_codecs`; `native_codecs` declares one PDF factory with id `stdio.native.pdf.v1`; `contribution` declares identity `pdf`; and `artifact_kind` declares `stdio.pdf`. The consumer accesses those functions through the package’s public root only.

[🧪️native-pdf-consumer/🔣️.json](🧪️native-pdf-consumer/🔣️.json) is an independent, literal JSON oracle with those four expected values. The consumer embeds it with `include_str!`, parses it through `serde_json`, and compares the complete object to an independently constructed object. This rejects changed, missing, or extra metadata fields in either object. The values exactly match the current public declarations; the fixture does not derive its expected data from the PDF definition source.

The fixture therefore supports the existing narrow claim: a downstream binary can use public PDF metadata, find exactly one native-factory identifier, and successfully construct a standalone definition without direct parent/catalog/framework imports. It does not yet establish PDF codec behavior or full definition semantics. Concrete untested public relationships are the selected factory's `artifact` label (`pdf`), its `kind` function result, invoking its codec constructor, and inspecting definition executables. It also does not consume a PDF-byte or mutation fixture. Those are only required if the restored-consumer acceptance claim is expanded from public-linking and metadata to codec or document-conformance behavior.
