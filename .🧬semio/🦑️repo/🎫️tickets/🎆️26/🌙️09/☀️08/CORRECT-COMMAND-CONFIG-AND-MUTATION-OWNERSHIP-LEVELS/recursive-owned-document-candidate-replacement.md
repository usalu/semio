# Recursive Owned-Document Candidate Replacement

## Current Implementation

The Plugin SDK retained replacement owner holds one unpublished parent-plus-members candidate. `OwnedDocumentMemberIngress` binds an ordinal, full `ArtifactRef`, exact recursive `OwnerRef`, admitted `MemberOpenRequest`, operation and generation. Its registry preallocates the declared ordinal set up to Store's 1,024-member closure limit, accepts transport-independent order, rejects duplicate ordinals, and bounded-closes retained requests and identity strings.

`ActiveArtifactStoreReplacement` opens each member through `MemberFactory::begin_open` and `MemberOpenOperation::step`. Actual decoded stores enter `ChildMemberRegistry`; transport claims never supply child projections. `DocumentClosureSourceView` exposes the candidate root snapshot and each decoded member's borrowed `ChildRestoreProjection` to Store's `OwnedDocumentClosure`. Only a completed exact closure advances to immutable content and `CompositionCoordinator` construction.

The public maintenance dispatcher keeps stages 0–7, which own the large tool, media, content and presence retirement values, behind a non-inlined inherent helper. Stage 14 therefore reaches the replacement driver without reserving stack slots for unrelated early-stage owners. The focused proof selects stage 14 before entering `PluginApp::maintenance_step`; the broad suite advances the ordinary round-robin dispatcher. The temporary direct-driver test API has been removed.

The publication boundary rechecks parent generation, child-content generation, cancellation, candidate completeness, replacement-retirement allocation and document-store publication authority without suspension. It then replaces the parent store, complete member registry, immutable content root, pending content retirements, composition coordinator and pending pins; advances child-content generation; and commits the prepared document-window reset in the same observable turn. The displaced bundle remains in the replacement owner and retires incrementally before terminal acknowledgement.

## Recursive Fixture

The native fixture uses a closed `RecursiveTestMembers` enum with one finite branch schema type. The same member variant represents both a branch with an optional nested handle and a leaf whose nested handle is empty. The accepted candidate is `replacement-parent` to `child-1` through root slot `slot`, then to `grandchild-1` through recursive slot `nested`. The schema itself is finite while the owned-document closure contains two real levels.

The leaf is admitted before the branch, proving ingress order is independent of closure order. The success law observes either the complete old bundle or the complete new bundle around every maintenance step. It checks both typed member snapshots, both ownership-graph edges, two persisted member envelopes, cleared displaced pins, one child-content generation advance and one document-window generation advance. Terminal acknowledgement and app close require every displaced owner to reach bounded terminal-empty ownership.

The rejection laws drive missing-grandchild, unreachable-extra and duplicate decoded-member candidates through complete bounded retirement and assert that the live parent, content root, child-content generation and window generation remain unchanged. Cancellation is exercised after a real member open begins, at closure validation, and during immutable-view preparation. A stale-authority law performs a real concurrent live child-content publication after the recursive candidate reaches `CandidateReady`; the candidate is rejected while the concurrent live generation remains authoritative.

## Language-Neutral Validation

The neutral JSON corpus describes eight success, topology-rejection, cancellation and stale-authority cases. The TypeScript oracle validates it with Ajv and independently uses Graphlib to check unique identities, exact parent/declaration equality, reachability and acyclicity. It permits publication only for a complete topology with live authority and no cancellation.

The registered root and ticket `retained-window-input` routes run this oracle with the existing retained-window oracle. Native tests use the `retained_window_input_recursive_` prefix, so the existing Cargo filter selects them.
