## 2 The blockers, from a user's point of view

### 2.1 Both window bodies are blank — and there is no canvas anywhere on the page

`document.querySelectorAll("canvas")` returns **`[]`**, at every one of four observation points:
after a 60 s settle, after clicking the `Preview` dock tab, after clicking the `Flow` dock tab, and
after clicking `Generate`. The Flow pane and the Preview pane both draw their frame and their title
bar and nothing inside. So: no node graph, no 3d preview, nothing to hover, nothing to select.

This is a REGRESSION against boot #4/#5, where `📓️node-graph-attach-2026-09-10.md` had the flow
canvases painting (`dag draw lod=normal/detail`). Something between then and the 21:28 tree stopped
the engine surfaces from mounting at all.

### 2.2 Clicking `Generate` does not open the generate mode's windows

The artifact declares three windows under `✏️editor/🎭️modes/🧬️generate/🪟️windows/` — `👁️preview`,
`📝️form`, `🗂️generations` — and the staged descriptor carries their labels (`Formular`,
`Generations`, `Preview`). After clicking `#playground.navbar.modes.generate` the DOM id set is
**byte-identical** to before: still `mode-dock-tab-0-procedural-main` and
`mode-dock-tab-1-procedural-preview`. No form, no generations window. Every boot in
`📓️status.md` observed only the two edit-mode windows, so generate mode has never once been
exercised at runtime in this ticket.

### 2.3 The geometry extension is never invoked, so no geometry can ever exist

In 60 s of armed diagnostics: `flowEvalTick` dispatched **184** times, and `invokeExtension`
dispatched **0** times. Zero. Not "invoked and faulted", not "invoked and unanswered" — never
invoked.

That is a different failure from every previous boot. Boot #12 reached
`invokeExtension dispatch failed {extensionId: flow-extension-math, capability: evaluate}`; boot #13
does not reach `invokeExtension` at all. All nine flow extensions DO load and hot-swap cleanly,
including `flow-extension-brep v0.3.0`. So the extensions are present and the tick runs, but the tick
never turns into an extension call.

Consequences down the chain, all confirmed absent from the trace: no `mesh`, no `scene`, no
`snapshot` of geometry, no `World3d`, no tessellation.

### 2.4 An invocation storm is eating the guest's memory budget

| action | dispatches in 60 s (armed) | dispatches in 90 s (unarmed) |
|---|---|---|
| `flowEvalTick` | 130 | 184 |
| `setContributions` | 52 | 93 |
| `setActiveExample` | — | 3 |

`setContributions` is an install-time action carrying a paged ~294 KB contributions payload
(`📓️contributions-delivery-2026-09-10.md`: 73 pages). It ran **93 times in 90 seconds**. Alongside it
`plugin_exchange entry … branch=command-invocation` appears 949 times and `applyHostEffects refresh
{"scope":{"kind":"full"}}` 314 times.

The cost lands exactly where the realloc lane warned it would:

```
[error] guest linear memory at 322240512 B — 60% of the 536870912 B budget,
        past the 60% install-peak ceiling
```

322 MB of a 512 MiB ceiling, on an app that is displaying two empty rectangles. `dlmalloc` never
returns wasm linear memory, so this is monotonic: the storm is a slow walk into the same allocator
refusal that produced boot #12's abort. This is the performance limit the ticket's objective asks to
be met with architecture work, and it is being hit while doing no useful work at all.

### 2.5 The guest's diagnostic writer emits one `console.error` call per token

`[DEBUG] cooperative-maintenance` and `[DEBUG] plugin_exchange` do not arrive as messages. They
arrive as hundreds of separate `console.error` calls, one per token, which the browser then has to
lay out as separate rows:

```
[error] [DEBUG] cooperative-maintenance instance=
[error] 1
[error]  turn=
[error] 1
[error]  generation=
…
[error] CooperativePoolSnapshot
[error]  {
[error] pump_calls
[error] :
[error] 1

```

Measured: **5 750 raw console lines for 90 s of boot**, which stitch back into **1 452** logical
messages — a 4× fan-out — and **7 775 lines** for the 115 s armed run. `plugin_exchange entry`
alone accounts for 949 of them. Two defects in one: the fan-out itself (a per-token host call on a
hot path, which the hot-path lane's "0 console lines" result in
`📓️hotpath-optimization-2026-09-10.md` cannot have been measuring), and the level — routine `[DEBUG]`
maintenance chatter is emitted at `error`, so it is indistinguishable from a real fault both to a
developer and to any automated gate.

## 3 What this changes about the plan

Boot #13 retires the whole class of problem the last twenty lanes were chasing: delivery no longer
traps, memory no longer explodes on a single answer, contributions install, the action chain is
healthy, the fold contract and work capacity hold, and the chrome is finished work. What is left is
narrower and further up the chain than the ticket has been looking:

1. no engine surface mounts in either window body (§2.1) — nothing renders, so nothing can be hovered or selected;
2. generate mode's three windows never open (§2.2) — a third of the artifact's windows are unexercised;
3. `flowEvalTick` never reaches `invokeExtension` (§2.3) — no geometry can exist;
4. an install-action storm walks guest memory to 60 % of budget while idle (§2.4, §2.5) — the architecture problem to solve, not a leak to patch.

## 5 — Root cause, closed: the contributions push is a 202-second sequential blockade

§4 ended at "the guest delivers no window UI". That was one link short, and the missing link
turns out to explain every symptom in this report at once. It is **not** a guest defect.

### 5.1 — What the console actually proves

Re-read of `🗑️generated/s13-diag-console.txt`, all figures measured, none inferred:

| Fact | Value | Evidence |
| --- | --- | --- |
| `contributions push` events | **1** (not a loop) | one `[DEBUG] contributions push` line, at 3169 ms |
| Payload size | **397 921 chars** | `chars` field of that line |
| Pages the payload is split into | **99** | `pageCount` field |
| Page-commands actually sent | **53 of 99** | `performInvocation …setContributions` count |
| First page / last page | 3187 ms / 111 464 ms | timestamps of first and last such line |
| Capture ended | 114 461 ms | last console line |
| **Cost per page** | **≈ 2.04 s** | 53 pages over 108.3 s |
| **Projected total** | **≈ 202 s** | 99 × 2.04 s |

So `setContributions` was never invoked 93 times as §2.4 read it. It is **one** push of **one**
398 KB payload, paged into 99 sequential guest commands at two seconds each. The 60- and 90-second
settles used by every probe in this ticket expire less than halfway through it.

### 5.2 — Why that blanks every window

`🏛️ShellHost/🟦️.tsx` pushes the pages in an awaited loop at `:4354`–`:4358`, and the **first
window-UI dispatch of the boot sits after that loop, in the same function**, at `:4386`:

```
:4354   for (const [page, json] of pages.entries()) {
:4357     await pluginEntry.handle.handleCommand(instanceId, wire, …);   // ×99, ~2.04 s each
:4358   }
          …
:4386   dispatch({ type: "SET_WINDOW_UI_BY_WINDOW_ID",
:4390     value: (current) => mergeRecordPreservingIdentity(current,
            windowInstances.map((instance) => [instance.id,
              cache.get(`window:${instance.id}`)?.value ?? current[instance.id] ?? pendingWindowUiNode()])) });
```

That closes the chain end to end, every link now checked against either source or console:

1. shell aggregates contributions → 398 KB;
2. the public-invocation envelope caps every string at 4 KiB → 99 pages;
3. the pages are pushed **sequentially awaited** → ≈ 202 s;
4. `:4386` is therefore unreachable for the first ~3.4 minutes of every boot;
5. `windowUiByWindowId` stays `{}` — the reducer's initial value at `🐚️Shell/🟦️.tsx:1137`, and its
   **only** writer in the codebase is `:4386`;
6. `🏛️ShellHost:9085` converts `{}` into `return []`;
7. `🎨️Canvas:1229` renders a `<Window>` only for a descriptor found in the `windows` prop, so it
   renders none — while `:1176` feeds the tab bar from the layout node instead. **Correct tabs above
   empty bodies is the exact signature of this ordering**, and matches boot #13's DOM byte for byte;
8. `flowEvalTick` fires 184× throughout, but contributions have not landed, so there is nothing
   addressable to evaluate and `invokeExtension` stays at 0. §2.3 and §2.2 are the same defect as §2.1.

`app.windowKinds` is fine and was briefly a suspect: the staged manifest declares all five editor
kinds (`procedural-main`, `procedural-preview`, `generation3d-generations`,
`generation3d-generate-form`, `generation3d-generate-preview`) and `sessionWindowInstances`
(`🛠️ShellHelpers/🟦️.tsx:4278`) returns one base instance per kind. Nothing is missing upstream.

Measured over the staged manifests in `🔌️plugin/📦️packages/🟦️typescript/dist/dev/🔌️plugin-modules`:

| Plugin | Contribution chars |

| `🧮️flow-extension-math` | 57 830 |
| `🏘️flow-extension-bim` | 56 372 |
| `🎨️flow-extension-draw` | 47 618 |
| `📚️flow-extension-dictionary` | 14 982 |
| `📃️flow-extension-list` | 14 968 |

The pushed 397 921 is that sum, less the receiver's own share. The procedural plugin is handed the

Incidentally this confirms the assembly lane's premise from the other direction: the manifest
declares apps for `generation2d` and `generation3d` only. There is **no assembly app at all**.

### 5.4 — The fix is architectural, in three separable parts

Ordered by leverage. The first two are the "optimize the architecture" case; the third is the
silence.

1. **Scope the payload to the receiver.** A plugin needs its own contributions plus those it can
   actually reference — for procedural that is brep, not bim/draw/math/dictionary/list/text/logic/
   primitive/note/puzzle. This alone is the difference between 398 KB and roughly 198 KB, and the
   right cut is by reachability from the document's flow graph, not by a hand-kept allowlist.
2. **Stop crossing bulk data through the 4 KiB string envelope.** The `.wit` data field is a `pack`.
   Contributions are the last bulk payload still travelling as a paged JSON *string*, which is
   exactly the mistake the extension-result path already corrected (see
   `📓️extension-result-realloc-2026-09-10.md`). Paging is a workaround for a transport that was
   never meant to carry 398 KB; the pack path carries it in one crossing. The 2.04 s cost *per
   4 KiB page* is itself the tell — a 4 KiB command cannot cost two seconds, so each page is
   dragging a full guest turn and its refresh fan-out (§2.5) behind it.
3. **Never let a data push gate the first paint.** The pending-window-UI dispatch must not sit
   downstream of the contributions push in the same function; windows should mount pending
   immediately and fill in as UI arrives. And `:9085`'s early return must go, so the
   `?? PENDING_WINDOW_UI_NODE` fallback 30 lines below does the job it was written for.

Laws owed: a window whose UI has not arrived renders its pending node, never an empty body; no
host→guest push may exceed one crossing per payload; contributions must land before the first
`flowEvalTick` is armed.

## 6 — Boot #14, long settle (260 s): the blockade ends in a guest OOM

The falsification test for §5. Probe `b14-longsettle`, settle 260 s — deliberately longer than the
≈ 202 s projected push — against the same 6018 serve. Capture:
`🗑️generated/probe-b14-longsettle-2026-09-10T19-57-24`.

**§5 is confirmed in effect and boot #13's headline finding is now wrong.** Boot #13's §1 reported
"no trap, no fault, no page error". That was only true of its 60-second window. With a longer
settle the boot reaches two states boot #13 never saw:

| Elapsed | State |
| --- | --- |
| 0–114 s | `bodies=0`, `canvases=0` throughout, tabs correct — the blockade, exactly as §5.2 predicts |
| **65.7 s** | `guest linear memory at 322371584 B — 60 % of the 536870912 B budget, past the 60 % install-peak ceiling` |
| **116.1 s** | **`rust_oom` → `process::abort` → `abort_internal` → `unreachable`.** Actor `procedural#1` traps |
| 121.0 s | "settled": **10 window UI nodes present** (`framework.window.proceduralMain`, `…proceduralPreview`, plus their controls/measures/engagement/utilityBar), **`canvases=3`** |
| — | **`meshes=0`**, and it can never be anything else: the actor died five seconds before the windows appeared |

So window UI and canvases **do** arrive — §2.1's "no canvas anywhere" and §2.2/§4's "the guest
delivers no window UI" were both artefacts of looking too early. The ordering defect is real and
costs about two minutes, but it is a *delay*, not the terminal failure. The terminal failure is that
the guest is dead by the time the UI exists.

### 6.1 — The fault is an out-of-memory abort, not a logic trap

The stack is unambiguous, innermost first:

```
std::alloc::rust_oom
  → std::process::abort
  → std::sys::pal::wasi::abort_internal
  → abort                                    // wasm-function[145688]
  → unreachable RuntimeError
```

`rust_oom` means the allocator asked for memory it could not get. Against a **536 870 912 B
(512 MiB)** budget the guest was already at **322 371 584 B (307 MiB, 60 %)** at 65.7 s — the
codebase's own diagnostic flags this as past the install-peak ceiling — and exhausted the rest over
the next 50 seconds. The worker error carries **`framesBytes=63345194`** (63.3 MB of retained
frames) at the moment of death.

This retires the whole "find the trap" line of work that ~20 lanes pursued: **there is a trap, it is
an OOM, and it is caused by the contributions push.** Session 1's realloc/abort instinct was right
about the mechanism and wrong about the trigger.

### 6.2 — One root cause, two amplifiers, both architectural

The two live lanes are aimed at exactly the two amplifiers, which is now confirmed as the right
split rather than a guess:

1. **Payload size — the window-bodies lane.** 398 KB of all-thirteen-plugins contributions, 98 % of
   it unaddressable by procedural, forced through a 4 KiB string envelope into 99 sequential guest
   turns. Scoping to brep plus procedural's own, and moving the payload onto the `pack` path so it
   crosses **once**, removes both the 202 s delay and ~99 of the 99 allocation events.
2. **Per-turn retention — the turn-cost lane.** wasm linear memory never shrinks, so anything
   retained per turn is monotonic. 307 MiB by 66 s and 63.3 MB of frames at death say each of those
   99 turns leaves several MB behind. Even after the payload is cut to one crossing, a per-turn leak
   of this size makes every user interaction a step toward the same abort.

Neither is fixable by tuning the 512 MiB budget: 512 MiB for one plugin boot is already far past
reasonable, and raising it only moves the abort later.

Law owed, in addition to §5's: the guest must survive an arbitrary number of host command turns
without monotonic growth, and a plugin must never be handed contributions it cannot address.

## 7 — Correction: `framesBytes=63345194` was a broken diagnostic, and it is now fixed

§6 quoted "63.3 MB of retained frames" from the worker error. **That number was inflated by its own
reporter and must not be used.** The OOM in §6.1 is unaffected — it comes from the guest's own
`rust_oom` stack and the 512 MiB budget diagnostic, not from `framesBytes`.

`replyError` in `🔌️plugin/📦️packages/🟦️typescript/🟦️.ts` sized `frames` like this:

```js
framesBytes = frames instanceof Uint8Array || frames instanceof ArrayBuffer ? frames.byteLength
  : frames !== undefined ? JSON.stringify(frames).length : undefined;
```

Its own comment claims it sizes the payload "WITHOUT ever JSON.stringify-ing it first unless it isn't
already a binary buffer". But a `turn`'s `events` is an **array** of wire buffers
(`runQueuedTurn(instanceId, events: readonly Uint8Array[])`), never a lone buffer, so the
`instanceof` test never matched and **every** report took the stringify path. `JSON.stringify` renders
a `Uint8Array` as `{"0":12,"1":255,…}`, which measured at **7.9×** per byte for a 1 KB buffer, **9.9×**
for 100 KB, and **11.8×** when the bytes are large values.

So the real payload on that turn was roughly **5.8–10.6 MB of wire bytes**, not 63 MB. Still large
for a single turn and still consistent with monotonic accumulation, but an order of magnitude
smaller, and the difference decides whether the events array or something else dominates the
512 MiB.

**Fixed** in the same file: an array whose members are all buffers is now summed by `byteLength`, so
the number reports wire bytes; a lone buffer still reports `byteLength`, and anything else still
falls back to stringify. Validated on six cases — lone buffer, array of three buffers, empty array,
`undefined`, a non-buffer object, and a mixed array that must still fall back — all pass, and the
module bundles (95 modules). The comment now records why the array path is the only correct one.

Method note for this ticket: **a diagnostic that has never been checked against a known input is
not evidence.** This one had a docstring asserting the exact property it did not have, and it sent
the memory hunt off by 10×.
