# Compiler image headroom reconciliation

Read-only audit; no write to the image, restart or cleanup.

Native image availability/🟦️.ts:12–25 executes diskutil info -plist on the supplied image mount and reads APFSContainerFree. At :8–10 the pure effective-availability function replaces the lower volume value whenever the container exceeds it by tolerance; it optionally caps the container number by hostFreeBytes. The difference itself is the entire staleness criterion: no mount-age test, volume-quota read, filesystem-write test or separate proof is performed. The log statement that the volume is stale is therefore an inference, not a verified diagnosis.

Component-pass/🟦️.ts:799 (current line at audit) passes volume statfs and container free but omits the optional host argument. Unit-cache/🧹️gc/🏦️headroom/🟦️.ts:125–144 discovers the image backing directory and does supply the host available bytes; this is an existing reference for the host-cap boundary. Even the capped heuristic does not prove the low volume reading is stale or rule out another capacity limit. A storage guard that substitutes this unverified value can miss low-volume/ENOSPC events.

Live read-only observation: diskutil info -plist .cache/b/r/m reports mount at that path, BusProtocol Disk Image, APFS container disk15, APFSContainerSize 103,079,215,104 bytes, APFSContainerFree 90,516,856,832 bytes. Node statfs at nearly the same time reported image available 536,760,320 bytes and host backing directory .cache/b/r available 44,887,097,344 bytes. Thus the 86 GiB figure is the image container, not host free, and exceeds this sampled host capacity. diskutil apfs list -plist disk15 independently shows disk15s1 CapacityQuota=0 and CapacityReserve=0 and CapacityFree 90,262,147,072 bytes; no APFS volume quota is configured in that snapshot. These non-atomic readings do not establish whether image statfs is stale or whether another quota/limitation exists.

The active log canonical-wgpu-reserve-after-resilience.log:18678–18693 reports volume availability falling as low as 0 MiB at :18689 while replacing it with 85,673 MiB container availability, then 75 MiB at :18693. Compare fresh statfs, diskutil info and diskutil apfs list on both mount and image-host directory to reproduce the evidence without mutation. Verify the actual backing file and identity before relying on a host cap; bounded write probes or remounts are not read-only and were not performed. The capacity correction should not certify available bytes above an unverified lower hard limit; guard tests should include lower statfs, absent host information, host below container, and finite volume quota.
