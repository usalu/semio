# Contributions Out Of The Crossing View State — the context is now a bounded projection again

Lane `view-state-carriage`, 2026-09-12, Opus execution agent. Repo MCP was down all session
(`-32602 invalid initialize params`); bookkeeping is on disk and no ticket was opened, closed or reopened.
Command outputs under `🗑️generated/view-state-carriage/`.

**Restage: RECOMMENDED, not required to observe the fix.** The Rust `ViewModel` lost a field, so a
served guest is out of contract parity until it is rebuilt — but the change only makes the host send
*less*, and every guest-side bound is permissive in that direction (`MAX_SURFACE_VIEW_CONTEXT_BYTES`
shrank 805 376 → 547 520 in source; the live guest still carries the older, larger bound and
therefore admits everything the new host produces). The runtime evidence in §5 was taken against the
live serve without a restage. **No wasm build was started and no dev server was restarted.**

---

## 1. What was wrong

`ResolvedPluginViewState` carried two long strings, `panelJson` and `contributionsJson`, each bounded
at 65 536 characters by the ONE language-neutral declaration
`🧰️framework/🔨️modules/🛂️manifest/🪟️view-context/🧬️schema/🔣️.json`. The React shell filled
`contributionsJson` on **every** refresh with the aggregated closure of every loaded plugin's topic
contributions — **248 635 characters**, measured live (§5). So every refresh built a context the
contract forbids, and the admission answered

```
[DEBUG] render failed [unknown] no-code Error: view context rejected at refresh-ui: view context: invalid panel data
    at admitCrossingViewContext (…/🔌️PluginRuntime/🟦️.tsx:935)
    at uiRefreshSurfaceEvents (…:940)
    at Object.refreshUi (…:1654)
```

(`🗑️generated/probe-interim-4/console.txt` line 13, 03:55) — every window body of the app became a
fault card.

### 1.1 The interim state I inherited, and why it was not the fix

By the time I started, a peer had **narrowed the gate** rather than the payload:
`admitCrossingViewContext` had been reduced to a required-FIELD check (`locale`/`terminology` are
strings) with a docstring that named the reason exactly — *"the shell's own `contributionsJson`
closure is measured at ~248 k characters against the view-context schema's 65 536-character
`maxLength`, a sized, separately-owned framework work package … Refusing it here would take that
package on by breaking every refresh."* That is this lane's package. The narrowed gate stopped the
throw and left the contract violated.

### 1.2 The finding that makes the fix trivial: **nobody reads it**

`ViewModel.contributions_json` has **no reader anywhere**. Contributions reach guests by exactly one
route, and it is not the view state:

| route | who |
|---|---|
| paged `setContributions` command run | `🛠️ShellHelpers/🧩️contributions/🟦️.ts` (host publisher) → `📔️registry` `sync_host_flow_extension_contributions_page` → `sync_host_flow_extension_contributions` → `parse_contributions` (the guest's own flow-extension registry) |
| `setContributions` config mutation | `config.contributions_json` on process3d / cad / forms / playbook / imperative / sourcing — a **config** field, never the view state |

Every `.contributions_json` read in the repo is one of those two. The forms plugin's own config module
still carries the historical note "*was read off `view_state.contributions_json`*" — that migration
already happened; only the producers were never cleaned up. The two remaining producers (React
`ShellHost`, wgpu Rust shell) were **write-only**.

The same is true of `panelJson`: no plugin reads `ViewModel.panel_json` and no plugin emits
`Effect::SetPanel` — it is host-local state on both ends (§3).

## 3. `panelJson` — measured, bounded, and one residual

**It cannot exceed 64 KiB in the React shell, and the one component that could grow without bound was
write-only and is now deleted.**

* `SpacePanelState` = `{ activePanelTab, programs, spawnedApps, activeSpawnedId }`, base64 pack.
* **`programs` is permanently empty** in the React shell — every one of the ten `buildSpacePanelState`
  call sites passes `[]` or forwards `currentPanel.programs`, and the app roster crosses as its own
  `setAppRegistrations` hint-push instead. Pinned by a law (§4).
* **The wgpu Rust shell was the one that actually filled it** — `SpacePanelState.workflows`, one
  `SpaceProgramEntry` per app of every loaded plugin, so it grew with the plugin closure. It was
  **never read back**: `spawn_plugin` recomputes the roster from `self.plugins` via
  `build_space_workflows()` wherever it is genuinely needed. Field removed; the remaining carriage is
  bounded by the open spawned instances. (The two shells' panel payloads were never interchangeable
  anyway — Rust wrote plain JSON keyed `workflows`, TypeScript writes a base64 pack keyed `programs`
  — which is itself proof that no guest ever parsed one.)
* No cap was raised.

**Residual, recorded not taken on.** The contract still *permits* a 64-entry `spawnedApps` roster of
256-character identifiers, which would exceed 65 536 characters; the shell never produces one, and my
law pins the realistic shape (§4). The clean end state is that `panelJson` leaves the crossing
contract entirely — no guest reads `ViewModel.panel_json` and no plugin emits `Effect::SetPanel`, so
it is host-local state on both ends and has no business in a host→guest projection. I did not take
that on: it moves the wgpu shell's session store, `TutorialUiSnapshot`, and the reactor's
`🪟️surface-view-state-routing` fixtures, which are live in the surface/tick lanes this session.
