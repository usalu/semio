## Measurement (instrumented relaunch, temporary `[DEBUG] [graph-owner-time]` per owner in the loader, removed again)

Per owner: total ms, hold ms (memo/checkpoint row verification), recover ms (checkpoint decode), rows, first stale rows, discovery phase ms.

- First 25 owners over 250 ms: 469 s total, hold 34 s (7 %), recover 3 s, discovery 432 s (92 %). Cold discovery of one owner costs 4-65 s on this host (`framework-os-dev` 61 s and 54 s, `dsl-derive-rs` 53 s, `workspace` 66 s); `framework-os-dev` is discovered twice because the admission closure observes an owner again whenever its target or input set grows (key = owner + targets + inputs). An isolated hold of the same rows takes milliseconds (`graph-slice-owner-hold-profile.ts`: 100 owners, 856 k row visits, 1.2 s), so verification is not the cost; the discovery of owners whose remembered rows went stale is.
- Why they were stale: in all 25 lines the first stale row of the remembered/checkpointed owner was `analysis ...📚️library/🔣️taxonomy.json`; `firstFailingRowV1` names it `replay-result` (the projection `{testDeliveryScopeDirectoryNames, generatorContracts}` changed; script `graph-slice-taxonomy-stale-why.ts`). `discoverBuildOwnerAdmissionFactsV1` read `readTaxonomyProjectionV1(taxonomy).generatorContracts` unconditionally, so EVERY owner (533 in the react inventory, 1435 in the wgpu one) recorded the whole projection as one `analysis` row. The file is the fleet's shared contract table, edited whenever a peer adds or changes a generator contract (mtime 00:58 during v14; 318 KB projection of a 1.4 MB file). One edit made every previously discovered owner stale, and a read takes hours, so every read met an edit before it finished.
- The other stale row seen, `global ["owner-registry", root, ["candidates"]]` (peers adding crates), only concerns the catalog owner and is already fine grained.

## Root cause

One shared input (the generator contracts of the taxonomy) was recorded by every owner as one whole-projection row. Any edit of any contract invalidated all remembered owner admissions at once (admission memo, owner checkpoint, in-process owner memos), an owner discovery is 10-60 s, so re-establishing a consistent view (about 533 x 2.3 discoveries) always took longer than the interval between peer edits. The project-record pass already solved this (`📜️contract-reads`: a tracked view records only what was read, as `global` rows); the owner admission pass did not use it.

## Fix

`🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/🕸️graph/📥️inference/🔎️owner-discovery/🟨️.mjs`:
- `ownerGeneratorContractsV1(workspaceRoot)` reads the projection unobserved (`observeDetachedSyncV1`, kept while the file keeps size and mtime) and hands the owner a tracked view (`trackGeneratorContractsV1`); every read (property, key listing, `in` probe) is recorded once per scope as a `global` row `owner-admission-generator-contracts`.
- `admissionGeneratorContractReadHoldsV1` + `registerGlobalFactV1(...)`: a recorded read holds while the same read has the same answer in the taxonomy as it is now (`generatorContractReadHoldsV1`). A separate name keeps the admission rows independent of the project-record rows, whose resolver answers from the contracts registered by a project environment.
- The unconditional `contractsPath=...readTaxonomyProjectionV1(...)` is replaced by `contracts=ownerGeneratorContractsV1(workspaceRoot)`.

Effect: an owner stays valid across a taxonomy edit unless the edit changes a contract it consulted (or the key listing it listed), exactly as for project records. The file is part of `graphAdmissionFormatUrlsV1`, so the admission format hash changes once and the first read after this change is cold (old memo and checkpoint are not used).

The temporary timing in `📥️load/🟦️.ts` is removed again (`grep -c DEBUG` = 0).

### 3. A registry follow restarts the attempt without the cross-pass memo

- Root cause: `createPassReuseV1()` (and its taken memo) was created inside `loadBuildGraphAttemptV1`, so every attempt of `settleOwnerRegistryV1` started with an empty memo; in-process owner memos survived, the taken memo did not.
- Fix: `settleOwnerRegistryV1` creates the read's taken memo once (`createReadTakenMemoV1`) and hands it to every attempt (`attempt(carried)`, type `RegistryCarryV1`); `loadBuildGraphV1` passes it as `options.takenMemo`; `createPassReuseV1({memo})` uses it (and calls `distrust?.()` on a carried memo, so trust marks of another agent's memo never cross an attempt). An owner is answered from it only while its job key and every row it consumed still hold, so a follow never reuses a stale owner. Note: the memo key contains the registry digest, so a follow that changes the digest still re-takes (this is the current key, not changed here).
- Test: `🧪️tests/🕸️graph/🧭️registry-follow` "the taken memo of the read is carried through every registry follow and is the read's own, never another read's".
