## Ruled out by measurement (scripts in this folder)

- Row verification is not slow: `graph-slice-hold-profile.ts` verifies 378k rows (all kinds) in under 4 s; `graph-slice-within-round-profile.ts` shows the within-round variant is as fast as the plain one; `graph-slice-owner-hold-profile.ts` verifies 633 real owners (1.2 M row visits, real analysis providers registered) in 5.2 s.
- Memo capacity: `ownerFactsMemoEntries` = 16384 is above the 1850 owners; the checkpoint ring has 256 slots.
- Stamp churn: only 711 of 23817 analysis rows and 226 of 13244 file rows changed in 3 h; restamping without content change is 0.

So the cost of a memo-hit attempt (about 15 min for 1850 owners) is NOT in the hold of rows. It is somewhere else in the per-owner path of `closeBuildOwnerAdmissionV1` / `observeOwnerFactsMemoizedV1` (closure walk, `recover` decode of checkpoint records with schema validation, GC pressure from the triple-held rows), or waiting (idle main thread) on an awaited port. This needs an instrumented run, not more reading.

## Recommended fix design (not implemented)

1. Do not restart the owner phase for a membership tail failure: keep the captured owner facts, name the vanished path from the error, evict only owner memos whose rows mention it (or its parent listing), re-run the owner closure (all hits) and re-hash membership. Cost of a retry drops from one attempt to seconds plus the touched owners.
2. Per-round diagnostics so the next measurement is conclusive: emit `[graph-retry]` for inventory retries with round, reason, path and elapsed; count per attempt memo hits, checkpoint recoveries and discoveries and the milliseconds spent in `hold`, `recover`, `observe`.
3. Stop holding three copies of the rows (lent memo observations are dropped once owners are seeded).

## Running React launch

It runs the old loader code; no change made here can reach it. It is not hung: it will either seal or fail after the retry budget (about 75 min from 00:21). Restarting it loses the in-process owner memos, but the on-disk checkpoint (67 packs) lets a restart recover owners without discovery. Recommendation: let it run; do not restart until the instrumented retry reason (item 2) exists.

## Scope blow-up fixed (fourth pass)

Root cause (found by a synthetic reproduction, not by reading): the plain `Map` scopes of `👁️observation/🟨️.mjs` (settle round, source capture, inference, dependency observation) were keyed by the row-table number of a row. The row table empties itself at 16 M characters (`rowStoreCharacters`) and never reuses numbers, so on a read of ~200 k rows of ~130 characters it empties several times per attempt. A memo hit re-merges the rows of its owner: every row whose number moved is a second entry of the same content in each enclosing scope. The scopes therefore held a row once per table generation and per enclosing scope (observed: 4.57 M entries for 209 k distinct rows), and the captured fact list handed on contained the same fact repeatedly. Each memo hit also copied every row of the owner into every enclosing scope.

Fix (`👁️observation/🟨️.mjs`): new `LayeredScopeV1` (extends `DetachedScopeV1`) replaces the plain Maps of `settleObservedComputationV1`, `captureObservedSourceInputsV1`, `observeInferenceComputationV1` and `observeDependencies`. A memo hit keeps the owner's stored row array by reference (one pointer per scope); a finished child scope hands its arrays to the parent by reference (`retainScopeV1`); the distinct rows are taken once, by content (`distinctObservationRowsV1`, independent of row numbers), when the scope is read, cached until the scope changes. Semantics are unchanged: first occurrence order, contradictory answers for one path kept.

Benchmark/test: `👁️observation/🧪️tests/🧺️scope-rows/🟦️.ts` (env `SCOPE_ROWS_OWNERS`, `SCOPE_ROWS_PER_OWNER`, `SCOPE_ROWS_SHARED_PERCENT`, `SCOPE_ROWS_ATTEMPTS`; defaults 1900 owners x 240 rows, 55 % shared, 4 attempts, 3 enclosing captures). Oracle: an independent `Set` of row JSON texts of the fixture.

| 1900 owners, 205,332 distinct rows | before | after |
| --- | --- | --- |
| entries in the enclosing scopes / facts handed on | 821,724 (4.0x, duplicate facts) | 205,332 (1.0x, exact) |
| wall time of the read | 2.2 s | 0.43 s |
| oracle test (observed set == union, no duplicates) | fails (205,464 vs 205,332) | passes |

Heap after GC at the end of the read was within noise in this process (the fixture rows dominate); the scope entry count is the measured quantity.

Tests run (`repo tools exec --light bun -- test ./<file>`): new scope-rows 2/2; repair-rounds 19/19, inventory 10/10, admission-memo 10/10, owner-checkpoint 7/7, registry-follow 8/8, retain-rows 3/3, stale-facts 2/2, candidate 2/2, owner-claims 2/2, row-table 12/12, read-parent 3/3, look-scope 3/3, source-names 10/10, hollow 4/4, catalog-producer 2/2, observed-catalog 2/2, adopt-registry 3/3. ## One broken import must not kill an unrelated slice (fifth pass)

Root cause: the process-wide failure handler and `worker.ts` classify a failure with `isHalfEditedModuleLoadV1` / `staleImplementationOfV1` (`🧷️format-stamps/🟨️.mjs`): any `ResolveMessage`, `BuildMessage` or `Export named ...` failure, also one found only down the `cause` chain, is "a peer is editing the implementation" and ends the worker with exit 75. That is right for a module of the Build tooling and wrong for a module of a project's own source. A source of owner X that imports a file a peer just moved (the table-column-model test with one `../` too few; the same text, `Cannot find module '<path>'`) reached that class unchanged, so the pool restarted the slice worker three times with the same text and refused the whole read ("ended 3 times in a row with exit code 75"), whatever slice was asked. Nothing turned the failure into a fact about owner X: only the `require.resolve` path of the command walk did (`unresolvedSourceImportV1` -> `BUILD_SOURCE_UNPARSEABLE`), and its wrapper still carried the `ResolveMessage` as `cause`, which the classifier walked into.

Fix:
- `🕸️graph/📥️inference/📦️project-nodes/🚧️source-failure/🟨️.mjs` (new): `ownerSourceFailureV1` turns a module-load failure whose importing file (or missing module) lies in the workspace and outside the Build library into the existing owner-level withheld failure `BUILD_SOURCE_UNPARSEABLE` (source = the importing file with its sha256, else the owner's project file), and records the miss (`observedRequireResolve`) in the observation of the owner, so the withheld owner is checked again exactly when the file appears. A failure of the library tooling, one that names no workspace file, and any other error answer `undefined` and stay what they were (restart). `project-nodes/🟨️.mjs` applies it in `inferProjectBodyTrackedV1`, in the late closure-reference catch and in `refsFailureV1` (farm children); the existing `unavailable` path then fails with the owner-scoped source and reason only when that owner is in the requested closure, and an unrelated owner no longer matters. A freshly modified source still rethrows (`unavailableProjectV1`), so settlement waits for the peer's edit.
- `🧷️format-stamps`: `staleImplementationOfV1` no longer descends into an error with an owner code (`loadFailure.ownerCodes` = `BUILD_SOURCE_UNPARSEABLE`, schema-first in `🧬️schema/🔣️.json`, python oracle and a new vector updated), so no wrapper of a withheld owner can restart a process.
- Tooling pin: the slice worker already opts into the process-wide `withImplementationPinV1`, which covered Source reads and self-checks only. `loadCurrentImplementationV1` (`🕸️graph/📥️inference/🟨️.mjs`) re-resolved the revision of the tree on disk and imported a fresh component graph mid-run, i.e. whatever a peer had half moved; pinned, it now keeps the component graph the run loaded. A lazy `import()` of a library module that a peer moved after the worker started is still a restart (the next worker loads the finished edit); a real snapshot of the whole library tree is not done.

Tests (`repo tools exec --light bun -- test ./<file>`): `📦️project-nodes/🚧️source-failure/🧪️tests/🟦️.ts` 3/3 (real Bun loader errors: owner source named with an independently computed sha256 and no stale classification; tooling/unattributed/ordinary stay; the miss is a recorded observation that stops holding when the module appears); `🕸️graph/📥️inference/🧪️tests/📌️pinned-implementation/🟦️.ts` 2/2; `🧷️format-stamps` implementation-edit 10/10 (new vector), format-stamps 16/16, dangling-store 6/6; withheld-rows 6/6, read-parent 4/4, repair-rounds and slice-worker-scope re-run.

## Seventh pass: units settle against their own snapshot (churn no longer holds the read hostage)

Root cause: `settleObservedComputationV1` took the whole round as one snapshot. Owner A answered from a memo whose rows were verified at t1, owner B was observed anew at t2; when any shared path changed between them the round contained the path in two states and the whole closure ran again (up to 64 times, each time with the trust of the loader reset, so every owner was verified again). With 50 machines editing, some path flips during almost every ~2 min round.

Design (`👁️observation/🟨️.mjs`, `🕸️graph/📥️load/🟦️.ts`):
- Units: the settle capture is a `SettlementScopeV1` that lists the row sets of the units merged into it: a memo hit (`retainObservedRowsV1`, the stored array) and a fresh owner observation (`captureObservedSourceInputsV1`, its own capture). No new API for the loader; the two events that already merge an owner now also name it.
- `settlementConflictsV1`: a path read in two states by different units is churn, not a contradiction: every unit holds a consistent snapshot of its own inputs, the rows of both states stay recorded (the seal keeps the observed content identity of every input, a later read finds the older row stale and re-checks only that owner through the owner memo hold). Only a contradiction inside one unit (or in what the settled computation read itself) repeats the round. A round without units behaves as before (one unit).
- `onRound` now receives `paths` (every path that was contested) and, for a tolerated round, `settled:true`. The loader writes `[graph-settle] {version,round,settled,paths,first[5],evicted,text:{en,de}}` (texts in `🧲️membership-follow` schema). A repeat round no longer resets the trust: it forgets only the owner memos whose rows name the contested paths (`evictOwnerFactsReferencingV1`), so the repeat re-observes those owners and answers every other owner from its trusted entry. A repeat without named paths (failure) keeps the old full reset.

Tests (`repo tools exec --light bun -- test ./<file>`), `🕸️graph/📥️load/🧪️tests/🌀️settle-churn/🟦️.ts` 4/4, real settle + real `observeOwnerFactsMemoizedV1` + real `observedFs` on a temp tree, independent model (declared inputs, content each owner saw, content now on disk):
1. one unrelated file flips on every discovery: settles in 1 round (`settled:true`, path named), every owner discovered once, the sealed rows hold both states by independently computed sha256; the next read re-observes exactly the owners the model calls stale (the two readers), the one after exactly the edited owner plus the flipping reader.
2. an owner's own input flips inside its observation: 1 repeat round naming that path, that owner observed twice, all others once, the sealed row is the last state only.
3. a never-settling contradiction inside one owner: refused after the limit (4) with that owner observed 4 times and every other owner once.
4. bilingual line.

(c) Recycling the slice worker between passes (the clean worker was 14x faster per owner) is the cheaper first measure and needs the pool to restart a worker at a pass boundary when its heap passes ~2 GB.

## Thirteenth pass: a repair pass takes again only the owners that changed, and a heavy worker hands the read to a fresh one at the pass boundary

Two measured wins of the twelfth pass, implemented. Tests are in the list below; the live effect is a projection from the twelfth-pass numbers, not a live measurement (the replica is edited by peers, and a 1310-owner read takes more than an hour).

### 1. Cross-pass reuse (the taken memo)

Design (schema-free, no new policy number: the memo is exact, so nothing needs a threshold):
- `🕸️graph/📥️inference/📦️project-nodes/♻️taken-memo/🟨️.mjs` (+ `.d.mts`): `createTakenMemoV1({holds,retain})`. An entry is the owner's answer as JSON text (a pass never shares an object another pass may have changed), the key of its job, and the rows its stored record consumed (`projectInferenceObservationsV1(cachePath)`, kept by reference). `replay(wanted)` answers an owner only while (1) the key is equal and (2) every recorded row still holds (`observationRowsHoldV1`, shared per validation round); the rows are retained into the running capture exactly as a look retains them, so the final `facts-hold` of the pass verifies them again. `evictReferencing(paths)` forgets the owners whose rows name a path or the listing of its parent directory (`createPathRowMatcherV1`, the same rule as `evictOwnerFactsReferencingV1`, which I did not touch because five test harnesses extract that function by name).
- Key of a job (`project-nodes/🟨️.mjs`, `memoKeyOf`): sha256 of the owner's job JSON, its admission (`ownerAdmissionOfV1`) and a per-pass context digest `v8.serialize([registryDigest, commandRevision, late, projectsByRoot, componentRoots, contracts, registry])` (the inputs the project farm already keys its hub on). A project added, removed or renamed anywhere therefore changes every key (a full re-take), a changed `project.json` only its own.
- Wiring: `emojiProjectJsonNodesBodyV1` remembers an owner at the end of `inferProject` (after its `targets` merge, never an unavailable owner, never when the record has no rows) and, before the take pass, `preloadTaken()` (inside the `try` of `runTakeBesideInferV1`, so an abort cleans up) puts the replayed owners into `taken`, `ledger` ("present") and `counted`; the take loop, `resolveOwners`, the farm, `waitHeavy` and `sweepOrphans` already skip `taken`. One line is logged (`[owners] ... answered from the previous pass ... / ... aus dem vorigen Durchgang ...`) and `reuse` stats are part of the `owners` slice-report source. Disabled in the late-closure mode (`onOwnerObservations` present: the part read), which would also need `derived` rows.
- Loader (`📥️load/♻️pass-reuse/🟦️.ts`, `createPassReuseV1`): one memo per attempt, handed through `discoverBuildGraphV1(..., takenMemo)` into the nodes context (not into `options`, which is hashed into the cache key). At each pass boundary `reuse.boundary({round,moved})` forgets the owners named by the stale paths of the previous round (`stale` rows of `buildGraphSourceFactsHoldV1(collect)`, plus `followedPathsV1` for a failed pass) and logs `[graph-reuse] {version,pass,round,moved,evicted,entries,heap,recycles,text:{en,de}}`.
- Finding that shaped the design: `observationsHold` stops at the first stale row (`stale=true` ends the workers), so the stale paths of a round are a partial list (a few rows, not all). Evicting by name alone would hand a stale owner to the next pass unverified. The named eviction is therefore only an accelerator; exactness comes from the row check in `replay`, which is the question a full look asks. Semantics equal a full re-take except for what a look also checks and the replay skips: the presence of the stored record's references in the store (`reusable`, 86 % of the look wall in the twelfth pass). A garbage collection of the store inside one read would be seen by the final seal, as before.

### 2. Worker recycling at the pass boundary

Existing mechanism reused: the pool already restarts a worker with a new environment on `plan-cut` (`createSlicePoolV1`, `restarts--; continue`, progress decision shown to the client by key `host-slice-owners-<key>`); the `handover` suite concerns another thing (custody handover of a read to current code: `SEMIO_STALE_IMPLEMENTATION`, exit 75, counted as a restart with a same-cause limit), which would count every recycle as a failing restart, so I did not use it.
- Policy (schema-first): `🧠️memory/♻️recycle/🧬️schema/🔣️.json` (+ `🟨️.mjs`, `🟨️.d.mts`): `heapMegabytes` 2048, `maximumRecycles` 3, the two environment names; every description is bilingual (`EN: ... DE: ...`). The pool puts the threshold (and, after a handover, the counters) into the worker environment; a run without it (direct `repo run`, tests) never recycles.
- Worker side: `reuse.boundary` measures the live heap (after `Bun.gc(true)`), and above the threshold throws `SEMIO_SLICE_RECYCLE` with `{recycles, round, passes, owners, heapMegabytes}` and a bilingual text. `👷️worker.ts` turns it into the message `{type:"recycle",state}` (found through the cause chain) instead of `error`.
- Pool side (`👷️slice-pool/🟨️.mjs`): the message finishes the worker (terminated and reaped as for a cut) with `code:"slice-recycle"`; `execute` starts the next worker with the carried state in its environment, does not count it as a restart or a failure (`restarts--`), tells the client with the decision `recycled` (EN/DE texts `host-slice-owners-recycled` in `🏡️resident/🧬️schema/🔣️.json`), and stops handing over after `maximumRecycles` (a read whose live set stays large still finishes in its last worker).
- What travels: the counters, notably `round`, so the repair budget (`repairRounds` = 4) is not renewed by a handover. What does not travel: the taken memo itself. Its rows are the heap that is being shed, and a fresh worker takes 1273 of 1310 owners from the owner records on disk in about 100 s (twelfth pass); the memo is rebuilt by that take. Owner checkpoints and records are already on disk, so nothing the read finished is lost.

### Numbers

Benchmark `graph-slice-pass-reuse-bench.ts` (this folder; real files, 1310 owners x 31 rows, five passes, three edited files between passes, warm file cache, one process; wall time of passes 2-5):

| pass model | pass 2 | pass 3 | pass 4 | pass 5 | total | CPU | owners taken per pass |
| --- | --- | --- | --- | --- | --- | --- | --- |
| before: every owner observed afresh | 615 ms | 415 ms | 440 ms | 472 ms | 1942 ms | 1898 ms | 1310 |
| after: taken memo (replay + stale owners) | 383 ms | 304 ms | 325 ms | 329 ms | 1341 ms | 1354 ms | 3 |
| lower bound: all rows verified, nothing stale | 320 ms | 268 ms | 286 ms | 310 ms | 1184 ms | 1139 ms | 0 |

-31 % wall, -29 % CPU, 1310 -> 3 owners taken per repair pass. This is the cache layer only: it cannot show the live saving, which is the look machinery the memo skips (the twelfth pass measured 7516 lookups for 1310 owners, observe 7826 s of which `lookup.reusable` 6749 s, 86 %; whole-pass re-takes of ~1250 owners in passes 2..5). Projection, not a measurement: passes 2 and later paid about four fifths of that observe time (~6000 s) for a handful of changed owners; with the memo they pay the row check above (seconds on a quiet host, bounded by the same file system contention as the seal's own verification) plus the take of the changed owners.
Recycling: not measurable offline (it is the GC and swap behaviour of a 3 GB heap). The measured inputs are the twelfth pass's: 1273 of 1310 owners in ~100 s in a fresh worker against ~1400 s for a pass in the long-lived 9 GB worker; one handover costs one such take (~100 s) and is paid only when the live heap is above 2 GiB at a boundary, at most three times per read.

### Not done / limits
- The memo is exact per owner but does not avoid the row check of every remembered owner at each pass; if that check turns out to dominate on the live host, the next step is a per-pass verdict map shared with the final `facts-hold` (the rows are the same objects).
- The memo is disabled in the late-closure (part) mode.
- The live effect of both changes is unmeasured; the first run after this pass should read the `[graph-reuse]` and `[owners] ... answered from the previous pass` lines and the `reuse` block of the slice report (`remembered`, `reused`, `evictedChanged`, `evictedKey`, `evictedNamed`).
- The running worker holds the old module; the changes apply to the next read.
