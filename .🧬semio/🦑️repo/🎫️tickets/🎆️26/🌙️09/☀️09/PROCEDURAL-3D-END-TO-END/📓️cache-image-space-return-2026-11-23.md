# Cache Images Give Space Back To The Host While Mounted

## Problem
The host data volume fills (11-20 GiB free of 228 GiB) and component builds die at the end with "The disk is full". The fixed cache images grow to their high-water mark and never shrink: `.cache/b/r/fixed.dmg` holds 44.5 GiB of host blocks for 19.7 GiB used inside, `d` holds 27.6 GiB for 17.5 GiB (measured read-only, 22:20). About 35 GiB is returnable on those two images alone.

## 1. What the repo uses (read from the code and the kernel inventory)
- Format: `hdiutil create -format UDIF` (`🍎️image/🤫️silence`), then `hdiutil resize` to the declared size. That is a flat read/write image (`image-type: read/write disk image`, no sparse bundle, no sparse image, no ASIF). The backing `fixed.dmg` is one sparse file on the host APFS volume; its apparent size is the declared size (r: 96 GiB), its allocation is what the host pays.
- Inside: Case-sensitive APFS, one volume `semio` in one container (`image/🧬️schema` `ImageProtocol.filesystem`).
- Attach: `diskutil image attach --nobrowse --mountOptions owners --mountPoint <dir>/m` (`ImageProtocol.attachProgram`). `hdiutil info` shows the live images as `framework name: DiskImages2`, which is that stack (a legacy `hdiutil attach` shows an icon path and a different image type). So the live images already use the UNMAP-capable stack.
- Existing return path: `reclaimNativeImageV1` detaches and re-attaches an idle image. It needs the exclusive lease `native-fixed-image:<dir>` nonwaiting, so it ends as `lease-timeout` whenever any build runs.

## 2. Measurements (scratch images under `🗑️generated/scratch-image`, 0.8-1.8 GiB, all deleted; scripts `image-space-return-*.sh` in the ticket folder)
Procedure: write 1 GiB of random bytes, `sync`, delete, `sync`, read the host allocation (`st_blocks*512`) of the backing.

| Case | created | after write | after delete (mounted, +15 s) | after the action |
|---|---|---|---|---|
| RAW, `hdiutil attach` | 2 MiB | 1026 | 1026 | detach 1026, re-attach+detach 1026: never returns |
| RAW, `diskutil image attach` | 2 | 1026 | 1026 | detach 2 |
| RAW, diskutil, **unmount of the APFS volume only** (image stays attached) | 2 | 1026 | 1026 | 2.4 in 3 s, remount fine |
| ASIF, diskutil | 12 | 1034 | 1034 | detach 1034, next attach+detach 13; volume unmount 13.6 |
| UDSB sparse bundle, diskutil, volume unmount | | 1041 | 1041 | 209.6 MiB left, remount failed (`Failed to find disk`): rejected |
| sparse bundle, hdiutil | 20 | 1042 | 1041 | `hdiutil compact` while attached: `Resource temporarily unavailable`; after detach 1040; compact detached 16 |
| RAW, diskutil: wait 90 s, `mount -u -o ro`, `purge`, `diskutil apfs defragment`, `fsck_apfs -n` | | | 1026 | no effect |
| **RAW, diskutil: add or mount and unmount a SIBLING APFS volume of the same container, main volume stays mounted** | | 1030 | 1030 | **6.3-6.6 MiB within 1-3 s**, every round |
| same sibling trick, image attached through `hdiutil attach` | | 1030 | 1030 | nothing (backing even grew to 1695 on the next churn) |

Findings:
- APFS trims freed extents into the image stack, but the container only flushes that trim when a volume of the container unmounts (or the image detaches). Nothing flushes it while all volumes stay mounted.
- A second small APFS volume in the same container ("sibling", `semio-trim`) can be mounted and unmounted at will while the busy main volume is untouched. That unmount flushes the container trim, so the freed blocks return to the host as holes in the backing file. This is the only in-place trigger found.
- Safety under load (`image-space-return-stress.sh`): a loop writing and rotating 4 MiB checksummed files, an open file descriptor, a shell working directory inside the volume, four rounds of 512 MiB write and delete each followed by a kick. Backing stayed at 167-219 MiB (live data about 160 MiB), every file and the open writer intact, `fsck_apfs -n` after the final unmount: "appears to be OK". The test in the repo repeats a reduced version (open descriptor, kept file hash, mount table, two kicks).
- A container below 512 MiB refuses a second volume (`-69493`); the live images are 10-100 GiB.
- The kick needs no lease holder to drain: open files, cwd and writers do not matter because the main volume is never unmounted.
- Rejected: sparse bundle/sparse image/ASIF (no better in place, compact only offline, partial or format-new), a hole-punching helper on the backing from outside (races the inner allocator and could destroy data just allocated), forced unmount of the main volume (kills builds).

## 3. Implementation
Schema first: `🍎️image/👟️kick/🧬️schema/🔣️.json` (the image policy JSON for this feature): settle polls, interval, command bound, per-platform mechanism with every program and argument, the corpus schema.

- `🍎️image/👟️kick/🟦️.ts` (one interface, three platforms)
  - `nativeImageKickMechanismV1(platform)`: `sibling-volume` (macOS), `fstrim-mounted` (Linux), `offline-only` (Windows), `null` otherwise.
  - `nativeImageKickDueV1`: the existing reclaim rule (floor, ratio, tight host relief) plus a minimum interval (60 s) between kicks.
  - `kickNativeImageV1(port, hooks)`: ensure, kick, settle on the allocation, always dispose; cancellation between steps and polls, failures of kick and disposal both kept.
  - macOS port: `diskutil info -plist` names the container; `hdiutil info -plist` must list that container among the image's own entities (refuses a host container, so no volume is ever added to the host APFS); `diskutil apfs list/addVolume -nomount` creates the sibling online once; `diskutil mount nobrowse -mountPoint <scratch>` and `diskutil unmount` kick; disposal unmounts (force as last step) and removes the scratch directory.
  - Linux port: `fstrim --verbose <mount>` on the loop-backed filesystem mounted with `discard` (holes via `FALLOC_FL_PUNCH_HOLE`). Needs the privilege `fstrim` needs (root or CAP_SYS_ADMIN in a devcontainer).
  - Windows: no port. A dynamic VHDX compacts only while dismounted or mounted read-only (`Optimize-VHD -Mode Full`), so the platform stays on the existing exclusive cycle (`createNativeImageWindowsReclaimPortV1`), i.e. the drain window.
  - Package entry: `📦️packages/🟦️typescript/…/🍎️image/👟️kick/🟦️.ts`.
- `♻️reset/🟦️.ts` (`repo cache gc`, the pressure planner): `reclaimImageIfQuiescentV1` first tries `kickRepositoryImageOnlineV1` under a nonwaiting SHARED lease (never overlaps an exclusive detach cycle, never waits for builds). A kick that reduced the allocation returns `reclaimed`; anything else falls through to the old exclusive cycle. No more `lease-timeout` skip for macOS/Linux while builds run.
- `⚡️caching/🦀️cargo/🗃️unit-cache/🧹️gc/♻️auto-reclaim/🟦️.ts`: after every collection the automatic reclaim runs the kick (`defaultKick`, best effort, cancellable, injectable `kick`). Without it the honest available space, which is capped by the host free bytes, never rose after the collectors deleted units.
- Tests
  - `👟️kick/🧪️tests`: 11 pass. Corpus `🔣️.json` (due cases, exact command scripts for macOS with and without the sibling, Linux) checked against the schema and against the independent Python oracle `🐍️.py`; settle, cancellation, failure aggregation, refusal of a foreign container, forced unmount fallback; real image test (macOS only): attached with diskutil, 512 MiB written and deleted with an open descriptor, kick returns more than 400 MiB, descriptor still writable, file hash intact, no scratch mount left, second kick stable; allocation cross-checked with Python `os.stat`.
  - `♻️reclaim` tests of the image-slack module: 14 pass (new case: online kick means zero exclusive leases and zero detaches).
  - auto-reclaim tests: 13 pass (new: kick after collect, failing kick never fails the reclaim, cancellation propagates).
  - Not run here: Linux (`fstrim`, scripted only) and Windows (no port, `offline-only` asserted).

## 4. Early admission for component builds
Where it fails today: `disk.full` is the typed refusal of an `ENOSPC` (`🏗️build/💽️disk`). Admission before a build already existed only as a used-share check of the cache partition with a fixed 4 GiB growth for Cargo (`🌡️host-capacity/💽️disk`), and per batch inside the driver (`runPass`), measured after the plan is known but only when that batch starts. Nothing compared the whole plan with the host volume that holds the image backing.
- Pure rule in `🏗️build/💽️disk/🟦️.ts`: `diskAdmissionNeedBytesV1` and `diskAdmissionShortfallBytesV1`. Need = max(largest batch, planned footprint x plan share) less the credited share of the image slack (blocks the image already holds but does not use), plus the reserve, against the free bytes of the host partition that holds the backing file. Policy numbers live in the component-pass schema (`Policy.upfrontPlanShareBasisPoints` 5000, `upfrontSlackCreditBasisPoints` 5000): conservative defaults, not measured, tune them from the footprint history.
- `admitNativeBuildUpfrontV1` (component pass): runs right after the batches are predicted and before the first pass. A shortfall first asks the cache collector (`reclaimStorage`, which now kicks too), measures again and only then refuses with `disk.admission-insufficient`, bilingual (en, de), naming partition, free, need, plan, credit, reserve, what is missing and `repo cache cas gc`. Nothing was started, so no hour is lost.
- Tests: corpus of 7 cases with the independent Python oracle `🐍️admission.py` and exact en/de refusal texts (`💽️disk/🧪️tests`, 9 pass); `🧩️component-pass/🧪️tests/🚪️upfront` (1 pass: roomy host admits, shortfall offered to the collector once, still short is refused with the German and English text, cancellation honored).
- Known gap: the existing driver measures the host share only on macOS (`hostBytes` is Infinity elsewhere). The upfront rule measures the backing directory on every platform, the per batch gate should follow.

## 5. Safe switchover (nothing was applied to live images)
The kick does not need an idle image. Two things must hold; the code already refuses otherwise.
1. Confirm the stack: `hdiutil info | grep -B14 '<image>'` shows `framework name: DiskImages2` for every image to be kicked (r and d do). An image attached by the legacy stack (icon path, `image-type: read/write`) never unmaps: detach and re-attach it once through `repo` (which attaches through diskutil) while it is idle.
2. Confirm the container is at least 512 MiB (true for all).
Then, in order, preferably while the compiler image is quiet but it is not required:
1. Let the tree with this change replicate to the machine.
2. `repo cache gc` once: the kick adds the sibling volume `semio-trim` online (`diskutil apfs addVolume ... -nomount`, a metadata operation of a few MiB), mounts and unmounts it, and the allocation of `r` drops from 44.5 GiB toward its used size plus metadata (about 20-22 GiB expected), `d` from 27.6 toward 18 GiB. Watch with `stat -f %b .cache/b/r/fixed.dmg`.
3. Verify: `diskutil apfs list` shows two volumes in each container, `mount` shows no `semio-kick-` mount, builds still run.
4. From then on every `repo cache gc` and every automatic Rust reclaim kicks. Rollback is `diskutil apfs deleteVolume <semio-trim device>` (online) plus reverting the code.
5. Idle window only (optional): run one full `fsck_apfs -n` of the container after a detach for assurance. The stress test did, clean.
Windows hosts and any host where the kick fails keep the old behavior: the exclusive detach/attach (macOS) or `Optimize-VHD` cycle, which needs the image to be drained; use the new upfront admission so builds fail early there instead of at their end.

## Follow-up: why the live gc returned nothing (diagnosis and fix, 2026-11-23 22:40-23:20)

### Answers
1. Did the kick run? Yes, and before the exclusive cycle. The old code counted any decrease as "reclaimed", so a 0.01 GiB drop printed "Reclaimed image rust: 48.54 GiB -> 48.53 GiB" and hid that nothing was returned. It ran after the collection phase (collection freed 0 B: "within budget"), so there was nothing fresh to trim either. Kick lines were missing because the kick printed nothing.
2. Is the space really free? Yes. `diskutil apfs list`: r container 103.08 GB with 9.8-11.3 GB in use, d 38.65 GB with 18.4 GB in use. `diskutil apfs listSnapshots` shows no snapshots on either volume, `tmutil` finds none, no purgeable pool inside a non-boot container, and the allocation stays far above use (r 40-50 GiB held for 10-20 GiB used).
3. Does a manual sibling mount and unmount on live r return space? No. Test on the sibling `semio-trim` only: wrote 1 GiB into it, deleted it, unmounted: allocation grew by 1 GiB and stayed (38935 -> 40113 MiB, the rest is builds growing the file); a plain mount+unmount: 78086368 -> 78086368 blocks. The same test on live d returned the blob and some stale blocks once (28174 -> 26978 MiB), but a later canary on d returned 0 B.

### Root cause (measured on scratch images)
DiskImages2 on this macOS (27.2.1) forwards APFS trim to the backing file only for containers up to 2^35 bytes (32 GiB). Same test (1 GiB written and deleted, sibling kick), declared RAW size in bytes:
- 20e9, 23e9, 26e9, 30e9, 32e9, 34e9, 34 359 738 368 (2^35): returns to 2 MiB.
- 35 433 480 192, 36e9, 37e9, 38e9, 44e9, 50e9, 60e9: nothing returns, 1026 MiB stay. Free host space (20-27 GiB) and whether the host is nearly full at run time make no difference (30 GB image with 5 GiB filler: still works).
- Not only in place: a 50e9 image whose freed blocks were never returned still held them after main volume unmount, detach and re-attach through diskutil (the "attach trims everything" behaviour that works on small images). So the existing offline cycle cannot return space of r either.
- A 100e9 ASIF image: no return in place, none after detach.
- The sibling trick and the attach cycle work on every image below the limit, including stale blocks written by the legacy `hdiutil` stack.
r (96 GiB) is above the limit. d (36 GiB) is slightly above: its early success was probably the first 32 GiB of its address range; the later canary returned 0 B. Hypothesis, not proven: blocks above 2^35 are never unmapped.

### Fix in code
- The kick now carries a canary: the sibling volume gets a 256 MiB file that is written, fsynced, deleted and unmounted; the sum of the allocation decreases afterwards (builds only add increases, which are ignored, so busy images are measured fairly) must reach 50 % of it. `kickNativeImageV1` returns `effective`, `canaryBytes`, `canaryReturnedBytes`. The canary is skipped when the sibling is not a real mount (never writes onto the host) or when the host has less than 8x its size free.
- An ineffective kick is no longer reported as reclaimed. `repo cache gc` prints a bilingual line naming the image, the returned bytes and the 32 GiB limit, then falls through to the exclusive cycle as before; the automatic Rust reclaim reports the same once per image.
- Tests (kick 12 pass): pure return-sum function (growing builds do not hide a return), canary threshold, both languages of the message, `effective` in the real-image test, corpus unchanged. auto-reclaim 13 and image-slack reclaim 14 still pass.

### Re-run of `repo cache gc --lang=en` on the live tree (builds running, so counts also rise by their writes)
- r blocks 88 822 320 -> 96 675 680 (run 2) and 97 847 528 -> 81 973 760 (run 3, the drop is a build finishing, not the kick); d 55 252 592 -> 55 771 864 -> 56 296 160. The new line appears for r and d ("11.09 MiB of 256 MiB returned" / "0 B of 256 MiB returned"). Nothing is returned by the kick on these two images and none ever will be at their current size.
- The "graph" image (4.31 GiB) is below the limit and the kick works there but it holds almost no slack.

### What this means for the switchover (replaces step 2 of the plan above)
The sibling-volume kick is only useful for images of at most 32 GiB. To return space of the compiler image the container must stay below 2^35 bytes. Options, in order of preference:
1. Split `rust` into several images of at most 32 GiB each, with the cache layout sharding by lane or by hash (the existing partition table already names one directory per image). All trim machinery is then in place and measured.
2. Shrink `r` to at most 32 GiB (its used size is 10-20 GiB; `/System/Library/Filesystems/apfs.fs/Contents/Resources/apfs_shrink_diskimage -q` reports the minimal size, offline only) and rely on the existing reclaim ledger (soft 15 %, target 25 % of the partition) with the new admission, accepting a smaller budget.
3. Keep 96 GiB and accept the high-water growth: then only the upfront admission (section 4) protects builds, and one offline recreate of the image (retire and rebuild, recomputable contents) returns everything when idle.
`d` (36 GiB) should be reduced to 32 GiB the same way.

## Sharded images (2026-11-24)

### 0. Finding first: the sibling volume breaks the next attach (fixed in the kick, live images still carry it)
`diskutil image attach --mountPoint` works only for an image with a single mountable entity (its own help text). The kick of the sections above left its sibling volume `semio-trim` in the container for good. Measured on a scratch image: attach, add the sibling, detach, attach again at the mount point gives `Error: Failed to mount the volume`. `ImageProtocol.attachArguments` always passes `--mountPoint`, so every image that carries the sibling cannot be attached again after any detach (the exclusive reclaim cycle, a retirement, a reboot). `diskutil apfs list` shows `semio-trim` in 4 live containers right now.
- Fix in code: the kick now deletes the sibling again at the end of every cycle (`diskutil apfs deleteVolume <device>` in `dispose`, also for a sibling an older kick left behind). Kick tests: 12 pass, the script corpus ends with the delete, the real-image test asserts the container has no `semio-trim` afterwards.
- Live images: the next kick of an image removes its sibling, but only for images that are due. Do not wait for that: remove them in the idle window (step 0 of the switchover) or any reboot before that cannot mount them. Nothing was changed on live images by this ticket.

### 1. Design
Why: macOS returns freed blocks of a mounted APFS image only for containers of at most 2^35 bytes (32 GiB), measured above. `r` (96 GiB) and `d` (36 GiB) never give space back. So every image of a partition must be at most the per-platform maximum.

- Policy, schema first. `🍎️image/🧩️shard/🧬️schema/🔣️.json` (`Protocol`) declares per-platform `maximumImageBytes` (darwin 34 359 738 368 = 2^35, the measured limit; linux 128 GiB, trim works at any size, the cap only bounds fsck and recreate time; windows 64 GiB, offline `Optimize-VHD` per image bounds the drain window), the 1 GiB minimum and alignment, 256 shards at most, the layout names, the `hdiutil`/`diskutil` lifecycle commands (Linux and Windows are `unsupported`: they stay one image per partition, only their caps are declared), the bilingual messages. The partition policy `budget/🔣️policy.json` declares per partition `imageShards` (`enabled`, `headroomPercent`, `hostFreeReservePercent`, `roots[{prefix,pattern,needBytes}]`, optional `maximumImageBytes`); its schema mirrors the shard `Rule` and a test proves both validate the same policy. Declared: `rust`: root `u/l`, key = lane id `^[a-z0-9]{1,12}$`, need 8 GiB, headroom 100 %; `dependencies`: root `j`, key = job workspace `^[0-9a-f]{20}$`, need 3 GiB. Both `enabled: false`: the live layout is unchanged.
- Shard key. A shard is the image of one key, the child directory of a root. For the Rust cache that is the lane (`u/l/<lane>`): the lane is the unit that the lane claim (`k/lane-<id>`), the live markers (`v`), `lane.json`, `lane.size`, the incremental state and the whole `<target>/<profile>` tree already keep together, and it is the unit the pool, the collector and `removeLaneV1` add, measure and delete. Everything no root claims stays in the home image: the shared unit store (`u/e`, `u/sealed`, `u/k` locks, `u/h` headroom, `u/s`/`q` slots), cargo home, components, nx. Units are restored into a lane by `COPYFILE_FICLONE` (clone, else copy), so a shard needs no cross-image clone to work. Why not a hash: a mount point is a path, so a hash bucket would change the logical path; per key keeps every path as it is. Id: the key itself when it is a short id, else `x` + 11 hex of its SHA-256 (collision checked).
- Same logical paths, no caller changes. A shard is mounted at `<partition>/m/<root prefix>/<key>`, the exact logical path, so a consumer sees one tree and every path keeps its length. Home keeps `<partition>/fixed.dmg` and `m` as today. Shard files: `<partition>/s/<id>/{fixed.dmg,shard.json}`, ledger `<partition>/shards.jsonl`.
- Event-sourced ledger. `born{id,key,root,path,capacityBytes,atMs}` and `retired{id,atMs}`, one line each, append only with one synced write; state is the fold (idempotent repeated birth, foreign key under a live id and unknown retirement are errors, a torn last line is ignored). The mount path is in the event, so a later change of the rule never orphans a shard.
- Birth and growth rule. Lazy: `ensureNativeImageShardV1` selects, and for a new key creates the image (`hdiutil create ... -fs "Case-sensitive APFS"`, same as the home image), attaches it through `diskutil image attach` at the logical path and only then logs it, all inside a lock; a crash leaves at most an unlogged image that the next birth replaces, `repairNativeImageShardsV1` re-mounts the logged shards after a reboot and retires the ones whose files are gone. Capacity: as large as the cap and the host share allow, `min(cap, 66 % of the host free bytes)` aligned to GiB, never below working set x (1 + headroom) and 1 GiB; the backing is sparse, so the declared size costs nothing until written. A key whose need exceeds the cap or whose need the host cannot hold is refused (`cap`, `host-free`, bilingual text). No in-place growth is needed: the image is born at its cap. Retiring a shard (`retireNativeImageShardV1`) detaches it and deletes its files: all of its blocks return at once, no trim needed, which is the cheapest reclaim for an evicted lane.
- Leases. Every image has its own resource `native-fixed-image:<image directory>`; the kick takes a nonwaiting shared lease per image, so an exclusive cycle of one shard never blocks the kick of another (proved with the real lease table).
- Reclaim and the kick. `reclaimNativeImageShardsV1` applies the existing due rule and the existing kick to every image of the partition, one after the other, each under its lease; a held lease, a failing image or an unmeasurable one is reported per image and never stops the others; totals add over the kicked images; cancellation propagates at once. `repo cache gc` (`reclaimImageIfQuiescentV1`) uses it when the partition has `imageShards.enabled`, `repositoryPartitionReclaimDueV1` is due when any image is bloated.
- Honest measure and headroom. `measureVolumeV1` (the single volume reading of the collector, headroom admission and auto reclaim) answers for a cache root inside a sharded partition (home mount with a non-empty ledger) the aggregate of all images: the volume is the partition budget, the used bytes those of all images, the free bytes the honest free bytes where the images on one host volume share that volume's free bytes once (a sum of per-image caps would count the same host space twice). Outside a sharded partition nothing changes.
- Upfront admission. `nativeImageShardAdmissionV1`: per host volume, growth of every image (need less the credited slack share, plus 128 MiB birth allocation for a shard still to be born) plus the reserve against the volume's free bytes; shortfalls add over volumes.
- Path budget. A shard adds `<partition>/s/<id>/{fixed.dmg,shard.json}` and the ledger below the workspace; `nativeImageShardPathBudgetV1` returns the longest of them and the longest partition directory that keeps all of them within 256 characters (230 for a 12 character id, 241 for a 1 character one). Files below a mount point need no new rule: the mount point is the logical path.

### 3. Not done, on purpose
- The live layout is not switched (`enabled: false`).
- Lane birth is not wired into the pool. `acquirePooledLaneV1` chooses a lane id inside a synchronous section under the catalog claim and enters it synchronously, in the Cargo wrapper process. The call site is one step before `enterLaneV1`: an async `prepare(id)` that calls `ensureNativeImageShardV1` after the claim is taken, which needs the catalog section split in two (choose and claim under the catalog claim, prepare outside it, enter and trim again under it). I did not change that hot path untested. Until it is done, shards are born by `shard-switchover.ts birth` for the lanes that exist, and a new lane lands in the home image (correct, only not space-returning).
- The admission function and the per-shard admission rows are not yet called by `admitNativeBuildUpfrontV1`; the reserve and shard rows must be assembled there from `repositoryCacheBudgetV1(...).partitions.*.imageShards` and the ledger.
- The Linux and Windows lifecycle (`unsupported`): partitions stay one image there.
- `dependencies` has no reset profile; step 6 retires `d` by hand.
