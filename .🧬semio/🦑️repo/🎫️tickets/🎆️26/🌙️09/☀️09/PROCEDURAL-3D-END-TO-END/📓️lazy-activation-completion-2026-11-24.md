# Lazy activation completion (2026-11-24)

Finishes `📓️lazy-extension-activation-2026-11-23.md` and `📓️node-kind-activation-trigger-2026-11-23.md`: a 3D document whose node kinds belong to a deferred flow extension now activates that extension from inside the live shell, in React and in WGPU, and the parked preview resumes by itself. No eager depends-on fallback.

## Root cause (three independent gaps, all verified in source)

1. **Shells never saw the deferred rows.** `resolvePlaygroundBoot` returns only the boot plan (`procedural`, `flow`). The React activator was fed `onDemandPluginEntries(plugins, registry)` where both arguments are that same plan, so its candidate list was empty: every `node-kind`, `tag` and `event` request answered `requested: []` and a `plugin` request answered `not-installed`. WGPU was worse: `bootFrameworkOsDev` passed the boot plan as the explicit module list and the frame Worker only computed a primary (and so a deferred set) when no explicit list was given; `prepared.deferred` was `[]` there too.
2. **Nothing asked.** The node-kind request was emitted only by the flow editor's `flowEvalTick`. Generation3d (and generation2d) never run that tick on an unserved graph: `preview_eval_run_effects` refuses to start the run when `servable` is false ("only `setContributions` can move it"), so no hop ever existed to carry an effect. The nodes therefore stayed queued/computing forever: pending, not failed, but with nobody asking.
3. **WGPU had no resume.** `semioWgpuActivateOnDemand` only mounted the module inside the frame Worker (`onDemandModules`); the shell never received the handle, so `plugins` never contained it and the contributions push never carried its operators. The request arm lived only in `dispatch-action`, but polled effects (`pending_effects`) reach the shell through `queue_host_effects`, which dropped a `PublishEvent`.

4. **A late registry generation killed the actor.** With the React activator fed (probe `react-lazy-activation-probe.mjs`: the door answers `requested/active: ["flow-extension-brep"]` and the "ready" notice shows) the refresh that pushes the new operators panicked the staged guest: `panicked at 🌊️flow/🗂️catalogue/🦀️.rs:150: superseded flow catalogue did not terminate`, then `wasm trap: unreachable` on every later call. `retire_superseded_catalogue` closes the displaced operator catalogue (every built-in and contributed `OperatorInfo`, tens of thousands of owned allocations at one item per step) inside one turn with a fixed 4096-step bound. An eager boot never moved the generation after the first catalogue read, so the bound was never reached; lazy activation moves it by design. Fixed by queueing the displaced catalogue (`SUPERSEDED_CATALOGUES`) and spending at most 2048 steps per catalogue read until it drains (no panic, bounded turn cost); law `a_catalogue_displaced_after_it_was_read_drains_without_panicking` (600 contributed operators, fails on the old bound). This also needs the flow hub rebuilt: the same code serves flow documents.
5. **A late install triggered no refresh.** `installPlugin` upserts `loadedPlugins`, but nothing re-runs `refreshUi`, and the contributions publisher is only entered from a refresh pass (keyed by the loaded plugin ids). The React activator now owes the live session one full refresh after a successful install.

## Design

Schema-first: `🧬️schema/🧩️plugin-modules/🔣️.json` `$defs.onDemandEmission` states the emission contract (topic, latch `registry-generation-and-unserved-kinds`, surfaces `flow.flowEvalTick` and `procedural.generation3d.pending_effects`). The request wire (`$defs.onDemandRequest`) and topic are unchanged.

**Guest (Rust).** The seam is `pending_effects`, which runs on every host refresh and already asks `servable`. `preview_eval::on_demand_run_effects(link, unserved)` (generation3d editor and viewer; the same pair in generation2d) returns one `Effect::PublishEvent` on `os.on-demand.request` per namespace of the unserved kinds (`semio_os_flow::on_demand_node_kind_requests`, the twin of the kernel's `nodeKindRequests`). A latch on `PreviewEvalRunLink.activation_asked = (flow registry generation, unserved kinds)` makes it ask once per generation and kind set: a refresh storm costs one request, a mounted extension that still leaves another namespace unserved (brep done, math missing) moves the generation and asks for the next, a servable graph clears the latch, a withdrawn extension asks again. Second seam (found live: the poll never carried the request on the boot path, the spy on `semioReactActivateOnDemand` saw zero calls): every route that owes the previews an evaluation (`setActiveExample`, generation commands, `setContributions`, import, inspector edits, view changes) now hands `unserved_kinds(snapshot)` explicitly to `owe_attached_previews_carrying` / `owe_attached_previews_for_mutations` (preview-eval, both surfaces) instead of a `servable` bool; the carrying call puts the activation requests on the gesture's own emit through the same latch. The window stays parked (the run never starts on an unservable graph, so no node is faulted); the activated extension's contributions push owes every attached preview an evaluation and carries the run start (`owe_attached_previews_carrying`), which is the existing resume.

**React shell.** `deferredPluginEntries(catalog, boot)` and `catalogPluginRegistryEntries(catalog)` (kernel `🎮️playground-boot`, one `pluginRegistryEntryOf` row projection shared with the boot planner) give the activator candidates and installed rows from the full catalog. `installPlugin` already resolves a deferred module through the extension source and the late `loadedPlugins` change moves the contributions publisher's registry key, which pushes `setContributions`. Notices: every phase except `resolving` raises the transient notice in the UI locale (`role=status` polite, `alert` assertive for unavailable, warning for cancelled), including a "ready" notice that replaces the loading one; cancellation goes through the existing per-plugin install abort (`semioReactCancelOnDemand`, the install band's cancel).

**WGPU shell.** The frame Worker plans from the variant (`bootVariant` no longer depends on whether a module list was supplied) and the dev entry passes no module list, so the renderer receives every catalog module while only the variant's closure is read; the deferred set is real. New door `semioWgpuResolveOnDemand(request) -> string[]` (`OnDemandActivator.owners`, the not yet active owners). The shell's host-effect funnel (`apply_host_effects_until_load`, which every dispatch path and every polled refresh feeds) queues `PublishEvent os.on-demand.request` as the framework action `activateOnDemand`; the action resolves the owners and installs each through the shell's own `install_plugin` (so the existing install band shows progress and its cancel stops the load), then `push_contributions()` and a full refresh, which resumes the document. An owner that cannot load shows the activator's localized text (`semioWgpuOnDemandStatuses`, en/de) as a transient notice (role from the announcement); a cancelled install is silent. The old fire-and-forget bridge function `request_on_demand_activation` is gone.
