Busy/mismatched/changed images refuse or skip. Native-build/💾️storage/🍎️image/♻️reclaim/🟦️.ts:28–56 detaches the existing device, attaches the same backing at a private UNMAP-capable scratch mount, waits for allocation to settle and detaches; it does not recreate or discard the image, and the next normal owner opens it. The implementation uses tmpdir for its private scratch (:63–77), rather than providing a separate persistent lane-lock namespace. It needs a successful exclusive lease and operating-system detach; external uncoordinated holders can still make detach refuse. Reclaim returns host blocks but does not promise correction of mounted statfs or success of subsequent unlink.

The wait eligibility predicate is budget/🟦️.ts:45–50: measured used bytes required, and either host pressure plus elastic bloat or mounted free below pressure floor plus allocated-minus-used at least reclaim floor. Current rust policy is pressure floor 6,442,450,944 bytes and reclaim floor 8,589,934,592 bytes. One non-atomic sample gave mount statfs free 0, fixed.dmg allocated 44,804,407,296 bytes, host available 39,624,507,392 bytes, and diskutil CapacityInUse 14,022,586,368 bytes. Those figures satisfy the latter arithmetic branch if the exact owner validates them; due, mapping and exclusive custody are rechecked at execution and were not proved here.

reclaimImageIfQuiescentV1 (:218–260) is the ordinary nonwaiting reclaim: it requires the image bloat rule (or separately admitted recovery pressure/slack), exclusive lease and same native reclaim cycle. repo cache gc calls it but the earlier GC unlink ENOSPC shows it did not resolve this condition. Elastic regrow/reset (:190–207) may retire/recreate the image and is not the non-destructive path requested. Compact compiler recovery only prunes eligible finalized compact stores under issued writer custody and could itself encounter the same filesystem refusal.

Consequently there is an existing authorized non-discard maintenance path to attempt; it is conditional, not verified as executable or sufficient on this host. If it skips/refuses or returns without making the mounted filesystem writable, the observed no-space unlink and ftruncate behavior remains a real recovery impasse requiring an owner-supported change or external-state change; bypassing locks or deleting the backing is not established safe.
