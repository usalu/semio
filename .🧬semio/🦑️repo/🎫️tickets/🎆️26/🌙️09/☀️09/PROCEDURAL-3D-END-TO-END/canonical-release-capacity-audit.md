Read-only source/log snapshot; no builds, edits to production or cache changes.

Both prototype and release are official declared modes for wasm32-wasip2 component and wasm32-unknown-unknown browser roles (repo library/🏗️build/🎚️mode/🦀️profile/🧬️schema/🔣️.json:18–33, :52–71). Playground target inference explicitly builds prototype and release preparation paths for both React and WGPU and dispatches the selected mode (🏗️build/🕸️graph/📥️inference/🎮️playground-targets/🟨️.mjs:265–278, :299–309). Thus a fully rebuilt, correctly published release closure is an authentic renderer test, subject to actual run verification; a historical receipt or mixed-mode staging is not that proof.

Release is not an evidenced remedy for the full component lane. Profile policy :431–436 specifies prototype-component opt-level s, debug 0, 16 codegen units, nonincremental, thin LTO; :465–470 gives the same settings for release-wasm. The policy declares panic, debug assertions, overflow checks, target stack and memory among preserved constraints (:415–421), but the Cargo profile identity is still different and cache reuse must be proven independently. Release may alter code generation or feature/profile-conditioned behavior, and even a passing release journey would not verify prototype-specific behavior or performance. No actual high-water measurement establishes release will fit; do not assume lower peak from release output size. Browser wasm prototype has opt-level 1, 256 codegen units, incremental, no LTO (:438–443), whereas release-wasm uses opt-level s and thin LTO; runtime and compile performance can differ.
