# Oversized Hover Publication Review

The opaque token is accepted by `next_hover`, which preserves direct IDs even when absent from topology. However, the host's `apply_interaction_verb` unconditionally invokes `revalidate_and_persist_interaction_state` for Hover immediately after that step (`🔌️plugin/🧵️instance/🖼️render/📥️staging/🧭️interaction/🦀️.rs` 347–372, 426, 464). That invokes `validate_state`, whose hover filter keeps only IDs in the domain topology (`📡️replication/📡️wire/🕹️interaction/🦀️.rs` 793–810). Generation3d's topology contains authored nodes, ports and edges, not `preview-hover:<revision>:<index>`. The token is therefore removed from the authoritative hover before the app's render wrapper can expand it. A leftover view is built before validation, but does not establish that normal interaction state or graph render receives the token.

Fix at an owned boundary that expands an authorized live window publication before topology validation, or explicitly admits and retires publication identities in the host topology. Preserve source-window ownership, stale-token rejection and document revalidation. Add an actual host reserved Hover dispatch through validated state and graph render, with >4096 bytes of targets, a leave and a second window. A direct `PreviewHoverPublications::resolve` unit alone does not cover the gate.

Window publications are replaced only on successful assembly and retired on the next render's mounted-window inventory; global monotonically allocated table revisions distinguish different table generations. A Flow companion payload over 64 KiB was not verified in this pass: the local token keeps the world action short, but expansion into any later bounded graph-hover companion needs an explicit separate transport or capacity law. No test or build was run.
