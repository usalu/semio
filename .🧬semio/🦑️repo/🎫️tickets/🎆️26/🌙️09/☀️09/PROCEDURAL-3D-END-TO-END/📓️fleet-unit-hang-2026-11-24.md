# Fleet unit hang of hub-15 (2026-11-24)

- Hung unit: `semio_hub_flow_component` (linked wasm final), operation `b2907920-d972-4ba2-b69c-380082f60767`, action `1b4fa319de7e`, EXECUTING on worker g1-server for 1439 s.
- Unblocked: `repo remote-execution cancel all-stuck` (only that operation was stuck). The counter went to "0 on the fleet", the unit waited ~3 min in local memory admission (needs 4767 MB + 2458 MB margin), then "1 running locally".
- Root cause: the deadline of an offloaded unit was factor 4 times the recorded local cost (496697 ms, 8.3 min = 33 min) plus 600 s outage patience for linked units = 43 min, while the same unit costs 8.3 min locally. The scheduler keep-alives and the worker heartbeat continue while the action hangs, so silence detection never fires; only the deadline can end it.
- Fix: factor 4 -> 2 in `🚀️offload/🧬️schema/🔣️.json` (policy.deadline), outage patience no longer added to the execution deadline in `🚀️offload/🟦️.ts` (it stays on the overall budget and the download). Test vectors `🚀️offload/🧪️tests/⏱️timeouts/🔣️.json` updated first (failed), plus the hub's real cost vector; python oracle unchanged and agrees. `bun test` of that file: 12 pass.
- Not done (follow-up): a progress-based liveness (CPU time of the task process group in the worker heartbeat, next to the existing memory usage) so a stalled action is dropped before the deadline; local admission wait has no visible bound either.

## Second occurrence (lazy-activation-semio-hub-flow-component, 18:37-18:48 UTC)

- Operation `b2109e8e-bb71-4027-849d-09b2e901985c` (action `43df70ac27ed`, final unit `semio_hub_flow_component`, on g1-server). Ended with `repo remote-execution cancel all-stuck` at 18:48 UTC once it matched; the log then showed "1 running locally, 0 on the fleet".
- (a) Why all-stuck said "No unfinished operation matches": the scheduler had restarted at 18:37:35 (status: `restored 1, resumed 1`). A restored executing operation had `startedAt` reset to the restart time, so its age counted from the restart (8 min) and stayed below `stuckSeconds` (600) for 10 min. Fix: the journal row now keeps `runningMilliseconds` and `restore` backdates `startedAt` by it (`🗓️scheduler/🟦️.ts`, `📓️journal/🟦️.ts`); test "keeps counting the age of a restored executing action" fails before, passes after (29 scheduler tests pass).
- (b) Why the 2x deadline did not fire: the local-cost record of the unit (`.cache/b/r/m/u/c/semio_hub_flow_component`) is the running average of local compiles and had grown to 1659511 ms (27.7 min; it includes the slow, memory-starved local compile of hub-15; it was 496697 ms the day before). 2x = 55 min, capped only by the linked cap of 60 min, so the deadline was far away. Fix: linked cap and linked unknown value are both 20 min (schema `deadline.linkedCapMilliseconds/linkedUnknownMilliseconds` = 1200000); vectors in `🚀️offload/🧪️tests/⏱️timeouts/🔣️.json` updated first (including the 1659511 ms case -> 1200000) and the python oracle agrees.

## Local cost record no longer absorbs starved compiles (2026-11-24)

- Root cause: the only writer of `.cache/b/r/m/u/c/<crate>` is the unit-cache rustc wrapper (`⚡️caching/🦀️cargo/🗃️unit-cache/📜️script.ts`, `writeUnitCostV1`). It recorded `ranMs`, the wall time of the whole inner call, i.e. of `semio-build-scheduler` (`native-build/🎟️admission/🦀️.rs`), which first WAITS for the broker's memory admission and only then runs rustc. The record then moved halfway to every observation, so hub-15's memory-starved serial-backend final (496697 -> 1659511 ms, i.e. an observation of ~2.8e6 ms) doubled the record.
- Rule (schema `policy.cost` in `🚀️offload/🧬️schema/🔣️.json`, function `offloadCostRecordV1` in `🚀️offload/📐️policy/🟦️.ts`): the observation is the broker-measured run AFTER admission (`UnitProvenanceV1.wallMs`; whole-call time only when nothing was measured). A run whose (user+sys CPU)/wall is below `minimumUtilisation` (0.5: starved by memory pressure, swap or cores) only upper-bounds the cost: it never raises the record (`contendedRaiseWeight` 0), may lower it (`contendedLowerWeight` 0.5) and teaches a unit without record nothing (`learnContendedFirst` false). Calm runs move the record by `calmWeight` 0.5 as before.
- Not special-cased: the serial LLVM backend is the constant local configuration of every cdylib final, so it is part of the cost, not contention.
- Wiring: `writeUnitCostV1(root,crate,ranMs,measure?)`; `script.ts` now writes the record after `recallProvenanceV1` with the measurement.
- Tests (failing first): `🚀️offload/🧪️tests/🧮️unit-cost/{🔣️.json,🐍️.py,🟦️.ts}` (9 vectors incl. the hub-15 numbers, independent python oracle, file round trip). `repo test-file`: unit-cost 4 pass, offload 41 pass, cargo unit-cache 28 pass. Existing `⏱️timeouts` "riding through a lost scheduler" still fails under load (60 s ride-through), unrelated.
- The existing record `semio_hub_flow_component` (1659511) was not touched; it decays by halves with calm runs (or delete the file).
