## 3. Eval path: op chain → renderable mesh

Sequence (generation3d editor commands, `🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/🎮️commands/`):
1. A widget edit self-dispatches `flow-eval-tick` (`⏱️flow-eval-tick/🦀️.rs:18`, `delay_ms: 0`) repeatedly until the graph settles.
2. `handle()` (⏱️flow-eval-tick/🦀️.rs:14-32) calls `session.tick(&mut host)` → `host.evaluate_step(FLOW_EVAL_TICK_STEP_BUDGET)` where `FLOW_EVAL_TICK_STEP_BUDGET = 512` (`🧰️framework/🛍️products/💻️os/🔨️modules/🌊️flow/🖥️host/🦀️.rs:2310`) — a bounded, cooperative pump, not a synchronous whole-graph solve.
3. Per-node results are memoized in `neural_cache` keyed by `node_hash = neural::node_hash(&operator_id, input)` (`🧰️framework/🛍️products/💻️os/🔨️modules/🌊️flow/📔️registry/🦀️.rs:90`) — unaffected upstream nodes reuse cached values across ticks/edits (incremental, not brute-force whole-document re-evaluation).
4. When a node needs the brep extension, the host emits `Effect::InvokeExtension{extension_id, capability:"evaluate", request_json}` (⏱️flow-eval-tick/🦀️.rs:20-26) — a discrete host↔extension round trip per unresolved operator; the extension's `bundle().handler("evaluate", …)` (`✏️s/🔌️plugins/🌊️flow/🧩️extensions/📐️brep/🦀️.rs:1950-1952`) runs inside the extension, tagged `ExecutionMode::Linked` (line 1947) — linked into the same component as its host app, not a separately-loaded wasm module. The result returns via the `flow-eval-resolve` command → `session.seed_node_cache(node_hash, output_json)` (`✅️flow-eval-resolve/🦀️.rs:17`), which re-triggers another tick.
5. Once no widgets remain pending (`!more`, ⏱️flow-eval-tick/🦀️.rs:27-28), `preview_tessellate_effects(...)` runs. Tessellation itself is memoized twice: an in-process `mesh_cache` keyed by `(handle, tolerance.to_bits())` (`🧰️framework/🔨️modules/🌊️flow/📐️brep-geometry/🦀️.rs:510-527`), and a session-level `preview_mesh_json_by_handle: BTreeMap<String,String>` populated via the `flow-tessellate-resolve` command → `session.resolve_preview_tessellate(node_hash, output_json)` (`🔺️flow-tessellate-resolve/🦀️.rs:17`, `🖥️host/🦀️.rs:2541-2550`). Cache invalidation for generation3d's own path is **handle-liveness-based** (`retain_preview_meshes(live_handles)`, `🖥️host/🦀️.rs:2521-2524`), not a blanket clear on every edit — a full-wipe method (`set_eval_json`, `🖥️host/🦀️.rs:2484-2504`) exists but is wired only into generation2d's `set-eval-outputs` command, not generation3d's tick/resolve commands.
6. Mesh wire shape: `MeshData` (`🧰️framework/🔨️modules/🏗️mesh-engine/🦀️.rs:22-45`) — flat `f32` `positions`/`normals`/`colors`/`uvs` + `u32` `indices`, plus `face_ids`/`vertex_ids`/`edge_positions`/`edge_ids`/`edge_uvs` arrays (these back client-side component picking, §4). It crosses the extension boundary as a **JSON string**, `crate::os_pack::json::to_json_string(&mesh)` (`🧰️framework/🔨️modules/🌊️flow/📐️brep-geometry/🦀️.rs:530,890-892` and the `tessellate` handler at `✏️s/🔌️plugins/🌊️flow/🧩️extensions/📐️brep/🦀️.rs:1953-1958`) — not the compact `pack::encode_record_body` wire form, and not the heavyweight `pack::encode_json_value` container either; a third, ad hoc JSON-string path with per-element id arrays repeated as JSON (no binary packing).
7. A second, separate wasm surface exists: `#[cfg(all(target_arch="wasm32", not(target_env="p2")))] mod wasm_bridge` (`🧰️framework/🔨️modules/🌊️flow/📐️brep-geometry/🦀️.rs:544-567`) exports `tessellate`/`dispose`/`brep_invoke` via `wasm_bindgen` for a browser "flow-core" bundle (referenced from `🧰️framework/🔨️modules/🧊️3d/🟦️.ts`'s `ensureBrepWasmLoaded`), explicitly excluding `wasip2` — distinct from the plugin-component `extension_guest` path in §3.4/3.5. **Which surface the `:6018`/`:6118` procedural3d playground actually exercises at runtime was not confirmed by this static read** — flagged for a runtime check.

## 4. Hover / selection / picking

Picking is client-side for the web/React render target, not host-Rust and not a wgpu compute pass. `World3dHost` (`🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🌐️World3dHost/🟦️.tsx`, 5355 lines) is a **shared** react-three-fiber viewer (used by puzzle/block/procedural/etc., not procedural3d-specific — confirmed by a puzzle-related comment at line 141). `onClick`/`onPointerMove`/`onPointerOut` handlers on R3F mesh elements read `event.faceIndex`/`event.face`/`event.point` — three.js's own raycaster results, supplied automatically by react-three-fiber (lines ~1986-2116) — resolving to `onWorldPick(...)`/`onInstancePointerDown(...)`/`onComponentHover(...)` callbacks against the `face_ids`/`edge_ids`/`vertex_ids` arrays baked into `MeshData` at tessellation time. These bubble to a domain-neutral `dispatch("interactionHover"/"interactionSelect", …)` call, not a generation3d-specific command — confirmed by generation3d's own `world-pointer-down` command handler (`✏️editor/🎮️commands/🌍️world-pointer-down/🦀️.rs:14-16`) being a no-op stub (`Ok(Emit::default())`), i.e. the artifact itself never resolves a pick.

**Open question**: a second, native picking surface exists in parallel — `world3d_states: AdmittedSurfaceMap<World3dState>` in the wgpu render target (`🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🎯️targets/🧊️wgpu/…`), documented as "driven directly by the OS event loop." Whether this native path performs its own CPU ray-triangle intersection or simply reuses the React-resolved ids was not resolved by a static read (no definitive `Ray`/intersection routine found in the searched wgpu-target files within budget) — flagged for a runtime check rather than guessed.

Resolved hover/selection state is pushed into a **framework-owned `InteractionView`** (`🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️.rs:8591-8624`), which explicitly splits `state: &protocol::InteractionState` — doc: "persisted-local half... one `ApplyInLane{lane: HistoryLane::Interaction}` dispatch away" — from `hover: &InteractionHoverState` — doc: "the ephemeral-local half (`VcsArtifactApp::interaction_hover`), never persisted." `PreviewInteractionMarks::from_interaction` (`✏️editor/🦀️.rs:1478-1483`) reads both, with its own doc comment stating plainly: "Reads the framework-owned domain: hover off the ephemeral pointer channel, selection off the persisted interaction store. The app stores neither itself." This is **not** generation3d's own `🫧️transient` document — verified by reading `🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/🫧️transient/🦀️.rs` in full (67 lines): its only field is `generation_preview_text: Option<String>`, no hover/pointer/selection field. Hover propagation is "transitive" (`HoverSpec{transitive:true}`, `✏️editor/🦀️.rs:1355`): hovering a graph node lights up every associated world-preview instance and vice versa.

## 5. Performance hot spots (static)

- **Re-tessellation scope**: incremental at three layers, not blanket whole-document re-evaluation. Evaluation itself is scoped to the **currently selected generation only** — `generation_command_result_for` builds `preview_fixture` via `generation_fixture_for(&projection.fixture, &state)` (`✏️editor/🎮️commands/🧬️generation/🦀️.rs:33`), and `UpdateGenerationValues` carries `coalesce_key: "generation-values"` (line 38) so rapid slider drags coalesce into one work item rather than one eval per input event. Within that scope, `neural_cache` memoizes per-node (keyed by operator+input hash, `FLOW_EVAL_TICK_STEP_BUDGET=512` cache-missed dispatches/tick, `🖥️host/🦀️.rs:2310,2460-2461`) and tessellation is memoized per geometry handle (`preview_mesh_json_by_handle`, re-requested only for handles whose content changed via `note_pending_tessellate`, `🖥️host/🦀️.rs:2527-2539`). Still, the tick loop must fully settle (`!more`) before any new tessellate request is even considered (`⏱️flow-eval-tick/🦀️.rs:27-28`), and each cache-missed node incurs a discrete `InvokeExtension` round trip — a wide/deep graph delays first paint of the changed node even though upstream unaffected nodes are cache-hits.
- **Progress**: present at the interactive-job layer — `EditorApp<Generation3dPlayApp>`'s `step()` returns `ArtifactCommandWorkStep::Progress{ stage: "generation3d-preview-evaluation", .. }` while ticking (`✏️editor/🦀️.rs:291,296`), plus `set_computing_progress(active_widget_id, stale_widget_ids)` for per-widget active/stale UI state (`✏️editor/🦀️.rs:391,399-400`). **Absent at the kernel-call boundary**: the tessellate extension handler (`✏️s/🔌️plugins/🌊️flow/🧩️extensions/📐️brep/🦀️.rs:1953-1958`) is one synchronous function call with no progress callback and no cancellation token inside it — it runs to completion in one shot. Generic store-preparation `cancel()` flags exist (`Generation3dArtifactStorePreparation::cancel`, `✏️editor/🦀️.rs:589-591`; `Generation3dConfigPreparation::cancel`, lines 727-729) but nothing cancels an in-flight `InvokeExtension`/tessellate call specifically — `cancel_area_select` (line 968-973) is an unrelated UI marquee-select cancel. A slow/pathological node can only be superseded by a later tick, never aborted mid-flight by the user.
- **Mesh payload size**: `MeshData` serializes to one JSON string per handle, returned as one `Vec<u8>` blob over `InvokeExtension` and stored whole in `preview_mesh_json_by_handle: BTreeMap<String,String>` (`🖥️host/🦀️.rs:2347`) — no chunking or streaming. The only size lever is tessellation tolerance via LOD: `preview_tolerance(lod_mode)` maps `"coarse"→0.15`, `"fine"→0.02`, default `0.05` deflection (`✏️editor/🦀️.rs:1433-1438`) — fine at these 8 toy-primitive scales, a real cost at finer LOD or denser geometry since payload transport itself is never chunked.
- **Step budget**: `FLOW_EVAL_TICK_STEP_BUDGET = 512` ("max cache-missed neuron dispatches per `flowEvalTick`") is generic to the flow evaluator (shared with the standalone `flow` plugin), not procedural3d-specific. A separate `GENERATION3D_RETAINED_WORK_ITEMS = 32` (`✏️editor/🦀️.rs:205`) gates whether a command's estimated footprint (`widgets.len()+2`) stays within a retained-work-item ceiling for generation mutations (lines 260-267) — an unrelated memory/coalescing constant, not a wasm pump. No `puzzle3d`-style fixed intake/pump budget (that plugin's reported 4096-step intake, 3-interactive-steps-per-4096-turns cadence) was found scoped to generation3d or its tessellate path — grepped and confirmed absent, not merely unchecked.
- **No validate gate**: none of the 8 examples' op chains include `brep.measure.validate` (confirmed absent from all 8 DSLs) even though the operator exists (`✏️s/🔌️plugins/🌊️flow/🧩️extensions/📐️brep/🦀️.rs:99,708,1717`) — an invalid boolean/offset result (shell-not-closed, non-manifold-edge, per the known 15 failures) flows straight to tessellate/render with no structured health check.

## 6. Gap list, ranked by user impact

1. **`sphere-cut-with-torus` and `sphere-box-fuse` sit on the currently-broken boolean path.** Their primitives (`sphere_prim`/`torus_prim`/`box_prim`) are fine — confirmed exact analytic despite a stale quality tag (§1) — but `brep.bool.cut`/`brep.bool.fuse` is exactly the exact-imprint algorithm with 5 Boolean + 1 engine-cut known failures as of 2026-09-08. Highest risk of visibly broken/missing geometry among the 8, and the two richest/most interesting examples to demo.
2. **Zero automated regression coverage links any example to real kernel output.** All 16 example-level tests (8 Rust + 8 TS) only check DSL-text non-emptiness (plus, for `box-fillet-preview`/`sphere-cut-with-torus`, a DSL-parse/inference-determinism check unrelated to geometry). A kernel regression in any op silently breaks preview for that example with no CI signal. The "8/8 green" claim is unverified since 2026-08-07 and cannot currently be re-verified without a manual playground run. No `🖼️assets/` fixture (expected image, expected mesh stats) exists for any of the 8 to even make such a check possible today.
3. **No cancellation for the actual tessellate/kernel call, only for the surrounding job.** Progress *is* reported at the interactive-job layer (`ArtifactCommandWorkStep::Progress{stage:"generation3d-preview-evaluation"}`) and generic store-preparation `cancel()` flags exist, but the tessellate extension handler itself is one synchronous call with no progress callback or cancellation token inside it — a slow/pathological node stalls that call with no way to abort it specifically, only supersession once it eventually returns.
4. **Mesh crosses the host/extension boundary as an uncompacted JSON string**, not `pack`'s binary wire format, with per-element id arrays repeated as JSON and no chunking — the only size lever is tessellation tolerance (LOD 0.15/0.05/0.02), not transport. Will not scale gracefully once examples move past toy-primitive tessellation density.
5. **No automatic `validate()` gate** before tessellation for any example — an invalid boolean/offset result renders whatever the tessellator produces rather than surfacing a structured error to the user.
6. **The kernel's own fidelity contract has drifted from its code.** `OPERATION_QUALITY` still tags `sphere_prim`/`cylinder_prim`/`cone_prim`/`torus_prim` as `MeshDerivedBRep`, but the actual primitive-construction code has been exact analytic since the 2026-09-03 W1-E rewrite (§1). Anyone auditing kernel fidelity from the contract table alone (as the Aug-7 doc's successors likely will) will over-estimate risk on 4 of the table's 91 rows — worth a one-line fix to the table itself.
7. **Two open/unresolved runtime questions worth settling before further perf or picking work**: (a) which of the two parallel wasm tessellation surfaces (`wasip2` plugin-component extension, `ExecutionMode::Linked`, vs. a separate non-p2 `wasm_bindgen` "flow-core" browser bridge) the `:6018`/`:6118` procedural3d playground actually exercises at runtime; (b) whether the native wgpu render target's `world3d_states` picking path does its own CPU raycast or reuses the React-resolved ids — both need a runtime check, not a static read.
