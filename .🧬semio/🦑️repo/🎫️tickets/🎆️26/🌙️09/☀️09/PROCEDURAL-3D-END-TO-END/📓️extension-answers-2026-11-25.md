## Math: `invariantViolated registry admission requires its original source slot and caller`
- Guard: `SharedRegistryIssuer::validate` in `🧰️framework/🛍️products/💻️os/🔨️modules/🧠️neural/⚙️engine/📔️registry/🏗️admission/🦀️.rs` (unchanged since 11 Nov, so the 24 Nov math component has the same code).
- Callers: `evaluate_invoke_json` (wasm glue, one admission step per invoke turn) and brep `infer_geometry`; both pass the resources' own `original_registry` slot and the turn's `StepContext`.
- Cause: admission spans many turns. The compared identity contained the Source epoch by equality, but the actor issues a strictly increasing epoch every turn (`receive_next_issued`), and a per-turn stack-local recipient address (reactor `dispatch_step`: `let mut spent=...default()`). Turn 2 therefore refuses. Fixture callers never bound an epoch, so every unit law missed it.
- Red (law `original_registry_issuer_follows_its_source_forward_and_refuses_every_other_source`, `law-admission-red2.txt`): exact fault text on the first later-epoch turn. Fix: `SourceIdentity::continues`: operation, generation, Source parent, cancel node, clock, caller slot equal; epoch never backwards; recipient no longer compared. Green: `registry_admission` 3 passed, 0 failed (`law-admission-green6.txt`).
- What the recipient address protected: that the paid receipts of one admission go to one caller ledger. That is now carried by the Source parent identity plus operation and generation (another actor's Source, a reborn actor: refused at any epoch, law asserts it with a second fixture caller) and the slot address (another caller slot: refused).
- Test-only repairs in that target: stale `step`/`close_step` calls (new `body` argument), closing helpers drive `semio_framework_job::close_original_effect_step`; a whole registry retirement demands 424 copy bytes, so zero-progress polls under a 1/3/64 byte grant are legal, closing turns use at least 4096.

## Brep silence: other causes read from source (candidates, none proven)
Every turn of one evaluate runs `RetainedExtensionInvocation::step` -> `evaluate_invoke_json` -> `EvaluationInvokeCursor::step_original` -> `evaluation_drive_original` (wasm `📥️request`, `🎫️evaluate-request-admission-and-drive`). A turn returns "no payload, no refusal" silently in these places, so 64 turns without `respond` need no fault:
1. `cx.should_yield()` (fuel 0 or `now >= deadline_us`) at the top of `step_original` and of the drive loop. If the turn deadline given to the brep invocation had already passed (brep started 14 s behind math on the same requester actor), every turn returns before any work. Needs the reactor turn budget of that invocation: host side, not in the extension.
2. `grant.maximum_items==0||maximum_depth==0` or fuel 0 -> zero progress.
3. In the drive: `retained.advance(..)` that makes no unit and no receipt returns an empty reply (`receipt==default && units==before_units`): a first unit that needs more than the turn's retained grant never pays and never faults. A brep operator with large mesh capacity would do this under a small capacity grant.
4. Only the owner selected by `RETAINED_EXTENSION_CURSOR` is stepped per turn; a pending math owner would starve brep only if math never completes (it did).
The brep law uses a 1 MiB capacity / 64 KiB copy grant with a new epoch per turn; if it is green the cause is host-side (1 or 2), if red the fault text names the refusal.

## `stopped=input` after 1 poll (run h): what it means
Not a guest wait. `stopped` is the HOST worker's pump tag (`🧵️shard-worker-source/📨️message-handler/🟦️.ts`, law `🎭️actor/🖼️wire-turn/🚚️more-work-drive/🟦️.ts`): after a turn that answers `more-work` and carries nothing the worker re-polls the guest itself, unless `hostInputSeq` moved. `hostInputSeq` is ONE counter per worker (`🎬️actor-state-and-lanes/🟦️.ts:47`), bumped by every message posted to that worker for any actor or kind (`++hostInputSeq` first statement of the handler). So `stopped=input` after 1 poll means: a message reached that worker during every drive (another actor on the same shard worker, e.g. the procedural `flowEvalTick` traffic, or a queued next turn). The guest is not waiting for an input page, resume token, host answer or module read: it answered `more-work` with `eff=0`, its normal "pump me again" (a request needs many pumps: parse slices, slot lookup, insertion, drive units).
Consequence: with the drive defeated each crossing gives the guest exactly one pump, and the host ends the call after 64 submitted `more-work` turns (`INBOUND_REQUEST_TURN_BUDGET`): brep gets 64 pumps. Math runs 511 polls per crossing and stops on steps because nothing interrupted it. The first request page is consumed by the guest's own parser steps (1 pump each); nothing in the guest waits on the host.
Native law: `live_graph_extrude_answers_within_the_live_turn_budget...` counts pumps (one `evaluate_invoke_json` call = one pump = one live poll) and fails if an operator needs more than 64 (message names the row and operator, `[turns]` lines give the count). If brep needs more than 64 pumps natively, the cause is "64 pumps per request budget cannot fit the first unit while the worker interrupts the drive"; if it needs fewer, the interruption alone is not enough and the guest differs from native. Not edited without that number. Candidate fixes at the owners (not applied): scope `hostInputSeq` per actor in the message handler (a message for another actor must not interrupt this actor's drive), and/or let the inbound-request budget count only turns that did no work.
