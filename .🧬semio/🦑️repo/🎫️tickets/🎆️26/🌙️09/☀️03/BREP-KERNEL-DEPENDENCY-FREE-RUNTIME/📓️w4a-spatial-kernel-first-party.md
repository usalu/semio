  - `createBoxFromCorners`/`createBoxFromCornersDiff` — exact, via `box`+`translate`.
  - `solid.sphere`/`solid.cylinder`/`solid.cone` primitives — via `sphere`/`cylinder`/`cone` + `rotate` (axis-angle from canonical `+Z`, computed in pure TS) + `translate`. Verified primitive placement convention by reading `make_box`/`make_sphere`/`make_cylinder`/`make_cone` in `…/✳️brep/🧬️schema/🔺️diff/🧱️primitives/🦀️.rs` directly (box: min-corner at origin; sphere: centered at origin; cylinder/cone: base at origin, apex/top on `+Z`) rather than assuming.
  - `curve.line`/`curve.polyline`/`curve.circle`/`curve.arc`/`curve.controlPointCurve`/`curve.interpolateCurve` — **pure TS, no `brep_invoke` call**. Traced the legacy `BrepjsWasmEngine.executeCommandDiff` and found every one of these only used OCCT (`threePointArc`, `bsplineApprox`, `circle`) to read back a start/end point that is *already* known analytically from the same inputs (arc start/end are on the same circle already computed via `arcSamplePoints`; an interpolating/control-point curve's first/last vertex is provably its first/last pole) — so the OCCT round-trip in the legacy code was redundant for exactly these six commands, not a required dependency.
  - `solid.booleanUnion`/`solid.booleanDifference`/`solid.booleanIntersection` — via `fuse`/`cut`/`intersect`.
  - `extrudeWire`/`extrudeWireDiff`, `offsetFacesDiff`/`offsetFaces`, `surface.extrudeCrv`, `surface.loft`/`networkSrf`, `surface.sweep1`/`sweep2`, energy-wall `…From2PointsAndHeight`/`…FromCurveAndHeight` commands.
  - `volume`, `solidVolume`, `faceArea`, `edgeLength` (pure TS via `edgeCurveLength`, matching the legacy fallback path), `vertexDistance` (pure TS), `adjacentSolids`/`sharedFacesBetween` (pure TS graph walk, ported verbatim — never touched brepjs even in the legacy code), `tessellate`, `exportModelToStep`, `deconstruct`, `disposeSolid`/`syncSolidsFromModel`.
  - **Known trait-surface limitation, not fixed here** (would require editing `⚙️engine/🦀️.rs`, out of scope): `BrepKernel` has no generic "wire from mixed edge handles" constructor, only `polyline_wire`/`rectangle_wire` from raw points. So every wire handed to `extrude_wire`/`planarFaceFromWire`/`loft`/`sweep` is built by **polyline-sampling** the `Model` wire (`wirePolylinePoints`, reusing `edgeSamplePoints` from `🧮️preview`) rather than exact line/arc/NURBS edges — exact for straight-edge wires, chordally-approximated (`MeshDerivedBRep`-equivalent) for curved ones. Flagged as a follow-up: a `wire_from_edges(&[GeometryHandle]) -> GeometryHandle` (or similar) `BrepKernel` method would let `extrudeWireDiff`/`faceArea`/`offsetFacesDiff` become exact for curved wires too.
  - **Face-id ↔ `FaceRef` mapping**: `BrepKernel` primitive constructors return a bare handle with no caller-chosen label, so `tessellate`'s Rust `face_groups`/`face_infos` entity ids can't literally equal the `Model`'s `FaceRef` strings. Implemented a normal-direction map (`boxFaceNormalMap`/`normalKey`): since `boxModelDiff` and `primitiveHandle("box", …)` are called with the *same* corners in the *same* call, I know each box face's world normal ↔ `FaceRef` a priori (bottom/top/±X/±Y), and match it against `face_infos[].normal` (quantized to 1e-3) at tessellate time. Verified exact for the box case with an in-file test (`createBoxFromCornersDiff includes one face bucket and matching FaceRef entity ids on tessellate`). Falls back to the raw Rust label for any solid without a tracked normal map (non-primitive/shell-derived solids) — those get a stable but not model-matching `entityId` until a similar per-construction mapping is added for extrude/loft/sweep results.
  - `shellSolidHandle` (best-effort topology reconstruction for shell-based/edited solids, e.g. `syncSolidsFromModel` after a vertex move): polyline-samples each face's wire, `planarFaceFromWire` + `sewFaces` + `healSolid`. Not exercised by this ticket's required test list; not guaranteed for non-planar or heavily-deformed shells.
