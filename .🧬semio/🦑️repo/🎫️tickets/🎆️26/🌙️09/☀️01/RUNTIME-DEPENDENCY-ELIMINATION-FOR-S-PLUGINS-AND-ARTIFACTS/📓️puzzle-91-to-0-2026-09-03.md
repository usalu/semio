## Root causes fixed (own-file edits, all under `✏️s/🔌️plugins/🧩️puzzle`)

1. **`command_from_action` trait signature (E0053, 3 sites)** — `ArtifactApp::command_from_action`
   moved to `Option<&dsl::DslValue>`. Puzzle keeps its `Command` enums' internal representation as
   an opaque `Option<serde_json::Value>` blob (unlike cad/architect, which eagerly parse into typed
   fields) — the ~90 individual `🎮️commands/*` handler files all read `args.get(...)` on that
   `serde_json::Value` and are untouched by design (not part of the 91 errors, would be a large
   unwarranted refactor to touch). Fix: convert the ONE boundary argument via the pre-existing
   `impl From<&DslValue> for serde_json::Value` bridge (`🧰️framework/🔨️modules/🌱️value/🦀️.rs`), then
   delegate to the existing `Puzzle{2,3,5}dCommand::{try_from_action,from_action}` unchanged. Files:
   `◻️2d/…/✏️editor/🦀️.rs`, `🧊️3d/…/✏️editor/🦀️.rs`, `🖐️5d/…/✏️editor/🦀️.rs`.

2. **`Puzzle{2,3,5}dCommand` derive shape** — these enums derived `value_derive::ToValue,
   value_derive::FromValue`, which cannot work while a variant field is `Option<serde_json::Value>`
   (no such impl exists nor should exist — see the ticket's own ban on
   `impl ToValue for serde_json::Value`). Swapped to `Serialize, Deserialize` (matches the enum's own
   doc comment: "`OpBinary` is a plain JSON-bytes bridge... a generic `args: Value` field is not
   representable in the DSL grammar" — `type Command: protocol::OpBinary` has no ToValue/FromValue
   bound, so this is safe). 2d needed a new `use serde::{Deserialize, Serialize};`.

3. **`Puzzle3dScale` / `Puzzle5dScale` missing `ToValue`/`FromValue`** — hand-written
   `Serialize`/`Deserialize` existed but not the DSL pair, breaking every containing struct's derive
   (8 + 4 error sites). Added hand-written `impl dsl::ToValue`/`impl dsl::FromValue` mirroring the
   existing serde impl's bare-number-or-`[x,y,z]`-array shape, in
   `🗿️artifacts/🧊️3d/🦀️.rs` and `🗿️artifacts/🖐️5d/🦀️.rs`.

4. **`Puzzle2dFillText`** — same gap: had hand-written `Serialize`/`Deserialize`, needed the
   `ToValue`/`FromValue` twin (encodes as `DslValue::String`). Added in
   `◻️2d/…/✏️editor/🎚️config/🦀️.rs`.

5. **Config/ConfigMutation `ArtifactDsl`/`OpBinary`/`OpText` impls** (2d/3d/5d, ~19 error sites) —
   these called `serde_json::{from_str,to_string_pretty,to_vec,from_slice,to_string}` directly on
   types that only derive `value_derive::ToValue/FromValue` (no unconditional serde). Rewrote to
   `dsl::json::{from_json_str,to_json_string}` (and `dsl::json::to_string_pretty` +
   `dsl::json::from_dsl_value` for the one pretty-printed `print_dsl`, to preserve the on-disk
   human-diffable format). `brush_candidates: Vec<serde_json::Value>` field on `Puzzle2dConfig`
   (component *and* its schema-descriptor twin) changed to `Vec<dsl::DslValue>` — this was the actual
   `serde_json::Value: ToValue/FromValue` violation at that derive.

6. **`MeshData: serde::Serialize`** (3 sites) — `mesh-engine` is deliberately serde-free (per the
   task brief, verified untouched). Converted the two `json!({"id":…,"data": mesh_from_kind(…)})`
   call sites (`◻️2d/…/🎲️board/🦀️.rs`, `🖐️5d/…/🧊️3d/🦀️.rs`) to build `dsl::DslValue` directly via
   `dsl::DslValue::object([...])` + `dsl::ToValue::to_value(&mesh)`, then `dsl::json::to_json_string`.

7. **`BrushCollisionFreeResult`/`BrushPreviewState`: serde::Serialize`** — both already derive
   `ToValue`/`FromValue` (no unconditional serde). Fixed the 3 production call sites
   (`🖐️5d/…/🧠️precompute/🦀️.rs`'s `brush_candidates`/`brush_preview_json`,
   `🧊️3d/…/🪟️windows/🧊️main/🦀️.rs`'s `world_brush_preview_json`) to route through
   `dsl::json::to_json_string`/`dsl::ToValue::to_value` instead of `serde_json`.

8. **`Puzzle{2,3,5}dSnapshot`/`Puzzle3dMutation`: serde::Serialize`** — these are the real
   artifact-level types, already migrated to unconditional `ToValue`/`FromValue` +
   `#[cfg_attr(test, derive(Serialize,Deserialize))]`. Fixed the production callers still using
   `serde_json` directly: the 5 example-fixture `document_json()` functions (2d/3d/5d ×
   concrete-forest/nakagin/capsule-dream), `set_active_example`'s two `LazyLock` static parsers,
   3d/5d editor's `parse_example_dsl`, and 3d's `gesture_preview`/`Puzzle3dFillDisplayPayload` decode
   — all switched to `dsl::json::to_json_string`/`from_json_str` or `dsl::ToValue`/`dsl::FromValue`.

9. **`ArtifactChild<SemioKitSnapshot>`/`SemioKitType`: serde::Serialize`** — `ArtifactChild<S>`
   already has an unconditional hand-written `ToValue`/`FromValue` in `🏪️store` (framework, untouched).
   Fixed `5d`'s `kind_catalogs_child_handle`/`normalize_kind_catalogs_for_snapshot_value` to route
   through `dsl::ToValue`/`dsl::json::to_json_string` instead of `serde_json::to_value`.

10. **`editor::puzzle{3,5}d`'s local "Document"/"Fixture" scratch-mirror struct family** — a
    deliberate structural twin of the real artifact snapshot (own doc comment: "stays a local
    structural-twin mirror... re-serialized to the JSON string this module's
    `document_from_json`/`.example(...)` call sites expect"), name-colliding with the real
    `crate::artifacts::puzzle{3,5}d::*` types but living entirely in `crate::editor::puzzle{3,5}d`.
    It derived `value_derive::ToValue, value_derive::FromValue` + `#[value(...)]` alongside serde,
    which cannot work while it holds `Option<serde_json::Value>` fields (`scale`, `meta`,
    `kindCatalogs`, `kindCompatibility`) — confirmed via grep that nothing in the crate ever calls
    `ToValue`/`FromValue` on these local types (only `serde_json::from_value`/`to_value`). Stripped
    `value_derive::ToValue, value_derive::FromValue` and every `#[value(...)]` attribute from the
    whole region (`◻️2d` has no such region; `🧊️3d` editor lines ~125–465, `🖐️5d` editor lines
    ~231–431), keeping the existing `Serialize, Deserialize` derive that was already there.

11. **`InteractionState.selection` field-not-method (E0599)** — `protocol::InteractionState.selection`
    is `BTreeMap<String, DomainSelection>` (a field), not a method — only
    `semio_framework_plugin::app::InteractionView` has a `.selection(domain)` convenience method.
    `puzzle2d_board_events_reduce` (2d editor) takes the raw `&protocol::InteractionState`, not an
    `InteractionView`; fixed its one call site to
    `interaction.selection.get(PUZZLE2D_INTERACTION_DOMAIN).cloned().unwrap_or_default()`. Left the
    *other* `interaction.selection(...)` call in `handle` untouched — that one's parameter really is
    `InteractionView`, which does have the method.

12. **Misc `DslValue`/`Value` boundary mismatches** — `semio_framework_plugin::selection_ids` moved to
    `Option<&DslValue>`; puzzle2d's own `selection_ids(args: Option<&Value>)` wrapper now bridges via
    `args.map(dsl::DslValue::from)`. `graph::manifest::KindDef.presentation` moved to
    `Option<DslValue>`; `manifest_catalog_rows` in 2d editor now matches
    `dsl::DslValue::Object(...)` and bridges each value back to `serde_json::Value` via `Value::from`.

### Why the number went UP, not to 0 — diagnosed, not guessed
The 134 current errors are dominated (76/134) by a NEW category never in the original 91:
`expected Value, found JsonValue` / `expected JsonValue, found Value` (E0308) at ~15 distinct call
sites across `🧊️3d`/`🖐️5d` editor `🦀️.rs`, plus a clutch of `E0599 no associated function
\`deserialize\` found for Puzzle5dCatalog{Part,Grip,Fastener,Rope}Kind`, one
`E0432 unresolved import \`dsl::os_pack::json::json\`: no \`json\` in \`json\`` (a literal typo/
incomplete import), and a large re-appearance of the SAME
`editor::puzzle3d::component::{Puzzle3dObject,Puzzle3dFixture,Puzzle3dTargetVolume,...}: serde::Serialize/Deserialize`
family I had already fixed (item 10 above) — i.e. the peer's local "Document"/"Fixture" scratch
struct region (same one I stripped `value_derive::ToValue/FromValue` + `#[value(...)]` from) is being
independently rewritten *again*, this time to hold `dsl::DslValue` fields directly instead of
`serde_json::Value` — a deeper version of the same fix, but landed mid-flight: the struct
definitions changed, the ~50 call sites across the file that still say `serde_json::from_value`/
`Value::Object`/`json!` have not all been updated to match yet. None of this traces to any file or
line I edited for the original 91 — confirmed by cross-referencing every new error's file:line
against my own 21-file edit list above; the overlap is exactly the "Document" region files, which
the peer's newer edit legitimately supersedes.

I deliberately did not attempt to complete this — it is a live, in-progress edit by another session

I did not attempt to chase or "finish" the other session's in-flight struct-field conversion — doing
