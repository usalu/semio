# The Eighth Seam — `app_commands!`'s hardcoded serde derive

Companion reading: `📓️final-plugin-manifests.md` (the agent that found this seam),
`📓️verified-outcomes.md` (the seven seams migrated before this one), `📓️serde-fanout-playbook.md`
(the conversion recipe this work reused).

## Headline

`semio_framework_plugin::app_commands!` (`🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️component.rs`)
no longer derives `::serde::Serialize, ::serde::Deserialize` on the `Command` enum it generates — it
now derives `$crate::ToValue, $crate::FromValue` (first-party). `semio-s-plugin-fem` compiles and is
now genuinely, verifiably serde-free — `serde` removed from both its 39 payload/nested types and its
`Cargo.toml`. `semio-framework-os-kernel` stays at the documented 0-errors/33-warnings baseline.

## The macro path problem, and how it was resolved

Three macro arms (plain, keyed, keyed+ctx) each had one line:

```rust
#[derive(Clone, Debug, PartialEq, ::serde::Serialize, ::serde::Deserialize, dsl::DslOps)]
```

changed to:

```rust
#[derive(Clone, Debug, PartialEq, $crate::ToValue, $crate::FromValue, dsl::DslOps)]
```

`$crate` (not a bare `ToValue`/`FromValue`) was the deliberate choice, for the reason the ticket
brief predicted: `macro_rules!` gives *item/macro* path segments the invocation site's own name
resolution (not full proc-macro hygiene) once they're multi-segment — the existing `dsl::DslOps` /
`::serde::Serialize` spellings already relied on this (their doc comment says so explicitly: "`dsl`/
`serde` are referenced unqualified... NOT via `$crate`, since they are NOT the defining crate").
Relying on the same convention for `ToValue`/`FromValue` would have required every one of the ~190
call sites to already have `use semio_framework_value_derive::{ToValue, FromValue};` in scope, which
is not the case (checked: 0/476 files needing conversion already had it). `$crate::ToValue` sidesteps
that: it always resolves to whatever crate defines `app_commands!` (`semio-framework-os-kernel`,
confirmed via `extern crate self as semio_framework_os_kernel;` in that crate's own `📦️glue.rs`),
regardless of the invoking plugin's own imports.

That required `semio-framework-os-kernel` to re-export the **derive macros themselves** (not just the
traits) at its crate root. It already re-exported the traits (`📦️glue.rs`: `pub use
crate::os_dsl::schema::{DslValue, FromValue, ToValue, ValueError};`). Added immediately after:

```rust
pub use semio_framework_value_derive::{FromValue, ToValue};
```

This is safe — a derive macro and a trait of the same name live in separate Rust namespaces (macro
vs. type), so the two `pub use` statements coexist with zero conflict at the crate root itself.

**Verified rather than assumed**: every crate invoking `app_commands!` (27 plugin crates, found by
walking up from each of the 183 files that use the macro to the nearest `Cargo.toml`) declares
`semio-framework-os-kernel` as a **direct** dependency, under the key `semio-framework-os-kernel`
with `package = "semio-framework-os-kernel"` (or no rename) — so `::semio_framework_os_kernel::`
paths generated by the derive resolve everywhere the macro is used. No exceptions found.

## A regression this surfaced and fixed: derive-macro/trait dual-import collisions

Re-exporting the derive macros under the same names as the traits at `os-kernel`'s crate root meant
every file that already imports **both** — `use semio_framework_os_kernel::{FromValue, ToValue};`
(or the `dsl::{...}` / `crate::{...}` self-alias spellings, for files mounted inside os-kernel or the
`semio-framework` facade) for the trait, **and** `use semio_framework_value_derive::{FromValue,
ToValue};` for the macro — now imports the same macro-namespace item twice, which is `E0252`. Found
by compiling, not by review: `semio-framework` (the facade crate) failed with exactly this on
`🧰️framework/🔨️modules/🛂️manifest/🦀️component.rs`.

Swept the whole repo (`🧰️framework` + `✏️s`) for the dual-import shape: 27 files import both names
from both sources. **21 were already safe** — they alias the derive import (`use
semio_framework_value_derive::{FromValue as FromValueDerive, ToValue as ToValueDerive};`), a
pre-existing convention (seen in `➗️mathematical`, `🔋️energy`) that anticipated exactly this
collision. The other **6 were real conflicts**, fixed by deleting the now-redundant
`use semio_framework_value_derive::{FromValue, ToValue};` line (the trait import alone now carries
both meanings, since it resolves through `os-kernel`'s crate root):

- `🧰️framework/🛍️products/💻️os/🔨️modules/🛂️manifest/🦀️component.rs`
- `🧰️framework/🛍️products/💻️os/🔨️modules/📖️playbook/🦀️component.rs`
- `🧰️framework/🛍️products/💻️os/🎚️config/🧬️schema/🧬️mutations/🪪️sign-in/🦀️.rs`
- `✏️s/🔌️plugins/🏭️process/🗿️artifacts/🧊️process3d/🏅️standards/🔖️1/🪆️subsets/✳️any/🧬️schema/📸️snapshot/🦀️component.rs`
- `✏️s/🔌️plugins/🏭️process/🗿️artifacts/🧊️process3d/🏅️standards/🔖️1/🪆️subsets/✳️any/🧬️schema/💡️inferences/🦀️component.rs`
- `✏️s/🔌️plugins/📐️cad/🧩️extensions/🏢️aec-building/🦀️component.rs`
- `✏️s/🔌️plugins/🏗️fem/🗿️artifacts/◻2d/🦀️component.rs` (fem's own `FemDof`/`FemCombinationTerm` file — see below)

Re-checked `semio-framework` after the fix: clean (0 errors, 25 warnings, all pre-existing/unrelated
dead-code and unnecessary-qualification lints).

## Payload-type sweep — measured, not assumed

The brief warned "most already have it from earlier waves — measure how many actually lack it before
assuming scale." Measured by parsing every `app_commands! { ... "id" [as "key"] => module::Payload,
... }` invocation repo-wide (183 files, 763 rows after resolving the 2d/3d-twin duplicate-name cases
correctly) and checking each named payload's own `#[derive(...)]` line for `ToValue`+`FromValue`:

**565 of 763 rows (74%) were missing them** — the opposite of "most already have it". Only five
plugin crates (`➗️mathematical` 7/7, `🏗️fem` 37/37, `🏭️process` 33/33, `💠️lowpoly` 47/47, `🪐️space`
70/70) plus 4 framework-internal test rows were already fully covered. The other ~20 plugin crates
(`✒️writer`, `🌀️procedural`, `🌊️flow`, `🌍️gis`, `🌿️vcs`, `🎞️animate`, `🎥️shooting`, `🎬️sequence`,
`🏛️architect`, `💡️reasoning`, `📋️forms`, `📏️layout`, `📐️cad`, `📕️norm`, `📖️playbook` (9 rows),
`📜️imperative`, `📸️remodel`, `🖍️draw`, `🖨️raster`, `🗒️note`, `🧱️block`, `🪵️sourcing`) had it missing
on nearly every row. Since flipping the shared macro is atomic — every invocation site is affected
the instant the derive line changes, with no way to roll it out crate-by-crate — leaving any of these
missing would have broken ~20 previously-compiling plugins. **All 565 were converted** rather than
left partial, per the ticket's "leave every crate compiling" constraint.

**Shape distribution** (nearly uniform, confirming "trivial DslRecord command struct" as claimed):
551 were exactly `Clone, Debug, PartialEq, Serialize, Deserialize, dsl::DslRecord`; 8 were the same
with fully-qualified `serde::Serialize, serde::Deserialize` and `dsl::MutationLeaf` appended; 5 added
`Default`; 1 was a minor spelling variant. Converted mechanically: `Serialize`/`Deserialize` tokens
(qualified or not) removed from the derive line, `ToValue, FromValue` inserted before the first
`dsl::`-prefixed token, a `use semio_framework_value_derive::{FromValue, ToValue};` import added
(scoped correctly for the 131 payloads nested inside their own `pub mod verb { ... }` block — 110 of
those already had `use super::*;` making a file-root import sufficient, the other 21, all in
`🏛️architect`, declare their own complete import list per module and needed the import placed
inside each module directly), and any now-dead `use serde::{Deserialize, Serialize};` removed where
provably unused elsewhere in the same file/module.

Field-level `#[serde(...)]` attributes existed on only 30 of the 476 touched files; all mirrored to
`#[value(...)]` per the established table (`rename_all`, `rename`, `default`,
`skip_serializing_if`, `deny_unknown_fields`) with one exception:

**One hand-written fix**: `✏️s/🔌️plugins/🌍️gis/.../📏️set-layer-stroke-scale/🦀️.rs`'s
`SetLayerStrokeScale.value: Option<f64>` used `#[serde(deserialize_with = ...,
serialize_with = "serialize_scale")]` — a hand-written finiteness guard rejecting `NaN`/`Infinity`
at the serde-encode boundary, unsupported by the derive (documented as hand-write-only). Removed the
attribute and the now-dead `serialize_scale` helper entirely rather than replicating it: the
identical finiteness check already runs, independently and load-bearingly, inside
`MutationKind::diff` (`mutation.invalid-number` fault) — the codec-level guard was defense in depth
for a JSON-text boundary this type no longer crosses via `Serialize`. `required_nullable` (the
paired `deserialize_with`, used by a sibling type too) was left untouched — no `ToValue`/`FromValue`
conversion needed there since its behavior already matches plain `Option<T>` handling.

## `semio-s-plugin-fem` — the acceptance test — now genuinely serde-free

Before this session fem's 37 command-payload structs plus 2 nested types (`FemDof`,
`FemCombinationTerm`) carried `Serialize, Deserialize, ToValue, FromValue` **additively** — a
restoration from an earlier session that discovered the macro's hard requirement but had no way to
remove it, since the macro itself still demanded serde. With the macro fixed, that requirement is
gone. Removed `Serialize`/`Deserialize` (and the fully-qualified `Eq, Serialize, Deserialize,
dsl::DslScalar` form on `FemDof`) from all 38 affected files, deleted the explanatory "🚧️ permanent
constraint" comments and `use serde::{Deserialize, Serialize};` imports (now stale — the constraint
they documented no longer holds), deleted the matching `#[serde(rename_all = "camelCase")]`
duplicate-attribute lines (12 structs already carried the `#[value(...)]` mirror alongside), and
removed `serde = { workspace = true }` plus its explanatory comment from fem's `Cargo.toml`.
`serde_json` was never present (fem's stdio bridge uses `pack::json`, confirmed clean by grep before
this session started).

`FemDof` needed no new work beyond the derive-line edit — it already has **hand-written**
`ToValue`/`FromValue` impls (`◻2d/🦀️component.rs:66`, a bare-string enum codec the derive's
tag-based enum support doesn't cover), which the earlier `#[derive(Serialize, Deserialize)]`-only
line means it was *never itself* satisfying the macro's transitive requirement through a derive —
worth flagging since a plain grep for `#[derive(...ToValue...)]` would have missed it and
under-reported fem's true coverage.

grep-confirmed after: zero `serde`/`serde_json` references in fem's own code outside
`🧪️oracle`/`🔬️probes`/`🏭️generator`/`🧫️fixtures` (the two remaining hits are a doc-comment mentioning
a *method name*, `to_serde_value`, on a foreign stdio bridge type — not a crate reference).

## Which plugin manifests can now drop serde

**Confirmed and done this session**: `semio-s-plugin-fem` — `serde` removed from `Cargo.toml`,
`serde_json` was never present.

**NOT done, correctly out of scope** (each crate's app_commands!-forced payload types are now clean,
