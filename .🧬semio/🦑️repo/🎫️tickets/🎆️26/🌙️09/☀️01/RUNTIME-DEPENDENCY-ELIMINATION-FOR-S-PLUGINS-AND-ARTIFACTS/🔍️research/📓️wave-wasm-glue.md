# Wave 6 — wasm-bindgen / js-sys / web-sys elimination from `✏️s/` production manifests

Scope: 25 `wasm-bindgen` + 6 `js-sys` + 3 `web-sys` entries (34 manifests total) under `✏️s/`.

## 1. Structural claim verification

The brief's claim — "every `wasm-bindgen`/`js-sys`/`web-sys` usage in `✏️s/` sits behind
`#[cfg(target_arch = "wasm32")]` and belongs to editor-playground/browser-preview, never the
`wasm32-wasip2` plugin ABI" — is **half right and half a trap**:

- **Confirmed true**: all 34 manifests declare the crates only in a
  `[target.'cfg(target_arch = "wasm32")'.dependencies]` block (one, `🏭️process`'s root crate,
  already used the more precise `cfg(all(target_arch = "wasm32", target_os = "unknown"))`).
- **The trap**: `target_arch = "wasm32"` alone is **also true for `wasm32-wasip2`**
  (`rustc --print cfg --target wasm32-wasip2` shows `target_arch="wasm32"`, `target_os="wasi"`,
  `target_env="p2"`). So this dependency **was already being pulled into the real plugin
  component build** for every manifest except `🏭️process`'s root crate — not merely an inert
  declaration. The fix is not "tighten the cfg to `target_os = "unknown"`" (deferred as a Wave-B
  fallback we didn't need) but **delete the dependency and its call sites entirely**, per the DoD
  (a target-scoped `[dependencies]` table still counts as a violation).
- Framework's own real component-guest ABI trio (`semio_owned_alloc_v1` /
  `semio_owned_dealloc_v1` / `semio_owned_poll_v1`, generated by the `plugin_exports!` macro in
  `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️component.rs`) is correctly gated
  `#[cfg(all(target_arch = "wasm32", target_env = "p2"))]` — i.e. it *is* precise, and it is
  untouched by this wave (class A was never needed: nothing routed plugin-runtime logic through
  wasm-bindgen).
- `✏️s/🔌️plugins/🎬️sequence` (not in our 34) is the reference pattern: hand-written `extern "C"`
  functions (`sequence_bridge_create/allocate/send/poll/...`) plus a hand-written JS host
  (`🟨️sequence-host.js`, `🟨️sequence-browser.js`) — zero wasm-bindgen/js-sys/web-sys.
- **Nothing under `✏️s/` builds for `wasm32-unknown-unknown`.** Repo-wide
  `grep -rln "wasm32-unknown-unknown"` hits only `🧰️framework/**` (the framework's own UI/editor
  engine crates use `wasm-pack`/`buildEngineWasm`) plus `rust-toolchain.toml`/`.cargo/config.toml`.
  `buildEngineWasm` (`🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/📦️packages/🟦️typescript/📦️index.ts`)
  builds per-playground "engine" crates declared in the generated
  `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/📇️registry/🤖️generated/🟦️playgrounds.ts` catalog.
  Cross-checking every row: **only `puzzle2d`'s row self-engines its own plugin crate**
  (`engines: ["./✏️s/🔌️plugins/🧩️puzzle/📦️packages/🦀️rust"]`); every other plugin (writer, gis,
  animate, shooting, fem, process, layout, cad, imperative, trinity, draw, raster, sourcing) has
  `engines: []`, and where an engine path *is* listed (gis/raster → `🗺️surface`) it points at a
  **framework** crate, never the plugin's own.

Net effect: 33 of the 34 manifests' wasm-bindgen bridges are **class (B), and provably dead** (no
build target ever produces a `wasm32-unknown-unknown` artifact for them). One (`🧩️puzzle`) is
class (B) and **provably live**.

## 3. Incidental cleanup: the `wasm_bindgen_futures` alias pattern

Six crates (`🌀️procedural`, `🎞️animate`, `📏️layout`, `🏗️fem`, `🔱️trinity`, `🖍️draw-fsm`, plus
`🧩️puzzle` which is untouched) carry
`#[cfg(target_arch = "wasm32")] extern crate semio_framework_async as wasm_bindgen_futures;` in
their `📦️glue.rs`/library root — a first-party alias so wasm-bindgen's own async-method macro
expansion (inside the now-deleted `#[wasm_bindgen] impl … { pub async fn … }` bridges) resolves
`wasm_bindgen_futures::…` to the framework's own async runtime instead of the real crate. This is
**not** itself a third-party dependency (it never appears in the `grep -rnE '^(wasm-bindgen|…)'`
gate), but once every bridge that needed it was deleted, the alias — and, in 5 of the 6 crates, the
`semio-framework-async` dependency it existed to satisfy — became genuinely dead code. Removed the
alias line from all 6 glue.rs files (procedural/animate/layout/fem/trinity/draw-fsm), and:
- procedural, layout, fem, trinity, draw-fsm: removed the now-fully-unused
  `semio-framework-async` target dependency entirely (nothing else in the crate references it).
- animate: kept `semio-framework-async` (it has a **separate, unconditional** `[dependencies]`
  entry used by real code — `semio_framework_async::WorkerSubmitErrorKind` in
  `…/🎬️present/…/🚪️io/🧬️mutations/💾️binary/🦀️component.rs`) but removed the now-redundant
  wasm32-target-scoped duplicate entry.
- `🧩️puzzle` keeps the alias (its bridge is live).

## 4. The one exception: `🧩️puzzle` — why it was left alone

`◻2d/…/✏️editor/🌉️wasm/🦀️component.rs`'s `BoardSession` is a **~50-method WebGPU canvas session**
(`attach_canvas`, `renderFrame`, `pointerDownScreen`, `wheelScreen`, `setSelectionOptions`, brush
tools, LOD, grid snap, …), built by `✏️s/🔌️plugins/🧩️puzzle/📦️packages/🦀️rust/📜️script.ts`'s
`WasmScript` → `runWasmPackWebBuild(...)` → npm package `@semio-tech/puzzle-wasm`
(`semio_puzzle_bg.wasm`/`.js`/`.d.ts`), consumed at
`🗿️artifacts/◻2d/…/✏️editor/🌉️wasm/🟦️component.ts` via `@semio-tech/framework-renderer-react`'s
generic `Board2dWasmSession` interface, registered as the `puzzle2d` playground's own build engine
(`playgrounds.ts`: `engines: ["./✏️s/🔌️plugins/🧩️puzzle/📦️packages/🦀️rust"]` — the **only**
self-engine row among all 34 manifests). `git log` on the bridge file shows a commit 6 days before
this ticket started (2026-08-26), i.e. this is live, maintained, shipping code, not a leftover.

`attach_canvas(canvas: HtmlCanvasElement, …) -> Promise` fundamentally needs a live JS object
reference (the DOM canvas) and wasm-bindgen's `Promise`/`JsValue` machinery — this is exactly the
class of problem wasm-bindgen/js-sys/web-sys exist to solve and that a hand-rolled owned-JSON
`extern "C"` ABI (the sequence-plugin pattern) is a poor fit for without reimplementing a large
slice of wasm-bindgen's object-table machinery by hand.

Per the ticket's own class-(B) options, the compliant fix is **route it through the framework**:
`🧰️framework/🔨️modules/✍️editor/📦️packages/🦀️rust` (`semio-framework-editor`, description:
"Canvas-agnostic editor state machine… for the framework") **already carries wasm-bindgen/
js-sys/web-sys as a framework dependency** and is the natural home — but `puzzle`'s own file
header explicitly documents that this exact code was *deliberately moved out of* the generic
framework `🗺️surface` module ("audit finding A4") specifically because it names puzzle-specific
types (`Puzzle2dSnapshot`, `BoardHost`, …) directly, which conflicts with the framework's
domain-neutral mandate. Making it framework-generic requires designing a real trait/macro
surface (something like a generic `WasmCanvasSession<H: BoardHostLike>` wrapper owning only the
canvas/WebGPU/Promise plumbing, with puzzle supplying a plain-Rust command-dispatch trait) —
genuine framework design work, plus a matching TS-side change if the exported JS class shape
moves, plus real interactive verification (WebGPU canvas + pointer/drag) that this environment
cannot safely rubber-stamp in one pass.

**This is the one manifest left unfinished.** Recommended follow-up (own ticket slice):
1. Design a generic wasm-bindgen canvas-session wrapper in `semio-framework-editor` (or a new
   sibling framework module) that owns `HtmlCanvasElement`/`Promise`/`JsValue` and dispatches by
   method name + JSON to a plugin-supplied plain-Rust trait (mirroring the `AbiHandleTable`/
   `AbiPageWriter` pattern already in `🧰️framework/🔨️modules/🌉️abi/🦀️component.rs`).
2. Reimplement `puzzle`'s `BoardSession` as an instantiation of that generic wrapper, with zero
   wasm-bindgen/js-sys/web-sys imports left in `✏️s/🔌️plugins/🧩️puzzle/**`.
3. Verify with a real `wasm-pack` build (`bun nx run <puzzle-crate> wasm`) and load the resulting
   `semio_puzzle_bg.wasm`/`.js` in a real browser page (a Claude Browser pane, or the actual
   `puzzle2d` dev playground) to confirm pointer/drag/attach-canvas still work end to end — static
   review is not sufficient proof for this one, given it is the only live consumer in the slice.
