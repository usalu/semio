# 📐️ First-party intrinsic-dimension parser — built and oracle-verified; wiring deferred, blast radius now precisely mapped

## The required API, as found (not guessed)

`preview_media_natural_size` (`🧰️framework/🛍️products/💻️os/🔨️modules/♾️infinite/🎲️board/🔌️ports/➡️directed/🕸️dag/🦀️component.rs:460`):

```rust
fn preview_media_natural_size(src: &str) -> (f64, f64) {
    use canvas::icon_codec::{board_resolve_icon_kind, BoardResolvedIcon};
    match board_resolve_icon_kind(src, |_| None) {
        BoardResolvedIcon::RasterRgba8 { w, h, .. } => (f64::from(w), f64::from(h)),
        BoardResolvedIcon::SvgPlain(s) | BoardResolvedIcon::SvgThemed(s) => {
            if let Ok((_, _, bw, bh)) = canvas::svg_icon::svg_icon_content_bounds_from_str(&s) { ... }
            (64.0, 48.0)
        }
        BoardResolvedIcon::None => (64.0, 48.0),
    }
}
pub fn image_widget_size(src: &str) -> (f64, f64) { preview_image_node_size(src) } // wraps the above
```

`src` reaches here from `set_image_src` (`🌊️flow/🖥️host/🦀️component.rs:1620`, ordinary guest-reachable
mutation handler) as a literal `data:image/...;base64,...` or `data:image/svg+xml...` string, or a
raw inline `<svg>` string, or an icon-catalog/shortcode/math/emoji/text token. `board_resolve_icon_kind`
(`🖼️canvas/🦀️component.rs`'s `icon_codec` module) decodes that string into a `BoardResolvedIcon`:
`RasterRgba8` (via `image::load_from_memory`, full pixel decode), `SvgPlain`/`SvgThemed` (raw SVG
string), or `None`. For the SVG branch, sizing goes through `svg_icon::svg_icon_content_bounds_from_str`
— which is **not** a `width`/`height`/`viewBox` attribute read; it parses via `usvg::Tree::from_str`
and returns the union of every visible path/text/image's *painted* bounding box. That distinction
matters for scope (see "What was NOT implemented" below).

## Formats implemented, and why

- **PNG, JPEG, GIF, WebP (VP8/VP8L/VP8X)** — all four, because `icon_codec::is_raster_data_url_payload`
  matches all four MIME prefixes (`png`/`jpeg`/`jpg`/`webp`/`gif`) as real `set_image_src` input, not
  hypothetical future need.
- **SVG width/height/viewBox** — implemented per the ticket brief's scope (XML attribute reading,
  not a renderer). Its exact resolution rules (unit conversion, percentage-vs-viewBox, absent vs.
  malformed vs. explicit-zero) were **reverse-derived against `usvg::Tree::size()` empirically**
  (dozens of probe cases run live against real `usvg` before writing the parser), not assumed from
  the SVG spec text, because `usvg` is lenient in ways the spec doesn't obviously imply (e.g. a
  non-numeric `width` is treated as *absent*, but a numeric zero/negative `width` is a hard parse
  failure; `viewBox` tolerates trailing extra numbers; an overflowing exponent like `1e400` parses
  to `inf` and is then treated as absent, not propagated).

## Before/after wasip2 link-count — unchanged, and exactly why

```
semio-s-plugin-puzzle: 104 (before) → 104 (after)
semio-s-plugin-flow:   104 (before) → 104 (after)
```

`cargo tree -i usvg / rustybuzz / fontdb / image` on `wasm32-wasip2` still resolve (not "nothing to
print") for both plugins — **unchanged from before this pass**, and that is a deliberate, considered
outcome, not an oversight. Wiring the parser into `preview_media_natural_size` alone cannot move this
number: `cargo tree` measures **Cargo-level dependency declarations**, not per-function reachability.
`usvg`/`image` are declared unconditionally in `semio-framework-os-infinite`'s `Cargo.toml` (`image`
in plain `[dependencies]`; `vello_svg` — which hard-depends on `usvg 0.46.0` as a **non-optional**
dependency regardless of its own feature flags, confirmed by reading its published manifest — in
both target tables). The only way to drop the count is to remove those declarations for
`wasm32-wasip2`, which requires **every** non-test production code path in that crate to stop
referencing `usvg`/`image` types on that target.

### Why that is a materially larger, riskier change than `infinite-host-deps-split.md` scoped

That research traced `usvg`/`image`'s only two production consumers as (a) `preview_media_natural_size`
(the bounds-query this session closes) and (b) `IconPaintCache::get_or_build` in
`➡️directed/🦀️component.rs` (the icon **painting** cache — `SvgDocument::parse_icons` +
`vello_svg::append_tree`/`render_themed`, plus `image::load_from_memory`'s full RGBA decode for
raster), and found `IconPaintCache`'s only real callers were host-only browser bridges + tests for
**flow and puzzle**. Tracing it further this session found:

1. **`IconPaintCache` is an unconditional struct field** of both `DagHost` (flow,
   `➡️directed/🕸️dag/🦀️component.rs:2535`) and `BoardHost` (puzzle,
   `➡️directed/➕️normal/🦀️component.rs:2312`) — not merely a function called from a gateable entry
   point. Its *lifecycle* methods (`new`/`close_step`/`clear`/`terminal_is_empty`/`Drop`) don't touch
   `usvg`/`image` and can stay unconditional; only `get_or_build`/`append_icon_at_screen_rect` (and
   their callers `paint_scene`/`build_vector_scene` and their private paint-helper functions) need
   gating — narrower than gating the whole type, but still a multi-function, multi-file cut.
2. **A third plugin uses this same shared infrastructure**: `semio-s-plugin-trinity`
   (`✏️s/🔌️plugins/🔱️trinity/`, depends on `semio-framework-os-infinite` directly, ships a
   `plugin-entry`-default `cdylib` — a real wasip2 component) defines its own
   `World::paint_scene` (`🌍️world/🦀️component.rs`) calling `self.board.build_vector_scene()`
   (puzzle's `BoardHost`, from `➕️normal`). **This plugin was not named or traced by
   `infinite-host-deps-split.md`.** Grepping trinity's own tree for a caller of its `paint_scene`
   found none inside the plugin itself — its caller, if any, is external and unverified by this
   session. Gating `BoardHost::build_vector_scene`/`get_or_build` for `wasm32-wasip2` without also
   gating trinity's `World::paint_scene` would be a **hard compile error** on trinity's own wasip2
   build (an unconditional `pub fn` referencing a now-target-absent method), a regression this
   session did not introduce and is not positioned to safely fix blind.
3. A `paint_scene`/`build_vector_scene` caller audit repo-wide also surfaced
   `🗺️surface/🕸️node-graph/🦀️component.rs` (wraps the same `DagHost`, its own real caller is a
   `#[wasm_bindgen(js_name = renderFrame)]` binding — browser-only, not wasip2-reachable, but not
   independently re-verified end-to-end this session) and
   `🧰️framework/🔨️modules/📺️renderer/🧑️‍🎨️engine/🧱️elements/EngineCanvas/🧊️component.rs` (a
   host-only rendering engine, plausibly never part of any plugin's wasip2 component, also not
   independently re-verified this session).

Closing this fully means gating `IconPaintCache::get_or_build`/`append_icon_at_screen_rect` plus
every `paint_scene`/`build_vector_scene` entry point across **at least three** plugin surfaces
(flow, puzzle, trinity) and re-confirming `🗺️surface`/`📺️renderer` are genuinely unreached on
`wasm32-wasip2`, then running `cargo check --target wasm32-wasip2` **foreground** for each affected
plugin — each observed elsewhere in this ticket to take 30+ minutes. Attempting that within this
pass's remaining budget, for a third plugin this session had not previously traced, would mean
shipping a cross-cutting change to shared painting infrastructure without the foreground
verification this ticket's own `📓️deflate-inflate-defect.md` and `📓️verified-outcomes.md` exist to
demand — the exact failure mode ("written but unverified" landing on a default path) this ticket was
written to stop repeating. It was deliberately left for a follow-up pass instead, with the blast
radius now mapped precisely enough that a follow-up doesn't have to re-derive it.

## What was NOT implemented, and why

`svg_icon_content_bounds_from_str`'s real job (**painted-content bounding box**, i.e. the union of
every visible path/text/image's rendered extent — used to auto-fit compiled Typst icon SVGs that
carry padding beyond their content) is a materially different, harder computation than
width/height/viewBox attribute reading, and is out of this module's scope by the ticket brief's own
words ("XML attribute reading... do not build a renderer"). This module reads the **declared**
intrinsic size instead — the textbook-correct "natural size" semantics for a genuinely uploaded
image/SVG widget (exactly what `preview_media_natural_size`'s own name promises), but not a drop-in
replacement for icon-auto-fit bounds. A future wasip2 arm for `svg_icon_content_bounds_from_str`
using this module would therefore be a **disclosed, intentional** behavior difference from native
(declared box vs. painted-ink box), not a bug — same "two implementations, one signature" pattern
already used for `wgpu`'s no-adapter case elsewhere in this ticket.
