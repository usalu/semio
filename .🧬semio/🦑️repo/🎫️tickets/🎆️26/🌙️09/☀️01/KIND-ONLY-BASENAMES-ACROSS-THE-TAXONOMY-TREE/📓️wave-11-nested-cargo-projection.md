## Three things I had to fix beyond the catalog's literal text — each verified, not guessed

1. **Cargo.toml's own `build`/`[lib].path`/`[[bin]].path` fields.** The catalog's `mappings` and
   `authoredSourceFragments` never touch these three manifest fields (the fragments are prose-only),
   but the moved `Cargo.toml` still said `path = "🦀️lib.rs"` / `build = "build.rs"` / `path =
   "📦️bin.rs"` — files that no longer exist at those relative locations. Repointed all three at the
   catalog's own `adapters` (`📚️library/🦀️.rs`, `🏗️builder/🦀️.rs` → see next point, `💾️binary/🦀️.rs`),
   which is exactly what those adapters exist to be pointed at.
2. **Cargo build scripts cannot be named with an emoji-only stem.** `build = "🏗️builder/🦀️.rs"`
   fails with `error: invalid character '🦀' in crate name: build_script_🦀️` — Cargo derives an
   internal `build_script_<stem>` identifier from the build path's basename, and only `[lib]`/`[[bin]]`
   paths are exempt from this (their crate name comes from `[package]`/`[[bin]].name`, not the file
   stem). Verified by actually invoking `cargo check` twice — once with the emoji path, once after.
   Fix: added one ASCII-named `build.rs` at `destinationRoot` (`📦️packages/🦀️rust/build.rs`) whose
   entire body is `include!("../../🏗️builder/🦀️.rs")`, i.e. an extra, Cargo-mandated shim in front of
   the catalog's own kind-only adapter — the adapter itself is untouched and still byte-identical to
   the ledger. This is a real Cargo limitation, not a taxonomy oversight I get to silently paper over
   elsewhere: it will hit every OTHER `build.rs` this repo renames to `🦀️.rs` too.
3. **The build script's own logo-asset path was already stale before I touched it.** `🏗️builder/🦀️.rs`
   read `manifest_dir.join("../../../../🔣️semio_logo.svg")` — but the real file has already been
   renamed to `🧑️‍🎨️engine/🔣️.svg` by an unrelated, already-completed rename elsewhere in the repo.
   The catalog's own `cargo-build-logo-watch`/`cargo-build-logo-output` `authoredSourceFragments` are
   `oldValue === newValue` (a no-op) for this exact line, so applying them literally would not have
   caught this — confirmed by running the actual build script (`cargo check`) and hitting `copy semio
   logo: NotFound`. Repointed the *source*-side references only (2 of 3 `semio_logo` mentions); left
   the `OUT_DIR` output basename alone since it is self-consistent (the same generated code both
   writes and reads it under that name).

## Blocked and left deliberately alone — each with evidence, not force

* **`🐚️plugin-bridge.ts`** — disk hash/size no longer match the pinned `sourceHash`/`sourceSize`
  (24176 bytes vs pinned 24228). `git diff HEAD` shows the entire delta is reference-repointing text
  from the *separate*, already-completed wave-1 kind-only rename (`🟦️boot.ts`→`🟦️.ts`,
  `🧊️component.rs`→`🎯️targets/🧊️wgpu/🦀️.rs`, etc.) — not a semantic edit, but still a byte mismatch
  against the ledger. Left at its old location, untouched; its 3 `authoredSourceFragments`
  (`plugin-bridge-boot-prose-1/2/3`) were skipped, not force-applied.
* **`🧪️vitest.config.ts`** — absent from the working tree (`git status` shows an unstaged delete from
  the same wave-1 cleanup). Recovered its exact preimage from `git show HEAD:<path>` and confirmed
  BYTE-FOR-BYTE against the pinned `sourceHash`/`sourceSize` (`c1b2fbb4…`, 211 bytes) before trusting
  it — then materialized the destination (`🟦️typescript/🧪️test/🟦️s.ts`) directly with the catalog's
  `newValue`, since `oldValue` there is provably the file's entire original content.
* **An interdependent group of 10 `authoredSourceFragments`** (6 in `📜️script.ts`, 4 in
  `📋️project.json`) were applied, then REVERTED. `single-package-artifact-producer` (which defines
  `runBrowserArtifacts`) failed to match because a concurrent, unrelated edit had already rewritten
  that exact span of `📜️script.ts` to add a `decodeAstralEscapes` helper (fixing how `Bun.build`
  mangles astral-plane/emoji text in bundled output — directly relevant to this emoji-named repo, just
  not to this ticket). The other 6 fragments in that group *did* match and applied, leaving 3 live call
  sites invoking `runBrowserArtifacts` with no definition, and `writeFileSync`/`relative` used but no
  longer imported — a real compile break I introduced by partially applying an interdependent set.
  Reverted all 10 back to `oldValue`, confirmed self-consistent again (imports match usages, all
  classes/router registrations restored), and left the whole "producer consolidation" feature for
  later, deferring to whoever owns the `decodeAstralEscapes` work in progress.
* **`🎠️activation.rs`** (os-host) — its `wgpu-owner-glue` reference token was updated (required, listed
  as a `referenceConsumer`), but the file itself was NOT renamed to `🎠️activation/🦀️.rs`. It is not
  part of this catalog's `mappings` (it lives entirely outside `sourceRoot`/`destinationRoot`), and a
  SEPARATE, unrelated fixture — `🧫️fixtures/🧪️nested-cargo-package-authority/🔣️.json` — records its
  path in `destinationPathBytes` measurements. That authority fixture's own SHA-256 is pinned as
  `structuralGoldenSha256` inside the FROZEN `🧫️fixtures/🧪️remaining-package-purity-authority/🔣️.json`
  (a hard-constraint file this ticket must never touch). Renaming `activation.rs` would desync the
  authority fixture without any way to re-pin the frozen file's golden hash, so it was left exactly
  where it is. Verified `nested-cargo-package-authority` is not actually read by any live code path
  (`grep` across `📚️library/🔍️discovery` and `🧹️normalization` found zero references to that filename)
  — it is orphaned documentation, not a gate, but the frozen pin over its hash is still real and still
  off-limits.
