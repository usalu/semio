### 1.3 The second oracle route — `🧪️tests/🏛️export-epjson-runs-in-energyplus/`

Three files, `🥒️.feature` + `🦀️.rs` + `🐍️.py`, tagged
`@capability-energy-model-1-io @oracle-energyplus-25-2-0-direct-epjson @oracle-input-subject-raw
@comparison-ordered-json-v1`.

The handoff is the framework's own `@oracle-input-subject-raw` mechanism (the `📷️io-lowpoly-png-1`
precedent): the Rust SUBJECT's real output is the raw epJSON, handed to the Python ORACLE verbatim
via `subject_raw_inputs`; the oracle never re-authors a document and never reads the Rust.

| scenario family | cases | what the oracle actually does |
| --- | --- | --- |
| `schema-validity-<case>` (`@level-quick`) | 600, 600FF, 610, 620, 640, 900, 900FF, 910, 920, 940 | runs `jsonschema` against EnergyPlus's own 858-object-type `Energy+.schema.epJSON`, asserts zero violations with their JSON paths, then re-derives every fact the subject claimed straight from the bytes |
| `nothing-dropped-<case>` (`@level-quick`) | 600, 900 | independently re-derives, from the committed model alone, the refusal codes a faithful writer OWES, and the list of model entity names absent from the document |
| `energyplus-run-<case>` (`@level-long`) | 600, 600FF, 900, 900FF | validates, then runs `energyplus -a -w … -d … <file.epJSON>` on those exact bytes, reads `eplusout.sql` through stdlib `sqlite3` and the `Zone Information` record out of `eplusout.eio`, and compares against the committed `🔮️energyplus.json` |

**Tolerance 3 % annual, ±0.5 K free-float** — not the sibling case's 10 %. Both sides here are the
same EnergyPlus 25.2.0 build reading the same `WindowMaterial:SimpleGlazingSystem`, so the
+5.7…+8.1 % glazing offset `📓️bestest-contract.md` documents is *common to both* and cannot appear
as a difference. The only thing that can move these numbers apart is the document.

**No ladybug, no openstudio wheel, no honeybee** in the adapter: stdlib `sqlite3` + `jsonschema`
only. That is not a shortcut, it is a requirement — the repo test host provisions its Python oracle
environment from the root interpreter (3.14) and W-B measured that the compiled `openstudio` wheel
has no cp314 build. Reading EnergyPlus's own tables directly is also one fewer library between the
claim and the answer.

**W-F → whoever owns `🚪️io/🦀️.rs`'s composer registry.** The epJSON leaves are NOT registered as

lane's. Until then the codec is reachable through the editor commands above and through the test

### 3.3 Trap: a transient `eplustbl.htm` fatal

The FIRST `oracle-epjson` run of step 3 died with

```
**  Fatal  ** OpenOutputTabularFile: Could not open file "…/direct-work/eplustbl.htm" for output (write).
```

after writing `eplusout.sql`, `.eio`, `.eso` and the rest into that same directory. The identical
command re-run against the identical inputs succeeded, and three manual runs with different `-d`
paths and working directories never reproduced it, so this is a transient filesystem race between
EnergyPlus's tabular writer and the `shutil.rmtree` + `mkdir` that immediately precedes it — NOT a
path-length or non-ASCII-path problem, which was the first hypothesis and was measured and
discarded. It matters only because it is LOUD: `_run_energyplus_epjson` checks the exit code AND
`eplusout.sql`'s existence and reports the `.err` tail, so a run that dies this way cannot be
mistaken for a clean one, and a stale `eplusout.sql` from a previous run cannot be read as a fresh
result (the work directory is emptied first — W-B's §7 trap).
