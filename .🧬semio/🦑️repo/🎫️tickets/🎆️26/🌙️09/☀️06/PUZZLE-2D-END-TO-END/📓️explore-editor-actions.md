## 0. Headline findings (read this first)

1. **The ticket brief's "6 Migrated / 34 BatchOnlyPendingRewrite" does not match current source.** Source has exactly **4** `.action_interactive_job(..., Migrated)` declarations (`addNode`, `forceLayout`, `setActiveExample`, `applyBoardEvents`, editor `:2267-2270`) and **34** `BatchOnlyPendingRewrite` (editor `:2271-2304`). Two more command ids — `setLocale`, `setTerminology` — have **no classification declaration at all** (default `Unclassified`, same as `BatchOnlyPendingRewrite` for UI-dispatch purposes: both fail `validate_ui_dispatch_classification`, `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️.rs:12078-12084`, which only special-cases `Migrated`). 4 + 34 + 2 = 40, matching the ticket's "40 actions" count, but the split is **4 / 34 / 2‑unclassified**, not 6/34. A background agent confirmed puzzle2d is the *only* editor in the repo (checked against cad, flow, dag, wires, sequence, writer, animate, procedural/generation2d&3d, vcs, and puzzle3d) that never declares `setLocale`/`setTerminology` as `ActionDefinition`s at all — every other editor, including puzzle3d (`.view_action("setLocale", ...)` 3d‑editor `:7217`, `.action_interactive_job("setLocale", Migrated)` 3d‑editor `:7394`), does. This is a real manifest gap in puzzle2d, not a shared/injected default.
2. **The plugin's own `🔏️publication-authority/🔣️.json` fixture is stale relative to source** — it lists only 3 routes for `Puzzle2dPlayApp` (`addNode`, `forceLayout`, `setActiveExample`), all still `BatchOnlyPendingRewrite`, and doesn't mention `applyBoardEvents` at all (`✏️s/🔌️plugins/🧩️puzzle/🔏️publication-authority/🔣️.json:6-14`), while source has already flipped all 4 to `Migrated` with real `PUBLICATION_CONTRACTS`.
3. **The TS oracle (`✏️s/🔌️plugins/🧩️puzzle/📦️packages/🟦️typescript/📜️script.ts`) is *also* stale for puzzle2d specifically** — its `ownerOracle` function hard-codes the assumption that `Puzzle2dPlayApp`'s source contains **no** `bounded_first_step_tool_proofs!` macro and **no** dedicated retained-command job factory (`script.ts:85-89`: asserts the production source does NOT contain `bounded_first_step_tool_proofs!`, `BoundedFirstStepCommandJobFactory` impl, or `registry.register(BoundedFirstStepCommandJobFactory`). But the editor file already has its own `Puzzle2dRetainedCommandJobFactory` + `bounded_first_step_tool_proofs!` block (editor `:1075-1141`, `:2012-2021`), mirroring 3d/5d's pattern. Given this, the audit script would currently fail (`bun ./📜️script.ts publication-authority-audit Puzzle2dPlayApp`) for reasons independent of the fixture desync in point 2 — **the TS oracle script needs a real code change for puzzle2d** (treat it like 3d/5d's branch: check for `Puzzle2dRetainedCommandJobFactory`, its `PUBLICATION_CONTRACTS`, and the `Puzzle2dConfigStorePreparationFactory`/`Puzzle2dArtifactStorePreparationFactory` equivalents), not just a fixture JSON edit. This exact fixture-vs-source desync on `Puzzle2dPlayApp` was independently observed and worked around from the *other side* by the puzzle3d ticket (it added owner-name scoping to the audit script specifically so puzzle3d could be verified "while puzzle2d's fixture is desynced by another session" — see §5).
4. **Shared cross-dimension infrastructure that puzzle3d needed to newly build already exists for puzzle2d and is already wired up**: `Puzzle2dRetainedCommandJobFactory` (`ToolJobFactory` + `ArtifactOwnedToolJobFactory` impls, editor `:1075-1141`), the `bounded_first_step_tool_proofs!` macro block (`:2012-2021`), a working `build_tool_job` (`:2028-2050`), and two already-implemented bespoke `PuzzleCommandWork`s (`Puzzle2dActiveExampleWork` `:1243-1376`, `Puzzle2dForceLayoutWork` `:1429-1554`+). What puzzle2d is missing relative to 3d is almost entirely **registration-list membership** for the other 34-36 ids, not new architecture — very close to 3d's "wave E" mechanical-wiring situation.
5. **The single largest real risk-item is the fill-session family** (`setFillCount` + 7 `brushFillSession*` verbs), backed by `🎮️commands/🧮️set-fill-count/🦀️.rs` at **2,401 lines** — an async background-job architecture (`WorkerPool`, a process-global `AtomicPtr` session-slot registry, its own `impl InteractiveJob for ArtifactBoardFillJob`), not a synchronous `reduce()`-shaped chunked computation. This cannot be wrapped in `PuzzleCommandWork`/`BoundedFirstStepCommandWork` as-is; it needs its own bespoke job/factory design, analogous in spirit but not in code shape to puzzle3d's `fillBuildTick`/`Puzzle3dPrecomputeCommandWork` (which puzzle3d *could* bridge because its precompute cache round-trips through a persisted `Config.fill_checkpoint` field each call — worth checking whether puzzle2d's `Puzzle2dConfigMutation::Fill { runtime: Puzzle2dFillRuntime }`, `🎚️config/🦀️.rs:326`, gives it the same bridging property; if so the model is closer than it first looks, but the *code* (WorkerPool vs. synchronous `handle_action_impl`) is materially different from 3d's).

## 3. Wave grouping for the 34 pending + 2 unclassified actions

### (a) Mechanical wiring only — generic reduce + `BoundedFirstStepCommandWork` fallback (24 actions)

Once (i) `build_config_store_one_item_preparation_factory`/`build_artifact_store_one_item_preparation_factory` exist and (ii) a generic `puzzle2d_retained_reduce_generic`-style fallback function is written (mirroring `puzzle3d_retained_reduce`'s "3 special cases then `app.handle_action_impl`" shape, or more simply extracting `handle()`'s dispatch-match-plus-diff body, editor `:1928-2007`, into a standalone fn callable without `ArtifactView`/`DraftView`), these are pure registration-list edits — no new business logic, matching puzzle3d's largest bucket:

`engagementInput`, `engagementControlSelect`, `engagementSubmit`, `engagementAbort`, `focusSelection`, `setBrushNodeSize`, `setGridFactor`, `setBrushKindWeights`, `setCamera`, `setLodModeForPane`, `setGridSnapEnabled`, `setSuggestionOffset`, `setSelectionFlag`, `deleteSelection`, `duplicateSelection`, `patchInspectorNodes`, `brushCycleCandidate`, `brushSetCandidateIndex`, `brushOpenSlot`, `brushCommitSlot`, `brushCancelSlot`, `setLocale`, `setTerminology`, `setActiveExampleStep`.

Edit sites per action (same 4 lists for every id in this bucket):
1. Add the id (string literal) to `PUZZLE2D_RETAINED_TOOL_IDS`, editor `:1072`.
2. Add an `ArtifactToolPublicationContract { tool_id: "<id>", lanes: &[...] }` row to `PUBLICATION_CONTRACTS`, editor `:1135-1140` (lane per the "Correct lane(s)" column in §1's table).
3. Add the id (string literal) to the `tools: [...]` list inside `bounded_first_step_tool_proofs!`, editor `:2020`.
4. Add a match arm in `build_tool_job`'s `match request.command.action_id() { ... }`, editor `:2035-2041`, e.g. `"<id>" => Box::new(crate::retained_command::BoundedFirstStepCommandWork::new("<id>", puzzle2d_retained_reduce_generic, puzzle2d_generic_extent))` (names illustrative — whatever the new generic fn/extent pair end up called).
5. Flip `.action_interactive_job("<id>", InteractiveJobClassification::BatchOnlyPendingRewrite)` → `Migrated`, editor `:2271-2304` (for `setLocale`/`setTerminology`, this is instead *adding* a new `.view_action("setLocale"/"setTerminology", ...)` declaration plus a new `.action_interactive_job(..., Migrated)` call — they have no existing manifest entry, see §0.1).
6. Update `✏️s/🔌️plugins/🧩️puzzle/🔏️publication-authority/🔣️.json` to move the id into a `Migrated` group with matching lanes (whole fixture needs a broader rewrite regardless — see §0.2).
7. Add the id to the puzzle-local `PUZZLE2D_RETAINED_TOOL_IDS`-derived `evidenceToolIds`/vectors only if a hostile-fixture test needs a concrete vector for it (existing pattern only exercises `addNode`/`forceLayout`/`setActiveExample`, `🗄️retained-jobs/🔣️.json:7`).

Caveat flagged by the command-handler audit: `patchInspectorNodes`, `setSelectionFlag`, `deleteSelection`, `duplicateSelection` iterate over an unbounded `selected_ids()` list with **no extent cap today** — an `extent()` fn modeled on `applyBoardEvents`'s `PUZZLE2D_BOARD_EVENT_BATCH_LIMIT` (editor `:1147-1156`) should be added as part of the migration, not assumed safe by default (`_ => 1`-style extents would silently mis-budget a large selection).

### (b) Needs a real multi-step `Work` completion (9 actions + 1 already-done pair)

- **`reorganize`** (editor `:2293`) — calls the exact same `force_layout::force_layout` handler as the already-Migrated `forceLayout` (editor `:1968`, `"forceLayout" | "reorganize" => force_layout::force_layout(ctx)`). Cheapest fix in the whole ticket: add `"reorganize"` to `PUZZLE2D_RETAINED_TOOL_IDS` (`:1072`), `PUBLICATION_CONTRACTS` (`:1135-1140`), the proofs `tools:` list (`:2020`), and a `build_tool_job` arm pointing at the *existing* `Puzzle2dForceLayoutWork::default()` (`:2037`'s sibling) — zero new logic.
- **`redrawHandles`** (editor `:1967`, handler `🎮️commands/🔄️redraw-handles/🦀️.rs:7-11`) — looks trivial (12 LOC) but is a single whole-fixture, non-yielding engine call (`apply_edge_handle_snap_to_fixture_v1_json`) with no size guard, structurally identical to what `forceLayout` looked like *before* it got `Puzzle2dForceLayoutWork`'s chunked/extent-bounded treatment. Wrapping it in the plain generic reduce risks the same step-deadline/output-cap failure mode `forceLayout` was rescued from — should get its own bounded, incrementally-chunked `Work` (or reuse/extend `Puzzle2dForceLayoutWork`'s machinery) rather than the bucket-(a) generic fallback.
- **The fill-session family (8 actions): `setFillCount`, `brushFillSessionBegin`, `brushFillSessionStep`, `brushFillSessionClear`, `brushFillSessionAdopt`, `brushFillSessionCancel`, `brushFillSessionRetry`, `brushFillSessionDiscard`.** Backed by `🎮️commands/🧮️set-fill-count/🦀️.rs` (**2,401 lines** — by far the largest command file; every other command file is 7-107 lines). This owns a process-global `AtomicPtr` session-slot registry, a `WorkerPool`, and its own `impl InteractiveJob for ArtifactBoardFillJob` — a genuine async background job, not a `reduce(command, snapshot, config, interaction, hover) -> Emit` shape. It cannot be expressed as `PuzzleCommandWork`/`BoundedFirstStepCommandWork` without either (i) a bespoke `Work` type that bridges into the existing `WorkerPool`/session-slot machinery each `step()`, or (ii) a different job/factory design entirely, separate from `Puzzle2dRetainedCommandJobFactory`. `Puzzle2dConfigMutation::Fill { runtime: Puzzle2dFillRuntime }` (`🎚️config/🦀️.rs:326`) does give it a persisted round-trip field analogous to puzzle3d's `fill_checkpoint` bridging — worth checking whether that's enough to make a bespoke `Work` viable, but treat this as its own sub-effort/wave, scoped and estimated separately from everything else in this ticket, exactly as the command-handler audit recommends.

## 4. Where puzzle2d already differs from the 3d precedent

- **`applyBoardEvents`** has no 3d equivalent verb — it's puzzle2d's single browser-flush verb: the `🖥️Board2dHost/🟦️.tsx` frontend component (`🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🖥️Board2dHost/🟦️.tsx:88,112`, `PUZZLE2D_FLUSH_NOW_EVENT_NAMES = new Set(["select","preselectCancel","brushCandidates","brushPlace","edgeCreate","edgeDelete","nodeDelete"])`) batches interactive board events client-side and flushes them all through `applyBoardEvents`'s `eventsJson` argument in one call, rather than dispatching one server action per board interaction. Already Migrated; its reduce fn (`puzzle2d_board_events_reduce`, editor `:1164-1206`) is the best template in the file for what a generic reduce for the rest of bucket (a) should look like — it rebuilds scene+host from `(command, snapshot, config, interaction)` with **no** `ArtifactView`/`DraftView`/`EngineHandles`/live `operation` (explicitly sets `operation: None`, editor `:1194`), runs the SAME per-event dispatch table (`apply_board_events::apply_board_events`), and diffs before/after exactly like `handle()` does.
- **`forceLayout`** already got the bespoke-Work treatment puzzle3d didn't need for its own `forceLayout`-shaped concerns until directly asked — puzzle2d's is a real chunked N-body-style layout simulation (`Puzzle2dForceLayoutWork`, editor `:1429-1554`+, its own `Puzzle2dForceStage`-like staged state machine per the `🗄️retained-jobs/🔣️.json` hostile-mutation vectors referencing `Puzzle2dForceStage::Nodes`/`Repel`/etc — though this exact enum name wasn't directly located in the editor file scan, the fixture's hostile mutations at `🗄️retained-jobs/🔣️.json:19-23` assert its cursor-stage names must exist verbatim, mirroring puzzle3d's identical pattern for its own `Work`s). This means puzzle2d's `redrawHandles` (see §3b) is exactly the kind of case 3d's extent-budget-audit flagged: a whole-document single-shot engine call masquerading as "trivial."
- **No `🌉️wasm` bridge asymmetry found**: puzzle2d has its own `✏️editor/🌉️wasm/{🦀️.rs,🟦️.ts,🧪️fixtures/}` bridge directory, structurally parallel to puzzle3d's and puzzle5d's equivalents — nothing puzzle2d-specific stood out here relative to the other two dimensions.
- **The fill-session architecture (§3b) is the deepest divergence from 3d.** Puzzle3d's fill precompute (`fillBuildTick`, `Puzzle3dPrecomputeCommandWork`) stayed inside the synchronous `reduce()`/`Work::step()` shape by caching progress in `app.precompute` (a `RefCell` rebuilt each call, restored from `config.fill_checkpoint`) — expensive but still fundamentally a "compute a bounded chunk, return, get called again" loop. Puzzle2d's fill session instead delegates to a real multi-threaded `WorkerPool` + process-global session registry + its own `InteractiveJob` impl, i.e. genuinely concurrent background work outside the request/response cycle. Applying the 3d recipe's "just wrap the existing call in `BoundedFirstStepCommandWork`" trick here would be a **category error** — it would need a bespoke retained-job design, not a `PuzzleCommandWork` at all, or a `Work` that itself polls/bridges into `WorkerPool` state (unclear from static reading alone whether that's architecturally sound — flag to the ticket owner as an open design question, not a known-safe migration).
- **`setActiveUtility`'s cross-cutting coupling**: unlike puzzle3d where `setActiveUtility` is a clean framework-injected action, puzzle2d's handler (`🎮️commands/🧰️set-active-utility/🦀️.rs:16-19`) additionally constructs a `Puzzle2dFillActionCtx` and calls `discard_fill_job(...)` inline — i.e., switching utilities silently cancels any in-flight fill job. This couples an otherwise-trivial framework action to bucket (b)'s hardest item and should be re-examined once the fill-session job architecture is redesigned, since `setActiveUtility` is already `Migrated`-by-injection today and this coupling already runs live.
