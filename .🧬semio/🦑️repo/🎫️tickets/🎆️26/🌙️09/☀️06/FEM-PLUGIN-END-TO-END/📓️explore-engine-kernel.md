## 1. Per-file API / implementation / tests

### `➕️algebra/🦀️.rs` (319 lines)
Dense linear-algebra primitives: `Mat2`, `VecD(Vec<f64>)` (with `dsl::ToValue`/`FromValue`), `MatD` (dense matrix incl. `lu_solve`, `add_triple_product`, `add_at`), `Mat3d`, plus free 3D vector helpers `vec3d_sub/length/normalize/cross`. No tests in this file (exercised indirectly by every other module's tests). No `todo!`.

### `🔢️sparse/🦀️.rs` (5769 lines, the largest file)
- **Storage**: `Coo` (triplet builder, `add`/`add_block`/`to_csr`/`to_csc_sym_upper`/`to_dense`), `Csr`, `CscSym` (symmetric upper-triangular CSC).
- **Direct solver**: `ldlt_factor(&CscSym) -> LdltFactor` (symmetric indefinite LDLT, tracks `negative_pivot_count` for buckling-mode sign), `LdltFactor::solve`/`solve_many`.
- **Iterative solver**: free `pcg(...)` plus a full `PcgJob`/`PcgJobConstruction` **interactive, checkpointable, cancellable** job (`InteractiveJob` impl, `PcgStats`, `PcgStage`, `PcgQuality`, `PcgPreview`, `close_step`, checkpoint bytes round-trip).
- **Eigensolver**: `subspace_iteration(&LdltFactor, &Csr, n, p, max_iter) -> EigenPairs` (shifted subspace/simultaneous-iteration eigensolver for the smallest modes, used for both modal and buckling) plus its own interactive `SubspaceIterationJob`/`SubspaceRestoreCursor`.
- **Reordering**: `rcm_order(&[Vec<usize>]) -> Vec<usize>` (Reverse Cuthill-McKee bandwidth reduction).
- **Interactive-job scaffolding**: `LdltJob`/`LdltRestoreCursor`, `MountedScalarSlots`, `NumericalPageCursor`, `NumericalCheckpointFault` — a whole bounded-resource, resumable-job framework wrapping every numeric kernel so the OS's step-budget/cancellation contract is honored (see gap analysis below on whether the plugin actually calls these vs. the plain free functions).
- **Tests (26 `#[test]` fns)**: `ldlt_matches_dense_lu_on_random_spd`, `ldlt_matches_dense_lu_on_1d_laplacian`, `ldlt_solve_many_matches_solve_per_column`, `ldlt_reports_zero_pivot_on_singular_matrix`, `pcg_matches_ldlt_and_dense_lu`, `rcm_reduces_bandwidth_on_scattered_path_graph`, `dense_symmetric_eigen_jacobi_matches_known_eigenvalues`, `subspace_iteration_matches_diagonal_analytic_case`, `subspace_iteration_matches_dense_jacobi_on_small_nondiagonal_case`, plus an extensive suite of checkpoint/resume/cancellation/timing tests for `PcgJob`/`LdltJob`/`SubspaceIterationJob` (e.g. `pcg_job_checkpoint_resume_is_exact`, `ldlt_job_checkpoint_resume_matches_reference`, `p6h_ldlt_microcursor_max_plus_one_cancel_deadline_stale_replay_and_numerical_parity`, `adversarial_solver_steps_stay_below_eight_milliseconds` — a real wall-clock perf-budget assertion at `sparse/🦀️.rs:5731`).

### `🏗️model/🦀️.rs` (648 lines)

## 2. Mesh-preview / meshing bridges — what mesh, and who validates it

**2D**: `FemRegion{outline, holes, thickness}` → `crate::mesh::triangulate` (own Bowyer-Watson Delaunay, **holes supported**) → `Tri3Cst` elements for solving; separately, `build_semio_mesh_snapshot` extrudes the SAME triangulation by the region's thickness, splits to tets, and takes boundary faces to build the exported OBJ/STL solid (`◻️2d/🕸️meshing/🦀️.rs:159-188`).

**3D**: `FemSolid{outline, holes, height, layers, base_z}` → same `triangulate` on the footprint → `extrude_tri_mesh` (N layers) → `split_to_tets` → **Tet4** elements for solving (`🧊️3d/🕸️meshing/🦀️.rs:74-114`). So 3D is always tet, always footprint-derived from a 2D triangulation — there is no direct tet/hex meshing of an arbitrary 3D solid boundary, only prismatic extrusion of a 2D outline.

**Fixture provenance — genuinely external, not self-referential.** The fixtures under `🧫️fixtures/{region-one-hole, scale-one-hole-1e6, scale-one-hole-1e3, scale-one-hole-1e-3, degenerate-sliver-outline, region-two-holes, degenerate-hairline-thickness, polygon-triangle, polygon-l-shape, rect-unit-square, rect-thin-plate, rect-floor-slab}/{expected.obj, expected.stl, expected.metrics.json}` are generated by `✏️s/🔌️plugins/🏗️fem/🗿️artifacts/◻️2d/🏅️standards/🔖️1/🪆️subsets/🌐️any/🏭️generator/📜️script.ts`, which:
1. Builds each `FemRegion` shape independently via **`manifold-3d`** (`CrossSection(...).extrude(...)`, a real solid-boolean/CSG kernel, EvenOdd fill so holes subtract themselves without needing to agree with our winding convention) — this is the volume/area/genus ground truth.
2. Exports via **`three.js`**'s `STLExporter`/`OBJExporter`, then re-imports via `STLLoader`/`OBJLoader` (an independent reader, no knowledge of our snapshot type).
3. Measures round-trip fidelity with `manifold-3d` (`relativeVolumeError`, `relativeAreaError`, `normalizedSymmetricHausdorff` — both metrics required; the oracle's own doc-comment records a same-shape-wrong-elevation defect that passes on volume alone (`~1.3e-16`) but is caught by Hausdorff at `4.465e-01`).
None of this reimplements `crate::mesh::triangulate`/`extrude_tri_mesh`/`split_to_tets` — the oracle registration (`◻️2d/🏅️standards/🔖️1/🪆️subsets/🌐️any/🔮️oracle/🔣️.json`) is explicit that this validates the **carrier capability** (a polygon-with-holes prism round-trips through OBJ/STL), not that our triangulator agrees with anyone else. There is also a `fem2d-python-independent` oracle (second Python implementation of the whole mutation/model schema, declined third-party libraries like `code_aster`/`OpenSees`/`anastruct`/`PyNite` because none of them edit-the-model rather than solve-it) — this is a **mutation-schema** oracle, not a numerics oracle, and its own rationale text flags a real defect it found (`FemNode`/`FemElement`/etc. are empty objects in the mutations JSON schema, a verbatim-but-untyped copy of the snapshot schema).
**Net finding: there is a real, independent geometry oracle for the mesh EXPORT capability, but no third-party numerical oracle anywhere in this repo for the FE solver itself** (stiffness/mass/modal/buckling/stress) — those are only validated by the in-repo closed-form/patch tests listed in §1/§4.

## 3. Inference path and one traced call

`🧬️schema/💡️inferences/🦀️.rs` for `Fem2dInference` (`✏️s/🔌️plugins/🏗️fem/🗿️artifacts/◻️2d/🏅️standards/🔖️1/🪆️subsets/🌐️any/🧬️schema/💡️inferences/🦀️.rs:1-30`) declares **exactly one derived/cached inference field: `bounds`** (`Fem2dBounds`, geometric bounding box + node count, see `📦bounds/🦀️.rs`). There is **no cached inference for displacements, reactions, stresses, mode shapes, or buckling factors** — the `ArtifactInferrer` for fem2d only wires `bounds` through the OS-wide inference cache (`ArtifactInferrer::infer_cached` passthrough, doc'd as intentional since bounds is a whole-snapshot scalar with no per-entity caching benefit).

**Trace: editor action → mutation → analysis → viewer, two distinct paths found:**

1. **Cheap/synchronous path** (results window render): `✏️editor/🎭️modes/✏️edit/🪟️windows/📊️results/🦀️.rs:render()` (dispatch on `DisplayMode::{Static,Modal,Buckling}`) calls `crate::fem2d_engine::fem2d_solve_all(doc)` / `...modal_buckling::fem2d_modal_mode_values(doc, mode_index)` / `...fem2d_buckling_mode_values(doc, case_id, mode_index)` **directly and synchronously on every render**, re-solving the whole model from the current `Fem2dSnapshot` each time (comment at `✏️editor/🦀️.rs:420`: "`fem2d_solve`/`fem2d_solve_all` run fresh inside `render()`/`export_media` whenever the results..."). This is genuinely event-sourced (recomputed from the snapshot, no mutable cached state) but bypasses both the inference-cache mechanism and the interactive-job machinery — a large model re-solves on the UI thread on every frame/interaction.
2. **Interactive/background path** (mounted analysis session): `✏️editor/🧵️session/🦀️.rs` (2662+ lines) implements a real `BoundedJob`/`InteractiveJob`-based **mounted revision session** (`FEM2D_MOUNTED_JOB_KIND = "semio.fem2d.mounted-analysis"`) that drives `FemJobGraph` through an explicit 8-stage plan (`ValidateReferences → BuildDofMap → OrderEquations → Assemble → Factor → Solve → Recover → Finalize`, `✏️editor/🧵️session/🦀️.rs:1163-1187`), each stage step-budgeted/cancellable/checkpointable, feeding a `Fem2dLiveVisual`/`Fem2dMountedVisualLease`. Every editing action (`addNode`, `addBar`, `addMaterial`, `addRegion`, `addLoadCase`, `setSelfWeight`, `setAnalysisSettings`, `removeSelection`, etc.) is registered `InteractiveJobClassification::BatchOnlyPendingRewrite` (`✏️editor/🦀️.rs:732-747`), i.e. the OS's interactive-job gate requires these mutations to route through this job machinery rather than a synchronous handler; `setCamera`/`setResultDisplay`/`setLocale` are `Migrated` (direct, non-batched).

So the sparse/mesh/analyses kernel's extensive `InteractiveJob` infrastructure (§1) **is** wired into the plugin for mutation-triggered re-analysis (path 2), but the actual results-window rendering that a user sees after switching to the results tab (path 1) still goes through the plain synchronous `fem2d_solve_all`/`fem2d_modal_mode_values` calls — two parallel solve paths exist and it is not obvious from this reading alone whether path 2's committed result ever reaches path 1's rendering, or whether path 1 is a completely independent re-solve. This seams worth a follow-up runtime trace (not verifiable without running the app).

| ShellFacet3 | Flat shell patch test (membrane+bending); no closed-form cantilever comparison found | scikit-fem (shell support is limited) | Patch test yes (exact); cantilever/buckling tests are qualitative (`deflects_toward_tip_load`, `compression_destabilizes...`), not closed-form |
| Modal (free vibration) | Euler-Bernoulli cantilever beam natural frequencies `βₙ²/(2πL²)·√(EI/ρA)` | scipy.sparse.linalg.eigsh, scikit-fem | **Yes**, exists — `modal_cantilever_matches_analytical_frequencies`, 10% tolerance, in-repo closed form (not cross-checked against scipy) |
| Buckling | Euler pinned-pinned column `π²EI/L²` | scipy (via geometric-stiffness eigenproblem), scikit-fem | **Yes**, exists — `buckling_euler_column_matches_analytical_load`, 10% tolerance, in-repo closed form |
| Nonlinear (large-deflection/material) | N/A | code_aster, OpenSees | **Not implemented at all** |
| Meshing (2D Delaunay + holes) | Area/volume conservation, angle bounds | gmsh, triangle, meshpy, **manifold-3d + three.js (already used)** | **Yes**, both in-repo area/volume tests AND the external manifold-3d/three.js OBJ/STL round-trip oracle described in §2 |

**Summary**: every implemented analysis type (linear static, modal, buckling) and every implemented element family has at least one in-repo closed-form or patch-test check; NONE of the numerical solver paths (stiffness/mass/modal-frequency/buckling-load values) are cross-validated against an actual third-party library (scikit-fem, PyNite, anastruct, scipy) — only the mesh-EXPORT geometry capability has a genuine external oracle (manifold-3d/three.js). The "10% tolerance" on the two analytical benchmarks that DO exist (modal cantilever, Euler column) is fairly loose for what should be an exact match to <1% for a 7-9-element discretization.

## Gaps to fix (prioritized)

1. **No third-party numerical oracle for the solver itself.** The mesh-export geometry has a real external oracle (manifold-3d/three.js); the stiffness/mass/modal/buckling numerics have none. Every existing analytical check is an in-repo hand-calc, not cross-validated.
2. **Loose tolerances on the two analytical benchmarks that exist.** `modal_cantilever_matches_analytical_frequencies` and `buckling_euler_column_matches_analytical_load` both use 10% tolerance (`🧮️analyses/🦀️.rs:3442`, `:3477`) — should tighten to 1-2% once cross-validated against a reference, to actually catch regressions.
3. **"Order-of-magnitude only" tests are not real correctness checks**: `quad4_cooks_membrane_tip_deflection_is_positive_and_finite`, `plate_dkt_simply_supported_square_center_deflection_right_order_of_magnitude`, `hex8_meshed_cantilever_deflection_is_right_order_of_magnitude` — these would pass even with a formulation bug that's merely "roughly right." Should become closed-form/reference-value assertions.
4. **PlateDkt has no `geometric_stiffness`** — plate elements are structurally excluded from linear buckling analysis (intentional per the prior ticket, but still a real capability gap if plate/shell buckling is ever expected).
5. **No nonlinear analysis** (large-deflection, material nonlinearity) — confirmed absent by both grep and the API survey. If load-history-dependent or P-Delta-sensitive results are ever required, this is a from-scratch addition.
6. **Two parallel solve paths with unclear reconciliation** (§3): the results-window `render()` synchronously re-solves via `fem2d_solve_all` every call, while a separate `FemJobGraph`-based mounted-analysis session exists for mutation-triggered background solves. Whether these ever converge (i.e., whether a large model's results-window rendering can actually block the UI thread) needs a runtime trace, not just static reading — flag for a follow-up ticket with a running app.
7. **3D meshing is always a footprint-extrusion (2D triangulation → prism → tets)** — there is no true unstructured 3D tet mesher for an arbitrary solid boundary. Not necessarily wrong for the current `FemSolid` schema (which only models exactly that shape), but worth flagging if the schema is ever extended to general solids.
8. **`fem2d-python-independent` oracle's own rationale documents an unresolved defect**: `../🧬️schema/🧬️mutations/🔣️.json`'s member types (`FemNode`, `FemElement`, etc.) are empty objects with no properties — a copy-paste artifact from the snapshot schema, flagged by whoever wrote that oracle registration but apparently never fixed.
