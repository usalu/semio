## 1. Test platform mechanics

- Schema: `🧰️framework/🛍️products/🦑️repo/🔨️modules/🧪️test/🧬️schema/🔣️.json` (schema v2, `$id` `.../repo/test/v2`). Unit of coverage: `artifact × standard × smallest owning subset × runtime mutation × expected outcome class × fixture × subject implementation × platform`.
- Host: `🧰️framework/…/🧪️test/📦️packages/🐍️python/🐍️.py` (286 lines) — a plain `python3` script (`argparse`, `hashlib`, `json`, stdlib only). Invoked as `python3 🐍️.py --plan <plan.json> --out <results.jsonl> --adapter <component.py>`. It never parses feature files itself; it executes a plan the TS coordinator already built. Verified this is a plain, buildless script (head/imports checked) but did **not** run it — no plan.json exists to feed it (would need `bun ./📜️script.ts …` to generate one, which is out of scope here).
- Coordinator/logic: `🧰️framework/…/🧪️test/📦️packages/🟦️typescript/🟦️.ts` (6036 lines). Key pieces:
  - `fixtureUrisIn` (🟦️.ts:984) extracts every `shared://`/`local://`/`asset://` URI from `feature.description` + every step's `text`/`docString`/`dataTable`, **after** Scenario Outline → Examples substitution (`<placeholder>` replaced per row at 🟦️.ts:458).
  - `resolveFixtures` (🟦️.ts:1001-1014): `asset://` resolves against the **subset owner root** (`discovered.owner`), not a fixtures dir; `existsSync` failure ⇒ URI reported `missing`.
  - `test contract` (root of `🧰️framework/…/🧪️test/📜️script.ts:828`, wired as nx target `test-contract` in `📋️project.json`) runs `validateAllContracts`, writes `.🧬semio/🦑️repo/⚡️cache/breaches/testing.json`, exits 1 on any breach.
- **Oracle manifests** (`🧪️oracle/🔣️.json`, schema-linked to the same v2 schema) register per-owner `oracles[]`, `noOracleDecisions[]`, `mutationCatalogs[]` (kind vocabulary + fixture vector names — v1), and `mutationManifests[]` (capability/dispatch/outcome/oracleRequirements — v2, the actual release gate).
- **Subset policy** (`🪆️subsets/🔣️.json`) declares an artifact's conformance subsets and, when only one exists, `"subsetPolicy": "single"` with a rationale (silences the `unsplit-artifact-subset` medium finding).
- **`.feature` + `asset://`**: a Scenario Outline's steps carry `<col>` placeholders; the Examples table supplies concrete `dir`/`fixture` values; after substitution the literal `asset://…/<dir>/…/<fixture>/…` string must exist on disk under the owner root.
- **`verified-native-second-implementation`**: the *only* `SupplementalOracleKind`-adjacent kind that can discharge `missing-external-oracle` without a real third party (🟦️.ts:2841 `QUALIFYING_ORACLE_KINDS`). Earned, not asserted — `nativeSecondImplementationBreaches` (🟦️.ts:4868-4995) requires, in order: (a) `nativeSecondImplementation` evidence object present, (b) `format` is `isSemioNativeArtifact` (never a real interchange format), (c) the owner's own `mutationManifests` actually manifest that format, (d) **capability**-level 100% coverage (`ownCapabilities` ⊇ `manifestCapabilities` — see gap below), (e) a credible `noThirdPartySurvey` (named ecosystems + ≥1 declined candidate with a ≥10-char structural reason), (f) `subjectImplementationLanguage` ≠ `secondImplementationLanguage`, (g) non-empty `specificationSource`, (h) `fixtureCoverage.vectors > 0` and `capabilitiesCovered` non-empty.

### Breach kinds
`TESTING_BREACH_KINDS` (🟦️.ts:1388) is the **family** enum: `testing/taxonomy`, `testing/contract`, `testing/fixture`, `testing/oracle`, `testing/dependency`, `testing/discovery`. Each `breach()` call also carries a specific `id` string (task's "kinds"), all under family `testing/oracle`:
- `missing-external-oracle` (🟦️.ts:4839) — no qualifying oracle registered for a required capability.
- `insufficient-engine-independence` — qualifying oracles found but fewer independent engine families than required.
- `native-second-implementation-unearned` / `-not-native` / `-partial-coverage` / `-same-language` (🟦️.ts:4892-4991) — the specific ways a `verified-native-second-implementation` claim fails its earn-check.
- Plus family `testing/fixture` → `missing-fixture` (🟦️.ts:1677) and `orphan-fixture` (🟦️.ts:1683), which is what item 2 below actually trips.

- **Gap the automated gate cannot see** (unverified as a bug, but structurally real): `nativeSecondImplementationBreaches`'s 100%-coverage check (🟦️.ts:4935, "partial-coverage") compares **capability sets**, not mutation-kind sets. Likewise `oracleRequirementBreaches` (🟦️.ts:4816) only checks "is there ≥1 qualifying oracle for this capability" per mutation — `commit-reconstruction`'s own `oracleRequirements` entry is satisfied by the same registered oracle even though that oracle's own evidence explicitly excludes it. **The contract-phase gate is green for `commit-reconstruction` by construction, not because it is actually discharged by a second implementation.** This is the single most important finding of this audit — it means the manifest schema's discharge granularity (capability) is coarser than the taxonomy's actual claim granularity (kind), for any artifact — like this one — with a single blanket capability across all mutation kinds.

## 4. Fixture realism vs. "exhaustive mutations with real-world tests"

Inspected `🗞️delete-asset`'s before-fixture (`…/🧬️mutations/🗞️delete-asset/🧪️tests/🗑️removes-asset-a-170889/📸️snapshot/⬅️before/🔣️.json`, 345 lines — the fixture the plugin's own oracle rationale calls its "fully-realistic RemodelingSnapshot" reused across 40 vectors):
- **Scale**: 2 streams (1 video `stream-a` with 2 frames + 1 image-sequence `stream-b` with 1 frame), 2 cameras, 2 GCPs (one with 0, one with 1 observation), 1 rig entry. This is a minimal smoke-test scene, not remotely "exhaustive" in scale — it is exhaustive only in *mutation-kind* coverage, not in scene complexity.
- **Intrinsics plausibility**: `cam-a` (brownConrady): fx=fy=1000, cx=512, cy=384 — internally consistent as a **1024×768** sensor model, but `stream-a.source` declares `width:1920, height:1080` for the very stream bound to `cam-a`. **Principal point/focal length do not match the stated frame resolution** — for a real 1920×1080 phone camera you'd expect cx≈960, cy≈540, fx/fy in the 1400–1800px range (typical ~28mm-equiv FOV). `cam-b` (pinhole, fx=fy=800, cx=320, cy=240) is self-consistent for a 640×480 frame but `stream-b` (bound to `cameraId: null`, not `cam-b`) has no `source`/resolution at all, so nothing to check it against.
- **Payloads**: `results.sparse.points`/`colors`, `results.dense.positions`/`colors`/`confidence`/`classification`, `job.sparsePointCloudPreview` are short base64 blobs (e.g. `"AAAAAAAAAAAAAAAAAACAPwAAgD8AAIA/"` ≈ 3-4 float32s) — i.e. **placeholder stand-ins for a handful of points, not real point-cloud data**. `results.mesh.mesh` is only a content-addressed `childId` reference (no inline geometry); `watertight` stats (512 vertices / 1020 triangles / genus 0) are asserted numbers, not derived from any actual mesh payload in the fixture.
- **Verdict**: these are well-formed, schema-conformant **unit vectors** engineered to exercise one mutation each — good for catching structural/dispatch regressions, but they are not "real-world" in the photogrammetry sense (no plausible multi-view geometry, no real imagery, no real reconstructed points/mesh).

### What a real-world fixture set would look like
- A small (5–15 image) multi-view still sequence of one object/scene, shot or synthesized with **known ground-truth camera poses and a shared, plausible intrinsics block** matching the images' actual resolution (e.g. real EXIF-derived fx/fy/cx/cy for a modern phone: ~4000×3000 image, fx≈fy≈3300px, cx≈2000, cy≈1500).
- Real (or realistically synthesized) sparse/dense point clouds and a real watertight mesh — even a tiny one (a cube or simple prop) — computed once by an actual pipeline (or borrowed from a public SfM benchmark) rather than hand-typed float arrays, so `results.*` payloads are drawn from genuine reconstruction output.
- At least one GCP set with real-world-plausible geo coordinates and >1 observation per GCP across multiple streams, to exercise the georeferencing/GCP-cascade mutations meaningfully.
- **Existing sample data check**: grepped `✏️s/🔌️plugins/📸️remodel` and `🗄️stdio` for `.jpg|.png|.mp4|nakagin|sample|dataset` — no photogrammetry sample imagery/video assets were found anywhere in either tree (only the tiny `🗣️.dsl.semio` demo document under `📚️examples/🎬️demo/🖼️assets/`, which is a DSL text file, not imagery). **The repository does not currently hold any candidate real-world photogrammetry dataset** (e.g. no bundled "Nakagin" or similar public SfM sample) to build such fixtures from; one would need to be sourced or synthesized and its license/provenance recorded per the fixture-manifest schema's `provenance` block.

## 5. Third-party oracle candidates already in the repo for photogrammetry-adjacent outputs

`✏️s/🔌️plugins/🗄️stdio/🗿️artifacts/` already contains fully realized stdio artifacts (schema/oracle/io, not just stubs) for exactly the formats item 5 asked about:
- `🧱️ply` (PLY point cloud/mesh) — standard `🔖️1.0`, subset `✳️any`, has `🔮️oracle`.
- `🧊️gltf` (glTF 2.0, mesh output candidate) — standards `🔖️2.0`, subsets `♾️any`/`🎞️animation`/`💿️buffer`/`🎬️scene`/`💎️material`/`🕸️mesh`/`🪪️asset`/`🦴️skin`/`🎥️camera`, each with its own `🔮️oracle`/`🧪️oracle`.
- `🗽️obj` (Wavefront OBJ mesh) — standard `🔖️3.0`, subsets `📐️geometry`/`🎨️material`, each with `🔮️oracle`.
- `☁️las` (LAS/LAZ point cloud) — standard `🔖️1.0`, subsets `📼️vlr`/`📍️points`/`🎩️header`, each with `🔮️oracle`.
- `🔺️stl` (STL mesh) — standard `🔖️ascii`, subset `✳️any`, has `🔮️oracle`.

Backing third-party crates are already declared (optional, `oracles` feature-gated) in `✏️s/🔌️plugins/🗄️stdio/🧪️oracle/📦️packages/🦀️rust/Cargo.toml`: `ply-rs = "0.1"`, `las = "0.11"`, `tobj = "4"` (OBJ), `stl_io = "0.8"`. **No glTF crate is declared** in that Cargo.toml despite the `🧊️gltf` artifact tree existing — the gltf oracle's actual backing library was not verified in this pass (unverified — would need reading each gltf subset's own `🔮️oracle/🔣️.json` `package`/`ecosystem` fields, not done here for time).

**Does remodel's own `🚪️io` register any of these formats?** No. `…/✳️any/🚪️io/` only has `📥️import/🧩️deserializers/🗿️artifacts` and `📤️export/🧵️serializers/🗿️artifacts` subtrees (plus the top-level `🦀️.rs`/`🟦️.ts`) — did not enumerate their leaf contents in this pass (unverified whether they import/export PLY/OBJ/LAS/glTF today), but the `🧪️oracle/🔣️.json`'s own rationale is explicit that remodel's *native document* format (streams/calibrations/GCPs/job) has no third-party reader, which is a different question from whether remodel's **outputs** (sparse/dense clouds, mesh) could be *exported* to PLY/OBJ/glTF and checked against those already-registered stdio oracles as a **supplemental** (not discharging) cross-check. That would be a real, currently-untaken opportunity: since `replace-sparse`/`replace-dense`/`replace-mesh-result` mutations write point/mesh payloads, exporting those to PLY/OBJ/glTF and round-tripping through the already-registered stdio oracles would add genuine third-party evidence for the payload *shapes* even though the outer job-document envelope stays native.
