# Mounted Receipt Cardinality and Staging

Current source inspection found that the first adjacent group receipt design equated operation count with member edit count and copied a kernel mutation ID into `EditRef.edit_id`. Those are distinct authorities. A genuine two-operation member edit can have mutation IDs `edit#0` and `edit#1` while its single member edit remains `edit`. The build agent was given this concrete correction before integration: three operation vectors use the total forward-operation count; the member edit vector uses the exact touched member count; each member edit copies its original prepared edit ID exactly once. Native and neutral coverage must include this case and retain every causal dependency.

Original private group publication waits for each prepared receipt ACK before advancing the next member. Therefore complete host payload capture must happen per member before its ACK. Waiting for all future child edit IDs before capturing the parent's receipt would deadlock that authority ladder.

The root integration will retain one complete private receipt row per prepared member, including all encoded forward operations, fully framed inverse operations, all metadata/dependencies, the exact document handle, and the exact prepared edit ID. The row is captured before its original publication moves into staging. Original command child IDs go into dedicated preborn backing and remain stable before the final group metadata container is initialized. After every member row is retained and acknowledged, final operation vectors can be admitted using their now-known total cardinality and assembled one original ownership move per turn. The complete host group receipt and command record must be ready before the single common visibility flip.

The existing receipt primitives have actual passing runtime evidence through the current fallible Pack API: source 5 laws / 78 assertions; native 9 laws passed, 1090 outside the filter, summary 0.106 s, fresh Nx exit 0 in 16.5 s. This covers JSON/Hex output ownership, complete operation framing, original causal fields, cancellation, and child handle hashing. It does not yet prove the complete Pack-backed member row, full mounted consumer, command page integration, final fresh release build, or browser gates.

Command log growth must preserve the original visible history before the decision. Moving old live entries out during preparation, silently reserving at the decision, or permanently refusing after initial capacity fills would fail that requirement. The build agent owns a canonical paged command log with separately admitted eight-record pages, stable borrowed iteration, constant decision linking, and explicit original owner retirement. Its runtime proof and actual app integration remain required.
