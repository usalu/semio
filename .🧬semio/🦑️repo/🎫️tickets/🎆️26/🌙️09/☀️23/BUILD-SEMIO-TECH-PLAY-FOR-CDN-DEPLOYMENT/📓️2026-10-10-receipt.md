# 2026-10-10 receipt (cargo native-build provenance receipt: producer + readers)

Scope: `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/**` (note: the brief's `…/📚️library/🏃️process/📦️artifacts/…` path does not exist; the real owner is `🔨️modules/🏃️process/📦️artifacts/🏗️native-build`) and every producer/reader of the receipt. TypeScript only; no Rust crate is in scope, so there are no per-crate cargo result lines. Raw logs: `.🧬semio/🦑️repo/⚡️cache/play-fleet/receipt/*.log`.

## 1. Cause

A completed invocation of the playbook-procedural wasm graph (135 units, 19,439 distinct inputs, 379 proc-macro captures) produced a 337 MB receipt (`cargo-unit-provenance-cargo-artifacts-G9djNn.json`, release-pjvAl2). Breakdown of that file:

| part | bytes |
| --- | --- |
| `compilerResources[].resources` (69,907 rows, only 16,085 distinct, paths repeated 5x per row, directory rosters twice) | 114 MB |
| `compilerResources[].text` (copy of every `observation.json`) | 79 MB |
| `units[].depInfo[].text` (copy of every `.d`, 3 path copies per source) | 53 MB |
| `units[].inputs` (path + kind + sha per unit, 91,416 rows for 19,439 paths) | 23 MB |
| everything else | < 1 MB |

The writer also kept the bytes of every file it read in a Map (`.d`, `observation.json`, every consumed resource), serialized the lot with one `JSON.stringify` and wrote it once. 128 MiB cap, then 8 GiB stopgap, then `RangeError: Out of memory` for larger graphs.

## 2. Design (schema-first)

New leaf module `native-build/🧾️receipt/` (schema `🧬️schema/🔣️.json`, fixture `🧫️fixtures/🔣️.json`, tests `🧪️tests/🟦️.ts`, code `🟦️.ts`). Document schema `semio.cargo.provenance-receipt/v1`:

- One JSON object, written in order: scalars, `units`, `buildScripts`, `buildResources`, `compilerResourceRoot`, `compilerResources`, `invocationInputs`, `observedAtMs`, then the interned tables `strings`, `inputs`, `witnesses`.
- Every path is an index into `strings`. Every unit input is an index into `inputs` (`[pathRef, kind, sha256]`, one row per path; a conflicting second observation of a path is refused). Every resource row is an index into `witnesses` (hash-consed by content; key order preserved so the readers' `JSON.stringify` comparisons against the original `observation.json` still hold).
- Dep-info is no longer text: `{path, sha256, baseDirectory, sources[], checksums[]}` where `sources` and the rustc `# checksum:blake3=… file_len:…` rows are parsed from exactly the digested bytes. Compiler resource captures and build-script `OUT_DIR` roster files are kept as `sha256`; the readers now read the bytes from the tracked file (they already required the file's current digest to equal `sha256`, so no verification power is lost, and a refused/vanished capture now fails closed).
- `producerUnit`/`callerUnit` are unit indexes, decoded back to the same `message` object.
- Strict decoder: unknown schema, unknown fields (a `text` copy is refused), out-of-range refs, malformed digests all throw `Cargo provenance receipt …`. Old-format receipts are therefore refused and silently re-acquired by the ledger loader (no migration, no legacy path).
- Bounded memory writer: `CargoProvenanceStreamV1` serializes each record as it completes (1 MiB flush), file bodies are never retained (only digest + length), interned strings are flat copies (so tables do not pin `.d`/`observation.json` texts through substrings). The receipt streams to a private `.<name>.<uuid>.tmp` beside its destination, `physical.recheck()` runs, then atomic `rename` (a second `rename` for the build-dir ledger copy). A refused/failed run leaves no receipt and no temp file. Size cap `CARGO_PROVENANCE_RECEIPT_MAX_BYTES_V1` = 128 MiB (the hub readers already refuse larger claims).
- Physical budget: the 128 MiB/65,536/60 s caps in six producers and the 8 GiB/1,048,576/300 s stopgap are replaced by one `cargoProvenancePhysicalControlV1` (16 GiB, 4,194,304 work, 600 s, `deadlineMs` overridable). Measured on the real invocation: 3.53 GiB (digest pass + recheck) and 955,869 work, so the old stopgap had 9 percent work headroom and this has 4.4x. The runtime-graph CLI uses the factory with a 24 h deadline for its currentness owner (the 128 MiB control stays only for the actor-selection evidence walk, which validates a different object).

## 6. Findings for main (not fixed here)

1. `🔌️plugin/🖨️describe/🏭️fresh-component/🟦️.ts:82` `freshRun` calls `captureOwnedProcess` without `invocation`, so `testFreshComponentProcessV1` and `produceFreshComponentV1` (hub catalog publish) cannot run (its provenance code path only runs after that). Same peer refactor as `browser-bundle`. Owner: pl-c / describe.
2. `parseSelectedRuntimeActorEvidenceV1` (selection schema) embeds whole `RuntimeCargoObservationV1` objects and walks them with `maxWork 65,536` / `maxBytes 128 MiB`. Any real hub component (hundreds of units x hundreds of inputs) exceeds the work cap in expanded form regardless of the receipt size. The evidence should carry receipt claims (path + sha256) and re-decode on demand.
3. `runtimeCargoObservationCurrentV1` re-reads every unit's inputs per unit (`views` is per unit): about 0.6 ms per input reference, so a 135 x 677 receipt costs roughly one minute and hub-scale receipts a few. Sharing a per-path digest/blake3 cache across units would remove it.
4. The ledger loader `load()` in the runtime-graph CLI swallows decode errors (`catch { return [] }`); old-format receipts are therefore skipped silently and re-acquired, which is intended, but a corrupt new receipt looks identical. Consider logging the refusal.
