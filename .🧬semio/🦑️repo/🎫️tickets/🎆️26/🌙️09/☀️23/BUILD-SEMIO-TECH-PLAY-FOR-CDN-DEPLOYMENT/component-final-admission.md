# Component final admission: evidence-based cold model

## Findings
1. History does apply to component finals; there is nothing to fix in the key. `unitKeyV1` is `package@crate|target|profile|crateTypes` (e.g. `semio-hub-fem-component@semio_hub_fem_component|wasm32-wasip2|release|cdylib`), independent of target dir, lane and lock hash; the store is one file per cache root (`.cache/b/r/m/components/build-telemetry/units.jsonl`, `unitHistoryPathV1(cacheRoot)`), read at driver start. The history has no key for 79 of the finals simply because no attempt ever completed them.
2. Why no rows: `recordUnitHistoryV1` runs once, at the end of the driver's execution (`component-pass/🟦️.ts`, after `writeBuildReportV1`, guarded by `!signal.aborted` and remaining lease time). An attempt that is killed, aborted or fails before the end records nothing, not even the finals that completed. Recorded cdylib finals (release): fem (3 rows), norm-energy, norm-eurocode-materials, -structural, -eurocode: 7 rows; prototype: draw (1). Only 5 of the 84 workspace `*-component` cdylib packages have a release key. Recommended follow-up (not done: the driver is a 1200-line file in live use, and rows need the critical-path `remainingMs` that is known only at the end): record each unit as it completes (broker `completed` callback, partial observation with `remainingMs` = wall) so failed attempts still accumulate evidence.
3. Cold model was a constant: `componentFinalBytes` = 6 GiB for every unseen non-host cdylib, against recorded release peaks 1.41 to 4.74 GiB (median 2.38 GiB over rows, 3.2 GiB over keys).
4. Budget, computed and reproduced exactly (6.20 GiB): physical 16 GiB, reserve `min(6 GiB, 25%)` = 4 GiB; the launcher grants share `reserve + (eff - reserve) * tokens/parallelism` = 4 + 12 * 6/10 = 11.2 GiB (6 cargo jobs of 10 cores); the broker then takes `physicalBytes - admissionReserveBytesV1(physicalBytes) - nonRustc` = 11.2 - 2.8 - ~2.2 (driver's other children) = 6.2 GiB. So the share is not needlessly small: it is the cpu-token fraction of the memory above the reserve (7.2 GiB), and because the broker re-derives a reserve from the already reduced share (2.8 instead of 4 GiB) it is, if anything, 1.2 GiB more generous than the model's own 7.2 GiB. It is also above what the host really has free (vm_stat shows about 2 GiB free, 4.7 GiB inactive of 16 GiB, other agents share the machine). Not changed. Real lever beyond the cold model is only fewer non-rustc bytes (2.2 GiB) or more tokens.

## Change
- Schema `🎟️admission/🧬️schema/🔣️.json` Policy: new `componentColdQuantile` 0.5 and `componentColdMinimumRows` 3; `componentFinalBytes` (6 GiB) stays as the no-evidence bound.
- `🎟️admission/🟦️.ts`: `componentFinalKeyV1(key, profile)` (non-host, same profile, cdylib), `componentFinalPeaksV1(history, profile)` (all recorded peaks of that population); `predictPeakBytesV1(peaks, {kloc, component})` where `component` is the pool or `null` for non-finals (replaces the boolean `componentFinal`; no compatibility shim). Own history still wins (`headroom * p95(window)`); cold final = `max(ceil(headroom * quantile_R7(pool, 0.5)), floor)` when the pool has at least 3 rows, else the bound. The broker caches the pool per profile in `predict`; admit and probe share it. Overshoot safety is unchanged: charge is `max(predicted, actual RSS)`, freeze above budget or on swap-out, EASY backfilling, history updates after each pass.
- Sensitivity (honest): pooling rows gives median 2.38 GiB (x1.15 = 2.74 GiB); pooling one value per key would give 3.2 GiB (x1.15 = 3.68 GiB), which fits only once in 6.2 GiB. Rows were chosen because they are the recorded observations; 2 concurrent finals each reaching the 4.7 GiB tail exceed the budget, the broker then freezes further admissions but does not kill running units (physical limit is 12 GiB above the reserve).
