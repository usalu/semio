# Release fleet offload: why waiting units never reached the fleet

## Verdict
Three separate causes, two fixed or already fixed for the next attempt, one deliberately left alone:
1. The running attempt has no offload path at all (unit cache off, so the compiler chain is the memory scheduler alone). The launcher change of 12:45 (`release-unit-reuse.md`) turns the cache on at the next attempt start and with it the offload path.
2. Even with the cache on, the offload gate never asked the build's own admission broker. The broker's budget (6.2 GiB) is much smaller than what the host sample calls free, so a unit the broker queues looked admissible to the gate. Fixed: the broker now answers a read-only probe and the gate reads it.
3. The unit that waits in the observed stall is a wasm `cdylib` component final. The offload policy refuses `cdylib` (and its link arguments). That stays refused: see "cdylib: why not enabled".

## 1. How rustc units are offloaded (exact path)
- Cargo runs `RUSTC_WRAPPER`. With `SEMIO_UNIT_CACHE=on` the chain is `shim (wrapRustcV1, unit-cache/📜️script.ts) -> semio-build-scheduler (admission broker client) -> rustc` (`compilerWrapperEnvironmentV1`, `SEMIO_UNIT_CACHE_INNER`).
- `wrapRustcV1` computes the unit key, serves a local or fleet-cache hit, else calls `offloadUnitV1` BEFORE the inner scheduler. `offloadUnitV1` calls `offloadRustcUnitV1` (offload/🟦️.ts): hermetic REAPI-style action (`buildOffloadActionV1`), scheduler placement on a worker with headroom (`placementHasHeadroomV1`, `/v1/fleet/idle`), outputs written back into the real out dir, then the unit is published into the local unit cache under its key. Any refusal returns a reason and the unit compiles locally (`no-idle-machine`, `queue-timeout`, `inputs-too-large`, `worker-policy`, ...).
- Offload mode: `SEMIO_OFFLOAD`, default `auto`. In `auto` the old gate offered a unit only when (a) its recorded local cost is at least 2500 ms, and (b) `SEMIO_OFFLOAD_PRESSURE=door`, or the unit-cache slot queue is at least 1500 ms, or the host-capacity verdict for a 768 MB unit is `wait`. `SEMIO_OFFLOAD_PRESSURE=door` and `SEMIO_UNIT_CACHE_SLOTS=1` are set by `repo capacity run` only when the door refused the whole build (host-capacity/🟦️.ts `runWithFleet`).

## Why the release driver's units were not offloaded (evidence)
- `ps eww` of the driver's scheduler (pid 29922): `SEMIO_UNIT_CACHE=off`, `RUSTC_WRAPPER=.../semio-build-scheduler`, `RUSTC=rustc`, no `SEMIO_OFFLOAD*`, no `SEMIO_RELEASE_UNIT_CACHE`. `native-play.sh` exports `SEMIO_UNIT_CACHE=off` for the whole run and `compilerWrapperEnvironmentV1` returns `{}` when it is off. The offload logic lives only in the unit-cache shim, so the attempt (started 12:34:59, before the 12:45 launcher edit) cannot offload. No kill switch and no release-mode refusal exist: grep of `SEMIO_BUILD_MODE=release` against offload finds nothing; offload mode is `auto` by default.
- Admission happens in the scheduler, after (not before) the offload decision, so ordering is not the problem. The problem is what the decision reads: the host sample and the slot queue, never the broker. Observed `charged 6.0/6.2 GiB, admitted-wait 1, frozen`: the broker budget is physical minus a reserve (min(6 GiB, 25%)) minus the driver's other children; a cold wasm component is predicted at `componentFinalBytes` = 6 GiB, so one component fills the budget and the next waits (the dag component scheduler pid 29922 started 14:10 and its rustc only began 14:34: 24 min in the queue).
- Launcher state: `unit-cache-demoted` marker is absent, `SEMIO_RELEASE_UNIT_CACHE` is not set in the supervisor, so the next attempt runs with the cache on and offload `auto`.

## 2. What changed
- `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🎟️admission/🟦️.ts`: pure `admissionWouldWaitV1(state, waiting, candidate)` (the existing EASY-backfilling law run once more with the candidate, no state change); the broker answers `{"op":"probe", ...admit facts}` with `{"v":1,"op":"headroom","wait":bool}` and never queues the asker; prediction and state building extracted (`predict`, `stateNow`) so admit and probe share them. Schema: `HeadroomV1` in `🧬️schema/🔣️.json`.
- `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/⚡️caching/🦀️cargo/🗃️unit-cache/🛰️broker/🟦️.ts`: `brokerWouldWaitV1(environment, facts)` (undefined when no broker answers; same 2 s limit as the other broker calls).
- `.../🏗️build/🌐️remote-execution/🚀️offload/🚦️admission/🟦️.ts`: pure `offloadGateV1` (signals asked lazily in order: mode, round trip, door, slot queue, host, broker; unknown never offloads); re-exported from `.../🚀️offload/🟦️.ts`.
- `.../⚡️caching/🦀️cargo/🗃️unit-cache/📜️script.ts`: `offloadUnitV1` uses `offloadGateV1`; the broker signal is the new one. `always` and `never` behave as before; `auto` only gained the broker-wait trigger.
- Not changed: `SEMIO_UNIT_CACHE=off` default of `native-play.sh` (running script, untouched); launcher already decides per attempt.

## Provenance and reproducibility of the remote path
No release rule forbids remote execution (nothing in the Play site modules or the release verify mentions offload). Proof the remote path gives: the action is a canonical argv plus allow-listed environment plus an input-root digest (CAS content digests of every input; `maximumInputFiles` 8192, `maximumInputBytes` 512 MiB); the worker platform key includes the toolchain build (`312cc5b2932fbb31`, the same as this host) and `semio-offload-format argv-1`; paths are rewritten to `@root` with `--remap-path-prefix`, `-C` and `-Z` flags go through an allow-list (`validateRemoteExecutionRustcActionV1`, applied on both sides); outputs are re-checked for completeness (`missingOutputsV1`) and the unit event records `offloaded:<origin>`. `offload/🧪️tests/🎯️determinism` compiles the same planned unit locally and as a worker would, in different roots, and requires identical output bytes for lib, rlib, proc-macro and bin. That satisfies provenance for those crate types. It gives no proof for `cdylib`.

## cdylib: why not enabled
The units that fill the broker are wasm `cdylib` finals (`semio-hub-*-component`). They are not offered, on purpose and with reason:
- `OFFLOAD_POLICY_V1.crateTypes` is `lib, rlib, proc-macro, bin`; `flag("--crate-type")` refuses `cdylib` on the worker too.
- The release rustflags add `-C link-arg=--max-memory=536870912` and `-zstack-size=8388608`; the action validator allows only the macOS install-name and `-oso_prefix` link arguments, so the action would be refused (`worker-policy`) even if the crate type were allowed.
- No determinism test covers a linked wasm cdylib (the unit cache fleet tests treat wasm cdylib as shareable, offload tests do not).
- Memory: placement counts 768 MB per unit (`unitMegabytes`); measured component peaks are 1.2 to 4.7 GiB, cold prediction 6 GiB. A worker admits by its own pressure and headroom report, but nothing sizes the placement by predicted peak. Enabling needs (a) a wasm-only crate-type and numeric wasm-ld link-argument allow-list, (b) a byte-identity test for a wasm32-wasip2 cdylib across roots, (c) a predicted-peak field in placement. Not done here (security surface, no proof yet).

## Profile levers (numbers, nothing changed)
- Premise check: components are not fat LTO / `codegen-units=1`. Authored `release-wasm` (🎚️mode/🦀️profile schema) is `opt-level=s`, `codegen-units=16`, `lto=thin`, `strip=symbols`, no incremental; the running dag component confirms `-C opt-level=s -C lto=thin -C codegen-units=16`.
- The single-core look (cad 22+ min at 97 percent) is the scheduler on purpose: for a `cdylib` final with an admitted grant it rewrites `-Z threads=0` to `threads=1` (`frontend_tokens`) and appends `-Z no-parallel-backend` (`serial_backend`), because concurrent codegen and ThinLTO jobs each hold a module of the whole closure (peak memory, `🧵️frontend-threads` test). Recorded component finals (`.cache/b/r/m/components/build-telemetry/units.jsonl`, 6 keys): wall 10.0 to 31.3 min (median 23.9), peak 1.2 to 4.7 GiB, CPU/wall 0.78 to 0.90 (fem, which ran with threads: 2.68 and 10 min), output 86 to 196 MiB, all far under the 1 GiB cap.
- So per-component parallel codegen is possible in principle (fem: 2.7x CPU/wall and about 2.4x faster), at the cost of a higher peak; it is a memory-for-time trade the admission model currently refuses. A proof-bearing change would be: let the broker grant parallel backend to a component final when it is alone in the budget (running 0) and the host has idle cores. Output determinism with `no-parallel-backend` removed is not proven (LLVM codegen-unit partitioning is deterministic for a fixed count, but ThinLTO merge order under threads needs a byte-identity run on cad). Not changed.
- Second serialization cause, measured: the cold component prediction (6 GiB) vs measured median about 3 GiB. Until each component has a history row, the 6.2 GiB budget admits one component at a time. A kind-quantile cold prediction (recorded 5 of 6 under 4.7 GiB) would admit two. Not changed (documented upper bound, `unitFootprintBoundsBytes`).

## Expected speedup
- Next attempt (cache on, gate with broker): rlib, proc-macro and bin units that the broker queues, or that the host cannot carry, go to the fleet (11 workers, about 110 slots, running 0 to 2). The 4000+ library units of a cold closure are CPU-bound with 6 local jobs; with 9 idle cores and the fleet the library phase is bounded by the fleet round trip, not local cores. Estimate for the library phase: 3x to 6x faster than 6 local jobs when workers are idle; no estimate is honest without a run.

Largest lever is the cold prediction (about 2x on the component phase) and the parallel backend for a lone component (about 2x per unit), both blocked on proof above.
