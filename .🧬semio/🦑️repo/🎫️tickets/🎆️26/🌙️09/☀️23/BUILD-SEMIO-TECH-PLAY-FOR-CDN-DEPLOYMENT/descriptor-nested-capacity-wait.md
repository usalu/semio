# Descriptor Nested Capacity Wait

In generation `wTxgqdA`, descriptor PID 66294 held the shared host-capacity lease and waited for CPU slots while parent driver PID 19506 retained four CPU leases. The descriptor's managed job holds a jobserver slot. Other active compiler owners hold additional slots; the host-capacity label is a shared lease held during the CPU acquisition, not itself proof of a blocked shared lease.

Play declares `describe-tool` as `workerProtocol: jobserver`. The component driver's jobserver work path acquires one actual jobserver token and spawns the job as a child process. Descriptor artifact capture independently calls `compileUnitsForHostV1` and `withCompilerCapacityScopeV1` before Cargo spawn. Its available request has a planned minimum and maximum; one free CPU is insufficient when the request's minimum is larger, although the actual request for this process was not recorded here.

`withCompilerCapacityScopeV1` lends private credits only through its live `AsyncLocalStorage` parent frame, same namespace and issued control refinement; that frame does not cross a process spawn. Thus the separate descriptor child has no such parent and requests new kernel CPU leases even though its parent's pool and jobserver slot are held. This is a structural double reservation and can starve dependent work, but it is not proof of a permanent deadlock while unrelated owners can release slots. Environment markers do not authorize lending: `acquireCompilerCapacityLeaseV1` expressly refuses them. The in-process `withNativeBuildStageCapacityV1` borrower requires real retained frame and jobserver custody, and the paid-process custodian acquires its own real capacity for direct children; neither establishes a currently available cross-process borrower of the driver's held grant.

A correct repair requires a genuinely owned cross-process allocation with bounded credits, lifetime, cancellation and drain semantics, or an architecture that executes the compiler under an existing legal in-process borrower. A jobserver token or parallelism environment variable alone is not authority. No change, signal or build was made during this audit.

## Independent Admission Implementation Boundary

The existing job protocols describe how a job borrows from the component driver. `WorkerProtocol` in `native-build/🧩️component-pass/🧬️schema/🔣️.json` supports `jobserver`, `reserved` and `exclusive`. The release planner passes this field through to the driver's job runner. Adding an independently admitted process requires a different ownership contract. The job dependency barrier is already in the right place for component source admission, but the prerequisite runner, completions, subprocess cancellation, output drains, watchdog, jobserver and admission broker all currently live inside the same component capacity callback.

Both `describe-tool` and `native-transpile` reach `captureCargoArtifacts`, which acquires a real child-local `withCompilerCapacityScopeV1`. Font Assets uses the same compiler artifact capture path. The `fonts` publication command explicitly acquires an exact one-core lease, and the browser WASM build path independently acquires available cores. Other jobs were left outside the proposed initial classification. In particular, the existence of a TypeScript command or a policy label does not establish its own capacity contract.

`component-pass/🟦️.ts` initializes one admission broker with `admissionMemoryShareV1(effectiveBytes, tokens, hostParallelism)`, using the actual component grant. The broker uses that fixed bound, swap-out samples and per-unit resident memory to fund rustc work, and its unit records feed the generation report and saved scheduling history. Its interface supports pass registration and observations, with no lease-to-budget handoff or resizing. The Rust scheduler in `native-build/🎟️admission/🦀️.rs` falls through to passthrough if it receives no broker endpoint and pass. Keeping the same scheduler executable would preserve the `RUSTC_WRAPPER` recipe input, but passthrough would drop that memory admission and unit accounting. Giving the early phase the current broker interface without a grant would size it using a speculative core count.

A durable split needs a prerequisite execution and observation owner bound to the real child-local capacity. It can then reuse the driver's job attempts, cancellation, drain and dependency completions before acquiring the component-pass grant. It also needs to retain broker samples, unit history and existing output receipts across that phase boundary. The first regression should use an independently admitted OS child and a one-slot host analogue, verify the child acquires the physical slot before the component grant, exercise dependency failure and cancellation with joined cleanup, and establish that compiler unit accounting remains charged. Wiring a job enum or launching the existing command early would omit that ownership work. The read-only implementation assessment made no production changes and ran no Cargo, describe, replacement supervisor or compiler tests.

### Jobserver Width in Received Authority

The live native-transpile log shows `CARGO_MAKEFLAGS=-j1` for the driver FIFO. Cargo reported that the inherited external jobserver takes precedence over its explicit `-j` option. The child continued to publish host-capacity waits through 1,604 seconds. Those observations support a one-slot limit for this specific jobserver and run. The compiler broker's registered pass similarly carries job identity and target/profile, with no pool width receipt for a child.

A parsed `-jN` can differ from the physical pool to which its endpoint connects. An opened FIFO or semaphore verifies reachability and says nothing about the original number of credits. A current byte count omits borrowed tokens. The unit-cache stand-in can also replace an unreachable endpoint or supply a private scheduling pool to avoid rustc token stalls. That transport adaptation does not establish an issued compiler-width limit. The child-side use of `compileUnitsForHostV1({needed})` therefore has no existing received proof to consume.

A future bounded jobserver handoff would have to issue the upper bound from the live pool owner for this exact child, bind it to the same active client and original invocation, and recheck that the actual Cargo ingress retained that endpoint before capping physical demand. It could then preserve the existing real core lease, memory broker and artifact proof. This inspection found no existing handoff with those properties. No production, test, compiler or process changes were made.

The raw Cargo unit-graph reader validates dependency indices, rejects cycles and unreachable units, and represents build-script compilation and build-script execution separately. Its count bounds the enumerated Cargo units. A unit's compiler can still use additional jobserver credits for LLVM work. A build-script unit can also run its own child work.
