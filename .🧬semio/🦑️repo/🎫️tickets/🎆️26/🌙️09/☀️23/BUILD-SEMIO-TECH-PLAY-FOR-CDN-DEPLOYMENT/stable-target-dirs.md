# Stable target dirs across release attempts

Applies at the next attempt start (a running attempt keeps the code it loaded). No Cargo build was run; tests are unit level plus small offline Cargo fixtures.

## 1. Lock refresh: already write-free on an unchanged graph
`ensureCargoLockV1` (`🧰️framework/🔨️modules/🏃️process/🦀️cargo-workspace/🔒️lock/🟦️.ts`) first checks a receipt (lock and manifest digests), then probes with `cargo update --workspace --locked --offline`, which never writes. Only when that probe fails does it run a resolving `cargo update`, and Cargo writes `Cargo.lock` only when the resolved text differs. The dedupe repair writes only when a duplicate package row exists. So no write path exists for an unchanged graph; the log line "behind its manifests" (27 workspaces per attempt in `site-build-150550.log`) is the probe failing, i.e. a real difference. Evidence it is real: 36 `Cargo.lock` files differ from HEAD with semantic changes (for example `windows-sys 0.52 -> 0.61`, new `arbitrary` dependency edge). Likely cause: live manifest churn from other machines, plus last-writer-wins replication restoring older lock bytes. I could not prove or exclude a bytes-identical rewrite from the logs; to settle it, log `sha256(Cargo.lock)` before and after the refresh per attempt.
Change: none to the refresh. Pinned by test `a refresh of a current lock is a no-op...` (fake port: bytes and mtime unchanged, only `--locked` updates, a repeat makes zero Cargo calls). The real fix is item 2: the key no longer depends on the lock.

## 2. Target recipe key
Before: `t/<sha256(recipe)[0:32]>` hashed, besides toolchain, args, env, config, also the projected digest of every `Cargo.toml` and `Cargo.lock` of all ancestor directories (whole-file digest for workspace-wide builds, where the closure projection is unavailable). Any lock or manifest edit gave a fresh target dir.
After: `Cargo.toml` and `Cargo.lock` are witnesses only (still observed and rechecked, so a concurrent edit still invalidates the plan) but are not keyed. Keyed: Cargo and rustc identity (toolchain), arguments (target, profile, features, package selection, `--config` files and their digests), environment (rustflags, `CARGO_BUILD_*`, `CARGO_PROFILE_*`, `CARGO_TARGET_*`), `.cargo/config*`, `rust-toolchain*`, `CARGO_HOME` config, cwd, manifest path, lane build dir (lane isolation unchanged: one recipe lease per target dir, one claim per lane).
Safety argument: inside one target directory Cargo identifies every unit by `-C metadata` (package id, version, features, profile, dependency metadata) plus a fingerprint (source mtimes or hashes, rustflags, dependency fingerprints), so a changed lock or manifest yields fresh or stale units, never a wrongly reused one. Anything that Cargo's fingerprint does not see (rustc, Cargo, rustflags, target, `--config`, `.cargo/config`) stays in the key. Cost: units of removed dependency versions stay in the directory until the lane is retired (bounded by the pool and the collector).
Files: `…/🦀️cargo-workspace/🔒️lock/📐️closure/🟦️.ts` (`cargoRecipeKeyedV1`, `cargoRecipeInputsV1`), its `🧬️schema/🔣️.json` (`Protocol.witnessOnly`).
Tests: `…/📐️closure/🧪️tests/🔑️target-key/` (neutral vector corpus `🔣️.json`, independent Python oracle `🐍️.py`, production test `🟦️.ts`: 14 cases, 3 same-key pairs for lock and manifest edits, 10 different-key pairs for rustc, cargo, rustflags, target, profile, features, package set, config, toolchain file, lane). The existing closure tests were inverted where they asserted that a lock or manifest edit moves the key (witness rejection is still asserted); 18 pass including the real-Cargo scenarios (run with `RUSTUP_TOOLCHAIN=nightly-2026-07-20`; without it rustup has no default in this shell).

## 3. Eviction exemption for release product lanes
No "release generation" record exists, so a generation is approximated by activity: a product lane (`q` prefix) used within `pool.product.retainMilliseconds` (12 h, authored in the unit-cache schema) is retained. Retained lanes are neither counted against the pool's 16-lane and byte bounds nor ever trim victims (`boundedPoolV1`, used by `trimPoolV1` and `acquirePooledLaneV1`), and the collector (`planGcV1`, new `retained` flag from `listLanesV1`) exempts them from the 24 h idle age, the 23.4 percent lane share and the incremental share. Only free-space pressure removes them, after every other idle lane, so the disk emergency path still works. After 12 h without use they are evictable again.
Tests: `…/🏊️pool/🧪️tests/🛡️product-retention/` (neutral corpus, Python oracle for retention and trim, hand-authored collector vectors); the product-lane test was changed to assert retention inside and retirement outside the window; the pool-claims test used `q1..q3` as generic lane ids and now uses `m1..m3`. Pool model, claims, sessions, collector, headroom and live-holder suites pass.

## Expected effect
Target dirs of a product lane keep their name across attempts as long as toolchain, args, env and config are equal, and the product lanes survive between attempts (about 32 GiB no longer evicted by the 16 GiB quota), so Cargo's fingerprints make unchanged units fresh and only units whose sources or dependency graph moved recompile. The first attempt after this change is still cold (new directory names; old `t/*` directories are orphaned and reclaimed). Not addressed: the progress counter still shows 0 reused for Cargo-fresh units; free-space pressure can still evict a retained lane; the unit cache stays the reuse path for cross-lane duplication.
