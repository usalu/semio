# Pinned source for Play release builds

The repository already has a content-addressed source revision and a way to materialize it for native executors. The Play release driver currently has no input for such a revision. A future release can reuse the existing capture and storage machinery without a Git branch, Git worktree, or write into the shared checkout. It needs a held source view that every release process and retry inherits.

In release run `wCsXqmg`, two `job:describe-tool` attempts stopped with exit 75 after different Rust sources changed. The third attempt completed on a later live state. A repository graph generation pin fixes the graph that nested tasks use. The Rust source reader still opens descriptors at the physical paths passed to Cargo and rechecks their ancestry and identity. ## Existing machinery

- `pinRevisionV1` stages a supplied path roster into the CAS and seals a manifest of paths, modes and digests. `withPinnedRevisionV1` renews its lease while a consumer runs. Staging retries unstable per-file reads and returns `torn` and `absent` paths. It can publish a revision even with those paths, and independently stable file reads can still span different live edits. A release must refuse missing required files and torn reads and verify the complete roster as one observation. `observeStableTreeV1` already provides an example and host-neutral primitive for list, consume, re-list, and settle. ## Release integration

The native driver currently uses the exact authority repository root to derive the release plan, acquire compiler and dependency stores, configure pass manifests and working directories, and start prerequisite processes. The Cargo provider can refresh a stale `Cargo.lock`. The same Play command publishes the page cohort after the driver returns, and the Play verifier reads the generated catalog and descriptors from the workspace. Provisioning a separate source directory or shifting only Cargo's working directory would leave planning, jobs, or verification with a live input path. [Play script](../../../../../../../🏢️semio-tech/🎡️play/🔨️modules/📦️site/🟦️.ts) · [Native release driver](../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🏗️build/🧩️driver-stages/🟦️.ts) · [Compiler process boundaries](../../../../../../../🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🧩️component-pass/🟦️.ts) · [Repository Cargo inputs](../../../../../../../🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏃️process/🦀️cargo/📥️dependencies/🟦️.ts)

An implementation can retain the canonical workspace as the lease, cache, and publication identity while binding a separate source root and revision digest to the release invocation. The source roster must include current local edits, selected workspace manifests and locks, sources loaded by build scripts and procedural macros, generated sources and package assets, and the site and verification inputs. Generation and lock preparation need explicit writable scratch before the freeze or an owned output area. Once admitted, every attempt should inherit the same revision, and the final cohort should record it. A short private path outside the replica's scope and a path budget check are necessary for native Windows and the repository's 256-character limit. The pin and materialization need bounded lifetime, cancellation, and cleanup.

An initial integration proof can capture the descriptor tool's exact closure into a private source view, change a fixture source in the original tree between two child attempts, and confirm that both native attempts use the same captured inputs. That proof does not cover the complete Play pipeline. No build, source copy, mount, branch, or Git worktree was created during this audit.
