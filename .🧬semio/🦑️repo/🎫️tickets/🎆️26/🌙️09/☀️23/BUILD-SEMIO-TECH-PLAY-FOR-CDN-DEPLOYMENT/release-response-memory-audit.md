# Release Response Memory Audit

`servePublishedPlay` serves each file as a `Bun.file` response with Content-Length and has no authored per-file byte or stream limit. The published-page assignment refuses each whole family at 1,000,000,000 bytes or above. The repository artifact publication policy permits 8,589,934,592 output bytes and 16,384 files, but the lower page limit applies to these pages. Publication itself allocates each file into a buffer and keeps a family's contents in a map while forming its manifest; it is also not a streaming-memory bound.

The satellite browser adapter calls Playwright `route.fetch` and then `route.fulfill({response})`, disposing the response after fulfillment. The installed Playwright core collects every response chunk into an array, `Buffer.concat`s it, stores the complete buffer in `fetchResponses`, and converts it to a base64 string to fulfill the browser route. Thus a satellite response is buffered and base64 encoded, unlike the local file response, with peak memory proportional to the size and number of concurrent responses. Disposal removes retained response bodies only after fulfillment; it does not remove the peak. The server's permissive file path plus family-level limit does not guarantee this adapter can handle every allowed file under a given process memory budget. No complete current release cohort or measured large-file failure was available, so this is a concrete memory characteristic and risk, not a demonstrated current failure or a provider limit.

Evidence: Play `🔨️modules/🧪️e2e/📦️release/🟦️.ts`, `🎭️fixture/🟦️.ts`, site `📄pages/🟦️.ts` and `📄pages/📦️publication/🟦️.ts`; `⚡️caching/📦️artifacts/💾️storage/🧬️schema/🔣️.json`; installed Playwright `playwright-core/lib/coreBundle.js` response collection, `_storeResponseBody` and `Route.fulfill`. No build or browser load test was run.
