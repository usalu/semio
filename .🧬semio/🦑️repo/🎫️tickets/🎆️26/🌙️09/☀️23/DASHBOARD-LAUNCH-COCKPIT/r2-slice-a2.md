## Round 4 (newest): R2 readiness by listening port, R1 view limit

`cargo test -p semio-framework-repo-dashboard --lib` twice in a row (private build dir): 206 passed, 0 failed each.

- **R2.** Text alone never declares readiness. The address the matcher finds is only a **candidate** (`Live::offer`); the session gets `ready_url` when a TCP connect to the declared port succeeds on `127.0.0.1` or `::1` (`listening`, 100 ms connect timeout), polled from 50 ms with doubling backoff up to 1 s, only while the task lives (the candidate is cleared on restart and on exit; the loop timer wakes only for sessions with a candidate). The ready URL text is unchanged (match + path, or the printed address). Test `text_alone_never_declares_readiness_a_listening_port_does`: a child prints `waiting for the site http://127.0.0.1:<port>` and listens only after the test creates a gate file; 1.5 s of daemon turns later `ready_url` is still empty; after the gate it becomes `http://127.0.0.1:<port>/x`. Groups and `--wait-ready` use `ready_url`, so they wait for the port too.
- **R1.** The 17th `Attach` was refused with `limit`, which the view localized as "holds as many tasks as it allows". New error kind `view_limit` (`ErrorCode::ViewLimit`, schema enum, vector, used for both the 16-view and the 64-connection limit); `limit` stays the session limit. View (`🖥️terminal`, this message only): the catalogue has `error_view_limit` (en/de: "the daemon serves as many views as it allows; close another view and try again"); on that error the view shows it as notice and as `LinkState::Failed`, drops the refused connection and enters its normal reconnect backoff instead of staying connected with `0 running`. Test `a_refused_view_says_so_in_its_language_and_retries_instead_of_showing_an_empty_daemon`; daemon side `sixteen_attached_views_…` now expects `view_limit`.

## Round 3b: deterministic daemon tests

`cargo test -p semio-framework-repo-dashboard --lib` (target `target-fleet-a2`, `CARGO_BUILD_BUILD_DIR=…/private-build`) three times in a row: **205 passed, 0 failed** each time (61 s), while other agents compiled on the same machine; earlier loaded runs had failed.

- **Case mismatch** (`only.CMD` vs `only.cmd`): `a_program_resolves_to_its_executable_before_its_script_shim` compares paths case-insensitively (Windows paths are; `PATHEXT` upper-cases the extension it appends).
- **Event-driven waits instead of wall-clock bounds.** `View::until` and `Raw::read` multiply every stated bound by 6 (a deadline, not a duration to wait: a raw read returns 150 ms after the last frame); `until_progress` replaces fixed deadlines for the 12 MB burst and the paste by "fails only if no byte arrives for 120 s". The stalled view reads until it has 8 MiB and the replay-complete message, or no byte arrives for 120 s. All `sleep`s before an action are gone: the echo child prints `echo-ready`, the batch test waits for the program inside the batch file to print `sleeping`, the stalled view needs no pause. Duration assertions are gone (stop ladder: the exit code 9 proves termination before kill; batch: ends after the stop). The paste is 500 lines.
- **Root cause behind the remaining flakes: lost final output of short tasks on Windows.** The supervisor ended a session after a fixed quiet window and, in the first version of `Pty::finish`, closed the pseudo-console as soon as the process was seen to end, which can drop output conhost had not yet written. Now: after the process ends the session waits for 250 ms without output, then closes the pseudo-console, then reads until the output pipe reports `Closed` (up to 3 s on Windows; on Unix the master reports the end itself), with an 8 s hard limit. Status of a finished task therefore changes about 250 ms after the process ended. Not asserted any more: the text a process prints from a console-control handler right before `ExitProcess` (it can be lost by conhost; the exit code is asserted).

## Round 2c: connection panic `attempt to subtract with overflow`

Cause: the queued-byte counter was adjusted by hand at three sites and the `Drop` path pushed the Detach frame without adding its length, so the writer thread's `bytes -= frame.len()` underflowed on every connection end (panic in debug, silent wrap in release). That was already patched in round 2b; the root fix is now structural: `daemon::client::Outbound` owns the frames and the count, and `push` / `pop` are the only places that change either, each with the exact length of the frame it moves (`queued_bytes()`, `fits()`). Tests: `the_queued_byte_count_of_a_connection_is_the_sum_of_its_frames_through_partial_writes` (frames of 0 B to 256 KiB, written in growing partial pieces, count exact at every step and 0 at the end) and `a_queue_refuses_frames_beyond_its_limit_without_losing_count`. Verified with the debug binary against an isolated daemon: `daemon start|status|stop`, `run --detach --wait-ready`, `tasks`, `logs`, `restart`, `stop`, `kill` printed no panic (stderr and stdout grep for "panick"/"overflow": 0). Also hardened the Windows Ctrl+Break stage in `UI/🚇️pty/🦀️.rs`: it now waits until the process has seen its own copy of the event before it drops its shield, instead of a fixed 60 ms (one loaded test run had been ended by the event itself). `daemon` tests: 52 passed.

## 4. Public API

Wire (`daemon::ipc`, also `crate::ipc`): `ClientMsg`, `ServerMsg` (new `ErrorCode`: `Error.code: Option<ErrorCode>`, `ErrorCode::as_str`), `SessionCommand`, `SessionInfo` (status gains `Pending`, `Interrupted`), `TaskLabel`, `Ready{port,path,printed}`, `SpawnGroup`.

- `SpawnGroup::from_launch(&registry::Launch, client_env: &[(String,String)]) -> SpawnGroup`, `.message() -> ClientMsg`. Services in `requires` first (flattened, deduped by `command_id`), one `SessionCommand` per `LaunchProcess`, `group` set only on members of a compound, `stop: together` from `Launch.stop`. `client_env` is extra environment of this launch that overrides the launch's own; the requesting client's whole environment travels in the connection hello and is the base of every task.
- `daemon::client::Connection`: `connect(root)` / `connect_with(root, name, env)` (sends hello), `send(&ClientMsg)`, `input(session_id, bytes)` (input frames, use this for keys and paste), `receive(timeout) -> Vec<Message>`, `daemon_pid()`, `daemon_build()`, `skew() -> Option<Skew>` (`incompatible()`, `describe()`). `Message::{Control, Output, Disconnected}`. **For A-3:** the daemon now sends `ReplayStart{session_id,truncated}` before a replay (reset that session's terminal), `ReplayComplete{Some(id)}` per session and `ReplayComplete{None}` after an attach, `SessionRemoved`, `Pending`/`Interrupted` statuses, `Sessions` in pages (`more`), and replies `Error{code}` to the requester only. Show `connection.skew()` in the footer.
- `daemon::control` (used by A-1's `🧭️cli`): `connect_or_start(root, exe)`, `tasks(&mut conn, within)`, `offline_tasks(root)`, `select(&[SessionInfo], needle)` (id, 1-based position, command id, unique part), `run(conn, group, Wait::{Accepted,Ready,Exit}, timeout, &cancel, &mut progress) -> Result<Started{group_id,sessions,ready}, RunError>` with `Started::ready_url()` and `exit_code()`, `follow(conn, session_id, out, follow, &cancel) -> Followed`, `act(conn, session_id, Action::{Stop,Kill,Restart}, wait, &cancel)`, `logs_offline(root, session_id, out)`. Cancelling `run` sends `StopGroup`.
- `daemon::supervisor`: `serve(root, running)`, `Supervisor`, `start_detached`, `spawn_daemon`, `status`, `stop`, `child_environment`.
