# Exact Dashboard Source Freshness

Independent source inspection confirmed a current omission: the dashboard belongs to the repository Cargo workspace, but path dependencies such as the TUI core inherit package metadata and lints from the separate framework Cargo workspace. The old installation capture used only the repository workspace dependency table and only named the repository Cargo manifest as a separate metadata input. None of the captured dependency roots included the ancestor framework manifest, so an edit there could retain the same cheap installed-source digest.

The installation source schema now requires exact workspace `manifests` beside source `roots` and `digest`. Capture uses the runtime's native TOML parser and caches each parsed manifest. Every crate resolves its explicit or nearest Cargo workspace; normal, build and target dependency tables resolve inherited local paths through that actual owner's table. Capturing another workspace does not add its whole directory to the source roots. Startup hashes the stat signatures of the recorded roots and exact files without parsing TOML or reading source contents. Duplicate file signatures are counted once. The owning binary's lock remains relevant; an independent dependency workspace lock is excluded.

Schema and neutral workspace vectors were authored before the production change. They include a shadow root dependency table, a foreign table-form workspace dependency, a target build dependency, exact roots/manifests and nine relevant/irrelevant mutations. Tests compare native TOML output with the existing independent @iarna parser and validate captured records with Ajv. Existing digest callers and the explicit installation test record were updated together. A Gherkin scenario records the behavior. Independent read-only source review accepted the implementation; this is not a test pass claim.

The localized source-only dashboard control is `@semio-tech/repo-dashboard-rs:test-source-freshness`, dispatched by the existing package script before native installation. It filters the two source digest regressions from the execution suite. The first invocation reproduced an additional prebirth reader defect: it rejected valid Source execution metadata as if every declaration were orchestration. That invocation exited 1 before a test body. The reader now validates Source and Native leaves against the existing closed target-execution schema and gives them no child grants. Orchestration retains its separate strict child validation. Six neutral accepted/refused leaf vectors, an actual extracted-reader/Ajv test and an actual source-target bootstrap row cover the change.

The retry is session 13856, with temporary output at `🗑️generated/e2e-source-freshness-final.log`. It is queued for shared dependency publication; no body result is claimed here. The same assertions also belong to the full installed execution suite. Scoped whitespace validation passed. The execution owner was told to restart only its own old cold entry after this change so the new installation records the exact workspace manifests.

## Invalid Record Recovery

An additional inspection found a real lazy-rebuild defect: stale-capable tasks/logs/stop controls treated mere record existence as an installed executable. An invalid or old-schema record therefore skipped the rebuild check and failed later in the immutable reader. The existing closed installation schema now drives one shared metadata-validity helper for the installed probe, immutable-path resolution and Source freshness. It also verifies current platform, mode and exact digest-qualified path. The presence probe reads no executable bytes and adds no artifact access outside tooling custody. Valid but Source-stale records retain observation/stop access; invalid records take the existing rebuild path.

Nine neutral record mutations were authored before the production correction. The actual filesystem probe, path resolver and freshness functions are compared with Ajv plus an independent SQLite platform/mode/path decision. Missing, unreadable, old-schema, foreign-platform, other-mode, wrong-path, missing-manifest and unknown-field records refuse; the current record is accepted. An additional existing-schema launch vector proves an invalid record routes tasks through one rebuild before leased execution. These tests remain pending in both the Source freshness target and full execution suite. No new compatibility path or native artifact shortcut is introduced.

## Preserved-Timestamp Source Edits

The earlier cheap signature truncated modification times to milliseconds and recorded only name and size. Equal-size atomic edits with a preserved timestamp could therefore retain the same digest. The schema now authors device, inode, size, modification nanoseconds and change nanoseconds. Startup takes the same metadata-only filesystem observations with bigint facts and reads no Source contents. This signature follows existing repository metadata conventions and keeps the same exact root/manifest scope.

Three neutral replacement vectors cover a compiled dependency, its exact Cargo workspace manifest and an unrelated independent lock. The real fixture saves preserve the old size and whole-millisecond timestamp while changing equal-length text. An independent SQLite comparison of the before/after bytes and captured scope determines the expected invalidation. Both included replacements must invalidate; the independent lock remains irrelevant. Gherkin and the Source freshness/full execution tests include the regression. Actual owner execution remains pending; no test pass is claimed from source review.
