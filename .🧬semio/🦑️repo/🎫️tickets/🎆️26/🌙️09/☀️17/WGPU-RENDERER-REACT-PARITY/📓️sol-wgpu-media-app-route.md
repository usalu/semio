# WGPU Media App Route

The follow-on acceptance route uses the real `stdio-media` WAV and MP4 viewer apps with their authored `demo` examples. Both viewer bodies currently publish `framework.media.transport@1` with `MediaCapabilityStatus::Unsupported` and the explicit localized reason that encoded playback export is not registered. WAV's editor currently authors a structural sample table. No concrete resumable `playback:out` producer is registered in these stdio media apps. Browser host playback capability therefore cannot turn the existing real app's unsupported contract into a playable player.

The canonical sources are the WAV/MP4 viewer `🎭️modes/👁️view/🪟️windows/🪟️main/🦀️.rs` files under each stdio artifact subset. `media_transport_resource` projects trusted live owner fields, while the generic plugin media submission path requires an actual registered reserved tool and concrete `build_media_export_job`. This is the same application capability boundary for React and WGPU.

A permanent `browser-media-acceptance` command is now authored in the WGPU package `📜️script.ts`. It requires `--serve <url> --locale en|de --output <ticket-generated-directory>`, then opens both real app URLs using the public boot query axes. It never replaces the renderer, guest, frame worker, app root, resource registry or media transport. It checks the accepted DOM slot's SHA-256 token, audio/video kind and MIME, explicit unsupported state/reason, owning accepted node/window correlation through the production worker accessibility introspection, no fabricated media player, and no duplicate mirrored accessibility node. Logs and screenshots are generated under the supplied output directory.

The schema-first neutral journey fixture is `engine/🧫️fixtures/🎬️media-app-acceptance/🔣️.json` with its schema. Independent Ajv and production boot descriptor decoding validate that fixture in the existing focused browser suite. The orchestration module is target `🧪️tests/🎬️media-app/🟦️.ts`; the parent owns task/package/launch metadata registration.

The in-app browser connected to port7301 on this source turn and observed the staged boot failure: plugin puzzle's manifest misses required `name`. The runtime remained faulted before an accepted app root. This is failure evidence for the staged renderer artifact, and no real app-backed media acceptance pass is claimed at this checkpoint. Parent owns fresh renderer/component activation. The existing production-host Chromium tests independently establish native audio/video decoding and controls with a bounded transport oracle; they do not cross this stale app boot boundary.
