# 🎨️ W1k — wgpu theme/token parity with React

**Packet goal:** every colour and metric the wgpu renderer paints must come from the same generated token
source React's CSS is generated from, so nothing can drift; plus a law test that fails on any new
hand-written colour literal in a wgpu target.

**Result:** done. The 6 hand-written theme literals the audit named are gone, 4 more literals the audit
missed (found by the new law, not by grep) are gone too, the codegen now projects the palette's primitive
colours and three new token families into Rust, and `no_wgpu_target_paints_a_hand_written_colour_literal`
scans 76 wgpu production sources and is green with a 6-entry documented allowlist.

---

## 1. Pipeline recap (unchanged shape, extended payload)

`🧰️framework/🔨️modules/🖱️ui/🎨️styling/🔣️.json` is the single source. `📽️projection/🟦️.ts` renders it into
CSS (`🎨️palette/🎨️.css`, what React consumes), TypeScript, C#, Python and Rust
(`🎨️styling/🔤️tokens/🦀️.rs`, gitignored, regenerated by
`nx run @semio-tech/ui-styling-tokens:generate`). `🎯️targets/🧊️wgpu/🎨️theme/🦀️.rs` reads that Rust crate.

Before this packet the Rust projection carried only `strokes`/`radii`/`opacities`/`metrics`/`levels`/
`presence` and the four appearance palettes (`board`/`map`/`canvas`/`chrome`). It carried **no primitive
colours at all** — there was no way to say "paint this in `primary`" from Rust, which is why every
brand-coloured wgpu paint was a hand-copied literal.

## 2. Codegen changes

All schema-first: the JSON changed, the emitters follow.

### 2.1 `🔣️.json`

| addition | value | why |
|---|---|---|
| `metrics.chrome.controlHeightSmallUiSpacing` | `5.0` | `from_chrome`'s only inline magic multiplier (`chrome_px(5.0)`) |
| `metrics.chrome.iconInlineUiSpacing` | `5.0` | `chrome::ICON_TINY`'s `14.0` px literal; React paints the same inline control icons with `size-small` = `calc(5 × --ui-spacing)` = 16px |
| `metrics.chrome.iconChevronUiSpacing` | `3.0` | requested by a concurrent peer's `chrome::ICON_CHEVRON` (React `size-tiny`, `calc(3 × --ui-spacing)`) |
| `opacities.chromeFocusRingAlpha` | `0.6` | `focus_ring`'s hand-written `.with_alpha(0.6)` |
| `levels.veilAlpha` / `levels.veilBlurPx` | `0.4` / `8` | the modal scrim; mirrors `🖌️ui/🎨️.css:853-854`'s `--veil-alpha` / `--veil-blur` |
| appearance group **`outcome`** (light + dark) | `error`→`danger`, `warning`→`warning`, `success`→`success`, `progress`→`secondary` | the audit's P1 outcome-colour mismatch |
| appearance group **`diagram`** (light + dark) | `checkerLight`, `checkerDark`, `stroke`, `seam`, `accent`, `accentFill`, `shapeOutline`, `fieldResidual`, `fieldReaction`, `fieldDisplacement` | every remaining wgpu-only paint |

`progress` maps to `secondary` because that is exactly what React already uses for the same semantic:
`appearances.*.board.nodeStrokeComputing = { token: "secondary" }`. No new brand colour was invented.

### 2.2 `🌓️theme/🔣️.json` (the "mono" premade theme)

Given the same two new groups, resolved against mono's own palette. Required, because `parseUiTheme`
throws when a theme omits a declared palette group.

### 2.3 `🌓️theme/🟦️.ts`

`ThemePaletteGroup` and `THEME_PALETTE_GROUPS` grew from four groups to six. React's own
`applyUiThemeToRoot` is untouched — it emits `--color-*` from `theme.colors`, which is the same key the
new `outcome` group refs point at, so both renderers read one value.

### 2.4 `📽️projection/🟦️.ts`

- `StylingLevels` + `LEVELS_DEFAULT` gained `veilAlpha` / `veilBlurPx`; `emitRust` emits
  `levels::VEIL_ALPHA` / `levels::VEIL_BLUR_PX`.
- **New `pub mod colors`** in the Rust projection: for every `🔣️.json` `colors` entry, a `[f32; 4]`
  linear-RGBA constant plus a `*_HEX` `&str` (the authored sRGB hex). This is the Rust twin of CSS's
  `--color-*` and TS's `STYLING_TOKENS`, and it is what makes `Rgba::from_token(&colors::PRIMARY)`
  possible.
- The new appearance groups need no emitter work: `paletteGroupNames` is data-driven, so
  `OutcomePalette`/`OUTCOME_LIGHT`/`OUTCOME_DARK` and `DiagramPalette`/`DIAGRAM_LIGHT`/`DIAGRAM_DARK`
  (Rust), `STYLING_OUTCOME_PALETTES`/`STYLING_DIAGRAM_PALETTES` (TS) and the Python dataclasses all
  appeared for free.

`🎨️palette/🎨️.css` is **byte-identical** after regeneration — appearance groups are not projected to CSS,
and no `colors`/`spacing`/`fontStacks` entry changed. React's rendering is unaffected by this packet.

## 5. The law

`🧰️framework/🔨️modules/🖱️ui/🧪️tests/🔬️targets-wgpu-theme-token-parity/🦀️.rs`, mounted from
`🎯️targets/🧊️wgpu/🎨️theme/🦀️.rs`. Five tests:

1. **`no_wgpu_target_paints_a_hand_written_colour_literal`** — walks
   `🖱️ui/🎯️targets/🧊️wgpu`, `🖱️ui/🧱️elements` and `💻️os/🔨️modules/📺️renderer`, keeps `.rs` files whose path
   contains `🧊️wgpu` and not `🧪️tests`, and flags any `Rgba::new(` / `Rgba::from_srgb8(` whose **first
   three arguments** are numeric literals. Alpha is deliberately excluded from the test, so
   `Rgba::new(0.58, 0.64, 0.72, 0.9 * opacity)` is still caught; `Rgba::new(tip.color.r, …)` and
   `Rgba::from_srgb8(r, g, b, 255)` (a parsed user hex) pass. Allowlist entries are keyed by
   *(path suffix, enclosing `fn`/`const` name, reason)* rather than line number, so neighbouring edits
   do not invalidate them. It asserts `scanned > 0` and that each scan root exists, so it cannot pass
   vacuously.
2. **`outcome_paints_decode_to_the_same_hex_react_paints`** — reads the **generated palette CSS React
   actually consumes**, extracts `--color-danger/success/warning/secondary`, and asserts
   `Theme::light()`/`dark()`'s `error`/`success`/`warning`/`progress` decode to exactly those hexes.
   This is the live assertion the audit's packet 10 asked for.
3. **`every_theme_metric_is_a_multiple_of_the_shared_ui_spacing`** — 13 metrics, plus exact equality for
   `control_height_small` and `chrome::ICON_TINY`.
4. **`veil_is_the_dialog_surface_at_the_shared_veil_alpha`**.
5. **`spatial_axis_paints_are_the_brand_tokens`**.

**Allowlist (6 entries, each with its reason in the source):** the `#[cfg(test)]` scissor-mask white;
`CANVAS2D_SELECTION_RING`/`_GLOW` (verbatim port of React's own `rgba(251, 191, 36, …)` literal in
`canvas-2d-host.tsx` — tokenising only the wgpu half would *create* divergence);
`canvas_color_channels`/`canvas_gradient_color_at` (malformed-payload defaults in pure `[f64] → Rgba`
decoders with no `Theme` in scope); `mono_theme`.

## 6. Remaining gaps

1. **`mono_theme` (os Shell, 20 literals).** The "mono" premade theme's chrome palette is hand-resolved
   from `🎨️styling/🌓️theme/🔣️.json` because `semio-framework-os-renderer-wgpu` has no `ui_styling`
   dependency. Fixing it properly means projecting premade themes into the generated Rust crate. Blocked
   on a real schema inconsistency: mono's `chrome` group declares six keys the default theme does not
   (`canvas`, `window`, `panel`, `hoverWindow`, `hoverPanel`, `temporary`, `overlayBg`) and so cannot
   share `ChromePalette`. Reconciling the two chrome key sets is a packet of its own; the codegen would
   then emit `CHROME_MONO_LIGHT/DARK` and `Theme::mono(dark)` would live in the ui target beside
   `light()`/`dark()`.
2. **React-side literals.** `canvas-2d-host.tsx`'s amber selection ring is a raw
   `rgba(251, 191, 36, …)` string with no palette token; whoever owns the React canvas should add a
   token, after which the wgpu allowlist entry for `CANVAS2D_SELECTION_RING/_GLOW` can go.
3. **`🖌️ui/🎨️.css` duplicates the `levels` block by hand.** `--z-base…--z-menu`, `--glass-saturate`,
   `--level-shade-step`, `--glass-alpha-step`, `--glass-blur-step`, `--element-shade-step`,
   `--hover-shade-step`, `--veil-alpha`, `--veil-blur` (lines 833-855) are all re-declared literally in
   the hand-written CSS instead of being emitted from `🔣️.json`'s `levels`. They currently **agree**
   value-for-value (verified), but nothing keeps them agreeing. Moving them into the generated theme CSS
   is a small React-side packet; I left `🖌️ui/🎨️.css` untouched to avoid colliding with concurrent work.
4. **`applyUiThemeToRoot` reads dead keys.** It looks for `theme.metrics.chrome.glassSaturate`,
   `shadeStepPercent`, `elementStepPercent`, `hoverStepPercent`, `glassAlphaStep`, `glassBlurStepPx` —
   none of which exist under `metrics.chrome` in `🔣️.json` (they live under `levels`). So switching to a
   custom theme never overrides those CSS vars today. Latent React bug, found in passing.
5. **Gizmo placement is not at parity.** `gizmo::orbit_view_gizmo_placement` uses
   `min(w, h) / 3` for both axes and omits the folded-pane clearance, while React's
   `resolveSceneGizmoViewportPlacement` uses `width/3` and `height/3` separately and adds
   `uiSpacingPx(7) + chromeInset` to the Y margin. Pure geometry, belongs to a Scenes packet.
6. **Px sizing literals** in the os Shell/Scenes (see §4) — notably the search overlay's literal
   `400 × 0.55·h` box and the chrome dialog's `360 × 168`. A px-token law (the analogue of this packet's
   colour law) would be the natural follow-up.
