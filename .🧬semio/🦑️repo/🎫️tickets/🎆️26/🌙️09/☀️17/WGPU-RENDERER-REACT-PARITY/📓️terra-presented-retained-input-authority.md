# Presented Retained-Input Authority

## Finding

The new Shell presentation witness correctly delays host hit geometry, retained owner maps, widget maps, and accessibility visibility until GPU acknowledgement. It does not yet delay the retained **interaction authority**. The sole `UiWindow.tree` and `UiWindow.router` are reconciled to the candidate document before that acknowledgement, and every retained dispatch API reads those live candidate owners.

The Button-specific `presented_action` override cannot repair this boundary. On `PointerUp`, `dispatch_presented_ui_pointer_event` dispatches through the candidate router; when that produces no command it unconditionally publishes the descriptor from the presented hit ([`Interpreter/🦀️.rs:837-854`](../../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🗣️Interpreter/🎯️targets/🧊️wgpu/🦀️.rs)). Thus a release without a recorded press, a release after cancellation, or a release over B after pressing A can create an action that `EventRouter` intentionally refused. It also cannot model `Select`, value-bearing controls, focus, Tab, or accessibility.

The currently registered Button regressions exercise those three gesture shapes in [`presented-input-authority/🦀️.rs:258-325`](../../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🐚️Shell/🧪️tests/🎯️presented-input-authority/🦀️.rs). This audit did not run them.

## Smallest coherent protocol

Keep **two bounded, move-owned retained interaction revisions per surface**, not a Button action shim and not an unbounded tree clone:

1. `PresentedUiRevision` owns the only dispatchable `UiTree` and `EventRouter`, plus exact surface token, globally monotonic document epoch, and `interaction_epoch`. It corresponds to the last accepted pixels.
2. `CandidateUiRevision` owns the tree/reconcile/layout/paint work for the next packet and records `(base_presented_epoch, document_epoch, candidate_witness)`. It is never an input target.
3. An arriving document reconciles into the vacant candidate revision. Seed it with a **bounded key-and-widget-kind interaction transfer** from the presented revision: `WidgetState`, retained focus/hover/overlay state, and capture only where their key and widget kind remain exact. The existing document maximum is `UI_DOCUMENT_NODES = 128` ([`document/🦀️.rs:95-100`](../../../../../../../../🧰️framework/🔨️modules/🖱️ui/🧬️contract/📃️document/🦀️.rs)), so transfer is a cursor over that owned ceiling. It must not clone a complete present tree at input time.
4. Every event that changes presented router/tree interaction state advances `interaction_epoch` before dispatch. At presenter acknowledgement, under the same interaction/runtime lock that already calls `acknowledge_presented_input`, require candidate witness and `base_presented_epoch` to match. On mismatch, discard the candidate packet through its existing bounded retirement path and rebuild from the latest document plus current presented interaction state. This linearizes a physical event and an acknowledgement: whichever gets the lock first determines the displayed input authority.
5. On exact acknowledgement, atomically swap candidate UI revision, Shell hit/owner/widget/geometry families, accessibility projection, and presented epoch. Retire the former presented revision one owned step at a time. The old revision is never dispatched after swap.

This is a fixed two-revision allocation, priced explicitly by the document resident ledger, rather than a clone per update or pointer event. The resident contract presently budgets 64 full-document baselines; it must account for at most one pending candidate per admitted live surface before the second revision is admitted. If the candidate permit is unavailable, leave the presented revision authoritative and defer candidate work—never mutate it in place.

The candidate must be invalidated **before** a packet becomes physically present, not after GPU rendering. A retained pointer down changes the presented interaction epoch; an acknowledgement that loses the race cannot promote its stale candidate. If acknowledgement wins first, its pixels and its revision become authoritative before the later down. This covers press/cancel/release without a special post-render capture workaround.

## Dispatch seams

### Pointer and wheel

Stage an opaque `PresentedRetainedTarget` with each candidate hit:

`{ presented_candidate_witness, surface_token, document_epoch, interaction_epoch, node, node_key, widget_kind, rect, control_id }`.

Keep it beside the staged `HitTarget` in the Shell retained-owner map. At dispatch, validate `control_id`, kind, and rect against the resolved `InputState` hit, then call `Ui::dispatch_presented_pointer_event(target, pointer_id, event)`. That method resolves the **presented** tree by exact token/epoch and verifies `node`, key, and kind before forwarding to its own `EventRouter`. It returns ordinary `UiCommand`s; `apply_ui_commands` publishes their existing intents. Delete `presented_action` from `route_retained_pointer_press` and from interpreter dispatch, including its no-command `PointerUp` fallback.

The presented router's normal capture and `PointerUp` rules then decide Button activation. Press A/release B, release-without-down, and cancel all remain no-action paths without a parallel gesture ledger. The same dispatch carries old accepted geometry/spec to Slider, Ring, and NumberStepper; it preserves Select option/overlay sequencing and Input edit state. Wheel and hover need equivalent presented-revision entry points because they currently call `dispatch_ui_event` against the candidate tree ([`Shell/🦀️.rs:13320-13345`](../../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🐚️Shell/🎯️targets/🧊️wgpu/🦀️.rs), [`:13598-13609`](../../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧱️elements/🐚️Shell/🎯️targets/🧊️wgpu/🦀️.rs)).

### Keyboard, Tab, and accessibility

`content_focus` must carry a `PresentedUiRevision` identity in addition to its current node/key/kind. `retained_keyboard_focus`, `retained_node_is_select`, `retained_node_has_visible_focus`, and retained capture lookup must query that presented revision. Thus Tab computes its next focusable node from the controls the user can see; a candidate-only control cannot receive Space, editing, or Tab focus. At acknowledgement, transfer focus only for the same key **and** widget kind; otherwise clear it without manufacturing a blur action.

Accessibility needs a staged, exact projection target rather than only a staged visible-window string. Publish `{ presented revision identity, document node id, node key, virtual Select option }` with the same candidate witness as the pixels. `dispatch_accessibility_event` must resolve this presented target and invoke the presented router. Candidate-only or removed controls are refused until accepted. This preserves its current Select-option guard while making the guard presentation-correct.

## Fail-first laws

Extend the existing neutral `presented-input-authority` fixture and Shell behavioral module; use actual retained document publication, candidate paint, presenter acknowledgement, and the normal event funnel.

1. Retain the three Button laws already added: no down, cancelled press, and press A/release B produce zero actions.
2. Present a `Select` with one option set, build an unacknowledged candidate that moves it and changes options/binding, then pointer and keyboard-activate the visible popup. Only the presented option/action may occur. Candidate option IDs must be absent from the presented accessibility projection.
3. Present a `NumberStepper`, then create an unacknowledged candidate with different range/step/binding/rect. Its click and drag must use the old value semantics; the candidate rect must not route. This proves the non-Button path does not silently fall back to hit descriptors.
4. Focus an `Input` or Select in the presented revision, then build a candidate that removes that key or changes its kind. Before acknowledgement, text/Space and Tab use the presented revision. On acknowledgement, same-key/same-kind focus transfers; removal or kind change yields no focused control and no synthetic blur action.
5. Stage a candidate-only accessible Button/Select option, attempt accessibility activation before acknowledgement, then acknowledge and repeat. The first action is absent and the second occurs exactly once.
6. Start a presented pointer capture, prepare a candidate, and order its presenter acknowledgement after the pointer event. It must lose the `base_presented_epoch` check and leave the old pixels/gesture authoritative. Reverse the order and require the new presented revision to own the later event. This proves atomic acknowledgement rather than a timing-dependent capture exception.

The existing browser oracle at [`renderer/🧪️tests/🎯️presented-input-authority/🟦️.ts`](../../../../../../../../🧰️framework/🛍️products/💻️os/🔨️modules/📺️renderer/🧑‍🎨engine/🧪️tests/🎯️presented-input-authority/🟦️.ts) remains the neutral cross-implementation route. Add the corresponding mounted React controls and real DOM event sequences there; avoid source-string assertions and synthetic action publication.

## Confidence

High confidence that the current Button fallback is a live ownership violation and that candidate tree/router reads affect every listed widget path. The two-revision protocol is the narrowest source-consistent route that preserves `EventRouter` as the single semantic reducer. Its resident-permit accounting and bounded interaction-transfer cursor need implementation design against the resident owner, so their exact struct names are intentionally left to that owner.
