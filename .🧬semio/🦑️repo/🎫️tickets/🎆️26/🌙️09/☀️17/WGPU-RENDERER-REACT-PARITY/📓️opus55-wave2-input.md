## 1. Key repeat (React `KeyboardEvent.repeat` / winit `KeyEvent::repeat`)

One flag, carried end to end so Paint2d's 8-px stride (`PixelKeyInput.repeat`, already implemented) is reachable:
- `ui/🖌️render/🖱️dispatch/🫧️events-bubble-and-capture`: `DispatchEvent::KeyDown { key, modifiers, repeat }`.
- `ui/🖥️host`: `key_dispatch_event(.., pressed, repeat)`; winit path (`🪟️window`) passes `event.repeat`; the browser ABI (`📡️event`, `🪟️window/🟨️.js`) adds the flag as modifier-byte bit 16 (`KEY_REPEAT_BIT`) on key events; a key-up never carries it. `engine/.../🪟️winit-app/🚀️native-winit-app` passes `event.repeat` too.
- Browser wire: Rust `BrowserWireEvent::KeyDown` gains required `repeat` (no default, no compat); TS `BrowserFrameLosslessEvent` splits `key-down` (has `repeat`) from `key-up`; `BrowserFrameDomEvent` `keydown` has `repeat`; `🎮️input-wire/🟦️.ts` reads `event.repeat`.
- Shell KeyAction route: `semio_ui_wgpu_input::PointerModifiers` gains `repeat: bool` (the snapshot that already travels with every `KeyAction` into `handle_key` -> `handle_keyboard_async`); `interaction-state` builds `PointerModifiers { repeat: *repeat, .. }` for key-down; the shell keyboard route passes `modifiers.repeat` into `PixelKeyInput` (was hard-coded `false`). Pointer events keep `repeat: false`.
- All struct literals updated by hand: 13 `PointerModifiers` literals (gumball laws, authority-core x3, pointer-input, quick-search, canvas-pointer, mod-chord, chrome-parity x2, host-door, winit-p3c x2, shell-bound) and all `DispatchEvent::KeyDown` literals (enqueue-unit x7, dispatch-unit x12, winit-p3c, async-boundary, browser-input-wire projection).
- Fixtures/tests: `engine/🧪️tests/🧫️fixtures/🎮️wgpu-browser-input-wire/🔣️.json` (every key-down row has `repeat`; new row `key-down-held-arrow-repeats` with `repeat: true`; `pointer-order.json` key row), Rust law `🎮️wgpu-browser-input-wire` projects `repeat`, TS keyboard-scope test `carries the DOM auto-repeat flag of a held key on keydown only`, host `event-unit` test `browser_key_events_carry_the_auto_repeat_bit`.
- Not done: `SurfaceInput::KeyDown` (`ui/🖌️render/🗺️surface`) has no repeat; nothing reads it.

## 2. Click count (React DOM `MouseEvent.detail`, `dblclick`)

- Design: winit has no click count and the browser wire carries none, so the router counts. `EventRouter::note_press` (`ui/🎯️targets/🧊️wgpu/⚡️events/✍️drag-scroll-and-edit-api`) keeps ONE `ClickChain { seconds, x, y, button, count }`: a press by the same button within `DOUBLE_CLICK_SECONDS = 0.5` and `DOUBLE_CLICK_SLOP_PX = 4.0` per axis of the previous one continues the chain (count saturating, like `detail`), anything else restarts it. 0.5 s and 4 px are the OS defaults every browser reads (Windows 500 ms / 4 px, macOS 0.5 s); winit has no query, so they are constants in one place. The old private 0.4 s constants of Tree (`TREE_DOUBLE_CLICK_SECONDS`) and text (`TEXT_MULTI_CLICK_SECONDS`) are removed, so there is one value; `FocusState.tree_last_press` and `text_click` are gone; the chain is transferred with the router (`transfer_interaction_from`). The slider readout keeps its own 0.5 s rule (React's slider owns that timer; fixture `⌨️slider-readout-editing`).
- The count is the router's clock based (`advance_clock`), so tests drive it deterministically.
- Document `Table` rows (`document_table_row`): a single click only focuses (the press already focuses the row, React `moveTo`); the second click of a chain (count exactly 2, React fires `dblclick` at 2) fires the row's own `Trigger::Activate` once (`route_table_row_click`, `🌳️tree-roving-and-keys`). A single click no longer activates. Row action icons keep firing on a single click; a triple click fires nothing.
  - Fixture `ui/🧪️tests/🧫️fixtures/📊️table-row-grid/🔣️.json` `expected.clicks` now has `count` and a `fires` list (single click on the row: none; double: `open-space`; triple: none; empty slot likewise). Test `a_click_on_an_action_icon_fires_that_action_and_a_double_click_anywhere_else_on_the_row_its_activation` plus new `two_clicks_further_apart_than_the_os_interval_or_slop_are_two_single_clicks_and_never_activate`. TS twin: Interpreter table test `focuses a row on a single click and fires its own activation on a double click, once`.
- Tree: `route_tree_press` now uses `click_count() > 1` (React `event.detail > 1`); a third click also yields (the old code let it click again). React's interpreter wires NO `onDoubleClick` for document tree rows (`🗣️Interpreter/🧱️node-tree` only has one for the table; `🍃️item` forwards it only when given), so a double click emits nothing: unchanged and now documented.
- Surface table (`TableHost`) DONE (round 2, code only). React's base `Table` row does `if (e.detail >= 2) { onRowDoubleClick?.(...); return; } onRowClick(...)` and `TableHost` passes no `onRowDoubleClick`, so the second click of a double click neither re-picks nor activates. Plumbing: `UiCommand::Scene` gains `click_count` (router fills it from the click chain); `apply_scene_ui_command` takes `click_count` after `event` and stores it on `SceneIntentEvent::PointerUp`; the passive scene pointer handler receives it as `SceneModifiers.click_count` (new field, `0` = unknown); `passive_scene_pointer_button` returns before the row action for `SurfaceKind::Table` when `click_count >= 2` (after the list-transfer release, so a row drag still drops). Other list kinds (VFS `navigateUri` double click, feed, block list) are unchanged. Sites updated by hand: the `scene_command` constructor, the Interpreter engine caller, 12 `apply_scene_ui_command` test calls, 9 `UiCommand::Scene` test literals, the events-unit pattern, the `SceneIntentEvent::PointerUp` patterns, 4 `SceneModifiers` literals. New test: `the_second_click_of_a_double_click_on_a_surface_row_dispatches_nothing` (`🎞️Scenes/🧪️tests/🔬️wgpu-table`).

## 3. Text input leftovers (`ui/🎯️targets/🧊️wgpu`)

- First click places the caret at the pointer: `begin_text_pointer` places it through the parked layout; when the field has no current layout yet (first hover/focus not yet painted) the press is parked (`PendingTextPress`) and `EventRouter::settle_text_press` (called by the engine frame step right after `refresh_input_text_layout`) places it at the first layout, then spends it. Cancel clears it.
- Double/triple click then drag: a press now always arms `TextDrag { node, unit, origin }` (unit 1 character, 2 word, 3 logical line); `drag_text_pointer` extends by that unit, keeping the clicked span selected (anchor on the clicked span's far end when dragging back, as browsers do).
- Wheel over an UNFOCUSED textarea: `scroll_text_area` no longer needs an edit buffer (live text is the edit text, else the published value); `refresh_input_text_layout` now lays out every `longText` input (not only hovered/focused) and stores clamped scroll for textareas; the painter applies `scroll_offset` to a textarea even when it is not editing. The wheel still yields to ancestors at its limits.
- Auto-grow (React `Textarea`: `field-sizing-content min-h-huge`, overridden to `min-h-[4.5rem]` by the Interpreter): the paint walk parks `WidgetState.textarea_grow` (= wrapped lines x line height + 2 x padding) and asks for layout; mounted layout sets the `longText` control height to `max(TEXTAREA_MIN_HEIGHT, textarea_grow)`. No max height, like React. The single-row property-column mode (`h-medium`) does not apply to the Interpreter's textarea (it never passes `showLabel`).
- New tests (events-unit text vector laws): `the_wheel_scrolls_an_unfocused_textarea`, `double_click_then_drag_extends_the_selection_by_word`, `triple_click_then_drag_extends_the_selection_by_line`, `a_first_press_before_the_first_layout_places_the_caret_once_the_layout_arrives`. No test written for auto-grow (needs a font atlas; paint-unit candidate: `refresh_input_text_layout` on a wrapped `longText`, assert `textarea_grow` and a layout pass height).
