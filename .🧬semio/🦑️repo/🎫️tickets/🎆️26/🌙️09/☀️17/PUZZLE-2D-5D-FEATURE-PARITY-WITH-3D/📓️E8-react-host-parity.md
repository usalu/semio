## 2. 5d parity

Editor tree root: `✏️s/🔌️plugins/🧩️puzzle/🗿️artifacts/🖐️5d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/`

**Surface kinds emitted for 5d windows** (from `…/✏️editor/🪟️window/🦀️.rs` + per-mode window dirs):
- Editor / edit mode has **two** window kinds: `◻️2d` (…/🎭️modes/✏️edit/🪟️windows/◻️2d/) and `🧊️3d` (…/🎭️modes/✏️edit/🪟️windows/🧊️3d/).
- Viewer / view mode has **only** `🧊️3d` (…/👁️viewer/🎭️modes/👁️view/🪟️windows/🧊️3d/) — no `◻️2d` window under the viewer tree. If a read-only 5d view is expected to show both panes, this is a real hole; if the viewer is 3d-only by design, it's fine — worth confirming with the ticket owner, flagging as **unverified, not assumed**.
- `🧊️3d/🟦️.ts` (…/🎭️modes/✏️edit/🪟️windows/🧊️3d/🟦️.ts:1-15) is a thin typed twin: `PUZZLE5D_WORLD3D_WINDOW_KIND_ID = "puzzle5d-3d"`, `surfaceId: "puzzle.5d.play.3d"` — **same shape as puzzle3d's own window surface id pattern**, confirming the 5d 3d pane goes through the same `scene_surface`/`Puzzle5dScene` → `World3dHost` rendering path puzzle3d uses (doc comment at :1-4 explicitly says it mirrors `render(envelope: &Puzzle5dScene, tool_run: Option<&ToolRunView>, mesh_lane: &[String])`).

**5d 3d-window utility gap vs standalone puzzle3d:** puzzle3d's `🧊️main` window has three utilities — `🔄️transform`, `🚚️world-relocate`, **`🧊️volume-brush`** (`✏️s/🔌️plugins/🧩️puzzle/🗿️artifacts/🧊️3d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/🎭️modes/✏️edit/🪟️windows/🧊️main/🪛️utilities/`). 5d's `🧊️3d` window only has **`🔄️transform`** and **`🚚️world-relocate`** utilities (`…/🖐️5d/…/🪟️windows/🧊️3d/🪛️utilities/`) — **`volume-brush` is missing from 5d's 3d pane**, a concrete parity gap between paired-5d and standalone-3d, separate from the 2d-host gaps above.

**Hover/selection sharing between the two 5d panes:** not resolved from TS in this pass — the 2d↔2d peer-mirror mechanism (`BoardPeerScope`/`registerBoard2dPeer` in `🖥️Board2dHost/🟦️.tsx:287-369`) is generic and keyed by `controllerId`, so it would mirror 2d-pane-to-2d-pane state, but there is no equivalent peer-scope file found for 2d↔3d cross-kind mirroring; the 3d side's `interactionSelect`/`interactionHover` dispatch and the 2d side's `applyBoardEvents` both flow through the same generic `onAction`/framework dispatch, so cross-pane consistency for 5d most likely happens at the guest (`Puzzle5dScene`) level, re-deriving both panes' selection from one shared document selection rather than a client-side peer bus. This needs a guest-side (Rust) check to confirm, not resolvable from TS alone — **flagging as unverified**, not claiming a bug.

**5d-specific TS pieces found:**

## OWED list (host-side, concrete)

1. **Transform gumball for 2d nodes** — missing at the engine level (no rotate/scale handle in `♾️infinite/🎲️board/🦀️.rs` or the wgpu port) and consequently absent from `Board2dHost` (zero `gumball` references). Needs new board-engine handle roles + TS wiring (`WorldGumballTransformPreviewStore` is the 3d reference implementation, 🌐️World3dHost/🟦️.tsx:4884-4999).
2. **Suggestions popup for 2d** — `Board2dHost` has no `WorldSuggestionMenuRecord`-equivalent, no `acceptSuggestion`/`openVortexSuggestions` actions, no popup `ContextMenuController`, no `data-suggestion-menu-json` vitals. `session.setSuggestionOffset` only tunes in-canvas chrome; there's no DOM-level suggestions UI at all for 2d.
3. **Probe vitals gap** — `Board2dHost` exposes 10 `data-*` attributes vs 3d's 16+; specifically missing: `data-window-instance-id`, a guest-confirmed-vs-local selection split (3d's `data-guest-selection-json`), `data-interaction-json`, `data-status-json`, and any compute-phase/progress attributes. Headless probes against 2d have materially less surface to assert on.
4. **5d's 3d pane is missing the `volume-brush` utility** that standalone puzzle3d's `🧊️main` window has (`✏️s/🔌️plugins/🧩️puzzle/🗿️artifacts/🖐️5d/…/🪟️windows/🧊️3d/🪛️utilities/` has only `transform` + `world-relocate`, vs puzzle3d's `transform` + `world-relocate` + `volume-brush`).
5. **5d viewer mode has no `◻️2d` window kind** (only `🧊️3d` under `👁️viewer/🎭️modes/👁️view/🪟️windows/`) — unverified whether this is intentional (read-only viewer may be 3d-only by design) or a real gap; needs confirmation from the ticket owner / a guest-side check before treating as OWED.
6. **Board fixture sync has no paging** — `Board2dHost` re-parses the whole `fixtureJson` string on every scene change (`applyFixtureToSession`); 3d has an explicit paged mesh-upload queue (`PUZZLE3D_MESH_UPLOAD_QUEUE_PAGES`, `drainPuzzle3dBrushMeshQueue`). Not urgent against current fixture sizes, but will not scale the same way if 2d boards grow large.
7. **Cross-pane hover/selection sharing for 5d (2d↔3d) is unverified from the TS side** — the existing peer-mirror bus (`BoardPeerScope`) only mirrors 2d↔2d; whether 5d's paired 2d/3d panes share selection via the guest document or need a new cross-kind bridge needs a Rust-side check (`✏️editor/🎮️commands/🎛️engagement-control-select/🦀️.rs`, `🎯️retarget-fastener`, `📡️proximity-connect` are candidate command names to check next, not inspected in this pass).

## Non-findings (explicitly checked, not gaps)

- `subscribeSpawnedJobProgress` is unused in both hosts — this is a pre-existing framework-wide gap (only consumer is `🏛️ShellHost/🟦️.tsx`), not 2d-specific.
- The base right-click context-menu mechanism is shared/generic (`useMapContextMenuSpecs`, `openSurfaceContextMenu`) and resolves content guest-side for both hosts — the Hide/Show/Lock/Duplicate/etc. doc-comment in `Board2dHost` (🖥️Board2dHost/🟦️.tsx:217-223) describes guest-resolved menu content, not a missing TS implementation.
- The historical unquoted numeric `2d:` key that broke Vite's dep scan was **not found** in any current 5d schema/window TS file checked (`🎚️config/🧬️schema/🟦️.ts`, `🪟️window/🧬️schema/🟦️.ts`, `🎯️targets/⚛️5d-react/🟦️.tsx`) — appears already fixed, all keys are properly quoted (`camera2d`/`camera3d`, `"2d"`/`"3d"`).
- Both the dev plugin-modules wasm and the distribution bundle wasm include Puzzle5d symbols alongside 2d/3d — 5d is not missing from either build artifact.
