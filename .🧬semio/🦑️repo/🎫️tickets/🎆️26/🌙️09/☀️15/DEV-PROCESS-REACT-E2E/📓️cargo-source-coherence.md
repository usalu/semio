# Cargo Source Coherence

The direct repository Cargo launcher obtains and admits a Cargo compilation graph, then runs Cargo with the original checkout working directory: `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏃️process/🦀️cargo/🚪️launcher/🟦️.ts:281–298`. Its admitted execution path does not materialize a frozen Rust source tree. The relay independently admits the source boundary and then calls `startToolV1("cargo", ..., { cwd, ... })` at `📚️library/🏃️process/🟦️.ts:76–89`. Thus admission reads Rust content for source bounds and graph facts, but is not a lock on checkout source bytes throughout Cargo/rustc execution. Cargo can compile a dependency before a replicated edit and read a consumer after it. The observed matched source edit timestamps and diagnostics are consistent with this mechanism; they do not alone prove which bytes each rustc read.

The separate generated Rust unit path records source path, digest and byte length and verifies an individual unit against its descriptor (`📚️library/⚡️caching/🦀️cargo/📦️units/📥️inputs/🟦️.ts:11–14` and `📦️units/📥️descriptor/🎯️selection/🟦️.ts:42`). The selected Native snapshot in `📚️library/🏗️build/📥️inputs/🎯️selected/🦀️rust/🟦️.ts:7–10,28–33` is conditional on an eligible selected graph consisting only of unit and aggregate tasks; it supplies a snapshot to the Nx selected inventory and hashing integration. It is not evidence that ordinary `repo cargo` executes rustc against a frozen workspace. The snapshot capture rechecks source after its reader completes (`📥️inputs/🎯️selected/📦️snapshot/🟦️.ts:37–40`).

The documented fresh native generation parameter applies to the Play build and root release targets (`🦑️repo/README.md:1229`); its documentation does not claim a coherent checkout snapshot. No supported direct-Cargo option to freeze the source revision during replication was identified in the inspected launcher. A new direct Cargo run after the related edits have settled is a current-source retry, but may still encounter future concurrent edits. No build was started.

## Failed-pass recovery refinement

The launcher has bounded held-lane recovery for some failed passes (📚️library/🏃️process/🦀️cargo/🚪️launcher/🟦️.ts:253–272). It requires exit 101, a recognized dependency diagnostic, no full-storage recovery, no compiler signal, exactly one noncached failed unit with exit 1, and dependency artifact filenames. It checks bounded dep-info checksums against live in-workspace source bytes; a differing byte witness permits source readmission before retry. 🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🧩️component-pass/🔁️failure-churn/🟦️.ts:90–132,145–166,196–213 bounds the witness checks and retry count, rejects changed retry unit graphs, and prevents repeating a witness. The success message is logged only after source readmission completes.

In the exact PID 4897 supervisor segment (byte offsets 46024264–56521254 of 🗑️generated/supervised-editor.log), E0432 for ray_event is followed by renewed 1,030-unit source-admission observations and a refusal for native-registry active lines 4058/4000. This sequence is consistent with dependency drift being detected and held-lane readmission starting, then failing before its retry announcement or a new compile. The log does not directly print the drift witness or establish that Cargo retried or that the predicate problem is resolved. The PID 26307 segment (offsets 0–7201815 of supervised-native-scope.log) records two E0599 return_scoped_alias errors and exit 101; no held-lane retry announcement appears in that segment. It likewise does not establish why recovery did or did not qualify. Both are failed runs, not evidence of a fresh successful compile.
