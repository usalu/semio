# Graph worker memory accounting

The capacity ledger at 19:42 UTC on 21 November showed 4,352 MiB observed for the quiet Process3d React launcher (PID 34196) and 3,764 MiB for the separately admitted graph plan (PID 34231). The operating system process table put the graph plan service below the React launcher through PID 34204. The graph reservation records the attached slice worker's footprint. The enclosing default observer traversed the same descendant tree, so both rows priced the worker's memory. This could exclude a smaller command from admission while a larger request was waiting. The effective kernel pressure and floor are independent of these ledger entries.

The default heartbeat now treats a graph worker already observed under its separate grant as an excluded subtree. It samples the enclosing process and any explicitly attached trees together in one operating system snapshot. The traversal counts a process at most once and keeps attached processes outside the enclosing tree in scope. Injected observers continue to use their own measurement contracts. Assessment of the retained native and browser invocations uses their own logs because those processes had already entered with the older capacity implementation.

The shared process-tree fixture reproduced the incorrect result of 31 MiB. The corrected observer and an independent SQLite recursive query each returned 103 MiB. The footprint and sampling suites passed 30 cases, the separately invoked Windows suite passed 6, and the capacity gate suite passed 33. Real Linux and Windows-only process tests were skipped on this macOS host where applicable. Running the Windows stderr-once test in the same Bun process after the Linux sampling suite reused the prior warning state. The Windows suite passed in its own process.
