# Cargo Wrapper Fanout

A read-only process-tree sample of live Cargo PID 69197 found 112 processes and 3,930,464 KiB summed RSS, including approximately 90 Bun wrappers, ten scheduler children and two rustc. RSS sums count shared pages repeatedly. Sanitized process environment showed CARGO_BUILD_JOBS=1, SEMIO_COMPILER_PARALLELISM=1, jobserver flags -j1, and SEMIO_UNIT_CACHE_SLOTS=10. The one-core launch is not an evidence of a one-process wrapper bound.

The launcher obtains an exact compiler capacity and creates a same-sized jobserver (🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏃️process/🦀️cargo/🚪️launcher/🟦️.ts:230–241). Shared lane enables the unit-cache wrapper and does not pass its slots option. The cache launch default is availableParallelism(), which was observed as ten (📚️library/⚡️caching/🦀️cargo/🗃️unit-cache/🚪️launch/🟦️.ts:103–121). Cache slots are acquired only inside the local compile path, after wrapper startup, argument parsing and source hashing (🗃️unit-cache/📜️script.ts:87–110); cache and remote lookup/offload are reached separately at :139–174. The scheduler broker bounds downstream compiler work; it does not bound the earlier Bun wrappers or their lookup work. Setting slots to the admitted count would bound local compile-slot permits but alone cannot bound wrapper processes or their earlier work.

The reason Cargo started many direct wrapper children despite its observed one-job settings was not established by this audit. A safe source correction requires an explicitly bounded admission before expensive wrapper lookup, preserving jobserver ownership and release across cache hit, offload, cancellation and failure; it must also propagate the admitted count into local cache slots. Avoid asserting a particular patch correct without tests for those lifetimes and for the actual Cargo process. No live process or build was modified.

The 17:23 UTC filtered sample identified 91 direct unit-cache wrapper children, including several that had been alive for more than four minutes. Both live Cargo parents had `CARGO_BUILD_JOBS=1` and `SEMIO_COMPILER_PARALLELISM=1`; both exported an authored `-j1` FIFO jobserver and ten local cache slots. Sampled native-scope wrappers inherited a Cargo-generated FIFO authentication field. Neither Cargo parent had a numeric `--jobs` or `-j` argument overriding the environment. Upstream Cargo keeps a metadata-complete unit active until it finishes completely, and starts additional active units against held jobserver tokens. This makes metadata pipelining alone insufficient to explain the observed parent-child count. The installed binary and the provenance of its held tokens remain unverified. [Cargo job queue source](https://doc.rust-lang.org/stable/nightly-rustc/src/cargo/compiler/job_queue/mod.rs.html#576)

At 17:50 UTC, the same WGPU scope test using the isolated store (launcher PID 34321, Cargo PID 38196) had two repository Bun processes, one scheduler and one rustc in a live sample, with about 285 MiB summed Bun RSS. The isolated launcher did not exhibit the earlier shared unit-cache wrapper fanout at this point. This observation supports using the isolated lane to separate native behavior from shared caching while the exact cause is investigated.
