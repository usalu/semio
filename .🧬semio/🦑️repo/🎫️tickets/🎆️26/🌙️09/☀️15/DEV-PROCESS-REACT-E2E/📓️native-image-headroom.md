## Existing recovery behavior

- The shared launcher monitors image headroom while a compile holds its lane. A nonzero Cargo exit whose output matches the declared disk-full patterns triggers one single-flight collection attempt and one repetition of the exact Cargo command while its build directory, target directory, and lane lease remain held. If another collector holds the claim, the operation returns without waiting, reports zero removals, and proceeds to the retry. If the retry reports full storage, repo reports the remaining free space and returns its final outcome.
- Collection cannot remove the active lane or its live profile. The collection order accounts for idle incremental sessions, idle lanes and cold units under the store’s capacity rules. On exit, shared lane retention publishes owned provenance and then releases the lane. Its artifacts remain available until normal pool trim or pressure collection removes them. The pool tracks a 23.4375% lane share of the smaller applicable capacity or quota, and an idle lane can become collectible immediately under pressure.
- Shared target selection changes such as `--lib` or `--test <name>` preserve the lane key when the same `-p` set is selected. The pool prefers the newest free lane for that package set if it survives. Splitting shared commands can execute a subset before linking the others, while later invocations can still accumulate harnesses in that same lane.
- The isolated selector uses the same physical store but creates a distinct build, target and temporary namespace per invocation. Retirement removes the namespace after an invocation returns, including on failure. Serial one-target isolated calls therefore avoid accumulating this package’s test executables across commands. They do not reuse a pooled lane or its compiler unit-cache wrapper. Each still needs physical headroom for its dependencies and selected harness.
- The manifest declares eight named integration targets. Equivalent split coverage of the package’s regular harnesses includes `--lib` and these `--test` names: `process3d_bearbeiten_pane_smoke`, `process3d_interaction_behavior`, `process3d_workpiece_window`, `process3d_panels_inspection`, `process3d_panels_artifact`, `process3d_panels_catalogue`, `process3d_panels_workshop`, and `original_host_configuration`. An unfiltered Cargo test also selects library doctests by default, which can be covered by a separate `--doc` invocation when reproducing that command’s coverage. The presence of a linked binary is not a passing harness result. [Cargo test target selection](https://doc.rust-lang.org/cargo/commands/cargo-test.html#target-selection)

## Compiler profile admission

The repository storage argument gate rejects caller-supplied `--config profile.prototype.debug=0`. It accepts only the issued repository config path and the exact build/target directory selectors before the profile issuer adds its own configuration. The ingress also rejects caller `CARGO_PROFILE_*` environment variables. The effective Cargo profile verifier checks the exact settings issued by the native prototype profile, which fixes target debug to 1 and strip to none. The policy has no lower-debug native prototype test selector. Release has an independently issued profile and changes optimization, linking and debug checks in addition to debug information, so its result would be release verification.

No tests, eviction, image changes or cache writes were initiated by this preflight.
