# Component Pass Memory Admission

The current reported parent reservation is 4608 MB and the predicted final is 4256 MB: the prediction is 352 MB below that reservation, before considering other process overhead. This audit does not establish the final's actual peak or that it has started.

The first local pass has no enforced comparison against that parent memory reservation. `runPassesInJobSlotsV1` unconditionally assigns the first pass a local slot when `localHeld === 0`; the optional extra-local reservation accounting is only constructed when more than one local job is allowed. Nested compiler capacity scopes subdivide parallelism, and the facts they pass to the component driver expose parallelism only. The pass-level prediction is not used to refuse or enlarge the first local reservation.

The final is not simply an unguarded rustc: the driver configures the cache wrapper with the native scheduler as its inner compiler and supplies the broker endpoint and pass ID. A cache miss or ordinary fleet fallback calls that scheduler, which sends the parsed final unit to the broker and waits for its verdict. A missing broker or unparsable unit uses scheduler passthrough, so that guarantee is conditional on the expected wrapper environment and parse. A remote completed unit does not run locally.

The broker independently computes its budget from effective physical memory, a token share and its reserve; it is not capped by the actual 4608 MB parent grant. `admitWaitersV1` selects the first waiter when no unit is running even if the prediction exceeds the broker budget. Its additional `availableAdmissionV1` gate still blocks on warden guard/danger or high swap and ordinarily checks predicted bytes against sampled available memory less a 15% physical-memory margin and unrealized reservations of this broker's running units. It does not subtract other grants' unrealized reservations or compare against the parent grant. With unknown available memory it allows immediately; with known insufficient memory it allows an idle waiter after 180 seconds if the warden is calm (twice that for a recent cancellation). These are concrete paths by which an oversized final can proceed despite exceeding the enclosing reservation, subject to the other guards.

For expensive final units, offload policy tries a fitting fleet worker first. If none fits, it falls back locally unless `unitBeyondHostV1` sees a measured or learned peak above the 16 GiB class's 4096 MB final ceiling; a predicted 4256 MB alone is not the learned measurement that function reads. `never` mode remains local. An explicit beyond-host fleet refusal returns failure, but an offload exception is caught and can fall through locally. Local fallback still goes through the scheduler/broker chain described above. The warden's 4096 MB default final ceiling is reactive enforcement, not an advance reservation check, and can cancel a unit that grows beyond it.

The discrepancy is structural: the reported 4256 MB prediction happens to fit 4608 MB, but there is no proof that it or the total process tree stays within that grant. A complete fix should connect an actual retained memory allocation to the first pass and each final admission, include its non-rustc footprint and concurrent reservations, and make any larger final wait, acquire additional real capacity, or run under an independently admitted worker. Do not replace the guard with a time-based oversubscription rule. No build or source modification was performed in this audit.
