# CAS PUT and Collection Audit

The remote-execution sidecar constructs its host CAS with `refuseOverCap: true`. A CAS PUT enters `CasStoreV1.putChecked`, which calls its guard before creating the temporary object. When the write would cross the partition reserve, the guard requests an unbounded-step **unreferenced-only** sweep and waits within its bounded admission budget. Its collector excludes held, pinned, leased, linked and too-young objects. The server also periodically calls `casEnforceTickV1`; under reserve it sweeps unreferenced objects first, and its ordinary periodic sweep uses 4 GiB steps and a 60-second interval. The configured in-flight minimum age is 180 seconds. The 507s therefore do not by themselves demonstrate absence of collection or the availability of reclaimable safe objects.

There is a concrete diagnostic and deadline mismatch in the owner path. `RemoteCacheStoreV1.writeSignal` defaults to a 10-second timeout for the entire PUT, while the CAS admission policy allows 30 seconds for its synchronous collection. The store's `putChecked` catch converts **every** exception to the `capacity` outcome unless the outer server signal is aborted; the handler renders that outcome as HTTP 507. A slow collection or unrelated I/O exception can consequently be reported as insufficient storage. The reserve sweep is shared and is started without the per-request cancellation signal, so it can continue after one caller times out. This source evidence proves that misleading classification is possible, not that it caused this particular server's 507 or that a reclaimable object exists there.

An owner-level repair should preserve typed capacity refusal as 507, distinguish bounded timeout and infrastructure I/O as retryable service failure, and give the request a bounded duration that covers the actual guard admission budget and authorized input streaming. Tests should exercise a slow sweep that ultimately makes room, a completed protected-only sweep that really must refuse, cancellation, underlying I/O error and concurrent writers. The guard's holder, pin, lease, link, age and authentication boundaries must remain intact. No code was changed in this audit.

The standalone `repo remote-cache serve` command currently constructs its host store without the explicit `refuseOverCap` option; the sidecar uses it. Which launcher owns the observed `.70:6094` endpoint must be established before applying either path to the live server. Its status reports remote cache metadata and health, but the fleet status `cas` and `storage` sections are read from the querying machine. Remote worker records include host memory/pressure and warden information, including optional swap-volume free space, but do not expose the remote CAS root, holder census or filesystem reserve. Server-side status is needed to attribute the remote physical space.


## Fix and verification

The host-backed cache now reports the typed CAS cap refusal, disk low-space refusal, ENOSPC and EDQUOT as capacity; other host failures, including expiration of the bounded write, are unavailable. The HTTP server maps those to 507 and 503 respectively. Authentication and the filesystem reserve remain in force. The host write deadline includes the existing 30-second admission allowance plus its 10-second write budget. The offload per-request content deadline is 50 seconds (previously 20); its outer 300-second upload budget remains in force. Content HTTP retries include 503; replayable outage handling also recognizes 507.

The new focused host test failed before the fix and passed afterward (one test, seven assertions). The focused content deadline test also failed before the policy change and passed afterward. The complete HTTP admission owner fixture passed (four tests, 155 assertions): its leased-input over-cap scenario explicitly supplies healthy synthetic filesystem capacity, then low synthetic free space, proving both outcomes independent of the workstation disk. The HTTP status fixture also exercises 401, 503 and 507.

These edits affect future clients and servers; neither the running remote daemon nor the already sealed offload client was deployed or changed. A genuine 507 still requires addressing the owning server’s disk reserve; this evidence does not establish that its free space is recoverable.
