# Remote cache status contract audit

On 2026-11-26, `repo remote-cache status` resolved fleet facts generation 13 to the configured `.70:6094` endpoint and reported three authorized 404 read probes, while its signed GET `/status` returned HTTP 200 and `malformed`. An independent read through the same `resolveAuthorisedRemoteCacheV1` and `remoteCacheFetchV1` functions obtained JSON and validated it with the exact local `ServerStatus` schema: the complete validator errors are `/session is not allowed` and `/ledger is not allowed`. No credential values or response contents were recorded. The response has the expected status structure, including counters, and those two additional object fields. HTTP 404 probes prove reachability and authorization for those missing read paths; they do not establish successful uploads or general cache health.

This is a demonstrable local contract drift. The closed schema (`📚️library/🏗️build/🏃️execution/🧬️schema/🌐️remote-cache.json:333-338`) disallows unknown properties and has no `session` or `ledger`. The local handler (`🌐️remote-cache/🖥️server/🟦️.ts:173-176`) explicitly emits both when a counter ledger is configured; the same server module opens that ledger at line 377. `askServerV1` (`⌨️command/🟦️.ts:184-197`) validates the entire document and maps either schema failure to malformed, losing the server metrics. This explains the observed status error without asserting failure of the server or identifying its deployed source version. The server type and schema should be reconciled schema-first with tests covering the actual ledger-enabled response and independent validation, rather than weakening the closed shape or discarding fields.

The per-host graph service has a hosted cache (`🏠️hosted/🟦️.ts:12`); topology separately defines `repo remote-cache serve` launchers for Linux, macOS and Windows (`🤝️shared-worktree/🗺️topology/🟦️.ts:389,433,471`). A signed response does not identify which owns the remote port, so this audit does not decide the server/sidecar ownership question in `cas-put-audit-26.md`. The earlier CAS report concerns upload capacity and remains a separate question. No SSH, restart, server write, or production code change was performed.


## Fix and verification

The canonical closed ServerStatus schema now shares a closed Counters definition for cumulative and session ac/cas/nx counters, and defines a closed ledger with nonnegative integer sinceMs and restarts. Both fields remain optional as in the server type and actual handler; this preserves the existing no-ledger response. No unknown fields or untyped objects were admitted.

An isolated actual ledger-enabled HTTP server response failed the independent Ajv check before the fix. Afterward the focused test passed 17 assertions: both Ajv and the repository validator accept the emitted status and a no-ledger status, and reject five neutral malformed cases covering negative ledger values, extra keys and an invalid session counter.

The actual read-only repo remote-cache status --lang=en command subsequently exited 0 with serverFault null, remote reachable true and authorised true, and non-null entries, bytes, capacity, hit and miss metrics for fleet facts generation 13. This is a status observation; it does not establish that a CAS upload is possible or resolve the separate 507 reserve issue. No remote writes or service restarts were performed.
