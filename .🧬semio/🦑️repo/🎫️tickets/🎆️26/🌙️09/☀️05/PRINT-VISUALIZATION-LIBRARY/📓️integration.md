### The second-subject question, answered

**A second `typescript` subject cannot be added to an existing print case, and no coordination is
needed for that — the platform makes it structurally impossible.** The evidence, from
`🦑️repo/🔨️modules/🧪️test/📦️packages/🟦️typescript/🟦️.ts` and its `📜️script.ts`:

* `testAdapterFileKinds` maps ONE filename per language (`🟦️.ts → typescript`, `🦀️.rs → rust`,
  `🐹️.go`, `🐍️.py`, `🔷️.cs`), and `discoverTestCases` keys `adapters` by that mapping. A case
  therefore has at most one adapter per implementation.
* `TestAdapter` gives each scenario exactly one `subject` and one `oracle` handler
  (`type TestAdapter = { implementation, scenarios: Record<string, { subject?, oracle? }> }`).
* `selectImplementations` returns `Object.keys(discovered.adapters)`, and every print case's single
  adapter is `🟦️.ts` with `implementation: "typescript"` whose `subject` compiles the LaTeX probe.
  So `typescript` is already taken, by LaTeX.
* `evaluateCrossSubjectParity` compares subjects of *different* implementations, so it could never
  see two TypeScript subjects even if they existed.

Three ways forward, in the order I would take them:

1. **Fold the twin into the existing subject handler** (my recommendation, needs INTEGRATION-2's
   consent because the files belong to the namespace agents). In `🧪️tests/<case>/🟦️.ts`, the
   `subject` computes the twin's projection alongside the LaTeX one, throws on disagreement and
   returns the LaTeX projection unchanged. Parity against d3 is untouched, the LaTeX subject stays
   the subject of record, and the twin becomes a genuine second opinion on every existing vector:
   ```ts
   import { scaleLinear } from "../../🔨️modules/📊️viz-kernel/📐scale/🟦️.ts";
   subject: async (ctx) => {
     const latex = probeProjection(roundProbeNumbers(await compileVizProbe(…), 9));
     const twin  = { "scale/linear": rows(ctx).map(/* the same vectors through the twin */) };
     assertTwinAgrees(latex, twin);       // throws, naming every disagreeing key
     return { projection: latex };
   }
   ```
   I did **not** apply this to anyone's case — say the word and I will, case by case.
2. **New cases owned by the kernel module**, `📊️viz-kernel/🧪️tests/<case>/`. `ownerShipsImplementation`
   walks up from the owner looking for `📦️packages/🟦️typescript` and finds the kernel's own, and
   `loadOracleRegistry` merges every owner's contribution, so `@oracle-d3-scale` resolves from
   print's registry with no second registry to survey. Cost: the feature text is duplicated.
3. **New cases under print's `🧪️tests/`** whose subject is the twin — `render-scene` is exactly this
   shape and is green, so the route is proven. Cost: a case slug per module.
