# Base64 Receipt Review

The actual Rust source reader reports semio-framework-io-base64 at 19,834 bytes, 3 files and 353 active lines against the unchanged 32,768-byte, 4-file and 1,024-line limits; the reader cross-checks file stat sizes. This is not a compiler verdict. Base64 Cargo still has no runtime dependencies. The companion test binary installs first-party RequestedAllocator and uses dev-only base64 0.22.1 as an independent oracle.

The eleven neutral accounting vectors match the current transition logic: valid Zm9v produces work 12, read 8, copy 3 and capacity 3; empty produces work 4; a failing quartet produces work 5/read 4; early nonfinal padding produces work 2/read 1; cancellation at decode start produces work 7/capacity 0; cancellation after output produces work 11/read 8/copy 3/capacity 3. A quartet is loaded as a four-byte array before validation, so four read units are recorded even if sextet validation then rejects. A repeated frozen refusal resets the turn receipt to zero and retains original input and partial output. The existing Rust law checks source pointer, actual allocation observer and oracle status.

The per-turn unchecked additions are bounded by the issued usize maximum: each transition runs only after subtracting its conservative demand from remaining work, actual work does not exceed that demand, read is bounded by work, copied bytes by decoded input, and retained output is allocated at most once. No concrete strict error regression was identified in source inspection. Integration must still quote capacity before invoking the cursor, translate actual work/effects into the original caller and fund ownership transfer and close. No production edits or native builds were performed.
