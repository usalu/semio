# Browser Pixel Source Preparation

Current-source inspection found whole-payload `atob` and `Uint8Array.from` in the eyedropper/wand source path, followed by an unnecessary second RGBA copy of browser readback. Selection and flood work already yield, but this preceding source phase did not.

Authored a source-preparation schema and neutral valid/invalid/cancellation vectors before implementation. The new host helper drives the existing shared strict base64 cursor in bounded grants, yields between incomplete grants, exposes monotonic validation/decode progress and refuses output after cancellation, including the final callback. Existing native/TypeScript codec implementations retain the actual byte algorithm. The SDK explicitly reexports its existing cursor. Browser readback now keeps its owned buffer through a typed view rather than copying all pixels. Wand source and flood phases occupy the first half of progress, followed by existing selection combination.

Tests compare bytes with the independent base64-js library, require an event-loop yield, cancel in every phase and verify exact view offset/extent and buffer identity. They are authored but **not yet executed**. Parent repo MCP test call timed out after 300 seconds; subsequent process inspection did not find a surviving Raster test. Sandbox-local session/capacity/lease interfaces let a repo run advance, but its source-admission subprocess failed before tests with an auxiliary descriptor 3 EPERM write. This is an infrastructure failure, not a feature-test result. No test gate was disabled, and no permission request was retried after the user's correction.

Current source adds twenty unit source cases and four mounted cases. Mounted tests send actual independently encoded PNG bytes through the mocked browser decode boundary and require correct eyedropper color/contiguous-color selection; cancellation is held at an incomplete shared cursor grant and must prevent browser decode/publication. Static review caught and repaired a jsdom harness issue: its Blob lacks arrayBuffer, so the independent oracle uses browser FileReader. Bun's syntax scanner accepted the five changed TS/TSX modules, and both new JSON files parsed with paths under 256 characters. These are narrow source inspections; they do not establish type checking or executed test behavior.

Blank mask initialization now also uses bounded 32,768-byte fill grants with progress/cancellation; authored neutral vectors compare its exact bytes with Sharp-created RGBA images. Transparent blank pixels reuse zero initialization without a redundant fill. Both source paths check cancellation before allocation and after progress callbacks.

Remaining source preparation work includes the atomic browser decode/readback APIs and whole assets JSON parsing. Large-image end-user responsiveness and mounted integration remain unverified. Do not count this checkpoint as a complete performance or editor acceptance pass.

The initial 64 MiB encoded-file cap was removed after an independent import-policy audit. A 16 MP RGBA limit does not bound the compressed file's byte count, and the actual Raster import path has no such fixed file limit. The wrapper now enforces a caller-supplied file-byte admission when present and otherwise quotes the exact file extent already admitted by the artifact owner. Four neutral bound cases cover exact, undersized and invalid caller budgets. It does not infer a narrower source policy from pixel memory.

An additional static review found an older progress-reset seam outside this helper: selection combination reports the second half of progress, then selection-span publication restarts at zero. Repair its complete operation weighting and mounted neutral expectations before claiming monotonic whole-selection progress. No claim about that unchanged seam is implied by the source-byte helper's own monotonic progress contract.
