# Immutable Image Payload Contract

The fixed one-item store envelope permits 1 MiB of new preparation storage. A truthful bounded producer does not make a later 64 MiB image clone fit that envelope. Global widening or returning a fictitious small footprint would conceal the problem.

The chosen mutation payload remains a real decoded image on the wire. A composed-child handle alone is insufficient: `AddLayerAsset` must retain image bytes in durable event content. Internally, the new `RasterImagePayload` owns an immutable `Arc<SemioImageSnapshot>`. Its retained clone shares that original root instead of copying its pixel vectors. Fresh image allocation stays paid by the producer or genuine original native receiver before handoff; subsequent preparation declares the root/alias work it actually performs.

The authored API is `owned_birth_demands`, `alias_demands`, `from_owned(image, grant)`, `from_shared(arc, grant)`, `image`, and funded `owner(grant)`. Constructors return the original image/Arc on refusal and preserve actual work/ownership receipts. Fresh ownership uses the existing first-party `admit_shared_allocation`; shared construction and owner access cost an alias, with no new pixel allocation. `AddLayerAsset.asset` now uses this type. Mask row assembly quotes and pays the Arc birth separately from its key; rejected allocation preserves the private raw image.

Payload retirement uses `SharedControlledRetirement::lease`, which returns an alias while another child/history reader exists and takes responsibility for the deep image only when the final Arc closes. Using the default owning Arc retirement would wait for all readers and could stall a command's close path. Payload clone cursors bind the real original source and close unpublished aliases through this same contract.

Ordinary Arc output is required because existing composed children expose actual `Arc<SemioImageSnapshot>` owners. A sealed shared payload cannot export that Arc without violating its private storage contract. Native receiving now reuses the existing shared receiver state machine with a domain-neutral root construction policy. `NativeDecodeControl.receive_arc` shares the original recipient, grant/accept handling, cumulative allocation ledger and error preservation with sealed construction. The native mapped receiver performs the final allocation-free payload wrap. No synthetic decoder, forged grant, raw sealed-Arc escape, or synchronous cold constructor was added.

Neutral/native tests were authored before the production type. Genuine caller tests cover refused input preservation, pixel-pointer preservation, live-child alias closure, final-image retirement, transparent native/canonical wire representation and constant clone capacity. Additional source-authored tests cover preallocation quote denial, later success on the same input, enclosing receipt refusal after an Arc was born, and cancellation at each native receiving turn. Exact injected allocation/accept callback failures remain unproven because the genuine test fixture has no corresponding hook. None of these Rust tests has executed under the current source.

The native controls agent has source-mounted bounded preparation for six pixel routes and Add/Remove asset routes, with cached inverse handoff. The cold inverse helpers now retain the actual prior child Arc and refuse missing materialization instead of silently losing history. The cold Add diff still copies an image into the reference diff; the live bounded asset owner must bypass it. Cold text/binary mutation image decoding now refuses without original native receiving rather than constructing an unissued Arc. The corresponding owned protocol decode route and fixture migration remain required integration work. Bake/merge/import producers are also being migrated to actual funded roots; their old plain-image constructors are not final-source compile proof.

Physical capacity is distinct from the one-item metadata footprint. The current native initiating source was traced to 256 MiB capacity with 4 MiB reserved for retirement, while mounted component preparation currently narrows capacity to 16 MiB. The actual mounted installer and domain-specific original loan remain under audit. At 16 MP, clipped flood fill can retain 240 MiB of new pixel/scratch storage before preserved profiles/metadata. No universal bound on additional image frames/profiles/metadata is established. Maximum-image progress must be proved or explicitly refused using actual original caller authority; the immutable payload alone does not settle it.
