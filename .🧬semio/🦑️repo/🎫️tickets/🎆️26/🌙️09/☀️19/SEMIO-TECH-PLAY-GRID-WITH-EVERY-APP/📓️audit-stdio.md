# 📓️ Audit — stdio-in-play feasibility (read-only, topic `audit-stdio`, 2026-09-21)

## TL;DR

The ticket's "known facts" (242 MB, unlinkable, over the 1 M-function ceiling) describe the **library-only
`full-app-catalog` fleet (88 apps, ~600 000 functions)**, which the crate's own code and comments say must
**never** ship as a component. They do **not** describe the component `semio-tech play` would actually need.
The **shipped/default 9-app component** (`plugin-root` → `component-app-assembly`, exactly the nine
`s.stdio.*#editor` apps the committed descriptor declares) already **builds, links and jco-transpiles
successfully** in both profiles, measured directly in this audit:

| build | profile | core-module defined functions | limit | headroom |
|---|---|---|---|---|
| shared repo cache, default features, `--target wasm32-wasip2` | `wasm-dev` (unoptimized) | **387 787** (+43 imports) | 1 000 000 | 61 % free |
| hub trusted-catalog `stdio-target`, default features | `wasm-release` (opt-level s, thin LTO, cgu=1, strip) | **50 514** (+43 imports) | 1 000 000 | 95 % free |

Both counts were obtained by parsing the WebAssembly function/code sections directly (script below), the
same method the plugin's own `catalog-root` verifier (`assertComponentizableCore` in
`✏️s/🔌️plugins/🗄️stdio/📦️packages/🦀️rust/📜️script.ts:244`) uses. `jco transpile` was also run in this
audit against the 234 MiB `wasm-dev` core module extracted from the raw component and it **succeeded**
(447 KiB JS + full `.d.ts`, no error) — the "jco/wasm-tools cannot transpile" premise did not reproduce.

**Recommendation: Option A — wire the already-working default component into play (no plugin/Rust
engineering needed).** This is not hypothetical: a peer session was actively doing exactly this while this
audit ran (see "Live state observed" below). Estimated remaining effort is play-side wiring only, on the
order of the note/writer/dag lane work already in the ticket, not a new build-system capability.

## (1) What actually fails, and what doesn't

- `Cargo.toml` (`✏️s/🔌️plugins/🗄️stdio/📦️packages/🦀️rust/Cargo.toml`) defines two disjoint fleets behind
  feature flags:
  - `component-app-assembly` (pulled in by `default = ["plugin-root"]`) turns on
    `component-app-assembly` for exactly **7 crates**: csv, tsv, txt, json, xml, md, html — the source
    comment: *"What the SHIPPED wasm component assembles... Inside its own component every registered app
    is live code, so the full fleet blows `wasm-component-ld`'s 1 000 000-function ceiling — see
    `full-app-catalog`."* `full-artifact-catalog` (all 36 artifact crates, codec-only, no app UI) is always
    pulled in underneath it, so codec code for every format ships even though only 7 kinds get an editor.
  - `full-app-catalog` turns `component-app-assembly` on for **all 36** crates (88 apps). Its own doc
    comment in `✏️s/🔌️plugins/🗄️stdio/🔌️plugin/🦀️.rs:297-301`: *"this fleet costs ≈600 000 wasm functions
    and `wasm-component-ld` refuses it over wasmparser's 1 000 000-function ceiling. It is therefore the
    LIBRARY fleet (`cargo check ... --features full-app-catalog`)"* — i.e. it is explicitly documented as
    **never meant to be linked into a component**, and `full-app-catalog` is nowhere requested by any other
    crate's `Cargo.toml` or by any `--features` CLI arg in the repo outside the stdio crate's own tests
    (verified: `grep -rln full-app-catalog --include=Cargo.toml .` → only the stdio crate itself). Play's
    own `playpanecoverage` test (`🏢️semio-tech/🎡️play/🧪️tests/🧪️playpanecoverage/🟦️.ts:8-12,168`) asserts
    `default`/`plugin-root` must never reach `full-app-catalog` — this is a tested law, not a hope.
  - The plugin descriptor generated by the default-feature build (`✏️s/🔌️plugins/🗄️stdio/🔣️.json`,
    currently staged/uncommitted, see below) has exactly **9** `#editor` apps, matching the code path.
- The "242 MB" figure in the ticket brief matches the **`wasm-dev`** (debug/unoptimized) build cached at
  `.🧬semio/🦑️repo/⚡️cache/cargo/target/wasm32-wasip2/wasm-dev/semio_s_plugin_stdio.wasm` (245 907 428
  bytes, rebuilt 2026-09-21 10:46 by the framework-os-dev fast-iterate path — see (3)). That file **is**
  already a valid Component-Model binary (magic `00 61 73 6d 0d 00 01 00`, not a plain core module), i.e.
  it already linked. Its extracted core module has 387 787 defined functions — under the ceiling, not over
  it.
- `FRESH_COMPONENT_MAX_BYTES = 256 * 1024 * 1024` in
  `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🖨️describe/🏗️component-build/🟦️.ts:14` (dev-profile size
  admission bound, comment: *"GIS plugin's dev component is ~193 MiB; procedural ~80 MiB"*) already
  anticipated stdio's dev build being large; 245.9 MB fits under 256 MiB. So neither the byte-size bound nor
  the function-count ceiling is actually violated by the default component today.
- Conclusion: there is **no current build/link/transpile failure** for the component play needs. The
  "unlinkable" state the ticket inherited is stale — it was true of an earlier all-in-one shape of this
  crate (or is a conflation with `full-app-catalog`), and has since been fixed by the 7-crate
  `component-app-assembly` feature split. What's missing is purely play-side wiring (2)-(3) below.

Verification method used (read-only, no cargo build triggered by me): a small Python script parsing the
WASM function (id 3) and code (id 10) section header varints, matching the plugin's own
`inspectWasmCoreStructure`; and running the repo's vendored `node_modules/.bin/jco transpile` against the
cached `wasm-dev` artifact into a scratch directory (`/tmp/audit-stdio-scratch`, not under the repo).

## (3) How the component is assembled, and what `activate-stdio-react-dev` needs

- **Descriptor build pipeline** — `CatalogRootScript` in
  `✏️s/🔌️plugins/🗄️stdio/📦️packages/🦀️rust/📜️script.ts:909-991` (`bun ./📜️script.ts catalog-root
  --build-root <dir>`): `cargo rustc -p semio-s-plugin-stdio --profile wasm-release --lib --crate-type
  cdylib --target wasm32-wasip2` (line 943, **no `--features`**, i.e. default = the 9-app fleet) → `jco
  transpile` the raw component → `jco wit` + a hand-rolled WIT actor-world check → build
  `semio-framework-plugin-describe` and emit the descriptor pack/JSON → `assertComponentizableCore` (the
  1 M ceiling check) → independent SHA-256/Pack oracles cross-check → `bun nx run
  @semio-tech/plugin-registry:generate` → publish `🛂️.descriptor.semio` + `🔣️.json` atomically.
  This exact pipeline already ran successfully today: `✏️s/🔌️plugins/🗄️stdio/🛂️.descriptor.semio` (446 903
  bytes) and `✏️s/🔌️plugins/🗄️stdio/🔣️.json` (42 717 lines, 9 `#editor` apps) are both present on disk,
  staged (`git status` shows `A ` — added to the index, not yet in a commit; the ticket's "committed on
  2026-09-20" is imprecise, it is pending the repo's periodic auto-commit). The hub's trusted catalog
  (`.🧬semio/🌐hub/{rb1-prod,jc1-boot}/trusted-catalog/build-26d1e241.../stdio-target/`) has an
  **independently reproduced, byte-identical** 48 056 453-byte release component plus a completed
  `.semio-fresh-component-work/extract/` (jco-transpiled `.js`/`.d.ts`/core wasm) from the same pipeline,
  confirming this is not a one-off fluke.
- **Fast dev-iteration path** (what `activate-<variant>-react-dev` actually uses) —
  `buildPluginComponent` in
  `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🖨️describe/🏗️component-build/🟦️.ts:56-62`: `cargo rustc
  -p <pkg> --lib --crate-type cdylib --target wasm32-wasip2 --profile wasm-dev` (no `--features` either),
  then `extractPluginCore` runs the same `jco transpile`. This is the UNOPTIMIZED path (comment at line 11:
  *"deliberately NOT the runtime bound on a shipped component"*) and is what produced the 245.9 MB /
  387 787-function `wasm-dev` artifact this audit measured — successfully.
- **Plugin registry already knows about stdio.** `PLUGIN_BUILD_TARGETS` in the gitignored, regenerable file
  `🧰️framework/…/🔌️plugin/📇️registry/🤖️generated/🧩️plugins/🟦️.ts` already has a committed-quality `stdio`
  row (package id `semio:stdio`, `wasmOut: "semio_s_plugin_stdio.wasm"`, 36 `on-artifact-kind` activation
  events) — this part of the plugin/component machinery needs no new engineering.
- **What play is actually missing** — three purely play-side pieces, none of them a build/link concern:
  1. `PLAYGROUND_BUILD_TARGETS` (from Cargo.toml `[[package.metadata.semio.playground]]` rows, regenerated
     via `bun nx run @semio-tech/plugin-registry:generate`) needs one row per reachable editor app. As of
     this audit, `Cargo.toml` has exactly **one** stdio playground row (`variant = "stdio"`, the markdown
     app, ports react 6110/wgpu 6210).
  2. Play's own pane catalog `🏢️semio-tech/🎡️play/🔨️modules/🧩️runtime/🔣️.json` has **60 panes and zero for
     stdio**. A pane entry looks like (matching the `note` pane): `{ "variant": "note", "label": "Note",
     "tagline": "...", "description": "...", "icon": "note", "example": "demo" }` — stdio needs at least one
     such entry pointing at `variant: "stdio"` (the markdown row already declared).
  3. `🏢️semio-tech/🎡️play/📋️project.json`'s `activate-dev` target's `dependsOn` (27 entries, all
     `@semio-tech/framework-os-dev:activate-<variant>-react-dev`) and `prepare-dev`/`prepare-release`'s
     `dependsOn` (27 entries each, `prepare-<variant>-react-dev`/`-react-release`) are **hand-maintained
     lists**, not generated — confirmed no codegen writes `project.json`. None currently mentions `stdio`.
     `prepare-e2e` only depends on `activate-dev`, so it needs no separate edit.
  - `playActivationLanes()` (`🏢️semio-tech/🎡️play/🔨️modules/🧩️runtime/♻️activation/🟦️.ts:24-39`) computes
    the greedy lane cover **dynamically** from whatever panes exist in the catalog — once a stdio pane
    exists and its playground row resolves, the lane math itself needs no code change, only the
    `project.json` `dependsOn` entry that actually invokes the nx target.
  - `playPaneClosureRoot` (same file, line 45-47) scopes a pane's closure to its own `app`, so an
    app-scoped stdio pane pulls in only the `stdio` component, never a "s" host aggregation of every
    plugin — there is no risk of accidentally re-triggering the `full-app-catalog` fleet through play.

## (4) `wasm-release` profile and who runs it

`Cargo.toml:594-621` `[profile.wasm-release]`: `inherits = "release"`, `opt-level = "s"`, `lto = "thin"`,
`codegen-units = 1`, `strip = "symbols"`, `incremental = false`, `trim-paths = "object"`; `panic` is not
overridden (comment: wasm32-wasip2's target spec already defaults to abort). Comment block above it
explains each choice against alternatives (why `"s"` not `"z"`, `"thin"` not `"fat"` LTO, etc.) and states
plainly: *"os-dev's `📜️script.ts` passes `--profile wasm-release` when building plugin crates"* for
publication, while dev-loop iteration always uses `wasm-dev` (unoptimized, per (3)). This audit did not find
a ticket note under `.🧬semio/🦑️repo/🎫️tickets/🎆️26/🌙️09/☀️1{7,8}` that specifically analyzes stdio's
release-profile link — the authoritative source turned out to be the crate's own `📜️script.ts` and
`🔌️plugin/🦀️.rs` comments plus the hub's already-successful trusted-catalog build, not a ticket-note
conclusion. The release build is **not** speculative: the byte-identical 48 056 453-byte artifact exists in
two independent hub build directories (`rb1-prod` and `jc1-boot`, both timestamped today) with a completed
jco transpile beside it, and this audit's own section-count parse puts it at 50 514 defined functions
(+43 imports), 95% headroom under the ceiling — comfortably falls under.
