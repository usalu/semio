# 📇️ registry-projection — `live home` host-predicate drift (2026-09-21)

Topic: the `@semio-tech/plugin-registry` unit test `🧪️tests/📖️generated-projection` failed on
`live home: expected true to be false`.

## Root cause

Two twins of the same predicate had drifted apart:

| implementation | file | app-pinned clause |
| --- | --- | --- |
| `resolvePluginHostConfig` (kernel, runtime authority) | `🧰️framework/🔨️modules/🎠️kernel/🟦️.ts:3214` | ✅ `if (variant?.app !== undefined) return undefined;` |
| `runtimeComponentClosure` (`appScoped` root) | `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🕸️dependencies/🧩️runtime/🟨️.mjs:36` | ✅ `if (component.host && !appScoped)` |
| `projectedHostPluginFilter` (projected JSON twin) | `…/📇️registry/📖️catalog-view/🟦️.ts:28` | ✅ added in commit `48b9d63cf6` (2026-09-20 23:20) |
| `isHostPlaygroundFilter` (generated-module twin) | `…/📇️registry/🟦️.ts:56` | ❌ **missing** |

On 2026-09-20 the `🪐️space` crate gained two app-pinned playground rows — `home`
(`s.space.home@1/*#editor`) and `space` (`s.space.space@1/*#editor`) — beside the unpinned host row
`s`. The rule the other three implementations state is: **host mode is a property of the SESSION, not
of the crate** — a playground row that names an `app` boots that one artifact app standalone, even on
the host crate, so it must NOT be treated as the unfiltered studio hub. `isHostPlaygroundFilter` was
never updated, so it still answered `true` for `home` and `space`, while the projection twin answered
`false`; the cross-check at `🧪️tests/📖️generated-projection/🟦️.ts:77` caught exactly that.

The projection side (and the kernel, and `runtimeComponentClosure`) states the intent; the generated-
module twin was the stale one. This is confirmed by the consumers: play's `playPaneClosureRoot`
(`🏢️semio-tech/🎡️play/🔨️modules/🧩️runtime/🟦️.ts:45`) already passes `appScoped: row.app !== undefined`
for exactly these rows, the `workspace` group in `🔨️modules/🧩️runtime/🔣️.json` panes `home` and `space`
as ordinary app panes, and `hostVariant` is `s` — the only row that may mean "everything".

Across the live generated rows only `home` and `space` change classification (verified by simulating
both predicates over `🤖️generated/🎠️playgrounds.json` + `🔌️plugins.json`): after the fix the host
filters are exactly `undefined`, `""` and `s`.

## Out-of-scope reds found in the same package (NOT fixed, not mine)

`🧪️tests/🚀️launch/🟦️.ts` fails 2/10, identically before and after my change. Root cause, verified by
running `playgroundLaunchNamePrefix` over every live playground row — three prefix COLLISIONS:

```
COLLISION "🪐️space"          s, space
COLLISION "🗄️stdio🔣️.json"   stdio-json, stdio-json-i
COLLISION "🗄️stdio📰️xml"     stdio-xml, stdio-xml-valid
```

`generateLaunchJson` synthesizes a launcher only when `out.includes(JSON.stringify(reactName))` is
false (`🚀️launch/🟦️.ts:219-226`), so the second variant of each colliding pair silently gets none —
hence `space:react has 0 launcher(s) on port 6109` / `space:wgpu … 6209` — and the stdio pairs produce
the four duplicate names the identity law reports. The fix belongs in
`🚀️launch/🏷️name-prefix/🟦️.ts` (`playgroundLaunchNamePrefix` must distinguish an app-pinned row from
the crate's unpinned row, and a subset-pinned dialect such as `i-json` / `valid` from its base app).
Both collisions were introduced by the 2026-09-20 `home`/`space` rows and by play-stdio's nine
`stdio-*` panes. Note `check-generated` is green, so the committed `.vscode/launch.json` carries the
same gaps.

# 🚀️ Follow-up — launch-name prefix collisions (2026-09-21, same topic)

The two `🧪️tests/🚀️launch` reds reported above, fixed at the root.

## Root cause

`playgroundLaunchNamePrefix` must be INJECTIVE over playground variants, because `generateLaunchJson`
names every launcher `🛠️dev<prefix><renderer>` and synthesizes one only when the skeleton does not
already carry that name (`🚀️launch/🟦️.ts:238-240`): two variants sharing a prefix silently cost the
second one BOTH of its launchers. It was not injective, for three independent reasons:

1. **Eponymous-artifact collapse shadowed the plugin-level row.** `combinePluginAndArtifact` collapsed
   `<pluginFolder><artifactFolder>` to `<pluginFolder>` whenever the two slugs matched — so the
   app-pinned row `space` (`s.space.space@1/*#editor` → `🪐️space`) collapsed onto the bare `🪐️space`
   that the plugin-level studio-host row `s` (no `app`) already owns. Result: `space:react has 0
   launcher(s) on port 6109`, `space:wgpu … 6209`.
2. **The dialect SUBSET was not in the name.** `stdio-json` (`…json@rfc8259/*`) and `stdio-json-i`
   (`…json@rfc8259/i-json`), `stdio-xml` (`…xml@1.0/*`) and `stdio-xml-valid` (`…xml@1.0/valid`)
   differ only by subset, which the prefix never carried — the four duplicate names the identity law
   reported.
3. **Loose artifact-folder matching (latent, same function).** `findArtifactFolder` accepted an
   `endsWith` match in `readdir` order, so `s.stdio.json` resolved to the config leaf
   `🗄️stdio/🗿️artifacts/🔣️.json` (slug `.json`, which ends with `json`) instead of the real artifact
   folder `🧾️json` — the wrong taxonomy emoji, and the reason both json variants landed on the same
   folder in the first place.

## Fix

`…/📇️registry/🚀️launch/🏷️name-prefix/🟦️.ts` — the prefix is now
`<plugin folder><artifact folder><subset folder>`, every segment a real taxonomy folder name:

- `findArtifactFolder`: **exact slug first**, `endsWith` only as a fallback.
- new `appDialect(app)` splits `s.<plugin>.<artifact>@<standard>/<subset>#<role>` into all three
  coordinates (it replaces `appArtifactSlug`, which read only the artifact).
- new `findSubsetFolder(...)` appends the row's
  `🗿️artifacts/<artifact>/🏅️standards/🔖️<standard>/🪆️subsets/<subset>` folder when the pinned subset is
  not the wildcard `*` — the taxonomy already carries `🛜️i-json` and `✅️valid`, so no name was invented.
- `combinePluginAndArtifact` takes `collapseEponymous`: the `<plugin><artifact>` → `<plugin>` collapse
  may fire only when the plugin publishes a SINGLE playground row, so it can never shadow a sibling.
  (`🗒️note` and friends keep their bare names; only `🪐️space`, with three rows, stops collapsing.)

`…/📇️registry/🚀️launch/🟦️.ts` — new `assertDistinctLaunchNamePrefixes`, called at the top of
`generateLaunchJson`: a duplicate prefix now **throws** instead of silently dropping a playground's
launchers. That is the second half of the root cause and the guard against the next such row.

Exactly five rows change prefix; every other one of the 76 is byte-identical (diffed before/after over
the whole registry):

| variant | before | after |
| --- | --- | --- |
| `space` | `🪐️space` (collided with `s`) | `🪐️space🪐️space` |
| `stdio-json` | `🗄️stdio🔣️.json` | `🗄️stdio🧾️json` |
| `stdio-json-i` | `🗄️stdio🔣️.json` | `🗄️stdio🧾️json🛜️i-json` |
| `stdio-xml` | `🗄️stdio📰️xml` | `🗄️stdio📰️xml` (unchanged) |
| `stdio-xml-valid` | `🗄️stdio📰️xml` | `🗄️stdio📰️xml✅️valid` |

No `stdio-*` variant, port or Cargo row was touched. The studio host `s` keeps `🛠️dev🪐️space…`, so the
eight launchers devs use daily (incl. `👤️1`/`👤️2`, `📦️served`, `🧊️wgpu🖥️native`) are unchanged — the
alternative (giving the bare name to the `space` app row and renaming the host's) was rejected for
that reason. The seed's curated `"s".namePrefix` is still `🪐️space`, so `.vscode/🧩️launch.seed.jsonc`
needed no edit.
