## Root causes, grouped

### 1. Part-21 conformant header writer vs non-conformant in-memory state — `ifc` ×3
`step::engine::part21::write_header_record` (landed 2026-09-05 after a `ruststep` differential run) pads every
mandatory `HEADER` record out to ISO 10303-21 §8.2's full attribute arity and spells an empty `LIST[1:?] OF
STRING` `('')`, never `()`. `step`'s own `Part21Header::default()` was moved to that conformant minimum;
IFC4's OWN mirror type was not, so `parse(print(x)) != x` for every header stated short or with `()`:
- `IfcHeader` still `#[derive(Default)]` (all-empty) → `v4::…::io::…::codec_round_trip` (`decode_pack` handed
  back the padded header). Fixed by a hand-written `Default` = `ifc_header_from_part21(&Part21Header::default())`.
- `demo_ifc_snapshot()`/`demo_ifc2x3_snapshot()` stated `file_description[0]` as an EMPTY aggregate → the printer
  emitted `('')` and the shipped fixture said `()`. Both demos now state the conformant spelling.
- the 2x3 `exact_native_between_noop_inverse_absorb_and_supported_rewrite` replaced the whole seven-attribute
  `FILE_NAME` record with a one-value list, so the re-import assertion compared a padded record against a short
  one. It now writes attribute 1 (`FILE_NAME`'s name slot, §8.2.3) — what the test actually proved.

### 2. Stale shipped fixtures — `ifc` ×1, `docx` ×2, `dwg` ×1
Regenerated ONLY through each crate's own printer, never by hand:
- `docx`: the three demo assets were mutually inconsistent (`📜️example.docx` 09-19 21:51, the DSL/pack twins
  09-20 01:14) and predate the committed `demo_docx_snapshot()` line that sorts OPC parts path-ascending — the
  package normal form a decode hands back. `word/numbering.xml` and `word/styles.xml` were swapped, which is why
  `demo_subset_integrated_roundtrip`'s `IoFidelityClass::Exact` byte compare failed. Refreshed with the crate's own
  committed `#[ignore] zzz_write_native_docx_fixture`.
- `dwg`: `🎒️.pack.semio` was still the 51-byte pre-codec stub `decode_pack` rejected with `Truncated(22)` — the
  exact state the crate's own `zzz_write_demo_fixtures` doc comment describes. Refreshed the same way (889 bytes now).
- `ifc`: no regenerator existed, so I added the same committed `#[ignore] zzz_write_demo_fixtures` shape `dwg`/`docx`
  already ship, for both standards, and used it.

### 3. One fixture claimed by two standards — `ifc` ×1
`🔖️2x3/…/📚️examples/🎬️demo/🖼️assets/` is the ARTIFACT-level `demo` example (`ifc::examples::demo`), whose text is
IFC4's `stdio.ifc.dsl` Part-21 body — the registered `s.stdio.ifc` codec's. The 2x3 `fixture_honesty_law` (added
09-08) `include_str!`d that same file, but `Ifc2x3Snapshot::print_dsl` emits a completely different DSL
(`stdio.ifc.2x3`, the tagged value encoding), so its `parse_dsl` died on `unknown token "ISO-10303-21;"`. 2x3 now has
its own fixtures under its own `🧫️fixtures/🎬️demo/`, generated by its own printer.

### 4. Grammar facet files that could not match their own printer — `ifc` ×2
- the 2x3 SNAPSHOT grammar spelled `HEX` and `IDENT`-shaped tagged values. `HEX` is not a terminal this dialect
  has: `📖️grammar/🦀️.rs`'s `terminal_matches` resolves an all-caps symbol against token KINDS and there is no
  `Hex` kind, so the production never matched anything. The built-in is the lowercase `hex` MACRO. Rewritten to the
  exact tag scheme its `🧬️mutations`/`🔺️diff` siblings already spell (they share the `enc_part21_*` primitives).
- the 2x3 MUTATIONS grammar declared a FIFTH field on `ifc2x3-snapshot` that `enc_ifc2x3_snapshot_into` never
  writes (it emits `[schema,header,instances,edmPreamble]`, and `dec_ifc2x3_snapshot` demands exactly 4). Dropped.

### 5. A raw mutation that aborted the process — `ifc` ×1
`Ifc2x3Mutation::SetSnapshot`'s `agg_diff` called `validate_ifc2x3_snapshot(...).expect(…)`. Every sibling SUBSET
enum (`cobie`/`sav`/`cv20`) `reject`s instead, and `agg_inverse` hands back `SetSnapshot(base)` for EVERY mutation —
so an inverse taken against a still-default snapshot panicked by construction. The base enum is the RAW model-edit
path; schema conformance is owned by `encode_ifc2x3` and by each subset's validator reached through `build()`, which
is exactly what `wrong_schema_via_raw_mutate_still_fails_build` asserts. The `expect` is gone; nothing else changed.

### 6. Absorb dropped one of two inserts at the same position — `ifc` ×1
`absorb_entities` kept `d1`'s add indices (positions in the INTERMEDIATE list) and appended `d2`'s adds (positions in
the FINAL list) unchanged, so two inserts at index 1 both claimed index 1 and `apply`'s own `invalid-add-target`
guard rejected the merged diff. `d1`'s surviving adds are now transported through `d2`'s own insertion positions with
the file's existing `transport_forward`/`unrank_excluding`, the same way the index-keyed sibling
`absorb_indexed_collection` already did.

### 7. A JSON-null `extras` change vanished from the wire — `gltf` ×1
`GltfNodeDiff.extras`/`extensions` and their 14 siblings are `Option<Option<GltfJson>>`: "unchanged" / "cleared" /
"set to a JSON value". `GltfJson` has its own `Null` variant (glTF 2.0 `extras` may legitimately hold JSON `null`),
so `Some(Some(GltfJson::Null))` and `Some(None)` both printed bare `null`, and `Option`'s own `FromValue` read either
back as the outer `None`. Measured with a temporary probe (since removed): diff wire
`{"nodes":{"modified":[{"index":0,"diff":{"extras":null}}]}}` decoded+re-encoded to `…"diff":{}` — the change and
its inverse both silently disappeared. All 16 such slots now carry `#[value(with = "json_presence")]`, a presence
tag using the same `state`/`value` vocabulary `GltfDataPresence` (the change-extras mutation payload) already
spells in this artifact. Snapshot-side `extras` (`present_json`) was already correct and is untouched.
