## `fixture-digest-mismatch` — root causes and decisions

### dxf@r12/✳️any — 58 breaches, ONE root cause

All 58 entries were `before.dxf` (shared base copy of `drafting-plate.dxf`, identical bytes across
every mutation recipe) or `after.dxf` files whose **on-disk sha256 differed from the manifest's
recorded sha256 for every single file in the subset**, including the base `drafting-plate.dxf`
fixture itself, which the generator's own header comment describes as "untouched in content by this
retrofit — verified byte-identical to the previously committed fixture."

Decision: **(b) regenerate.** Ran the declared generator
(`🏭️generator/📜️script.ts generate --out <scratch>`, which builds and shells out to the real `dxf`
0.6 Rust engine) into a ticket-scratch directory and compared byte-for-byte against both the
committed fixtures and the manifest's recorded digests for all 38 recipes (76 files):

- Every regenerated file's sha256 **matched the manifest's recorded sha256** (0 mismatches).
- Every regenerated file **differed from the on-disk fixture** it was meant to replace.

This is airtight: the generator is deterministic (per its own documented fixed-timestamp handling)
and reproduces exactly what the manifest has always said, so the on-disk fixtures had drifted —
corrupted or hand-touched at some point after the manifest was last correct — never the reverse.
Copied the regenerated bytes over all 38 recipes' fixture files (76 `.dxf` files under
`🖊️dxf/…/✳️any/🧫️fixtures/`); manifest required **no edits**. Verified post-copy: 0/76 mismatches
against the manifest.

### note@1/✳️any — 10 breaches, same cause, same fix

Identical pattern on a different subset: `creates-an-ink-block`, `deletes-the-ink-and-text-blocks`,
`duplicates-the-ink-block`, `duplicates-the-ink-and-text-blocks`, `redraws-the-sketch-polyline`
(before + after `.dxf`, 5×2 = 10 files) — on-disk bytes did not match the manifest; the shared
`before.dxf` bytes matched across all five recipes (same base document), consistent with drift, not
five independent corruptions.

Decision: **(b) regenerate.** Ran `🏭️generator/📜️script.ts generate` (this generator only honors
`SEMIO_FIXTURE_OUT`, not a `--out` flag — it wrote directly into the committed `🧫️fixtures/`
directory). `git status` confirmed exactly the 10 flagged files changed and nothing else (all other
recipes byte-identical to what was already committed), and all 10 now hash to the manifest's
recorded sha256. Manifest required no edits.

Side effect noted and reverted: this generator has a pre-existing bug — its `manifests`-index-merge
path writes a `🔣️.json` snapshot into the **fixtures** directory (`../🧫️fixtures/🔣️.json`) rather than
the oracle directory. That file was already tracked in git (committed independently by another
concurrent session minutes before this run, commit `e5465a2c`, unrelated to this ticket). My
`generate` run overwrote its content as a byproduct; I restored it to the last-committed content via
`git show HEAD:<path> > <path>` (not a modifying git command) since deleting or rewriting it is out
of this shard's scope and not part of either target breach. Left as-is for its owner.

### mathematical@1/✳️any — 2 breaches, opposite cause

`carrier-change-coefficient` before/after JSON. Regenerating with the declared generator
(`🏭️generator/📜️script.ts generate --out <scratch>`) produced bytes **identical to what was already
on disk** (both 1280 bytes, matching sha256) — and **different** from the manifest's recorded sha256
(which described 1320-byte files).

Decision: **(a) manifest stale.** The fixture is current, correct, and reproducible; the manifest was
never updated after some earlier content change to the carrier (1320 → 1280 bytes — likely a shape
change made after the manifest was first written; the git history for both files was folded into the
same mass rename commit so it can't be dated more precisely, but reproducibility settles it either
way). Hand-edited exactly the two `sha256`/`bytes` fields for `carrier-change-coefficient` in
`🧪️oracle/🔣️.json` to the actual on-disk values.

I first tried the generator's own `manifests` command to regenerate this entry mechanically, but it
rewrites **all 10** carrier entries plus round-trips the entire JSON file through `JSON.stringify`,
which silently reformatted an unrelated `1e-09` → `1e-9` numeric literal in a pre-existing
`comparisonTolerances` block elsewhere in the same file (a JS number-serialization artifact, not a
real change). That diff was discarded (via `git show HEAD:<path>` restore — again read-only, not
`checkout`) in favor of a minimal two-field hand edit that touches nothing else.

## `fixture-generated-by-non-qualifying-oracle` — root cause and decisions

`QUALIFYING_ORACLE_KINDS` (`🧰️framework/…/🟦️.ts:2746`) = `third-party-library`, `third-party-cli`,
`standards-reference-tool`. `SUPPLEMENTAL_ORACLE_KINDS` (never discharges) = `metamorphic`, `inverse`,
`round-trip`, `property`, `cross-semio-implementation`.

**One root cause across all six artifacts, no exceptions:** every subset here went through an earlier
retrofit (ticket `26/08/27/SUBSET-SCOPED-EXTERNAL-ORACLE-MUTATION-TESTING`) that split what had
originally been registered as a single qualifying oracle into two oracle-registry entries — a
`cross-semio-implementation` entry (the "what SHOULD a mutation produce" computer, correctly
downgraded because both the fixture and the subject code descend from one reading of the spec — this
is the `reimplementation-registered-as-third-party` gate's own reclassification, visible verbatim in
each entry's `rationale`) plus a **new, separate, correctly-kinded `-reader` entry**
(`third-party-library`, e.g. `dxf-crate-r12-mutate-reader`, `jszip-docx-ecma-376-mutate-reader`) that
genuinely discharges the requirement — it only reads/parses the format independently and never
predicts an answer. In every one of the 65 breaches, the fixture manifest's `generator.oracle` field
had simply never been repointed from the old (now-downgraded) id to the new reader id sitting right
next to it in the same `oracles[]` array, registered under the matching capability, with a working
comparison pipeline (`comparisonProfile` → named `comparisonPipelines[]` entry → real `probes[]`
commands pointing at scripts that exist on disk — checked for each artifact below).

Fix applied uniformly: retarget `generator.oracle` in the affected `fixtureManifests[]` entries from
the non-qualifying id to the sibling qualifying reader id already registered for the same capability.
No new oracle entries, no kind reclassification, no fixture regeneration — the bytes were never in
question, only which existing registry entry gets credited as having produced them.

(25/25, 15/15), and for avi (22/22), confirming every non-qualifying reference in the file was one of
the flagged breaches and nothing else was touched. dxf/gif/obj were single hand-edits, each verified
against the specific flagged fixture id.

I did not invent any of these reader oracle ids or their qualifying `kind` — every one was already
present in the registry, already correctly kinded, already wired to a real comparison pipeline and
real probe scripts. The `.🧬semio/…/26/08/27/SUBSET-SCOPED-EXTERNAL-ORACLE-MUTATION-TESTING/` ticket's
own leftover patch script (`📜️docx-patch-oracle.cjs`) independently corroborates this history for
docx: it shows the reader was originally registered directly as `third-party-library`, then a later
pass (the `reimplementation-registered-as-third-party` gate) split it into the current
cross-semio/reader pair — the fixture manifests were simply never migrated to point at the new split.
