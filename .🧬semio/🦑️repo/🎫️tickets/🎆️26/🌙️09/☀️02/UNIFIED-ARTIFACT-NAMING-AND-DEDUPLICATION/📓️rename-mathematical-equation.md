### The `s.<plugin>.<artifact>`-doubling bug, found and fixed
The blanket pass has no way to tell "the plugin id spelled as `mathematical`, not as a path segment" from "the artifact id spelled as `mathematical`" — so it initially corrupted every `s.mathematical.mathematical` capability/dialect id into `s.equation.equation` (first segment wrongly renamed too), and the un-prefixed grammar-header form `mathematical.mathematical.snapshot`/`.diff`/`.mutations`/`.inference`/`.dsl`/`.cmd`/`.presence`/`.config` into `equation.equation.*`, plus the ANTLR grammar name `Mathematical_mathematical_snapshot` → `Equation_equation_snapshot`. Caught it by diffing against the "only the **second** `mathematical` in the doubled id is the artifact" rule (confirmed against the sibling `animate`→`presentation` rename's precedent report, which hit and fixed the exact same shape: `s.draw.draw`→`s.draw.drawing`, plugin-scoped `s.draw.standard.v1` left alone). Fixed with two corrective sweeps:
- `"s.equation."` → `"s.mathematical."` (revert the wrongly-renamed first segment) — 47 files.
- `"equation.equation"` → `"mathematical.equation"` and the `Equation_equation`/`equation_equation`/`EQUATION_EQUATION` compound forms → `Mathematical_equation`/`mathematical_equation`/`MATHEMATICAL_EQUATION` — 33 + 7 files.

Net result, verified by grep: `s.mathematical.mathematical` → `s.mathematical.equation` everywhere (dialect const, `#[artifact_schema(id = …)]`, capability-row table, playground `app` id, grammar/protocol headers, ANTLR/EBNF/ABNF grammar names), while genuinely plugin-scoped ids that never doubled (`s.mathematical.schema.artifact`, `s.mathematical.standard.v1`, `s.mathematical.localization.en/de`, `s.mathematical.grammar.*`, `s.mathematical.composer.*`, `s.mathematical.codec.*`, `s.mathematical.inference.artifact`) correctly kept their plugin-id first segment.

A hex-encoded fixture blob (the demo example's `🗣️.dsl.semio` DSL asset, and its byte-identical mirror inside the plugin's own `🔣️.json` manifest) carried the same identity strings as raw hex bytes (`mathematical-scene-<hash>`, `mathematical-text!…`, `mathematical-table!…`, `mathematical-value!…` — composed-child handle identities). Decoded, re-encoded with `equation-` prefixes (hash suffix and stdio-side schema refs left untouched), and verified no other file in the plugin carries the same hex.

### `EquationSnapshot` name collision — decision
Before this rename, `EquationSnapshot` already existed as a field type (`equation: EquationSnapshot` on both `MathematicalArtifact` and `MathematicalSnapshot`) — the persisted single-equation content: an `EquationNode` expression tree plus a `next_label` allocator, doc-headed "🔖️Equation" and living beside the already-correct `EquationNode`/`EquationNodeKind`/`EquationNodeLabel` family.

**Decision**: kept the artifact-level rename canonical (`MathematicalSnapshot` → `EquationSnapshot`, matching the `{ArtifactName}Snapshot`/`{ArtifactName}Artifact`/`{ArtifactName}Diff`/`{ArtifactName}Mutation` convention every other artifact follows and that the plugin-root/glue-file/manifest/cross-plugin references already assume) and renamed the pre-existing narrower type to **`EquationExprSnapshot`** — it is specifically the expression-tree + label-allocator content of one equation, so "Expr" disambiguates it from the whole-artifact snapshot without breaking the `Equation*` sibling family's naming pattern. All 18 use sites (struct def, `Default`/`impl` blocks, the `equation:` field on `EquationArtifact`/`EquationSnapshot`/`EquationDiff`/`EquationFixture`, the binary/text io codecs, and the `roots` inference) were updated consistently; re-grepped for `EquationSnapshot` vs `EquationExprSnapshot` afterward — no file uses both bare names in the same scope, and (checked separately) `MathematicalNode`→`EquationNode` also lands on an already-used name (the AST node type) but the two live in genuinely different modules with no shared `use`/glob-reexport, so it is not a Rust conflict — flagging it here only as a residual naming ambiguity, not a bug.
