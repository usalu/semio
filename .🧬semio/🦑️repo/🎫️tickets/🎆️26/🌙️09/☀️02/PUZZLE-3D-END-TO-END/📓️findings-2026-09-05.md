## 2. The lane audit was mostly a false alarm — one real finding

An audit reported 8 publication-lane mismatches that would fault at runtime. I read the gate
(`🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️.rs:22897-22904`) rather than taking it:

```rust
if (!emit.artifact_mutations.is_empty() && !publication_lanes.contains(&…::Artifact))
    || (!emit.config_mutations.is_empty() && !publication_lanes.contains(&…::Config))
    || (!emit.draft_mutations.is_empty() && …Draft)
    || (!ephemeral.presence.is_empty() && …Presence)
    || (!ephemeral.transient.is_empty() && …Transient)
    || (!emit.child_emits.is_empty() && …Child)
{ return Err(plugin_sdk_fault("typed-operation emitted a store lane absent from its exact factory publication contract")); }
```

Two things follow that the audit got wrong:

- **`effects` is not lane-gated at all.** It is not in the list. So `engagementAbort` and
  `engagementSubmit` emitting effects under a `["Config"]` declaration is fine.
- **The gate is one-directional** — emitted-but-not-declared only. Over-declaring a lane is not a
  runtime failure, so `addBrushObject`, `addObjectKind`, `rotateSelection`, `scaleSelection`,
  `translateSelection` declaring `["Artifact","Config"]` while emitting only artifact mutations is fine.

**The one real mismatch: `relocateTargetVolume`** — declared `["Config"]`, but
`Puzzle3dRelocateVolumeWork` emits `artifact_mutations`. That trips the gate. It must move to the
`Artifact` lane.

## 5. `setFixtureJson` cannot fit the transport — a third, different trap

Every id in `bounded_first_step_tool_proofs!` shares the contract
`ToolExecutionContract::resumable(8_192, 512, 1, 262_144, 7_500, 1, 1)`. The first parameter is
`max_raw_wire_bytes`, enforced at dispatch (`🧰️framework/🔨️modules/🎯️action-bus/🦀️.rs:643`):

```rust
if declared_bytes > contract.max_raw_wire_bytes {
    return Err(ToolDispatchError::RawWireLimit { controller_id, tool_id, actual: declared_bytes, maximum: contract.max_raw_wire_bytes });
}
```

`setFixtureJson` takes an entire fixture as its argument. Measured on disk:

| example | bytes |
|---|---|
| `🌲️concrete-forest/…/🗣️.dsl.semio` | 5,805 |
| `🏗️nakagin-capsule-tower/…/🗣️.dsl.semio` | **128,755** |

The JSON form is larger again. Against an 8,192-byte cap that is a guaranteed `RawWireLimit`
rejection for any realistic fixture.

The cap is not a per-action choice: `PUZZLE_COMMAND_RAW_BYTES = 8_192`
(`🎮️commands/🧵️retained/🦀️.rs:10`) is the size of a fixed `raw: [u8; PUZZLE_COMMAND_RAW_BYTES]` array
inside `RetainedPuzzleCommandJob`, shared by puzzle 2d, 3d and 5d. Raising it inflates every retained
job in all three dimensions for one action's benefit. `setFixtureJson` is therefore held back with an
honest blocker; closing it needs a chunked/resumable wire path.

Contrast `setActiveExample`, which is fine: its payload is just `{"exampleId":"nakagin"}` and the
fixture is resolved internally. That is the shape `setFixtureJson` lacks.

## Three distinct failure classes, worth keeping separate

The migration surfaced three traps that all look like "flip the label" from outside but fail differently:

| class | example | how it fails |
|---|---|---|
| missing reducer dispatch | `setFillCountStep` | **silently** — reducer's default arm is `_ => {}` |
| lane not declared | `relocateTargetVolume` | faults at publication |
| payload exceeds transport | `setFixtureJson` | rejected at dispatch with `RawWireLimit` |

Only the first is silent, and the silent one is the one a compile and a green test suite would both miss.

## 6. The "systemic selection wire-size risk" is narrower than reported

The wave-E report flags `deleteSelection`, `translateSelection`, `rotateSelection`, `scaleSelection`,
`duplicateSelection`, `setSelectionFlag` and `patchInspector` as all carrying `ids: Vec<String>`
against the 8,192-byte wire cap, i.e. ~230 ids and they break. Checked against source; it is narrower
than that, though not zero.

**Selection does not normally travel on the wire.** `RetainedPuzzleCommandJob` carries
`interaction_state: Option<Arc<protocol::InteractionState>>` as its own field, separate from the
fixed `raw: [u8; 8_192]` buffer. Commands read the selection from there:

- `delete_selection` (`✏️editor/🎮️commands/🗑️delete-selection/🦀️.rs:6`) takes **no args at all** — it
  reads `ctx.selected_object_ids()`, `selected_vortex_ids()`, `selected_attraction_ids()`,
  `selected_target_volume_ids()`, `selected_reference_ids()`. Nothing rides the wire. Safe at any
  selection size.
- `translate_selection` (`🚀️translate-selection/🦀️.rs:15`) calls
  `mesh_selection_ids(args, &ctx.selected_object_ids())`, and `mesh_selection_ids`
  (`✏️editor/🦀️.rs:435-440`) reads `args["ids"]` only as an **override**, falling back to the
  interaction selection when absent or empty.

So the exposure is exactly: a caller that explicitly populates `args["ids"]` with a large list. That is
the mesh/sub-object path, not the ordinary "select things and hit delete" path. The right check is a
runtime one — drive a large selection through the gumball and through mesh-level selection and see
whether `RawWireLimit` appears — not a static bound on `Vec<String>` length.

Recording this because the report's framing would have someone re-plumb seven actions that do not need
it, while the one case that does need attention (an explicit `ids` override) is not a size bound on
selection at all.

## 7. Four migrated actions exceed the work cap on Nakagin — but NOT at boot

`RetainedPuzzleCommandJob`'s Preflight phase faults with "puzzle command exceeds fixed semantic work
capacity" when a `Work::extent()` returns `None`, and the bespoke `extent()` bodies self-reject above
`PUZZLE_COMMAND_WORK_ITEMS = 4_096` (`🎮️commands/🧵️retained/🦀️.rs:12`).

`Puzzle3dWorldRelocateWork::extent` (editor `🦀️.rs:4225-4230`):

```rust
let object_vortices = document.objects.len().checked_mul(PUZZLE3D_RELOCATE_VORTICES_PER_OBJECT)?;   // = 64
let items = document.objects.len().checked_mul(2)?.checked_add(object_vortices)?.checked_add(document.attractions.len())?;
(items <= PUZZLE_COMMAND_WORK_ITEMS).then_some(items)
```

i.e. `objects × 66 + attractions`, so it dies above **62 objects**.

Object instance counts, counted from the DSL sources (rows between the `objects [...] {` header and its
closing brace):

| example | object instances | `worldRelocate` extent | verdict |
|---|---|---|---|
| concrete-forest | **1** | 66 | fine |
| nakagin | **180** | **11,880** | **exceeds 4,096 — faults at preflight** |

An audit reported Nakagin as 121 objects; recounted directly, it is **180**, so the overshoot is worse
than reported (2.9× the cap, not 1.9×). Same class affects `createAttraction`, `acceptSuggestion` and
`patchInspector` per `📓️extent-budget-audit.md` — those numbers were NOT independently recounted here
and inherit the same undercount, so treat their magnitudes as lower bounds.

**Severity is bounded by which example boots.** `default_fixture()` returns
`CONCRETE_FOREST_EXAMPLE_FIXTURE`, so the app starts on the 1-object example where every extent is
fine. These four actions only die after switching to Nakagin — which the ticket does require to work.

**This is not a regression from the migration.** These `extent()` bodies predate it; they were simply
unreachable behind the classification gate. Before, the actions were dead with
`interactive-job.not-ui-safe`; now they are dead with "exceeds fixed semantic work capacity". The
migration did not break them, but it also does not deliver them.

**The fix is to tighten the bound, not to raise the cap.** `objects × 64` assumes every object carries
64 vortices; real objects carry a handful. Counting actual vortices gives a much smaller and still
sound bound. That is Work-body work.

## 8. `runtime live cleanup faulted for instance 1` is CLOSED — and lowpoly has the latent version of it

The Sep 2 investigation recorded every actor turn faulting with
`{"origin":"plugin","code":"plugin.internal","message":"runtime live cleanup faulted for instance 1"}`,
traced to `take_returned_snapshot_read_retirement` erroring when `snapshot_retirement_factory` is
`None`. **That fault is structurally impossible on puzzle3d's current boot path.** Chain, verified:

1. `Puzzle3dPlayApp::build_document_store_owners()` and `build_config_store_owners()` both return
   `Some(...)` — editor `🦀️.rs:6710-6716`.
2. `EditorApp<E>` forwards both verbatim to `E::…` — `🔌️plugin/🦀️.rs:27241-27246`.
3. Every editor app boots through one production factory, `editor_surface`'s `factory` fn
   (`🔌️plugin/🦀️.rs:27908-27912`) → `VcsArtifactApp::with_registry_on_bus`.
4. `with_registry_on_bus` (`🔌️plugin/🦀️.rs:19478-19495`) installs owners via
   `install_member_store_owners_exact` whenever the hook returns `Some`.
5. `install_member_store_owners_exact` (`🏪️store/🦀️.rs:14364-14372`) does
   `*self.snapshot_retirement_factory = Some(owners.snapshot_retirement);` — **the exact field the
   fault site at `🏪️store/🦀️.rs:14746-14750` reads.**

Step 5 checked personally against source, not inherited from the report. The regression test
`local_interaction_query_return_does_not_fault_the_next_maintenance_step` (editor `🦀️.rs:7735-7768`)
exercises this path and would catch a recurrence.

### The latent version, in the reference implementation

`💠️lowpoly` — the app cited repo-wide as the 100%-migrated reference — **overrides neither
`build_document_store_owners` nor `build_config_store_owners`**, so it falls to the trait's `None`
default and its stores never get a retirement factory installed at all. It does not fault today only
because it apparently never exercises a *returned* document-store snapshot-read lease. That is a
behavioural accident, not a structural guarantee: the first call site that returns such a lease turns
it into puzzle3d's Sep 2 bug.

`✒️writer` matches puzzle3d (overrides to `Some`). So the correct reading is the opposite of the
obvious one: puzzle3d is not missing something lowpoly has — **puzzle3d and writer do something
lowpoly does not**, and lowpoly is the outlier carrying the risk.

Worth a ticket of its own; recorded here so it is not lost.

## 9. Measurement discipline: "zero errors" needs a warnings check

A peer reported stdio compiling with **0 E0277** under their feature set, then retracted it on
inspection: their log showed `Checking semio-s-plugin-stdio` followed immediately by
`error: couldn't read …`, and **zero stdio warning lines across the whole compile**. `couldn't read`
aborts during module expansion, *before* type checking — so "no trait-bound errors" meant "no trait
bounds were ever evaluated".

**The discriminator: a crate that genuinely type-checked emits WARNINGS.** Zero errors AND zero
warnings from a crate means it never compiled, not that it is clean. This is the same falsely-clean
family that has produced most of this ticket's wrong answers, in a new disguise.

Consequence still open: it is not yet established whether stdio's 225-error serde/`ToValue` wall is
feature-gated away from puzzle, or whether lowpoly is simply the only crate getting *far enough* to
reach it — in which case everyone hits it one blocker later. Feature-unification and that reading make
identical predictions until some build type-checks stdio for real.

## 12. Machine limits are now the binding constraint, not the code

```
vm.swapusage : used 50065M / 51200M   (~1.1 GB free)
load average : 109 / 102 / 99
sccache      : 1 compile request, 0 executed; a client pinned 25 min at 0.0% CPU
```

Consequences worth recording:

- **`%CPU` is not a liveness signal on this box.** macOS puts processes launched from background tool
  calls under background task policy. A build measured at 1.3% CPU was substantially self-throttled,
  not starved. Re-applying `taskpolicy -B` across the process tree every 5s (new children start
  throttled again) took it 1.3% → 4.3%. A peer measured 4.3% → 7.7% on theirs. Real penalty, not the
  whole story — contention is the rest.
- **`Blocking waiting for file lock on build directory` is the sccache deadlock**, not a slow peer.
  Escape is a private `CARGO_TARGET_DIR` plus `RUSTC_WRAPPER=""` — but that is a COLD build, and with
  ~1 GB of swap free a cold build will thrash or be OOM-killed. On this repo an OOM'd dev build fails
  **silently**: a port that never binds, cause invisible unless stdout was captured.
- Therefore: at this level of memory pressure, "start another isolated build" is not a free action.
  A `dev puzzle3d` boot was deliberately killed rather than allowed to acquire the lock and start a
  cold wasm build, because it would likely have taken the warm `cargo check` down with it.

## 13. The boot is blocked by machine exhaustion, not by code

`bun dev:puzzle:3d` was launched with `SEMIO_PLUGIN_PROFILE=wasm-release`, stdout captured, and
`taskpolicy -B` re-applied across its process tree. It reached:

```
[framework/surface/rs] wasm-pack build --dev --target web …
[INFO]: 🌀  Compiling to Wasm...
    Blocking waiting for file lock on build directory
```

and stayed there for over an hour.

### Diagnosis

The lock is `/Users/ueli/Documents/semio/target/debug/.cargo-build-lock` (found via
`lsof -a -p <cargo> -d cwd` plus the crate's own open fds — NOT by guessing a target dir).

Profiling every holder — age, parent, CPU, and **rustc descendants** — split them three ways:

| class | count | disposition |
|---|---|---|
| orphans: `ppid=1`, 0.0% CPU, **no rustc descendant**, >1h old | 8 | **killed** (ignored SIGTERM, needed SIGKILL) |
| real work: `cargo test -p semio-s-plugin-process` (pid 5360), orphan but rustc child **7.5% CPU, state RN, 6h** | 1 | **spared** |
| the user's IDE: rust-analyzer under Cursor (pid 2189) | 2 | **spared** |

Checking for rustc *descendants* rather than direct children is what spared 5360; a cargo at 0% CPU
with a busy rustc grandchild is normal and must not be killed. A cruder sweep would have destroyed six
hours of someone's compile.

Peers were told the exact criteria before any kill, and semio-1b confirmed none were theirs and flagged
one detached pid to avoid (34252, isolated target dir — verified untouched).

### The actual constraint

```
vm.swapusage: total = 65536.00M  used = 64903.44M  free = 632.56M
free + inactive RAM: 5.5 GB
```

**Swap is 99% consumed.** That is why a single rustc has been at 7.5% CPU for six hours — it is
thrashing, not progressing. It also kills the obvious workaround: relaunching `dev 3d` with a private
`CARGO_TARGET_DIR` means a COLD wasm build, and semio-1b measured this exact profile at 8.6 GB RSS
before stalling with swap at 45/46 GB. There is not 8.6 GB to be had.

**And an OOM'd dev build on this repo fails silently** — the port simply never binds, with
`spawnSync cargo ETIMEDOUT` invisible unless stdout was captured. So starting one now would not merely
fail; it would fail in the shape hardest to diagnose.

Deliberate decision: **do not start a cold build under 632 MB of free swap.** Wait for pressure to drop.
This is an environmental limit, not a puzzle3d defect — the code is compiler-verified
(`cargo check -p semio-s-plugin-puzzle --lib` → 0 errors, 277 warnings).

### `SKIP_ENGINE_BUILD=1` — the correct safety rule

`buildEngineWasm` (dev `📜️script.ts:932-956`) builds three crates and the early return at `:940` skips
**all** of them together; it is not per-crate freshness-checked. Each writes to a DIFFERENT path:

```
surface    …/🗺️surface/📦️packages/🦀️rust/🕸️bindings/framework_surface_bg.wasm
editor     …/✍️editor/📦️packages/🦀️rust/pkg/framework_editor_bg.wasm        ← pkg, not 🕸️bindings
flow-core  …/🌊️flow/🫀️core/🕸️bindings/flow_core_bg.wasm                     ← one level ABOVE the rust pkg
```

I first declared editor and flow-core "never built" because I looked for a uniform `🕸️bindings` path
under each crate's `📦️packages/🦀️rust`. All three exist. **Rule: the flag is safe only when all three
artifacts exist at their own per-crate paths AND `find <crate> -name '*.rs' -newer <artifact>` returns
zero.** mtime age alone is not staleness — flow-core's wasm is a day old but no source is newer than it.

### `SEMIO_PLUGIN_ONLY=puzzle` — a speedup that silently breaks the boot

Added on the reasoning that puzzle was the only plugin whose source changed. True for compilation,
**wrong for booting**. The OS assembles a plugin catalog from every plugin's descriptor, and the flag
suppressed generation of the others:

```
plugin.descriptor-unavailable: /🔌️plugin-modules/🗄️stdio/🔣️.json (HTTP 404)
plugin-assembly.package-id: component package identity was not declared
Framework OS boot failed
```

On disk: **38 of 59** plugin dirs had a descriptor; `🗄️stdio/🔣️.json` was absent.

Removing the flag was also *cheaper* than feared — the dev script then computes the real dependency
scope itself and prints `program build scope: puzzle, stdio`, i.e. two crates, not 59. The manual
restriction was both unsafe and unnecessary.

**Generalisation:** a build-scope flag is safe for the artifact you are rebuilding and unsafe for
anything downstream that consumes its *side effects*. `SKIP_ENGINE_BUILD` was verifiable (artifacts on
disk, freshness checkable). `SEMIO_PLUGIN_ONLY` was not, because what it suppresses is a catalog entry
generated as a side effect of building.

### Diagnosing a dark canvas — three indistinguishable causes

An empty dark pane at `localhost:6013` can be any of:
1. plugin fleet still loading (network shows the module graph streaming — 2,200+ requests)
2. plugin missing/faulted (console shows `plugin.descriptor-unavailable` / `boot fault text`)
3. the silent-empty-fixture bug — `from_json_str(...).unwrap_or_else(|_| empty_fixture())` renders
   nothing and logs nothing

A screenshot cannot separate them. `read_console_messages` + `read_network_requests` + the server log
can. Never call a dark rectangle either way.

## 21. A private target dir inside the repo is NOT safe — put it outside

At 17:17 a repo-wide clean deleted **every** `target*` directory at the repo root — mine and every

### The failure signature is misleading

```

       No such file or directory
error: could not compile `semio-s-plugin-stdio` (lib) due to 1 previous error
```

It names a **dependency crate** and reads as a compile failure. Disk had **400 GB free**, so it was

orphaned lock holders, and now a full clean — and the first fix that addresses the class rather than
the instance.

## 23. CORRECTION to §21 and §22 — the eager `LazyLock::force` was NOT waste

§21 removed these from `initial_snapshot`, reasoning that nothing depends on them and the default
document (concrete-forest, 1 object) never uses Nakagin:

```rust

LazyLock::force(&PUZZLE3D_EXAMPLE_OPERATIONS);
```

**That was wrong, and it introduced the boot regression §22 then misattributed to machine contention.**

`initial_snapshot()` is called from `VcsArtifactApp::with_registry_on_bus`

actor's budgeted window is its first `poll()` (`🟦️.ts:388`, `turns === 0` → `first-step`).

So those two `force` calls are a deliberate **phase shift**: pay the 128 KB DSL parse during unbudgeted

one carrying my regression**. Contention was not the cause.

Restored verbatim.

### The reasoning error, stated plainly

I checked whether anything *depended* on the calls — every other reference is lazy or in tests — and
concluded they were dead cost. Wrong question. The right question is **which execution phase a call
runs in**. A `force` whose entire purpose is to move work out of a budgeted window is, by construction,
indistinguishable from a redundant call under a pure reachability check.

**Rule:** before deleting an apparently-redundant eager initialisation, establish which phase it runs
in and whether that phase is budgeted. `LazyLock::force` with no other reader is a warm-up signal, not
dead code.

§22's closing advice stands (never raise `INTERACTIVE_STEP_CEILING_US`), but its diagnosis — "not
fixable from puzzle3d's source, likely environmental" — is withdrawn. It was self-inflicted and is

## 26. Leading explanation: activation is budgeted, and this ticket made it ~10x heavier

`VcsArtifactApp::with_registry_on_bus` (`🔌️plugin/🦀️.rs:19894`) is the app **activation** path. Inside

The fault names the **guest lifecycle turn**, and its check lives in `⚛️reactor/🚪️lifetime/🦀️.rs:244`

which the naming and the `first-step` (`turns === 0`) detection both suggest — then **everything above

That reframes this ticket's central change. `bounded_first_step_tool_proofs!` now declares **62** tools

**If confirmed, the fix is NOT to raise the ceiling.** Activation doing O(migrated routes) validation

## 31. 🐛️ Second framework bug: `spawnDaemon`'s zero budget kills every daemon on the next tick

Four serve attempts died at `trunk serve failed for wgpu renderer` with **zero trunk output** — not even
its `🚀 Starting trunk` banner. Two hypotheses were falsified before the real one:

- *Port collision* — killed the stale 6013/6022 servers; still failed.
- *Leaked env* (`CARGO_TARGET_DIR`/`RUSTC_WRAPPER` are copied wholesale by `trunkEnv`) — relaunched with
  a clean environment; still failed. Running `trunk serve` by hand with the same args **works** and
  compiles normally, so trunk and its config were never at fault.
- *PATH* — checked in a detached `bash -c`: `/Users/ueli/.cargo/bin/trunk`, `trunk 0.21.14`. Fine.

### The actual cause

`📚️library/🏃️process/🟦️.ts:31`

```ts
/** 🖥️Default dev-server and daemon budget (ms): zero permits long-lived sessions and their builds. */
export const DAEMON_BUDGET_MS = 0;
```

`📚️library/📦️packages/🟦️typescript/🟦️.ts:2216` (`spawnDaemon`)

```ts
const timer = setTimeout(() => { killed = true; if (child.pid) killBudgetTree(child.pid); }, daemonBudgetMs());
```

`setTimeout(fn, 0)` does not mean *no timeout* — it fires on the next event-loop tick. So the documented
"zero permits long-lived sessions" contract is inverted in practice: **every `spawnDaemon`-fronted
process is killed immediately**, before it can emit a line. That is every dev server in the repo.

Proven both directions: with `SEMIO_DAEMON_BUDGET_MS=86400000` trunk starts and stays up
(`🚀 Starting trunk 0.21.14`, `📦 starting build`, process alive); with the default it dies silently.

### Fix applied

```ts
const budgetMs = daemonBudgetMs();
const timer = budgetMs > 0 ? setTimeout(() => { … }, budgetMs) : undefined;
```

plus `undefined`-guarded `clearTimeout` in `kill` and the `exit` handler. Restores the documented
semantics — zero means unbounded — without changing behaviour for any caller that sets a real budget.

Unrelated to §28's WIT staleness; both had to be fixed to reach a running app.
