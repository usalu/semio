## Correction to the previous session's central conclusion

The 2026-09-03 note concluded `fillBuildTick` "genuinely cannot be migrated by wiring" and needs a
`PuzzleCommandWork::step` signature change across 2d/3d/5d, because `fill_build_tick_cached`
"deliberately does not spawn".

**That is wrong.** Read today at
`🗿️artifacts/🧊️3d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/🎮️commands/🪣️fill-build-tick/🦀️.rs:35-58`,
`fill_build_tick_cached` does all of:

```rust
let effects = spawn.into_iter().map(|(job, input)| Effect::SpawnJob { job, kind: FILL_JOB_KIND.into(), input, placement: JobPlacement::Isolated }).collect();
... vec![Puzzle3dConfigMutation::Snapshot { config: next }]   // persists the advanced checkpoint
Some(Emit { config_mutations, effects, ui_scope: ..., ..Default::default() })
```

It spawns the isolated fill planning job AND persists the advanced checkpoint.

The reason this works without a live app: **there is no live app instance in this design.**
`with_puzzle3d_app_for` (`✏️editor/🦀️.rs:2168`) constructs a fresh `Puzzle3dPlayApp::default()` on
every call and restores session state from `config.fill_checkpoint`. `ArtifactApp` methods are
associated fns with no `&self` — the docstring at :2164 says so explicitly. So "the live precompute
session" that the previous analysis was trying to reach does not exist; the checkpoint in `Config`
IS the session.

`PuzzleCommandWork::step` already receives `config: &A::Config`. Therefore the Work arm can call
`with_puzzle3d_app_for(config, |app| fill_build_tick_cached(app, config))` and return that `Emit`
verbatim — the same thing `ArtifactEditor::handle` (:6776) already does. **No trait change. No 2d/5d
churn.**
