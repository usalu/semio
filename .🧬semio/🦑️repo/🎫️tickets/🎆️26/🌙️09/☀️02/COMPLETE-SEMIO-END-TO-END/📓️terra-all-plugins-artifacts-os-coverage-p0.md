# Terra: Plugin, Artifact, and OS Runtime Coverage

## Outcome

The generated registry describes the fleet, but it is not an activation or installation
receipt.  The largest **bounded, source-backed** native gain is the existing
`local-stdio-gis-open-v1` path: exactly two plugin packages (`stdio`, `gis`), 28
native codec receipts (26 + 2), and one GIS Map editor open target.  It has not
been proven by a completed native/process run in this audit, so its operational
coverage remains zero until that receipt exists.

This is deliberately not a claim that all 59 catalog components or all 92 artifact
roots work.  Browser and WGPU document-open/render activation each remain at zero
verified components.

No product source was edited for this audit.

## Host Reality, Not Just Declarations

The Hub correctly refuses a document-open route when no configured authority is
ready, and resolves a target only from `openable_catalog`
(`🌎️hub/📦️packages/🦀️rust/🚀️bin.rs:2185-2207`).  At startup, the authority is absent
unless both `OS_HUB_TRUSTED_CATALOG_BUNDLE` and
`OS_HUB_TRUSTED_CATALOG_PROFILE` are present
(`.../🚀️bin.rs:388-399`); readiness derives from a loaded catalog with a nonzero
open-target count (`.../🚀️bin.rs:6317-6356`).

The only linked provider set is deliberately small: its literal inventory is stdio
and GIS at `🌎️hub/🗿️artifact-authority/📇️native-openable-provider/🦀️.rs:9-33`, with
the 26-receipt stdio exact-closure check at lines 93-124 and two GIS receipts
constructed at lines 53-74.  It is an appropriate bounded native closure, not
evidence that the remaining 31 plugin packages are loadable.

The browser/WGPU bridge fetches a descriptor from a caller-supplied module URL and
registers an empty capability set (`.../🐚️plugin-bridge.ts:211-215`).  Its comments
also document that `render` is reconstructed as a `surface-visible` turn,
window engagements/measures are unimplemented, and only one window surface is
rendered (`.../🐚️plugin-bridge.ts:48-54`, `140-148`).  It is not currently a client
of the Hub verified catalog/open-plan authority.

The native WGPU loader scans an arbitrary modules directory for the first `.wasm`
in each plugin directory, skips missing components in space mode, and may construct
an empty descriptor manifest (`.../🌉️ProgramBridge/🎯️targets/🧊️wgpu/🦀️.rs:723-769`,
`772-797`).  This cannot establish the exact selected component/descriptor closure
needed for a trusted document open, and there are no first-party plugin WASMs in
the source tree to exercise it.

## Highest-Gain Single Runtime Implementation

Complete and execute the already implemented **server-owned stdio+GIS trusted
bootstrap**, then make the client consume its verified open plan rather than a
module URL/directory scan.  This is the largest honest incremental gain because it
is the sole native provider closure with exact, statically validated factories:

1. Build fresh wasm components for only `semio-s-plugin-stdio` and
   `semio-s-plugin-gis`; the materializer explicitly requests those packages
   (`🌎️hub/📦️packages/🦀️rust/📜️script.ts:4011-4047`).
2. Materialize the exact 26+2 codec closure, retain GIS Map and Terrain codecs, but
   select exactly one Map editor target (`.../📜️script.ts:4050-4075`).
3. Validate an isolated candidate Hub before publishing the canonical
   `local-stdio-gis-open-v1` pointer; the pointer is bounded and binds bundle hash,
   generation and profile (`.../📜️script.ts:4206-4226`).
4. Have native/browser clients receive the Hub authenticated open-plan receipt and
   load only the package/component/descriptor/target named by that receipt.  Do not
   route this through `loadPluginModule(pluginId, moduleUrl)` or WGPU directory
   scanning.

The source already exposes `trusted-stdio-gis-bundle-check` and
`trusted-stdio-gis-bootstrap` (`.../📜️script.ts:5998-6005`).  Its `--native` and
`--process` modes build an isolated Hub, materialize the bundle, validate it before
publication, retain current across a bad candidate, rotate it, and reject the old
plan (`.../📜️script.ts:4775-4801`).  That is implementation scaffolding, not a
completed result in this audit.

### Concrete native/process acceptance

The implementation is accepted only with a retained ticket-owned native/process
receipt showing all of the following:

1. A fresh stdio and GIS component build, exact raw/core/descriptor hashes, and
   provider inventory exactly `{semio:stdio: 26, semio:gis: 2}`.
2. An isolated Hub starts with both trusted-catalog environment values; readiness
   says artifact authority and open-plan are ready; the selected profile is exactly
   `local-stdio-gis-open-v1`, contains exactly the two packages, and has one GIS
   Map editor target.
3. An authenticated Author opens a persisted `s.gis.gismap`/`gis.map` document.
   The returned plan binds catalog generation, component hashes, descriptor hash,
   schema/pack hash, Map surface, and grant.  A Viewer cannot obtain the writable
   editor plan.
4. A missing profile, changed hash, wrong document kind, and the stale plan after
   rotation are denied before codec/client activation.  A rejected candidate leaves
   the old current pointer byte-identical.
5. One actual native client process renders the selected Map surface from that plan
   and emits one persisted, authenticated edit.  Browser and WGPU may be claimed
   separately only after each uses this receipt rather than dynamic URL/scan
   activation.

This would change the verified native frontier from 0 to **2/33 plugin packages,
28 native codecs, and 1 document-open target**.  It would not change the all-fleet
claim: the remaining 31 plugin packages, 26 extensions, and 91 artifact roots
still need their own fresh component plus host activation receipts.

### Follow-up: prepared loaded-catalog acceptance law

The newly added `prepared_gis_binding_fixture` and
`gis_map_binding_constructs_from_loaded_catalog_and_retains_verified_bytes` are
sound on read-only inspection (`🌎️hub/🗿️artifact-authority/🔏️trusted-catalog/🦀️.rs:1421-1508`).
They deliberately combine synthetic, hash-checked component bytes with the actual
GIS assembly descriptor and actual native GIS codec receipts.  The fixture says so
explicitly and never invokes a component; its test proves loader admission,
editor/viewer/foreign-contributor binding behavior, tampered-backing-file rejection,
and that the binding retains the loaded catalog bytes/digest.  It makes no synthetic
component-execution claim.

There is no apparent global-codec duplicate-registration flaw in the three-case
loop.  `TrustedCatalogLoader` holds the artifact assembly barrier across preflight
and publish (`.../🔏️trusted-catalog/🦀️.rs:521-527`).  The shared document-codec
registry accepts an exactly equal registration idempotently, but rejects a different
codec for the same schema before mutation
(`🧰️framework/🛍️products/💻️os/🔨️modules/🏪️store/🦀️.rs:9615-9644`, `9688-9696`).
All three fixture passes request the same real GIS factory receipts; a foreign
descriptor changes only the declared inference contributor and is rejected by the
frozen-binding constructor, not by registering a second codec.

Fixture path/type construction is internally consistent: `PathBuf`, `Ordering`,
and the ticket-owned `SEMIO_TEST_ARTIFACT_DIR` convention are already imported and
used by the surrounding fixture machinery; hashes and byte lengths are refreshed
before persistence.  The target comes from the frozen corpus and the loader requires
an isolated descriptor app whose target is literally `wasm`
(`.../🔏️trusted-catalog/🦀️.rs:561-580`); the special stdio+GIS profile independently
requires the same Map editor target at lines 856-884.  This is a static review, not
a compile result; the existing Hub build remains uncompiled as requested.
