# WAL Writer Signal Integration

## Decision

Use the qualified fixed WorkerPool hook as the idle wake for a bounded backend-owned writer table. The prior plan to submit a release DbIoTask from lost-owner cleanup is rejected: that path recursively enters maintenance while holding the lost-owner mutex, consumes task arena slots, and can starve its own retirement. The separate Terra packets retain the exact evidence.

## Next Coherent Slice

1. Add a fixed signal cell per backend slot × writer slot (64 × 32), owning only the exact active full key, request state, a never-reset terminal epoch, and one bounded waiter waker. A permit captures the next terminal epoch before exposure. Reject epoch overflow before acquisition. Removal of a terminal table entry increments that cell's epoch before the writer slot can be reused; old explicit closers therefore keep their completion proof after later writers or backend generations reuse the cell.
2. Add one fixed controller row per backend slot containing the exact backend control, its already-owned pool handle and its installed maintenance-hook ticket. Permit Drop first marks only the exact signal cell, releases that mutex, then requests the exact controller's hook. It never enters the backend/task/lost-owner registries, allocates a job, or performs I/O. Full task/lost-owner arenas cannot lose this release intent.
3. Bind the actual backend control before publishing registration. Install the hook before exposing any permit; on registration failure retain/retire the exact executor/credit and remove any installed hook through its retained second-close opportunity. Every backend's close state retains its hook ticket until table terminality and exact remove=true. Hook callbacks run one bounded requested release step on Lane::Io and never borrow the table across a callback invocation.
4. A mutation's table admission consults the exact signal request as well as its local releasing flag, so a queued but unstarted mutation is fenced immediately after release is requested. Only the already-pinned operation may resume. The exact operation close clears its pin and requests another hook turn. A pinned guard returns Idle, not endlessly rearmed More; explicit later operation completion provides its wake. Unlock errors keep the table, signal and fault intact; no false completion.
5. Acquisition preflights document, duplicate, capacity, generation, epoch and backing before invoking a private guard constructor on Lane::Io. There must be no fallible branch between successful guard construction and placing it in its reserved table entry. Do not open a guard then drop it on table admission failure. The existing primitive acquire-with-owned-guard tests do not themselves provide this production acquisition sequence.
6. Add typed acquire/result ownership, stamp every actual mutable WAL task, and update all backend implementations, wrappers and fixtures together. Result cleanup moves/drops the permit only into its fixed release signal, then the normal acquisition result handback retires its short-lived task. A long-lived permit never keeps the acquisition task lease.
7. ArtifactWal acquires before inventory/recovery/create, retains the same permit through every submit and rotation, and exposes a retained asynchronous close that drains active bytes then waits for its captured terminal epoch. Its old synchronous buffer close is not an overall writer-release witness. Compaction, engines, CLI and tests must use the same authority surface; no raw compatibility mutation API remains.

## Acceptance Before Claiming Writer Exclusion

Exercise actual Memory/FS typed acquire plus each of six mutable operations with correct and hostile exact stamps, dropped acquire results, saturated task/lost-owner rings, a yielded/pinned append, release dispatcher failure, unlock fault, independent child-process contention, and backend recycling. Check exact cell epochs, operation/backend/page credit return, and ordinary asynchronous close. SQLite/remote guards require their own true cross-process implementation; a new read-only provider packet is active. Sequential WAL recovery and worker-hook receipts are prerequisites, not proof of this integrated boundary.
