## 0. Design sources and a real discrepancy between them

Two hub-side design documents exist and disagree on scope/shape, dated two days apart:

- `📓️terra-hub-inference-job-coordinator-audit.md` (2026-09-03) — the large `P5-I0..I5` packet: full `InferenceJobV1` CQRS/event-sourced coordinator, `InferenceJobRequestedV1`/`InferenceJobV1` schema, six MCP tools (`inference_request`, `inference_get`, `inference_cancel`, `inference_proposal`, `inference_approve`, `inference_apply`).
- `📓️terra-ai-map-proposal-approval-current-p0.md` (2026-09-05, newer) — the "smallest honest P0": four authenticated HTTP routes only (`POST /inference/gis-map/jobs`, `GET .../events?after=`, `POST .../cancel`, `POST .../approval`), and explicitly narrower state machine `accepted → claimed(epoch) → running(progress*) → offered(proposalHash) → approval-prepared → applied(reconciled)`.

The task brief's four routes match the **P0 packet**, not the coordinator audit's six-tool P5-I5 packet. I have treated the P0 packet as authoritative for route shape/count and the coordinator audit as authoritative for the deeper authority/freshness rules it states more precisely (subject/session/generation revalidation, stale-detection, CAS result handling) since the P0 packet incorporates rather than contradicts those rules. `fable-coordination.md` line 10 confirms `fable-ai-map-proposal` (Opus) owns exactly the P0 packet's "four authenticated routes" server side; this lane owns only the MCP-side client wiring.

This is static metadata discovery — no wasm activation, no live plugin process.

## 2. What `HubRemoteBinding` already holds vs. what a job request needs

File: `🧰️framework/🛍️products/💻️os/🔨️modules/🌉️mcp/🏠️workspace/🔗️remote/🦀️.rs` (922 lines) plus its `🧩️pair/🦀️.rs` submodule (1421 lines).

### Already present and reusable

- `HubRemoteBinding` (struct, line 105-118): `hub_origin`, `space_id`, `state: RwLock<HubRemoteBindingState>` (`Unbound|Refreshing|Ready(Arc<AuthorizedDescriptorSnapshot>)|Revoked`, line 43-48), `progress`, `diagnostic`, `generation: AtomicU64` (binding-refresh fence), `authority_generation: AtomicU64` (a *second*, coarser fence minted only on successful refresh, `next_authority_generation()` line 359-361), `observed_event_seq`, `authenticated_user_id`, and `pair_actor: Mutex<pair::CanonicalPairActor>` (the P4-C mount).
- `AuthorizedDescriptorSnapshot` (line 32-40): `authenticated_user_id`, `session_expires_at_ms`, `space: MemberSpaceViewV1`, `membership: MemberView`, `observed_event_seq`, `documents: HashMap<DocumentScope, AuthorizedDocumentView>` — `AuthorizedDocumentView` (line 25-30) carries `scope`, `descriptor_digest_v1`, and the raw `view: DocumentView` (`{descriptor, head_seq, commit_seq, epoch}`, `📇️directory/🧬️schema/🦀️.rs:1426-1431` — **note: no frontier/chain-hash here**, only sequence counters).
- `ready_snapshot(wall_now_ms)` (line 153-163) is the one call any tool handler needs to obtain a live, session-expiry-checked snapshot; it self-revokes on expiry.
- `HubRemoteBinding::mount_canonical_pair` (`🧩️pair/🦀️.rs:507-…`) is the P4-C actor call that **does** produce the missing pieces: it takes `scope`, `catalog_generation: Option<u64>`, an optional `expected: &CanonicalPairMountIdentity` (for cache-hit dedup), and returns a `CanonicalPairMount` (`🧩️pair/🦀️.rs:148-166`) whose `identity()` is `CanonicalPairMountIdentity { hub_origin, authority_generation, scope, descriptor_digest_v1, active_checkpoint_id, etag, catalog_generation }` (line 137-145) and whose `baseline()` is a real `ArtifactFrontier { document_id, head_edit_ordinal, head_edit_id, last_commit_seq, chain_hash }` (`📇️directory/🧬️schema/🦀️.rs:1356-1362`).
- The wire path it fetches is `GET {hub_origin}/spaces/{space_id}/documents/{document_id}/active-checkpoint/pair` (`🧩️pair/🦀️.rs:544` region — built at `mount_canonical_pair`'s `request.path = format!("/spaces/{}/documents/{}/active-checkpoint/pair", …)`). **This is a different, already-shipped path than the `GET /spaces/{space_id}/documents/{document_id}/artifact-bootstrap` name `📓️terra-mcp-authenticated-workspace-audit.md:52` originally proposed for P4-B — the implementation (per `📓️sol-mcp-canonical-pair-cache-mount-p4c.md`) settled on `active-checkpoint/pair` instead. Any new inference-job route naming should follow this same `/spaces/{space}/documents/{document}/...` convention already live on the hub, not invent a fifth shape.**
- `NativeHubBindingDriver` (line 472-643, native-only) is the background-thread actor pattern: it owns a dedicated OS thread, its own `TokioHostRuntime`, and drives `binding.refresh(...)` plus the directory WS stream in a loop, calling back into `HubRemoteBinding`'s atomic state. **This exact pattern (a dedicated actor thread + `runtime.block_on` bridging sync tool calls to async HTTP) is what an `inference_submit`/`cancel`/`approve` implementation must copy**, because (see §3) the MCP tool-call surface is fully synchronous.

### What is genuinely missing

1. **No request/job id minting anywhere in this binding.** `HubRemoteBinding`/`CanonicalPairActor` mint only `mount_id`/`receipt_id` counters (`🧩️pair/🦀️.rs:316-317`) for the pair cache — nothing corresponds to a hub `jobId` or a client `idempotencyKey`. A new counter or UUID source is needed on the MCP side purely to generate the P0 packet's client-supplied idempotency key (the hub still mints `jobId`).
2. **No durable job-status object on the MCP side at all.** There is no `InferenceJobV1`-shaped struct, no cursor-tracking type for `GET .../events?after=<cursor>`, and (per §1) the existing `InferenceJobPayload`/`job_get`/`job_cancel`/`JobRegistry` path is the wrong, non-durable, non-hub-aware substrate.
3. **No typed hub-HTTP client method for the four new routes.** `DirectoryClient<T>` (`📇️directory/🔌️client/🦀️.rs:750-851`) exposes only `spaces`, `space`, `events`, `event_page`, `me`, `command` (the last takes a closed `&DirectoryCommand` enum — **not** extensible to arbitrary JSON bodies) and a private `request_json` helper (line 770, not `pub`). Exactly as P4-B/P4-C did for the canonical-pair GET (`CanonicalPairTransport`/`NativeCanonicalPairTransport`, a hand-rolled parallel wire client because `request_json` couldn't stream binary), the four inference-job JSON routes need either (a) four new `pub async fn` methods added directly to `DirectoryClient<T>` in the **same file** (they are plain JSON POST/GET, so `request_json` *can* be reused here, unlike the binary pair fetch), or (b) a narrow sibling client next to `DirectoryClient`. Given P4-B/P4-C's own precedent language ("Add a typed, bounded binary/client method to `DirectoryClient` (or a narrowly named hub artifact client next to it) rather than exposing its private `request_json` internals" — `terra-mcp-authenticated-workspace-audit.md:54`), option (a) is the lower-risk, lower-diff choice here since these bodies are small typed JSON, not streamed binary.
4. **No `Author`-role/proposal-hash typed shape on the MCP side.** `InferenceApprovalRequestV1 { jobId, proposalHash }` (named in the P0 packet, `terra-ai-map-proposal-approval-current-p0.md:56`) does not exist as a Rust type anywhere under `🌉️mcp/**`. The MCP crate does not need to *check* the `Author` role itself (the hub re-derives and checks it server-side per `terra-ai-map-proposal-approval-current-p0.md:58`), but it does need the typed request/response DTO to serialize the call and to render a useful local error when the hub's `PERMISSION_DENIED` comes back.
5. **The scope/document target for "the job" is ad hoc.** Nothing today names "the current inference target document" as a first-class concept the way `HubRemoteBinding`'s single `space_id` is fixed at construction; `mount_canonical_pair` takes an explicit `&DocumentScope` per call, so `inference_submit` must take (or the workspace must already know) an explicit `documentId` argument — there is no implicit "current document" in a headless MCP workspace bound to a hub space with potentially many documents.
6. **Base frontier/pack digest are *not* actually missing** — they are already obtainable via `mount_canonical_pair`'s `CanonicalPairMount::baseline()`/`identity()`, contrary to a naive read of the task prompt. What's missing is the *glue*: nothing today calls `mount_canonical_pair` and then forwards its `identity`/`baseline` fields into a job-submission request body. Per the coordinator audit (`terra-hub-inference-job-coordinator-audit.md:71`), the hub re-derives its own binding from server objects at admission anyway — so the client-side contribution is likely just `DocumentScope` + `requestedInferenceSchema` + budget + idempotency key, with the mount identity used only for a **local** staleness check/UI display, not sent as trusted input. This must be confirmed against the (currently absent) `fable-ai-map-proposal` report before assuming the request body shape.

## 3. Policy/authority seams for `inference_submit`/`inference_cancel`/`inference_approve`

File: `🧰️framework/🛍️products/💻️os/🔨️modules/🌉️mcp/🛡️policy/🦀️.rs` (405 lines).

- **The existing `PolicyEngine`/`AgentPrincipal`/`ApprovalGate` is a local, CLI-configured scope+approval gate and is orthogonal to hub authority.** `AgentPrincipal::scopes` (line 67-72) comes from `--scopes` flags expanded through `MCP_SCOPE_TABLE` (line 26-42) into `kernel::CapabilityId`s; `PolicyEngine::authorize_scopes` (line 197-204) and `gate_approval`/`resolve_approval` (line 221-258) operate purely on locally-held `HandleTable` state and a locally-parsed `AutoApprovePolicy` (`--auto-approve never|readonly|all`, line 114-139). **None of this reaches the hub.** This matches `terra-mcp-authenticated-workspace-audit.md:15`'s finding verbatim: "CLI policy is a local admission/presentation policy, not hub authorization... must never authorize remote data." The three new tools need a **new MCP scope** (e.g. `inference.execute` expanding to a new `jobs.infer`/similar `kernel::CapabilityId`, following the existing `artifact.write → documents.write, jobs.spawn` pattern at line 29) purely as a local admission gate — it is *not* a substitute for hub authority and must not be treated as one.
- **The real gate is server-side and this MCP crate cannot implement it — only call it and honestly surface its outcome.** Per `terra-ai-map-proposal-approval-current-p0.md:58`: hub re-runs `check_live_inference_author` (`🌎️hub/💡️inference/🛂️authorization/🦀️.rs:7`, checks exact session/user/auth-generation/scope **and** current `Author` role) at accept/claim/every checkpoint/offer/read/cancel/approval. "An `Admin` is not implicitly allowed... only `Author`." MCP's job here is: (a) always send the current `HubRemoteBinding`'s live authenticated bearer/session (already handled transparently by `NativeDirectoryTransport`/`LocalHubCredential`, never by MCP composing its own auth header), (b) map the hub's `PERMISSION_DENIED`/expired-session responses onto `GatewayErrorCode::PermissionDenied`/`PluginUnavailable` (never fabricate a local "you are not Author" check — MCP has no membership/role table of its own beyond the `MemberView.role` already in `AuthorizedDescriptorSnapshot.membership`, which is a **snapshot at last refresh**, not authoritative at call time).
- **Per-connection session binding is presently a non-issue for correctness but a real future gap.** `DEFAULT_SESSION_ID = "sess_default"` (`🌉️mcp/🦀️.rs:297`) means every mutation-protocol tool call in one MCP process uses one fixed `SessionHandle` — but `HubRemoteBinding` is itself one-per-process (one hub subject per `semio-os-mcp --hub` invocation), so there is currently no *multi-subject* ambiguity to bind against. If/when the MCP process becomes multi-connection (P1b's own documented future work, `🦀️.rs:294-297` comment), job ownership (`subject.userId`/`originalSessionId` in the coordinator audit's schema, `terra-hub-inference-job-coordinator-audit.md:51`) must be attached at that point — out of scope for this packet but worth flagging as a load-bearing simplifying assumption.
- **Progress streaming semantics: polling the events cursor, not MCP progress notifications.** `🧭️protocol/🦀️.rs` implements `notifications/cancelled` as a recognized-but-discarded no-op (`METHOD_NOTIFICATIONS_CANCELLED` constant, line 300; dispatch arm `DispatchOutcome::NoResponse`, line 913) and has **no** `notifications/progress`/`progressToken` support at all (grepped the whole `🌉️mcp/` tree — zero hits for `progressToken`/`progress_token`/`notifications/progress`). `GatewayBackend`/`ResourceRegistry` (`🧭️protocol/🦀️.rs:621-627,773-781`) are fully **synchronous** trait methods returning `Result<T, GatewayError>` directly (no `async fn`, no `impl Future`) — confirmed by every existing handler signature (`fn inference_list_handler(...) -> CallToolResult`, no `async`). This means: (a) a real MCP `notifications/progress` push is not architecturally available without a protocol-layer change this packet does not scope; (b) an `inference_submit`/`inference_get`-with-jobId tool call **must** be a synchronous call that either blocks briefly (bounded, like `ui_focus`'s `SHELL_COMMAND_TIMEOUT_MS` pattern, `🖥️ui/🦀️.rs:26`) or returns immediately with a cursor, and the caller polls `GET /inference/gis-map/jobs/{id}/events?after=<cursor>` via repeated `inference_get`-style tool calls. **This is exactly what the P0 packet's own route shape assumes** (`GET .../events?after=<cursor>: owner-private bounded progress page`, `terra-ai-map-proposal-approval-current-p0.md:54`) — so no protocol gap actually blocks this design, it just means "progress" in MCP terms is a cursor the client re-polls, never a push.
- **Cancellation propagation** must be an explicit `inference_cancel` tool call to `POST /inference/gis-map/jobs/{id}/cancel`, never inference from the discarded `notifications/cancelled` no-op above (that path is currently wired to nothing and must not be repurposed silently — doing so would be a protocol-semantics change well outside this packet, since `notifications/cancelled` is meant for *JSON-RPC request* cancellation, not job cancellation).
- **Approval requires `Author` + proposal hash — MCP's only obligation is a correct, minimal, typed `InferenceApprovalRequestV1 { jobId, proposalHash }` body** (per §2.4) and honest propagation of the hub's stale/rejected verdicts (`ResultRejectedStale`/`Stale` in the coordinator audit's event vocabulary, `terra-hub-inference-job-coordinator-audit.md:66,73`) as retryable `PLUGIN_UNAVAILABLE`/`PRECONDITION_FAILED`, never a silent success.

## 4. Minimal typed DTO additions (no `serde_json::Value` at the boundary)

None of the four routes' request/response shapes exist as Rust types in the MCP crate today (grepped for `InferenceJob`, `GisMapProposal`, `proposalHash` under `🌉️mcp/` — zero hits outside this report). New types needed, following the crate's existing `#[derive(... ToValue, FromValue)] #[value(rename_all = "camelCase")]` convention used everywhere in `💡️inference/🦀️.rs` and `🛡️policy/🦀️.rs`:

- `GisMapInferenceJobSubmitRequest { document_id: String, requested_budget: InferenceBudget, idempotency_key: String }` (space id comes from the already-bound `HubRemoteBinding`, never re-sent) — mirrors `InferenceJobRequestedV1`'s closed shape (`terra-hub-inference-job-coordinator-audit.md:44-47`) minus every server-derived field.
- `GisMapInferenceJobHandle { job_id: String }` — the tool's `inference_submit` return value; this is the value a subsequent `HandleTable::mint(HandleKind::Job, …)` could wrap (reusing the *handle table primitive*, not the *JobRegistry* — these are separable; `HandleKind::Job` already exists at `🎫️handles/🦀️.rs:51,66`).
- `GisMapInferenceJobEventPage { cursor: String, events: Vec<GisMapInferenceJobEvent> }` and a closed `GisMapInferenceJobEvent` enum mirroring the P0 packet's state vocabulary (`Accepted|Claimed{epoch}|Running{progress}|Offered{proposalHash}|ApprovalPrepared|Applied{...}|Cancelled|Stale|Failed`) rather than a free-form JSON blob — matches the coordinator audit's own instruction ("never a private locator, bearer, or raw client actor" in any wire field, `terra-hub-inference-job-coordinator-audit.md:79`).
- `InferenceApprovalRequest { job_id: String, proposal_hash: String }` — the exact `InferenceApprovalRequestV1` shape named in the P0 packet (`terra-ai-map-proposal-approval-current-p0.md:56`).
- A closed `InferenceJobError`/mapping from hub HTTP status to `GatewayErrorCode` (401/403 → `PermissionDenied`, 404/410/frontier-mismatch → `PreconditionFailed` or `NotFound` depending on which, 409 duplicate-approval → `SideEffectRejected` or a no-op success depending on idempotent semantics, timeout/5xx → `PluginUnavailable` retryable) — following the exact pattern `binding_error_to_gateway` already establishes in `remote/🦀️.rs:655-665`.

These should live in a new `🌉️mcp/💡️inference/🧬️schema/🦀️.rs` (or a `job` submodule of `💡️inference/`) with a companion neutral JSON-Schema fixture, mirroring how `🏠️workspace/🔗️remote/🧬️schema/🔣️.json` and `🧩️pair/🧫️fixtures/🧬️.schema.json` already pair Rust types with schema-first fixtures in this same crate.

## 6. Dependency-ordered file list and collision risk

Ordered by hard dependency (each step assumes the previous is real, not stubbed):
