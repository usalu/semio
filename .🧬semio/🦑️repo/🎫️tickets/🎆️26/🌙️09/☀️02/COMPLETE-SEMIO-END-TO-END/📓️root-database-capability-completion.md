This narrows the stall to the database opening path after root creation and before catalog publication, without uniquely attributing the historical run to one race.

Root and the independent read-only audit found a concrete missing completion recheck in `DatabaseCapabilityOpenFuture::poll`: it tests an empty completion, releases that mutex, then separately installs a waker and returns Pending. A worker can publish and find no waker in that window. CatalogRead, CatalogBootstrap, and CreateCatalog already have check/register/recheck; the DB I/O public operation tests terminal state and installs its waker under one slot mutex.

A second concrete interleaving consumes Ready while the publisher is between storing completion and removing the previous waker. The public fast path calls `release_success` while the old waiter remains retained; retirement declines, then the publisher clears the waiter without another retirement call. That can strand exact admission/registry ownership. The bounded planned repair clears the public waiter before either Ready bookkeeping path, and rechecks completion after registration.
