# Current Scene Preparation Asset Boundary

The current DrawingAssetsOwner is the explicit reexport of OriginalIndexedRecord from framework value/paged/record. Its public size, entryAt and entries preserve insertion order; it has no sorted-key interface. entryAt and entries construct a two-field borrowed tuple on each read, and its cold constructor uses an internal raw key array. Those cold APIs must not be misreported as funded preparation or as an already sorted asset source.

The old DocumentSceneJob synchronously uses Object.keys(source).sort(), allocates raw frames/maps/sets and pixel buffers, then publishes a raw plan. It cannot feed the new consuming ScenePlanOwner without a genuine defining producer. The next coherent preparation work needs explicit staged key ordering under the same ledger or a deliberately changed canonical ordering contract with neutral expected output first; simply swapping entries would change the old sorted output. Existing sources/caller containers must remain borrowed and unchanged.

For produced RGBA assets, the Scene owner currently only borrows incoming pixels. A genuine builder must own actual RetainedWorkBytes plus priced reference cells privately and close them with the original bank; a raw pixel array followed by an ownership tag/copy wrapper is insufficient. Existing borrowed-pixel copy laws must remain unchanged. No Source edit or semantic run was performed for this diagnosis. The active Scene12+Text6 hold does not include the old preparation file, but defining owner changes remain frozen until Root releases that scope.
