# Native Default Work Blocker

NativeDefault currently exposes a Result-only native_default(grant), and array/tuple implementations invoke child defaults within the same physical item. Receive-derived optional/bare/container default fields invoke NativeDefault while retaining only a sizeof-based byte quote. Fresh exact derive inspection confirms path-default callbacks are NOT executed: those fields are deliberately required in native input (the canonical wire decoder alone applies the path callback). Neither path carries an authentic defining child CPU outcome, and a provider that allocates can create unquoted bodies or lose an earlier owned default if a later child fails. A wrapper CPU1 or a sum inferred from copied items is not acceptable.

A bounded full-Source census found the default trait, receive derive, paged receive wrappers, native map/set, Graph PropertyBag, viewport, Flow snapshot, DagExpandedPaths, neural Dictionary, stdio owner macro, procedural cameras, DrawingAttributes and Energy camera defs. Existing data-only empty/scalar/header defaults can be canonical allocation-free initializers invoked only during an actual funded selected publication turn; arrays of Copy defaults can remain fixed metadata only when the initializer itself is pure. Arbitrary allocating/custom defaults require an actual retained resumable default producer, preserving all partial owners and same-source CPU/capacity authority. Pure NativeReceive header initializers must never execute these semantic defaults.

No Default API body was changed yet. The canonical Native receiver migration does not claim this path is funded or SourceReady. Root contract review is required before removing the old convenience and hand-migrating every actual provider/caller. Native-owned --lib and reached domain gates remain mandatory, unexecuted.

Correction: the earlier broad callback description was inaccurate for the native derive. Path defaults are required native fields. The concrete blocker is the Result-only NativeDefault provider composition and lack of per-child bounded custody/work; no native arbitrary-path callback migration is needed.
