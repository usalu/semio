# Audit: surface/arena budgets that shape "+N" paged trees

Read-only investigation. All paths relative to repo root. Line numbers as of 2026-09-16 HEAD.

## 1. Builder-side child cap — `UI_BUILT_CHILDREN_MAX`

File: `🧰️framework/🔨️modules/🖱️ui/🧬️contract/🏗️builder/🦀️.rs`

- `UI_BUILT_CHILDREN_MAX: usize = 32` — line 51.
- `UI_BUILT_CHILD_RETIRE_SLOTS: usize = 384` — line 52 (see below).
- `BuiltChildren` (line 170-256): backing is `Option<Box<[Option<Box<BuiltNode>>]>>`, i.e. a **fixed 32-slot** boxed array, allocated lazily on first `try_push`. `try_push` (line 185-205) refuses (`Err(node)`, returns the exact node unboxed) once `self.len == UI_BUILT_CHILDREN_MAX` (line 186-188). There is no "grow past 32" path anywhere — the backing slice is sized to `UI_BUILT_CHILDREN_MAX` at allocation time (line 191-192) and never resized.
- **Why 32, concretely**: no numeric justification lives beside the constant itself; the number is inherited/propagated downstream as "the built-children contract" and other modules derive their own row budgets *from* it (see §2). It reads as a chosen round capacity for one wasm-side node's fan-out, not a measured wasm/memory ceiling.
- `credited_clone` (line 217-223): a second owner of the same children, never `Clone` — cloning would duplicate one `BuiltChildRetireKey` and let two owners publish the same retirement slot. Each child is credited independently (`child.credited_clone()?`), and each embedded `UiValue` inside that child pays its own arena alias credit (§2) — so an aliased/memoized page is refused, not overdrawn, if the argument arena is out of room.
- **Retirement reservation** (line 55-168): `BuiltChildRetireAuthority`, a process-global `LazyLock<Mutex<..>>` (line 87) with exactly `UI_BUILT_CHILD_RETIRE_SLOTS = 384` slots. Every *live* `BuiltChildren` that has allocated backing reserves one slot (`reserve`, line 95-109); when the `BuiltChildren` (or its `IntoIter`) drops without having been fully consumed, ownership of the still-boxed backing is *handed back* into that slot for retirement (`publish`, `Drop` impls at line 330-352) rather than freed synchronously — `close_built_node_page_one` (line 159-163) drains one page of backing per call, cooperating with the U1 run-to-completion budget rather than dropping a whole tree in one frame. 384 is thus a concurrency/backlog ceiling on *how many built-children pages can be in flight (live + queued for retirement) at once*, independent of the 32-wide fan-out.
- `positional_key` (line 549-554): `"#{index}"` — the fallback reconciliation key for a child with no author-set id. It is only stable while sibling order/count is unchanged (docstring, line 549-551), which matters for virtualisation: shifting the visible window changes which node occupies position N, so any row relying on the positional fallback (instead of a real id) will appear to reconcile as "removed+inserted" rather than "moved" the moment the viewport scrolls.

**Enforcement — guest and host, same code path, not "guest builder then host re-checks":** `UI_BUILT_CHILDREN_MAX`/`BuiltChildren` live in `semio_framework_ui_contract`, a `wasm32-wasip2`-safe crate shared unmodified by (a) every plugin's own editor/panel code (compiled into the plugin's wasm binary — e.g. the puzzle3d panel in §3) and (b) host-native code in the same repo that also builds `BuiltNode` trees directly without going through a plugin at all (`🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/🦀️.rs:452-484` `paged_text_carrier`, and `⏯️tool-run/🦀️.rs:343` `if surface.children.len() == UI_BUILT_CHILDREN_MAX`). So there is exactly **one** enforcement point — `BuiltChildren::try_push`'s length check — and it is structural (the backing array is physically 32 slots), not a policy the host re-validates after decoding wasm output. The **separate** host-side reconcile budget (§3) is a different, independently-enforced ceiling on top.

## 2. `UiValue` argument arena — `🎬️action/🦀️.rs`

File: `🧰️framework/🔨️modules/🖱️ui/🧬️contract/🎬️action/🦀️.rs`

Constants (lines 18-68):
- `UI_TEXT_MAX_BYTES = 512` (line 18) — every `UiText` is `{ bytes: [u8; 512], len: u16 }` (line 71-75), an **inline, fixed-size** buffer, never boxed. `UiText::try_from_str`/`try_from_string` refuse (return `None`/`Err`) past 512 bytes; `UiText::clipped` (line 137-151, see §4) is the one path that instead truncates and appends `UI_TEXT_CLIP_MARK = "…"` (line 20) and never fails.
- `UI_FIXED_LIST_ITEMS = 32`, `UI_FIXED_BYTES = 32 * 1024` (lines 21-22) — capacity params for `UiFixedList`/`UiFixedBytes`, independent of the builder's `UI_BUILT_CHILDREN_MAX` (same number, different subsystem).
- `UI_VALUE_MAX_ITEMS = 256` (line 24) — cap on `UiList`/`UiMap` logical length.
- `UI_VALUE_NESTING_DEPTH = 256` (line 29) — max nesting an authored `UiValue` may carry; sizes `UiComponentComparisonCursor`'s fixed frame stack (§4), independent of arena admission capacity.
- `UI_VALUE_ARGUMENT_ENTRIES = 4` (line 33) — "the four-key maps every interactive panel row binds" (docstring): `domainId`/`merge`/`method`/`targets` for an interaction pick, or `entity`/`flag`/`ids`/`value` for a row-action toggle. This is exactly the "4-entry map" the ticket asks about.
- `UI_VALUE_ROW_ACTIONS = 2` (line 36) — "a visibility toggle and a lock toggle."
- `UI_VALUE_ROW_COLLECTIONS = 1 + 2 * UI_VALUE_ROW_ACTIONS = 5` (line 39) — one Activate-binding argument map, plus (map + nested id-list) for each of the two row actions.
- `UI_VALUE_ROW_ITEMS = (1 + UI_VALUE_ROW_ACTIONS) * UI_VALUE_ARGUMENT_ENTRIES + UI_VALUE_ROW_ACTIONS = 3*4 + 2 = 14` (line 42) — every argument map's entries plus the one id each row-action's nested list holds.
- `UI_VALUE_PAGE_ROWS = UI_BUILT_CHILDREN_MAX - 1 = 31` (line 54) — **derived from §1's constant**, not independently chosen. Docstring (lines 43-53) states the reasoning explicitly and gives the actual measurement: "at `UI_VALUE_ROW_ITEMS` pages of roughly a kilobyte each, a four-section page would claim ~1.8 MiB of payload the live surfaces need — enough to regress `semio-framework-ui-runtime`'s resident-credit laws. This page holds them exactly at their baseline." I.e. 31 was picked to stay under a byte budget measured against §with the resident authority, not derived from a hard wasm/message-size ceiling.
- `UI_VALUE_LIVE_PAGES = 1` (line 64) — **deliberately** one page admitted at a time, process-wide (see below); docstring: "A second panel assembling beside the first therefore does not get a page of its own: it reads `ui_value_headroom` and pages against what is left."
- `UI_VALUE_ADMISSION_SLOTS = 1*31*5 = 155`, `UI_VALUE_AGGREGATE_ITEMS = 1*31*14 = 434` (lines 65-66).
- `UI_VALUE_AGGREGATE_BYTES = UI_VALUE_AGGREGATE_ITEMS * size_of::<UiPageSlot>() + UI_VALUE_ADMISSION_SLOTS * size_of::<UiCollectionSlot>()` (line 928). `UiPageSlot` (line 897-907) = `epoch: u64` + `next: usize` + `Option<UiPageValue>`, where `UiPageValue::Map(UiText, UiValue)` (line 891-894) inlines a full 512-byte `UiText` key *and* a `UiValue` (whose `Text` variant also inlines 512 bytes, line 1812) — so one `UiPageSlot` is roughly 1.0-1.1 KiB regardless of what it actually holds. `UiCollectionSlot` (line 909-926) is ~140 bytes of bookkeeping (retirement links, alias count, byte/item counters). Multiplying out gives a total arena backing on the order of **~0.46-0.48 MiB** for the whole one-page arena — see the coincidence flagged in §3.

**Per-row cost, concretely** (`UI_VALUE_ROW_COLLECTIONS`/`UI_VALUE_ROW_ITEMS` docstrings, lines 30-42):
- One tree row with **no binding**: 0 arena collections, 0 arena items. Free.
- One row with **one Activate binding carrying a 4-entry map**: 1 collection (the map), 4 items (its entries).
- The same row **plus two row actions** (the canonical shape these constants are sized around): 5 collections (`1 + 2*2`), 14 items (`3*4 + 2`).

**`ui_value_headroom()`** (line 1216-1218, docstring 1197-1213): reads `arena.free_collection_count`/`free_page_count` without admitting or retiring anything; `UiValueHeadroom::rows()` (line 1207-1212) returns `(collections/5).min(items/14)` — i.e. **whichever of collections or items runs out first**, floor-divided per canonical row. This is what `panel_page_rows()` (host-shared `semio_framework_plugin`, `🔌️plugin/🦀️.rs` — see §3 comment block) calls to clamp `UI_VALUE_PAGE_ROWS` down further when other panels of the *same plugin instance* have already spent some of the one live page.

**`UI_RESIDENT_AGGREGATE_BYTES` / "four resident surfaces" law and its fixture** — file `🧰️framework/🔨️modules/🖱️ui/🧬️contract/🎟️resident/🦀️.rs`:
- `UI_RESIDENT_SLOTS = 64`, `UI_RESIDENT_SURFACE_BYTES = 8 * 1024 * 1024` (8 MiB) — lines 10-11.
- `UI_RESIDENT_DOCUMENT_BYTES = UI_DOCUMENT_NODES(128) * size_of::<UiNodeRecord>()` (line 16) — "what ONE surface costs when its body FILLS the document contract... a PRICE... where `UI_RESIDENT_SURFACE_BYTES` is a MAXIMUM."
- `UI_RESIDENT_AGGREGATE_BYTES = UI_RESIDENT_SLOTS * UI_RESIDENT_DOCUMENT_BYTES` (line 31) — **this is a fix**, documented inline (lines 18-30): it *used to be* `4 * UI_RESIDENT_SURFACE_BYTES` ("four times the per-surface CEILING, the imagined concurrency of a four-surface session"), and a real incident (ticket 26/09/09/PROCEDURAL-3D-END-TO-END, wave B58) showed the React generation3d editor peaking at **26 concurrently-resident surfaces** while the aggregate assumed 4, causing a terminal `SurfaceReconcileFault::ResidentCredit` that silently froze one window's graph forever. The fix reprices the aggregate off the SLOT ledger (`UI_RESIDENT_SLOTS = 64`) times a real per-document price instead of a multiple of the per-surface ceiling.
- **The `🎬️action/🦀️.rs:55-58` docstring's "authored law is exactly four resident surfaces" text predates this fix and is now stale relative to the code** — the resident aggregate is no longer literally "4 surfaces' worth"; it is priced per real document content across 64 slots. This is a documentation/implementation sync gap worth closing, not a behavioral bug (the code itself is the fixed, correct version).
- Fixture: `staticCountsAgainstAggregate` is asserted in `🧰️framework/🔨️modules/🖱️ui/🧬️contract/🎟️resident/🧪️tests/🎟️resident/🦀️.rs:8` — `assert_eq!(actual.bytes > 0, fixture["staticCountsAgainstAggregate"].as_bool().unwrap())` — and the aggregate-equals-slots-times-document-bytes identity is pinned again at `🔄️refresh/🧪️tests/🔄️refresh/🦀️.rs:186` and `🎟️resident/🧪️tests/🎟️resident/🦀️.rs:73`.

**Is the arena process-global across all panels of all plugins, or per plugin instance? — Two different arenas, two different answers:**
1. The **`UiValue` argument arena** (`UI_VALUE_ARENA`, a `static LazyLock<Mutex<UiValueArena>>`, line 990) lives inside `ui_contract`, which is compiled *into each plugin's own wasm binary*. Because each plugin runs as its own wasm component instance with its own linear memory, this static is **one arena per plugin instance**, shared by every panel/window *of that same plugin* (hence `UI_VALUE_LIVE_PAGES = 1` starving a second panel of the *same* plugin, per the docstring) — but plugin A and plugin B each get their own independent copy, not a shared one.
2. The **resident ledger** (`RESIDENT_LEDGER`, `static Mutex<ResidentLedger>`, `🎟️resident/🦀️.rs:106`) and the host's `SurfaceReconciler`/reconcile budgets (§3) run on the **host** side (the incident above talks about "the React generation3d editor," i.e. host-rendered surfaces across potentially many plugin-backed windows) — that ledger is process-global **across every surface the host reconciles, from every plugin**, which is why the real incident above involved 26 simultaneous surfaces, not 26 panels of one plugin.

## 3. Surface reconcile path — `SurfaceReconciler` / `FlatPresentedNode`

File: `🧰️framework/🔨️modules/🖱️ui/🧠️runtime/♻️reconcile/🦀️.rs` (host-side; the sibling `semio-framework-ui-runtime` crate the builder file's docstring warns never to depend on from the contract crate).

- `FlatPresentedNode` (line 628-632): `{ parent: Option<usize>, node: crate::TreeNode, child_ids: ui_contract::UiNodeChildren }`, where `TreeNode` is a **type alias for `BuiltNode`** (`🧠️runtime/🎭️present/🦀️.rs:78`, `pub use ui_contract::BuiltNode as TreeNode;`) — i.e. one `FlatPresentedNode` embeds a *whole* `BuiltNode` inline (its `key: UiText` 512-byte buffer, its `Component` enum sized to its largest variant, its `bindings`/`children`/`rejected_children` paged-list handles), plus a second fixed-size `UiNodeChildren` (`UiFixedList<UiNodeId, 128>`) for the flattened child-id list.
- **Byte accounting is charged as `size_of::<FlatPresentedNode>()` (a fixed, compile-time struct size) PLUS the measured `semantic_usage.bytes` for that node's actual bindings/component content** — see lines 1440 and 1470: `size_of::<FlatPresentedNode>().checked_add(self.semantic_usage.bytes)`. So it is **not** purely "billed by `size_of` of a fixed struct regardless of content" — every node pays a fixed per-node overhead (the struct itself) *plus* a real content-derived charge from the semantic census (`SurfaceSemanticCensusStep`, lines 1427-1468). The fixed component is real, though: because `Component`'s enum variants (e.g. `TreeItemProps` at `🧩️component/🦀️.rs:451-462`, which inlines `Label`/`Option<UiText>`/`Option<UiText>` — three ~512-byte fields — plus a `UiFixedList<RowAction>` handle) are not boxed, every `BuiltNode`/`FlatPresentedNode` pays for the *largest* variant's inline bytes even when it is actually holding a small one (e.g. `Separator`).
- `PANEL_RECONCILE_NODE_BUDGET = 16` — `✏️s/🔌️plugins/🧩️puzzle/🗿️artifacts/🧊️3d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor/📌️panels/🗿️artifact/🦀️.rs:39`, docstring lines 37-38: "Host reconcile credits one `FlatPresentedNode` per presented node (~0.46 MiB). The 8 MiB surface byte cap therefore admits at most 16 nodes; 18 Nakagin rows landed 30 KiB over." `SECTION_ROWS = UI_BUILT_CHILDREN_MAX - 1 = 31` (line 33) is the per-section builder cap (§1/§2), but the *effective* cross-section row budget actually used is computed at line 240: `PANEL_RECONCILE_NODE_BUDGET.saturating_sub(1 + SECTIONS).min(semio_framework_plugin::panel_page_rows())` — with `SECTIONS = 4` (line 36) that is `16 - 5 = 11` rows **total across all four sections** (objects/references/target-volumes/attractions) before `panel_page_rows()`'s own clamp is even applied. That is a very small number relative to a 40-60 row viewport target.
- **The 8 MiB cap is per-surface, not aggregate**: `SURFACE_RECONCILE_SURFACE_BYTES = ui_contract::UI_RESIDENT_SURFACE_BYTES` (`♻️reconcile/🦀️.rs:2275`), and `SurfaceReconcileLimits::default().max_bytes = SURFACE_RECONCILE_SURFACE_BYTES` (line 582-584). Each `SurfaceReconciler`/reconcile pass is scoped to one `SurfaceId` (one panel/window's document), so 8 MiB is the ceiling for *that one surface*; the resident ledger's aggregate (§2) is the separate, larger, process-wide-on-the-host ceiling across every surface.
- **`~0.46 MiB` coincidence worth flagging**: independently computing `UI_VALUE_AGGREGATE_BYTES` (§2) from `size_of::<UiPageSlot>()` (~1.0-1.1 KiB, dominated by an inlined `UiText`+`UiValue` pair) and `size_of::<UiCollectionSlot>()` (~140 bytes of bookkeeping) times the item/collection counts lands very close to ~0.46-0.48 MiB — i.e. numerically close to the *whole one-page UiValue arena's total backing*, not obviously the marginal cost of one `FlatPresentedNode` struct on the host side (which is a different, smaller struct on a different side of the wasm boundary). This suggests the puzzle3d docstring's "~0.46 MiB" may be reusing/echoing the guest-side arena's total footprint rather than a measured host-side `size_of::<FlatPresentedNode>()`; recommend the design work re-derive `PANEL_RECONCILE_NODE_BUDGET` from an actual `size_of::<FlatPresentedNode>()` print (the codebase already has the pattern for this — see `⚖️compare/🧪️tests/⚖️compare/🦀️.rs:31`, `eprintln!("[DEBUG] comparison-frame bytes={} depth={} cursor={}", ...)`) rather than trusting the inherited number.
- **`PANEL_RECONCILE_NODE_BUDGET = 16` predates the page-exact fix below.** `git log -S"PANEL_RECONCILE_NODE_BUDGET"` shows it was introduced 2026-09-10 (commit `f39d4b0`); the page-exact reservation fix in `🌱️value/📋️list/🦀️.rs` landed 2026-09-13 (commit `b2064cc`). The constant has not been touched since. Given the fix (below) removed the exact "reserve full 32-slot capacity up front" behavior the puzzle3d comment blames for the 16-node ceiling, **16 now looks like a stale, unrevisited number rather than a currently-measured one.**

**"UiFixedList cold push priced full capacity" — now page-exact — the actual fix:**
- `🧰️framework/🔨️modules/🖱️ui/🧬️contract/🎬️action/🦀️.rs:341-354` (`reserve_next_slot`) documents the historical bug directly: "A full-capacity reservation here priced one `ActionBinding` at 32 slots × 2 KiB × 3 census copies (~240 KiB) and one `RowAction` at ~300 KiB, which capped a surface at ~16 actionable rows of its 8 MiB reconcile budget (process3d workshop, 12 machines + 4 catalogs: `ui.surface-render … bytes: 8390387`, ticket 26/09/15/DEV-PROCESS-REACT-E2E)."
- The fix itself is in `🧰️framework/🔨️modules/🌱️value/📋️list/🦀️.rs`: `PAGE_BYTES = 4096` (line 23); `PagedList::page_items()` (line 120-126) computes `(PAGE_BYTES / size_of::<T>()).max(1).min(N)` — i.e. one page reservation now admits **at most one 4 KiB chunk's worth of slots**, never the full logical capacity `N` (32) at once. `reserve_one`/`next_allocation_bytes` (lines 209-248) only ever grant one page at a time. `reserve_full` (line 259-266) — the old cold-full-capacity path — still exists but is now explicitly reserved for "interactive owners admit one page with `try_reserve_one`" per the `UiFixedList::try_reserve` docstring (`🎬️action/🦀️.rs:309`) — i.e. the *cheap* incremental path is now the default one interactive rows use.
- Net effect: today, admitting one `ActionBinding`/`RowAction` should cost roughly one 4 KiB page per collection touched (bounded by `PAGE_BYTES`), not 240-300 KiB — a >50x reduction from the number `PANEL_RECONCILE_NODE_BUDGET`'s docstring still cites.

## 4. Wasm boundary crossing — encoding, `refreshUi`, diffed vs whole-tree

- **Encoding is `pack`, via a JSON intermediate, per patch-op field — not JSON on the wire and not a whole-tree resend.** `🧰️framework/🛍️products/💻️os/🔨️modules/🔌️plugin/⚛️reactor/🦀️.rs:1587-1596` (`pack_patch_field`): `serde_json::to_value(value)` → `dsl::DslValue::from(&json)` → `store::pack_rt::encode_wire_value(&value)`. `kernel_patch_op_to_wit` (line 1615 onward) converts each `UiPatchOp` variant (`Upsert`/`SetComponent`/`SetLayout`/`SetActivity`/`SetChildren`/`SetStyle`/`SetAccessibility`/`SetBindings`/`SetMenu`/`Remove`/`SetRoot` — full list at `📃️document/🦀️.rs:210-254`) into a WIT `PatchOp`, each carrying exactly one `pack`-encoded field (line 1587-1589 comment) except `Remove`/`SetRoot` which need none. `kernel_ui_patch_to_wit` (line 1576-1585) wraps a *sequence of ops* (`patch.ops.iter().map(kernel_patch_op_to_wit).collect()`) targeting individual node ids, not a full serialized tree.
- **Retained/diffed, confirmed by `UiComponentComparisonCursor`.** `🧰️framework/🔨️modules/🖱️ui/🧬️contract/⚖️compare/🦀️.rs:400` defines the cursor; it is embedded in `ExistingComponentComparison` inside the host reconciler (`♻️reconcile/🦀️.rs:653-668`) specifically to walk an **existing** record's component against the newly-presented one and decide whether it actually changed (`RecordOwnedCopy::Comparison`, line 648, 653-657) before emitting a patch op — i.e. unchanged nodes/fields do not get re-sent. The cursor's frame depth is fixed to `UI_VALUE_NESTING_DEPTH = 256` so this comparison stays inside a bounded byte envelope regardless of how deep an authored `UiValue` nests (`🎬️action/🦀️.rs:25-28`).
- **The 512-byte `UiText` overflow was fixed to no longer fail the whole refresh.** `UiText::try_from_str`/`try_from_string` (lines 90-124) still return `None`/`Err` on overflow — any code path that propagates that with `?` can still abort a whole node's construction. But `UiText::clipped` (lines 133-151) is the documented escape hatch: "Display copy that must never fail admission: the whole value when it fits, otherwise the longest char-boundary prefix leaving room for `UI_TEXT_CLIP_MARK`... Use it only for descriptions and summaries whose full text stays reachable elsewhere... never for identifiers or values." This directly matches the memory note "One UI Admission Fault Kills Every Later Refresh" — the mitigation is available and used for descriptive text, but is explicitly **not** a blanket fix: identifiers/keys/values that still go through `try_from_str` can still refuse and (depending on the caller) abort the surrounding assembly.

## 5. Per-row cost table

| Row shape | Arena collections | Arena items (map/list entries) | Approx. wire bytes (pack-encoded patch op) | Approx. host reconcile bytes charged |
|---|---|---|---|---|
| (a) No binding | 0 | 0 | A few bytes: `key` string + component tag + label text only (defaults are `skip_serializing_if`-elided, e.g. `BuiltNode.bindings`/`.menu`/`.layout` at `🏗️builder/🦀️.rs:397-412`) | `size_of::<FlatPresentedNode>()` fixed overhead only (no semantic bytes) |
| (b) One Activate binding, 4-entry map | 1 (`UI_VALUE_ROW_COLLECTIONS` minus the 2 row-action pairs) | 4 (`UI_VALUE_ARGUMENT_ENTRIES`) | ~tens-to-~150 bytes packed (trigger + action id + 4 short key/value pairs) | `size_of::<FlatPresentedNode>()` + one page-exact reservation (≤ `PAGE_BYTES` = 4096 B) for that map, post-fix (§3) |
| (c) (b) + two row actions | 5 (`UI_VALUE_ROW_COLLECTIONS`) | 14 (`UI_VALUE_ROW_ITEMS`) — this is the exact shape those two constants are named for | Proportionally larger: 3 argument maps + 2 nested one-id lists, each pack-encoded | `size_of::<FlatPresentedNode>()` + up to 5 page-exact reservations (≤ 5 × 4096 B ≈ 20 KiB worst case, likely far less since a 4-entry map fits in far under one page) |

**Rows that fit under each budget today:**
- **Builder fan-out (§1):** exactly 32 children per `BuiltNode`, structurally — always true regardless of row shape, since it counts nodes not bytes.
- **`UiValue` arena (§2):** `ui_value_headroom().rows()` = `min(free_collections/5, free_items/14)`. From a cold arena (`UI_VALUE_ADMISSION_SLOTS=155`, `UI_VALUE_AGGREGATE_ITEMS=434`): `min(155/5, 434/14) = min(31, 31) = 31` canonical (activate+2 row-actions) rows — matching `UI_VALUE_PAGE_ROWS = 31` exactly, confirming the constant is precisely arena-sized for shape (c). For shape (a) rows the arena is not the binding constraint at all (0 cost); for shape (b) rows alone the arena could in principle admit far more than 31 (`155/1 = 155`, `434/4 = 108`) — the "31" ceiling specifically prices the *worst-case fully-interactive* row, so any panel whose rows are mostly (a)/(b) shape is leaving real headroom on the table under today's single-shape budget.
- **Host reconcile 8 MiB / node budget (§3):** the puzzle3d panel's own computed budget is 11 rows across 4 sections (`PANEL_RECONCILE_NODE_BUDGET(16) - 1 - SECTIONS(4)`), independent of and *tighter* than the arena's 31 — this is the binding constraint in practice for that panel, and (per §3) it is very likely stale relative to the page-exact fix.

## 6. Classification: hard facts vs declared laws vs arbitrary constants

**(i) Hard runtime facts:**
- `UiText`'s 512-byte inline buffer and every enum's fixed-size layout (not boxed) are genuine Rust/wasm memory facts once chosen — inline (unboxed) fields make every instance of a struct pay for its largest possible content, and that is unavoidable *given the current type shapes* (not the same as saying 512 itself is forced by any external ceiling).
- The wasm component-model boundary requiring an explicit serialize/pack step per patch op (§4) — genuinely structural, not adjustable by picking a bigger constant.

**(ii) Declared laws pinned by tests (name the tests):**
- `UI_RESIDENT_AGGREGATE_BYTES == UI_RESIDENT_SLOTS * UI_RESIDENT_DOCUMENT_BYTES` — pinned at `🎟️resident/🧪️tests/🎟️resident/🦀️.rs:73`, `🔄️refresh/🧪️tests/🔄️refresh/🦀️.rs:186`, and `🌳️root/🧪️tests/🌳️root/🦀️.rs:126`.
- `staticCountsAgainstAggregate` fixture — `🎟️resident/🧪️tests/🎟️resident/🦀️.rs:8`.

**(iii) Arbitrary constants / self-imposed, with evidence they could be raised or restructured:**
- **`UI_BUILT_CHILDREN_MAX = 32`** — no measured-limit justification found beside the constant; everything downstream (`UI_VALUE_PAGE_ROWS`, `SECTION_ROWS`, the retirement authority width, the command-palette/tool-run paging trees) derives from it rather than an independent measurement. Raising it changes the *shape* of every one of those derived constants at once (they are literally `UI_BUILT_CHILDREN_MAX - 1` etc.), so it is refactorable but not "just bump one number" — it is one number with many syntactic dependents (`grep` count: builder crate + 7 other crates reference it directly).
- **`UI_VALUE_LIVE_PAGES = 1`** — explicitly "deliberately" one (docstring, `🎬️action/🦀️.rs:55-56`), chosen to keep the arena small enough not to "regress `semio-framework-ui-runtime`'s resident-credit laws," not because more pages are impossible. This is the most promising lever for more simultaneously-interactive rows *within one plugin instance* without touching the 8 MiB host-side cap, since it only affects the guest-side argument arena.
- **`PANEL_RECONCILE_NODE_BUDGET = 16`** (puzzle3d panel, `🗿️artifact/🦀️.rs:39`) — per §3, introduced 2026-09-10, *before* the page-exact `UiFixedList` fix (2026-09-13) that the puzzle3d docstring's own rationale (240-300 KiB/row) says caused the 16-row ceiling. This is the single strongest "arbitrary/stale, should be re-derived" finding in this audit: the real per-row byte cost that produced "16" appears to have dropped by >50x, and the constant has not been revisited.
- **`UI_VALUE_ROW_ACTIONS = 2`, `UI_VALUE_ARGUMENT_ENTRIES = 4`** — these describe *today's* authored row shape (one activate binding + hide/lock toggles, 4-key argument maps), not a hard ceiling; a viewport design that wants a uniform per-row price should treat these as "the current worst case" rather than as fixed physics.

## Implications for a viewport-windowed tree

Target: ~40-60 visible, interactive rows at once.

1. **The binding constraint today is `PANEL_RECONCILE_NODE_BUDGET` (effectively 11 rows for puzzle3d, §3), not the builder's 32-children or the arena's 31-row page.** Before doing anything else, re-measure `size_of::<FlatPresentedNode>()` directly (add a debug `eprintln!` the way `⚖️compare/🧪️tests/⚖️compare/🦀️.rs:31` already does) and recompute the 8 MiB / node-cost budget against the **post-page-exact-fix** real cost, not the pre-fix 240-300 KiB/row figure the current docstring still cites. This alone may raise the practical ceiling from ~11-16 toward 40-60 without changing any constant, only the (stale) reasoning behind `PANEL_RECONCILE_NODE_BUDGET`.
2. **`UI_BUILT_CHILDREN_MAX = 32` would need to grow (or the paging strategy would need to change) to hold 40-60 rows in one built node's `children`.** Since `UI_VALUE_PAGE_ROWS`, `SECTION_ROWS`, and the puzzle3d/catalogue panels' own row math are all defined as `UI_BUILT_CHILDREN_MAX - 1`, raising this one constant mechanically raises the guest-side row ceiling everywhere it is used — but it also raises `UI_VALUE_ADMISSION_SLOTS`/`UI_VALUE_AGGREGATE_ITEMS` (both are `UI_VALUE_PAGE_ROWS * ...`), which raises `UI_VALUE_AGGREGATE_BYTES`, which must be re-checked against whatever budget the guest wasm instance's own memory affords. Alternatively, a true streaming/windowed design could keep `UI_BUILT_CHILDREN_MAX` unchanged and instead present the *visible slice* as a flat sibling list re-keyed on scroll (accepting the positional-key reconciliation cost noted in §1) rather than growing the fixed 32-ary fan-out.
3. **`UI_VALUE_LIVE_PAGES = 1` is worth raising if multiple panels of the same plugin need independent live windows simultaneously** — it is documented as a deliberate, revisitable choice, not a hard ceiling, and only affects the per-plugin guest-side arena (not the host's 8 MiB/32-slot budgets).
