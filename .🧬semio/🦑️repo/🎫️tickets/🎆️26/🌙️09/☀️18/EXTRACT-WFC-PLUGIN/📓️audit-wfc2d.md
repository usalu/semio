### Known-gaps triage (wfc2d.md §8)

| gap | rating | why |
|---|---|---|
| 1. `Image` media not hydrated | nice-to-have | No example uses it; declared in the type's own docstring; the brief's core ask (bitmap/vector/image *variants exist and round-trip*) is met — only live hydration through a host is missing, and that's cross-cutting composed-child infrastructure work, not specific to this slice. |
| 2. Entropy is prior, not post-propagation | nice-to-have | Correctly labelled in the docstring; doesn't affect correctness of the assignment or contradiction verdict, only the UI hint quality. |
| 3. `.feature`/`.py` triplet not mounted into `--lib` | nice-to-have | The same laws are independently proven by the 15 mounted per-kind fixture tests plus the standalone Python oracle run; wiring the host-runner adapter is explicitly W2/W3 infra work shared across all artifacts, not a wfc2d-specific shortfall. |
| 4. `ModelBuilder::compile()` runs in one job step | nice-to-have | Disclosed trade-off, within documented step budget for the target tile-alphabet size; matches the engine's actual capability (no steppable multi-relation compiler exists yet). |
| 5. `render` not threaded the transient lane at the `ArtifactEditor` trait boundary | **blocking-for-brief** | This is the direct implementation of the brief's "2d preview" window showing the solved assignment. As coded, `ArtifactEditor::render` (the actual host-invoked render path) always passes `Wfc2dTransient::default()`, so through the framework's own render entry point the preview can **never** show a solve — only `render_body` called directly (i.e., in tests) does. If the "spawned solve job progress" wiring mentioned as W2 work is not done, the preview window is non-functional for its stated purpose in an actual running editor, not just imperfect. |
| 6. TS barrel layout mismatch (six thin facade files) | nice-to-have | Self-consistent workaround, flagged for a plugin-root-level decision; doesn't affect this artifact's own correctness. |
| 7. No foreign io hop | nice-to-have | Correctly reasoned (a WFC problem spec has no external interchange format). |

### Additional finding not in wfc2d.md's own gap list

- **Bitmap tile media renders as a text label, not pixels, in `wfc-2d-preview`** (see item 2e above). This is **blocking-for-brief**: the audit brief explicitly requires "drawing each slot rect with its tile media (bitmap pixels and vector paths), not just labels," and for `Bitmap`-media tiles the current code does exactly what the brief says not to do. The `Vector` path is fully correct. This is not disclosed anywhere in `wfc2d.md`'s known-gaps section, so it reads as an oversight rather than a stated trade-off. Given no bundled example currently uses `Bitmap` media (all three examples use `Vector`), the gap is currently unexercised by any test — no red flag was raised because nothing in the test suite would catch it.

## Ordered fix list

1. **Wire the app-transient solve into `ArtifactEditor::render`** (known gap 5, upgraded to blocking). Either thread the live `Wfc2dTransient` through the framework's render call (subscribing to spawned-job progress per the `React Host Never Refreshes On Spawned Job Progress` memory) or, at minimum, make the gap loudly visible (e.g. a "not yet wired" scene marker) so a host integrator can't miss it. This is the single biggest gap between what's coded and what the brief needs to actually work end-to-end.
2. **Render `Bitmap` tile media as real pixels in `wfc-2d-preview`**, using the renderer's existing `kind:"image"` + `dataUrl` layer contract (`CanvasLayer::data_url`) instead of a `rect` + name label. Requires converting the palette-indexed base64 pixels into a `dataUrl` (e.g. PNG/base64) at render time, and ideally a bundled example that actually uses `Bitmap` media so a render test would catch a regression.
3. **Add a bundled example (or at least a render test) exercising `Bitmap` media**, since all three shipped examples use `Vector` only — the Bitmap path is currently both under-rendered (fix 2) and untested.
4. Minor: remove the two bare `//` comments inside `impl Drop for Wfc2dSnapshotRetirement` (`🚪️io/📸️snapshot/💾️binary/🦀️.rs:83-84`) — fold into the preceding `///` doc comment on the `drop` fn or the struct, per the "no comments inside definitions" convention.
5. Cosmetic: `wfc2d.md` §8 should list the Bitmap-preview gap explicitly so a reader of the slice report isn't surprised by it (documentation completeness, not code).

Everything else audited — document model, mutation set, reusable `wfc-graph` window and its `SlotGraphView` purity, the graph-route inference with its three previously-latent job bugs fixed, the fixture/test/oracle scaffolding, and the naming/verb/icon/float/label conventions — is solid and matches both the plan and the slice's own (largely honest and well-disclosed) report.
