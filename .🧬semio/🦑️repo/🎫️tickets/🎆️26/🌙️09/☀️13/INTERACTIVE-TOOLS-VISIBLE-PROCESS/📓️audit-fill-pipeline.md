# Fill Tool Algorithm Pipeline — Audit

Editor root `E` = `✏️s/🔌️plugins/🧩️puzzle/🗿️artifacts/🧊️3d/🏅️standards/🔖️1/🪆️subsets/✳️any/✏️editor`.

## 1. FillJobStage state machine

Enum at `$E/⏳️precompute/🪣️fill/🦀️.rs:868-885`:

```
DiscardTail, PrepareFixture, PrepareCatalogs, PrepareMeshes, PrepareEntries, PrepareSpatial,
PrepareLookup, PrepareConfiguration, PrepareTargets, SelectTarget, PrepareCandidates,
SelectCandidate, ConstructPreview, QueryBroadPhase, TestCollision, AcceptCandidate, Complete
```

Dispatch table: `step()` at `🪣️fill/🦀️.rs:4295-4356` (impl `InteractiveJob for FillBuilder`).

- `DiscardTail` (`discard_tail_one`, :3318-3358): weight-only replan path (`begin_soft_replan`, :3305-3319) — pops ONE unapplied `appended_objects` tail entry per call, withdraws its spatial-index owner (`CollisionIndexRemoval`, resumable), then rewinds to `PrepareTargets` once the tail reaches `applied_count`. **Not used by `setFillCount`** — only by distribution/weight slider changes.
- `PrepareFixture/Catalogs/Meshes/Entries/Spatial/Lookup/Configuration` → `prepare_one()` (:3364-3374) dispatches to per-stage `*_one` fns (e.g. `prepare_fixture_one`, :3373-3398) that each copy exactly ONE fixture/catalog/mesh/compat/weight row per call from `FillPreparationRoots` into the builder's `FixedOwnerVec`/`FixedOwnerMap` pages, guarded by `preparation_capacity_refusal` (:1041-1062, refuses up front if the *source* scene already exceeds `DOCUMENT_*_SLOTS`).
- `PrepareTargets` → `prepare_targets()` (:3577-3690), itself a `TargetPreparePhase` sub-machine (Reset→Blocked→Enumerate→BuildSeedWeights→BuildFrontierWeights→OrderSeed→OrderFrontier→Finish, defined :892-900): builds the blocked-vortex set from existing attractions, enumerates every open vortex on every fixture+appended object into seed (same-object-as-a-just-placed-piece) vs frontier buckets, Fenwick-tree-weights them (`weighted_pick`, :851-863, using `fill_rng`), and produces `self.targets` — a full weighted *permutation* of all open vortices for this round, seed-first, `target_rotation = sequence.len() % targets.len()` so different plan lengths start scanning at a different rotation.
- `SelectTarget` → `select_target()` (:3701-3717): walks `self.targets` from `target_cursor` (rotated); publishes `preview.target_vortex_full_id` immediately; stalls to `Complete` when the cursor exhausts all targets (no more open vortices this round).
- `PrepareCandidates` → `prepare_candidates()` (:3718-3812), a `CandidatePreparePhase` sub-machine (Reset→Enumerate→Classify→DrainCross→DrainSame→BuildSameWeights→OrderSame→Finish, :904-911): enumerates every `(object kind, source vortex)` pair compatible with the target via `brush_fill_candidate_at`, classifies each into "cross-kind" (sorted by a diversity score) vs "same-kind" (weighted-random), and produces the final `self.candidates` list, cross-kind first.
- `SelectCandidate` → `select_candidate()` (:3818-3827): walks `self.candidates` from `candidate_cursor`; publishes `preview.candidate_object_kind_id`.
- `ConstructPreview` → `construct_preview()` (:3829-3869): resolves world pose from the target vortex + candidate template (`brush_preview_from_candidate`), resolves the mesh body, checks target-volume containment; on success sets `current_preview` **and** `preview.candidate_ghost = current_preview.clone()` (:3875) — the ghost pose is published the instant a geometrically-valid candidate is found, *before* collision testing.
- `QueryBroadPhase` → `query_broad_phase()` (:3877-3902): begins/steps a resumable spatial-hash AABB query (`CollisionSpatialIndex::begin_query`/`step_query`) against already-placed objects; on completion fills `preview.candidate_page` (up to 8 nearby ids) and moves to `TestCollision`.
- `TestCollision` → `test_collision()` (:3903-3970, returns `Option<StepOutcome>` and is the ONE stage excluded from the fuel/"same-stage-Yield" fast path, see below): pops one broad-phase pair id per call, runs one incremental Monte-Carlo overlap sample via `CollisionOverlapState::step` against that single other object, publishes `sample_cursor`/`inside_both`/`last_sample` every call. On `overlap > overlap_budget` → `reject_candidate("solid-overlap")`; on a clean finish of that pair → advances `broad_phase_cursor`; once the pair list is exhausted → `AcceptCandidate`.
- `AcceptCandidate` → `accept_candidate()` (:3972-4144), an `AcceptPhase` sub-machine (Validate→CheckAttractions→BuildVortices→BeginSpatial→StepSpatial→InstallLookup→Commit, :913-919): builds the pending `FixtureObject`/`AttractionProps`/vortex list, checks against existing attraction pairs, inserts into the resumable spatial index (`begin_replacement`/`step_replacement`), installs the `placed_lookup`, then **Commit** pushes onto `self.sequence`/`self.appended_objects`/`self.appended_attractions` **in the builder's own memory only** (no document mutation yet — see §4) and republishes `preview.accepted_count`. Loops back to `PrepareTargets` unless `sequence.len() >= max_count` → `Complete`.
- `reject_candidate`/`reject_target` (:4166-4188) bump `rejected_count`, clear the acceptance/collision working state, and route back to `SelectCandidate`/`SelectTarget` respectively — the candidate ghost is cleared here (`reset_collision(true)` when target-level, kept for candidate-level rejects mid-sequence in some paths).

**Units of work per `step()` call**: exactly one micro-unit per call for every stage (one fixture row, one target-enumeration item, one Fenwick pick, one collision *sample* against one *other object*, one accept-phase sub-step). `step()`'s tail (:4356-4380) special-cases: for the 11 "busy" stages (`DiscardTail`, all `Prepare*`, `PrepareCandidates`, `QueryBroadPhase`) a call that leaves the stage unchanged returns bare `StepOutcome::Yield` *without* calling `publish_preview` — so the UI only actually receives a new preview frame when the stage transitions, or unconditionally for `TestCollision`/`AcceptCandidate`/`SelectTarget`/`SelectCandidate`/`ConstructPreview` (every call through those always falls to `publish_preview`, :4378). `context.consume_fuel(1)` is charged on every stage except `TestCollision` (:4358-4360), i.e. collision sampling is fuel-free and can run many samples per host turn.

**One candidate's flow**: `SelectTarget` (pick target vortex, from the pre-built weighted `targets` permutation) → `PrepareCandidates`/`SelectCandidate` (pick a candidate kind+source-vortex, from the pre-built weighted `candidates` list) → `ConstructPreview` (compute pose, ghost published) → `QueryBroadPhase` (find nearby placed objects) → `TestCollision` (sample-by-sample overlap vs. each nearby object) → `AcceptCandidate` (commit into `appended_objects`, sequence advances) or `reject_candidate`/`reject_target` (advance cursor, retry next candidate/target).

## 2. What's published today, and who reads it

`FillBuildPreview` (schema `✏️s/…/🧬️schema/🦀️.rs:645-685`) fields: `operation, base_revision, registry_generation, sequence, generation, stage, target_vortex_full_id, candidate_object_kind_id, candidate_ghost: Option<BrushPreviewState>, current_pair_object_id, collision_count, sample_cursor, inside_both, last_sample, candidate_page: [Option<String>; 8], truncated, rejection_reason, target_cursor, candidate_cursor, accepted_count, total_count, search_count, rejected_count`.

**This already covers almost everything the new design asks for at the data level** — it is a per-step, per-candidate diagnostic stream, not a "whole plan" snapshot. What's missing is (a) a collision/danger color signal (see below) and (b) a history of *all* tried candidates (only the current one is ever live).

- `candidate_ghost` is set in `construct_preview` (fill/🦀️.rs:3875) and cleared in `reset_collision(true)` (fill/🦀️.rs:4183-4190) / on target-level reject (fill/🦀️.rs:4183) / on preparation-capacity refusal (fill/🦀️.rs:4301). It survives across every `TestCollision` sample for the *same* candidate (many publishes with the same ghost while the sample cursor advances), then either disappears (reject) or the object becomes real via `AcceptCandidate`.
- Transport: `fill_preview_json_page(color, status_label)` (precompute/🦀️.rs:3024-3040, backed by `FillPreviewJsonCursor`/`preview_json_step` in fill/🦀️.rs:290-480) resumably serializes the preview into a ≤4 KiB JSON string, budget-limited to 256 one-field grants per host frame / a 2 ms wall-clock deadline (precompute/🦀️.rs:3026-3028). Called from `world_fill_preview_json` in `$E/🎭️modes/✏️edit/🪟️windows/🧊️main/🦀️.rs:864-871`, gated on `envelope.active_utility == "fill"`. **The `color` argument is `object_kind_color(catalog, candidate_kind)` — the candidate's catalog swatch, not a collision-state color.** There is no danger/highlight distinction published anywhere in the pipeline today; a rejected candidate simply vanishes rather than flashing red.
- `fill_preview_object_kind()` (precompute/🦀️.rs:3049-3051) is a cheap peek used only to pick that color before the full JSON page is built.
- Consumer: `🧰️framework/…/World3dHost/🟦️.tsx`. The wire shape is a `WorldBrushPreviewRecord` (:330-337, shared with the *manual* brush tool) that carries the ghost's own pose fields at the top level **plus** a nested `fillBuildPreview: WorldFillDiagnosticRecord` (:339-362) with the full diagnostic. `suppliedFillDiagnostic = brushPreview?.fillBuildPreview` (:5271); `visibleBrushPreview = fillMode ? (fillDiagnostic?.candidateGhost ? brushPreview : null) : brushPreview` (:5306) — i.e. the fill tool reuses the exact same `BrushPreviewGhost` renderer (:3667-3690) as manual brush placement, always drawn in `palette.highlighted` style (`meshColor = preview.color ?? style.meshColor`, :3674) — **no red/danger palette branch exists**. `FillDiagnosticOverlay` (:3695-3739) renders a single bottom-left HUD `<div>` with `statusLabel`, `stage`, `accepted/total`, and either the rejection reason or the collision count — a live textual readout, already wired, but it shows only the *current* candidate's state, not a growing feed.
- Grep confirms `candidate_ghost`/`candidateGhost` never appears anywhere else in the TS tree (framework-wide) — `World3dHost/🟦️.tsx` is the only consumer. `fill-preview-json`/`fill-p4e`/`fill-envelope` vitest suites (`✏️s/🔌️plugins/🧩️puzzle/🧪️tests/🔬️interactivity-puzzle-fill-*`) only mutation-test the Rust source text (see §7), they don't exercise a live UI.
- **Conclusion for item 2**: the ghost *is* rendered today, live, while `fillMode` is active and a fill job is running — but (1) it is functionally invisible in practice because `fillBuildTick`/the job only run while the fill tool's window is open and armed (`worldFillBuildShouldTick`), and in the *current UX* the user mostly interacts via the count slider then looks away while the plan silently completes in the background; (2) it never shows collision (danger) state, only "there is a candidate" vs "there isn't"; (3) it shows one candidate at a time with no memory of what was tried before it.

## 3. Job bridge: worker ⇄ app ⇄ UI, and cadence

- `FILL_JOB_KIND = "semio.puzzle3d.fill"` (precompute/🦀️.rs:44). `FillJobRequest { job, operation, generation, base_revision, slot, registry_generation }` (precompute/🦀️.rs:71-79) identifies one envelope slot in a small fixed registry (`FILL_ENVELOPE_MAX_OPERATIONS = 4` slots, :52).
- Admission: `enqueue_fill_job`/`enqueue_fill_job_spending` (precompute/🦀️.rs:3168-3260) — a **resumable admission census** (`FillBuilderOwnerCensusCursor`, budgeted `FILL_ENVELOPE_CENSUS_UNITS_PER_TURN = 4_096` units/turn, :48-58) walks every owner the live `FillBuilder` retains and registers it into a `BoundedJob`/`JobBudget` envelope (`semio_framework_plugin::reactor::jobs::{BoundedJob, BoundedJobFactory}`) before a real `Effect::SpawnJob { kind: FILL_JOB_KIND, placement: JobPlacement::Isolated, .. }` is ever issued (`fill-build-tick/🦀️.rs:20-24`). Only after the whole builder is admitted does the worker actually start stepping.
- Poll: `poll_fill_job()` (precompute/🦀️.rs:3272-3287) reads the registry's `observation(&request)` (a small `FillObservation { generation, sequence, available, done }`) and diffs it against the last-seen value — this is the ONLY thing the 120 ms tick round-trips; the worker's own `FillBuilder::step` loop runs independently inside the bounded job (driven by `worker.pump_one(&fill_worker_pool(), Lane::Background)`, referenced in the fill-envelope mutation tests), not by the UI tick.
- `fill_observation` carries exactly 4 fields: `generation` (preview generation, monotonic per replan), `sequence` (preview publish sequence, monotonic per `publish_preview` call), `available` (`sequence.len()` in the plan so far), `done` (stalled or `sequence.len() >= max_count`).
- Cadence: client-side `createInFlightSkippingInterval(..., 120)` in `World3dHost/🟦️.tsx:5910-5917` dispatches `fillBuildTick` every 120 ms *only while the previous dispatch's `OperationCompleted` has returned* (in-flight-skipping, not a blind `setInterval` — a 2026-09-09 incident measured 252 ticks/35 s piling into an unbounded queue and starving every other action before this guard existed, comment at :5901-5906). `worldFillBuildHostTickAllowed(true, isolatedJobDriveIsActive(), takeIsolatedJobUiPoll())` further gates so only a queued UI-poll dispatches while the Isolated job is mid-drive (fill-build-tick/🦀️.rs:9-13 doc comment). Server-side, `fill_build_tick` (fill-build-tick/🦀️.rs:15-31) does at most: one `poll_fill_job()`, and if no job is live, one `enqueue_fill_job()` (which itself may spawn `Effect::SpawnJob`).
- `cancel_fill_job_for(job, operation, generation)` (precompute/🦀️.rs:3365-3371) is an identity-gated cancel — a stale (job,operation,generation) tuple silently no-ops, so a cancel button rendered for an already-superseded run can't kill the new one (`fill_job_identity`, :3351-3363).

## 4. `setFillCount` — how it actually applies, and the `reveal` slider key

**Important structural fact**: `setFillCount` does **not** read from the live `fillBuildTick` background job. It runs its own **separate, synchronous, deterministic replan** inside the interactive-command state machine `Puzzle3dPrecomputeCommandWork` (`$E/🦀️.rs`, `Puzzle3dPrecomputeCommandStage` enum), stages `FillPrepare`→`FillPlan`→`FillApply`→`Publish` (`🦀️.rs:6975-7038`):

- `FillPrepare` (:6975-6987): builds a **brand-new** `Puzzle3dPrecomputeSession::new()`, syncs it to the current scene, and seeds `set_fill_applied_count(config.fill_count)` — i.e. it reconstructs the plan from scratch rather than reusing the session `ctx.app.precompute` that `fillBuildTick` drives.
- `FillPlan` (:6988-7002): if the fresh session hasn't yet planned enough placements to cover `max(requested_count, config.fill_count)`, it drives `precompute.precompute_step_lane(PrecomputeLane::Fill, 1)` **one unit per command-work turn** until enough are available or the plan is `done`. Because the RNG seed (`scene.seed`) and the planning algorithm are identical to the background job, this reproduces the *exact same deterministic sequence* — see §6.
- `FillApply` (:7003-7011): calls `set_fill_count::apply_chunk` (`$E/🎮️commands/🧮️set-fill-count/🦀️.rs:21-33`) → `apply_fill_count_chunk(target, MAX_PLACEMENTS_PER_STEP=1)` (precompute/🦀️.rs:3065-3082): compares `current` (`fill_applied_count`) to `target = min(requested, sequence.len())`; moves `next` by at most 1 toward `target`; if growing, slices `appended_objects[current..next]`/`appended_attractions[current..next]` into `added_objects`/`added_attractions`; if shrinking, slices `appended_objects[next..current]` **in reverse** into `removed_object_ids`. `apply_chunk` turns these into real `Puzzle3dMutation`s: `create_object`, `connect_vortices`, `delete_object` (set-fill-count/🦀️.rs:23-31) — **one placement mutation per command-work turn** (`MAX_PLACEMENTS_PER_STEP = 1`, set-fill-count/🦀️.rs:12).
- `Publish` (:7031-7038, the `tool_id == "setFillCount"` branch): emits the accumulated `fill_mutations` plus, only if the value actually changed, a `Puzzle3dConfigMutation::SetFillCount { count: requested_count }` — this is what persists `runtime.fill_count` on the document/config side.
- The **slider's `reveal` key** (`fill/🎭️modes/✏️edit/🛠️tools/🪣️fill/🦀️.rs:38`, `reveal: Some("puzzle3d-fill".into())`) is a pure **client-side, zero-round-trip** visibility cutoff: while dragging, the client writes `worldRevealCutoffStore.set(PUZZLE3D_FILL_REVEAL_GROUP_ID, value)` (`ShellHelpers/🟦️.tsx:2816-2845`) and `isRevealCutoffHidden(instance)` (`ShellHelpers/🟦️.tsx:2842-2845`) hides any rendered `WorldInstanceRecord` whose `revealIndex >= cutoff`. Only on gesture release does the committed value round-trip through `setFillCount`. This works because `render` (`🦀️.rs:8302`, `puzzle3d_fixture_with_fill_display_memo`, :1683-1710+) *already* grafts every planned-but-not-yet-applied object (`available_count > applied_count`) onto the rendered fixture as an ephemeral tail (`append_fill_display_tail`, :1667-1674, tagging each with `reveal_index`) via `precompute.compose_fill_display(available_count)` — so the client can instantly show/hide any prefix of the *plan* without any of it being a real document mutation; only the committed slider value round-trips to actually persist mutations via `setFillCount`.

## 5. `FILL_COUNT_MAX` / `PUZZLE3D_FILL_COUNT_MAX` — every use, and what breaks unbounded

Two distinct constants, both `1000`, deliberately not unified (doc comment precompute/🦀️.rs:16-18):
- `PUZZLE3D_FILL_COUNT_MAX: u32 = 1000` (`$E/🦀️.rs:73`) — UI-facing: clamps the slider's `max` (fill tool measure, :36), clamps `parse_count` in `setFillCount` (set-fill-count/🦀️.rs:19), clamps `engagement-repeat-last`/`engagement-submit` fill counts (`🎮️commands/🔂️engagement-repeat-last/🦀️.rs:8`, `🎮️commands/📨️engagement-submit/🦀️.rs:19`). Sibling constants exist per artifact: `PUZZLE5D_FILL_COUNT_MAX` and `PUZZLE2D_FILL_COUNT_MAX`, both also hardcoded `1000` — a parallel design in the other two puzzle artifacts.
- `FILL_COUNT_MAX: usize = 1000` (precompute/🦀️.rs:19) — planner-facing: `FillBuilder::begin_preparation` sets `max_count: FILL_COUNT_MAX` and `preview.total_count: FILL_COUNT_MAX` **unconditionally** (fill/🦀️.rs:3050, 3074) — i.e. the background planner *always* plans to 1000 regardless of what the slider currently requests; every fallback `FillProgressSummary`/`FillBuildProgress` also defaults `max_count: FILL_COUNT_MAX` (precompute/🦀️.rs:3005, 3017, 3019).

Fixed-capacity structures explicitly sized off it (`⏳️precompute/📐️geometry/🦀️.rs:32-51`):
- `DOCUMENT_OBJECT_SLOTS = 2048` — comment: "the scene it starts from plus a full `FILL_COUNT_MAX` (1000) plan; Nakagin carries 180 objects, worst case 1180; 2048 is the next power of two above it."
- `DOCUMENT_ATTRACTION_SLOTS = DOCUMENT_OBJECT_SLOTS` (2048) — "the scene's own plus one per placement."
- `DOCUMENT_VORTEX_SLOTS = 2 * DOCUMENT_OBJECT_SLOTS` (4096), `DOCUMENT_CELL_SLOTS = 4 * DOCUMENT_OBJECT_SLOTS` (8192) — indirectly derived from the same object budget, not directly from `FILL_COUNT_MAX`, but sized assuming a bounded plan.
- `preparation_capacity_refusal` (fill/🦀️.rs:1035-1063) preflights the *source scene* against `DOCUMENT_OBJECT_SLOTS`/`DOCUMENT_ATTRACTION_SLOTS`/etc — it does **not** check `max_count` against anything, because `max_count` is currently always the constant.
- Tests pin the relationship explicitly: `assert!(DOCUMENT_OBJECT_SLOTS >= FILL_COUNT_MAX + 1024, …)` (`📐️geometry/🧪️tests/🔬️unit/🦀️.rs:506`); `assert!(nakagin("objects") + FILL_COUNT_MAX <= DOCUMENT_OBJECT_SLOTS, …)` and the attraction equivalent (`🪣️fill/🧪️tests/🔬️unit/🦀️.rs:1119-1120`).
- `FILL_ENVELOPE_MAX_BYTES = 256 × 16 KiB = 4 MiB` and `FILL_ENVELOPE_MAX_ITEMS = 65_536` (precompute/🦀️.rs:46-49) bound the whole admitted envelope (every retained owner page together) — these are generous relative to a 1000-item plan but are still a hard ceiling, not a growth-on-demand budget.

**What breaks with an unbounded slider**: every `FixedOwnerVec<_, DOCUMENT_OBJECT_SLOTS>`/`FixedOwnerMap<_, DOCUMENT_ATTRACTION_SLOTS>` etc. is a **compile-time-sized fixed page** (`FixedOwnerVec`/`FixedOwnerMap` in `📐️geometry/🦀️.rs`) — `try_push`/`try_insert` return an `Err`/rejected-owner variant once full, which the current code treats as `preparation_capacity_refusal`/`fixed_rejection` → the whole job **faults** (`fill/🦀️.rs:4306-4312`, `StepOutcome::Fault`). There is no growth path today: a document already at or near 2048 objects, or a requested count materially above ~1868 (2048 − 180), would make `AcceptCandidate`'s `try_push`/`try_insert` fail outright. Simply removing the slider's UI clamp (`PUZZLE3D_FILL_COUNT_MAX`) without touching `FILL_COUNT_MAX`/`DOCUMENT_OBJECT_SLOTS` would silently cap the *achievable* count at whatever the fixed pages allow and then hard-fault past that, not simply "plan more slowly."

**What a chunked/grow-on-demand design needs**: (a) `FillBuilder::max_count` must become the actually-requested count (not a hardcoded `FILL_COUNT_MAX`), with a `raise_max_count(new_target)` that just bumps the field and, if the builder is `Complete`/stalled at the old max, resets `stage` back to `PrepareTargets` to keep going (no replan, no RNG rewind — see §6); (b) `DOCUMENT_*_SLOTS` need either a materially higher static ceiling sized to the largest realistic ask (still fixed-capacity, matching the "no dynamic allocation" discipline the `FixedOwner*` types encode) or the `FillBuilder`'s planning-side owners (`appended_objects`, `appended_attractions`, `sequence`, `placed`, `placed_lookup`, `candidate_cache`, `blocked_vortex_ids`, `candidate_seen`) would need to become genuinely unbounded `Vec`/`HashMap` collections decoupled from the document-scale fixed pages that model the *persisted* document (the persisted-document pages can stay fixed since a real document has its own realistic ceiling; the *planning* structures are the ones that need to scale with an unbounded ask); (c) `FILL_ENVELOPE_MAX_BYTES`/`MAX_ITEMS` need re-deriving from the new ceiling, and the admission census (`FillBuilderOwnerCensusCursor`) needs to keep being resumable at whatever the new page sizes are (already unit-budgeted, so this is a constant change, not an algorithm change).

## 6. Determinism / RNG — prefix invariant

- `fill_rng(rng_state: &mut u32)` (`⏳️precompute/🖌️brush/🦀️.rs:434-437`) is a plain LCG (`x = x*1664525 + 1013904223`, then normalized to `[0,1)`), seeded once from `roots.scene.seed` at `begin_preparation` (fill/🦀️.rs: `rng_state: seed` in the constructor, ~:1102) where `scene.seed: u32` (`🧬️schema/🦀️.rs:566`) is itself set from `Operation::new(..., scene.seed as u64)` in `start_fill_preparation` (precompute/🦀️.rs:1899).
- **Because the planner always plans to the full `FILL_COUNT_MAX` regardless of what the slider currently asks for** (§5), and the RNG stream and every weighted pick (`weighted_pick`/Fenwick trees) are purely a function of `(seed, scene, catalogs, weights)` consumed in strict step order, **the plan for any count N is exactly the prefix of the plan for any count M > N** — there is only ever one canonical sequence per (scene, weights) pair, and `apply_fill_count_chunk` (precompute/🦀️.rs:3065-3082) literally slices `appended_objects[current..next]` out of that single `sequence`/`appended_objects` vector. Raising the slider from 100→150 is therefore already a pure "continue from the locked 100" operation today — confirmed structurally by `apply_fill_count_downward_move_keeps_the_plan_intact` and `decreasing_fill_count_keeps_the_plan_intact_and_does_not_replan` (`⏳️precompute/🧪️tests/🔬️unit/🦀️.rs:191, 296`).
- **Lowering the count via the slider does NOT touch the plan (`fill.sequence`/`appended_objects`) at all** — it only walks `fill_applied_count` backward and emits `delete_object` mutations for the tail already-applied objects (`apply_fill_count_chunk`'s `next < current` branch, precompute/🦀️.rs:3074-3078). The *planned* prefix stays intact in memory so raising the slider back up is instant (no replan). `tail_removal`/`DiscardTail` (fill/🦀️.rs:3305-3358) is a **different** mechanism entirely — it discards from the *plan itself* and is triggered only by `begin_soft_replan` when the object/vortex weight distribution changes (a genuinely different RNG outcome is needed), never by `setFillCount`.
- This means: a redesign that "continues from the locked N instead of restarting" gets this invariant for free as long as it keeps (a) one seed per (scene, weights) generation and (b) a single monotonically-growing `sequence`/`appended_objects` — the only change needed is making `max_count` dynamic (§5/§8) instead of always racing to 1000 in the background.

## 8. Minimal-invasive redesign sketch

Goal: (a) plan only toward the requested count and grow incrementally, (b) publish every tried candidate + verdict as a live stream, (c) commit accepted objects as real document mutations as they lock, (d) progress = accepted/requested + status label.

Because the state machine, preview struct, and RNG-prefix invariant already do most of this (§1-2, §6), the change is narrower than a rewrite:

1. **`FillBuilder::max_count` becomes dynamic** (fill/🦀️.rs:1083, currently `pub(crate) max_count: usize` — already a plain field, not a const-derived one). `begin_preparation` (fill/🦀️.rs:~3050) stops hardcoding `max_count: FILL_COUNT_MAX`/`total_count: FILL_COUNT_MAX` and instead takes a `requested_count: usize` parameter. Add `pub(crate) fn raise_max_count(&mut self, requested: usize)`: sets `self.max_count = self.max_count.max(requested)`; if `self.stage == Complete` and `self.sequence.len() < self.max_count`, un-stalls back to `PrepareTargets` (mirrors the existing `AcceptCandidate::Commit` transition check at fill/🦀️.rs:4143, just re-entered). ~15-20 lines.
2. **Drop the "always plan to 1000 in the background" behavior**: `start_fill_preparation` (precompute/🦀️.rs:1891-1910) currently ignores the slider's current value entirely; it should pass `envelope.runtime.fill_count.max(some small default like 100)` as the initial `requested_count`, and `fill_build_tick`/`setFillCount` should call `raise_max_count` when the user drags past what's already targeted, instead of relying on a plan that silently already went to 1000. ~10 lines in `start_fill_preparation` + a new call site in `set-fill-count/🦀️.rs`'s `apply_chunk`/`request`.
3. **Every tried candidate becomes a stream item, not a transient field.** Today `preview` is a single mutable struct republished each `step()`; the UI already re-derives "fresh vs stale" via the `(operation, base_revision, registry_generation, generation, sequence)` monotonic tuple (`World3dHost/🟦️.tsx:5271-5288`). Add a bounded ring buffer on the wire type, e.g. `pub tried: [Option<FillTriedCandidate>; N]` (N≈16-32, mirrors the existing `candidate_page: [Option<String>; 8]` fixed-array idiom already used for `FillBuildPreview`) where `FillTriedCandidate { ghost: BrushPreviewState, verdict: FillCandidateVerdict }` and `enum FillCandidateVerdict { Testing, Accepted, RejectedCollision, RejectedOther(reason) }`. Populate it by pushing into the ring at the existing three points that already know the outcome: `construct_preview` (push `Testing`, fill/🦀️.rs:3875), `test_collision`'s `overlap > budget` arm (rewrite the pushed entry's verdict to `RejectedCollision`, fill/🦀️.rs:3960-3961), `reject_candidate`/`reject_target` (rewrite to `RejectedOther`, fill/🦀️.rs:4166-4188), and `AcceptCandidate::Commit` (rewrite to `Accepted`, fill/🦀️.rs:4142). This is a data-shape addition to `FillBuildPreview` plus ~5 one-line writes at existing verdict points — no new control flow. Estimated 60-100 lines across schema + fill/🦀️.rs + the JSON cursor (`FillPreviewJsonCursor` needs the new field threaded through its field-by-field resumable encoder, `preview_json_step`, another ~80-120 lines mirroring the existing `candidate_ghost`/`candidate_page` cases at fill/🦀️.rs:359-480).
4. **Danger vs. highlight color**: add a `collision: bool` (or reuse `FillCandidateVerdict`) to the wire ghost shape; on the client, `BrushPreviewGhost` (`World3dHost/🟦️.tsx:3667-3690`) branches `style = preview.collision ? palette.danger : palette.highlighted` instead of always `palette.highlighted` (:3674) — check `MeshStylePalette` for an existing `danger` entry (its type isn't in this audit's file list; if absent, add one alongside `highlighted`/`neutral`). ~10-15 lines.
5. **Accepted objects become real document mutations as they lock, not after the whole plan.** This is the biggest structural change, because today `AcceptCandidate::Commit` only pushes into the *in-memory* `appended_objects`/`sequence` (fill/🦀️.rs:4142-4148) and the *only* place that turns plan entries into `create_object`/`connect_vortices` mutations is `setFillCount`'s separate synchronous replan (§4, `Puzzle3dPrecomputeCommandStage::FillApply`, `🦀️.rs:7003-7011`) driven by the slider commit, decoupled from the live background job. To make locking-in immediate: either (a) have `fillBuildTick` itself call `apply_fill_count_chunk(fill.sequence.len(), MAX_PLACEMENTS_PER_STEP)` against `ctx.app.precompute` right after `poll_fill_job` observes `available` increase — turning the *background* tick into the thing that emits `create_object`/`connect_vortices` mutations continuously (removes the render-time "ghost tail" grafting in `puzzle3d_fixture_with_fill_display_memo`, §4, since accepted objects would already be real document objects by the time render runs); or (b) keep the current `applied_count`/`available_count` split (so the slider can still logically "not have caught up") but change its default behavior so `fillBuildTick` always requests `apply_fill_count_chunk(target = min(requested, available), ...)` up to the currently-visible count every tick, i.e. make "reveal" and "commit" the same operation rather than a client-only visual cutoff. Option (a) is more invasive (removes the whole `reveal`/`compose_fill_display`/`FillDisplayMemo` mechanism, ~150 lines across `🦀️.rs:1652-1710`, `fill/🎭️modes/…/🛠️tools/🪣️fill/🦀️.rs:38`, and the client `worldRevealCutoffStore`/`isRevealCutoffHidden` machinery) but matches the new design's "no hidden precompute" intent literally; option (b) is smaller (~20-30 lines in `fill-build-tick/🦀️.rs`) and keeps the reveal mechanism as a pure animation/pacing layer over an otherwise-live commit stream.
6. **Progress = accepted/requested + status label**: already present almost verbatim — `preview.accepted_count`/`preview.total_count` (schema :672, 680) just need `total_count` to stop being the constant `FILL_COUNT_MAX` (fixed by step 1/2) and instead reflect `max_count` (the live requested target); `FillDiagnosticOverlay`'s `{accepted}/{total}` (`World3dHost/🟦️.tsx:3730-3733`) and `WindowMeasure::Slider.ready`/`.loading` (fill tool `count_measure`, `🛠️tools/🪣️fill/🦀️.rs:24-38`) already read off `fill_progress_summary()` (precompute/🦀️.rs:3011-3019) — no new plumbing needed there beyond making `max_count` dynamic. A `status_label` string already exists as a caller-supplied parameter to `fill_preview_json_page`/`preview_json_step` (currently just `labels.fill_progress`, a single fixed localized string) — extending it to something like "searching…" / "placing…" / "done" per stage is a small `match self.stage` in `world_fill_preview_json` (`🧊️main/🦀️.rs:864-871`).

**Rough total for the whole redesign**: constants/dynamic-max-count plumbing (~30 lines), tried-candidate ring buffer + JSON cursor cases (~150-200 lines), danger color branch (~15 lines client), continuous-commit change to `fillBuildTick` (~20-150 lines depending on option a/b above), plus updating the ~15 existing tests that currently assert `max_count == FILL_COUNT_MAX` / the reveal-tail behavior (§7) to match the new semantics. No new files are structurally required — every change lands inside the six files already named in this audit's file list, aside from possibly a new `FillCandidateVerdict` enum which fits naturally in the schema file next to `BrushPreviewState`.
