# IFC SQLite Snapshot Field Research

The assigned IFC artifact has five snapshot dialects: IFC4 wildcard and IFC2x3 wildcard, cv20, sav and cobie. Actual persisted fields were read before schema design. The two standards have different owned types and require individually handwritten semantic schemas and mappings; STEP's snapshot projection is not their model.

IFC4 IfcSnapshot owns schema, an IfcHeader with three ordered raw typed-value lists (fileDescription, fileName and fileSchema), and ordered IfcEntity values with unsigned64 identifiers, primary type names/arguments and additional ordered complex types/arguments. IfcValue has unset, derived, signed64 integer, binary64 real, string, enum, unsigned64 reference, aggregate and typedValue(name, ordered items). Its header is richer than STEP's interpreted header fields and must retain every value and variant. The planned tables give each header list its own ordered ownership relation, retain primary/complex arguments and distinguish aggregate children from typed-value arguments. Exact binary64 companions and explicit entity FKs preserve all native states.

IFC2x3 Ifc2x3Snapshot owns schema, a Part21Document and optional Ifc2x3EdmPreamble. That document is the actual persisted model in this standard: ordered instances each with unsigned64 identifier and an ordered list of (type-name, arguments) pairs, plus three ordered Part21Header value lists. Part21Value owns reference, string, enum, signed64 integer, exact Part21Decimal, list, typed(name, ordered items), unset and derived. Its decimal is not binary64: negative boolean, arbitrary coefficient string, unsigned32 scale and optional signed32 exponent must be preserved independently, including leading coefficient zeros and exponent presence. Decimal conversion to f64 or serialized Part21 is inappropriate.

The optional IFC2x3 EDM preamble has sixteen separately named strings: producer, module, creationDate, host, database, databaseVersion, databaseCreationDate, schema, model, modelCreationDate, headerModel, headerModelCreationDate, user, group, license and options. Its optional presence requires an explicit root FK to a named preamble relation. No opaque text payload will carry this model.

The existing three named IFC2x3 validators operate directly on borrowed Part21Document fields. Their genuine rules differ: CV2.0 schema/view claims, forbidden structural types, exactly-one project/units advisory and object-placement resolution; SAV schema/view, required structural-analysis model and group/load advisories; COBie schema/view, space names, building/storey and type assignment advisories. Controlled owned validators will preserve these rules and diagnostics without native encoding or graph cloning. The existing bare declarations bind the two wildcards; named declared routes require exact ownership validation and tests.

Current TS owner types expose lossy number identifiers/integer values, number binary64 reals and optional empty complex collections. IFC2x3 already distinguishes exact decimal fields but still needs strict primitive widths and complete typed ownership. Matching actual Artifact/Diff/Mutation consumers and public declaration checks will be repaired with the providers. Native wire/proto scalar widths remain unchanged. Research is preparatory; IFC SQLite implementation and runtime success are not claimed yet.
