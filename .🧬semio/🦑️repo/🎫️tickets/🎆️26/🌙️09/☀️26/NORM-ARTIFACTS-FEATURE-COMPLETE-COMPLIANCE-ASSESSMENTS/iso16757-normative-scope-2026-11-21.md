# ISO 16757 electronic product catalogue coverage

The trace maps current catalogue data checks to the 2015 architecture, the 2016 geometry edition, and the dictionary and interchange editions published in 2025. The first edition of Part 1 remains published while work on its replacement continues. The geometry part uses primitives from STEP and IFC and defines additional geometry for the building services domain. Independent external geometry and data dictionary round trips remain necessary. [Part 1](https://www.iso.org/standard/57613.html) · [Part 1 revision project](https://www.iso.org/standard/94406.html) · [Part 2](https://www.iso.org/standard/62080.html) · [Part 4](https://www.iso.org/standard/85070.html)

Part 5 specifies use of IFC and EN 17549-2 for exchange between catalogue providers and building services designers. The existing report has internal exchange, structure and identifier checks. Real-world conformance requires the normative catalogue view, the corresponding representation, an independent consumer and round-trip evidence. Draft publication numbering must remain separate from the released edition. [Part 5 publication](https://www.iso.org/standard/85071.html) · [Part 5 draft](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso%3A16757%3A-5%3Adis%3Aed-1%3Av1%3Aen)

## IFC4 catalogue projection

The exporter now emits an IFC4 project library, class groups, concrete proxy product types and declaration and group relationships. A declared dictionary name and optional version are exposed through a library association. The base document can be opened by an IFC4 consumer. IfcOpenShell 0.8.4.post1 independently validated the emitted STEP file against EXPRESS rules and checked three products, group membership, declaration, the dictionary link, and round-trip names containing Unicode, an apostrophe and a backslash. The Rust exporter yielded identical bytes when the input product order changed. IFC4 documentation prohibits direct IfcTypeProduct instances even though the EXPRESS schema accepts them, so this projection uses concrete proxies with an undefined predefined type. [IFC4 type restrictions](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2_TC1/HTML/schema/ifckernel/lexical/ifctypeproduct.htm) · [Proxy type](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2_TC1/HTML/schema/ifcsharedbldgelements/lexical/ifcbuildingelementproxytype.htm) · [Dictionary library information](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2_TC1/HTML/schema/ifcexternalreferenceresource/lexical/ifclibraryinformation.htm)

The ISO 16757-5 exchange view still requires verification. The generic IFC proxy projection carries identities, class memberships and the supplied dictionary reference. Product variants, properties, ports, geometry, native model-view classes and dictionary URI mappings remain outside this export. The native crate check was queued behind the repository graph and capacity gates. [Part 5 publication](https://www.iso.org/standard/85071.html)
