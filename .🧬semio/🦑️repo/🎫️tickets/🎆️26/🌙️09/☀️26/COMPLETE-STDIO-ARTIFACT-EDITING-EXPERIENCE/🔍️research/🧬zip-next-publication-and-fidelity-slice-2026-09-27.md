# ZIP Publication and Fidelity Follow-Up

ZIP text target resolution now yields one entry per command turn and supports persisted checkpoints. Store publication still uses the generic atomic inverse/diff/apply path; this remains a real responsiveness gap for large entry payloads. The DOCX worker mounted a reusable preparation route seam at `BoundedNativeEditingEditor::native_edit_preparation_route`, with a precise mutation predicate and no generic fallback after recognized refusal. ZIP must mount its own route for RenameEntry and SetArchiveComment, page inverse strings and the post snapshot through RetainedTextCopy/RetainedBytesCopy, then hand the exact edit and post owner to the live authority's one-item sealer. Cancellation must retire partial and sealed owners under byte/item grants. The generic retirement implementation for Vec<u8> is per-byte/per-item, so ZIP needs a budgeted byte owner rather than that default for payload buffers.

The source ZIP decoder already parses compression method, local and central extras, DOS date/time, flags, versions, attributes, and per-entry comment, then discards them before creating `{name,data}`. The writer substitutes extension-based compression, canonical timestamps, flags and extras. Preserving authored entry sequence and Unicode names fixes only two losses. A schema-first metadata model and neutral ZIP fixture with independent `zip` reader assertions are needed before claiming complete archive editing.

Avoid a nullable raw-metadata cache that creates two unequal snapshots for the same default header: authored metadata must have stable encode/decode semantics. Prefer explicit first-party header fields plus deliberate constructors for new logical members. Keep derived CRC/sizes/offsets coherent with payload and compression edits. Stored/deflate codecs exist; other unsupported methods must continue to fail explicitly rather than dropping members. Local and central extras are distinct and their unknown bytes must survive; offset-bearing ZIP64 records require coherent rebuilding. Encoding flags, comments and original raw name bytes need an explicit policy so renaming a Unicode member cannot reuse stale encodings. Existing OPC package-order behavior now preserves content-part order by default; format-specific order remains explicit.

No implementation or runtime proof for the metadata model is claimed here. Current full component and native ZIP/family checks are still separate gates.
