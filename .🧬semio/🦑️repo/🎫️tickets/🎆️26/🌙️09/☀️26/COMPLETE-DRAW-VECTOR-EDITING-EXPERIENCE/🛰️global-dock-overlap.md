## Native Pane Placement Audit

The native shell's real palette paint path is `paint_window_pane_chips_step`, currently deriving `cursor.rect` directly from `window_pane_chip_rect` without occupancy reservation. The authoritative open-panel source already exists as `open_floating_panel_rects(theme)`, which computes current anchor boxes from visible populated tabs and measured retained content, before panels are walked. Native Actions/Search/Measures/Utilities bodies each have separate placement paths; for example Utilities derives its rail origin independently from the authored bottom-left chip, and window_measures_rect derives its own right-aligned content rectangle. Simply shifting the painted chip would leave its unfolded body behind, so a complete repair needs one shared pane placement result consumed by both chip and body paths. Using last frame's panel_rects would risk stale ownership; current anchor geometry is available and should be used.

The existing native mounted pane law file is `🧪️tests/🪟️wgpu-window-pane-chrome/🦀️.rs` (module `window_pane_chrome_tests`). It already provides engaged_pane_shell, builtin atlas, incremental 4096-op painting and pane_overlay_hits assertions. This can support actual native hit geometry and restoration tests. All eight pure anchor cases are already neutral and cross-validated, but native window palette integration has not been implemented or tested. No native chip-only workaround was introduced.

Intrinsic expanded-body sizing must remain stable when reservation changes. Reading only an already clamped body's current rectangle can alter perpendicular obstacle membership and cause repeated offset changes. A clean next stage should preserve requested size separately, compute a bounded placement/scroll region for header and body together, and provide an explicit reachable alternative when no complete pane rectangle fits. Current React integration proves measured placements that fit; it does not prove this full intrinsic-size/no-fit contract.
