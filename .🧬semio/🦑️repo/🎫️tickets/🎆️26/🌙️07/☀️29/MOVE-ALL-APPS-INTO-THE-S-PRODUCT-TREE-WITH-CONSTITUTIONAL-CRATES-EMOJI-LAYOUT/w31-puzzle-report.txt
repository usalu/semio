W31 constitutional split — puzzle plugin (2d, 3d, 5d apps)
=============================================================

SCOPE: split the largest multi-app plugin (puzzle, ~23,222 lines across
2d/rs, 3d/rs, 5d/rs, plugin/rs) into three parallel constitutional app
trees per the recipe at w31-constitutional-split-recipe.md, following the
gis (multi-app) and note (single-app) precedents.

RESULT: all 21 app crates + the thin bundle compile clean and pass tests.

  s/plugin/puzzle/app/2d/{rs,engine,dsl,op,pack,protocol,ui}/rs
  s/plugin/puzzle/app/3d/{rs,engine,dsl,op,pack,protocol,ui}/rs

DEVIATIONS FROM THE RECIPE (all content-mapping judgment calls, no logic
rewritten):
  - Per-app small `⚠️ Errors` enum (Puzzle3dError, Puzzle5dError) placed
    in `rs` (not `engine`) — matches original puzzle_3d/puzzle_5d
    structure and keeps it visible to both engine and downstream slots
    without an engine→op-style circular risk.
  - `PuzzleXPlayProjection` (the `serde_json::Value`-boxed document type
    the live `XPlayApp` actually stores, predating the typed
    `PuzzleXProjection`) plus its `DocumentDsl`/`DocumentPack`/
    `Operation`/`OperationDiff` impls live in `op`, not `ui` — they
    cluster tightly with the Operation enum's Value-bridge logic
    (`apply_puzzleXd_operation_to_value` etc.) already required to live
    in `op` per the circular-dependency rule, and `ui` already depends on
    `op` so nothing is hidden from it.
  - `PuzzleXEnvelope`/`PuzzleXStore` type aliases live in `op` (need both
    `rs`'s Projection and `op`'s own Operation type; can't live in
    `engine` without giving `engine` a forbidden dependency on `op`).
  - The wasm-bindgen `Puzzle3dDocumentVcs`/`Puzzle5dDocumentVcs` bridge
    structs (dispatchText/dispatchBinary/projectionJson/envelopeJson) —
    originally colocated with the wasm-pack-built engine code — moved to
    `ui` instead, since they need `op`'s Store/Envelope types and `engine`
    must never depend on `op`. Confirmed dead from the JS side (grepped
    the whole repo; nothing calls dispatchText/envelopeJson on these
    specific bridges) so this is risk-free. `puzzleXdParseDslJson`
    (actually used by all three Storybook stories) stayed in `engine`,
    the crate that's still wasm-pack-built under the unchanged npm
    package names `@semio-tech/puzzle-{2d,3d,5d}-rs`.
  - Test-module granularity: whole `#[cfg(test)] mod` blocks (host_tests,
    tests, force_graph_tests, puzzle3d_vcs_tests, etc.) were moved intact
    to the slot matching their PREDOMINANT subject (e.g. all of
    `host_tests` → engine, since it exercises `BoardHost` end to end) —
    except the handful of individually-identifiable dsl/pack/op/protocol-
    law tests at the tail of each monolith's biggest test module
    (assert_dsl_round_trip / assert_dsl_pack_equivalence / the one real
    DocumentStore round-trip test per app), which were extracted
    individually into dsl/pack/protocol per the recipe's explicit
    content-mapping rules. This is a pragmatic granularity choice given
    the file sizes (2d alone had ~3,850 lines of test code across 3
    modules); no test was dropped, only relocated.
  - `puzzle_2d_engine::puzzle_2d_lod_scale_json` (used by 5d's `ui` for
    the paired 2D/3D lod picker) is re-sourced directly from the kernel
    crate `infinite_board_port_directed_normal` in 5d's `ui` Cargo.toml
    rather than adding a 5d→2d app-to-app dependency, since the function
    is a plain kernel re-export with no puzzle_2d-specific behavior.
  - puzzle_5d's `rs`/`engine` depend on puzzle_3d's `rs`/`engine`
    (pre-existing cross-app dependency: Puzzle5dError wraps
    Puzzle3dError, Puzzle5dPrecomputeSession wraps
    Puzzle3dPrecomputeSession) — carried forward unchanged, just
    repointed at the new `app/3d/{rs,engine}` locations.
  - No `s/plugin/puzzle/shared/rs` crate created — nothing was actually
    shared by ≥2 of the three apps at the entity/op/engine level (Rule S
    not triggered).

FINAL-STEP cleanup (leftover sibling wrapper files):
  - `s/plugin/puzzle/{2d,3d,5d}/rs` each had their own
    project.json/package.json/script.ts (+ `pkg/` wasm-pack build output,
    + build.rs/asset/ for 2d only) wiring an nx `wasm`/`test` target and
    an npm package `@semio-tech/puzzle-{2d,3d,5d}-rs` exporting
    `./pkg/puzzle_{2d,3d,5d}.js`. Grepped the whole repo: these are LIVE
    consumers, not dead code —
      * framework/renderer/react/index.tsx dynamically imports
        `@semio-tech/puzzle-2d-rs/pkg/puzzle_2d.js` for the "board-2d"
        canvas renderer.

        `@semio-tech/puzzle-{2d,3d,5d}-rs` to call `puzzleXdParseDslJson`.
    So instead of deleting, the whole wrapper (project.json, package.json,
    script.ts, and for 2d also build.rs + asset/NotoColorEmoji-subset.ttf)
    was RELOCATED verbatim (paths/cwd/import recomputed via
    `python3 -c "import os; print(os.path.relpath(...))"`) into the new
    `app/<a>/engine/rs` directory — same npm package name, same
    `wasmBaseName`/`pkg.files` config, so `framework/renderer/react` and
    the Storybook stories needed ZERO changes (they resolve by npm
    package name, not path). Only `runCargoTestBudgeted([...])`'s Cargo
    package-name argument was updated to the new constitutional name.
  - Root `package.json` workspaces: replaced
    "s/plugin/puzzle/{2d,3d,5d}/rs" with
    "s/plugin/puzzle/app/{2d,3d,5d}/engine/rs".
  - Root `script.ts` POLICY_COMMAND_ENVELOPE_COMPLETENESS_ALLOWLIST:
    removed the 3 old monolithic entries + the (now test-free) bundle
    entry, added the 9 new files that carry an
    `assert_dsl_pack_equivalence(`/`assert_document_pack_round_trip(`

    predicate the policy check itself uses, not a guess.
  - Also found and fixed one genuine EXTERNAL Rust consumer of the old
