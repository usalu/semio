# Compiler source witness retry integration

The owned `verify-witness-retry` route selected both integration cases. Each stopped in `cargo:planning-capture` when the checkout compiler ingress refused Cargo’s `rustc -vV` probe. Both cases got past fixture lockfile generation. Neither wrote a stub compiler attempt, so the run yielded no integration verdict about retry or staging. The language-neutral fixture expectations are two attempts and a second-attempt stage for a newly resolvable source witness, and two attempts with no stage for a repeated missing witness.

The affected test body calls `runStub`, which holds `withLawStorageV1` and supplies only temporary Cargo home and target state. The route issues a valid test invocation, while actual planning still needs an owned compiler configuration view and the exact Cargo flags and environment that view projects. The component driver requires `withCargoInputs` and `withPassInputs` together. Its production call site in the plugin driver stage binds `repositoryCargoCompilerInputsV1` and `withRepositoryCargoPassInputsV1` to the same retained `withRepositoryCompilerStoreV1` reservation, invocation and granted network policy. Fitting that arrangement to the fixture means retaining the fixture manifest under an admitted workspace, taking an owned compiler lane, retaining the pass input selection across planning and retries, and continuing to feed the authored synthetic diagnostics through the stub Cargo process. The scheduler is already supplied by the test, so the fixture itself has no Rust build dependency.

The canonical Cargo law admission fixture demonstrates a private repository with checked profile sources and a real compiler-store view. The ticket’s generated directory is 104 characters long on this checkout. The canonical `privateRepositoryDeepestV1` check projects 316 characters for a graph workspace rooted there, exceeding the 256-character limit. Its normal fallback places private scratch outside the ticket. The live checkout’s compiler store can supply compact lane paths while the source fixture stays in ticket scratch, but opening it during Note stage42 would use the same store and capacity coordinator. This investigation left production code and the running stage unchanged and did not bypass the compiler launcher.

## Scoped integration recipe

1. Use `stage-note-guest.ts verify-witness-retry` to issue an original invocation for the two existing cases. Keep the fixture workspace and fake Cargo files under the ticket’s generated directory. Leave the checkout compiler guard in place.
2. Use the checkout as the owned workspace and Cargo planning cwd and retain the absolute fixture `Cargo.toml` as the pass manifest. Use `repositoryCargoNetworkV1` to derive the grant from that invocation, and open `withRepositoryCompilerStoreV1` with the fixture’s release mode and a control derived from the original invocation. Acquire an owned component lane for the fixture package with compact target and build paths. Use the compiler reservation’s declared lease directory and a fixture-owned short cache subdirectory in the reservation.
3. Use `nativeBuildPassInputRequestsV1` with the lane paths and the store environment to declare the fixture selection. Hold it with `withRepositoryCargoPassInputsV1`, keeping the same invocation, workspace, network grant and storage when binding both driver input ports. Derive each `repositoryCargoCompilerInputsV1` consumption from its request arguments. Give the driver the real storage reservation and source boundary, deriving capacity and stage writer custody from that storage.
4. Preserve the fixture’s fake Cargo build and unit-graph stream, explicit scheduler and assertions on attempts, held target and build paths, and staging. Use real Cargo for metadata via the issued inputs. Rerun the two isolated cases after the live Note stage releases capacity and check each expected outcome.
