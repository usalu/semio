# Note guest browser publication cache contention

Attempt 48 (`wJjV81j`) passed Cargo’s `wasm32-wasip2` build and retained the 127,556,752-byte linked Note component. Its descriptor stage completed and populated its stage cache. Model publication then failed while opportunistic compiler headroom recovery requested the exclusive `cache-prune` lease. The wait was one millisecond. Transpilation stopped when the original process admission closed. The driver’s provenance record reports `closed:false` and the report records that it never reached the final recheck.

The supported browser stage requires a newly published model receipt tied to its component and provenance, plus the actual transpiled units under the issued storage policy. The retained bytes and descriptor do not supply that receipt. The supported continuation is the same warm `components iterate note` command through the ticket’s stage launcher, which reuses units and stages according to the driver’s normal validation. Only compiler headroom recovery opts into deferring contention. The cache maintenance owner catches a typed timeout only from its exclusive `cache-prune` acquisition, only for a nonwaiting request, and checks the original control before returning. The recovery callback exits that attempt so the existing headroom loop can remeasure and retry. Maintenance body errors, blocking requests and other acquisitions retain their existing behavior.
