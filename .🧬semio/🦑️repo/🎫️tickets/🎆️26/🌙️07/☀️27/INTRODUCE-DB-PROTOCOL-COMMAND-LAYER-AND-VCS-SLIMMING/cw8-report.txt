   `vcs::ReconcileReport { ..., severity: vcs::ReconcileSeverity::Warning }` inside a real

5. `dsl/rs/lib.rs:441,443,654,656` (test module) — `<DerivedOperation as vcs::OpText>::...` /

All five were simple, safe, pure renames (same trait/type, different import path — Rust guarantees
identical behavior) — none required the "report and leave the shim in place" fallback.

Re-ran the same exhaustive, multi-line-aware, comment-excluding scan after all fixes: **zero** real
`vcs::<shim-name>` references remain anywhere in the repo outside `.claude/worktrees/`/`.repo/`
ticket backups.

Deleted the shim region from `vcs/rs/lib.rs` (was lines 31-64, marked `//#region 🚧️TEMPORARY
protocol shim` / `//#endregion`). The `pub use protocol::{merge_concurrent_diffs, Edit, Operation,
OperationDiff, OperationMeta, OpText, ReconcileReport, ReconcileSeverity};` line is gone. It was
NOT simply deleted outright, though: `vcs/rs/lib.rs`'s own body still spells ~150 bare references
to `Operation`/`OpText`/`Edit`/`OperationMeta` throughout (generic bounds like `Operation: OpText`,
`Edit<Operation>` struct literals, `crate::Operation<P>` disambiguating the trait from a
same-named generic parameter) that predate the shim and are unrelated to it — so a bare deletion
would have broken the crate's own compilation. Replaced with a PRIVATE (non-`pub`) `use
protocol::{Edit, Operation, OperationDiff, OperationMeta, OpText, ReconcileReport};` — this keeps
internal ergonomics working while ending external `vcs::Operation`/`vcs::OpText`/etc resolution,
which is the actual thing "the shim" means. `merge_concurrent_diffs` and `ReconcileSeverity` were
dropped from even the private import: neither is referenced bare anywhere inside `vcs/rs/lib.rs`
(confirmed via cargo's unused-import warning disappearing once trimmed) — both stay reachable only
via fully-qualified `protocol::` inside vcs (already used that way at several call sites), never
via `vcs::`.

## 2. Policy lints (root `script.ts`)

Added three new policy-rule regions plus a Cargo-dep allowlist prefix change, registered in the
`policy` export next to `policyPackCompletenessBreaches`/`policyNoPackFilesBreaches`:

- **`policyProtocolMigrationBreaches`** (`//#region 🔧️PolicyRuleProtocolMigration`) — scans every
  `*.rs` file (`policyAllRustFiles`) for `vcs::<Name>` (qualified-path form, comment-line- and
  `crate::vcs::`-excluding) or a multi-line `use vcs::{...}` block importing any of: `Operation`,
  `OperationDiff`, `OperationMeta`, `OpText`, `Edit`, `merge_concurrent_diffs`, `ReconcileReport`,
  `ReconcileSeverity` (the deleted shim's own name set) plus the CW3-extracted
  `semio_framework_core` types (`HybridLogicalTimestamp`, `OperationEnvelope`, `OpDag`,
  `UndoPolicy`, `MergeStrategyKind`) and the hub wire-frame enums (`HubClientFrame`,
  `HubServerFrame`) — guarding against any of those ever being re-shimmed onto `vcs::` again.
  **Current breach count: 0.**
- **`policyCommandEnvelopeCompletenessBreaches`** (`//#region 🔧️PolicyRuleCommandEnvelopeCompleteness`)
  — mirrors `policyPackCompletenessBreaches`'s shrinking-allowlist pattern: any file that already
  calls `assert_dsl_pack_equivalence(`/`assert_document_pack_round_trip(` must also call
  `vcs::test_support::assert_command_envelope_round_trip` (added in CW7). Computed the current gap
  via the same `grep -rl` approach prior policy additions used: 56 files call the pack-round-trip
  asserts, 55 of them (all except `vcs/rs/lib.rs` itself, which proves the mechanism via its own
  `DemoProjection`/`LossyOperation` fixtures — same precedent as
  `POLICY_PACK_COMPLETENESS_ALLOWLIST`) don't yet call the command-envelope assert. Seeded
  `POLICY_COMMAND_ENVELOPE_COMPLETENESS_ALLOWLIST` with exactly those 55 files. **Current breach
  count: 0** (fully covered by the seeded allowlist, as expected on day one).
- **`policyDbServerOnlyBreaches`** (`//#region 🔧️PolicyRuleDbServerOnly`) — new
  `policyDiscoverCargoTomlFiles` walker (same `POLICY_SKIP_DIRS` pattern as the other file
  discoverers) finds every `Cargo.toml` in the repo (including the root one); for each whose
  directory is NOT under `db/`, `framework/product/os/hub/`, or a `compose/**/hub/**` path (checked
  structurally via path segments, not a fixed prefix, since `compose/server/hub/rs` isn't a single
  literal prefix), flags any `db`/`db_*` path dependency found via a Cargo-dependency-line regex
  (mirrors `POLICY_CARGO_DEP_RE`'s style). **Current breach count: 0** — the only current db/db_*
  dependents are `framework/product/os/hub/rs`, `compose/server/hub/rs`, and `db/*` crates
  depending on each other, all inside the allowed set.
- **`POLICY_ALWAYS_ALLOWED_DEP_PREFIXES`** gained `"protocol/"` (apps now depend on it directly per
  CW7's import sweep). Did NOT add `"db/"` — db stays reached only through the hub servers and
  (behind a feature) `db_engine`, enforced instead by `policyDbServerOnlyBreaches`.

Verified via an ad hoc bun script directly importing and calling script.ts's exported `policy`
linter function (the exact code path `bun ./script.ts lint`'s nx target / the repo's GraphQL
linter infra ultimately invokes — a prior ticket in this same campaign,
`26/07/26/DSL-MIGRATION-LOCK-STEP-...`, used the identical technique for the identical reason:
`bun ./script.ts lint` itself runs a heavy repo-wide nx ESLint + dependency-cruiser pipeline
unrelated to these Rust-facing checks and would take far longer than exercising the actual new
code). Result: all three new lint kinds report 0 breaches; the pre-existing 43 breaches across
other lint kinds (`app-plugin/*`, `dsl-migration/completeness`) are unchanged, confirming nothing
else regressed. One false positive was found and fixed during this verification:
`policyProtocolMigrationBreaches` initially flagged compose's own `crate::vcs::Edit` references
(its internal GraphQL entity module happens to be named `vcs` too) — fixed by excluding matches
immediately preceded by `crate::`.
