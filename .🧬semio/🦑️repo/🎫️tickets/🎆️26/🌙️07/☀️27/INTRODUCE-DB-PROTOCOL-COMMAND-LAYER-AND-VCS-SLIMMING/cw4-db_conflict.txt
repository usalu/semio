What was implemented
---------------------
Replaced the stub lib.rs with a real, tested conflict-detection engine for concurrent commands
against the same document base frontier, built in five regions:

- 🔖️CommandTouch — `CommandKind` (kind tag newtype) and `CommandTouch` (one command's declared
  identity/kind/ConflictRule/HybridLogicalTimestamp plus its accumulated `db_state::TouchedSet`
  and a `claims: Vec<String>` list of uniqueness-constraint keys it holds). Builder-style
  `.touch(region)` / `.claim(key)`. `order_key()` gives a total deterministic order:
  `(HybridLogicalTimestamp, command_id)` — the HLT is already actor-tiebroken per protocol_core,
  command_id is the final tiebreak for two commands from the same actor at the same tick.

- 🔖️Bloom — `PathBloom`: a fixed-size bitset bloom filter (default 2048 bits / 4 hash functions,
  this crate's own choice) over touched-region paths, used as an O(bits) pre-filter before the
  O(regions²) full touched-set intersection scan. `might_intersect` is proven to have zero false
  negatives (tested with 500 randomized trials of disjoint/overlapping path sets) and
  conservatively returns `true` on a bloom-parameter mismatch rather than risking a false
  negative. `PathBloom::new` validates `num_bits`/`num_hashes` > 0 before allocating the backing
  Vec (repo's "validate before allocating" convention).

- 🔖️KindMatrix — `CommandKindMatrix`: declarative, structural (not touched-region-derived)
  commutativity knowledge between command kinds — `declare_commuting(a, b)` (symmetric) and
  `declare_read_only(kind)` (a kind that never conflicts with anything, e.g. queries). Acts as an
  override layered on top of region detection; `ConflictDetector::detect` skips the region/bloom
  work entirely for a declared-commuting pair.

- 🔖️Resolution — `ResolutionPlan` (Commutes/Transform/Merge(kind)/Crdt(kind)/Reject), a
  `From<protocol::ConflictRule>` bridge, and `combine_conflict_rules(a, b)` which combines the two
  conflicting commands' declared `ConflictRule`s: same rule on both sides -> use it; differing
  rules -> falls back to `Transform` (the one reconciliation mechanism defined generically over
  any `Operation<P>` regardless of declared merge strategy, per `protocol_causal::
  OperationTransform`).

- 🔖️ConflictRecord / 🔖️Detector — `ConflictKind` (TouchedRegion(Vec<TouchedRegion>) |
  Constraint(String)), `ConflictRecord { command_id, conflicting_with, kind, resolution }` (the
  type the `db` facade's frozen `CommandReceipt.conflicts: Vec<ConflictRecord>` field is built
  from), and `ConflictDetector::detect(&[CommandTouch]) -> Vec<ConflictRecord>`: sorts the batch
  by `order_key` first (so the returned conflict SET is provably independent of the caller's
  input order — tested directly), then for every pair applies kind-matrix override -> bloom
  pre-filter -> real `TouchedSet`-based intersection (reusing `db_state`'s
  read/read-never-conflicts law, additionally collecting which regions overlapped for
  diagnostics), plus a separate pass detecting shared uniqueness-constraint claims (which can
  span commands touching entirely disjoint overlay paths, unlike region conflicts) — those always
  resolve to `Reject`.

Deviations from the contract
-----------------------------
None on the frozen field-level contract (no signatures in the "## db crate family" section
directly name db_conflict's own API — it's covered by the plan's Part 2 table row, which was
followed literally: "Touched-region intersection, bloom filters, command-kind matrix, transform/
semantic-merge/CRDT via protocol declarations, constraint conflicts, ConflictRecord registry,
deterministic resolution").

One deliberate, documented design boundary (not a deviation, a consequence of the contract's own
hard rule): "command payloads are opaque protocol::OperationEnvelope/binary bytes below
db_document — no db crate below it interprets operation semantics". Since db_conflict sits below
db_document and never sees a concrete `Operation<P>`/`OperationDiff<P>` type, it cannot itself
call `protocol_crdt::merge_concurrent_diffs` (which is generic over the concrete diff type). This
crate owns the DECISION (touched-region + constraint conflict detection, deterministic
prioritization, and translating declared `ConflictRule`s into a `ResolutionPlan`); executing that
plan against the concrete diff is `db_document`'s job once it has the real `Operation<P>` type in
scope. This boundary is documented at the top of the module doc.

Extension seams left (none block the crate's core mechanism)
--------------------------------------------------------------
- `combine_conflict_rules`'s "differing rules -> Transform" fallback is a reasonable, documented
  choice for the genuinely ambiguous case of two different command kinds declaring different
  ConflictRules; a future crate with more context (e.g. db_document, which knows both concrete Op
  types) could make a more precise choice per specific kind pair. Not a stub — it's a real,
  justified default, just not necessarily the only sensible one.
- `PathBloom` sizing (2048 bits / 4 hashes) is a fixed default; a future tuning pass could size it
  per-batch based on actual touched-region count. Not required for correctness (the filter is
  provably conservative regardless of sizing), only for false-positive-rate tuning under load.

ADDENDUM — follow-up session, same wave
==========================================
A second session was independently dispatched on this same ticket/crate after the above report
was written (concurrent-agent overlap — this ticket's crate was picked up twice). That session
found this file already fully implemented (as documented above) mid-way through its own
context-gathering, and per CLAUDE.md's "extend, don't replace" rule for already-substantial
concurrent work, kept this implementation as-is and only closed one explicit gap against the
plan/contract line: "constraint conflicts (unique name, single parent, non-overlapping
intervals)" — the version above only had a generic string-keyed `Unique` claim, with no
first-class single-parent or non-overlapping-interval support (both need value/range comparison,
not exact-key equality, so they couldn't be expressed as `Unique` claims).

Extension made:
- New `Constraint` enum (region `//#region 🔖️Constraint`): `Unique(String)` |
  `SingleParent { child, parent }` | `NonOverlappingInterval { track, start, end }`.
- `CommandTouch.claims` retyped `Vec<String>` -> `Vec<Constraint>`. `.claim(key)` kept (now
  pushes `Constraint::Unique`, same call signature, no existing caller broken); added
  `.claim_parent(child, parent)` and `.claim_interval(track, start, end)` builders.
- `detect_constraint_conflicts` rewritten to run three independent "first holder wins, later
  violators conflict against it, non-violating re-claims fold in silently" tables (unique-key map,
  child->(parent,holder) map, per-track claimed-interval list). All three still resolve to
  `ResolutionPlan::Reject` — a structural constraint violation is never mergeable, matching the
  pre-existing `Unique` behavior.
- Module doc header line updated to name all three constraint kinds explicitly.
- One pre-existing test's expected string updated (`constraint_conflict_detected_across_
  disjoint_touched_paths`: `ConflictKind::Constraint` description is now `"unique:<key>"` instead
  of bare `"<key>"`, since the description is now disambiguated per constraint variant — same
  conflict, same resolution, just a clearer message).
- Two new tests added: `single_parent_constraint_conflicts_only_on_diverging_parent`,
  `non_overlapping_interval_constraint_conflicts_only_when_ranges_actually_overlap`.

No Cargo.toml change was needed for the extension (only `std::collections::HashMap`, already
in scope).
