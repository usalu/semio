Unplanned fix outside framework/sync
-------------------------------------
`vcs/rs/lib.rs` (last touched today by a concurrent session, commit 8f6db11da3 "🚩️363") had
`use semio_framework_hash::hash_bytes;` gated `#[cfg(not(target_arch = "wasm32"))]`, but
`operation_envelope_from_edit` (NOT wasm32-gated) calls `hash_bytes` unconditionally — this broke
the wasm32 build of every crate depending on `vcs`, including `framework/sync`, before I touched
anything. `semio-framework-hash` is an unconditional dependency in vcs/rs/Cargo.toml (pure blake3,
no OS dependency, and other call sites already build fine for wasm32), so the cfg-gate on the
*import* was simply wrong for this newer call site — the one remaining native-only use
(`impl BlobStore for FolderSqliteStorage`, sqlite-backed) is already separately
`#[cfg(not(target_arch = "wasm32"))]`-gated on its own impl block. Fix: made the import
unconditional, with an inline comment explaining why. This is additive/non-conflicting (loosens an
overly-narrow gate, doesn't touch anyone's in-flight logic) and unblocked my own wasm32 verify step
for this wave; flagging it here per the shared-file protocol rather than silently absorbing it.
Verified `cargo build -p vcs` still succeeds natively after the change.

New frame-handling flow
------------------------
- **Wire bridge**: this actor's internal `semio_framework_core::OperationEnvelope` (what
  `vcs::DocumentVcsStore`/`ChannelBackbone` speak — UNCHANGED, out of this wave's scope) is
  converted to/from `protocol_causal::OperationEnvelope` (what `protocol_wire::ClientFrame::
  Commands`/`ServerFrame::Commands` carry) only at the wire boundary, via `to_wire_envelope`/
  `from_wire_envelope`. `ActorId`/`DocumentId`/`OperationId` are literally the same type on both
  sides (`semio_framework_core` re-exports them from `protocol_core` verbatim), so only
  `schema_version`/`payload_hash` (recomputed on receipt, same as the existing
  `operation_envelope_from_stored_edit` already does for external folder edits) and
  `inverse.{target_operation,base_version,dependencies,undo_policy}` (no wire counterpart —
  `protocol_causal::InverseOperation` is deliberately simpler) need real bridging; this actor's
  diff payloads are always edit-shaped JSON (carrying their own `sequenceNumber`/`backwards`), so
  the recovery is lossless in practice, mirroring the pre-existing folder-edit-reconstruction
  pattern.
- **Connect**: `try_connect_hub`/`WasmActor::connect` send `ClientFrame::Hello{wire_version:1,
  protocol_version:1, schema, pack_schema_hash:[0;32] (placeholder — see Deferred), actor, token,
  resume_token, frontier}` as a binary WS frame on `Lane::Command`.
- **Outbound ops**: `relay_operations_to_hub` assigns a `batch_id`, converts envelopes via
  `to_wire_envelope` (stamping a fresh `HybridLogicalTimestamp` from a per-actor HLC seed +
  logical counter), tracks `pending_batches: HashMap<batch_id, Vec<local envelope>>`, sends
  `ClientFrame::Commands{batch_id, envelopes}`.
- **Inbound ops**: `ServerFrame::Commands{envelopes, origin, frontier}` — if `origin != self.actor`,
  converts via `from_wire_envelope` and delivers as `DocumentEvent::RemoteOperations` (unchanged
  event shape).
- **Ack handling** (`handle_ack`, new): `ServerFrame::Ack{batch_id, stages, frontier}` —
  `AckStage::Applied{outcome}` resolves the tracked batch: `Accepted` just emits
  `DocumentEvent::CommandOutcome{Accepted}`; `Rejected`/`Transformed` both first roll back the
  speculative local head by replaying each sent envelope's own precomputed `inverse` as a synthetic
  remote operation (`rollback_envelope` — this actor is schema-agnostic/Value-typed end to end, so
  it can't call into `protocol_command`'s generic typed-inverse trait machinery; replaying the
  envelope's own already-computed `InverseOperation` through the existing `ingest_remote` path
  achieves the same effect); `Transformed` then additionally delivers the hub's replacement
  envelope as a normal `RemoteOperations` event.
- **hub_version -> Frontier**: `hub_version: i64` replaced by `server_frontier: Option<
  protocol::RuntimeFrontierSummary>`, updated from every frame that carries one
  (`Welcome.server_frontier`/`Commands.frontier`/`Ack.frontier`); `resume_token: Option<String>`
  tracked from `Welcome.resume_token` and echoed on the next `Hello`.
- **Preview lane**: new `SyncSession::publish_preview`/`DocumentActorMsg::PublishPreview` ->
  `ClientFrame::PreviewPublish` on `Lane::Preview`; `ServerFrame::Preview` (filtered by
  `actor != self.actor`) -> `DocumentEvent::Preview`.
- **Presence**: `PresencePeer` <-> `serde_json::Value` via `presence_to_json`/`presence_from_json`
  (the wire's `ClientFrame::Presence{peer: Value}`/`ServerFrame::Presence{peers: Vec<Value>}` are
  schema-erased; this actor's typed `PresencePeer` is serialized/deserialized at that boundary).
- **TS fallback** (backbone-worker.ts, used only when the WASM module is unavailable): mirrors the
  Rust flow exactly using the new `encodeClientFrame`/`decodeServerFrame` TS codec and
  `toWireEnvelope`/`fromWireEnvelope`/`rollbackEnvelope` TS twins. The production browser path
  (Rust WASM `BackboneWorkerHost`) owns its own `web_sys::WebSocket` internally and never routes
  raw frame bytes through `backbone-worker.ts`'s JS at all — that file is purely a loader in that
  path (per the plan: "worker + backbone-worker.ts treat frames as opaque bytes" applies to this
  TS fallback, where frame *bodies* stay JSON.parse'd `unknown`/opaque payloads even though the
  envelope/frame *shape* is typed).

Deferred (expected/documented, not bugs)
------------------------------------------
- **Hub server is JSON-only until CW6**: nothing in this wave talks to a real hub — all Rust tests
  run against an in-process `MockHub` that speaks real binary `protocol_wire` frames (rewritten this
  wave), and the TS fixture test only decodes committed bytes. End-to-end wire compatibility against
  the actual `os-hub`/`compose-hub` binaries is not real until CW6 rebuilds them; that's this wave's
  explicit boundary, not something left broken.
- **No client -> hub whole-envelope snapshot push**: `protocol_wire::ClientFrame` has no
  snapshot-put variant (only causally-ordered `Commands`; the hub -> client snapshot direction is
  `Bootstrap::Snapshot`/`SnapshotChunk`/`SnapshotDone`, download-only). `DocumentActorMsg::
  LocalSnapshot` still persists to the folder binding; the old hub relay
  (`HubClientFrame::PutEnvelope`) has no wire-v2 equivalent and is dropped, documented inline in
  both the Rust actor (`drain_and_relay`) and the TS fallback (`handleLocalMsg`). How CW6's rebuilt
  hub reconstructs structural snapshots (presumably by replaying `Commands` batches) is a hub-side
  concern, not this wave's.
- **`Bootstrap::Snapshot`/`SnapshotChunk`/`SnapshotDone`**: accepted and ignored — no client-side
  pack decoder wired into `framework/sync` this wave (db/pack integration is a CW6+ hub-rebuild
  concern). A reconnecting client currently only catches up via a hub's follow-up `Commands` frame
  (which is what the rewritten `MockHub` does, mirroring `db_sync`'s `handle_hello` ->
  `decide_bootstrap` -> `commands_server_frame` shape from the CW4 report).
- **`pack_schema_hash`**: sent as `[0u8; 32]` placeholder (both Rust and TS) — no client-side schema
  pack hashing wired this wave; never validated since the hub is JSON-only until CW6 anyway.
- **`ServerFrame::CreditGrant`**: accepted and ignored — no client-side credit-based backpressure
  implemented (scope was frame plumbing, not congestion control).
- **`payloadHash` in the TS fallback's reconstructed `OperationEnvelope`**: a non-cryptographic
  FNV-1a-style placeholder (`placeholderPayloadHash`), not a real blake3 hash — confirmed via grep
  that this field is never actually read/verified anywhere in the JS side (it's carried only for
  shape compatibility with the postMessage `OperationEnvelope` type), so adding a real blake3 JS
  dependency just to fill it wasn't justified. The Rust side (native + wasm) does compute a real
  hash via `semio_framework_hash::hash_bytes`.
