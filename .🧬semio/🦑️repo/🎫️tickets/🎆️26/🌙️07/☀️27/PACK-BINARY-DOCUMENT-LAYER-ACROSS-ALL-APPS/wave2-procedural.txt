2. DocumentPack IMPL — MANUAL, NOT AUTO-DERIVED (important deviation for wave 3 to know)
--------------------------------------------------------------------------------
Procedural2dDocument/Procedural3dDocument do NOT carry `#[derive(dsl::DslDocument)]`
themselves (the flow_core/protocol field types are foreign to this crate — orphan rule).
They already manually implement `vcs::DocumentDsl` by delegating to a same-crate, DERIVED
`Procedural{2,3}dDocumentDsl` structural-twin type (`//#region 🔖️DslMirror`), converting at the
`parse_dsl`/`print_dsl` boundary. Since dsl_derive's `DocumentPack` impl is only emitted for
the type actually wearing `#[derive(dsl::DslDocument)]` (i.e. the twin, not the real document),
`Procedural2dDocument`/`Procedural3dDocument` got NO automatic `DocumentPack` impl from wave 1's
derive rollout. Added one manually in each crate's `//#region 🔖️Dsl`, immediately after the
existing `impl vcs::DocumentDsl` block, following the exact same delegate-through-the-twin
shape:

    impl vcs::DocumentPack for Procedural2dDocument {
        fn encode_pack_with(&self, options: &vcs::PackEncodeOptions) -> Result<Vec<u8>, vcs::PackError> {
            <Procedural2dDocumentDsl as vcs::DocumentPack>::encode_pack_with(&procedural2d_document_to_dsl(self), options)
        }
        fn decode_pack_with(bytes: &[u8], options: &vcs::PackDecodeOptions) -> Result<Self, vcs::PackError> {
            let parsed = <Procedural2dDocumentDsl as vcs::DocumentPack>::decode_pack_with(bytes, options)?;
            procedural2d_document_from_dsl(parsed).map_err(vcs::text_error_to_pack_error)
        }
    }

(same shape for Procedural3dDocument/Procedural3dDocumentDsl). Any other wave-2 family using
the same "local DSL mirror twin" pattern (the report calls out fem_2d and imperative_core as
sibling users of this pattern) will need the identical manual `DocumentPack` impl — it will NOT
appear "for free" just because the twin type derives `DslDocument`.

4. BLOCKING FINDING — confirmed pre-existing bug in pack/value/rs (OUT OF SCOPE to fix; pack/**
   is off-limits for this family) — needs a dedicated fix before this one call can be added
--------------------------------------------------------------------------------
`dsl_round_trip_sphere_cut_with_torus_fixture` (procedural/3d/rs/lib.rs) is the ONLY fixture
test in this family whose `#[dsl(table)]` collection field has non-empty rows with a
`#[dsl(block)]` nested record column made of mostly-`Option` fields — concretely,
`Procedural3dDocumentDsl.widgets` contains an `output-preview` widget whose `preview:
Vec<DictEntryDsl>` table has 2 rows, and `DictEntryDsl.value: ValueDsl` (6 mutually-exclusive
`Option` fields: null/bool/int/decimal/text/dict) has only ONE of those 6 set per row. Calling
`test_support::assert_dsl_pack_equivalence` on this fixture's parsed projection panics:

    thread '...' panicked at vcs/rs/lib.rs:3406:...:
    pack decode failed: schema error: missing field 'null' at 1:1

Root cause traced to `pack/value/rs/lib.rs`'s `decode_table_soa` (around line 1112-1119): its
fallback (non-primitive) column branch decodes each present cell with
`decode_value(reader, None, ctx, depth + 1)` — `spec: None`. Compare `decode_record_fields`
(same file, ~line 672-696), which backfills every spec-declared-but-wire-omitted field as
`FieldValue::Absent` — that backfill loop is driven by having a `RecordSpec` in hand.
`decode_table_soa`'s column decode has NO `RecordSpec` available (by design — a `TableSoA`
column is only tagged with `field_id`/`presence`/`elem_tag` on the wire, not a full spec, so an
*unknown* Table-shaped field can still round-trip generically). For a *known* nested
`#[dsl(block)]` record column (our case), this means a genuinely-absent `Option` field is never
inserted into the decoded row's `RecordValue` at all — not even as `FieldValue::Absent` — so
`ValueDsl::__dsl_from_record`'s generated `record.get(id).ok_or_else(|| ...)` (dsl/derive/rs/lib.rs
line ~444) fails with "missing field '<name>'" for whichever optional field the derive checks
first (`null`, since it's `ValueDsl`'s first declared field).

Confirmed NOT a bug in this crate's own code: every OTHER fixture/synthetic-widget test in both
procedural/2d and procedural/3d that exercises `Neuron`/`OutputPreview` widgets only ever does so
with an EMPTY `params=[ ]`/`preview=[ ]` table (no rows reach the buggy column-decode branch at
all), which is exactly why those pass. `hexagonal-mushroom-column.procedural3d` and
`rectangle-extrude-volume.procedural3d` were checked and confirmed empty-table-only.

Left the existing `assert_dsl_round_trip` call on this one test untouched (dsl-text round trip
is unaffected — the bug is pack-format-specific) and added a doc comment at the call site
pointing back to this file instead of adding the pack-law call, so `cargo test -p procedural_3d`
stays green. Re-add `test_support::assert_dsl_pack_equivalence(&projection);` there once
`decode_table_soa`'s fallback branch is fixed to backfill spec-declared-but-absent nested fields
the same way `decode_record_fields` already does for top-level/block records.

This is a general engine gap (`pack/value/rs`, not this family's file), so it will affect ANY
other wave-2 family whose DSL grammar has a `#[dsl(table)]` field with a nested
`#[dsl(block)]` record column made of `Option` fields where not every row sets every field —
worth flagging to whoever owns `pack/**` before wave 3 closes this ticket family out.
