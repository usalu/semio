# Replica Target Sharing Error Codes

The replicated m05 attestation at 20:18:09 UTC on November 21 reported 5,072 incoming entries and a lifetime count of 116,430 `blocked-sharing-violation` events. Its five existing failure rows left three report slots. The aggregate counts retry events, so its value does not represent 116,430 distinct files. The historical receipt cannot separate `EBUSY`, `EPERM` and `EACCES`. None of those codes alone identifies the cause of the rejection.

When a queued target unlink or final rename failed with a recognised sharing code, the replica retry function returned a code-free sentinel at the existing attempt limit. The terminal paths already recorded one generic blocked event and returned the path to the queue. They now pass the observed code with that same event to the resilience tracker. The tracker keeps a count and latest timestamp for each of the three fixed codes for the life of the process. It does not collect paths, operation arguments or error strings for this diagnostic. Staging, cancellation, normal queue cadence, retry limits, worktree-subset accounting and generic failure totals continue through their existing paths.

The schema declares the supplemental kinds `blocked-target-sharing-ebusy`, `blocked-target-sharing-eperm` and `blocked-target-sharing-eacces`. They use the same kind, count and timestamp fields as all current failure rows. They occupy remaining report slots after existing totals, blocked reasons and the ordinary incoming subset. Saturated reports can omit some or all code rows. The attestation and replica status health readers each enforce closed failure rows. An extra field inside a row would invalidate a report on a running reader with the current schema. The fixture checks the emitted rows against those exact two consumer schemas and the resilience schema. Existing verified trust and publication decisions use the unchanged general totals.

Before the implementation, the language-neutral fixture’s independent Python oracle passed while the production tracker and injected target unlink and rename tests reproduced missing code evidence. The fixture covers mixed codes, an uncoded generic event, another blocked reason, limited report space and recurrence-key eviction. The replica tests exercise three deletion outcomes, incoming put retry timing using a SQLite oracle, a Git target rename and a private stage failure outside this aggregate. The new rows describe only observations made by the running code after it is adopted. This audit made no deployment or m05 process or filesystem changes.

The three native test suites for resilience, replica races and fleet attestation passed 210 tests with 2,946 assertions.
