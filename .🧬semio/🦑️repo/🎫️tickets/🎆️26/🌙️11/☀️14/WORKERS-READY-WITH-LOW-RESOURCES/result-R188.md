## 2. Model (decision)

Options measured or costed:

| option | cost | verdict |
|---|---|---|
| (a) pin by clone of the declared inputs | macOS APFS `cp -c -R` on this loaded machine (load 36-43): 2 500 files 2.6 s (copy 4.2 s, hardlink 3.0 s); 30 000 files 17 s (copy 47 s, hardlink 27 s); bytes 0 for a clone. The needed set for a cargo task is small: the 509 member manifests+shims average 2.4 files and 2.9 KB each (1.2k files, 1.5 MB), plus the exact `sourceInputs` of the closure units, `Cargo.lock`, manifests, toolchain file. Linux: btrfs/xfs `cp --reflink=always` (FICLONE) same shape as APFS; ext4/tmpfs have no reflink: a hardlink would NOT pin (an in-place write by a peer changes the inode) so copy (bytes of the closure, a few MB, seconds). Windows: NTFS has no clone, copy; ReFS/Dev Drive block clone (FSCTL_DUPLICATE_EXTENTS_TO_FILE). | right end state, NOT done: the cargo path runs in the live root (`policy.cwd`, `authority.repositoryRoot` equality, `requireNativeStoragePathV1`, `cargoBuildOwnerAliveV1`, source boundary, build directory) and a relocated root needs the offload determinism law (`--remap-path-scope`, trim-paths) wired through about ten guards; that is several landings, not provable without the slice lab. The one place where a pinned view already exists (check 10, Rust unit snapshot) is contradicted by its own live re-reads |
| (b) detect and rerun | exists (check 5): 4 attempts, 2/8/30 s. The defect was the cost of a rerun, not the rerun: a changed lock named a new, empty target directory | kept, made cheap by (c) |
| (c) tolerate | read tracing is not needed: the build depends on a computable projection of the files it reads. A cargo build reads the whole `Cargo.lock` but its result depends only on the rows of the packages reachable from its roots plus the header; the root `Cargo.toml` is read whole but a new workspace member is one line of `members`, and the compilation plan, rechecked on its own (check 2, 4), decides whether the closure moved. Read tracing would need an interposer per platform (dtrace/fs_usage on macOS needs root, strace on Linux, ETW on Windows) | CHOSEN |

Chosen: fixed identity at start + projection of the volatile inputs onto what the build depends on + the existing bounded warm rerun for a real change. Concretely `P/🦀️cargo-workspace/🔒️lock/📐️closure/` (schema `🧬️schema/🔣️.json`: Protocol, Projection, Roots):
* `projectCargoLockClosureV1` / `cargoLockRootsV1` / `observeCargoLockClosureV1`: the recipe key and recheck of `Cargo.lock` use header + closure rows + non-package sections; anything not a closed lockfile, a root the lock does not name, a dependency it does not resolve, CRLF, non-UTF-8 -> the digest of the bytes (so never finer than the file).
* `projectCargoManifestV1` / `observeCargoManifestV1`: `Cargo.toml` by its parsed value without comments, formatting, key order and `workspace.members/exclude/default-members`; a file that does not parse -> bytes.
* `cargoRecipeInputsV1` is used by `cargoArtifactTargetRecipeV1` (N:274-279). Effect: a lock or root-manifest edit that adds, removes or edits a crate outside the closure keeps the target directory (rerun not needed, and if it happens it is warm: cargo's own freshness decides), passes the three rechecks and the final one after the compile. A real change of a closure row, of the header, of a dependency or profile in the root manifest, or of the package's own manifest raises a concurrent `input` edit of the `build` layer: named, bounded (4 attempts, 2/8/30 s = 40 s of pauses plus the replan), EN and DE text on exhaustion, restartable exit.
* the identity published for the task stays the Nx hash taken at start; the plan identity (check 2) and completed Source digests (check 4) are untouched, so a real edit of a closure source still reruns and the published result is the one of the inputs it was built from.

## 3. Laws (`P/🦀️cargo-workspace/🔒️lock/📐️closure/🧪️tests/🟦️.ts`, 18 tests)

Run staged (bun preload substituting the staged files, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0`), then under the lock. Red on the old tree: the module does not exist (import error), and the source-shape law fails on the old `native-build/🟦️.ts` (`expect(...).toContain("cargoRecipeInputsV1(")`); the real-build law's control (byte-exact observation) reruns.
* projection: schema validity; exactly the reachable packages; unrelated rows edited/added/removed/reordered leave the digest; eight kinds of closure/header/trailer change move it; eight whole-file fallbacks equal sha256 of the bytes.
* independent oracles: Cargo itself (`cargo metadata --offline --locked` closure of a synthetic workspace equals ours, before and after `cargo generate-lockfile` rewrote the lock for an unrelated member, and after a real closure change); `Bun.TOML.parse` closure equals ours on a hand-written lock and, for 40 sampled of the 500+ path packages of the REAL `🧰️framework/Cargo.lock`, none of which falls back (3.9 s); `Bun.TOML.parse` of the REAL 141 KB root manifest without the member lists gives the same digest as ours, and a new member line leaves it (parse 2 ms).
* cargo oracle for a new member: Cargo's closure of the built package is unchanged by a new member, and so are both projections; changing `resolver` in the manifest is refused with a concurrent edit.
* witness: passes while the closure holds; closure change -> `ConcurrentEditErrorV1` reason `input`, path = lock, rank = build rank - 1; vanished -> `vanished`; torn read read again after the declared 25 ms pause (fake sleep, 2 pauses), never settling -> `bytes` after 3 pauses.
* recipe: unrelated lock edit keeps the recipe key (sha256 of `cargoTargetRecipeCanonicalV1`, i.e. the target directory name), passes the recheck; the byte-exact observation it replaces fails on the same edit and changes the key; a closure edit changes key and fails the recheck; a new member in manifest and lock keeps the key; the package's own version bump changes it.
* bound with a fake clock: a moving closure reruns exactly `maximumAttempts` (4) with exactly the declared pauses (2000, 8000, 30000), no quiet-wait read for `input`; at exhaustion the error names the lock, carries both languages and `attempts` 4; sum of pauses = sum of the profile.
* REAL cargo build (offline, own target dir, `-j 1`, `build.rs` sleeping 2.5 s): while it runs the lock is rewritten every 250 ms (more than 3 times) and the closure source is rewritten with its own bytes: 1 run, key equal to the key of the inputs read at start, rlib built, published source digest = start digest. With one real edit of the closure source (adds a function) mid-build: 2 attempts, published digest = the NEW source. The byte-exact control: at least 2 runs and a different key.
