# R112: why `authority` and `observe` are huge in a read, and the file-hash fix (landing state at the end)

Scripts: `☀️13/FLEET-ONE-MACHINE-SHARED-HOT-CACHE-AND-REMOTE-EXECUTION/🧰️scripts/R112/` (`look.ts`, `patches.mjs`, `land.mjs`, `restore.mjs`, `battery.sh`, `window.sh`, `compare.py`, test source `stretch-verdicts.test.ts`). Server pid 7338 and its children were only read.

## 1. Baseline and explanation (measured)
Server log of pid 7338: `flow-extension-logic-rust authority=47558ms`, `dictionary-rust observe=107858ms`; the same log shows one starved sample "blocked 47613 ms" at 03:36:23. `authority` is the time `inferProject` spends before `observeProjectInferenceV1`: `projectAssemblyAuthorityV1` of a native owner, computed SYNCHRONOUSLY on the parent thread (`memoizedObservedComputationV1` requires a sync compute). The first native owner (logic-rust) pays for all of it, the others (dictionary-rust: 369 ms) hit the memo; every other owner's `observe`/`refs` is a wait for the one event loop behind that block (92 s `resolve-closure-refs` lines at 03:36). So: CPU in the parent for the authority owner, waiting for everyone else.
Own child (`bun --cpu-prof`, same step for logic-rust): 53 % of all samples in `ownerJobV1 > projectAssemblyAuthorityV1 > compute@native-manifests > memoRowsHoldV1 > projectObservationHoldsV1 > fileFact > readFileSync`. Counted with a preload: 89 953 file hashes (262 MB) for 578 distinct files; `🧰️framework/Cargo.toml` hashed 579 times, crate manifests 506 times. Cause: a memoized computation re-verifies its stored rows on every hit; the verdict memo is keyed by the validation round or the enclosing scope, and outside a round every hit (579 crates, each in its own nested scope) hashed its ~80-155 rows again, and `projectObservationHoldsV1` hashes the file even when the stat fast path already agreed.
Authority step of that owner, own child: 7.4 s CPU / 16-21 s wall before.

## 2. The fix (LANDED 2026-11-17 05:30:00-05:31:11 UTC, GREEN; 04:30 try restored, 05:00 lost the lock)
Correction: only (b) landed. (a) the per-stretch verdict memo broke the standing law of `🔂️validation-round` (an edit between hits must be seen at once without a round) and was dropped; the test file now has 4 tests for (b) only (CPU per owner after the first under 50 ms in one stretch and in separate stretches, edit seen, same-size rewrite seen).
`👁️observation/🟨️.mjs`: (a) `stretchRoundV1`: verdicts of rows and of stored row arrays are shared by all looks of one synchronous stretch when no validation round exists (cleared by `queueMicrotask`, so an await ends it); (b) `fileShaV1`: content digest of a live-disk file remembered by path + stamp (size, mtime, ctime, ino), never for stamps younger than 2 s, used by `fileFact` and by the restamped-file branch of `fileFactHolds`; a write always moves ctime.
Measured (own child, logic-rust, authority step): 7 490 ms CPU / 21 s wall -> 433 ms CPU / 1.5 s wall; file hashes 89 953 -> 578 (one per distinct file).
Take-style look of all 115 owners of the newest wave that have a stored record (`look.ts`, shared pass, no derivation, authority included, same machine, load 40): before 2 977 ms CPU per owner, 0.26 owners/s = 15.7 per minute (settle 327 s CPU, jobs/authority 59.9 s CPU); after 698 ms CPU per owner, 1.04 owners/s = 62 per minute (settle 65 s CPU, authority 1.6 s CPU). Only 115 owners of the 4 479 have a record in a form the harness can look at, so "200 owners" could not be run; the figures are per owner, scale linearly. Harness caveat: all jobs are built in one stretch, so (a) helps it more than the server, where each owner is its own stretch; (b) carries that case (unit test below).
