## 1. Executable bit in sealed code
Schema `🛡️resilience/🧬️schema` `SealedFile.executable` (required, no compat). `sealCodeV1` records the bit and writes the seal copy with that mode; `publishCodeSnapshotV1` writes the store copy with it; `companionsCurrentV1` also compares every bit, so a `chmod` alone (no digest change) re-seals. Kit (`🥾️provision/🟦️.ts`): `KitFileV1.executable`, kit files written with the mode, `verifyKitV1(kit, snapshot)` names "execute bit differs at ...". `🐚️.sh` overlay parses `"executable":true|false`, restores the bit on added, replaced and byte-identical files, both directions; a seal without the field is "not intact" and the checkout stays. `🔵️.ps1` validates the field and chmods where the OS has a bit (PowerShell 7 on unix); on Windows the bit stays in the manifest/staged mode (not representable on NTFS).
Tests: resilience fixture + Python oracle (`executable` in the language-agnostic store case), "a seal records the execute bit ... a chmod alone makes the seal stale"; provision "the overlay restores the sealed execute bit ..." (3 directions), "an old seal without the field is not intact", kit bit + drift test. All green.

## 2. Sealed cross-group transport (`🌐️remote-cache/🔐️sealed`, schema first)
- Keys come from the existing fleet identity: the Ed25519 `origin` key of `<peer>-server` is converted (u=(1+y)/(1-y)) to X25519; nothing new is published. Asker: one-time X25519 key; HKDF-SHA256; AES-256-GCM; AAD binds group, timestamp, nonce. Reply keyed from both one-time keys and the request hash (forward secret, bound to its request). Inner request keeps the normal signature, so roles are unchanged. Replay: envelope table (one-time key + nonce, 60 s skew) plus the verifier's own nonce table. No new library (`node:crypto` only).
- Policy (schema value, `access.transport`): `crossGroup` is always `sealed`; `inGroup` is `sealed` (default when absent: clients seal by themselves from the facts `cache.transport`) or `trusted-lan`. The committed topology rows say `trusted-lan` explicitly, so the live group behaves as today. Server refuses a foreign plain request with 403 "sealed transport required"; `GET /status` shows `fleet.transport`. Direct peer transport in the cache sidecar now seals; key from `links.<peer>.serverKey` pin, else the peer registration in the mounted/relayed store (self-signature checked), else 503 `server-key-unknown` (a plain miss).
- Proofs: vectors validated by the schema; independent Python oracle (stdlib only: Ed25519, Edwards-to-Montgomery, X25519, HKDF; checked against RFC 8032/7748 vectors) derives the same keys and IVs; ciphertext opens with WebCrypto AES-GCM using the oracle keys; X25519 secret equals the OpenSSL CLI one. Law tests on a loopback TCP tap: the observer sees `POST /v1/fleet/sealed` and none of blob bytes, digest, path, project name, `Semio-Fleet`, origin ids (control: the same observer reads a plain in-group request); a flipped byte in either direction is refused and nothing is stored; the recorded message replayed gets 401 and nothing is served. Plus tamper, wrong server/group, clock, size bound, reply bound to its request.
- NOT covered: message sizes and timing; the relayed route (trusted mount, files readable by mount holders); first sight of an unpinned peer server key; the scheduler/gRPC path is not sealed: a foreign `submit` is now refused there (the R12 gate test was changed accordingly) until a sealed client exists, so cross-group remote execution (R12 gap) stays closed. In-group `sealed` mode covers the cache server only. Not run over two real networks.
