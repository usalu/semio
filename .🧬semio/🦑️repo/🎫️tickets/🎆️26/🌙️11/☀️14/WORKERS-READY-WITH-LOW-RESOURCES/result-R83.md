## 1. Problem 1: g1-m05 stalls on a reused pid and the stall rule never fires

Cause found in `origins/g1-m05/ready-log-tools.txt`: the normalisation of R74 replaced `N s` spellings only. The activity lines `"elapsedMs":1.19…` (floats, and integers such as `44`, `0`) were new lines for ever, so `readyStallTrackerV1` saw progress every few seconds. Replaying the real mirror of that log (101 lines, a look every 5 lines over the last 60) through the tracker of `T/🧰️scripts/R83/`-style scratch code: old tracker 20 of 20 looks show progress, new tracker 4 of 20 (the first sight of each distinct line, the last at look 10; the distinct set is finite: the sweep report lines `1 idle databases` and `5 settled claims` each count once), so the stage is stopped 10 minutes after it.

Changes (`S/🌲️process-tree/🧬️schema/🔣️.json`, `🟦️.ts`):
- `normalisePatterns` now remove every elapsed-time spelling: seconds/minutes/hours with a unit (`h`, `hours`, `Stunden` added), JSON members named like `elapsed`, `waited`, `since`, `duration`, `uptime` or ending in `Ms`/`Milliseconds`/`Seconds`/`Sec` (integers and floats), any other JSON member holding a fractional number (a counter is never fractional), epoch milliseconds. Counters stay: `N of M`, `javascript-selected-payload:48022` versus `:48054`, `completedOperations`.
- New `readyHolderWaitTrackerV1`, `readyHolderRestartV1`, `readyCodeChangedSinceV1` and policy numbers (`holderWaitPatterns`, `holderWaitRestartMilliseconds` 600000, `codeCheckMilliseconds` 60000, `codeRoots` = `🧰️framework/🔨️modules/🏃️process` and `LIB/⚡️caching`, extensions, skipped folders). A stage that waits on a named holder (`holds the dependency store since`, `waiting for it (`, `waiting for the holder|lease`) for 10 minutes while ANY source file below the code roots was modified after the stage started (metadata only, first hit, once a minute) is stopped with its whole process tree and started again at once. New refusal `stage-code-changed`, new reason `code-changed` (both languages in `🧬️schema`), no failure, no attempt, no back-off, mirror `ready-log-<stage>-stalled.txt`, timing outcome `stalled`.
- `S/🟦️.ts`: `runReadyStageV1` tracks the holder wait next to the stall tracker and reports `codeChanged` (the file); `runReadyV1` maps it to the refusal and the next start's reason.

Laws (red before, green after; BEFORE run of `land.py` on the old code is in `T/landings.md`):
- `🌲️process-tree/🧪️tests`: fixture rows with the real m05 lines (resource with `elapsedMs` floats plus `still working after N s` plus `waiting for it (N s of at most 21600 s)`: fresh only at the first sight; `lease-sweep:*` with integer `elapsedMs`; `(shared, 1300 s)`, exponent floats, epoch ms, ISO stamps), the negative `javascript-selected-payload:48022 -> :48054` is progress while `48022` with a new elapsed value is not, 40 looks of the real shape give one fresh look; holder cases (9 rounds incl. reset by a round without a holder line and 599999 ms versus 600000 ms); the Python oracle (`🐍️.py`) derives the stall verdicts and the holder waits again from the schema patterns; `readyCodeChangedSinceV1` on a real temp tree (old file, newer file, skipped folder, other extension, missing root).
- `🧪️tests` (ready): loop law for `stage-code-changed` (no failure/attempt/back-off, refusal and reason EN+DE, next start reason `code-changed`); real-process laws with a fake `repo`: a stage printing only `elapsedMs` floats is stopped as stalled after the (shortened) limit, one whose resource counter grows is not; a stage waiting on a holder is stopped with `codeChanged = code/b.ts` only when a file changed after its start, unchanged code lets it wait to its normal end.

## 4. Not verified / notes

- The stall rule and holder restart were proven with fixtures, a Python oracle and fake-`repo` processes on macOS; Windows `taskkill` of the stopped tree is R74's code, not re-run here.
- `codeChanged` uses file modification times after the stage's own start, not content: on a busy fleet some file below the code roots is nearly always newer, so a stage that waits 10 minutes on a LIVE holder is also restarted (it then queues again). That is the requested trade (new code may know the holder is dead), costs one restart per 10 minutes of wait.
- g1-m05 is not unblocked: see section 3 (holder 91672).
- The relief before a create only looks at the volume's free bytes; a quota (EDQUOT) is invisible to `statfs`, there only the reactive relief after the failure helps.
- Which filesystem of g1-m04 has the quota, and whether it is offline: see section 2; needs a person at the machine. Not seen: a real EDQUOT from the real machine through the new code.
- A stage that was adopted by a restarted `ready` child counts the 10 minutes from the adoption, not from the real start of the wait.
