Status: LANDED 2026-11-18 01:00:00 to 01:01:16 UTC (76 s under the lock, entry in landings.md). Running services load the old code until restarted.

## 1. What it is, and the arithmetic

- g1-m07 (2026-11-18 00:01 to 00:29 UTC, run 1709 s, `ready-log-workspace-failed.txt`): the Nx invocation of the probes' `build` target runs `prepareNxToolingStorageV1` (`⚡️caching/🚀️bootstrap/📜️script.ts` `runIssued`, once per Nx invocation, progress text "Planning build tool storage" = resource `nx:storage-planning`). It calls `planNxToolingStorageV1`, which sizes the publication of the one SDK the build tool needs: the **Nx SDK** (`@semio-tech`'s `nx` package set, sealed pristine snapshot `.cache/b/t/m/sdk/<digest>`) and its **derivative** (the per-environment copy `nx/<identity>`: copied files of `node_modules/nx`, patches, the sealed source index, the authorizer snapshot and the compiled authorizer program). All three probes (`norm-din4108`, `norm-din4108-rs`, `repo-mcp`) run through Nx, so they need the same single derivative; there is no per-project SDK.
- The formula `nxSdkDerivativeHeadroomBytesV1` (`🎟️capacity/🧮️formula`) charged `snapshot copies (1) x maximumSnapshotBytes + program copies (2) x maximumOutputBytes + inputBytes + maximumIndexBytes + patch + receipt` and refused when that exceeded the **fixed** `maximumPublicationBytes` = 134217728 (128 MiB) of `📋️policy.json`.
- Policy values today: `maximumSnapshotBytes` 100663296, `maximumOutputBytes` 33554432 (authorizer snapshot policy, grown for workspace scale), index 16777216, patch 33554432, receipt 65536. Sum with inputBytes 0: **218169344**; with the real captured inputs of this Mac (262144): 218431488; with the declared maximum input (16777216): 234946560. Ceiling 134217728. So no input at all could pass, even an empty SDK (matches R160: parts at least 218169344 against 134217728). The ceiling was written when the authorizer policy was 24117248 / 8388608 (sum then 108068864 at maximum input); the policy grew, the ceiling stayed a separate fixed number.
- Reproduced on this Mac with the real descriptor values (index of the sealed SDK: 11701 entries, copy-allocated 23171072 bytes at 4 KiB units, `.cache/b/t/m/sdk/e921066e...`, read-only): before the fix the formula throws the exact message (test `📏️artefact-scale` red 6 of 6 on the unchanged tree); the whole need after the fix is 1012633600 bytes (0.94 GiB) = copy 23171072 + (11701 + 64 entries) x 65536 + publication 218431488, under the declared headroom 2147483648. The check happened before looking at whether publication was even required, so every Nx invocation of every machine would have failed here.

## 2. Fix by construction

- `🎟️capacity/🧮️formula/🟦️.ts`: no artefact size is spelled any more. The clone charge is `2 x maximumSnapshotBytes + 2 x maximumOutputBytes + maximumInputBytes`; the derivative charge is the sum of its parts and its **ceiling is the same sum with the declared maximum input**, both read from the authorizer snapshot policy, the derivative schema policy and `📋️policy.json`. `maximumPublicationBytes` is removed from the policy and its schema (the second copy of the same fact), so a grown artefact policy can never again outgrow a separate number. The only remaining refusal of the chain is the declared headroom (`maximumHeadroomBytes` 2147483648 = 2 GiB, also the maximum of the three retention/physical schemas), reached by the real SDK at 1012633600 bytes with a factor 2.
- Typed refusal `sdk.derivative-capacity` (`🏗️build/📖️texts`, EN and DE): "Not enough storage to publish the {derivative} of the {sdk} SDK: it needs {need} bytes, the declared ceiling is {ceiling} bytes and {free} bytes are free on the tool store ...". Raised (a) by the formula (headroom above the ceiling; the planner passes the observed free bytes `facts.bavail*bsize`), (b) by `requireToolingPublicationValueV1` (was `Error("Released managed tooling capacity required before SDK publication: {...}")`, now need = required, free = available) and (c) by the compiler-publication check of the tools module (was `new Error("SDK derivative compiler publication byte ceiling exceeded")`). The existing free-space comparison and the one retry after maintenance (`observeToolingHeadroomV1`, `withToolingHeadroomRecoveryV1`) are reused unchanged; R146's `disk-short` stays the ready-stage check (it guards the stage before the lease, this one guards the publication inside it).
- Laws: `🎟️capacity/🧪️tests/📏️artefact-scale` (8; red 7 of 8 on the unchanged tree, green staged): real descriptor values (11701 entries, 23171072 copy, 262144 inputs) equal an independent SQLite oracle that reads the three policies; the largest declared input; clone charge from the declared sizes; the policy and schema declare no fixed publication number; typed bilingual refusal naming `nx`, `derivative`, need, ceiling and free; no numeric literal of six digits in the formula; no untyped refusal text left in formula, headroom and tools sources. Existing tests brought to the derived numbers (greenfield, no migration): capacity `🟦️.ts` and `📤️derivative/🟦️.ts` oracles and `🔣️.json` corpora, the archive ceiling law. `🏗️build/📖️texts/🧪️tests` scans the formula folder for the new key.
- Before this, the two pure capacity tests (`derivative capacity charges exact captured input images`, `shared-pristine derivative capacity API`) were red on the unchanged tree with the exact message of the wall.

## 3. "Planning build tool storage" repeated

- One planning per Nx invocation (`📜️script.ts` `runIssued`; the `nx` backend `cacheProbe` plans once more). The log tail of g1-m07 shows three repetitions; the origin log has **no per-line timestamps** and the host service log lives on that machine, so the duration of the phase on g1-m07 is not recoverable. Known: the stage ran 00:01:08 to 00:29:37 UTC (1709 s); the planning lines are at the very end, after the last `[repo] still working after 620 s; last phase started: source.served`.
- Each repetition re-did, for the same sealed SDK: authenticated read of the 2 MB index (twice), JSON parse, schema validation of 11701 entries, re-serialization to prove canonical form, and the walk of all entries with a schema validation per file for the disposition (1459 copied files), plus 92 progress/yield steps. Measured on this Mac read-only against the real index at load 46: parse 4 to 5 ms, schema validation 82 to 308 ms, canonical re-serialization 6 to 61 ms, entry walk 218 to 285 ms: **0.3 to 0.65 s CPU per plan, identical every time**.
- Fix (mechanism): new member `🎟️capacity/🧾️sealed-plan` (`sealedSdkIndexV1`, `sdkIndexCopyBytesV1`): the verified index is memoised by sha256 of its bytes plus the snapshot (4 entries), the copy sums per allocation unit in a WeakMap on that verified object; a repeat costs one sha256 of 2 MB. Content-addressed, so a changed byte, another snapshot or another unit is a miss; a cancelled walk stores nothing. The authenticated reads, the lease checks and the progress heartbeat of a first plan are unchanged. Law `🧾️sealed-plan` (5; red 5 of 5 before: module absent): equals the direct loop at two units, a repeat is the same object with 0 progress steps, tamper/snapshot/unit/cancel cases.
- NOT done: the memo lives in one process. If the three repetitions of g1-m07 ran in separate processes only the in-process part helps; a durable receipt next to the index would be the next step (needs a decision on where the sealed store accepts a new file).

## 4. Only the tools a slice needs

There is one SDK and one derivative for all targets, so the three probes plan the same derivative, not three.
