## 6. The `native` stage: what a fresh worker downloads, and whether it is sliceable (read from the code, not run; proposal only)

Source: `🔩️native/🥾️bootstrap/🐚️.sh` (Unix), pins in `🧬️schema/🔣️.json` (`Pins.assets`: tool, version, platform, arch, url, sha256; no byte counts in the pins, sizes below are measured from the copies on this Mac or estimated and said so). The stage is `setup` with no component argument; the script knows only `node` and `rust` as arguments (lines 1330 to 1340), everything else runs unconditionally in this order (lines 1341 to 1363):

| step | what it fetches on a fresh macOS or Linux worker | size | needed by a Go slice |
| --- | --- | --- | --- |
| `ensure_native_toolchain` | macOS: `brew install pkg-config cairo pango` and `brew install --cask font-dejavu` (host-wide, network, may need a password); Linux: packages through apt, dnf, pacman or zypper with `sudo`; then `ensure_user_cc` (a user-local Zig 0.14.1 as C compiler when none) and `ensure_user_pkg_config` (builds pkg-config from source) | brew: hundreds of MB (cairo, pango and dependencies; estimate); Zig archive about 80 MB (estimate) | no (only native C/C++ builds) |
| `ensure_launcher` | builds the Go launcher with the pinned Go: archive `go1.26.9` from dl.google.com | 146 MB installed (measured, `go-pinned` seed), archive about 70 MB (estimate) | yes (this is the Go toolchain) |
| `ensure_node` | Node 24.15.0 `tar.xz` from nodejs.org | about 30 MB archive, about 200 MB installed (estimate) | no for Go; yes for TypeScript owners |
| `ensure_rust_toolchain` | `rustup-init` 1.29.0 from static.rust-lang.org, then `rustup toolchain install` of the pin in `rust-toolchain.toml` (nightly-2026-07-20, minimal profile, components `rust-src llvm-tools-preview clippy`, targets `wasm32-unknown-unknown wasm32-wasip2`) | rustup-init about 20 MB; the pinned toolchain is 2.5 GB installed on this Mac (measured `du`), the download is a fraction of that (estimate 600 to 900 MB) | no (and not for any Go or TypeScript owner) |
| `ensure_dotnet` | the pinned `dotnet-install.sh` from raw.githubusercontent.com, then the SDK 8.0.421 from Microsoft's CDN (global.json) | SDK about 230 MB archive, `~/.dotnet` is 1.8 GB here with three SDKs (the one pinned SDK is about 600 MB installed, measured as `native/dotnet` in the tools partition) | no |
| `ensure_uv` | uv 0.11.6 archive from github.com | about 20 MB archive, 46 MB installed (measured) | no (python and cmake owners only) |
| `repo_bootstrap` | none (installs the command links) | | yes |

So a fresh worker downloads on the order of 1.5 to 2.5 GB through five hosts (dl.google.com, nodejs.org, static.rust-lang.org plus the Rust distribution server, Microsoft, GitHub, ziglang.org, plus Homebrew or the Linux package mirrors), of which a Go slice needs about 70 MB. The Rust toolchain alone is more than half.
This Mac cannot run the stage as it is: `~/.dotnet/dotnet` is a 10-byte stub (R157 wall 63), `dotnet --list-sdks` prints nothing, `ensure_dotnet` does not find 8.0.421 (present in `~/.dotnet/sdk`) and would download the installer and the SDK. Not run, not repaired.

**Sliceable: yes, the script already holds each step as a function; only the argument parser does not expose them.** Proposal (not implemented): `setup [component ...]` with components `native-toolchain node rust go launcher dotnet uv` (today `node` and `rust` exist), default = all (nothing changes for a bare machine); the declared kinds of the slice map to components exactly like the lab's `kinds` table does for `tools` (go: `go launcher`; typescript: `node launcher`; rust: `node rust native-toolchain launcher`; wasm: `rust`; python and cmake: `uv native-toolchain`; dotnet: `dotnet`); the same table must drive both stages (one schema, TypeScript and shell read it: the shell cannot import it, so the component list is generated into a shell fragment or the script gets the list as arguments from the `native` stage entry of `READY_STAGES_V1`, which the sidecar already declares per stage). Per component a digest-keyed marker (version, sha256 of the pin) so a component that is installed and matches is not even probed, and `brew install` only when a component that needs it is selected and only for what `command -v` and `pkg-config --exists` show missing (today it runs `brew install` on every setup, host-wide). The readiness plan (`READY_STAGES_V1`) then carries the component list per worker role, and a slice worker for Go pays about 70 MB instead of 2 GB. Risk: a worker that later receives a Rust owner must run the extra component before its first read; the `tools` stage already does this for tools, so `native` components can be requested the same way by the first stage that notices a missing one.

## 5. Walls (numbered from 80)

80. **Why a Go or TypeScript slice needs Rust at its first command (R159 wall 72): the resident watcher is a Rust binary and its caller opens the Rust toolchain before it looks whether the binary exists.** `provisionNxTools` and `withRepositoryResidentWatcherV1` (`⚡️caching/🚀️bootstrap/🛠️tools/🟦️.ts`), reached from the first command that starts the resident service, entered `withRepositoryCompilerStoreV1` (rustup bootstrap in the tools partition `i/<vers>/rustup-init`, then the toolchain generation) and only inside it `ensureWatcherV1` located `repo-watch` by the digest of its pinned source and compiled when absent. So a machine that already holds the published watcher still needs rustup-init: offline it dies with `Original offline Rustup bootstrap absent`. Fix, landed 00:04 UTC: ask first (`findInstalledWatcherV1`, no compiler), open the compiler store only when absent. Proof by run: with the fix in my frozen root and `repo-watch` (0.7 MB) in the warm set, the first command of the Go slice (`repo-mcp` stage) passes in 59 to 80 s with no Rust step and no download; before, 14 s to the refusal. Test `🏡️resident/🧪️tests/🔎️installed-watcher` (3). A machine without the published watcher still needs Rust once (the binary is built, not fetched by digest): a fresh worker should receive `repo-watch` from the fleet store like the other tools (not done).
81. **One switch for "no network" is also "no install": with `CARGO_NET_OFFLINE=true` the dependency producer refuses (`Original offline producer requires current exact ready generations`) even when the bun cache holds every package.** An offline worker with a warm cache cannot rebuild a generation; the lab lifts the switch for the `dependencies` stage only and guards that stage by the refused registry files plus a refusing proxy (section 1). Proposal: offline should mean "install from the cache, fail on a miss" (`bun install --frozen-lockfile` is already offline-capable with a complete cache); not done.
82. `GOFLAGS=-mod=mod` (a guard of R157) made every Go build of the lab fail in workspace mode (`-mod may only be set to readonly or vendor when in workspace mode`) and would let `go` rewrite `go.mod`: removed, test added.
83. **The dependency store cannot be cloned or seeded as generations; only its cache can.** The partition is a disk image; the lab copies the 3.3 GB `bun-cache` (70 to 82 s at load 45, 8 parallel `cp`) and the stage then really installs from it: `dependencies` 1255 s, 1395 s, about 1250 s in three runs at 16 GB / 8 cores, no download (`downloads.log` empty, registry refused), so a worker with the cache but no generation still pays about 21 minutes. Almost all of it is the ownership walk of the freshly installed store (`Store ownership walk` 0.4 to 1.1 M operations at 500 to 2600 per second, then the receipts), not the install: that is R159 wall 73 and belongs to R162. R168's note applies to a seed of generations (needs `.installed.json` and `.installed.ndjson` derived on the machine, not copied): not attempted, this lab seeds none.
84. **A real `dependencies` stage rewrites every `node_modules` link of a reusable frozen root into the generations of the lab's state, which the end of the run deletes** (the next run then fails at `repo --help` with `exact managed workspace Source binding required`). The lab now gives the root its links back at the end (`relinkFrozenRootV1`, 322 links made again as in the live tree, root `node_modules` rebuilt as a directory of entry links; test `🧊️frozen`). A frozen root outside the real path (`/tmp` is a link to `/private/tmp`) was not the cause of the next wall.
85. **The Go launcher does not read the dependency store where the build writes it (item 3 of the task, found by the failing `tools` stage).** `tools` failed within 0.3 s in three runs (`Unexpected error: exact declared managed workspace generation path required`; by hand: `The dependency namespace .../node_modules is a link to <lab state>/b/d/m/j/<gen>/node_modules, which is no generation of this checkout's dependency store`): `📦️workspace-namespace` computed `generationRoot` as `<root>/.cache/b/d/m/j`, not below `SEMIO_MACHINE_STATE_DIRECTORY`. Every worker with a moved state root fails the first command after `dependencies`. After the same command was repeated by hand with the root `node_modules` link deleted, `repo tools setup toolchains bun go` ran in 12 s (`Provisioning bun 1.4.2`, `go 1.26.9 already matches its pin`): the tools part of the slice is cheap when the partition is warm. Fix prepared with its test (`MachinePath` for the generation root, test red when the root is not moved), proven on a flattened copy; landing in the 02:00 window (see the landing entry) or, when the freeze of 02:05 prevents it, at 03:30.
86. **The launcher of a lab machine was the live account's stale binary**, so no Go change could reach a lab (the `native` stage, which builds it on a worker, is skipped here): the lab now builds the launcher from the sources of the tree it reads with the Go of its home, offline, before the stages (`sliceLabLauncherBuildV1`, test builds a one-file launcher and runs it; at this load about 10 to 20 s).
87. **One download happened in this work and it was mine.** At 01:36 UTC I ran the install script of the launcher by hand with an environment that had no refusing `curl` in the PATH and a home directory that did not exist any more (the lab had already ended: a lab ends at the first stage failure); the script downloaded the pinned Go 1.26.9 archive (dl.google.com, SHA-256 checked, about 70 MB) into `/tmp/slw-z1o7oG/m1/h/.local/share/semio/go` (not the live account), and I deleted it. Rule since: no manual run outside the lab driver; tools are only run through the lab's own environment with the shims first.

### The `tools` stage, measured (wall item 2)
- `repo tools setup toolchains bun go`: 9 to 10 s with a warm partition, log lines only `bun 1.4.2 already matches its pin.` and `go 1.26.9 already matches its pin.`: **a Go slice prepares exactly `bun go`, proven by a run** (before: prime plus the 12 s of provisioning by hand). No step of the real stage (`tools setup all`) is slow in the slice; the one declared step `compiler-helpers` (cap 1200 s) runs only for `names.length === 0`, i.e. never for a slice.
- What a real worker's `tools setup all` costs was not run (it would provision rustup, nextest, llvm-cov, wasm tools, dotnet, uv, python, cmake, chromium and bazel). Mechanism faults in the code that decides it, from reading `runToolchainsSetupV1` (not run): the provisioning is serial in table order (`setupToolsV1` loops one tool after the other; the tools are independent: bun, go, uv, cmake, ninja, nextest, llvm-cov, python, dotnet could be fetched in parallel), the `compiler-helpers` step (cargo helper build, cap 1200 s) runs after all tools and only when the whole table is selected, and the verification of every tool is repeated after provisioning (`verifyToolV1` twice per tool). The first can be proven only by timing `tools setup all` on a fresh partition, which needs the network; not done.
