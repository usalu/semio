## Causes (evidence: g1-m07 round 18 try 1)

1. A lent action backfills past the machine's own waiting command. `admitRemoteExecutionActionV1` (`LIB/🌐️remote-execution/🌡️load/🟦️.ts:89`) asked the host decision for the lent action as a `batch` request. The decision lets a smaller request overtake a head that waits only because of memory (`HC/📏️decision/🟦️.ts:215` region; existing law "a head held back only by foreign pressure never blocks smaller requests"). So with the local cargo `check` requests of 3584 MB waiting ("5 ahead"), lent 1536 MB actions were admitted one after the other, held the memory, and the local request never fit ("1485 MB spare above the 2048 MB floor"). The memory they held also showed up as "unmanaged" in the decision, so the local waiter saw even less room.
2. A machine that had not finished its bootstrap still lent. `checkRemoteExecutionAgentReadinessV1` (`LIB/🌐️remote-execution/🛰️agent/🩺️readiness/🟦️.ts`) asked only for policy, worker key, sandbox; the sidecar (`🛰️sidecar/👷️agent/🟦️.ts`) never looked at `.cache/f/native-bootstrap.done`.
3. The graph governor wait was unbounded. `graphOwnerAdmissionV1` (`LIB/🧠️memory/🟨️.mjs:119-121`) admits a second owner only if `headroom - remaining >= estimate` (and never for an unlearned kind), and the pump (`🟨️.mjs:165`) then polled forever. With the host starved by cause 1 the headroom was 413 MB (then -6, -81 MB) against a learned peak of 465 MB, the single running project itself waited for its own `exec` capacity behind the same queue, so neither side could move: "465 of 413 MB reserved, 1 projects running", no change for 15 minutes. The line also named neither the project nor how long, and printed negative budgets.

## Changes

1. Capacity schema: new priority class `lent` in `Request.priority` (`HC/🧬️schema/🔣️.json`, with description). `HC/📏️decision/🟦️.ts`: a lent request is ordered after every other request (rank 4), never ages into `interactive`, and is refused with `queue-order` whenever any request that is not lent waits in the same evaluation (`localWaits`, set by `refuse`); a local request that is admitted does not hold it back, so lent work takes only capacity the local user is not asking for. `📐️estimates` keeps the class (`hostRequestPriorityV1("lent",…)==="lent"`). No preemption of running actions. The remote-execution admission now asks as `lent` (`🌡️load/🟦️.ts`); new refusal `not-ready`.
2. Readiness: policy `worker.readyMarker` (`LIB/🔣️policy.json`, schema `WorkerPolicy`, default `.cache/f/native-bootstrap.done`). Readiness returns the new why code `bootstrap-pending` (EN and DE sentence, schema enum) before the key check. The agent gets `ready()`: while false every admission refuses with `not-ready`, every load report says `headroom:false` and `bootstrap-pending`, so the scheduler places nothing there; this also holds when a re-bootstrap removes the marker while the agent runs. The sidecar passes `ready:()=>existsSync(marker)` and the join line is bilingual and says the state. The toolchain need (rustc) was already part of the join (`no-toolchain`).
3. Governor (`LIB/🧠️memory`, schema values `waitBoundMilliseconds` 60000, `fleetFallbackMilliseconds` 180000, `fleetAskMilliseconds` 10000, `grantMegabytes` 2048, `refusalExitCode` 75): the wait is measured from the last progress (head enqueued, last admission, last completion). With at most one project running and the head waiting a bound, the smallest pending project is admitted if its estimate fits the grant of one project (`ownerLimitBytes` when declared, else `grantMegabytes`); otherwise every waiter fails with `GraphMemoryRefusedErrorV1` (`code BUILD_GRAPH_MEMORY_REFUSED`, `exitCode 75`, `detail.needBytes/availableBytes/freeBytes`). Zero running was already immediate. With an optional `fleet` port (`GraphFleetPortV1`), after the fleet bound it asks for the pending keys (answer bounded by `fleetAskMilliseconds`, once per stall); owners it takes fail with `GraphOwnerFleetErrorV1`. Waiting and learning lines name project, need, seconds waited and the bound; budgets are clamped at 0. New lines `admittedAlone`, `refused`, `fleet` (EN and DE).

## Consequences the others must know

- A machine without `.cache/f/native-bootstrap.done` lends nothing any more, including this checkout (the group server / developer machines that never ran `native-bootstrap.sh` leave the lending pool until the file exists). Its join line says so in both languages.
- Anyone who builds a host-capacity `Request` by hand may now use `priority:"lent"`; `Operation.priority` (authored operations) is unchanged. Other consumers that switch exhaustively over `batch|interactive` of a request (none found in the repo) would need the new value.

## Log lines a worker must show

- join, ready: `joining <scheduler> ready (native bootstrap done, marker …/.cache/f/native-bootstrap.done), offering rustc for N target(s) / bereit (natives Bootstrap abgeschlossen), bietet rustc für N Ziel(e) an`
- join, not ready: `joining <scheduler> without a worker: this machine has not finished its native bootstrap (<marker>), so it lends no work to the fleet yet / ohne Worker: …` and in the load report `worker.why.code bootstrap-pending`, `headroom:false`.
- governor wait: `graph: waiting for memory headroom (465 of 413 MB reserved, 1 projects running): <project> needs 465 MB and has waited 12 s; after 60 s it runs alone if it fits the 2048 MB one project is granted, otherwise the run is refused with exit 75`
- governor progress: `graph: <project> waited 60 s for 465 MB of headroom (413 MB free, 1 project(s) running) and now runs because it fits the 2048 MB one project is granted`
- governor refusal: `graph: <project> needs 4096 MB but one project is granted 2048 MB here and 413 MB are free after 60 s: refused with exit 75 (try again later or let the fleet infer it)`
