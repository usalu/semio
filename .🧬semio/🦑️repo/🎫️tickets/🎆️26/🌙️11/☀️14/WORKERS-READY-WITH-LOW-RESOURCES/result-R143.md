## Walls (numbered from 30, evidence, status)

30. **A selected read never used the fleet (the reason for `present 0 fetched 0, everything here`, R140 run 5).** `project-nodes/🟨️.mjs` created and installed the fleet port of the owner loop only `if(!options?.ownerAdmission)`, and a read of a selected scope (every `run-many --projects`, every `tasks` selection, so the readiness probes and `workspace:setup`) always has an owner admission. So such a read never looked an owner record up in the fleet cache, never claimed an owner, never published one: run 3 (12 minutes, 52 owners computed): the lab cache server saw 12 CAS GET 404 and nothing else. Fixed (landing 1): the port is opened for admission reads too; the farm, look queue, owner pool and warm pass stay off for them. Law `project-nodes/🧪️tests/🤝️selected-fleet` (red before). After: A publishes all 53 owners (53 action-cache PUT, 53 CAS PUT, 54 claims granted, run 5), a retry of the same read finds 53 of 53 records present instead of computing 52 again (run 4 attempt 2), and B fetches (run 5).
31. **A fresh machine that fetches before it ever stored a closure of one namespace crashes: `ENOENT lstat <graph store>/build-lock-closures`** (run 5, B, 84 s in: "resident service met an unexpected failure"). `missingInventoryNamesV1` treated a missing leaf file as absent but required the namespace directory to exist. A fetching worker is exactly the machine that has none. Fixed (landing 2): the namespace directory may be absent (`inventoryAncestryV1`, `recheckInventoryAncestryV1`); a directory that appears meanwhile is the typed change `BUILD_STORE_CHANGED` (the batch looks again). Law `👁️observation/🧪️tests/🫙️fresh-namespace` (2, red before). The real-store law `🪪️presence` is red before and after (3 pass 33 fail in this environment), so the end-to-end proof of this fix is run 6.
32. **No read of the live tree converges while the build library changes.** Run 3 with `SEMIO_BUILD_TRACE_AUTHORITY=true`: attempt 1 `[graph-retry] reason producer-error` (membership digest before and after differ: the graph members are every `.ts`, `.mjs` and manifest of the 53 owners, 16245 files, and a peer added or removed one), attempt 2 `producer-error` with the fact `…/project-nodes/🟨️.mjs` changed from `ebaae770…` to `17b9c97b…` (the inference module itself, edited by a peer during the read). Run 4: `observed-facts` and `admission` retries. The lab now counts the churn: run 5 saw 30 files below `framework` changed during 11 minutes. Each retry repeats the start phase (source admission, command-source imports, selected-*: 200 to 390 s) while the owners are no longer computed again (53 of 53 present, wall 19 of R140 is gone for admission reads with fix 1). Status: not a defect of the build, a property of measuring on a tree that 20 agents edit; the proof of `ready: true` needs a frozen root (wall 38).
33. **Two machines started at the same moment compute 20 of 73 owners twice (38 percent), the duplicates are not claim races.** Run 4: claims granted 54 (one machine won 52 of them: its claim is held 0.6 s on average, the owners are fast once the shared closures are warm), denied 20 (409); the other machine computed 29 owners and stored 34, taking 27 from the fleet, of which 7 "did not hold here and were inferred again" (A: 5 of 9). Run 5 (B started later): of the records B took, 4 did not hold and B re-inferred them without any claim (the re-inference of a fetched record that does not hold publishes with `head`, never claims: 4 PUT from B, 0 claim POST from B). Two causes are open: (a) fetched records that do not hold in a tree that is the same checkout (churn of wall 32 explains some; a machine-specific observed fact such as a path below the lab's own state root would explain a fixed set: not separated, the disk images that hold the records are detached when the run ends); (b) a re-inference of a record that did not hold is not claimed, so two machines that both find it stale both compute it. Not fixed.
34. **The Rust toolchain is installed inside the read of a Go slice** (run 2: `rustup`, `cargo-nextest`, `nightly-2026-07-20` in the service log, 76 to 104 s of activity `tools` on every machine, because the lab replaces the `tools` stage by `repo --help` and `repository:command` provisions the rest). Status: open; the lab should run the real `tools` stage once and clone it (R137 and R136 list the same).
35. **The start phase (150 to 390 s on a loaded 16 GB machine, repeated for every attempt and service restart) is not shared by the fleet.** The admission memo (`selected/<scope>.admission.json`) and the sealed selected publication are per machine; a machine that fetches all 53 owner records still derives the admission closure itself. This is where R137's scope-keyed generation head would apply: a selected read does not publish or restore a generation (`loadBuildGraphUnpinnedV1` with `baseline:true` goes straight to `loadBuildGraphAttemptV1`). Not done.
36. **A 16 GB machine infers a selected read one owner at a time** ("no memory peak learned for language:typescript projects yet (256 MB assumed, 937 MB headroom), inferring one at a time: repo-cache-reset has waited 0 s for the running project", every run). With the farm off for admission reads the parent computes alone: 52 owners took 150 to 250 s. Open (the farm cannot serve an admission, see wall 30 note).
37. **Service restarts on code change.** Run 4 (22:03) and the other agents' labs: the resident service of the current code replaced the running one while reads were in flight ("the code on this machine changed while the graph service started"), a landing by any agent restarts every lab read. Same cause as wall 32.
38. **Proposed: a frozen root for the lab** (recorded, not built). The reads must not see peer edits: a private checkout of the 53 owners cannot be a plain copy because the facts include directory listings of the monorepo (30288 `readdir` and 36093 `lstat` rows in the closure of repo-mcp) and the tools path of the checkout; it needs a content-addressed snapshot (`git archive` of the closure plus a registry of the same ids) and a service started from it. Until then a step is only provable in a quiet window (`churn` 0 in the verdict).

## Run 6 (B 420 s after A, both after fix 1 and fix 2; the nearest thing to steps 2 and 4)

- A (m1): attempt 1 computed 53 owners (52 PUT, 53 claims granted), its service was replaced by one of the current code during the run (wall 37), attempt 2 found 53 of 53 present.
- B (m2) started at 420 s: its take pass found the 53 records in the fleet and judged 52 of them stale for its tree ("52 stale in the fleet"), fetched 17 that hold, computed 36 itself (25 published, 23 of the fetched records "did not hold here and were inferred again", 53 "not shared" is the counter of records it could not neutralise, see wall 39), and after its own retry (attempt 2 and 3) found 53 of 53 present, 0 computed, 0 stale. The 24 keys that both machines stored are the records B recomputed after 24 files below `framework` had changed (the lab's `churn`: 24, among them Rust test files and the course target): this is a recompute of the owners whose inputs changed, not the same owner computed twice from one tree state. Whether exactly the owners that depend on a changed file are the stale ones was not checked owner by owner.
- Neither machine reached `ready: true`: both are in the retry loop of wall 32 when the timeout (1321 s) ends the run.
- What this shows: (a) the exchange works in both directions (B's 159 + 136 successful GETs, A's 52 PUTs); (b) a machine that starts after another reaches "all present" by fetching or recomputing only what its tree makes stale; (c) the zero-compute, zero-build second machine of step 2 is NOT demonstrated, because the tree changed under both.

39. **B counts all 53 of its own records as "not shared"** (`refused` counter of the fleet port: `neutralRecordV1` could not express the record without the machine root; run 6, B, first attempt; A has 0). A's records were shareable, B's were not, with the same checkout. Not examined (the images with the stored records are detached when the run ends). A record that is not shared is never offered, so a third machine could not fetch what B computed. Open, small to reproduce: `--keep` plus reading the `refused` reason.
40. **The ready path was never run to the `build` target.** The lab runs the `workspace` stage with `--dry-run` (still the default); `--execute` exists now but needs the Go toolchain installed by the real `tools` stage (wall 34) and writes `bin/<mode>/repo` below the live checkout (a gitignored directory; the lab does not back it up). So "the probe's `build` target, then `ready: true`", the remote cache hit of the build target for B and the task hash identity (machine-specific paths or environment) are all UNVERIFIED.
