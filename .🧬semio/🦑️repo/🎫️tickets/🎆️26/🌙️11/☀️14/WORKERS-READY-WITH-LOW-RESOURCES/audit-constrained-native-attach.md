# Constrained Lab Native Image Attach

The cold lab reached its 8192 MiB machine grant and started `repo-mcp`. On 2026-11-21 its first native storage opener had waited more than eight minutes in PID 16438, `diskutil image attach`, for `m1/s/b/l/fixed.dmg`. The APFS lab volume at `/private/tmp/lv-HMuSep` was mounted with `noowners`. The 63 MiB backing existed and the intended mount directory still belonged to the outer device. The exact process sample reported `-[SKDiskImage attachWithParams:error:]` semaphore waits in all 95 observations. Following owned cancellation, the launcher preserved the backing when inventory showed a partially attached child with no proven mount. Independently verified non-forced detach of the two private devices then released 11.48 GB.

The lab launcher had used the default `hdiutil attach` ownership policy. It now requests `-owners on` and verifies ownership on the exact mounted outer path in the current mount table before launching the frozen child. Existing backing and mount identity checks, grant and disk admission, and inventory-based cleanup run on the same paths. The neutral fixture covers owners on, owners off and an owners-on ancestor without an exact mount. The focused test failed before the launcher change. The complete launcher suite then passed 17 tests with 174 assertions, using an independent SQLite model for the admission decision.

Small private APFS probes showed why owners on is necessary but insufficient to conclude the local host can finish the cold run. The same sparse-image configuration mounted with ownership enabled according to `diskutil info -plist` parsed by `plutil`, with distinct device identity and the expected UID after setting mode 0700. The nested canonical attach below this owners-on parent still timed out after 20 seconds. A standalone canonical attach of a tiny SPARSE image also timed out after 20 seconds. A canonical UDIF control created directly on host APFS and sparsely grown from 64 to 160 MiB, with 67,133,440 bytes physically allocated, timed out before mounting after 45.007 seconds. Its post-close native inventory reported no surviving association. These controls reproduce the StorageKit wait without an outer volume or nesting. No alternate attach backend or disk floor change is supported by the observed results.

A separate host-only probe on macOS 27.2.1 (26B131) ran `diskutil image` without a backing image or mount path and timed out at 12.02 seconds. On the same host `diskutil info -plist /` completed in 0.72 seconds and `hdiutil info -plist` completed in 0.06 seconds. The image verb stalls even without an attach request or a repository path.

The production activation guard had checked the mount table only for a modeled repo parent. The first lease image inside the cold outer volume had no modeled parent and bypassed the guard. Every owned image activation now checks its actual hosting mount immediately before accepting the attach. The existing remount guidance applies only if the physical path exactly matches the retained modeled parent; the external-volume refusal directly names the physical mount and requires ownership. The neutral direction test failed before the guard changed. Four focused tests passed with 26 assertions, including a real top-level opener on a private sparse APFS volume independently shown as `noowners` by the native disk information API. The opener failed at the new guard and native inventory had no association with the child backing.

The receiver test had expected an expired borrower to reject terminal close. The old assertion failed in an isolated run under an actual issued Original. The established terminal-release contract accepts the live borrower and captures its exact lease and kernel pin before expiry. After expiry the terminal token can only release that same guard, and body authority expires on schedule. The corrected receiver fixture waits for actual cancellation by deadline, verifies a new callback is refused, and uses independent SQLite exclusive acquisition to verify that the shared guard still exists before terminal close and has been released afterward. No production custody code was changed in this follow-up. The receiver and cleanup-command suites passed 9 tests with 306 assertions under a projected Original, and the dedicated borrower suite passed 9 tests with 49 assertions under its declared Original.

The native storage body currently runs `captureOwnedCommandV1` within `withRequestedIssuedResourceControlV1(bodyControl, 0, ...)`. Zero inherits the original deadline and signal, so activation has no independent shorter deadline. The command machinery joins process-tree close before cleanup. The distinct accepted cleanup budget can settle a proven mount by exact association and retains ambiguous or partly attached images. Introducing an earlier client kill would require proof that the separate native daemon cannot attach after an empty post-close inventory. No new attach deadline was selected in this repair.
