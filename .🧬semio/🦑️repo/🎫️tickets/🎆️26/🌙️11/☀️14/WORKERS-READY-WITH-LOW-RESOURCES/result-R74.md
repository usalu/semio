## 2. Why tries restart, and what "code kept changing" compares

Evidence from the store (`ready-timings.json`, `ready-log-workspace*.txt`): m01/m02 workspace tries do not end every 2 to 5 minutes (runs of 5451 s, 1690 s, 2543 s, 2648 s with exit 75). What looked like restarts is the slice counter `Reading the project graph slice (N s)` of a worker that was cut or restarted inside ONE try (cut level steps on memory growth: "grew to 9931 MB, limit 6553", and exit-75 restarts). Exit 75 of the slice worker is the stale-implementation exit (`🧷️format-stamps` `exitIfStaleImplementationV1`), raised by three comparisons: (a) a declared format stamp whose live value differs from the loaded one (content), (b) a loaded module that no longer parses (a half-written file of a peer), (c) a Source revision (`📥️inputs/🔏️revision` `current()`): its sha256 differs from the loaded sha256 (stat is only a fast path, so timestamps alone never decide). The real defect: the slice worker is not pinned. The CLI (`📜️script.ts` `withImplementationPinV1`) and the host service (`useProcessWideImplementationPinV1`) both commit to the code they loaded ("an edit meanwhile is left to the next invocation"), the worker (`👷️worker.ts`) did neither, so any peer edit of ANY module it touched later ended a running load with 75 and the pool counted three of them as "code kept changing" (m03, four times).

Fixes: `B/🏡️resident/🏗️composition/🌐️host/👷️slice-pool/👷️worker.ts` opts into the process-wide pin and runs the whole load inside `withImplementationPinV1` (a loaded Source edited later never refuses; a module that is half-written at load time still restarts). `🟨️.mjs` (pool): a worker that lived at least 60 s before it ended with 75 started a new count (like the format-stamp protocol), quick ones stop after 3 as before, the total is bounded at 12 (`sliceRestartProgressMilliseconds`, `sliceRestartTotalMaximum` in the resident schema), the error reports the total. Sidecar: the `ready` role restarts for new code without waiting for its stage (`ready.serveDeferralMilliseconds` 0, `sidecarRestartPolicyForV1`): the stage is a detached process that the next child adopts, so a worker whose stage waits for hours gets the new ready code within the quiet period (90 s, at most 10 min) instead of after up to 60 minutes; no new stage starts while the restart waits. The sidecar restart itself was already content-based (closure of the role's files, byte digest, quiet period, bounded 10 min) and the `ready` stage digest hashes inputs only, so a code landing never restarts a running stage.
Laws: resident `🔁️restart` "a worker that lived past the progress time..." (5 long restarts finish, quick ones stop, total bounded), `👷️slice-worker-scope` "the slice worker is committed to the code it loaded" (source-structure law: pin before the first import, load inside the pin; a real-process law of the pin itself was not written), sidecar `🔁️restart` "a ready role restarts for new code even in the middle of a stage..." (and the graph role still waits).

## 3. m06: 2 048 MB reservation waited 1 430 s with 4.8 GB free

Found: (a) the ledger already drops the grant of a dead pid on every read (`readGrants`: `kill -0` plus heartbeat), so "dead grant" is not the cause for dead processes; the hole was a REUSED pid: a live process at the pid of a dead holder kept the grant for the heartbeat limit of 6 hours. (b) The owner pool children are no grants (documented in `ownerPoolHostOfV1`) but they hold the memory and cores the gate sees as used, and `ownerPoolTargetV1` only reserved 25 % of the cores for a waiting request and always kept one child, so the readiness stage's plan reservation waited while the pool kept its children (the pool even drained one child per look and a drained child finishes its owner first).
Fixes: `H/🎫️gate/📖️status` `readGrants` reclaims a grant at once when its heartbeat is older than two beats AND the process at its pid started after the grant was admitted (`hostGrantPidReusedV1`, start time by `ps` etime, never for a live holder that only blocks its event loop). Owner pool: `ownerPoolHostOfV1` reports the oldest wait of the machine's own work (not farm workers, not lent); `ownerPoolTargetV1` returns `children 0, reason waiting` for a request that has waited 5 s to 10 min (older ones were not held up by the children, the pool comes back); the runner drains and SIGKILLs every child 3 s later, so the pool yields within about 5 s.
Laws: `H/🧪️tests/♻️pid-reuse` (dead pid removed, reused pid removed, blocked-loop holder kept, start time of a real process within 2 s), owner-pool fixture (5 new target cases, authored by hand, equal to the Python oracle), sidecar `🏊️pool` host mapping, and the real-process law "the pool yields to the machine's own waiting work" (3 real children, gate request appears, 0 children within 4.5 s, back after it is served; red before: the children never ended within 20 s).
