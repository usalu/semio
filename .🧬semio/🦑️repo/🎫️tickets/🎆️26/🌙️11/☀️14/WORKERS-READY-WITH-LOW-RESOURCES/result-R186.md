## 1. B: is the stage output lost by adoption? No. What was lost, and why

Read from the code (`🚦️ready/🟦️.ts`, `runReadyStageV1`, `🏃️wrapper`):
* The stage already writes its own log file: the supervisor opens `.cache/f/ready/<stage>.log` with `openSync(log,"w")` and starts the detached wrapper with `stdio:["ignore",handle,handle]`; the file descriptor belongs to the stage process tree (shared offset), and the supervisor closes its copy at once. A supervisor restart cannot lose a byte; "adopting" is already only "wait for the pid, tail the file, read the exit file". The record is `running.json`.
* So the lost text of m10 was not lost by the adoption. The stage log itself did not hold it: ready.json.tail, `ready-log-workspace.txt` (the 16 KB window of the log) and the `-failed` mirror all end in the same bytes: a half machine row (`...cargo:artifa`) directly followed, with no newline, by the repo's own `Internal error: Owned Nx invocation failed (1): nx run-many ...` and `repository:command failed with exit code 1`. The other workers' failed logs (g1-m08 04:21: `NX Original process admission closed - first failure: ...`, `Nx run failed: 1 task(s) did not succeed ...`) show what a normal Nx failure prints between the last row and `Internal error`. On m10 that block is absent. The text never reached the file.
* What the supervisor did lose or hide, now fixed:
  1. The `-failed` mirror and `ready.json.tail` took the plain last 20 lines of a 16 KB window. A flood of machine rows (the artifact plan prints about 23 000 rows of ~205 bytes in 5 s) or heartbeat sentences after the failure text would have pushed the text out. New `failureLinesV1`: last 1 MiB of the log, machine rows and heartbeat sentences removed (`failureNoise`), last 20 lines for `ready.json.tail`, last 199 for the mirror, a provenance line first.
  2. The log of the failed try was overwritten by the next try (`openSync(log,"w")`). Now renamed to `<stage>.previous.log` first (one try back, on the machine).
  3. A stage process ended by a signal was recorded as a bare exit `null`/1 (the wrapper dropped the signal). Wrapper exit record is now `{exit, signal, spawnFailed, endedMs}` (schema `Exit`), the runner appends a bilingual line naming the signal.
  4. Nobody could tell which supervisor started a stage and which adopted it. `running.json` (schema `Inflight`) now carries `supervisor`; the mirror's first line says "started ... by supervisor A, adopted by supervisor B at T" (EN/DE).
  5. `nxCloseCodeV1` in `⚡️caching/🚀️bootstrap/📜️script.ts`: `completed.once("close", value => accept(value ?? 1))` turned an Nx child that died by a signal (code `null`) into a plain exit 1, which is exactly what the m10 line `Owned Nx invocation failed (1)` looks like. Now the signal is printed (EN/DE) before the 1 is reported, unless this run itself cancelled.

## 2. Why a landing restarts the supervisor while a stage executes

By design, in `🛰️sidecar/🧬️schema` `Restart.ready.serveDeferralMilliseconds = 0` ("new code reaches a machine whose stage waits for hours at once ... its stage is a detached process that the next child adopts"). R183 is the example: its holder custody and yield only help a stage in flight if the supervisor runs the new code. The restart is therefore necessary when the sidecar closure (the files the ready role imports) changed, and not otherwise; the watch is by closure digest with a 90 s quiet time and 10 min maximum deferral, so one window of landings gives one restart (m10: R183 landed 05:00:00 to 05:01:58, restart 05:02:32, ready.json pid 48109 unchanged until now). The restart did not cause the failure: the stage pid, its log, its process tree and the exit file are independent of the supervisor. What the restart does cost: the in-memory trackers (stall, holder, phase) restart from "now", the peak memory restarts at 0 (`peakMegabytes` 3311 is the adopter's view), and the tail the new supervisor mirrors starts with whatever the log holds. None of it touches the stage. No change made to the restart policy.
