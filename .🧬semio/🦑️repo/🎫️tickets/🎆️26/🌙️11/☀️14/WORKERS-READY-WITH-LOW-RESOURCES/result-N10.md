- **Retention rule now (slot supersession, members `🧹️retention` + `💾️entries`):** entry slot = function, project root, command, cwd, role, name, view, port, entry files (never the inputs/settings). Per slot the newest entry (mtime, ties larger name) is current; an older one goes once the current one is >= 1 h old. Damaged entries go after 1 h. Layers and values are children: pinned while any kept entry names them, removed when unnamed and neither written nor *reused* for 1 h (a writer refreshes the mtime of every layer/value it reuses and no longer trusts its own "written" memory for more than a quarter of the grace). Grace = `closureStoreGraceMilliseconds` 3 600 000 (schema, EN/DE). The count sweep stays as the last resort. Runs: first save of a process when the cross-process marker `ce/collected` is older than `closureStoreCollectIntervalMilliseconds` (10 min), and in `repo cache gc` for every selection.
- **Growth/fullness rule now:** (1) a write that meets ENOSPC runs the same collection with `closureStoreEmergencyGraceMilliseconds` (60 s) and retries once, then fails; (2) a pressed elastic image (free < `pressureFreeBytes`) is recreated 1.5x larger (aligned, capped by `maximumBytes`, host free + own allocation minus the 50 % reserve), the size is kept in `.cache/b/c/elastic-growth.json` so the born image gets it (the reset deletes the receipt); (3) only then the typed refusal.
- **Why it did not grow with 92 GiB free:** the due rule compared `elasticCapacityV1` (need 3 GiB x 400 % = 12 GiB, a static number) with the image (12 GiB): never greater, whatever the host had. And growth is a recreate (raw `UDRW` cannot resize while mounted), which needs a quiescent moment that a busy machine never gives. Now fixed as in (2); the recreate still waits for quiescence, which is why (1) prunes first.

- The reader (`workspace/🟦️.ts` `portableInputs`) now throws an error whose message carries `ENOENT: closure-missing:<key> <namespace> leaf is not on this machine`, the project names (up to 16) in `missingProjects`, and writes `[graph] closure-missing <namespace>/<key> named by <projects>` to the service log, so the next round shows which projects name the leaf even when the heal does not run.
- Other callers of `portableInputs` (`🧭️discovery/🟦️.ts:78`, `📥️load/🟦️.ts:63`) have no heal of their own: the sealed graph document path already treats ENOENT as a miss (it falls through to a recomputation); discovery does not. I did not change them.

## Where the reference comes from (answer to the question)
`portableInputs` reads the tokens `{env:"SEMIO_SOURCE_CLOSURE_<sha256>"}` that sit in the project nodes; the generation fragments of a restored fleet generation carry the producer's tokens. The restore (`restoreGenerationV1`) downloads manifests, indexes, frontier and fragments only; the closure leaves live in the producer's `build-input-closures/` and are NOT part of the 5104 documents. A restored generation therefore names leaves that exist only on the producer. Whether a local leaf with the same name exists depends on whether both trees give the same inventory text (the key is the hash of the inventory of the files, so it is equal only when the files listed and their facts are equal). That a worker with one stale project gets 233 unresolved closures out of 5100 restored projects fits this; I could not read the restored fragments of g1-m01 (not on this Mac).

## What is NOT done (and why)
- **Carrying the leaves with the generation, or refusing a restore that names absent leaves.** The upload records only documents of the generation (`remote-exchange/🟦️.ts`, `generationDocumentPathsV1`) and skips unchanged documents through a memo, so the set of referenced leaves is not known without reading every fragment; adding closure rows (content addressed, so verifiable by their name) means a new row kind in the action result, a read of all fragments or a per-fragment index at upload, and a write path at restore. I did not attempt it without being able to run a restore. This is the real class fix and should be the next package: publish `c/<sha256>` rows for the leaves named by the generation's fragments (dedup by `content.missing`), restore them with `ifAbsent` after verifying `sha256(bytes)==name`.
- **Targeted rebuild of only the owners that name the leaf.** The builder takes its dirty set from the fact plan, not from the request; the only lever that exists is `invalidate` (cold plan), so a leaf that is gone costs a cold plan with reuse of valid inference records. Records that name the missing leaf (project records and derived nodes) are purged in repair rounds 2 and 3, so those projects are recomputed here and their leaves are republished.
- Nothing was run against a worker or this Mac's graph. Tests: load tests 47 + 1 pass (tag, text-only, cause chain, message-only heal through the repair rounds); the workspace reader change is only transpile-checked (no fixture harness for `portableInputs` found).
