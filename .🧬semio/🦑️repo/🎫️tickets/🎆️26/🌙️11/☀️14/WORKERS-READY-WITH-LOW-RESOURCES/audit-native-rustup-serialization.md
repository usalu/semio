# Native Rustup writer serialization

The m11 and m12 macOS native logs reported a Rustup conflict installing `llvm-tools-preview`, including the existing `llc` component path and a nonempty rollback directory. The same symptoms can result from overlapping mutations or existing contradictory material. The mirrors do not identify another writer. Both machines later cleared Rust through normal retries. The m12 third attempt entered .NET provisioning at approximately 01:03 UTC on November 20. The evidence does not establish persistent user-home corruption.

There were three repository-controlled entry points into the effective user Rustup home. The native Bash and PowerShell scripts both install the pinned profile during full and Rust-only setup. The pinned tool setup command independently used a bare `rustup toolchain install`. Passive checks of the Rustup proxy also inherited its default automatic install setting.

The native entry points now serialize through one stable file in the effective `RUSTUP_HOME`. Bash holds an inherited file descriptor and uses macOS `lockf` or Linux `flock`. PowerShell uses a sharing-exclusive file stream and holds it through the synchronous installer invocation. It waits only for filesystem sharing/lock contention, releases the stream in its normal unwind, and propagates unrelated storage errors. No file content or user toolchain needs to be removed or renamed. The file remains in place between acquisitions to keep a stable physical lock identity. The repository's targeted tool setup delegates to the same native Rustup-only entry point. Its passive Rustup probes set `RUSTUP_AUTO_INSTALL=0`.

The repository's separately verified Rust generation lives under the private tools partition, with its own Rustup home and per-generation custody. It does not lock the user profile mutated by the native scripts. Some managed compiler routes already use that generation, while the native profile installation, generic tool verification and some registry executor paths still refer to the user-home Rustup proxy. A verified private generation cannot be reported as a successful repair of the separate user profile. Cold Bash Rust-only setup precedes launcher install. Cold PowerShell Rust-only setup can also precede it, and full Ready bootstrap can reuse an existing launcher with nested repository bootstrap suppressed. The normal retries succeeded without a repair that edits a pre-existing user toolchain.

The real-process neutral test first demonstrated overlap on macOS. The second process entered and left its mutation while the first was held at a gate. After the correction it waited, including through a pathname alias of the same physical home. SQLite independently checked the event order. The test has a Windows-native PowerShell branch using the same corpus. This Mac verified the macOS branch and could not execute the Windows branch. The native toolchain, Bash 3.2, workspace resolution and tool setup suites passed 63 tests with 585 assertions and four Windows-only skips.

The lock coordinates the repository entry points above. An independent writer that bypasses those entries does not acquire it, and the lock alone does not rewrite an already inconsistent installation.

## Physical access and installer lifetime

The shipping macOS utility accepts `/usr/bin/lockf -t N 9` against an inherited descriptor and keeps its file when used in descriptor mode. On Linux the matching port uses the system `flock -x -w N 9`. The open file description owns the lock, including inherited descriptors, so the last holder's exit releases it. A macOS process test used an actual external installer fixture. It killed only the two private bootstrap shells, observed a separate contender wait approximately one second and time out, then observed the next contender acquire after the installer exited. [Apple lockf source](https://github.com/apple-oss-distributions/shell_cmds/blob/main/lockf/lockf.c), [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)

The initial append descriptor unnecessarily required every account to have write access to the empty lock file. A read-only lock file reproduced that failure. The Unix native path now exclusively creates a missing empty regular file and then opens it read-only. Windows creates a missing file or opens the existing file read-only, with the same sharing-exclusive semantics. Both still refuse a file that cannot be opened under the existing account permissions. No user ACLs change. Cooperating accounts with access to the same physical home contend on the same file, also when they reach that home by an alias. Distinct physical homes have independent locks. The POSIX proof uses a local filesystem. Unix network filesystems with different advisory lock requirements need to support the same descriptor semantics to admit the operation. [Windows CreateFileW sharing and access](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Linux flock filesystem behavior](https://man7.org/linux/man-pages/man2/flock.2.html)

Windows retries creation races and sharing/lock contention within the declared deadline and propagates other failures. A sharing-exclusive stream belongs to the process that owns its handle. The Windows launcher now explicitly gives each Rustup process a duplicate of that lock and only its original standard handles via the Windows process attribute list. The child can retain the lock if its PowerShell wrapper exits. The wrapper waits for the actual child and preserves its exit status. This uses the built-in Windows APIs and .NET only. The bridge is a readiness input only for the Windows native stage. [Windows error codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-), [Windows process inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance), [Windows handle-list contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)

Microsoft Roslyn compiled the bridge locally in C# 5 mode. The authored Windows normal-entry test uses a real synthetic executable to hold the lock while its PowerShell wrapper alone is killed, then observes deadline expiry and release. It awaits execution on native Windows. The shared two-process contention test uses the same corpus for both platforms and verifies a read-only lock file, aliases, timeout and exclusive entry order. Ready input coverage uses an independent Python digest oracle.
