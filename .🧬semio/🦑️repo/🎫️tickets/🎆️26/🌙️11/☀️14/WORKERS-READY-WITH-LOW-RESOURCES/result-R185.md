## 1. One mechanism (task 1)

Design: the readiness loop calls the registry's collection when a stage's declared need does not fit; the wait only follows when nothing collectable remains.

- `🌡️host-capacity/🧹️disk-recovery/🟦️.ts`: `collectInOrderV1` (the loop that was inline in `recoverDiskV1`, extracted: registry order, volume read after each collector, a failing or too slow collector never stops the next, cancellation between collectors, progress lines), `recoverNeedV1` (judges by the **need alone**: free >= need, no cushion or reserve of the derived budget, therefore it works on a 1 GiB and on a 4 TiB volume alike; answers `admit`, `refuse` with the largest consumers and their commands, or `fixed-shares` when the volume is unreadable), `DiskLanguageV1` = `en | de | both` and `diskTextV1` (both joins English and German with a slash; used by the collectors, image slack and replica store so that a log line is bilingual). `recoverDiskV1` uses the same loop (19 old tests unchanged and green).
- Readiness `🚦️ready/🟦️.ts`: port `recover({stage, short, signal, report})`, new codes `disk-collecting` (status while the registry runs: "freeing space by priority now ... progress is in the log") and `disk-consumers` (nothing collectable: need, free, and "the largest consumers and what frees each: root (MB): `command`; ..." in EN/DE). The real port builds `realDiskWritersV1` and calls `recoverNeedV1` with `language: both`, cancellation is the loop's signal. Only `space` is collected; an inode shortage keeps the old wait (byte collectors do not measure inodes; not solved, see Open).
- Order that runs for the host volume (`relief: host`, ascending): leaked-staging 60, leaked-images 61, compile-caches 62, stale-waves 40, footprint-logs 41, read-verdicts 42, cas-lru 70, replica-lost 80, replica-store 85 (server only), image-slack 90 last. Image-internal writers (`relief: image`: cargo-incremental, tool-generations, closure-layers, dependency-generations) never run for a host-volume need, because deleting inside a fixed image returns nothing to the host (R172 measurement).
- Law first, red before: `🚦️ready/🧪️tests/💽️disk-recovery` (5 tests): 2993 MB free, 4096 MB needed, fake collectors -> leaked-staging then cas-lru run in order (+800, +600), the image slack never, the stage starts, a bilingual progress line per collector, status `disk-collecting`; nothing collectable -> `disk-consumers` with the five largest roots sorted, each with its exact registry command, EN/DE, no placeholder, collection repeats each minute, the stage starts when space returns; failing collector does not stop the next; cancellation mid-collection ends the loop without starting the stage; a running stage is not gated. `🧹️disk-recovery/🧪️tests/📥️need` (5 tests): priority order and stop on 1 GiB / 238 GiB / 4 TiB volumes, no-op when it fits, unreadable volume, refusal list (five largest plus image slack and store even when small), failure isolation, cancellation, collector over budget cut, EN/DE/both lines. ## 2. The need (task 2)

What the check measures: `statfs` of `.cache` and of `os.tmpdir()`, both on the **host volume**. Verified on this Mac: `.cache` is device 16777234 (`/System/Volumes/Data`), the images are separate devices mounted **below** it at `.cache/b/<p>/m` (`df`: rust image 30.9 GB free inside, 27 % used, while the host has 34.8 GB free). So 4096 MB means host blocks, not image-internal space. They are different quantities: a stage that writes into an image consumes host blocks only up to the image's allocated size (growth beyond its slack); a collector that deletes inside an image helps the image, not this check. The collector that helps the host check is a host-relief one; the image slack (reclaim/retire) is the only way to turn image-internal free space into host space.

Is 4096 a declared estimate: yes. `diskRequirements.workspace` = 4096 MB / 100000 inodes (R146 table, "declared estimates, not measured"). `slice-memory.json` and the R135/R166 numbers are **RAM** (rss, heap, footprint), not disk; the store has no disk footprint of any stage (`ready-timings.json` had peak RAM only). Nothing in the store can derive the number today, so R185 adds the measurement and the rule:
- every successful, non-adopted stage run now records `growthMegabytes` = free space before minus after on the checked volume (schema `Timings`), written into `ready-timings.json` (also in the store);
- `readyDiskNeedV1(stage, runs)`: declared estimate until a successful run is measured; then `max(floor 1024 MB, ceil(max growth of the last 5 ok runs x safetyFactor))`, with the safety factor read from the workspace scale family through `CAS_RESERVE_FACTOR_V1` (2), not copied. `readyDiskShortV1` and the real port use it; the wait/refusal text names the number in use.
- Law: declared without measurement, failed/null/other-stage runs ignored, 1500 MB growth -> 3000 MB, tiny growth -> floor, last five runs only, equal to an independent Python model on 4 cases, and a 3100 MB machine admits a measured 3000 MB stage while the declared 4096 would wait.
- Honest limits: net growth underestimates when a collector frees space during the run (the stage's own gate), so the measured need can only lower a declared one after at least one clean run; on g1-m01 the workspace stage has never succeeded (all runs `stalled`), so its need stays the declared 4096 MB until a run succeeds. Not verified on a worker. Not done: subtracting the slack of the images a stage writes into from the host need.

## 3. In-place reclaim first (task 3)

- `🖼️image-slack/🟦️.ts`: `collectImageSlackV1` has an optional `reclaim(id, signal)` port. For every mounted image above its slack floor in the reclaim profiles (rust, tools, graph, dependencies, products, diagnostics, nx; the inelastic ones too, since nothing is recreated) it tries the UNMAP cycle first; `reclaimed` -> line "Image X: N of slack returned in place by an unmap cycle, nothing recreated; M returned to the volume", the image is never retired afterwards, loop stops at the target; `skipped`/`failed` named (EN/DE) and then, only for an elastic image still needed, retire as before. Cancellation checked right after the reclaim. Without a port the behaviour is the old one.
- `describeImageSlackV1`: slack of reclaimable images counts as bytes; the refusal command is `cache-reclaim-<p>` first (`... or/oder ...cache-regrow-<p>` for an elastic one).
- Real binding: `runImageReclaimV1` spawns `repo run repo-cache-reset:cache-reclaim-<p>` (clean environment, marked as a recovery child, killed with the signal). New script verb `reclaim <partition>` in `♻️reset/📜️script.ts` calls `reclaimImageIfQuiescentV1` (exclusive non-waiting lease, pending retirement refused, bloat rule) and prints one JSON line `repository-cache-reclaim` (`reclaimed` with before/after bytes or `skipped`); seven targets `cache-reclaim-{rust,tools,graph,dependencies,products,diagnostics,nx}` in the project file (dashboard texts EN/DE).
- Laws (`🖼️image-slack/🧪️tests/♻️reclaim`, 6 tests): policy and targets declared; reclaim before retire, reclaimed image never retired, inelastic reclaimed; skipped -> retire for elastic, skip reason named, failed reclaim named; target stop, unmounted/small images skipped, cancellation, legacy path; refusal commands; **real synthetic image** (hdiutil, 384 MB, six "unit" files with sha256, 160 MB filler written and deleted): allocation before > 140 MiB, the collector drives `reclaimNativeImageV1` with the Darwin port, host blocks come back (> 100 MiB), size and inode of `fixed.dmg` equal, image detached afterwards, re-attached the unit files have the **same sha256**. Passed in scratch.
