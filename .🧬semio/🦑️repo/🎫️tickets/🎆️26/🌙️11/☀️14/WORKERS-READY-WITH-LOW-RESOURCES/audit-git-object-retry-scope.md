# Git Object Retry Scope

The current replica applies `.git/` paths and pending staged worktree paths as stage inputs. Its existing 64-per-turn cap limits cooled ordinary worktree retries, not Git objects or staged paths. A low ordinary-incoming sharing counter therefore indicates the repeated failures are outside that ordinary branch; it does not prove they are Git objects, because pending staged worktree paths also use the non-ordinary attempt. No physical queued path or stage prerequisite set is exposed in the mirrored aggregate.

For a known incremental stage with a known base, `stageObjectsForApplyV1` names required loose objects and separates other Git objects. It returns undefined when there is no recognized incremental stage, when the base is pending, or when base evidence is unavailable. The stage application may explicitly request hydration of the other object set when it needs packed or otherwise missing objects. Object deletions retain a separate complete-pack fence.

A bounded ordinary post-stage retry of proven unrelated cooled objects could preserve exact stage priority, but must leave the explicit stage hydration path able to obtain every required object, preserve the undefined-proof fallback, current HLC cooldown and fair eventual retries, and retain the deletion fence. A private regression should cover more than 64 unrelated failing objects, exact incremental stage projection, required packed-object fallback, fairness, cancellation and changed entries. This is a testable source hypothesis, not a demonstrated physical m05 remedy. No state or process was changed.
