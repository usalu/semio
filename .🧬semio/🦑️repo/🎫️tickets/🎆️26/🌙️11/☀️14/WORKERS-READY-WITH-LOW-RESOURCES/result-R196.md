## 1. What was found (verified in code or by experiment)

1. Replica write path (`🤝️shared-worktree/🔁️replica/🟦️.ts:1756-1787`): an applied remote change is written to a temporary file in the store tmp and `rename`d over the target (retry on sharing violation); `:445` and `:3063` the same for state. So the replica never writes a file in place. Local edits (editors, agent `Edit`, `writeFile` truncation) do write in place. Consequence for hardlinks: safe against the replica (a rename replaces the directory entry, the pinned inode keeps the old bytes: law `rename-replace by the replica leaves a hardlinked pin intact`), NOT safe against a local in-place edit. Choice for file systems without clone: copy within a byte bound (independent inode, exactly the start state), hard link farm beyond it within a file-count bound with `verify()` (size, mtime, inode) at the end of the task and the R188 rerun on a difference, typed refusal beyond both (task stays on the live tree). Order and bounds are in the schema (`materialise.strategies`, `maximumCopyBytes` 512 MiB, `maximumHardlinkFiles` 50 000).
2. Cargo path invisibility (experiments on a synthetic two-to-four crate workspace, pinned `nightly-2026-07-20`, offline, own `[workspace]` and target dir): Cargo names a path package by its place in the workspace and fingerprints by relative path and mtime, so a view that keeps the mtime (clone does, `utimes` after a copy) is `Fresh` in a second view of a different path with the shared target directory, with no wrapper. What leaks the path is the compiler output: the repository's workspace already has the answer, `cargo-features = ["trim-paths"]` with a `trim-paths` profile (Cargo remaps the workspace root inside the compiler and keeps it out of the fingerprint). With it the rlibs of a build in a view are byte-identical to a build of another view in another target dir and contain no view path. A path-bearing `RUSTFLAGS` remap is fingerprinted: every view gets its own units (control test, all four units rebuilt). Stable cargo has no `-Ztrim-paths`: the synthetic law needs the pinned nightly and skips without it.
3. Real path: macOS `tmpdir()` is `/var/...`, the compiler records `/private/var/...`; a remapping or trim of the other spelling missed it (found by the first red churn run). The view root is therefore the `realpath` of the views directory.
4. Modification time is the freshness input of Cargo. A new view clones the mtime of the live file, so a rewrite of equal bytes in the live tree (new mtime) would rebuild that crate in the next view. A per-directory ledger (`mtimes.json`, path to digest and time) gives a file the time it had when the same bytes were first pinned and new bytes a time not before the opening. Law (cargo): every closure file rewritten with equal bytes plus one real edit of `tc` rebuilds only `tc`.
5. Unit cache keys (read, not run): the fleet key is portable (`portableRootsV1` with the workspace root from `SEMIO_UNIT_CACHE_WORKSPACE_ROOT` and the cwd become tokens; a unit whose output is not path-clean is keyed on its real paths) and is unaffected by the view path when the profile trims paths. The LOCAL key (`script.ts:113`, `keyEnvironmentV1`) still carries `CARGO_MANIFEST_DIR` raw (`policy.key.environmentNames`), so the local tier does not share across views of different hashes; Cargo's own freshness in the shared target dir does (law above). Proposed (not made, it moves every local key): neutralise the workspace root in `keyEnvironmentV1`. The view sets `SEMIO_UNIT_CACHE_WORKSPACE_ROOT` to its root (`taskViewCargoEnvironmentV1`).
6. Existing precedent: `LIB/📥️inputs/🎯️selected/📦️snapshot` already pins the inputs of Rust unit tasks as an immutable store copy (`{path,digest,bytes}` rows). The view takes the same row shape; R188 check 10 (its live re-reads) disappears when that snapshot is replaced by a view.

## 2. What was built

`LIB/🏞️task-view/🟦️.ts` (schema first, concise, bilingual texts):
* `openTaskViewV1({source,directory,hash,inputs,...})` pins the declared inputs (rows `{path,digest,bytes}` or `{path,link}`): staged beside the final name, first strategy the file system supports (clone `COPYFILE_FICLONE_FORCE` = `clonefile`/`FICLONE`; byte copy within bound; hard link within bound), every file compared with the digest the hash was computed from, published by one rename. A live file that moved between hashing and pinning gives `{kind:"moved",paths}` (nothing published, no lease, no staging): the executor rehashes before it starts, so no compile minute is lost. Typed refusals `too-large`, `path-too-long`, `unsupported` (EN and DE). Progress callback, `AbortSignal` (leaves nothing). A lease file per open view (`.use/<hash>.<pid>.<token>`).
* Content keyed by the task hash: the same hash opens the same view (reuse = manifest compare plus `lstat` of every row, 0.04 s for 2 500 files), concurrent opens publish one, a view that no longer matches its manifest is made again.
* `collectTaskViewsV1` / `selectTaskViewsToCollectV1` (pure): leased and young views never go, idle beyond 6 h go, then least recently used beyond 48 views or 16 GiB logical; race guard (the view is moved away by one rename, the leases are read again, the view is put back if a task took it); only direct hash-named children, never through a link; staging directories older than 1 h go.
* `taskRootModeV1`: the one switch (below). `taskViewsDirectoryV1`: `<machine state>/f/tv` through `machinePathV1` (same volume as the checkout, so a clone is possible; short: the policy refuses a root over 120 characters or a path over 240).
* Registry (R169): writer `task-views` (priority 35, derivable, host relief, collector `age-prune`, command `repo cache gc`) in `🌡️host-capacity/🧹️disk-recovery` schema; `🔌️real/🟦️.ts` binds it to `collectTaskViewsV1` by dynamic import (an unloadable module cannot break `repo cache gc`), measure and collect use the machine-state directory.

## 3. The policy (one switch) and its default

Schema `Policy.executionRoot`: `{environment:"SEMIO_TASK_ROOT", default:"live", classes:{"readiness-probe":"view","interactive":"live"}}`. `SEMIO_TASK_ROOT=live|view` wins over everything (turn back to live without code), then the class of the task, then the default. Default chosen: `live` for everything, `view` for the class `readiness-probe` (the Rust probe, 9 to 24 minutes, where a stage fails on one churn event and a rerun is a cold build). Why not `view` everywhere: a developer who edits and rebuilds expects the live tree, short tasks cannot observe churn, and the view costs a clone plus a digest pass. Nothing calls `taskRootModeV1` yet, so the effective behaviour today is live for all.

* (e) fallback law: injected "no clone" gives copy; beyond the copy bound hard links, in-place edit detected by `verify()`, rename-replace invisible; nothing fits gives a typed refusal EN/DE; a non-capability error (`EIO`) is not swallowed. NOT tested on a real ext4 or NTFS volume (ports injected).
