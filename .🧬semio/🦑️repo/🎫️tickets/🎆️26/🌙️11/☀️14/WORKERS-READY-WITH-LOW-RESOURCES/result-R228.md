## 1. Verified in code (R196 and R198 claims)

* R198's wall is real: `withRepositoryCargoArtifactPlanV1(manifest,args,root,...)` (`LIB/⚡️caching/📦️artifacts/🏗️native-build/🟦️.ts`) takes ONE `root` that is authority check, machine state (`cargoDirectories(root)`, lease dir, store, preparation), source (`path`, `.cargo/config.toml`), published directory and lane crates. * New finding: the machine state of this checkout is INSIDE the checkout (`machinePathV1(<checkout>,".cache","f","tv")` = `/Users/ueli/Documents/semio/.cache/f/tv`). Cargo reads `.cargo/config.toml` of every ancestor of its working directory, so a view below the checkout inherits the repo's `.cargo/config.toml` (and on this Mac `~/.cargo/config.toml`): an undeclared input the view cannot remove. A cargo task therefore needs a state root outside any directory with a `.cargo` configuration; the runner refuses (typed `ambient-config`) instead of silently reading it. Default state root `hermeticStateRootV1` = `SEMIO_HERMETIC_STATE_ROOT` else `<machine state>/f/hm` (will refuse inside this checkout until the variable names a root elsewhere, e.g. under `/Users/Shared`; also keep it under 120 characters).
* Path independence of the bytes on the pinned nightly: with `cargo-features=["trim-paths"]` + `trim-paths="all"` + `debug=false` the binary is byte-identical across two view paths and two target dirs (the repo's profile already trims). `env!("CARGO_MANIFEST_DIR")` is NOT trimmed: such an output carries the view path, and is refused as `path-leak`.

## 2. Built

New member `LIB/🏞️task-view/🧱️hermetic` (schema first `🧬️schema/🔣️.json`: Policy, Receipt, EN/DE Texts; `🟦️.ts` about 290 lines; `🧪️tests/🟦️.ts` 15 tests):

* `runHermeticV1(request)`: pins the declared `paths` as a view through `runOnTaskRootV1` (forced `SEMIO_TASK_ROOT=view`; no view means a typed `unavailable` refusal, NEVER a live run: the caller keeps its existing path as fallback). The task runs with cwd = view and an environment ALLOW LIST (PATH, HOME, RUSTUP_*, TMP*, ... plus fixed `CARGO_INCREMENTAL=0`, `SOURCE_DATE_EPOCH=0`, `CARGO_NET_OFFLINE`), output directory in `SEMIO_TASK_OUTPUT_DIR`. Before the run the view is swept of everything that is not declared (a stray file of an earlier run can never be seen), after it every extra file is `wrote-into-view`. Then: `undeclared-input` (on failure, files named in the output that exist live but not in the view), `read-outside-view` (cargo dependency info of the units compiled in this run: any path outside the view, CARGO_HOME and RUSTUP_HOME, which also catches absolute reads that succeed), `output-unexpected`, `output-missing`, `path-leak` (view, state or live root bytes inside an output), `failed`, `aborted` (AbortSignal kills the child, nothing published). Outputs are published atomically as `<state>/o/<key[0..32]>/` with `receipt.json` (validated against the schema by ajv in the test).
* `hash` = digest of the declared input rows (relative paths, no root in it), `key` = sha256(hash, toolchain identity `rustc -vV`): identical on every machine of the platform.
* `cargoInputClosureV1(workspace)` (declared inputs from `cargo metadata --offline --locked`: workspace manifest, lock, toolchain file, `.cargo/`, per path package manifest, build script and `src tests benches examples`, never `target`; a path package outside the workspace is reported in `outside` and refused) and `runHermeticCargoV1` (`--locked --offline`, pinned toolchain, artifacts named relative to the target dir).
* TS: `runHermeticV1` with a `bun build` command (no cargo specifics).

Independent oracles: Python `hashlib` digest of the output; a plain `cargo build` of a pristine copy in another directory has the same bytes as the hermetic output; a plain `bun build` of a pristine copy has the same digest as the hermetic bundle.

## (5) Registry dependencies from the pinned offline cache: done
`seedRegistryV1`: every registry package of `Cargo.lock` is taken from a `.crate` file of the offline cache (`$CARGO_HOME/registry/cache/*`, or `registryCaches`) whose sha256 equals the locked checksum (the pin), unpacked by an own gzip-tar reader (`untarGzipV1`, no external tar, rejects paths that leave the archive; equals the system `tar` in the law) into `<state>/h/vendor/<name>-<version>` with a Cargo directory-source checksum file, and cargo gets `--config` source replacement. A plain cargo build is NOT an oracle for this case: its registry paths are trimmed to a different spelling (`itoa-1.0.18/src/lib.rs`), the bytes differ by design.
