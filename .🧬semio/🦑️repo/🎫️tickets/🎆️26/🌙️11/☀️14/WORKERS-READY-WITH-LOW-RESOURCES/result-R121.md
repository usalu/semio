## 1. What moved (landed)
- Job `observe` (R114) with `refs: true` (asked only inside a take, with a read-scoped verdict directory and a row log): after the verdict `holds` the child re-reads the record it just judged, checks that the sha256 of its header line is the `headerDigest` it answered, resolves the closure references (`resolveClosureRefsPlanV1`: the resolved project plus a plan of the rows) and files `{v, headerDigest, resolver: pid, project, plan}` as `refs-<headerDigest>` in the verdict directory of the read (tmp + rename). The reply carries the small reference `{path, digest, size, headerDigest, resolver}` beside `verifier` (the process that verified) and `headerDigest`: the record states which process verified, which resolved, against which digests.
- The parent keeps only the reference (`offered`). For the header it read it calls `adoptOwnerRefsV1`: reads the file, removes it, checks size and sha256, parses, and lists the rows in its own row log from the closure store (`closureApiV1(...).adopt`: layers listed by digest through the existing `closureLayerListV1`, once per log and layer; no entry is loaded, nothing derived or walked). Anything that does not hold (no file, other digest, other header, lost layer, no child, layer not stored in the child) resolves in the parent exactly as before; `ownerRefsCountsV1 = {adopted, resolved}` counts both.
- The plan (`closureApiV1(...).plan`) is `resolve` without a log: entry rows, digests of the layers to add, digests of the layers a derived fact stands for, the derived facts; `adopt` replays it in the same order (exclude supports, add entry rows, add layers) so the lists are the ones `resolve` builds. `resolveClosureRefsV1` and the new function share one binding function (`bindClosureRefsV1`).
- 2. Shared reference data: the closure entries are shared per read by the store plus R119 verdict files (a child verifies a shared entry/layer once per round); the layers of the parent's log are listed once per read and layer (memo per log), then every owner adds only ids. The refs files themselves are per owner (the project), the shared part is not repeated in them (digests only).
