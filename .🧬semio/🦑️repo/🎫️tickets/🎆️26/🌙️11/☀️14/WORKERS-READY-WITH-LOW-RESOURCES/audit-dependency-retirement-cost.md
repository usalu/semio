# Dependency Retirement Cost Audit

The m02 tools mirror at the read-only sample showed genuine `dependencies:selected-postorder` work advancing from 229,221 to 230,057. These work units include preflight, descriptor paths and peer checks; they do not time individual operations or establish which operation dominates.

`🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/⚡️caching/💾️storage/🔒️enforcement/📦️budget/📥️opening/📤️publication/🟦️.ts` lines 233–244 first validates the captured payload, stamps, all directory rosters and entries. For every removal it fences the remaining roster, checks the exact entry, calls the actual descriptor-relative removal, checks the parent identity and roster again, checks the removed name and validates every remaining hardlink peer transition. Root boundary calls and receipt-last sync ordering are part of the custody and crash contract; lines 247 onward retain generation and source references. These checks must remain at their current safety boundaries unless an equivalent atomic primitive is demonstrated.

A contained CPU optimization exists at line 243: the current G top-level groups each filter all D directory keys, costing O(G·D) plus bucket sorts. One pass can bucket each key by its first component, followed by the same byte-sorted group order and the same descending-depth/byte comparator within each bucket. Preserve both existing group boundary calls, check/cancellation and exact `processDirectory` ordering. This removes repeated scans without altering a descriptor, roster, peer, source, unlink, rename or durability check. Its likely effect on this particular run is unmeasured; a capsule with one top-level payload group gains little. Sorting depth keys once rather than repeatedly splitting inside comparisons is another equivalent CPU reduction if it retains precisely the same comparator.

Per-removal `matchesNames` can make a large directory expensive and hardlink peer scans can make large alias groups quadratic, but skipping or batching those validations could miss a concurrent peer or rename; this audit does not establish an equivalent safe replacement. Grouping peer visits by parent might reduce repeated descriptor traversal only if each reopened parent remains anchored and every peer is independently checked after each unlink, with cancellation, race and unchanged visitation behavior proven; it is not established as safe or beneficial here.

The private postorder effects and independent SQLite order oracle belong to `⚡️caching/🚀️bootstrap/📦️dependencies/💾️storage/🧪️tests/👓️reading/🟦️.ts` lines 196 onward, including cross-directory hardlinks, cancellation, mutation fences and progress. Receipt-last crash cuts are in `💾️storage/🧹️retirement/🗃️unready/🧪️tests/🧹️cuts.ts`. A change should extend their language-neutral cases and independent order oracle with many mixed-depth top-level groups, byte-order ties, cancellation and exact boundary/order events, while retaining real descriptor and race coverage. No production code or worker was changed, and no benchmark was started.

## Postorder bookkeeping

The postorder effect now assigns each validated child directory to its top-level role during the connected preflight. It sorts each role once using the depth already held by its bound relative descriptor path and preserves the existing UTF-8 byte ordering and boundary calls. The previous scheduler filtered the full directory roster separately for every role and re-split path strings in each depth comparison. The file effect now uses its already verified physical identity and retained peer list directly, avoiding two parses of the serialized stamp per file, the intervening decimal round trips, and materializing a second list of live peers. Every preserved peer is still read and compared against the physical unlink transition. The function still checks the exact remaining directory roster around every removal and syncs the same directories before their parent removal.

The real descriptor fixture checked the complete removal sequence independently in SQLite using role, parent depth, binary path order and the binding receipt position. The baseline passed the exact-order oracle before the optimization. The first candidate passed the selected payload and physical postorder tests with 182 assertions, covering deep paths, internal/cross-directory/external hardlinks, mutated entries and rosters, cancellation, sync failures and receipt cuts.

In nine paired, alternating Bun trials with 7,413 directories in three roles and 58,455 generated file identities, median isolated ordering work fell from 66.149 ms to 27.457 ms. Inode bookkeeping fell from 281.933 ms to 76.066 ms. The independent physical tests establish actual removal semantics. The synthetic benchmark measures only CPU bookkeeping and does not attribute the hours of live tools time to these operations. g1-m02 advanced past selected-postorder work 250,087 under its already running tools command. A new command or an exact physical receipt is required to measure any effect there.

## Full regression

The first full run exposed a stale injected binding port in a separate selected-owner fixture. Its exact error was `ReferenceError: tryRepositoryDependencyBindingsV1 is not defined`. The fixture now uses the current binding and Native volume observation ports and checks the result dispositions independently. [Selected owner fixture](audit-dependency-selected-owner-fixture.md)

Under coordinator load, four existing fixtures encountered Bun's default five-second limit while running owned subprocesses or many real descriptor cases. They now use the corresponding existing build-test laws with explicit cancellation and drain budgets. The seven Store worker variants retain their individual 10-second limits. The parent uses the existing SDK runtime law, whose body is funded for all seven sequential child lifetimes and cleanup. Other laws retain the shorter custody budgets. No production stage deadline changed.

The complete dependency reader passed 99 tests and 143,008 assertions, with seven worker-only test variants skipped in the parent process. The separate unready-capsule receipt-last crash suite passed 41 assertions. The physical lock fixture took 5.09 seconds and the all-scope fixture 16.68 seconds in that run. The closure and cancellation laws now settle these cases before deleting artifacts or closing the shared test birth.
