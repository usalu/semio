## Verdicts

1. **Whose consent is it? Measured on this Mac (macOS 27.2.1, `log show` of `com.apple.TCC`, 20 h):** every Documents access of a semio process was judged against the subject `/Users/ueli/.local/share/semio/launcher/bin/repo` (identifier `a.out`, answer 2/2 = allowed by the user), with `responsible_path` = the launcher and `accessing` = the **bun** runtime that the launcher had replaced itself with. Never was the subject a bun path (6 rows, `scratchpad/P6/tcc.txt`). Processes started inside the agent app were judged against the app (`com.anthropic.claude-code`, 3 rows). So the consent is stored for **one executable path, the launcher**; the bun runtime path (with its content hash) is not what is asked for, as long as the launcher is the first image of the process.
2. **Signatures:** launcher = `Identifier=a.out`, `flags=adhoc,linker-signed`, no team, CDHash `f78030384d62a5ca…` (this Mac). So its consent is bound to path and code signature: **it is lost when the launcher is rebuilt to other bytes**, kept when the sources are unchanged (installer: `go build -trimpath`, `cp`, `mv -f`; Go sources of the launcher last changed 11-13 22:22, so the bytes of g1-m08's launcher were identical in rounds 4 and 5). Bun = Developer ID `7FRXF46ZSN`, identifier `bun`, hardened runtime: a stable identity, but TCC does not use it for these processes. The bun path contains the hash of the pin, so a runtime update changes it.
3. **How the service is spawned:** `spawnHostServiceV1` (`🏡️resident/🏗️composition/🌐️host/🟨️.mjs`): `spawn(argv, {detached:true, stdio:[ignore,log,log]})` from the client process, then `unref()`. No launchd job, no double fork, **no responsibility disclaim**: `strings`/`nm -u` of the pinned bun show `posix_spawnattr_setflags` and no `responsibility_spawnattrs_setdisclaim`. The launcher itself `syscall.Exec`s into bun (`🐚️unix-host/🐹️.go`), so it never stays as a parent. Consequence: the service inherits the responsible process of whoever ran the client (agent app, terminal, controller script), whatever its parent pid is afterwards.
4. **The replica daemon** is a LaunchAgent (`/bin/sh boot.sh run`). Its shim runs `repo` (resolved from `PATH`) only when `[ -d $worktree ] && cd $worktree` works, and **falls through to the cached bun directly** when that `repo` ends within 20 s with another code than 0/75 (`🔁️replica/🥾️entry/🐚️.sh`). The g1-m08 process chains show exactly that: `boot.sh -> bun boot.mjs -> bun supervisor` (rounds 3, 4, 5, pid 75476 -> 75484 -> 75485), while the sample of 12:37 UTC showed `boot.sh -> repo (Go) blocked in open`. So the daemon lost the launcher identity once and runs under the bun path now.
5. **`PATH` `repo` is not the launcher on g1-m08:** every round prints `Another repository frontend is on PATH: /Users/ueli/.local/bin/repo. Installed launcher: .../launcher/bin/repo`. `repo run repo-mcp:install` replaces the link `~/.local/bin/repo` by the native command (`📥️installation/🟦️.ts`, `nativeRepoLauncherLinkV1`) whenever that is rebuilt; `/usr/local/bin/repo` (used by the compact/relay/cache LaunchAgents) points to `~/.local/bin/repo`. So the services of the machine start whatever file that link names: a **new identity with every rebuild of the native command**. The bootstrap also rebuilds and replaces the launcher at the start of every run (`ensure_launcher`).
6. **Why round 4 passed and round 5 failed: not provable from the archived evidence; here is what it rules out and what remains.**
   - Same bun in all rounds (`90987a3a…`), same ancestry for the starting client (`ChatGPT -> codex app-server -> Python -> bash -> bash -> bun repo run workspace:setup`), same detached shape (service wrapper PPID 1 in both: 27987 and 37382). So **not** the runtime, **not** the parent chain, **not** detach versus no detach.
   - Round 3 service (16:57) was before the click (about 17:35 UTC); round 4 service started 17:41:44 (host-f74179f31e9f, implementation e03583e0), 6 minutes after it; round 5 service started 18:00:27 (host-6feebb05efe3, implementation 00f09767) after the build agent had restarted for changed code (17:53:42) and after the bootstrap had again rebuilt the launcher and re-installed the native command (17:59:55 to 18:00:15). The old service (pid 27988) kept running with access, as a process that was granted keeps its decision.
   - Because the service inherits the client's responsible process (item 3) and the foreground `repo` of the same bootstrap was never refused, the two cannot both be judged against the same app unless the identity that counts is the **first image of the chain**, which is a `repo` binary (launcher or the native command in `~/.local/bin/repo`), exactly the dialog the owner saw ("repo would like to access ..."). That identity is bound to its bytes (item 2). The launcher's bytes were identical in rounds 4 and 5; the native command's bytes changed with the Rust/Go sources landed between 17:38 and 18:00. **Most probable: the grant of 17:35 belonged to the bytes that existed then (the native `~/.local/bin/repo` or the launcher), round 4 ran the same bytes (or the install was a no-op), round 5 ran new bytes.** Alternatives I cannot exclude: the grant was given to the replica's `repo` only and round 4 was served by a still-valid decision of another process; or the consent is cached per responsible process lifetime.
   - **One read-only measurement decides it** (not available here, no access to g1-m08): `python3 T/🧰️scripts/P6/tcc-attribution.py --start '2026-11-14 18:35:00' --end '2026-11-14 19:05:00'` on g1-m08 lists, for each consulted Documents access, the accessing process, the responsible executable, the subject and the answer. ## The design (implemented in the payload; all texts EN + DE)

One identity: the **launcher at its install location**. Every long-lived role must have it as first image of its responsible chain; no role may depend on the app that happened to start it.

| Role | Before | After |
|---|---|---|
| Replica daemon (LaunchAgent) | `repo` from `PATH` only when `cd worktree` works, otherwise bun directly | worktree below Documents/Desktop/Downloads on macOS: always the launcher by absolute path, root from `SEMIO_WORKSPACE_ROOT`, no `cd`, **no fall-through to a bun of another path**; `bootVersionV1` 4 -> 5 (the daemons install the new shim after the self-test) |
| compact / relay / cache LaunchAgents | `/usr/local/bin/repo -> ~/.local/bin/repo -> (native command)` | provision links `/usr/local/bin/repo` directly to the launcher on macOS |
| Resident graph service | detached child of whichever client | on macOS, checkout below a protected folder, runtime = the running bun, launcher present: a **launchd job** `tech.semio.repo.service.<hash>` (`gui/<uid>`), program = launcher, arguments = the same `script.ts repo service host run`, working directory = checkout, environment of the client, log = service log; property list written owner-only and removed after `launchctl bootstrap`; `SEMIO_SERVICE_LAUNCHD=off` or any failure -> the former direct spawn; `service host stop` boots the job out |
| Foreground `repo` | first `EPERM` or "unexpected failure" deep in the run | `requestInvocationPlanV1` probes the checkout first (8 s, never blocks: ok / denied / waiting / unprotected), before any service is started or asked; denied or waiting ends with the typed refusal **code `consent`, exit status 4** (the provision script's consent code) and the click, EN or DE; `repo service host start` does the same |
| Service start | bound its socket, failed later on the first request | probes before it binds anything; denied or waiting: log line, typed exit row `access-denied` (state, folder, checkout, implementation tag), receipt, **exit 4**; the client that waits for it reads the row and refuses at once with the same typed refusal (no 60 s "unavailable") |
| Service during a request | refusal `internal/access-denied`, process stayed alive holding the denied state | refusal code `consent` (key `access-denied`), then the service **closes itself** (`access-denied`, exit 4) so the next client starts a fresh one |
| `repo preflight` | only the replica's `access.json` | the `access` check also reads the receipts `service.json` and `client.json` and fails with `worktree-access-denied: these macOS roles cannot read <worktree>: <roles>` + the exact click, EN and DE |
| Provision script | native bootstrap code 4 -> generic "pending" exit 3 | `native_consent`: exit 4 with the click and the identity path |

Texts say: the dialog `"repo would like to access files in your Documents folder"`, System Settings > Privacy & Security > Files & Folders > Documents Folder > `repo` (path of the launcher printed), or Full Disk Access; asked once per machine; a checkout outside Documents, Desktop and Downloads needs none.

New members (schema first): `🏡️resident/🔐️consent/` (`🟨️.mjs`, `🟨️.d.mts`, `🧬️schema/🔣️.json` with the receipt), `🏡️resident/🏗️composition/🌐️host/🍎️launchd/`, refusal code `consent` in the resident schema and `RepoErrorCodeV1` (`repoErrorExitCodeV1("consent") = 4`), 2 + 2 texts in the resident schema, 2 in the build catalog, 2 in the preflight texts.

## Third burst: the consent now survives bootstrap runs (landed 22:0x CET, T lock, 16 files, 2 new)

**Measured:** the Go launcher is byte-reproducible: two builds from the same sources, in different folders two seconds apart, with the pinned Go 1.26.9, `-trimpath -ldflags "-s -w"`, have the same sha-256 (`4dfba362…`), so nothing needed to be made reproducible; with `codesign -s - --identifier tech.semio.repo` the result is also identical (`cf25f2b7…`, CDHash fixed, identifier `tech.semio.repo` instead of `a.out`). The round-7 loss therefore came from **replacing the file** (new inode and mtime on identical bytes) and from the bootstrap swapping `~/.local/bin/repo` (`link_user_tool` re-linked it over the native command on every run, then `repo-mcp:install` replaced the link again). The launcher is Go; the native command `repo-mcp:install` already compares digests and publishes only on a change. Reproducibility of the native (Rust) build was not measured; it is no longer the identity.
**Changes:** (1) installer: stamp of sources + flags + layout beside the launcher; nothing happens while it fits; a rebuild to the same bytes replaces nothing; a real change installs `versions/<16 hex>/repo`, switches the link `repo` atomically, keeps the three newest versions, prints "The launcher changed: macOS asks once more ..."; on macOS the file is ad-hoc signed with the fixed identifier `tech.semio.repo`. (2) bootstrap `link_user_tool`: leaves a link that is already right alone and never replaces a real file named `repo` (the native command). (3) A launcher whose sha differs from its marker is state `changed`: the probe is started, the client ends with exit 4 and the text "The launcher repo changed: macOS asks once more" (EN/DE), a running service keeps its old file (versions are never overwritten). (4) tests: `🚀️launcher/🧪️tests/🧷️no-touch` (real Go: second run same inode, mtime and hash of file, link and stamp; a stamp-less rerun says "same bytes" and changes nothing; a changed source installs a new version, the old file is untouched, the message appears in both languages), `🔩️native/🥾️bootstrap/🧪️tests/🧷️link-user-tool`, plus the extended launchd and consent suites; the existing install-contract (9) and bash-three suites pass.
**TCC and a fixed identifier (not tested, no dialog may be answered here):** Apple documents that a grant is matched by the code requirement recorded when it was given; for an ad-hoc signature that requirement is the code directory hash, so a fixed identifier does **not** keep a grant when the bytes change. The identifier only gives a stable name. Therefore real launcher changes are rare and announced: the launcher sources had **one commit in the last seven days** (`git log --since=7.days` on `📦️packages/🐹️go`; its files last changed 11-13 22:22), the installer folder two, the registry none.
