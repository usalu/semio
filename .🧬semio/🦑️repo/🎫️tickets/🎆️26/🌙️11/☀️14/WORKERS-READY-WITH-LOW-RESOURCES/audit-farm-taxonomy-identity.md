# Farm taxonomy identity fallback

Read-only source and live-log inspection; no worker or farm was started. The foreground log names `identity differs: records (analysis:…/🔣️taxonomy.json)` and falls back to parent inference. It does not print either compared digest or the two analysis values.

Current farm identity has two independent fields: captured implementation digest and record identity. Record identity hashes the record stamp and sealed module-load authority digest. The parent sends its authority rows in the worker session. The worker initializes its own inference environment, then adopts those parent rows only if no same-identity local load row has a different meaning; otherwise it reports conflicts and retains its own authority. The parent accepts a worker only if both implementation and record identities equal its own. The log identifies the records component and the taxonomy analysis conflict, not a mismatch of captured implementation digest or merely a project-loader filename.

The taxonomy analysis is graph-relevant: its projection includes `testDeliveryScopeDirectoryNames` and `generatorContracts`; the latter participates in the project inference environment and record keys. An edit outside that projection should not change this semantic fact under the current implementation. A changed projection, parser identity/revision or differing observations could cause the conflict; the log alone cannot select among them, prove a source edit, or quantify which value changed. The existing fallback avoids accepting records under mismatched authority. The live log now shows parent work running, but does not establish that it has completed.

Safely using a newly created farm requires the parent and worker to run the same authenticated captured implementation and to agree on the record stamp and sealed relevant load authority, including the taxonomy analysis meaning, under a valid current Original. If the source meaning actually moved, the parent must first obtain a correctly revalidated/rebuilt authority rather than silently adopt a newer worker value under its old key. If the observations agree and a fresh worker presents matching identities, it may serve normally under the existing acceptance gate. Current farm code remembers a refused hub key in the process and falls back for that key, so merely spawning another identical pool is not shown to clear the refusal. No live restart or change was made.
