# R6: `repo tools setup all` on a fresh or half-funded store (g1-m02, 1554 s, `Complete acquired dependency retirement plan required`)

LANDED 2026-11-15 05:01 (T/landings.md "Package R6 landing"; originals T/🗑️generated/R6-landing-050154; rollback `T/🧰️scripts/R6/land.py --rollback <dir>`). T = FLEET-ONE-MACHINE ticket folder, LIB = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`, SETUP = `LIB/⚡️caching/💾️storage/🔒️enforcement/📦️budget/📥️opening/📤️publication/⚙️setup`. No graph command, nothing killed. `LAND-OK` written and removed again.

## Cause
- `SETUP/♻️retirement/🟦️.ts:35` (old): `readRepositoryDependencyRetirementPlanV1` demanded `{acquired:true,value:Plan}`. The native owners (`withNativePlatformProtectedMaintenanceParentV1`, non-waiting EX on `native-fixed-image:<dir>`) answer exactly `{acquired:false}` when any other process holds the image lease. The driver treated that as a malformed plan and threw the bare assertion. Funding (`💰️funding`) and the producer preparation (`⚙️setup/🟦️.ts`) already waited for a held store through `retryWhileDependencyStoreBusyV1`; the retirement loop (plan, observe, retire = three owner calls) did not. Same for the settlement reader (`Acquired closed dependency retirement settlement required`).
- So the state that triggers it is a held image lease at the retirement phase (a sibling `repo`, graph service or a shared hold), not a store state: never funded (`image.json` absent) returns before retirement; an interrupted funding is reconciled before; a partially retired generation is a normal plan (the candidates `unready`, `unready-metadata`, `retained-unready`, `empty` are retired in prefix order); a holder entry removed by R1's dead-holder reclaim only removes a claim. A smaller image changes nothing here (envelope checked earlier by `currentEnvelope`).
- The 26 minutes were not a wait: the log has no dependency-store wait line over 2 min. `source.served` is only the last profile mark before the sealed child `tools setup all` runs (`🏛️sealed/📥️execution/🟦️.ts:22`), so the 30 s ticker names that phase for the whole child. The time was the funding itself (`prepare-current-dependency-bootstrap` installs every scope into the store; `[script] ... javascript-installed-paths` rows only), silent about what it did. On the 32 GB server the same step took about 7 min. The retirement then failed at once on a held store.

## Fix
- `♻️retirement/🟦️.ts`: new `RetirementOwnersV1` (observe, plan, maintain, waits) with the genuine owners as default `retirementOwnersV1`; every owner call goes through `retryWhileDependencyStoreBusyV1` with a fresh parent observation per attempt; busy means exactly `{acquired:false}`, any other shape is validated. Wait is bounded by the new schema constant `Protocol.maximumBusyWaitMilliseconds` = 120000 (`🧬️schema/🔣️.json`); past it the rest is deferred to the next setup with a bilingual warning `dependency-store.retirement-deferred`; ancestor holders still end after 15 s with `dependency-store.ancestor-holds`. Every phase replans from the store, so an interrupted (SIGINT) or half-retired store resumes.
- Typed bilingual refusals (code `failed`): `dependency-store.retirement-plan-incomplete` (reason `not-acquired`|`oversized`|`malformed`, bytes, first violation) and `dependency-store.retirement-settlement-incomplete` (operation, prefix, violation). Progress lines: `dependency-store.retiring` (per generation) and `dependency-store.preparing` (before the silent funding step). Texts in `LIB/⚡️caching/📖️texts/🔣️.json`.
- `SETUP/🟦️.ts`: one line `sayCachingV1("dependency-store.preparing")` before the producer wait.

## Tests (BUN_RUNTIME_TRANSPILER_CACHE_PATH=0, rehearsed on an overlay first, then after landing in the tree)
- New `SETUP/♻️retirement/🧪️tests/🔁️busy-driver/🟦️.ts`, 12 pass: fresh store retires nothing; half-funded store with capsule, metadata, never-ready, empty and inactive leftovers retires in sorted order (independent oracle: sorted obsolete prefixes; every faked plan and settlement validated by Ajv against the wire schema); busy plan, busy observe/retire waited with fresh parent; progress names the holder; bounded deferral then resume; ancestor refusal; SIGINT between observe and retire and after a retire resumes without double retirement; four malformed-plan shapes and a bad settlement give typed refusals rendered in EN and DE.
- After landing: retirement test 5/5, busy-funding 19/19, setup tests 8/8, texts test 3/3 (all exit 0), observation test `native-build/.../📸️observation/🧪️tests` 8/8 (was 6/2: its setup ports were stale since R1/Q1; I added the missing ports). Every edited file parsed with the bun transpiler and every import resolved (dry run).

## Real run on this Mac (after landing, one run)
`repo tools setup all`, about 18385 lines, 1100 s, exit 1, NOT clean:
- It waited about 132 s behind pid 69893 (`show projects`), printing the holder line every ~10 s (new wording works), then printed the new `Funding the dependency store…` line and installed all scopes.
- It then failed in the producer step, before retirement was reached: `Producer reader and completed input validation failed: Current complete Source binding or whole receipt changed`. The tree changes live under a 17-minute install (replica and other agents), so the source binding fence trips. That is a different, earlier fault than R6's; not changed here. A `[lease-order]` warning (`javascript-dependency-bindings` rank 5 requested while the image, rank 7, is held) was printed once right at the start of the funding; also not changed.
- So the retirement path was proven by tests only, not by a real store.

## What the worker must see
- A held store: lines `Process <pid> (<command>) holds the dependency store since <time>; waiting for it (<s> of at most <limit> s)`, never `Complete acquired…`.
- Funding: the `Funding the dependency store…` line, then retirement lines `Retiring obsolete dependency generation <prefix> (<n> retired so far)`.
- Over 120 s busy during retirement: a warning, retirement deferred, setup continues.
- NOT fixed: a 16 GB worker may still need many minutes in the funding install, and any edit of the checkout during it can trip the "Source binding … changed" fence (needs its own package: freeze or re-read the binding instead of failing).

## Faults found by the real runs, and what is proven
1. **Source binding changed after a 17-minute funding (R6b).** Cause with file:line: `boundary()` in `completeRepositoryDependenciesV1` (`LIB/⚡️caching/💾️storage/🔒️enforcement/📦️budget/📥️opening/📤️publication/🟦️.ts`, the check that threw `Current complete Source binding or whole receipt changed`) compared the full stat stamp (size, link count, mtime) of EVERY package directory (the parent of each `node_modules`, taken by `readJavascriptDependencyPreservationSourceV1`, `BOOT/…/💾️storage/🟦️.ts:329-337`, stamp via `javascriptDependencyStampV1`). Any create/delete/rewrite of any file in any of the packages' directories changes that stamp, so on a tree that is edited every minute the check could never hold for 17 minutes. Verified on the live tree: no `node_modules` leaf and no `dependencies.json` had changed; only directory stamps can.
   Fix: new `javascriptDependencySourceMovementV1` (BOOT storage) judges endpoint rows and ancestors exactly and a package directory by identity (dev, ino, mode) only for the bootstrap funding (`purpose==="bootstrap"?"identity":"stamp"`); a real move is a typed refusal `dependency-store.funding-moving` naming `what` (rows, parents, ancestors, receipt) and the path. `retryWhileDependencyFundingMovesV1` (funding module) re-runs a funding whose consumed inputs moved (typed refusal or the stable text of the input recheck, found in cause and aggregate chains) at most 3 times with pauses 2, 8, 30 s (schema `FundingMovementProtocol` in `⚙️setup/🧬️schema.json`), then ends in a typed bilingual exit-75 refusal `dependency-store.moving`. PROVEN: new test `⚙️setup/🧪️tests/🌊️moving-tree` 7 pass (unrelated edit in a package directory changes nothing, independently checked with fs stat; rows/identity/ancestor moves are named; k = 0..3 moves then success with the declared pauses; exhaustion gives code `unserved`, EN and DE text; wrapped failures found; cancellation); busy-funding 19, busy-driver 12, setup 8, retirement 5, texts 3, observation 8 (from the repo root) all green. REAL EVIDENCE: after the landing, run 1 completed the whole 30-minute funding install without the binding failure (before: failed after 17 minutes).
2. **`"bazel" is not a declared SelectedPlanProtocol role` (R6c).** After the funding, the retirement plan refused the dependency image because the Bazel module cache (`<image>/bazel/modules/<digest>`, created by the deps-build-tools operation) is not a declared role. Fix: role `bazel` (directory, self-managed, bilingual writer text) in `BOOT/…/🧬️schema/📥️install.json` `SelectedPlanProtocol.partitionRoles`, new accepted case `bazel-module-cache` in `PUB/🧪️tests/📋️roles/🔣️.json`; roles test green.
