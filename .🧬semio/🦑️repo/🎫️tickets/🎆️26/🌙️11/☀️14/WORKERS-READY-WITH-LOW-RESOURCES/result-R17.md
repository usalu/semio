# R17: the build-agent sidecar no longer restarts every 30 to 60 seconds

## Cause (measured, not as assumed in the brief)
- "Code changed" was already decided on the sidecar's own import closure (content digest, `🧮️closure`), and the replica supervisor does not decide it: it compares the entry script hash only when a new daemon adopts a launcher (`🧷️sidecars`, `claim`). Nothing in the replica module needed to change, so no replica landing and no `1113-landings.md` entry.
- The real cause: the agent role ran the graph server in its own process (`void superviseGraphServerV1(context)`), so the closure of the agent was **571 files** (graph server 554 of them: graph, inference, graph-state, caching, resident hooks). Every edit of the build graph code by the fleet (R5c and others) restarted the agent, its worker, and the graph server. Measured with the repo's own watch: agent 571, graph 554, scheduler 35, cache 63 files.
- After the change: agent **77 files**, graph child 555, scheduler 36, cache 64.

## What was built (all landed 06:27 local, `T/🧰️scripts/R17/land.py`, `T/landings.md`)
1. Graph server as a child process of the agent with a closure of its own (`superviseGraphChildV1` in `🛰️sidecar/👷️agent`): an edit of graph code restarts only this child (status 75, started again at once), a crash restarts it after a 1 s to 15 s back-off, the agent stops it with SIGTERM (it saves its state) when it stops or restarts, `SEMIO_GRAPH_SERVER=off` starts nothing. Works with launchers that are older than this change (no launcher change).
2. Debounced, graceful restart (`createSidecarRestartDebounceV1` in `🧮️closure`, `createSidecarRestartV1` and `sidecarRestartPolicyV1` in `🛰️sidecar/🟦️.ts`, schema `🛰️sidecar/🧬️schema/🔣️.json`): the closure must differ from the one the process started with; restart after 90 s without a further change, at the latest after 600 s of deferral; an edit that is reverted cancels the wait; the agent then drains (stops taking actions, in-flight actions finish, up to 300 s grace) and exits 75; the other roles exit at once. Values: `watchMilliseconds` 30000, `quietMilliseconds` 90000, `maximumDeferralMilliseconds` 600000, `graceMilliseconds` 300000 (environment overrides for tests: `SEMIO_SIDECAR_WATCH_MILLISECONDS`, `_QUIET_MILLISECONDS`, `_MAXIMUM_DEFERRAL_MILLISECONDS`, `_GRACE_MILLISECONDS`).
3. Drain of the worker (the R5 prepared design, re-baselined; R5c must drop it): `drainWhenIdleV1` and `drain` option in `🌐️remote-execution/🛰️agent`, new admission refusal `draining` (TS union and the `Refusal` enum of the remote-execution schema).
4. Serve state of the graph server (`ServeState` in the wanted schema, `serveStateFileV1`, `readServeStateV1`): `.cache/f/graph-server/serve-state.json` is written atomically after every round when it changed (held requests with the projects already reported fresh, completed claim keys, kind of read). A new process of the same owner and platform restores it, renews the same claims at once (a claim nobody holds any more is given up), answers with at least the old list, and hands its read the published projects (`infer(reason, signal, published)`, logged as "the read starts from the N projects that are published already").
5. Log: for every restart one line per language (English / German) that names the changed files, the deferral and why it is due; one earlier notice when the edit is first seen.
