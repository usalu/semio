## Verdicts

1. **The audit confirms what was already fleet-shared** (`deps-js-all` and the JavaScript part of `deps-build-tools` through install packs, `deps-cargo` through crate blobs, the downloads of every pinned tool through blobs). **Three were only believed to be shared and were not**: `deps-python` (the uv seam `fleetUvPortV1` had no caller, `FF/🐍️uv/🟦️.ts:129` before the landing; the store has no `v1/fleet/uv` directory at all), `deps-go` (the package-manager environment that attaches the group mirror, `BOOT/📦️dependencies/🔌️managers/🟦️.ts:153`, is never used by the `go` branch of `prepareDependencies`, `native/🟦️.ts:68`, so `go mod download` always went to the upstream) and the cargo-installed tools of `deps-wasm` and `deps-trunk` (`cargo install --locked` of wasm-pack, trunk and wasm-bindgen-cli compiled from source on every machine, `native/🟦️.ts:51`; this is the largest compile left in the family).
2. **A latent collision**: the uv seed was named by the digest of the lock alone (`uv-<lock>.json`). Wheels carry platform tags, so with seven macOS machines, one Linux and one Windows machine the last publisher of any class would have replaced the seed of the others. Now named by lock and host class.
3. **"Platform class" of `graph-state/platform-class` is the wrong class for installed trees.** `posix-shared` puts macOS and Linux together because a project record is JSON that is byte-identical there (measured by P14: 496 of 498 records). An installed tree holds native executables and optional native packages. So the setup records have three kinds: `neutral` (one class for everybody), `posix` (that same `posix-shared` class, only for trees without native code) and `host` (OS, architecture and, on Linux, libc: `linux-x64-gnu` is not `linux-x64-musl`). Every task of the family is `host` or `neutral`; none is `posix` today.
4. **Closure entries did not travel.** `documentsOf` published only the document `record` (`B/🪪️graph-state/📦️project-records/🟦️.ts:38` before); the entries live in `…/inference/selections/<id>/ce/{e,l,v}` of each machine (2.4 GB on the server for 4 775 projects, P12), so a taken record still derived its closures (`produceClosureEntryV1`, `B/🕸️graph/📥️inference/🧭️script-inputs/🟨️.mjs:1163`, store load at :1173, derive on a miss). Now the entries a record names travel with it (section "Closure entries").
5. **Not changed, named**: the JS install key has no libc (`fleetInstallKeyV1`, `FF/📦️install/🟦️.ts:63`: bun version, platform, architecture, recipe); a glibc and a musl Linux would share a key and the optional native packages differ. The fleet has one Linux machine, so nothing collides today. Three `generate` tasks have `cache: true` and no declared outputs. Playwright Chromium has no sha256 pin.

## Closure entries (the second half of the package)

- **Law**: a taker that gets a record from the fleet gets the closure entries the record names, in its own store, with its own paths and its own digests. Export: `closureTravelV1.export(root, image)` reads `closureRecipes` of the record and walks the shared entries their values refer to (`sharedReferencesOfV1`); each entry is one document `closure-<recipe key>` with its layers and value inline, root-neutral exactly like the record (`neutralizeRootV1`, `portableRowsV1`); shared provider entries are byte-equal across projects, so the content-addressed upload stores them once. Import: before the record is written, `closureTravelV1.import` rejects a bundle whose recipe does not hash to its key, keeps an entry that is already there, and stores the rest through `store.save`, which recomputes every digest from the local rows. A wrong entry still costs a derivation and never a wrong graph, because every consumer checks the rows against its own tree (`closureEntryHoldsAsyncV1`, :1135 region). The record's own lookup then finds the entries in the store (`produceClosureEntryV1` :1173) instead of walking.
- **Re-offer**: the marker of an offered record now carries the format (`:closures-1`), so each machine offers its stored records once more with their entries, paced by the existing offer limit (64 pending). Bundles of unchanged entries are remembered by their file stamp (512 entries, 128 MiB), so a shared entry is decoded once, not once per project.
- **Counter**: `stats().closures`; the progress and summary lines print it ("graph: 50 projects taken from the fleet with 12 closure entries, 3 inferred here" / DE).
- **Limit, named**: an entry that only a farm worker derived and its parent has not persisted yet is not in the store when the record is offered; that record travels without it (the taker derives, as before). The producer of the entries must be the machine that persists them (the graph server), which is where the offers come from.

## What a worker's setup log must show (restored vs built)

All lines print to the console of the task, in the language of `SEMIO_LANGUAGE`, both languages joined by ` / ` when it is unset.

- Cargo tools (`deps-trunk`, `deps-wasm`): `[setup] cargo-tool:trunk: restored from the fleet, 1 files, 17.3 MB, class darwin-arm64, key 1a2b3c4d5e6f` (0 compiles) **or** `[setup] cargo-tool:trunk: built here (the fleet has no output for these inputs), class darwin-arm64, key ...; published to the fleet: true`, **or** `built here and kept local (<reason>)` with one of: no fleet store on this machine, this platform has no shareable class, the build left no output, the output holds a link that cannot move, this machine cannot sign a record. A waiting machine prints `another machine builds this output, waiting for its upload`. A restored executable that fails the version check prints `the restored output did not pass its check (...), building it here`. A tool that is already installed prints nothing (the probe returns first).
- Python (`deps-python`): `[setup] uv-cache: N wheels restored from the fleet, uv downloads only the rest`, or `the fleet has no seed for this lock and class darwin-arm64, uv downloads the wheels`, then `N wheels published to the fleet, class darwin-arm64`.
- Go (`deps-go`): `[setup] deps-go: module downloads go through the fleet mirror http://<group server>:6094, the upstream is the fallback` or `no healthy fleet mirror, module downloads go to the upstream`.
- JavaScript (unchanged lines): `[DATA] Store dependency generation adopted {"donor":"fleet"}` and `[DATA] Store dependency fleet {"stage":"restore"|"publish"|"wait"|"claim"|"skip",...}`. A 16 GB worker whose log has neither line for a scope installed it from the network.
- Graph: `graph: N projects taken from the fleet with M closure entries, K inferred here`; M > 0 on a worker is the proof that closures are not derived; after the first hits `ce/e` of the worker grows by imports, not derivations (`closure entries before/after` of `ROUND-NOTE-P12.md`).
