# Low-resource complete-head adoption feasibility

Read-only current-source review; no live command or remote dispatch. `audit-compatible-peer-0432.md` establishes m01/m08/m10 reported 16,384 MB and the authored serving threshold is 24,000 MB. Current graph sidecar `runGraph` runs the existing Wanted server with `mayServe` false and zero headroom below that threshold; its automatic refresh is part of that serving path. The sidecar callback named `adoptGraphReadV1` resumes an already-running local read, not adoption of a fleet head. These facts do not show an existing automatic or one-shot scheduled head-only adoption on the 16 GiB peers.

The normal whole-generation loader already has a current-only path: for an unpinned whole request with no matching local seal, it checks that a complete compatible fleet head is ahead and local builder is idle, acquires local builder custody, restores through the existing signed exchange with inference disabled, and verifies the resulting seal. A matching local seal is served directly; a missing, incompatible or unavailable head refuses rather than starting whole inference under `current`. This supplies the existing cache, identity, storage and custody machinery; platform similarity or source attestation alone is not enough to claim a head is compatible.

The narrow integration surface would be a separate head-only local scheduling callback in the existing supervised graph sidecar/Wanted loop, using its existing local readiness-busy and host-capacity gates and cancellation lifecycle, then invoking the normal `current` whole loader through the repository-owned local command/capacity interface. It must not weaken `mayServe` for full inference or turn Wanted into arbitrary remote command dispatch. Admission needs the complete-ahead check, idle local builder and a bounded resource budget; an already-current seal should result in no additional adoption. A per-origin in-flight guard and recheck under actual builder custody are needed because polling, sidecar restart, concurrent local consumers and fleet head changes can otherwise duplicate attempts or make an earlier ahead observation stale. Capacity, storage and signed verification remain authoritative, and no claim that this fits 16 GiB is made without a physical measurement.

This is a feasibility direction, not an implemented feature or proof that the existing `current` command is itself automatically scheduled on any peer. The loaded sidecar revisions and current peer availability are not established by source inspection.
