# R101: the fleet produced no owner results because every record was refused at the end, not because of lanes or claims

Scripts: `T/🧰️scripts/R101/` (T = `☀️13/FLEET-ONE-MACHINE-SHARED-HOT-CACHE-AND-REMOTE-EXECUTION`): `repro.mjs` (one separate child on g1-server: opens a kept wave, claims, infers and publishes real owners; `R101_ONLY`, `R101_COUNT`, `R101_TRIES`), `overlay.ts` (runs staged files against the live tree), `land1.py`/`land2.py`/`restore*.py`/`window*.sh`/`runall.sh`, the staged tests. Landings: `landings.md` entries "R101 landing 1" (23:02 UTC) and "landing 2" (23:30 UTC).

## 3. "inputs changed while it ran" (the cause of `published 0`)
Measured with `repro.mjs` and a debug copy of `observeInferenceComputationV1` through the overlay (one real owner, `@semio-tech/os-store-cursor-rs`, 7 s): the owner's 368 rows were consistent, not racy (`young` empty, `racyMs` 2000), the authority rows of a nested project are empty. Nine rows failed the end check, all `closure` rows of three closure entries, and the provider answered `!stale` because the entry was **missing** from `closureEntriesV1` (the bounded in-process cache, 96 MiB, holds two of the 37 to 42 MB entries; an owner with three or more evicts its own entries while it runs). `settleClosureRowsV1` before the check did not help (it fills the cache one entry at a time and evicts again). So it was not a change elsewhere in the tree: every owner with more closure entries than the cache holds left no record, on every machine, which is why 13 of 14 claims of g1-m07 and 6 of 6 of the server ended `no-record`, and the owners that did publish earlier were the light ones.
Fix (landing 1): the closure rows are verified by the provider (`verify`: per closure the entry is made current, every query answered at once and compared with the recorded answer; an entry the tree touched is derived again, a changed answer still voids the record), the other rows as before (`projectRowsHoldAtEndV1`). If the publish still says `no-record` the owner is claimed and inferred once more at once (`noRecordRetries` 1); a second miss is a failure. Landing 2: a look at a stored record judges its closure rows the same way (`projectRowsHoldV1`).
Proof: `owner-pool/🧪️tests/🔁️no-record` (3), `observation/🧪️tests/🏁️rows-at-end` (1), `🔎️lookup-holds` (1) red before (function missing), green after. Real owners: `os-store-cursor-rs` `no-record` in 3 of 3 runs before, `ok true` after (7.7 s, 3 closure entries); `value-snapshot-read-rs` (the `lastError` of g1-m07) `ok true` in 7.2 s.

## 1. Slots and target 1
Host view of g1-server at 23:05 (`host.mjs`): 10 cores, 11 554 MB available, 9 `graph-farm` grants of 1 cpu and 1536 MB with `observedMegabytes 0` plus the `projects` grant (2 cpu, 14 336 MB reserved, 6 679 observed): `foreground.cpu 11` so `byCores 0`, `unrealizedMegabytes 11 113` so `byMemory < 1`, load 17.75 so `byLoad` negative: the pool kept one child and said `nothing-fits` / `yielding`. The old formula had no floor between "all cores" and "one child" and a hard load gate that other agents' test processes trip. Workers: the reader's own farm grants book the cores in the same way.
Fix (landing 2): no hard load gate (the children run at priority 10 and take what is left); a quarter of the cores (`minimumShareBasisPoints` 2500) while the memory fits and none of the machine's own requests waits; the idle cores the sidecar measures from `os.cpus()` between two looks (`idleCores`, children's own load not counted) grow the pool by as many children; waiting own work, memory and pressure rules unchanged. Proof: fixture + independent Python oracle (3 new cases, 1 changed), `🎚️lanes` (2). With the same host view the target is 3 children instead of 1. Per-job footprint stays the pool's measured p75 + 15 % of the children's own resident sizes.

## 2. 434 claim attempts, 14 claims, 0 published, `held` 101
`held` is a refusal ("someone else holds the claim"), not a stored result. Measured with `repro.mjs`: 328 of 330 random claims answer `stored` (each costs 0.24 to 1.5 s under load: one cache round trip plus the freshness verdict of the stored note); only about 3 % of the wave is open, and every puller of the fleet (10 machines times their children) converges on those same few hundred owners (heavy ones first in list order for everybody), so most open claims were held by another machine working on the same owner, and every owner that was granted ended `no-record` and went back to the pool, to be claimed and fail again by the next machine. Claims were lost to the other pullers, and the owners cycled instead of being published. Not changed: the heavy-first order is still the same list order for every puller (a rotation of the start per puller would spread the first claims; not done, no measurement yet).

## 4. `fetched 0` on workers
`slice-memory.json` of g1-m07 / g1-m01: ledger `present 1, fetched 0, stale 10 to 15` of 15 looks. A look fetches the stored record, seeds it and re-checks the rows; a record with closure rows whose entries the cache cannot hold together, or that the take refuses to derive (`BUILD_TAKE_MISS` after R91), ends `stale`. By reading the code this is the same eviction as in point 3 (`lookup()` in `observeInferenceComputationV1` judged closure rows from the cache); landing 2 changes the look to the provider verdict. Not reproduced on a worker (the server holds every entry locally) and no worker has run the new code yet.
