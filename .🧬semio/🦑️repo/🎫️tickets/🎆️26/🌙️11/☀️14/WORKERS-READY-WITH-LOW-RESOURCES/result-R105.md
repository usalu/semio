- `claim` (`GS/📦️project-records/🟦️.ts`, `createProjectFleetPortV1().claim`) asks `tryGraphEntryV1` for the state digest `projectRecordStateV1({root, fleet, keyText: [stamp, null, key], platform})`; any entry under it is `stored` unless `staleNoteOf` says its record is stale.

## 3. Why `published 0`, `claimed 0`, `running 0`, "yielding", slots 5-9
- `stored` rises because every claim of the pull answers `stored`: `staleNoteOf` (the freshness verdict behind `claim`) fetched only `record.br`, checked the file rows of the record and treated every `closure` row as fresh (`closureHoldsOfV1`: an unanswerable row is never stale). It never looked at the closure entries the record carries, which is exactly what a taker imports and verifies. So the pool judged the record fresh, never refreshed it (a refresh needs a granted claim), and no machine computed it: `claimed 0`, `running 0`, `published 0` (g1-m01: `claimAttempts 1110` ≈ `stored 1082`).
- `reason "yielding"` with `slots 5-9` is the capacity gate's target (`ownerPoolTargetV1`: the machine's own graph read holds the cores, the pool keeps what is left); it says how many children may run, not that anything is wrong with the records. With nothing to claim the children idle.

## Fix (landed 2026-11-17 01:31:56 to 01:34:00 UTC, lock claude-R105)
`GS/📦️project-records/🟦️.ts` 74dc85d46a4a -> e5576e38c42a: exported `closureBundleHoldsV1` (rows and layers of one closure bundle probed in steps, the taker's verdict); `staleNoteOf` fetches the closure documents deferred and, for a record older than `minimumAgeMilliseconds` whose own rows hold, localizes every closure bundle the way `takeClosures` does and probes it; one verdict per stored blob (kept `keptMilliseconds`, so the shared entry is probed once per child), an unlocalizable bundle counts as stale (the taker could not import it either). A stale record now yields the refresh claim (`refreshStateV1`) and the pool recomputes it; the refreshed record carries closure entries that hold.
Tests (`GS/📦️project-records/🧪️tests/🤝️pool-reader/🟦️.ts`): (1) pool path `claim` + `publish` then reader path (`gate` in a take look, then the verdict on the closure entries imported into the reader's store) in one test: found while the tree holds, `claim` says stored; after a closure file changed the reader rejects and `claim` must be granted (red before: `Expected granted, Received stored`), the refreshed record is found; (2) three origins on one cache: stored by origin one, found by two and three, a pool of origin two says stored exactly while they find it, after an edit a pool of origin three refreshes.
