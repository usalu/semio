## 1. `cpp-setup`: what is pinned and why the compiler was refused

- `runRepositoryCmakeV1` (`🏗️build/🛠️cmake/🏃️execution/🟦️.ts`) builds `files = {tools/cmake, tools/ctest, tools/compiler, tools/ninja, source/CMakeLists.txt, source/CMakePresets.json}` and hands it to `withCmakeInputsV1` -> `withArtifactSourceSetV1`. That keeps one read-only descriptor per file, digests it at admission and at close, and rechecks identity (dev, ino, size, mode, mtime, ctime, **nlink**) before each consumer. Single-link is demanded so a second name cannot be used to change a pinned file behind the pin; nothing is copied into a publication.
- Only the compiler can be the culprit on this host: both root CMake files have `nlink` 1 (checked), cmake and ninja come from the tools partition, the compiler is `program(environment.CXX ?? "c++")` = `realpathSync(which c++)` = `/usr/bin/c++` (`ls -li`: inode 1152921500312612130, 78 links shared with `clang`, `git`, `make`, ...). N1 was right that nothing sets `CXX` on macOS.
- Rejected alternatives: relaxing `regular()` (it guards every publication source, not only the compiler); making `tools setup` provide `CXX` (it would still point at a hard-linked system file; a fresh Mac with only the Command Line Tools has no other compiler).
- Design, `systemCompilerV1(located, requested, environment)` in `🛠️cmake/🪟️toolchain/🟦️.ts`: a single-link compiler is returned unchanged (Linux, Windows, Homebrew and every ordinary case behave as before). A hard-linked file on darwin is resolved like `xcrun --find`: `DEVELOPER_DIR`, then the `xcode-select` selection (`/var/db/xcode_select_link`), then `/Library/Developer/CommandLineTools`; in each `Toolchains/XcodeDefault.xctoolchain/usr/bin/<name>` (Xcode) before `usr/bin/<name>` (Command Line Tools); the first whose `realpath` is a regular single-link file wins. It returns `{command, file}`: `file` (here `.../clang`, 124 MB) is pinned, `command` (`.../usr/bin/c++`) is what CMake runs. The name matters, measured on this Mac: CMake with `CXX=<toolchain>/clang` fails to link a C++ program, with `CXX=<toolchain>/c++` it builds and runs. Anything else (no toolchain found, or a hard-linked compiler on another host) is refused with the bilingual `build.cmake.compiler-single-link-required` (names the compiler, the link count and `xcode-select --install`).
- Diagnosability: `regular()` now says which file and how many links: `Single-link regular artifact source required: <path> (<n> links)`. The old text did not name the file, which is why the cause had to be inferred.
- Cost: the 124 MB real compiler is hashed at admission, at close and at each recheck (the 200 KB shim was free); on this Mac pinning it takes well under a second per pass. The pinned total stays far below `maximumInputBytes` (512 MiB).

## 2. `deps-build-tools`: the funding parent and the busy refusal

- Throw: `⚡️caching/💾️storage/🔒️enforcement/📦️budget/📥️opening/📤️publication/⚙️setup/💰️funding/🟦️.ts` `withFundingParentV1`: `if(!selected.acquired)throw Error("Genuine dependency funding parent is busy")`. `selected` is the result of `withNativePlatformProtectedMaintenanceParentV1` (`🏃️process/📦️artifacts/🏗️native-build/💾️storage/📤️publication/🌐️platform/🟦️.ts`), which takes the exclusive lease `native-fixed-image:<directory>` with `timeoutMs:0` and answers `{acquired:false}` when another process holds it.
- "Funding parent" = that exclusive maintenance lease of the dependencies cache image, under which funding is observed, reconciled and the producer prepared (`setupRepositoryDependencyPublicationV1`, `⚙️setup/🟦️.ts`). It is not a capacity grant of the `workspace:setup` orchestration; the children do not draw from a parent grant, they contend for one image lease. Every dependency-store operation of every parallel task passes through it, so with `--parallel=2` two children meet there. A second place had the same flaw, `⚙️setup/🟦️.ts`: `Genuine dependency bootstrap producer is busy` (`prepareRepositoryDependencyBootstrapV1` returns the same `acquired` result).
- Which sibling held it in the report is **not proven**: the fifteen lines show `repo ... native owner-command ... "setup" "git"` running next to `deps-build-tools`, but the log does not say who took the lease. N1 made `deps-build-tools` the Original of `tools setup all`, so it now reaches the dependency store (the earlier refusal `Original Repo build caller required` happened before this point); that is why the refusal changed.
- Fix (`retryWhileDependencyStoreBusyV1`, same file): repeat the whole attempt (re-observe the parent, open the lease partition, try the lease, close the partition again) while the answer is `acquired:false`; first pause 200 ms, doubling to at most 2 s, with a quarter of random jitter so two waiting children do not stay in step; the lease partition is closed while waiting; the control's cancellation and deadline end the wait at once; the bound is the existing store-sync queue bound `maximumQueueWaitMilliseconds` = 21600000 ms (6 h), then the bilingual refusal `caching.dependency-store.busy-timeout` (code `timeout`); an attempt that throws is not retried. The body of the attempt runs only when the lease was acquired, so a retry never repeats an effect.
- Texts (`⚡️caching/📖️texts/🔣️.json`, EN and DE; `sayCachingV1` added beside `refuseCachingV1`): `dependency-store.waiting`, `dependency-store.busy-timeout`; build catalog `cmake.compiler-single-link-required`.
- Same class, deliberately left: other `acquired:false` throws that are not on the path of this report: `🏪️store/🟦️.ts:154` (`Quiescent pre-pin cache storage admission required`, has its own `wait` flag), `♻️reset/🟦️.ts` (`Whole-cache reset EX admission required`), `💾️cache/💾️volume/🟦️.ts` (`Genuine producer writer was not acquired`), `🧹️whole/🟦️.ts` (`Actual Native continuation writer required`). If a worker run shows one of them, `retryWhileDependencyStoreBusyV1` is the helper to wrap it with.
