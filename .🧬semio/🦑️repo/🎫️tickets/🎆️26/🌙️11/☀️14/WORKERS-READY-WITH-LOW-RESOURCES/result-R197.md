## Wall 100 (found, fixed in the ready runner, landed 10:00:00 UTC): the runner of the next stage ends `diskimages-helper`, and a toolchain copy into the tools image is left half
- Run 1 (first run with per-machine checkouts, 16 GB / 8 cores): `repo-mcp` failed after 23 s with `The pinned go 1.26.9 is not provisioned`. The warm copy had reported `go copy 17.4 s 258.9 MB`; at the failure `s/b/t/m/native/go/1.26.9/…` held only LICENSE, PATENTS, `misc`, `test` (6 MB) and no `.toolchain.json` (`preparedArchiveV1` reads that receipt: ENOENT is the message). `kills.log` of the machine: `Process 18396 (diskimages-helper) received SIGTERM from the ready stage runner … (stage prime …): it stood in the roster of an earlier try of this stage` at 09:24:54 and SIGKILL at 09:25:06, one second after the warm copy ended and while the tools image was being written. Same defect as R178's wall 93 symptom (run 5: a toolchain copy with empty files after `diskimages-helper` was ended); R178 had put it down to two simultaneous labs.
- Cause: `readyKillPlanV1` ends the root of a stage, everything below it and every recorded orphan. The helper macOS starts for the first attached disk image is a child of the process that attached it, i.e. of the `prime` stage's tree, and it serves every image of the user (the live checkout's too). Ending it drops writes in flight to the worker's partitions. It had not hit earlier labs because the image was attached by a command whose roster was not killed.
- Fix: `Policy.sharedSystemProcesses = ["diskimages-helper"]` (schema) and the plan never contains a process with that name (`🌲️process-tree`), law `🛡️shared-helper` (2; 1 red before); process-tree tests 16/16. By hand: with the go tree copied again the same `repo run repo-mcp:build` built the launcher module (150 s). NOT known: whether a real worker's first attach makes the helper part of a stage roster (a worker's `kills.log` is on its machine). Real-worker impact is possible on any machine whose first image attach happens inside a stage.
