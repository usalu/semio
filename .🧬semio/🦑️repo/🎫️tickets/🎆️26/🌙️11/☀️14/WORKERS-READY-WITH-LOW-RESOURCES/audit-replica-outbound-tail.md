# Replica tail following during outbound journal failures

The daemon's store turn publishes local changes before following peer journals. A non-sharing error from regular publication escaped the turn. The hot batch requeued its paths, so the same failure could bypass tail following on every retry. The 10-second store guard controls a stalled reachability probe. The reproduced filesystem exception returned promptly while the store remained reachable.

A native two-origin probe first showed healthy inbound materialisation, then replaced only the receiver's outbound segment directory with a regular file. The healthy peer published another file. The receiver counted three ENOTDIR round failures and the inbound file remained absent. A direct follow using the same receiver and store materialised it while the outbound blocker remained in place. The durable probe is `outbound-tail-probe.ts`. It defaults to verifying the fixed behavior and accepts `--expect-starved` to reproduce the prior result against code that still has the fault.

A nonfatal regular publication error now permits one inbound attempt before returning the original error to the existing outer reporting and backoff. The hot batch retains its requeue. The fallback does not repeat an early recovery follow and respects cancellation, store stalls, origin custody and retirement. An independent inbound exception gets its own follow diagnostic. The priority-stage helper already records non-abort publish exceptions and continues the turn, so it uses the existing path.

The native regression uses a neutral JSON fixture and has SQLite read the peer journal independently to identify the expected inbound byte count and SHA-256. Before the change the receiver read was null and SQLite selected the published 37-byte file. After the change the receiver materialised the matching bytes while its journal stayed blocked and the same failure remained visible. The focused run passed five tests covering this case, stalled store recovery, recurring-error backoff, duplicate-origin custody and retirement. No live daemon or shared store was modified. This is a reproduced failure mechanism. The exact cause of m03's observed older digest remains unverified.
