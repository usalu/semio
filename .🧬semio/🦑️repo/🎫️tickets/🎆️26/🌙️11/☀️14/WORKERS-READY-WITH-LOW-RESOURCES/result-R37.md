## 2. Findings that change the picture
- **(a) is already narrowed.** `B/🕸️graph/📥️inference/♻️revision/🧬️schema/🔣️.json` (since 10-31) declares top level sections of data files that nothing of the graph reads; their row carries `ignore` and is a canonical sectional digest. Live code classifies today **6** digest rows (the graph schema row of generation 237 is gone), the caching policy ignores `storage`, the build policy `hostCapacity, workers, remoteCache, remoteExecution`. Of the six policy edits of the 14 days (checked against the section line ranges of the file) **four were absorbed** (two `storage` edits, one `hostCapacity` edit, one pattern inside `workers`); two touched read sections (`namedInputs` negations; `generatedDirectories` plus the `toolchains.cargo.environment` rename together with a `storage` change) and staled every record, correctly. A per-kind split of what remains was measured and rejected: the sections left are read by all kinds (`toolchains.javascript` by all, `toolchains.cargo` by 4 456 of 5 101 = 87 percent, the other tools by under 10 percent), so a split gains at most 13 percent of one section. The existing sectional list is the right tool; a section may be added only with a recomputation oracle (its schema says so), none of which exists for the remaining ones.
- **(b) the 17 helpers are two different things.** Only the compaction list is an over-approximation. The same 17 files are also real imports of the repository tooling: all 17 sit in the 17 `scriptProvider:*` groups and in `toolClosure:cargo-command:native` (about 2 066 files each, gen 237), because the scripts that run every command import the input stack. Removing the compaction list alone would save only the owners that do not execute the tooling (5 043 to 4 724, 319 owners). Replacing the helper bytes by a "protocol version plus frozen vectors" was designed and **rejected**: the executed tooling is code identity of every command (changing it may change outputs), a version string would weaken that for no gain on 4 724 owners, and an existing law (`📋️data/🧪️tests`, "compact helper … include shared DATA and exact reader behavior") pins the list on purpose.
- **(c)** the files reach commands through three routes: `commandSources*` (after R29 the `native-toolchain` tool of the providers project), `default`/`production`/`sharedSources*` (inputs loop over the toolchain files) and, for 142 projects, `cargoToolchain`. A Rust crate's `check`/`test` key holds bunfig and tsconfig only through the command list.
- **(d)** `cargoToolchain` has **141 projects that name it in their own targets** (`test` 100, `test-native` 35, `build` 32, `check` 28, `lint` 4 …) and **one cross reference** (`@teaching/architecture-course` group `proctorCargoManifests` names it of `@teaching/proctor`); no `^cargoToolchain`. In 4 313 nodes it is a dead group (no target reaches it). Its files are not dead: four Rust packages name it in `lint` (`./📜️script.ts lint`), whose tools registry knows rustfmt, so rustfmt.toml and the shim are content facts of those tasks. rustfmt.toml and the shim reach the other 4 300 crates only through `native-toolchain` and `default`, not through this group.
