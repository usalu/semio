## 2. What was built

Everything schema-first, tests with an independent Python model where a rule exists, EN/DE texts. No legacy path: the readers' key is the only key.

1. **One key.** `PN/🟨️.mjs` `ownerRecordKeyTextV1(key)` = `[record stamp, null, key]` (read from the observation schema, the observation module is NOT touched, so `OBSERVATION_REVISION` and the key of every non-nested path stay); the pool driver claims and publishes under it. Law: key of the pool = key of the reader of a settlement round = key of a Python model on a fixture with a second machine root (`PN/🧪️tests/📥️take`, test 1; also asserts the formulas in the observation source).
2. **Waves and notes keep their own slot** (`PN/🌐️owner-pool/🟦️.ts` `stateOf`: tooling includes the id of the wave or of the record state). Law: two manifests never share a slot, and `classifySlotsV1` keeps both `current` where the old slot collected the older one.
3. **A stored record that does not hold is refreshed** (`GS/📦️project-records/🌱️fresh`, new; port `claim`): the file rows (`file`, `analysis`) of a stored record are compared with the puller's tree (digests, the same ones the taker checks); a stale record is claimed under a state of its own (named by the stale entry) and replaced by compare-and-swap, so the newest writer wins. Records younger than 2 minutes and records that cannot be decided count as fresh (no ping-pong between machines). **Second landing (R68b):** a record older than the newest code file of the build tool (`codeEpochV1`: newest mtime of the code files below `library` and `🔨️modules`, margin 5 s, looked up once per machine and minute, kept in `.cache/f/owner-pool-fresh/`) is stale too, because a landing in the tool code stales every record through the closures although no file row changes (that is how the first landing's records would have stayed "stored"). Fresh verdicts are shared by the processes of a machine for 10 minutes and only trusted when newer than the epoch. A reader that seeded a stale record and infers the owner itself publishes with the same swap (before: refused as divergent, the stale record stayed).
4. **A reader first takes, then schedules** (`PN/📥️take`, new; `PN/🟨️.mjs` `resolveOwners`): before any inference, 12 parallel looks resolve every owner of the plan against the local store and the fleet cache inside a look-only scope (`runTakeLookV1`: the gate never claims, never waits, never publishes; `takeAway` makes a miss impossible to infer by accident, also when there is no farm), faults are looked at again (3 times, 4/8/16 s), the owners that are missing are published AT ONCE as one wave (only the missing ones, own slot) so that the pool of every machine pulls them, the reader infers them in its governed loop while a poll (growing pause 2 s to 20 s, resets on an arrival, 48 names per look, rotating) takes any record that appears before the loop reaches the owner. Bound 15 min, fails open (a failing pass leaves every owner to the normal path), `SEMIO_GRAPH_TAKE=off`. The progress line: `owners {done} of {total} done: {present} present, {fetched} fetched from the fleet, {here} inferred here ({running} running), {wanted} wanted from the fleet, {stale} stale in the fleet` (+ German), every 10 s and at the end; counters of the phase row advance during the pass so the server's read watch sees progress.
5. **Heavy owners are never waited on the server alone** (`GS/🙋️wanted/📖️read` `fleetReadV1`): still published as wanted, but also handed to the governed inference last (alone, solo grant), skipped as soon as the fleet delivers them.
6. **A fault of the cache is asked again** (`gate`: up to 2 further looks after the back-off and the rest of the breaker) before the owner is computed.
7. **Provider ports** (`B/🕸️graph/📥️inference/🧭️script-inputs/🟨️.mjs` `scriptProviderIdsV1`, used by the taker's provider list).
8. Landed together with it: the whole R67 package (35 files).

Not built: the server answering `told` from arriving records by itself (the take pass of its read does it for the owners of its wave: they are `fresh` when the read ends); a priority field of a wave (pullers take the 3 newest waves; the reader's wave holds misses only).

### Tool closures
Both landings touch files that are inside tool closures (`PN/🟨️.mjs`, `GS/📦️project-records/🟦️.ts`, `GS/🙋️wanted/📖️read/🟦️.ts`, `🧭️script-inputs/🟨️.mjs`, owner-pool, R67's eight): checked with `proof/` against the closure documents of production entries `8df515a4…`, `cf681a78…`, `aebb8d02…` (22 359 paths, 7 012 import edges). The shortest import path from a tool root to `project-nodes/🟨️.mjs` is `walk-farm/👷️child/🟨️.mjs` → `📥️inference/🟨️.mjs` (the barrel that imports every component) → `project-nodes`: the walk child opens the real inference deriver, so the whole inference component graph (transport and wave code included, because `openGenerationDeriverV1` lives in the same component file as `emojiProjectJsonNodes`) is an input of every derived closure fact. That is a semantic dependency of the derivation on its code, not an import accident of the pool alone; the record key itself never contains it (the key holds the record stamp), the staleness comes from the observed closure rows. Cutting it means moving the deriver out of the wave component (a refactor of the component roster and its tests) and was NOT done. The observation module (`OBSERVATION_REVISION`) was kept untouched on purpose. The consequence of the landing: every record is stale once; the pool (R68b) now refreshes them by itself instead of leaving it to the readers.

## 3. Tests (all green before landing in `ws`, again under the lock)
New: `PN/📥️take/🧪️tests` 4 (policy schema, poll pause and ledger line equal a Python model on 16 rounds and 3 ledgers; pass looks once and repeats only faults with bounded concurrency; poll grows, resets, rotates); `GS/📦️project-records/🌱️fresh/🧪️tests` 4 (digest rows, verdicts incl. code epoch and age against a Python model, refresh state, file digest follows content, epoch from real files, kept); `PN/🧪️tests/📥️take` 11 against a real cache server and real ports of several machines: **all owners stored → 24 of 24 fetched, 0 inferred**; **36 of 40 stored → exactly the 4 missing are missing/inferred**; **an owner another machine stores while the reader polls is taken within poll bound + 600 ms and never reaches the inference** (2 of 4 missing arrive); a stale stored record is refreshed by a puller, a second puller sees `held`, the reader takes it, the refresh is not repeated, a record that holds stays `stored`; a record older than the tool code is refreshed although all file rows hold; a reader that re-infers a stale seeded record replaces it for every other machine; a first `fault` of the cache is asked again and the owner is taken (`retried` 1, `computed` 0); two manifests never share a slot (classifier keeps both, old slot collects one); **key law** (pool = reader = Python model, root of another machine gives the same digest, selected targets/inputs); too heavy owners are handed to the inference last and nothing waits on the server; provider ports localize.

Updated: `PN/🧪️tests/{🚪️away,📈️inferred,🚦️governed-dispatch}` keep their literal pins (the take look is `lookProject`, not `inferProject`; `prepare:farm?()=>{missed.add(name);return away(()=>farm.prepare(` is intact). Existing suites that ran green in `ws` and under the lock: owner-pool 19, project-records (6 directories), wanted (4 directories), memory (7), project-nodes (8), farm 30, present 4, fleet-read 5, stopped-wave 5, sidecar pool 5, the R67 list (ready 25, process-tree 9, walk 5, storage 3 + 2), both standing preflight tests.
Private end-to-end (`proof/reader-e2e.mjs`, real pool children, real reader code, private cache server, workspace copy): found two real defects that the unit laws could not (the farm-less compute hole of the look, fixed with `away.take`; the provider-port rows). The harness cannot enter the graph-writer custody, so a reader that must INFER fails there ("Original bounded graph writer custody required"); the take path to the point of the record holding in a harness without `phaseControl` is therefore not proven end to end (see section 6).
