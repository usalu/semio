## 2. Why two versions are installable under the name `typescript`

Measured in `bun.lock`: `@bytecodealliance/jco@1.39.0` (declared exactly in the workspace) depends on `typescript` EXACTLY `7.0.2` and on `typescript-compiler-api` = `typescript@6.0.3`; everything else asks `^5.9.3`. An npm-style tree holds one `typescript` per directory, so the lock records `typescript@5.9.3` at the root and `@bytecodealliance/jco/typescript` = 7.0.2 NESTED (`bun.lock` line 16256; same pair in all 12 generations under `.cache/b/d/m/j/*`). The 7.x package is the native compiler: `exports["."]` is `./lib/version.cjs` (version only, no API).

Can the `dependencies` stage give different hoisting per machine? From what is on disk: the install is `bun install --frozen-lockfile`, linker `hoisted`, bun pinned `1.4.2` in the generation `package.json`, and the lock names the nested position explicitly, so a complete install gives the same placement on every platform (all 12 local generations: root 5.9.3, nested 7.0.2). A layout in which bare `typescript` is not the root 5.9.3 therefore comes from outside a complete frozen install. Candidates I could not verify here: (a) the parser-only install of the build bootstrap ("closure mode", parser slot `w/128`, present but empty in a full install) or an interrupted or partial install; (b) a code location with no `node_modules` above it (Bun auto-install would then answer the bare name with whatever the registry calls latest; NOT tested); (c) a module half loaded when the disk is full (g1-m01 was at 98.9 percent used): the interface checks the API as well as the version, so (c) is a typed refusal too. None of this needs a different `dependencies` result per platform; what matters is that nothing checked it.

## 3. The interface

New member `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/🚀️bootstrap/🔷️typescript-compiler/` (schema `🧬️schema/🔣️.json`, `🟨️.mjs`, `🟨️.d.mts`): the only place that loads the compiler.
- Declared version: `📦️parsers/package.json` `devDependencies.typescript`, which must be exact (`5.9.3` today); a range or a missing field is the refusal `typescript-compiler-declaration`.
- Resolution: never the bare name. Two declared directories in order: the install slot of the parser package (`📦️parsers/node_modules/typescript`), then the direct dependency of the workspace root (`<root>/node_modules/typescript`; root = nearest ancestor of the module with `bun.lock`). Each candidate is read by its `package.json` (name `typescript`, version equal to the declared one); only a match is loaded (absolute path of its `main`), then version and the API listed in the schema (15 functions, 4 objects: `preProcessFile`, `createSourceFile`, `resolveModuleName`, `sys`, ...) are verified.
- Refusal: `TypescriptCompilerRefusalV1` (`code`, `retry` always `never`, `wanted`, `resolved`, `found`, `missing`, `tried[]`, `en`, `de`; schema `Refusal`; message = English + " / " + German). Codes: declaration, absent, version, api.
- Exports: `typescriptCompilerV1(options?)` (cached per path and version), `inspectTypescriptCompilerV1` (manifests only, never loads the 9 MB compiler), `typescriptCompilerFileV1` (main file path, used for the revision hash). Types are own record types only (`TypescriptCompilerV1` is `{version} & Record<string, any>`); no type of the compiler package is exported.

Routed through it (bare name gone): `📦️parsers/🟨️.mjs` `parserTypescriptV1` (so the inference reader `⚡️caching/📥️inference`, `🧭️script-inputs` and every `parserTypescriptV1()` user), `🕸️dependencies/🟦️typescript/🟨️.mjs` (`parseRuntimeImports` and the revision hash), `…/⚙️configured/🟦️.ts`, `🎛️commands/✅️verify/🔷️typescript-project/🟦️.ts` (child and installed check), laws `🧩️plugin-consistency/…/🧪️diff-only-law`, `🔬️interactivity-audit/🧭️all-app`, `🧫️test-store-isolation` (type-only namespace shim), `🧹️normalization/🧪️support/🏗️source-services`.

Left on purpose (each with its reason in the law's table; the law fails when an entry stops loading by bare name): `🏗️build/🟦️typescript/🧩️units/🔌️repository` (typecheck unit of one project: that project's own compiler, a member may declare another version; the same hoisting exposure remains there, anchored at the project directory), hermetic provider `🔷️typescript` and `🏃️process/🏗️build/🟦️typescript`, `⚡️caching/📦️artifacts/🟦️typescript` (tsc binaries of the project or workspace they build), `…/🧬️declarations` (compiler of the workspace it builds, anchored at that directory), `✅️verify/🧟️generated-corruption` (anchored at the explicit root), `🏃️process/🛠️repository-tooling` (framework module, tsc path from the caller's directory), `🧪️test/🗺️test-layout` and `…/📄️retirement-file/🧪️.ts` (test module and framework test support cannot import the repo product; test-layout has 115 uses). Files under `🧪️tests` and `🧪️testing` load the compiler as an oracle and are outside the law.

## 5. The `dependencies` stage verifies the compiler

`🌐️remote-execution/🛰️sidecar/🚦️ready`: new refusal code `tooling-compiler` (EN and DE). After a `dependencies` run that exits 0 the loop asks the port `compiler` (real: `inspectTypescriptCompilerV1({root})`, two manifest reads); a refusal turns the stage into a failure (back-off, not recorded done, typed text in the tail and in the `ready.json` refusal). Every loop turn also checks a `dependencies` stage recorded done earlier, so machines that were green before the check existed show the wall in `dependencies` (the record is dropped, the failure stored with back-off). Tests `🔷️tooling-compiler` (4), ready main 40/40, resume 8/8, probes 4/4, stage-plan 2/2.
