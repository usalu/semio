# R1: the dependency store wait that never ends

Landed 2026-11-15 03:20 under `T/landing.lock` (entry in `T/landings.md`, originals for `land.py --rollback` in `T/🗑️generated/R1-landing-032036`). Script: `T/🧰️scripts/R1/{land.py,payload.py}`.

Paths below are relative to `LIB` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`, `PUB` = `LIB/⚡️caching/💾️storage/🔒️enforcement/📦️budget/📥️opening/📤️publication`.

## 1. Cause (from code, not proven on the worker)

1. The printed line comes from `retryWhileDependencyStoreBusyV1` (`PUB/⚙️setup/💰️funding/🟦️.ts`, line 25 before the change, `say` at line 30; text `LIB/⚡️caching/📖️texts/🔣️.json` `dependency-store.waiting`). It loops while `attempt()` returns `acquired:false`.
2. `acquired:false` is `withProtectedMaintenanceParentV1` (`🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/💾️storage/📤️publication/🌐️platform/🟦️.ts`): it takes the lease `native-fixed-image:<dependencies image>` in mode `exclusive` with `timeoutMs:0` and maps "Resource lease timed out" to `acquired:false`. Both users of the wait (funding parent in `withFundingParentV1`, producer preparation in `PUB/⚙️setup/🟦️.ts`) need that exclusive lease. A lease is an SQLite file lock held by a living process; any other holder in any mode (shared too) makes the attempt fail.
3. Who holds it shared: `repo run` itself. `LIB/🏗️build/⌨️command/🏃️task/🟦️.ts` wraps the whole task graph in `withRepositoryCacheStoreV1(root,"dependencies",...)`, and `LIB/🏗️build/⌨️command/⚙️runtime/🟦️.ts:8599` does the same for every other `repo` command. An opened store is a shared borrower of `native-fixed-image:<dir>` for the lifetime of that command. So `repo run workspace:setup` (pid 67978 in the evidence) holds the dependencies image shared for the whole run, and its descendant `repo tools setup all` (73661, task `workspace:deps-build-tools`, added by N1) asks for the same image exclusively. The descendant cannot succeed until its ancestor ends, and the ancestor ends only after the descendant: a self-deadlock across processes. A standalone `repo tools setup all` works because `runtime.ts` calls `setupRepositoryDependencyPublicationV1` before it opens the store itself; only N1's placement beneath `repo run` exposes it.
4. Nothing in the old wait looked at the registry, so the line named nobody. The lease registry (`🧰️framework/🔨️modules/🏃️process/🔒️leases/🧭️order/🗂️registry/🟦️.ts`) already records pid, command, start and the held resources of every holder; the lease order checks skip non-blocking requests (`timeoutMs:0`), so no self-deadlock rule ever fired for this wait.
5. Dead holder: SQLite file locks vanish with the process, so a dead holder cannot keep the lock itself. What stays is its registry file (the registry only prunes entries when someone reads with prune on, and treats an entry as live up to 300 s after the last heartbeat). The earlier tries that were interrupted with SIGINT therefore cannot be the lock holder unless a survivor exists; the evidence process list shows only the graph service host 41996 (not an ancestor, not shown holding anything). Not proven: the registry was not read on the worker, so the holder is inferred as the ancestor `repo run` (67978), not observed.

## 2. What changed (4 files)

- `PUB/⚙️setup/💰️funding/🟦️.ts`: `observeDependencyStoreHoldersV1(directory,resource,ports)` reads the registry entries of the lease directory and returns the live holders (pid, command, since, mode, `ancestor`) and the gone ones. Ancestor means: this process, or a parent found by `ps -o ppid=` (PowerShell on Windows) whose registered start is not later than ours (a reused pid of a dead holder is not an ancestor). Entries of dead holders are removed at once and reported. `processAncestorsV1` is the pure walk. `dependencyStoreWaitPortsForV1(lease)` adds the lookup to the default ports; both call sites pass it (funding parent and producer preparation in `PUB/⚙️setup/🟦️.ts`).
- Loop behaviour in `retryWhileDependencyStoreBusyV1`: (a) if every live holder is an ancestor for `ancestorGraceMilliseconds` (15 s) the wait ends with the refusal `caching.dependency-store.ancestor-holds` (code `refused`, English and German, names pid, command, since) instead of waiting up to 21600 s; a sibling holder next to the ancestor keeps the wait alive; an ancestor that lets go inside the grace is simply waited for. (b) a gone holder is logged as `dependency-store.holder-gone` (warn) with pid, command and since, and its entry is deleted. (c) the progress line names the blocking holder (`dependency-store.waiting-for-holder`: pid, command, since, seconds of limit); without a registry entry the old line is used.
- `LIB/⚡️caching/📖️texts/🔣️.json`: three new messages (sorted, both languages).
- Tests in `PUB/⚙️setup/🧪️tests/⏳️busy-funding/🟦️.ts`; the static wiring test was updated to the new call form.

## 3. What this does NOT do

It does not make `repo run workspace:setup` pass `deps-build-tools`: the exclusive maintenance still cannot coexist with the run's own shared store hold, and releasing a hold of a running `repo run` is a change of the run's store lifetime (`task/🟦️.ts`) that I did not make blind, with no graph command allowed on this machine. What it changes: the six-hour silent wait becomes a refusal after 15 s that names the ancestor, so the next report proves the cause. The structural fix still to take (needs a machine where `repo run` can be exercised): either run `repo tools setup all` once as a standalone command before `repo run workspace:setup` in `native-bootstrap.sh` and have the task skip when the funding is current, or let `repo run` open the dependencies store only after the tasks that need exclusive maintenance have run. Decision for the coordinator.

## 6. What a worker's next try must show

During the stall, within about 15 s after the first wait line: either `Process <pid> (<command>) holds the dependency store since <time>; waiting for it` (a real sibling, expected to finish), or the refusal `Process <pid> (<command>) started this command and has held the dependency store since ...` with `<command>` = `... repo run workspace:setup` (cause confirmed), or `... no longer exists; its claim was removed` (a dead earlier try). If none of the three appears and the old line `Another process holds the dependency store` still prints, the holder is not in the registry (an unregistered process) and the next step is to read the lease file of `native-fixed-image:` directly.

## R1b: proceed under the ancestor's hold (prepared, NOT landed; waiting for LAND-OK)

Script: `T/🧰️scripts/R1b/{land.py,payload.py}` (T = the FLEET-ONE-MACHINE ticket). `land.py --dry-run` against the live tree after R1: `dry run: 4 files, 0 refused, 0 invalid` (edited files parse with the bun transpiler, every relative import resolves). Not landed by order of the coordinator.

**Mechanism chosen and why.** The siblings do not give a mechanism to reuse: `deps-js-all` writes into the dependencies image as a consumer (`withRepositoryCacheStoreV1(...,"dependencies")`, shared hold plus the finer `build`/`bindings`/`writer`/pin leases of `bootstrap/📦️dependencies/🚦️concurrent`), and `deps-go`/`deps-cargo`/etc. (`bootstrap/📦️dependencies/🏗️native`) write into the tools store and workspace environments, not into the funded image. Only the funding step (`setupRepositoryDependencyPublicationV1`: funding parent, producer preparation, retirement, reconcile) needs the exclusive whole-image lease, and the native layer proves exclusivity with a kernel lock, so it cannot run beneath a shared holder. So design item (2) was implemented; item (1) was not.

**Item (2), implemented in the payload.** In `PUB/⚙️setup/🟦️.ts`, before the first exclusive observation: if the registry shows the store held, every holder is this process or a live ancestor (registry entry of a live pid, started no later than this process, pid on the real `ps` parent chain) and every hold is shared (`dependencyStoreShelteredByAncestorV1`), and the image envelope is current with nothing pending, and `readRepositoryDependencyFundingCurrentV1` finds no funding journal beside the image and a marker `dependencies.json` that names `repository:dependencies-store` with the whole declared `filesystemBytes`, the step ends with the line `dependency-store.current-under-ancestor` (en/de, names pid, command, since) and no exclusive access. Otherwise nothing changes: it asks for exclusivity, and with only ancestors holding, the 15 s typed refusal of R1 stays as the honest answer. Skipped in that case: producer preparation, retirement of obsolete generations, funding reconcile (they run on the next standalone `repo tools setup all`, which I ran: exit 0, bazel ready, 7 min). Known gap, stated in the docstring: the currency check reads the marker and journal file as a reader; a journal row that disagrees with the marker is only visible to the exclusive observation.

**Item (1), not implemented.** `repo run` performing the exclusive funding before it takes its hold would have to run the step under an Original whose arguments are exactly `tools setup all` (twelve purpose checks in `PUB/🟦️.ts`), i.e. spawn a nested `repo tools setup all` before opening the store, from inside the run kernel in `LIB/🏗️build/⌨️command/🏃️task/🟦️.ts`. That change to the core run path cannot be proven without repeated graph runs on this machine, and it only matters when funding is missing (fresh worker); there the R1 refusal fires after 15 s with the ancestor named. Decision for the coordinator: on fresh workers run `repo tools setup all` once standalone first, or approve item (1) as its own package.
