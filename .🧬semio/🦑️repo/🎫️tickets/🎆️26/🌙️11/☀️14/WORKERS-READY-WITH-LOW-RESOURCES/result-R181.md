Risk accepted by B: a change of code outside the surface that really changes what a task outputs (for example the process authority starting commands with another environment, the cargo-neutral parts of the unit cache, the plugin projection logic that does not show in the target options) does not move the hash until someone bumps `semantics.revision`. What guards it: (1) the per-task declared inputs, command line, options and tool versions that Nx hashes anyway (a changed projection of a target shows in its own options); (2) the surface files are byte-keyed, so the argument wire and the executors cannot change silently; (3) the task semantics law records the wire per revision; (4) the Cargo determinism law of the offload tests compares rlib/rmeta across checkouts and fails when the cargo argument builders change what is compiled; (5) the Python oracle law. NOT guarded: behaviour of the process authority below the executor (environment scrubbing, working directory, sandbox), which only a human bump of the revision (and a fixture of the real executor plan, which could not run outside `repo test`: the Nx cache namespace refused the plain bun process) can cover.

## 5. A2: the supervisor ends a read only for declared semantics (staged)

Old rule (R151/R176): a stage in the reading phase for 30 minutes (x speed factor) is killed when ANY file below three code roots (`🧰️framework/🔨️modules/🏃️process`, `📚️library/⚡️caching`, `📚️library/🏗️build`; `.ts .mjs .js .json`, not tests) has an mtime after the phase start; a stage waiting on a named holder for 10 minutes the same after the stage start. With 50 machines editing, that means "every 30 minutes a read ends".
New rule: policy `semanticsSources` (schema `🌲️process-tree`) replaces `codeRoots`, `codeExtensions`, `codeSkipDirectories`: two declared constants, `selected-exchange/🧬️schema/🔣️.json /definitions/Policy/const/revision` (the R171 head key revision: what another machine accepts from a sealed read) and `👁️observation/🧬️schema/🔣️.json /$defs/record/const/stamp` (the persisted record format). `readySemanticsV1(root)` reads both values at the start of the stage (two small files, never a tree walk), `readySemanticsChangedV1(root,before)` names the source whose value now differs (an unreadable source, as during a landing, is no change). The kill conditions `readyStaleStopV1` (reading or unknown phase, stale age) and `readyHolderRestartV1` (holder wait) stay as they were, only their trigger changed from "a file changed" to "a declared semantics source changed". The edit of any other file ends nothing: the stage seals under the implementation it loaded, the next stage start loads the new code. Edited: `🌲️process-tree/🟦️.ts` (`readyCodeChangedSinceV1` removed), schema, `🚦️ready/🟦️.ts` (baseline `semanticsAtStart` taken with the tree policy). Tests: process-tree `🟦️.ts` (the old file-scan test replaced by two: semantics changed only by a declared value; the two sources exist in the checkout and hold a number and a `semio.graph-record/N` stamp), `🕰️stale-stage` (all file touches that meant "code changed" now bump the declared value; new law: tooling files rewritten every 100 ms for the whole 2.7 s run, the stage is never stopped), ready main test (holder restart uses the declared value; another file edit lets the holder wait go on).
Staged results: process-tree 16/0, stale-stage 14/0, ready main 41/0, resume 8/0, stage-plan 2/0, tooling-compiler 4/0, probes 4/0. Red on the old code: stale-stage 5 of the rewritten behaviours red (14 tests, 9 pass 5 fail), process-tree test red at import. The churn law is green on the old code only because the new policy has no `codeRoots` (old code scans nothing); the old behaviour it forbids is proven by the old e2e test it replaces (a single touched file stopped the stage after the stale age).

- Anyone who changes how a task is started (executor surface, owner argument wire, Cargo argument builders) is covered by the surface bytes; anyone who changes the process authority, the environment given to commands or other behaviour outside the surface in a way that changes task OUTPUTS must bump `semantics.revision` in `🧮️engine-digest/🔣️.json` and append a history row in `🧪️tests/🔖️task-semantics/🔣️.json` (outputs hash printed by the failing law). A plain bump without a changed wire needs its own row.
- A new test dir needs its name in the taxonomy first (`🔖️task-semantics`, `🔒️loaded-implementation` were accepted by the taxonomy as written; if discovery complains, that is the cause).
- The `spawn-only` test of the engine-digest suite stays red on live and staged code (`🏗️build/📜️script.ts` is reachable from the executor closure); pre-existing, not touched.
- Open: the owner records and the exchange head are still judged by the fact digests of the files they read; only the implementation files are now facts of the process. Tooling files read as DATA inputs (a script that the graph reads as an input of an owner) are still facts of the tree, correctly.
