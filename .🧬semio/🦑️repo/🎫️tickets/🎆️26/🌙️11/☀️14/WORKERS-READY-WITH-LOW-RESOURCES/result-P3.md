## Verdicts
1. **Server blocked its own queue: FIXED (tests, not live).** `runWantedServerV1` blocked in one read of up to 45 min (old `inferTimeout`), serving only between reads; a request arriving during a refresh waited for it (and the refresh was killed at 2700 s every time: build-agent.log 13:20, 14:57, 15:52 "ended with status 1 after 2701 s"). Now the loop is non-blocking, every 5 s it takes over live requests (claim), writes `priority.json`, reads `pending.json`, answers incrementally and keeps a sign of life (heartbeat 20 s), starts a read only if none runs. Steering: waves take `names=sorted dirty` first 48 (`generations/🟨️.mjs`, `scaledOwnerWaveV1`); `orderOwnersV1` now puts the priority owners first (new module `🕰️generations/🧭️steering`, schema first), and after every plan and every published wave the read writes which priority owners are still dirty; a priority owner that is not dirty is fresh in the server's tree.
2. **"0 taken" / "0 arrived": cause proven, FIXED.** (a) The reader never looked at records at all: `taken` came only from the served-answer document, which the server wrote only after a whole read. (b) The fleet record key contained the producer's module-load state: `projectRecordStateV1` hashed `authorityText` (all `loadObservations` rows = data/policy/schema files read while loading the inference code) although the record itself declares no authority (stored headers: `authority:[]` in 2870 of 2870 decoded records; header digest = sha(stamp, null, key)). Proof from the production cache (read-only, `scratchpad/p3/an2.py`, `an3.py`): of 2861 projects with a record, 8 have two records 4 h apart: same header digest, different state digest (e.g. `9202aa0cb1` 12:16 vs `9dc058a830` 16:24), i.e. the key moved with unrelated tree state; 620 of 620 projects present on two platforms have the same header digest (the project key itself is machine and time independent). Fix: key = (inference revision, project identity, platform, project root), no authority; the record carries its observations and the taker revalidates them against its own tree (`lookup`), so equal project inputs ⇒ reusable by any machine and generation. A fleet record that does not hold in the taker's tree is replaced by the taker's (seeded gate publishes; `offer` re-offers when the local record file changed: marker = digest:size:mtime). "Arrived": the served answer is now a live set (fresh-from-pending), refreshed every round with a heartbeat; records are taken by the normal inference gate (hits) with the new key. NOT done: a reader-side probe that counts arrival by looking up records directly (needs the project keys of the wanted projects, which only the inference setup computes). After the first round with this code all old records (old keys) are unreachable; the next full refresh re-offers every local record (bounded 64 pending).
3. **Request size and bound: confirmed + FIXED.** The 703 are the stale part of the worker's slice (request.dirty of the slice read). The server infers whatever `repo show projects` finds dirty (its whole tree), steered first to those. Rate: not re-measured (earlier 60-90 projects/min ⇒ 703 ≈ 8-12 min). Reader bound now tracks progress: refuse after `silenceMilliseconds` 300 s without any sign of life of the server, after `waitMilliseconds` 900 s without a new arrival, `waitMaximumMilliseconds` 2 h; steady arrivals extend it (test: 1000 projects, 5 s apart, outlives 15 min). Served answers older than the request ttl are ignored.

## Round 3 follow-up (17:22-17:27 UTC): why the server served nothing, and the fix
- **Cause, proven read-only on the live server:** the build agent of g1-server runs with `SEMIO_REMOTE_CACHE_INSTANCE=semio` (and ENDPOINT `:6090`, ACCESS read-write); the workers' bootstrap unsets those variables, so they use the instance the fleet announces, `main`, on `:6094`. `graphFleetSettingsV1` with the agent's environment gives instance `semio`, with the stripped one `main` (script `scratchpad/p3/rd2.ts` vs `rd3.ts`): `readWantedV1` for g1-m03/m06/m07 returned `undefined` in `semio` and the live 703-project requests (expiring in about 1000 s) in `main`. The server therefore never saw a request and also published its records into `semio`. The loop was alive (refresh started 16:59:39), `mayServe()` was true (host view: totalMegabytes 32768), no claim was live (claims.jsonl: no unexpired claim in the last hour; the claim of g1-m08 had expired and every new try has a new key through `createdMs`, so a stale claim never blocked).
- **Fix (one landing under the lock, 17:23 UTC):** `graphExchangeEnvironmentV1` drops the explicit remote cache overrides from the environment of the graph server and its reads (client, settings, child `repo show projects`), so exchange and project records use the fleet's instance like the workers. Heartbeat: `graph-server: alive, N machines seen, M requests held, read none|request|refresh` every 60 rounds (5 min). Tests: sidecar graph 8, server 11, wanted 6.
- **Observed after the landing:** build-agent.log 17:23:40 `graph-server: serving 703 stale projects for g1-m03` (and m02, m07, m06; 509 for m01); a `show projects` child is running (4.5 GB growing), `.cache/f/graph-server/priority.json` holds the 5 requests. ## Round 3 gap: arrived but not used (landed 17:50 UTC under the lock)
- **Cause (code):** "arrived" was the server's plan ("not dirty in my tree"), but a fresh project is never inferred by the server's read, so its record was never uploaded under the fleet key: the only upload paths are `publish` after a compute and `offer` at a local hit, and a fresh owner is not visited. The worker's builder did look the records up (the gate precedes the farm and the compute) and found nothing. Also `offer` dropped everything beyond 64 pending uploads.
- **Fix:** before every wave the server's read runs one pass over exactly the priority projects that its plan lists as fresh (`offerFreshPriorityV1` in `discoverPart`: `prefetchBuildGraphProjectsV1` on their roots, a local hit offers the record, nothing is inferred), once per project; `offer` now waits for a free slot instead of dropping; the port prints `graph: N projects taken from the fleet, M inferred here` (EN/DE) every 50 decisions in the worker's inference, and the existing `[fleet] ...` summary at the end of each pass. The worker's own builder takes records through the same gate (new key, verified against its tree by the local lookup) and infers only what is missing or does not hold. Tests: fixture "arrived but partial" (8 asked, 5 fresh offered by root, 3 dirty left, none twice), failing pass tolerated, burst of 150 offers all stored, progress line, steering `freshPriorityV1`.

## Round 5: `request-failed dad6d735 Error` after `2 taken` (landed under the lock)
- **Cause:** the throw is `Observation leaf changed before delivery`, from `physical.recheck()` at the end of `readInferencePhysicalRecordV1` (stack col 284 of line 1030 = the leaf fence). It fires when the record file at `cachePath` is replaced between the read and the delivery: a farm worker, the fleet take (`importProjectRecordV1` renames over it) or a peer writing the same project while the parent looks it up. A race, not damage and not a field the reader rejects. The empty message was only the way the service log printed the stack.
- **Fix:** `readInferenceRecordOrMissV1` (lookup): a replaced leaf is read again up to 3 times, then, like a damaged record, is a miss with one line (`graph: the record of <dir>/<file> cannot be read (<reason>), inferring the project here / ...`); the error has the code `BUILD_INFERENCE_LEAF_CHANGED` and a full message; every other failure still fails. Test `🍂️leaf-race` (3): replaced once/twice read again, keeps changing and damaged are a miss with one bilingual line, absent has no line, other failures keep their message.
- Round 6 should show, if the race recurs, the `cannot be read ... inferring the project here` line instead of a failed request. Not verified live.
