# Coordinator Replica Recovery With a Live Heartbeat

At 09:23 UTC on November 21, the native heartbeat still identified daemon 50009 and supervisor 77538. The owned daemon lock named the same child. The heartbeat reported a live event loop with about 50 ms lag and activity `git`, while the last normal health publication remained at 09:14:04. There was no direct Git child at the sampled instant. The coordinator held journal cursor 176:51749 and had not emitted any of the 1,947 expected stage registers.

The CLI exposes no authenticated local restart request. Code adoption can set a restart flag and wake idle sleep, but the outer loop first waits for its current turn. The current store guard abandons a turn only when an independent store probe and operation progress are both overdue. A responsive store path does not time out an unrelated indefinitely pending local Git operation. The native boot watchdog separately checks inbound heartbeat freshness and event loop lag. A live timer can continue throughout that kind of asynchronous hold. The recorded activity class does not identify the exact filesystem call or lock holder.

The installed macOS LaunchAgent is `gui/501/tech.semio.fleet.replica`. Its loaded service had KeepAlive enabled, a 5-second throttle and a 30-second service exit timeout. The installed `boot.sh` traps SIGTERM, forwards it to its recorded supervisor child and waits. The native supervisor asks its exact daemon child to stop and waits 20 seconds by default before forcing that child to end. Launchd then re-enters normal boot, which performs current-worktree admission and signed fallback selection as usual. This is narrower than changing the service or signalling a PID or process group directly.

Before the recovery, graph reader 43705 was in detached runner 43704's process group, and Cargo processes 28650 and 32202 were in separate groups and had unrelated detached ancestor trees. An orderly terminal replica stop can still stop its explicitly managed sidecars. The graph sidecar's stop checkpoints and detaches its observer, leaving the runner alive for reattachment. The graph runner has a 30-minute orphan window while no observer renews its watch file.

The coordinator recovery used the service boundary and reached the supervisor's bounded stop fallback. The successor ran PID 75191 and published an attestation on code `13ae325fe423` at 09:25:47. Both Cargo processes and the original detached graph runner and reader survived with the same process identities. At 09:26:07 the new graph server logged reattachment to reader 43705. Author journal segment 176 advanced from byte 51,749 to 671,391. It contained 1,986 newly closed events, including all 1,947 expected stage register actions, consisting of 1,942 links and 5 deletes.

The three existing installed-entry and supervisor SIGTERM fixtures passed with 20 assertions. These cover the service shim, verified graceful reload with its detached stage and the blocked versus clean supervisor exit paths. The coordinator observation was read-only from this task.

An automated extension should act only on a named owned operation with explicit completed-work progress. It should require stale local operation progress and independently stale successful attestation publication, a fresh successful store probe, and the exact child in its run phase. Idle, capacity waits and unrelated transfers stay outside this gate. Cancellation must preserve the original writer and admit no further mutating turn until the child drains or the supervisor ends that exact child at its own bound. A separate diagnostic and restart backoff avoids misclassifying this as evidence against a newly admitted binary.
