## What the code does (verified by reading, `🔁️replica/🟦️.ts` autoCompactV1 / fleetCompactV1, `🗜️compaction/🟦️.ts`)
- **When.** The daemon loop calls `autoCompactV1` every round; it only starts if `automatic`, origin == `<group>-server` (here `g1-server`, this Mac, daemon pid 14996), not already running, and the last attempt was >= 10 min ago. Then it compacts only if there is no snapshot, or >= `snapshotEvents` (100,000) events behind the newest snapshot, or anything behind and the newest snapshot is >= `safetyHours` (3 h) old. Newest snapshot is from 2026-11-18 03:30 (about 21 h old): **the first run starts on the first round after the daemon restarts into the new code**; afterwards at most every 3 h (each run writes a new snapshot), or sooner after 100,000 events. A skipped run (locked/refused/aborted) is retried after 10 min.
- **Config reach.** The daemon reads the topology at start; the json is in its code digest, so **every replica daemon of the fleet self-restarts** after the landing (like any landing under the module). Workers get only the jump (`catchUpEvents` 20,000, tested), not compaction (server-only).
- **Lock.** `v1/compaction.lock` (mkdir, refreshed every minute, taken over after 2 h; a killed run keeps it up to 2 h, next attempt says `locked`, harmless; shown in R172).
- **Safety.** Snapshot written first and re-read whole (`scanSnapshotV1`); journal segments only below the snapshot cursor, below the head, older than 3 h, below every fresh synchronising origin's attested cursor, as a prefix; blobs only when neither the snapshot nor any later event names them and mtime >= 3 h, via rename to `v1/trash`, re-read of events appended meanwhile, put back on a race; a vanished segment aborts and restores; kill at any mutation proven by `💥️killpoints.ts`.
- **Silent / never-attested origins.** `readHoldersV1`: attestation older than `staleHours` (12) -> `stale`, `sync` off -> `off`, retired, or no attestation -> `unattested`: none of these hold anything back. So **g1-m09 (no attest.json at all) never blocks**, and g1-m04/g1-m06 hold segments back only while their last attestation is < 12 h old (now all attested within 3 min, cursors present); at worst a segment stays 12 h longer. Segments are small (29 files, 40 MB); the 43.8 GiB are blobs, which no holder influences. A replica that returns after its segments went resumes from the newest snapshot (`rejoin`, no data lost; test "a replica whose cursor points into a removed segment resumes ... whether it attested long ago, never ..."), `rejoin-required` only if no snapshot is ahead. A returning replica reading an old event whose blob was reclaimed (a version superseded by the snapshot) gets one `blob-missing`, the entry stays queued and is superseded by the later event (documented in the README, laws "a publish that races ...", "a file that went back ..."). No defect found that makes it unsafe or blockable forever: **no code fix was needed**, so no red-first fix; the change itself is test-first (below).
- **IO cost (estimate from code and R172, NOT measured live).** One full fold of all journals (about 40 MB of segments) and a snapshot write of about 100 MB plus a re-read; a directory listing/stat of every blob (R172's deep report took 35 s under load); then rename + unlink of about 94,257 blobs (43.8 GiB, from R172) and snapshot pruning to 2 (about 2.3 GiB). It runs in the server daemon's own process (async, cancellable, `progress` stages `retire`, `reclaim`, `litter`), not a child. Afterwards about once per 3 h with a small amount of garbage (0.6-1.7 GiB per day).
