# Resident startup ownership

The resident plan and consent-restart clients previously claimed a pathname with exclusive create and wrote a JSON PID record afterward. A contender treated either incomplete JSON or a live writer past the configured 120-second age as permission to remove the lock. An earlier client’s unconditional pathname cleanup could then remove a successor’s claim. Two separate local starter processes reproduced both duplicate physical startup callbacks and removal of the replacement pathname. The long cold g1-m05 wait prompted the investigation. Its worker evidence does not establish these races occurred there.

The cold client now claims the existing per-implementation startup or consent-restart name through the repo’s physical file lock. Exclusive creation supplies an empty stable file. Each contender opens that file and attempts a nonblocking kernel claim, keeping its descriptor only while it owns startup. It never parses, replaces or removes the file. The kernel releases ownership when the original descriptor closes or the process dies. An owner checks the socket again under its grant before invoking the spawn callback. The existing liveness polling, silence deadline, hard wait ceiling and transport failover still apply. Cancelling a waiting client does not send any signal to the active client or service.

The native launcher currently registers only Bun 1.4.2 for the repository CLI. The graph plan/start and consent-restart entry points use that launcher. The framework’s separate Node adapter has no declared resident startup route. The native lock module is loaded only on the cold path. On POSIX the private directory and stable file are tested at modes 0700 and 0600. On Windows the file remains in the existing per-account runtime directory. The existing kernel32 backend holds a byte-range lock on its own handle and closes both contended and successfully acquired handles.

The private schema fixture uses separate startup clients, actual local sockets or pipes, and SQLite to count spawn callbacks. It exercises a live owner beyond the former age, an empty already-held file, forced pathname replacement before late release, process death, waiter cancellation, startup timeout and consent restart. The original code failed the first five boundary cases. The new fixtures and the existing Windows backend suite passed 13 tests with 615 assertions on macOS. The Windows handle-settlement checks used the existing Win32 model and the independent Python layout oracle. The live Windows kernel case requires a Windows host. No real resident service was started, stopped or restarted for verification.

The grant covers the startup client’s lifetime. A detached child that survives the death or cancellation of its own launching client remains outside this grant. A hot socket can be reused immediately. The private abandoned-client fixture recovers before any service has bound its socket, so it does not establish a service-child custody handoff between clients.
