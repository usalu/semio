# R224: a landing is applied new files first, and a module that arrives late is waited for

Package R224, 2026-11-19. Problem from `result-R222.md` section 5: on Windows worker g1-m05 the new directory `🌡️host-capacity/🪟️native-memory` arrived more than 90 s after the modified `📡️sampling/🟦️.ts` that imports it; every CLI start in the gap failed with `Cannot find module`, six restarts (about 77 s), exit 75, one attempt lost.

## 1. Cause (read from the daemon code and the live store)

- **The publisher is not the cause.** The journal of g1-server (`/Users/Shared/semio-store/v1/origins/g1-server/segments/000000000155.jsonl`, lines 3501 to 3531) holds the R222 landing in the right order: the five `native-memory` files at hlc `1795046402618` (00:00:02.618), the 22 modified files (`📡️sampling/🟦️.ts` among them) at `1795046403049`, 0.43 s later. New files first.
- **The applier is the cause.** `applyQueueWork` in `🧰️framework/🛍️products/🦑️repo/🔨️modules/🤝️shared-worktree/🔁️replica/🟦️.ts` took `replica.queue.snapshot()` (ascending path id) and applied creations in one pool. A path id is assigned when the path is first seen, so every EXISTING path has a lower id than every NEW path: with a queue of any length all modifications are applied before all new files, whatever the publisher minted. There was no dependency order at all; a new file that fails once (blob not readable yet, sharing violation, directory in the way) is `queued` with a cooldown of up to 30 s while the modification that imports it goes through.
- **Measured (attestations in the store, `origins/*/attest.json`, `latency.applyMs`, last 100 applies, at 2026-11-19 00:15 to 01:30 UTC):** g1-m05 (windows) p50 407,087 ms, p95 450,491 ms, queue `incoming` 1,334, `failures: blocked` count 193,736, only 6 sweep passes and 21 hot passes; the macOS and Linux workers p50 0.2 to 6.8 s (g1-m01 0.2 s, g1-m03 1.5 s, g1-m04 1.1 s, g1-server 1.9 s); g1-m10 p50 134 s with `incoming` 4,326. A standing queue of 1,300 or more entries on Windows is the window in which the importer sat ahead of its import, and it is the same on every machine whose queue is long. The gap of the incident (more than 90 s) is inside one p50 apply time of that machine. I could not read the local replica log of g1-m05 (it is on that machine): the exact entry that held `native-memory` up (blob wait, sharing violation, or only its place at the end of the queue) is NOT proven; ordering plus the bounded hold below do not depend on which it was.

## 2. What was built

1. **Daemon: new files first, modifications held while a new file of the same landing is undelivered** (`🔁️replica/🟦️.ts`, `orderCreationsV1`, `releasedChangesV1`, two sequential pools instead of one). Creations are split into paths this machine does not hold (new files, new directories) and paths it holds in another version, each sorted by the event that minted it (`ms`, `counter` of the manifest columns, no allocation). The new ones are applied first and the pass waits for them; a modification is released only when no new file published up to 5 s after it (`deliveryWindowMilliseconds`) is still queued, and a new file holds modifications for at most 120 s (`deliveryHoldMilliseconds`, per file, so a stuck new file never freezes the rest). A held modification stays in the queue (`blocked` event, reason `delivery-hold`, count). Removals and the `.git/objects` pack rules are unchanged.
2. **Loader: a missing sibling module is waited for, not counted** (`🧷️format-stamps/🟨️.mjs` `missingSiblingModuleV1`, `staleImplementationOfV1` now carries `missing`; `🔄️reexec/🟨️.mjs` `awaitDeliveryV1` and the new branch of `runWithStaleReexecV1`). When the load failure is `Cannot find module '<./ or ../ path>' imported from <file>` (from the Bun `ResolveMessage` fields `specifier`/`referrer`, or from the message; POSIX and Windows spelling, decided by the referrer), the outermost command polls for that file every 1 s for at most 120 s in total (budget kept across restarts in `SEMIO_STALE_REEXEC_WAITED`), then restarts at once WITHOUT spending one of its 6 restarts (at most 30 such restarts, `SEMIO_STALE_REEXEC_DELIVERED`); a file that never arrives falls back to the old counted restarts. Packages and bare names are untouched. New protocol keys in `🧬️schema/🔣️.json` (`loadFailure.deliveryWaitMs`, `deliveryPollMs`, `deliveryRestartMaximum`, the two environment names) and texts `deliverywait`, `deliverylate` in English and German.
3. **Landing helper `🧰️scripts/R224/land-lib.sh`** (T = fleet ticket folder), the one way a landing script writes the live tree from now on: window wait (or exit 4 when the next window is more than `LAND_MAX_WAIT` 720 s away), lock `landing.lock` plus any `LAND_EXTRA_LOCKS` with own owner text, exit trap (also INT/TERM; a termination while writing restores exactly), bases compared under the lock (nothing written on a difference), NEW files first, wait for the replica delivery, bases compared again, MODIFIED files, `land_tests` hook (staged tests, `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0` exported), exact restore on any red (only files still holding our bytes are restored; directories the landing created are removed, children first). The delivery wait is a real acknowledgement (`land-ack.py`): it waits (60 s at most) until the journal of this machine holds a `put` for every new path, takes the head cursor after them, and waits up to `LAND_DELIVERY_LIMIT` (120 s) until every healthy peer (fresh attestation, sync on, `queue.incoming` at most 50) attests a cursor at or after that head AND an empty incoming queue (read everything, applied everything). Peers with a stale attestation or a backlog are named as skipped, peers that do not answer in time as `lagging`; the landing then goes on (bounded, never a freeze). Exit 5 (restore) only when the daemon of this machine never published the new files. Format schema `land-manifest.schema.json` (`land.tsv` lines `N<TAB>path` / `M<TAB>path`), texts `land-texts.tsv` (EN and DE, both printed unless `LAND_LANG`).
   Use: set `LAND_STATE` (scratch dir with `land.tsv`, `base/<path>` for every M, `new/<path>` for every line), optionally define `land_tests`, `. land-lib.sh`, `land_run R<nnn> "what"`. Worked example: `🧰️scripts/R224/land.sh`.

## 4. NOT verified

- The exact cause of the gap on g1-m05 at the level of one queue entry (see section 1); the effect of the daemon change on a Windows machine (none runs here); the real delivery time of a landing through the new order on any machine until the first landing with a new imported module after the daemons restarted onto the new code.
- No independent implementation oracle for the apply order (the daemon is the only implementation; the laws state the rule directly). The manifest schema is only checked by the pattern in Python; `land.tsv` is read by shell.
- A peer with a standing backlog above 50 (g1-m05 1,334, g1-m10 4,326 now) is not awaited by the helper; the helper does not help them, the daemon fix does.
- `🧷️format-stamps/🧪️tests/🟦️.ts` could not run on the overlay (reads the live sibling schemas); it ran on the base and runs under the lock on the new files.

## 5. What other agents must know

- Write landings with `land-lib.sh` (new files first, then wait for the delivery, then modifications). A landing whose new files are listed as `M` or whose new files are put in the same step as their importer reproduces the incident on any machine with a queue.
- Until the daemons run the new code (canary order, after the restart), every machine still applies old paths first; a landing that adds an imported module should wait for the acknowledgement (`delivery:` line of the helper) before the modified files, which the helper does.
- A new member directory of the replica module is not needed; the new test files are plain files in existing `🧪️tests` directories.
- The old fixed 6-restart loader behaviour is unchanged for everything but a missing sibling module (`./` or `../` specifier): a half-edited module that fails to parse still uses the counted backoff.
