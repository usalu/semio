# R192: why the whole-workspace read does not finish (walls A to D, living report)

Written 2026-11-18 from 06:37 UTC. Scratch: `scratchpad/R192/` (`base/`, `stage/`, `b2/`, `land.sh`, `land2.sh`, `csample.ts`, `pool-run.ts`, `preload.ts`). Everything before the landings was read-only on the live tree, the read and the fleet store. The 7-hour refresh read (pid 42303) was not touched.

## A. TypeScript "lacks the API": one cause, 1892 owners (not 187)

Numbers (`.cache/f/graph-server/read.log`, 31 616 lines, 2603 to 2652 of 4775 projects): 1892 DISTINCT owners carry `is set aside ... farm children could not infer ... (The TypeScript compiler of the tooling at .../typescript (version 5.9.3, wanted 5.9.3) lacks the API the tooling uses: createPr)`, 8 more `a worker could not infer project ... it is inferred in this process` with the same text, 36 other set-asides (`Native dependency has no build project owner`) and 4 (`closure references ... verdict stale`). The 187 of the audit were only the first lines. The faults are spread evenly over all 7 hours, so it is not a transient state.

Cause (reproduced, red first): the read, its farm children and its slice workers do not run the tooling from the files; they run a CAPTURED immutable implementation (`ps`: `bun --eval` of the loader in `📥️source/🔏️closure/🍞️bun`, snapshot named by `SEMIO_GRAPH_WORKER_SNAPSHOT`). In that loader `createRequire(...)` is replaced by `capturedCreateRequire`; a captured module may only load requests the sources DECLARE as literal sites (`closureLiteralSitesV1`: `import`, `require("x")`, `createRequire(..)("x")`), admitted as `installed:<pkg>@<version>` (checked against the installed version) or as a captured file. Anything else throws `sourceImportRefusal('require', ...)`. R152 (landed 2026-11-17 21:19 UTC) replaced the bare `typescript` request by `own(join(row.path, row.main))`, an ABSOLUTE path built at run time: no process of the main shape notices (it is a plain `require`), the captured shape refuses it. `typescriptCompilerV1` then did `try { compiler = own(path) } catch { compiler = undefined }` and turned the swallowed exception into "every API name missing" with `found = row.found` = the version of the manifest: hence "version 5.9.3, wanted 5.9.3, lacks the API: createProgram, ...". Both facts in the message were true and the cause was thrown away. The refresh read started at 00:26 UTC on that code (since R152) and every owner whose inference parses TypeScript (script routers, source analyses, component targets) failed in all 3 tries.

Reproduction in one process of exactly this shape: new law `🔷️typescript-compiler/🧪️tests/🍞️captured` builds a snapshot of the real interface files and runs it through `buildSourceClosureLoaderV1` (the loader of the read); on the live code at 06:40 it fails with the verbatim refusal of the read (`typescript-compiler-api`, found 5.9.3 = wanted 5.9.3, all 19 names missing). One real farm child on a set-aside owner of the slim lab (`pool-run.ts`, `@semio-tech/norm-en1991`, uncaptured child) infers it in 63 s: the shape, not the owner or the memory (`BUN_JSC_forceRAMSize` down to 96 MB loads the 9 MB compiler fine), is the fault.

Fix (staged, tested, landing 1 at the 07:00 window, see below):
1. `📦️parsers/🟨️.mjs` holds the one declared request `slot("typescript")` (`createRequire(import.meta.url)`), beside `package.json` that pins the version; the closure admits it as the installed package at the pinned version (installed-drift check included), every process shape loads the same file. `typescriptCompilerV1({load})` takes that loader; the default stays the path load for processes that are not captured.
2. A loader that throws is no longer "missing API": new refusal code `typescript-compiler-load` (EN and DE) with the new field `cause` (schema `Refusal`, required, nullable). An answer without the API is still `typescript-compiler-api`.
3. `🕸️dependencies/🟦️typescript/🟨️.mjs` (`parseRuntimeImports`) uses `parserTypescriptV1()` (it was the second absolute-path user in the read).
4. Law `🚫️bare-name`: the parsers file is the one allowed declared site.

Process shapes covered by a test: main (existing 9 tests), captured loader = farm child and slice worker (new law, real loader, real compiler 5.9.3, equal to an independent `createRequire` import of the package). Not a shape of the tooling: a bundle that moves the module away from its package; a bundle placed outside the tree could not find the parser slot with the old code either.

Silent set-asides: every set-aside line now carries the running count, and the first and every 50th say a census by reason (`asideCensusV1`, EN and DE): a tooling fault shows as "1892 owners are set aside by this read, by reason: 1892 x The TypeScript compiler ...". Law `🧮️aside-census` (3).

## B. "waiting for a farm child ... [no children]": the words were false, the farm had children

`describe()` of the project farm (`project-farm/🟨️.mjs`) reads `pool.farm.snapshot`, a property the farm never had (`🩹️describe-guard` only added a `?.` guard so that the missing property no longer crashes): the function returns "no children" for every pool, always. Evidence that children existed: `ps` shows 10 children of pid 42303 (6 `bun --eval` farm children of 270 to 810 MB, 1 h 25 min to 1 h 56 min old, and 4 small pool children of 53 min), no zero-children interval was seen, and `[owners] owner looks: 4775 owners in 797 farm jobs ... for 9 children`; the 1502 lines are the stage label of owners queued behind busy children (`STAGE_LOOK_V1`), "[no children]" only the broken tail. The real limits were: 8 to 9 children by the memory governor (`waiting for memory headroom (2036 of 7453 MB reserved)` 573 times, `waiting for the memory governor to let the owner back` 63 times) on a 32 GB machine whose load average is 46 (118 agent processes), and children at nice 0 (read farm class) against the same load. Fix (landing 2): the farm answers `snapshot` (busy, idle, starting, empty, queued, alone, restarts); the line now names the real counts. Law `🔭️snapshot` (2; red before: `snapshot` undefined).

The invariant "owners missing and no child running: start a child or fail within a bound" exists already for every farm wait (`waitForChild`, `hopeless`, R117/R177: `no-usable-child`, `holding`); no farm without a child was found in this read. NOT changed.

## C. Rate and the fleet

Counted at 07:08 UTC: the read stands at 2709 of 4775 projects and `read.log` holds 1932 `is set aside` lines (1892 compiler, 36 missing crate owner, 4 stale closure): at most 777 owners were really inferred in 6 h 40 min (about 2 per minute), the other 1932 were counted as done because they were set aside. Ledger of the read (`[owners] owners N of 4775 done`, last line): 128 owners done in the owner-look stage: 1 present, 0 fetched from the fleet, 127 inferred here (27 running), 99 to 103 "stale in the fleet", then `4647 published as wanted for every machine of the fleet`; everything after that is the parent's `build:projects` inference (2652 of 4775), which logs `parked: inferring in this process ... [no children]` for `language:cargo` owners of 200+ s with 0 rows: one thread, no help. ~6 owners per minute is the single-threaded tail, not fleet work.

Why idle workers do not help: the wave of this read `5d96a18f` (created 06:30 UTC, 4774 units) has ONE child file (`child-54`, origin g1-server) after 22 minutes; the waves of the workers (`7a656549`, `97c70755`, `9c4626dd`, `c8127739`, `39c72d7d`, 411 to 591 units, published by the m4/m6 machines) have 8 to 17 children each, ALL of origin g1-server. So the 32 GB machine's pool helps the workers' small waves while its own large wave has one niced pool child (the gate keeps one child while the machine's own work runs); the workers' pools were not seen in any child registry of the replicated cache. The workers hold records for their 590 selected owners only: records for the other ~4180 owners exist nowhere.

Machine-local rows (50, then 100 sampled): of the records the 8 other machines published in the last 6 h (2645 of 8028; the other 5383 are this machine's own), random samples decoded from the CAS and every observation row checked here with the landed code (`csample.ts`, same method as R184): 100 sampled: 91 fresh, 9 stale; the 9 stale: 8 by one changed `Cargo.toml` of the workspace (`🧰️framework/Cargo.toml` size 140978 and two member manifests: tree edits since the producer read), 1 by a `readdirNames` of a plugin directory. A first sample of 50 gave 40 fresh and 10 stale before `closure` rows were excluded: `closure` rows cannot be judged outside the read (no provider registered in the probe), they are not counted. So the machine-local directory rows R184 fixed (`🤖️generated`, hollow directories) are not the dominant cause any more; the remaining stale records are real tree churn. The 99 of 128 stale in the fleet during the read were measured with the code of 23:30 yesterday (before both R184 landings).

## E. A second set-aside fault (36 owners) that a fresh read does not have

`Native dependency has no build project owner: 🧰️framework/🔨️modules/🖱️ui/🔨️modules/📏️border-presentation/📦️packages/🦀️rust (required by ...:build; candidate)` sets aside 36 owners (`semio-s-artifact-procedural-3d-*`, `procedural-2d-*`, `sequence-*`, `cad-cad-*`, ...). The crate exists and is a workspace member (`🧰️framework/Cargo.toml` line 305); its directory and `Cargo.toml` were created at 03:07 to 03:08 UTC on 18 November, after the read started (00:26): the read keeps the owner registry of its start. Not a code fault: a fresh read sees the crate. It is the reason to end a read that is older than the workspace churn it reads.

## D. Would a fresh read behave differently? (for the coordinator)

Yes, in A: with landing 1 the 1892 owners that failed on the compiler load can be inferred by farm children and the slice workers; the running read keeps the old code (R181 rule) and will keep setting those aside until it ends. B: only the text changes. C: a fresh read has the R184 landings (hollow directories, `🤖️generated`) the old one lacks, so fewer owners are stale in the fleet; the single-thread tail disappears only if the owners that were set aside by the compiler fault are inferred by children. Restart advice: do not restart before landing 1 is green and the workers have been seen on the new code; after that a restart of the g1-server service is the cheapest way to turn 1892 set-asides into inferred owners.
