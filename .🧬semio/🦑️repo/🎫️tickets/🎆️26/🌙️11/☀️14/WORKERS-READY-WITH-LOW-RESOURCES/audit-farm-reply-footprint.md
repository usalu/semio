# Farm reply memory sampling

A worker can finish a graph job while the final physical memory read is still pending. The farm cleared the job timer when it received the reply, then waited for that read before releasing the reply or closing the pool. Its slot report omitted both the memory-reading and retiring states. A running whole graph printed some pools with zero busy, idle, starting and empty slots while work was queued. The live log omitted the state of those slots.

Two controlled regressions reproduced a completed reply held beyond a 1.2-second test bound. One kept the sampler pending during normal operation. The other closed the pool with a pending sample. An independent SQLite count supplied the expected settling slot. The fix gives the optional final sample the schema's five-second deadline, cancels it when its worker retires or the pool closes, and passes cancellation to the host sampler. When an optional sample is unavailable, the existing reported-memory fallback still applies. The worker result and the pool's subsequent scheduling now settle within the deadline. Slot progress identifies memory sampling and retirement.

The normal 2,048 MiB command grant ran all nine focused files. All 24 tests passed with 179 assertions, including the real kernel sampler, retirement of the capped child, the alone retry and an over-cap failure. The real process fixture now holds smaller randomly filled buffers long enough for sampling and reads a sentinel after the hold period. The previous fixture assumed `ps` resident bytes would match the allocated buffer during compression and swap. Two additional checks verified the declared schema and bilingual messages against the independent model. Nine adjacent tests passed with 108 assertions across retirement, job resource release, progress timing and memory admission. A separate concurrency fixture had counted successive jobs as simultaneous when both overlapped a longer job. The test now counts jobs running at the same instant and covers that exact sequence.
