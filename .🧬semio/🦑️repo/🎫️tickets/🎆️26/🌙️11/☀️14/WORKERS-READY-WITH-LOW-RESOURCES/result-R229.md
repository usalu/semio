## 2. What the Rust probe waits for (best available evidence, no phase data exists)

No `[phase]` row exists anywhere, no cargo `--timings` report exists in the stores or target dirs (searched `cargo-timing*` under `.cache` and `/Users/Shared/semio-store`: none), the unit event logs of the workers are local to the workers, and the only event log on this Mac is from 2026-11-14 (local hits, no fleet tier). What can be said from reports and code:

1. m01, the clean case (R203 section 3): 10 min 38 s for `norm-din4108-rs:build`, `688` of `756` units had their slot refreshed by that run (fleet restores, claim-on-hit) and **0 new unit puts**. So that run compiled and published no unit. Whatever the other 68 units were (build scripts, proc macros, bypass, units not shared), the 10 minutes were NOT spent in rustc of missing units. m03 8m42 (R203): same shape with 76 puts. The 22 to 24 minute runs (m08, m07) ran concurrently with each other and with a loaded server.
2. Plan passes: one pass (`cargo build --unit-graph`) measured 4.7 s (R186, rows `cargo:artifact-plan 756 units 5.85 MB elapsed 4.68 s`); there are five passes per build (plan, rechecks before the lease, after the lease, before consume, final, R188). About 25 s plus source admission with a memo: small against 640 s.
3. The graph slice read of the stage (about 250 s on m02, 420 s on m01) is before the Nx run, not in the probe task.
4. **How wide cargo runs on a worker.** `native-build/🟦️.ts` sets `CARGO_BUILD_JOBS = facts.parallelism`, the compile units granted by `planCompileUnitsV1` (`🎟️capacity/🧮️units`): `shareBasisPoints 5000` of the cores, so a 4-core worker gets `-j2` (a 10-core Mac mini `-j5`), lower under memory (`(free - 2048 MB) / 512 MB`) or pressure. Every restored unit is still one process of the compiler wrapper (`rustc-wrapper`, `/bin/sh` stand-in, then bun) that cargo starts like a compile: it computes the key (digests of the source and of every extern), looks locally, asks the fleet for the root hint, asks for the action result, downloads the blobs, writes the store entry, restores the outputs, and waits up to 600 ms for the slot claim. That is 3 sequential round trips to a server that runs on the busiest Mac, per unit, with **at most the granted compile units of them at a time**.
5. Wrapper process start is NOT the cost: measured here at load 46, nice 19: 0.27 s per call (boot, bypass, one `rustc -vV`), 756 x 0.27 / 2 = 100 s even at `-j2`.

Model (not measured): restore wall = restored units x t / jobs. With 690 units: t = 0.5 s gives 172 s at -j2 and 69 s at -j5; t = 1.0 s gives 345 s and 138 s; t = 1.5 s gives 517 s (8.6 min) and 207 s; t = 2.0 s gives 690 s (11.5 min) and 276 s. The observed 8.7 and 10.6 minutes (m03, m01) need t of 1.3 to 1.8 s at `-j2`, three round trips of about 0.5 s each against the loaded server; the 22 to 24 minute runs need `-j1` or a server answering in seconds. The shape (restore-bound, width = granted compile units) fits every number and the single hard fact (m01 compiled nothing).

So the working hypothesis is: **the dominant phase is the fleet restore of about 690 units through at most `-j2..5` wrappers, latency-bound, not CPU-bound**. The ledger will confirm or refute it with two rows the first time it runs: `unit:restore-fleet` (sum of seconds over workers, count) divided by `cargo:jobs` (new row, the width) against `cargo` wall. If `unit:restore-fleet / jobs` is below half of the cargo wall, the hypothesis is wrong and `cargo:start`, `cargo:critical`, `plan:*`, `recheck:*` say where the time is.

## 3. The fix by construction (lever landed, default unchanged) and what is not done

The restore needs round trips, not cores. The compile units are limited to a share of the cores for a reason (memory, the machine's other work) that does not apply to a served unit. The wrapper already has an independent compile gate (`SEMIO_UNIT_CACHE_SLOTS`, `acquireSlotV1`, only around a real compile). So cargo may run `factor` times as many jobs as granted compile units while the compilers stay at the grant:
* New member `native-build/🧱️restore-width` (schema `Policy`: `environment SEMIO_CARGO_RESTORE_WIDTH`, `defaultFactor 1`, `maximumFactor 4`, `maximumJobs 16`; `restoreWidthV1(granted, environment) -> {jobs, slots, factor}`): without a unit cache (`RUSTC_WRAPPER` and `SEMIO_UNIT_CACHE_ROOT`, not `SEMIO_UNIT_CACHE=off`) the factor is 1; jobs = max(granted, min(granted x factor, 16)); slots = granted.
* `native-build/🟦️.ts`: `CARGO_BUILD_JOBS = width.jobs`; when the factor is above 1 `SEMIO_UNIT_CACHE_SLOTS = width.slots` (compiles stay at the grant); prints `[restore-width] jobs= compile-slots= factor=` and adds the ledger row `cargo:jobs`.
* DEFAULT IS UNCHANGED (factor 1). I did not switch it on because (a) the real proof needs a cargo build (not allowed here before the seal; the whole read ended with an error at 00:58 UTC and a refresh read started, no seal message came), (b) a wider cargo pool also hands rustc more job tokens (`🎰️jobserver` passes cargo's pool to the compiler) and cargo runs build scripts at the pool width, so memory and CPU behaviour of the 68 real compiles under factor 3 must be seen once. To try it: set `SEMIO_CARGO_RESTORE_WIDTH=3` for one worker's probe (the environment of the stage or of the task) and compare `cargo` wall and the rows `unit:restore-fleet`, `unit:wait`, `cargo:jobs`.
* Further levers if the hypothesis holds (not built): (1) one round trip less per hit: ask the root hint together with the result (the `adopt()` before `obtainFleetUnitV1` is a sequential round trip for every unit, also for the vast majority that is not rooted), (2) a private bounded token pool for the wrapper's compiles so the width can be raised without touching what a compile sees, (3) prefetch of the blobs of the dependency-order front.

## 4. Fix of the delivery path (landed with the lever)

`🚦️ready` (supervisor of the stages):
* `readyMeasurementLinesV1(log, root, sinceMs, width)`: the lines of the stage log (last `failureWindowBytes` = 1 MiB) that start with `[phase] `, `[cargo-timings] `, `[units] `, `[nx-task] `, `[restore-width] `, `[compile-units] ` (schema `measurementLines`, last `measurementMaximumLines` = 80, cut to the mirror line width); when the log has none, the newest ledger tables its tasks wrote since the stage started (`phaseLedgerRunLinesV1`; a task stopped by the stage timeout leaves its table in `.cache/f/phase-ledger/<pid>.jsonl`, never in the log).
* The log mirror (`ready-log-<stage>.txt`) is now these lines first, then the newest non-measurement lines of the tail (total at most 200); the failure mirror and the stalled mirror carry them too (`failure: [provenance, measurement, failure lines, note]`, and the stalled mirror takes `result.failure`).
* Test `🚦️ready/🧪️tests/📏️measurement-lines` (4): a successful stage with the ledger followed by 1200 machine rows (the 16 KB tail window alone does NOT hold the ledger, asserted; the mirror starts with the four wanted lines, at most 200 lines, the rest is still the newest log lines); a failed stage keeps them beside the error text; a stage whose log has none gets the newest table of a stopped task (real `phaseLedgerFileSinkV1`) and nothing for a window after now; the patterns, the bound of 80 and the cut width.
