## 1. Question 1: why does g1-m01 not fetch the record the fleet already holds

Evidence chain (all measured):
1. The record IS fetched, the key is NOT the problem. `slice-memory.json` of g1-m01: ledger `present 582, fetched 3, here 5, stale 1`, `fleet {seeded 59, reinferred 5}`, three looks of `@semio-tech/s-dev-composition` of 10.5, 4.8 and 18.4 s (a fetch plus a check). In `project-nodes/🟨️.mjs` a look that ends `BUILD_TAKE_MISS` with outcome `fetched` is marked `stale` (line `error.outcome==="fetched"?"stale"`): the record was taken from the cache and then rejected by this machine's own check of its rows against its tree.
2. Which record: the cache server on this machine (`.cache/f/cache-server/v1/main/ac/`, 35 112 entries; the blobs are in `~/.cache/semio/cas/v1/o/<2>/<62>`, brotli) holds exactly ONE record of this owner since 2026-11-17 22:15 UTC: digest `eaf474ff...`, published 04:42:02 UTC by g1-m02 (record.br `9e6008ac...`, 6.8 KB, 37 observation rows). Before 04:42 there was none in the server for the current inference revision, because the three ready machines never published it (they inferred it themselves).
3. Which row fails: I decoded the record (`unpackRecordV1`, `localRecordV1` for this root) and ran `observationRowFreshV1` on all 37 rows on this machine (same tree as g1-m01): 36 hold, ONE fails: `readdirNames ⟦root⟧/✏️s/🧑‍💻dev` fact `3df860b7...`. This machine's listing of that directory digests to `efad070e...`. The names differ by exactly three entries that exist in the working tree but not in git HEAD: `🏗️builder` (holding only an empty `🌐️vite`), `🧬️schema` (empty) and `🤖️generated` (a generated directory, already filtered). The record's digest equals the digest of the HEAD listing of the directory (24 names; checked against `git ls-tree` of the last 54 commits). So g1-m02 has no empty leftover directories, this machine (and g1-m01, long-lived replica with the same history, `git status` view has no untracked entry there) has them.
4. Root cause: the directory fact (`directoryFactV1` in `👁️observation/🟨️.mjs`, filter `📂️source-names`) removes operating-system noise and generated output but keeps EMPTY DIRECTORIES. An empty directory is what a deleted tracked file leaves behind on a replica that had it; a replica made later never has it. Git cannot hold it. So two machines with the same tracked tree give two different facts, every record that lists such a directory is stale for the other group of machines, and the stale-note refresh (`staleNoteOf`/`refreshStateV1` in `project-records`) just ping-pongs the record between the two groups.
5. Why nobody recomputes it: the pool children of the largest machine (g1-server, grant 9830 MB) open the ask wave `7a656549` (created 04:36, ONE unit, `megabytes 4706`, `admission.inputs` set) 22 times in 12 minutes and every child ends "finished its wave after 2 to 14 s and 0 owners": the claim answers `stored` (a record exists) or `held`; the freshness verdict of the claimer is decided on its own tree, where the very same row fails, so the refresh chain depends on which side of the leftover directories the claimer is on.
6. Key parity (R164's open point) is confirmed from the other side: the ledger shows `fetched`, so reader and producer compute the same key for an admission read; admission/scope in the key is NOT the cause.

Fix (by construction, law: two machines, one tracked tree, any set of leftover empty directories, same fact): the directory fact leaves out a HOLLOW directory, one whose source-tree view (noise and generated output removed) holds no file anywhere below it (links and anything unreadable count as source). Same rule in the `readdir` (typed) and `readdirNames` kinds; `directories` (the TypeScript host probe) unchanged.

## 2. Question 2: why is the owner barred on g1-m01

`neverHere` (project-nodes, `graphOwnerEnforcementV1`) for an admission read (no farm, so no child footprint) takes `estimateOwnerCostV1(table, name)` over ALL samples of the cost table; the table is shared through the fleet (`costs.br` documents) and the estimator takes the maximum of the aged newest samples. Samples that a BIGGER host measured (a lax heap that shares its warm-up; the estimator's own comment says they only inform an owner nobody here ran) therefore bar the owner on a 16 GB machine: g1-server's table holds 1624, 1075 and 834 MB (host 32 768 MB) for this owner, the ask published by g1-m01 says 4706 MB (managed 2353 x factor 2) while R163 measured 858 MB alone. The farm path (R163) already ignores stops before 00:30 and compares only stops; the in-process path never did. A bar is valid evidence only from this host or a smaller one. Fix: `ownHostTableV1` (samples with `hostMegabytes <= this host`) in `neverHere`. A real overrun here still records a stopped sample on this host and bars (set-aside path unchanged). I could not read g1-m01's own `owner-costs.3.json` (not in the store); the cause is derived from the code, the fleet-shared table and the 4706 MB ask, not from its file.

## 3. Question 3: why no pool claims the ask

- (a) "no idle core ... 7 of 10 idle": not an arithmetic fault of the target but of the reason: `ownerPoolWhyIdleV1` passed the gate's `yielding`/`nothing-fits` through even when the target (3 to 8 children) was ABOVE the children that run, i.e. when the pool is starting; the runner then printed the bound that the gate named (`load` or `cores`) as if it held the pool. Fix: the reason is passed through only while the target is at most the running children; otherwise the pool is `starting`.
- (b) g1-server does run children (22 children for the ask wave in 12 minutes, the gate keeps one child where the machine's own work is present); the missing claim was the `stored` answer of item 1.5, not the yield. No new exception for foreground work is needed.
- (c) The ask is visible in the wave directory: `.cache/f/owner-pool-waves/7a656549...` (1 unit, `megabytes 4706`, admission inputs, publisher g1-m01), plus `59f53579...` of another reader with the same owner at 4690 MB.

## 8. Found at 06:00: the 1800 s bound of the heavy wait is never reached (Question 4, the real cause)
g1-m01 (old code, one read) is at "waiting for the fleet to infer ... 1983 of 1800" at 06:02 and goes on (a read that started 05:20, 2530 s old). `slice-memory.json` twice, 2200 s apart: `fleet.seeded` 59 -> 2333, `reinferred` 557, `looks.count` 1936, ledger still `stale 1`. The read looks the owner up every poll, imports the same fetched record (`seedFrom` counts it for its origin), then rejects it as stale, and `awaitWantedV1` takes `progressSign()` = the SUM of `fleetPort.producers()` plus the taken names as proof of progress: every re-import raises the sum, so `progressAt` is renewed about once per second and the "30 minutes without progress" never comes (the 6 h `limit` is the only end). A reader that waits for a record it keeps rejecting therefore waits forever by its own doing. Fix (lands 06:30): the sign is the number of machines that delivered plus the arrived owners (`Object.keys(producers).length`), so a record that is seeded again moves nothing; the wait then ends `stalled` after 1800 s and the retry-alone path of landing 1 runs the owner here (alone, a solo grant, the real overrun stop recorded). Test `🧪️tests/🫥️self-progress` (2; red on the landed code 2 of 2, evaluates the real line: 2000 re-seeds leave the sign, a second machine or an arrival moves it).
