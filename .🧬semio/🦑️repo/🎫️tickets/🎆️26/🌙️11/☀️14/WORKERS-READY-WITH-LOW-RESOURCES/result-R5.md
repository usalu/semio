# Package R5: the project graph against edits of the build tooling (2026-11-15 04:30 to 05:10, live tree, load 8 to 13)

T = `.🧬semio/🦑️repo/🎫️tickets/🎆️26/🌙️11/☀️13/FLEET-ONE-MACHINE-SHARED-HOT-CACHE-AND-REMOTE-EXECUTION`, LIB = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library`, B = LIB/🏗️build. No graph command was run; only the generation store of this machine (`.cache/b/g/m/generations`, 119 manifests) was read.

## Verdicts (short)
1. **The premise "every build-module edit makes all projects stale" is no longer true for the implementation digest, and it is true for exactly one mechanism: the file lists of the command source closures that sit inside every project's node.** Measured, not assumed (section 1).
2. I fixed what can be fixed by data and proven by tests without a graph run: six new **scheduling domains** (437 files of the build module) leave every task key, every command closure token, and the Nx engine digest. This is a real but partial reduction (143 of the 2 351 files of the Rust driver closure; 6 percent). **The remaining blast radius is the membership of the keyed part of the command closures (about 1 700 files), and removing it needs an architecture change I did not make blind** (section 4).
3. **Landing causes one last full invalidation** (the policy data row, the closure tokens and the engine digest change). Re-keying old records in place is not principled and not done (section 5).

## 1. Mechanisms, with evidence

### (a) The implementation digest of a generation: already isolated from code
- `B/🕸️graph/🕰️generations/🔌️load/🟨️.mjs:143` `implementationDigestV1(rows)` hashes `[kind, path, stamp | sha256]` of the rows the host hands in (`B/🕸️graph/🕰️host/🟦️.ts:146` `implementationRows`: every loaded file of the graph host and of the inference plugin, then `classifyImplementationRowsV1`, `B/🕸️graph/📥️inference/🔖️stamps/🟨️.mjs:112`). Classification drops every file below a protocol fragment (17 infrastructure fragments `none`, 18 inferrer groups) and replaces each group by one declared stamp; only data files that no group covers stay as content rows. Executable files nobody claims are named by `unclassifiedCodeV1` (`🔖️stamps/🟨️.mjs:123`) and a test keeps that list empty for the whole loaded implementation (`🔖️stamps/🧪️tests/🟦️.ts:85-93`, "every executable file ... is claimed ... and no fragment is dead").
- The record identity is the same idea: `B/👁️observation/🟨️.mjs:141-148` (`inferenceRecordIdentityV1`, `authorityDigestOfRowsV1` leaves files below stamped fragments out).
- **Measured:** the manifest `implementation` of the last 126 generations of this machine is `b1f7adc6...` without a single change (gens 108 to 234, 11-14 13:14 to now) although the build module was edited by dozens of landings in that time. Earlier: it changed at gens 104, 107, 108, 109 (the N9 landing on 11-14 12:23 to 13:14, the last time all 5 101 projects went stale through this door).
- Conclusion: statement P13 line ~38 ("the scripts change files that are in the closure of every project, so the implementation digest changes") was true before N9 and the stamps; it is not true for code files any more. What still moves the digest: a **data** file no group covers (`B/🔣️policy.json`, `⚡️caching/🔣️policy.json`, group schemas) and a **bumped stamp**. Stamps are hand bumped (`/N` suffix; two derived by conformance corpus, N9). That is a correctness risk (a forgotten bump keeps stale records) and not a cost risk.

### (b) The per-project node closure: the actual cause of the mass staleness
- Every project node carries named input groups `commandSources0..n` (and `testCommandSources`). Their literal file lists are replaced by content-cut chunks and referenced as `{env: "SEMIO_SOURCE_CLOSURE_<sha256 of the chunk's file list>"}`: `B/📥️inputs/🟨️.mjs:202-228` (`compactSourceInputs`, tokens at 225), assembled per project in `B/🕸️graph/📥️inference/🧱️project-assembly/🟨️.mjs:347-357` and `457-461`. The contract of a token is only the **list of file names** (`.cache/b/g/m/build-input-closures/<key>.json` = `{"version":1,"files":[...]}`); the content hash is taken when the task is hashed (`B/📥️inputs/🧮️digest/🟨️.mjs:9`). So a body-only edit changes no token (consistent with N9), **adding, removing, renaming a file or changing an import inside a tool closure changes the token of one or two chunks, and the node of every holder changes.**
- The facts behind a token live in each project: the source analysis of every closure file (`reasonAnalysis`), the directory listing (`readdir`), the file rows. Hence "analysis 77, readdir 28, file 25 leave 659 projects stale" (P3/P12 logs) after a landing that touched closure membership.
- **Measured on the store** (`T/🧰️scripts/R5/measure.py 110`): since the last implementation change, 112 delta waves (and 126 now) re-inferred **7 101 projects, 7 020 of them (98.9 percent) changed their fragment, 81 came out equal**. Where the fragments differ (random sample of 2 per wave): `namedInputs/*/env` (a closure token) 119 times, closure token plus `edgesEnv` 51, chunk count of a group (`namedInputs/*` length) 39 plus 17, `edgesEnv` alone 9. In words: re-stamping with an equal result is rare (1.1 percent); the work is real differences in the closure tokens.
- **Who holds the tokens** (gen 223, 5 101 owners, `T/🧰️scripts/R5/boundary.py`): 15 tokens are held by 1 000 or more projects (six by 4 350 to 4 480, five by 3 118 to 3 119 = every Rust project). 13 to 16 closure tokens per project is the mode (1 920 + 645 + 1 091 + 730 projects). Four examples of landings and the projects they restaled, found as new tokens against their predecessor (`added` = new file in the closure): graph-state `wanted/*` (3 files, 1 437 projects), cargo unit-cache `complete/*` (2 files, 1 365), resident `consent/*` and `launchd` (3 files, 1 365), `closure-repair` and `memory/owner-scope` (3 files, 706).
- **What is in the closure of a Rust project** (`relativeScriptInputs` of the cargo driver, live): 2 351 files; 515 were already left out by the nine scheduling domains; the rest is the driver's transitive imports: `bootstrap/tools` 84, `cargo/units` 70, `bazel` 67, `graph/inference` 57, `process/testing` 65, `dependencies` 50, `os/modules` 91, resident, graph-state, remote-execution, doctor, profile, workers and memory (the part I now cut).
- The per-tool layer for shared command closures already exists (`B/🕸️graph/📥️inference/🧭️script-inputs/🔌️provider-closures`: "a library edit that changes such a shared closure changes one group of one project"), but only for two declared tools (cargo driver, lock owner) and the script provider ports. All other command closures are listed per project.
- The Nx engine digest (the "nx plugin entry" part of every Nx hash) is the same idea: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/🧮️engine-digest/🟦️.ts` cuts the scheduling prefixes plus its own domains (bazel route, cache retention, cargo route, whole graph) out of the digest.

### (c) Sidecar restart on "code changed"
- `B/🌐️remote-execution/🛰️sidecar/🟦️.ts:70`: every 30 s `watch.changed()` (closure digest over the file contents of the role's import closure, `🧮️closure/🟦️.ts`, exact and correct: a touched or identical file never counts) sets `changed`, logs "code changed, restarting" and **aborts immediately** (`controller.abort()`), exit status 75, the launcher starts the child again. In-flight actions of the agent are cancelled (`👷️worker/🟦️.ts:222,269` return `cancelled`).
- Closure size measured with the repo's own import graph: agent 144 files (graph 41, remote-execution 21, graph-state 16, cas 11, resident 8), scheduler 25, cache 39, graph role 122. Restarting for a byte of code it runs is right; **dropping the in-flight work is the defect.** Fix (designed, not implemented, belongs to the sidecar package): two signals, a `drain` signal that stops taking new actions and an `abort` that fires when the drain finished or after a bounded grace (e.g. 120 s), exit 75 after the drain; the launcher already restarts without a gap.

### (d) Resident service replaced on code change
- `B/🏡️resident/🏗️composition/🟨️.mjs:16-23` `residentImplementationV1`: hashes the bytes of **every** `.mjs/.json/.rs` file of the resident member except tests; `🏛️service/🟨️.mjs:109,159` marks the service stale and refuses `tier=service` commands with `stale`; `🏗️composition:51` ends with status 75 and the supervisor starts a new service. Scope is the member (not the module): an edit of any resident text or schema replaces the service, an edit of the graph port or protocol modules it imports from outside the member does **not** (stale code can run). Fix (designed): replace the directory walk by the import closure of the service entry (the sidecar watch is the same function: `createSidecarClosureWatchV1`), hashed by content; not done here (resident package).

## 4. What is not fixed, and the design for it
- The keyed part of the command closures is the content of the cargo driver and the TypeScript runners, and any membership change in it restales 3 100 to 4 400 projects. **Design:** make the tool closure an **environment-scope** object instead of a per project fact: the node holds a stable reference to the tool by name (like `toolClosure:cargo-command:native`), the file list and its analysis facts belong to one record per tool (kind = tool, key = tool identity), computed once per generation; the task hash resolves the list at hash time (the digest script already reads the list from a store: `🧮️digest/🟨️.mjs:9`). Then a membership change re-evaluates one tool record and 0 projects, and the task keys still change when tool bytes change. The pieces that must change together: `compactSourceInputs`, `taskEnvironments`, `inferenceInventoryRecordHoldsV1` and `inferenceInventoryReferencesHoldV1` (the checks `file.sha256 === key` assume immutable content addressing), `🎯️selection/📥️scope/🟦️.ts:49`, the farm session (`lateClosures`), the retention of closure records and the fleet exchange of generations. I did not do this without being able to run a graph build; a mistake would under-key tasks silently.
- Hand bumped stamps (`/N`): replace by a digest of the import closure of each inferrer group, normalized by the existing conformance corpus approach (N9). Not done: it would not change one number measured above.
- (c) drain and (d) closure based resident identity: designs above, not implemented.
- `🏗️build/🔧️tools/🏗️bazel` (67 files), `🕸️graph/📥️inference` (57), `🕸️graph/🕰️generations` (33) and `⚡️caching/🕸️graph` look like candidates, but each needs a decision about whether it derives bytes (generations has declared keyed islands for the codec); I left them keyed.

## 5. Numbers to expect after landing
- **The landing itself restales everything once.** It changes: `B/🔣️policy.json` (a data row in the implementation digest of every generation, so all 5 101 projects are stale for every machine, wave size 48 on this machine: about 106 waves, the same 40 to 60 minutes as the last time), the file lists of all closure tokens that contained a file of the new prefixes (3 100 to 4 400 holders), and the Nx engine digest. **Re-keying old records in place is not principled**: the new fragment really differs (smaller lists), a record cannot be proven equal without inferring it, and a migration path would be a compatibility layer (forbidden by AGENTS.md). So: no re-key, one more refresh; do it before releasing workers, do not edit the build module until the server has published once.

An edit of another file of the build module: unchanged from today (body edit 0; membership or import change in a keyed closure: the 553 of 575 fresh sampled projects hold the tokens).
- A new file anywhere under the six domains' prefixes is neutral by construction; a new member directory fails the guard until classified.

## Verdict
1. **The tool-record indirection (the "main fix") is NOT built.** I stopped before writing it, deliberately: it cannot be added without changing at least nine places that today rely on "a closure token is the sha256 of an immutable record", and I cannot run a graph build or a task hash end to end here. A mistake would not fail loudly; it would key tasks on too little. **Consequence for the plan: if R5 lands as prepared, the node-embedded file lists remain, and the tool-record change will need its own last full refresh later.** If the coordinator wants exactly one refresh, hold the R5 landing until the tool-record package exists (below) and land both together.
2. **Drain on restart of the sidecar is built and landed into the same `land.py`** (contained, 5 new tests, existing sidecar tests unchanged).
3. Today's landings measured before/after (table below): with the scheduling domains alone, **R2 stops re-staling 553 of 575 sampled projects (0 after)**; P14 does not (it adds keyed files); R1b, R4, R6, R7 never changed a node (they added no file to a closure).

## 1. Why the indirection is not a small change (inventory)
The token `SEMIO_SOURCE_CLOSURE_<sha256 of the record>` is checked as "name equals content hash" at every one of these sites, and a stable-key reference (tool identity, mutable file list) breaks each of them unless it is changed together:
- writer: `B/📥️inputs/🟨️.mjs:202-228` (`compactSourceInputs`, `publishInputClosureV1` which refuses a record whose bytes differ), farm staging `B/📥️inputs/🟨️.mjs:92` ("Closure content differs from its name");
- readers: `B/📥️inputs/🧮️digest/🟨️.mjs:9` (`taskEnvironments`: `file.sha256 !== key` throws), `B/👁️observation/📥️reuse/🟨️.mjs:43,68` (`inferenceInventoryRecordHoldsV1`, `inferenceInventoryReferencesHoldV1`: no-follow, single-link, bounded reads), `B/📥️inputs/📋️data/🟨️.mjs:12` (closed record `files`/`version` inside a frozen, digest-pinned epoch), `LIB/⚡️caching/🕸️graph/🔏️seal/🎯️selection/📥️scope/🟦️.ts:49` (selection scope recomputes the sha), `B/🕸️graph/📁️workspace/🟦️.ts:59-90`, `B/📥️inputs/🪶️lean-inventory/🟨️.mjs:5`, the Bazel closure schema (`B/🔧️tools/🏗️bazel/🔗️closure`);
- retention: namespaces in `B/📥️inputs/💾️storage/🧬️schema/🔣️.json`, `B/🗄️cas/📂️areas`, `LIB/⚡️caching/💾️storage/🧾️ledger/🔣️policy.json:524`, the headroom closure scan (`…/📏️headroom/🧾️closures`), all keyed on `[a-f0-9]{64}.json` names.
**Design that keeps every one of these invariants** (so the follow-up can be done without weakening them): (a) the node holds `{env:"SEMIO_TOOL_CLOSURE_<K>"}` with `K = sha256(tool identity)`, where the identity of a group is its shape, i.e. the list in which every closure marker is replaced by its recipe key (`closureRecipeKeyV1`) and literal items stay; (b) the immutable content-addressed closure record stays exactly as today (so all content checks, farm staging and retention keep working); (c) a small **tool index** `build-tool-index/<K>.json = {version:1, tool:K, closure:<sha of the current immutable record>}`, replaced atomically by whoever resolves the group; (d) `taskEnvironments` follows index → record → digest at hash time, `scope.ts` and `workspace` follow the same two steps; (e) the neutral filter (scheduling domains, and tests files that no non-test module imports) is applied when the record is written, so a new test file or a neutral-domain file changes no record. A name based exclusion of every `🧪️tests` directory is **wrong**: the live closure of the Rust driver has 300 files in tests directories (15 percent of its build and caching files) and 8 of them are execution code imported by `script.ts` files (`⚡️caching/🧪️tests/🔬️script-commands`, `cargo/📦️units/🧪️tests/🔬️script-commands`, `bazel/🧪️tests/🧬️schema/📋️dispatch.json`, ...); excluding by name would under-key those tasks. (f) The open problem that I could not solve blind: the analysis facts of the closure files are held per owner, so even with a stable node the owners whose closure changed are re-inferred (equal result, early cutoff downstream) unless those facts move to the tool record too; that is the late-closure mode (`closureApiV1`, `resolveClosureRefsV1`) and needs a graph build to validate.

## 2. Drain on restart (built)
- `B/🌐️remote-execution/🛰️sidecar/🟦️.ts` (main): on "code changed" the **agent** role no longer aborts at once; it fires a `drain` signal (new optional `drain` in the sidecar context, `🧰️shared`), logs "finishing the work in flight (up to N s), then restarting", and aborts only after `SEMIO_SIDECAR_DRAIN_SECONDS` (default 300). Scheduler and cache roles keep the immediate restart (they have nothing to drain).
- `🛰️agent/🟦️.ts`: new `drainWhenIdleV1(drain, busy, done, poll)`; the agent refuses new actions while draining (new admission refusal `"draining"`), and stops when `state.running` is 0, so its in-flight actions finish. The agent role returns instead of looping when the drain fired (the launcher restarts it with the new code, status 75).
- `🛰️sidecar/🕸️graph/🟦️.ts`: the graph server counts in-flight answers (`busy`), `mayServe` and `mayRefresh` answer false while draining, and the wanted server stops when the last answer is delivered; the supervisor loop ends on drain. A graph read that outlasts the grace is aborted as before (the waves already uploaded stay).
- Tests, new `🛰️sidecar/🧪️tests/🚰️drain/🟦️.ts` 5 pass (no signal never calls; waits for 2, then 1, then 0 in flight and calls once; drain before start with 0 in flight calls at once; a stopped watch never calls; the probe is asked again at every check). Existing: `sidecar/🧪️tests/🕸️graph` 8 pass (as before), `🧮️closure` 3 pass 1 fail (the real-restart test is red **before** the change too).
- **Not verified:** the three real-process tests of `sidecar/🧪️tests/🟦️.ts` (scheduler, lease, cache) fail in my rig even on an unedited copy of the tree (they need the live environment), so the drain inside a real agent process is not exercised; `land.py` runs them live after the landing (expected 0 red, they pass on the live baseline). ## The three blockers (not in the R5b list)
- **B1, restore on other machines.** A mutable tool index is local. A machine that restores a generation from the remote cache (every worker, as the line above shows: 5104 documents downloaded) holds nodes that name a tool key but has no index entry and no tool record, so its first task hash fails or must run the whole closure walk. The index and the tool records have to travel as documents of the generation (`🌐️remote-exchange`, the sidecar uploader of P13/P14) and be verified on restore; that is a protocol change with its own schema, not a local file.
- **B2, who keeps the index true.** With the facts gone from the owners nothing marks a project stale when a tool closure changes, which is the goal, so a separate step must re-evaluate every known tool shape once per read (the closure entries are already verified once per pass: `ensureClosureEntryV1`, `withClosurePassV1`) and publish record plus index atomically. If that step is skipped or fails, task keys silently stop seeing new files. It needs a fault policy (fail the read, never serve a stale index) and a generation-level fact that the index was refreshed at this generation, or two machines will disagree about the task key of the same task.
- **B3, queries that read membership.** `withoutExcludedSourcesV1` (`project-assembly:211`, `closures.query(group.inputs,"excludedPaths",patterns)`) and `some(...)` decide the node from the closure content. They are recorded as derived facts today and keep working, but a membership change that flips their answer must still restale the owner; the fact move must keep exactly those facts and drop only the walk observations, which needs the derived-fact layer (`🧮️derived-nodes`, `✂️cutoff`) to be exercised on a real graph with a membership change. That is a graph-build experiment of an hour per iteration at this load.
