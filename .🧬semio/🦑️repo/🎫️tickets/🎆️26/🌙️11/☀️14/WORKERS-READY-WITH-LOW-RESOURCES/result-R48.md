## 1. The chain: where setup needs the graph and where the refusal is decided

1. `native-bootstrap.sh` runs `🔩️native/🥾️bootstrap/🐚️.sh setup`. Its function `repo_bootstrap` runs `repo run repo-mcp:install` (`🐚️.sh:1289`), `repo dependencies sync --all`, then `repo run workspace:setup` (`🐚️.sh:1296`). `repo tools setup all` itself (tool installation, `B/🧰️tool-setup`) needs NO graph: the worker states `failed: workspace:setup` come from the two `repo run` lines.
2. `repo run <project:target>` asks the per-host graph service for a plan. A `tasks` selection is served as a SLICE: `loadBuildGraphOnceV1` (`B/🕸️graph/📥️load/🟦️.ts:146`) goes to `loadBuildGraphSliceV1` (`:161`), which calls `loadGenerationGraphV1` (`B/🕸️graph/🕰️generations/🔌️load/🟨️.mjs:356`) with `slice.roots` = the selected projects. `sliceClosureV1` takes only the owners those tasks import (transitively), so the unit is already the package: the stale set is the stale owners of that closure (78 on g1-m02), not the 5 102 of the repo. Whole-repo completeness is not a precondition anywhere on this path (membership of 8 318 parts and the facts of the closure are read, the other owners' records are not inferred).
3. When the closure has stale owners the load goes (`🔌️load/🟨️.mjs:409-414`): `host.fleetRead` (`B/🕸️graph/🤝️prefetch/🟦️.ts:97` `fleetReadStaleGenerationV1` -> `B/🪪️graph-state/🙋️wanted/📖️read/🟦️.ts:16` `fleetReadV1`: take what the fleet already published, publish the request, infer the rest locally in waves), then `host.prefetch` (`prefetchBuildGraphProjectsV1`, `🤝️prefetch/🟦️.ts:30`, plan stage `inference`), then `host.withBuilder` (builder custody, the wave `compute` -> `discoverPart`).
4. The inference runs in the slice worker process (`B/🏡️resident/🏗️composition/🌐️host/👷️slice-pool/👷️worker.ts:8`, `loadBuildInvocationGraphV1`). Its concurrency is `projectConcurrencyV1` (`B/🕸️graph/📥️inference/📦️project-nodes/🟨️.mjs:97`, min(8, cores)) plus the project farm (`planFarmWorkersV1`, `:324`), the owner wave is `scaledOwnerWaveV1`/`nextOwnerWaveV1` (`🕰️generations/🟨️.mjs:38,45`, 48 owners, up to 960).
5. THE DECISION: the slice pool samples the process TREE every second and calls `judge` (`slice-pool/🟨️.mjs:44`) with `planGuardVerdictV1` (`slice-pool/🧱️limit/🟨️.mjs:54`): over the plan limit (6 553 MB on 16 GB) it settles once, then refuses when available memory is under the 2 048 MB reserve (`memory`), pressure is critical, or the tree is over the ceiling (60 % of the machine, `ceiling`). Before this package the refusal branch (`slice-pool/🟨️.mjs:52`) finished the load with the error `plan-memory`; the service maps it (`B/🏡️resident/🏛️service/🌐️host/🟨️.mjs:167`, `🧯️failure/🟨️.mjs:98` `planRefusalOfV1`) to the bilingual `host-graph-plan-too-heavy` and exit 75. The same refusal also arrives from inside the worker (`createPlanStageGuardV1`, key `build.graph.plan-too-heavy`, thrown from `prefetchBuildGraphProjectsV1`). Measured cause (rounds 28/29, R36): 8 owners in flight plus farm workers, each compiling TypeScript programs of 2.2 to 3.4 GB, tree 9 966 MB against 6 553 MB.
6. The nothing-else-works part: the other dead end of the same path is the fleet wait (`fleetReadV1`, `graph.wanted-expired` / `graph.owner-too-heavy`). It refuses only when the machine cannot run even the smallest wave, or a single owner exceeds the solo grant. NOT changed (see section 5).

## 2. Design (what is built)

Idea: the refusal was a verdict about the SIZE OF THE WORK, not about the machine, so the work is made smaller and the load continues. Owner records are persisted per owner, so a smaller restart repeats nothing.

- New member `B/🧠️memory/✂️cut/` (schema first: `🧬️schema/🔣️.json`; `🟨️.mjs`, `🟨️.d.mts`, tests). A ladder of 6 levels. Level 0 = usual work, no cap. Level k = projects at once `8 / 2^k` (4, 2, 1, 1, 1, 1) and owner wave `10000 / 2^k` basis points (48 owners -> 24, 12, 6, 3, 1, 1). Pure functions: `graphCutV1`, `graphCutAfterV1` (one level per doubling the tree was over the limit, at least one, none at the last level), `graphCutStartLevelV1` (doublings between the 10 240 MB measured for uncut work and the plan limit: 16 GB Mac -> 1, 8 GB -> 2, no limit -> 0), `graphCutLearnedV1` (a finished load keeps its level while its peak was near the limit, relaxes one level when under half of it), `graphCutEnvironmentV1`, `graphCutConcurrencyV1`.
- Slice pool (`slice-pool/🟨️.mjs`): a refusal verdict (`ceiling|memory|pressure|unknown`) or the worker's own `build.graph.plan-too-heavy` becomes `plan-cut` while a level is left. The `run` loop starts the worker again at the next level (it does not count against `sliceRestartMaximum`), with `SEMIO_GRAPH_CUT_CONCURRENCY` in its environment and the narrower `SEMIO_SLICE_WAVE_BASIS_POINTS`, and reports the bilingual progress line `host-slice-owners-cut` (step k of 6, tree MB, limit MB). A pool starts at the level its plan limit asks for and remembers the level that worked. Only a load already at level 6 (one project at a time, one owner per wave) still gets the typed `plan-memory` (now with `cutLevel`).
- Worker side: `projectConcurrencyV1` (now exported, takes an environment) and `planFarmWorkersV1` honour the cap, also where the plan has no limit.
- Texts: `host-slice-owners-cut` in `B/🏡️resident/🧬️schema/🔣️.json`, English and German.
- Machines without a plan limit (serving machines, 24 GB and more) start at level 0 with no cap in the environment: unchanged behaviour.
- Unchanged and relied on, not rebuilt: fetching finished per-package records from the fleet (`fleetReadV1`, generation 238/239 reach the fleet cache, R45), local inference owner by owner in waves, publication of finished records to the fleet by the project fleet port and `offerFreshPriorityV1`.
