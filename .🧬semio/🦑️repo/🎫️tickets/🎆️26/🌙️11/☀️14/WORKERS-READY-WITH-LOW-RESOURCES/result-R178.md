## Wall 92: a cache copied into a lab is invisible to a package manager whose registry is the lab's refused loopback registry; `nx:install` then asks the registry (lab-only fix, LANDED 05:46 UTC)
- Run 3 and run 7 (16 GB / 8 cores; walls 90 and 91 handled in the frozen root): `repo-mcp` 72 s and 67 s, `dependencies` 1148 s and 1038 s ok, `tools` 14 s and 10 s ok, then `workspace` read the slice (about 200 s, step table below) and stopped at `nx:install` (the install of the Nx SDK by the pinned bun): `ConnectionRefused downloading tarball tar-stream@3.2.1`, `@nx/js@23.2.0` ... 368 tarballs, although `…/downloads/@nx/js@23.2.0@@@1` is in the warm directory.
- First guess, REFUTED by a by-hand experiment (landed 05:02, replaced at 05:46): the version entries of the cache are absolute links into `/Users/Shared/semio/...` (a checkout the tree left on 2026-11-15; dangling in the live tree too, harmless there because the Nx SDK is sealed). Relinking them (368 made) did not help; an install from the unrelinked copy with the default registry works.
- Cause (experiments with the pinned bun 1.4.2 on the SDK's own `package.json` + `bun.lock`, scratch directory, proxies refused): bun names a cache entry after the registry it fetched from (`name@version@@@1` for the default registry, `name@version@@<host>@@@1` otherwise, e.g. the `@@192.168.178.70@@@1` entries of the dependency cache). With the lab's registry files (`.npmrc` and `.bunfig.toml`, R161 section 1) OR the env var `NPM_CONFIG_REGISTRY` alone the key becomes `@@127.0.0.1@@@1`, so the warm entries (default registry) are not found and bun fetches. Without any registry setting the same copy installs in 7 s from the cache; with the setting and links named `name@version@@127.0.0.1@@@1` -> `name@version@@@1` it installs too (368 aliases).
- Fix (lab-only, landed 05:46): `sliceLabRegistryAliasV1(root, url)` in `🔬️slice-lab/🏠️home/🟦️.ts` makes, for every directory entry of the first two levels named for the default registry, a link under the host name of the lab's refused registry; the warm items `bun-cache` and `downloads` carry `registryKeys: true` (schema) and get it after the copy. Refusal stays: the registry is still the refused loopback address; a package the cache does not hold still fails at once. Test `warming makes the default-registry entries of a cache addressable under the registry of the lab` (new, 26/26 home tests green; an entry of a foreign registry gets no alias, the source is unchanged, a second call makes none).
- Consequence for real workers: none (no registry override, default keys). Consequence for the lab guard design: a guard by registry file changes the cache key, so every future warm item of a package-manager cache needs `registryKeys`.
