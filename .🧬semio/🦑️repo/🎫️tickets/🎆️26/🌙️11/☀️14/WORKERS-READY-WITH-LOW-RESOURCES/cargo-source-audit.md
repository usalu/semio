# Cargo Source Verification Audit

The Cargo ingress accepts `repo cargo --store=shared|isolated --configuration=prototype|release [--parallelism=<cores>] -- <cargo subcommand> <args>`. It plans and admits workspace source boundaries before dispatch, then invokes Cargo in the original working directory. Admission reads and hashes source for boundedness; it does not provide the compiler with a frozen source tree. The shared store uses a pooled target/build lane and content-addressed unit cache. The isolated store creates and retires a private target/build/temp namespace, not an immutable source snapshot. Neither store selection alone prevents source edits during compilation. See `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏃️process/🦀️cargo/🚪️launcher/🟦️.ts` (lines 200–203, 233–244) and `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/📥️source/🎟️admission/🟦️.ts`.

The 1647 log checked `semio-framework-pack-json` at line 20789, then `semio-framework-mesh-engine` at 44998 and failed on `member_at` and `swap_members` at 45345 and 45351. The earlier exact log failed in `semio-os-dsl` on `step_work_demand`; neither proves all later crate boundaries. These observations are consistent with mixed-time inputs but do not themselves prove the edits or establish that current sources compile.

For a narrower diagnostic after relevant sources settle, the supported command is `repo cargo --store=shared --configuration=prototype --parallelism=1 -- check --locked -p semio-framework-mesh-engine --lib`. It checks that package and its selected dependency closure, not window-config or all earlier boundaries; it still reads the live tree. Follow a successful diagnostic with the original window-config command for the actual target. A third manual rerun is not the immediate best step while the wrapper is automatically retrying. No supported immutable source route was established from this ingress inspection; an isolated target store does not establish source immutability. The wrapper performs generation checks described below, so the earlier recommendation for independent proof of all source stability was too broad. No builds were launched in this audit.

## Post-Cargo Generation Checks

The 1822 log lines 42295–42307 show Cargo completed OS DSL, then a shared resource-directory admission and generation-snapshot retries exhausted, after which the outer command restarted (1/6). Cargo Finished is therefore not the overall wrapper result. The generic progress text does not identify the exact changed file or which witness raised the generation event.

The Cargo ready consumer (cargo dependencies ready storage, lines 62–75, 113–128) revalidates a selected ready receipt after its body: it hashes recorded workspace Cargo manifests and lock inputs, validates their dependency topology, and rejects a changed original receipt. Its fetched alternative checks selected lockfile digests and registry archive stamps. Once the body has run this local snapshot retry does not rerun the body; propagated churn can trigger the outer command restart. Separately, the JavaScript dependency reader (bootstrap dependencies storage, lines 99–104 and 901–907) pins a verified dependency generation and rechecks its receipt or source-owner digest and custody after its body; moved generations are rejected. These are meaningful post-consumption checks, but their declared scope is dependency readiness and ownership, not an established frozen or post-verified roster of every Rust source byte read by rustc. The directory admission message identifies a lease, not the identity of the moved source. The restart does not prove a particular Rust method changed or that a successful generation check alone seals every Rust source.
