## 2. Cause (reasoned, NOT proved; no Windows machine reachable)

* Own handles: the order in the caller is clean. `withDirectory(prefix, ...)` (names/roster check) is awaited and closed before `capturePreservation`; `readEntry` closes its probe handle; the capsule handle is the target, the parent handle is an ancestor. Retention 1 of 2 succeeded through the same code. An own reader is therefore the least likely cause here (my first guess in the task text was not confirmed by the code order).
* The step was refused only for the second tree, after the first moved. Windows answers ACCESS_DENIED to a DIRECTORY rename when something outside the call blocks it: a file below the tree open without `FILE_SHARE_DELETE`, a running executable image or mapped file below it (memory-mapped, e.g. a binary of a half-installed tool that a stale process still runs), a read-only mark, or missing rights. The log lists live `tools`/`identity` commands from earlier tries on that machine (pids 7616 since 11-17 04:15, 31664 since 01:41) and the real build command 36528 (`run @semio-tech/fem-3d-rs:check`, since 03:54) which holds the dependency store; any of them or a child of them, or Defender/indexer, may have a file of `35ae...` open. Registered store holders are excluded by the exclusive maintenance parent (that is how the stage got here), so the blocker is an unregistered foreign handle or image. To decide by hand on m05: `Get-CimInstance Win32_Process | ? ExecutablePath -like 'C:\semio\.cache\b\d\m\j\35ae*'` and Resource Monitor > CPU > Associated Handles, search `35ae`.
* Old rule: one attempt, no wait, so a transient handle (scan, indexer: milliseconds to a minute) failed a stage that then retried 14 times with back-off of minutes; each stage retry re-ran the whole producer.

## 3. What was built (fix by construction)

Schema first: `RelativeRenameSettlement` (new definition in `📁️descriptor/🧬️schema/🔣️.json`), plus `shareDelete`, `renameExClass 65`, five NT names.
* (a) Own handles: every handle opened by the relative layer records `(parent handle, name)` (`lineage`); `artifactWindowsRelativeHandlesBelowV1(open, lineage, entry)` counts open own handles that are another handle on the same name or anywhere below it. `settleArtifactWindowsRelativeRenameV1` asks for that census before EVERY attempt; non-zero is `ArtifactWindowsRelativeRenameRefusedErrorV1` reason `own-handles` at once, never waited for (bug of the command, said so in EN/DE). So a rename over an own open handle is impossible to reach.
* (b) Share modes: all opens of the relative layer (`openChild`, every role including the `delete` source, the exclusive create, the synchronous file reader) now include `FILE_SHARE_DELETE` (directories read|write|delete, files read|delete). Other programs (and our own other processes) can rename or delete what a command only reads; the facts checks already detect a delete-pending entry. The publication opens (`DELETE` access, read share) are unchanged.
* (c) Rename: first `FileRenameInformationEx` (class 65) with `FILE_RENAME_POSIX_SEMANTICS|FILE_RENAME_IGNORE_READONLY_ATTRIBUTE` (0x42, no replace); on `STATUS_INVALID_INFO_CLASS|NOT_SUPPORTED|INVALID_PARAMETER|NOT_IMPLEMENTED` the classic class 10 in the same attempt (remembered). Transient statuses (ACCESS_DENIED, SHARING_VIOLATION, DELETE_PENDING, CANNOT_DELETE, USER_MAPPED_FILE) are retried with 50 ms doubling to 2 s, total budget 60 s (30 x the cap: one scan of an on-access antivirus over the tree; schedule 50,100,200,400,800,1600, then 2000, last pause cut to the budget; 36 attempts). Cancellation (`checkpoint`) is checked before every attempt; progress is one stderr line `[DATA] Windows preservation rename waiting {...}` at the first failure and then at most every 5 s. Any other status is the old generic failure (unchanged). After the budget: typed refusal reason `foreign-handles`, texts EN and DE naming source, target, `0x...`, NT name, the status in words (EN/DE table in the schema), attempts, waited ms and the holders: `NtQueryInformationFile(FileProcessIdsUsingFileInformation = 47)` on the source handle gives the pids that hold the folder itself (own pid removed); it cannot name holders of files BELOW the folder (Windows has no such query), so the text says "not determined" when none and points to Resource Monitor.
* "Internal error" must not be the outcome: the boundary `reportRepoErrorV1` (`📣️progress/🟦️.ts`) now finds the first typed bilingual refusal (`CargoLockRefused` or `WindowsRenameRefused`) through `AggregateError` members and `cause` (first failure first, depth 8) and renders its text in the chosen language, exit 1. A chain without a typed refusal is still an internal error naming every member.
* (d) Design review. Retention moves a tree that no registered command reads: it runs under the exclusive maintenance parent of the store, so every registered reader (the shared holders, R183) is excluded by construction; a foreign handle is by definition an unregistered program. That is also the Mac and Linux situation, where `rename` of a directory with open files works because POSIX unlinks by name and leaves open files alive; Windows has no equivalent for the directory case unless every opener allowed delete, so the design that relies on POSIX rename-over-open is the one thing Windows cannot give; (b) and (c) buy back what Windows can (share-delete cooperation, POSIX rename on NTFS 1709+), the bounded wait covers transient foreign handles, and the refusal tells a human what to close. NOT done: per-attempt never-renamed generation directories. The canonical generation name `<gen20>` is bound by the stage (`Fresh absent canonical lock root required`), the ready bindings, the retained-capsule reader (`readJavascriptDependencyRetainedUnreadyCapsuleDataV1`: payload `p`, receipt, intent) and the retirement sweep; a rename-free retirement (marker inside the tree plus an attempt-numbered stage name) changes all of them for every platform and cannot be proved without a Windows machine. Proposal if (b)+(c) are not enough on m05: attempt-numbered stage directory (`<gen20>.<n>`), retire by a marker file and delete later with `FILE_DISPOSITION_POSIX_SEMANTICS` (already used by the module for bindings).
