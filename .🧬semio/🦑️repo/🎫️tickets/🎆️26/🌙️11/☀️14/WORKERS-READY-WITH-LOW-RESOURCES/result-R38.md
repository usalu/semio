## A. g1-m04: what the line really is

### Premise corrected: there is no systemd unit and no 4096 MB limit in this refusal
- `grep` for `systemd|systemctl|MemoryMax|MemoryHigh` in all g1-m04 reports and logs: no hit. `SERVICE_UNDER_USER_SLICE` of the R30 test is our own cgroup, not a unit. The service is started by the client (`repo service host run`, parent pid 1977 in `round-24-try-12.bootstrap-last40.txt`, log `/run/user/1000/semio-repo/1000/host-83cab94e8485.log`). `spawnHostServiceV1` (`LIB/🏡️resident/🏗️composition/🌐️host/🟨️.mjs`) creates `semio-service-graph-<hash>` next to `semio-jobs` with `memory.max = serviceLimitMegabytes` (was the constant 4096 in `🧠️memory/🧬️schema/🔣️.json`), `memory.high` 90 %, no swap. So the service limit is a code constant, rewritten at every service start; no root file anywhere.
- The refusal text is produced by `🏡️resident/🏛️service/🌐️host/🟨️.mjs:166` (`error.code==="memory-budget"` -> `host-memory-budget`). The error comes from the slice pool (`👷️slice-pool/🟨️.mjs:56`) when the kernel killed the leaf cgroup of ONE slice load (`memory.events oom_kill>0`). Wording "the service holds N MB of its N MB" is misleading (it is the load, not the service); I left the text.
- The N is not 4096. It is the leaf cgroup `memory.max` of the load = `sliceLimitPolicyV1`: `max(64, service limit - used - 256, lent, min(plan limit, learned peak))`, `lent = min(8192, 75 % of MemAvailable - 1536)`. The eleven values reproduce: 5340 ... 6381 = `lent` for MemAvailable 9168 ... 10 300 MB, and 6339 = `min(6339, learned)` (6339 = 40 % of 15848 = the plan limit; the pool writes back `peak * 1.25` after each breach, so the limit saturates there; 6364, 6381, 6384 are `lent` of the later higher availability).

### Cause
The kernel kills the load at `memory.max` without any settle. The plan of this repo needs 7-10 GB (Macs: 8071 -> 10051 MB). On macOS the pool guard (`planGuardVerdictV1`) lets a plan between the plan limit (40 %) and the ceiling (60 % of the machine) run: settle once, then refuse only at critical pressure, when available < 2048 MB, or above the ceiling. On Linux the kernel limit lay at 40 % (plan limit), below the guard ceiling (60 %), so the guard never got to judge. Same plan, same machine, other verdict.

### Fix (landed)
1. `👷️slice-pool/🧱️limit/🟨️.mjs`: new `slicePlanCeilingMegabytesV1` (the guard ceiling: `max(60 % of the machine, plan limit)`, 0 where the guard is off); `sliceLimitPolicyV1` takes `planCeilingMegabytes` and never sets the kernel limit below `ceiling + 256 MB margin`. `👷️slice-pool/🟨️.mjs` passes it. g1-m04 numbers: ceiling 9508 MB, kernel limit 9764 MB (was 5340-6384). The pool guard (settle first, then continue/refuse `memory|pressure|ceiling|unknown`) now decides, exactly as on macOS, and a refusal is the typed `graph-plan-too-heavy` (exit 75), not exit 1.
2. The service cgroup limit comes from the machine: new `graphServiceLimitMegabytesV1(host)` in `🧠️memory/🟨️.mjs` = `max(serviceMinimumMegabytes 2048, 60 % of the machine)`; schema constants `serviceLimitMegabytes: 4096` replaced by `serviceHostShare: 0.6`, `serviceMinimumMegabytes: 2048` (schema, fixture, `.d.mts`). Spawn uses `graphServiceLimitMegabytesV1(fleetHostReadingV1().hostMegabytes)` (physical memory bounded by a real machine-level cgroup limit, R30 reading). g1-m04: 9508 MB. Checked on this Mac: 32768 -> 19660.
3. Existing groups with the old limit: no unit to fix. `prepareServiceGroupV1` tolerates `EEXIST` and writes `memory.max`, `memory.high`, `memory.swap.max`, `memory.oom.group` again at every start, as the delegated user, no sudo. The landed files are in `serviceRevisionFiles`, so the running service on g1-m04 (started under the old revision) is reloaded by the next `repo` client; the new service rewrites the limit of the same group (`graph-<hash of runtime dir>`) before it is placed in it. Needs nothing from the owner. If cgroup v2 is not delegated the code does nothing (as before), then no kernel limit exists and the guard alone applies.
4. "Settle/shrink before refusing": already the pool behaviour (`type:"settle"` message to the worker, `graph-plan-settled` line, then judge); it was only unreachable on Linux. Not changed.

### Proof
- NEW `LIB/🏡️resident/🧪️tests/🐧️leaf-ceiling` (4 tests, green): (1) kernel limit for 9 machine cases (4/8/15.8/16/32 GB, unknown host, tiny available) equals an independent Python computation, is >= ceiling + margin wherever a ceiling exists, unchanged where the guard is off (>= 24 GB); (2) the g1-m04 case: old formula gives exactly 6339 (reproduces the log), new gives 9764, verdicts of the guard (settle, continue, refuse memory/pressure/ceiling) all happen below the new kernel limit and 7000 MB was above the old one; (3) service limit equals Python, 15848 -> 9508, 16384 -> 9830, floor 2048, no `serviceLimitMegabytes` left in policy or spawn; (4) a pre-existing group with 4096 MB is rewritten to 9508 MB / 90 % high through the cgroup ports.
- Before: red (module exports missing). After: green. Neighbours green on the live tree: booking 3, plan-guard 11, plan-limit 3, host 36, cancel 37, reservation 8, revision 2, reload 11, plan-refusal 4, restart 3, failure 14, linux-host (R30) 15. Identical pre-existing reds before and after, not touched: `🧠️memory/🧪️tests` process tree reader, `🧱️job-limits/🧪️tests` watchdog kill.
- cgroup v2 semantics used, from the kernel documentation (cgroup-v2.rst) as I know it, not read from a Linux machine: `memory.max` is a hard limit, on overrun the kernel reclaims and then OOM-kills (the whole group with `memory.oom.group=1`); `memory.high` only throttles; the effective limit is the smallest along the ancestor chain; a write to `memory.max` of an existing group is effective at once; a group holding processes cannot enable controllers for children (why the leaf is a sibling of the service group).
