Fix (landed, live files): a process-wide "former root" table, `👁️observation/🏚️relocation` (`noteFormerRootV1`, `rebaseTextV1/RowV1/RowsV1`, `adoptRecordedRootsV1`). Boundary-safe (`/Users/Shared/semio-store` is not touched), idempotent, nested roots refused. Same mechanism makes a generation made on another machine (other checkout path) usable. A real change is still caught: it is content/type checked after the rebase.

Before/after (real data, same probe, same sampled rows): stale old-root rows 65 774 of 65 774 (100 %) -> 370 of about 77 000 free-kind rows (0.5 %, the files and directories peers really edited since generation 238). ## 2. Status 75 "The stamps moved again after the restart"

Cause: `runWithStaleReexecV1` allows 6 restarts and counts every one; a read of 17 s per attempt in a tree where agents land edits that move declared stamps finds them moved again each time (6 x 17 s = the observed 106 s). A live tree always moves.
Fix: a restart whose moved stamps have other live values than the previous restart's (signature of `id=live`) followed a moving tree and does not count; the same values again still count (a real loop is still bounded at 6) and a patience of 30 min (`movedPatienceMilliseconds` in the schema) bounds the follow. Test: `🧷️format-stamps/🧪️tests` "a restart that finds the stamps moved to other values ..." (18 restarts with moving values stay at count <= 2; identical values exhaust; patience exhausts).

## 3. `🧬️launcher.ts` "hang"

Not a product hang and not tied to the move. `🤝️shared-worktree/🔁️replica/🧷️sidecars/🧪️tests/🧬️launcher.ts` is a fixture program (the supervised launcher the real test `🟦️.ts` spawns with `SIDECAR_TEST_DIR`), not a test. R44's `land.py` ran every `.ts` under any `🧪️tests` folder with `bun test`, so it started the launcher, whose child dies at once (`SIDECAR_TEST_DIR` undefined) and is restarted forever ("agent ended with status 1, starting again in 15 s") at 0 % CPU; `bun test` has no test to time out. Reproduced here (40 s, killed by me). Fix in the harness: `R47/land.py` runs only files named `🟦️.ts`. Not done: a guard in the fixture itself (module belongs to R46, `🤝️shared-worktree`): it should exit when `SIDECAR_TEST_DIR` is unset. Other landing scripts that walk `🧪️tests` (R44 pattern) have the same bug for `🧬️daemon.ts`, `🧬️child.ts`.

## 5. Follow-up: first real measurement (child 19234, `settle closures=7392 ... failed=0 wall=835246ms ask=703614ms/29`)

What `ask` waits on (starved-stack samples of 19234.log, 16:52 to 16:57Z): it does not wait on awaits, locks or leases. The stacks are `walkImportsV1 < lstatSync / existsSync / probe < directoryProbablyExists / tryFile (typescript.js module resolution) < footprintPulseV1`, blocked 1.5 to 8.5 s each, loop lag 1 to 12 s, 5.5 M live objects. It is the closure walkers actually running (TypeScript module resolution, one synchronous syscall at a time on the main thread), 7390 walks, 29 chunks of 256: about 24 s per chunk at 10 % CPU because every syscall sits in a kernel that is at 70 to 80 % sys (git pollers, mds, nfsd, see R45 #5). `entries=7473` against 168 before shows why `slow=7390` and `vouched=0`: this was the first complete derivation in the new root, there was no manifest entry to vouch (`entry===undefined` goes slow by construction). `failed=0` and `summary=paths:2748` show the rebase works: the stale set fell from 101 161 paths to 2 748.

Not fixed: making that one-time derivation parallel. Synchronous syscalls on one thread cannot be batched; it needs worker threads or child processes for the walkers, which I did not build. It happens once per relocation (or after a manifest loss), not on every read.

Second read (2): NOT observed, because a read is still running and I did not start one. What the code and laws say it does:
- Every closure has a manifest entry and a persisted node now, so nothing is derived again (law `✂️cutoff/🧪️tests/🪢️hard-parts`, 3 rounds: 0 derivations).
- `summary configs:true, modules:true` (a stale bare-resolve or registry row, or any package.json/project.json edit by a peer) makes the config and bare-module parts "hard": they are never vouched by stamps, so each such closure takes the slow path. The slow path only re-checks the part rows through the host `holds` (journal-filtered when a journal cursor exists, plain stat otherwise), each shared row once per start (law: at most 1 + 40 rows for 40 closures), no walk. So the second read will show `slow` high and `vouched` low, but `ask` should be minutes of row checks rather than 14 minutes of walks, and seconds once the journal cursor is committed. I did NOT make hard parts vouchable by content digest: the only complete list of what a bare resolution reads is its recorded probe rows, and stamping all of them costs as much as checking them, while a short list (config names plus `node_modules` package directories) would be a soundness risk I could not prove in this window. This part of the request is open.
- If the second read still shows `slow` about 7390 with a long `ask`, the first thing to read is whether `facts` ran as a verify epoch (no journal cursor) in that trace.

Resume after a kill (3): persistence was already incremental (node store flushed after every chunk of 256 closures, manifest saved at most every `manifestSaveMilliseconds`), so a killed read loses at most the chunk in flight (about 24 s here). One gap closed and landed: a chunk that is cancelled (signal) now flushes the nodes it already derived before it throws. Law `🪢️hard-parts` "a start cancelled half way": with chunks of 10 the next start derives at most half (was all 40 before the chunk size was lowered in the test; without the flush a cancel inside a chunk loses that chunk). Not covered: SIGKILL inside a chunk (that chunk is lost) and the facts phase (not resumable, now journal-vouched instead).

## 6. Audit follow-up (audit-R47-R48.md): findings checked against the code, fixed in landing 3

- A1 REAL, fixed. `projectObservationHoldsV1` and `current` (sync checks for project records and writes) read the recorded old-root path. Both rebase now. Law "the synchronous record checks read a recorded old-root path as the live path, also while the old tree still exists": red before (old tree keeps the recorded bytes, live edited, `observationRowsHoldV1` answered true; checked by removing the rebase from `current`), green after, and it also holds when the old tree is gone.
- A2 REAL, fixed. The table is still process-wide (the observation layer does not know the workspace), so the fix is conservative: every live root the process serves is registered (`noteLiveRootV1`, called on each index open); a mapping from a root that is any served workspace's live root is dropped and refused for good, and a root taught with two different live roots is dropped and refused. Cost: in a multi-workspace service the rows of the moved workspace stay stale (re-checked, never wrongly fresh). Law "a root of one workspace never rewrites the rows of another workspace ...".
- A3 REAL, fixed. A former root that nests with, or chains into, another former or live root is refused together with the other, so the result no longer depends on the insertion order. Law "chained and nested former roots give the same answer in every insertion order" (4 orders).
- A4 REAL, fixed. The JSON-escaped form of a root (`C:\\Users\\x`) is matched and replaced in question text too; separators `/` and `\` both count for nesting. Law "a Windows root is rebased in the JSON text ..." (run on macOS with string data, not on Windows).
- B1 REAL, fixed. A restart that follows a moving tree is free only if it ran at least 60 s (`movedProgressMilliseconds`); quicker followed restarts are counted and stop at 30 (`movedFollowMaximum`), so flapping A->B->A->B ends. Whether a long run made real progress is judged by its duration only; no stage-level criterion exists.
- B2 REAL, fixed. The 10-minute progress reset no longer applies when the moved values are identical to the previous restart's, so the 6-restart cap holds for long reads. Law "a restart is bounded ..." covers identical values after 10 minute runs, flapping values, and long-run progress staying free.
- Not touched (R48's): C1, C2, C3, D1. D2 (originals under `🗑️generated`): my edits were made in place on the live files, no rollback copies were taken for R47; the landings.md entries list the digests.
- Red-before was checked by reverting only for A1; for A2 to B2 the laws assert behaviour the previous code could not have (single table, no escaped match, no follow cap, unconditional reset), I did not re-run them against the old code.
- Landing 3 ran after the read (31945/31946/19234) had already ended, so no read was affected; format-stamps "wiring" test is still red from a peer's discovery edit.
