## Implementation keying (point 3), verified in code, no fix needed
- The sidecar only orchestrates. Every inference is a fresh child `repo show projects` (`🛰️sidecar/🕸️graph/🟦️.ts` `inferGraphReadV1`, `Bun.spawn([command,"show","projects"])`) that loads the tree as it is when it is spawned; the code of the sidecar process is not part of the records.
- The records the read publishes carry the implementation: the generation manifest has `implementation` (`🕸️graph/🕰️generations/🟨️.mjs:97,102,416`), taken from the loaded implementation revision (`🕸️graph/📥️inference/🟨️.mjs:77,119,123`, `implementationRevision()`), and a manifest of another implementation covers nothing for a request (`🕸️graph/🕰️generations/🔭️coverage/🟨️.mjs:48` `manifestImplementation!==implementation` returns undefined). So results of an old implementation are never taken for the new one.
- The only records the sidecar publishes itself are the served answers (`🙋️wanted/🟦️.ts:108` `servedStateV1`: keyed by requester, not code-dependent), the cost file and the wave uploads (copies of generations that carry their own implementation). A record under a wrong implementation identity cannot arise from the deferral.
