# R8: a missing build input closure leaf is a cache miss, never an error

## Cause (why the two earlier repairs did not catch g1-m03 round 14 try 5)
Evidence: `workers/g1-m03/round-14.try-5.service.txt` lines 34-35 (`generation 221 (5100 projects) restored from the remote cache … 0 projects stale`, then `refreshing 267 projects`), lines 139-162 (`graph:slice-worker`, expansions of 167, 341, 233 closures, then `closure-missing … named by @semio-tech/framework-os-mcp` and `request-failed … ENOENT: closure-missing:5d52130e…`), stack `🕸️graph/📁️workspace/🟦️.ts:87:451` and `📥️inputs/💾️storage/🟨️.mjs:146`.

1. The restore (`restoreGenerationV1`, `🌐️remote-exchange/🟦️.ts`) downloaded only the 5104 generation documents. The closure leaves live in the producer's `build-input-closures/` and were never uploaded or fetched, so every restored fragment named leaves that exist only on the producer (233 of them reached the failing slice). N10 "What is NOT done" named this and left it.
2. The failing read is the pinned slice read in `🏡️resident/🏗️composition/🌐️host/👷️slice-pool/👷️worker.ts:20` (`loadBuildInvocationGraphV1(… pin …)`), a worker thread that expands the sealed generation 222 of the parent. N10's heal (`load/🟨️.mjs`, expand catch) can only help when the reader is a builder that may invalidate and rebuild; a pinned read has no builder to rebuild (the pin names the parent's generation), the first round (`repairs++>0` gate) did not repair at all, and the worker's error crosses to the parent as a plain text (`errorOfMessageV1`), so the parent had no heal either: the request failed with the ENOENT text. N10 follow-up 2 fixed the recognition of the text but not the missing carrier (1) nor this path (2).
3. Nothing ever asked the fleet: a leaf was either on the machine or an error.

## Fix (file:line are of the landed files)
- `🕸️graph/🩹️closure-repair/🟨️.mjs` (+ `.d.mts`): the ONE closure leaf function set. `obtainClosureLeafV1` (present / fetched from the fleet cache, verified against its name `sha256(bytes)==key`, bounded to 16 MiB, written under writer custody through `adoptStagedGraphLeavesV1` / `refetched` / `missing`; any failure of the fetch is `missing`, never an error), `readClosureLeafV1` (read, obtain once, else the typed `closureMissingErrorV1`: code `closure-missing`, message `closure-missing:<key> <namespace> leaf is not on this machine`, no `ENOENT` text, carries key, namespace and the projects that name it), `closuresOfFragmentsV1` / `closureOwnersV1` (which leaves the fragments name and which owners name them; memo per content addressed fragment), `settleClosureLeafV1` (obtain, else purge the records that name the key = mark exactly those projects stale; prints the one log line).
- Readers routed through it: `📁️workspace/🟦️.ts` `portableInputs` (the graph read; was the only throw of ENOENT), `📥️inputs/🧮️digest/🟨️.mjs` (task digest) and `🔧️tools/🏗️bazel/🔗️closure/🟦️.ts` (absent leaf is now the typed error). `👁️observation/📥️reuse` (`inferenceInventoryReferencesHoldV1`) already treats an absent leaf as a miss (recompute) and is unchanged; `⚡️caching/…/📥️scope/🟦️.ts` still reads its leaf with its own `readScopeMetadataV1` (not changed, see not verified).
- Upload (`🌐️remote-exchange/🟦️.ts` `uploadClosuresV1`): the leaves named by the fragments of the generation (memo `<root>.closures.json` per fragment, so a wave delta reads only new fragments) are uploaded BEFORE the head, deduplicated (`content.missing` once, only for keys not in `<root>.closures-sent.json` of this instance), bounded (20000 leaves, 16 MiB each, Policy `maximumClosures`), listed in the head action result as `c/i/<key>.json` / `c/l/<key>.json` (keeps them alive in the cache). The leaves this machine does not hold are reported with their owners and add to the head's `stale`.
- Restore (`restoreClosuresV1`): the fragments in memory are scanned before the pointer is written; absent leaves are read from the cache by name (verified, 8 at a time, bounded) and written; the leaves nobody holds come back as `outcome.closures.missing` with the owners naming them and `outcome.stale`, never as a failure. `load/🟨️.mjs` `settleRestoredClosuresV1`: each such leaf is settled once (`host.settleClosure`), the heavy owners are asked of the fleet through the normal fleet-first path (`host.fleetRead`), and the generation is invalidated once so the request derives those records (they are removed) in the same request.
- Heal in the expand catch (`load/🟨️.mjs`): every builder round settles the leaf first (round 1 included); `refetched` needs no invalidation; otherwise fleet-first for the named owners, then invalidate. A shared reader now reports the named owners as `pending.dirty` (with their roots) so the normal fleet read / prefetch path derives them before the builder takes over. After the bounded rounds the failure is the typed `closure-missing` error, never ENOENT.
- Host (`🕰️host/🟦️.ts` `settleClosure`): fleet fetch through the new `exchange.leaf` (cache by name, verified), local cost table decides `asked of the fleet` for the log line; `🤝️prefetch/🟦️.ts` `fleetReadStaleGenerationV1` now returns the fleet decision.

## The line a worker must show
`[graph] closure-missing <64 hex key> named by <n> projects: refetched` or `… : re-derived` or `… : asked of the fleet` (one per absent leaf per settlement; `n` = owners of the generation that name the key). No request may end with `ENOENT … closure-missing`; if the line shows `re-derived` the same request prints the normal inference / `fleet` lines for those owners and completes.

## NOT verified
- No graph command, no real restore from the production cache, no worker: the restore, the settle and the slice path are proven with a real cache server and the mock world, not with a 5100 project generation. The measured cost of the fragment scan at a restore (46 MB of brotli, in memory, once per restore) and of the first upload scan (all fragments; later uploads read only new ones) is NOT measured.
- Re-deriving uses the only lever there is (`invalidate` = cold plan with reuse of valid inference records, plus removal of the records that name the leaf): a worker with a restored generation that has no local records for the other 4800 projects may still pay a cold plan; a precise per-owner stale mark (dropping owners from the restored manifest) is not done, the manifest `membership` and fact index would need the same change.
- A PINNED slice read cannot rebuild: if a pinned generation names a leaf that is gone after the parent's settlement, the slice worker ends with the typed `closure-missing` error (not ENOENT) and the parent's request fails with that text; the restore-time settlement is what prevents it. The parent does not retry a failed slice worker on this error.
- `⚡️caching/…/📥️scope/🟦️.ts` (selection scope reads a leaf directly) is not routed; no type check (`tsc`) of `🕰️host/🟦️.ts` was run (bun only strips types).
- The heavy label uses the local cost table; whether the fleet then serves the heavy owners (and its wait bound) is the existing fleet-first path and was only exercised through a spy.
