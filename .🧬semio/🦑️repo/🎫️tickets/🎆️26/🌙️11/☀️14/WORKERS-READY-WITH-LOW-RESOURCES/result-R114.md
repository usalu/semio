## The decision and what it means in code
"The parent verifies what it adopts" is replaced by "exactly one process verifies each record, and the verdict names the record it judged". The name is `headerDigest`: the sha256 of the header line of the stored record, which holds the digest of the key, the digest of the result, every inline observed row and every block digest of the rows kept in blocks. A reader that holds the same header line holds the same rows.

- `👁️observation/🟨️.mjs` `verifyStoredProjectRecordV1({cachePath,key})`: reads the record plainly (no reader custody of the graph store; the custody wrapper admits plain READS only inside this function, through an `AsyncLocalStorage`), checks the key digest, settles the closure entries (derived in the child when stale), verifies every row (closure rows through the provider, the others through `current`) and answers `{verdict: holds|stale|other|missing, headerDigest, rows, verifier: pid}`. A verdict is never kept: the next verdict judges the files as they are then.
- `observeInference` / `observeProjectInferenceV1` take `verdict({headerDigest})`: after reading the record of the asked key the reader asks for the verdict; `holds` for exactly that header makes it the candidate without `settleClosureRowsV1`, without `projectRowsHoldV1` (twice in the old code) and without any probe; anything else (other header, stale, failure, no verdict) verifies as before.
- Farm child: job kind `observe` (`👷️service/🟨️.mjs` -> `observeProjectRecordV1` in `📦️project-nodes/🟨️.mjs`, binds the closure store writable like a warm job, weight 0.01 so a child that serves hundreds of them is recycled by memory only). `farm.observe(job)` runs through the same child choice, retry and loss handling as `farm.warm`.
- Take pass: `inferProject` passes `verdict` only in a take (`away.take===true`) and only while a child is ready (`farm.width()>0`); the wait is bounded by `OWNER_VERDICT_WAIT_MILLISECONDS_V1` = 180 s, then the parent verifies itself. The lookups of the take pass run in up to 12 parallel looks per lane (`TAKE_POLICY_V1.concurrency`), each awaiting a child, so the take now scales with the children, not with the one event loop. The parent's loop is free while a child verifies.
- Also: `verdict` clock key in `observationLookupClockV1`.

## Barrier found
A farm child cannot run the whole `observeProjectInferenceV1` lookup against the real store: reading a managed record needs reader custody (`requireRepositoryBuildGraphObservationPathV1`, an issued resource control and invocation of the parent). The child therefore reads plainly. This works on the real store: 60 of 60 real records of the newest wave were read and judged outside custody (`plainread.ts`: 10.8 ms CPU per record, median 5.3, p90 29.7, average record 5.3 KB packed). A block that the collector removed meanwhile makes the child answer `missing`/fail and the parent verifies itself.

## Measured
- Reader CPU per owner with the verdict adopted (model, 4 real children, 50 owners, 200 closure rows each): 3.6 ms; settle, verify and rows verified 0 (test `🧒️children`, bound 50 ms). Reading the record itself under custody is not in this figure: the plain read of 60 real records costs 10.8 ms CPU each (median 5.3, p90 29.7), the custody read of the parent does the same work, so the reader's remaining per-owner cost in the take is about 11 ms for the read plus the retention of its rows plus `refs`.
- What the verdict removes from the reader, real records (own process, 6 owners of the newest wave that have a record, entries made fresh first, take-style look, load 35-43, two runs): settle 10.6 and 10.5 s CPU for 6 owners = 1.75 s per owner (145 layers checked, 22 614 indexed, 40 s wall in layer checks), refs 1.6 s for the 4 owners that got that far; so 2.03 s CPU per owner before, of which settle is 86 %. After the landing the reader does that work in none of its own time: a child does it. (Earlier waves: settle 0.43 s per owner, R112; the owners here are the large ones of the wave, hence more.)
- The refs-only run after the landing could NOT be measured cleanly: between two runs of the harness the closure entries are already stale again (peers edit continuously: `stale 6 of 6` in the refs-only runs, so every take answered a miss before refs ran, 49 and 61 ms CPU per owner are the misses, not refs). The only refs figures are 1.6 s per 4 owners (0.4 s each, cold cache, after the settle) and R112's 0.22 s.
- Owners per minute on the 136 owners that have records: not measured (no real read with the new code; harness cannot replay children). Arithmetic from the measured numbers, to be confirmed by a read: the parent is left with read 11 ms + refs 220 to 400 ms + rows retention, i.e. 2 to 4 owners per second per parent thread (120 to 240 per minute, against 64), and the settle work (0.43 to 1.75 s CPU per owner) spreads over the children (cores minus one, memory permitting) instead of the one thread.
- Children CPU utilisation: not measured (needs a real read).
