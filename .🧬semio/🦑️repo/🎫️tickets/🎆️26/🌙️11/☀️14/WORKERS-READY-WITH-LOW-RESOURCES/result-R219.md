Gaps found (and what this package does about each):

1. A machine with NO generation that starts a whole read does not look for a fleet head before it takes the builder custody; the restore only happens inside the custody, and nothing stops N machines without a head from each starting a whole read (the custody is per machine; the only fleet-wide claim was the graph server's refresh interval `graph-refresh`, which governs the background refresh, not an explicit `repo graph --graph-policy fresh` or a `request` read). Built: the whole-read gate (section 2.2).
2. A head published mid-read by the wave uploader has `stale>0`; a waiting machine that fetched it would start its own build of the remaining owners, i.e. a second read. Built: waiters only fetch a COMPLETE head (producer knew 0 stale), a partial head only shows progress.
3. R210's open item: a `current` question on a machine without a generation could not fetch the fleet's complete generation (it refused and told the user the fleet holds one). Built: the fetch-only path (section 2.3).
4. No machine-size rule: a 16 GB worker could be the one that claims a whole read (the failure mode `farm-overrun`). Built: machines below the serving size (24000 MB) yield 5 minutes before they claim.

## 2. What was built (schema first)

### 2.1 `look` on the generation exchange (`🌐️remote-exchange/🟦️.ts`, edit)
`remoteGenerationLookV1` and `GenerationExchangeV1.look`: one short request (no document downloaded), verdict `{state: none|other-code|partial|complete, ahead, held, owners, stale, origin, ageSeconds}`; `held` = owners of this machine's own sealed generation (0 without), `ahead` = a restore would take it (same rule as `ahead`).

### 2.2 Whole-read gate (new member `🕰️generations/🤝️whole-gate`, schema `🧬️schema/🔣️.json`, `🟦️.ts`)
`wholeReadGateV1`: complete head that a restore would take: fetch at once (no claim). Else claim key `sha256([domain, registry identity, platform])` (lease 120 s, heartbeat 15 s, the lease helper `holdV1` of the selected exchange, now exported); holder reads and calls `release` after it published (the loader releases in a `finally` after `publishRemoteGenerationV1`); the others wait in 30 s slices with a progress line (EN/DE, names the holder and, for a partial head, owners and stale count), bound 12 h, fetch the complete head when it appears (`waited`), take over when the lease lapses (`taken-over`), read locally at the bound or on any fleet fault/no claims/read-only (`unreachable`), cancel throws. A machine that holds its own generation is `skipped` (reads the difference alone). Machines below the serving size yield `smallMachineDelayMilliseconds` (5 min) before claiming. Loader edit (`🔌️load/🟨️.mjs`): `wholeReadGateV1(host,...)` before the builder loop (only for whole, non-pinned, non-`current` reads; the host supplies `host.wholeGate`), `release` in a `finally`; host edit (`🕰️host/🟦️.ts`): `wholeGate` from `wholeReadGateOfHostV1` (fleet client of the selected exchange, origin as owner, memory of the machine); `🟨️.d.mts` documents the host member.

### 2.3 `current` fetches a complete head (`🔌️load/🟨️.mjs`)
`GENERATION_NONE_SEALED` path: when the fleet holds a complete head a restore would take AND the builder custody is idle (`host.builderIdle`, non-blocking probe), the question takes the custody once with `fetchOnly`: restore, no inference, no refresh, serves the generation as `current` with its age (`sealedAge`). An incomplete head, an other-code head or a read going on here (custody not idle) keep the typed refusal of R210 (progress text unchanged). The custody wait after the idle check is the normal custody queue (a reader that sneaks in between is waited for with the usual custody progress lines).

## 5. NOT verified / open

- Nothing ran against the real 4785-owner generation: the documents/MB of the head, the download time on a worker (disk, LAN), and the restore + content verification time of a cold 16 GB worker are unmeasured (only the action-result size is computed, 1.67 MB). The restore verifies facts by content against the worker's tree: the cost on 4785 owners is the unknown that decides "answers in seconds".
- Real host wiring (`graphFleetSettingsV1`, signed fetch, real `builderIdleV1` with generation -1, real custody) was only import-smoked; the real-server tests use the mock host and the exchange against a real cache server, and a graph-fleet client with token undefined (the production cache requires a token: same client as the selected exchange, which has a real-server law).
- The claim heartbeat is a timer of the reading process: a parent that blocks its event loop for more than the 120 s lease lets a second machine take the claim over (a duplicate read, not corruption). Not measured on a real read.
- Workers do not run whole reads in the ready loop (R137 probes are selected reads), so no origin-folder evidence appears by itself: step 5 needs a command on each worker. Making a ready stage run `repo show projects` would change the readiness contract and is NOT proposed here.
- A head from other code (`other-code`: stamps of the inferrers differ, e.g. a stamp bump landed after the seal) is not fetched by the gate and the machine reads (the claim still serializes it).
- Taxonomy/registry admission of the new member name `🤝️whole-gate` and `tsc` typing of the new files were not run (the staged runs are bun only).
- Not built: cancelling a local inference when a head appears mid-read; a published per-owner digest table (R171 style) for whole heads (the facts index does the job, but a differing-owner list without downloading the fragments would need it).
