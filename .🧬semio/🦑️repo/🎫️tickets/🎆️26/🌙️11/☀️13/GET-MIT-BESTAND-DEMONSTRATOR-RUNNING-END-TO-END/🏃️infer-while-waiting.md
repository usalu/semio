# Infer While Waiting (Cooperative Completion)

## Problem
`fleetReadV1` published the wanted request and `awaitWantedV1` only polled; this machine inferred what was missing only afterwards (`host.prefetch`). With ~1900 stale projects and one serving machine (hours) the Mac idled while it could do ~40 light projects/min.

## Design
`fleetReadV1` takes an optional `infer(names, signal)` (the governed inference the caller runs after the wait; never throws except on cancellation). When the request is outstanding, the machine can run a wave (`plan.waveProjects > 0`) and light projects remain, a local loop runs beside `awaitWantedV1`:

- Order: light projects only (heavy ones keep the solo rules after the light ones), ascending recorded cost, ties by name descending. The server (`orderByCostV1`) works demand, heavy, cost DESCENDING, so the two sides meet in the middle. Projects the servers leave to this host (`left`, cross-platform bound) go first: nobody else infers them.
- Batch: `plan.localProjects` (the light projects one wait allows, 72 on a 16 GB Mac). Before each batch the served list is refreshed and served projects are skipped; so overlap is at most what the fleet delivers during one batch (inferred wins, `arrived` never counts it). `leftHere` is now a union over answers so a bound project is not forgotten once the server stops listing it.
- Same governed path: the host's `fleetRead` is now a method that passes `infer: names => this.prefetch({...request, dirty: names, roots})`, i.e. `upgradeBuildCapacityBeforeRebuildV1` + `prefetchStaleGenerationV1` (capacity gate, claim registry, slots, memory governor, `release` between runs). Nothing is reserved before the first batch starts; the post-wait prefetch/build later hits the records.
- Narrowing: after every batch `publishWantedV1` is called again with the same `createdMs` and only the projects neither served nor inferred. The protocol allows it cheaply (idempotent renewal: subset, later expiry, same claim and position; the server's next round reads the shorter list). When nothing is left no request is published; it lapses at `ttlMilliseconds` (20 min) because there is no withdraw message (an empty list would only be read as a `foreign` request by `claimWantedV1`). Noted limitation.
- End: the wait ends when served ∪ inferred covers every stale project (`take` accepts served, bound-to-host and inferred names, so progress also resets the stall bound). The wait ending by its bounds (silent/stalled/limit) stops the loop after the running batch and leaves the remainder to the caller's existing path. While the loop runs the old "light remainder fits one wait" settle rule is off; after the loop ended or failed it applies again. A failing `infer` says so (en/de) and the read waits for the fleet only. Cancellation: passed to `infer`, rethrown after the wait.
- Result: `FleetReadV1.inferred` (only when cooperating); `arrived` = fleet only; `missing` excludes locally inferred projects; heavy owners then follow `solo(kept)` unchanged.
- Without `infer` (or an unreachable fleet, or a machine that cannot run a wave) nothing changes.

## Live defects and root fixes (round 2)
Live log: each batch started a farm (1 own worker, then host grants up to 8), the farm hub outlives a construction (idle close 5 min) so the workers of all batches stayed, the slice worker's process tree reached 9924 MB against the slice-guard ceiling (60% of 16384 = 9830 MB) and the read was refused with `graph-plan-too-heavy`, stage "?" / operation "?".

1. Workers accumulating / unbounded farm. Two roots: (a) the farm size ignored the plan's memory (`planGraphFarmV1` bounded only by work and cpu), so any prefetch of >= 128 projects asked the host for 8 workers whose processes count in the tree the slice guard judges; (b) the hub kept workers between batches. Fixes: `planFarmWorkersV1` (`🧠️memory/🪜️plan-stage`, new policy `treeShare` 0.5 of the host, below the guard ceiling; Infinity on serving machines or limit `off`) bounds `planGraphFarmV1` through a new `maximumWorkers` (reason `memory`, told as `serial` when under 2) and `openProjectFarmV1`; `project-nodes` passes it for every farm, so the non-cooperative path is bounded the same way. A 16 GB Mac now gets at most 4 workers beside a 1.3 GB plan (about 7.5 GB tree). `inferBatchV1` (`🤝️prefetch`) runs one batch's governed `prefetch` and then `closeProjectFarmsV1` in `finally`, so workers and host grants are gone before the next batch (several batches never accumulate, also when one fails); the host's `fleetRead` wires `infer` through it.
2. Stage "?" / "?". The prefetch inference ran outside any plan guard, so the slice service never got a stage event. `prefetchBuildGraphProjectsV1` now runs in `createPlanStageGuardV1` (same refusal `graph.plan-too-heavy`) and marks the declared stage `inference` first, like the post-wait inference of `discoverBuildGraphPartV1`; this names stage and operation for the cooperative batches and the ordinary prefetch alike.

Files: `🧠️memory/🪜️plan-stage/🟨️.mjs`, `🟨️.d.mts`, `🧬️schema/🔣️.json`, `🧪️tests/🟦️.ts` (schema test knows `treeShare`); `🕸️graph/📥️inference/📦️project-nodes/🟨️.mjs`, `🏊️project-farm/🟨️.mjs`, `🟨️.d.mts`, `🏊️pool/🟨️.mjs`, `🏊️pool/🟨️.d.mts`; `🕸️graph/🤝️prefetch/🟦️.ts`; `🕸️graph/🕰️host/🟦️.ts`; new test `🕸️graph/🧪️tests/🏊️cooperative-farm/🟦️.ts` (3 pass: bound numbers, several batches with a simulated farm never above the allowance and zero alive between batches incl. a failing one, stage and wiring structure).
Other touched suites: `plan-stage` 11 pass, `plan-stages` 3, `fleet-read` 5, `prefetch-booking` 2, `offer-fresh` 2, `offered-once` 4, `project-farm` 30 pass (with `SEMIO_TEST_ARTIFACT_DIR` set; without it they fail on the environment). ## Round 3: one continuous run instead of batches (throughput)
Live: with batches of 48 every batch re-entered `prefetchStaleGenerationV1` (store selection, stamps over all files, claim admission), `discoverBuildProjectsV1` (whole-workspace setup, every plan stage) and a farm spin-up/teardown; 5-9 min per 48 projects. The design is replaced; the batch loop and `inferBatchV1` are gone.

Design:
- `fleetReadV1` calls `infer({names, skip, done})` ONCE: `names` are all light projects not yet served, lightest first. `skip(name)` is synchronous and reads the served set that the wait's polling keeps current (every ~2 s): true when the fleet delivered the project (dropped, never counted as inferred) or the wait ended by its bounds (the rest is left to the caller at once; recorded in `cut`). `done(name)` fires after each project and every `narrowMilliseconds` (new policy, 30 s) the request is republished without the inferred ones (same `createdMs`). After the run, every name neither cut nor skipped counts as inferred (covers owners a peer claim computed). Failure and cancellation as before.
- One governed path: `inferRunV1` -> host `prefetch(request, {hooks})` -> `prefetchStaleGenerationV1` with `chunk: MAX_SAFE_INTEGER` (new `chunk` option of the claim registry `prefetch`/`admit`: one claim over all names instead of 128-owner chunks) -> ONE `prefetchBuildGraphProjectsV1` (one plan stage entry `inference`, one setup) -> ONE `discoverBuildProjectsV1` -> ONE `openProjectFarmV1` (workers bounded by `planFarmWorkersV1`, reused for every project of the run, 1900 projects planned at once). In `project-nodes` the job list is sorted by `options.ownerRank` (after the solo-heavy rule) and `loop` asks `options.skipOwner(name)` before each job; `onOwnerObservations(name)` feeds `done`. `closeProjectFarmsV1` runs once at the end (also on failure).
- A peer command waits on the single claim instead of re-claiming 128 at a time; the claim is `done` when the run ends.
- Not implemented: owners bound to this host (`left`) do not jump the queue any more (the order is fixed at the start; they are inferred in lightest-first order like the rest).

Tests: `🙋️wanted/🧪️tests/📖️read` (20 pass, 3 runs): one `infer` call, lightest first, arrivals dropped mid-run (`dropped` never inferred), no project both inferred and taken, narrowing visible during the run, both counts en/de, a run still going when the wait ends is cut at once (`missing` = cut), failure and cancellation. `🕸️graph/🧪️tests/🏊️cooperative-farm` (3 pass): over a 300-name run exactly one prefetch / plan-stage entry / farm open, peak workers within `planFarmWorkersV1`, order and 50 mid-run arrivals skipped, one release also when the run fails, plus the structure of the hooks in `project-nodes`, prefetch, host and claims. Also pass: `plan-stages` 3, `fleet-read` 5, `prefetch-booking` 2 (marker adjusted to the new `prefetch` signature), `offer-fresh` 2, `offered-once` 4, claims 124, `too-heavy` 6, `inferred` 3, `away` 1, wanted root 9, server 15.
Not verified live: real throughput (expected to approach the non-cooperative ~40/min since setup, stages and farm are paid once); the service must reload.
