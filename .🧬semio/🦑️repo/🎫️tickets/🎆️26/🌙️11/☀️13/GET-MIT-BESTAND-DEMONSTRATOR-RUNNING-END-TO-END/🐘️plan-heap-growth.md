Read-only analysis. Log: `/private/var/folders/n2/f4tcy7ks04sb8njd18x7l1lh0000gn/T/semio-repo/501/host-e957b3fd40e8.log` (lines 1098-1995). Paths below are relative to `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/`.

## What the log actually says (corrects the premise)
- The 19.4M objects are NOT an accumulation over 4774 projects. At the stop only **9 of 4774** projects had finished ("Inferring projects: 9 of 4774 ... 1 running", log 1989). Every project waits in the memory governor ("waiting for memory headroom (1645 of 1108 MB reserved)", recorded peaks of 1645-2753 MB per owner), so exactly one owner runs at a time and the farm never engages (no `farm`/worker line in the log; `engage` needs `coldInference` or `wantedRoots`, `project-nodes/🟨️.mjs:291`).
- The heap sample ring in the plan stop detail shows the shape: heapUsed flat at 0.9-1.0 GB and external 0.65-0.76 GB from 667 s to 677 s (rss already 4.5 GB), then a burst 677 s -> 693 s: heapUsed 1.0 -> 3.0 GB and external 0.7 -> 2.3 GB, i.e. +2 GB heap and +1.6 GB external in about 15 s while 5-6 owners ran one after another (demonstrator, writer-js, mathematical-js, fixture-generator-equation-1-any, ...). The earlier "worker" sample in `graph-plan-too-heavy` (968 MB heap, 5.78M objects, 2.94M strings) is the same VM before the burst: strings x3.4, Objects x4.0, Arrays x2.3 in the burst, WeakRefs constant (138k = row-table views, not the problem).
- Heap + external growing together by this ratio is the signature of `JSON.parse` of large stored layers/entries: the text becomes an external string, the result becomes Objects/strings/Arrays.
- Context: `no usable generation (invalidated)` plus hundreds of `closure-missing ... re-derived` lines (log 157-...): the remote-cache generation restore removed the durable closure entries, so every closure entry of every owner is derived from scratch or reloaded from the closure store in this one process.

## Ranked retention suspects

### 1. Derived closure entries keep their parsed layers in memory, uncharged by the cache (largest, est. 1.5-3 GB heap+external in a cold run)
- `🕸️graph/📥️inference/🧭️script-inputs/🟨️.mjs:1216` (`derive`): the new entry is `{recipe,value,rows,layers,...}` and is put into `closureEntriesV1` WITH `layers` (arrays of row objects: every file stamp, analysis rows with `nestedObservations`, walk layers up to 11 MB JSON each, 5 314 layers / 25 big ones for one owner per `🕸️graph-slice-slowness.md` session 3).
- The cache charges `closureEntryBytesV1 = JSON.stringify([value,rows]).length + 8*layers.length` (`:1030`) with limit 96 MiB (`closureEntryCacheBytes`, `🧬️schema/🔣️.json:11`). A layer of 100k rows counts 8 bytes. So the "96 MiB" cache really pins whole layers; entries survive until 8192 entries or 96 "nominal" MiB.
- Declared but unused limits: `closureLayerCacheBytes` 384 MiB and `closureLayerRowBytes` 384 (`🧬️schema/🔣️.json:14-15`) are referenced nowhere in code (grep finds only the JSON): the layer charge was specified and never wired.
- `closureLayerViewsV1` (`:1034`) shows the intended design: stored entries keep only digests and stream layers per batch; derived entries are the only ones holding parsed arrays. Entries loaded from the store are also re-verified by reading every layer (`closureEntryHoldsAsyncV1` `:1184-1186`), each a full brotli + `JSON.parse` of the layer: transient peaks of 3x record size (compressed Buffer + decompressed Buffer + string + objects; `MAXIMUM_RECORD_BYTES` = 256 MiB, `💾️entries/🟨️.mjs:12`, `unpack` `:21`).
- Minimal fixes: (a) after `store.save` succeeded in `derive` (`:1216`) set `entry.layers = undefined` and keep `entry.digests = saved.digests` (the stored-entry path already works with digests, `closureLayerViewsV1:1038`), keeping the parsed arrays only when there is no store (`store === undefined`); (b) charge layers in `closureEntryBytesV1` using `closureLayerRowBytes * rows` (use the declared limit, or delete it) so the cache can evict; (c) `ensure`/`holds` for a `walk` layer should hash the compressed file (digest of file bytes) rather than unpack+parse when only existence/integrity is checked.

### 2. Shared script cache of the whole run: `scripts.reachState` and `walkNodes` (est. 0.3-1 GB, grows with distinct owners)
- `createScriptInputCache` (`:57`) is created once per `emojiProjectJsonNodes` call (`project-nodes/🟨️.mjs:200`) and shared by all owners. `reachStateV1` (`:599`) holds `graph`, `reverse`, `reaches`, `resources`, `sets`, `nodes` Maps keyed by module keys for every module any command walk touched, each node keeping `parts`/`shared`/`config.parts` (arrays of observation rows) and path strings. `releaseOwnerStateV1` (`:1227-1233`) clears `files, closures, commandDependencies, declared, paths, walkNodes` but NEVER `reachState`, and only every 32 owners (`OWNERS_PER_RELEASE_V1 = 32`, `:1223`; with 1 owner at a time under the memory gate, 32 owners = 32 x 2 GB peaks before the first release, and the `shrink` of `closureEntriesV1` is also only done then).
- Evidence this matters: the plan limit trips after 9 owners, never reaching the first release at owner 32.
- Minimal fixes: release every owner while the governor is under pressure (`governor.pressure()` is already passed as `shrink`, `project-nodes/🟨️.mjs:296`: make `releaseOwnerStateV1` release when `shrink` is true regardless of the counter, and also drop `reachState.reaches` (memo by key) then); clear `reachState` in the same release (rebuild cost is the walk, already accepted for `walkNodes`); intern path strings (`closurePathNameV1`, `:198`, already memoised per workspace in `paths`, which is cleared, but `reachState`/`graph` keys keep their own copies) via `graphStringInternerV1`.

### 3. Plan-wide observation capture and derived facts (est. 0.3-0.8 GB, bounded by repo size but pinned strongly)
- `captureObservedSourceInputsV1` (`👁️observation/🟨️.mjs:296-300`): the plan-wide `captured` Map receives every unique row of every owner through `inherit`/`retainObservationsV1` (`:168`, `:185-192`), keyed by `rowTableV1.id`. The row table (`🔢️row-table/🟨️.mjs`) is compact, but this Map holds the row OBJECT views strongly, so views never become collectable (that is why WeakRefs stay at 138k while Objects grow): each row is `{kind,path,fact}` plus `fact` object (`{size,mtimeMs,ctimeMs,ino,sha256}` flat, analysis with `nestedObservations` arrays) = about 3-4 Objects and 2-3 strings (path, sha256, kind), i.e. up to millions of Objects/strings for a repo with tens of thousands of files across 5 000 owners, 100s of bytes each.
- `derivedFacts` (`🧭️discovery/🟦️.ts:90`, filled `:94`) keeps one `{row, support}` per derived fact for the whole plan; `support` is appended to the row log (`rowLog.append`) but `fact.row` objects stay.
- `rows` per owner: persisted into `rowLog` (disk) and released (`releaseProjectInferenceRetentionV1`, `👁️observation/🟨️.mjs:430-434`; `forgetObservedInferenceRowsV1` `project-nodes/🟨️.mjs:296`): this part is correct and bounded, `originalInferencePublications`/`projectImages` (32 MiB limit, `🧠️memory/🧬️schema/🔣️.json:20`) are not leaking. The in-process caches are all byte-bounded (analysis 16 MiB, settled reads 32 MiB, file record images 16 MiB, row store 1M rows / 16M chars, `👁️observation/🧬️schema/🔣️.json:521-549`) but the bounds are small relative to the uncharged items in suspects 1 and 2.
- Minimal fixes: for the plan-wide capture store only the row ids (rowTable numbers) and materialise rows lazily when the owner result is assembled (`rows:[...captured.observations]`, `🧭️discovery/🟦️.ts:156`); or spill `captured` through the row log the same way owner rows are; keep `derivedFacts` support in the log (already) and the `row` as id.

## Why `mit-bestand-praesentation-projektetage` "needs" 2 GB
- It is the FIRST owner of the run (`0 rows`, "1 running" in log 1747-1777); `grew by 2091 MB` is measured as process growth during its owner scope (`graphParentMemoryGovernor`, one owner at a time), so the owner pays the process warm-up that nobody had paid yet: loading the implementation and the TypeScript compiler, creating the shared closure entries (native command inputs, every `script-provider` port x view, tool closures: `sharedClosureRecipesV1` `:1245`, derived on first touch because `primeSharedClosuresV1` only runs when there is no closure store, `project-nodes/🟨️.mjs:296`) and parsing/verifying their stored layers. These shared walks cover the `repo` command closure (`repo ./📜️script.ts dev|build|test`, its import closure is the whole build library), the same for every `repo ./📜️script.ts` owner, so the first project is charged with it and later ones just reuse them (which is why the next owners cost less than 2 GB each, but still 1.6-2.7 GB from recorded peaks).
- It declares no TypeScript program (`📋️project.json` has no `metadata.semio.closure.typescript`, no tsconfig), so it is not a `ts.createProgram` cost; its own inputs are `{workspaceRoot}/…/🌐️vite/🟦️.ts`, `🎞️slide/**/*.ts`, `🌐️public/**/*` and the two workspace deps (`@semio-tech/presentation`, `presentation-react`).
- Consequence: because the cost is the shared warm-up, the "too heavy" mark and the limit of 1756 MB per project are wrong for this owner: it is not heavy, it was first. Fix: prime shared closures once before the owner loop regardless of the store (a dedicated scope outside any owner, so the governor attributes it to the plan not to an owner) or order light owners first.

## Other observations
- RSS is 4.5 GB while the heap is 0.9 GB before the burst: 3+ GB of rss is not JS heap (allocator retention of decompression buffers, brotli, `Buffer.toString`, plus the slice/farm child processes counted in rss growth); JSC does not return pages, so `Bun.gc(true)` does not lower it (also noted in `🕸️graph-slice-slowness.md`).
- `releaseOwnerStateV1` period 32 was chosen for the warm-cache case (many cheap owners). Under the memory gate (1 owner at a time, 1.6-2.7 GB each) it defeats the purpose.

## Recommended order of fixes (minimal)
1. In `derive` drop `layers` after a successful save (`:1216`), charge layers (or wire `closureLayerCacheBytes`). Expect the largest drop in heap+external.
2. `releaseOwnerStateV1`: release at once when `shrink` (pressure) is true; clear `reachState`.
3. Prime shared closures outside the owner scope so the first owner is not blamed; then the 1756 MB limit stops flagging `projektetage`.
4. Plan-wide capture: keep row ids, not row objects (`🧭️discovery/🟦️.ts:92-156`).
5. Add a permanent diagnostic: on plan stop write `v8`-style heap snapshot is not available in Bun; use `bun:jsc` `heapStats()` plus `samplingProfilerStackTraces()` behind an environment variable in `plan-stage:60`, and extend `objectTypes` to 16 entries plus `protectedObjectTypeCounts`.
