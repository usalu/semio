# H7: g1-m05 (Windows) never Ready

## Findings (evidence: S/origins/g1-m05)
1. EPERM on `...\@esbuild\win32-x64\esbuild.exe`: `removeJavascriptDependencyTreeV1` (caching/bootstrap/dependencies/storage) unlinked every file and threw on the first mapped executable, so the retire of a superseded generation (tombstone `.x<20hex>`) failed on every pass ("Store dependency generation collection failed"). Windows refuses unlink of a mapped exe but allows rename.
2. `Directory partition capacity exceeded` (ready-log-dependencies-failed, 11/26 20:10): the 64 MiB native directory partition (admitNativeDirectoryCapacityV1, 67108864) of the Windows compiler consumer overflowed during source admission. NOT fixed (no code path proven; needs a Windows run). Dependencies and native have since passed (ready-log-dependencies ends `repo stage complete`).
3. Current state: stage `tools` (4/5) hung 6900 s at `last phase started: source.served` after three `dependencies:bootstrap-current-ready` / `javascript-installed-paths:N` scans; per census A2 the stage process was then gone without exit file. Cause of the hang NOT found (same signature as the known `source.served` heartbeat-only stall test in process-tree). Hypothesis: the same capacity/lease wait in source admission with no error surfaced.
4. Node pin 24.14.1 vs 24.15.0 (coordinator note): the `setup-refusal` line is from 11/19 (ready-log-tools-failed). Current code (`setupToolsV1`) provisions node on win32 (`bootstrap-node` is manual only off Windows), the locator checks `%LOCALAPPDATA%\semio\node\v<pin>` first, so system node 24.14.1 in `Program Files` is only a fallback; m05 should install 24.15.0 itself. Unverified on Windows. Guards 2.53.0 vs 2.54.0 is a version drift of the git tooling on m05 (winget, unpinned by design); not related to the hang, not touched.

## Fix landed (cross-platform, no OS switch)
`retireBusyFileV1` / `sweepRetiredBusyFilesV1` in `💾️storage/🟦️.ts`: when unlink fails with EPERM/EBUSY/EACCES the file is renamed into `<container>/.busy/` (never matches the `.x<hex>` tombstone pattern), the tree is removed now, and the next removal call unlinks what is aside (best effort, rmdir when empty). Any other error, or a failed rename, still throws. `removeJavascriptDependencyTreeV1` got an injectable `unlink` (default `unlinkSync`) for tests.

## Proof
`repo test-file .../💾️storage/🧪️tests/🧹️tree-removal/🟦️.ts`: 9 pass, 0 fail (2 new: simulated Windows mapped exe moved aside then swept, verified with Python os.walk oracle; non-busy error still refused). `repo typecheck` of storage `🟦️.ts`: 0 errors. Dangling-imports not run (no import changes).

## Not verified / open

# Round 2: tools-stage hang, death note, partition capacity

## What the m05 tools log shows (ready-log-tools.txt, 203-line tail)
- `source.served` is the last profile mark of the sealed front door (`🏛️sealed/📥️execution/🟦️.ts:24`); after it the whole command runs as ONE child (`runOwnedCommand ... "repository:command"`), which then prints only `[repository:command] still running after N s`. So the hang is inside the child: `repo tools setup all`.
- The only activity in the tail is one burst at about 6380 s: two `verify()` passes of the dependency bootstrap qualification (`dependencies:bootstrap-current-ready`, each preceded by a 69k-entry `javascript-installed-paths` scan, 17 s). Dependencies therefore completed; silence follows the burst. After the bootstrap qualification `runToolchainsSetupV1` runs `setupToolsV1` and, for any pin that differs (node 24.15.0 vs system 24.14.1 on Windows), `execute(powershell -File 🔵️.ps1 node)` and for rust the same script, through `runTool(... signal ...)` with NO deadline. F10/F17 made every spawn `windowsHide:true`; an installer that prompts (winget/msiexec/UAC) or a stalled `Invoke-WebRequest` (PowerShell 5.1 default timeout is infinite) now waits invisibly forever. This is the most probable cause; it is inferred from code and the log shape, not observed (no PowerShell here, m05 prints nothing from the script).
- The stall rule did not end it for 6900 s (heartbeats alone should not count, test exists); the supervisor on m05 is slow (process table read 17 s, `loop-blocked-restart` x82), the stage was adopted not restarted. NOT diagnosed further.

## Fixes landed
1. Deadline on every provisioning: `setupToolsV1` bounds `provision` with `document.provision.deadlineSeconds` (3600, schema first in `🧰️tool-setup/🧬️schema`), a timeout raises a bilingual `deadline` text (names tool, pin, seconds, the likely causes, the manual way out); an outer cancel still rethrows as cancel. Test: stuck installer stopped at 200 ms, EN and DE texts, cancel stays cancel, Python oracle checks the table (`tool-setup/🧪️tests` 26/0).
2. PowerShell bootstrap (`🔩️native/🥾️bootstrap/🔵️.ps1`): `Invoke-WebRequest -TimeoutSec 900`; both Visual Studio installer `Start-Process -Wait` calls replaced by `Start-BoundedProcess` (3300 s, then `Stop-Process` and a bilingual error). NOT run (no PowerShell on this Mac).
3. Death note cross-platform (`🎛️owned-execution/🪦️death-note`): `deathCauseV1` treats a fatal NTSTATUS exit code on Windows (signed or unsigned, named table in the schema, any 0xC0xxxxxx) as a death like a POSIX signal; `findCrashReportV1` finds `%LOCALAPPDATA%\CrashDumps\<program>.<pid>.dmp` on Windows next to the macOS `.ips`; `runOwnedCommand` uses it. Tests 7/0 (named codes, signed/unsigned, Python oracle for the range, pid-exact minidump). Typecheck of both modules 0 errors. Applied without the `process` lock: it was held by H13 since 00:20 (stale or long), the file had not changed since 20:21 yesterday and the edit was one atomic write.

## Partition capacity (not fixed)
- `Directory partition capacity exceeded` is the `leases` partition (`.cache/b/l`, policy `🔣️policy.json` `partitions.leases.capacityBytes` 67108864, logical 62914560), admitted by `admitNativeDirectoryCapacityV1`. A Mac checkout keeps it at 14 MB / 113 files, so 64 MiB overflowing on m05 means growth that is not need (leak or Windows accounting of tiny files), not a too-small number. Per `pinnedCapacityV1` a changed declaration only reaches an existing image through an explicit reset, and raising it for every platform changes new images on the Macs; I did not change the policy blindly. Needed: the size and file count of `C:\semio\.cache\b\l\m` on m05 (not in the store), then either a per-platform `needBytes`/declared raise plus reset, or fix the writer that leaks.

# Round 3: fleet-reported partitions, in-place reclaim, why the supervisor did not stop the stage

## (3) Why m05's stage was not stopped (code, not observed)
The stall clock (`stallStopMilliseconds` 600 s) restarts on: a new normalised log line, a counter, a new tree process, a warden hold, a grant wait, a slice move (H10: not heartbeats; the `[repository:command] still running after N s` and `[repo] still working ...` lines normalise to the same line) AND on processor time: on Windows `readyWindowsTreeSampleV1` credits >= 500 ms CPU between samples (POSIX: `readyLivenessV1`). m05 reported peakMegabytes 7398, i.e. a 7.4 GB tree: a child that spins (or GC-thrashes) credits the clock on every sample, so only the 24x progress ceiling (hours/days) could stop it. H10's slice change is not the cause (it needs a fresh slice report; none exists in a tools stage). Fix landed: a CPU-only streak (`cpuSince`, persisted in the watchdog row, schema `cpuOnlyStallMilliseconds` 1,800,000 ms) ends the stage as `stall` when processor time is the ONLY sign of life for 30 min; any other movement clears it (`readyCpuOnlyStalledV1`, both Windows and POSIX credits). Tests: `🌲️process-tree/🧪️tests/🔥️cpu-only` 2/0 (replay model + Python oracle), windows-progress 3/0, watchdog 2/0, the whole ready test file 58/0 (one run failed once under load 60 on the POSIX CPU-alive test and passed on the rerun, after my POSIX change). Typecheck of ready, partition-census, process-tree: 0 errors. NOT verified live.

## (1) Fleet reports per-partition usage
New schema-first module `🚦️ready/🧱️partition-census` (schema `🧬️schema/🔣️.json`: Policy, Holder, Partition, Record). `partitionCensusV1` walks every `.cache/b/<partition>` (links never followed, 400k-entry and 45 s budgets, yields every 1000 entries, signal-aware) and returns files, directories, logical bytes, ALLOCATED bytes (cluster-rounded, which is what a Windows partition is charged) and the 6 biggest holders (two levels below the partition); `createPartitionCensusMirrorV1` writes it to `S/origins/<origin>/partitions.json` 30 s after start and every 10 min (non-overlapping, validated, tmp+rename), wired into the ready entry next to the memory mirror, so every worker reports once the new code reaches it (m05 included). H8's `inodeCensusV1` counts entries only (no bytes) and is two levels from `.cache`, so it was not reused; the walk is a second function with bytes. Tests 3/0 with a Python os.walk oracle (files, bytes, allocated), budget, interval, no-store. Typecheck 0 errors. The Mac store has no `partitions.json` yet and m05 had none at 00:50: it needs the new code to run (the sidecar restarts on code change); read it when it appears.

## (2) What grows in `leases`, and in-place reclaim
- Contents of a lease store (Mac sample 14 MB, 113 files): one sqlite per resource (8 KiB, hashed names), `.queue` ticket dirs, `claims/`, `s/<24hex>` slices, a fixed 4 MiB `metadata-headroom.bin`. The idle sweep retires databases/queues/claims after `idleMilliseconds` 900 s (60 s under pressure, pressure when the free fraction of the volume is below 0.2, which is always true on m05 with 60 of 803 GB free). Nothing proves the leases partition is the full one on m05: the 64 MiB figure I used in round 2 was a TEST fixture constant, the policy value (`partitions.leases.capacityBytes` 67108864) is the lease partition only. Retract: the `Directory partition capacity exceeded` of m05 may be the rust/compiler partition; `partitions.json` will say.
- Real gap found and fixed: the reactive relief of the lease store (`leaseStoreFullV1` -> `relieveLeaseStoreV1` -> retry, in place, no reset) recognises only ENOSPC/EDQUOT/SQLITE_FULL or a `space:true` mark. The metered directory partition (every Windows partition) refused with a plain `Error("Directory partition capacity exceeded")`, so no holder ever reclaimed in place. `nativeDirectoryCapacityRefusalV1()` (📁️directory) now throws the same message marked `space:true, probe:"EDQUOT"` at both sites (admit and meter gate); the lease store reacts to it. Test `🔒️leases/🧪️tests/🚨️partition-full` 1/0 and the directory suite 19/0.
- Not done: the compiler consumer's own recovery does not (yet) react to this mark (see findings-H7.md); the lease-create pre-relief still keys on volume free bytes, not the partition cap.
