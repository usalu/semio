# H10 Result: stalled stages and version drift

## 1. Stall detector (what it measures)
Code: `.../sidecar/🚦️ready/🟦️.ts` (stage runner) with `🌲️process-tree/🟦️.ts`. A stage is stopped with SIGTERM ("stalled", not counted as failure) when `stallStopMilliseconds` (600 s, scaled by machine speed factor) pass without "movement": a new normalised log line, a growing `taken N of M` counter in the log, CPU >= 500 ms in the stage's OWN process tree, a new child, a warden hold or a grant wait. Elapsed-time spellings (`(2073 ms)`, `(N s)`) are normalised away.

## 2. Evidence (13 origins, ready-log-*-stalled.txt, ready-timings.json)
- 11 of 13 workspace stalls end on the same last lines: `Starting the repo graph service` / `Loading the project graph of 440cffa5563d` / `Planning the selected targets and what they need.` then SIGTERM after 606-690 s (m10: 20 runs in a row at ~610 s, many 1000-2200 s when the stall clock was reset by other moves).
- The planning work runs in the resident graph service's slice worker (a bun process OUTSIDE the stage tree, 80-170 MB stage vs 2.3 GB RSS worker). Its CPU is never credited, and its own progress (`taken 559 of 616`, ledger done/running, uptime 614 s, in `slice-memory.json` and the owned slice report) is not mirrored into the stage log tail, so the stage looks silent.
- m10 sample (`ready-log-workspace-sample.txt`): worker main thread busy 100% for 188 s, one hot native frame, heap 1.77 GB / 15.5M objects, `ownerFactsMemo` 1.38 GB on a machine with swap 8-9 GB: slow GC/memory-bound planning, not a deadlock. The tail of m04/m05/m08 `tools` stalls and m05 `dependencies` are similar (counters / steps repeating after normalisation; m08 tools shows `Checking declared package providers: N edges` climbing).
- m02/m08/m13: 67/162/90 `[capacity] waiting` lines (admission wait of 6 min+ behind `graph-plan` 4.5-4.9 GB) precede the same silent planning.
- Verdict: FALSE stalls (slow but progressing, memory-bound on 16 GB machines), plus a repeated-restart loop that throws away the progress of the planner each ~10 min ("no lost work on retry" is violated for the in-memory plan; sealed owner results do persist, hence the counters creep).
- The units ledger (`compiled 787`) in those rows is machine-wide counters, not stage evidence; not used.

## 3. Fix landed
- New pure `readySliceMovedSignatureV1(report, startedMs)` in `🌲️process-tree/🟦️.ts`: signature of the fresh owned slice report (phase name/done/total, owners ledger done/running/total, owners finished/taken); `null` for a report of an earlier attempt, a finished read or a malformed one. CPU/uptime excluded on purpose: a spinning loop that decides nothing is still a stall.
- `🟦️.ts` stage runner (mirror tick, next to the existing grant-wait/slice-silent check): a changed signature calls `moved()` (restarts the stall clock). The kill rules `sliceSilentMilliseconds` (900 s without a report write) and hard caps are unchanged, so true wedges (stopped loop, same counts for 10 min) still end as stalls with the real reason.
- Test: `🌲️process-tree/🧪️tests/🚶️slice-moved/🟦️.ts` (independent CPython model); `bun test ./🟦️.ts` passes (5 expects). Syntax of both edited files verified with `bun build --no-bundle`.

## Round 2: ready-suite "detached grandchild ... reaps by pid" (test fault, product reaping is sound)
- Cause (test, not product): the fake `repo` script was the SAME for both stage runs. The second run (tools, 2.5 s stall bound) therefore re-ran the whole script: it launched three NEW detached grandchildren and looped `echo; sleep 0.3` forever. The stage liveness rule (`readyLivenessV1`: a process that joins the tree counts as life) is correct by design for builds that start children; under load each `sleep` child was present at every sample, so the stall clock restarted forever: the second `runReadyStageV1` never stalled (hang to the 360 s test timeout) and its new orphans were never in the cleanup list ("killed 1 dangling process"). Before the load-scaling the first stage ended before the helpers registered ("pids undefined").
- Product check: reaping by pid+startMs (`reapRegistry`, orphan window `windows()`/`human()`) worked in every run where the stage reached its end; the reaped list equalled exactly `[orphan, agent]`. No product edit made (none needed; no landing slot used).
- Fix (test only, `🧪️tests/🟦️.ts`): the script now exits at once for `tools` (second run only reaps), and for the first stage waits on helper registration (`until the registry folder holds the entry`, 0.1 s polls, 300 s cap) instead of sleeping, then prints one line and `exec sleep 3600`, so the stall bound runs only from the last registration and a single idle child stalls deterministically.
- Proof: `nice -n 10 bun test ./🟦️.ts -t detached` at load 62: 2 pass / 0 fail, 15 expects, 36 s; the grandchild test alone 31 s; no leftover `grandchild.js`/`sleep 3600` processes afterwards.
- Unverified: rest of the ready suite not rerun this round.

## Round 3: stale-code waiting stage (`stage-code-stale-waiting`), landed 09:00 under `landing.lock.ready` (released)
- Why `stage-code-stale` never fired on m04: it needs a changed `semanticsSources` value (a result-format bump), never a changed supervisor code, and the capacity wait lines (`short by N MB`, `load 6.99`) change every look so they counted as log progress.
- Rule: a stage whose recorded code digest differs from the digest of the code now running (or has none and another supervisor adopted it, as m04's) and whose last line is a wait, with no new non-wait line, no counter, no processor time and no new process for `staleWaitingMilliseconds` = 900 000 ms (3x `codeQuietMilliseconds`, scaled by the speed factor) is stopped (`kill("restart")`) and starts again at once on current code. Not a failure, stall count not advanced, finished work stays stored. A stage making real progress or on current code is never touched.
- Code: `🌲️process-tree/🟦️.ts` `readyWaitLineV1`, `readyStaleWaitingV1`, scaled policy; schema `staleWaitingMilliseconds`, `waitPatterns` (EN/DE); ready `🟦️.ts` `readyModuleCodeV1()` (12-hex sha256 over module sources, tests excluded, once per process), `code` recorded in the in-flight record (schema `Inflight.code`), `input.code` seam, `workedAt` (moved by `movedByCpu` and non-wait new lines/counters), refusal `stage-code-stale-waiting` and reason `code-stale-waiting` in EN/DE, supervisor message in both languages.
