## Finding 2: per-file analysis is NOT where a cold single owner spends its time
Owner harness (`🔬️owner-harness/📜️cli.mjs`, owner `repo-graph-maintenance`, selected test, load ~50, `--cpu-prof`): cold 19-21 s CPU / 42-65 s wall; same process second infer 3.8 s wall; fresh process with a warm analysis store still 15 s CPU. Inclusive CPU of the cold run: TypeScript parse of analyses (`analyzeSourceV1`) 9.8 s, module closure graph (`machineClosureGraphV1` -> `loadClosureGraphSyncV1`, 44 MB brotli chunks: decompress, sha, JSON parse, schema check, intern; `chunkRecordsV1` 6.9 s) 9.8-14.7 s, closure walk `walkImportsV1` 10-18 s. With a warm store the closure-graph load (about 10 s CPU per fresh process) is the largest single item, and a cold process also saves the graph again (`saveClosureGraphV1` 16 s in the cold run). Next lever for the 300 s: make that load cheaper or lazy (skip per-chunk schema validation of an already digest-verified chunk, keep one decoded graph per resident worker, or load only the chunks the owner's roots reach). Not done; needs a service-side profile (`SEMIO_REPO_PROFILE=1`) after the window.
Side effect to know: the harness shares the machine closure graph directory (`.cache/f/closure-graph`, content-addressed, atomic) like any graph process; my cold runs refreshed it (normal behaviour, no foreign state).
