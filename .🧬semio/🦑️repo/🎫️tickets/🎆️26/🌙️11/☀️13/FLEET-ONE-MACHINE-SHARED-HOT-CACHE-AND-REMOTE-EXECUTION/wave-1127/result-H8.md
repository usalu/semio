## Round 2: attack the 428,796-inode need (evaluation; the census is the only landing, see `T/landings.md` "Wave 1127 H8")
m04 live at 00:20: 299,130 free, need 428,796, no census line yet in its tail (the worker has not run the new sweep or has not re-swept; the tail still shows the 11/25 failure).

Facts measured on this Mac (`.cache/b/d/m`): six generations in `j/` (root + `♻️mit-bestand ✏️s 🌎️hub 🎓️teaching 🏢️semio-tech`, lockfiles 17.7k-20.7k lines each = 3.2-3.5 entries/line each), plus the shared `bun-cache` with 146,008 entries that the need does not count. On Linux (backend `copyfile`) the cold peak is therefore about generations (~390-430k) + cache (up to ~146k), i.e. above 428k, not below.

- (a) Scope the install: the only lever that cuts the need by a factor. The stage `dependencies` runs `dependencies sync --all` (all six scopes). `--scope <owner>` exists, and the store type already has `{kind:"scopes",owners}` (`💾️storage/🟦️.ts:753`) but the command exposes only `--all` or one `--scope`. The `workspace` stage builds `@semio-tech/norm-din4108` (owner `✏️s`), `norm-din4108-rs` and `repo-mcp` (root): root + `✏️s` = 18,986 + 20,518 lines x 3.6 = about 142k inodes, plus a cache of about one scope (~70k), which fits m04's 299k. macOS workers do not scope (all six are installed; their stage is `--all`). Not landed because: (1) a scoped selection does not publish the global sync receipt (`💾️storage/🟦️.ts:1032`, only `kind==="all"` seals it), so later `repo run`s may call ensure and install the remaining scopes anyway (the ENOSPC would then move to the workspace stage); (2) changing `stage.arguments` changes `readyStageRecipeV1` (line 703) digest and re-runs the stage on every ready worker. Safe design for the follow-up: a worker-local reduced variant used only after the inode sweep proved the full set cannot fit (healthy workers never reach it, so no digest churn), with `--scopes .,✏️s` added to the command and the ensure path taught to treat "reduced worker" as complete; needs a live Linux check I cannot make.
- (b) Two generations at once: the need does not count two generations. The 428,796 is the sum of six distinct scopes (cold), not an old plus a new generation of one scope. Retiring superseded generations before installing is already done by the `dependency-generations` collector (inodeRank 1); a staged swap would only reduce the warm update peak (one scope, ~70k), which is not what blocks m04.
- (c) Backend: `hardlink`/`symlink` are kind `alias`, refused by the manager protocol: `🔌️managers/🧬️schema/🔣️.json:21` (`refusedBackendKinds: ["alias"]`), enforced in `🔌️managers/🟦️.ts:113` and `:125` (`"Supported non-aliasing install backend required"`); `🍞️bun/🔣️.json` maps hardlink and symlink to `alias`. The rule applies to the package store itself (the generations are immutable and fenced by physical membership with `stamp.dev`/`stamp.ino` in the source fence, `💾️storage/🧬️schema/📥️install.json`), not to repo sources; a hardlink to the shared bun-cache would also let a mutated cache file change a "sealed" generation. `clonefile` (reflink) is allowed but saves bytes, not inodes, and bun on Linux has no reflink backend in the recipe. So no backend change.
- Other holder found, not landed: the shared `bun-cache` (146k entries here) is not a registered writer, so no sweep frees it; a collector that clears it while the `bun:dependency-storage` resource is not held would free up to 146k inodes on a machine whose installs finished, and m04's gap is 129k. Not landed without the census confirming that m04 holds such a cache (its last failed install extracted only 2 packages, so likely it does not).
