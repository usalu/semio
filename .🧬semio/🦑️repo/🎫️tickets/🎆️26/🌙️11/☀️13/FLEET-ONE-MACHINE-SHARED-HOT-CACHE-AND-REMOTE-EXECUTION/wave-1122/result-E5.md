## 2. Zero-downtime cache handover
Design: the launcher (the supervised parent, which does not restart for code changes) owns the handover.
- The restarting cache child sends `{type:"successor"}` over the IPC channel instead of exiting. The launcher starts a successor child (`SEMIO_SIDECAR_SUCCESSOR=1`) with the new code while the old one keeps serving.
- The successor binds the same port with `SO_REUSEPORT` (new option `reusePort` of the runtime serve contract, Bun adapter and portable Node adapter), tolerates the held directory lock (successor mode), starts its scan in the background and reports `{type:"listening"}`.
- The launcher then sends SIGTERM to the old child, which stops accepting and drains its requests (round 2 graceful stop), exits 75; the successor becomes the supervised child; it takes the directory lock as soon as the old one releases it (polled every 500 ms).
- Fallbacks: a successor that does not report within 120 s or exits early, a port that cannot be shared (Windows: `reusePort` is ignored, the bind fails), or an old child that never gets an answer (self-abort after 150 s) all end in the old behaviour (stop, start again). Nothing hangs.
Measured on macOS (bun script): with two sockets on one port, all new connections go to the newest listener, the older one only drains.
Proof: `🖥️server` test `a successor on the same directory and port takes over while the first drains` (6 clients asking in a loop through the whole handover: 0 failures, more than 50 complete answers, the successor holds the lock afterwards); `🛰️sidecar/🧪️tests/🤝️handover` (the real launcher with a fake role: 4 clients, both generations answered, 0 failed requests, the successor stays supervised). Other suites: server 9/0, restart 3/0, remote-cache 21/0, sidecar 4/0, restart 23/0.
Not verified live: the running cache process was started before this code, so the next restart is still the 36 s path; the first real handover happens at the restart after that. Two processes briefly share the claim journal and the store directory (atomic writes, in-memory claim tables per process): a duplicate claim in that window only causes a duplicate compile.

## Design gap and fix
Before: `repo cargo` asked the host for a grant for the whole run. When the host said wait, the door waited; the only way out was `offloadFanOutJobsV1`, which asked a different question (would one unit queue, with an empty ledger) and, when yes, ran cargo with no grant and no local bound at all.
Now (one verdict, the door's):
- While the door waits, it asks `offloadFanOutJobsV1({doorRefused:true})`. That reads the live table of the scheduler (`fleetHeadroomV1`, one signed `/status` request with a 3 s limit): another machine of this platform, not draining, a free slot, its own admission says headroom, offers the current action format. Without a published scheduler, without such a machine or when the scheduler does not answer, nothing changes: the door keeps waiting.
- With headroom, cargo starts with no host grant but with `SEMIO_UNIT_CACHE_SLOTS=1` (one local compile at a time, the minimal local grant; the cargo launcher now honours that variable) and `SEMIO_OFFLOAD_PRESSURE=door`, restored afterwards. The wrapper takes that variable as the door's verdict (it skips its own, empty-ledger, probe) and offloads every eligible unit; units the fleet declines wait for the one local slot.
- The initial check (before waiting) still uses the unit probe, now also requiring fleet headroom.
Thresholds stay in E7's host decision (nothing changed there); see findings-E5.md.
