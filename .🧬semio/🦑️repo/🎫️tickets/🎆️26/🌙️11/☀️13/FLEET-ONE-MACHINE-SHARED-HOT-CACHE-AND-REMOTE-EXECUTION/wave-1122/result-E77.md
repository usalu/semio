# Result E77: generations and restarts (2026-11-22 16:05 to 16:45)

## 1. Dependency generations: why m01's image `d` is full, and the collector fix (LANDED)
### What "entries 4096" really is (E71's reading was wrong)
`Store dependency generation collection deferred {"entries":4096}` is NOT the generation count. `entries` is the number of filesystem entries one post-publication slice has removed (`slice.entries`), and 4096 is `concurrentProtocolV1.retention.postPublicationCleanupEntries` (with 2000 ms, `🚦️concurrent/🧬️schema`). `SelectedPlanProtocol.maximumGenerations` (4096) is a different, unrelated ceiling and never refused anything. m01's log (`ready-log-dependencies.txt`, 05:30) shows the counter `dependencies:collect:256 .. 3840` and then the deferral: the publishing command removed 4096 entries (a fraction of ONE generation: one generation is about 100k-600k entries, 1.5 GB) and stopped by design, leaving the tombstone `.x<key>`.
### Why the image fills (all from code + coordinator evidence, nothing was computed twice)
- A generation is content-addressed: key = hash of the scope's package.json, bun.lock, bunfig, patches (coordinator `j/<key>` holds exactly those files). Same inputs, same key, one generation. 6 scopes; the coordinator shows three re-key events (11-16, 11-21, 11-22 08:13) that each re-keyed all six scopes (a root manifest edit stales every scope, E58); each event is a real input change. So no "computed twice" bug here.
- Retention keeps what a pointer retires: `pointer.maximumRetired` 8 per scope, retained 6 h, the newest retired one of a scope 24 h (rollback), unless the image is under pressure (free < 25 %), then 0 s. Coordinator: 6 current + 12 retained = 18 generations = 27 GB; m01's 36 GiB image holds the same plus the 4 GiB package cache and the building set, i.e. it sits at 0.4 GiB free.
- The only collector that applied the pressure rule is the one run after a publication, and it is sliced (4096 entries / 2 s). After a stage's last publication nothing continued it: the workspace stage that follows does not publish, so m01 stayed full for hours. The collector of `repo cache gc` / hourly `--idle` (E58/E72) did not know retention at all: it treated every generation named in a pointer's retired list as referenced, so those 12 generations were never candidates there.
### Fix (members `📦️dependencies/♻️collection`, `🧹️cache-gc/⌨️command`)
- Paged, resumable, cancellable: `collectDependencyGenerationsV1` is async; a generation is retired by removing its ready marker, renaming to its tombstone `.x<key>` and unlinking in batches of 256 entries (progress callback per batch, `AbortSignal` checked per batch, optional `maximumMilliseconds` which returns `more:true` instead of failing). The remaining tree is the cursor: the next run finishes every tombstone first (`finished`). There is no entry ceiling and no wholesale deferral.
- Retention rule in the pure planner (Python oracle, 8 cases): never current/held/bound/pinned; retained generations rest `retainedGraceSeconds` (6 h) or the newest of a scope `rollbackSeconds` (24 h); under pressure (image free fraction < `pressureFreeFraction` 0.25, measured with `freeSpaceSyncV1`) every finished generation is due at once, unfinished ones still rest 6 h. The policy numbers are asserted equal to the concurrent storage protocol's retention.
- `repo cache gc` (whole, `--area=dependencies`, `--idle`) prints progress (`cache:dependencies-<phase>-<done>-<total>-<entries>`), counts, "image under pressure", and `--idle` is bounded by `idleCompactionMaximumMilliseconds`; pin leases stay claimed exclusively before any removal (E72).

## 2. `readyDecideV1` no longer waits for a deferred restart (LANDED)
Rule chosen: a deferred supervisor restart never holds a stage back. Reason: `createSidecarRestartV1` already waits while a stage is busy (a progressing stage is never stopped for new code; the restarted supervisor adopts the stage), so the wait only idled the worker (restart debounce: 5 min quiet, 30 min max, re-armed by each of about 40 landings a day; H9 saw m01/m07/m10/m12 in `sidecar-restarting` at 16:17).
