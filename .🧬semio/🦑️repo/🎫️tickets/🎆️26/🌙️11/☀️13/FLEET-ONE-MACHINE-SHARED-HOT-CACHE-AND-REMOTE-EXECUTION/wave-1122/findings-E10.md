## F1. Every authenticated PUT to the live fleet cache from this machine hangs (the likely root of "nx puts 0" and of Bazel never uploading)
Measured 2026-11-22 ~01:50 with a signed client (`remoteCacheFetchV1` with the fleet identity, signers cache-read and cache-write both present):
- `GET /main/ac/000...` answers 404 in 8-50 ms; unsigned `PUT` answers 401 in 51 ms; signed `PUT /main/cas/<wrong digest>` answers 400 in 28 ms (rejected before the store).
- Signed `PUT` of a valid blob (23 bytes AND zero bytes), of an Nx key `/main/v1/cache/<key>`, on instance `main` and on a fresh instance: no answer, not within 10 s and not within 80 s. The request is sent plain (trusted-lan, not sealed).
- Consequence: the Nx flight PUT (502 after its upstream timeout) and Bazel uploads through the signing proxy never land; ac puts stayed at 4525 across a real Bazel build through the proxy against the live server.
- Hypothesis (not proven): the request reaches `RemoteCacheStoreV1.store` -> host CAS `putChecked` -> `guard.admit` (`B/🗄️cas/🚦️guard/🟦️.ts`). This Mac's data volume is 97 % used (35 GiB free of 926 GiB), the CAS holds 37 GB; at/over the partition critical watermark `admit` runs a collection and awaits it (`await run(quote,signal).task`), and every PUT waits behind it. Other machines' puts (19887 cas puts since start) may succeed because their own CAS partitions are not critical. The write budget (10 s `writeSignal`) does not cut the wait, because the PUT answers nothing at all instead of 507.
- Owner: E4 (server) / storage lane (CAS guard). Needed: admission must never block a PUT longer than its write budget (answer 507 `capacity` with retry-after), and the server host should not sit at 97 %. Repro script (no secrets printed): scratch `put4.ts` in the E10 scratch folder; it needs only `SEMIO_WORKSPACE_ROOT`.
