# Result E18: learned estimates, bounded admission, lazy graph import

Landing record: `../landings.md` ("Wave 1122 E18", file list with sha256 prefixes and test counts). `HC` = `🧰️framework/🔨️modules/🏃️process/🏗️build/🌡️host-capacity`, `B` = build library, `BP` = `B/🌡️host-capacity`.

## 1. How estimates are learned, and what inflated them
Store: `<host-capacity dir>/estimates.json` per machine (`~/Library/Caches/semio/host-capacity` on macOS), classes keyed `operation` < `operation:kind` < `operation:project:target`, 16 samples each, each sample a peak as basis points of the default size. `HC/📐️estimates` turns a class into a ratio (decayed 0.9 quantile + 25 % margin, 30 to 200 % of the default); `command` has a fixed default of 2048 MB, so 200 % is exactly the 4096 MB that m12 asked for.
Confirmed causes (code reading plus live `ready.json`, whose stage `peakMegabytes` is 6163):
- `learnableHostRunV1` let a **failed or cancelled run teach whenever its partial peak exceeded the estimate** ("can only raise"). The tools stage failed repeatedly (roster error, exit 1) with a tree peak of 6163 MB = 300 % of 2048; every such run was recorded and pushed the class to the 200 % cap. Same rule in the test-worker learner.
- The learn-time clamp was the whole capacity above the floor (14336 MB on 16 GB), not the share a class may ask for (50 %) and not the declared class ceiling.
- A run under memory pressure was learned like any other (a tree reading of a thrashing host counts shared and compressed pages many times).
- `command` had no declared minimum, so a 4096 MB request was not shrinkable and could only wait for a holder (`--language`, 3 to 4 GB for 50+ minutes).

## 2. What changed
- `learnableHostRunV1(status,{limited,pressured})`: only a completed run on a host without memory pressure teaches; the one failed run that still teaches is a job the gate itself stopped at its memory limit (`limited`, set by `learnedRunAfterOutcomeV1`, peak already grown by the breach growth). Failed, cancelled and system-killed runs teach nothing.
- `hostLearnCeilingV1`: every learned peak is clamped to `maximumShareBasisPoints` of the room above the floor and to the class ceiling when the class declares one (the product passes it as `ceilingMegabytes`). Quantile stays the robust decayed 0.9 quantile with the existing outlier rule.
- Pressure: the gate notes a `pressured` run when the shared `sample.json` (age under two heartbeats, no extra probing) shows pressure above normal or a swap stop (`hostUnderPressureV1`); the product does not learn such a run.
- Admission always progresses: `command` declares `minimumMegabytes` 1024 (`B/🔣️policy.json`), so the existing shrink rule admits it with the room the host has (reason `shrunk`) as soon as the room covers 1024 MB. New `wait.starvedMilliseconds` 1800000: past it a request that no shrink can serve (room under its least need, or a hard stop that does not admit the minimum) is refused with reason `starved` and a named bilingual error, `memoryWaitedOut` when other grants hold memory (names the holders), `memoryStarved` when nothing of ours runs. Stage fails and retries instead of waiting. Schema (`Wait.starvedMilliseconds`, `Errors.memoryWaitedOut`, en/de), `hostStarvedMillisecondsV1`, decision and gate edited.
- Lazy graph: `BP/🟦️.ts` imported `🕸️graph/🕰️generations/🔌️load/🟨️.mjs` statically. `sealedCurrentReadV1` is now async and imports it only for a `show`. Module closure of the product host-capacity module measured with a load-recording Bun plugin: 391 modules before, 52 after, 0 graph or inputs modules.
- Build guide en/de updated. No store migration: stale poisoned stores heal by the half-life (3 days) and are bypassed anyway because a `command` request is shrinkable now (see not verified).

# Round 3: the 11,176 MB ask of a one-target dry run
Reproduced offline with the live store of this host and the real ask (`repo run repo:test-cache-reset --dry-run --exclude-dependencies` -> operation `run`, lineage `run:dry`, `run:repo:test-cache-reset:dry`): reservation floor 11176 MB, ratio 71 %.
Cause: not a class ceiling and not the execution estimate (execution 2.5 GB; the dry class measured 1.6 to 1.8 GB peaks). The floor is `min(declared class ceiling, max(learned assembly, learned plan))` (`estimateHostPhasesV1`); the dry lineage had no declared ceiling, so the learned global `phase:plan` class decided: its 16 samples include peaks up to 14 GB (ratios 125k to 139k basis points of the 1024 MB reference, runs of 20 to 55 minutes under load: thrashing tree readings), 0.9 quantile with margin = 11176 MB. The plan phase only reads a served graph.
Fix (landed under the host-capacity lock): (1) `estimates.maximumPhaseMegabytes` 4096 (schema, type, policy; only the assembly and plan phases, optional field): a learned phase size never exceeds it; (2) class ceiling `dry-run` (pattern `:dry$`, 2304 MB, the minimum of the graph readers; measured peaks 1.8 GB + margin) so every dry run and single-target planning class is declared small and learned sizes stay under it (the round-1 learn ceiling still applies to what is stored).
Proof: `🧯️progress` gained a test with Python oracle vectors (plan peaks 100, 400, 1094, 14243 MB give 512, 512, 1368, 4096 MB; class ceilings of 6 class keys); oracle `--check` equal; all suites of round 2 rerun, 0 fail (estimates 15, phases 14, scaling 4, gate 33, product main 17, shrink 6, cargo-scaling 10, job-limits 16, others as listed in landings).
Live: the same offline estimate now gives floor 2304 MB. A real `repo run repo:test-cache-reset --dry-run --exclude-dependencies` on this coordinator (load about 32) printed `[capacity] run: sized at 64% of the default from 1 earlier run(s) of its class` and `[capacity] admitted run: 1 job(s), 2304 MB reserved (9639 MB available, 4096 MB floor)` with no waiting line (E22: 11,176 MB asked, 31 to 450 s wait). I stopped that run after the admission (own pid only); the rest of the dry run (graph slice, dependency generation) is not part of this lane.
