## Why the automatic CAS collection never ran (root causes, all fixed)
1. `guard.admit` passed the writer's AbortSignal (cache write budget 10 s) into the collection; a scan of a 40 GB store takes minutes, so every timed-out PUT aborted the scan (partial, nothing freed) and then answered 507. Now the collection is detached; the writer only stops waiting (`within`). Test: write that times out does not cancel the collection.
2. `casEnforceTickV1` had no caller. The server now runs its own interval every `enforceTickMilliseconds` (30 s, CAS policy) for the host store.
3. The usage hint of a collection misses what other processes wrote meanwhile (measured: hint 2048 B, disk 4096 B, cap 3000 B -> guard said "fits" forever; at 38 GB/h this is the real drift). The tick now calls `guard.remeasure()` first.
4. The cap was a fixed 32 GiB. Now `casEffectiveCapBytesV1` = min(declared cap, `capHostSharePercent` 3 % of the partition, store + free above `machineHostFloorV1` (D1's one shared floor definition)), never below `minimumCapBytes` 1 GiB, aligned to the machine step; recomputed on every decision. 926 GiB / 33 GiB free / 36 GiB store -> well below 32 GiB. Python oracle over 120 combinations.
5. Over-cap writes no longer wait: on a measured partition `cap-exceeded` is `collect-background` (unmeasured stays `collect-now`); the critical share remains the hard refusal. Fixture case + oracle updated.
6. Fleet-cache namespace: `pinLive` pins newest slotted entries until 80 % of the effective cap, older ones stay evictable (before: every current/retained blob pinned, so the host collector could never go below the pinned set; 16 GB of 27 GB written in the last hour was pinned).
   NOT tested on its own (no dedicated test; remote-cache suites pass); the entry then misses instead of the partition becoming critical.

## Compaction on idle (coordinator decision: no downtime window)
- New `B/🧹️cache-gc/🛌️idle` : `compactOnIdleV1` + `planIdleCompactionV1`. For every due image with its minimum interval elapsed (1 h, stamps in the temp folder) it takes the exclusive lease with ONE non-waiting try (so it only runs when no other holder exists = the caller was the last holder) and runs the existing bounded cycle (detach, UNMAP attach, settle); pass bound 10 min; only a completed cycle stamps; busy images are retried at the next trigger. An opener that arrives meanwhile waits on the existing lease and never fails.
- Triggers today: `repo cache gc` (all images, no interval) and `repo cache gc --idle` (interval 1 h, compaction only; cheap when nothing is due). NOT wired into the exit of every `repo` command: images d and t are held by the CLI process itself, and a compaction of up to minutes at command exit would delay MCP/agent commands; decision needed on running `repo cache gc --idle` from the reclaim tick of the scheduler/cache server (the cache server tick would be the natural host; it holds no image lease).
- Tests (4/0): plan vs Python model; stamp/busy/not-due/too-soon/failed rules with scripted ports; pass bound; REAL throwaway 400 MB APFS UDRW image with two shared holders: busy while both hold, still busy after one releases, `compacted` after the last release, a third opener arriving mid-cycle waits and then holds (after the exclusive release), backing file shrank by > 50 MB. No image left attached.
- Due rule (landed earlier): on a tight host (free < reclaimTightHostFreeBytes) the 300 % ratio no longer applies, floor/8 stays (d 17G/7.2G and g 14G/7.3G were never due before). Tests: reclaim 26/0, image-slack reclaim 13/0; budget 16 pass / 3 fail (same 3 pre-existing, need the repo runner).

# Round 2: compaction on idle runs from the supervised sidecar of every machine
- Decision (coordinator): not on a command's critical path; from the long-lived sidecar maintenance loop on every worker, at background priority; the cache server's sidecar does it on the coordinator.
- `B/🧹️cache-gc/🛌️idle/⏲️loop/🟦️.ts`: `startIdleCompactionLoopV1` (first pass after `idleCompactionFirstDelayMilliseconds` = 10 min so a starting worker is not loaded, then one pass 1 h (`idleCompactionIntervalMilliseconds`) after the previous one ended; never overlapping; a failing pass only reports; stop/signal cancels timer and running pass), `runIdleCompactionChildV1` (spawns `repo cache gc --idle` of the workspace as a child with `SEMIO_CACHE_BACKGROUND=1`, `setPriority 19`, killed by the signal; the reclaim cycle cleans up on SIGTERM), `startSidecarIdleCompactionV1` (roles `agent` and `cache` only; ready/pool/scheduler/graph start nothing).
- Wiring: `B/🌐️remote-execution/🛰️sidecar/🟦️.ts` child main starts it right before `runRemoteExecutionSidecarV1` with the sidecar's abort signal, so a drain/stop/restart of the sidecar cancels the pass (an image mid-cycle is returned attached, per E14's cleanup). Every worker runs an agent sidecar, the coordinator also the cache sidecar: both get the loop; two sidecars on one machine are safe because each pass takes the exclusive lease with one non-waiting try and the 1 h stamp is per machine (temp folder), so the second one ends `too-soon`/`busy`.
- Tests (fake clock, 4/0): first-pass delay and interval, no overlap while a pass runs, failure reported and loop continues, stop cancels the running pass and the timer, aborted signal never schedules; role wiring: agent and cache run at exactly the declared delay/interval with the sidecar's root and environment, other roles run nothing. Sidecar suite 5/0.
- NOT verified: a real sidecar restart on a worker (code reaches workers through the replica; their supervisors restart them); first real pass on a worker not observed; Windows/Linux sidecars start the loop too but their partitions are directories, so each pass answers `not-due` at once (cost: one child process per hour).
- Note: on a machine whose images are always held (long-lived resident readers), a pass answers `busy` every hour and compaction waits for a gap; the stamp is only written after a completed cycle, so the next pass retries.
