# E20 result: closure-first discovery for selected reads

## Verdict
No code change landed (no lock taken, nothing in `T/landings.md`). Reading the code and the live logs shows that the premise "the selected read's first stage inventories the whole tree and admits all ~3,600 owners before cutting the closure" is NOT true of the current code. The cause of the 80-minute, restarting reads is elsewhere (below). I added a test folder that pins the closure-only behaviour so a regression would be caught.

## What the code does today (verified)
- `B/🕸️graph/📥️load/🟦️.ts` `inventory()` for a selected scope calls `closeBuildOwnerAdmissionV1` (`B/🕸️graph/🚪️admission/🟦️.ts:155`). It is a frontier walk: it admits only the selected task owners, then the owners reached by declared `dependencies`, file-to-owner resolution of the files an owner observed, task `dependsOn` edges, `dependencyInputs` and catalog providers. `selection.kind==="all"` is the only branch that admits every registry owner. With `excludeDependencies` it admits the target owner only.
- Each admitted owner is observed by `discoverBuildOwnerAdmissionFactsV1` (`🔎️owner-discovery/🟨️.mjs:282`), which reads its manifest, command-source closure, native closure and the input globs of the selected targets only. There is no tree walk (`workspaceBuildFilesV1`, `walkCargoToml`) in this path: `files` come from `admission.files`.
- Churn is already per owner: `observeOwnerFactsMemoizedV1` answers from the memo while every row holds; `evictOwnerFactsReferencingV1` forgets only owners whose rows name the changed path or its parent listing; `buildGraphMembershipV1` only covers the admitted files and directories, so a member vanishing outside the closure cannot throw `BUILD_MEMBERSHIP_CHANGED`. An older sweep oracle for the frontier exists (`🚪️admission/🧪️tests/📋️frontier`, Python).
- The "20k to 220k distinct source observations" in the progress line is not the closure's size. `describeSliceReadStepV1` takes it from `readSliceReportSourceV1("caches").interned`, the process-wide interned row count, and the "x of 600" is the elapsed seconds against the 600 s bound of the `inventory` step (so "1263 of 600" means the step is 663 s over its declared bound). The first 20k to 45k rows are present before the first owner finishes (loading the build implementation's own sources), not a tree walk.

## What actually makes the layout read stall (for E1/E2/E8, not changed here)
1. Product closures are legitimately hundreds to over a thousand owners (catalog providers, `^build` through every wasm/Rust crate); closure-first cannot shrink them, only per-owner cost and restart cost can.
2. Counters drop from 396 to 11 and the observation count from 219k to 143k: that is a new slice worker process (empty caches), not a round of the same process (rounds keep the process-wide interned count). Candidates, not proven: exit 75 stale-implementation restarts after peer landings (seen in that log: four `exit code 75 ... Cannot find module .../🧾️ledger/🎚️machine/🟦️.ts` lines caused by a half landing), the worker exceeding its memory reservation (2364 MB requested, 2107 MB granted) and being recycled, and the lock `repository-graph-optional-ledger` waits of 2 to 6 minutes (E17's ledger fix is in the tree after 03:00; the 03:25 restart should show it).
3. After any restart a worker re-verifies every stored row of every owner it takes from the checkpoint/memo (`hold`), O(rows of the whole closure): 150k rows is minutes under load. Lever: verify rows lazily per owner at use, batch the `stat` calls per directory, or keep one verified-at stamp per directory listing for the length of a round.
4. The `inventory` step bound is 600 s (`🧠️memory/📋️slice-report/🧬️schema/🔣️.json`); a legitimate large closure exceeds it by design (1263 s seen), so on a worker the readiness watchdog classes it `step-overdue` and restarts the stage. The bound should scale with the owners left (or be replaced by progress-based liveness: owner checks moving).

# Round 2

## (1) Lazy memo verification (landed, `🕸️graph/📥️load/🟦️.ts`)
The up-front check was the whole admission memo (`buildGraphSourceFactsHoldV1(lent.observations)`, every row, phase `memo-check`) before any owner was asked; when one row was stale the work was thrown away and every owner re-verified its rows again. Now the memo only seeds the per-owner facts (`memo-seed`); `observeOwnerFactsMemoizedV1` verifies each owner's rows (shared verdicts of the round) when the owner is first asked for, so a row is still verified before its owner's record is used. When every owner was a memo hit the memo file is not rewritten (`unchanged`). The `memo-check` phase is gone from the inventory sequence. Tests: `📁️inventory` vectors updated (hit = memo-read, scoped-discovery, membership-hash, no memo-publish) 10/0.

## (2) Progress-based inventory liveness and honest counters (landed, `🧠️memory/📋️slice-report/🟨️.mjs`)
- The progress line `N of M` of the `inventory` step now carries `N` = seconds since the step last made progress (new observation of this read, completed owner check, verified memo row, phase change) and `M` = the stall bound (600 s). The sidecar's step watch (`readyStepWatchV1`) treats `seconds<=bound` as alive, so a read that keeps completing owners can no longer be marked `step-overdue` by elapsed time; a read quiet for more than the bound plus the stall window still is. No sidecar code change was needed.
- "distinct source observations" is the interned-row growth since the inventory step started (this read), not the process-wide count that included the implementation's own sources loaded earlier.
- Test: `🧠️memory/📋️slice-report/🧪️tests/🧭️inventory-progress` (quiet time resets on each kind of progress, grows without it, counts from the step start). Removed the superseded `inventory owner checks move both watchdog languages...` test and its fixture `📈️owner-checks.json`. Open: `🪜️read-steps` case "inventory reports new source observations while a repeated sample keeps the same progress" fails; the step line text was changed by a peer (the counter note was removed from `text`, `step:true` added to the emitted event) while the fixture still expects the old line; not mine, not fixed.

## (3) Restart cause of the layout session (from logs)
- `activate-2.txt` (pre-03:00 code): resets 396 to 11, 199 to 15, 1162 to 15 each coincide with a new slice worker process (observation count falls too) and with `repository-graph-optional-ledger` lock waits of 2 to 6 minutes held by a silent holder, plus four `slice worker ended with exit code 75 ... Cannot find module .../🧾️ledger/🎚️machine/🟦️.ts` lines (a half landing of a peer).
- `activate-3.txt` (post-03:00 code, restarted 03:25): owner checks rise monotonically 30, 37, 44, 60, 87, 111, 155, 199, 514, 565, 786, 830 over 1351 s, no drop, no ledger wait line (0), no exit 75. So the restarts seen before came from (a) the ledger convoy (fixed by E17, bounded busy loop) and (b) exit 75 on peer landings (debounce by E8 plus the stable tree). Nothing else in the graph lane restarts the worker; the jump 199 to 514 is memo hits answered quickly after the first cold owners.
- Remaining cost is the cold first pass: roughly 1 owner check per 1.6 s over the first 1300 s at load 40 to 70 (large owner roots, TypeScript import closures), which closure-first cannot remove. Still true: the 600 s `inventory` bound is displayed as the stall bound now.
