# Round 2

## (1) Why m05's receipts stopped, and the fix
The message comes from `StoreStalledV1` in `🤝️shared-worktree/🛡️resilience/🟦️.ts` (`createStoreGuardV1`). Root cause in the guard, found by reading: when a store call exceeds its deadline the guard abandons it, but `calling` (for `call`) and `turning` (for `turn`) were only cleared when the abandoned call RETURNED. A call that never returns (a hung SMB/NFS or locked-file syscall; a blocked fs call cannot be cancelled) therefore kept every later `call` throwing "Store call refused: an earlier store call did not return within its deadline" and every later `turn` answering `busy`, for ever. A probe that never answered had the same effect (`probing` stayed set, so no new probe, so the state never left `stalled`). Whether the first hang on m05 was SMB/NFS, a lock or a path length is not visible in the receipts (the first hung call is not logged); the guard is now robust to all of them.
Fix (`🛡️resilience/🟦️.ts`): flags are released at abandonment; a probe unanswered after 3 deadlines is orphaned and a new one started; the guard recovers once a probe answers (existing rule: 5 deadlines after the last abandonment); at most 4 leaked (never-returned) calls/probes are tolerated (they hold pool threads), beyond that it stays stalled. Tests `🧪️tests/💓️beat.ts`: never-returning `call`, never-returning `turn`, never-answering probe, cap of 4 (6 pass there, 26 in `🧪️tests/🟦️.ts`, replica suites unchanged).
Live: m05's receipts resumed at about 00:20Z (a watchdog restart of the daemon, not this fix; this fix has not reached m05).

## (3) Rollout order and m05
The gate is `🚦️canary/🟦️.ts` (`decideCanaryV1`): when no origin runs a digest, candidates go one after another (server first, then ids bytewise): first after 2 min, each further one 5 min later; followers go once a canary stayed healthy 1 min. So the worst wait of a machine at rank k is 2+5k minutes on a STABLE digest; it is not held by one slow machine (a leader that never attests simply drops out of the candidate list after 60 s). What actually holds the fleet now:
- Code churn: 12 lanes edit the module, every edit is a new digest, which restarts the 2 min wait; on top, the follower pending digests read "ran before and was superseded (revert)" (`suspectCodeV1`) because intermediate trees repeat digests that a machine already ran. Observed 00:10Z: the server runs eb0bfdb8, followers 3ee44a3a, m06 1a63001c, m05 e092f50c: the fleet runs five different daemon codes. Recommendation (not changed, design decision): freeze edits to `🤝️shared-worktree` for 10 minutes so one digest can pass wait + canary.
- m05 specifically: its pending digest 51b8ab4d was REFUSED by m05 itself at 00:11Z ("the worktree code does not start: the watchdog of the daemon fell silent", `S/origins/g1-m05/refused.json`), so it fell back to the snapshot e092f50c (old code, still without the rename fix and without the guard fix). The silent watchdog is most likely load (the install uses 7 GB, incoming queue 7,000-8,400 entries, applyMs p50 80 s) and not the code, but this could not be proven; the refusal then keeps that digest out for good, and the blocked rename backlog (the very EPERM) keeps the apply queue busy, so a new digest may never arrive in time. Chicken and egg.
