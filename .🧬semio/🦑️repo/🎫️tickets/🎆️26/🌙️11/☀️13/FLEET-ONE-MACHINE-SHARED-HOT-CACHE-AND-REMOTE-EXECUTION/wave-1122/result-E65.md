## 2. Cause: a worker counted its running remote actions twice (fixed)
`admitRemoteExecutionActionV1` (`🌐️remote-execution/🌡️load/🟦️.ts`) measured the unmanaged memory (used minus the grants) against the LOCAL grants only and then added one 2048 MB reservation per running remote action. What those actions really hold is already inside the sample, so it was counted as unmanaged and again as reservation. On a 16 GB machine: floor 2048, free 5789 MB, one running remote action: budget 14336 - 10595 - 2048 = 1693 MB < 2048 -> `no-headroom (memory)` although 3.7 GB were free (this is m13 at 15:27; m10 same with 6250 MB free). Every extra running action cost another 2 GB of phantom load, so a 16 GB worker stopped lending after one or two actions.
Fix: the remote pseudo-grants join the ledger before `withUnmanagedHostV1` (the documented rule "a grant counted by what it holds, unobserved by its reservation, nothing counted twice"). Local-first stays: local waiters (`queue-order`), pressure, swap, floor, disk and slot rules are untouched; a machine whose room is really used up still refuses.
Test (new, `🧪️tests/🔎️why/🟦️.ts`): 16 GB, 6000 MB free: 0, 1 and 2 running actions admit; 3000 MB free with 1 running refuses `memory`; full slots refuse `slots`. Arithmetic of the old code for the same view: 1904 MB < 2048 (refuse), so the test fails on the old code. Tests: why 11/0, fleet 9/0, disk 6/0, refusal-reason 3/0, remote-execution main 17/0. Landing in `T/landings.md` "Wave 1122 E65".
Live after the landing (15:41): g1-m10 (7294 MB free, 3 local grants) and g1-m13 (8081 MB free) report `headroom true, idle`; idle count for a requester went 0 -> 2 candidates (3 with headroom). Caveat: free memory also rose on both machines in the same minutes, so the live flip is consistent with the fix but not proof by itself; the unit test is the proof.

## 4. What others must know
- Offload works end to end on this fleet; the saturation seen now is real (all machines read graph slices, four are out of disk, three are in memory pressure), not an admission or placement defect, except the double count fixed above.
- 4 workers refuse for disk (m01, m08, m11, m12 with 0.4-1.7 GiB free; worker reserve 3 GiB + 0.5 GiB per action, policy `remoteExecution.worker.disk`). The reserve is right; the machines need space (E52/E64 domain). m08 has 8.4 GB RAM free and idle load: only disk stops it.
- A direct `wrapRustcV1` call needs `fleetRemoteEnvironmentV1(...)` in its environment, otherwise the fleet tier is silently off (no event, no skip reason): this cost one wasted probe. `fleetUnidentifiedReasonV1` returns nothing for "no endpoint in the environment".
- Probe crates and scripts stay in `T/🧰️scripts/E65`; scratch caches in `/private/tmp/.../scratchpad/E65` (unitA-E, out*).
