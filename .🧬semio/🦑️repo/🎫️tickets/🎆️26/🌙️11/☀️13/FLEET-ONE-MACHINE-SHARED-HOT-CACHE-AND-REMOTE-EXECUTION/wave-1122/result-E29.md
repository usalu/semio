# Result E29 (owner-isolation), 06:25

## Verdict
(1) The incident was a stale module import in the long-lived service, not a mixed read. Fixed: the route tables are no longer a process-lifetime JSON import and are observed inputs of the owner that reads them.
(2) One owner's inference failure no longer decides the read by itself: it is observed again while its rows moved, and only a failure that reproduces on a stable snapshot becomes a named bilingual failure of that owner. The closure walk keeps every other owner's record and can leave out an owner the selection does not need. All in the tree, tested; not exercised against a live resident service (see NOT verified).

## 1. Root cause
- `projectWithDefaults` (B/🕸️graph/📥️inference/🧱️project-assembly) calls `requireCanonicalTestAggregateV1(json, root)` for the caching owner. It derived the routes from `canonicalTestRoutesV1()` whose default arguments are `readCachingTestTableV1()` / `readBuildTestTableV1()`; those read the suites JSON through `import table from "./🔣️.json" with {type:"json"}`.
- The resident service loads the graph implementation per revision (`createRevisionLoader`), but the roster only covers the inference components. `⚡️caching/🗂️suites/🧮️aggregate/🟦️.ts`, the two `🗂️suites/🟦️.ts` and their JSON are imported statically below it: Bun keeps them for the life of the process, and they are not in `implementationFiles()` either, so no edit of the tables ever moves the revision. The project JSON, in contrast, is read through the observed filesystem on every owner observation.
- Evidence: on disk both files agreed at 06:03 (and at 06:00:49 the project already carried `test-build-test-file`). The error `route-undeclared:test-build-test-file` means "the target exists, the route table lacks `build-test-file`": exactly the table as imported before 05:42 against the project file read after 05:49. A mixed read cannot produce it at 06:00: nothing the read observed was inconsistent then, and the settle loop of the inventory repeats an identical failure only twice before it throws (`signature===previousFailure`), which is what killed the 45-minute read. A stale import reproduces identically in every round, so the existing repair rounds could never have helped.
- Not proven from the log itself (ref 9f6fd3bf was not retrievable from here); the conclusion rests on the code path, the timestamps in your report and the test below that fails with a once-imported table and passes with the new reader.

## 2. What changed
- `⚡️caching/🗂️suites/🧮️aggregate/🟦️.ts`: new `CanonicalTestReadV1`, `readCanonicalTestRoutesV1(read)`; `canonicalTestRoutesV1()` defaults and `deriveCanonicalTestAggregateV1(project, read)` / `requireCanonicalTestAggregateV1(project, root, read)` read the tables from disk at every call (workspace root derived from the policy path), never from the imported module.
- `project-assembly/🟨️.mjs`: passes `observedFs.readFileSync(join(workspaceRoot, path))`, so both tables are rows of the owner that consumed them (edit of either table re-observes that owner; a pair edited mid-read makes the owner's rows stale). `derived-config/🟦️.ts` and `🕰️host/🟦️.ts` preflight pass their workspace reader.
- New member `B/🕸️graph/📥️load/🛟️owner-isolation/` (schema first: policy, EN/DE texts, Failure shape): `observeOwnerWithRetryV1`: an owner failure runs `hold(rows)` on the rows captured up to the failure. Rows moved, or a source written within the racy window (2 s): pause (round x 250 ms, never past 2 s, long enough to leave the racy window) and observe the owner again, at most 4 rounds. Rows held and calm: the failure is stable and becomes `BUILD_OWNER_FAILED` (named owner, rounds, `stable`, text.en/text.de, message `EN / DE`, `cause` = original error). Four rounds that keep moving: the same code with `stable:false` and its own text. Foreign failures (abort, `BUILD_AUTHORITY_CHANGED`, `BUILD_COLLECTED_ERRORS`, `BUILD_SOURCE_UNPARSEABLE`, `BUILD_MEMBERSHIP_CHANGED`, stale implementation codes, `replicaUnsettled`, typed concurrent edits, and anything `followedPathsV1` follows) pass through unchanged, so every existing follow-up keeps its own behaviour.
- `📥️load/🟦️.ts`: `observeOwnerFactsMemoizedV1` observes through that loop (stderr `[graph-owner-retry]` JSON with bilingual text per retry).
- `🚪️admission/🟦️.ts` (`closeBuildOwnerAdmissionV1`, new optional 4th parameter `report`): a named owner failure no longer ends the walk. Every other owner is still observed (and memoized, checkpointed). At the end an owner is needed when the selection is `all`, it is named by an `owners` selection, it has a non-optional target or requested inputs, or another admitted owner depends on it; a needed failure throws one named failure listing all needed owners; an unneeded owner is dropped from the admission (owners, targets, inputs) and reported (`[graph-owner]` line with the "left out" text), so the rest seals. The failure is not memoized, so a later read observes the owner again.
- Whole reads: the owners-round already follows failures through `failedFacts` and `repairRounds`; they now also benefit from the stale-import fix. A stable failure there still ends the read (raw error, as before); I did not turn it into a withheld (`unavailable`) project because that row is keyed on a source digest and the cause here (a table) would never re-validate it. Say so if you want the withheld route for stable owner failures in whole reads.
