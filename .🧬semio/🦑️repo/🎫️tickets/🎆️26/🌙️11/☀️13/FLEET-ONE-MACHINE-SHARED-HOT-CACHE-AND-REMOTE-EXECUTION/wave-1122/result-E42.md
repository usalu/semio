# Result E42 (cargo-metadata-coalesce), 12:45

## Verdict
The premise of the lane is not true: **no Rust owner runs `cargo metadata`** (or any Cargo process) during graph inference, so there is nothing of that kind to coalesce. What I measured instead: the seven to eight Rust owners that sat at "0 rows" for 6 to 20 minutes are CPU and memory bound in ONE thread (the parent's inference child, pid 74385: 1.2 to 2.3 GB RSS, 57 to 69 percent of one core, 35 CPU minutes in 80 minutes of wall time) on a host that is swapping (32.3 of 33.8 GB swap used, 63,606 free pages = 1 GB). The farm/pool does not take any of it (`The pool of this machine is idle with 0 children ... starting: 0 of 4 children run` for 25+ minutes). I built no coalescing, because the two candidates I tried to coalesce (a persisted Cargo path closure; a single flight of concurrent async memos) are either too small or do not occur (numbers below). One small landing: the owner harness mapped native roots wrongly and now does what the full read does.

## (1) What a Rust owner repeats, from code and measurement
- Code: no `spawn`/`exec` in `B/🕸️graph/📥️inference`, `👁️observation`, `🧮️derived-nodes` or `🪪️graph-state` except `ps` samplers (`takeChildrenCpuV1`, the `<defunct>` children seen under 74385) and the owner-pool reaper. The word "cargo metadata" occurs in inference only as a declared input glob (`nativeLockInputs`, `🧭️script-inputs/🟨️.mjs:1020`: the replay must hash every `Cargo.toml`/`Cargo.lock`) and in `repo cargo` execution (`captureCargoCompilationPlanV1`, `🏃️process/📦️artifacts/🏗️native-build/🕸️units/📥️capture`), which already recalls `cargo metadata` + unit graph from a persisted plan memo keyed by lock, toolchain, configuration digest, compiler and arguments (`port.plans.recall/remember`). So the Cargo-level resolution is already content-keyed; it is just not on the inference path.
- Live: while the read ran, `ps` under 74385 showed only `<defunct>` sampler children for 12 s of polling; `lsof` of the harness process showed no cargo process either.
- The Cargo-level work an owner does is the TOML path-dependency closure: `nativeDependencyRoots` (`🦀️native-manifests/🟨️.mjs:241`), `cargoSourceSetV1`, Rust source walks. Measured (script `T/🧰️scripts/E42/cargo-closure.mjs`, 40 of 4,509 Cargo owners, `T` = ticket root): sharing one cache across the owners of a process 22.6 s CPU in total (median 32 ms per owner, 0.85 s for a 356-member closure); a fresh cache per owner (what a farm or pool child that has not seen the others pays) 106.9 s (median 2.4 s): 4.7 times, but only 2.4 s per owner and only for the first owners of a process. In the CPU profile of a cold late-mode owner (below) `compute` of that closure is 25.7 s of 364 s wall (7 percent). Not the minutes.
- What the minutes are (owner harness in late mode, as a generation build runs, fresh closure store, `E42_LATE=1`, script `T/🧰️scripts/E42/concurrent.mjs`; CPU profile `bun --cpu-prof`): block-catalog-rs 50 s CPU, bim-model-rs 56 to 108 s CPU, 8 to 313 s for the other two; 906 to 2,285 rows each. Profile of a cold late-mode owner: `readFileSync` 47 s self, `gc` 30 s, `toString`/`stringify`/`parse` 40 s, `lstatSync`/`statSync`/`existsSync` 33 s, `writeSync`/`writeFileSync`/`rmSync` 32 s (progress and closure-store writes), TypeScript parse (`parseListElement` 25.6 s inclusive), closure-layer verification (`indexedLayerHoldsAsyncV1` 48 s inclusive, `current(rows)` of the observation module 53 s inclusive), `yieldInferenceV1` 32.8 s. ## (2) Coalescing experiments (none landed, both reverted byte for byte)
- Persisted Cargo path closure: not built. Gain at most 2.4 s per first owner of a process (above); the owner records themselves are already content-keyed, and E1's analysis store covers the parse.
- Single flight of concurrent async memos in one process (`memoizedObservedAsyncComputationV1`: today the entry is stored only after the computation, so two owners that ask the same key at the same time both compute it): implemented in a new module `👁️observation/🛫️single-flight` (owner / wait / free claim, waiter slices with `checkpoint`, a cycle guard over the flights of a chain, a maximum wait) and instrumented with counters. Result of a real run, 4 Rust owners in parallel in one late-mode process: **3,476 claims, 3,476 owners, 0 waits, 0 free**, i.e. there is NO concurrent duplicate computation among the memoized walks (3,424 `walkImportsV1` and 52 closure computations, each exactly once). The hypothesis "seven owners each compute the same thing at the same time" is refuted for this memo; the module and the edit were removed (lock observation 11:17 to 11:32 and 11:55 to 12:05; `🟨️.mjs` sha256 prefix 7391f5fa before and after; no test or schema key remains).
- Record identity: the digests of the four owners are identical in every run (sequential, 4 in parallel with and without the flight, 2 lanes): 17b751e2, e3b1f45b, c37dcde7, 2dfdcfed (sha256 prefixes of the record images).

## (3) Concurrency, farm and host headroom
- In-process concurrency is NOT the cause, measured twice with opposite outcomes, so I make no claim: one run of the same four owners one after the other cost 87.7 s CPU / 116.6 s wall at load 28 (11:14); four at once cost 229 s CPU / 495 s (load 36), 322 s / 735 s (with the flight, load 32), 267 s / 528 s (load 31); two lanes 313 s / 993 s (load 36 to 42); the same sequential run repeated at load 40 (12:20) had used 281 s CPU after 17 minutes and was not finished when I killed it. The cost of one owner moves by a factor of 3 to 4 with the host state alone (swap 32 of 34 GB: page-ins count as CPU), more than with the concurrency. The one clean number is therefore "about 22 to 70 s CPU per cold Rust owner at load 28 to 40, about 1 owner per minute per thread at best".
- `farmHostMegabytesV1` is used by the live read (caller `project-nodes/🟨️.mjs:729` passes `availableMegabytes: await hostAvailableMegabytesV1()` into `planFarmWorkersV1`). With the real functions and the live process environment as far as it is visible (`SEMIO_HOST_CAPACITY_PLAN` and GRANT only, no plan limit, host 32,768 MB at or above `serveHostMegabytes` 24,000) `planFarmWorkersV1` returns Infinity, `planGraphFarmV1` returns 9 workers (reason cpu) and `reserveFarmV1` returns 5; yet the log says `inferring 111 projects in this process (memory)` and the owner pool reports `0 of 4 children run`. I could not find which input differs in the live process (candidates: the farm identity refusal `REFUSED`, the lean slice plan of that process, the host-capacity gate answering "no headroom" for the children, `ask.alone` of the read). The host genuinely has no headroom (1 GB free, 32 of 34 GB swap), so widening the farm would only add swap I/O; I did not change the farm.
- Owners/min: live read 97 owners in 104 minutes = 0.93 per minute (a part fetched from the fleet), the 8 Rust owners together about 0.4 per minute. Harness, one thread, at load 28: 4 owners in 117 s = 2.1 per minute; at load 36 to 40: 0.25 to 0.5 per minute.
