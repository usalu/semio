## (1) Journal resumable under churn (landed, lock graph)
- Key: a non-repair build's journal key is now `{parent, identity, cold}` (was also membership digest, owner names, added, removed), so a restart finds its waves after any file add/remove or edit. Repair builds keep the old full key. The header records the `membership` digest (schema key added).
- Resume reconciles when the work differs from what was journaled (`reconcileWaves` in `🔖️journal/🟨️.mjs`): it keeps every journaled owner whose rows still hold against the tree (`hold`, the plan's own row check) and whose derived questions' supports hold, rewrites the rows files without the others (so no stale or doubled rows), reverts the others to the parent's owner row, and derives only the fresh plan's dirty owners that were not kept (the plan against the parent runs as before, so moved paths are exactly the owners that come out dirty or invalid). Exact same work (same membership and same names) takes the old path with no verification (a stale owner there is published and caught by the next plan, as before).
- Safety limits: reconcile applies only while the environment is stable (journal env digest equals the parent's, fresh plan has no env change, no added or removed config, nothing dropped, no edge-only appends); otherwise the journal is dropped and the build starts over (as before).
- Tests `🧪️tests/🔖️journal` 7/0 (old "other owners not taken up" replaced; the oracle graph is compared in both): kill after wave 1, edit an unrelated owner, restart: 56 of 103 owners derived (the 48 of wave 1 are not derived again), one generation published, equals the Python oracle; same with a finished owner edited too: that owner and its dependants are derived again, the rest kept, one generation, equals the oracle.
