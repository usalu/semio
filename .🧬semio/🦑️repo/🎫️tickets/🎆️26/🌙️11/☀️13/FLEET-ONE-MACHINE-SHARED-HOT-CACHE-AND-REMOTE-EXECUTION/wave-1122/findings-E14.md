# E14 findings (round 3): why every `repo run` crashes or waits minutes

Two independent half-landed peer changes break every command that reads the graph or writes graph facts. Both are outside the run/serve path; E1 holds `landing.lock.observation` (since 01:28), so I did not edit that module.

## A. `repo run` crash 1: new observation kind `global` is written but the closed schema refuses it (owner: whoever lands `observeGlobalFactV1`, area `👁️observation`, coordinate with E1)
- Error: `Closed inference observation block rows required` (log reference fa4f717d) and, after the blocks were removed, `Closed inference record header required` (reference 7560ee77), both from `🏗️build/👁️observation/🟨️.mjs`.
- Cause, proven: `persistInferenceBlockV1` writes a block, then reads it back (last line of the function); the read validates `blockRowsValidatorV1` (`$defs.observationRows`, items `$defs.observation`). The peer's new code (`observeGlobalFactV1`, `registerGlobalFactV1`, `kind:"global"`, in the working tree since 01:35, generator contracts of `🕸️graph/📥️inference/📜️contract-reads`) emits rows `{kind:"global", path:"[\"generator-contracts\",root,...]", fact:[...strings] | {"\u0000keys":[...]} | {"\u0000absent":true} | tree}`. `$defs.observation.properties.kind.enum` has no `global` and `fact` has no array/tree branch, so the validator refuses a block whose name is its own content hash. Script `T/🧰️scripts/E14/validate-blocks.ts` validated 7193 persisted blocks of this checkout: exactly 2 fail, both with `/N/kind must be an allowed enum value`, both `kind: global`.
- Why it kills the service instead of being a miss: (1) the post-write read in `persistInferenceBlockV1` is not wrapped in the `observationBlockDamagedV1` handling the pre-write read has; (2) `observationBlockDamagedV1` does not list `Closed inference record header required` / `Complete inference header and result required`, so `readInferenceRecordOrMissV1` rethrows a record that cannot be validated instead of treating it as a miss.
- Needed (small, in `👁️observation`): add `global` to the kind enum and a `fact` branch for it (a `global` row has an open JSON fact, so give it its own row definition selected by `kind` instead of a generic object branch that would break `oneOf` exactness); wrap the final `settleObservationLeafV1(... .recheck())` of `persistInferenceBlockV1` in `try{}catch(error){if(!observationBlockDamagedV1(error))throw error; unlink leaf; blocksRefused.set(...); return false;}`; add the two header messages to `observationBlockDamagedV1`. Until then every graph read that infers an owner touching the generator contracts fails after about two minutes.

## B. `repo run` crash 2: ledger refused, optional-collector launch took the graph writer down (fixed in my lane, root data fault open)
- Error: `Closed cache ledger required: area caps leave less free space than the soft reclaim threshold of bazel-workspaces` (reference daa5a796), thrown by `cacheLedgerV1()` inside `launchGraphOptionalCollectorV1` (default parameter evaluated outside the function's try) during `withGraphFactWriterV1`.
- Data cause: the new ledger area `fleet-cache-index` (`⚡️caching/💾️storage/🧾️ledger/🔣️policy.json`, partition `products`, `basisPoints: 1000`) takes 10 percent of the products partition. `T/🧰️scripts/E14/ledger-fit.ts` reads the policy with that one value changed: 1000 to 200 all refuse, 100 passes. Owner: the remote-cache lane that added it; it needs a value between 100 and 199 or a smaller reclaim threshold, and the ledger is invalid fleet-wide until then (every machine that replicates this tree).
- Fix landed (area `cache-gc`): `launchCollectorV1` resolves the default ledger inside its try; a ledger that cannot be read is reported in both languages and returns `failed`, the writer carries on. Proof: `T/🧰️scripts/E14/launch-ledger-refused.ts` (decision `failed`, bilingual line) and the crash reference daa5a796 no longer occurs in `repo run`.

## C. Where a single-target run waits (measured 01:50 to 01:55 on the coordinator, load 21 to 31)
`repo run repo:test-cache-reset --dry-run`, policy fresh: graph service start 8 s (`launchd` route refused since boot, falls back to the app's access), `Loading the project graph` then `Planning 1 targets` and 110 s of owner inference with no sealed generation (current pointer is the quarantined 260), then crash A. Policy `current`: no service wait, `Planning 1 targets`, the same 110 s (there is no sealed graph to serve) then crash A (or crash B before the ledger fix at 36 s). So the avoidable wait is not queuing but that `Planning` needs a whole graph and none is sealed; a read that crashes never seals one, so every later run starts cold again (E2 round 3 describes the same loop). Once A is fixed and one whole read seals, `current` answers from the sealed state in seconds; I could not measure that warm state.

## D. Why a single target reads about 3,600 owners (answer to the coordinator, with E10 F2)
`Planning 1 targets` is not a slice read: resolving `repo:test-cache-reset` to a task needs the project graph, and the graph is built from every owner record of the tree (3,600 owners, 83k source observations). The `graph_policy` only decides whether a sealed generation may be served (`current`) or must be verified against the tree (`fresh`, the default of `repo run`). There is no sealed generation (pointer 260 is a quarantine pointer, every whole read of the last 20 h was cancelled by sidecar restarts after peer edits, E2), so even `current` starts a cold whole read; the 600 of the "taken N of 600" counter are the owners of the `workspace` stage, the 3,600 are the owners of the whole read. Exit code 75 of the slice worker is the stale-implementation restart: each peer edit of a graph source file restarts the read from the journal (E1/E2 resume work), so a read that needs more minutes than the gap between two peer edits never finishes. That is the structural wait; it is removed only by (a) a sealed generation existing (one uninterrupted read), (b) serving it with `current` for a project run whose own sources did not change, (c) deferring the restart of the reading worker while its progress advances (E2/E8). I did not change the run path for (b): `repo run` defaults to `fresh` by the build policy and the policy file is not mine; the lever is `SEMIO_BUILD_GRAPH_POLICY=current` or `--graph-policy current`, measured below.

## E. The error `Closed inference observation block rows required` (E10 F2 and my crash A)
Same error, same cause as section A: E1 round 3 added row kind `global` to the observation module; records and blocks written by the new code carry `global` rows. Persisted blocks written while the schema did not yet list `global` stay on disk (2 found at 01:45), and any process running code or schema from the other side of the landing fails the block's closed-rows check; with the pre-landing read path that failure propagated as a crash instead of a miss. E1's landing (schema `1351aa47`) now lists `global`; my change (below) turns any remaining refused block or record into a miss.

## F. Round 4: what the run path actually does, and what is still avoidable
- **A single-target run already uses a selected (closure) read**: `loadBuildGraphOnceV1` takes `loadBuildGraphUnpinnedV1(...{baseline:true})` for every selection other than `all` (default, pinned by `🕸️graph/🧪️tests/🔪️slice-read`); the generation slice is opt-in (`SEMIO_BUILD_GRAPH_SLICE_READ=generation`) and needs a sealed whole generation, which does not exist here (pointer 260 quarantined). I therefore did not change the mode switch.
- **The selected read is not closure-only in its first stage**: its phase order, read from the progress lines of `repo run repo:test-cache-reset --dry-run` (cold, load 20 to 31): wait for the load ahead (30 s) then for a free slice worker (2 of 2 busy, 2 loads ahead: 404 s in the real run), then `checking the file inventory of the tree` (20k to 118k, in another run up to 220k distinct source observations, `x of 600`), `taken 0 of 1`, `reading the owners (round 1) 7 of 3600`, a second inventory pass (`1 of 600`), `sealing and publishing the graph of this read`. The inventory pass and the owner admission (`scoped-discovery`, `discoverBuildOwnerAdmissionFactsV1`) walk the whole tree (3,600 owner roots) to decide which owners exist, before the closure of the target is cut. Making that stage closure-first (follow declared dependencies from the owner registry roots, admit only reachable owners, memoise per owner) is a change of `🕸️graph/📥️load` and `📥️inference/🔎️owner-discovery` (E1's area, lock `graph` held by E1 round 4); I did not start it and wrote no counting test for it (no fixture exists that counts owners read).
- **Queueing that is avoidable** (observed): (1) the slice pool has 2 workers, so a one-target run waited 404 s behind two other reads, one a whole-tree read; (2) a second dry run of the same target waited 5+ minutes for `repository-graph-optional-ledger:<workspace>`, taken exclusively and queued by `withGraphFactWriterV1` (`📥️inputs/💾️storage/🟨️.mjs:66`) and held by the resident host for its whole graph job; a run should try-lock that ledger and skip the optional-cache bookkeeping when it is held. Not changed (inputs storage area, graph writer semantics), proposed for E1/E2.

## G. Round 5
- Optional ledger (`📥️inputs/💾️storage/🟨️.mjs:65-67`, `openOriginalGraphLedgerV1`): the queued exclusive lease `repository-graph-optional-ledger:<workspace>` is held only while the SQLite ledger is opened, but the open loops on `SQLITE_BUSY` with the lease held (`await control.yieldContinuation()` and retry, no bound). The 6-minute holder seen in run 2 is therefore a process waiting for another process's SQLite write lock on the ledger database, and every graph writer of the machine queues behind it. Proposal (inputs area, E1/E2 round 7 lock): bound the busy loop (for example 5 s), release the lease and let optional writers (`optional` flag) skip their accounting instead of waiting; not landed because the ledger gives the quota decision of the same writer and I cannot prove the skip safe without that writer's tests running.
- Slice pool: `maximum` was fixed at 2; it is now `clamp(floor(totalMegabytes / 8192), 2, 4)` (32 GB host: 4, 16 GB worker: 2). Memory stays guarded by the pool's own reservation (`reserving`, learned peak per slice), so a fourth slice waits for memory instead of swapping. There is no priority plumbing from `frame.priority` to the pool (every client sends the default 5), so a real interactive lane needs the plan frame to carry a priority through `planner.plan` -> `loadSlice` request -> pool; the scheduler band exists only in the governor (`governor.enter(agent/priority)`), which is not what queues in the pool.
- Slice read under churn: this round's instrumented run of the same target was in its graph read after 603 s (cold again: peer landings change the implementation digest), so nx admission could not be isolated in the time the machine allowed; it was aborted by me.
