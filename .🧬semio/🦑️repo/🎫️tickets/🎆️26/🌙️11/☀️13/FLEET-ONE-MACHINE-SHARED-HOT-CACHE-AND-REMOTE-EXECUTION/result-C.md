# Package C: retention by slot supersession (server and local)

Root `B` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/`, `U` = `…/📚️library/⚡️caching/🦀️cargo/🗃️unit-cache/`. Landings are recorded in `landings.md`.

## Contract other packages use (unchanged since the first version of this file)

Module `B/🪢️slots` (`🟦️.ts`, schema `🧬️schema/🔣️.json`, Python oracle `🧪️tests/🐍️oracle/🐍️.py`):

- `slotIdV1(domain, parts)` = lowercase hex SHA-256 of the JSON array `["semio-slot-v1", domain, ...parts]`.
  - Rust unit (package B fills it as in `result-B.md`): `slotIdV1("rust-unit", [toolchain, targetTriple, profile, packageId, crateName, crateKind, sortedFeatures, sortedCfg])`.
  - Nx task: `nxTaskSlotV1({project, target, configuration}, platform)` = `slotIdV1("nx-task", [project, target, configuration ?? "", "<os>-<arch>"])`. The platform is always part of the Nx slot: Nx hashes may differ per platform and machines of two platforms must not supersede each other's keys.
- Wire: header `x-semio-slot: <slot id>` on `PUT /<ns>/ac/<sha>` and `PUT /<ns>/v1/cache/<key>` (400 when malformed; ignored for `cas`). An entry stored with the header is slotted, one without keeps the age/LRU rule.
- Claim (make a key current again): `POST /<ns>/v1/slots` with `{"entries":[{"kind":"ac"|"nx","key","slot"}]}` and a write token; answers `{claimed, missing}`. A PUT of an existing key with the header (409 for Nx, 200 for ac) is also a claim. A read never claims. Package B's client should call the claim endpoint after a remote hit of a key whose slot has a newer key (revert); package A/E code that runs Nx should call `registerNxSlotsV1` (module `B/🌐️remote-cache/🪢️nx-slots`) after a run with the rows of `readNxTaskRowsV1(<nx workspace-data db>)`.
- Local unit cache: optional `slot` in the entry JSON (package B writes it). A cache hit on a slotted key claims it (`claimUnitV1`, rewrites the newest variant with the current time, at most every 5 minutes per key).
- Active claims: `RemoteCacheStoreV1` option `claimed(namespace, kind, key)`; the server wires package B's `ClaimTableV1.claimed` into it, and an entry being written is claimed too.
- Grace: `remoteCache.server.graceSeconds` in `B/🔣️policy.json` (default 600, schema `ServerPolicy`), flag `--grace-seconds` on `repo remote-cache serve|gc`.

## What was built

1. Rule (pure, `B/🪢️slots/🟦️.ts`, `classifySlotsV1`): per slot the newest `storedAt` (ties: smaller key) is current; older keys are superseded at the `storedAt` of the next newer key and reclaimable `grace` after `max(supersededAt, own storedAt)`. States `current`, `retained` (readable, in grace), `expired`, `unslotted`.
2. Fleet cache server (`B/🌐️remote-cache`): sidecar `v1/.meta/<ns>/<kind>/<shard>/<key>.json` (slot, storedAt, referenced blobs) written after the entry; `💾️store` keeps an in-memory slot index, `claim()`, supersession and blob reclaim in `collect()`; `🧹️collector` planner order: dangling, superseded beyond grace (not claimed), age (only entries without a slot and not claimed), then the size budget takes retained before unslotted before current, least recently used first, and never a claimed entry or one stored within the grace (a write that cannot fit is refused with 507 instead). External `repo remote-cache gc` leaves supersession to a running server (`deferred`), because only the server knows the claims.
3. Blobs: `B/🗄️cas/🪦️reclaim` (`reclaimCasObjectsV1`) removes a blob only when no remaining entry references it (sidecar refs for slotted entries, refs read from the other entries) and the host store's own protections allow it: a live pin of any holder, an access within `minAgeMs` (ledger, covers a concurrent re-put), a hard link into a workspace. Dry run supported.
4. Readers: `B/🌐️remote-cache/📂️entry` (`readRemoteCacheEntryV1`): values up to 4 MiB are read whole before the response head is decided, so a collector that unlinks the file afterwards cannot tear or fail the answer and a value gone before the read is a 404 (this also keeps `Content-Length`; the wire fixture test caught the loss in a first streaming variant). Larger values still stream lazily from the path: a removal between decision and open ends the transfer, which the client sees as a failed read (a miss), never as a part taken for a hit.
5. Local unit cache (`U/🧹️gc/🪢️supersession`): `supersedeUnitsV1` per slot, newest variant time as `storedAt`, objects only superseded entries referenced go back to the host store; wired into `collectGarbageSingleFlightV1` through `supersedeLocalUnitsV1` (at most once per 5 minutes per root), so the command (`gc`), maintenance, watching collector, launch and collect-now triggers all run it. The "free-space pressure" trigger is the same function: `relieveUnitCachePressureV1` starts it. `casEnforceTickV1`'s only caller is the resident host service port `cache.tick` (`B/🏡️resident/🏗️composition/🌐️host/🟨️.mjs`), which only enforces the CAS caps; it is not a trigger for supersession.
6. Local Nx cache: `B/🌐️remote-cache/🪢️nx-slots` (`supersedeNxCacheV1`, `readNxTaskRowsV1`, `registerNxSlotsV1`). Slot of a task from `task_details(hash, project, target, configuration)` of the Nx workspace-data SQLite database; `storedAt` is the later of `cache_outputs.created_at` and `accessed_at` (a local hit proves the worktree needs it).
7. Verification: `repo remote-cache gc --directory <dir> --current-keys <file> [--json] [--grace-seconds n]` audits a cache against the key set of the current state (one key per line) and reports entries that are neither current nor in grace (exit 1 when any is stray), `auditRemoteCacheDirectoryV1`. Used in tests as the oracle that does not use the supersession rule.
8. Fixes: 1-byte rounding in `⚡️caching/💾️storage/🧾️ledger/🎚️machine/🧪️tests/🟦️.ts` law "blocked never grows" (the largest-remainder split can move one byte per store; the law now allows `stores.length` bytes); stale "120 GiB" docstring in `B/🗄️cas/🧬️schema/🟦️.ts` (now describes the 32 GiB cap and 90 % / 75 % watermarks).

## NOT verified / limits

- No real fleet run: the fleet server was not restarted with the new code, no Rust unit or Nx task was uploaded with a slot, so the reduction of a real cache (the 200 GiB bound, 256 GB workers) is not measured. A running server needs a restart to pick the code up (the daemon restart is not mine).
- Package B's client must send `x-semio-slot` and call the claim endpoint after remote hits; the Nx post-run hook (`registerNxSlotsV1` + `supersedeNxCacheV1`) is a library, not yet called from `⚡️caching/🚀️bootstrap/📜️script.ts` (shared file, other agents edit it). Until it is, Nx entries on the server stay unslotted (old age/LRU rule).
- `supersedeNxCacheV1` was tested on fabricated cache directories and databases; the layout of a real Nx 23 cache directory (`<hash>/`, `<hash>.commit`) and whether Nx tolerates removed `cache_outputs` rows (the `forget` port is not wired) is unverified. Nx hashes cannot be enumerated without Nx itself, so `--current-keys` takes a file; the build graph (`🧮️task-model`) cannot give Nx hashes, and semio-engine action keys depend on dependency output digests, so there is no cheap enumeration of the current key set; for Rust units supersession is the rule, as designed.
- A straggler machine that uploads an older state after a newer one makes the older key current until the newer one is claimed again (last writer wins within a slot, mitigated by the grace and by claims on every hit); a platform-neutral Nx key claimed by two platforms flips between their slots.
- A collector in another process and the server racing on the same key can, in a window of microseconds between re-check and unlink, remove an entry whose sidecar was just refreshed: the effect is a miss, never a torn entry.
- Blob reclaim can remove a blob that a local, non-pinning user (a current local unit cache entry) shares by digest; that user then sees a lost object and recompiles (same effect as the host CAS LRU).
- On a machine with several lanes/worktrees on different states, the local rule keeps only the most recently used state per slot (by design for single-worktree workers).
- Windows/Linux not run (macOS only); the code uses only node:fs, bun:sqlite (Nx database reader only) and the existing CAS.

## 2026-11-14: blob liveness (package J's report)

**Diagnosis.** Not the supersession rule. `reclaimCasObjectsV1` only offers blobs of entries it removed and the sidecars of the live entries were correct (checked file by file). The cause: the machine's disk is at 94 to 95 percent, above the host CAS's partition high watermark (0.90). Every `put` into a CAS root (also a fresh test root) runs the CAS guard, which starts a collection down to the low watermark; with `minAgeMs: 0` in my test it took every unpinned blob, live ones included. My test was therefore green at 90 percent fill and red above it. Reproduced and confirmed: the same scenario with the partition thresholds set above the fill keeps the blob.

**Real finding on the same cause (not a test artefact).** The fleet server's host CAS (`~/.cache/semio/cas`) shrank from 8.2 GiB to 0.9 GiB under that partition pressure, and 26 of the 28 entries of `/var/lib/semio-remote-cache` are now truly dangling (their blobs are gone from the host CAS). The host CAS evicts by LRU/partition and knows no entries. A live fleet cache therefore loses blobs while the disk is above 90 percent, whatever the retention rule does; it is a miss for the readers (the server drops stale results on read), not a torn restore. The disk of this machine must be brought under 90 percent (or the server given its own CAS root with relaxed partition thresholds, e.g. `SEMIO_CAS_ROOT` in the fleet unit); I did not touch either.

**Second bug found and fixed (data loss in the external collector).** `repo remote-cache gc` and the ledger delegation verified action results against the store directory only, but blobs live in the host CAS, so every action result looked dangling and a real (non dry-run) gc would have deleted all live action results of a host-backed server. The collector now asks the host store (`hasBlobs`, wired in the command); a result is dangling only when the host store lacks one of its blobs. Test: `🔗️restorable` "an external collection that verifies action results ...".

**Mitigation added.** `RemoteCacheStoreV1.pinLive()` pins, under the holder `remote-cache-live-<pid>`, every blob of the synchronized state (slotted entries that are current or within the grace) in the host CAS after every collection (the 300 s maintenance timer), at most one hour, released on close. The host CAS's eviction by cap, age or partition pressure then leaves them alone (the pin judges liveness by the server's local pid, which is the right owner here; a dead server loses it at once). Blobs of entries without a slot stay under the host rules. Test: host CAS collected with a 1-byte cap, current blobs survive, an unrelated blob goes, and the pin ends with `close()`.

**Kinds of referenced blob and what the collector does with them** (`🏷️retention/🧪️tests/🔗️restorable`, all pass twice in a row):
- unit outputs (action result, several blobs, shared blobs): current restores whole, old-only outputs reclaimed, shared outputs stay.
- Nx archives (host body behind a reference file): current restores; unslotted archives and other slots untouched.
- graph documents (package F, action result with a large document blob and a stdout note): same.
- install packs, pinned downloads, crate archives, wasm payloads through receipts (package G/H): these are bare `cas` blobs (or an unslotted `inst-<key>` manifest entry) that no entry of mine references, so they are never candidates for reclaim and survive any churn. Package H's pinned blobs and install packs live in the group store (`<store>/v1/fleet/fetch`, `fleet/install`), not in this CAS, unless uploaded to `/cas/<sha>`.
- Residual: a bare blob whose digest equals a blob of a removed superseded entry, referenced by no live entry, could be reclaimed unless the host store protects it (a live pin, an access within `minAgeMs`, a hard link). Consumers get a miss and fall back (G's restore verifies every byte and re-executes; H's pinned fetch verifies the sha and falls back to the group store or upstream). Not eliminated; only a pin by the owner closes it (package G/H could pin through `host.pin`).
- Property test: 6 seeded trials of 14 rounds of random puts (ac with shared pool blobs, Nx archives, with and without slot), store-driven or external collections at random times; after every collection each live entry restores whole, the newest key of every slot is live, bare blobs stay.

**Claims against package L's capped lifetimes.** `claimed()` is true only while the lease is live. The protection of a fresh entry never depended on it: an entry stored within the grace is protected by its `storedAt`, independent of the claim table. Test: a live claim keeps a superseded entry past the grace; after the lifetime cap the claim lapses and a fresh entry in its grace is still kept; once claim and grace are both over it goes.

**Not verified.** No real-fleet run; the pin is tested against a local CAS with a 1-byte cap, not against partition pressure on a full disk.
