## Findings that change the GR1 picture

1. The selected exchange is already fetch-first and already wired. `loadSelectedThroughFleetV1` (`G/📥️load/🤝️selected-exchange/🔌️attempt/🟦️.ts`) is called from `G/📥️load/🟦️.ts` (`selectedThroughFleetV1`, inside the graph custody, selected scopes only). A machine that finds a head for its scope (key = domain, revision, platform, scope digest) verifies every blob hash and every owner digest, keeps the owners whose rows hold in its own tree and re-reads only the others (`acceptSelectedOwnersV1`). It needs no Ready state and no `serveTotalMegabytes`. The Ready circularity of GR1 applies only to the whole-generation head adoption in the sidecar (`🌐️remote-execution/🛰️sidecar/🕸️graph/📥️adoption`), which is a different, background lane.
2. What is missing on the fleet is the head of the `workspace` selection, not a worker-side policy. A head is published only by a read that finishes (`publishSelectedGenerationV1` after `input.read`). On a 16 GB worker that read takes 2 to 3 h, so nobody finishes it; the coordinator never runs that selection. The per-owner records are published as soon as an owner is inferred (`createProjectFleetPortV1` gate `publish` and `offer`, `G/../🪪️graph-state/📦️project-records/🟦️.ts:359`), from every machine, so (3) of the task already holds at the owner level (the coordinator log says "6 offered"). A head needs the whole selection (graph text, rows of all owners, admission facts), so a partial head cannot be built per owner.
3. "30 wanted from the fleet, 0 fetched" is not a serve-policy block. `ledger.want` (`G/📥️inference/📦️project-nodes/🟨️.mjs:797`) marks every owner that is still missing after the first take pass; the log line "24 waiting for the fleet, which has not stored them yet" lists owners that are only queued behind 6 running ones (norm-eurocode-structural-plugin 1487 s, norm-eurocode-materials-plugin 1475 s, realparts-of-powers-z-n 1306 s, 2d-compute 1056 s, abi-rs 552 s, action-bus-rs 380 s), because memory headroom (3,072 MB grant, 2.1 to 2.2 GB held) lets 6 to 8 infer at once. Only 29 of 128 owners were listed as stored in the fleet; 87 were present locally (so nothing to fetch), 0 fetched because the fleet had none of the missing 41. The fleet has none because no machine finished inferring them, and the fleet cache refuses uploads under pressure (fleet status: `upload-failed`, `spool-full` on every worker; W1: "0 stored, 23 not shared"). The same log shows the read then stopping: "no owner made progress for 5 minutes (98 of 128 owners done)" (read.log line 4632 to 4640). So the blocker for (4) is slow cold cargo owners plus a full or refusing fleet cache (R3 lane), not the wanted board.
4. Present local records are not offered by take looks on a machine with a plan-stage limit (`deferOffer:away.take===true&&planStageLimitBytesV1()!==Infinity`, `project-nodes/🟨️.mjs:720`). They are offered by the priority offer pass (`offerFreshPriorityV1`, only the names other machines asked for, `G/🤝️prefetch/🟦️.ts`). That is why 87 present owners did not become fleet records. Open item, not changed (see below).
