1. g1-m02 became Ready because ONE `workspace` run was never stopped: 0 stall stops in 14 h (the others 13 to 30 each), its graph read ran uninterrupted (a 7,714 s read at 02:18Z, then warm owner records), then the build ran 23 min (2,143 units compiled) and ended `ok` at 07:54.

"Attempt 17" is mostly 17 stall stops, not 17 failures. The stall stop ("nothing new for 10 minutes") hits a read whose `taken N of 608` counter stands still while 6 to 8 looks are in flight.
3. The look itself is the slow part, on the worker, not the fleet: `gateTimings` of the fleet are all 0 on m03 and m10 (the records are stored locally); the time is in `authority` (m03: 812 s over 17 looks, 48 s each, 73 ms on the coordinator) and in the presence verification of the mounted image, whose `mappingGrant` of the post-verify was still active after 125 s (m03) and 65 s (m10). Records are durable (m08 had 52 of 69 owners back 70 s after a restart), but every restart pays the file inventory (about 220 s) and the owner rounds again.
4. The host warden suspends and cancels exactly these reader processes (slice-worker, graph pool-child): m10 15/13/13, m02 6/5/7, m01 4/4/4, m08 4/2/4; m06 cancelled a slice worker at pressure critical. A suspended reader shows nothing new, so the stall rule killed the whole stage. Fixed on my side (below); note sent to the warden ticket.
5. The "trees differ" belief of W6 is explained and no longer holds as a delete defect: at 08:16 all 13 origins attest the same manifest `83fb9565` with 451,866 files and 0 of 1,024 bucket digests different; `deleted 17` is identical in every view; the differing lines are in-flight edits (below). The coordinator is the outlier: its view pass takes 117 to 347 s (5 % duty), publish p50 40 s / p95 150 s, the replica's own verdict for it is `diverged view.digest`.
6. g1-m13 has a 7.8 GiB dependencies image (the born minimum for darwin); the install needs 9 to 18 GiB on its peers, so it can never finish `dependencies` and its remote-execution work directory (inside that image) has 0.3 GiB. Not fixed: needs a model change (section 3).

## 3. g1-m13, g1-m04, g1-m05
- g1-m13 (dependencies attempt 29, `lstat .../d/m/j/307631934f0e2b89ee1f/bindings.json: no such file`; 16 failed runs in 12 h): its `.cache/b/d/m` image is 7,801 MiB (peers 36,863; 326 MiB free). The dependencies partition is a FIXED image born at `max(min(declared 36 GiB, 20 % of host free), needBytes.darwin)`; m13's host had ~16 GB free, so it got `needBytes.darwin` = 7,491,026,944. The coordinator's same volume holds 14 GiB (j 9.0, bun-cache 3.3, python 2.0, remote-execution 0.2); the peers use 9 to 18 GiB. So the stage cannot finish (files vanish under a full volume) and the remote-execution work directory (`d/m/remote-execution`, inside that image) has 0.3 GiB: "0 of 10 slots usable, one action needs 1.0 GiB". This is NOT the CAS cap (host store 7.5 GiB on workers is CAS5; separate and not involved). Root: the declared darwin need (the install model `concurrentRequiredImageBytesV1(true)`, 6.7 GB) is below every measured use, and a born fixed image never grows. Tried `needBytes.darwin` 20 GiB: reverted at once because 3 budget tests encode the model (install after the ledger shares must be the smallest capacity; the 16 GB RAM/60 GB free profile then needs 61.5 GB). Follow-up lane (needs a design call): (a) measure the install model with bun-cache, python and generation included (about 14.5 GiB), (b) put the remote-execution work directory in its own sized volume or on the host volume, (c) let `dependencies` below its need be a doctor error with the auto reset, as the elastic partitions already do.
- g1-m04 (linux, `/home/deck/semio`): `dependencies` waits for 6,144 MB free on /home, has 3,845 to 4,950 MB; all collectors free 0 B (nothing derivable left). Genuine host disk shortage of about 2.3 GB; needs a human to free space or a smaller need on Linux (37.8 GB declared). Same family as m13, not a code defect of this lane.
- g1-m05 (windows): attempt 37; the stage is stopped by the stall rule while "Another process is building the dependencies (598 s): waiting for that build" (a stale holder, the known pid-reuse verdict, open since W1), and the last real failure is "Declared provider descriptor changed (e2e1621e)" (package.json edited under the sync).
