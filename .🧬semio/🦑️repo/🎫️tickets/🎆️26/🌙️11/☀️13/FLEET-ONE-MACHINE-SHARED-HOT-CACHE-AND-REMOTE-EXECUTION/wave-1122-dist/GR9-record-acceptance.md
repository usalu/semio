## 4. Item 3, incremental repair: not implemented, and why
The moved rows that really matter are `analysis` rows whose replay result changed (an import added or removed) or an `exists`/`resolve` flip. A closure entry is a flat list of rows plus the resulting file list; it does not keep the import edges between modules, so there is nothing to re-walk from the moved file. Repairing one entry means partially re-walking the module graph (`🕸️module-graph`, `🧠️reach-memo`, `👓️walk-views`), whose state lives in the per-process `scripts` cache and is dropped every `OWNERS_PER_RELEASE_V1` owners. An incremental repair needs the edges stored per entry (entry schema version bump, every stored entry and every fleet entry invalid once) and a re-walk entry point that takes the moved files as seeds. Both are changes to the walk, not to the record layer, so I did not do them blind. What does exist and already limits the damage: the farm verdict (`observeProjectRecordV1`) settles stale entries in a governed child; the take (no derive in the parent) is the only place that declares them stale. A cheaper next step with a measurable effect is for the take to hand an `absent`/`stale` closure miss to that farm verdict instead of ending the look (open item 1).
