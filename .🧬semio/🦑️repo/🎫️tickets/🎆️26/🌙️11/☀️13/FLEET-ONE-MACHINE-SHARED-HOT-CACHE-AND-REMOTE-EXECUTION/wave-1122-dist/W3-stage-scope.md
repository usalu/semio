- At 21:41 the head of scope `2f245baf...` (published 20:30 by GR14) was GONE from the fleet cache: `getResult(selectedHeadKeyV1)` = miss, no file in `cache-server/v1/main/ac`. So every worker that restarted after about 21:00 looked up, missed, and inferred itself (restarts by the 10-minute stall rule, 8 to 16 attempts).
- Mechanism (code): blob-bound eviction plans removals tier first, then least recently accessed (`🌐️remote-cache/🧹️collector/🟦️.ts:62-79`; store `💾️store/🟦️.ts:268`). A head is published without a declaration, so it is tier 1 ("undeclared"), the same tier as every project record, and it is read once per worker start; the compile units are tier 2 and go last. Under 34 GB of churn a tier-1 entry that was not touched for a while is the first victim; the idle-age rule also applies to tier < 2 only (`collector:48`). I did not observe the eviction itself (no server log of it); it is the only rule in the code that explains a 223 MB entry disappearing while its slot was never superseded (`selectedHeadSlotV1`), and it is consistent with the counters. Not proven.
- The sealed local copy of the coordinator (`.cache/b/g/m/selected/2f245baf....json` and `.authority.json`) was also removed from the coordinator's own graph store, so the 20:18 read could not be republished (`probe-publish.ts` ENOENT); the only way to a new head is to read again.
