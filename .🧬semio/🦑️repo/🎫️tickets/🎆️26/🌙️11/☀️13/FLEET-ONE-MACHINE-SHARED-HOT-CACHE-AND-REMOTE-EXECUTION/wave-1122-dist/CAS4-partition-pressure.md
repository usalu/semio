# CAS4: partition pressure must not evict held entries (2026-11-23 19:35)

## Root cause (verified in code, `🗄️cas/🧹️collector/🟦️.ts`)
`heldNeed = totals.shortfallBytes > 0`, and `shortfallBytes` is the part of `max(capNeed, partitionNeed)` the unreferenced candidates could not free. At 96 % partition use `partitionNeed` is ~0.16 x 926 GiB, far more than the store (25 GiB, 10.7 GiB referenced) can ever give, so after removing every candidate the shortfall stayed > 0 and the capacity stage (`evictHolders`) took the 1,000 LRU entries of the registered holders. Every tick of the sidecar's continuous collector (`casEnforceTickV1` -> guard -> `collectCasV1`) repeats this for as long as the partition is above 90 %.

## 18:42 loss (item 3): which stage removed the objects
The `{"entries":463}` record at 18:42:00 (pid 98103) is written by `pruneEntriesV1`, i.e. it DETECTS entries whose objects were already gone; it is not an eviction. Evidence that the capacity stage did not write it: `evictHolders` unlinks the entry file first and logs `capacity` in the holder's own log; the clone log has no `capacity` record at all. The objects vanished behind the entries, before the keeper hard links existed (`v1/k` directories born 18:35:54-55; holder files exist from the sidecar's first new-code collection at ~18:35), so the removing stage is an object collection that did not know the clone's holder: the collectors of the old-code processes (16216 from 18:25, 9362/9366/9430, the 2025-11-22 closures) or the new sidecar's first scan before it had registered the clone; not provable afterwards, no collection log exists. What this change closes for the future is the reachable path of the new code: partition-driven eviction of held entries (the live dry run before the change planned 1,000 of them; the same plan runs each tick). The holder log now says which: see 4.

## Changes (schema first)
1. Planner (`🧮️plan.ts`): `totals.capShortfallBytes` (still missing against the store's OWN cap in force) and `partitionShortfallBytes` (missing against the partition); `shortfallBytes` keeps its meaning. The collector evicts held entries only for `capShortfallBytes`, after all unreferenced/expired blobs are gone (planner stage order unchanged), LRU.
2. Protected share: schema `Policy.holderProtectedShare` = 0.4 of the cap per live holder (`🫂️holders/🧮️plan.ts` `protectCasHolderEntriesV1`): a holder's most recently used live entries up to that many bytes are never evicted by the cap stage (the crossing entry stays whole; dead entries are never protected). So one cap spike cannot wipe a running build's cache.
3. Honest report: under partition pressure the collector removes only unreferenced/expired blobs and the status line says so: "The partition is 96.3% used but the store holds only X GiB of it (n%); the remaining Y GiB of pressure is not the store's, so no held entry was evicted." (EN+DE, `partitionNotStore`); when the floor stops the cap eviction: "N entries of live holders stayed protected (floor F GiB per holder)."
4. Attribution: holder eviction records now `{version,atMs,pid,role,capacity,capacityBytes,reason:"capacity"}` with `role` in `guard-background | guard-admission | operator | recovery | collector`; `pruneEntriesV1` writes `{reason:"lost",role:"prune"}`. Unit-cache `Eviction` schema gained `capacity, capacityBytes, reason(capacity|lost), role` (it lacked `capacity*`/`reason` although they were already written).
5. `repo cache cas gc --unreferenced [--dry-run]` (catalogue entry + flag, EN+DE, help snapshots regenerated): planner `unreferencedOnly` takes every candidate and nothing else (no areas, no held-entry stage, shortfalls forced to 0). Protected as always: held, pinned, leased, hard-linked, younger than `minAgeMs` (180 s, the in-flight grace), plus the re-check right before every unlink.
