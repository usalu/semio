## 2. What changed (code only; schema-first)
Schema (`🗄️cas/🧬️schema/🔣️.json` Policy, EN+DE messages `statusCap`, `capRefused`): `incrementBytes` 2 GiB, `transientLeaseMs` 30 min, `admissionBudgetMs` 8 s (existing `capBytes`, `highWatermark` 0.9, `lowWatermark` 0.75, `capHostSharePercent`, `enforceTickMilliseconds` 30 s).
- (a) Admission (`🚦️guard`): a store opened with `refuseOverCap` (the cache server's host store, `🛰️sidecar/🗄️cache`) judges a write that would exceed the effective cap: one collection (incremental, shared single-flight) is awaited for at most `admissionBudgetMs`; if the store is still over the cap afterwards (or a futile collection finished within the min age) the WRITE throws `CasCapRefusalV1` (EN/DE). `RemoteCacheStoreV1.store` already maps a put error to `capacity`, i.e. HTTP 507; the offload/upload callers already skip the upload or run locally. Every other CAS store keeps today's behaviour (never refuses on cap; critical partition refusal unchanged). The detached collection keeps running after the writer gave up.
- (b) Continuous collection: automatic collections are `incremental`: above the high watermark they free `incrementBytes` below that watermark (planner `need = min(after - low*cap, after - high*cap + increment)`), not down to 75 %; the 30 s tick (`casEnforceTickV1`) re-collects whenever the store grew more than half an increment since the last completed collection (the 10-minute cooldown no longer hides growth for `cap-high`). Manual `repo cache cas gc` / `repo cache gc` still free down to the low watermark. Partition need (host disk) is untouched and still full.
- (c) Transient inputs: clients (`httpRemoteExecutionContentV1`, offload `shipOffloadActionV1`) send `x-semio-lease: input` on HEAD and PUT of action inputs; the cache server leases those digests (`CasStoreV1.lease`, append-only ledger `v1/x/<writer>.jsonl`, expiry = now + `transientLeaseMs`; renewed by every HEAD/PUT while the action is prepared). While leased: protected like a pin. After expiry, if nobody read the blob later and it is neither pinned nor hard-linked: ALWAYS taken by the next collection (reason `age`, planner stage 1, before any LRU), and the tick runs such a sweep every `transientLeaseMs`. Never pinned, never counted into `pinLive`. Worker-published outputs carry no mark, so they stay normal and pin-eligible. Stale ledger lines of vanished blobs are compacted by the collector.
- (d) Reporting: `repo cache cas status [--json]` now prints/returns cap in force, declared cap, high/low watermarks in GiB, increment, transient lease and the number of leased/expired blobs. NOT done: `repo fleet status` and the `repo cache status` ledger view have no CAS section (fleet-status schema has three strict `storage` definitions + fixtures; adding a field was out of the time box). Open item.
- Out-of-process safety: collector re-checks live leases right before every unlink (stamp-based reload per shard, bounded).

## 3. Effect and activation (important)
The code runs inside the live cache server (6094, sidecar) and in every process that opens the CAS. It takes effect ONLY at the next natural restart of the cache sidecar (guard, lease endpoint, refuseOverCap) and of the requester/worker processes (the `x-semio-lease` header). Until then: old behaviour (hourly big-batch collections, inputs treated like outputs). A new client against the old server is harmless (header ignored); a new server with old clients just sees no leases. No server/RE restart was done (play site-build `[run] 04:14:20` active, gate `pinned/supervisor.out`).
No collection was run: the server's own collector was holding `gc.lock` at 04:40, df showed 48 GiB free, and unleased input blobs of the running play offload must not be taken by an extra collector (old code cannot know they are inputs). Before/after sizes: none (no relief action taken).
