## 1. What the step "checking the file inventory of the tree" really is
- It is not a walk with one stat per file. The slice step `inventory` (`L🕸️graph/📥️load/🟦️.ts` `inventory`, label from `🧠️memory/📋️slice-report`) contains the whole scoped discovery: `settleObservedComputationV1` runs the 608 owner admissions in PASSES, and every pass verifies the recorded rows of every owner (`observeOwnerFactsMemoizedV1` -> `hold` -> `buildGraphSourceFactsHoldV1(rows, ..., withinRound=true)`). The counter "completed owner checks" is cumulative over passes: m10 19,778 / 608 = 32 passes in 6,904 s of ONE attempt (215 s per pass, `slice-memory.json` `inventory.active`), m01 36,951 = 61 passes in 10,221 s (168 s per pass), m13 9,315 in 24,500 s. "N distinct source observations" is the size of the capture of the CURRENT pass (95k to 102k while a pass is young on a machine without a head memo, 217k with the head's memo seeded), not a property of the machine: that explains 95k versus 217k.
- The admission memo of the head (`.cache/b/g/m/selected/2f245baf....admission.json`, 123 MB) holds 289,461 observation rows: lstat 110,066, **readdir 100,587**, exists 17,885, analysis 16,265, resolve 11,174, fileExists 10,279, file 8,480, global 6,414, directoryExists 3,819, field 3,278, readdirNames 602, stat 291, others < 200. Only 8,480 are file rows (these already verify by `stat` and compare size/mtime/ctime/inode, hashing only on a difference, with an in-process digest memo `fileShaMemoV1`).
- Measured on the coordinator (load 20, `W5/probe-kinds.ts`, sampled rows, first pass): readdir **207 to 260 us per row**, lstat 30 to 43 us, resolve 68 us (8 us warm), fileExists 44 us (19 us), stat of a directory 6.6 us, raw `scandir` 87 us. A readdir row is verified by recomputing the whole directory fact (`facts.readdir` -> `directoryFactV1`: sorted typed listing, name filter, hollow walk below every subdirectory entry, JSON, sha256) with no memory between rounds (a round caches only inside itself, `roundTreeReadsV1`). 100,587 rows x 207 to 260 us = 21 to 26 s per pass on the coordinator; the workers run at load 8 to 33 on 10 cores with 16 GB and swap, about 10 times slower = the measured 170 to 215 s per pass.
- Why 30 to 60 passes: a path that an owner read moved under the pass (50 machines write the replica; W4 section 1) restarts the pass; with a pass of 3 minutes some path always moves. W4's taken memo makes a repeated pass cheaper for owners but still verifies every row of every owner again, and 100k of those rows were full recomputations. The stall rule (10 minutes without a taken owner or observation) then kills the process.
- Per-owner discovery is not the remaining cost: m10's active owner (`@semio-tech/dsl-derive-rs`, `source-inputs`) was at 84 s, which is the slow tail of one pass on that machine.

## 3. The root fix (landed): a stamp memo for directory facts
Where: `O📂️directory-stamps/🟨️.mjs` (new, schema `🧬️schema/🔣️.json`: `entries` 200,000, EN/DE texts), hooked into `O🟨️.mjs` (`typedListingV1`, `roundHollowV1`, `facts.readdir`, `observationCollectionsV1`, `releaseInferenceMemoryV1`, new export `observationDirectoryFactCountsV1`).
- The fact of a directory listing depends only on the listing of the directory and on the listings the hollow walk read below its subdirectory entries (the generated/noise/local name rules are static policy). Every listing is now stamped with a `stat` taken BEFORE the read (mtime, ctime, inode, size) and the computation of a fact captures the (path, stamp) of every listing it read, including those answered from the round cache and the hollow cache (hollow verdicts now carry their listings). The fact is remembered with these stamps; `facts.readdir` first checks them: one `stat` per consulted directory (once per round, a round is one snapshot), and a hit costs no listing, no hollow walk, no digest.
- Correctness: (1) any name added, removed, renamed or retyped in a consulted directory moves its mtime/ctime, so the fact is recomputed; a change deep below a hollow directory moves the stamp of the directory that was listed, which the ancestor's entry carries (test). (2) A stamp younger than the racy window (`racyMilliseconds`, 2,000 ms) is never remembered, so a change in the same clock tick cannot keep it (same rule as the file digest memo). (3) A listing that failed or had no stamp makes the fact unmemoizable. (4) Only live filesystem reads use it (an observed world port, as in the law tests, bypasses it). (5) The recorded row is compared as before (`JSON.stringify(fact)`), so a fact that differs from the head's is reported stale and its owners re-inferred exactly as before.
- Measured (same sample, same machine): readdir verification pass 1 207 to 260 us/row, pass 2 **27 us**, pass 3 **18 us** (10 to 14 times); lstat 43 to 9 us. At 100k rows that is about 2 s instead of 21 to 26 s per pass on the coordinator and, scaled by the observed 10 times, 20 to 30 s instead of 170 to 215 s on a loaded worker, after one cold pass. The memo is per process (it lives as long as the graph child); a restart pays one cold pass of 3 to 4 minutes (open item 1).
- Tests (`repo test-file`, one at a time, all green unless noted): new `O📂️directory-stamps/🧪️tests` 5/0: (a) a warm memo of 40 directories: 0 listings and exactly 40 memo hits (= one stat per directory); (b) one name added in one of 12 directories re-lists exactly that directory and only its row is stale; (c) a file added below a hollow directory moves the ancestor's fact, removing it restores the old fact; (d) a directory changed inside the racy window is listed again each time and a vanished directory reads `!ENOENT`; (e) unit law of the memo (young stamp, failed listing, moved stamp, capacity order); every fact equals the independent Python reader (`🐍️.py`, which re-implements the name rules from the policy JSON). Observation: round-listings 3/0, listed-children 4/0, validation-round 4/0, exhaustive-hold 2/0, stale-row 3/0, check-memo 2/0, retention 5/0, discovery-reads 3/0; source-names hollow 4/0, machine-local-dirs 3/0; graph observed-facts 7/0, load inventory 10/0. machine-local-paths 18 pass / 1 fail: the law "every kind the schema declares ..." sees a `global` fact in the verifier that no schema lists; it fails identically without my lines (the `global` row is not in my diff).

## 4. The other asked items, decided
- (b) Restrict to the files the selection's owners reference: already the case. The rows verified are those of the 608 owners of the head; the whole tree is walked only for membership (`workspaceBuildFilesV1` + `buildGraphMembershipV1`), which for a selection comes from `admission.files` and costs one lstat per member and directory. Nothing outside the head's rows is read in a pass. What was too expensive was the recomputation of their directory facts, fixed above.
- (c) Change feed: the replica's segment files (`/Users/Shared/semio-store/v1/origins/*/segments/*.jsonl`, `put`/`delete` with path and sha) name every file change with an HLC. It would be the right first-pass accelerator (a cold pass could skip stamping the directories no segment touched since the head) but it reports files, not directory entry changes made outside the replica (a build output, a local edit), so it can only ever be a hint and must never replace the stamps; not done, see open item 2.
- (d) A path that moves invalidates only its own row: the verdict of a row is per row (`verdicts` WeakMap per round) and the memo drops exactly the facts whose consulted directory moved (test (b): 1 of 12).
- File rows: already one stat when the recorded stamp matches; when it does not (a replica rewrites mtime/ctime/inode, so every file row recorded on ANOTHER machine misses) the content is hashed once per process (`fileShaMemoV1`, bound 200,000 entries; the tree holds more files than 200,000 on m06/m07, so the memo is cleared whole when full: open item 3).
- m01 "door.script": not a hang. `[repo] still working after N s; last phase started: door.script` is the heartbeat line of the repo CLI naming the last CLI phase it emitted; the graph read is a child of that phase and prints slice progress, not CLI phases.
