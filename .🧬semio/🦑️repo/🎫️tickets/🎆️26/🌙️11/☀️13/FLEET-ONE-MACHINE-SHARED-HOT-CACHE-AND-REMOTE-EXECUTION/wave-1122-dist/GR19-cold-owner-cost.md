`B` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/🏗️build/`, `SI` = `B🕸️graph/📥️inference/🧭️script-inputs/`, `EL` = `B🪪️graph-state/📦️project-records/🚚️entry-lane/`, `T` = ticket folder. Lock `lock.graph-closure` (released). Probes, scripts, raw summaries: `T/wave-1122-dist/GR19/` (`run.sh` one owner per fresh process, `one-owner-v7.mjs` GR18's probe plus a drain step and a bounded profile, `summ.py`, `prof.py`, `callers.py`, `layer-census.mjs`, `fleet-server.mjs`, `run-tests.sh`, `*-summary.txt`). Stores and profiles lived in the session scratchpad and are deleted (largest 97 MB; the private fleet 29 MB). No restart, no hand-started service except my own private scratch cache server on 127.0.0.1:6199 (killed), the play build untouched, one heavy process at a time.

## Verdict
1. The cold cost was not the derivation. In a profile of a marginal cold Rust owner (tools warm, `2d-trace-rs`, before the fix) 91 % of the samples were the OFFER of its own entries: `packBundleV1` re-packed, for every offered entry, the shared tool entries the owner refers to (cargo toolchain closures of up to 62,015 layers each), reading their layer files again and converting 37,000 rows each time, then compressed and hashed them again. 36 of 40 profile seconds. The derivation of the owner's own six entries is about 1.5 CPU s.
2. Landed: (a) a shared entry is packed ONCE per entry version: its neutral document is kept in memory and in a digest-addressed file `d/<recipe key>.<24 hex>.br` of the machine store, reused by every later offer of this process and of every other process of the machine, valid while the stored entry has the same stamp and the closure keys the document consulted still answer the same (`consultedHoldV1`); (b) the compressed blobs and their hashes of those same bytes are made once (`packGraphDocumentV1`, `blobHashV1` memo on the bytes object); (c) a recently saved layer is served from memory (weak reference, checked against the file) to the offer that follows its save; (d) the offer is OFF the critical path: `lane.enqueue` returns at once, one drain per process, bounded queue (256), deduplicated by entry key, progress, cancellation, jobs written to an outbox that the next process of the machine adopts when the writer is dead; (e) a derived entry and a taken entry are stamped from memory when they are stored (no layer read back, no layer index file written).
3. Measured, same host (load 20 to 60 on 10 cores, a play release running), walk farm off (so every CPU second is in the measured process, as in GR16-GR18), one fresh process per owner, the same 8 Rust owners as GR18 and 8 TypeScript/project owners (table 2, 3). Marginal cold Rust owner: GR18 20 to 78 CPU s (median 42) -> 2.4 to 2.7 CPU s, 360 to 400 MB, 6 to 10 s wall. Target "single-digit CPU seconds and < 500 MB" is met by the marginal Rust owner and by the warm owner of every kind; NOT met by the first owner of a machine (tool import or tool derivation, 18 to 44 CPU s, 1.3 to 1.5 GB) and not by the large TypeScript owners (`cad-js`, `component-deployment-contract`, `dag-plugin`: 40 to 53 CPU s, 1.4 to 2.5 GB).
4. `cargo-workspaces`: 1,000+ CPU s and 3.3 GB (GR18, stopped), 462 s (GR17) -> 42 CPU s cold (32.4 s owner + 8.3 s drain), 2.4 GB peak, warm 3.7 s CPU / 580 MB. It is no longer an outlier by two orders of magnitude, still 15 times a Rust owner. Cause, with evidence in section 4: not quadratic in members and it reads no Cargo root; its nine script targets each derive an entry whose command closure is the whole library import graph (30,107 layers per entry), and each entry is packed, compressed and stamped; the old 1,000 s was the offer re-packing the shared tools 17 times on top.
5. Item 2 of the task (one packed file per closure entry INSTEAD of layer files) was measured and NOT built: the data say it would multiply the store. Census of the real store (`GR19/layer-census.mjs`, 41,066 entries): 11,981,650 layer references name only 62,477 distinct layers (9,931 layers are named by 100 or more entries, 20,636 by 2 to 9, 13,706 by one); 152 entries have more than 10,000 layers (largest 160,961). A file per entry holding its layers inline would store about 190 times the layer bytes (3.0 GB -> about 570 GB); the shared layers ARE the deduplication. The layer file count is paid once per machine (62k files, course-rs first owner: 10.8k to 72k writes, 18 to 44 CPU s), not once per owner, so it does not decide the 57 CPU hours. What the task wants from item 2 (the offer uploads a digest-addressed file, no re-pack, verified-once stamps keyed by the digest) is what (a), (b) and (e) above do for the part that repeats.
6. Item 3 (walk the shared core once per read): GR16 already moved the toolchain script behind a tool reference (`cargo-execution`), so a marginal Rust owner no longer walks 2,381 files; its walk is 3 to 14 % of its profile. A shared machine-store walk memo was not built; open item 2.
7. Extrapolation of the whole read (5,231 owners), estimate: warm fleet, cold machine ("adopt", tools imported once, 19 CPU s): Rust 2,600 x 2.6 s + other 2,631 x about 6 s (adopt measurements: 2 to 7 s, `cad-js` outlier) = 6.8 k + 15.8 k = 22.6 k s = 6.3 CPU h; cold fleet (everything derived and offered once): Rust 2,600 x 6 s (mean of 7 marginal incl. the 28 s `dag-dag-rs`) + other 2,631 x 19 s (mean of 8) = 15.6 k + 50 k = 66 k s = 18 CPU h (GR18: 57 h). Under the 5 CPU-hour target only for the Rust half; the TypeScript/project half, not the Rust half, now sets the total. Everything in this section is an estimate from 16 owners, not a whole read.

Cold on the tools-warm store, private empty fleet: 42.1 CPU s, 42.4 s wall, 2.46 GB resident, 17 entries derived and 5 published inside the run (the other offers drained afterwards: drain 11 s wall, 8.3 CPU s), 115 reuses of shared documents; warm 3.7 CPU s, 3.6 s wall, 580 MB, 37 of 37 entries stamped, 0 derived. Algorithm: its project has nine script targets (`members-check`, `contract-check`, ... each `repo ./📜️script.ts <command>`), and the command closure of that script is the whole library import graph (the script imports `🗂️workspaces/🦀️cargo/🟦️.ts` and the process, cache and build modules; 8,322 files under the library); each target is an entry of about 30,000 layers (census: `target-sources` 30,107 layers). It reads no Cargo root and spawns nothing; cost grows with the number of targets times the closure, not with the 4,677 roots. Remaining lever (open item 1): the nine head entries share almost every layer, so their documents could be packed against the layer digests once.

## 4. What changed (file:line at landing time; sha256 12 hex after in `T/landings.md`)
- `EL🟦️.ts` `createClosureEntryLaneV1`: `enqueue`, `adopt`, `cancel`, `progress`; `offerNow` (the former `offer`, still awaitable and the contract of the existing tests); packed-document memory and files (`rememberedOf`, `rememberPacked`, `packedMemoryV1` bounded by the policy `packedMemoryBytes`, `forgetPackedClosureDocumentsV1` for tests); `flush` waits for the drain; counter `reused`. `EL🧬️schema/🔣️.json`: `offerQueue` 256, `packedMemoryBytes` 128 MiB (the policy form identity moves once; no compat code).
- `SI🟨️.mjs`: the awaited `Promise.race([lane.offer(...), 15 s])` is `lane.enqueue(...)`; `closureFleetLaneV1` passes `outbox` (`o/`) and `documents` (`d/`) of the store, adopts dead writers' jobs and registers a `beforeExit` flush; `flushClosureOffersV1`; `stampKnownEntryV1` (derive start and import start are the `since` of the witness, so a path written inside the walk or the verification refuses the stamp); `bundleLayersHoldV1`; `keepDerivedClosureV1` and `closureTravelV1.import` stamp from memory.
- `SI💾️entries/🟨️.mjs`: `save` answers the entry `digest`; `layersSync` takes a recently saved layer from a weak reference (length and file existence checked). `B🪪️graph-state/🛰️exchange/🟦️.ts`: `packGraphDocumentV1` and the blob hash are memoized on the bytes object.
- Soundness: a remembered document is used only while (1) the stored entry's stamp (size and mtime) is the one it was packed from, (2) every closure key it consulted answers as then (`consultedHoldV1`), (3) the lane's root, the policy form and the entry key match (file name and the `id` in its header); a rewritten entry is packed again and its older file removed. The offer reads the store when it runs, so the newest entry is offered. A job lost with its process is adopted by the next process of the machine; a lost offer costs one derivation elsewhere, never a wrong graph. Honest limit: the drain is per process, not one daemon per machine; jobs survive through the outbox, a detached offerer process was not built (open item 3).
- Layer files: unchanged format (see verdict 5).
- Roster test: `O🧪️tests/🧫️fixtures/🔣️.json` `semantic.declarationExports` gets the four names that exist in `O🟨️.mjs` and `O🟨️.d.mts` (`finishOnLoadedImplementationV1`, `forgetRoundReadsV1`, `loadedImplementationRecordedFactV1`, `observationDirectoryFactCountsV1`): `O🧪️tests/🟦️.ts` 69/0.

## 6. Open items, by expected gain
1. Head-entry packing (40 % of a large TypeScript owner, 24 % of `cargo-workspaces`): a process-wide memo of neutralized rows keyed by row identity needs `consulted` recorded per hit (the memo is valid per host, key map and policy; a hit consults no key, so `packBundleV1` must return the keys the memoized rows consulted or the remembered documents lose their validity check); then the nine `cargo-workspaces` heads and the many heads of a project share their conversion.
2. A machine-store memo of the module walk (nodes keyed by file digest and resolution witness), so a fresh pool child does not walk the shared 1,900 files again (3 to 14 % of a marginal owner, 14 % of `cargo-workspaces`).
3. One detached offerer per machine (the outbox format is ready: `o/<entry key>.<pid>.json`); today the drain is per process and a killed process leaves its queue to the next one.
4. `dag-dag-rs` and `dag-plugin` end in `Native dependency has no build project owner: .../🧿️semio/🏅️standards/🔖️v1/🪆️subsets/🌊️flow/👥️member/📦️packages/🦀️rust` (candidates 4,857): a path in the tree names no owner; the owner run still produced its entries before the error. Not mine.
5. First owner of a machine (18 to 44 CPU s, 1.3 to 1.5 GB, up to 72k layer writes): layers in one file per import batch with a digest index would cut the writes; the census shows it must stay content-addressed across entries.
6. A clean cold-fleet measurement of the whole read needs an owner list of all 5,231 and a quiet host; this report extrapolates from 16.
