# O15 final component rustc: why LTO ran on one thread, and the fix

## Cause (verified live, read-only, pid 66999 = `semio_hub_energy_component` final, 61 min wall, 52 min CPU, RSS 0.7 GB)
- The jobserver was fine. The driver (`🧩️component-pass/🟦️.ts:529`, `createJobserverV1(tokens)`) makes the fifo; Cargo passes it on; the unit-cache wrapper (`UC/🎰️jobserver/🟦️.ts` `jobserverPlanV1`) leaves a fifo endpoint untouched (a private 3-token pool only when `SEMIO_COMPILER_PARALLELISM=1`; here it is 4); `semio-build-scheduler` execs rustc with the inherited env. `ps eww`: rustc has `CARGO_MAKEFLAGS=-j --jobserver-fds=fifo:…/jobserver.fifo --jobserver-auth=fifo:…`, `MAKEFLAGS=-j4 --jobserver-auth=fifo:…`; `lsof`: fd 3/4 = that fifo. SEMIO_COMPILER_PARALLELISM=4, SEMIO_UNIT_CACHE_SLOTS=10, SEMIO_BUILD_BROKER set (the broker only admits/charges whole units, it never sees codegen threads or tokens).
- The cause is a rustc flag. `ps -o command` of rustc ends with `-Z threads=1 ... -Z no-parallel-backend`. `semio-build-scheduler` appends it to EVERY `cdylib` final whenever a grant exists: `🎟️admission/🦀️.rs` `serial_backend` (line ~462, called at line ~574 as `serial_backend(bounded, tokens)`), added to bound memory ("peak = front end plus one module"). With `-Z no-parallel-backend` rustc runs codegen and ThinLTO work items inline and never asks the jobserver for a token. That is why writing 6 tokens into the fifo changed nothing, and why `sample` showed `lto cgu.NN` workers taking turns (1528+431+38 of 1996 samples = one thread) while the main thread waited in `do_thin_lto`. (`-Z threads=1` is only the front end, `frontend_tokens` in the same file; not the cause.)
- Key effects: none. The flag is added at the process that starts rustc, after the unit-cache key is computed. The key uses `rustc -vV` through the wrapper chain plus normalized args (`UC/🔏️key/🟦️.ts:223` toolchainIdentityV1); the scheduler binary's digest is not part of it (only its path names a memo file), so a rebuilt scheduler cannot change a unit key.
- Same flag is mirrored for remote actions: `…/🌐️remote-execution/🚀️offload/📜️action/🟦️.ts:37` (`offloadSerialArgumentsV1`); untouched here (open item: size by the worker's cores).

## Fix (landed in main)
`serial_backend` now adds `-Z no-parallel-backend` only when the grant is exactly ONE job (`tokens == Some(1)`: rustc has no token beside its implicit slot and the starved private pool would invent three). With 2+ granted cores the flag is absent and rustc's codegen/ThinLTO workers acquire tokens from the real jobserver. Accounting = the jobserver itself, one grant for units and intra-rustc threads: 1 unit running of 4 granted cores -> 3 tokens free -> up to 4 codegen threads; 4 units running -> 0 extra. Memory is bounded by the same grant (at most `tokens` modules in flight); front end stays 1 thread.
Files (main, sha256 12): `🎟️admission/🦀️.rs` ef2d07e2fac6 -> 416728658316 (docstring, condition, unit test `serializes_the_back_end_of_a_one_job_cdylib_final`); `🧪️tests/🧵️frontend-threads/🔣️.json` b41b52075be4 -> 23c96ec90997 (cdylib tokens 8/8 no flag; new `cdylib-one-job`, `cdylib-two-jobs`); `🐍️.py` 257b25e19e5c -> eddb7e72b815 (oracle); `🟦️.ts` 4a8b61cac72f -> 8f97116eedb4 (shared scheduler build under `SEMIO_TEST_ARTIFACT_DIR`, which the old test lacked: it failed on compiler ingress here before this change; new real-rustc test).
Tests: `repo test-file …/🧵️frontend-threads/🟦️.ts`: 4 pass / 0 fail (59 expects, 25 s), including the new real-rustc test: 32-module cdylib, `lto=thin`, `codegen-units=16`, fifo with 3 tokens, via the scheduler: grant 4 -> CPU/wall > 1.25, grant 1 -> < 1.25 and lower. Prototype numbers (load 27 on 10 cores): parallel 9.8 s wall / 16.3 s CPU (1.66), serial flag 20.5 s wall / 15.7 s CPU (0.77). Not run: the Rust `cargo test` unit tests of the wrapper (ingress refuses raw cargo); the scheduler compiled with the change inside the test.
