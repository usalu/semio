## 1. Which path lost the 77 units
The events of O21's run A0 are gone with its scratch, so the path is established from the code plus what O21 recorded (`upload-deferred: down`, entries absent on the server, proof ended and scratch deleted minutes after the build).
- Offloaded results: the worker never publishes. The requester receives the result and goes through the same publish as a local compile (`UC📜️script.ts` ~:249-265: local publish, then `shareFleetUnitAwaitingV1` queues the spool job). No worker-side or result-side hole; there is exactly one publisher, the requester.
- Dropped by a counted reason: after U1 none of spool-full, 4-try upload-failed, 1 h expiry can fire for an outage (6 h age only). A0 ran U1 code (the wrapper is sealed from the tree at run time, U1 landed 08:5x, A0 ran 14:15).
- `upload-deferred: down` is a deferral, not a drop: the job stays in `fl/up`. It leaves the spool only by upload / refusal / age. So the 77 were still waiting in the scratch cache root's spool when the proof moved on (B started 7 min after A0 ended, with the server unreachable at load 60+) and the root was deleted with its worker. The only way a waiting job is lost in the code is therefore: the upload worker is not alive and nobody starts it again. The worker was a detached child that only the NEXT build in the same root restarts (`startUploaderV1` is called only when a unit is queued); a scratch/lane root that never builds again, a killed or crashed worker, a reboot, a build tree torn down: spool orphaned for good. That is the gap fixed here. Secondary defect found on the way: the "is a worker alive" test was heartbeat-mtime (10 s), so a killed worker blocked its own replacement for 10 s.
- Not a cause: pin/proof read-only (A0 ran `read-write`, upload on), sidecar handover (no sidecar is involved in the unit spool before this change).
Residual loss paths left (open): a job older than 6 h; `upload-entry-gone` if the local unit entry is evicted while the job waits (the local store GC does not know the spool; no case observed).

## 2. Fix (root: the machine's long-lived sidecar drains, not a child of the build)
- NEW `UC🛰️fleet/📮️registry/🟦️.ts`: every queued job registers its cache root in `<host CAS root>/unit-spools/<sha256 root>.json` (identity `endpoint|generation|token hash` + the `SEMIO_*`/host environment, never a name matching TOKEN|SECRET|PASSWORD|CREDENTIAL|API_KEY|PRIVATE); rewritten on identity change or every 10 min.
- NEW sidecar role `spool` (`SC📮️spool/🟦️.ts`, started as supervised child of the agent exactly like `ready`/`pool`, own closure, `SEMIO_SPOOL=off` disables, priority class standard): every 5 s `sweepSpoolsV1` looks at each registered root; a vanished root or one empty for 1 h is forgotten; a root with waiting jobs and no live worker gets a detached upload worker (a restart of the sidecar never interrupts an upload). A spool queued under a token is drained only by a process that names the same token (identity must match), otherwise counted `skipped`.
- `startUploaderV1` returns whether it spawned, registers the root, and decides liveness by the lock holder (`claimHeldV1`, pid based) instead of heartbeat age. `enqueueUploadV1` is idempotent per key (a unit queued twice is one job: exactly once in the spool; the server write is once because the lock allows one worker per root).
- Schema: fleet `uploader.sweepMilliseconds 5000`, `registryRefreshMilliseconds 600000`, `registryRetentionMilliseconds 3600000`, `layout.spoolRegistry`; priority schema role `spool`; roles list of the priority test.
- The build still starts its own detached worker (fast path, and the only drainer on machines without a fleet agent); both use the same lock.
