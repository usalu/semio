## 1. The 16:48 out-of-memory error of the whole read
- Log: `.cache/f/graph-server/read.1795448900859.log` (4,029 lines; the read of runner 11559, rotated at 16:48). It reached `owners 128 of 128 done: 91 present, 22 fetched, 15 inferred` at 4,370 s, then `all project results are in, storing 455 project fragments` at 4,880 s, then the heavy child grew `3.1 -> 5.3 -> 11.3 GB` (heap census: strings 5.7 M -> 22.5 M, objects 2 M -> 16 M, external 1.2 -> 4.7 GB) in about 110 s and died with `Out of memory (reference 534390f9)`. It never printed the `indexing` line, so it was not the patch step that E54 fixed.
- What grew: `createBuildJournalV1().wave` (`G/🕰️generations/🔖️journal/🟨️.mjs`). At the end of every wave that has more waves to follow, the build writes the rows of all upserts and appends of the wave to the journal. `rowsOf(list)` turned every log-backed list into an array of row objects, `encodeJournalRowsV1` made one JSON line per 4,096 rows, joined all lines into one string and `Buffer.from` copied it: the rows of all returned owners plus the edge-only owners, held as objects, strings and one buffer at once (about 4.5 times the bytes written; measured below). The owner count does not bound it; the rows per wave do.
- Fix: the wave is written part by part. Each owner's list is read in batches (`list.batches()`), the lines go to a part file of at most `partBytes` = 8 MiB (`key.<n>.rows`, n = position in `carry.files`), each part is written and dropped; the header lists all parts (the schema already allowed a list of rows files). Resume (`reconcileWaves`) re-reads the parts for its second pass instead of retaining all decoded entries.
- Regression test `G/🕰️generations/🧪️tests/🔖️journal-memory/🟦️.ts` (child process, log-backed lists of 400 and 1,600 owners x 1,000 rows, half upserts, half appends, real file port): parts are at most 16 MiB, every owner round-trips with exactly its rows, the resident set added is below 0.8 x the bytes written and does not grow with the owners. Measured: new code 171 MiB added for a 281 MiB journal (1,600 owners); old code (HEAD copy) 313 MiB added for a 70 MiB journal (400 owners, 4.5 x), 82 MiB at 100 owners.
- Not proven live: the running read (started 16:53:46) loaded the old journal code; it is in wave 1 (81 of 132 owners at 17:15) and will reach this step with the old code. I did not restart anything (preamble). The next read loads the fix. If this read dies again at about 5,000 s with the same census, that is this bug, not a new one.

## 3. g1-m05 `unshareable`
- Meaning (`G/../🪪️graph-state/📦️project-records/🟦️.ts`, `documentsOf` -> `neutralRecordV1` -> `neutralTextV1`): the finished record could not be turned into the platform-neutral form. On a Windows checkout (`C:\semio`) the neutral form maps the root spelled with forward slashes (the way the inference writes commands) to the root token; a text that still holds the root with backslashes (or doubled backslashes) in free text is refused by design (`UnportableV1 "root spelled with backslashes"`, test `🪟️windows-spelling`). The record is then neither published nor taken. Path rows themselves (backslash separators) are converted correctly; the exact free texts that trip it on m05 are not known (the pool never said, only `failures.unshareable = 515`).
- Harm found: the refusal was `deterministic`, so `fail()` of the pool driver wrote a failure note per owner to the fleet ("leave it to the machine that runs the wave"): 515 notes made by a machine-local spelling. Fixed: `unshareable` is never deterministic, and the refusal text now carries an excerpt of the offending text (`root spelled with backslashes: "...C:\semio\libs..."`), so the next run shows the real shape in `pool.json` (`lastError`).
- Stop burning claims: `ownerPoolSharelessStepV1` (`🧮️lifecycle`): after `unshareableLimit` = 3 `unshareable` failures in a row without a published record in between, the pool claims nothing for `unshareablePauseMilliseconds` = 10 min (children drained, reason `unshareable` with EN+DE text in `pool.json`), then probes again; one more refusal pauses it again at once, one published record frees it.
- Tests: `🌍️two-platforms` new case with a Windows-shaped fixture (`C:\semio`, record whose command names `C:\semio\libs`): claim granted, publish false, code `unshareable`, not deterministic, text names the spelling, a second Windows claim of the same owner is free and publishes (11 pass); `🧮️lifecycle/🚫️unshareable` 4 pass.
- Not done: converting free-text backslash spellings into the token (a design decision: "refused, not published raw" is a tested law). Once the excerpt shows which texts occur, the right fix is probably to emit them with forward slashes at the source.
