## Verdict
1. A cold TypeScript owner is not a walk problem. Profiles (section 1): median owner `canvas-react-renderer` (23.7 CPU s): import walk 34 %, offer packing 19 %, Wasm compile index 6.5 %, store save 6 %; heavy owner `component-deployment-contract` (89 CPU s, 3.07 GB): offer packing 39 % (canonical row order 12.6 %, neutral rows 10.2 %, install/generation rows 13.7 %), brotli 9.6 %, walk 9.4 %, stamps 6.7 %, gc 4.9 %; first owner `course-rs` on an empty machine and fleet (58.4 CPU s, 1.8 GB): offer packing 36.7 %, walk 12.9 %, layer writes 6.5 %, stamps 5.7 %, gc 5.1 %.
2. Walk evidence that decided item 2: in ONE process, `canvas-react-renderer` built 4,955 walk nodes, the next owner `course-react` 5,090 nodes of which 7 were new, and still cost 21.8 CPU s (canvas 23.2 s). The nodes are already shared in-process by `cache.walkNodes`; what a second owner pays is the per-entry work over those nodes (pack, stamp, save), not module parsing (which the machine analysis store `sa/` already memoizes per content). A cross-process module-walk memo can only save the node build of the first owner of a fresh process (2,805 new nodes, about 8 CPU s at load 60). It was NOT built (reasons and design in section 4).
3. Landed: (a) a process-wide memo of packed layers in the offer (`PT🟦️.ts` `layerPackMemoV1`): each layer is converted to the neutral form and ordered canonically once per process for all offered entries, valid only while the key map answers the closure keys the layer asked as before; heavy owner: packing 39 % -> 13.6 % of the profile, peak RSS 3.07 -> 1.84 GB; (b) Wasm compile index: the owner of each output is found by walking up the path through a table of owner roots instead of testing all 4,869 owners per output: 340 ms -> 33 ms CPU per index on the real registry (same index, checked equal), every fresh process pays it; (c) cargo resolution receipts: a staged pool/farm child reads through to the dataset's `rr/` receipts (2,813 on the coordinator) that the parent adopted, so a fresh child derives and writes 0 receipts for unchanged crates (GR18: 15 % of a warm first owner); (d) a verification stamp states each path once (calm check and tuple from the same stat; was two stats per path), the stamp being the top term (15 %) of the heavy owner after (a).
4. `dag-dag-rs` / `dag-plugin` "Native dependency has no build project owner": a probe artifact of GR16-GR19, not a registration or lookup defect. The probe reused a session copied at 09:36 whose registry (4,851 owners) predates 18 new `👥️member` crates added by peers at 09:24 (`✏️s/🔌️plugins/🗄️stdio/🗿️artifacts/🧿️semio/Cargo.toml` members); the live session of 17:14 holds 4,869 owners and those 18 roots, and with it `dag-plugin` ran without the error (m1 pass). In production the error is loud and handled: `B🕸️graph/📥️inference/🧬️schema/🔣️.json` `OwnerRegistryWorkerFailures` lists this code and prefix, so the farm stops the wave and restarts it with the current registry (`project-farm` `forwardOwnerRegistryFailure`, `project-nodes` `stopRegistryWave`). The entries produced before the error are closure entries keyed by recipe and verified by their rows, so they are valid and reusable; no silent failure. Side finding (not changed): the head's `registryDigest` is the digest of `catalogProviders` only (`project-nodes/🟨️.mjs:653`), so two wave heads with different owner sets carry the same digest; validity rests on the rows of each record.
5. Measured after (section 2), honest: the host and the tree moved under every pass (peers edited the shared core, my own observation landing at 18:24 staled every entry once), so per-owner CPU is not comparable 1:1 with GR19 (GR19 ran at load 20 to 60 on a quieter tree). Owners that were fully stamped in the warm pass: 2.3 to 2.6 CPU s, 220 to 340 MB (compiler-syntax-ecma-ts, course, dag-dag, draw-js, 2d-trace-rs); marginal Rust owners 3.3 to 3.8 s cold. Targets NOT met: whole cold read under 5 CPU-hours, no owner above 10 CPU s / 1 GB (section 3).

## 3. Extrapolation of the whole read (5,231 owners, 16 GB worker under a ~5 GB grant), estimate
From the medians above (not from a whole read): cold fleet: Rust 2,600 x 4 s (marginal 3.3 to 3.8 s; tail `dag-dag-rs` 15.6 s) + other 2,631 x 23 s (median of the 10 TypeScript/project owners, cold, this load) = 10.4 k + 60.5 k = 71 k CPU s = 19.7 CPU h; adopting (warm fleet): Rust 2,600 x 2.6 s + other 2,631 x 2.5 s for unmoved owners = 13.3 k s = 3.7 CPU h (warm floor), up to about 6 CPU h with the stale tail seen here. One 16 GB worker, 5 children of under 1 GB (the median owners are 0.25 to 1 GB; cad-js 2.2 to 2.5 GB and cargo-workspaces 1.9 GB need 2 to 3 slots of the grant): cold about 4 h CPU-bound, adopting 45 to 70 min. Target "under 5 CPU-hours cold" is NOT reached; it is reached only by the adopting case. The cold figure is dominated by the TypeScript/project half and by the shared core moving under the read (every core edit stales every entry once).

## 4. What changed (file:line at landing time; sha256 in `T/landings.md`)
- `PT🟦️.ts:173` `RowMemoV1` gains `asked` (closure keys a row's conversion asked, with the answers); `neutralRowsV1` re-uses a remembered row only while the key map answers its keys as before and asks them again, so the caller's `consulted` stays complete; `LayerPackMemoV1`/`layerPackMemoV1` (per host and policy, bounded by `packedLayerRows`, starts empty past the bound) and `packedLayerRowsV1`; `packBundleV1(input, host, keys, policy, layerMemo?)`. The document is byte-identical with or without the memo (law). `EL🟦️.ts` creates one memo per lane; `EL🧬️schema/🔣️.json` `packedLayerRows` 1,048,576 (EN+DE description; the form `closure-entry-v1` is unchanged).
- `B🕸️graph/📥️inference/🔎️owner-discovery/🕸️wasm-outputs/🟦️.ts` `wasmCompileOutputIndexV1`: `byRoot` table of resolved owner roots and `ownerOf` ancestor walk replace `[...owners].filter(within).sort()[0]` per output (quadratic in owners x outputs). Equal index on the real registry (30 outputs), 10x less CPU.
- `B📥️inputs/🦀️resolution/💾️receipt/🟨️.mjs` `createCargoReceiptWriterV1(directory, publish, archive?)`: reads own receipts first, then the archive; writes only to its own directory. `B📥️inputs/🟨️.mjs` `warmCargoResolutionV1` passes `scripts.context.cargoReceiptArchive`; `B🕸️graph/📥️inference/📦️project-nodes/🟨️.mjs` `createProjectInferenceEnvironmentV1` sets it to the dataset directory (`dirname` of the analysis store `sa/`, where `rr/` lives beside `ce/` and `sa/`). Soundness: a receipt is used only when the digests it records still hold (`holds(context, stored.reads)`), wherever it was read.
- `B👁️observation/🟨️.mjs` `observationWitnessV1`: one `statSync` per path gives both the calm check (mtime and ctime before `since - RACY_MS`) and the kept tuple; `witnessCalmV1` removed; docstring states the rule. Same refusals as before (the tuple is now taken at the same instant as the calm check instead of a moment later, which can only make a later check fail, never pass wrongly).
- Not built, with reasons: (1) the machine-store module-walk memo (task item 2): evidence in verdict 2; a sound version must persist each node's rows and nested layers (the Wasm index layer of 6,000 rows is shared by many nodes), key it by the walk key and the file digest, and replace the row probes by a verified-once witness per node plus per shared layer; it saves only the first owner of a fresh process (about 8 CPU s of 23 at this load). (2) Persisting the Wasm index across processes (task item 3): after the ancestor lookup the remaining cost is the observed read of 1,642 manifests (field rows); persisting it needs a "witnessed computation" entry point in the observation module that accepts stored rows without probing them in the round, which is a change of the core's validation contract; not done. (3) Cross-entry sharing of witness stats (nine heads of `cargo-workspaces` stat the same paths nine times): safe by the argument in item 3(d) but needs a scope (pass) the stamp call does not have; not done.

## 6. Open items, by expected gain
1. The shared core moves under every read: in these passes 11 to 17 entries per large owner went stale between passes. GR10 option 1 (walk boundary at view-pruned prefixes) and the take-time re-ask (GR10 4.3) decide the cold whole read more than any per-owner term now.
2. Stamp witnesses (15.6 % of the heavy owner after the pack memo): per-row visit work (`JSON.stringify` of every fact) and per-entry stats of the same paths; share both per pass across the entries of one owner (the nine `cargo-workspaces` heads).
3. Brotli of offered documents (9 % heavy owner): documents of one owner share most layers; compress at a lower quality for the fleet transfer or pack layers once as content-addressed blobs.
4. Persisted Wasm index (observed manifest reads) and the module-walk memo, as designed in section 4; both only for the first owner of a fresh process.
5. `tsconfig.json` read about 2,350 times per owner process: memo per process keyed by file stamp instead of per walk host.
6. The probe should always copy the newest live wave session (`GR20/run.sh` uses `$SP/gr20/wave`, copied from the live 17:14 wave); GR16-GR19 numbers for `dag-dag-rs`/`dag-plugin` include work of a run that ended in the stale-session error.
