## What it hot-loads (8 files, all imported per wrapper call)
1. `🚀️offload/🔌️client/🟦️.ts` (the 12:05:47 defect): the old ride-through counted its 20 s budget from the FIRST submission, so a unit that had run longer than 20 s when the scheduler restarted got no ride-through at all (`14 Call closed without status` at once, then a local compile of a 20-30 minute final). Now `executeOffloadV1` itself rides through: a lost call (connection refused or reset, stream ended without an answer) is retried with jittered back-off 0.25 s doubling to 2 s, as a `WaitExecution` by the operation's name; the outage budget (`rideThroughMilliseconds`: 60 s, linked units at least `worker.outage.seconds` = 600 s) counts from the first lost call and is reset by every row heard; an operation the restarted scheduler does not know (`NOT_FOUND`, up to three times in a row) is submitted again (the scheduler joins the identical action in flight, restores it from its journal, or answers a finished one from the action cache); the unit deadline (counted from the first EXECUTING) and the overall wait keep running through the outage; the phase timers are paused during each back-off. `executeOffloadRidingThroughV1` is removed (one mechanism).
2. `🚀️offload/🟦️.ts`: both call sites use `executeOffloadV1` with `rideThroughMilliseconds`; a remote non-zero exit goes through the classifier: environmental failures decline with reason `remote-failed-local-redo` and `<class> on <worker>, exit N: <stderr head>` (the unit compiles here once; the event log counts them), ordinary compiler diagnostics stay the build's verdict. Plus the CAS6 client half (`patientUpload`, `void built.release()` in both `finally` blocks).
3. `🚀️offload/🩺️failure/🟦️.ts` + NEW `🩺️failure/🧬️schema/🔣️.json`: the classifier and its schema'd list (codes that name a missing input stay `incomplete-inputs`; classes `missing-crate`, `unreadable`, `linker`, `crash`, `disk`, `no-diagnostic`, each with its patterns).
