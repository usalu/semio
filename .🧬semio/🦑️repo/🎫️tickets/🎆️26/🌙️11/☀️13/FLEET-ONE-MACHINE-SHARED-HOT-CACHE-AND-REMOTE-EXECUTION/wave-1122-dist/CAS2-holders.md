# CAS2: unit-cache roots are registered reference holders of the host CAS (2026-11-23)

## Root cause (verified in code)
The host CAS collector (`🗄️cas/🧹️collector`) protects only pinned digests (pin files of live pids), leased transient inputs, hard-linked objects and objects younger than `minAgeMs` (10 min). A unit-cache entry (`<root>/e|r/<2>/<key>/*.json`, naming outputs/stdout/stderr digests) pinned nothing, so ANY root's blobs (main checkout and `~/.sinc/<name>` clones alike) were plain LRU candidates after 10 min. The main checkout was not protected either: `reclaimCasObjectsV1` is not a protection, it is only the retirement path (supersession) that offers blobs of entries it removed. CAS1's 2 GiB incremental steps + R3's unpinning made the hourly turnover (27 to 38 GB/h) take the oldest blobs; `lookupUnitV1` then saw `lostObjectV1` -> local miss, `pruneEntriesV1` deleted the entry (the 549/204 `entries` records in `y/evictions.jsonl`) and the fleet tier had evicted too -> "0 reused", compiled again. G8 (B1): `pruneEntriesV1` `rmSync(<root>/o)` is a no-op (nothing writes `o`; objects are in the host CAS, spill is under `k`/temporary); removed the dead line anyway. It never harmed.

## Design (schema first: `🗄️cas/🧬️schema/🔣️.json` `Holder`, policy `holderTtlMs` 24 h, `holderRenewMs` 15 min, `holderCacheMs` 30 s)
1. Registration: `holdHostObjectsV1(root)` (unit-cache `💾️store`) writes `~/.cache/semio/cas/v1/h/<kind>-<sha16(root)>.json` {root, `indexes` [{directory, `references`: `outputs.*.sha256`, `stdout`, `stderr`}], evictionLog, renewedAt, expiresAt}. Called from `writeEntryV1`, `writeBuildRunV1` and every local hit of `lookupUnitV1`/`lookupBuildRunV1`; throttled in-process to one write per 15 min. CAS stays domain-neutral: it knows only "JSON files under these directories name digests at these dotted paths".
2. Scaling: no digest list is written anywhere. The collector reads each live holder's entry files sequentially (one open file at a time, `readCasHeldV1`, typed Map digest -> holder), once at scan start and once before the evict pass; `reclaimCasObjectsV1` uses a 30 s cache (far below `minAgeMs`: an entry published later has touched its objects). Main 963 entries, clone 1196 entries, ~8 MB each: milliseconds. A holder expires after 24 h without renewal or when its root vanished (record removed by the next reader).
3. Collection order under the cap: (a) expired transient inputs and unreferenced objects, LRU (existing planner, held objects are counted but protected); (b) only if the planner still has a shortfall: `planCasHolderEvictionV1` (pure, `🫂️holders/🧮️plan.ts`) takes least recently used ENTRIES (access = newest access of their objects) whose removal frees an object nobody else (no remaining entry, pin, lease, hard link, min-age) keeps, repeated until the need is met; entry file unlinked first, then `reclaimCasObjectsV1` with a fresh held set removes the freed objects. Each holder's own `evictions.jsonl` gets `{capacity:<entries>,capacityBytes,reason:"capacity"}` (so `readEvictionsV1` shows kind `capacity`); the collection result carries `holders {holders,entries,heldBlobs,heldBytes,evictedEntries,evictedBlobs,freedBytes,reason:"capacity"}`; `formatCasCollectionV1` prints it (EN+DE). Dry run only counts. Fleet-published copies stay governed by the server bound (R3), unchanged.
4. Reporting: `repo cache cas status [--json]` lists every holder (pin holders = cache server live set/derived nodes, each unit-cache root with entries/objects/GiB, transient inputs) plus referenced vs unreferenced GiB (`holders`, `referencedBytes`, `unreferencedBytes`).
5. Coherence: unit-cache entries have no byte budget of their own (the `unitShare` of `gc` governs build unit directories, not CAS bytes); the CAS cap is the single byte bound and the capacity stage evicts whole entries, so `lostObject` pruning no longer finds half-evicted entries (it only meets blobs removed by older collectors or by hand).

## Activation (nothing restarted)
- Collector side (evicts and protects): every process that runs `collectCasV1` / `reclaimCasObjectsV1`: the cache SIDECAR (6094, restart at its next natural restart), any `repo cache gc`/`cas gc`, builds' guard background collections. Until they run the new code the old collector still ignores holders (it cannot read `v1/h`).
- Registration side: every build wrapper/unit-cache process (cargo wrapper, offload, play clone) registers on its first entry write/hit with the NEW store code. A clone on old code registers nothing and stays unprotected even against a new collector, so the pinned clone must sync BEFORE its next build: 
  `🏗️build/🗄️cas/🫂️holders/🟦️.ts`, `🫂️holders/🧮️plan.ts`, `🧹️collector/🟦️.ts`, `🪦️reclaim/🟦️.ts`, `⌨️command/🟦️.ts`, `🧬️schema/🔣️.json`, `🧬️schema/🟦️.ts` (all under `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/`), `⚡️caching/🦀️cargo/🗃️unit-cache/💾️store/🟦️.ts`, `⚡️caching/🦀️cargo/🗃️unit-cache/🧹️gc/🪢️supersession/🟦️.ts`. A running cargo wrapper keeps old code until its next invocation (each rustc call is a fresh process, so effectively the next build step).
- Order: sync clone first (registration), restart sidecar second (protection). After that `repo cache cas status` must show one `unit-cache` row per root. Existing entries of the play clone whose blobs were already collected stay lost (compile once more); everything published after registration survives the hourly turnover.

## Open
- Not measured live (no CAS touched, play gate respected): the bytes the roots' entries hold. Expect small (the clone's entries name a few thousand objects); if the cap is smaller than live-entry bytes the capacity stage evicts LRU entries, visible as `capacity` in each root's `evictions.jsonl`.
- Holder TTL 24 h: a clone idle longer loses protection (its entries age out by LRU like any candidate).
