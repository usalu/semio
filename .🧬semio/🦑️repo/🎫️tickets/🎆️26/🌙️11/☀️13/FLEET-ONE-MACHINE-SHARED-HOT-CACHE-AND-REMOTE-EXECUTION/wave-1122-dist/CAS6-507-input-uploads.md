## 2. Fixes
(a) Cap follows free room (schema `Policy.sizing.roles[].freePercent`, cache-host 70; ceiling `capBytes` 96 -> 256 GiB): `casEffectiveCapBytesV1` wants max(share, floor, 70 % of room), room = store + free - headroom (above the partition high watermark), re-evaluated on every admission, blob-bound and status call. Live inputs: cap about 130 GiB, blob bound (50 %) about 65 GiB. It shrinks as free room shrinks. Vectors `📋️capacity` regenerated, Python oracle extended.
(b) Transient class: PUT with `x-semio-lease: input[:<action>]` is a transient write: `guard.admit(.., transient)` never refuses for the cap (only for a critical partition). Leases are per action (`h`) with a timestamp (`a`); `DELETE /<instance>/cas/<digest>` with the lease header ends that action's lease to `transientGraceMs` (60 s); blobs shared by another action stay leased. Client: `RemoteExecutionContentV1.release`, `input:<action digest>` intent, released right after the action finished (rustc and command offload). Collector order unchanged (expired transient first).
(c) 507 body names the bound and holders: "Insufficient storage: The store holds X GiB of its Y GiB cap in force (role, Z GiB free); largest holders: ... / (DE)" (holder scan in the background, at most once a minute). Client: `retryRemoteExecutionContentOutageV1` retries 507 and 5xx/unreachable (not 4xx) with doubling pause; offload uploads use it for at most 30 s (`patientUpload`) before the local fallback. NOTE: the play clone runs a sealed copy, so only the server side takes effect there; the client patch reaches the clone when its files are synced (files: `🌐️remote-execution/🗄️content/🟦️.ts`, `🚀️offload/🟦️.ts`, `🚀️offload/📜️action/🟦️.ts`).
(d) Restart handover exists (launcher spawns a successor with `SEMIO_SIDECAR_SUCCESSOR=1`, it binds with reusePort, then the old one drains) but every second restart was a gap: the promoted successor kept the env flag, so its own restart skipped the handover (log: 02:03 handover, 02:33 gap 5 s, 03:33 gap 14 s, 08:16 gap 27 s, 09:43 handover). Fixed: `settleSidecarSuccessorV1` clears the flag when it listens, `sidecarHandsOverV1` decides. The live process 9286 (10:43) still carries the flag, so the restart that brings this code is one last gap; clients ride it only with the new client code.
