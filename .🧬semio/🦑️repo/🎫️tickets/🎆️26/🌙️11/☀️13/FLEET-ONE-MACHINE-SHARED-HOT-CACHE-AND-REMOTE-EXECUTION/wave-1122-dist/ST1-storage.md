# ST1 storage: rust image detached, graph image full (2026-11-24 03:20 to 04:05)

## A. Rust image `.cache/b/r` (repaired, content intact)
- Symptom: `fixed.dmg` unattached; `repo` openers moved the stray entries of `m` to `m-stranded-1795485957802` (what `quarantineStrandedNativeRootEntriesV1` does so an image can mount) and then `diskutil image attach --mountPoint` failed with "Failed to mount the volume".
- Root cause of the failed attach (reproduced on a throwaway 600 MB image): the container held a second APFS volume `semio-trim`, the scratch volume of the in-place kick (`🍎️image/👟️kick`, landed 2026-11-23 23:03 local; sidecars restarted onto it at 00:04). A kill between `ensure` and `dispose` leaves it, and `diskutil image attach --mountPoint` works only for an image with ONE mountable entity (the kick's own schema text says so). Offline reclaim at ~00:14 (image mtime) then detached the image, its attach failed on the sibling, and the cleanup retry failed the same way, so the image stayed detached for 3 h. I could not read `log show` (no entries); the order is from the sidecar logs plus the artifacts, so the exact 00:14 trigger is inferred, the sibling volume is proven.
- Repair done: `diskutil image attach --noMount` -> `diskutil apfs deleteVolume disk15s2` (20 KB `semio-trim`, empty) -> detach -> `diskutil image attach --nobrowse --mountOptions owners --mountPoint .cache/b/r/m` (same arguments as `nativeImageAttachArgumentsV1`). The volume `semio` (3.3 GiB: cargo home, compiler store, `u` unit cache, configuration, published, ...) mounted with all its content (newest mtime 11-23 18:58). `image.json` needed no change. The stranded directory held only P4's `cargo/home/registry/CACHEDIR.TAG` skeleton (4 KB, disposable build state; no cargo/rustc was running): deleted. P4's processes were not touched.
- Root-cause fixes (all tested):
  1. `attachNativeImageV1` (new member `🍎️image/🔗️attach`): on an attach failure it deletes leftover `semio-trim` volumes of an UNMOUNTED image (a mounted image is never touched, a kick may be running), detaches what it attached, and attaches again; any other failure keeps its own error. Used by the opener (`🧹️cleanup/🎛️command` activate), the reclaim cycle attach and the doctor repair.
  2. A detached image is now an ERROR in `repo doctor` (`storage.image-detached`, `-blocking`), both with the automatic fix `repo doctor --fix --only=storage` (repair `storage-images` now attaches every detached image, not only while `node_modules` dangles). Oracle, fixtures and tests updated.
  3. Writers can no longer fall through silently: after a reclaim detach the plain mount directory becomes read-only (0555, `guardDetachedNativeImageMountV1`), so `mkdir -p m/cargo` fails with EACCES instead of writing to the host disk (P4's case); the next attach mounts over it unchanged.
  - Open: a SIGKILL between detach and the guard, a reboot, or images detached before this change keep the writable plain `m`; doctor reports them as errors but nothing blocks the writers. Routing every writer through a mount check (the cargo wrapper P4 used writes to `CARGO_HOME` under `m` directly) is a separate lane.

## B. Graph image `.cache/b/g` (freed 8.16 GiB: 0.2 -> 8.3 GiB free)
- Contents: `generations/j` 9.1 GiB, `inference` 6.3 GiB (4.6 GiB of it one closure-entry store `ce`), `derived-nodes` 0.8 GiB.
- Why retention missed it: `generations/j` holds BUILD JOURNALS (`<key>.<n>.rows` + `<key>.json`, ~3 GiB per interrupted generation build). A journal is cleared only by a build with the same key; the key contains the workspace membership, so every killed or superseded build left a journal nobody can ever resume (4 keys, 3 dead, 8.16 GiB). The graph reclaim (`repo cache gc --area=graph`) knew nothing about them: its optional-cache quota looked at 462 MiB of 1 GiB while the image was 100 % full.
- Fix: `graphStaleBuildJournalsV1` (graph reclaim, before everything else): keeps the newest journal and every journal written within `journalGraceMilliseconds` (1 h, schema `🧬️schema/🔣️.json`), retires the rest, rows first and header last, cancellable, dry run counts. Run live with `repo cache gc --area=graph`: "Removed 3 dead build journals of the generation store (8.16 GiB); 1 kept". The in-flight build's journal (163df..., 94 files, 01:41) and every record a running read holds were kept; the current generation was not touched.
- Why `--dry-run --area=graph` took 318 s: the time was `source.served` (the command waits for the served source under host load 50+ with two long reads running), not collection; the same command ran in 58 s a few minutes later.
- Open: `inference/selections/<scope>/ce` (4.6 GiB) is referenced by records and kept by design; with the journals bounded the graph image steady state is about 6.3 inference + 0.8 derived + 1 generation + at most 2 journal groups (~3 GiB each, scale with the workspace) = about 14.5 of 18 GiB. A CAS5-style per-role image size (graph partition 18 GiB -> 24 GiB) needs the elastic resize cycle on a live image; not done here to avoid touching the image under two running reads.
