## 1. Who held the lock and why nothing below the watermark was removed
- `v1/gc.lock` was held by pid 76726 (the cache sidecar of `repo service host run`), alive, 25-36 % CPU, RSS swinging 150 MB - 1 GB, heartbeat frozen for minutes. Not a leak: a collection that could not finish.
- Cause: the lease ledger `v1/x/*.jsonl` had grown to 246 MB (480 MB on disk, ~2.4 M lines, 17 segments, one writer segment of 76 MB). `readCasTransientsV1` re-parsed ALL of it, and the collector's evict pass re-read it at EVERY shard whenever the segment stamp changed (258 shards, writers append constantly) = hundreds of GB of JSON parsing per collection. Compaction (only after a finished collection, only segments idle 2 h) therefore never ran, which fed the growth: a loop. Collection was also gated on the 90 % cap watermark, so the 29-34 GiB "referenced by nobody" (expired inputs, 35 GiB/h inflow) waited for it.
- Fixes (cas `📌️pins`, `🧹️collector`, `🚦️guard`, schema): (a) incremental lease reader: per root, per segment cursor (inode, offset after the last complete line), a re-read costs only the new bytes; a rewritten/shrunk segment restarts the root. (b) Segments rotate at `Policy.transientSegmentBytes` (8 MiB). (c) Compaction takes segments idle two leases (1 h, was 2 h) and drops ended leases as well as lines of gone blobs. (d) Continuous sweep in the service tick (`guard.sweep`, `Policy.sweepEveryMs` 60 s, `sweepStepBytes` 4 GiB per step, again at once while a step freed >= 90 % of it): objects nobody references plus expired transient inputs, older than the in-flight grace (180 s), regardless of any watermark; never held, pinned, leased, linked. (e) A refused manual `gc` names the holder: "Another collector already runs on this cache store: process 76726 holds the lock, last progress N s ago ..." (EN+DE, `lockedBy` also in `--json`). The manual run already queued up to `lockWaitMs` (120 s) behind the holder.
- Tests: cas 60/0 (new: segments incremental/rotation/compaction, sweep in bounded steps with a pinned object kept: store 10 -> 7 -> 4 -> 2 -> 2 MiB, lockedBy EN+DE), holders 12/0, server admission 2/0. The existing "tick collects in small steps" test now passes `sweep:false` (it tested the watermark rule only).

## 2. Hard free-space reserve
- Schema `Policy.sizing.roles[]`: `reservePercent`, `reserveFloorBytes`; reserve = min(half the partition, max(percent of the partition, floor)). worker 4 % / 8 GiB, builder 6 % / 16 GiB, cache-host 8 % / 72 GiB. 926 GiB cache host: 8 % = 74.08 GiB (floor 72). Justification: a release build needs free disk above ~70 GiB (its sparse image can still claim 43 GiB; the host died at 96-98 % used = 19-37 GiB free), plus 2 GiB margin = 72 GiB floor; the percentage keeps the reserve proportional on larger disks (4 TB: 328 GiB); builder 16 GiB = one release's transient + safety on a 256 GiB disk, worker 8 GiB = transient inputs x2.
- cap in force = min(proportional cap, store + free - reserve), aligned down 256 MiB, never below `minimumCapBytes` (`casEffectiveCapBytesV1`; the old body is `casProportionalCapBytesV1`). Under pressure the cap falls below the store, so the collector frees expired inputs and unreferenced data first, then oldest unheld candidates, in the existing bounded steps (incremental: 2 GiB below the high watermark of the cap; the cap-high trigger fires about store/9 above the reserve, i.e. before it is touched). Held, pinned, leased, linked entries are never taken for the reserve: the policy handed to the collector carries `heldCapBytes` (the proportional cap) and the planner judges `capShortfallBytes` (the only stage that may evict held entries, CAS4 rule) against it.
- Admission: a write that would leave less than the reserve free is refused by the cache server after the bounded collection, transient inputs included (507 body: "...free-space reserve ..."; `CasCapRefusalV1.reserve`). `remoteCacheBlobBoundV1` (50 % of the cap in force) follows.
- Status: `repo cache cas status` prints the reserve and distance (or the BELOW text and what the store does), EN+DE, JSON `reserveBytes`/`reserveDistanceBytes`; fleet status `cas.reserve` fact and line.
- Tests: capacity vectors extended to 1156 rows (reserve rows: all roles x 3 sizes x free 2..115 GiB x store), independent Python oracle `🐍️capacity.py` equals TypeScript equals frozen; shrinking-free sequence (free 130 -> 30 GiB, store 90): cap never above store + free - reserve, monotone, below the store from free < 74.08; planner: heldCap keeps held shortfall 0 while the candidates (40 of 25 needed) go; guard: transient write refused with room 6000 MiB < reserve, admitted with room. cas 60/0, holders 12/0, server 10/0, admission 2/0, remote-cache main 27/0, host-capacity disk 8/0, fleet-status 26/0.
