# O14: component jobs planned from local memory AND fleet slots

`NB` = `🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🧩️component-pass/`. Snapshot = `/Users/ueli/.sinc/play` (read only; every patch was applied to copies).

## Cause (confirmed in the snapshot file)
`component-pass/🟦️.ts:515`: `componentJobs` was asked only when `fleetRemote > 0`, and `jobSlots = max(1, min(componentJobs?.jobs ?? 1, tokens + fleetRemote))`. Every job after the first held a light slot (no jobserver token, no memory charge) on the assumption that its units go to workers. With offload `never`, fleet down, or no worker that fits a final, `jobSlots` was 1: a strictly serial lane, even with 20 GB free.

## Change (key neutral, scheduling only)
1. `NB🧵️job-slots/🟦️.ts`
   - `admitLocalComponentJobV1`: one law for "may one more local job start": the first always; further ones only below `maximum` (cap 3 and local grant), readable memory, normal pressure, and `peak <= available + owned - floor - reserved` (owned = RSS the build's own compilers already hold, at most the reservation, added back so nothing is charged twice; reserved = sum of the running local jobs' predicted peaks).
   - `planLocalComponentJobsV1`: the same law as a plan (longest prefix of the next finals whose whole reservations fit above the floor); a test proves plan = number of starts the live law grants one after the other.
   - `planComponentJobSlotsV1`: combines BOTH resources into `{jobs, light, local}`: light = fleet jobs - 1 (as O10), local = min(wanted, `localJobsMaximum` 3, tokens), all bounded by `componentJobsMaximum`. A fleet that fills the cap leaves one local slot, so a build with workers behaves exactly as before. No fleet: local jobs only.
   - `runPassesInJobSlotsV1`: new option `local` (+ `signal`). Light slots fill first; a local job beyond the first holds a real reservation of its predicted peak (a `local` slot = a jobserver token for its cargo, plus the ledger entry), re-reads the memory before each start (not only at driver start), otherwise waits: progress line at start and every 60 s (EN / DE), woken by a settling job, a 5 s poll, `check` or `signal`. The first job always starts (progress never depends on a prediction). Without `local` the old schedule vectors are unchanged (existing 5 tests green).
   - `componentPassPeakMegabytesV1`: the reservation of a pass = the broker's own prediction per crate from the unit history (`predictPeakBytesV1`, headroom x p95 of the crate's recorded peaks); a final never recorded = headroom x p90 of the recorded finals of the profile (6144 MB bound below 3 recorded finals), so an unseen big final is not mistaken for the median one; a pass holds the largest `min(packages, tokens)` finals at once. History is re-read before each candidate, so finals that just finished locally teach the next start.
2. `NB🧵️job-slots/🧬️schema/🔣️.json`: policy `localJobsMaximum` 3, `localJobsPollMilliseconds` 5000, `localJobsProgressMilliseconds` 60000, `unmeasuredQuantile` 0.9; definitions `LocalJobReason`, `LocalJobsHost/Decision`, `LocalJobAdmitHost/Decision`, `ComponentJobSlotsHost/Decision`; texts EN+DE.
3. `NB🟦️.ts`: option `localJobs?` ({maximum, floorMegabytes, sample, peakMegabytes}; every default is live: `readCompileUnitsHostV1` for free memory and pressure, `broker.stats().actualRunningBytes` for owned, `admissionReserveBytesV1(admissionMemoryBytesV1())` for the floor = the broker's own machine reserve, unit history for peaks). The job count no longer needs `fleetRemote > 0`: `planComponentJobSlotsV1` runs always; with more than one local job a plan line `[component-jobs] component build: N component job(s) may hold a local reservation at once (...)` is logged. `driver-stages` is NOT touched, so O11 is not required.
   - Offload `never` / fleet down: `fleetJobs` = 1 -> light 0, local up to 3 from memory. Remote jobs keep the O10 behaviour (same light slots, same fleet jobserver).

## Guard against the lock cycle
Local jobs are at most `localJobsMaximum` = 3 and never more than the local grant; the total of all jobs stays under the authored `componentJobsMaximum` (24 in main, 6 in the snapshot); a fleet-saturated lane keeps its previous 1 local + light shape. All jobs still share one build dir exactly as before (the 12-cargo cycle was seen at 12, this adds at most 2).

## What to expect on the live play run (honest)
The floor is the broker's reserve (min(25 % of RAM, 6 GB) = 6 GB on this 32 GB host). Two finals overlap only while `available + owned - 6 GB - reserved >= second peak`. History knows 24 finals (median 1.2 GB, cad 6.5 GB, puzzle 5-6 GB); the other ~45 `semio_hub_*` finals are unmeasured and are reserved at about p90 x 1.15 (about 7 GB): such a final overlaps only with ~20 GB free. Small finals (editor, surface, node_graph, flow: 0.4-2.3 GB) and every final that has finished once locally overlap readily, and each local final that completes adds its own record, so the overlap grows as the run proceeds. Nothing exceeds the floor: the first job always runs, so no deadlock.
