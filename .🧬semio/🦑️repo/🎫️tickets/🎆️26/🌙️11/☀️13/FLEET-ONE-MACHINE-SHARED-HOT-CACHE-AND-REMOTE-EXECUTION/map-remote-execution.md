## 1. What the module implements

Files (25 total, all `🟦️.ts`-named except schema/fixture/python):
- `🟦️.ts`: shared types and helpers. Digest, platform properties, `remoteExecutionPlatformMatchesV1` (line ~67: every required property must be offered with the same value), `remoteExecutionHostPropertiesV1` (`Arch`, `OSFamily`; `darwin`->`macos`, `win32`->`windows`, `x64`->`amd64`).
- `🏃️entry/🟦️.ts`: a 7-line process entry that runs `workers` (used as a child process).
- `⌨️command/🟦️.ts`: CLI operations `serve` (line 91), `workers` (line 151), `status`. Options table at lines ~24-30.
- `🖥️server/🟦️.ts`: gRPC handlers for `Capabilities`, `Execution` (Execute, WaitExecution), `ActionCache`, `ContentAddressableStorage` (FindMissingBlobs, BatchUpdate/ReadBlobs, GetTree), `ByteStream` (Read/Write). Plus HTTP worker API: `POST /v1/workers`, `DELETE /v1/workers/{id}`, `POST .../poll?wait=`, `POST .../heartbeat`, `POST .../tasks/{id}/result`, `GET /status`, `GET /healthz`. Tokens: read, write, worker (bearer, constant-time compare). Refuses non-loopback listening without tokens.
- `🗓️scheduler/🟦️.ts`: in-memory scheduler, pure logic over a content store. Dedup by `instance|action-hash`, AC lookup (`prepare`, line 71), FIFO queue, `dispatch()` (line 185) hands the first queued operation whose platform matches a waiting worker with free slots. Leases, heartbeats, requeue on loss (`requeue`, line 178; max attempts from policy, default 3), sweep for timeouts and unmatched platforms (`sweep`, line 250; `unmatchedSeconds` default 120).
- `👷️worker/🟦️.ts`: worker agent. Registers, long-polls, executes actions in a per-task private root under `<dir>/work/<name>/<uuid>/root`, reports ActionResult. Blob cache `RemoteExecutionBlobCacheV1` (content-addressed, verified, LRU prune) under `<dir>/blobs`. `executeRemoteExecutionActionV1` (line 159) fetches Action, Command and input tree, materializes files (clone via `COPYFILE_FICLONE` when `materialize=clone`), runs the command through the sandbox, walks declared `output_paths`, uploads outputs to CAS, returns an ActionResult (stdout/stderr inline if <= `inlineOutputBytes`, else digests).
- `🔒️sandbox/🟦️.ts`: three strategies: `darwin-sandbox` (`/usr/bin/sandbox-exec` with a profile that denies network, denies file writes outside the root and denies reads under /Users, /Volumes, /private/tmp, /private/var/folders, /private/var/tmp except the root), `linux-sandbox` (bubblewrap: `--unshare-net`, `--unshare-pid`, `--ro-bind / /`, root bound writable, `--clearenv`), `isolated-root` (no confinement). `auto` falls back silently to `isolated-root` (line 77).
- `🗄️content/🟦️.ts`: `RemoteExecutionContentV1` interface plus `httpRemoteExecutionContentV1` (HTTP client for the repo's remote-cache server: `/<instance>/cas/<sha>`, `/<instance>/ac/<sha>`, bearer token, retries on 408/429/5xx).
- `📡️wire/`: `🚪️grpc` (own HTTP/2 gRPC server and client, status codes), `📦️protobuf` (own codec driven by `📋️messages/🔣️.json`, generated by `🐍️generator/🐍️.py` from Bazel's own protoc descriptors; the python generator is standard-library only), tests use `protobufjs` as an oracle (`📡️wire/🧪️tests/🟦️.ts` lines 3-4).
- `📖️texts/🔣️.json`: EN/DE message catalogue.
- Policy: `🔨️modules/📚️library/🏗️build/🔣️policy.json`, section `remoteExecution` (environment names `SEMIO_REMOTE_EXECUTION_{ENDPOINT,PLATFORM,INSTANCE,PROPERTIES,JOBS,SCHEDULER,WORKER_TOKEN}`; server defaults: grpc 8980, worker HTTP 8981, `localWorkers: 1`, `leaseSeconds: 30`, `maximumAttempts: 3`, `defaultActionSeconds: 3600`, `maximumQueued: 100000`; worker: `concurrency: 0` (= availableParallelism), `heartbeatSeconds: 5`, `pollSeconds: 20`, `directory: .🧬semio/🦑️repo/⚡️cache/remote-execution`, `materialize: clone`, `sandbox: auto`, `inlineOutputBytes: 4096`).

What an "action" is here: a standard REAPI `Action` (command digest, input root digest, timeout, optional platform), whose `Command` carries arguments, environment, output_paths, working_directory and platform. The module does not invent its own action format. Inputs: the client uploads the input tree to the CAS (the remote-cache server); the worker fetches it blob by blob into a private root. The worker does NOT read the shared NFS store and does NOT assume an identical worktree; everything needed must be in the CAS. Outputs: uploaded by the worker to the CAS, referenced by digest in the ActionResult, also cached in the AC on exit code 0 (`report`, scheduler line ~237+).

Gaps against REAPI as stated by the module itself: `output_files`/`output_directories` (REAPI 2.0) are refused (worker line 190); only `output_paths` (2.1) accepted. Capabilities advertise low 2.1, high 2.3 (server `GetCapabilities`).

## 3. Platform handling

- Matching: `remoteExecutionPlatformMatchesV1` (`🟦️.ts` line ~67). Required action platform properties must all be offered with equal value. Offered properties = `Arch` + `OSFamily` from `process.platform`/`process.arch` (`macos`/`windows`/linux name; `amd64` for x64, `arm64` otherwise) plus `SEMIO_REMOTE_EXECUTION_PROPERTIES` / `--properties`. Toolchain version, target triple, libc, cargo/rustc version are NOT modeled; they must be encoded by the client as extra properties, which nothing does today. (The Bazel path encodes its own `platform.properties` from its contract.)
- Unmatched actions fail after `unmatchedSeconds` (120 s) with code 9 (scheduler sweep, line ~258).
- Two macOS arm64 machines with different absolute worktree paths: the worker places every input tree in its own private root (`<dir>/work/<worker>/<uuid>/root`), so the cwd and input paths seen by the action are the private root, not the client's worktree. This is good for hermeticity, but any absolute path baked into the client's command line or into rustc dep-info, build script env, or `--remap-path-prefix`-less artifacts will point at the client's path. Nothing rewrites or remaps paths. The module has no rustc/cargo-specific logic (guess: a Bazel-style cargo rule would need `--remap-path-prefix` or relative paths; not verified in code).
- Proc-macros and build scripts: nothing special. They run as ordinary executables inside the input root. Executables are resolved with `resolveExecutable` against the PATH from the Command environment (worker line ~128). A proc-macro dylib needs the same host arch, which the platform properties must guarantee.
- Sandbox confinement by OS: darwin uses `sandbox-exec` (deprecated-looking but present; the profile denies reads under /Users, so host toolchains under /Users (e.g. `~/.cargo`, `~/Library/Caches/semio/runtimes/bun`) are unreadable unless materialized into the input root; guess on exact effect, from profile text only). Linux uses bwrap with `--ro-bind / /` (host read-only view). Windows only has `isolated-root` (no confinement).
- Network: every action runs with `network:false` (`👷️worker/🟦️.ts` line 202). No caller can request network. `cargo fetch` / crates.io or npm installs will fail unless deps are vendored into the input tree.

## 4. Scheduling

- Worker choice: FIFO over the queue; `dispatch()` (line 185) gives the first queued operation that matches the worker's properties, to the first waiting worker (in Map insertion order) that has a free slot. No load, no CPU, no memory, no affinity, no per-worker weight.
- Load awareness: none. Concurrency is a fixed number per worker (`concurrency`, default `availableParallelism()` when 0). Module does not import `🌡️host-capacity` (grep: no match in `🌐️remote-execution`).
- "Local first, offload under pressure": does not exist. Bazel with an endpoint set is remote-only for hermetic actions. Outside Bazel nothing offloads.
- Queueing: `maximumQueued` 100000; over the bound returns code 8.
- Cancellation: client abort; the scheduler keeps the operation for `lingerSeconds` (5 s) after the last subscriber leaves (`detach`, line ~103), then cancels; a running task is cancelled through the worker's poll/heartbeat answer (`cancel` list). Worker kills the process group (`killTree`, SIGKILL, line ~120).
- Progress: `serve` and `workers` print stage lines; Execute streams Operation snapshots (CACHE_CHECK, QUEUED, EXECUTING, COMPLETED) per REAPI.
- Timeouts: action timeout from `Action.timeout` capped at `defaultActionSeconds*4`; worker kills on timeout (code 4); scheduler sweep also expires EXECUTING tasks after timeout + lease.
- Retries: requeue (up to `maximumAttempts`, default 3) when a worker is lost (no heartbeat for `leaseSeconds`, 30 s; 3x while it waits on poll), when a worker abandons a task, when heartbeat no longer lists a task after the lease, or on worker-reported codes 10 and 14. Action failures with exit code != 0 are NOT retried (they are completed results).
- Worker death: `drop()` requeues the worker's running tasks; `deregister` on graceful stop.
- Dedup: identical in-flight actions share one operation (`execute`, `deduplicated` counter).
- Caveat: scheduler state is in memory only (`Map`s); restart loses queue and running state (no persistence code found).

## 6. Gaps: goal (offload cargo/rustc and nx from a saturated machine to idle fleet machines, share results)

- No client integration for cargo/rustc. `repo cargo` path (`🏃️process/🦀️cargo`) is local only. Would need: REAPI Action generation for each rustc invocation (inputs = crate source closure + toolchain, outputs = rlib/rmeta/dep-info), path normalization (`--remap-path-prefix`, relative paths, `-C` flags), proc-macro and build-script handling, and a cross-machine toolchain property.
- No client integration for nx. nx task graph has no remote executor hook in the repo's nx backend (`🔧️tools/🧶️nx/`); not investigated in depth (guess: needs a custom runner).
- Only the Bazel backend submits work, and only with an env var; default backend is nx.
- No load signal: no CPU, memory or pressure input to the scheduler; no "local first, offload when pressured" policy; no host-capacity integration (`🌡️host-capacity` exists in `🏗️build` but is unused by this module).
- Worker placement: static platform properties only; no toolchain-version property convention; a macOS arm64 worker with a different Xcode/CLT or Rust toolchain is indistinguishable unless the client adds properties.
- Absolute paths: private input root per task, no path remapping; cargo dep-info and env-dependent outputs may not be portable across machines (guess; needs test).
- Network denied for every action: cargo registry fetch and npm install cannot run remotely unless vendored.
- Sandbox asymmetry: darwin and linux confine; Windows does not (`isolated-root` only). `auto` silently downgrades to `isolated-root` when sandbox probes fail (`🔒️sandbox/🟦️.ts` line 77).
- Cross-OS: REAPI actions carry platform properties, so a Linux worker can take a Linux action; but a macOS action cannot run on Linux or Windows (different toolchains, sandboxes and binaries). Cross-OS offload is only for platform-independent actions (for example data generation or tests with self-contained binaries; guess).
- Scheduler state is in memory; restart loses queued and running work (no persistence found).
- Service provisioning: no launchd, systemd or Windows task definition for `repo remote-execution serve` or `workers`. Shared-worktree provisioning (`🥾️provision`) covers only replica, cache and relay.
- The shared-worktree relay (`tech.semio.fleet.relay`) is unrelated to execution. Do not confuse it with a remote executor.
- Test gaps: wire test needs `protobufjs` installed; command status test is stale on `apiVersions`; cluster and bazel integration tests not run here.
- Name collisions to watch: `🌐️remote-cache` (CAS and AC over HTTP, port 6090, currently running) vs `🌐️remote-execution` (REAPI executor, port 8980/8981, not running).
