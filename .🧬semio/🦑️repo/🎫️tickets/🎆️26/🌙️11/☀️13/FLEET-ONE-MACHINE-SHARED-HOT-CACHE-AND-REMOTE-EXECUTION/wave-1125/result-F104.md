# F104: heap profile that finds the holder of late-wave memory

## 1. What the three existing profiles hold (scratchpad `heap/heap-profile-{14256,56752,91577}.json`)
Each is a 3 KB summary: managed MB, nodes, edges, `totalBytes`, 12 classes (count, self bytes), 12 "retainers" (heavy nodes of the breadth-first retention tree: retained bytes, string count, path from the root). So they DO carry retainer info (a BFS tree, an upper bound of a dominator tree; shortest path charged), but only property names along ONE path, no grouping by holder, no counts per holder.
**Key finding: the snapshot reaches only a fraction of the "managed" figure.** `totalBytes` (reachable from the root after the snapshot's own GC) is 409 MB (managed 2995, 91577, wave 1), 515 MB (2997, 14256), 804 MB (2806, 56752). 73-86 % of the managed number is NOT reachable heap. `managed` = `heapUsed + external` (`bun:jsc` heapSize + extraMemorySize), sampled WITHOUT a collection in `reportRetainedGraphMemoryV1`. So the 3.5 GB "unnamed" is largely not a retained structure: it is uncollected garbage, extra (native/external) memory, or both. The reachable part (what a leak fix can reduce) is 0.4-0.8 GB. The new profile prints both numbers (`process.heapUsedMegabytes`, `externalMegabytes`, `arrayBuffersMegabytes`, `collectorCapacityMegabytes`, `protectedObjects`, `snapshotMegabytes`, `unreachedMegabytes`) so the next run settles it.
Named live holders seen in them: (a) `StrongRootBlock > Promise > ... AsyncFunctionGenerator > JSLexicalEnvironment > 6:Array` 251 MB / 1.1M strings (56752): a local array of a suspended async function (a live in-flight value, not a leak across waves); (b) `Timeout/Immediate > callback:AsyncContextFrame > Frame > value:Object > arm:Function > Env > Env > body:Function > Env > options > onInferred/onPhases` 34 MB / 190k strings, also `policyOwners`: see fix below; (c) `reuse > holds > pending > entry > carry > exact:Array` 85 MB (14256); (d) `closureStoresV1 > ... table` 16 MB; (e) `GlobalObject > ModuleLoader` 25-33 MB (module records, source text).

## 3. Holder fixed and tested
`🏗️build/👁️observation/🚧️read-parent/🟨️.mjs` `withReadParentScopeV1`: the scope object (`{alive, arm}`) is the value of an AsyncLocalStorage store, so every `AsyncContextFrame` of every timer, Immediate, pending promise and bound callback the wave starts references it. Its `arm` closure shared one environment with the `body` argument of the same function, so any surviving frame kept the wave's `body` (configFiles, options with `onInferred`/`onPhases`/`policyOwners`, context) alive: exactly the `arm > Env > body > options > onInferred` path of profiles 91577 and 56752. Fix: the scope is created in its own function (`readScopeV1`). Test: a read's inputs are freed once the read is over while the scope is still held (old shape 0 of 10 freed, new 9 of 10 in a scratch A/B; the test retries up to 5 times because JSC scans the stack conservatively). read-parent 4/0. This is real retention but about 34-44 MB per wave at most in the profiles, so it is not the 300-490 MB/wave slope.

## Update (17:15 lead): `closure:entries.value` 4106 entries / 604 MB
- Cache: `inference:closure-entries` in `🕸️graph/📥️inference/🧭️script-inputs/🟨️.mjs`, a bounded LRU already (8192 entries, 96 MiB, schema `closureEntryCacheBytes`), keyed by `workspaceRoot\0recipeKey`, valued by `{recipe, value (closure file list or record), rows (shared row refs), layers/digests, answers Map, checked}`. It is process-lifetime on purpose: entries from finished waves are re-asked by later waves.
- Cause: the byte charge was wrong, not the bound missing. `sizeOf` charged `closureEntryValueItemBytes` = 16 B per value item on the stated premise that "the strings of values are shared". A value loaded from the durable store (`store.load`, JSON-parsed) owns its strings, so one path of 80-150 chars cost about 100-200 B real vs 16 B charged: the cache believed it held 96 MiB while holding about 600 MB (4106 entries, about 147 KB each, still under the 8192-entry cap, so nothing evicted).
- Fix: `closureEntryChargeBytesV1` (exported): per string item 16 + `closureEntryValueStringBytes` (40, new schema limit, EN/DE) + 1 byte per character, charged whole (an upper bound, shared strings only make it conservative). The 96 MiB budget now holds about 600-700 such entries; an evicted entry is re-read from the store (`store.load`, then `closureEntryHoldsAsync` check), which is what the loader at the `ensureClosureEntry` path already does.
- Test `🧪️tests/🪣️entry-bytes` 2/0: 12 waves x 40 owners of 800-path values (JSON-parsed, unshared) in a 4 MB cache: charged bytes <= budget at every step, really held characters <= budget, the oldest wave evicted, and recomputed answers equal the originals and the retained ones.
- Not done: (a) the value still duplicates the stored value file in memory (an id + lazy load would remove the copy; a larger change of `answers`/`checked` users, left for a follow-up); (b) the sibling `inference:closure-values` cache (`parsedValues` in `💾️entries/🟨️.mjs`) uses the same 16 B/item charge but is capped at 64 entries, so it is bounded in entries; its byte charge should get the same function. (c) the census `closure:entries.value` samples 16 entries and does not de-share strings, so it may over-state; the new charge and the census should now agree within the same order.
- Checks: typecheck script-inputs passed, dangling-imports clean, closure-collections-shared 1/0, closure-store-limits 3/0.
