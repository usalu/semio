## 2. Reduction: decision and why no profile change was landed
- cad: the charge is the bitcode of the whole dependency closure (6,259 MB of rlibs) held from the start of thin LTO to the end (stack samples in `run_thin_lto`, `computeImportForModule`; back end already serial). Thin LTO off is impossible (1,000,000 function limit, ticket 26/08/29); codegen-units and debuginfo do not change the closure size; fat LTO is larger. So no profile value (LTO mode, codegen-units, debuginfo, opt-level) selected by the build policy brings it under 4,096 MB. Not changing release output quality for no gain: profile stays `release-wasm` (opt-level s, thin LTO, 16 CGU).
- What does reduce it: a smaller closure. Clean candidates, none landed (each is a multi-hour rebuild plus a product decision): drop `semio_s_artifact_stdio_txt_tests` (160 MB bitcode, a tests crate inside a release closure) from the cad/puzzle closure; split the dwg snapshot objects (229 MB) and the binary-io registry (190 MB) by family (`split-families`/`split-app-fleet` actions on the carving list); split the final into components per domain. The carving entries stay, they leave the list only when remeasured below 4,096.
- dwg objects library: could not be measured below the ceiling without the split; it is offloadable (lib), so routing (below) covers it.

## 3. Admission routing (changed)
Already present: placement sizes a unit by its learned peak (+25 %, cap 16,384) against each worker's reported free memory minus committed (`placementHasHeadroomV1`), the broker holds a unit until its forecast fits, and an expensive unit (peak >= 4,096 or time >= threshold) asks for a worker with room for 30 s.
Gap found: when no worker had room within 30 s the gate answered `final-wait` and the unit compiled on the requesting machine, i.e. on a 16 GB worker that cannot carry it (the warden then cancels it).
Fix: `offloadGateV1` takes optional `beyondHost`; an expensive unit with no fitting worker that is beyond this machine returns `offload:true, queue:true, reason:"final-beyond-host"`, so it queues on the fleet for a bigger machine (the 32 GB coordinator as worker) instead of compiling here. `unitBeyondHostV1` (admission policy): largest of carving measured peak and learned peak > class final budget AND this machine's total memory <= class host (16,384 MB). The coordinator (32 GB) and unmeasured units behave as before. The unit-cache script passes `os.totalmem()`.
Rule-6 fallback remains: no compatible worker, scheduler down or queue timeout still falls back to local.

## Round 3: beyond-host units never fall back to local; unit-admission failures
- Rule: a unit known to exceed the requester's class (gate reason `final-beyond-host`) is waited for on the fleet and never compiled on the requester. Only a requester that is itself a large host (total memory above the class host) is not beyond-host and compiles locally.
- Schema (`offload/🧬️schema/🔣️.json`, `Policy.beyondHost`): `timeoutMilliseconds` 3,600,000 (60 min), `progressMilliseconds` 30,000, `retryMilliseconds` 5,000; reason `beyond-host-refused`; English and German texts `beyondHost.waiting` / `beyondHost.refused`.
- Code: `offload/🚛️beyond-host/🟦️.ts` `awaitBeyondHostV1` runs the offload attempt with the remaining time as queue wait, repeats it while the fleet is only busy or unreachable (`no-idle-machine`, `infrastructure`), prints every 30 s "{queued} waiting, running on {holders}, typically {s} s, at most {min} min more" (from the scheduler `/status` via `fleetQueueV1`) in both languages, ends at once as `cancelled` on abort, and after the timeout or any reason that no larger machine can fix (`no-compatible-worker`, `incomplete-inputs`, `remote-failed-local-redo`, `queue-timeout`, ...) returns `beyond-host-refused`. The unit-cache script turns that into a failed compile (exit 1, bilingual message), never a local compile.
- ETA is not a prediction: the scheduler exposes no per-operation position or estimate, so "position" is the queue length, "holder" the origins that run actions now, "typical" the median of the last queue waits, and the bound is the remaining timeout.
- Tests: new `🚛️beyond-host` 6/0 (busy fleet then success, timeout refusal, immediate refusal reasons, cancellation before and during, progress cadence, EN/DE text); offload `🟦️` 41, `⏱️timeouts` 15, `🏁️finals` 5, `🚪️gate` 4, `🩺️failure` 4, unit-cache 28, all pass.
- Not verified live: no real queue wait against the coordinator; `fleetQueueV1` was not run against a live scheduler. A beyond-host unit now blocks its compile slot of the build for up to an hour while the coordinator is saturated.
- The 2 `🏋️unit-admission` failures were NOT caused by the CPU gate (load is null in those hosts; probes confirmed). Cause: the host-capacity policy `memory.interactiveReserveBasisPoints` 2500 (min 2048, max 8192), whose reserve `decideHostCapacityV1` counts as unmanaged memory at least (`unmanaged=max(measured, reserve)`), lowers the spare of the admission by `reserve - unmanaged` (1,760 MB in the case 8000 available, three held units). The Python oracle and the fixtures predated the reserve. Fix in this area: the oracle models the reserve (`reserve_of`), vectors regenerated (`--check` clean), the one hard-coded expectation (a unit at its peak, 5,000 MB instead of 7,000) updated. 12/0.
