## 4. Resource leaf bytes: no validity decision depends on them (no digest/witness change)
Consumers of the closure digest / node witness / node `extra.sha256`, and what each decides:
- `boundedScriptInputsV1` reuse (`held.digest === fact.digest`): decides whether the cached walk RESULT (the list of file names, compiled set, ports, tools) is still the answer. The list depends on structure only: a module node's digest covers kind, name, resolved edges, ports, generated imports, router words (edges come from parsing the module, so an edit that changes an import moves the digest); a resource node is never parsed, so its bytes cannot change the list. The esbuild oracle in the source-discovery test agrees (a `?raw` source's own imports are not followed).
- `closureGraphFactHoldsV1` (the `closure-graph` global row of an owner record / closure entry / project): decides whether the recorded WALK ANSWER (names, view answer) still holds. Same argument; the owner record stores file names, not bytes.
- Node witness (`layeredWitnessV1`, lstat/exists rows): decides whether a stored node may be followed without revisiting the module; protects physical custody and structure (a resource that turns into a symlink or vanishes fails the witness).
- Fleet adoption (`🛰️fleet`): compares the adopting machine's own bytes with `extra.sha256` before trusting a node, so a foreign node is never adopted on bytes that differ.
- Readiness and generation inputs (`🕰️generations/🔌️load`, `selected-exchange`): their `closure` digest is the membership/names digest of a generation and the graph head digest, not the walk digest.
- Task result validity is not decided by any of these: the walk list becomes the target's `inputs` and the task hash is over the BYTES of every listed file (existing proof: `⚡️caching/🚀️bootstrap/🔌️nx-plugin/🧪️tests/🎯️precise-command-inputs`, "Nx hashes the bytes of every listed closure file"). A changed PDF/fixture is in the list, so it changes the task hash and the result is not replayed. The command-walk graph never kept resource bytes in its digest (file leaves with byte digests belong to the Cargo/sources families), so there is no regression to repair.
Test added (source-discovery, per resource leaf `a/b.pdf`, `a/raw.ts`): the discovered `files` contain the leaf, hashing the listed bytes changes after a one-byte edit of the leaf and returns after restoring it. Honest limit: it models the hash as the existing precise-inputs test does (bytes of the listed files); I did not run an Nx task here (seal window).
Residual inefficiency, not a correctness defect: after a byte edit with no structural change the stored node keeps the old `extra.sha256` until the node is rebuilt, so a peer holding the new bytes will decline to adopt that node and walk it itself. Including the sha in the witness would fix this at the cost of re-witnessing every resource on each edit; not done because no validity decision needs it.
