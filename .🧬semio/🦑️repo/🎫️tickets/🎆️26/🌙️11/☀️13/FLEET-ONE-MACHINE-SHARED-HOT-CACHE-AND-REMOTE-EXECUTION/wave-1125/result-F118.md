# F118: Who sent the SIGKILL to the coordinator's graph read (2026-11-26 17:58 CET)

## Verdict
No repo enforcer, no warden, no kernel jetsam and no other lane sent the SIGKILL. The sealed graph child (a `bun` process) ended itself with a Bun/JavaScriptCore trap while it stood above its 3072 MB grant, 63 s after its last trace line, in the same way as the earlier "seal read" at 06:56. The 18:30 time in the task is the coordinator's clock; the real kill was 17:58:07 CET (log mtime 17:58:07).

## Evidence chain
1. Process identity. `coord-graph7.log` starts "admitted graph: 3072 MB reserved". The granted CLI runs the sealed child through `runOwnedCommand(..., "repository:command", ...)` (`🏛️sealed/📥️execution/🟦️.ts:28`); that child installs the footprint gate from the inherited grant (`useEnvironmentGateV1`). Footprint trace `$TMPDIR/semio-footprint/5265.log` (UTC stamps, +1 h = CET) names it: pid 5265, gate installed with grant 3072 MB.
2. The process died at 17:58:07.7. Kernel log: `17:58:07.700701 kernel: [bun: killed] exiting with signal 9, force exiting the process`. Crash report `~/Library/Logs/DiagnosticReports/bun-2026-11-26-175809.ips`: pid 5265, launched 17:40:37 (the read had run 1040 s), `EXC_BREAKPOINT`, `signal SIGKILL`, termination `{namespace FOUNDATION, flags 2, code 1}`, faulting thread = main thread, parent "Exited process" (the outer CLI ended after).
3. Same signature at the earlier seal read: `bun-2026-11-26-065602.ips`, pid 70905, launched 06:07:32, killed 06:56:00, identical exception/termination and identical main-thread frames at image offsets 2851348, 11081668, 52475832 ... (same bun binary, 60243968 bytes). Both reports differ from the 2026-11-22 ones (SIGTRAP, namespace SIGNAL) and from an external kill: an external SIGKILL leaves no crash report with a faulting main thread.
4. Common trigger in both traces (`5265.log`, `70905.log`): the footprint gate printed "held 3135 MB of its grant of 3072 MB; collected and shrunk to 3237 MB" (06:54:43 UTC-5: "held 3065 ... shrunk to 3148") followed by a heap census, then no trace line at all for 63 s (72 s) although the gate heartbeat runs every 30 s, so the main thread was blocked or starved until the process ended. The footprint stood above the 3072 MB grant since 16:56:25 UTC (3089 MB) and resident was 3.7 GB, with 9.7 GB swap used on the host. The WTF 3 GB kill-threshold idea was tested and is FALSE for this bun (see the forceRAMSize section): a plain process holds 3.6 GB live without a trap.

## Candidates excluded
- (a) repo supervisor / grant enforcer: the only in-process "grant" code is the footprint gate (`🧠️memory/🦶️footprint/🟨️.mjs`), which collects, shrinks and waits, and never signals. `runLimitedJobV1` + watchdog limiter (`🧱️job-limits`) is used only by `repo scheduler run` (`🗓️scheduler/⌨️command`), not by the graph path. `runOwnedCommand` writes a bilingual "Process N received SIGKILL from owned execution" line to stderr for every signal it sends: the log has none. `bunTestCeilingV1` applies to `bun test` only.
- Graph server read follower (`🌐️remote-execution/🛰️sidecar/🕸️graph/🔭️read/🟦️.ts` stop(): SIGINT then SIGKILL after 15 s): needs 25 min without a wave (`inferStallMilliseconds` 1500000) or, for memory, host pressure != normal AND 300 s silence AND footprint >= 2x grant (`memoryOverrunV1`); the host pressure was "normal" (`state.json`) and the silence 63 s. The graph runner (SIGINT, SIGKILL after 10 s) is only reached through the same stop.
- (b) host warden: `mode` = observe, `state.json` counters cancelled 0, `cancelled/` empty, last alarm in `alarms.jsonl` 16:17:23 (an observe-only slice-worker cap report), `warden.log` quiet after 16:53. The loop only signals with `effective==="enforce"` and writes a `cancelled/<pid>.*.json` record first.
- (c) kernel memorystatus/jetsam: no `memorystatus: killing` line for bun in the 6 h window (only idle daemons at 15:13), no `JetsamEvent-*.ips` after 12:29.
- (d) another lane/tool: lease reclaim defaults to mode `request` (a polite yield, needs a stuck standing), no `reclaim.jsonl`; no pkill pattern matches (the kill carries a crash report from inside the process).

## Root-cause fix (landed)
The store phase ("all project results are in, storing N project fragments") ran its jobs through `mapLimit` with 32 at once and never asked the footprint gate, so a read that already stood at or above its grant packed (JSON text + Buffer + brotli output, up to 64 MiB each) 32 owners at a time on top of it with no pause for collections, heartbeats or samples.
- New `🧺️store-batches/🟨️.mjs` (`mapBatchesV1`, declared in `🟨️.d.mts`): bounded batches, `admit` (footprint gate `admit(signal)`) before every batch, an event-loop turn (`after`) after every batch, cancellation checked between batches, answers in item order.
- `🕰️generations/🟨️.mjs`: the fragments loop now runs `mapBatchesV1(stored,{batch:P.fragmentBatch,signal,admit:footprintGateV1()?.admit,after:setImmediate,...})` with the same per-job progress and cold release as before. New policy number `fragmentBatch` = 16 (schema `🧬️schema/🔣️.json` with EN and DE description, `GenerationPolicyV1` in `🟨️.d.mts`).
- The main file is kept under the 64 KiB bounded-source cap (65190 bytes; a first attempt that inlined the helper made it 66227 and the Source admission refused it), hence the separate module.
- Tests: `🧺️store-batches/🧪️tests/🟦️.ts` (7 tests: policy bound, order and peak concurrency equal to `Promise.all(map)`, language-agnostic batch-size vectors in `🧪️tests/🔣️.json`, gate asked before every batch and blocking the next batch, cancellation between batches, progress totals, empty list). Existing `📈️wave-progress` and `🌊️waves` pass.

## Not changed, and why
- "SIGTERM with checkpoint before SIGKILL": every repo-owned kill path of this read already escalates (graph server stop: SIGINT, then SIGKILL after 15 s; runner: SIGINT, 10 s; owned execution: SIGTERM, grace, SIGKILL, with a kill record). The kill here is the runtime ending itself, which no handler can intercept; a checkpoint before it is only possible by never reaching the limit.
- Open risk: the gate's `admit` waits at most once per 120 s (`waitCooldownMilliseconds`) and the inference phase itself lived above 100 % of the grant for 90 s before the kill. If the crash recurs in the inference phase, the next lever is a gate tier above `hardPercent` (for example 95 %) that waits without cooldown and cuts the project wave; that is a policy decision for the coordinator.
- No lock was taken for this landing (peers were editing `🕰️generations/🌐️remote-exchange` and `📡️wave-upload` at the same time, different files); the three touched files were rewritten atomically (temp + rename) from a fresh read.

## Follow-up: BUN_JSC_forceRAMSize (coordinator lead), tested, not confirmed
- Env reconstruction: the sealed child receives `graphChildEnvironmentV1` (`🏛️sealed/🚦️trampoline`, `📥️source/🔏️closure/🚪️command`), so `BUN_JSC_forceRAMSize=536870912` (childHeapMegabytes 512). Live bun processes on this host show 512 MB, 1024 MB and unset values. The crash report and footprint trace do not record the environment.
- Scratch experiment (pinned bun 1.4.2, scripts and raw output in `T/🧰️scripts/F118/`: `grow-live-heap.mjs`, `release-at-grant.mjs`, `run-*.txt`), one run at a time, capped at 4 GB RSS: grows the live heap by 128 MB steps (objects with strings and arrays).
  - unset: reached 3591 MB heap, RSS 4572 MB, no trap, max step 422 ms.
  - forceRAMSize 512 MB: 3101 MB heap, RSS 4164 MB, no trap, max step 1497 ms.
  - forceRAMSize 1024 MB: 3099 MB heap, RSS 4364 MB, no trap, max step 1309 ms.
  - 512 MB plus the gate's collect, shrink, collect at 3.6 GB RSS: no trap, 199 ms first release, then 1 to 11 ms.
- Result: no EXC_BREAKPOINT at any live size, GC pauses at most 1.5 s (not 60 to 72 s). A small ramSize does not by itself make bun trap or stall that long on a pure heap. The synthetic run lacks what the graph child has (about 1.2 GB external memory, 15M objects, 10 pool threads, a host at 9.7 GB swap), so the lead is not excluded for the real mix, but it is not reproduced and I changed no policy: the task asked for the policy fix only if confirmed.
- Next lever if the crash recurs: rerun the real graph read once with `BUN_JSC_forceRAMSize` raised to the grant (override through the environment of one coordinator run, never the live tree) and compare; a swap-bound stall (host swap 9.7 GB used, 1.5 GB free) remains the likeliest source of the silent minute.

## Follow-up 2: third crash (bun-2026-11-26-201924.ips, pid 56834), stderr, symbols, parent
- Same signature (EXC_BREAKPOINT, signal SIGKILL, FOUNDATION code 1, main thread), same bun (image uuid 4C4C447C-5555-3144-A138-DBD9C49417A3 = the pinned runtime). Timing again: launched 19:31:59, "storing 375 project fragments" at about 2805 s (20:18:44), crash 20:19:22: 35 to 40 s into the store phase, as at 17:58 (storing 17:57:27, crash 17:58:07). It ran with the batched store of this lane (landed 18:09), so batching alone does not prevent it: the process was at 4.6 to 5.0 GB against a 3072 MB grant, host swap 9.6 of 11 GB.
- Symbolication: not possible. The pinned bun is stripped (nm shows 704 dynamic symbols, atos resolves nothing) and the trap prints no bun.report URL. What the frames do show: the crash frames differ per crash (first frames at image offsets 2851348 in the first two reports, 40687408/40686964/40621008 in the third, which now also lists a "JSC Heap Collector Thread"), only the interpreter frames below (about 3.08M to 3.29M, 6138960, 11081364/11081668) are shared. So it is not one deterministic assert: it is a generic JSC/runtime abort reached from whichever allocation or collection step fails first, in the JSC heap (offsets 40 to 45 M are JSC code; the thread list includes the heap collector). Consistent with allocation failure under exhausted swap (CRASH() after a failed mmap/malloc is silent, no panic text); not proven. A Zig panic or an NSException path is unlikely: both print to stderr, and Bun's crash handler would have printed its report.
- Parent: not dead first. The parent that spawned the child printed "repository:command was killed by SIGKILL" and "exit 137" after the child died, so it was alive at the death; `parentProc: Exited process` is only the state when the report was written, after the wrapper exited. The "7.5 MB resident" figure is the same in all three reports (5.8 MB in the first) and is read after teardown, not at the crash.
- stderr: `runOwnedCommand` already pipes and forwards the child's stderr, so a panic text would have appeared; there was none because the runtime trapped without writing one. Landed so that a death never stays silent: new `🎛️owned-execution/🪦️death-note` (`ownedDeathNoteV1`, `findCrashReportV1`, schema with EN/DE texts) wired into `runOwnedCommand`: when the child dies from a signal that owned execution did not send, it writes two lines (English, German) with label, pid, signal, the last 12 stderr lines or the statement "no output (the runtime ended without a panic message)", and, on macOS, the path and exception of the DiagnosticReports file written for exactly that pid (waits up to 8 s for it). Tests: `🪦️death-note/🧪️tests/🟦️.ts` 5 pass (note texts, silent child, report match by pid and age, late report, and a real `/bin/sh` child that kills itself: the note carries "last words"); the existing `🎛️owned-execution/🧪️tests/🟦️.ts` still passes (7). Typecheck of the touched paths shows no error in them (5 errors in peer files: `📥️capture/🚪️entry` tests, `💾️cache/🧹️retirement` tests, `📣️progress` test); dangling imports 0.
- Where the root fix lies: the child stands 1.5 to 2 GB above its grant for the whole last phase of inference and the gate's waits expire (one wait per 120 s). The kill is the last step of that overshoot, not of the store loop. Recommended next step for the coordinator: make the over-grant state a hard state for the project wave (stop admitting new projects while the footprint is above 100 % of the grant, release between waves, no cooldown), and do not start a heal while host swap is above about 80 % full.
