# F106: why the settle test failed, what "managed" measures, metric and settling fixed

Scripts and raw runs: `T/🧰️scripts/F106/` (`metric-experiment.mjs`, `first-collection.test.ts`, `settle-fresh.test.ts`, `collector-trials.test.ts`, `external-accounting.mjs`, `heapstats-cost.mjs`, `worker-gc.mjs`). All runs under the pinned Bun 1.4.2 (`.cache/b/t/m/bun/90987a.../bun`).

## 1. Why the settle test failed: NOT F104's change
F104's `signal` pass-through is only in `reportRetainedGraphMemoryV1`; the failing test never calls it. The failure is reproducible only with the repo's bunfig preloads: bisecting them with `bun test --config` gave exactly one trigger, the test orphan guard (`🏃️process/🧪️testing/🟨️bun/🪦️orphans`, starts a Worker thread, setrlimit through ffi). With `SEMIO_TEST_ORPHAN_GUARD=off`, or without that preload, the test passes (6/0); with it, 3 of 3 runs fail (managed 100-129 -> 294 MB). Deeper bisect (fresh process each, `settle-fresh.test.ts`): the garbage array is read in the same turn that drops it (`released=garbage!.length;garbage=undefined`) and the collection runs in that same turn: JSC scans the stack conservatively and the releasing call's frame still references the array, so even `fullGC`/`gcAndSweep` leave it (294 MB = dead heap not freed). Any yield after the release fixes it: microtask, setImmediate or setTimeout(0) each 3/3 gave 294 -> 4 MB; fullGC alone, gcAndSweep alone, `Bun.gc(true)` alone: 3/3 still 294. `releaseBuildGraphV1` already documents this ("a collection inside the releasing call still sees the caller's stack") and yields; `settleGraphMemoryV1` and the parent collector's `finish` did not. (The guard only changes timing/stack layout; the same stale reference can occur without it, the plain runs just did not hit it.)

## 2. What "managed" = `heapUsed + external` measures in Bun/JSC (numbers)
- `process.memoryUsage().heapUsed` ~ `bun:jsc heapSize()` and `external` = `extraMemorySize`. JSC's `heapSize` ALREADY INCLUDES `extraMemorySize` (native strings, ArrayBuffer backing stores): 200 MB `Bun.file().arrayBuffer()`: `heapSize 200, extra 200` with no cells; 200 MB bytes + 200 MB decoded string: `heapUsed 400, external 400` -> "managed" 800 for 400 real. So `heapUsed + external` counts native memory twice, and `heapUsed` can also read 0 while the buffer is live (`heapUsed 0, external 200, heapSize 200`).
- A buffer is booked at the next collection that visits it, not at allocation: `new Uint8Array(300 MB)` read 0 managed until after a GC.
- Lazy sweep / `Bun.gc(true)` vs `fullGC`: a collection that cannot free (stack reference) leaves `heapSize` at the pre-collection capacity (3M records: 109 -> 271 MB right after one `Bun.gc(true)`, 600 for a 300 MB buffer); a plain script with no stale reference frees to 0 with one `Bun.gc(true)`. `fullGC` and `gcAndSweep` are not better than `Bun.gc(true)` here; what matters is the stack. `Bun.shrink` changes no counter.
- `heapStats()` costs 144-150 ms per call at 2M objects (it walks the heap); `memoryUsage()` and `heapSize()` cost 2 us. Never sample with `heapStats`.
- Mmapped sources: `Bun.file().text()` (200 MB) books `heapSize 200 + extra 200` (once, not twice in `heapSize`); `TextDecoder.decode` of a Buffer books both the buffer and the string. Sliced strings (1500 x 40 chars of a 2 MB parent) book ~2 MB total: sliced parents are visible and small here.
- Consequence for the read: the 3-4 GB "managed" of F100/F104 against 0.4-0.8 GB reachable = uncollected garbage kept by same-turn stack references at the sample point + native memory counted twice. The counted-twice part is bounded by the external share (strings, buffers: about 50 MB per 4M short strings, hundreds of MB for file sources); the rest is garbage the sampled collection could not free.

## 3. Fix (schema first)
- Schema `🧠️memory/🧬️schema/🔣️.json`: new policy field `collectYieldMilliseconds: 0`; `PhysicalPressureCase.counters.heapSize` (optional) with the rule in its description and in the top description (EN/DE); fixture `🧪️tests/🔣️.json` and the language-agnostic corpus `🧪️tests/🎫️reservation/🔣️.json` got two rows (runtime heap contains external; heapUsed lags) with the SQLite oracle `coalesce(heapSize, heapUsed+external)`.
- `graphMemoryPressureBytesV1` returns `heapSize` when given, else `heapUsed+external` (Node keeps external apart: still correct). `createMemoryPortsV1().sample` reads `process.getBuiltinModule("bun:jsc").heapSize()` (constant time) when present. Grant/budget/governor/collector decisions all go through this sample, so they now charge live heap plus real native allocations once, and a leak is no longer hidden among double counted bytes.
- `yieldGraphTurnV1`; `settleGraphMemoryV1` yields one turn between release and collection; `createParentCollectorV1().settle()` (yield, then `finish`) is used at the end of the wave in `project-nodes` (`await parentCollector.settle()`), so the surviving `liveBytes` that sets the next trigger and the wave meter is no longer inflated by the ending call's stack. The sync `afterProject` collection mid-wave is untouched (its stack holds live work).
