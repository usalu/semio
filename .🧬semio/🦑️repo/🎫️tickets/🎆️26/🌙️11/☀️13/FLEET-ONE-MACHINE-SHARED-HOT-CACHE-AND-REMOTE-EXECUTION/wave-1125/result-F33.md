## 2. g1-m05 (Windows): `Original installed dependency directory changed (reference 05baafef)`
Facts: thrown by `scanJavascriptDependencyInstalledPathsV1` (storage 🟦️.ts line 45/51) which compares `dev,ino,mode,nlink,size,mtimeNs,ctimeNs` of every directory of the generation at visit start and end; the scan runs ~1000 s (the `javascript-installed-paths:N` shared holds) over a sealed generation (`j/<generation20>`) or the installer output (`verifyJavascriptDependencyCompletedExportsV1`). The error carried no path and no key, so the writer cannot be named from the log. The failed log shows no replica write, second installer or resume re-link in the window (F14's resume path only touches workspace links, never the generation directory). Most likely on Windows: `ctimeNs` (NTFS ChangeTime) of a directory is moved by attribute/index touches of Defender or the indexer without any entry change; NOT proven, because the keys were never logged.
Staged fix (all in the scan function, which the existing harness transpiles standalone: only `process`, `console` and the already injected names used):
- Message now names the path and the changed keys with before/after values.
- On `win32` the directory `ctimeNs` is not compared (an entry change still moves `mtimeNs`/`size`); files stay strict.
- A change error restarts the walk from scratch (hash, counters, ledger rows reset), bounded by new schema constant `maximumScanAttempts: 3`, logging `[DATA] Installed dependency scan restarted {...}`; abort errors and other failures are not retried. So the stage no longer fails on a one-off change and still fails (with the named path) when a writer keeps changing the directory.
- New test `🧪️tests/🔁️rescan`: a directory disturbed once (mtime or size) is named in the error with attempts=1, and with 3 attempts the scan restarts once and returns the same digest/entries as an undisturbed scan with exactly the 4 ledger rows of one walk.
