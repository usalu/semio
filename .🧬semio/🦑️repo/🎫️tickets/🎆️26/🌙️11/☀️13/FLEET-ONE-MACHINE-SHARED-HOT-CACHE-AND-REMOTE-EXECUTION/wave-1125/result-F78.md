## Cause
1. The text is wrong, not the file. `withheldSource` (graph/generations/load) was printed for every owner `unavailable` row without `missing`, and it ignored `row.reason`. Those rows come from four places in graph/inference/project-nodes: (a) a real parse error (line 684, reason "Invalid Build project metadata ...: <json error>"); (b) `unavailableProjectV1` for BUILD_SOURCE_UNPARSEABLE; (c) `ownerFailureAsWithheldV1`: ANY non-foreign inference failure of the owner (a logic error, an exhausted owner-isolation retry, a farm child failure) is re-labelled `BUILD_SOURCE_UNPARSEABLE`, with the sha256 of the declaring project.json attached as identity; (d) `asideOwner` (line 781). Path (c) is the one that fits: the sha256 matches the unchanged valid file, while the real reason (a bilingual "Owner ... failed on settled inputs: <cause>" line, up to 2048 chars) was never shown. No JSON parser is involved: Python and the graph agree the file is valid.
2. Why the row persists: a stable owner failure is stored as an `unavailable` fragment whose observed rows are what the failed inference read. `unfoundedWithheldOwnersV1` keeps it while the facts about the declaring file hold (they do: bytes unchanged); `revalidatedWithheldOwnersV1` re-infers it only 3 times (5-minute cool-down), then "stays until one of its rows changes". A failure from a transient or since-fixed cause therefore sticks.
3. The actual recorded reason could not be read during the seal window (store blobs are 59 GB, no graph read allowed); the coordinator log carries only the generic line. After the next whole-graph read the new message shows it.
