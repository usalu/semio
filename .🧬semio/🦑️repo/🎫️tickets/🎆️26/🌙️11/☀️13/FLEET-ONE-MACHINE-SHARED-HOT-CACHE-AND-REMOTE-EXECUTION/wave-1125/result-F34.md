## 1. Which collector, and why its liveness check missed the running cargo
- Failing path `.cache/b/r/m/b/p/prototype/build/semio-framework-pack-http/cf085c40b268a8e7/fingerprint/invoked.timestamp` is a build unit `<store>/b/<base>/<profile>/build/<crate>/<hash>` of the shared Rust image, exactly what `collectUnitsV1` (`gc/🧱️units`) removes. It is reached by `repo cache gc --area=cargo-store` (ledger row, one spawn per area since F4 round 4), the automatic reclaim of Cargo admission, `reclaimUnitStorageV1` and the watcher, all via `collectRustImageV1`/`collectGarbageSingleFlightV1`. m01 was under pressure (free fell 21.9 to 8.3 GB during the stage), so the pressure branch ran.
- Not the other collectors: the incremental collector removes only rustc incremental sessions (flock of the compiler's own lock, rustc tolerates a lost session); CAS compact-on-idle compacts ledger/pin shards, no build directory; private target prune (`🏃️process/🦀️cargo/🚪️launcher`, isolated sweep) claims a resource lease per nonce and skips held ones; lane removal (`removeLaneV1`) takes the lane claim and refuses on a live pid marker; dead action-root retirement is not on the cargo path; component runs live under `components/runs`, not `build/`. The disk-recovery image retire/reclaim is exclusive, non-waiting.
- Root cause (read in code, matches the 2026-10-04 addendum of the lock-aware memory): for a profile whose build lease compilers hold (`busy`), `unitEligibleV1` still allowed every unit that was not among the newest two of its crate and idle >= 3 h (`busyMinimumAgeMilliseconds`), superseded or pressure. The only per-unit proof was the unit's `.lock` flock, but Cargo reuses a fresh unit without taking that lock and without touching mtime, and a unit the build has planned but not yet started (m01's cargo spent 600+ s in the frontend phase) has neither. So a running cargo's planned unit looked "idle, unlocked, not newest" and went, and the lease that did say "a compiler is here" was only used as a softer age rule. The lane marker (pid) only exists for `u/l/<id>` lanes; the shared `b/p/prototype` profile has none.
- The lease probe itself is sound here: resource name = `[ns, realpath-canonical build dir, profile]` reproduced on this Mac (sha256 of the name has a `.sqlite` in `.cache/b/l/m/data`), so a busy profile was recognised; it just did not protect.
- Not provable from `S/`: the m01 stage log omits 12,023 earlier lines and the gc lines (`removed build unit ...`) are not in it, so the exact removal line is not seen; the diagnosis is by code and by the identical earlier incident.
