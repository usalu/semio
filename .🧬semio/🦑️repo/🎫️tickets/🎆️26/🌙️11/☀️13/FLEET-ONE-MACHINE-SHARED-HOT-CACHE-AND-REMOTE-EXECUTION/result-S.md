Landings 1 to 4 in `landings.md`. Targets (fleet hit < 60 s, warm < 10 s, parent < 3 GB) were NOT proven end to end: no `repo graph` run COMPLETED tonight (11 runs, all stopped by me with SIGINT), because the live tree never settles (below). What is proven is stated per item.

## 1. Memory: where it really went (measured, `footprint`/`vmmap`, JSC `heapStats`)
- RSS is the wrong gauge. The parent's JS heap after GC is 0.6 GB (1.5 GB at the end of a closure pass); the 12 GB RSS were freed-but-resident malloc pages ("App-Specific Tag 1", 11 GB reclaimable, physical footprint 355 MB). The number that matters is the PHYSICAL FOOTPRINT (jetsam, `footprint <pid>`); the capacity learner of the graph door sizes from RSS ("sized at 160 percent ... 8673 MB") and should be switched to footprint (not done).
- Found with a 0.25 s footprint sampler: a spike of +5.5 GB in 3.5 s (peak footprint 7.3 GB) at the end of EVERY verification pass that found stale rows. Cause: `plan()` searched every class (47 000) once per stale row (33 000) to name the owners of a stale row for the first 16 reasons; with no owner to name it never stopped. Fixed (`rowOwnerNamesV1`, one pass; equal to the old search on 40 random indexes). Measured: peak parent footprint 7.3 GB -> 1.3 GB in the same pass, 2.4 GB over a whole command with 3 passes and 3 build rounds (e11, sampled every 0.25 s), RSS 12 GB -> 5.8 GB (8.6 GB after three rounds).
- Restore of the fleet generation (what a fleet hit pays): `transformGenerationV1` decoded the 91 MB fact index into 700 000 row objects, JSON.stringify'd it, regex-replaced the root, parsed and encoded it again. Real generation (5104 documents, 378 MB expanded): 11 s + 11 s and PEAK FOOTPRINT 10.4 GB. Now `transcodeFactIndexV1` rewrites the binary document (string table renumbered, objects reordered, no rows as objects), byte-equal to the old path (6 tests: POSIX, emoji and Windows roots, both directions): 6.1 s + 6.4 s, peak 2.0 GB (the rest is the 5100 fragments).
- The 16 GB rule: this brings the parent below 3 GB footprint in the verification and restore paths. NOT done: the heap limit from the reservation in the launcher registry (the hint map is fixed; I did not touch the launcher), streaming the final assembly (stage 1 end), and farm workers (1.5 GB each).

## 2. Verification by change cursor (item 2)
`🪪️graph-state/📍️cursor`: the replica manifest is the cursor. A snapshot (path -> 128 bit of sha256 of the shared files the graph walk can enter, 119 000 paths, 3 MB brotli, `.cache/f/graph-state/snapshots`) is what a generation was verified against; `since(snapshot)` is the set difference with the manifest now; rows are vouched unless their path is dirty or lies where the manifest cannot see (roster ignore classes, anything the replica daemon does not share: its own gitignore matcher). Rows of unseen regions go to the old directory-stamp classifier (level 2); the membership scan stays (the manifest cannot see gitignored siblings; scan changes of directories are added to the dirty set). Health tiers: trusted / verify (daemon reports failures, as here: `blocked` count 4400, then every manifest entry is checked against size and mtime like a git index, sync lstat 0.5 s) / unusable (old watcher journal, and the output says so in English and German). The snapshot travels with the generation (`s/<instance>.snapshot.br`, `Note.snapshot`), installed as the cursor of the restored generation. In-process resume: the later rounds of one command are delta passes.
Proof: 20 tests (instance and rows equal a Python model, store, health tiers, composition, levels of doubt) and a property test (8 seeds x 25 random edits of a real tree, stale set through the cursor == full pass, soundness caught three real defects while writing it: a cached snapshot, name-only files, the root listing). Live, same command: pass 1 (epoch, unavoidable, no cursor exists) 150 to 180 s; pass 2 doubt 7 s + facts 7 s + closures 35 s; pass 3 the same. Before: three passes of 160 s each. Doubt classification of 705 000 rows: 27 s -> 4 s (found by replaying a real index).
NOT proven: a warm read and a fleet hit in seconds. The closure re-derivation (35 s) remains whenever hot script files changed: 4 files (`🕰️host`, `host-capacity`, `offload/admission`, the unit-cache script) sit in the closure of 3 400 to 4 200 projects (measured from the fact index), so every edit of them stales ALL projects (4 876) and the cutoff then re-asks 3 000 to 6 900 closures. The time floor of a read after such an edit is about 35 s, with or without a cursor.
