## 2. Offload robustness (`🚀️offload`)

- Upload timeout aborts the upload: `runBoundedOffloadPhaseV1` (client) gives the work an `AbortSignal` that fires at the limit or on build cancel and ends the phase at that moment even for work that ignores the signal. `buildOffloadActionV1` already passed the signal to every `content.missing/write`, the HTTP content client puts it into `fetch`; test proves the server sees the connection close. Seam: `ports.uploadMilliseconds`.
- `onStage` is passed through: `offloadRustcUnitV1({onStage})` forwards each stage once to the caller and writes `stage.queued` / `stage.executing` lines (en and de, in the offload schema texts) to `x/offload.progress`.
- Overall wait derived from the action timeout: policy `timeouts.executeMilliseconds` (1500000) replaced by `executeMarginMilliseconds` (30000); `offloadExecuteBudgetMillisecondsV1()` = `actionSeconds*1000 + margin` = 1230000 ms. It now bounds the wall clock from submitting (connect and queue count against it), and `executeOffloadRidingThroughV1` gives every re-submission only what is left of it.
- Classification without message regex (`🚀️offload/🩺️failure`): `classifyOffloadStatusV1` (gRPC code: 8 no-idle-machine; 9 worker-policy when the protocol marker `OFFLOAD_REFUSAL_PREFIX_V1`, now one shared constant written by worker and read by scheduler and client, else no-idle-machine; 14 transient infrastructure; everything else infrastructure) and `classifyOffloadExitV1` (typed only: exit 126/127/above 128/negative is infrastructure, a structured rustc diagnostic whose `code.code` is E0460/E0463/E0464/E0583/E0786 is incomplete-inputs, everything else is the compiler's own result and is returned as is, never recompiled). The old `INFRASTRUCTURE_FAILURES` stderr regexes are gone.
  Trade-off: a genuine E0463/E0583 in user code is still recompiled locally once (the local run then gives the authoritative answer); worker environment faults that only show as plain stderr text (disk full, linker, temp dir) are no longer detected by text. Worker-side faults that throw reach the requester as a non-OK status and fall back to local; the disk guard (`🛰️agent/💽️disk`) refuses admission before ENOSPC.

## 3. Bazel

`--noremote_local_fallback` is now emitted only when the pool's platform differs from the host platform (contract `remote.localFallback: "same-platform"`). Justification: the flag is not needed for correctness when the pool serves the host's platform, because the local fallback runs the same pinned bun toolchain, so design rule 4 applies and a dead scheduler falls back to local. It stays required across platforms (default pool linux-x64 from a macOS host) because the fallback would execute a foreign-platform bun and fail with an exec format error; there failing closed is the only honest outcome.
Fleet-derived Bazel executor: adopted only when a bearer token is in the environment (`SEMIO_REMOTE_CACHE_TOKEN` or the named variable) and then routed to the host's own platform. Reason: the fleet scheduler accepts signed requests only and Bazel can send only a bearer token, and an executor makes `bazelExecutorCacheFlagsV1` drop the HTTP cache flags; enabling it on every fleet machine would have refused every action and lost the Bazel HTTP cache. Without the token the Bazel path stays local (documented in the `bazelRemoteExecutionV1` docstring and tested).
