# Package T: a unit is byte-identical wherever it is compiled, or it is not shared (2026-11-14 06:00 to 07:15)

Landing: `landings.md` "Package T landing 1". Scripts: `🧰️scripts/T/` (`mirror.sh` scratch mirror of the touched members, `runtest.sh` clean-environment test runner). New members (unit cache `U = ⚡️caching/🦀️cargo/🗃️unit-cache`): `U/🧭️remap` (+ `🔍️embedding`), `U/🪪️extern`, `U/🛰️fleet/📥️adopt`.

## The rule the system enforces
1. A shared unit's bytes must be a function of its key. Everything that made them a function of the machine is removed at the source: recorded source names (remap `all` scope, landing 10), the names of the working directory, registry/git sources, OUT_DIR and the absolute-vs-relative form of the source (all reproduced on the worker from the REQUESTER's own `--remap-path-prefix` list), and for Mach-O links the object-file paths (`-Wl,-oso_prefix` at the output directory) and the install name of proc-macro libraries (`@rpath/lib<crate><extra>.dylib`; before, the output path was inside the library).
2. The key says what the bytes can depend on: machine roots of a remap are keyed by their ROLE (cargo registry cache, git checkouts, compiler source copy), never by where they are on the machine, so a registry crate's key no longer depends on `CARGO_HOME`, user name or rustup home (before: `--remap-path-prefix=<CARGO_HOME>/registry/src=` was in the key text of every registry unit, verified with `normalizeRustcArgumentsV1`); the recorded name of the working directory is part of the key; a unit whose source turns `CARGO_MANIFEST_DIR`/`OUT_DIR` into a VALUE (scan of the files rustc reads, `pathSensitiveV1`), or whose working directory no remap covers, is keyed on the real paths too (fleet key part `real-paths`), so two machines share it only with equal paths; after a compile, a unit whose output bytes hold this machine's checkout, manifest, workspace or lane path while the scan announced nothing is NOT shared (`remote-skip path-dependent ...`, counted in `skipped`, shown by `repo fleet status` as "N skipped").
3. Bytes that are not reproducible are never compared downstream: a proc-macro library enters its dependants' keys through the identity of the unit that built it (`U/🪪️extern`: `<lib>.semio-unit` beside the library, `unit:` + digest of the unit's portable key and real paths), trusted only while the file still names the library's current sha256. (Linkers differ between machines of one Darwin major: bytes of a Mach-O are not guaranteed equal across machines even though the tests show them equal across directories.)
4. If the fleet nevertheless holds other bytes for a key (the server refuses a second upload with 409), the fleet's copy wins on every machine: the client reports `diverged`, the uploader installs the fleet's unit as the newest local variant of the key (`adoptFleetUnitV1`), logs `remote-skip diverged ...`, counts `skipped` and releases the claim. Single-flight claims make this rare; first upload wins, everyone downloads the same bytes.

## What remains non-deterministic (stated, not hidden)
- Workspace units compiled with `-C incremental` (the cargo default for path crates in dev profiles): measured on a 3-function crate with the same source: rmeta 029fdb88e686 non-incremental against 4d007ca2bd6d incremental (O's note "rmeta equal" is wrong for this toolchain), rlib 4bbf19ed811e non-incremental, 1f3c5a3b101d / 6b814dbea0c6 / 07ccc86478c5 for three incremental compiles of the SAME inputs (two cold session directories, one warm). So an incremental rlib is not reproducible even against itself. Not excluded from sharing: the rule above (single-flight claim, first upload wins, 409 adopted) keeps every machine on one copy; excluding them would remove the bulk of the cache (738 of the units of the live plugin build). The cost is that a machine that compiles such a unit itself keys its dependants on its private bytes until it adopts the fleet copy. Dropping `-C incremental` for non-focused units would make them deterministic at the price of the edit loop on lower crates: a product decision, not taken.
- Mach-O proc-macro libraries and bins across machines with different linker builds: equal across directories (proven), not guaranteed across machines; the proc-macro case is handled by the identity rule; bins are never an extern.
- Build-script RUN results are not shared (B), the offload action result carries the worker root marker (above).
- Windows paths: the remap model is POSIX only (path separators other than `/` are not handled).

## Debuggability and runtime uses of paths
- The recorded names are now the cargo spellings: `./<workspace-relative path>` for workspace units, `<registry>-<hash>/<crate>-<version>/src/...` for registry crates, `/cargo/build-dir/...` for generated files, `/rustc/<commit>/...` for the standard library. A debugger finds sources through its source map: lldb `settings set target.source-map . /Users/Shared/semio` (workspace), `settings set target.source-map index.crates.io-1949cf8c6b5b557f/ ~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`, `/rustc/<commit> <rust-src dir>`; rust-lldb/`rust-gdb` pick up the `/rustc` mapping from the sysroot automatically. The dev profile already used `trim-paths = "object"`, so debug info was relative before; what changed is the metadata (panic locations of inlined generics) and `file!()` of ABSOLUTE sources (registry crates).
- Grep of the workspace (550 `.rs` files): `env!("CARGO_MANIFEST_DIR")` in 373 files (fixture lookups in tests and tools; its VALUE is not touched by remapping, and such units are keyed by the real path by the scan), `file!()` in 17 files (all `fixture_json(file!(), "...")`-style or `PathBuf::from(file!())` joined with the current directory): `file!()` of a workspace crate is unchanged by `--remap-path-scope=all` (relative source as given: verified `wl/src/m.rs` in both scopes), so no runtime path breaks; only absolute sources (registry crates, path crates outside the checkout) change their `file!()`, and none of those is used at runtime.
