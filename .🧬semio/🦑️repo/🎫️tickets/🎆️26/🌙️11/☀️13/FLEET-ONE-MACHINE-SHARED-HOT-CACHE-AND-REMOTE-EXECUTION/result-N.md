# Package N: the install pack seeded and restored for real, mirror, uv, and sidecars that survive restarts

Scripts (patches, proofs, measurements): `🧰️scripts/N/`. Landings: `landings.md` ("Package N landing", "landing 2", "outside the build lock"). All numbers are from this machine (g1-server, `/Users/Shared/semio`) on 2026-11-14 01:20 to 02:25. `LIB` = `🧰️framework/🛍️products/🦑️repo/🔨️modules/📚️library/`, `FF` = `LIB/⚡️caching/🚀️bootstrap/🛰️fleet-fetch`.

## 1a. Publishing the install pack of sealed generations (done, with a format change)

**What was wrong.** Nothing could publish a sealed generation: the publish hook sat only in the `fresh` loop of the dependency producer (and the "reused" branch), and the producer is not entered when receipts are fresh. And the first real publish failed at once: the installer's own `scan` returns `version` and `maximumPathUnits` beside the five declared shape fields, the closed `InstallManifest` refused it ("/shape/version is not allowed"). Fixed (the shape is reduced to the five declared fields; the unit test's scanner now returns the extra fields so this cannot come back).

**Cost of H's format, measured.** One generation (`86415d69…`, 55 422 files, 1.5 GB): one gzip-1 tar = 457 MB and 52 s. Six generations = 2.7 GB monolithic (H's format, and a second copy on every machine that publishes). The six generations share almost all packages: 8.4 GB of trees hold 2.17 GB of unique packages (Python signature oracle, `dedup.py`).

**New format (schema first, `FF/🧬️schema/🔣️.json` `InstallManifest.index`, `InstallIndex`).** One deterministic gzip tar per package (below `node_modules`, `@scope/<name>`, `w/<i>/node_modules`), named by its own SHA-256, in `<store>/v1/fleet/install/blobs/<aa>/<sha>`; links (the 253 to 405 absolute workspace and store links) and empty folders are rows of an index blob, never tar entries, and folders inside a unit are not archived (their mtimes made identical packages differ); manifest (signed, bound to the lock integrities) -> index blob -> unit blobs, renamed in that order. A stat-signature cache (`.cache/f/install-pack-units.json`) lets a later publish of the same machine reuse blobs without reading them. Restore streams each blob through SHA-256 into `tar`, recreates links under the restoring worktree, then checks the publisher's per-file fingerprint and the installer shape. Prune keeps 18 states (three lock states of six scopes), drops blobs no kept manifest names after an hour. `fleetInstallSeedV1` publishes every sealed generation the fleet lacks; the producer calls it at its start (build phase, before the early return), so `repo dependencies sync --all` seeds a warm machine. No supported shorter path exists because the producer owns the pins and the lease.

**Real result.** Machine g1-m02 picked up the new code through the replica (not me) and published all six scopes of its own tree between 02:07:23 and 02:10:20 (177 s for six): 1031 to 1088 units, 229 to 405 links, 508 to 606 MB each. Its `lock.sha256` values equal those of my six generations (the matcher `match.ts`). On disk: per-generation sums 3 293 MB, **unique referenced blobs 738 MB** (4.5 times smaller than six archives; H's single archive per generation would be 3.3 GB). My own first publish (02:02, 706 MB of blobs, first generation, about 3 min including the scan) was orphaned by m02's manifests (independent installs have different file mtimes, so blobs do not dedupe across machines; mine are pruned an hour after their last use by the next publisher): the store holds 1 481 MB in 3 652 blob files right now, 743 MB of them orphans. Entries: 6 manifests, 6 index blobs, about 3 100 unit blobs.

Proof by tests (`FF/📦️install/🧪️tests`, 15 pass): restore on another machine equals the shape and python's `tarfile` lists exactly the files plus the index links; generations that share packages share blobs (second pack adds one changed package and one index) and an independent store receives byte-identical blobs from a copy at another path; sealed-but-never-published generations are seeded, a second seed publishes nothing; tampered blob refused; the attack, relocation, claim-single-flight and retention tests of H, rewritten for the new format. `FF` crates 4, mirror 8, fetch 8 unchanged.

## 1d. uv (done: seeding by wheel hash, real uv, `--locked` stays valid)

`FF/🐍️uv`: `fleetUvPublishV1` takes the unpacked archive of every locked wheel (`uv.lock` wheel URLs with `hash = "sha256:…"`) from a warm cache, only where uv's own pointer (`wheels-v6/pypi/<name>/<stem>.http`) records the same SHA-256, as content-addressed unit blobs plus a signed manifest named by the lock digest, with the two pointer files in the index; `fleetUvRestoreV1` places archive, pointers and uv's absolute archive link (the entry `wheels-v6/pypi/<name>/<stem>` is a symlink to `archive-v0/<id>`, which uv needs) into an empty cache. The index URL is untouched, so `--locked` is valid; a wrong or missing seed only means uv downloads as before. Proof with the real uv 0.11.15 (`🐍️uv/🧪️tests`, 2 pass): a probe project is locked and synced online (donor cache), the seed is published, an empty cache without it fails `uv sync --locked` with `UV_OFFLINE=1`, after the restore the same command succeeds and the packages import; pointer digests equal the lock hashes (independent reading of uv.lock). Real lock (503 wheel entries of all platforms, `/Users/Shared/semio/uv.lock`) against this machine's 22 GB `~/.cache/uv`: **79 locked wheels are in it** (the rest of the 22 GB is other archives), publish 4.7 s, 179 MB in the store for 493 MB unpacked, restore into an empty cache 3.2 s. `ensureGenerationV1` (managers) has an optional `fleet` port (`fleetUvPortV1` is its uv adapter). **Not wired in production**: `ensureGenerationV1` has no caller yet (the uv and Go managers are not in the production dependency flow), and the cache the production flow would use is `UV_CACHE_DIR` of the manager (`uv-cache` role), not `~/.cache/uv`. Not measured: a full `uv sync` with the real lock (needs Python 3.14 and several GB).

## 2. Sidecars

**Why 12 restarts in under an hour (and 44 to 46 per day).** From `.cache/f/sidecars/*.log` and `health.json`: every restart is the sidecar's own line "sources changed, restarting" (agent 46, scheduler 44, cache 12 in the logs), restarted by the supervisor after 1.2 to 2.3 s. No crash, no EADDRINUSE, no back-off beyond the first step, RSS 72 MB for each after 3 minutes (no growth seen; I did not watch a day). The cause: the watcher fingerprinted the mtime of **every file of the two modules (`🌐️remote-execution`, `🌐️remote-cache`)** for all three roles, so any edit in either module by any agent (and every replica rewrite of such a file on the other seven machines) restarted agent, scheduler and cache; the scheduler restarted again when the cache moved. Cost of a restart before this package: cache: all claims forgotten (two machines may compile one unit), interrupted uploads and long polls (clients fell back to local at once and marked the tier down for 15 s), scheduler: queue, running actions and load table forgotten (clients fell back to local), agent: its worker left and re-registered under a new id.

**Fixes (all landed, tests with real processes on scratch ports and scratch stores).**
1. **Restart only when the code the role runs changed.** `🛰️sidecar` is split into `🧰️shared`, `👷️agent`, `🗓️scheduler`, `🗄️cache`, `🧮️closure`; a process loads only its role; the closure (static and literal dynamic imports, type-only imports ignored) of the role is hashed by file content; a touch, an identical rewrite, an unrelated file or another role's module changes nothing. Roles have different closures (agent 20+ files without the scheduler and server code). Tests `🧮️closure` 4: python regex oracle for the import scan, semantic table above, real process (touch and other-role edit leave it, own-module edit restarts the role once with one log line, SIGTERM exits 0).
2. **A restart no longer depends on the daemon.** Measured twice tonight: the replica daemon sat at 100 percent CPU for 15 to 17 minutes (pid 15670 from 01:48, then pid 37802 from 02:06 on; `health.json` frozen, sidecars defunct, no restart) after the sidecars had exited for new code, so cache and scheduler were DOWN (port 6094 and 8981 refused) for about 30 minutes in total. The process the daemon starts is now a launcher that runs the role in a child and starts it again by itself on status 75; any other exit ends the launcher with the child's status as before. `🛰️sidecar/🧪️tests` 3 pass. I do not know what the daemon was doing (stacks are unsymbolised; its log stops at "publish"); it stalled both times right after bursts of file changes (my landings were among them, but the first stall started before my first landing). That needs its owner.
3. **Cache restart loses nothing that matters.** `🎟️claims/💽️journal`: append-only journal (`<cache dir>/v1/claims.jsonl`), replayed on start (claims alive at the last write come back with 20 s extra to reconnect and renew; lapsed claims, torn last line, finished cool-offs are dropped; compaction after 20 000 events; an I/O fault disables only the journal). Tests: journal 3 (fake clock, python replay oracle, compaction, unwritable journal), claims 8 (+ python model, unchanged), **real server process SIGKILLed and started again on the same directory: a second machine is told `held`, the holder renews `granted`** (restart test 1). Clients (`unit-cache/🛰️fleet/📡️client`): a call to a server that was reachable within 5 minutes is retried with jittered back-off (250 ms doubling to 2 s) for 12 s before it counts as a fault and before the breaker is marked; a long poll that lost its server asks again; a holder whose renew says lost re-claims before giving up. Tests: claim, await and release issued during a 2.5 s outage complete after it and the breaker stays closed (restart test 2); a server that stays away is given up after the budget and later calls answer at once (restart test 3). In-flight uploads are retried by the same path (uploader jobs 120 s).
4. **Scheduler restart loses no running work.** The worker sends the tasks it still runs in its registration (`resumed`, schema first) when it re-joins; the scheduler adopts them (also merging into an operation the requester has already re-submitted, which would otherwise be dispatched a second time); the worker's report re-registers on a 404 and retries 8 times; the requester (`executeOffloadRidingThroughV1`) re-submits for 20 s on transport-level declines (connection refused or reset, stream ended without answer, UNAVAILABLE), never on a refusal, a timeout or a cancel; after the budget it compiles locally as before. Test with real processes: the scheduler (and its cache) SIGKILLed 2 s into a 5 s action and started again on the same ports: the requester gets the result, **the worker started the action exactly once**, two registrations. Another test: an unreachable scheduler gives a transient decline after the budget. The queue itself is still memory only: queued (not yet running) actions are re-submitted by their requesters, the load table refills within one report interval.
