# CAS auto-cap, disk admission, typed disk errors (agent 0ec9c8a1)

All paths below are under `🧰️framework/`. Logs: `🗑️generated/cas-*.log`.

## Root causes found
1. The cap/watermarks ran only in manual `repo cache cas gc`. `repo cache gc --area=...` (what `launchBudgetSweepIfDueV1` starts automatically) skips the host store, and nothing on put/adopt looked at it.
2. gc itself was pathologically slow: the ledger `v1/l` held 767,815 one-line segment files (one per writer process and shard, 3 GB on disk). The collector re-read every segment 3 times and, worse, `view.refresh()` re-listed and re-statted all ~3,200 segments of a shard before EVERY eviction. Compaction only ran after a gc finished, so the ledger could never shrink.
3. gc needed to write before it could delete (lock file, ledger compaction, access-touch on read) and failed on a full disk. ENOSPC surfaced as `Internal error: ENOSPC` (single choke point `refuseInternalV1`).
4. Store now: 155,107 objects, 220 GiB, none hard-linked (so the cap was simply never applied).

## Budget derivation design (coordinator decision; design only, no code written, repo edits frozen)
Goal: the sum of all area budgets on a partition is at most capacity minus reserve, shared out by policy weights. No absolute declared sizes remain.

1. Schema (`⚡️caching/💾️storage/🧾️ledger/🧬️schema` and `🔣️policy.json`): replace every `budget: {bytes}` by `budget: {weight}`. Keep `{remainder:true}` for the one area that takes what is left. Add per partition `reserveBasisPoints` (never allocated, also the free floor of the disk admission) and a `floorBytes` per area only where a tool needs a minimum to function (measured, not guessed).
2. Capacity per partition comes from the existing statfs envelope (`image.json` filesystemBytes), so budget(area) = floor + weight/sum(weights) * (capacity - reserve - sum(floors)). The existing machine budget (`🎚️machine`, weighted max-min fairness with floors and headroom) is the engine: extend it to cover the loose roots (`repository`, `native`, `rust`) and the host CAS, so one function derives every cap.
3. Host level: one disk budget = partition size x `hostShareBasisPoints`, apportioned to (a) image partitions, (b) repository/native/rust roots, (c) host CAS cap. The CAS `capBytes` becomes derived from (c) instead of the constant 120 GiB, and `partition.high/low/critical` stay as the backstop for what other users of the disk take.
4. Invariant test (language-agnostic, JSON fixture plus Python oracle): for random partition sizes, weights and floors, the derived budgets sum to at most capacity - reserve, respect floors, and are monotone in weight. A ledger validation rejects any policy whose floors alone exceed capacity - reserve.
5. Migration is a hand fix of all policy rows at once (no compatibility layer), plus recreating the g and p images whose envelope differs from the policy. Order: schema and oracle first, then `readCacheLedgerV1` derivation, then policy rows, then images; each step lands after the freeze.
