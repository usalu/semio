# Repo graph service: slice-load OOM, unhandled refusal

## Findings
- "rederivation 256 of 256" is not a stuck loop. The cutoff settler works in chunks of 256 closures; each chunk re-prints that phase while it loads parts and flushes. The baseline log advanced `verification` 0 -> 2538 of 6709 in 400 s, then the slice worker (own cgroup, limit = 4096 MB service limit - usage - margin = 2583 MB) hit its limit.
- Memory root cause (`graph/derived-nodes/closure-kinds`): the settler holds the support of every unchanged answer ("held") until the generation is patched. Every closure loaded or derived its own copies of the rows it read, so a row shared by thousands of closures existed thousands of times (exit log of the dead worker: 9.5M objects, 7.8M strings, 1.5 GB heap + 1 GB external for 2823 closures; the fact index holds only ~224k distinct rows). Measured with the heap-child harness (2000 closures x 150 rows from a pool of 30000): 288 MB before, 22 MB after.
- Fix: rows of parts are interned through a weak pool (`internRow`, swept after each chunk), so retained support is one object per distinct row and nothing is kept for dropped parts.
- Negative headroom ("-63 MB headroom", serial one-at-a-time, ~60 s per Rust owner): `cgroupMemoryHeadroomV1` charged `memory.current` including reclaimable inactive file cache. It now subtracts `inactive_file` from `memory.stat`. The remaining serialisation of a kind with no learned peak is the existing admission law (learn first).
- The 1159 owners are the dependency closure of the requested project (`refreshClosure` verifies only the closure), not the whole workspace; they are all dirty because generation 325 is 113 h old and 9 snapshots drifted. A first rebuild is therefore large once; later runs are incremental.
- Error handling: `PlanRefusedErrorV1` / `HostUnavailableErrorV1` were not `RepoError`s, so `reportRepoErrorV1` returned false and the door rethrew them as uncaught exceptions. `requestInvocationPlanV1` now converts them to `RepoErrorV1` (`graph.plan-refused` carrying the service text in the request language, code `refused`; `graph.host-unavailable`, code `failed`), rendered in en/de at the CLI boundary with exit status 1.

## Follow-up: scope of a single-project slice, and cost
- Scope root cause (`graph/generations/load` `sliceClosureV1`, reproduced with `scope-trace.mjs` on generation 325): a Rust `check` of `@semio-tech/norm-en1990-rs` has an edge closure of 668 owners and no `gis-gismap-js`. The catalog provider of the `✏️s/🔌️plugins` consumer root (`@semio-tech/s-dev-composition`, 166 imports) was admitted together with everything it imports, which added the whole `@semio-tech/*` TypeScript tree (slice 1094, containing gis-gismap-js). A consumer reads only the provider's catalog source file, and `assembleStream` already drops edges outside the slice, so providers now join alone. Result: slice 669 owners, cutoff suspects 6709 -> 2070 in the live run, owners to infer 1237 -> 812, gis-gismap-js no longer part of it. Tests: new fixture case 19 in `generations/load/🧪️tests/🔣️.json` (provider with imports whose imports must not be admitted) plus the Python oracle updated to the same law (90 tests pass).
- Hang root cause: the slice load cgroup was created as kind `service`, so `memory.high` sat at 90% of `memory.max`; anonymous memory cannot be reclaimed (no swap), so a worker above that line was throttled to a crawl (1149 s, 0 rows, 23% CPU, memory pressure full avg10 29%) instead of ending as a typed refusal. The slice limit is now a hard `job` limit (no `memory.high`): an overrun is killed by the kernel and surfaces at once as the localized `memory` refusal with exit 1 (`slice-pool/limit`, test in `resident/🧪️tests/🛑️cancel`).
- The "1078 of 920 MB reserved" wait is the governor holding back a second owner while the first one runs; it is not a self-wait (one owner always runs). It lasted only because the running owner was throttled.
- Cost not solved: even with the smaller slice the worker reaches ~3 GB RSS (JS heap + external about 1.5 GB at the last sample; the rest is anonymous native memory) when the first Rust owner starts, and its event loop blocks for tens of seconds. Heap composition after the cutoff phase is still ~3M objects and ~7M strings (the in-memory derived node graph and fact index rows), not the settled supports. A real fix needs the owner phase to run in a fresh process (or the cutoff graph released before inference) instead of in the same worker; not done here.

## Follow-up 2: measurement of the owner phase (cost still open)
Measured with a temporary `[DEBUG]` probe in the slice worker (removed again) on the real 669-owner slice of `@semio-tech/norm-en1990-rs:check`:
- Cutoff phase: live heap grows to ~9M objects (~1.9 GB) across chunks, falls to ~2.6-3.6M objects (~0.75 GB heap + external, RSS ~1.0-1.2 GB) once the settler releases its graph. A JSC heap snapshot at that point (400 MB live) shows no large leak: the retained rows are the membership `frontier` (35 MB), `references.includes` (12 MB) and similar. Dropping the held supports before compute changed nothing (3.60M vs 3.62M objects), so the cutoff result is not the problem.
- Owner phase: with the limit lifted to 9 GB (temporary experiment, reverted) the worker grew to RSS 6.3 GB, 4.6 GB heap + 3.5 GB external, ~24M objects, with only 1 of 812 owners completed. The growth is inside owner inference (Rust/cargo owners; first owner 11-26 s, 1000+ rows) and is cumulative, so a fresh process or a released cutoff graph (about 1 GB) cannot bring it under 2.5 GB. The cold first build of a generation that is 113 h stale infers all 812 owners.
- Result: with the hard limit the run now ends in about 4 minutes with `The plan cannot continue: the service holds 2805 MB of its 2805 MB memory limit ...` (localized, exit 1) instead of hanging; it does not reach cargo.
- Next step: profile `discoverPart` for `language:cargo` owners (snapshot taken at 1.5 GB into the owner phase, with the limit raised) to find the cumulative structure; candidates are the per-crate native dependency closures and the Rust source caches in `📥️inference/🦀️native-manifests`.

## Follow-up 3: root cause of the owner-phase blow-up (session 0ec9c8a1)
Profiled in isolation with `owner-inference-profile.mjs` (this folder): it drives `emojiProjectJsonNodes` of one temporary copy of the inference module for chosen owner roots inside a private graph-fact staging directory, and prints `heapStats` after a full GC (objects, heap, external, peak RSS) plus the bounded-cache sizes; `retainers-v8-heap.mjs` and `analyze-v8-heap.mjs` read a v8 heap snapshot (string histogram by value, retainer paths). Profile logs were tool output and are deleted; the numbers are quoted below.
- Not cargo `discoverPart`, not the native dependency closures and not the Rust source caches: the 46 en1990 owners alone reproduced it (16.4M objects, 3.4 GB heap, 4.6 GB RSS after 6 to 8 owners, then flat; later owners add about 15k objects each, so the "cumulative" growth of the earlier measurement was the first owners materialising the shared closure entries). The caches the code reports (`inferenceCacheSizesV1`, bounded caches) held only 60 MB charged.
- String histogram of the snapshot: 10.4M strings for 330k distinct values; 131001 copies each of the provider ids `build:command-references|command-imports|script-provider-ports` (one analysis row per source file per provider), 267k copies of single sha256 digests. Retainer paths: `closureEntriesV1` entries (`rows`, `layers`) parsed from the durable closure store, plus the loaded layer cache.
- Root cause: every closure entry of the shared recipes (native command inputs, provider ports in every view, tool closures) lists the observation rows of the whole TypeScript module graph (about 131k files times three providers). Rows that came out of `store.load`/`layerSync` are fresh `JSON.parse` objects, rows derived in process came from a `rowTableV1` that empties itself at 16M characters (far below that working set), so every entry and every layer held its own copy of the same rows: O(entries x files) objects. The entry caches charge the serialised size (96 MiB, 32 MiB), not the heap they pin, which hid it. A second cost: a layer above the layer budget was never cached and was read, brotli-unpacked, hashed and parsed again on every hold check of every owner (about 20 s of a 37 s owner, 88 s before).
- Fix (root): `createRowPoolV1` (`👁️observation/🔢️row-table`), a weak pool that never empties and holds nothing a live row does not hold, makes equal observation rows one live instance (nested rows of analysis rows first, keyed by fields and nested instances, not by the text of the record); `shareObservationRowsV1` exposes it. The closure store shares rows on `layerSync` and `load`, `produceClosureEntryV1` on derivation. The layer cache is charged per row (`closureLayerRowBytes`, 384 MiB budget) because shared rows cost references, so large layers stay cached across owners.
- Test (language-agnostic): `👁️observation/🔢️row-table/🧪️tests/🪢️row-pool/` (`🔣️.json` synthetic many-crate workspaces, `🐍️.py` independent Python model that generates the rows and counts the distinct ones, `🟦️.ts` runner): the live objects after parsing 200 crates x 500 rows equal the model's distinct count and the held heap objects stay below 48 per distinct row (without the pool the same fixture holds about two orders more and fails; checked).
- Before/after, 46 en1990 owners in one process: 16.4M objects, 3.4 GB heap, 4.6 GB RSS -> 1.8M objects, 0.35 GB heap, peak RSS 1.8 GB. Heaviest single owner (`framework-tool-run-rs`): 88 s -> 37 s.
- Row identity of the pool was made cheap (field concatenation for analysis and flat file facts, `JSON.stringify` only for other shapes): the first version cost about 25 s of an 88 s cold heavy owner.
- Live run `repo run @semio-tech/norm-en1990-rs:check --output=static` with the fix (log `🗑️generated/oom-fix-run2-0ec9c8a1.txt`): cutoff phase passed, owner phase advanced to 157 of 812 owners (13 per 2 min while the host was calm, 4 to 5 per minute under load) with the slice worker steady at 2.7 to 3.0 GB RSS (previously 6.3 GB with 1 owner done) and no memory refusal. I stopped it at 1666 s because the host was out of swap (load 38, 8.7 of 8.9 GB swap, one owner 300 s), so the run did not reach cargo. Remaining cost is time: about 4 s per owner warm in isolation, but 56 s for the first owner (shared closures derived once) and heavy hubs (`framework-tool-run-rs`, `framework-rs`, `s-dev-composition` with 117k rows) 37 to 96 s each.
- Open: (1) the worker still carries the cutoff graph (about 1 GB) into the owner phase; (2) a harness run of 70 framework owners hit `closure.provider-entry-stale` because `closureEntriesV1` (96 MiB, charged 2x the stored size) cannot hold the three provider entries a script owner needs at once, so `ensureProviderEntriesV1` evicts the one it just loaded (pre-existing; entries should be charged by what they pin now that rows are shared, or answered from the store); (3) `closureEntryHoldsAsyncV1` re-validates 131k-row entries per validation round.
- Verified: row-table suites (14 tests) and shared-prime suite pass; the observation block suite fails on its fixture schema before and independent of this change.

## Follow-up 4: closure entry eviction, owner-phase memory and throughput (session 0ec9c8a1)
Harness: `owner-inference-profile.mjs` over 28 owners (2 hub owners, 20 random TypeScript owners, 6 Rust owners) in one process with a private staging directory; logs `🗑️generated/graph-owner-before-mix.log`, `graph-owner-after1..3.log`. Host load average 24 to 28 throughout, so wall times are noisy.
- Correctness (`closure.provider-entry-stale`): reproduced in the baseline at owner 15 (log before-mix). Root cause: `closureAnswerV1` read the provider entries back from the bounded `closureEntriesV1` after `ensureProviderEntriesV1` had loaded them, and the cache charged 2x the stored record (all rows), so three provider entries (about 50 MB each) evicted each other. Fix: `ensureProviderEntriesV1` returns the entries it ensured and the answer is computed from those held references, so eviction can only cost a reload, never a refusal; entries are charged by what they pin now (`closureEntryRowBytes` = 32 per shared row, schema `🧬️schema/🔣️.json`, en and de) instead of the stored size; `resetClosureEntriesV1(entryBytes)` takes the budget. Test (`🔌️providers`, "an evicted closure entry is answered again"): the late-closure answers under a budget that holds no entry equal those under the declared budget; verified to fail (stale error) without the fix.
- Memory, root cause found by a heap snapshot at owner 10 (1773k strings, 929 MB): the walk question strings (`{"walk":1,"workspaceRoot":...}`, about 340 characters) in `sidecar.members` of every loaded closure entry, 15k to 27k separate copies of each question (each `JSON.parse` of an entry makes new strings; every layer names its questions). Fix: the closure store interns them on load (`💾️entries`). Test `🧪️tests/🪢️walk-questions` (strings held for 4 loaded entries x 300 layers stay below half the names; 25019 without the fix, 7211 with).
- Memory, cutoff graph: `build` kept `previous` (the whole previous frontier) and every cached fact index alive into `compute`; it now drops both (`indexCache.clear()`), and the host hook `releaseCutoff` (`GenerationHostV1`, implemented in `🕰️host`) releases the observation caches, string interner and ports the cutoff verification filled, once, after the plan and before the first owner starts. Test in `🕊️early-release`. Not measured in the live worker (needs a stale generation run); the isolated harness has no cutoff.
- Throughput: owner time is now spread thin (profile of the 28 owners: layer unpack and parse 10 s, entry parse 5 s, `walkImports` 14 s for entries that went stale, one-off playground catalog 6 s); no per-owner re-read of layers remains because the three entries and the layers stay resident. No sync directory walk dominates.
- Block suite: not a fixture-schema failure; the child fails with "Original captured runtime entry provider required", which is only provided when the suite runs through the repo test runner, never through a bare `bun test`. Fixture, schema and the three sibling block suites pass. No repo tooling defect.
- Before/after on the same harness (28 owners): before, run aborts with the stale error at owner 15 after 185 s (heap 432 MB at owner 15, hub owner 114 s); after fix 1 only (no interning), 28 owners complete in 82 s but heap 3.5 GB (entries resident with duplicated question strings, 1040 MB at owner 13); after all fixes 28 owners complete in 190 s under load 28 (82 s at lower load), heap 294 MB at owner 15 and 0.86 GB at owner 27; typical owner 1 to 5 s, hub owner (36k rows) 28 to 76 s, first owner 25 to 37 s (store load plus one-off setup).
- Verified: providers (5), shared-prime (2), durable-entries (3), late-closures (4), walk-questions (1), generations load suite (90), generations suite (30), early-release (3).
- Open: full 812-owner live run not repeated (host busy); hub owners still 30 s or more.

## Follow-up 5: re-verification peak, host-derived slice limit, invalidation (session 0ec9c8a1)
- Resident service: holds little; the 3528 MB limit is the slice worker's leaf cgroup (service limit 4096 - service usage - 256 margin). The worker peaks after the owners, when the new generation's fact index is built (`readIndex` + `patchFactIndexV1` + pack) and during verification (1.5 GB at "verification 1610 of 1778", 3.4 GB peak over a 613-owner rebuild).
- Measured in isolation on the sealed index (701k rows, 11.8k owners, 80M consumer-row incidences): unpack 0.4 GB live; `patchFactIndexV1` peak RSS 2.93 GB / 12.5 s. Cause: `refineFactIndexV1` built one joined string key and one array per row (700k). Fix: group by a numeric hash of the sorted consumer list, one list per distinct group (peak 2.32 GB / 5.8 s). `createFactIndexV1` row keys are now hashed in bounded pieces (`canonicalKeyV1`, no whole-fact text, `canonicalJsonV1` no longer clones); `refreshMetadata` drops the superseded index from the cache after patching.
- Tests: `🧪️tests/♻️refine` ("14 bytes per consumer-row incidence": 9.7 bytes now, 20.5 with the per-row keys; child-process peak), fact-codec key equals the Python model, all generations suites pass (the retire suite needs the repo runner's artifact directory).
- Limit from host headroom: `sliceLimitPolicyV1` lends the load `hostShareBasisPoints` (7500) of `MemAvailable` above `hostFloorMegabytes` (1536), at most `maximumMegabytes` (8192), never below what the service limit leaves (`HOST_POLICY_V1.sliceHostElasticity`, `hostAvailableBytesV1`; test in `🛑️cancel`). - Invalidation: a norm TS target run served the current generation with no re-verification in 34 s (`graph-owner-run4.log`), i.e. unrelated edits do not dirty it. The 613-owner rebuilds seen in runs 3/5 follow my own edits to the graph implementation (implementation stamp rows), as designed.
