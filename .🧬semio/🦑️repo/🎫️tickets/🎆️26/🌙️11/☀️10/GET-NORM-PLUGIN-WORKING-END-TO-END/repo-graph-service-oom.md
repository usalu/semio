# Repo graph service: slice-load OOM, unhandled refusal

## Findings
- "rederivation 256 of 256" is not a stuck loop. The cutoff settler works in chunks of 256 closures; each chunk re-prints that phase while it loads parts and flushes. The baseline log advanced `verification` 0 -> 2538 of 6709 in 400 s, then the slice worker (own cgroup, limit = 4096 MB service limit - usage - margin = 2583 MB) hit its limit.
- Memory root cause (`graph/derived-nodes/closure-kinds`): the settler holds the support of every unchanged answer ("held") until the generation is patched. Every closure loaded or derived its own copies of the rows it read, so a row shared by thousands of closures existed thousands of times (exit log of the dead worker: 9.5M objects, 7.8M strings, 1.5 GB heap + 1 GB external for 2823 closures; the fact index holds only ~224k distinct rows). Measured with the heap-child harness (2000 closures x 150 rows from a pool of 30000): 288 MB before, 22 MB after.
- Fix: rows of parts are interned through a weak pool (`internRow`, swept after each chunk), so retained support is one object per distinct row and nothing is kept for dropped parts.
- Negative headroom ("-63 MB headroom", serial one-at-a-time, ~60 s per Rust owner): `cgroupMemoryHeadroomV1` charged `memory.current` including reclaimable inactive file cache. It now subtracts `inactive_file` from `memory.stat`. The remaining serialisation of a kind with no learned peak is the existing admission law (learn first).
- The 1159 owners are the dependency closure of the requested project (`refreshClosure` verifies only the closure), not the whole workspace; they are all dirty because generation 325 is 113 h old and 9 snapshots drifted. A first rebuild is therefore large once; later runs are incremental.
- Error handling: `PlanRefusedErrorV1` / `HostUnavailableErrorV1` were not `RepoError`s, so `reportRepoErrorV1` returned false and the door rethrew them as uncaught exceptions. `requestInvocationPlanV1` now converts them to `RepoErrorV1` (`graph.plan-refused` carrying the service text in the request language, code `refused`; `graph.host-unavailable`, code `failed`), rendered in en/de at the CLI boundary with exit status 1.

## Follow-up 3: root cause of the owner-phase blow-up (session 0ec9c8a1)
Profiled in isolation with `owner-inference-profile.mjs` (this folder): it drives `emojiProjectJsonNodes` of one temporary copy of the inference module for chosen owner roots inside a private graph-fact staging directory, and prints `heapStats` after a full GC (objects, heap, external, peak RSS) plus the bounded-cache sizes; `retainers-v8-heap.mjs` and `analyze-v8-heap.mjs` read a v8 heap snapshot (string histogram by value, retainer paths). Profile logs were tool output and are deleted; the numbers are quoted below.
- Not cargo `discoverPart`, not the native dependency closures and not the Rust source caches: the 46 en1990 owners alone reproduced it (16.4M objects, 3.4 GB heap, 4.6 GB RSS after 6 to 8 owners, then flat; later owners add about 15k objects each, so the "cumulative" growth of the earlier measurement was the first owners materialising the shared closure entries). The caches the code reports (`inferenceCacheSizesV1`, bounded caches) held only 60 MB charged.
- String histogram of the snapshot: 10.4M strings for 330k distinct values; 131001 copies each of the provider ids `build:command-references|command-imports|script-provider-ports` (one analysis row per source file per provider), 267k copies of single sha256 digests. Retainer paths: `closureEntriesV1` entries (`rows`, `layers`) parsed from the durable closure store, plus the loaded layer cache.
- Root cause: every closure entry of the shared recipes (native command inputs, provider ports in every view, tool closures) lists the observation rows of the whole TypeScript module graph (about 131k files times three providers). Rows that came out of `store.load`/`layerSync` are fresh `JSON.parse` objects, rows derived in process came from a `rowTableV1` that empties itself at 16M characters (far below that working set), so every entry and every layer held its own copy of the same rows: O(entries x files) objects. The entry caches charge the serialised size (96 MiB, 32 MiB), not the heap they pin, which hid it. A second cost: a layer above the layer budget was never cached and was read, brotli-unpacked, hashed and parsed again on every hold check of every owner (about 20 s of a 37 s owner, 88 s before).
- Fix (root): `createRowPoolV1` (`👁️observation/🔢️row-table`), a weak pool that never empties and holds nothing a live row does not hold, makes equal observation rows one live instance (nested rows of analysis rows first, keyed by fields and nested instances, not by the text of the record); `shareObservationRowsV1` exposes it. The closure store shares rows on `layerSync` and `load`, `produceClosureEntryV1` on derivation. The layer cache is charged per row (`closureLayerRowBytes`, 384 MiB budget) because shared rows cost references, so large layers stay cached across owners.
- Test (language-agnostic): `👁️observation/🔢️row-table/🧪️tests/🪢️row-pool/` (`🔣️.json` synthetic many-crate workspaces, `🐍️.py` independent Python model that generates the rows and counts the distinct ones, `🟦️.ts` runner): the live objects after parsing 200 crates x 500 rows equal the model's distinct count and the held heap objects stay below 48 per distinct row (without the pool the same fixture holds about two orders more and fails; checked).
- Before/after, 46 en1990 owners in one process: 16.4M objects, 3.4 GB heap, 4.6 GB RSS -> 1.8M objects, 0.35 GB heap, peak RSS 1.8 GB. Heaviest single owner (`framework-tool-run-rs`): 88 s -> 37 s.
- Row identity of the pool was made cheap (field concatenation for analysis and flat file facts, `JSON.stringify` only for other shapes): the first version cost about 25 s of an 88 s cold heavy owner.
- Live run `repo run @semio-tech/norm-en1990-rs:check --output=static` with the fix (log `🗑️generated/oom-fix-run2-0ec9c8a1.txt`): cutoff phase passed, owner phase advanced to 157 of 812 owners (13 per 2 min while the host was calm, 4 to 5 per minute under load) with the slice worker steady at 2.7 to 3.0 GB RSS (previously 6.3 GB with 1 owner done) and no memory refusal. I stopped it at 1666 s because the host was out of swap (load 38, 8.7 of 8.9 GB swap, one owner 300 s), so the run did not reach cargo. Remaining cost is time: about 4 s per owner warm in isolation, but 56 s for the first owner (shared closures derived once) and heavy hubs (`framework-tool-run-rs`, `framework-rs`, `s-dev-composition` with 117k rows) 37 to 96 s each.
- Open: (1) the worker still carries the cutoff graph (about 1 GB) into the owner phase; (2) a harness run of 70 framework owners hit `closure.provider-entry-stale` because `closureEntriesV1` (96 MiB, charged 2x the stored size) cannot hold the three provider entries a script owner needs at once, so `ensureProviderEntriesV1` evicts the one it just loaded (pre-existing; entries should be charged by what they pin now that rows are shared, or answered from the store); (3) `closureEntryHoldsAsyncV1` re-validates 131k-row entries per validation round.
- Verified: row-table suites (14 tests) and shared-prime suite pass; the observation block suite fails on its fixture schema before and independent of this change.

## Follow-up 4: closure entry eviction, owner-phase memory and throughput (session 0ec9c8a1)

- Correctness (`closure.provider-entry-stale`): reproduced in the baseline at owner 15 (log before-mix). Test `🧪️tests/🪢️walk-questions` (strings held for 4 loaded entries x 300 layers stay below half the names; 25019 without the fix, 7211 with).

- Throughput: owner time is now spread thin (profile of the 28 owners: layer unpack and parse 10 s, entry parse 5 s, `walkImports` 14 s for entries that went stale, one-off playground catalog 6 s); no per-owner re-read of layers remains because the three entries and the layers stay resident. Fixture, schema and the three sibling block suites pass. No repo tooling defect.

### What was done (index phase, root cause fixed)
- Root cause of the post-owner peak (re-measured on the sealed index a2443e: 747,601 rows, 11,826 owners, 57,948 classes, 29.4 M owner references, 105.6 M incidences): a build decoded the whole index (0.9 GB live), `derivedUpsertsV1` copied every held support into its own array (one list per question, O(questions x rows) pointers), and `patchFactIndexV1` made three more object copies of all classes. The decoded index was also cached after the patch.
- New `🌊️stream-patch` (`patchFactIndexBytesV1`, `emptyFactIndexViewV1`): patches the packed bytes through the lazy `openFactIndexV1` view. Old classes are read one by one straight into typed arrays (`document.classTyped`, new), owners arrive as row batches or lazy iterables and become interned runs (`streamUpsertClassesV1`, new, next to `bulkUpsertClassesV1`), strings are merged in one sequential pass over the front-coded table (renumbering, never decoding), facts are copied with renumbered string ids and deduplicated by their bytes, only new rows and facts are encoded, and compaction merges classes over typed lists (`classesOfChunksV1(..., {typed:true})`). The result is canonical: `encodeFactIndexV1(decode(bytes))` equals the bytes. A cold build is the patch of the empty index.
- Codec: the view exposes `document` (offset tables), the encoder's value, list and string collectors are exported (`writeFactValueV1`, `writeFactListV1`, `collectFactStringsV1`, `createFactSinkV1` with `truncate`) so the encoder and the streaming patch share one writer.
- Wiring (`🟨️.mjs`): `build`, `refreshMetadata` and the merge after a lost swap all use `patchView` (open base view, stream patch, open result); `packFactIndexBytesV1` packs the raw bytes; `readIndexView` replaces `readIndex` in merge; the dead `derivedSpill` path (nothing produced it, a path string would have been iterated as characters) and the string-path branch of `createFactIndexV1` are removed; `derivedUpsertsV1` no longer flattens held supports.
- Measured on the real index (child process, `graphmem-real5/9.log`): no-op patch 3.5 s, +436 MB; re-upserting 1000 derived owners (9.6 M incidences, 67,771 distinct rows) 9.7 to 15 s, peak +855 MB over the open view (was: decoded index 0.9 GB + about 0.8 GB of per-question lists + 2.3 GB patch peak); output 86.85 MB vs 86.98 MB, strict decode ok, canonical. Peak is dominated by old bytes, new bytes, the section buffers and 4 B per class entry; it no longer grows with the number of upserted owners or their rows.
- Tests (`🧪️tests/🌊️stream-patch`, Python oracle `🐍️.py` for the consumers of every row after a patch script, run when Python is present, and it was): 60 seeded worlds x 7 random patches equal the in-memory model (`patchFactIndexV1` stays as that model), canonical bytes, consumers equal to the model and to Python; cold build equals patch of the empty index; batch sources equal array sources byte for byte; refinement through typed lists; child-process peak bound of less than 2 bytes per owner-row incidence for 400 owners x 15,000 batched rows. Cutoff suite gained a test that a held support reaches the patch uncopied and gives the model's consumers. Updated the generations test that expected a whole decode on build. Results: stream-patch 4/4; cutoff 159/159 (one GC-timing test, "a settle keeps the row lists ... holds neither the deriver nor its captures", fails about 2 of 3 runs even alone under load; it asserts a WeakRef is collected after five `Bun.gc` rounds, so it is conservative-stack sensitive and not related to this change); the whole generations and derived-nodes tree: 899 pass, 1 fail (a fact-codec timing test that passes alone), 1 error (`🌊️stream/🔌️external` needs the repo root as cwd).

### Remaining blocker, root causes found (not fixed)
1. One owner needs more than the host gives: the root project `workspace` infers about 270k observation rows (142k `analysis` rows with kilobytes of nested facts, 4.1 M strings = 1.4 GB external, 8.9k closure layers charged 314 to 384 MB, 270k live row-pool entries) with a live burst of 2.7 GB heap + 1.9 GB external, on a 1.5 GB baseline left by the cutoff phase. On this host (16 GB, 8.5 to 10 GB swapped, MemAvailable 5 to 9 GB with the fleet) the derived limit is 2.9 to 4.4 GB, below the ~4.6 GB the owner peaks at. Needed next, in this order of payoff: (a) spill the observation rows of an owner to a row log as they are observed and keep only typed row ids per owner (`discoverBuildGraphPartV1` keeps `nodeRows` plus a `sharedRows` Map of every distinct row for the whole slice; with a spill the stream patch reads each distinct row once, sequentially, and the working set per owner is its own rows only); (b) stream the closure layers of the shared script closures instead of caching 8.9k parsed layers; (c) run the owner phase in a fresh process (baseline 1.5 GB released); (d) give plan admission the worst learned owner (peak + baseline) so a plan whose limit cannot hold it waits with a typed progress line instead of being killed after 20 minutes.
2. The learned owner peaks are inflated and never decay: `owner-peaks.json` of the selection holds `project` 2.2 GB, `language:typescript` 586 MB, `language:rust` 4.49 GB and `language:cargo` 3.16 GB, each the maximum growth of the headroom while one owner ran (it includes the shared closures the first owner builds and uncollected garbage) and applies to every owner of that kind. Fix direction: key the root project apart from crates and learn a decaying peak (last completions) instead of an all-time maximum.
3. RSS lags the live set: right after a collection the worker showed heap 160 MB + external 135 MB while RSS was still 3.4 GB and fell to 2.5 GB half a minute later (allocator retention; `MIMALLOC_PURGE_DELAY=0` and the service's `BUN_JSC_forceRAMSize=1024 MB` are inherited by the worker, `graphChildHeapBytesV1` (512 MB) is declared but used nowhere). - Cause (confirmed in `exit.log` by reg5): the resident service ends with exit 124 because the Script watchdog (`🧰️framework/🔨️modules/🏃️process/🧭️routing/📥️invocation/🏃️process/🐕️watchdog`) saw no output, no progress and no child for 10 min, while the host serves the Nx cache endpoint on port 6090.
- Fix: a host declares itself as serving (`enterScriptProcessServiceV1`, `scriptProcessServiceCountV1`); a serving process is never judged stalled, because idle is its normal state and its own lifecycle (retirement, cancellation) ends it. `B/⌨️command/🌐️host/🟦️.ts` `withHostedRemoteCacheV1` declares it for the whole life of the service and releases it when the service stops, after which the ordinary rule applies again. Declared waits and the pure decision rule (`scriptProcessStallDecisionV1`, checked against the SQL oracle in the fixture) are unchanged.
- Test: watchdog suite, new case "a serving host is never reported as stalled however idle it is, and is judged again as soon as it stops serving" (idle 400 ms against a 60 ms stall period: 0 stalls; after release: 1 stall; double release counts once). `repo tools exec bun -- test .../🐕️watchdog/🧪️tests/🟦️.ts`: 15 pass, 0 fail (`graphmem5-watchdog1.log`). Needs a service restart to take effect.

### 2. Owner reuse (root cause found and fixed)
- Re-measurement: the Follow-up 9 probe (checked before `settleClosureRowsV1`) overstated the miss. With the real order (settle, then check) on a stored record of the real store (copied to scratch: 03724d4a.., 8 closure rows), all rows hold; the 8 closure rows fail only before settle. So the closure rows were NOT non-deterministic, not compared against another generation and not invalidated by an unrelated edit: the entry for the recipe was loaded (v2) and verified row by row.
- Cause: stored closure entries contain `analysis` rows (about 1,300 per entry) that name a source analysis provider (`build:command-imports:v1:<owner>`). `sourceAnalysisFactHoldsV1` answers false while that provider is not registered in the process, and providers are registered lazily by `prepareSourceAnalysesV1()`, which the graph load and the first parse call, but not the lookup of a stored record. A process that infers owners in a fresh process (a farm worker, a service after restart) therefore finds the first stored entry (and record) stale, derives it again (75 to 210 s measured under load, 4 closure entries derived on one record) and only then has providers registered. Every fresh process pays this again because a worker does not persist what it derives; that is the 7 to 95 s per owner of describe4.
- Fix: `settleClosureRowsV1` (`B/👁️observation`) now always asks the closure provider (also when no row is a closure fact), and the provider's `settle` (`B/🕸️graph/📥️inference/🧭️script-inputs`) calls `prepareSourceAnalysesV1()` first, so everything a stored fact is checked against is ready before the check, in every record lookup (settle runs before `current`).
- Racy files: a record is never persisted when a file it read was stamped within `racyMilliseconds` (2000) of the start; freshly edited files are therefore not reusable for 2 s. Not a defect; the test waits it out.
- Test `🕸️graph/📥️inference/🧪️tests/♻️owner-reuse` (language-agnostic fixture `🔣️.json` + schema; each build runs in a fresh `bun test` child process `🏭️build.ts`; closure rosters equal esbuild's): world of 4 owners sharing one closure. Build 1 infers all 4; build 2 (fresh process, no edits) infers 0 and derives 0 closure entries (100 percent reuse); an edit of one owner's data re-infers only that owner; an edit of a shared module that changes no import re-infers none; a new import changes the answer of one owner and re-infers only it; a third fresh build reloads all. Without the fix the same test fails at build 2 (first owner re-inferred, `graphmem5-reuse6.log`); with it: 2 pass, 43 expects (`graphmem5-reuse5.log`). Regression run with late-closures and closure-facts: `graphmem5-reuse7.log`.
- Not proven on the real store: a full `describe norm` rerun (forbidden until told). Expect the owner phase to reload records; a record whose closure files really changed (other agents edit `🏃️process`) still re-derives only its stale entries. Side finding: 637 closure entries on disk are version 1 (never loadable, re-derived once and replaced); harmless.
- Regression run (`graphmem5-reuse7.log`, late-closures + closure-facts + owner-reuse): 27 pass, 1 fail. The failure is `🧷️closure-facts` "records that read the same closure share its fact blocks" (header line 78,739 bytes against a 2,560 byte bound: the record header carries its rows inline instead of in blocks). It measures how a record is written, which this change does not touch, so it looks like another agent's change to the record writer; not investigated. Late-closures all pass.
