# Native Development Candidate Audit

The supported native Play listener is `serve-play-native.ts` on port 6034. It starts the actual Play Vite configuration in prototype mode with Standards scope and consumes the existing activation lanes and built prototype module root. It does not itself admit an arbitrary linked component.

The development activation path reads lane completion receipts and maps installed extensions to the lane that staged them (`play/🔨️modules/🧩️runtime/♻️activation/🟦️.ts`). Browser module publication (`framework/…/plugin/🌐️browser-bundle/🏗️materialization/🚀️commands/🟦️.ts`, `publishComponentModuleV1`) requires a component receipt matching the actual build mode and the semantic descriptor returned by the module. It stages through the owned artifact destination. The fresh verifier additionally requires a canonical receipt binding the descriptor and exact raw bytes, and rejects ambient target/cache authority. The linked Energy candidate whose compiler provenance was refused cannot pass this path merely by starting the native listener or activating a lane.

No supported option for admitting that unreceipted candidate into an ordinary human browser session was found in the inspected Play launcher, activation, or browser publication paths. The private Playwright interception is evidence for the candidate, but is not the existing user-facing development admission mechanism. Do not substitute its bytes or invent a receipt. The shortest supported path remains the in-flight provenance-checked component build, then normal browser publication and activation; port 6034 can continue serving the other signed components while it runs. This is a source audit, not proof that no other repository mechanism exists.
