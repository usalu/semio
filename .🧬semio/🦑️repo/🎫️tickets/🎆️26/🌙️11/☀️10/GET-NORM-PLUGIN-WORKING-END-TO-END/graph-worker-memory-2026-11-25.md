# Fleet graph workers and desktop memory

The graph-worker pool forced a first child when no local repository work was active. A 16 GiB fixture with just 1 MiB above the 2 GiB floor therefore started a worker estimated at 500 MiB or more. A second path started a child when the host capacity sampler threw. Both paths reproduced before correction. These findings explain how additional memory demand could be admitted. The available incident records do not identify the process that triggered the macOS application pause.

The pool now enforces the same memory floor when serving remote work, includes running children in its calculation, and retries failed host samples on the next poll with zero new workers. A sampling error is recorded in pool status. On critical pressure or swap rates high enough to stop the pool, all of its children drain together. A busy child that misses the existing three-second grace period is terminated. The same decision loop resumes work after capacity recovers.

Eight focused tests covered sizing, fit and recovery, an unavailable sampler, fixture agreement with an independent Python implementation, and the live runner using a stub launcher. Two further tests used three small graph workers, exercised foreground waiting and memory pressure independently, and verified the worker count fell to zero before resuming. These tests exercised the production code. The incident was never recreated on the host.

At 20:23 CET, the macOS filesystem event daemon showed roughly 5.3 GiB RSS while the browser sweep was still waiting. Its allocation varied markedly across samples. The system diagnostic directory had earlier disk-write reports for Bun and bsdtar, and no November 25 jetsam report was found there. The archive report attributed 2.15 GB of file-backed writes over 140 seconds to bsdtar and recorded its footprint at roughly 10 MB. This evidence does not attribute the desktop pause to bsdtar, the event daemon, or any individual repository process. No operating system service was terminated.

The CLI capacity help now describes the computed floor and hard pressure stops in English and German. Four stale remote-execution help snapshots also needed refreshing after the cancellation command was added. The bilingual snapshot check passed 175 assertions.

## Resume review, 2026-11-26

A source-only review of the in-progress page-in resume gate found that a missing per-subject nonresident measurement becomes zero. The Darwin footprint port may be unavailable, Linux charge reads may fail or be skipped below the sampling threshold, and Windows rows have no such measurement. Thus an apparently fitting resume can have unknown actual page-in cost. An overdue non-cancellable subject with a known cost exceeding available resume room receives neither cancel nor resume until the host sample changes. With persistent OS warn and otherwise quiet measurements, eligible suspended subjects can resume but the level and admission hold remain guard indefinitely; this is distinct from a paused-process deadlock.

The common sampler labels the rate swap-out but sums swap-ins and swap-outs on both Darwin and Linux; the acute traffic condition can therefore include swap-in alone. Windows exposes neither compression nor swap traffic, so the compression-and-traffic acute branch cannot fire on that platform. These findings were sent to the implementation owner while edits were in progress; they do not establish a final implementation defect or a runtime reproduction. No pressure test or service restart was performed.

## Owner-pool reservation sizing

The sidecar owner pool samples `readRemoteExecutionHostViewV1`, backed by `readHostCapacityStatusV1`, and maps active non-lent grants to their reserved minus observed memory. Graph-farm grants contribute only 25% of that difference. The sizing function then caps the ordinary held difference at 15% of total physical RAM because the sidecar always supplies `waitingMegabytes`, including zero. This can admit remote background work beside a larger local late-phase reservation. For a 16,384 MiB host with 6,000 MiB available, a 2,048 MiB pool floor, a 3,870 MiB unrealized reservation, no waiters, available CPU and an 800 MiB child, the 2,457 MiB cap leaves 1,495 MiB in the pool calculation and permits one child; protecting the full reservation would leave only 82 MiB above the floor. When the ledger omits an active reservation, the mapped hold is zero. This is a calculation from current source, not a live launch or a runtime peak measurement.

The remote rustc and command worker uses a different admission path. `🛰️agent/🟦️.ts` and `🌡️load/🟦️.ts` pass the actual host grants and synthetic in-process held units into `evaluateHostCapacityV1`; current `retainsHostReservationV1` protects a visible graph-plan or explicit retained reservation in full. Unlike the owner-pool sizing cap, that decision therefore accounts for the full visible durable local grant. However, the worker action loop catches an exception from its admission callback and treats it as admission at both polling and task stages.

In the reverse direction, the action worker stores admitted peaks in its own `demands` map for its next remote admissions and does not publish those synthetic rows as host ledger grants. Owner-pool children likewise have no individual host grant according to the sidecar's pool contract. A local gate sees their growing physical usage through host samples, but not their as-yet-unrealized remote peak from these paths; the remote admission and local gate are not one atomic reservation. This source observation does not rule out an independent grant for a particular run, nor does it assert a reproduced overlap.
