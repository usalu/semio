# Capacity ledger during source updates

Host capacity admission and status share the per-user ledger. Before this change, a row that failed the closed grant schema disappeared from accounting immediately. An admission scan could then delete the row after the lock stale interval, even when the holder was still live. A fixture with a newer field on an otherwise ordinary 6,144 MiB grant reproduced the missing row and an otherwise admissible command entering its body in the same private ledger.

The current gate now distinguishes known grant accounting from the stable owner identity of an unfamiliar row. When the accounting cannot be understood and the owner may still be live, both admission and status return a localized refusal and preserve the row. The owner header only establishes liveness. It conveys no memory relief or grant custody, so an unfamiliar row cannot be inherited, upgraded or offered in handover through that header. A known dead or reused PID and a known prior boot still permit reclamation. Bytes with no readable owner identity block for the ordinary grant stale interval. The holder updates its liveness heartbeat independently of its memory measurement, so a failed or delayed scan does not age out another owned grant.

The language-neutral fixture and SQLite oracle cover live and expired-heartbeat holders, invalid accounting, dead and reused PIDs, a previous boot, and unreadable fresh or expired records. The gate test verifies that the attempted command leaves its queue clean, never executes its body, and preserves the unfamiliar record. A separate test verifies that an already-admitted owner keeps its heartbeat while the strict scan refuses the foreign row. The framework decision, durable reservation, and liveness suites all passed, with 35 tests and 4,735 assertions.

The fresh local CLI also failed closed against an isolated live fixture. Both `repo capacity status --json` and a harmless 128 MiB capacity launch exited 1, with the grant bytes unchanged and the child never started. After the fixture advertised a dead owner, status exited 0 and displayed zero grants. The reclaiming fixture independently verified deletion of retired rows. The production ledger was never modified by these probes.

The resident graph service is tied to the captured implementation identity. The pre-change worker host PID 72064 and launcher PID 72030 were still alive, although a fresh `repo service host status` reported no graph service for the current resolved implementation. Fresh clients therefore use a separate service identity. Existing clients can still use the already-captured process until its normal retirement. A source change cannot replace old code already resident in that process. Such an old reader can still drop or reclaim rows it does not understand until it retires. Present clients and future versions descending from the updated reader have the fail-closed protection, but neither old resident retirement nor fleet-wide adoption is established. No service was manually restarted.
