# Capacity admission: starvation, reservation overcommit, session fairness

Ticket 26/11/25/FIX-CAPACITY-ADMISSION-STARVATION-AND-RESERVATION-OVERCOMMIT. Code under `🧰️framework/🔨️modules/🏃️process/🏗️build/🌡️host-capacity/` (decision in `📏️decision/🟦️.ts`).

## Research (causes, from the code and `repo capacity status`)

1. Large requests starved because of two things working together.
   - `orderHostWaitersV1` ordered waiters by class, then by the memory their session holds, then by arrival. Aging only promoted batch to interactive, which every aged waiter gets alike, so a waiter of a heavy session stayed behind the requests of lighter sessions for ever, and a request that is never the head never becomes the strict barrier (`blocked`) that drains the others.
   - The session cap refused with `session-cap` and `continue`d before the barrier code, so a cap-refused request could never become the barrier head either.
2. The session cap was judged by what a session reserved, not by what its grants are charged. The decision already charges a grant that finished ramping at what it observably holds (`committedOf`), so the 15.9 GB reserved against 5.4 GB observed was not what the budget saw, but it was what the cap and the fairness order saw: one session with 7 grants, 6.5 GB reserved (cap 6553 MB), kept its 18 waiting requests (800 to 1000 MB included) behind `session-cap` while 2.3 GB were spare.
3. The cap bound whenever a second session merely held a grant, even if it waited for nothing: not work-conserving.
4. A tried and reverted change: lowering the floor of the settled charge. It only applies to grants still ramping after `settledAfterMilliseconds`, and the law test `memory-fit` (never more shrunk reservations growing at once than the slots allow) failed with it, so the floor stays.

## Change

- `orderHostWaitersV1(waiters, ledger, starving)`: within one class, starving waiters (waited `wait.agingMilliseconds`, 300 s shipped) come first and by arrival (the oldest request heads the line, whatever its session holds); the others keep the fair share order. The ledger rows now carry what each grant is charged.
- Session cap: counts what grants are charged (`committedOf`; admissions of the same round at their reservation), binds only while another session has a request waiting that this round has not admitted and that the cap itself would serve (two sessions both over the cap do not hold each other back), and no longer applies to a starving request, so the head of the line can become the barrier.
- Unchanged and still holding: floor, interactive reserve, budget, hard stops (pressure, swap), starved refusal, the warden as backstop. No row (grant/waiter/policy) schema change, so grants held by running processes stay valid and processes on old code and new code decide on the same files; old processes simply keep the old behaviour until they restart.

Bound on a wait: once a request has waited 300 s it heads the line and (when its memory is only held by running grants) drains the rest: admitted when the grants running at that moment release enough, in the scenario 365 s.

## Tests (never weakened)

- New `🧪️tests/🚦️starvation/` (scenario, independent Python oracle `🐍️.py`, fixture): a heavy session's 3500 MB request behind a saturating stream of a light session is admitted at the second the oracle names (365 s) and without aging the same stream starves it for the whole horizon; the cap counts charged memory, is work-conserving and does not let two over-cap sessions block each other.
- `🧪️tests/🛋️reserve/` fixture and oracle updated to the work-conserving cap (oracle orders by held memory and models "another session waits"); new case. Harness arrivals are now recent so the old order is exercised.
- `🧪️tests/🟦️.ts`: starving order unit test.
- Oracle `🔼️upgrade/🐍️oracle/🐍️.py` ported to the new order (starving first, charged ledger); fixtures of upgrade, blockers and followup regenerated by the oracles (only worlds whose order changed differ).

## Verification

`repo test-file` over the 29 test files that use the decision: all pass.

The two failures seen first were not caused by this change (checked by running the envelope test with a copy of the decision code that has the ordering and cap changes switched off: same 5632 MB):
- `exactGrantRequired` placeholders (`tests/🟦️.ts`): another developer's uncommitted new message needs `{cores}`, `{reserved}`, `{availablecores}`; the test's value map lacked them. Added to the map.
- End-to-end envelope plan 5632 vs 6144 MB (repo-library `🌤️followup`): the gate sizes a request against the real host (`hostProfileV1`), capped at `maximumShareBasisPoints` of it; this 16 GB Mac gives (16384-2048)*50% = 7168, less the 1536 MB fixed block = 5632 per job. The test assumed a host of 32 GB or more. Its expectation is now derived from the real host with independent arithmetic.
