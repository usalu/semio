# Capsule Dream original caller lifetime

The v2 Capsule run began with 528,482,304 bytes of original fixture copy stock. At splice cursor 42 with 180 completed items, 140,020,745 copy bytes remained. The mounted subturn still had its normal 32,768-byte copy, 16 MiB capacity, and 1 MiB release limits. The actual blocked 1,507,328-byte release is a separate physical allocation issue documented in `capsule-paged-parts.md`. The old remaining stock is a baseline for the rebuilt paged representation.

## Fixture and host ownership

The test fixture admits one `OriginalFixtureScope` for its whole app lifetime. Its caller lends the context exactly once and retains one return table, decoder, cancellation node, and cumulative recipient. `fixture_renew_turn` settles the previous receiving scope before a new callback. A live return claim pins the actual Source. The fixture then renews only available turn fuel and payload page opportunity while preserving the same grant, original recipient and claims. The general renewal path resets turn bookkeeping against the already issued original origin. The stock in `🎟️caller.json` also covers construction, other fixture activity and close.

The native frame host has one `NativeFrameCaller` per initiating event. Fresh epochs keep the original operation, generation, clock and deadline, and carry the remaining original stock after accepted receipts. Its standard initiating-event policy reserves cleanup up front. Business work receives up to 29,360,128 items, 528,482,304 copy bytes, 264,241,152 capacity bytes, 268,435,456 release bytes and 58,720,256 fuel under a 30-second wall lifetime. The supplied launch policy can choose other finite grants. The guest relay separately intersects each allowed epoch with its finite operation treasury, preserving transport and cleanup reserves, and only debits validated original receipts. Resumption supplies a new callback opportunity under the same finite original operation.

`arm_host_lifetime` can overlay the standard native initiating-event limits in the registered fixture. It measures the called operation from its arm point on the existing scope. The full Capsule functional law does not currently arm it. The original fixture clock is deterministic and its action lifetime should be assessed separately from debugger wall time.

## Verification options

An additional authored Capsule scale fixture may admit a finite larger Source from the start, retain the same scope through dispatch and terminal close, and capture each paid receipt. Its mounting, publication, retirement and idle-streak guards would keep their current bounds. This would establish that the registered action reaches and retires the expected complete document while identifying the actual cumulative consumption. A standard-stock test remains necessary to assess the initiating host limit.

A production-equivalent verification can run the normal host with its existing authored policy and compare the finished receipt, remaining original stock and terminal ownership. If the live paged version exhausts original stock or wall time, lowering the native fixture overhead alone can distinguish debugger cost from actual mounted work. Continued semantic exhaustion calls for reducing repeated whole-document clone and retirement cost in the real Store batch preparation. Original claims and receivers must stay on their authentic source throughout that work. A new Source belongs to a separately admitted operation after its predecessors settle or return custody through the existing protocol.

## Undoable replacement and bounded preparation

`ArtifactStoreBatchPublication` already commits the original gesture as one `Edit`, one history ledger slot and one undo step. `admit_apply_batch_with_pages` supplies typed mutation inputs to this publication engine. In its `Preparing` phase `batch_item_base` captures the previous staged root for the next input. `fold_batch_item` checks a prepared edit with exactly one forward row, appends its inverse and provenance, and replaces the staged post with its sealed `Arc`. The paged source makes input custody bounded and leaves the per-mutation post preparation contract intact. The owned batch source accepts an authored item source with the same single-forward prepared result contract.

`Puzzle5dStorePreparation::advance` uses `apply_diff_cold`. The central cold helper clones the base before applying the diff to unpublished scratch. A 64-row splice thus clones the accumulated scene and replaces the typed part list. State-only history replay also delegates each operation to its authored preparation and is entered after history already exists. It cannot author this switch in one semantic preparation. The mounted genesis replacement creates its envelope with `empty_document_envelope_from_genesis_owners`; the new Store has a fresh history and no undo to the prior Store. The transaction and composition paths group edits and still use per-item preparation.

One eligible path is a registered 5D scene replacement operation with exact inverse data under the existing one-item Store authority. It would prepare a replacement once while retaining bounded page encoders, inverse ownership, and native replay validation. This requires a new authored operation and must prove its real footprint against the 1,048,576-byte one-item declaration and the original host axes. The Capsule DSL asset alone is roughly 3 MiB, so an unbounded cold whole-document copy or handing the asset text to one normal turn is insufficient. A second eligible path preserves existing splice wire and makes unchanged table pages shareable across staged snapshots. The framework offers immutable persistent lists and original-work page forking, and this needs compatible Puzzle 5D table access, splice, and wire paths. The current `PagedList` bounds retirement while still cloning the rows when used through the cold helper. No source changes were made in this audit.

## Native v6 cumulative copy witness

The v6 Capsule test advanced beyond cursor 42 with paged parts. After 5,025,886 Store units it stopped at cursor 48 and 192 completed items. The original source had 28 copy bytes left, 5,931,742 items, 96,013,650 capacity bytes, 323,346,188 release bytes and 1,999,959 turn fuel. The publisher retained two returned snapshot reads and emitted the usual stall fault after 4,096 unchanged units. Its initial copy stock was 528,482,304 bytes, so the published operations consumed 528,482,276 bytes of original copy authority. No equivalent per-allocation release obstruction appeared in this run.

The existing staged snapshot `Arc` only shares the same immutable root. The 5D cold diff calls `Arc::make_mut` on a shared whole typed snapshot and list-delta commits materialize a new editable parts table. Each sealed per-splice post therefore eventually leaves another original scene to retire. The additional copy work is independent of the change that bounds each backing allocation. A single domain operation or persistent shared pages would reduce the actual cumulative copy work. A larger isolated fixture Source would verify terminal behavior under that source while leaving the production lifetime question separate.

## Mounted switch and terminal measurement

The registered v13 editor settled Capsule Dream at turn 9,302 with 376,165 Store units and 377,297 total Work units. Its real mounted scene held all 2,880 parts and 2,864 fasteners. The test verified the Work and physical-currency limits of the initiating event.

The first close run reached the displaced snapshot return rung at the fixture's earlier 524,288-turn horizon. Two diagnostics changed only that horizon. Both completed to the exact terminal-empty witness. The second measured 2,932,411 active close turns with zero consecutive idle turns and a second immediate terminal verification. The fixture now admits 4,194,304 close turns with the existing 4,096 consecutive-idle limit. Its grant and maximum settlement turns are unchanged. The independent caller policy suite passed ten tests, including the SQLite comparisons for the close horizon and idle threshold.
