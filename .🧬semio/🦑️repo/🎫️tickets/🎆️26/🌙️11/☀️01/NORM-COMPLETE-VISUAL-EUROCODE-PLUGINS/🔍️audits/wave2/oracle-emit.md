# Oracle emit (wave 2): check-outcome oracles for the v11 to v14 families

Python only (niced, dry runs through `heavy.sh`), no Rust, no git writes. The three `🔮️oracles/🚦️check-outcome/🐍️.py` now emit `status` next to `utilization` for the new ids; the three check-outcome adapters (`🧪️tests/🚦️check-outcome-enXXXX-1/🐍️.py`) read `row.get("status")` before falling back to `pass_or_fail` (needed for `unverifiedBasis` and for fails at utilisation 1). Scripts: `🧰️scripts/feature-rows/gen1991.py`, `gen1993v13.py`, `gen1994v11.py` (idempotent, `--write`). Status rules were read from `CheckBuilder::build` (an unverified NDP of a passing check makes it `unverifiedBasis`; an explicit `.status(Fail)` reports utilisation `max(.,1)`).

Informative rows are utilisation 0; the value is in the extra `value` field of the JSON (ignored by the feature) and pinned in `--self-check` (hand values, a scipy ODE for the unbalance force). Registry reads are emulated: the first informative row after a read reports `unverifiedBasis`, the next row of the same computation (`footbridge-horizontal`, `hoist-test-dynamic`) reports `pass`, `rail-dynamic` and `machine-force` read nothing and pass. This drain rule is read from the code, not run: if an undrained read leaks from an earlier check into one of these, Rust would report `unverifiedBasis` on a `pass` row.

- Findings for the en1993 owner (not fixed, Rust untouched):
  1. `plateweld`, `grout` and `mjrd` are built without a remedy, so a failing one hits `debug_assert!(status != Fail || !remedies.is_empty())` in `build()` (debug test profile). The fail fixture therefore keeps them at or below 1 (weld 0.66, grout 0.5, mjrd absent because `anchorLength` = 0 removes the T-stub); no fail row exists for these three. A failing `mjrd` is unavoidable whenever `tbend` or `cbend` fails, so any realistic overload document panics until `mjrd` gets a remedy.
  2. The existing en1993 rows for `3.6.shear` etc. say `pass` although those checks cite `ndp.en1993.gamma-m2` (`.ndp(..)`), which is unverified in the registry; `build()` turns such a pass into `unverifiedBasis`. If the Rust run shows that, the old rows (and the older en1994/en1999 pass rows) need the status adjusted; the new rows already carry `unverifiedBasis`.
