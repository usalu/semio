### Disagreements and analysis (Rust read statically against the oracle; nothing could be run)
1. Pin joint moment, EN 1993-1-8 Table 3.10: `special-parts-checks` called `pin_moment_ed(n_ed, gap, outer, inner)` into `F (b + 4c + 2a)/8`, i.e. outer + 4 inner + 2 gap. The formula comes from the pin loaded by the middle plate (b) and supported by the two outer plates (a each) with the gap c between: M = F/2 (b/4 + c + a/2) = F (b + 4c + 2a)/8, so b = middle plate, c = gap, a = outer plate. The Rust weighted the middle plate four times and the gap twice (showcase pin: 15.5 F instead of 9.1 F, 70 % too much moment). A certain bug (the equation has no other physical reading). Fixed: new `pin_moment_of_plates(f, outer, inner, gap)` in `🧮️clauses/🪢️tension-components/🦀️.rs`, called from the pin check, hand-value test `the_pin_moment_counts_the_gap_four_times_...` (100 kN, 20/25/2 mm -> 912 500 N mm) in the clause tests, plus the oracle rows `en1993.1-8.3.13.pin.ten-1` (0.267). The kernel `pin_moment_ed` (letters of the standard) and its third-party golden stay untouched. Needs a rebuild to confirm.
2. Fatigue gamma_Mf (1-9 Table 3.1): the Rust maps DamageTolerant = 1.0, SafeLife = 1.15, LowConsequence = 1.35 by method only. The standard's table is a 2x2 (damage tolerant: 1.00 low / 1.15 high consequence; safe life: 1.15 low / 1.35 high); 1.35 is safe life with high consequence, and the document has no consequence class. The oracle takes the same low-consequence reading for the two methods the document can express (no row uses `LowConsequence`). Open question for the owner: add a consequence class to the row or document the reading.
3. Bracing deflection `ndp.en1993.bracing.deflection-limit-divisor` = 500 (registry, "no spec text in the repo"). I recall the stiffness criterion of 5.3.3 as delta_q <= L/2500 for first-order analysis; 500 is the divisor of the imperfection e_0 = alpha_m L/500. Unverified from memory, therefore the oracle reads the registry value (L/500) and the row is `unverifiedBasis`; if the print says L/2500 the Rust and the oracle both change one registry row.
4. Eq. 5.2 / alpha_cr: the Rust compares alpha_cr with `alpha-cr-min` = 3.0 (amplified first order bound), while 5.2.1(3) requires alpha_cr >= 10 for first-order analysis and 3 only as the limit of the amplified method. The row is a "must be at least 3" check, so a frame with 3 <= alpha_cr < 10 passes (the explanation names the second-order requirement). Design choice, not a formula disagreement; both oracle and Rust implement it the same way.
5. k_tau with longitudinal stiffeners (Annex A.3): the Rust adds k_tau,sl whenever I_sl > 0, also for a/h_w < 1, where A.3 gives a different branch (I could not confirm the second formula from memory). The oracle uses the same single formula, so the fixture (a/h_w = 2) cannot expose it.
6. Eq. 6.67 / `lm`, chi_LT general case, Table 6.4: agree.
7. EN 1993-1-5: the oracle's first draft had four formula errors that the Rust got right (chi_w of a non-rigid end post is 0.83/lambda_w; I_st,min branches by a/h_w < sqrt(2) as 1.5 h_w^3 t^3/a^2; the 0.8 weights the bending term in 7.2; types b/c use l_e in l_y). They were corrected after reading the Rust kernel, so the independence of those four formulas is weaker than for the others; the fire, fatigue, torsion, frame, hollow-joint and tension rows were written before the Rust was read (the hollow joint and the tension kernel were read once and agree on every formula except finding 1).
8. Not a disagreement but a limit: `en1993.1-5.9.2` uses the finite-element I_T of the kernel (`analyse_section`) against `sectionproperties`; both are finite-element values, rows carry 5e-2.
