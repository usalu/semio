## 1. S1 gamma_G,sup/inf

Finding: the combination generator (`any/🧬️schema/💡️inferences/⚖️checks/🧮️combination-generator`, `combinations_dir`) applies the single-source rule per effect. `report-helpers::actions_with` multiplies each action by its influence at the checked member, so the sign of the resulting effect (not of the action) picks gamma_G,sup (adverse in the direction) or gamma_G,inf (relieving); a relieving variable is never counted. That matches Table A1.2(B) note 1 (all permanent actions of one source take sup if the total effect is unfavourable, inf if favourable). Existing tests: `review_demo_a/b`, `gamma_sign_regression_*`.

The gap is A1.3.1 (a permanent action whose magnitude varies from place to place is split into individual favourable/unfavourable parts). One action id has one influence, so a G acting on both spans of a continuous beam got one factor. Fix: new module `⚖️checks/🪜️span-arrangements/🦀️.rs`.
- `continuous_beam_envelope(&SpanBeam, g, q, &SpanFactors) -> SpanEnvelope` (re-exported from the checks crate): each span's permanent load takes gamma_G,sup or gamma_G,inf (2^n), variable load gamma_Q q on every span subset (2^n); each arrangement solved by the shared mechanics `solve_continuous_beam`; envelope = peak sagging per span, peak hogging, max/min reaction per support.
- Numbers (two spans 6+6 m, g 20, q 15 kN/m, 1.35/1.0/1.5): M_sag 151 423.65 N m (sup on the loaded span, inf on the neighbour) against 145 000.36 N m with gamma_G,sup on both spans (+4.4 %, previously un-conservative). M_hog 222 750, R_max(support) 371 250, R_min,0 33 937.5.
- Regression test: `🧬️schema/🧪️tests/⚖️compliance/🦀️.rs` `one_permanent_action_is_unfavourable_in_one_span_and_favourable_in_the_other` (closed-form three-moment, asserts > 4 % above the single-factor value).
- Oracles: PyNite 3.0.0 and anastruct, new check `mechanics.beam-span-envelope` (harness adapters `pynite/🐍️.py`, `anastruct/🐍️.py`, additive; log as shared fixes). Cases `en1990.mechanics.two-span-gamma-arrangement-envelope` and `unequal-spans-gamma-arrangement-envelope` in `🧪️tests/🧫️fixtures/🔮️oracle-cases/third-party-mechanics-extended.json`; PyNite blessed (151 423.65 = my closed form), anastruct within 1e-4 (profile numerical-v1 is 5e-3). Rust adapter in `💡️inferences/🧪️tests/🎯️oracle-wiring`. The two old en1990 cases (`mechanics.beam-envelope`, gamma_G,sup on every span) were removed; the en1994/en1995 copies are flagged to their owners (requests).

## 2. ViewOptions consistency (scene, editor, viewer)
Read-only review, no change needed:
- `scene::view_of`/`resolved_view`: explicit Combination/TrafficGroup ids win, lane positions (`CombinationItem`, `TrafficGroupItem`) resolve to ids against the document, stale positions are dropped (follow the governing combination). `live_scene_of(doc, report, &ViewOptions)` passes the resolved view into `KitDoc.view`, so the fingerprint stamp (`ViewOptions::stamp_text`) changes with the combination/group and re-projects every entity that reads it; `input_of` reads the same keys (`combination()`, `traffic_group()`), and the fallback `project()` is fed the same values.
- Editor: `norm_live_editor!(.., scene = |d, r, view| viewport::scene_of(d, r, view))` is 3-arg; viewport `render_with` builds `view_options_of(&lane)` plus the explicit combination id from the selector (so the live scene follows the active combination and group); the latency bench closure is 2-arg as the `gate` signature requires (`ViewOptions::none()` is `&'static`, matches `scene_of(.., &ViewOptions)`). `full_scene_of` (baseline) stays view-free by design.
- Viewer: `norm_viewer_surface!(.., scene = |d, r, view| live_scene_of(d, r, view))` 3-arg; `render_lane` -> `view_options_of(&view.lane)`.
- Test `the_typed_view_carries_combination_and_group_without_a_string_codec_and_the_live_scene_honours_the_lane` covers lane -> resolved ids -> scene equality and "another group re-projects"; the `#group=` codec is gone.
