# Background Sync Terminal Investigation

The active Windows fleet replica uses `C:\semio`, not this workspace at `C:\git\semio`. Its installed `semio-fleet-store-mount` task runs `cmd.exe` under an interactive token every minute. Its installed `semio-fleet-replica` task similarly runs `powershell.exe` and has a one-minute retry trigger. Either can produce console windows; the mount task is a particularly direct recurring candidate.

The active replica's watchdog recorded repeated silent-loop restarts and a stalled store. This is separate from the window configuration and must not be hidden by disabling synchronization.

The active checkout's topology renderer already generates headless `conhost.exe` task actions, but the installed task definitions still launch `cmd.exe` and `powershell.exe` directly. Its service-definition maintenance currently covers replica and compaction, not the mount task. Updating only the replica task would leave the once-per-minute mount popup.

The `repo` launcher in this workspace fails validation because the launcher registry text `namespaceDangling` is missing or inconsistent. Pointing `SEMIO_WORKSPACE_ROOT` at the active checkout makes `repo --help` work, but does not update the installed tasks.

An initial task update was rejected by Task Scheduler with `ERROR: Access is denied`. After an administrator approval request, the mount, replica and compaction actions were updated to use a hidden Windows Script Host launcher while retaining their existing triggers and task identities. The installed task definitions were re-read and confirmed to use the launcher. A direct test showed that the launcher waits for a child and returns its exit code 17; an observed running mount launcher had no main window.

The existing `conhost.exe --headless` proposal was tested with a child returning exit code 17; the host returned 0 instead. It therefore cannot preserve Task Scheduler's failure and retry semantics. The fleet's automatic service-definition maintenance can overwrite the installed replica and compaction changes and does not cover the mount task. A durable repair must address that maintenance and provisioning path.

The installed launcher returned the correct child exit code when invoked directly through both `cscript.exe` and `wscript.exe`. However, an isolated Task Scheduler test remained in the running state without returning its expected exit code, and a later scheduler query timed out. A diagnostic scheduled script reached its first trace write but did not complete when reading the local launcher configuration. Its test tasks were removed. Attempts to terminate the specifically identified orphaned test processes and remove a locked diagnostic output did not finish releasing all files; do not kill other processes or delete unrelated data to clear them. The mount task also remained in the running state during the observation period, so a successful scheduled run could not be verified. The replica status reported the daemon stopped and a backlog before the task update; it remained unhealthy afterwards. The installation is not fully validated: investigate the scheduler and replica before claiming that synchronization or failure reporting is working. Verify on Windows that repeated triggers open no visible windows, report failures and continue synchronization.
