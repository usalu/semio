# Service generation churn: why 14 generations in 5 h, what changed, what is left

## Findings
- **The sealed snapshot you describe already exists** (`🏛️sealed`, README): a content-addressed store of the tool closure under `.🧬semio/🦑️repo/⚡️cache/implementation`, a trampoline that starts the sealed door, `SEMIO_SEALED_DOOR_DIGEST` as the implementation key of the host service (`hostImplementationV1`: sealed digest wins), a running command keeps the snapshot it started with, a new digest has exactly one cause (a promotion), previous snapshots are kept while quiet, and `withImplementationPinV1` pins what a slice worker loads. It is switched off: `🏛️sealed/🔣️.json` `defaultMode` is `live`, and the promotion rule `explicit` relies on a landing gate that runs `SEMIO_REPO_SEAL=promote`. In this one shared worktree every agent edits the tool and runs live, so the key of the service is `sha256("live", root, seal, hostServiceRevisionV1())`, the digest of the 21 files and folders of `HostPolicy.serviceRevisionFiles` read from the live tree. Each edit of one of them by any of the 50 machines (or by me: service host, schema, launchd) is a new implementation.
- Mitigations that were already there and explain the rate: `settleHostImplementationV1` (clients keep asking for the settled implementation until the tree is quiet 90 s or has differed 10 min) makes at most one generation per 10 min of continuous editing, which is the 14 generations in 5 h; the old generation drains (`drainStallMilliseconds` 30 min), and the pool hands queued loads to the younger one.
- What was missing: (a) nothing bounded the number of live generations: a client of a newer key started a service beside two that were still draining (each reads or holds 2 to 6 GB); (b) a client-side file (`launchd` start path) was part of the key although a running service never uses it.

## Changes (each with a test)
1. **At most two live generations** (`maximumGenerations` 2 in `HostPolicy.reload`). `liveGenerationsV1` (service module, exported through the resident index) reads the descriptors of the checkout (same identity, live process, not stopping) newest first. `settleHostImplementationV1` gets `generations`: when the deferral is due but two services of other implementations still live and the wanted one is not among them, the client keeps asking for the settled one, for at most `generationDeferralMilliseconds` 30 min (the drain bound), so a successor starts beside the old one only while fewer than two live, and the old generation drains after its in-flight plans. `settledHostImplementationV1` passes the live generations.
   - Tests: `🧭️invocation/🕰️settled/🧪️tests` (every live count x deferral age against an SQLite oracle; 40 edits at 5 min give at most `ceil(200 min / 10 min)` starts and never more than 2 live), `🏡️resident/🧪️tests/🧬️generation-cap` (descriptor reading: dead, stopping, other checkout, damaged).
2. **Only plan-semantics inputs move the key.** `🍎️launchd` removed from `serviceRevisionFiles` (it only runs in the process that spawns a service). `hostServiceRevisionV1(library)` takes the library root, and `🏡️resident/🧪️tests/🔖️revision` proves on a temporary library that an edit of a test, a text, a doc, an unrelated module, another test folder or the launchd path keeps the key, and an edit of the plan code or of the schema moves it. Tests, docs and unrelated modules were already outside the list.
3. **A plan binds to the implementation it started with** by the earlier client work (`graph-service-silence.md`): the client asks the implementation it started on first (the draining generation holds its job and the same request joins it), follows the successor only when that service is gone, and the silence of a plan counts only for a service that does not answer.

## Verified
`🧭️invocation/🕰️settled` 3 pass, `🏡️resident/🧪️tests/🧬️generation-cap` 2 pass, `🔖️revision` 5 pass, `🔄️reload` 12 pass, `🥇️generation-handover` 5 pass, `🫥️quiet-service` 8 pass. No service was restarted and pid 20374 was not touched; the live effect needs the next generation (clients pick up the settle change per command, the service-side export at the next service start).

## Not done, and the switch that finishes it
- Running the service from the sealed snapshot needs `🏛️sealed/🔣️.json` `defaultMode` `sealed` plus a promoter (a landing gate or a periodic `SEMIO_REPO_SEAL=promote`), and every agent that edits the tool runs its own commands with `SEMIO_REPO_SEAL=live`. That moves every command of every agent from "my edit is live at once" to "my edit is live after a promotion", so it is a team decision and not made here. With it, the implementation key is the promoted digest and the churn is one generation per promotion by construction; the cap above stays as the bound.
- Comment-only edits of listed files still move the key (the digest is of bytes; an independent oracle of a comment-insensitive digest would need a parser). The settle window (90 s quiet) absorbs most of them.
