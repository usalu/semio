# "The capability token is missing, forged or expired."

## Which token
The client's **service capability token of the plan request** (`mintCapabilityV1` in `🚪️client/🛰️plan/🟨️.mjs`, verified in `runPlan` of `🏛️service/🌐️host/🟨️.mjs`): an HMAC token over the caveats scope, worktree, agent and `notAfter`, minted by the client from the **key file of the runtime directory**. It is not a per-request grant token and not a lease/capacity grant. The service answered one refusal key `capability` for three different causes (no token, MAC does not verify, `notAfter` passed) and the client treated it as `retry: never`, so it ended the whole run-many.

## Why it was refused (what the code allows, which of them was the live cause is not provable from the log)
1. **One key file for all generations** (`key` in the per-user runtime directory, shared by every implementation tag). Each service reads the file at start, or creates it, and its keeper restores its own key byte for byte when the file is missing (macOS temp cleanup) and never overwrites a different key. Two generations alive at once (the older draining, as the 14 generations of the last hours show) can therefore hold different keys while the file holds one: a client that is bound to the older generation (what the previous change does: ask the original implementation first) mints with the file's key and the old generation answers `forged`. This is the path that the follow/reattach work made reachable, and it matches "after 1825 s of work, more Planning lines, then the refusal".
2. **Lifetime 60 s from minting, checked when the service reads the frame.** A service that is paged out (the `UN` state observed earlier) reads a hello+plan frame minutes later: expired.
3. A reconnect that sends no token (hello without `cap`) was not reachable from the client, but the service now says so too.

## Fix
- **Per-generation key**: `hostEndpointsV1` names the key `key-<tag>`; the tag is derived from the implementation, so a client reads the key of the service it asks, an older and a younger generation never judge each other's tokens, and the service removes its key file when it exits (no accumulation).
- **Fresh handshake on every connect** (already the case: each exchange reads the key file and mints a token) with a lifetime of `capabilityLifetimeMilliseconds` 600 s (longer than the plan silence bound 120 s).
- **Typed, retryable refusals**: `capability-missing`, `capability-forged` (names the service tag), `capability-expired`, each in English and German saying which token (the service capability token of this plan request) and why, with `retry: later`. The client turns them into a retry with a fresh handshake (key file read again, new token) up to `capabilityRetryMaximum` 4 times, says so in its progress line, and only then reports the typed refusal; other capability denials (scope) stay fatal.
- **Renewal**: the token is verified once per plan frame, so there is no long-lived token to renew while a plan runs; every reconnect, reattach and follow of a successor is a new handshake with a new token (this is the renewal), and a verification that happens late (stalled service) is covered by the longer lifetime and the retry.

## Addendum: ts-test-3 ended silently after the retry line

Evidence: the last line of `ts-test-3.log` is the forged-token retry line (20:54:24), no verdict, no heartbeat after it, pid 62229 gone; no warden alarm, no stage-runner kill row and no exit-log row mention it, and the exit code was not captured.
- **The retry path itself is sound**: the new test `forged token after a follow to the successor, then retry, then success` (client starts on the older implementation, `identify` returns the successor, the successor's key is wrong, repaired at the retry line) ends with the plan reply (`🏡️resident/🧪️tests/🔐️capability-token`, 6 pass). So the process did not end inside `requestPlanV1`; a thrown or rejected error would have reached the door as a typed refusal (that is how the first run printed its last line).
- **What can end a Bun client without a word**: measured with the repo bun: a process whose event loop runs dry while a promise is unsettled exits with code 0 and prints nothing; a top-level `await` on such a promise hangs (`-e`); a signal listener keeps the loop alive in Bun (a guard with signal hooks turned the silent exit into a hang, so none is installed). A SIGKILL cannot be reported by anyone. I could not tell from the log which of these ended 62229.
- **Fix: a guaranteed final verdict** (`🧭️invocation/🛰️plan/🏁️verdict`): `requestInvocationPlanV1` runs under `guardPlanVerdictV1`. Until the request returns or throws, any process exit prints the bilingual line "The graph plan request ended without an answer (...) / Die Graph-Plananfrage endete ohne Antwort (...)" to stderr and turns exit code 0 into 1; after the result or the error nothing is printed. Tests with real processes (5 pass): text in both languages, finished request prints nothing, a drained loop with an unsettled promise prints the verdict and exits nonzero, `process.exit(0)` while open becomes exit 1, and the guard installs no signal listener. `🧭️invocation/🛰️plan` 19, `🤝️handover` 4 still pass.
