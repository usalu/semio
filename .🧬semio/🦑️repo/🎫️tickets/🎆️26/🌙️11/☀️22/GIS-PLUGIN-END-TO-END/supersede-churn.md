# Supersession churn: planning ends with rc=1 after three hand-overs

Scope: `repo run` planning logs `🗑️generated/ts-rerun*-*.log`, `browser6/7/8-*.log`, service logs `/var/folders/*/T/semio-repo/501/host-*.log` (timestamps there are UTC), `terrain-all9-6.log`.

## Root cause (three independent defects that multiplied)

1. A superseded generation handed over a read the moment it was superseded. `sweep` called `handOverQueued("superseded")` at the first sight of a newer sibling descriptor, and `drainAndExit` did it again at the start of every drain (`reload`, `idle`, ...). `handOverQueued` aborts every job still queued at the governor and calls the slice pool `handover`, which sets `handing` for the rest of the generation: the pool then refuses to start any further worker, a restart after a cut or an external SIGKILL included. So exactly the reads that were waiting for host capacity (ts-rerun3: "waiting for host capacity ... queued for 6 s") or restarting after a kill (ts-rerun2/4: "ended from outside ... cut smaller ... continues") were refused with `handover`, lost their queue place, and asked the next generation, which was superseded the same way within minutes. Three of these in a row ended the client (`maximumHandovers` = 3), rc=1. The in-flight count that gates the drain also ignored every request that was not yet inside the governor (`governor.inFlight`), so a queued read never counted as "in flight" and a connection holding it was retired by the 300 s idle-connection rule.
2. The client limit counted hand-overs, not progress. A read that did 20 minutes of real work between two hand-overs spent the same budget as one that never started.
3. Supersession fired on more than changes to loaded code: `newerSibling` looked at every `host-*.json` in the shared runtime directory, so a service of another checkout or state directory that started later superseded this one and made this one wait for it (`olderBusyServiceV1`); and every client asked for the exact hash of the tree as it was in that second, so each edit followed by a `repo run` of any agent started its own generation (the 90 s quiet and 600 s maximum deferral existed only inside a running service, `createHostReloadV1`, not for the clients that spawn services).

What was ruled out: the implementation hash is a content hash over the bytes of the declared revision files (`hostServiceRevisionV1`), so `touch` never changed it. Of the 66 declared revision files, 62 are in the import closure of the service entry (`⌨️command/🌐️host/🟦️.ts`, 1850 files); the four that are not (`🔐️consent/🔎️sample`, `🌡️host-capacity/⌨️command`, and the two files of the process-library host-capacity folder: gate contract, warden main) are rarely edited, so narrowing to the loaded closure would not have helped here and a closure-wide identity (823 to 1850 files) would have widened supersession. Not changed.

## Fix (no shims, schema first)

Service, `🏡️resident/🏛️service/🌐️host/🟨️.mjs`
- Supersession is only a marker now: `supersededSince=newerSibling()?supersededSince??at:undefined`. Nothing is handed over, nothing is aborted. The superseded generation drains: it keeps its queued, waiting and restarting reads and its pinned code until its last plan answered, or until the stall bound (`reload.drainStallMilliseconds`, 30 min without observed original work) when it hands over what is left.
- `drainAndExit` hands over (`handOverQueued`) only at the cut, immediately before the final aborts, not at the start of a drain.
- New `plansInFlight()` = max(governor in flight, requests of all connections) feeds `supersededDrainDueV1`, so a queued read holds the drain.
- `sameCheckoutV1(identity, identity)` (exported): the descriptor now carries `identity` (`root`, `state`); `newerSibling` and `olderBusyServiceV1` (new `identity` option, wired in `⌨️command/🌐️host/🟦️.ts`) only look at services of the same checkout and state directory.
- The wire frame `Progress` gets the optional `observed: true` (schema `🏡️resident/🧬️schema/🔣️.json`), set on a `slice` frame whose read observed original work; replays to late joiners never carry it.

Client, `🧭️invocation/🛰️plan/🟦️.ts`
- `stalledHandoversAfterV1({stalled,progressed,maximum})`: an ask that saw an `observed` frame resets the count; only `maximum` hand-overs in a row without progress end the request. Custody policy key renamed `maximumHandovers` to `maximumStalledHandovers` (schema, `.d.mts`, test); no alias kept.
- `settledHostImplementationV1` (+ pure `🧭️invocation/🕰️settled/🟦️.ts`): while the tree moved away from the implementation whose service of this checkout still answers, clients ask for that implementation until the newest edit of the service files is quiet for `reload.quietMilliseconds` (90 s) or the tree has differed for `reload.maximumDeferralMilliseconds` (600 s); then everybody asks for the wanted one. A burst of edits makes one generation after it, not one per edit and client. A sealed door digest, a service that no longer answers, no record and an unmoved tree ask for the wanted implementation at once. The record `settled-<root hash>.json` sits in the runtime directory and is best effort.

## Live verification (`🗑️generated/supersede-dry-1.log`, `supersede-dry-2.log`)
`touch` cannot supersede (the identity hashes bytes), so I made a harmless reversible content edit: one trailing newline appended to `🧭️invocation/🔄️reload/🟦️.ts` (a declared revision file) at 09:12:05 while the read of `repo run @semio-tech/gis-js:test --lang=en --dry-run` sat queued at the capacity gate (the exact state that used to be handed over), then reverted (sha1 `116b7ab8...` restored).
- 09:11 generation pid 32367 (host-4b21ce702f9f) started for the first client. 09:12 a second client started after the edit: it joined the same service (settled record `settled=<old hash>`, `firstAt` set), no second generation for the edit.
- 09:16 the quiet period ended and a replacement generation started (pid 43286, host-3c940c34ab88); pid 32367 became the superseded generation.
- The read stayed in pid 32367: no "handed over", no "superseded" line, no rc=1 in either client log (0 matches in both). The slice read finished after 738 s ("publishing the sealed graph to the fleet"), and only then, 08:24:58 UTC, did 32367 log `shutdown superseded` (drained, nothing in flight). Before the fix the same sequence handed the queued read over at the first sweep after 09:12.
- At the time of writing the dry runs were past planning and waiting for their own run slot (`semio.host.capacity/v1`, 245 s and counting, "not enough free memory"), as in earlier runs, so the final `exit` line is appended to the two logs when they end.

## terrain-all9-6 and `source.served`
`source.served` is not a wait. It is the last profile mark of the door boot (`profileMarkV1("source.served", ...)` in `🏛️sealed/📥️execution/🟦️.ts`); the heartbeat `[repo] still working after N s; last phase started: <mark>` prints the last mark and no later code adds a mark, so every `repo cargo` run reads "source.served" from second 2030 on. The lane did not stall in it: `terrain-all9-6.log` shows 69 `door.capacity` heartbeats, 481 `[capacity] waiting ... cargo-orchestration ... behind graph-plan` lines (the 1536 MB batch request queued behind graph-plan grants held by repeated 15 to 30 min graph reads, 5 running, 2 ahead), then `[cargo:test] still running after 11786 s`, and it ended `exit 101` at 13.8k s (3.8 h) with `could not compile semio-plugin-actor-input-decoder` and `-wire` (other agents editing those crates mid-run) on a compiler image reported 100 % full. A cargo run sends no plan request (see `graph-plan-coalescing.md`), so supersession did not touch it directly; this fix helps it indirectly by ending the repeated failing and restarting graph reads that kept graph-plan grants in front of its batch request. The misleading heartbeat is a separate small defect (the door should print the current wait, e.g. the capacity gate line, instead of the last boot mark); not fixed here.
