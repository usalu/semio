## Resource Use

- **Machine (11:26):** 16 logical cores at 100% CPU, with 12 rustc, 6 cargo and 10 Chromium processes. 22 of 64 GB RAM free, 123 GB disk free. The CPU is saturated. Adding more parallel cargo would slow every build, because rustc is the bottleneck.
- **Agents:** 4–7 Sonnet agents at a time, each with private target dirs and `-j 3`. The coordinator alone builds the wasm, at `-j 6`. Matrix runs go one app at a time, because concurrent cold boots time out.
- **Not used:**
  - the shared fleet and remote execution: the native fallback was chosen to avoid getting stuck;
  - Haiku agents: almost all remaining work is fix-and-verify, not audit.
- **Waste observed:** about 8 cold dependency builds per hour, because every agent compiles the same framework in its own dir.

## Clean Long-Term Solutions for Development Speed

1. **Shared, content-addressed build cache for native test builds:** sccache-style, keyed by source hash plus profile.
   - Today every agent rebuilds the whole framework privately (30–60 min cold) because a shared target dir serializes on one lock.
   - A read-mostly shared cache, or the repo's own remote cache through `repo test`, would turn most law runs into minutes.
2. **Fast incremental wasm publishing:**
   - Split the FEM component's 230 MB core into a stable framework rlib layer and a thin plugin layer, or move to dynamic component linking, so a plugin fix does not relink the world.
   - Make `prototype` incremental-safe again (no thin-LTO state reuse after crashes).
   - Target: under 10 min from edit to browser.
3. **Atomic multi-file edits in the shared tree:**
   - Peers' half-written edits broke builds about 6 times today (derive crates, `plain_refusal`, `Cargo.toml`, `semio-os-inference`, `actor-input-wire`, a TS export).
   - A staging area per agent, with an atomic publish of a compiling change set (`repo` transaction or a per-agent overlay that only lands when it type-checks), would remove that class entirely.
4. **Cheap mounted-app laws:** mounted FEM laws take 30–60 min to build and can hang on framework bugs. Two changes would make them fast and fail-fast:
   - a framework-level fixture harness with a bounded turn budget and a stall witness;
   - a prebuilt test binary per plugin.
5. **A browser matrix that is part of the repo:**
   - Promote `matrix-v3` into a maintained, schema-first conformance suite, with per-check fixtures, fresh contexts and accessible selectors only.
   - Run it in parallel with one browser context per area against a warm server pool.
   - Most failures in this pass were harness issues, so stable aria-first selectors pay off immediately.
6. **Guard laws in CI for build-shape regressions:** the wasm locals guard, wasm size budgets, and per-command turn and crossing budgets (as with selection), so performance and transpile regressions fail at the law level, not in the browser hours later.
7. **Remove leftover `[DEBUG]` diagnostics behind a feature flag:** boot diagnostics flood the console and the logs, slowing analysis; a typed trace channel can be switched on per run.
8. **A one-command native fallback (`fem-dev up`):** build, describe, materialize, serve and smoke-boot, with the known Windows pitfalls handled (os error 206 path length, `STATUS_ACCESS_VIOLATION` retry, cold-vite warmup). This would save every new agent its first 1–2 hours.
9. **A cancel-safe launcher:**
   - The app's task-kill walking stale PIDs forces detached launches and kills unrelated cargo trees.
   - A small process supervisor owned by `repo` (job objects on Windows) would make long runs safe to start from any agent.
