## Consolidation (specified, not implemented)

One place, the group server (`g1-server`, the only machine with the `relay` and the archive), in a new `consolidate` command run by the relay once a day, under a store lock `v1/git-consolidation.lock` (mkdir, refreshed, like `compaction.lock`):

1. Preconditions (else skip and report): every local `.pack` is published (`unpublishedPacks` empty), no queued object put, no `.git/*.lock`, `fleet` settled on objects, free space ≥ new pack + reserve.
2. Write: `git pack-objects --revs --all --reflog` (HEAD, refs, reflog, stash) with `--cruft` for unreachable objects younger than 14 days into the store `tmp` (never into `.git/objects/pack`), `index-pack`/`verify-pack` it, check with `planPacksV1` that every object of the packs to be retired is in the new pack or is unreachable and older than 14 days.
3. Publish atomically: move `pack`, then `rev`, then `idx` into `.git/objects/pack` (a reader sees a pack only with its idx last, as git writes); the replica publishes `.pack` first, then companions (existing rule). Write `<stem>.keep` for it.
4. Retire only after every attested origin reports the new pack applied (`attest` extension: pack stems present), the covered stems and all their companions and `multi-pack-index` are deleted by the server; the existing rules (deletes after all creations, `pack-incomplete`) carry the deletes to the workers. The 02:03 incident was step 4 before step 3; the order above cannot produce it.
5. Workers never repack; the config hardening (above) and the `.keep` keep clients from doing it.

Expected: 26.5 → ~4-6 GiB in `.git` on each of 8 machines, ~20 GiB fewer blobs after the compaction age.
