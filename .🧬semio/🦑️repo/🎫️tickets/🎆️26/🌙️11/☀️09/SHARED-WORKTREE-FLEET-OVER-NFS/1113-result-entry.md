## Problem and answer

Every service definition ran `repo ./📜️script.ts run` inside the replicated worktree, so a broken `📜️script.ts`, a broken file it imports statically, a `repo` launcher that cannot resolve the workspace inside the worktree, or a missing worktree bricked the machine, and replicated code is written by other machines. The service entry now lives outside the worktree and is installed, hash-verified and kept current by the daemon itself.

## Built

1. **Installed boot program** (`🔁️replica/🥾️entry/`: `🟨️.mjs`, `🐚️.sh`, `🔵️.ps1`, `🟦️.ts` (daemon side), `🧬️schema`, tests). Installed as `boot.mjs`, `boot.sh`, `boot.ps1` with `worktree`, `entry.json` (schema `EntryManifest`, written last), `boot.prev.mjs`, `state.json`, `refused.json`, `code/<digest>/`.
   - **Location per OS** (per account, writable without privilege, outside every worktree, found by the same rule in four places, fixture-tested for all three systems): macOS `~/Library/Application Support/semio/fleet/entry` (not under Documents/Desktop, so no consent prompt, survives a relocation, and is not the replicated tree; `~/Library/Caches` was rejected because the system may purge it), Linux `$XDG_DATA_HOME/semio/fleet/entry` (default `~/.local/share/...`, durable user data, not a cache), Windows `%LOCALAPPDATA%\semio\fleet\entry` (per user, local, never roamed). `.cache/f` was rejected: it is inside the worktree, which is exactly what can be missing or wiped.
   - **Shim** (`boot.sh` / `boot.ps1`, dependency-free): finds a runtime in the order `repo` launcher inside the worktree (keeps the macOS consent of the launcher), newest cached bun, `bun` on the path; runs `boot.mjs`, then `boot.prev.mjs`; ends only for exit 0/75, after 20 s of running or on a stop signal; otherwise waits (2 s doubling to 60 s) and tries again, writing `shim.txt`.
   - **Boot program** (`🟨️.mjs`, Node built-ins only): order worktree supervisor (as the `--boot-child` process with the readiness, early-failure, watchdog and kill rules of the old supervisor), newest intact sealed snapshot (`<worktree>/.cache/f/code`, `<entry>/code`; every file hash checked), hash-verified store snapshot (`<store>/v1/bootstrap/code/<digest>/`, ranked by fresh attestations, per-file sha256/bytes, fetched into `<entry>/code`), then the worktree code forced when it was refused only as a revert. A failing snapshot is refused for an hour. It never exits by itself: with nothing runnable it writes `state.json` (schema `EntryState`: phase `starting|running|waiting|exhausted`, source, digest, reason, last attempts, next try) and polls with a doubling backoff (5 s to 5 min); a missing worktree is phase `waiting` and the code starts when the worktree appears. It stops on a stop signal and, since version 2, when its parent (the shim) dies, taking its daemon with it.
   - **Update by a healthy daemon** (`maintainEntryV1`, called after the self-check passed at every start and hourly): version compared with `entry.json`; higher version → proven by `selfTestV1` (throwaway worktree: a supervisor that starts is found ready and stopped; a failing supervisor falls back to a sealed snapshot that starts), installed through temp files and renames (previous kept as `boot.prev.mjs`, manifest last) and read back against the hashes; lower version refused (`refused-downgrade`), same version with other bytes refused, damaged installation repaired, failed self-test refused with installed files and manifest byte for byte unchanged (`refused-selftest`, failure kind `entry-boot` in health and attestation), another worktree's installation not taken over (`refused-foreign`, only provisioning and relocation pass `--take-over`; this stops a test or a scratch checkout from redirecting the service of a machine).
2. **Service definitions** (`🗺️topology/🟦️.ts`, `entryDirectoryPathV1`): systemd unit `ExecStart=/bin/sh <home>/.local/share/semio/fleet/entry/boot.sh run`, macOS agent `/bin/sh <home>/Library/Application Support/semio/fleet/entry/boot.sh run`, Windows task `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<home>\AppData\Local\semio\fleet\entry\boot.ps1" run`; none has a working directory any more (a missing working directory also fails a launchd job with 78 and a systemd unit with 200/CHDIR). Compact and relay keep their definitions. Provisioning installs the program before rendering the service (`🐚️.sh` step 6a, `🔵️.ps1` step 7b, both `--take-over`), fills `__WORKER_HOME__` for Windows, and relocation detection reads the entry's `worktree` file first.
3. **Migration of machines that already joined, without a human where possible.** `📜️script.ts` is now a 56-line trampoline (Node built-ins only, import-safe, 4.5 KiB); the old content moved to `🔁️replica/🛟️supervisor/🟦️.ts` (module exports `scriptMainV1`; stage copy, snapshots and `--boot-child` use it). For `run` the trampoline hands over to the installed shim when `entry.json` names this worktree and shim and program match their manifest hashes (and uses the supervisor when the shim fails within 10 s); everything else runs as before. The first healthy start of the new code installs the boot program, the next service restart takes it, no privilege. Additionally a macOS account that owns its LaunchAgent gets the plist rewritten by its own daemon (`migrateAgentV1`: exact rendered shape only, `plutil -lint`, previous kept). Windows tasks are re-registered by the worker account without elevation (prompt (c)).
   - **Guard**: `entryGuardedV1` / `admitEntryScriptV1` in `materialise`: an incoming change to `🔁️replica/📜️script.ts` is applied only if it is under 16 KiB, imports only `node:` built-ins statically, prints `trampoline-ok` for `--trampoline-self-test` and hands a command and `run` without boot program to a stub supervisor (run in a throwaway directory). Otherwise the previous content stays, event `refused` (`entry-guard: …`) and failure kind `entry-guard` show it, a later good change applies.
   - **What remains privileged**: the service definition of a machine that still has the old one (LaunchDaemon plist, systemd unit) keeps running `repo ./📜️script.ts run` until someone with root changes it; exact commands per OS in `1113-entry-prompts.md` (a) macOS system daemon, (b) Linux, (c) Windows without elevation. Until then the single points of failure are the `repo` launcher, the working directory and the trampoline file, and the trampoline is guarded.
