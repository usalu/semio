## Details for P0 and P1

### 1. P0: self-restart without self-check

- Location: `🔁️replica/🟦️.ts:1486-1501` (the loop breaks on `restart` from the attester, then `closeReplicaV1` and `restarting`); `🩺️attest/🟦️.ts:293-298` (restart after the code digest differs and is stable for `stable` ms, default 5 s); `⌨️command/🟦️.ts:289-299` (exit code 0), `:341-343` (busy lock exits 1, other errors rethrow). Code digest `attest:81-92`.
- Confirmed: the restart decision does not compile or import the new code. The new process loads the module graph with static ESM imports; any missing export or syntax error fails at start.
- Scenario A (broken commit): a committed module change with a syntax error or a missing import reaches a daemon. After 5 s of a stable digest, the daemon exits 0; the service manager starts the new code; it fails; `KeepAlive` (launchd) or `Restart=always` (systemd, README 118-119) restarts it again and again.
- Scenario B (half delivery, deadlock): change to three files A, B, C where B is in cooldown (`cooling` at replica:1299, 1307, 1317 gives up to 30 s; or a `blocked` sharing violation at 1288). A and C are new on disk, B is old; the digest is stable for 5 s; the daemon restarts; the new A imports a symbol that only B's new version provides; the process fails at import. B is never materialised because only a live daemon materialises files.
- Consequence: all replicas on the affected machines stop, including the attester. The corrective commit is a file in the replicated worktree, so nothing can deliver it. Recovery needs physical or SSH access on each machine. README 118-123 and contract "Self-restart" describe the restart as safe; no guard is in code.
- Fix direction: (1) before `return "restart"`, run the new code in a child process (import the entry point and the module graph, or run `status --json`) and exit only on success; otherwise keep the old code running and emit `restart-refused`. (2) Restart only when no queue item lies under the module path. (3) Keep a last-known-good copy outside the replicated tree, so a service can start the previous code. (4) Service definition: crash-loop breaker (`StartLimitBurst`/`StartLimitIntervalSec` or a launchd equivalent) that falls back to last-known-good.

### 2. P1: forward clock jump freezes an origin and survives restarts

- Location: `replica:826-827` (own clock adopted from own head with bound `Number.MAX_SAFE_INTEGER - 60000`, so no future bound applies), `:887` (clock persisted), `:920` (`mint`), `:1364-1366` (`admit` holds events more than 60 s ahead), `:1406-1408` (`held` until wall catches up); `journal:63-68` (`mergeClockV1`), `:84-87` (`winsV1` is string compare, equal never wins).
- Scenario: machine M runs with its wall clock one hour ahead, publishes events at `hlc = wall + 1h`, then its clock is corrected. On restart, `openReplicaV1` takes `max(clock.json, own head hlc)` with no upper bound, so M keeps minting `+1h` values until the wall clock catches up. Every other machine holds M's origin from the first future event (`replica:1408`).
- Consequence: M's writes are unapplied fleet-wide for the skew duration (verdict `lagging`); M's later writes beat any newer write by another machine to the same path in that interval (`winsV1`); the loser goes to `lost/` only on machines that overwrote it (`conflictWinnerV1`, `replica:1241`, and `keepLost`).
- Fix direction: at open, cap the restored clock at `wall + 60 s`; in `mint`, never issue a value above `wall + 60 s`; if the own journal already holds future events, emit a `clock-reset` event and refuse to publish until the wall clock catches up instead of silently continuing.

### 3. P1: stage publish silently disabled; apply resets the local index

- Location: `git:240-242` (`readKnown` swallows parse errors; a corrupt file becomes `tree:null`), `:251` (`writeKnown` swallows write errors), `:285` (`before===""` returns silently), `:287` (`write-tree` null returns silently), `:299` (`known.tree===null` returns `waiting` with no event and no `writeKnown`), `:300-301` (`diff-tree` null returns silently), `:352-358` (apply: `read-tree` when `local!==known.tree`).
- Scenario A (lost record): `.cache/f/git-index.json` is truncated (no fsync, `:249-251`). `publishIndexV1` returns `waiting` (`:299`) and does not write the record. `applyIndexV1` returns early when there are no pending registers (`:323`); otherwise `:357` does `read-tree` to the base, replacing the local index, so unpublished local staging is lost. Until a remote register arrives, the record stays `null` and nothing publishes.
- Scenario B (`.git` replaced): the old `known.tree` object no longer exists. `diffTreeV1` returns null (`:145`), `publishIndexV1` returns `none` (`:301`) on every round, silently. Apply then fails `diffTreeV1(known,baseTree)` (`:355`) and `ok=false`, which is `blocked: index-busy` (`:360`), so the stage is stuck until someone requests `rebase`.
- Consequence: no event, no verdict. `status` still prints `shared` (`replica:1807`, based on the base register only). The machine's stage diverges from the fleet and nothing heals it except `rebase`, which replaces every machine's stage with this one.
- Fix direction: make the known tree explicit in the journal (write it as a register of this origin, or rebuild it from own journal on start); treat a missing record or missing object as an error event and a publish request, not as `waiting`; `status` should report `stage: diverged-local` when publish is disabled.

### 4. P1: base publish voids other machines' staged entries and resets local indexes

- Location: `git:302-308` (more than 5000 changes publish a new base), `:334` (entries with `hlc <= base.hlc` are voided), `:352-358` (apply computes the delta to the base or `read-tree`s it), `:364` (voided entries are settled); README "Stage" bullet and `1113-rollout.md` line 20 (known: unpublished worker stage replaced at first start of new code).
- Scenario: machine A runs `git add -A` of 6000 files; A publishes a base at hlc `H1`. Machine B published three staged entries at `H0 < H1` a moment earlier. On B (and every machine), `:334` voids B's three entries. B's `applyIndexV1` computes the delta from B's known tree (which included its own entries, published at `:325`) to A's base (`:354-356`), so B's local index loses its three entries as well.
- Unmerged variant: a user in a merge or rebase (forbidden, but possible) has unmerged entries; `writeTreeV1` returns null (`git:133-134`); `publishIndexV1` returns `none` (`:287`); apply then takes `readTreeV1` (`:357`, since `local===null`), discarding the unmerged state of the local index.
- Consequence: staged state disappears silently on the fleet and on the machine that staged it. The worktree files are untouched, but staging, and any commit built from it, differs from intent. Verdict stays `ok` because all machines agree.
- Fix direction: a base must only supersede the publishing origin's registers (per-origin base), or it must carry the set of registers it intends to replace; never reset a local index while `write-tree` fails (conflict state must be preserved, and the apply should be deferred); make `rebase` warn about discarding other machines' staged entries.

### 5. P1: crash window between publish/apply and the known-tree record

- Location: publish: `git:294` (`host.emit` then `writeKnown` at 294), `:305`, `:315`; apply: `git:359` (`updateIndexV1`), `:363` (`writeKnown`); caller `replica:1128-1130`, `:1326-1327`.
- Scenario A: `host.emit` appended entries (`replica:747-758` appends, sets cursor and state), then the process is killed before `writeKnown` (`git:315`). On restart `publishIndexV1` compares the stale known tree with the local tree (`:300`) and emits the same diff again with fresh hlc (greater than any other register the fleet published in the meantime, `winsV1`). Result: a newer register published by another machine in the meantime is overwritten by a re-emitted value (silent revert).
- Scenario B: `updateIndexV1` succeeds (`:359`), process killed before `writeKnown` (`:363`). On restart, the publish step runs first (`:325`), sees the applied remote entries as local changes (`known.tree!=local`), and re-publishes them as local edits with new hlc. This is the publish-first rule of the contract being violated by the crash window.
- Consequence: remote stage state is re-attributed to the local machine after a crash during a stage update; a newer register can be reverted. This is the g1-m03 class (state says one thing, disk or journal another) in the git realm.
- Fix direction: write the intent before the side effect (`pending: {tree, hlcs}` in the record, compare on restart), or derive the known tree from the own journal; never re-emit a path whose own journal entry already matches the local tree.

### 6. P1: linearisation reverts the winner's other changes on the branch tip

- Location: `git:474-482` (`mergedTree`: `read-tree -m --aggressive`, then `writeTreeV1(index)` returns null when any path is unmerged, then `?? theirs` returns the loser's whole tree; also `:480` for `read-tree` failure); `:513-514` (uses `mergedTree`); README "Concurrent commits", bullet "Rewrite", which says "a path both sides changed differently takes the original tree" (per path); `writeTreeV1` null at `git:133-134`.
- Scenario: from parent P, commit cA (winner, higher hlc) changes F1 and F2; commit cB (loser) changes F2 differently and F3. On the loser's machine, `linearizeRefV1` re-creates cB on cA. For F2 both sides changed, so the merged index has an unmerged entry; `writeTreeV1` returns null; the code uses cB's whole tree, so F1 reverts to P in the new tip. Only the conflicting path is documented to take the original.
- Consequence: silent content regression on the branch tip for paths the loser never touched. Recoverable from the winner commit (an ancestor), but nothing reports it; event `linearised` says `rewritten` only.
- Fix direction: resolve per path: a path the loser did not change keeps the winner's blob; for a path both changed, keep the loser's blob (as documented) and emit a `conflict` event naming the path; never fall back to the loser's full tree.

### 7. P1: local state without fsync; torn files crash the daemon at start

- Location: `replica:532-541` (`readJson`: parse error rethrown at 533; `writeJson`: no `sync` before `rename`, line 539), `:842-858` (`checkpoint` writes `state.json` without fsync, renames at 857), `:609-667` (`replayLog`, `loadState`, `loadLocal`: parse errors throw at 616, 647, 659-660), `:820-836` (open: errors release the lock and rethrow); `git:249-251` (`writeKnown`, no fsync).
- Scenario: power loss after the rename of `state.json` (or `clock.json`, `cursor.json`) but before its data reaches disk leaves a zero-length file. **Unconfirmed trigger:** depends on the filesystem (ext4 `auto_da_alloc` covers some rename cases; APFS and NFS do not promise it).
- Consequence: `openReplicaV1` throws (`:533` rethrow, `:647`). `runV1` never starts; the command rethrows (`command:342-343`) and the service restarts it forever. Recovery is hand-deleting `.cache/f/state.json`, which forces a full rehash and rejoin.
- `git-index.json` variant (`git:241-242` swallows the parse error): silent, see finding 3.
- Fix direction: fsync the temporary file before rename and the directory after; on unparsable local state, move it aside to `.cache/f/lost/state-<ms>.json`, emit one `error` event and rebuild from the store (rehash path already exists).

### 8. P1: no timeout on store I/O or git; a stalled mount freezes the loop

- Location: `replica:519-521` (`storeReachableV1` is a `stat` with no timeout), `:1457` (loop calls it every round), `:1091` (`appendEventsV1` on the store), `:1466-1496` (single awaited loop body and pause); `attest:309` (`reachable()` inside `tick`); `git:95-114` (`git()` spawns with no timeout; `abort` only via caller signal); `attest:283-287` and `:301-304` (`viewBusy`/`gitBusy` promises that never resolve block all later refresh).
- Scenario: the group server reboots while workers mount with `hard` (the plan uses `hard`, README "Client caches" and `preflight` checks `hard`). A `stat` or `open` on the store blocks in the kernel; the single loop awaits it.
- Consequence: no `store-unreachable` event (the check itself hangs); local publish stops (`:1091` and the loop); attestation stops (`attest:309`), so `fleet` goes stale; a hung `git status` leaves `view` stale forever, so `view.digest` diverges.
- Fix direction: run store I/O (reachability, append, head read) in a separate task with a timeout that abandons the promise and reports `store-unreachable`; add a kill timeout to `git()`; have the attester's heartbeat independent of store I/O; give `viewBusy`/`gitBusy` a timeout that clears them.

### 9. P1: lock is a pid probe with a racy steal; survives reboot

- Location: `replica:555-564` (`readLock`: `alive(pid)` at 560, stale for pid 0 after 5 s at 563), `:566-588` (`acquireLock`: `wx` create at 571; steal by rename at 578-581; `ReplicaBusyV1` at 584 and 587), `:820-822` (`reclaimStagingV1` after acquire); `journal:216-220` (two writers of one segment truncate each other).
- Scenario A (reboot): `.cache/f/daemon.lock` survives reboot. After reboot the recorded pid belongs to an unrelated process; `alive()` returns true (`:560`); `acquireLock` throws `ReplicaBusyV1`; the command exits 1 (`command:341`); the service restarts it; the loop repeats until the lock is removed by hand.
- Scenario B (steal race): two starters read the same stale lock; starter 1 renames it away and creates its own lock; starter 2 then renames starter 1's fresh lock (`:580`) and creates another; two live daemons for one origin. **Unconfirmed trigger**: needs two starts at the same moment (service restart overlapping a manual `run`).
- Consequence: crash loop, or two writers on one origin, which corrupts the journal (truncation at `journal:220`).
- Fix direction: OS advisory lock (`flock` / `LockFileEx`) held by the process, released by the kernel on death; no pid probe needed; remove the rename-steal path.

### 10. P1: origin id is not enforced as unique; join does not check it

- Location: `replica:924-932` (`ensureHome` writes `home.json` only when absent), `:1560-1608` (`joinV1`: no check of an existing origin directory, head or attestation); `journal:84-87` (equal hlc never wins), `:196-232` (`appendEventsV1` truncates to its own head, `:220`); README "Add a machine" (warns, does not enforce).
- Scenario: a machine is provisioned with `--origin g1-m02` while g1-m02 exists. Both write `origins/g1-m02/segments` and `head.json`; each truncates the other's tail (`journal:220`); both mint hlc with the same millisecond and counter; `winsV1` never replaces an equal value, so each machine keeps its own winner.
- Consequence: events lost in the store; permanent silent divergence (no verdict names the cause; `fleet` shows `diverged`, not "two machines").
- Fix direction: create `origins/<id>/origin.json` with an exclusive create at join, containing a machine key; refuse join when the origin already has a head or a different key; add the machine key as the final tie-breaker in the hlc.

### 11. P1: fleet verdict is blind to daemon code; a skewed writer makes a dead daemon fresh

- Location: `attest:215` (voted fields: manifest, head.commit, indexTree, view.digest; `code` is not voted), `:218-247` (`judgeFleetV1`), `:224` (`Math.max(0, age)` clamps a negative age to 0), `:227` (fresh if `age <= 60`); README "Attestation" bullet on `fleet` (the same four fields).
- Scenario A: one machine runs old daemon code (rollout), with the same manifest and heads. `fleet` exits 0.
- Scenario B: writer clock ahead by 3 min; its daemon dies at T; its `wallMs` is `T + 180 s`; for the next four minutes `age` is clamped to 0 and the origin counts as fresh and settled.
- Consequence: a rollout can be declared complete while code differs; a dead machine can satisfy the verdict for the skew amount.
- Fix direction: vote `code` as a fifth field; compute `age` as `now - wallMs` and treat a negative age as `stale`; document that the reader's clock must be NTP-synchronised (`preflight` does this, but `fleet` does not check it).

### 12. P1: a corrupted blob is trusted forever

- Location: `journal:173-176` (`writeBlobV1`: existing target returns `false` without hashing), `replica:1857-1859` (`relayBlob`: existing destination returns `false` without hashing), `:1272-1277` (materialise: hash mismatch becomes `blob-missing` reason `blob-corrupt` and `queued`), `:1317` (cooling retries every 30 s).
- Scenario: a blob file in the group store is corrupted (bit rot, or a write that reported success and was damaged). A worker saves the same content again: `prepare` (`:946`) calls `writeBlobV1`, which sees the file and skips it.
- Consequence: every receiver of that content queues the path forever (30 s back-off). The store never repairs itself. Only a different content for the same path or a manual store repair helps.
- Fix direction: re-hash an existing blob on write and on relay (cost acceptable: blobs are immutable and content-addressed); on mismatch, rewrite from the local source or from the other group store; the materialise side should try the other group store before queueing.

### 13. P1: missing or short segment stalls publish; a snapshot can be written from an incomplete fold

- Location: `journal:216-220` (`appendEventsV1`: `throw` at 219 when the segment is shorter than its head), `replica:1489` (error event every round, not noted); `replica:1521-1539` (`foldInto`: `rejoin-required` and `break` at 1537-1538), `:1617-1626` (`snapshotV1` writes regardless of folds that reported `rejoin-required`), `:1663` (`incomplete` only gates deletion); `:1344-1358` (`recoverFromSnapshot` relies on the newest snapshot).
- Scenario A (publish stall): `head.json` says `bytes=N` but the segment file is shorter (store crash without fsync on the store side, or manual removal). `appendEventsV1` throws at `:219` on every publish; no code path repairs head or segment (`repair` at `:703-724` does not touch segments). The origin publishes nothing; the error repeats every 250 ms.
- Scenario B (snapshot): a sealed segment of origin X is missing. `foldInto` reports `rejoin-required` and stops folding X (`:1537-1538`). `snapshotV1` writes a snapshot with a manifest without X's later events and cursors that do not cover X. This snapshot is the newest one by hlc (`journal:419-445` sorts by hlc). Machines that join later use it as base.
- Consequence: local publish of that origin stops without a repair path (A); new joiners get a manifest that silently lacks X's events and must re-enter the rejoin path (B). Fleet verdict for existing machines is unaffected, which hides B until a join is attempted.
- Fix direction: `snapshotV1` must refuse when any origin's fold reported `rejoin-required`; `appendEventsV1` should truncate to the last complete line of the segment and report `journal-repaired` when the segment is shorter than head (never publish a head that the segment does not hold); add the check to `verify`.

### 14. P1: closed event schema makes an unknown event a permanent stall for old daemons

- Location: `journal:90-94` (`requireEventV1`, closed schema; path check), `:293-294` (corrupt line throws); `replica:1395-1401` (`followOnceV1`: error is noted once, origin is skipped, cursor does not move).
- Scenario: a new daemon writes an event with a new field or operation (for example a new kind of register). An old daemon reads that origin: the line fails the closed schema; `readEventSpansV1` throws; the origin is skipped on every round with the error noted once per process.
- Consequence: silently (after one note) the old daemon never applies that origin again. `fleet` shows `lagging` for it, with no reason. Mixed-version rollouts (the contract's own model) therefore have a poison-pill failure mode.
- Fix direction: add a schema version to events; an old daemon should advance past lines whose version is newer, emit `unknown-event` with the origin, and count them in `status`.

### 15. P1: no automatic healing of divergence

- Location: `replica:691-724` (`repair` request, consumed on the next pass), `:1466` (only trigger); `rebase` request path at `git:290-295`; `fleet` (`command:255-271`) reports but never triggers a repair.
- Scenario: a machine misses register updates (the g1-m03 case in `1113-rollout.md` lines 43-48 needed a manual `repair`), or the store diverges from local state; `fleet` exits 1.
- Consequence: divergence persists until a human issues `repair` or `rebase` on that machine. `rebase` replaces every machine's stage (finding 4).
- Fix direction: periodic self-check against the folded store (the `verify` logic, cheap for the manifest and the stage tree); on mismatch queue the repair automatically with back-off and emit `drift`; keep `rebase` manual and make it show the list of entries it would discard.

## Notes for the robustness requirements

- Focus 1 (idempotence): publish and apply are idempotent per step except the windows in findings 3, 5 and 7. The journal append is idempotent through the head truncation (`journal:220`), and state replay after a crash is idempotent by hlc (`replica:790-811`).
- Focus 2 (store outage): an `ESTALE`/`EIO` during append is a non-sharing error, so it fails the round and is retried; a hung mount is finding 8. A partial write is recovered by the truncation at `journal:220`; a head ahead of its segment is finding 13.
- Focus 3 (git interplay): `index.lock` is handled as a retry (`git:360`); `git write-tree` does not need it. Finding 4 covers the forced base and unmerged cases. Objects arriving after refs: a ref is materialised without checking objects (`replica:1216-1219` only for `put` on branch refs, and linearise retries on missing objects); transient unreadable refs are possible; **unconfirmed** impact.
- Focus 4 (old daemons): the new code drops realm paths only through the sealed-path filter; no path loses registers silently inside the new code except through the snapshot gap (13) and `dropped` outcomes (`replica:1212-1213`, ignored paths). Detection exists in `fleet` only (finding 15).
- Focus 5 (clocks): finding 2 and finding 11; a wall clock that jumps backward is handled by the monotonic `tickClockV1` (`journal:55-61`), but the attestation `wallMs` goes backward too (`attest:313`).
- Focus 6 (growth): `lost/` (finding 18), `noted` (18), path table (18), `view.txt` rewritten whole on every change (`attest:146-149`, a 270k-file dirty tree makes that file large); journal segments are bounded only by `compact`, which is a daily job per origin.
- Focus 7 (self-restart): finding 1 (including the half-delivery deadlock and the restart storm of finding 25).
- Focus 8 (swallowed errors): listed in finding 16; the `noteOnce` keys that hide recurrence are `blocked:journal:<code>` (`replica:761, 1098, 1117`), `error:git:<message>` (`:1129, 1327`), `error:<path>:<message>` (`:1314`), `error:<origin>:<message>` (`:1382, 1400`), `attest:<message>` (`:1493`).

## Unconfirmed items (could not be settled from the code)

- Whether `git gc`/`prune` deletes of loose objects that another machine's stage still references cause missing objects (finding 20). The journal publishes deletes for shared `objects/**` (`boundary:185`), so the mechanism is there; the interleaving is not confirmed.
- Whether a `packed-refs` rewrite racing a loose-ref delete can rewind a branch on a receiver (finding 20). Only loose `refs/heads/**` and `HEAD` get linearisation (`boundary:173-187`, `replica:1191-1208`); `packed-refs` is last-writer-wins.
- Power-loss behaviour of the store and the local disks (finding 7).
- Whether a `hard` mount really blocks the daemon thread on the platforms in use (finding 8). The code has no timeout either way.
- Whether a segment file can be shorter than its head on a real store (finding 13A).
- Whether a truncated or corrupt blob arises in practice (finding 12).
