# Git State Contract (2026-11-13)

Supersedes the file-level `.git` sharing described in `git-state.md`. Repo MCP did not connect in this session, so the ticket bookkeeping is manual.

## Faults observed on the live fleet (g1-server, g1-m01, g1-m02, g1-m03)

- `.git/index` (69 MB) is published as a raw file. It holds per-machine stat data (ctime, inode, device), so every `git status` on one machine rewrites it, the others apply it, refresh it, and publish it back. g1-m01 and g1-m02 alternate two blobs forever.
- `.git/logs/**` is shared. Every machine appends its own reflog line on each auto-fetch; the appends overwrite each other about once a minute (`overwritten` events, files in `.cache/f/lost`).
- `.git/config` is shared. It holds per-OS keys (`core.filemode`, `core.ignorecase`, `core.symlinks`, `core.precomposeunicode`) and machine paths (`commit.template`). A Windows or Linux worker receives the macOS values.
- IDE files in `.git` (`compose-*`, `cursor/`, `gkcommittemplate.txt`, `hooks/`, `FETCH_HEAD` variants) are shared.
- Nothing proves that all workers hold the same state. `status` shows only event lag.
- A daemon keeps running old code after the module's source replicates to it.

## Shared git state

Allow-list inside the root `.git` (everything else in `.git` is private to the machine):

- `HEAD`, `packed-refs`, `shallow`
- `refs/**`
- `objects/**` except names starting `tmp_`, names ending `.lock`, `objects/info/alternates`

Private therefore includes `index`, `index.lock`, `sharedindex.*`, `logs/**`, `config`, `hooks/**`, `info/**`, `description`, `FETCH_HEAD`, `ORIG_HEAD`, every in-progress operation file, and every IDE file.

A path that becomes private (boundary change or `.gitignore` change) is forgotten locally. A delete MUST NOT be published for it. Incoming events for a private path are dropped.

## The shared index (stage)

The index is not a file on the wire. It is a register per path plus one base register, carried by the existing `link` operation in a virtual realm under the sealed directory, so no version of the daemon can mistake it for a worktree file:

- Base: path `.cache/f/index`… is not usable (it would be the parent of the entries), so the base is `.cache/f/index-base`, `link` target `tree <oid>`.
- Entry: path `.cache/f/index/<worktree path>`, `link` target `<mode> <oid>` (stage 0 only), or `delete` = the path is absent from the index.
- Effective index = tree of the base, overlaid by every entry whose HLC is greater than the base's HLC. An entry older than the base is void.
- Per register, last writer wins by HLC (`winsV1`). No mtime rule, no `lost` copy.

Publish (local stage detected): on a change of `.git/index` (watcher) and on every scan, `tree = git write-tree`. Equal to the known tree: nothing. Otherwise `git diff-tree -r -z <known> <tree>` gives the changed paths; each becomes one entry event. The known tree is the fold of the registers this machine has published or applied, so it needs no record file and survives a crash between a publish and its bookkeeping. However many paths differ, they become entries, appended in batches of 5000; a base (`tree <oid>`) is published only when the manifest has none yet (group server) or when `rebase` is requested, never for a large change, so no register staged elsewhere is voided by a bulk stage. `rebase` reports every register whose value differs from the stage it publishes (event `published` with `reason` `rebase` and `count`, and `.cache/f/lost/rebase-*.tsv`: path, origin of the register, `<mode> <oid>` or `absent`). A stage that cannot be written (unmerged entries, failing git) is not published and is reported; a missing `.git/index` is restored from the registers and publishes no delete. `write-tree` creates tree objects in `.git/objects`; they replicate as files.

Apply (remote stage): always run the publish step first, so a local unpublished stage is never attributed to the remote. Entries: one `git update-index --index-info` batch (mode `0` removes). Base: `git read-tree <oid>` (index only, the worktree is not touched), then re-apply entries newer than the base. A stage with no proof of its origin (no register of it applied yet, lost state) is replaced by the shared fold after its index file is copied to `.cache/f/lost/index-*` and an `overwritten` event names the number of replaced entries; a stage that `write-tree` cannot write (unmerged entries) is never reset. The paths being written are recorded in `.cache/f/git-index.json` before the write and cleared after the registers are settled; after a crash they are not published as local edits. Missing object or `index.lock` held: the event stays queued and is retried with back-off from 1 s to 30 s. After apply, known tree = `git write-tree`.

Stage health: `.cache/f/git-index.json` (`{version:1, state:"shared"|"waiting"|"degraded", reason, since, applying}`, tmp + fsync + rename) records why sharing waits (`waiting-for-base`, `objects-missing`, `index-busy`) or is degraded (`unmerged`, `write-tree-failed`, `git-failed`, `index-lock-stale` after ten minutes, `backup-failed`). Every change emits one `blocked` (or `repaired` on return to `shared`) event and `status` shows it; no waiting or degraded state is silent.

A commit does not change the index, so it publishes nothing in the realm. It replicates as objects plus the ref file.

Concurrent commits: branch refs (`refs/heads/**`, and `HEAD` while detached) are linearised by the machine that authored the losing value, with plumbing only. When a remote ref `put` is applied over a local ref value that was written on this machine (published by this origin, or changed since the last published value) and that is neither equal to nor an ancestor of the incoming commit, every local commit missing from the incoming history is re-created oldest first with `git commit-tree` on top of the incoming commit (one parent, author, author date, committer and message kept, tree = the per-path three-way merge (`diff-tree` base to tip and base to original: a path only the original changed is taken, a path only the tip changed stays, a path both changed identically stays, a path both changed differently takes the side with the later committer time with the tip winning ties, never a whole tree), the ref moves with `git update-ref` against the old local value, and the next scan publishes it as an ordinary ref change. The `linearised` event carries the number of conflicting paths in `count`. A commit that adds nothing to the new tip and repeats the tip's message, or repeats an author line and message of the incoming history, is dropped. An ancestor local value is a fast-forward; an incoming ancestor keeps the local value; a local value applied from another origin, `refs/remotes`, `refs/tags` and `packed-refs` stay last writer wins. Missing objects or a moved ref keep the event queued (`blocked`, `objects-missing`; after five minutes again as `objects-missing-timeout` with the waited seconds). Detached `HEAD`, new branches and tags need no extra rule: `HEAD` of a detached worktree is linearised like a branch, new branches and tags are plain last writer wins. Every hlc round has one winner that is never rewritten, so n concurrent commits need at most n-1 rounds; the replica emits a `linearised` event with winner, loser and result.

Join: `read-tree` the base, apply the newer entries. Verify: fold base ⊕ entries in a temporary index (`GIT_INDEX_FILE`), `write-tree`, compare with the local `write-tree`.

A worktree without a root `.git`, or a machine without `git`, skips the realm entirely (events stay unapplied in state, no error loop).

## Per-machine git configuration

At daemon start and at join, `.git/config` is normalised locally through git itself: `core.autocrlf=false`, `core.safecrlf=false`, `core.eol=lf`, `core.protectNTFS=true`, `core.protectHFS=true`, `core.longpaths=true` on Windows, `core.filemode` (false on Windows, true elsewhere), `core.symlinks` and `core.ignorecase` from a probe of the worktree volume, `core.precomposeunicode=true` on macOS, `core.fsmonitor=false`, `core.untrackedCache=true`, `index.version=4`, `gc.auto=0`, `maintenance.auto=false`, `core.logallrefupdates=true`. Remote, branch and user sections are kept. A `commit.template` that points outside the worktree is removed.

Every git process of the replica is pinned (the same list on every operating system): `GIT_CONFIG_NOSYSTEM=1`, `GIT_ATTR_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` and `XDG_CONFIG_HOME` at an empty file and directory below `.git/semio-pin/`, no inherited `GIT_CONFIG_*`, and `-c core.excludesFile=`, `core.attributesFile=`, `core.quotepath=false`, `core.precomposeunicode=true`, `core.autocrlf=false`, `core.safecrlf=false`, `core.eol=lf`, `core.longpaths=true`, `core.protectNTFS=true`, `core.protectHFS=true`, `core.fsmonitor=false`, `gc.auto=0` (git 2.32 or newer). The attested view adds `core.ignorecase=false`, `core.filemode=false`, `core.symlinks=true`. On a volume that is case- or normalisation-insensitive the view adds ` D <path>` for tracked paths whose exact spelling is absent on disk and `?? <path>` for NFD-only spellings, so the lines equal Linux's. `.git/info/exclude` is a per-machine input that no flag removes; its rule count is a guard.

## Names, bits and guards across operating systems

- The case fold is NFC plus a generated code-point table (union of APFS, NTFS and Linux casefold); the path policy counts UTF-16 units (256) and `preflight` measures the absolute path against the real limit per operating system.
- The executable bit: on POSIX the disk is the truth; a volume that cannot hold it (Windows) keeps the manifest bit when a file changes, takes the staged mode for a new file, defaults to false and never writes; the view ignores the bit.
- `attest.json` carries `guards` (or `null` until measured): git version, pins hash, volume behaviour, `.git/info/exclude` rules, case-dependent ignore rules, case mismatches, tracked-but-ignored, refused tracked paths, links, paths over the budget, executable-bit mismatches. The verdict is `diverged` on a difference in `guards.pins`, `guards.infoExclude`, `guards.caseIgnore`, `guards.caseMismatch`, `guards.trackedIgnored`, `guards.trackedRefused`, `guards.modeMismatch` and lists capability differences as `warnings`.

## Structural conflicts (one path set that is valid everywhere)

- Two live manifest entries clash when their folded paths (`foldNameV1`) are equal or the folded path of a file or link is a directory prefix of the other. The rule is a pure function of the folded manifest: entries newest hlc first, an entry that clashes with a kept one is retired. Every machine derives it alone; no event is published for it, no machine waits for another, snapshots and compaction are untouched.
- A retired entry leaves the tree before its winner is written (lost copy in `.cache/f/lost/<winner hlc>/<path>`, `overwritten` and `superseded` events), its register becomes a delete with the hlc of the retired entry and its manifest row stays parked in the persisted queue, so the rule is re-evaluated after a restart and the entry returns when its winner goes away. `verify` does not report a parked entry as missing; `queue` does not count it.
- Git: the index realm is exempt (its paths are virtual). A retired path is absent from the tree, so `git status` shows the same deletion on every machine; the stage of a retired path follows its own register as usual.
- Apply never follows a symbolic link: every ancestor is inspected with `lstat`; a link of the fleet is an ordinary entry of the rule, a local-only link blocks with `symlink-in-the-way`. The publisher does not publish a path reached through a link.
- A `put` that repeats content the path had earlier while its `base` is not the content it replaces is a stale republish: it is not applied where the register still holds the replaced content (`stale-republish`), the newer content is published again.

## Change detection (tiers, hints, hook)

Nothing in the daemon depends on operating-system file events. Five tiers hand paths to one publish step per round (a path found twice is published once, because the publish compares size, modification time and hash with the recorded state); the recursive native watch is only an accelerator (`run` accepts `watch: false` in code).

- Hint tier: the drop directory `.cache/f/hints/` (sealed, local, mode 1777). A hint is a file of NUL- or newline-separated paths, absolute or relative to the worktree, created under a name starting with a dot and renamed inside the directory. The daemon polls the directory every 50 ms, reads finished files (at most 1 MiB each, at most 5000 paths per poll), removes them, drops paths outside the worktree or below `.cache/f`, matches absolute paths also through real paths, and publishes the paths in the next loop round without the 150 ms debounce. Unfinished (dot) files older than a minute are removed. `touch <path>…`, `touch --stdin` and `touch --hook` write hints; `touch --hook` reads a Claude Code `PostToolUse` payload, takes `tool_input.file_path` and `tool_input.notebook_path` and exits 0 whatever it reads or finds.
- Hot tier: the root and every directory up to three levels deep are checked with every pass (a create in the root is found within one pass). The paths this replica published, applied, was hinted about or saw from the watcher during the last 10 minutes (newest 20 000; a publish or apply of more than 500 paths notes none). One pass about every 300 ms (the interval grows to eleven times the CPU time of the pass) compares `lstat` with the recorded state (a racy entry is rehashed once its racy window has passed), checks the modification time of the directories that contain hot paths and the stat signature of `.git/index`, and publishes what changed.
- Directory tier: the modification times of the known shared directories (filled by every full walk, kept in memory). A pass `lstat`s every known directory in slices of 10 ms, starts at the earliest 2 s after the previous pass and after nine times the CPU time it used (10 % of a core), and lists again only the directories whose time moved (files of that directory, unknown subdirectories recursively; a recorded file that is no longer listed, and every file below a removed directory, is published as a delete).
- File tier: an `lstat` of every recorded path (every `--scan` seconds at the earliest, 90 by default, jittered, and after nineteen times the CPU time of the last pass: 5 % of a core) compared with the record; it finds in-place edits and deletes of cold files, creates are the directory tier's job.
- Walk tier: the walk of the whole shared tree at start (only when no directory table was restored from the saved state) and then every 30 minutes (`walkSeconds`, jittered) or after twenty times the CPU time of the last walk (5 % of a core), in the background; an outage, sync switched on again, a `.gitignore` change, a repair or a hint overflow (more than 20 000 pending paths) ask for one and get it when that gate opens (42 s of CPU on 272 000 files).
- Every tier's wait is `max(interval, cost × (100 / duty − 1))`; `cost` is the CPU time of its own last pass (the wall time for the view). The last cost and the duty cycle are attested in `latency.tiers`.
- Hook: the `PostToolUse` command copies the payload into `.cache/f/hints/` as `h<pid>-<time>.hook` (dot name, then rename) without launcher or JSON parser; the daemon parses `*.hook` files (up to 32 MiB) like `touch --hook` does.

Every tier works in slices of at most a few milliseconds between follow rounds.

## Attestation (same state on every worker)

Each daemon writes `origins/<origin>/attest.json` in the store of its own origin directory, at most every 5 s and whenever a value changes:

`{version:1, originId, groupId, platform, wallMs, hlc, sync, code, cursors:{<origin>:{segment,bytes}}, files, manifest, head:{ref,commit}|null, indexTree|null, view:{staged,modified,deleted,untracked,digest}|null, guards:{version,pins,volume:{caseInsensitive,normalisationInsensitive,symlinks,longPaths},infoExclude,caseIgnore,caseMismatch,trackedIgnored,trackedRefused,links,overBudget,modeMismatch}|null, latency:{publishMs:{p50,p95},applyMs:{p50,p95},samples:{publish,apply},tiers:{hot,sweep,file,walk,view:{passes,lastMs,dutyPercent}}}, queue:{incoming}, pending?:{code,ok:false,reason}, failures?:[{kind,count,lastMs}], fallback?:{guard:"code-fallback",source:"snapshot"|"store",reason}}`

- `platform` is the fleet platform name of the topology (`linux`, `macos`, `windows`), not the Node name.
- `pending`, `failures` and `fallback` are present only while they apply (refused or reverted code, counted recurring failures, a daemon on fallback code).
- Code that predates the guards writes no `guards` (older still: no `latency`). A reader treats such a file as present with `guards: null` (every `guards.*` field exempt) and a silent latency, marks it `legacy`, and `fleet` adds the warning `guards-unknown` for it; it is compared on `code`, `manifest`, `head.commit`, `indexTree` and `view.digest` like every other attestation and is never `missing`.

- `manifest` is an order-independent digest of the shared-file state (XOR of sha256 over `path\0operation\0value`), maintained incrementally. Realm paths are excluded; `indexTree` covers them.
- `code` is the sha256 over the daemon's own module sources (sorted relative path + bytes of `🤝️shared-worktree/**/🟦️.ts` and `📜️script.ts`).
- `view` is the working-tree view a git GUI shows, from `git --no-optional-locks status --porcelain=v1 -z --untracked-files=all --no-renames` (`null` without git). `digest` is the sha256 over the sorted (UTF-8 bytes, NFC paths) `XY path` lines of everything not purely staged (worktree column not blank, or `??`) joined by `\n`; the counts are entries with a staged change, a worktree modification, a worktree deletion, and untracked entries. The full lines are `origins/<origin>/view.txt` (atomic write, own origin directory, only when the digest changed; its sha256 equals `digest`). The daemon computes the full view once at start. Afterwards it keeps the lines of the view and the staged entries and classifies again only the paths it knows changed (published or applied; at most 1500 distinct, else a full pass) with `git status --porcelain=v1 -z --untracked-files=all --no-renames -- <paths>` under literal pathspecs, plus, after a stage or `HEAD` change, the paths that differ between the old and the new index tree (`git diff-tree`) or whose index column differs from `git diff-index --cached HEAD`; the answer replaces every table entry at or below those paths. A delta starts 1 s after the last changed path (5 s after the first) and keeps a duty cycle of 10 %. A `.gitignore` among the paths, more than 1500 paths or a failed delta ask for a full pass (quiet 5 s, duty 25 %); the full pass also runs as verification, at most every 10 minutes and 5 % of the time, only when something changed since the last full pass, and replaces the lines (it corrects drift: nested repositories, ignore rules, files the daemon refuses). `stale: true` in `view` is set from the first tick on which a change is known and not yet shown (a changed path, a running delta or forced pass, a changed stage, a restart seed); an origin with a stale view is `lagging` (not settled, not compared). It runs in the background, never concurrently, cancellable; the first attestation waits for the first view when git is present.
- `latency` is passive: `publishMs` is the time from the modification time of an edited file to the moment its event was written, `applyMs` the time from the wall clock inside a remote event to its application, each as nearest-rank `p50` and `p95` (whole milliseconds, `null` without samples) over the newest 100 samples, `samples` their counts; edits and events older than ten minutes are not samples, nor are events found by the start-up walk, the tree walk or the file sweep (`publishMs`) and events published before this daemon started (`applyMs`). It refreshes with the 5 s heartbeat. The git state (`head`, `indexTree`) is read from a stamp of `.git/HEAD`, the ref it names, `packed-refs` and `.git/index`, and git is started only when the stamp moved or after 5 minutes.
- The relay copies `attest.json` and `view.txt` with `head.json`; compaction keeps both.
- `checkpoints` (agreement on a moving tree, 2026-11-13, see `1113-result-agree.md`): `{manifest?:{cursors,wallMs,files,manifest,buckets}, git?:{cursors,until?,wallMs,head,indexTree}, view?:{cursors,until?,wallMs,digest,buckets,pending}}`. `cursors` is a cut (one `segment/bytes` per origin) at which the daemon had applied everything it had read (empty incoming queue, no apply in flight); `until` is the cut after a reading that took time (git state, view). `buckets` splits the manifest digest (XOR of the first two bytes of every term, bucket = low eight bits of FNV-1a over the UTF-8 bytes of the NFC path, 256 buckets, 1024 hex characters) and the view lines (term = sha256 of the `XY path` line, bucket by the path after the third character); `pending` is the 256-bit mask (64 hex characters) of buckets with a change the daemon knows of and the view does not yet show. `fleet` compares two origins over the events between their spans (per origin after the lowest `from` up to the highest `to`, read from the journals): everything outside the buckets those events touch must be equal; an event on the git state (`.git/HEAD`, `.git/refs/**`, `.git/packed-refs`, `.git/shallow`, the index realm, `.gitignore`, `.gitattributes`, `.gitmodules`) leaves `HEAD`, stage tree and view undecided. Verdicts: `ok` (checkpoint at most 60 s old, no event older than 60 s missing from the cut, every decided component equal), `lagging` (no common checkpoint yet), `diverged` (different values at the same position in the history, naming field and buckets). Code without `checkpoints` is compared the old way and flagged `no-checkpoints`.

Retirement. A machine that left the fleet for good is retired, never deleted: origin ids are not reused and its journal stays history and part of other replicas' cursors. `retire <origin> [--reason <text>]` writes `origins/<origin>/retired.json` atomically (tmp + fsync + rename):

`{version:1, originId, by, hlc, wallMs, reason, retired}`

- `by` is the origin of the machine that ran the command. This is the one deliberate exception to "own origin directory only", because the retired machine is silent.
- `retire <origin> --undo` writes a newer record with `retired: false`; of two records the one with the newer `hlc` wins. The relay copies `retired.json` of every origin of a peer store by that rule, and compaction keeps it.
- Refused: the own origin, an origin not in the store, an origin whose attestation is at most 60 s old unless `--force`.
- A daemon whose own origin is retired logs one `retired` event, publishes and applies nothing, keeps attesting with `sync: false` and checks the record every round; `retire --undo` from any machine re-admits it.

`fleet` command (and a table at the end of `status`): one row per origin with platform, age, lag, the latency (`publish p50/p95 | apply p50/p95`), and a verdict. A retired origin has the verdict `retired`: it is not compared, need not be fresh or settled, and the other origins are judged against the heads of the non-retired origins only. Origins whose cursors equal every such head are *settled*; all settled origins must agree on `code`, `manifest`, `head.commit`, `indexTree` and `view.digest` (an origin with `view: null` is exempt from the last). The table has a column `view` = `modified/deleted/untracked`. `fleet --diff` (not with `--json`/`--wait`) prints per origin that differs from this machine the lines only there and only here from `view.txt` (40 per side, then `+N more`) and exits 1 when any differs or an attested view is unavailable. Exit 0 when every origin with sync on that is not retired is settled, fresh (attested within 60 s) and agreeing and at least one is `ok`; exit 1 otherwise, with the differing fields named. `--wait <seconds>` polls until agreement or timeout, with progress, cancellable.

## Self-restart

The daemon records `code` at start: the sha256 over its module sources and every file they import (shared libraries, schemas, text catalogues). After a round in which the digest on disk differs and has been stable for 5 s it starts a fresh process of the same runtime on the replica script with `self-check` (all modules load, all schema definitions compile, all text catalogues are complete in every language, the current local state can be read; nothing is opened for writing) under a 60 s deadline. It persists and exits 0 with a `restarting` event only when that process exits 0 with the same digest, after a per-origin delay (0 to 60 s from sha256 of origin id and digest), at least 30 s after its own start, and while its incoming queue is empty (given up after 5 minutes). The service manager restarts it (launchd `KeepAlive`, systemd `Restart=always`, Windows task restart); provisioning for Linux and Windows must guarantee a restart after exit 0.

A failed check keeps the old code running: event `restart-refused` with the reason, `pending:{code,ok:false,reason}` in the attestation, re-check only when the digest on disk changes again. A digest that was refused before, or that ran before and was superseded (a revert), is not checked or adopted: event `code-reverted`, `pending` in the attestation.

Last known good: whenever a check passes and at every start, the checked closure is sealed into `.cache/f/code/<digest>/` (mirror of the repository paths, `sealed.json` last, newest two kept), and `.cache/f/code/history.json` records the digests run and refused. The service entry (`📜️script.ts`, Node built-ins only) loads the worktree code and self-checks it; when that fails or the code is a revert it runs the newest sealed snapshot that loads. `self-check` never falls back.

## Boot stage, fallback code and admission

`📜️script.ts run` supervises the daemon as a child process. A start that ends non-zero before `started` or within 60 s tries, in order, the newest intact unrefused sealed snapshot, a snapshot from `<store>/v1/bootstrap/code/<digest>/` (hash-verified, then sealed locally) and last the worktree code that was set aside as a revert. A daemon on a fallback attests `fallback:{guard:"code-fallback",source,reason}`. Healthy daemons publish their sealed snapshot to the store. New code is switched to only when another origin attests its digest, a store snapshot of it exists, or all its changed files were published by this origin; the self-check also dry-opens the real state on a mirror and boots the checked daemon once in a scratch worktree. A watchdog thread writes `.cache/f/boot/beat.json`; `status` shows a blocked loop as busy, `loop-blocked` goes to `health.json`, the supervisor kills a daemon blocked for 15 min and ends within the grace period on SIGTERM. Details: README section "Boot that cannot be bricked".

## Rollout on the live fleet

Old daemons do not self-restart. On each worker the running replica is stopped once as the worker account (`kill <pid in .cache/f/daemon.lock>`); the service manager starts the new code. Until then an old daemon drops realm events as ignored (sealed path) and keeps publishing raw `.git/index`, `.git/logs` and `.git/config`, which new daemons drop.

## Ownership (parallel executors, one file each where possible)

- Executor A (git state): `🚧️boundary` allow-list, new member `🌿️git` (plumbing interface + index register), hooks in `publishOnceV1`, `materialise`/`applyQueue`, `joinV1`, `verifyV1`, the watcher filter in `runV1`. Exports `gitStateV1(worktree,signal?):Promise<Readonly<{present:boolean;head:string|null;commit:string|null;indexTree:string|null}>>`.
- Executor B (attestation): new member `🩺️attest`, incremental manifest digest in `setFile`/`forget`/load, attest write and self-restart in `runV1`, `fleet` command and `status` table, relay copy, provisioning restart policy.
- Both edit `🔁️replica/🟦️.ts`: re-read before every edit, small anchored edits, never rewrite or reformat the file, never revert a region you did not write.
