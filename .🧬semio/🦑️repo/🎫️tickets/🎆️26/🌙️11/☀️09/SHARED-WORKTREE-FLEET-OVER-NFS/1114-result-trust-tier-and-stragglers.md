## 1. Trust tier
**Why it was `verify` for ever.** `manifestTrustV1` (build side, `🪪️graph-state/📍️cursor`) and `replicaHealthyV1` (`📥️replica`) demanded `failures.length===0`; `failures` of the health file are lifetime counters per kind since the process started (126 360 `blocked` git-pack events of the stuck apply, 9 `refused` ticket paths, 4 `attest`). One such event made every graph read pay the verification for the whole life of the daemon.

**The rule** (`decideTrustV1`, one function, both sides): `unusable` unless the health file is at most 30 s old, its store `ok` and its process alive; `verify` unless the `trust` statement holds a verification that began after the last loss and is at most ten minutes old; else `trusted`. A health file without a `trust` object (a daemon of older code) is `verify`.

**The statement** (health schema, `trust`): `scope` `shared-source` (every shared path except `.git/`, `.cache/`, the ticket tree, AppleDouble), `verifiedMs`, `lostMs`, `lostKind`.
- *Verification facts the daemon owns:* the file sweep (every manifest file against the tree, `scanSeconds`, about 90 s) and the directory sweep (every known directory, every 2 s duty-limited) each record the time they began when they ended clean; the oldest of the two is `verifiedMs`; a complete tree walk (30 min) counts for both. A file sweep or walk that finds a file that differs, is older than 30 s when the sweep began and is not in the hot set, or a path the manifest holds and the tree lacks without the hot set knowing it, is drift: `lostKind` `sweep-drift`.
- *Losses:* `classifyFailureV1` decides per failure key. Cannot make the manifest wrong for the scope (no loss): `blocked:objects:*` and every path under `.git/`, `refused:` and every other path-bound kind outside the scope (the ticket tree), `attest`, `skipped`, `skew`, `watch`, `scan`, `seal`, `entry-boot`, `git-broken-*`, a peer's journal read error, `error:git:*`. Can (loss, immediate): a failed apply or blocked journal append, `unstable:` and `blocked`, `refused`, `blob-wanted`, `entry-guard` for a source path, `state-missing`, rejoin, and every unknown kind (unknown means loss).
- *Return of trust:* only a file sweep and a directory sweep that both began after the last loss. A failure that keeps recurring (a stuck apply on a source path) never lets it return, which is correct.
- *Health file carries it, `status` shows it* (EN/DE texts `status.health.trust.pending`, `status.health.trust.lost`); the lifetime `failures` stay in the file for `status` and play no part in the tier.

**Agreement by schema.** `🔏️trust/🧬️schema/🔣️.json` (Trust, Policy, Fixture), the health schema of `🛡️resilience` and `🔁️replica` (status) and `🪪️graph-state/🧬️schema` carry the same `Trust`; a graph-state test diffs the two definitions and the policy time.

**Proof.** `🔏️trust/🧪️tests` (7): language-agnostic fixture (12 paths, 33 failure keys, 15 health files, 7 tracker sequences), reproduced by TypeScript and by the independent Python oracle `🐍️.py` (shares no code); the 126 360-counter case; stale counters do not withhold trust, a source-path failure does, a sweep that began before the loss does not return it, a clean file plus directory sweep (or walk) does, a recurring loss never does. `🔁️replica/🧪️tests/🔏️trust.ts` (4, real replicas): a running daemon with a refused ticket path in its failures writes `trusted`; a walk of a tree that equals the manifest verifies it; an old cold file changed behind the back of every tier is drift (verdict `verify`), the next clean walk after the publish returns `trusted`; a young edit is no drift; hot and young files are no drift in the file sweep, old cold and vanished ones are. Consumer: `📍️cursor/🧪️tests` (20, the daemon gate now has 9 cases) and `🧪️tests` (14, replica health gate, schema agreement). Negative control: with the old rule the "lifetime counters" cases fail by definition (they assert `trusted` with a non-empty `failures`).

## 2. g1-m07
**What the store shows.** `origins/g1-m07` (10:51): attest 2 s old, code `5b7aec94…`, then `33090cda…`, queue 0, apply p50 2090 ms, head `5ececaa7`, checkpoints equal. Its journal restarted at 10:33 (`segments/000000000000.jsonl`, 638 events, 575 puts): three pack blobs of 3.67 GB (`pack-58516ce`, hlc 02:41, identical sha256 to the one g1-m04 published at 01:17), 1.99 GB (`pack-76d2c3fc`, 07:07) and 3.97 GB (`pack-a140057f`, 10:33). g1-server's consolidation (pack `39364f77`, 10:09, deletes at 10:12:49) retired the first two; `tmp` is empty now.

**Mechanism (code reading + store, not observed on the machine).**
1. `createStoreGuardV1.turn` aborted the turn as soon as the probe (`stat` of the store root) had been outstanding for the deadline (10 s). A 4 GB staged copy to NFS plus its single final `fsync` blocks every other call of the mount for minutes, so the probe was late, the turn was aborted, `storeBlobV1` unlinked the staging file and the next round started again at byte 0: a staging file of 1.5 to 3 GB that grows, disappears and returns under one pid (50906) for hours; the main loop was inside the turn the whole time (attest 4 to 6 min old, apply latency 150 to 280 s).
2. `storeBlobV1` without a `known` hash copied the whole file into `tmp` before it looked at the store: a pack the store already holds (uploaded by another machine, republished after a state reset or journal restart) costs the full copy for nothing.

**Fix.** `storeBlobV1`: (a) a source of at least 64 MiB without `known` is hashed locally first and, when the store holds that blob intact, nothing is staged (test: store `tmp` made unwritable, the call still reports the blob); (b) the staged copy flushes every 32 MiB (`storeFlushBytesV1`) so the stream is paced and never silent; (c) `alive` is called at every copied, flushed or verified chunk. `createStoreGuardV1` gets `beat()`; `turn` abandons only when the probe is overdue **and** no beat came within the deadline. The replica passes `replica.beat` for blobs of at least 64 MiB. Tests: `🛡️resilience/🧪️tests/💓️beat.ts` (3: a beating turn survives a hanging probe, a silent one is abandoned, no beat behaves as before), `📒️journal/🧪️tests/🚰️upload.ts` (4: flush interval and progress, equals the plain copy and an independent sha256, `alive`, no copy when the blob exists).
Consequence to know: the upload still runs inside the publish turn, so a machine's attestation is as old as an upload is long (4 GB at 50 MB/s: 80 s). A resumable upload outside the turn is not built.
