## 1. Follow change signal

**Design (differs from the sketch in one point).** After `head.json` (tmp, fsync, rename) the origin creates an empty file `v1/heads/<origin>_<segment>_<bytes>_<events>_<hlc>` whose **name is the head**, then removes its previous name (create before remove: a reader sees both or the new one and takes the later; a crash leaves a stale name that the next publish of a process removes, readers take the later anyway). Why names and not `v1/heads/<origin>` with the head as content: on a busy fleet the directory changes almost every round, and N small files would then be read every round, no better than today; with the name as the head one `readdir` gives every head, no file is opened. Follower: `stat(v1/heads)` per round; signature `ino:mtime:size:nlink`; `readdir` only when it changed, again after 30 ms and after 1.1 s without further change (a coarse timestamp, ext4 jiffies or a 1 s file system, can hide a second change inside one tick), and every 10 s (stale client attribute cache). The flat head is a hint, never the truth: every 10 s the follower polls `head.json` of all origins and takes the later head, origins without a flat entry are polled through `head.json` every round, and the head read from a name is passed to `readEventSpansV1` (no second `head.json` read). It is written only after `head.json` and the segment bytes are durable, so a hint is never ahead of the data. A failed flat write is swallowed (`head.json` already moved); a lost hint costs at most 10 s. The relay reads the peer's flat heads the same way and writes flat heads for the origins it carries (after `head.json`, also when the head was already current but the flat entry was missing). Code: `📒️journal/🟦️.ts` `publishFlatHeadV1`, `readFlatHeadsV1`; `🔁️replica/🟦️.ts` `followHeads`, `relayOnceV1`.

**Directory mtime on NFS: not measured.** `linux-nfs-report.md` and `mixed-os-report.md` measured how fast a replaced file shows, not a directory mtime. By reasoning: with `actimeo=1` (Linux) the directory attributes are cached up to 1 s, the same staleness the file attributes have under that option; with `acdirmin=acdirmax=0` (macOS) every `stat` revalidates. A change inside one timestamp tick is covered by the 30 ms / 1.1 s re-reads, a stale cache by the 10 s refresh and audit. **Re-measure on a worker**: seconds between a publish on the group server and the first changed directory signature on a Linux and a macOS worker; if it exceeds the file-poll delay, lower the 10 s refresh.

**Mixed version.** Old origin (no flat head) is polled through `head.json`; old follower ignores `v1/heads` (nothing in old code lists `v1`: `listOriginsV1` reads `origins`, compaction and reclaim read `blobs`/`snapshots`/`tmp`, the bootstrap reads `bootstrap`); old relay copies `origins/<id>` only, so a group fed by an old relay has no flat heads for those origins and its followers poll them the old way; names that do not parse (for example macOS `._` companions) are ignored. Checked by running both versions against one store (`🧰️scripts/1113-mixed-version-check.ts`): old and new origins follow each other, old relay copies a new origin, old compaction leaves `v1/heads` alone, the new relay then produces flat heads, a new worker joins from that peer.

**Tests.** Journal (`📒️journal/🧪️tests/💾️store.ts`): one name per append holding the head, later of two names, garbage names ignored, no `v1/heads` and old origin read via `head.json`, cache identity when unchanged and notice of a change, unwritable `v1/heads` does not fail the append, first publish of a process removes leftover names. Three replicas (`🔁️replica/🧪️tests/💾️store.ts`): convergence through flat heads and zero `head.json` accesses in idle rounds with flat heads (counted through the `node:fs/promises` hook); origin without flat head followed, stale flat head corrected by the audit (clock advanced 11 s); relay writes flat heads and a new worker joins from the relayed store.

## 2. Single-pass blobs

**Design.** `storeBlobV1` (journal): one read of the source in 1 MiB chunks through two alternating buffers, hashed while written into `v1/tmp`; the blob name is the sha256 of the bytes written, so name and content cannot differ; a source whose size or mtime changed (or whose bytes do not hash to a hash the caller held) is `stable:false`, nothing is stored. `prepare` hashes first only when the file has the size of its recorded version (the touch case needs no copy at all) and uses `known` so an existing blob is not read; otherwise the single pass. `writeBlobV1` stays as the known-hash form on the same primitive. `copyVerifiedV1` (apply and relay): copy with hash in the same pass, compare with the name before the rename, `"corrupt"` removes the copy; no read-back (`materialise` lost its `hashFileV1` of the copy, `relayBlob` its read-back). `ensureOnce`: the `tmp` and prefix directories are created once per process (retry after ENOENT), which removed about 2 `mkdir`s per blob (2,008 to 259 per 1,000 files). **Racy after apply**: `materialise` records `seenMs = stamp + 2 s` when the temp file's mtime has sub-second precision (so the next full scan treats the file as seen after its own timestamp and does not hash it), `seenMs = now` otherwise (coarse timestamps stay racy). Test: after an apply of 20 files `walkLocalV1` finds 0 changed and `publishOnce` publishes 0 (it was 20 before). The residual risk is a same-tick local rewrite of identical size within the timestamp granule after the apply (nanoseconds on APFS, 4 ms jiffies on ext4).

**Mixed version.** Same blob names, same layout; only the way the bytes are produced differs. Old and new code share blobs freely.

**Tests.** A wrong-content blob is never applied (replica test with a tampered blob: `blob-corrupt`, path queued, tmp empty; unit test: `copyVerifiedV1` returns `corrupt` and removes the file, also on the clone path); the relay refuses a peer blob whose content is wrong (`Relay blob differs from its hash`), writes neither the blob nor the head, leaves no staging file; a source that changes while it is copied (unit, mid-copy) and between hash and copy (replica, hook rewrites the file at `open`) is never published and leaves no blob; sha256 of a 64 MiB+ file by clone and by stream equals Python `hashlib`.

## 3. Journal read cost and bounded catch-up

**Design.** `isEventV1`, `isManifestEntryV1`, `isHeadV1`, `isPathV1`: hand-written twins of the schema definitions; `requireEventV1`, `readHeadV1`, `appendEventsV1`, `readNewestSnapshotV1`, `writeSnapshotV1` use them and call the generic validator only on a refusal, to name the error (messages unchanged). `readEventSpansV1` gained `known` (a head already read) and `maxEvents`. `followOnceV1` is a loop of slices: one segment and at most 1,024 events per origin, then apply, local kept-publish and persist; the next slice starts only while less than 500 ms of the round have passed, so the caller (publish, attest) regains control about every half second whatever the backlog. Race with the latency agent's `reuse` parameter resolved (`followOnceV1(replica,signal,reuse)`).

**Tests.** Equivalence of the hand validators with the generic validator **and Ajv** on 30,000 fuzzed events plus the fixture, 10,000 each of entries, heads and paths; admission equals the Python oracle (`🐍️.py events <file>`, new mode) on 6,000 fuzzed events (>500 accepted); `maxEvents` chain without gap or repeat; `known` head. Replica: 3,000 events behind with `Date.now` advanced so each call is one slice: every call ≤ 1,024 events, the replica publishes its own file between slices and a third replica receives it before the backlog is consumed, all 3,000 files arrive.

## 4. fsync policy (measured counts)

Counts per operation (`💾️store.ts` journal test, hook on `FileHandle.sync`): new blob 1; blob that exists 0 (the fsync is decided from the hash after the copy, so a copy that is dropped is not synced; before: also 1 per duplicate); journal append 1 per segment touched plus 1 for `head.json` (2 per batch of up to 256 events, 0.008 per file; the batch is already one append and one fsync); flat head 0; plain copy 0; relay blob 1 (new: it had none). Per published file 1.008 before and after; per applied file 0.

Rule, documented in the README: **blob durable (fsync before its rename) → events durable (fsync) → `head.json` durable (fsync before rename) → flat head (hint, not synced).** A blob name never exists without durable bytes, so an event is never durable ahead of its blob; the relay now follows the same order (the audit's side finding: a relay head could reach the store before its blob bytes). A blob lost before its event is durable is recreated from its source by the next publish (`publishOnce` retries unpublished paths). The explicit blob fsync is nearly redundant on an NFS client (close commits) and cheap locally; it stays because the ordering is the guarantee. Applied files are not fsynced (cache; a rescan restores state).

## 5. Large files

From 64 MiB (`largeBlobBytesV1`): `copyFile` with `COPYFILE_FICLONE_FORCE` when source and target directory share a device (the group server: worktree and store), else streaming in 1 MiB chunks through two buffers (never the whole file in memory: tested as RSS growth below the file size for 64 MiB+; measured peak RSS 209 to 239 MB for 1 GiB, which includes the bench process and its two replicas); fallback on `ENOTSUP/EXDEV/ENOSYS/EINVAL/…`. After a clone the file is hashed from the clone (one read) and its mtime set to now. Progress events `publish-blob`, `apply-blob`, `relay-blob` (`path` or `origin`, `done`, `total`, throttled to 4 per second) and cancellation between chunks (publish, apply, relay take the signal): test cancels the publish of a 64 MiB file at the first chunk, leaves nothing in `v1/tmp`, republishes, applies on a second replica (progress seen, sha256 equal). Not changed: a changed 4 GB pack is still copied whole (delta copy out of scope); relay `relaySnapshot` still stats every blob of a new snapshot.
