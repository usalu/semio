# Lane `rss-profile`: where the planner RSS goes

## Harness (reproducible, cgroup-capped, light)

- `🧰️scripts/rss-profile.ts` + `rss-profile.sh <label> [nodes]`: runs the real planner phases in one process on the real repo: fact index view walked (681k rows), module load, workspace walk (30,881 files), `discoverBuildProjectsV1` (real worker farm), contributions, edges, metadata, plan serialisation. Marks after forced GC plus 3 s scavenge wait (`heapStats`, `/proc/self/status` anon/file/swap, ArrayBuffers), 2 s ticks, optional JSC heap snapshot (`RSS_SNAPSHOT_FILE`), `RSS_LIMIT=N` (N sampled owners), `RSS_OFFSET`, `FORCE=<bytes>` (`BUN_JSC_forceRAMSize`), runs under `systemd-run --user --scope -p MemoryMax=3G -p MemorySwapMax=0`. The invocation envelope comes from a live planner's environment (`🗑️generated/rss-profile/env.txt`, regenerate from `/proc/<planner>/environ`).
- `rss-heap-analyze.mjs` (JSC snapshot to spanning-tree subtree sizes), `rss-stage-summary.py` (peak RSS/heap per planner stage from a log), `rss-force-sweep.sh`.

## Findings

1. Live JS data is small. After a forced GC at 40 projects: JS heap 328 MB (139 MB strings, 58 MB ArrayBuffer = the packed index, 15 MB objects), `extra` 253 MB; RSS 1.4 GB right after GC and ~0.7-0.9 GB lower once the allocator scavenger ran (it needs ~1 s: RSS read right after `Bun.gc(true)` overstates by ~150 MB even for the bare index view: 386 MB then 230 MB).
2. The 2.5-3.3 GB peaks are transient garbage: stage `build:command-source-imports` (TypeScript programs and parses for every declared project) reaches heap 1.07 GB and RSS 1.96 GB at 20 projects because `childHeapMegabytes` = 2048 (`BUN_JSC_forceRAMSize`) lets JSC keep garbage until about 2 GiB. HWM at 40 projects was 2.17 GB with 1.4 GB after GC.
3. `BUN_JSC_forceRAMSize` sweep, same harness, cold stages: 2048 MiB peak 1963 MB, 768 MiB 1480 MB, 512 MiB 1475 MB with all fixes below (the 978 MB figure of an earlier 512 MiB run was partly served from the project cache and is not comparable).
4. Project records are not the problem: parent RSS after 83 of 4751 projects was already 2.2 GB, i.e. the cost is fixed per stage, not per project; the host memory governor then throttled to 1 project at a time ("1135 of 1024 MB in use") which also explains the slow cold plans.
5. Module level unbounded state in `📥️inference`: the nine Maps/Sets of requests.md; the worst was `closureScriptsV1`, which pinned the whole script input cache (files, closures, command dependencies) of the last run for the life of the process because `resetClosureEntriesV1` never cleared it.
6. Latent bug found: `📥️inputs/💾️storage/🟨️.mjs` `evictOptionalGraphLruV1` read `quotaSchema.policy.lowWaterBytes` (undefined, TypeError whenever the optional graph LRU ran). Fixed to `quotaSchema.definitions.DefaultPolicy.const.lowWaterBytes`.

## Fixes

- `🧠️memory` policy `childHeapMegabytes` 2048 to 512 (schema and fixture): largest single lever (-25 to -50 % peak, no slower: the 512 MiB run finished in 48 s warm).
- All module level collections of `📥️inference` are `createBoundedCacheV1` caches: `latestRegistrations` (256), `cacheDecisions` (1024), `moduleGraphPublications` (2), `compilerRevisionsV1` (64), `precisionDocumentsV1` (4), `reclaimedDirectoriesV1` (256), closure recipes/inputs (64 MiB each), closure entries (16384 entries / 128 MiB accounted, recomputed on demand), in-flight (4096), failures (1024), scripts (16). `resetClosureEntriesV1` now also clears `closureScriptsV1`. The query registry is the fixed table `CLOSURE_QUERIES_V1`.
- Lint/test `📥️inference/🧪️tests/🔒️lint/🟦️.ts`: no module level `Map`/`Set` in any inference component (upper-case fixed tables and WeakMaps allowed); self-test of the declarator shapes.
- Resident digest cache: `🏡️resident/🗃️state` per-file digests are held in a bounded LRU of owners (`resident:digest-owners`, `digestCacheMaximumFiles` 2,000,000 declared-but-unenforced to 262,144 enforced); an evicted owner rehashes on its next change (never during its own refresh). Test: bounded cache with 2 files stays equal to the naive oracle after an edit.

## Result

Peak planner RSS on the harness (cold stages, 20 owners, forced real inference): before 1963 MB (2.17 GB at 40 owners), after 1475 MB. The 1.2 GB target is not reached: remaining peak is live heap about 700 MB in `build:projects`/`project-assembly` plus the 230 MB index view and allocator overhead. Next levers (outside this lane): release observation rows/script input cache per stage in `👁️observation` and `🕸️graph/🟦️.ts`, patch the index from the view, run command-source-imports programs with a shared SourceFile registry.

bun test (direct runtime): inference lint 2 pass; `🧠️memory` + resident state + bounded 31 pass; inference closure-facts/module-memo/late-closures/interned-closures 27 pass, 3 fail with ENOENT in `requirePrivateRepositoryWorkspaceV1` (test workspace env, not from these edits). Host service (`repo service host`) was not profiled directly: no heap hook in that process; it shares the same inference stage and bounded caches.

## Round 6: the 7 GB in-job kill (host graph service)

- Hypothesis check (`/proc/<pid>/cgroup`, `/proc/<pid>/environ`, code):

## Round 8: slice worker pool, plan counters, what a plan really costs

- Harness `rss-slice.ts` (the service's `loadSlice` body in process: `loadBuildInvocationGraphV1` for `run repo:test-build-observation`, policy `fresh`, 1 GiB heap target, cgroup cap 6 GiB, event-loop lag sampled every 100 ms) on the live tree while other agents edit: after 25 minutes (the run's `timeout 1500`) it had not finished: membership 1 s, facts 10.5 s, then "Verifying graph facts" over 319,836 facts (about 10 minutes under host load) and "Verifying input closures: 0 of 2005 closures" for the rest of the 25 minutes at heap 1.9 GB + 1.3 GB external, RSS 3.0-3.3 GB. Event-loop lag: max 114 s, 129 stalls longer than 1 s. ### Round 9 correction: the guard follows the cgroup, not a fixed budget
- The fixed `sliceBudgetMegabytes` is gone. The pool's guard compares the service's current cgroup usage (`cgroupMemoryHeadroomV1`: `memory.current` of its own cgroup, and the smallest `memory.max` up the tree, `max` = unlimited; RSS where cgroup v2 is unreadable) plus the policy margin `sliceSafetyMarginMegabytes` (256) with the limit, once a second; the usage already contains the growth of the other running slice and the resident graph. A load is cancelled only when continuing would cross the limit; with no limit nothing is ever refused. Refusal `code:"memory"`, EN/DE message with the figures: "The plan cannot continue: the service holds {current} MB of its {limit} MB memory limit (safety margin {margin} MB), ..." / "... der Dienst belegt {current} MB seines Speicherlimits von {limit} MB (Sicherheitsabstand {margin} MB) ...".
- Tests: a 400 MB allocation against a ceiling 150 MB above the current RSS is refused with both figures and the service stays up; the same plan under a 4,000 MB ceiling completes and is never counted as refused; `cgroupMemoryHeadroomV1` takes the smallest `memory.max` up the tree (job-limits 15 pass); resident host/plan 23 pass.
- With the 4096 MB service cgroup, a cold plan growing to 2.8-3.3 GB on top of a 0.7 GB resident graph still ends near the limit; whether it is refused depends on the real headroom at that moment, which is the intended behaviour until the cut-over replaces the full verification.

### Round 9 fix: the service's own memory exit no longer kills a service whose pool governs the growth
- Root cause (live dry-5, exit.log: `reason:"memory", code:75`, RSS 3157-3229 MB, main heap 52-57 MB, `workers: []`): the resident sweep of the host service (`🏛️service/🌐️host`) compares whole-process RSS with `HostPolicy.maximumResidentBytes` (2.5 GiB), drops every workspace and index, and at 1.25 times that retires the service for a restart. RSS includes the slice workers' heaps, which the slice pool already governs against the cgroup headroom, so a heavy load made the service exit (and cancel every plan) before the pool's guard could cancel the one plan. `workers: []` because the exit row read only the running loads' samples.
- Fix: the sweep skips the memory exit and the index drop while a slice load runs (`ports.workers.active`, the pool's `busy()`), so the pool's guard is the only governor of that growth and cancels just its plan with the typed `memory` refusal; the memory exit still applies to the service's own memory when no load runs. The pool keeps the last sample of the two most recent loads after they end (`running:false`), `MemoryStatus.workers` items gained `running`, and every exit row carries `workers` and `workersBusy` (also on the `crash` and `stop:` paths, which share `record`).
- Test (real worker threads, `🧪️tests/🌐️host`): a worker allocating 900 MB with a service restart threshold only 60 MB above the base RSS and a pool ceiling 250 MB above it: the plan is refused (`memory`), the service did not close, status answers and validates (`budgetRefusals` 1) and carries the worker's last sample (`running:false`). Verified that the test fails (0 pass, 1 fail) with the old unconditional sweep. Resident host/command/exit-log tests: 27 pass.
