# rowstore: the planner's memory after the closure settle

Lane `rowstore` of the build-graph ticket. Scope: `BUILD/👁️observation`, `BUILD/🕸️graph/**`, `BUILD/🕸️graph/📥️inference/**`. Isolated runs only (never the live service, never `repo run repo:test-build-memory`). Scripts are in `TICKET/🧰️scripts/rowstore-*`; generated output (heap snapshots, logs, measure JSON) is deleted.

## 1. Method (what changed against the sixth pass)

The sixth pass could not name the roots because (a) a V8 heap snapshot of Bun/JSC does not traverse the contents of `Map`, `Set` and `WeakMap`: everything they hold shows up as "held by GC roots" or as unreachable (108 of 188 MB in the 1,000-closure snapshot had no retaining edge; the 103 k "root pinned" strings are Map keys), and (b) the release experiments measured in the same async frame as the settle: a suspended async frame keeps its dead registers, so `result = undefined; Bun.gc(true)` frees nothing (the earlier "releasing everything frees almost nothing" was this artifact; a `WeakRef` on the result stays alive until the frame returns).

Therefore:
1. `rowstore-heap-roots.py`, `-maps.py`, `-maps2.py`, `-paths.py`, `-strings.py` over `Bun.generateHeapSnapshot("v8")` of 1,000 closures (`entries-heap-snapshot.ts`; the snapshot, 162 MB, is deleted): sizes and incoming edges of every Map/Set/WeakMap by its context name, shapes of the retained objects, string classes. This gives the *named* collections (`table`, `slots`, `rowKeys`, `sourceAnalysisImages`, `facts`, `walkNodes`, `reachState`...) and their cost, not their contents.
2. `rowstore-collections.ts` patches `Map.prototype.set` and `Set.prototype.add` before the modules load, records every collection that crosses 3,000 entries with the stack of the insertion (`WeakRef`, so it never pins), and prints the survivors after the settle with the deriver, the settler and the result dropped. This names every module-level or closure-captured structure that grows with the repo by creation site.
3. `rowstore-weak.ts`: `WeakRef`s on deriver, scripts, settler, graph and result prove what the settle itself retains (all freed at 50, 1,000 and 6,707 closures once the frame returns), so everything that survives is module-level.
4. `rowstore-measure.ts` (the harness for all numbers): the 6,707 derived questions of the real index (`pseudo.json` written by `rowstore-pseudo.ts`, the index is not loaded in the process), optional lazy fact index view with every row read once (`ROWSTORE_VIEW=1`), the real settle, `heapStats()` after three event loop turns and `Bun.gc(true)`, a 100 ms sampler for the peak, results kept only inside a function scope (`stage()`).

## 3. Compact row store (schema first)

`BUILD/👁️observation/🔢️row-table` is replaced, there is no second representation:
- schema: limits `rowStoreRows` (1,048,576) and `rowStoreCharacters` (16,777,216) in `👁️observation/🧬️schema/🔣️.json` (EN and DE descriptions), plus the changed limits `settledReadBytes` 32 MiB, `fileRecordImageBytes` 16 MiB, `verifiedBlockRows` 1,048,576.
- `createStringTableV1()`: one table of texts, equal texts one number (paths, kinds, digests, string facts, JSON texts stored once).
- `createRowTableV1({maximumRows,maximumCharacters})`: one row = entries of typed-array columns (kind, path, shape, digest, aux, hash, chain), flat file stamps (`size,mtimeMs,ctimeMs,ino` + digest id) in a `Float64Array`, analysis facts as a record (provider, revision, result digest, source stamp, nested row numbers in a `Uint32Array` pool), any other fact as JSON text; chained hash buckets verified by column comparison, no key string per row. A row object is a view: `canonical(kind,path,fact,make)` returns the live row or `make(sharedPath)`, kept in a `WeakRef`; `row(id)` returns the live row or makes one from the columns; `materialize(id)` always makes one. Numbers are never reused: `clear()` and the budget keep counting, a row object that outlives a clear is numbered again by content (`id(row)` checks the epoch).
- consumers moved: observation row interning (`canonicalObservationV1`, `internObservationsV1`: no use of the global interner), analysis images (numbers), settled reads and file record images (numbers), verified blocks (numbers); `inferenceCacheSizesV1` reports the store (rows, strings, characters, bytes). The facts of the persisted JSON are unchanged (rows have the same key order `kind,path,fact`; shapes that would change the JSON text, such as other key orders or extra keys, are stored as JSON text).
- cost at 6,707 closures: 89,261 rows, 99,758 strings, 12 M characters, 35.7 MB estimated (24 MB of it are the path characters), which the old table held as one row object per row (plus a hash Map entry, a `slots` WeakMap entry and the pinned interner copy of each path).

Tests (language agnostic fixture `🔢️row-table/🧪️tests/🔣️.json`, schema `🧬️schema/🔣️.json`, independent oracle `🐍️.py` in Python):
- grouping equal to the model for every case (also with every row in one bucket: `hash:()=>1`);
- a row made from the columns serialises to the JSON text the Python model prints for the same row, for primitives, numbers, nulls, arrays, nested objects, flat stamps, reordered or extra stamp keys and analysis facts with nested rows (nested analysis in analysis included);
- a row whose object died is made again with the same number; clear and budgets never reuse a number; the string table;
- heap bound: 300,000 generated rows (60,000 emoji paths, flat stamps, analysis facts with nested rows) must grow heap + extra by less than 96 MB with no row object held (`SEMIO_ROW_STORE_ROWS`, `SEMIO_ROW_STORE_HEAP_MB`).
- settle heap bound (`✂️cutoff` tests): 3,000 generated questions with 150 rows each settle through the real settler, after the result is dropped the heap grows by less than 24 MB (1.2 MB measured; `SEMIO_SETTLE_QUESTIONS`, `SEMIO_SETTLE_HEAP_MB`); the same test proves that the answer rows are kept only with `answers:true` and that the captures of a finished settle are collected.

Durability: the answer is the value of the derived node of the question, stored with its observed rows by the node graph exactly like a closure entry, so it is computed once while its rows hold and reused by every plan of the workspace store; no second store was added.

## 8. Third pass: the steady heap per chunk

Method: `rowstore-measure.ts` with `ROWSTORE_CHUNKS=1` logs `Bun.gc(true)` plus `heapStats()` at every `flush` event of the settler (after each chunk of 256 closures) and the size of the settler's derived graph; with `ROWSTORE_COLL=<mb>` it dumps the Map/Set tracker (creation sites, entries) at chunks 2 and 6. A heap snapshot diff cannot name Map contents (section 1), so the tracker diff between chunk 2 and chunk 6 is the diff by structure.
- Grown by chunk (2,600 closures): `closure-kinds` `table` (parts: 8,608 to 13,180 entries) and `metas` (13,180 entries of path, directory and outside lists per part), kept to the end of the settle although every part is durable in the node store; the derived graph nodes (256 per chunk, 2,587 at the end, `evicted` 0, small: a key, a digest and part numbers per node); the walk memo Maps (`walkNodes`, `files`, `reachState`: 11 k to 17 k entries, saturating with the distinct modules, not with closures); the string table of the row store (54 k to 72 k, bounded by its budget). TypeScript identifier caches are not among the growers: they exist only inside the eight heavy questions, which now run in the child.
- Fix: `forgetParts()` after every chunk drops the parts the held supports do not keep and empties `metas` and `outsideRows` (only when a store holds the parts; without one the parts are the only copy and stay until the end as before). Post-chunk heap over 2,600 closures: 176 to 356 MB before, 176 to 301 MB after; peak RSS of the same run 2.07 GB to 1.23 GB, peak heap 1.21 GB to 0.66 GB.
- Test (`✂️cutoff` tests): 2,560 generated questions with 400 distinct supporting rows each settle through a node store in chunks of 256; the heap after every chunk must stay within 50 MB (`SEMIO_CHUNK_QUESTIONS`, `SEMIO_CHUNK_HEAP_MB`). It fails without the fix (117, 219, 330, 424, 520 ... 1,028 MB, about 100 MB per chunk) and passes with it.
- Full settle (6,707 closures, lazy view included, 27 chunks): post-chunk heap 328 MB at chunk 1, 760 to 880 MB at the end, in steps (chunks 6 to 7, 20, 25: closures that walk many new modules), so it is NOT flat over the real index: it follows the number of distinct modules (22 k) held by the walk memo, which the first pass showed (releasing it every chunk costs twice the time and still peaks at 1.1 GB heap). Peak during the settle: RSS 3.03 GB, heap 1.23 GB, extra 0.98 GB (3.29 GB and 1.36 GB before this pass); after the settle: RSS 1.65 GB, heap 445 MB with the view.
- Target under 1.5 GB peak RSS: not met at 6,707 closures; met at 2,600 closures (1.23 GB). To flatten the real settle the walk memo needs a byte budget with eviction of the least recently used module nodes (not a full release): that is the next step and a redesign of `walkNodeV1`'s memo in `script-inputs`.
- Code a live run uses and that changed in this pass: `🧩️closure-kinds/🟨️.mjs` (settler), earlier passes `📦️project-nodes/🟨️.mjs` (heavy routing, child process) and the observation module.
- Both heap-bound tests of `✂️cutoff` now run their settle in a fresh child process (`🧪️tests/🧮️heap-child/🟨️.mjs`): in the shared test process the settle-growth test measured 481 MB after 150 earlier tests (order dependent, unrelated to the settler: it also failed with the fix removed), in a fresh process 1.2 MB.
- Suites after the third pass: 986 pass, 99 fail (cutoff 156/0); the failing set is the pre-existing one of section 5.

## 9. Fourth pass: byte-budgeted reach memo

Design (differs from the request on one point, with the reason): the memory that grows with the modules a settle touches is the *reach sets* (`reachState.reaches`, one sorted `Int32Array` of module numbers per module or strongly connected component, quadratic in the module count and counted as extra memory), not the module nodes (a few KB each). So the budget and the least-recently-used eviction apply to the reach sets (`🧭️script-inputs/🧠️reach-memo`: schema + policy `reachBytes` 128 MiB, `entryBytes` 16, `🟨️.mjs`, `🟨️.d.mts`; override `SEMIO_REACH_MEMO_BYTES` or `createScriptInputCache({reachBudgetBytes})`; a set shared by the members of a component is charged once). An evicted set reloads *without* a durable store and without parsing: it is the union of the sets of the targets in the retained module graph (`graph`, `nodes`, `walkNodes`), so nothing had to be persisted; `trim()` runs only at the start of a closure walk, never while a walk is building (a walk reads the sets it has just stored). Module nodes themselves are not evicted: evicting one forces every node that reaches it out too (its reach sets contain it), which cascades through the hubs.
- Differential test (`🕸️module-graph/🧪️tests`): 120 generated modules, 40 closures asked twice with a new pass in between, through `deriveClosureFactV1` with an unbounded memo and with a 1-byte budget (evictions > 0): the facts and the support rows are identical.
- Real index, 6,707 closures, post-chunk heap (MB, sampled at the first verification of the next chunk, after the parts are forgotten; no view; the host was loaded by live runs, so seconds are comparable only between rows of this table):

| reach budget | seconds | peak RSS | peak heap | post-chunk heap |
|---|---|---|---|---|
| unbounded | 1,180 | 2.51 GB | 1.10 GB | 222 rising to 779 (old sampling) |
| 256 MiB | 1,165 | 2.76 GB | 1.04 GB | identical to unbounded (budget not reached) |
| 128 MiB (default) | about 1,140 | 2.75 GB | 0.91 GB | 193, 220, 286, 339, 390, then 414 to 546, still rising |
| 64 MiB | 4,119 | 1.96 GB | 0.87 GB | 193 ... 390, then flat 345 to 347 from chunk 11 on |

- Targets: flat within 50 MB after warm-up: met only at 64 MiB; peak RSS under 1.5 GB: not met at any budget (1.96 GB at 64 MiB); time within 1.3 times: met at 128 and 256 MiB, not at 64 MiB (3.5 times: every closure rebuilds its sets by union). No budget meets all three, so the default stays at 128 MiB (the one that costs no time and lowers the peak heap by 0.2 GB); 64 MiB is the flat, slow setting.
- What remains: the work per closure of rebuilding a union is what makes 64 MiB slow; a cheaper rebuild (union of the already stored sets of the direct targets only, the Tarjan and `build` passes skipped when the graph records are retained) or persisting the sets across settles (keyed by the stamp and digest of the module nodes they were built from) would let a small budget run at full speed. The peak (1.96 GB at 64 MiB, 2.7 GB at 128 MiB) is made of the transient walk of one large closure (heap spikes of +0.3 to +0.5 GB in one chunk, freed in the next), so the next lever is that walk, not the memo.
- Suites after this pass: 992 pass, 100 fail; the failing set is the pre-existing one plus `✂️derived-walks`, which fails only under the host load (5 s default timeout) and passes alone (4/4).

## 10. Fifth pass: bitset reach sets (the LRU memo is gone)

- Representation (`🧭️script-inputs/🧠️reach-memo`, schema + policy `guardBytes` 256 MiB, EN/DE): a reach set is a dense bitset of 32 bit words over the module numbers, one buffer shared by every module of a strongly connected component (the walk's Tarjan pass already condenses the graph) and by every component with an equal set (hash-consing, FNV over the words and a word comparison); the union of the target sets is a word-wise OR in the order the Tarjan pass completes components (reverse topological, linear); members iterate in ascending order by bit scan. The LRU memo, `trim`, the budget override and the context option are removed; the byte bound is only a guard that throws `BUILD_REACH_SETS_GUARD`. A set of 22 thousand modules costs at most 2,752 bytes (tested). Roaring containers were not needed: measured on the real index at chunk 8 of 27 (2,300 closures), 14,944 distinct sets together weigh 8.5 MB (5.2 MB at chunk 2), so at 22 k modules the total is a few tens of MB, under the 64 MB aim; sets are dropped from the store (`retain`) whenever a pass invalidates module nodes.
- Tests: `🧠️reach-memo/🧪️tests` (members, union and membership equal Python sets on random cases, also over 22,000 numbers; equal sets are one buffer; the 2.75 KB bound; the guard) and `🕸️module-graph` (the bitset walk equals the independent Python reachability for 30 closures over a generated 140-module graph with cycles, asked in two passes of one cache). The old unbounded-vs-tiny-budget test is replaced by this oracle test.
- Real index, 6,707 closures (host load average about 12 from other lanes): 1,099 s against 1,180 s for the unbounded sorted arrays (time at most 1.0 times: met, within noise), peak RSS 2.87 GB (2.51 to 2.76 GB before), peak heap 0.99 GB, post-chunk heap 241, 217, 219, 286, 245, 325, 342, 394, 350, 364, 420, 454, 422, 466 ... 523, 577, 531, 548, 551, 564 MB: NOT flat and the peak RSS target (1.5 GB) is NOT met.
- What this shows: the reach sets were not what makes the post-chunk heap rise (they are now 5 to 10 MB and the trajectory is unchanged against the 128 MiB LRU run). The 64 MiB LRU run was flat (345 MB) only because its constant eviction made everything slow (3.5 times) while it also emptied the reach map entries with their long module key strings (one `resourceKey + key` string of about 300 characters per module and per memo lookup); the remaining growth is the module nodes of the walk memo (graph records, `walkNodes` entries, `files` entries and their key strings, 22 k modules at roughly 15 to 25 KB each), which none of the changes of this lane touch. Next candidate: intern the module key once per module (a number) so `graph`, `reverse`, `reaches`, `walkNodes` and `files` stop holding 5 copies of a 300 character JSON key each, and drop the per-lookup `memoKey` concatenation.
- Persisting the sets across settles: not done. The sets are numbered by the process local module counter, so a persisted set would have to be stored as component member keys and edges of the module graph (the walk records with their observed rows), a second durable store in `script-inputs` that the settler's store does not reach; and a clean second settle is already served by the durable closure entries (`kept`), which this harness cannot show (no graph writer scope, so no store). Not measured: the clean second settle time.
- Transient walk of the large closure: re-read. The +0.3 to +0.5 GB steps seen in the earlier pre-forget samples are the per-chunk parts and `metas` (338 k path strings built by `buildMeta` for the parts of one chunk, gone in the next chunk), not a transient allocation of the walk; streaming `metas` (keeping only size, outside rows and the touched verdict per part) is the change that would remove them, not done.
- Suites touched by this pass (one file at a time): script-inputs 4, module-graph 5, reach-memo 2, walk-views 4, heavy-questions 3, durable-entries 3, late-closures 4, derived-walks 4, cutoff 156, all without failures.

## 11. Sixth pass: module keys as numbers, streamed part summaries

- Module keys (`🧭️script-inputs/🟨️.mjs`): `walkKeyV1` and the `files` memo key now return the number of the key text in a per-cache string table (`createStringTableV1` of the row store module, `cache.moduleKeys`), the text is stored once; `walkNodes`, `files`, `reachState.graph/reverse/reaches` and the graph record targets key on numbers; the reach memo key is `slot * 2^22 + module number` (slot per resource set), so the per-lookup `resourceKey + "\u0001" + key` concatenation and four of the five copies of the 300 character JSON key are gone.
- Streamed part summaries (`🧩️closure-kinds/🟨️.mjs`): `buildMeta` builds the full path summary of one part, puts it into the node store and keeps in memory only `{size, outside, touched}` (the verdict against the dirty summary of the running settle, computed while the strings exist); the path, directory and bare arrays of one part are garbage before the next part, so the 338 k path strings of a chunk never exist together; parts loaded from the store go through the same slimming.
- Real index, 6,707 closures (host load average about 11): 1,101 s against 1,099 s before this pass (time 1.0 times, met); peak RSS 1.95 GB (2.87 GB before), peak heap 1.00 GB; post-chunk heap 181, 203, 204, 269, 227, 330, 276, 329, 282, 296, 352, 357, 319, 380, 338, 342, 401, 359, 364, 370, 423, 431, 436, 398, 401, 406 MB (was 241 to 564 and rising): after chunk 21 it is flat within 40 MB, over the whole run it still grows about 10 MB per chunk until the module set saturates, so "flat within 50 MB after warm-up" holds only from chunk 21 of 27. Peak RSS under 1.5 GB: NOT met (1.95 GB).
- Remaining peak: the transient walk of single large closures (peak heap 1.0 GB against a steady 0.2 to 0.4 GB) plus allocator retention (RSS minus heap about 1 GB); not attributable further here.
- Clean second settle: not measured. `🧰️scripts/owners-setup.sh` makes a private 10 GB copy, but its harness (`owners-harness.ts`) runs the whole `loadBuildInvocationGraphV1`, not the settle, on a source snapshot that predates these changes (it needs `owners-sync.sh` first) and every copied file has a new stamp, so the first run is cold by construction and the second would measure the whole load, not the durable closure entries.
- Suites: cutoff + derived-nodes 170, script-inputs 4, module-graph 5, reach-memo 2: all pass.

## 12. Seventh pass: the time regression (a harness effect, one real defect)

Bench: `🧰️scripts/rowstore-time-bench.ts` (a copy of the 30th-pass `integration-settle-edits.ts` that stops after the clean round; wall, process CPU, RSS per round; `CACHE_ROOT`, `SKIP_COLD`, `ONLY_COLD` for profiling), all 6,707 closures, cold then clean journal, same machine, load average 18 to 22 (the 30th pass: 11 to 14).

| code | cold wall s | cold cpu s | clean wall s | clean cpu s | RSS end of round |
|---|---|---|---|---|---|
| 30th pass table (load 11 to 14) | 173 | 199 | 8.2 | 9.3 | 2.9 / 3.7 GB |
| before this pass (parts forgotten and rebuilt every chunk) | 421 | 365 | 73 | 68.5 | 1.34 / 1.45 GB |
| after this pass | 275 | 200 | 54.7 | 39.3 | 1.29 / 1.52 GB |

- The 1,100 s of the memory harness was the harness, not the settler: its 100 ms sampler calls `heapStats()` (a walk of a 1 GB heap) and `process.memoryUsage()` and it runs a full GC per chunk. Its peaks stay valid, its seconds do not. The settler itself: cold CPU 200 s equals the 30th pass (199 s); the wall difference is the load.
- One real defect found by the bisect (`--cpu-prof` on 1,500 closures, then switching features): forgetting parts every chunk made every chunk re-persist (`store.put`) and rebuild the summary of the shared parts (hot modules) and reload them. Fixed in `🧩️closure-kinds`: a part is persisted and summarised once per settle (`persisted`), summaries stay for the settle (they are slim since the sixth pass), and only parts used by a single closure are forgotten between chunks (`uses`); the flatness test still passes. Effect: cold CPU 365 s to 200 s, clean CPU 68 s to 39 s.
- Not a cause (profile and switches): the heavy-question child process (8 questions, about 3 s each, not asked in the clean round), the string table, the reach sets, the forced GC (5 percent of the 1,500 closure profile).
- Clean round: 39 s CPU / 55 s wall against 8 s in the 30th pass. The 30th pass settled in memory; since the chunked durable settle (31st pass, 17 s) every clean round re-verifies the stored answers by loading 12 k part and summary records from the node store (`parse` 12 percent, `readFile` 10 percent, `writeSync` 10 percent of the profile). Under 1 s only happens through the `kept` markers of a published index (`markIndexed`), which this bench does not set; not reachable here. A next step with a measurable gain: persist the slim summary `{size, outside, volatile, config}` as its own small record and read only that when the dirty set is empty.
- Targets: cold at most 180 s wall at the same load: not demonstrable (275 s at load 18 to 22; CPU equal to the 30th pass, which measured 173 s at load 11 to 14); clean under 1 s: not met (55 s wall, markers not exercised); peak RSS at most 2 GB: met (1.95 GB peak with the sampler, 1.5 GB at the end of the rounds).
