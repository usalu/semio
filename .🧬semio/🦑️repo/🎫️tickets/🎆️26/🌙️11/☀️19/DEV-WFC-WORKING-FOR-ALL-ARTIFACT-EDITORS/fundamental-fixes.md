## Provenance prefetch pinned a previous build's uplifted `.d`, so the final recheck refused every rebuild of a changed component (rc=75)

- **Symptom:** after `0 failure(s)` and `1 component(s) staged`, the log showed `Another process edited …/semio_hub_wfc_component.d while it was read (its bytes changed)` for 5 attempts, then `Final recheck: not reached` in the report and `rc=75`. Nobody edited the file: its mtime was the end of the Cargo pass and it never changed afterwards.
- **Root cause:** `CargoProvenanceSessionV1.prefetch` (`🧰️framework/🔨️modules/🏃️process/📦️artifacts/🏗️native-build/🟦️.ts`) hashes a unit's outputs and its dep-info the moment Cargo announces the unit. Cargo uplifts a cdylib's `.wasm` and `.d` into the target directory in place and only after the announcement. In a warm lane the previous build's `.d` still exists at that moment, so `existsSync` passed and the stale bytes were pinned; Cargo then replaced the file, and the session's final recheck saw different bytes under the same path and reported another process's edit. A fresh lane or a fully fresh (unchanged) build never hit it, which is why only rebuilds of a changed component failed, and why the fast all-fresh run had passed the recheck. Rebuilds of ordinary rlibs are unaffected because their outputs are content-addressed in the build directory and never rewritten.
- **Fix:** the session records when it opened, and `prefetch` skips every output or dep-info last written before that (`writtenThisSession`). It is only an optimisation: the receipt write still observes those files after Cargo exits.
- **Test:** `…/🧾️receipt/🧪️tests/🟦️.ts` gains "prefetch never pins a previous build's output or dep-info that Cargo then replaces in place"; it fails without the fix and passes with it. The same file's "an observation that meets another process's edit…" test fails on a jittered backoff value (1983 ms against 250 ms), a churn-policy drift that is not touched by this change.

## Component driver deadlocked after a successful build: the model publication frame waited for an input owner only the driver's exit closed

- **Symptom:** after `0 failure(s)` and `Final recheck: passed`, `component.log` went silent while the process held all compiler-CPU leases and the exclusive cargo custody lease; the idle watchdog ended it after 10 minutes (rc=124) and `[component] … materialized` never printed.
- **Root cause:** the driver (`runNativeBuildDriverV1`, `🧩️component-pass/🟦️.ts`) starts the plan's Cargo input owner with `planContinuations.start` inside the compile body. The owner is retained on purpose: it stays open on a gate until `close()`. The component driver runs that body inside `withComponentModelPublicationV1` (`🔌️plugin/📦️model/🟦️.ts`), which holds a retained writer-operation frame (`withCompilerWorkspaceSharedWriteV1`). A retained frame cannot retire before every operation accepted beneath it has settled (`🪢️lifetime/🟦️.ts`, async-context inheritance), and the owner counts as such a child. The only `close()` was in the driver's `finally`, which runs after the publication frame has retired, so each waited for the other. A temporary drain trace printed the single unsettled child as the operation created at `📥️inputs/🟦️.ts:30`; the hang point sat after `model storage rechecked` and before the writer release.
- **Fix:** when the run has no result consumer and no retained compilations, the driver closes both input owners before it returns the continuation from the compile body (`if(!options.consume&&options.retainCompilationBytes===undefined){await inputContinuations.close();await planContinuations.close();}`). Nothing uses the held inputs after the body in that case; with a consumer the owners stay held until it has run, as before.
- **Test:** `…/🧩️component-pass/🎟️stage/🧪️tests/🟦️.ts` gains a source-shape test for that retirement (a behavioural test needs an issued Script invocation that bare bun cannot supply). The hang was reproduced and fixed on the real build only (run `wUsDJwb`: 941 units, 0 failures, `component-ok`, `[component] semio:wfc: built, described and materialized`).
- **Not part of this fix:** repeated `rc=75` runs were another agent's source edits landing during the 20-minute window (the final custody recheck correctly refuses a changed source), and one run failed on a peer's mistyped FEM manifest path and another on an undefined `lend_reason` call.

## Original manifest metadata receiving reported "ready" before it began (`staged original metadata is absent`)

- **Symptom:** every plugin action command (WFC bitmap/grid2d `Load Example`, `setActiveExample`) failed with `Value(InvalidValue "staged original metadata is absent")` at `🛂️manifest/🦀️.rs` `advance_manifest_step` (`context_ready` stage), the editor stayed blank (`original-turn.source-not-ready`) and later commands queued behind the failed command ("has not answered Load Example").
- **Root cause:** `OriginalManifestMetadata` (`🛂️manifest/metadata.rs`) encoded its state machine with bare phase numbers and used `11` twice: as the initial phase when the command carries a view state (`let phase=if bytes.is_some(){11}else{8}`; phase 11 builds the Pack parser) and as the terminal "ready" phase (`ready()` was `phase==11`, set at the end of phase 10). With a view state, `advance` saw `ready()` immediately, returned `true` without ever staging `meta`, and the caller then unwrapped `receiving.metadata.meta` (`None`). Commands without a view state started at phase 8 and were unaffected, which is why only actions with a view snapshot (all editor actions) broke. The `🛂️manifest/🦀️.rs` uncommitted change (+8/-2) was only `[DEBUG]` logging and not the cause.
- **Fix:** the terminal phase is now its own value `13` (`ready()` is `phase==13`, phase 10 ends with `self.phase=13`); `11` stays exclusively the parser-start phase. No other reader of metadata phases exists (the receiving's own `phase==10||11`/`13` in `🦀️.rs` belong to the separate command-receiving machine). The edit was made by a peer agent at 09:45; this entry records and verifies it. The served component built before it (run `wUsDJwb`, admitted 09:27) still contained the collision, so the plugin component was rebuilt.
- **Follow-up for hygiene:** the phases should be a named enum so two states cannot share a number; left out of this minimal fix.
- **Verification after the rebuild (run `wYliI07`, rc=0; prepare/activate/serve re-run for all five, ports 6041-6045 answer 200):** the `staged original metadata is absent` failure is gone, but bitmap `Load Example` (seq 7) still does not complete ("has not answered Load Example").
