# OS preview launcher diagnosis

The active matrix runner accepted the OS request but port 5602 failed its readiness check. The runner launches the existing OS showcase through `repo capacity run`, then `repo tools exec vite`, using the previous ticket’s `vite-round3-os.config.ts` in prototype mode. The launch produced no fresh Vite output.

`repo --version` reached the launcher banner and stalled before printing the runtime status. The version command calls `ProvisionRequest.Locate`, which probes the workspace tools partition before the host user cache on macOS. An independent read of the workspace Bun `.toolchain.json` timed out while the equivalent host user-cache receipt responded. Reads of the Vite entry point and package manifest through the root `node_modules` link timed out as well. File metadata lookups resolved the files and identified the tools and dependencies as separate mounted volumes.

The newer launcher at the repository's launcher install location could report its Bun runtime when given a private `SEMIO_MACHINE_STATE_DIRECTORY`. It rejected the relocated dependency namespace because the workspace's managed link still points to the original cache generation. Native Vite also stalled when it read its package manifest through that link.

The OS fixture resumed through the existing showcase config and source on native Vite. The recovery entry point uses an isolated npm install with direct dependencies selected from the repository lockfile and install scripts disabled. It redirects package resolution for that preview process, prebundles its CommonJS browser dependencies, and serves the original HTML entry and CSS. The in-app browser ran the same responsive OS stories. Application source, workspace package links and the mounted repository images were left in place. A read-only clone used to reproduce the mounted-read failure was detached. [Recovery entry point](os-verify-recovery.mjs) · [Isolated install input](os-verify-deps.json)
