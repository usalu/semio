## 1. `metrics.self.*` measures the collector, not the process
- `metrics.self.cpu` is now the process CPU time (`process.cpuUsage` delta, new source `cpuMicroseconds`) spent inside the collector's own `step` (every tick, slow step, ring write, publication look, open), as a percent of one core over the clock span since the last report (reported one step late, as before). `metrics.self.memory` is the bytes the collector retains (tier row buffers, accumulators, counter maps, derived from the ring layout: about 44 KB; an analytic figure, not an allocation trace, a per-tick heap probe would cost more than it tells).
- New catalogue metrics `process.ready.cpu` and `process.ready.rss` keep the whole readiness process (the old numbers). Catalogue is now 71 metrics; rings of every machine were recreated (layout digest), history before 04:1x CET is gone, by design (greenfield).
- Live, 10 min window, all 13 publishing origins: **collector CPU 0.12 - 0.31 % of one core (mean about 0.18 %, m05 Windows 0.02 %), retained 44 KB; readiness process 0.7 - 1.6 % CPU and 49 - 87 MB RSS**. The budget (< 0.5 % core) holds for the collector everywhere; the 30 MB RSS cannot be attributed to the collector from rings (the readiness process as a whole is 49-87 MB, M6 measured +10 MB peak for the collector inside it). Highest: g1-m15 0.31 % (heaviest-loaded machine).
- Tests: collector `self` unit test (0.25 % from 2500 us of 1 s, whole process separate), loop test (100 us per step in a 5 ms clock span = 2.000 % exactly, process far above, retained bytes bounded).

## 4. Origins that publish nothing
- **g1-server**: the build agent started the readiness child on every machine except the group server (`SEMIO_FLEET_ORIGIN === <group>-server` excluded it), so `runReady`, which M3 made start the collector and wait for abort on the server, never ran there. Fix: the exclusion is gone in `B/🌐️remote-execution/🛰️sidecar/👷️agent/🟦️.ts` (test pins it). Live: the agent restarted at 03:36Z (max deferral 1800 s), the ready child started (4 children instead of 3), and `origins/g1-server/metrics/` appeared. Second cause found live: a **test process held the machine-wide `collector.lock`** (see below), so the real service idled until it ended.
- **Test processes steal the writer lock**: `build-contract` test members (checkout inside the OS temp dir, origin `g1-m09`, temp store) call `runReady` and so `startFleetMetricsV1`, which took the lock of the real ring directory `~/Library/Caches/semio/host-capacity/metrics` for the minutes the test ran: the real service stepped idle (published nothing), the test's rings got into the local files. Fix: `startFleetMetricsV1` does nothing when the root (or `SEMIO_FLEET_ROOT`) lies inside the OS temp directory (`metricsScratchPathV1`, tested). Test members that were built from older code still steal the lock until they end; the real service takes the lock over the moment the holder dies (observed, pid 715 after pid 45794).
- **g1-m04 (Linux)**: its last file in the store is 21:27 Nov 25 (ready.json), the machine was offline or its replica stopped, so no code of this ticket ran there. By code reading the collector does not depend on the readiness stage (it starts first in `runReady`), on no POSIX-only source (`os.cpus`, `statfs`, `/proc` through the warden state, `loadavg`), and writes only 5 ring files, a lock and a baseline locally (about 12 MB, 7 inodes; last report 38724 free inodes) plus appends over NFS. If inodes ever ran out the collector now reports once (both languages) and retries every 30 s instead of failing every second. **Live now: g1-m04 publishes, 53 of 66 supported origin metrics fed** (the Linux platform set).
- g1-m09 is not provisioned (no origin files).

## 5. AppleDouble `._t*.ring` stubs
- **Finding**: the stub content is the `com.apple.provenance` attribute, which macOS attaches to every file a provenance-tracked process creates on the NFS store; the NFS client materialises it as a 4 KB `._<name>`. It is not caused by `copyFileSync` and cannot be avoided from user space: every status file written with temp + rename (`._ready.json`, `._attest.json`, ... about 10 per origin dir) gets one as well, and the stub is rewritten with each new file. Observed live: the stubs of the rings come back after a sweep (writing a ring in place seems to re-mark it as well), so they are an OS artefact to tolerate, not a state to reach.
- Done: the publisher now writes the first whole copy with plain chunked `open/write` (no copyfile, so no attribute of the source can travel), removes the stub of a file it copies whole, and sweeps every `._*` of its target directory every 10 min (`sweepMilliseconds`, schema). The store hygiene rule `🧹️origin-files` (`B/🕸️graph/…/🌐️owner-pool/🧹️origin-files`) now also retires, at once and whatever their age, every `._*` in the origin directory and its `metrics` directory (schema `appleDoublePattern`, `appleDoubleDirectories`; Python oracle and a fixture case; 5/0). Readers: `readSeriesV1`, the Rust reader and the dashboard open only `t<N>.ring` and list origin directories (dot names excluded); a test puts 4 KB stubs beside the rings and reads the same series.
- Not done, cannot be done from user space: preventing the stubs. They are bounded (one per file name, 4 KB each, 4-5 per origin `metrics` dir and about 10 beside the status files), the publisher (10 min) and the pool (1 h) retire them, the OS recreates them, readers ignore them. A real fix is outside this repo (mount option or an NFS export that stores attributes natively).

## 6. Found live: the group server's readiness child used 85 % of a core (fixed)
Enabling the ready child on the server exposed a Bun 1.4.2 defect: a process whose event loop holds only an awaited, never-resolving promise and unref'd timers spins (4.5 s CPU in 10 s in a 6-line scratch script, 0.01 s with one ref'd long timer). `runReady` of the group server (idle until abort, collector timer unref'd) did exactly that: g1-server's `process.ready.cpu` went from 1 % to 85-89 % for the 7 minutes the first child lived (read from its own ring, onset 04:48 CET). Fix: `runReady` holds a ref'd 1 h interval while it waits (`🚦️ready/🟦️.ts`), cleared at abort; a test spawns an idling server-mode `runReady` and asserts < 500 ms CPU in 4 s. Verified live: the restarted child used 0.07 s CPU in 20 s. Any other role that idles on a bare promise has the same problem; none found (the others hold ref'd timers or sockets).

## Not verified
- The overhead of the collector on Windows and Linux is read from the live rings only (m05 0.02 - 0.05 %, m04 0.27 %); no isolated measurement.
- `metrics.self.memory` is analytic (layout), not an allocation trace.
- Test members built from code older than this landing still take the machine-wide writer lock while they run (minutes), so the real service on this Mac (the server) has gaps in its rings during such runs; they stop once the members are rebuilt from the new code. A ring directory keyed by origin and store would remove the contention for good; I did not do it because it orphans the 12 MB of existing local rings on every machine.
- g1-m04 and g1-m05: only the published rings were read, not the machines themselves.
