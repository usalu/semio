# Lanes: duplicate, overcommitted and unremovable Cargo lane images

## Symptom
Host 228 GiB, free space fell from 42 GiB to 0 during `cargo test --workspace` of the bim model (`The disk is full: partition .cache/b/r/m/cargo has 0 B free`, `clang: unable to make temporary file`). Seven lane shards (`.cache/b/r/s/<lane>`, ledger `.cache/b/r/shards.jsonl`) held 8 to 17 GiB each, the declared capacities of all shards added up to 293 GiB on a 228 GiB volume.

## Root causes (three, found in the code)
1. **Copies of one lane.** `planPoolAcquireV1` takes only a *free* lane of the same crate set (`warm`). When the `*` lane (whole workspace) was held by a running test, the next whole-workspace command of the same agent started a second `*` lane (`ped16c6` and `p803402`, same session, agent and `crateKey`), which rebuilt all dependencies into a fresh 9 to 13 GiB directory. Nothing ever removed the idle copy.
2. **No admission of births or capacity.** `nativeImageShardCapacityV1` sized every lane image as `min(32 GiB, 66 % of the host free space at that moment)`: no bound on the sum of declared capacities, no free-space floor for the new lane's working set, and no retirement before a birth. The pool trim only looked at *recorded* bytes (`lane.size`, `null` for fresh lanes counts 0) against a quota derived from the machine total without the 60 % host share.
3. **No sharded lane could ever be removed (the reason the idle ones stayed).** `retainRemovedLaneV1` scans the lane base for target bindings before any removal. On a mounted lane image the base holds the root-only `.fseventsd` of macOS, so the scan threw `EACCES`, the custody was reported as `unresolved lane custody` and `removeLaneV1` refused every lane (`retentionConflict`). Trim, cache gc of lanes and my own retirement all stopped there. `removeLaneTreeV1` would also have failed on the same directory.

## Fix (schema first, all with tests)
- **Shard rule (framework, `💾️storage/🍎️image/🧩️shard`)**: `nativeImageShardWantBytesV1`, `nativeImageShardCommittedBytesV1`; `nativeImageShardCapacityV1`/`nativeImageShardSelectV1` take a commitment budget per root: a birth is shortened to the room the budget leaves and refused (`budget`) below the working set with headroom; `nativeImageShardBirthEventV1` rejects a birth that would exceed it; `ensureNativeImageShardV1` takes `budgetBytes`. Schema: new message `overcommitted` (en, de) and the `commitment` corpus section; oracle `🐍️.py` and corpus `🔣️.json` extended (6 cases). The public re-export `📦️packages/🟦️typescript/…/🧩️shard/🟦️.ts` lists the new members.
- **Machine budget with the 60 % host share (library)**: `compilerLaneStoreBytesV1` = compiler store quota of the machine total bounded by `machineHostCapV1` (60 % of the volume); `compilerLaneQuotaBytesV1` uses it (it did not apply the host share before). The same number is the commitment budget of the lane images (`commitmentBytes` of `acquirePooledLaneV1` / `acquireProductLaneV1`, wired in the compiler lane view and `withAgentLaneV1`). Ports (`LaneImagePortsV1`) carry `hostFreeFloorBytes` (`machineHostFloorV1`) and `budgetBytes`.
- **Same owner, crate set and flavour never coexist**: `planPoolAcquireV1` takes `owner`/`flavour`; a lane of the same owner, crate set and flavour held by a live process is waited for (`busy` naming the lane, message `poolSameCrates`), then reused warm. `planPoolDuplicatesV1` plus `planPoolTrimV1`/`trimPoolV1` shed idle copies first (keep: held, else requested, else newest), regardless of bounds and recency. Never a claimed, requested, held (restart hold) or product lane.
- **Admission and LRU retirement before a birth**: `planLaneAdmissionV1` (pure) and `admitNewLaneV1` run before `ensureLaneImageV1` of every new lane (pooled and product): while host free is below floor plus the working set of one lane, or the declared lane capacities leave less than a new image needs, the least recently used idle lane is removed under its claim, its image is retired whole and the host is measured again. A shortage that all idle lanes together cannot cover is not worked on (no pointless destruction; the birth is then refused and the lane stays in the home image). Message `poolAdmitted` (en, de).
- **Custody scan**: `layout.volumeMetadata` (schema, `.fseventsd`, `.Spotlight-V100`, `.Trashes`, `.TemporaryItems`, `.DocumentRevisions-V100`) is skipped at the root of a lane base by `discoverLaneEvidenceV1` and `removeLaneTreeV1`.
- **Not done (documented decision)**: narrow-crateKey lanes still compile their own dependency set. Reusing the dependency artifacts of the `*` lane needs a shared dependency target (Cargo cannot share `deps/` between differently keyed target dirs without the unit cache serving them), i.e. a design of its own: make the unit cache the only dependency store and let narrow lanes hold only incremental state of their focus crates (the unit cache already does this for units it can key; the 17 GiB of `pa7844a` are mostly dependencies it did not serve). Admission and retirement above bound the cost until then. Growth of an existing image is not planned either: images are sparse and bounded by the commitment and the existing gc.

## Reclaim
Method: framework API from the ticket script `lanes-retire.ts` (`removeIdleLaneV1` under the lane claim, then `retireIdleLaneImagesV1`), after `lsof +D` on the three mounts (no user) and `ps` (the only rustc is a remote-execution build in `.cache/b/d`, not a lane). The first attempt was refused with `unresolved lane custody` (root cause 3); after the fix `pfc4846` and `p803402` were removed and their images retired whole; `p2c1160` was retired in the first pass.

| | before | after |
|---|---|---|
| `df -h /Users/ueli` free | 45 GiB (78 % used; 25 GiB at the start of this task) | 46 to 48 GiB right after, then 37 to 59 GiB as other sessions and the model-test loop run |
| live shards | 12, declared capacity 293 GiB | 7, declared 169 GiB (lane root 83 GiB) |
| `.cache/b/r/s` host size | about 47 GiB | about 30 GiB (`ped16c6` 8.9, `pa7844a` 10, `q90be4b` 4.6, `w` 3.1, `cargo` 2.2, `sealed` 1.0, `pabcece` 0.3) |

- Retired: `pfc4846`, `p2c1160` (bim entities tests, agent 3efc810a), `p803402` (duplicate `*`; `ped16c6`, the newer one, was kept and is in use by the restarted model test). Also retired by the existing idle-image rule in the same pass: `pb777d4` (only a `born` row, no lane) and `d` (the reserved static default lane has no `lane.json`, so the rule counts it as lane-less; its detach succeeded, so nothing used it; regenerable cache).
- Left alone: `pa7844a` (own, 10 GiB, crates `semio-hub-stdio-bim`, idle but not in the list), `pabcece` and `q90be4b` (agent `default`, other session, used within the policy window).
- The next lane birth will find the lane root over its budget (83 GiB declared against about 68 GiB: 49.4 % of 60 % of 228 GiB) and retire the least recently used idle lanes first, as designed.
- Open: `retireIdleLaneImagesV1` treats the reserved lane `d` as gone on every acquisition (pre-existing); a guard for `UNIT_CACHE_POLICY_V1.pool.reserved` is a one-line follow-up that I did not make because it changes the default lane's lifecycle.

## Reserved lane guard
- `retireIdleLaneImagesV1` (`🧵️lane/🏊️pool/🧩️image/🟦️.ts`) skips every shard whose key is in `UNIT_CACHE_POLICY_V1.pool.reserved` (schema value `["d"]`, the static default lane of `.cargo/config.toml`). The reserved lane has no `lane.json`, so the idle-image rule counted it as lane-less and retired it on every acquisition. The guard reuses the existing schema constant, the same one the pool, trim and temporaries code already filter with.
- Test: `🧩️image/🧪️tests/🟦️.ts`, "the reserved default lane is never retired as idle, its image stays while an idle ordinary lane goes" (births `d` and `p000001`, retires only `p000001`, `d` stays in the ledger). `repo test-file` on that file: 7 pass, 0 fail.
- Open item above (`d` retired on every acquisition) is resolved by this guard.
