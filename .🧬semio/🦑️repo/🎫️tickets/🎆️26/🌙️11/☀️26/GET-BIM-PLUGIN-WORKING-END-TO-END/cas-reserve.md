# CAS hard reserve scaled to the volume (cache-host on a 228 GiB laptop)

## Root cause
- `casEffectiveCapBytesV1` = `min(proportional, max(minimumCapBytes, store + free - reserve))`. The cache-host reserve was `max(8 % of the volume, 72 GiB)` (`reserveFloorBytes` 77309411328). The 72 GiB came from a 926 GiB release-build host (70 GiB needed free plus 2 GiB). On 228 GiB it is 31.6 % of the volume: store 27.8 + free 37 = 64.8 < 72, so the term went negative and the cap clamped to the 1 GiB minimum. That refused writes above the cap, trimmed unit-cache objects, and kept units from surviving across runs.
- The fixed floor ignored the machine budget (`hostFreeFloorBytes` 15 GiB / `hostFreeFloorPercent` 6, `hostSharePercent` 60), which already scales with the volume.

## Should cache-host apply on a laptop?
- The role is not configured. The fleet cache server (`repo service host`, `remote-cache/🖥️server`) declares `cache-host` in `~/.cache/semio/cas/v1/r/cache-host.json` while it runs, renewed every `holderRenewMs`, and it truthfully serves blobs here. A laptop that serves a cache is a cache host, so removing the role would drop the server blob floor and the 70 % free-room claim that sizing needs.
- Decision: keep the role and make its sizing proportional. The reserve and caps are now volume-derived, so the role is harmless on a 228 GiB volume and unchanged on a 926 GiB one. `SEMIO_CAS_ROLE=builder` stays an explicit override.

## Fix (schema-first)
- Policy value `sizing.reserveFloorMaxPercent: 12` in the CAS policy JSON (`🗄️cas/🧬️schema/🔣️.json`), typed and validated (0 < x <= 50) in `🧬️schema/🟦️.ts`.
- `casReserveBytesV1` (`🌡️partition/🟦️.ts`) = `min(total/2, max(reservePercent of total, min(reserveFloorBytes, 12 % of total), machineHostFloorV1(total)))`. New exported `casReserveFloorBytesV1`.
  - 926 GiB cache-host: 74.08 GiB (unchanged). 600 GiB: 72 GiB. 256 GiB: 30.72 GiB. 228 GiB: 27.4 GiB (was 72). 100 GiB: 12 GiB (was 50).
  - Never below the machine budget's host free floor, so the CAS never plans to use what the machine budget keeps free. The floor itself scales (13.5 GiB on 228).
- Result on this host, live and read-only (`repo cache cas status`): cap in force 55 GiB (was 1 GiB), held cap 60 GiB, machine ceiling 136.75 GiB, reserve 27.39 GiB with 23 GiB above it. Writes are no longer refused at 1 GiB.
- Graceful over-cap: the planner already evicts least-recently-accessed unheld candidates down to the low watermark and judges held entries only against `heldCapBytes`; a new test pins that order. Collapse to the minimum now happens only when `store + free < reserve + 1 GiB`, where emptying the store could not restore the reserve. The "store never grows into the reserve" rule and the cap refusal after a bounded collection are deliberate, tested contracts (stores of a cache server only), and are unchanged.
