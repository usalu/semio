# Optimizer Work Directory Drain

Demonstrator `wmJDEkF` and Procedural `w1AN8vL` both reached the optimizer handoff error `ENOENT` when renaming the restored core into `optimized/`. Read-only inspection found the restored source core intact in both run directories, with 266,559,030 and 113,112,756 bytes respectively. The destination parent was absent. The fault was neither a missing compilation output nor a cache hit presenting an empty output.

Both logs already showed a separate compiler provenance refusal before the optimizer ended. The component's browser stage waits for both model and optimize. A fail-fast dependency promise rejected that stage on the blocked model branch while the optimize branch still owned its work. The resulting blocked completion woke discard, which removed the entire component work directory. The still-running optimizer's cache publication then restored its core into the recreated stage source directory. The following rename rejected because the sibling destination directory had already been removed.

The driver now waits for every prerequisite to settle before it resolves a stage's readiness or propagates a blocked completion. It remembers the first rejection as it arrives and still skips the dependent stage on failure. Existing cleanup stages drain their dependencies regardless of success. The downstream completion therefore represents the transitive work lifetime, so the existing finalizer can delete its workspace only after both branches are finished. The fix preserves the cache and Wasm checks, staging gates, actual optimizer arguments and the primary model or provenance error.

The isolated production-driver regression uses the real component optimizer and stage-cache restore around a small valid core. It holds cache restoration while the independent model branch fails, then verifies that the optimized core is installed and validated before discard removes the work. SQLite checks the neutral event order. Restoring the original fail-fast dependency check in the isolated test runtime reproduced the exact optimizer rename ENOENT alongside the original model refusal. The fixed production scheduler passed, installed the valid core before discard, and surfaced only the original model refusal. No release component or expensive optimizer was run by this verification.
