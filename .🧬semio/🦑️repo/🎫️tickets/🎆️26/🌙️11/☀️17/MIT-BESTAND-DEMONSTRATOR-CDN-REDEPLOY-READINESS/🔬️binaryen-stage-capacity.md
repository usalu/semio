# Binaryen Stage Capacity

The Energy `wKZ8QJX` report and stage timestamps show `optimize` taking 2,896.373 seconds (48 minutes 16 seconds), 10:36:16.784 through 11:24:33.157. It ran after transpile, with describe and the provenance observation already holding grants. The driver was granted three compiler jobserver slots out of twelve host cores. The initial available-slot admission gave one slot to the optimizer. The provenance stage settled 24.825 seconds after optimizer start and describe settled 597.600 seconds after it started. There were no running rustcs during all 1,403 optimizer timeline rows, and 1,112 rows showed only one held stage token. This is unused capacity inside the admitted driver. Aggregate host usage does not establish that all twelve cores were free.

The original scheduler took its available slots once. The optimize stage passed that count as `context.parallelism` to the shipped optimizer, which set `BINARYEN_CORES`. Binaryen v130 reads the variable when its process-local singleton pool is initialized and uses serial work at a width of one. Later jobserver releases could not change an already spawned optimizer. This was under-allotment, rather than a thread-count flag override or global oversubscription. [Pinned Binaryen thread pool](https://github.com/WebAssembly/binaryen/blob/version_130/src/support/threads.cpp)

The production optimizer now uses the parallel-start intent. Its jobserver opportunity prefers two issued slots for up to 30 seconds, about one percent of the observed stage. It acquires no partial allocation while waiting and respects ordinary queued work ahead of it. Driver-stage slot releases wake the opportunity. Cargo's direct FIFO or semaphore returns have no JavaScript release callback, so an unaccompanied external return can wait until the bounded fallback checks the channel. If the larger grant is still unavailable, it queues for a normal single slot and proceeds on the scheduler's existing rules. One-slot builders proceed immediately. After admission the stage can include other actual free slots, and the capacity callback must exactly match the held count. The optimizer's command, release flags, inputs, cache key and staging checks are unchanged. Separate paired roots can continue to stream on their other slots.

The deterministic three-slot regression holds two slots, observes that the optimizer is still waiting, lets an independent ordinary waiter take the free slot, releases one blocker and verifies the optimizer receives exactly two. It also covers cancellation and a timed one-slot fallback, with SQLite independently checking the held-slot counts. With the old immediate scheduler restored only for the isolated test, the optimizer starts early and the assertion fails. With the updated scheduler, the pinned Binaryen optimizer produced identical bytes at worker counts one and two using the real shipped arguments on a small neutral module. The module validated and returned its authored result. No full optimizer replay or module build was started; the full-module wall-time benefit remains unmeasured.
