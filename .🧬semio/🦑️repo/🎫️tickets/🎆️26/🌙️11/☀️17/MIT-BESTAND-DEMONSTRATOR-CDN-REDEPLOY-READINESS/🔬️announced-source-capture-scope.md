# Announced Compiler Source Capture Scope

At the observed driver revision, `runAdmittedPass` sets `sourceCapture` only for prototype, one planned pass and one package. All profiles still pass `sourceWitness` into Source admission and the provenance session when full compilation export is not requested. Thus the release-generation `cs` checks establish admission capture, not that release Cargo announcements retained an intermediate consumed version. No explicit explanation for the guard was found in code or ticket evidence.

The callback for an eligible non-fresh local path-package artifact is awaited inside `withIssuedResourceOperationV1(inputs.control, ...)`, within the still-live Cargo input continuation. The witness constructor requires the issued storage reservation and confines its directory to that backing. It checks advertised absolute artifact roots, reads adjacent dep-info, accepts only already-admitted workspace paths with exact BLAKE3 and extent, and retains bodies under SHA-256. Final receipt selection independently matches rustc's checksum, enforces one consumed version per path, and rereads selected bodies. Missing or changed dep-info and unavailable intermediate bytes are skipped; they do not authorize publication. A missing retained body must match current bytes at seal or fail.

Bounds include 16,384 unique files, 262,144 associations, and min(storage allocation, 1.5 GiB) retained bytes. Physical provenance control has a 16 GiB base maximum and 4,194,304 work units, scaled by component count. ENOSPC and exhausted retention bounds skip optional capture, rather than weaken the seal. Path association is based on the admitted roster, not every arbitrary compiler dependency.

The source-witness fixture exercises matching intermediate bytes, different length or equal-length different bytes, unadmitted source and missing dep-info, including concurrent announcements. Component-pass tests separately check mixed consumed versions in both orders and modified retained blobs. Its real-driver `provenanceSeal` after-announcement scenario is declared with a **release single** and expects the retained intermediate body to permit the receipt, which appears inconsistent with the current prototype-only guard. No tests were run for this audit. Extending the guard for pairs or multiple passes also needs integration coverage for shared paths, distinct component closures, failed/retried attempts, cancellation and bounds; early observation must not incorrectly select a failed attempt's consumed versions. The guard's removal alone is not a demonstrated speed or safety result.
