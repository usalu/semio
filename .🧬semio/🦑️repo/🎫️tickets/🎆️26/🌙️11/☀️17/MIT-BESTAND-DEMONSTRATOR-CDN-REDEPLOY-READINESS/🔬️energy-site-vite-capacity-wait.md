# Intermediate Energy site compiler-capacity wait

The running site process PID 59906 entered `withViteCompilerCapacityV1` and was still waiting after about 17 minutes. The repository lease status at inspection showed its shared `semio.compiler.host-capacity/v1` gate held, but no exclusive compiler CPU slots. Process build PID 38896 held slots 4–7; Demonstrator PID 56259 held 0–3 and 8–9. Both were live. Thus two of twelve slots were free, not all slots reserved.

Vite calls `countedCompilerCapacityRequestV1()` with the host's actual core count. Its authored 50% share and 50% minimum select a maximum of six and a minimum of three slots on this 12-core machine. Its picker takes any available slots for one nonblocking attempt, releases them if fewer than three are available, and waits before retrying. Two free slots therefore cannot satisfy it until a holder releases another. The registry reports no wait-for cycle, and this snapshot does not establish unfairness or a lost lease. The current Vite path has no existing setting that lowers this minimum: it sets `SEMIO_COMPILER_PARALLELISM` and `GOMAXPROCS` only after the grant. The different Bun-bundle class is not a Vite override.

The outer host grant PID 59899 reserves 3,000 MB; host status observed approximately 130–134 MB for its tree and did not mark it lent. The compiler capacity implementation publishes admission-wait edges, but the inspected Vite path does not bind the host wait-marker listener used by Cargo. This indicates a potential future custody improvement, not a proven safe change for this live run: whole-tree idleness and resume/re-admission must be preserved. Host status also showed no waiting machine-wide grants at this inspection, so a current memory queue benefit was not established. No process, policy, reservation or running file was changed; let Vite proceed through the existing gate.
