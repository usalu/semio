# Darwin Disk Arbitration Remount

A standalone C probe used Apple’s public Disk Arbitration API and normal, non-forced volume operations on a ticket-owned 96 MiB APFS image. \`DADiskUnmount\` returned success in 0.295 s. The same APFS BSD device, \`disk25s1\`, remained attached to the same image throughout the unmounted interval. \`DADiskMountWithArguments\` returned success in 0.046 s and mounted the same device at the same path with ownership enabled and browsing disabled. The host backing device, inode, and logical size stayed stable. A SHA-256 readback of untouched data matched. The scratch image was detached normally after the experiment. [Apple Disk Arbitration operations](https://developer.apple.com/library/archive/documentation/DriversKernelHardware/Conceptual/DiskArbitrationProgGuide/ManipulatingDisks/ManipulatingDisks.html)

The first scratch attachment used the legacy \`hdiutil\` stack as a control because a canonical \`diskutil image attach\` had already failed on a separate owned test. Host allocation stayed at 100,663,296 bytes across deleting 32 MiB of scratch data and remounting. A second test used the documented canonical \`diskutil image attach --noMount\` on the same detached scratch backing to isolate attachment from mounting. It hit the 18-second bound and exited through owned cancellation. The native image inventory showed no attached scratch device afterward. This check places the stall before a successful new attachment, independent of APFS mount options.

A read-only IOKit sample identified the existing Rust backing as an \`AppleDiskImageDevice\` on the AppleDiskImages2 controller and confirmed \`IOStorageFeatures.Unmap=Yes\` on that exact backing. This supports testing whether a volume-only remount can retain a trim-capable device. A physical block return on a DiskImages2-backed scratch image remains unverified while the canonical tool cannot attach it. The live Rust and products volumes stayed mounted throughout this experiment. Proof for the proposed reclaim requires the same BSD identity, stable backing, data readback, and a measured backing allocation decrease on a DiskImages2 scratch image before considering the live maintenance path.

The raw evidence is in \`🗑️generated/darwin-disk-arbitration-legacy.log\`, \`🗑️generated/darwin-disk-arbitration-canonical-no-mount.log\`, and \`🗑️generated/darwin-disk-arbitration-iokit.log\`.

The macOS 27 SDK additionally exposes DiskImageKit for creating and opening raw or ASIF images, layering, inspecting and truncating them. Its published DiskImage interface contains no volume mount or trim command. Apple describes APFS trim as asynchronous after deletion or free-space reclamation. These APIs do not establish an online trim actuator for an already-mounted Rust volume. [DiskImageKit](https://developer.apple.com/documentation/diskimagekit) and [Apple File System FAQ](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html).


## Guarded synchronous volume-only cycle

Apple’s released Disk Arbitration daemon clears callbacks when a client session ends and keeps queued requests. A timeout cannot certify that a late daemon unmount was cancelled. The ticket-only boundary helper therefore uses the synchronous \`unmount(path, 0)\` syscall and mounts the same existing APFS BSD device with \`/sbin/mount_apfs -o owners,nobrowse\`. On a second scratch control the direct operations took 0.379 s and 0.034 s, kept the same BSD device and FSID, and preserved owners, nobrowse, backing identity, and SHA-256 readback. [Apple Disk Arbitration session cleanup](https://github.com/apple-oss-distributions/DiskArbitration/blob/main/diskarbitrationd/DAQueue.c#L755-L824)

The guarded scratch replay acquired the same repository lease primitive and directory as the production image owner. A genuine shared reader refused the zero-wait exclusive request. After acquisition, an independently opened raw mount handle refused the operation before unmount. With both released, the full sequence verified the original file and mount. A second guarded run observed the actual unmounted interval and sent the worker SIGTERM. It restored the original mount and exact SHA-256 before returning cancellation. The worker places synchronous commands in separate process groups, applies command deadlines, and joins each operation before reading mount state. An unresolved kernel operation cannot safely release ownership until the worker returns. The scratch backing was detached after both tests.

The ticket-only entry \`repo tools exec bun -- <ticket>/🗑️generated/darwin-da/volume-boundary.mjs live-check\` tries the actual Rust exclusive lease and performs no mount mutation. The authorized \`rust OBSERVED_RESERVATION_BYTES [SECOND_OBSERVED_RESERVATION_BYTES]\` mode also requires positive live storage pressure against the normal floor, exact attached APFS/open-backing identity, physical UNMAP capability, a sole genuine exclusive holder, an empty compiler headroom ledger, and no raw mount handles immediately before unmount. It rechecks the same BSD device, filesystem, mount flags, original backing identity, Cargo directories, and hashes of the current compiler receipt and headroom history after restoring the mount. The read-only production Rust witness is APFS \`disk9s1\`, with owners and nobrowse on, and the two data witnesses are 130 and 7,860 bytes. The actual Rust operation still requires a genuinely coordinated idle interval.

The normal guarded run is in \`🗑️generated/darwin-volume-boundary-guard.log\`. The cancellation run is in \`🗑️generated/darwin-volume-boundary-cancel.log\`. Direct mount evidence is in \`🗑️generated/darwin-disk-arbitration-posix-identity.log\`. Those scratch tests exercised the legacy attachment, so physical reclaim from a retained DiskImages2 attachment remains unverified. A completed remount and a measured positive allocation delta are independent observations.
