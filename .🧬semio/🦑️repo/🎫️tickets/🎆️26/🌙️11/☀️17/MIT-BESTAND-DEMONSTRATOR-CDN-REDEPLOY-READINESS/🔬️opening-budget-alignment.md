# Opening Budget Alignment

The current shared continueOpeningTurns admits at most 1,024 empty more-work lifecycle polls after the initial open crossing, and errors on a further quiet result. Each host crossing first invokes guest poll once; the worker can then invoke up to 511 additional empty polls before the hard 512-step stop, subject to the original source deadline and remaining fuel, pending host input, actor lifetime, visible output and macrotask yield. One host crossing therefore has variable guest work. In energy-new-host-baseline.log, successive host replies r4 through r14 report epochs 1,035, 2,059, … 11,275: 1,024 epoch increments per crossing in that run. Epochs are not host crossings or necessarily one native job step. The fixture's 100 ms / 13 ms = seven turns is a historical measured expectation, not the runtime step cap; the default shard request budget is 100 ms and 50 million fuel, while the worker checks the source's own deadline and fuel.

Playwright waits 120 seconds for shell ready/error/not-found within a 240-second test. The old diagnostic Energy guest hit the host limit at 50.6 seconds (English) and 53.7 seconds (German), so that run was stopped by crossing count before the shell timeout. Its recorded repeated Store/Window states identify a real guest stall, not a healthy opening needing more budget; later source changes address those states but are not evidence that a rebuilt guest finishes within the host cap. Its native full fixture now completes app construction with physical accounting, but uses a different host and grant and does not report a corresponding browser crossing count or elapsed time. The separate native teardown previously stalled and has had subsequent fixes; it is not an opening time measurement.

Fresh staged Generator reached setContributions and failed a maintenance receipt invariant at epoch 9,931 in about seven seconds in each language; it was already past capture and did not hit either opening cap or Playwright timeout. Its staged units predate the later receipt fixes. An older Generator run timed out at 120 seconds after a command-size refusal and pending action; that is not a valid healthy opening duration.

No completed, current, browser-matched Energy/Generator opening measurement establishes numerical alignment between 1,024 host polls and the 120-second readiness window. Count, wall and fuel can each be limiting, and the native construction fixture alone cannot translate among them. On the next source-matched build, record first open and capture timestamps, host crossing count, per-crossing drivePolls/stop reason and remaining deadline/fuel, plus phase-specific progress; then compare successful and stuck paths. Retain current limits, cancellation and receipt behavior until evidence supports a change. No builds or tests were run for this audit.
