# Failed Pass Reclaim And Source Recheck

Process `wO0D1Ac` first emitted the real BREP analysis E0599. Its driver then reported reclaiming 2,106 files, 4,738 MiB, and after reporting the failed pass attempted a new source snapshot. The subsequent recheck repeatedly named `pceb75f/release/build/zmij/346ec9890494e44d/out/build_script_build` as vanished, four bounded observations followed by outer command retry. It is a compiler output path in the pass's own announced lane, not the BREP source that actually changed.

In `component-pass/🟦️.ts`, `runPass` marks the pass finished and schedules `reclaimPass` after provenance observation. `reclaimPass` removes announced outputs no remaining pass needs, subject to `session.canReclaimOutput`. After pending work, `failedPassConcurrentEditV1` receives `recheck: () => custody.recheck()`. Shared custody's recheck traverses its file claims including observed compiler outputs, so a legitimately reclaimed output can be translated into a spurious concurrent input edit. This path is separate from the real producer checksum drift documented in `🔬️process-brep-retry.md`.

The ticket-only `test-failed-reclaim-source.ts` uses actual shared physical custody and actual failure classifier: it observes a source and output, deletes the output as the reclaim would, and reproduces the vanished-output false edit. It also demonstrates that a source-only `CurrentPhysicalFilesV1.subset` recheck ignores the removed output while still detecting a changed source. That bounded test passed; it is not a complete production fix or proof of all source classifications.

A safe production design must recheck the exact retained input-role custody, including source, manifests, generated build-script/compiler-resource inputs, absent paths and directory rosters, and retain a path whenever it is both an input and an output. Exclude only output-only claims whose authorized removal actually settled, not every path under the build directory and not just the first error. Preserve genuine source drift detection and success provenance seals. Deferring the failing pass's reclamation alone can repair this singleton sequence but does not address a prior completed pass's already reclaimed outputs in a multi-pass build, and can defeat the storage guard. Existing completed-output relocation logic can help where it has verified transfers and nonoverlapping original claims, but the non-retention and failed-pass cases need their own exact ownership proof; substituting `recheckCompletedFiles` blindly is not proven safe. Add real driver regressions for failed single and multi-pass reclaim, output/input overlap, deleted/changed source, generated and directory input, and successful sealing before accepting the change. No production inputs or active processes were changed.
