# Bind the archive to the static acceptance run

A release inventory of the intermediate site took 3.6 seconds on this Mac for 3,494 files and 2,890,805,657 bytes. The local URL scan also passed. The previous packager invoked a byte counter, whitespace trimmer and digest utility independently per file. It produced a self-consistent archive but could package a later site revision if the shared output changed after the browser tests.

The full queue-verified static run now inventories its exact site before and after the browser suite. Only identical manifests and successful checks produce `🗑️generated/static-accepted.sha256`. Each new final attempt clears its previous acceptance marker. Package the accepted site with `package-site.sh <site> <durable-output> <ticket>/🗑️generated/static-accepted.sha256`. The output is verified against the accepted manifest while reading the compressed archive. The native fallback is selected with `PACKAGE_PYTHON` when the repository Python launcher is unavailable.

The inventory streams each file in one process, sorts normalized relative names and uses the existing GNU-style SHA-256 format. The portable manifest fixture agrees byte for byte with the system hash utility, rejects an overlength path and preserves the previous manifest on failure. The archive fixture rejects a self-consistent but different revision. A synthetic end-to-end package passed, then refused the same site after one HTML edit. The fixtures and intermediate inventory are packaging checks. The current static acceptance result remains 2/16.

The final static verifier now reads Playwright’s JSON results and checks for one actual final pass per pane in English and German. It also checks the origin request log for development bridge traffic. Real Playwright fixtures demonstrated that a skipped German Statik case and an expected failing case each produce process status zero. Both were refused by the release verifier, and an actual sixteen-pass fixture was accepted. Removing a pane, duplicating one or injecting a URL-encoded agent-bridge request was also refused. The existing browser assertions and accepted-manifest comparison continue to run. These controlled fixture results do not count as application boots.

The deployed module check now compares every file named by each staged component marker. An extension fixture with the correct receipt and core but a modified bridge reproduced a false pass in the previous check. JavaScript distributed beneath the extension route receives the normal vendor import relocation from the production asset copier. The verifier applies that same pure transformation to each staged extension script and compares the resulting bytes. The regression fixture now rejects the altered bridge, altered core and stale receipt. All 32 module directories in the current static build match the inventories and distributed contents of their respective staged directories. This confirms copy integrity. Successful rebuild receipts and pane boots are verified separately.

The path limit is checked in UTF-16 code units. A synthetic name containing non-BMP characters reproduced the previous undercount and agrees with the JavaScript string-length oracle after the correction. The current static tree contains 3,494 files and its longest absolute path measures 203 UTF-16 code units.

Packaging used to overwrite SHA256SUMS inside the captured Vite product, including when the accepted digest comparison failed. A synthetic site retaining an earlier manifest reproduced this mutation. The packager now builds the manifest inside a private ticket directory and adds those bytes under SHA256SUMS in the archive. A real system tar round trip independently verified with Python preserves every original input exactly and rejects a mismatched acceptance manifest without publishing a second archive.

A concurrent site build truncated the last capture log as soon as its capacity request entered the queue. Linked browser diagnostics use that log to locate the captured site. Each site invocation now streams to a private log and atomically publishes the capture after receipt settlement and capture validation. Final verification reads its own invocation log. The concurrent two-success, one-failure test preserved the previous capture while builds waited, retained it after the failure, and kept both successful invocations independently readable.
