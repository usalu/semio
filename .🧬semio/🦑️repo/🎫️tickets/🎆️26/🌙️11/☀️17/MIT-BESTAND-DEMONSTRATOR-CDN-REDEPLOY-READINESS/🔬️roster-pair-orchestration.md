# Roster Pair Orchestration

`roster-pairs.py` is a ticket-only supervisor around the existing `native-queue.sh`; it does not replace the queue, its stage acceptance, receipt recording, fallback or release identity checks. It reads the actual runtime case roster and treats a module as confirmed only when its recorded receipt matches the staged release receipt using the existing `release-receipts.py` parser. A run started by this supervisor or adopted predecessor is accepted only after its confirmation file changes and passes that comparison. The persisted state under `🗑️generated/roster-pairs-state.json` records active roots, failures and whether one new Demonstrator has succeeded. Failures are retried on a later invocation, not in an endless loop in the same invocation.

The scheduler counts adopted running roots as slots, validates live predecessor command identity, and refuses more than two roots. It prioritizes a new Demonstrator, GIS, then CAD; CAD waits for an active Procedural predecessor. Other singles may use one free slot. The five prevalidated pairs (text/math first, Flow/Playbook, metal/wood, beams/slabs, and CAD building energy/structure) start only with both root slots free and invoke `JOBS=2 native-queue.sh --pairs`. Once urgent singles are accounted for, a complete pair has precedence over cold singles when both slots are free. When only one member needs work it is submitted singly. A state lock refuses simultaneous supervisors; if interrupted while a child lives, the saved PID and start identity permit a subsequent invocation to adopt it. An unexpected PID identity change is a hard refusal. Inspect a stale lock and all live queue processes before any restart after an unclean supervisor exit; there is an unavoidable small interval between spawning a queue child and persisting its PID.

Run only after the current outer supervisor loops have been prevented from dispatching successors, while leaving the active queue children running. `python3 test-roster-pairs.py` passed synthetic subprocess checks of adopted predecessors, two-root capacity, fresh Demonstrator priority even with an old confirmation, CAD ordering, all five pairs, pair-first preference, failed-root persistence and resume; it also checked real receipt parsing and mismatch rejection against fixture receipts. No live queue was launched, stopped or modified by this work.

The process interface now uses Windows PowerShell/CIM `Win32_Process` creation time and command line on native Windows; POSIX retains `ps`. A failed or malformed Windows query refuses to continue rather than treating the process as absent. Live and recovered adopted queue processes must match both creation identity and the expected shell/script/root command; a different command at a reused PID is rejected. The synthetic suite exercises Windows CIM results, missing-process and query-failure cases, quoted Windows paths, and reused-PID rejection for both initial adoption and state recovery; it also re-ran the POSIX subprocess scheduler checks. The Windows backend was mocked on macOS and has not been executed on a Windows host.

A subsequent retry audit reproduced a stale-receipt gap: on restart the old scheduler discarded its recorded failures and could accept an unchanged matching receipt without retrying. The corrected state carries `retry_due` across invocations and only clears a requested or previously failed root after a new matching confirmation. Synthetic checks cover a stale matching receipt, partial pair success followed by singleton retry, and missing predecessor failure and later retry.

For a coordinator started with the revised protocol, `python3 roster-pairs.py --retry MODULE` enqueues one exclusive, state-specific request after verifying its owner PID, creation identity, command and state. Requests for an active root wait until that root settles; the supervisor persists the requested retry before consuming the marker. Duplicates coalesce. A request racing a normally exiting coordinator remains on disk for the next invocation. The existing already-running coordinator predates this protocol and is intentionally refused by the request command; it must be restarted under the owner’s normal handoff before the feature can operate. The tests exercise active-predecessor deferral, duplicate and unknown requests, and reused coordinator identity. No live queue was touched.
