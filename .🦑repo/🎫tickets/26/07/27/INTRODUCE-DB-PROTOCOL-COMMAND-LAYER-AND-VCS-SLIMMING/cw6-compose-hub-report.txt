New architecture
----------------
`compose-hub` is now `HubState`-shaped like os-hub's target design, minus a separate `HubDirectory`
trait (compose-hub's identity/tenancy bookkeeping is small enough that a concrete file-backed store
was pragmatic for this wave — see "Deferred" below):

- **`store` module** (replaces `schema` + `persistence`): `open_database(data_dir)` →
  `db::Database::open_at(<data_dir>/db, profile)` (FsStorage, zero-touch; `COMPOSE_HUB_DB_PROFILE`
  env var selects Dev/Test/Prod). `ComposeDirectoryStore` — file-backed (`directory.json`, atomic
  write-temp-then-rename) session ownership/share-token/compaction-config bookkeeping; the compose-hub
  analog of the plan's `HubDirectory` split (identity/tenancy stays out of `db`). `HistoryStore` —
  compose's own bespoke kit-history/lookback/compaction feature, now writing one JSON file per
  session under `<data_dir>/history/` instead of Postgres `history.*` tables (kept because
  `db_query::Query` is `Get`/`GetMany` point-lookups only right now — no historical/range read, so
  compose-hub still needs its own snapshot+change-log store for `/kit/at/{lookback}`,
  `/kit/at-version/{n}`, and `/history/compact`). All the pure JSON-shape functions
  (`serialize_session_kit`, `apply_change_log_to_kit` + its array helpers, `session_kit_id`/`_name`/
  `_string`) are unchanged verbatim from the pre-CW6b code — every test exercising them still passes
  unmodified.
- **`actor` module**: `SessionActor` now holds a `db::DocumentHandle` (not `PgPool`) plus
  `Arc<HistoryStore>`/`Arc<ComposeDirectoryStore>`. `apply_domain_command` is a pure, synchronous
  function (`state: &mut SessionState` + `entries`/`changes` out-params) — the exact same match arms
  as before, with every `sqlx_core::query::query(...).execute(...).await?` line replaced by a
  `(path, value)` push per `db_document`'s generic path-value diff convention (see its module doc:
  diff/inverse payloads are a JSON object of `/`-segmented paths → new value or `null` tombstone).
  `handle_domain_command`: clones `self.state` into a trial copy, applies the command to the trial
  copy + collects entries, wraps them into ONE `protocol::OperationEnvelope` (`operation_id =
  "<client_id>:<request_id>"` — preserves the original's per-(client,request) idempotency key, not
  the client-supplied `command_id`), submits through `db::DocumentHandle::submit`. Dedupe: `db`
  itself caches the receipt for a resubmitted `operation_id` (returns the same frontier); comparing
  `frontier.head_seq` before/after tells a genuine commit from a replay (safe because this actor is
  the sole writer to its document — single-writer-per-session, unchanged). `domain_version` IS `db`'s
  `head_seq` now (no separate counter). Compose presence (cursor/look/selection) is ephemeral —
  broadcast-only, never submitted to `db` (matches `db_preview`'s "never durable" law and
  `protocol_wire`'s loss-tolerant Preview lane) — and a new `WireEvent` broadcast channel
  (`Commands`/`Preview`) feeds the WS layer real wire-v2 frames alongside the pre-existing JSON
  `SessionEvent` channel (kept — several existing tests construct `SessionEvent` directly).
- **`directory` module**: `SessionDirectory` now holds `Arc<db::Database>` + `Arc<HistoryStore>` +
  `Arc<ComposeDirectoryStore>`. `session_state_from_kit_json` rebuilds a typed `SessionState` from a
  reconstructed kit JSON — the single place both session creation and cold-activation funnel through.
  `get_or_activate` reads `db`'s frontier for the authoritative `domain_version`, reconstructs the kit
  JSON via `HistoryStore`, rehydrates typed state, then spawns the actor exactly as before (DashMap
  entry-based race avoidance unchanged).
- **`api` module**: same routes/handlers, bodies swapped from `sqlx` calls to
  `SessionDirectory`/`HistoryStore`/`ComposeDirectoryStore` calls. `open_session_handle` maps
  `db::DbError::NotFound` to a clean `SessionError::SessionNotFound` (404) instead of a generic 500.
- **`ws` module** — the actual "client sync moves to wire v2" surface: binary lane-tagged
  `protocol_wire::{ClientFrame, ServerFrame}` frames over the same WebSocket route
  (`/sessions/{id}/ws`), replacing the pre-CW6b ad hoc JSON (which, notably, never parsed anything a
  client sent — `recv_task` was a pure no-op). Server now sends a real `ServerFrame::Welcome` on
  connect (`bootstrap: Tail` — no snapshot bootstrap yet, matches CW5's own deferral) and streams
  `ServerFrame::Commands`/`ServerFrame::Preview` from the actor's `WireEvent` channel. Inbound:
  `Hello`/`FrontierAdvertise`/`CreditGrant` acknowledged (inert — no credit-flow/resume-token
  validation implemented), `Commands` submits straight through `db::DocumentHandle::submit` and
  replies with a real `ServerFrame::Ack`, `PreviewPublish`/`Presence` rebroadcast.
- **`admin` module**: same routes/JSON shapes/embedded dashboard HTML (byte-identical — spliced in
  verbatim since it only talks to the JSON endpoints below it), query functions rewritten against
  `SessionDirectory`/`ComposeDirectoryStore` (`load_admin_persons` is empty for now — presence being
  ephemeral/in-actor-only means an admin-wide listing would need to poll every live actor; deferred).
- **`main`**: opens `db::Database` + the two file-backed stores under `COMPOSE_HUB_DATA` (default
  `./.semio/compose-hub`) instead of connecting to `DATABASE_URL`/running SQL migrations.

Deferred (documented, not silently dropped — matches this campaign's own precedent, e.g. CW5's
"Deferred" section)
------------------------------------------------------------------------------------------------
- **compose/client/lib/rs (the compose client library)**: NOT changed. Investigated first — its own
  `WebsocketBackbone`/`login(hub_url)` surface is a genuine pre-existing stub ("status surfaces once
  transport is wired", `let _ = (ctx, ..., hub_url, self);`), not a working JSON client to convert.
  compose's real local-first machinery (`kit_backbone`, `worker`, the embedded `gql` GraphQL server)
  runs entirely in-process against `vcs::DocumentVcsStore`/`ChannelBackbone` and never talks to
  compose-hub over the network today. Wiring a real client actor to speak `protocol_wire` against the
  now-rebuilt hub is a substantial, separate undertaking (mirroring CW5's framework/sync rewrite, but
  for compose's own bespoke vcs plumbing rather than the shared backbone) — attempting it as a rushed
  addendum risked destabilizing a 22k-line, currently-passing file for a feature that has no existing
  runtime caller yet. Recommend a dedicated wave/ticket once a client actually needs to connect.
- **No real inverse operations**: every domain-command envelope submits with an empty
  `inverse.inverse_diff` (schema "generic", `{}`). compose-hub never had undo/redo before this wave
  either; a real per-command-kind inverse (needed for wire-v2 `ApplyOutcome::Rejected`/`Transformed`
  rollback semantics on the client side, once a client exists) is future work.
- **Wire-native `ClientFrame::Commands` bypass compose's typed pipeline**: the WS layer's inbound
  `Commands` frame submits its raw path-value envelopes straight through `db::DocumentHandle::submit`
  (this is literally what wire v2 is for) but does NOT update `SessionActor`'s typed `SessionState`/
  `EntityChange` history — only the HTTP `/commands/domain` route (typed `DomainCommand`) does that.
  Reconciling wire-native diffs back into the typed replica needs either (a) a real client that speaks
  compose's typed operations over the wire (see above) or (b) teaching the actor to interpret
  arbitrary incoming path-value diffs generically. Documented inline in `ws`'s `handle_client_frame`.
- **No swappable `ComposeHubDirectory` backend family**: `ComposeDirectoryStore` is a single
  file-backed implementation, not a trait with sqlite/postgres/neo4j impls like os-hub's
  `HubDirectory` family. The campaign contract only itemized os-hub's directory backends as in-scope
  crates (`os-hub-directory-{sqlite,postgres,neo4j}`); compose-hub's identity/tenancy surface (owner
  token, share tokens, compaction config) is small and low-write-volume enough that a JSON file was a
  reasonable zero-touch default for this wave. Flagging as a legitimate follow-up if compose-hub ever
  needs multi-node/HA identity storage.
- **Bootstrap::Snapshot never sent**: `ServerFrame::Welcome.bootstrap` is always `Tail` — matches
  CW5's own client-side deferral (`Bootstrap::Snapshot`/`SnapshotChunk`/`SnapshotDone` accepted-and-
  ignored on the client that exists). A real client is expected to fetch the initial snapshot via the
  existing REST `GET /sessions/{id}/snapshot` and then tail live commands over WS.
- **`policyDbServerOnlyBreaches` lint** (root script.ts, per the campaign contract's Part 3) has not
  been implemented yet anywhere in the tree (grepped root script.ts — no match) — presumably CW8
  scope. Whoever lands it should confirm `compose/server/hub` matches the contract's
  `"compose/…hub…"` allow-pattern.
- Did not touch root `Cargo.toml`/`.vscode/launch.json`/root `script.ts` (shared, single-agent-serial
  per the campaign's own rule) — compose-hub is its own detached Cargo workspace and was never listed
  in root `Cargo.toml`'s `members`, so no root workspace change was needed for this wave.
