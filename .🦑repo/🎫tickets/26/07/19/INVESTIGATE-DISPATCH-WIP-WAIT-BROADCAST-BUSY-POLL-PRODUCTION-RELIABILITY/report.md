# dispatch_wip_wait busy-poll — production reliability investigation

Scope: `compose/client/lib/rs/lib.rs`, `ParentStore::dispatch_wip_wait` (~lib.rs:14267-14295), `EventBus` (~lib.rs:13999-14038), `ParentStore::spawn`/`spawn_child` (~lib.rs:14161-14192, 14304-14314).

## Mechanism inventory

- **A — OS-thread starvation (test-only artifact).** `spawn_child` (14304-14314) spawns one dedicated OS thread per child actor on native (`std::thread::spawn` + `futures_lite::future::block_on`). `ParentStore::spawn()` mints exactly 2 threads ("wip", "auth") per instance (14171-14172). Each `cargo test` that calls `spawn()` adds 2 more OS threads; on a host already oversubscribed (load avg 15-21 / 10 cores, many parallel test binaries), the scheduler can starve a child thread long enough that its event arrives after the 30s deadline, or starve the polling task itself so it never gets to call `try_recv()` in time. This explains the observed ~30.1-30.4s (always-hits-ceiling) pattern well, but it's a property of test-harness thread oversubscription, not of production, where a long-lived process runs a small fixed number of these instances/threads under normal load.

- **B — broadcast overflow (real production risk).** `EventBus::new` (14007-14013) creates an `async-broadcast` channel, capacity 1024, with `tx.set_overflow(true)` — once full, the sender **silently drops the oldest buffered message** rather than blocking. This bus is shared, unfiltered, by every `dispatch_wip_wait` waiter (10 call sites) **and** every live GraphQL subscription a client has open when unfiltered (`bus.subscribe()` at 18231-18232, 18268-18269). In production, more concurrent users → more mutations + more open subscriptions all sharing this one 1024-slot ring. If a given waiter isn't polled promptly enough (executor contention, or literally being outcompeted by other busy-spinning waiters, see C) while >1024 unrelated events are broadcast, its own `CommandSucceeded`/`OperationFailed` can be dropped with no signal — it just spins uselessly to the 30s deadline. This scales with production traffic and gets worse at peak load, unlike A.

- **C — self-amplifying CPU burn (real production risk, worst finding).** The wait loop (14278-14294) is `try_recv()` + `yield_now()` — a hot spin, not a blocking wait. Every in-flight mutation burns full CPU for its entire wait, up to 30s. N concurrent mutations = N hot loops competing with the 2 worker threads that need to actually finish and emit. Feedback loop: more concurrent mutation traffic → more spinning → more contention → workers/other waiters run slower → more spinning. Especially dangerous under CPU-limited/CFS-throttled containers (common in k8s): the spin burns the CPU quota, worsening throttling, which alone can push completion times toward 30s under just moderate concurrent load — no test-harness weirdness required.

## Answers

**(1) Is this a production risk under real load?** Yes — B and C are real and scale with production traffic; A is a test-parallelism artifact and not expected to reproduce in a normal long-lived deployment (fixed 2 threads/instance).

**(2) Should the bus use blocking `recv().await` instead of busy-polling?** Yes, but it only fixes C, not B — message loss is a property of `set_overflow(true)`, independent of how the receiver polls. No cross-platform (wasm32 + native) timer primitive is currently imported (`Cargo.toml` has `instant` for reading time only — no `futures-timer`/`async-io`/`gloo-timers`), which is presumably why the Instant-deadline busy-poll was used instead of a proper race. A real fix needs: (a) a timer usable both under `wasm_bindgen_futures::spawn_local` and native `block_on` (e.g. `futures-timer`, which has a wasm32 backend) raced via `futures_lite::future::or(events.recv(), Delay::new(timeout))`; (b) narrowing the subscription from unfiltered `bus.subscribe()` to something scoped (the existing `subscribe_paths` filter mechanism, 14033-14037, or a new request_id-scoped variant) so a waiter isn't sifting through every unrelated event, shrinking overflow exposure too. Both are dependency/architecture decisions, not one-line changes.

**(3) Is 30s an appropriate worst-case timeout?** No. The critical path (channel send, one actor apply, emit_event) is normally sub-millisecond/low-millisecond, no network I/O. 30s far exceeds typical client/gateway timeout budgets and produces a bad UX (silent hang, then an ambiguous error). Worse — it's a correctness bug, not just a timing one: the `Command` is already sent to the child's inbox *before* the wait loop starts (14276), and timing out does **not** cancel it. No request_id dedup/idempotency exists anywhere in `apply_kit_operation` (checked — none found). So on timeout the command still applies in the background while the caller was told it failed; a client that reasonably retries a "failed" mutation can double-apply it (e.g. two `CreateFixedPiece`s for one user action). Recommend: shrink the timeout to ~3-5s; separately fix the race via idempotent apply (dedup by request_id) or true cancellation before returning a failure; consider a distinguishable "still processing" vs "failed" response so clients don't retry blindly.
